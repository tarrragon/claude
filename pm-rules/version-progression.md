# 版本推進決策規則

> **核心原則**：每個版本分成兩期。規劃期可以討論方向、修改規格、釐清疑慮；規劃結束時凍結 scope，進入執行期，之後只照版本的工作與規劃文件執行，不再改這個版本的規格與設計。執行期發現的問題一律交給後續的維護小版本，唯一的例外是讓本版跑不起來的問題（見〈兩期：規劃期與執行期〉）。

---

## 版本層級語義

| 層級 | 語義 | 核心問題 |
|------|------|---------|
| **Wave** | 執行批次 | 同一個目標，分幾批做？ |
| **Patch** | 獨立可交付 | 完成後能獨立發布嗎？ |
| **Minor** | 功能里程碑 | 用戶能感知到新功能嗎？ |
| **Major** | 架構里程碑 | 系統基本能力改變了嗎？ |

---

## Q1-Q4 語義判斷

> 本流程圖假設版本 scope 已開放。scope 凍結時不進入此流程，改依〈版本生命週期〉的凍結分流處理。

```
[Q1] 和當前版本主題相同? → 是 → 新增 Wave
                          → 否 ↓
[Q2] 完成後能獨立發布? → 是 → 推進 Patch
                        → 否 ↓
[Q3] 需當前版本完成後才能開始? → 是 → 等待後推進 Patch
                                → 否 → 可並行開發，推進 Patch
[Q4] Patch 系列達成功能里程碑? → 是 → 推進 Minor
```

---

## 快速判斷檢查清單

1. [ ] 版本在執行期（scope 已凍結）？ YES → 讓本版跑不起來？YES → **本版處理**（`--scope-blocker`）；NO → 依〈版本生命週期〉凍結分流（承諾未達成→patch+1／改善、技術債、新能力→下一個 minor 候選池／框架→canonical issue）STOP
2. [ ] （規劃期）是規劃討論中發現的問題？ YES → **寫進本版規劃**，規劃結束前定案 STOP
3. [ ] [Q1] 和當前版本主題相同？ YES → **新 Wave** STOP
4. [ ] [Q2] 完成後能獨立發布？ YES → **新 Patch** STOP
5. [ ] [Q4] 達成功能里程碑？ YES → **新 Minor**

## 強制規則

| 規則 | 說明 |
|------|------|
| 規劃結束即凍結 | 版本開工前的規劃期結束時，必須執行凍結程序（見〈版本生命週期〉「凍結程序」），版本才進入執行期。scope 開放只存在於規劃期，不能帶著開放的 scope 開工 |
| 規劃期的問題進本版規劃 | 規劃期發現的流程缺口、技術債務、規格疑慮，在規劃結束前寫進本版的工作與規劃文件；寫不進去的，排進後續版本並附討論記錄 |
| scope 凍結後依問題性質分流 | 承諾未達成（規格寫了但沒做到、資料錯誤、跑不起來）→ 下一個 patch（x.y.z+1）；改善、技術債、新能力 → 下一個 minor（x.y+1.0）的候選池；框架問題（根源在 `.claude/` 通用資產、抽象後仍可攜）→ canonical issue，不進本地版本判斷（見 `framework-issue` skill〈決策入口〉） |
| 版本推進需語義理由 | 必須通過 Q1-Q4 判斷（僅 scope 開放時適用） |
| 活躍版本由 todolist.yaml 決定 | `status: active` 為 Source of Truth |
| 版本邊界以 active 為準 | 版本邊界時（舊版剛完成/新版剛啟動），todolist.yaml active 版本即為「當前版本」，無需推斷 |

**Why**：舊制一律無條件收入 active 版本、免除版本判斷，未區分「版本現在還收不收票」這一軸，實測（0.1.0）造成 pending 池膨脹至遠超必要交付範圍的規模——衍生問題與框架問題無差別流入同一 active 版本，必要與非必要工作無法分辨。**Consequence**：不分流會使版本收尾遙遙無期，且框架問題原地滯留在無法收件的本地池中，不會被推向能實際處理它的 canonical issue。**Action**：建票前先查 `docs/todolist.yaml` 對應版本的 `scope` 欄位；`scope: frozen` 時依上表分流，不再無條件視為本版本工作。

## 兩期：規劃期與執行期

每個版本（major、minor、patch 都一樣）分成兩期。專案與框架本身都適用。

| 期 | 可以做 | 不做 | 結束條件 |
|----|-------|------|---------|
| 規劃期 | 檢討開發方向、修改規格與設計、釐清疑慮、決定本版範圍、建好本版全部的票並寫定每張票的 acceptance | — | 版本的工作與規劃文件定案，執行凍結程序（〈版本生命週期〉「凍結程序」） |
| 執行期 | 照規劃期已建的票派發、驗收、合併 | 修改本版規格、為規格設計開討論、因新發現開本版衍生票 | 本版的票全部完成，發版 |

**順序：先建齊票，再凍結**。凍結後本版只收帶 `--scope-blocker <理由>` 的根票（收件條件以〈版本生命週期〉的階段表為準），所以規劃文件定下的本版工作，要在凍結前建成票；凍結前已建的必要票，由凍結程序回溯標上 `scope_blocker`。凍結後在本版建根票，只限下表第一列。

**執行期發現問題時**：

| 問題 | 去向 |
|------|------|
| 讓本版跑不起來（三項驗收檢查的第一項「能不能跑」過不了：測試紅燈、建置失敗、資料損壞） | 本版處理，建票時帶 `--scope-blocker <理由>` |
| 其他一切：設計問題、技術債、規格缺口、品質審查的建議、新點子 | 記錄成票或 issue，排進後續的維護小版本（patch）或下一個 minor，依〈版本生命週期〉的凍結分流。不在本版開衍生票，也不回頭改本版規格 |

**規劃票與 ANA 落地的版本歸屬**：規劃票於凍結時結案，規劃波建的執行期票是本版根票，不掛在規劃票下；執行期 ANA 的落地依上表建在後續版本（讓本版跑不起來而帶 `--scope-blocker` 者除外，屬本版範圍），在目標版本以 `--source-ticket <ANA-ID>` 建根票。關係選擇與 ANA complete 時點見 `.claude/pm-rules/ticket-lifecycle.md`〈ANA Ticket 落地下游血緣選擇〉。

規格真的寫錯、照做會做出錯的東西時，同樣不在執行期改規格：本版照原規格完成（或在跑不起來時走上面第一列），修正留給維護版本。維護版本的規劃期再檢討這段規格。

**Why**：執行期一邊做一邊改規格，每次修改都會引出新的審查與新的衍生票，版本永遠收不了尾。把「改設計」集中在規劃期，執行期的工作才有固定的終點。**Consequence**：執行期若照舊開衍生票、改規格，版本範圍會不斷膨脹，同一張票反覆退件，下游也不知道這一版到底包含什麼。**Action**：規劃期結束時一定要凍結；執行期遇到「應該順便改」的念頭時，寫成後續版本的票，然後回到本版的規劃文件。

驗收只審三項固定檢查，見 `.claude/pm-rules/verification-framework.md`〈驗收三項固定檢查〉。

## 收斂：patch 線與 minor 推進

規格凍結只能擋住本版膨脹，擋不住 patch 一個接一個開；維護本身沒有終點，永遠有可以改善的地方。收斂不靠限制 patch 數量，靠以下五條規則。這也是 Django、Kubernetes、Rust 等專案的共同做法：准入規則，加上由後繼版本結束支援，加上新版本穩定到來。

| # | 規則 | 內容 |
|---|------|------|
| 1 | patch 只修承諾未達成 | 只收本 minor 規格寫了但沒做到的行為、資料錯誤、跑不起來的問題。改善、技術債、新點子一律進下一個 minor 的候選池 |
| 2 | 後繼版本結束 patch 線 | 只有最新發版的 minor 收 patch。下一個 minor 發版時，上一個 minor 的 patch 線關閉，剩下的 pending 票移到新 minor 的候選池。patch 從哪裡發，見下方〈patch 的發版來源〉 |
| 3 | 凍結即開下一個 minor | 本 minor 凍結進入執行期時，下一個 minor 必須已在 `docs/todolist.yaml` 登記為 `planned` 並開始規劃，確保規則 2 的後繼一定會來 |
| 4 | 候選池逐項裁決 | 每次 minor 規劃時，候選池每一項只有三個結果：選入本版、放棄（關票並寫明理由）、保留一輪。連續兩輪規劃都未選入的，關票並寫明「經兩輪規劃未選入」；之後若重要，會再被提出，可從關票紀錄追溯 |
| 5 | 維護工作 30% 以內 | minor 的票中，從候選池選入的維護工作（改善、技術債）不超過三成，至少七成服務該 minor 的 roadmap 目標。比例以票數計算，roadmap 票依實際的原子工作拆，不為了讓比例達標而拆票。超過三成時，從票面 priority 最低的維護票開始改判「保留一輪」（規則 4），直到比例回到三成以內；同 priority 間的取捨由規劃者在被退回的票面寫明理由 |

**patch 的發版來源（規則 2）**：patch 發版前，先判定 main 是否已含後繼 minor 的改動，再依結果決定從哪裡發。判定以上一版留有可定址的發版 ref（發版 tag 或發版 commit）為前提。

| 判定：`git diff --name-only <上一版發版 ref>..main -- <發佈範圍>` | 發版來源 |
|------|---------|
| 輸出為空 | 從 main 發 |
| 輸出不為空（main 已含後繼 minor 的改動） | 從維護 worktree 發，程序見下表 |
| 例外閥：修正不急，由用戶裁定併進後繼 minor | 不發 patch。票改掛後繼 minor，以 `--scope-blocker` 寫明這張票原屬哪一版的承諾 |

`<發佈範圍>` 是發版載具實際送出的路徑。例如框架只發佈 `.claude/`，範圍外的改動不影響判定。

維護 worktree 程序：

| 步驟 | 動作 |
|------|------|
| 1 開維護分支 | 以 worktree 從上一版發版 ref 開分支：`git worktree add -b <維護分支> <路徑> <上一版發版 ref>`。共用主工作樹不切分支（`.claude/pm-rules/parallel-dispatch.md`〈派發位置判準〉） |
| 2 修正與發版 | 在維護 worktree 內修正並跑相關測試，從該 worktree 的 commit 發版，再對發版 commit 打新的發版 ref。發版載具只認 HEAD 時，在維護 worktree 內執行；載具支援指定 ref 時，傳入該 commit |
| 3 修正回併 main | 把維護分支上的修正 commit 以 `git cherry-pick` 帶回 main，經合併閘門合入。main 不回併時，後繼 minor 發版會把已修好的缺陷再帶出去 |
| 4 清理 | 發版 ref 打好、修正已回併後，清理維護 worktree 與分支。下一個 patch 從新的發版 ref 重新開 |

例外閥只在用戶裁定時使用，不是常規路徑。規則 3 要求凍結就開下一個 minor，後繼開工後 main 幾乎總含其改動；若常規做法是併進後繼 minor，patch 線只在「發版到後繼開工」之間的短時間內有效，規則 1、2 的 patch 線就形同虛設。

**Why**：main 已含後繼 minor 的改動時，從 main 發 patch 會連同後繼 minor 的半成品一起送給下游。**Consequence**：不做切換判定時，下游收到的 patch 會夾帶後繼 minor 未完成的功能。這違反規則 1 的准入範圍，下游也無從分辨哪些改動屬於 patch。**Action**：patch 發版前跑判定命令；輸出不為空就走維護 worktree 程序，修正一定要回併 main。

**patch 數量是健康指標，不是上限**：同一個 minor 的 patch 達到 3 個時，建一張 ANA 票，回頭檢討該 minor 的規劃與驗收為什麼漏掉這麼多承諾，結論用於下一個 minor 的規劃期。不因數量封頂，否則真正承諾未達成的缺陷會被擋下，或被偷塞進 minor。

**准入規則不限制修法深度**：規則 1 決定哪些承諾未達成的問題進 patch，不決定已進版的問題要修多深；「patch 範圍要最小」不能作為保留缺陷成因的理由。以最小範圍為由保留成因，同一缺陷會在後續 patch 以新症狀重現，每次都要重新診斷，patch 數量也隨之累積。修法深度由兩個問題決定：(1) 這個修法會不會重現產生缺陷的條件？會，就不算修法，改選消除成因的修法。(2) 消除根因需不需要一個還沒做的設計決策？不需要，本版就做；需要，只把那個決策延後，並確認延後目標票的範圍涵蓋它。判斷方式與案例見 `.claude/error-patterns/process-compliance/PC-LLM-001.md`。

**主控方規劃期的框架 issue 輸入**：主控方規劃 minor 時，候選池之外另讀 open framework issue 的輸入清單；「拖慢專案」標記達 2 則的 issue 是必審項，選入或寫明不選的理由。清單內容與標記規則見 `.claude/skills/framework-issue/references/escalation-flow.md`〈修復時點：版本分診〉，本節不重複。

**major 由 roadmap 決定**：major 只在架構里程碑時開（見〈版本層級語義〉），不因候選池累積的票數多而開。

**Why**：只要「改善」能進 patch，patch 就沒有終點；只要候選池沒有合法的「不做」出口，票就只會往後滾。規則 1 從源頭擋住改善流入 patch，規則 4 讓放棄成為已作成的決策（`.claude/rules/core/decision-trigger-binding.md` 規則 1 的狀態 (a)），規則 2、3 讓 patch 線有確定的終點，規則 5 保證 minor 以前進為主；規則 5 的比例若能靠拆 roadmap 票達成，分母會被灌水，比例就不再反映工作量的分配。**Consequence**：缺任何一條，都會退回「pending 池只增不減、版本一直在修舊東西」的狀態。**Action**：minor 凍結時依〈版本生命週期〉「凍結程序」確認規則 3 的後繼已登記；minor 發版時執行規則 2 的 patch 線關閉；minor 規劃時對候選池執行規則 4 並檢查規則 5 的比例。

## 版本生命週期

版本從建立到完成，在三個互相獨立的軸上前進：**版本歸屬**（票屬於哪個版本號）、**收件資格**（版本現在能否收新根票）、**執行資格**（該版本下的既有票能否被 claim/執行）。三軸混為一談是舊制的根因——舊制把 `status` 欄位當成三種語意共用的單一開關，`planned` 版本因此被誤判為「不能執行」；經查證 `lifecycle.py` 對版本狀態零檢查，**claim 不查版本狀態**：任何版本（含 `planned`）下已存在的票，今天就能被 claim 並執行，執行早已與版本狀態解耦。

| 階段 | status / scope | 收件資格 | 執行資格 |
|------|----------------|---------|---------|
| 規劃中 | `status: planned` | 可建票（須以 `--version` 明示指定） | 可執行（claim 不查版本狀態） |
| 開發中，scope 開放 | `status: active`，`scope` 欄位缺席或非 `frozen` | 可建票（含根票，跟隨版本推進正常流程） | 可執行 |
| 開發中，scope 凍結 | `status: active`，`scope: frozen` | 僅收帶 `--scope-blocker <理由>` 的根票（理由持久化為 ticket frontmatter `scope_blocker` 欄位，供發版側查詢）；`--parent` 子票不受影響 | 可執行（既有票不受收件閘門限制） |
| 已完成 | `status: completed` | 不可建根票（依情境回報 `VERSION_NOT_ACTIVE` 或 `VERSION_NOT_REGISTERED`） | 不適用（無待執行票） |

**凍結程序**（凍結步驟只在此處列全，其他文件指向本段，不各自列步驟）：

1. 在 `docs/todolist.yaml` 本版條目標 `scope: frozen`。
2. 對凍結前已存在、且屬版本契約必要的 `pending` 票，逐張執行 `ticket track set-scope-blocker <id> --reason <對應契約項>`。
3. 凍結的是 minor 或 major 時，確認下一個 minor 已在 `docs/todolist.yaml` 登記為 `planned`，未登記就先登記（〈收斂：patch 線與 minor 推進〉規則 3）。凍結的是 patch 時不需此步：它的後繼 minor 在上層 minor 凍結時已登記。

三步都完成，版本才進入執行期。

**Why**：第 2 步：發版檢查（見 `.claude/skills/version-release/SKILL.md`）以 `scope_blocker` 欄位區分阻擋與前移，只覆蓋凍結後才建立的根票（`--scope-blocker` 建票時寫入）；凍結前既有的必要票沒有這個建立時機，若不回溯標記，發版檢查會把它們誤判為可前移，必要工作因此被搬到下一版本。**規劃頁面（`docs/plans/` 等）不是 CLI 的資料來源**——「這張票是必要的」只寫在規劃文件不會被發版檢查讀到，必要性須進票面 `scope_blocker` 欄位才算數。第 3 步：執行期發現的改善、技術債、新能力依〈兩期〉要建在下一個 minor，該版本未登記時這些發現沒有合法去處。**Consequence**：漏第 2 步，必要工作在發版時被前移；漏第 3 步，執行期第一次需要「建在後續版本」時才發現目標不存在（實例：一次 minor 凍結只做了前兩步，到發執行期指派時才補登記下一個 minor）。**Action**：凍結時照上列三步逐項執行；本程序不以步驟數命名，增減步驟只改本段。

**scope 凍結後的分流去向**（對應上方強制規則表）：

| 問題性質 | 去向 | 說明 |
|---------|------|------|
| 承諾未達成（規格寫了但沒做到、資料錯誤、跑不起來） | 下一個 patch（x.y.z+1） | 登記規則見下方〈版本登記規則〉patch 列；准入判準見〈收斂：patch 線與 minor 推進〉 |
| 改善、技術債 | 下一個 minor 的候選池 | 不進 patch；在 minor 規劃時與新能力一起裁決 |
| 新能力 | 下一個 minor（x.y+1.0） | 需先於 `docs/todolist.yaml` 登記為 `planned` 或 `active`，登記門檻見下方〈版本登記規則〉minor 列 |
| 框架問題（抽象可攜 + 根源在 `.claude/` 通用資產，兩條件皆成立） | canonical framework issue | 不落地為本地版本票；該問題在本 consumer 的落地實作票才回頭建本地票，並掛 `--dedup-checked <issue 號>`（見 `.claude/skills/ticket/references/create-command.md`〈可攜問題分流硬閘門〉） |

**minor 完成後的分診與去向**（方案：分診定 topic patch，取代「patch 是被動容器、一律送最近後繼」）：

| 時點 | 規則 | 說明 |
|------|------|------|
| minor 完成後 | 分診一次，列出本 minor 承諾未達成的缺陷，依 topic 定下 patch 的主題；patch 數量不預設上限，由缺陷決定（健康指標見〈收斂：patch 線與 minor 推進〉） | 分診產出登記進版本索引（見下方〈版本登記規則〉），每個 patch 有 topic 與缺陷／範圍清單，不再是「凍結閘門路由到哪就算哪」 |
| 執行期新發現 | 依 topic 契合度進尚未開工的 patch；契合者寫判定依據於票面 | 無契合 topic 時回到〈版本生命週期〉分流表的三性質判斷，不自動落入最近後繼 |
| 例外閥 | 限契約行為錯誤或資料錯誤，可插進進行中的 patch；票面寫判定依據 | 例外閥是保險而非常態：使用比例上升代表分診 topic 切得不對，回頭檢討分診 |
| 前移（finish 時） | 未完成票的前移目標由分診指定，不再一律送最近的開放後繼 | 分診未指定者才退回「最近的開放後繼」預設；前移目標須已登記 |
| 框架票（修改 `.claude/` 通用資產；只適用主控方，consumer 不建此類票，角色判定見 `.claude/skills/framework-issue/references/escalation-flow.md`〈角色：主控方與 consumer〉） | 發現當期建票並優先執行（建票時點不延後）；finish 時與其他票同樣前移，只有版本契約依賴者加 `scope_blocker` 阻擋；同一張票前移第 2 次即收束進 canonical issue 後關票 | 見 `.claude/pm-rules/pm-quality-baseline.md` 規則 6；阻擋的根源在規則而非 `version-release` 工具，工具只擋帶 `scope_blocker` 的票 |

**Why**：舊制只有「下一個版本」一種去處，patch 是被動容器，「現在不做」沒有合法去向，票只能往後滾；實測單一 minor 的 pending 池因此累積到數百張，且框架票不經分診、無上限進入當期版本並阻擋其 finish。**Consequence**：不分診則 patch 的範圍由路由偶然決定，前移目標一律最近後繼會讓票池只增不減，框架票滾動則重演同一症狀。**Action**：minor 完成後先分診再開工；每個 patch 開工前依方法論〈版本契約五欄模板〉寫定契約；前移與框架票按上表處置。

**版本登記規則**（版本索引 `docs/todolist.yaml` 只登記已發生、進行中、以及範圍已定案的版本；凍結閘門的溢出目標與 `finish` 的前移目標都要求目標已登記，登記是它們的共同前置）：

| 層級 | 登記門檻 | 條目 notes 最少內容 |
|------|---------|-------------------|
| patch（x.y.z，z > 0） | 不需提案定義範圍——範圍由上層 minor 完成後的分診定下的 topic 與凍結閘門路由至此的票組成；分診時可預先登記為 `planned`（見下方〈預先登記與後續版本票池〉），未預先登記者於凍結閘門第一次把票擋向此版本時，先登記為 `planned` 再建票 | 登記時：「範圍 = 凍結閘門路由至此的票；整合測試 = 上層 minor 的整合測試仍通過」。凍結前：補上收斂承諾（逐條指名已發布規格條款而實作未達者）與缺陷清單，契約形態見方法論〈五步程序〉步驟 1 patch 列 |
| minor（x.y.0） | 提案已 confirmed，且整合測試、斷言來源、阻擋清單三者皆在提案中寫定（範圍已定案類，登記的是事實不是規劃） | 引用提案章節；整合測試與阻擋摘要 |
| major | 架構里程碑，判準同〈版本層級語義〉 | 同 minor |

**預先登記與後續版本票池**：

| 規則 | 說明 |
|------|------|
| 允許預先登記 | major 起始時可登記其下固定的 minor 清單（各解決哪些規格），minor 完成後分診並登記固定數量的 topic patch；登記的是範圍與 topic，不是工作量承諾 |
| 延後須附討論記錄 | 項目進入尚未開工的後續版本，須附「經討論後決定放在此處」的記錄（版本條目 notes 或決策記錄）；不在任何已規劃版本內的項目，須明確決定延後，不以版本標籤代替討論 |
| 後續版本票池在其規劃波逐張裁決 | 後續版本開工前的規劃波，對其票池逐張裁決（留、改派 topic、關閉、收束進 canonical issue）；此裁決取代獨立的停放文件——停放的實際載體是已登記的版本，風險在票池未被逐張裁決 |

**Why**：試行中獨立停放文件從未建立，延後項直接落入已登記的後續版本；停放不再是獨立載體，失效訊號因此移到「該版本票池在規劃波有沒有被逐張裁決」。**Consequence**：預先登記但規劃波不裁決票池，後續版本會成為新的墳場，與停放文件成墳場同型。**Action**：後續版本開工前的規劃波必含「票池逐張裁決」一步，裁決結果寫入工作日誌。

**Why 登記規則必須在框架而不只在專案的版本索引檔頭**：規則若只寫在某個專案的 `docs/todolist.yaml` 註解，其他 consumer 專案拿不到，凍結閘門在那裡撞到未登記目標時沒有可循的登記方式。**Consequence**：接手者只能手抄另一個專案的條目格式，或跳過登記直接改票的版本欄位，讓發版前移失去目標。**Action**：專案的版本索引檔頭只留一句指向本節的指標；登記動作目前為手動編輯版本索引並建立該版本的工作日誌主檔，CLI 化的觀測見 canonical `tarrragon/claude#16`。

**三層推進判準**（何時該正式開下一個 patch / minor / major，而非只是票的版本欄位已指向該處）：patch 的發版判準與 minor 同構——上層 minor 的整合測試仍通過，且無帶 `scope_blocker` 的 pending 票，不以是否有外部使用者依賴為前提；minor 需當前版本契約已發布且下一版本提案已 confirmed（滿足上方登記門檻）；major 為架構里程碑，判準與上方〈版本層級語義〉一致。版本契約五欄模板（topic 清單、預期變更、驗證方式分類、人工實測時段與前置檢查、結果值日誌事件）見方法論〈版本契約五欄模板〉。完整判準表、Why/Consequence/Action、patch 生命週期（收件窗口與關閉時機）、發版判準（契約阻擋而非池清空）、五步收斂程序（版本契約→範圍歸屬三問→依賴分批→溢出分流→凍結）與反模式，見 `.claude/methodologies/version-scope-convergence-methodology.md`。本節只定義凍結後的分流去向，不重複該方法論的判準內容。

| 規則 | 說明 |
|------|------|
| 新 Ticket 版本號預設對齊 active 版本 | 建立 Ticket 時，版本號預設跟隨當前 active 版本，除非有明確跨版本要求；scope 凍結時另受〈版本生命週期〉收件資格規則約束 |

## 版本收尾技術債整理流程

> **觸發時機**：決策樹第八層情境 C2（版本內所有 Ticket 已完成，無任何待處理任務）
>
> **來源**：W49 實踐 — Wave 收尾多視角審查 + 版本收尾技術債批量建 Ticket 模式

版本完成後、執行 `/version-release check` 之前，**必須**整理未追蹤的技術債。

### 流程

```
情境 C2：版本無任何待處理任務
    |
    v
[強制] 檢查 todolist.yaml
    → 篩選與當前版本相關的未排程項目
    → 識別需要帶入下一版本的技術債
    |
    v
有需要建立的技術債 Ticket?
    |
    +── 是 → /ticket batch-create 批量建立（歸入下一版本）
    |         → 建立後不影響當前版本完成狀態
    |
    +── 否 → 繼續
    |
    v
[強制] /version-release check
    → AskUserQuestion #13（版本推進確認）
```

### 技術債篩選標準

| 來源 | 判斷 | 處理 |
|------|------|------|
| todolist.yaml 已記錄但未排程 | 是否與下一版本目標相關？ | 相關 → 建立 Ticket；不相關 → 保留在 todolist |
| Phase 4 `/tech-debt-capture` 產出 | 已建立 Ticket？ | 已建 → 確認版本歸屬；未建 → 補建 |
| Wave 審查發現但未處理 | 是否阻塞版本發布？ | 阻塞 → 本版本處理；不阻塞 → 歸入下一版本 |

### 禁止行為

| 禁止 | 說明 |
|------|------|
| 跳過 todolist 檢查直接發布 | 可能遺漏已知技術債 |
| 將技術債 Ticket 建在當前版本 | 版本已完成，應歸入下一版本 |
| 只口頭記錄不建 Ticket | 必須有可追蹤的 Ticket |

## 權限需求變更檢查

若專案有面向使用者的權限宣告（如 Chrome Extension、行動 APP），版本發布或推進時須檢查權限是否較上一發布版本變更。**Why**：權限有變更而未同步更新權限說明文件，會導致應用程式商店審核因宣告與實際不符而卡關。**Action**：依專案類型同步更新對應的權限說明文件與上架頁；後端服務等無使用者端權限宣告的專案類型不適用。

各專案類型的權限宣告位置、同步更新對象與完整檢查步驟，見 `version-release` skill 的「權限需求變更檢查」章節；本規則僅在版本推進階段提醒，不重複定義步驟。

## 跨版本 Ticket 遷移決策

當 Ticket 需要從一個版本遷移到另一個版本時：

| 情境 | 決策 |
|------|------|
| 當前版本未完成但新版本已開始 | 評估 Ticket 是否仍相關，相關則遷移 |
| Ticket 依賴已在新版本實作的功能 | 遷移到新版本 |
| Ticket 描述的問題已被新版本解決 | 關閉並記錄原因 |

使用 `/ticket migrate` 執行遷移。

## 版本遷移觸發條件與判斷流程

### 觸發條件

| 觸發時機 | 說明 | 判斷入口 |
|---------|------|---------|
| 版本內所有 Ticket 完成 | 決策樹情境 C2 觸發 | 版本收尾技術債整理 → /version-release check |
| 新功能需求超出當前版本範圍 | Q1 回答「否」時 | Q2-Q4 判斷決定新版本層級 |
| todolist.yaml current_version 不一致 | Version Consistency Guard Hook 偵測 | 修正 todolist.yaml 或完成舊版本任務 |
| 舊版本有遺留未完成 Ticket | Version Consistency Guard Hook 偵測 | 評估遷移、關閉或完成 |

### 判斷流程

```
觸發遷移評估
    |
    v
[Step 1] 確認當前版本所有 Ticket 已完成
    → ticket track list --version {current} --status pending in_progress
    → 有未完成? → 先處理完成或遷移
    |
    v
[Step 2] 執行 /version-release check
    → CHANGELOG 更新? Smoke test 通過?
    |
    v
[Step 3] 更新 todolist.yaml
    → current_version: {new}
    → previous_version: {old current}
    → next_version: {new + 1}
    |
    v
[Step 4] 確認舊版本遺留 Ticket 處理方式
    → 仍相關 → /ticket migrate
    → 已解決 → 關閉並記錄原因
    → 不再相關 → 關閉並記錄原因
```
