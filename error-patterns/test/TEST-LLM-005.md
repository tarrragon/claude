# TEST-LLM-005: runtime 探針的執行形狀與實際呼叫不同，量到的落點與判定不代表真實行為

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 分類 | test（runtime 驗證手法） |
| 來源版本 | 3.5.0 |
| 首次觀測 | 2026-11-12 |
| 適用範圍 | 以手動或腳本實跑真實程式（hook、CLI、子行程）驗證修改，且被測程式的路徑或行為依 cwd、環境變數決定 |

## 摘要

**runtime 探針是為了補單元測試看不到的部分，但探針自己也是一次執行：它的 cwd、專案根環境變數與其他 env 若與實際呼叫不同，被測程式走的是另一條解析路徑，量到的寫入落點與判定結果屬於探針的形狀，不屬於真實執行。探針要照實際呼叫的形狀設定、確認寫入落點、以舊程式碼跑同一情境作對照，並在結束後清掉自己的產物。**

## 症狀

- 探針報告的寫入位置與事後在真實執行中觀察到的位置不同
- 探針結論「修好了」，但無法說明舊程式碼在同一情境下會怎樣——沒有對照，判不出差異來自修改還是來自探針設定
- 探針在共用目錄留下的檔案被受驗的偵測器命中（例：命名符合測試前綴的檔案），下一次閘門誤紅
- 多次探針的產物混在一起，無法分辨哪一筆屬於哪一次

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 被測程式依執行脈絡解析路徑 | 根目錄解析讀 cwd、git 狀態或專案根環境變數 | 探針的 cwd 或 env 不同，走的是另一個分支 |
| 探針形狀憑直覺設定 | 腳本以自己的 cwd 啟動子行程，或只設了部分環境變數 | 實際呼叫的形狀（例：由 harness 在某個目錄、帶特定 env 啟動）沒被重現 |
| 只看判定、不看落點 | 探針只記錄「通過／不通過」 | 判定剛好一致時，落點錯誤不會被發現；之後依該報告寫的落點紀錄是錯的 |
| 缺少舊碼對照 | 只跑新版程式碼 | 無法證明這次探針對修改有鑑別力（與測試斷言的鑑別力同一問題） |
| 探針產物未清理 | 探針寫入的檔案留在共用位置 | 成為下一次偵測的雜訊來源 |

## 解決方案

| 步驟 | 做法 |
|------|------|
| 1. 探針識別值 | 每次探針使用唯一、可 grep 的 session id 或標籤（例：`probe-<編號>-<隨機尾碼>`），只看含該值的項目，避免與其他寫入者混淆 |
| 2. 照實際形狀設定 | 先查清真實呼叫時的 cwd、專案根環境變數、隔離旗標與其他 env，探針逐項照設；以重建 env 啟動子行程時，確認沒有漏帶或多帶 |
| 3. 確認寫入落點 | 不只看判定，實際列出寫入檔案的完整位置，與預期落點比對 |
| 4. 舊碼對照 | 用修改前的程式碼跑同一情境；新舊結果須不同，才證明探針量到的是修改造成的差異 |
| 5. 記錄形狀 | 報告寫明每個情境的 cwd、env、程式碼版本、寫入位置；形狀與實際不同的列要標示並補跑 |
| 6. 清理產物 | 探針產物若可能被受驗的偵測器命中（例：符合測試前綴的檔名），驗證後刪除並確認計數為 0；保留的探針檔要列出路徑 |

## 預防措施

| 時機 | 檢查 |
|------|------|
| 設計探針 | 列出被測程式解析路徑時讀的所有輸入（cwd、env、git 狀態），逐項對齊實際呼叫 |
| 報告探針結果 | 每個情境有落點與舊碼對照兩欄；缺任一欄不算完成 runtime 驗證 |
| 探針結束 | 清理會被偵測器命中的產物 |

## 案例

修改洩漏哨兵後，以腳本實跑真實 hook 做三個情境的新舊對照，判定全部符合預期。複查時發現兩個情境的子行程 cwd 不在 worktree 內：被測的共用根解析函式依 cwd 判斷是否位於 linked worktree，cwd 不符就不回推主 repo，因此寫入落在 worktree 而非主 repo。判定沒有受影響，但報告記下的落點與實際閘門執行不同。照閘門實際形狀（cwd 等於該版本 hook 的根、專案根環境變數照設）補跑後，寫入落在主 repo，與真實執行一致。

同一輪驗證中，以測試前綴命名的探針檔正好會被受驗的哨兵判為洩漏，驗證後逐一刪除並確認兩個根的計數皆為 0。
