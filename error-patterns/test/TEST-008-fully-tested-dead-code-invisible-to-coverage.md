# TEST-008: 死碼備有完整綠燈測試，coverage 與測試結果皆不告警使其長期存續

## 症狀

- 某模組體量觸發檔案行數閾值告警，直覺處置為拆檔
- 盤點可達性後發現大比例函式在生產路徑上零呼叫者（實測案例：865 行中 457 行，52.8%）
- 這些函式**皆有完整測試且全數綠燈**（該案例 10 個 test class 共 396 行）
- coverage 指標不告警：測試確實覆蓋這些行，覆蓋率數字健康
- 測試結果不告警：函式行為正確，斷言全數通過
- 死碼因此被誤認為活碼，隨檔案一同被拆分、重構、同步，成本持續累積

## 根因

**測試驗證「函式行為是否正確」，不驗證「函式是否仍被呼叫」。** 兩者是不同命題，而測試工具鏈只回答前者。

coverage 工具量測的是「測試執行時哪些行被執行到」，測試本身就是執行者，故直接 import 並呼叫死碼的測試會讓那些行 100% 覆蓋。覆蓋率高低與生產可達性無關 —— 測試覆蓋率在此情境下反而成為死碼的保護色：一個沒有測試的死碼會在 coverage 報告中顯示為未覆蓋而引人注意，有測試的死碼則完全隱形。

延伸成因：模組被跨 repo 同步或從他處匯入時，函式隨檔案帶入但入口從未接線。這類死碼從第一天起就不可達，沒有「功能被移除」的 commit 痕跡可循，`git log -S` 也查不到曾被呼叫的證據。

## 後果

1. **拆檔等假修復**：對超標檔案拆分後，每個新檔皆「符合行數閾值」，死碼卻由集中一處變分散多處，更難辨識。指標達標而根因存續且惡化。
2. **維護成本持續支付**：死碼參與每次重構、型別遷移、lint 規則升級、跨 repo 同步，其測試也持續消耗執行時間。
3. **誤導架構判斷**：讀者依檔內函式推斷模組職責時，會把不存在的能力（如「這個 board 支援卡片版渲染」）當成現有功能。

## 偵測方式

對懷疑的函式做雙向查證，兩者皆空即為生產不可達：

```bash
# 1. 檔內呼叫者（排除定義行）
grep -n "<fn>(" <file> | grep -v "^[0-9]*:def "

# 2. 全 repo 引用（排除測試與定義檔）
grep -rn --include='*.py' "\b<fn>\b" <root> | grep -v "/tests/" | grep -v "<file>"
```

注意第 2 步的命中可能是**註解文字**而非程式呼叫（實測案例中 message 常數檔的註解寫「render_board_unicode 中的標題」，被 grep 命中但不構成呼叫）。命中須逐項判讀是否為可執行的引用。

呼叫鏈需遞迴收斂：若 A 只被 B 呼叫而 B 不可達，則 A 亦不可達。實測案例的寬度工具鏈即為此形態（`get_char_display_width` 只被 `calculate_visual_width` 與 `truncate_title` 呼叫，兩者皆只被卡片版渲染呼叫，整鏈四函式 114 行隨之不可達）。

## 預防措施

1. **檔案體量告警時，先查可達性再談拆檔**。順序反了就會做出拆散死碼的假修復。判斷句：這個檔的行數中，有多少是入口可達的？
2. **測試 import 清單是可達性線索**。若某函式的唯一 import 端是測試檔，而生產模組無人 import，該函式已無生產消費者。實測案例中生產端唯一 import 是命令註冊點（只取入口函式與兩個常數），其餘 17 個符號全由測試 import。
3. **跨 repo 同步或匯入模組後，確認入口已接線**。函式存在不等於被呼叫；接線與否需顯式驗證，不可由「檔案已同步」推論。
4. **刪除死碼須以行為等價為驗收前提**：刪除前後，入口命令的實機輸出逐字比對相同，且全套件測試數的減少量與移除的 test class 數相符（避免意外連帶失敗被當成預期減少）。
