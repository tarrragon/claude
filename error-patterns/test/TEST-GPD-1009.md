# TEST-GPD-1009: 以行為名稱推論可測性，未查實際觸發條件

依行為的名稱（如「不可見時暫停」）判定自動化測不到，轉交人工實機操作；沒有先查該行為的實際觸發條件能否在測試框架中製造。

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 分類 | test |
| 來源版本 | 0.6.0 |
| 首次觀測 | 2026-11-02 |
| 關聯案例 | 狀態管理套件大版本升級後的實機驗證票 |

## 症狀

驗證項被標為「自動化測試無法重現，需實機／人工操作」，理由只引用行為名稱或使用者視角描述（「視窗不可見」「背景執行」「縮小後」），沒有指出測試框架缺少哪一個能力。驗證因此被轉交給用戶操作 GUI，佔用用戶畫面並延後結論；用戶反問「能否自行驗證」後才改為自動化。

## 實例

狀態管理套件大版本升級，新版本新增「不可見時暫停監聽」。實作代理人回報「自動化測試無法重現視窗可見性，請實機留意」，PM 照此建實機驗證票並請用戶逐步操作。用戶一問，查證後發現：

- 套件的暫停觸發條件是 widget 子樹的 TickerMode 關閉，不是作業系統視窗的可見性。
- App 以 IndexedStack 承載多頁，非選取頁正處於 TickerMode 關閉狀態；widget 測試與 integration 測試完整支援此狀態。
- 視窗縮小對應的 App 生命週期變化，測試 binding 也提供模擬入口。

上列觸發條件都能在測試中製造，自動化結果還能留作回歸防護。

## 根因

「不可見」這個詞同時指使用者感知（視窗看不到）和機制條件（框架內部旗標）。判斷者以前者推論可測性：使用者感知確實需要人看，於是結論是需要人工。可測性應由後者決定，問的是「觸發這個行為的程式條件是什麼，測試能否製造它」。代理人的判斷沿派發鏈傳給 PM，PM 沒有重新查證就照單建票，所以錯誤判斷通過了兩層。代價是用戶的 GUI 操作時間，以及沒有留下回歸測試。

## 解決方案

可測性由程式的觸發條件決定，不由使用者感知決定。宣告「需人工驗證」前，依序回答：

1. 這個行為在程式中的觸發條件是什麼？查套件原始碼或文件，找到實際讀取的旗標、事件或回呼。
2. 測試框架能否直接製造該條件？例如 widget 樹狀態、生命週期事件、平台通道 mock、假時鐘。
3. 只有第 2 問的答案為「不能」，且能指名缺少的能力時，才轉人工；票面須寫出缺少的能力。

## 預防措施

- 接收代理人的「無法自動化」結論時，PM 先追問第 1 問的答案；回報中沒有觸發條件的，視為未查證。
- 與 `tool-discovery` 規則 1「宣告做不到前五問」同一精神：做不到的結論要有指名的阻擋點。
