# TEST-GPD-1003: 對照測試（拿掉修正後應轉紅）在同一個測試案例內放多條斷言，第一條失敗就中止，後面的斷言沒有執行，整體紅燈被誤讀成每一條斷言都有鑑別力

## 症狀

驗證修正是否有效時，常見做法是暫時把修正還原，確認測試轉紅（正向對照）。如果一個測試案例內寫了多條斷言，例如「label 只含訊息」「按鈕不在子樹內」「焦點不在此節點上」，還原後整個案例轉紅，看起來像是每條斷言都抓到了缺陷。

實際上，多數測試框架遇到第一條失敗的斷言就中止該案例（`expect` 拋出例外），後面的斷言根本沒有執行。紅燈只證明了第一條有鑑別力，其餘各條在還原版上可能是綠的，也就是沒有鑑別力。

實證（2026-10-30）：一次讀屏語意修正的對照測試，第一輪每個案例都在 label 斷言轉紅。改成每條斷言各自一個案例重跑後，19 條裡有 3 條在還原版上是綠的：其中 2 條是因為該變體本來就沒有那個問題，1 組是旗標本來就正確。原本的整體紅燈把這 3 條也算成了證據。

## 根因

**失敗會中止後續斷言，但報告只說「這個案例失敗」**。測試報告的粒度是案例，不是斷言。還原版的紅燈和修正版的綠燈，比較的都是整個案例，沒有逐條比較。

**寫斷言時以「同一個情境要驗的事」分組**。同一個 pump 之後要驗的事情放在一起很自然，也能省下重複設定。但對照實驗需要的粒度是「每條斷言一個判定」，這和撰寫時的分組方式不同。

## 解決方案

- 做對照實驗時，每條要宣稱有鑑別力的斷言，各自放在一個獨立案例內；共用的設定抽成 helper，讓拆開的成本降低。
- 或者在同一案例內收集所有失敗再一次報告（軟斷言），讓每條都能取得判定。
- 對照結果以表格逐條記錄：還原版紅或綠、是否有鑑別力。綠的那些標為回歸斷言，不算證據。

## 預防措施

- 審查對照證據時問：「這個紅燈是哪一條斷言造成的？其他條在還原版上有跑到嗎？」
- 只附一段紅燈原文時，核對它對應的是哪一條斷言，不要推廣到同案例的其他斷言。
- 紅燈原文本身也要完整：多行字串的 Expected／Actual 可能被測試框架或輸出擷取截斷，只剩第一行。截斷後兩者看起來相同時，無法判斷轉紅的原因，這條證據不能採用，要以不截斷的方式重跑取得原文。例外：Expected 本身是單行，且 Actual 截斷後的首行與 Expected 相同時，轉紅只可能來自截掉的後續內容，這時判讀仍成立，可採用並註明截斷。
