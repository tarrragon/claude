# TEST-BAL-008: 自建 fixture 的資料形狀與真實資料分佈不同，使歸納式推導的退化案例測不出來

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | test |
| 風險等級 | 中 |
| 首次觀察 | 2026-08-20 |

## 症狀

功能的職責是「從既有資料歸納規則，再套用到新輸入」——推薦、分類、自動歸屬、相似度匹配、
啟發式路由皆屬此類。測試以自建 fixture 覆蓋各條規則，全數通過；改以真實資料執行同一函式，
輸出明顯錯誤。

兩種典型錯誤形態：

| 形態 | 表面現象 | fixture 為何測不到 |
|------|---------|-------------------|
| 過泛條目吃掉全部匹配 | 任何輸入都命中同一個結果 | fixture 的每筆資料都是撰寫者刻意造的「合理」樣本，不會出現過泛條目 |
| 平手時結果不穩定 | 同樣輸入在不同時間給出不同結果 | fixture 資料量小且無重疊，平手情境不會自然發生 |

關鍵特徵：**測試不是寫得不夠多，而是資料不夠髒**。加測試案例無助於發現，因為新案例同樣
由撰寫者設計，同樣不會有那些形狀。

## 根因：fixture 是設計出來的，真實資料是長出來的

撰寫 fixture 時，撰寫者腦中已有該功能的正確模型，造的每筆資料都符合該模型。真實資料則由
許多人在不同時間、不同理解下累積，必然包含撰寫者沒設想過的形狀：

- **粒度不一致**：同一欄位有人填精確值、有人填涵蓋範圍（如路徑欄位有人填單一檔案、有人填整個目錄）
- **重疊歸屬**：同一實體同時符合多個分類，而分類欄位只能填一個
- **歷史殘留**：早期以不同慣例填入、後來規則改了但舊資料沒改

歸納式推導對這些形狀特別敏感，因為它把「既有資料」當成規則來源——資料裡的異常會直接變成
規則裡的異常，而不是被當成錯誤輸入拒絕。

## 與既有模式的邊界

| 模式 | 機制 |
|------|------|
| PC-165 / quality-baseline 規則 1 | mock 替身假裝成真實依賴，斷言驗證的是替身行為 |
| **本模式** | 沒有替身，測的是真函式；問題在**輸入資料的分佈**與真實世界不同 |

兩者都表現為「測試全綠但 runtime 錯誤」，但處置不同：前者要換掉 mock，後者要換掉資料來源。

## 解決方案

**GREEN 後、宣告完成前，以真實資料集執行一次同一函式，逐筆檢視輸出。**

具體步驟：

1. 寫一段一次性探針腳本，直接呼叫待測函式（不經 fixture、不經測試框架）
2. 餵入真實資料中的代表性輸入，含刻意挑選的邊界樣本（最泛的、重疊的、最舊的）
3. 逐筆判斷輸出是否合理——這一步必須人看，因為沒有預期值可比對
4. 發現偏差時**先補測試釘住該形狀**（把真實資料的形狀寫進 fixture），再修實作

步驟 4 是關鍵：直接修實作會讓同一形狀在下次重構時復發，因為 fixture 仍然不含它。

## 預防措施

| 時機 | 動作 |
|------|------|
| 設計歸納式功能時 | 先查真實資料的欄位填寫分佈（最泛的值是什麼、有多少重疊），再定判準 |
| 定閾值類參數時 | 閾值的合理性由真實資料決定，不由 fixture 決定；票面記錄該閾值的資料依據 |
| Phase 3b 收尾 | 於 acceptance 明列「以真實資料集複驗」一項，使其不依賴執行者記得做 |
| 撰寫 fixture 時 | 刻意加入至少一筆「過泛」與一組「重疊」樣本，使退化案例進入回歸保護 |
