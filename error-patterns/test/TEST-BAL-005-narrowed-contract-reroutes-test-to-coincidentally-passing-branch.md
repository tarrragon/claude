# TEST-BAL-005: 合法值收窄使舊測試改走另一分支，斷言因輸出清單重疊而巧合成立

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 高 |
| 發現時機 | 一次「移除某白名單值」的變更，commit 前多視角審查由正確性視角與 Good Taste 視角各自獨立命中 |
| 發現日期 | 2026-08-19 |

## 症狀

- 收窄某個合法值白名單（移除成員、合併判定條件）後，全套測試維持 100% 綠燈
- 其中若干測試的名稱與 docstring 宣稱驗證行為 A，實際執行時已改走行為 B 的分支
- 兩個分支的輸出**恰好共用字串**，使原本針對 A 的斷言在 B 的輸出上同樣成立
- 覆蓋率工具無告警：該測試確實執行、確實通過，只是通過的理由與它宣稱的理由無關

## 根因

收窄合法值使輸入的**攔截點前移**：原本能通過第一道檢查、在第二道檢查失敗的輸入，現在於第一道檢查就被擋下。測試的輸入沒變、期望的 exit code 沒變（兩個分支都回非零），變的只是路徑。

單有攔截點前移還不會造成靜默——真正使它不可見的是第二層：**兩個錯誤分支的輸出存在字串重疊**。收窄前的分支輸出「該 ticket 現有的章節：Problem Analysis, Test Results」，收窄後的分支輸出「有效值：Task Summary, Problem Analysis, Test Results, ...」。測試斷言 `"Problem Analysis" in output`，兩邊都成立。

重疊不是巧合的意外——引導型錯誤訊息傾向列出同一組領域名詞（現有章節 / 合法章節 / 建議章節），所以任兩個引導訊息的字串交集通常非空。收窄合法值的變更會系統性地把輸入從一個引導分支推向另一個引導分支，而這正是重疊最可能發生的地方。

後果是訊號反轉：全綠本應提示「行為 A 仍受保護」，實際上行為 A 已不可達、其守衛已失效，而測試繼續為它背書。下一個維護者若想修改行為 A，會以為有測試保護。

與既有模式的分界：

| 模式 | 機制 | 分界 |
|------|------|------|
| TEST-BAL-002 | 測試替身走簡化建構路徑，繞過 production 裝配 | 盲區在 production 與替身的差集 |
| TEST-BAL-003 | 生產端未落地，測試憑空造出 production 生不出的輸入 | production 路徑**不存在** |
| PC-165 | 斷言強度不足，unit test 綠燈遮蔽 runtime 失效 | 走的是**對的**路徑，只是斷言太弱 |
| 本模式 | 攔截點前移 + 分支輸出字串重疊 | 走的是**錯的**路徑，斷言強度足夠但驗錯了對象 |

## 解決方案

**收窄任何合法值集合時，對所有以被移除成員為輸入的測試逐一重跑並比對輸出全文，不看 pass/fail。**

判定方法是把測試的宣稱與實際輸出並列：

| 檢查 | 做法 |
|------|------|
| 該測試現在走哪條分支 | 印出完整 stdout/stderr，比對是哪一則錯誤訊息，而非只看 exit code |
| 宣稱與實際是否一致 | 讀測試名稱與 docstring 宣稱測什麼，與上一步的實際訊息對照 |
| 不一致時的處置 | 改斷言為實際路徑並於 docstring 寫明變更理由；若被測行為已不可達，連同該行為的程式碼一併評估存廢 |

**斷言錨定在該分支獨有的字串上，不用領域名詞。** 上例中 `"無效的 section: Execution Log"` 是白名單分支獨有，`"Problem Analysis"` 則是任何引導訊息都可能出現的領域名詞。前者能區分分支，後者不能。

## 預防措施

**觸發時機**：從任何白名單、枚舉、合法值集合移除成員時；合併兩個判定條件使其中一個恆為真或恆為假時。

**必要動作**：列出所有以被移除成員為輸入的測試，逐一比對輸出全文。這些測試多半不會紅燈，所以不會主動出現在視野裡——必須主動 grep 該成員的字面值才找得到。

**可稽核產物**：把比對結果（每個測試的實際輸出與宣稱行為是否一致）寫進 ticket 的 Test Results。缺此產物時，「我確認過測試還有效」與「我看到全綠就過了」無法區分。

**為何自檢清單抓不到**：全套綠燈是自檢的主要依據，但綠燈只證明斷言成立，不證明斷言測的是宣稱的路徑。此類缺陷須逐測試比對「名稱宣稱的行為」與「實際執行的分支」，非通用自檢項目可涵蓋——它需要知道這次收窄了什麼，才知道該查哪些測試。

## 案例

某 CLI 的 `--section` 參數有一份合法值白名單，其中一個成員是文件的 H1 容器標題而非可寫入章節，該值自納入起因存在性檢查提前返回而從未真正可用。移除該成員時，兩支測試維持綠燈：

- 一支名為 `test_error_message_lists_existing_headers`，docstring 宣稱驗證「找不到章節時列出現有標題的引導」
- 一支名為 `test_scenario_3_section_not_found`，宣稱驗證找不到章節的錯誤通道

兩支都以該被移除的值為輸入。移除後輸入在白名單階段即被拒，兩支測試實際執行的是「無效的 section」分支，該分支不列出現有標題、只列出合法值清單。斷言 `"Problem Analysis" in output` 與 `"Test Results" in output` 因合法值清單包含這兩個名詞而成立。

同時發現：被這兩支測試守衛的 `section_missing` 判定式在白名單收窄後恆為假，其引導輸出成為不可達路徑。測試無法覆蓋不可達路徑，所以它們繼續存在只能是假通過——刪除死分支與修正假通過測試是同一件事的兩面，必須同批處理。
