# TEST-BAL-011: 計時邏輯讀牆鐘時間，測試的假時鐘只推進計時器，同一測試結果隨執行節奏翻轉

> 出處：BAL 分域。原號 TEST-BAL-003（BAL 分域），收錄時改號為 TEST-BAL-011。

## 基本資訊

| 項目 | 值 |
|------|------|
| 風險等級 | 中 |
| 來源版本 | 未記載 |

## 症狀

- 涉及「延遲顯示」「最短停留」等時間門檻的元件，同一個測試在程式碼不變的情況下，有時綠有時紅
- 紅燈時的失敗點落在時間門檻附近（例如門檻前 10ms 應仍顯示載入、卻已切換）
- 改用較長的 pump 間隔或在負載較低的機器上執行，紅燈消失，使人誤判為機器負載造成的偶發問題

## 根因

測試框架提供的假時鐘只接管「計時器」一類的排程（Flutter widget test 的 fake async 接管 `Timer`、`Future.delayed`），不接管「讀取目前時間」的呼叫（`DateTime.now()`）。

被測程式碼若混用兩者——用計時器排程、再用 `DateTime.now()` 相減計算「已經過多久」——則測試推進的是假時間，程式讀到的卻是真實經過的時間。兩者的差距取決於測試實際執行花了多久，所以同一份測試會隨機器負載與 pump 節奏得出不同結果。

這與 `test-assertion-design-rules` 規則 D3（`DateTime.now()` 不進入斷言比較）不同軸：D3 管的是測試碼的斷言，本模式的牆鐘讀取在**被測的產品碼**裡，測試碼本身完全合規也會中招。

## 解決方案

- 時間門檻邏輯一律由計時器事件驅動：門檻開始時啟動計時器，門檻到期由計時器回呼設旗標，決策只讀旗標，不讀目前時間
- 確實需要讀目前時間的產品碼，改為注入可替換的時鐘（建構參數或 provider），測試注入與假時鐘同步的實作
- 驗收時用「誤實作翻紅」確認測試有鑑別力：暫時把切換邏輯改回直接替換，確認門檻測試轉紅後再還原

## 偵測

- 審查含時間門檻的元件時，搜尋產品碼中與計時器並存的 `DateTime.now()` 呼叫
- 同一時間門檻測試出現綠紅交替時，優先檢查本模式，不先歸因於機器負載

## 實例

整頁載入指示「出現後至少停留 300ms」的切換元件，初版以 `DateTime.now().difference()` 計算剩餘停留時間，widget test 中同一測試邏輯兩次執行一綠一紅；改為計時器回呼設旗標後結果穩定，並以誤實作翻紅驗證鑑別力。
