# TEST-GPD-1000: 把 provider 預設值改成帶無限動畫的狀態，被 IndexedStack 保活的背景頁讓不相關的全 App 測試 pumpAndSettle 逾時

## 基本資訊

- **Pattern ID**: TEST-GPD-1000
- **分類**: 測試設計（test）
- **風險等級**: 中（合併閘門會攔下，不會進入主幹；但盤點會漏，紅燈出現在看似無關的測試檔，排查要多一輪）
- **來源版本**: 0.5.0
- **相關 Pattern**: PC-BAL-061（驗收範圍只看 where.files，漏掉範圍外依賴同一行為的測試）

---

## 問題描述

### 症狀

- 把某個畫面狀態 provider 的預設值，從靜態畫面（例：已載入的矩陣）改成帶無限動畫的狀態（例：載入中的 skeleton shimmer、indeterminate 進度條）
- 盤點時只跑該畫面與外框的測試，全綠；合併閘門跑全套件，卻在其他畫面的測試檔紅燈，例外是 `pumpAndSettle timed out`
- 紅燈的測試從來沒有斷言那個畫面，只是透過共用的 `pumpApp` 掛載整個 App，再導覽到自己的畫面

### 根因

三個條件同時成立：

| 條件 | 作用 |
|------|------|
| 外框以 `IndexedStack` 一次建構所有頁面 | 背景頁仍在樹上，動畫照常排程 |
| 測試沒有注入該 provider，且讓狀態離開預設值的流程在測試的 fake async 中不會完成（例：真實的偏好設定或檔案還原） | 狀態永遠停在預設值 |
| 新預設值帶無限動畫 | `pumpAndSettle` 永遠等不到畫面靜止 |

舊預設值是靜態畫面時，前兩個條件早就成立，只是沒有後果；這些測試能綠，靠的是預設值剛好不帶動畫，這個前提從未被寫明。

---

## 解決方案

- 在共用的掛載輔助函式（例：`pumpApp`）提供確定的起始前提：注入一個流程會完成的替身（讓狀態經真實路徑落到穩定狀態），或直接注入穩定狀態；呼叫端已 override 同一 provider 時不重複注入
- 修輔助函式一處即可涵蓋所有呼叫端，之後新增的測試也不會再踩到

## 預防措施

- 改 provider 預設值前，盤點範圍要包含所有經共用掛載函式間接建構該畫面的測試：以 `grep -l "pumpApp(" test/` 之類列出全部呼叫端，而不是只看檔名或主題相關的檔
- 盤點時先在 worktree 暫改預設值、跑上述全部呼叫端，紅燈清單才算完整
- 外框用 `IndexedStack`（或其他保活容器）時，任何頁面的預設狀態都會影響全 App 測試，應視為共用前提

## 實例

一個 Flutter 桌面 App 為了讓啟動首幀不再閃出假資料，把 Domain 視圖的預設狀態由靜態矩陣改為「載入中」。前置票只盤點了 Domain 視圖與外框相關的測試，改成明確注入後全綠；實作票的合併閘門卻在破洞報告、節點詳情、Ticket 清單三個測試檔各紅 1 至 2 則，全是 `pumpAndSettle timed out`。分析後確認：這些測試以 `pumpApp` 掛載整個 App，用真實的工作區還原流程（在 fake async 中不會完成），Domain 頁停在載入中、shimmer 持續播放。修法為在 `pumpApp` 提供確定的起始前提。
