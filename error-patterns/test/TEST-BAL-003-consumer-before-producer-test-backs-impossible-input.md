# TEST-BAL-003: 消費端先於生產端落地，測試以 production 不可能產生的輸入為其背書

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 高 |
| 發現時機 | 一次「文案批次修正」票的事後多視角審查，Good Taste 視角在回答無關問題時附帶命中 |
| 發現日期 | 2026-08-18 |

## 症狀

- 某段比對／驗證邏輯有完整實作、有錯誤訊息、有測試覆蓋且測試全綠，但在 production 從未執行過一次
- 該邏輯的入口守衛（如 `if not data: continue`）恆為真，後續程式碼是不可達路徑——不是罕見路徑，是不可能路徑
- 後續維護者持續投入成本潤飾這段程式碼的訊息文字、補測試斷言，而這些訊息沒有任何使用者能收到
- 靜態掃描與測試覆蓋率工具皆無告警：該段確實「被測試執行到」，只是執行它的輸入是測試自己造的

## 根因

分階段建置中，資料的**消費端先於生產端落地**：schema 契約已宣告某欄位，讀取端據此實作了比對邏輯，但寫入端排在後續階段尚未實作。此時該欄位在 production 恆為初始空值。

單有這一層還不足以致命——真正使缺口不可見的是第二層：**測試為了驗證該邏輯，手工建構了一個該欄位非空的輸入**。這個輸入在 production 目前不存在任何產生路徑，等於測試構造了一個 production 生不出來的世界，然後在那個世界裡驗證了行為正確。

兩層疊加的後果是訊號反轉：測試綠燈本應提示「這段是活的」，實際上它掩蓋了「這段從未活過」。維護者讀到綠燈測試與完整實作，合理推論該功能運作中，於是把成本投入在改善它的細節上。

與既有模式的分界：

| 模式 | 機制 | 分界 |
|------|------|------|
| TEST-BAL-002 | 測試替身走簡化建構路徑，繞過 production 裝配步驟 | production 路徑**存在**，測試走了簡化版，盲區是兩者的差集 |
| PC-165 | 修復鏈假陽性，unit test 綠燈遮蔽 runtime 失效 | 功能**曾經或應該**有真實輸入，斷言強度不足 |
| 本模式 | 生產端尚未實作，測試憑空造出輸入 | production 路徑**不存在**，測試驗證的行為在現實中無法觸發 |

**案例狀態註記**：下方案例描述的 registry `files` 欄位，其生產端寫入路徑已於後續落地為推導物化值（claim 時重算，非獨立累積狀態）。本則記錄的是落地前「零 append 命中」的狀態；查程式碼確認該欄位現有寫入端，不代表本模式失效——本則描述的是分階段建置期間的暫態，同類缺口在其他欄位仍可能重現。

## 解決方案

發現此模式時，處置按根本性排序，順序不可換：

1. **先標註測試的虛構性質。** 在該測試類別／函式的 docstring 明記：其輸入在生產端落地前無 production 產生路徑，落地後轉為真實覆蓋，並引用承載生產端工作的追蹤項目。不加這行，下一位維護者會重新花一次確認「這段活不活」的成本。
2. **再為生產端缺口綁 trigger。** 「留待後續階段」這類敘述本身即無 trigger 延後（違反 decision-trigger-binding 規則 1）。建立追蹤項目承載二選一——實作生產端，或移除消費端邏輯——並讓消費端的註解引用該項目。
3. **最後才碰訊息文字，而且是等生產端落地之後。** 生產端未落地前修改該段的使用者訊息，是對不可達程式碼的重複 churn；更關鍵的是，訊息中的操作指引（「請重跑 X」）是否正確，取決於尚未定案的生產端設計——此刻改動有相當機率改錯，落地後反而要再改一次。

**不刪除消費端邏輯的判準**：若 schema 契約明文列有該欄位、且明文記載寫入邏輯屬後續階段，則此為分階段建置的正常中間態（建置順序倒置但非虛構）。刪除會丟失一份邏輯正確的比對器，生產端落地時需原樣重寫。問題不在程式碼存在，在沒有任何地方記錄它處於休眠、而測試把它呈現為活的。

## 預防措施

| 時機 | 檢查 |
|------|------|
| 為某欄位撰寫比對／驗證邏輯前 | 先確認該欄位有寫入路徑：grep 該欄位的 append／assign，而非只看 schema 宣告或初始化 |
| 為該邏輯撰寫測試時 | 若測資須手工建構出 production 尚無法產生的形狀，測試 docstring 必須明記此事並綁追蹤項目 |
| 審查「文案／訊息改善」類變更時 | 先問該訊息在 production 是否可達；不可達則變更本身即為浪費，且可能複製它要修的病 |
| 撰寫 schema 契約時 | 「留待後續階段」須綁追蹤項目，不得作為無 trigger 的延後敘述 |

**自動化可行性**：入口守衛恆真的偵測難以完全機械化（需資料流分析），但「某欄位只有讀取端無寫入端」可以近似檢查——對 schema 宣告的欄位掃描 append／assign 命中數，零命中即告警。此為可選的 hook 方向，非本模式的必要防護。

## 案例

一套 ticket 追蹤系統的多執行者協調層，其 session registry schema 契約列有 `files` 欄位，衝突偵測命令據此實作了 registry 與票面宣告的交叉比對並輸出不一致警告。但 registry 的註冊函式僅初始化 `"files": []`，其餘 5 處寫入點全為保留既有值的 merge 語意，無任何一處 append——該欄位恆為空，比對器入口 `if not registry_files: continue` 永遠 continue。

該狀態持續期間，一張後續票進一步為這條不可達警告補上操作指引「請校正票面宣告或重跑 claim」，並新增測試驗證該指引存在——該測試手工建構了 `files` 非空的 registry。事後審查發現時，該指引所述的「重跑 claim 會寫入 registry」尚未定案為設計，指引本身指向一個不存在的機制。

審查者的判語點出了本模式最反直覺的一面：該次修正動作本身複製了它要修的病——它潤飾了一句沒人能收到的訊息，並補了一個斷言虛構輸入的測試。

## 附帶觀察：本模式為何難以靠審查發現

發現它的審查者當時被問的是三個與此無關的問題（旗標去留、常數抽取、清查完整性）。它在驗證「這條警告訊息該不該改文案」時，才追到訊息所在的整段邏輯不可達。

這說明本模式的偵測難點不在技術，在**提問方向**：所有針對訊息內容、測試斷言、文案品質的審查提問，都預設了「這段程式碼會執行」。只有當審查者主動退一步問「這段在 production 跑得到嗎」，模式才會浮現。把這個問題加進防護類與驗證類標的的審查清單，比任何自動化都有效。
