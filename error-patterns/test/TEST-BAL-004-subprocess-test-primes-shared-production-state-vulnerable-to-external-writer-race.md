# TEST-BAL-004: 測試以寫入 production 共享狀態達成前置條件，遭外部行程競態使前置失效

## 症狀

- 全套件執行時偶發 1 個測試失敗，單獨重跑該測試必定通過
- 失敗訊息本身無明顯異常（非斷言邏輯錯誤），紅燈容易被歸類為「環境雜訊」而略過，不會被追查
- 命中機率低（實測單次 run 命中率介於 0.35%-4.9% 之間），連續數次取樣可能全綠，但全綠不代表缺陷不存在——依 PC-168，N < 5 的連續 GREEN 可能只是幸運連勝，不可據此判定非 flaky

## 根因

三項特徵疊加，缺一則不成立本模式：

1. **前置條件靠寫檔達成，而非依賴注入**。測試以 subprocess 呼叫受測程式，無法在被測行程內 monkeypatch 內部狀態，只能改為在測試開始前寫入一個 production 也會讀寫的共享檔案，以此模擬前置條件。這個做法本身把「測試隔離」讓渡給「共享可變狀態」。
2. **該共享檔案的路徑硬編於 production 原始碼的相對位置**（如 `Path(__file__).parent.parent`），在 import 時求值，不受測試慣用的專案根目錄覆寫變數（如 `CLAUDE_PROJECT_DIR`）影響。測試以為自己操作的是隔離的測試環境，實際上寫入的是與其他行程共用的同一份 production 檔案。
3. **競態窗口寬度隨機器負載放大**。單獨執行測試時，寫入與讀取之間的窗口很短；全套件執行時其他測試/hook 佔用資源使排程延遲增加，窗口隨之放大，因此全套件執行比單獨執行更容易命中外部寫入者的競態覆蓋。

三者疊加的結果：測試自以為建立了確定的前置條件，實際上該前置條件有一個測試不可控、不可預期的第二寫入者（production 自身的正常運作路徑），第二寫入者在窗口內覆寫測試剛寫入的值，使前置條件失效。

## 解決方案

- **移除共享寫檔作為前置條件的做法，改用依賴注入或行程內可控的替身**。若受測邏輯必須以 subprocess 呼叫（例如驗證 CLI 對外行為），前置狀態應注入到該 subprocess 專屬、與其他行程不共享的路徑，而非 production 共用檔案。
- **檢查路徑解析是否在 import 時對硬編相對位置求值**。若讀寫路徑用 `Path(__file__).parent.parent` 等相對於原始碼位置的寫法，會忽略測試環境的專案根目錄覆寫變數，使測試永遠操作到真實 production 路徑。應改為函式內動態解析（呼叫時才求值，而非模組層常數），並讓覆寫變數（如 `CLAUDE_PROJECT_DIR`）生效。
- **窗口寬度會隨負載波動，用時序注入而非重跑取樣驗證假說**。單獨重跑通過不能否證 flaky；若懷疑本模式，應以決定性方式在受控時序下重現（見下方案例的實驗設計），而非反覆執行等待巧合命中。

## 預防措施

| 時機 | 檢查 |
|------|------|
| 撰寫 subprocess 測試需要前置狀態時 | 問「這個前置狀態是否寫入了 production 也會讀寫的檔案？」是則優先改依賴注入或行程專屬路徑 |
| 測試涉及路徑解析且看到 `Path(__file__).parent...` | 確認該路徑是否在 import 時求值、是否受專案根目錄覆寫變數影響 |
| 遇到「全套件失敗、單獨重跑通過」的紅燈 | 不可直接歸類為環境雜訊；依 PC-168 要求 N >= 5 取樣並記錄 GREEN/RED 分佈，取樣全綠不等於非 flaky |
| 審查測試前置條件的建立方式 | 檢查該前置條件是否有測試不可控的第二寫入者（其他行程、排程任務、hook） |

## 案例

一個 hook 測試（`test_language_guard`）在全套件執行時偶發 1 個失敗、單獨重跑必定通過。查庫排除既有 pattern 後判定為新模式：PC-168 談的是取樣判讀方法，非共享狀態機制；PC-BAL-001 談的是建立端與驗證端清單漂移，非行程競態；TEST-BAL-002/003 談的是測試替身/消費端形狀問題，非 production 狀態污染。

以下數字為決定性重現實驗量測所得，非估算：

- 易損窗寬度介於 0.108-2.503 秒之間；外部寫入者（另一 production 排程行程）約每 146 秒寫入一次計數器檔案
- 決定性時序注入實驗：對照組（不注入外部寫入）3/3 通過（stderr 382 bytes）；注入組（於易損窗內強制觸發外部寫入）3/3 重現症狀（stderr 0 bytes），確認因果
- 測試單獨執行時的易損窗為 0.565 秒，全套件執行時放大至 7.191 秒，相差 12.7 倍，驗證「根因三」（窗口隨負載放大）

修復方案：計數器檔案路徑由模組層常數改為函式 `_get_sampling_counter_file()`，呼叫時才動態解析專案根目錄（`get_project_root()`），使 `CLAUDE_PROJECT_DIR` 得以在測試環境生效，消除路徑硬編問題（對應「解決方案」第二點；commit `dd704c4b`）。

同型硬編路徑另於 `install-guide-edit-reminder-hook.py` 發現，顯示本模式非單一檔案的孤立事件，凡是路徑解析寫法相同的 hook 皆應排查。
