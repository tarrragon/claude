# TEST-SCLK-001：快取化建置使「無 X」類驗收成為空訊號

## 症狀

驗收條件形如「編譯零警告」「無 lint 錯誤」「無型別錯誤」。執行建置指令，退出碼 0、輸出中確實沒有任何警告，驗收判定通過。

但該輪建置走增量模式，目標檔案因快取命中**完全沒有被重新編譯**。警告缺席反映的是「編譯器沒跑」，不是「跑了而沒有問題」。驗收條件在字面上成立，在語意上是空的。

**本案具體樣態**（1.4.0-W3-007 Swift 重構驗收）：

- ticket acceptance 含「Swift 編譯警告須為零」。
- 實作者與獨立驗收者各跑一次 `scripts/run-tests.sh`（內含 `xcodebuild test`），測試 179 + 57 全綠、輸出無新增警告，兩人皆判定通過。
- 驗收者追查建置日誌後發現：該輪 xcodebuild **零個 SwiftCompile 任務**，只有 CodeSign / Plist / Register 等步驟，Swift 源碼一行都沒重編。
- 驗收者另以獨立 `-derivedDataPath` 執行全新 `build-for-testing` 強制全量重編，才取得真正的警告清單，確認「本次修改檔零新增警告」為真。

結論本身正確，但若無這一步，通過的依據是空的。

## 根因

**驗證「無 X」與驗證「有 Y」的證據結構不對稱。** 「測試通過」是正向訊號——輸出中出現 `179 passed` 才算數，過程沒跑就沒有這行。「零警告」是負向訊號——輸出中什麼都沒有即判定成立，而「什麼都沒有」同時對應兩種不同的世界：檢查跑了且乾淨、檢查根本沒跑。

建置工具的增量最佳化正是刻意讓後者頻繁發生。開發者日常受益於此（不必重編未改動的檔案），驗收時卻繼承了同一個預設，且沒有任何輸出提示「本輪未編譯目標檔」。

與 TEST-BAL-001 同構：該案是 validator 抽取回空集後把「沒東西可檢查」讀成「沒有不符」；本案是建置未執行後把「沒有輸出警告」讀成「沒有警告」。兩者都是**訊號缺席被讀成訊號良好**。

## 解決方案

1. **確認產生訊號的過程真的執行過**：查建置日誌是否含目標語言的編譯任務（本案為 `SwiftCompile`），或確認編譯的檔案數非零。
2. **強制全量重建再驗**：用獨立的 derived data / build 目錄執行乾淨建置，代價是時間，換得證據不空。
3. **驗收後清理**：本案的 scratch derived data 為 692 MB，驗證完即刪除，不留在工作區。

## 預防措施

| 情境 | 動作 |
|------|------|
| acceptance 含「零警告 / 無錯誤 / 無 X」 | 該條的驗證步驟必須包含「確認產生 X 的過程已執行」，不可只看輸出無 X |
| 用建置或編譯結果作驗收依據 | 檢查日誌中編譯任務數非零；為零時該輪結果不構成證據 |
| 撰寫此類 acceptance | 條件寫成可證偽形式：「全新建置下目標檔案編譯警告為零」優於「編譯零警告」，前者把前提寫進條件本身 |
| 任何負向驗收條件 | 套用判準：這個「沒有」是觀察到的，還是沒觀察？呼應 tool-output-trust 規則 3，用固定值（編譯檔數、抽取計數）交叉驗證過程真的發生 |

**一般化**：所有負向驗收條件（無警告、無洩漏、無重複、無殘留）都應附帶「掃描確實覆蓋了目標」的證據。掃描範圍為空時的輸出，與掃描範圍完整且乾淨時的輸出，在字面上無法區分。
