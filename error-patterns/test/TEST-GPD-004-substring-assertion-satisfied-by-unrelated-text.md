# TEST-GPD-004: 守衛測試以自由文字子字串斷言決策，被輸出中的無關文字滿足而在決策未發生時仍綠

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 分類 | test |
| 來源版本 | 0.5.0 |
| 來源事件 | 完成閘門補辨識完成命令別名後，正向對照測試宣稱「被擋」，實地觸發顯示該情境實際放行 |
| 首次觀測 | 2026-10-14 |

## 症狀

守衛（PreToolUse hook）的輸出是一段 JSON，其中有結構化的決策欄位（`hookSpecificOutput.permissionDecision`：`allow` 或 `deny`），另有大量自由文字（檢查清單、警告、建議命令）。測試為了證明「某輸入被擋」，寫成：

```python
assert "deny" in out or "block" in out.lower(), out
```

修正前（守衛完全略過該命令）測試為紅，修正後轉綠，看起來像合格的正向對照。實地觸發同一情境，守衛日誌卻是 `should_block=False`、決策為 `allow`：該情境（驗收未勾選）在這支守衛本來就只出警告，從未被擋。測試能轉綠，是因為修正後守衛進入完整檢查，輸出的自由文字裡碰巧出現了 `block` 字樣（如 `blockedBy`、`blocking`）。

## 根因

1. **斷言觀察的是伴隨文字，不是決策本身**。決策有專屬的結構化欄位，自由文字只是說明；子字串比對會被任何含相同字母的說明滿足，無法區分「決策為 deny」與「說明中提到 block」。
2. **紅綠翻轉證明的是另一件事**。修正前守衛直接略過、輸出極短，修正後守衛跑完整檢查、輸出變長。測試的翻轉反映的是「有沒有進入完整檢查」，被誤讀為「有沒有被擋」。
3. **測試情境的前提沒有查證**。作者假設「驗收未勾選會被擋」，沒有對照守衛的阻擋條件清單；斷言寬鬆使這個錯誤前提無從暴露。

## 解決方案

1. 斷言解析結構化輸出，比對決策欄位：`json.loads(out)["hookSpecificOutput"]["permissionDecision"] == "deny"`。
2. 選用守衛真正會阻擋的條件作為情境（先讀守衛中設定阻擋旗標的分支，確認條件屬阻擋而非警告）。
3. 重跑 E2：移除被測修正後，新斷言必須轉紅。

## 預防措施

| 層級 | 措施 |
|------|------|
| 撰寫測試 | 被測對象有結構化決策欄位時，斷言一律比對該欄位；看到 `"<詞>" in out` 形式斷言決策，即視為鑑別力不足 |
| 驗收 | 守衛類修正除單元測試外附實地觸發：在真實環境餵入同一情境，以守衛日誌的決策值對照測試宣稱 |
| 與既有規則的關係 | 補充 `test-assertion-design-rules` 的 E2（守衛測試須含正向對照）：E2 要求有一個該紅的輸入，本模式要求斷言觀察的是決策本身，兩者缺一，正向對照都可能是假的 |
