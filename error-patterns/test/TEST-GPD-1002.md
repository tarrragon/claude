# TEST-GPD-1002: 以實測觀察到的結構形狀寫成斷言，比規格嚴且把疑似缺陷鎖成測試要求

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 分類 | test |
| 來源版本 | 0.5.0 |
| 來源事件 | 驗收要求「原因文字與按鈕在同一語意區塊」，實作者實測發現兩者與區塊解析到同一個語意節點，遂斷言三者節點 id 相等；同一觀察顯示按鈕可能失去自身語意節點，而規格要求按鈕有獨立節點 |
| 首次觀測 | 2026-10-29 |

## 症狀

- 規格只要求一個關係（同區、相鄰、包含），測試卻斷言一個具體形狀（同一節點、特定深度、精確子樹）
- 該形狀是實作者在當下實作上實測得到的，不是規格推導出來的
- 實測形狀本身可疑（與規格的另一條要求衝突），但測試把它固定為通過條件
- 日後修正該可疑之處時，這支測試會轉紅，修正者需先判斷「是修壞了還是測試錯了」

## 根因

撰寫斷言時，「規格要求的關係」與「當下觀察到的形狀」在實測結果中同時成立，實作者取了較具體、較好寫的那個。具體形狀蘊含關係，所以測試能證明驗收成立；但反方向不成立——關係成立時形狀未必成立。

後果是測試的鑑別方向錯置：它擋的不是「違反規格的變動」，而是「任何改變現況形狀的變動」，包括修正缺陷的變動。若實測形狀正是缺陷的表現，測試就成為缺陷的守護者。

與既有模式的分界：

| 模式 | 機制 | 分界 |
|------|------|------|
| TEST-BAL-005 | 斷言因輸出重疊而巧合成立，保護力不足 | 本模式保護力過度且方向錯，擋住合法變更 |
| TEST-GPD-002 | 斷言常數而非行為 | 本模式斷言的是行為，但斷言的粒度比規格細 |

## 解決方案

1. 回到驗收或規格條文，找出它要求的關係（同區、相鄰、包含、順序）
2. 把斷言改寫為該關係的判定，不論中間結構怎麼排列都能成立。例如以「沿父節點往上，必經過區塊容器」取代「節點 id 相等」
3. 以同一個判定函式做正向對照：構造關係不成立的結構，斷言判定為否
4. 實測形狀若與規格其他條文衝突，另建分析票追查，不在測試中固定它

## 預防措施

- 審查測試時問：「這個斷言是規格要求的，還是實測看到的？」後者需說明為何規格要求到這個粒度
- 實作者回報「實測發現 X」並據此斷言時，審查者要再問：X 有沒有違反任何規格條文
- 驗收條文寫成關係（「同一區塊或相鄰」）時，測試的斷言應能涵蓋條文中的每一個允許形態

## 案例

一次停用按鈕的修正，驗收要求原因文字與按鈕在同一語意區塊或朗讀順序相鄰。實作者以語意測試工具實測，發現原因文字、按鈕與區塊容器解析到同一個語意節點（區塊為 live region 容器），於是斷言三者節點 id 相等。審查時發現：同一觀察暗示按鈕失去了自身的語意節點，而規格要求按鈕節點帶 button 角色；若之後修正讓按鈕取得獨立節點，這支測試會轉紅擋住修正。斷言改為祖先鏈判定（訊息節點與按鈕節點沿父節點往上都經過區塊容器），並另建分析票追查按鈕節點是否被併入。

**後續查證**：分析票以語意樹傾印實測，按鈕其實有獨立節點（帶 button 角色、未併入父節點）。三者解析到同一個 id，是因為 `getSemantics` 回傳的是 finder 對應元件往上第一個擁有語意節點的祖先，按鈕的 key 掛在不擁有節點的包裝元件上。也就是說，被寫進斷言的「結構形狀」本身是取法造成的假象。這讓本模式的風險更明確：觀察到的形狀未必是實際結構，以它為斷言，鎖住的可能根本不存在。判定結構前先傾印語意樹，並逐層列出祖先鏈。

**反方向的修正**：修正後節點分離，原斷言改寫為「訊息與按鈕的最近共同祖先存在」。但任兩個節點必有共同祖先；傾印顯示該祖先是全畫面容器（往上到根節點每層都是全畫面），按鈕移到畫面任何位置都會通過，斷言從比規格嚴變成比規格鬆。最後改以「朗讀順序中兩者之間沒有具名節點」判定，並以插入中間節點的對照輸入證明會轉紅。兩次失誤的共同根因：沒有先問「規格要求的關係，在什麼輸入下應該不成立」，再確認斷言在那個輸入下會轉紅。

**對照輸入本身也要傾印確認**：第一版對照輸入用零尺寸的 `Semantics(label)` 當中間節點，該節點被語意樹丟掉，對照組照樣全綠，看起來像斷言通過。改用 `Text` 並傾印確認節點存在後，對照才有效。對照輸入是否真的構成「不成立」的結構，也要以傾印驗證，不能只看測試程式碼。
