# ARCH-BAL-021：撞號的版本號使分叉看似已同步，偵測到分叉的警告不阻擋寫入

## 基本資訊

| 欄位 | 值 |
|------|-----|
| 風險等級 | 高 |
| 來源 | 跨 session 框架資產同步任務（2026-09-03） |
| 發現日期 | 2026-09-03 |

## 摘要

**單調遞增的版本號無法表達分叉：兩個消費者各自從同一基準前進一步，會產生兩個號碼相同而內容不同的版本。** 表層訊號（版本號相等）指向「已同步」，實際狀態是「各自演化」，方向完全相反。同步工具即使偵測得到分叉，其警告若不阻擋寫入，覆蓋照樣發生——偵測與防護是兩件事，有前者不蘊含有後者。

危險之處在於兩層訊號同時失效且失效方向一致：人工掃版本號看到相等而放行，工具印出警告而不擋，兩者都不會使操作中止。

## 症狀

- 兩份同名資產的版本號相同，內容 diff 卻有實質差異
- 同步工具印出「both sides changed independently」「conflict」類警告，但操作仍成功完成
- 上游交接訊息說「直接 pull 即可」，而該指令會刪除本地獨有內容——交接方並非疏忽，是他無從得知對方也動過同一檔案
- 覆蓋後版本號「前進」了（或維持不變），版本歷史外觀正常，被刪的內容不出現在任何 diff 中
- 單向 diff（只看 `grep '^>'` 或只看 `grep '^<'`）判讀不出問題：「被對方改寫掉的舊版」與「對方沒有的真實工作」在單向輸出下同形

## 根因

1. **版本號是計數器不是雜湊**。它編碼「前進了幾步」，不編碼「從哪裡前進、走向何方」。分叉需要至少兩個維度才能表達，一維計數器結構上做不到。
2. **內容雜湊只證明兩份不同，不證明誰較新**。這是同步工具的已知限制（例如 `skill-sync` 的 SKILL.md 明文寫了版本字串只顯示不比較），但該限制的推論——「所以號碼相同不代表內容相同」——不會自動出現在讀者腦中。
3. **警告的設計目的是提示而非攔截**。非阻擋式警告在有 `--force` 的路徑上等於無防護；而批次同步場景幾乎必然帶 `--force`（互動提示會中斷自動化）。
4. **交接方的視野只有自己那半邊**。上游能看到「我改了什麼」，看不到「你也改了什麼」，故其給出的操作指令天然缺一半資訊。

## 防護

| 層級 | 做法 |
|------|------|
| 判定方向 | 不採同步工具的方向報告（它可能讀衍生索引如 `versions.json`，落後實際 git 樹）；改 clone 上游後逐檔**雙向** diff。單向 diff 對本情境無鑑別力 |
| 撞號處置 | 以上游為共用時間軸：保留上游該版本號的條目，本地那筆順延一號，合併後推回上游。禁止任一方單向覆蓋 |
| 版本註記 | 順延時在 CHANGELOG 註明撞號事實與順延理由，否則下一位讀者會把跳號讀成漏記 |
| 交接語言 | 跨 session 交接同步任務時，不寫「執行 `pull X`」，改寫「X 已更新，方向請自行雙向驗證」——指令形式的交接把驗證責任隱含地轉移掉了 |

## 邊界

- 與 `ARCH-BAL-008`（覆寫共用覆蓋層刪除他方獨有內容）機制相鄰但不同：該筆的表層訊號是「版本號前進」掩蓋內容缺失，本筆是「版本號相等」掩蓋分叉存在，且本筆額外涵蓋「偵測存在但不阻擋」這一層。
- 與 `ARCH-BAL-007`（非唯一識別符當主鍵致集合去重丟資料）共享「識別符不足以區辨」的根因，但後果路徑不同：該筆是自動去重靜默丟棄，本筆是人工判讀被誤導後主動覆蓋。
- 工具的分叉警告與人工的內容 diff **輸入不同源**，兩者結論一致構成有效交叉驗證，不屬 `PC-GPD-002` 所述的共享方法共振。

## 實例

跨 session 框架同步（2026-09-03）：對方推上 canonical 的 `foundation-design` 標 6.1.0，本地亦有一筆獨立的 6.1.0——雙方各自從 6.0.0 前進一步。對方的交接訊息給的是 `skill-sync pull foundation-design`，執行之會靜默刪除本地的「非 SaaS 專案適用條件欄與三維度處置段」。改以雙向 diff 判定後合併，本地那筆順延為 6.2.0 推回上游。`skill-sync push` 的 `.skill-sync-base` 三點定位確實獨立印出了 `both sides changed independently since last sync`，但屬 WARNING、不阻擋，`--force` 照樣覆蓋。
