# ARCH-BAL-012：第二份實作重新推導第一份刻意迴避的假設

## 基本資訊

- **Pattern ID**: ARCH-BAL-012
- **分類**: 架構設計（architecture）
- **來源版本**: v0.2.1
- **發現日期**: 2026-07-31
- **風險等級**: 高（第二份實作在生產環境完全不生效，但測試全綠且無任何告警路徑）
- **影響範圍**: 任何在既有元件旁新增第二個元件、而兩者需要對同一個外部結構（路徑命名、協定欄位、識別符格式）達成一致認知的情境

## 摘要

**既有實作為了避開某個外部規則的不確定性，刻意採用不需知道該規則的寬鬆寫法；新增的第二份實作為了另一個用途，重新推導了那個規則，並且推錯。**

第一份實作的「不假設」是深思熟慮的結果，但這個決策只存在於程式碼形態中，沒有被表述為約束。第二份實作的作者看到的是一個「已解決的問題」，而不是「一個被刻意繞開的坑」，於是在需要更精確的答案時，自行補上了第一份刻意不提供的那部分。

失效模式的關鍵在於它是靜默的：推導錯誤的結果通常是「查一個不存在的位置」，而查不到在多數設計中是合法狀態（等同「沒有東西」），因此不走任何錯誤路徑。第二份實作於是持續執行、持續什麼都不做，而它宣稱要封閉的缺口完全敞開。

## 症狀

- 新增的元件在生產環境從未產生任何作用，但它每次都被觸發、每次都正常返回
- 該元件的測試全綠，且新增測試也照樣綠
- 對照組（既有元件）行為正確，兩者處理的明明是同一件事
- 缺陷的定位需要人工比對「推導出的值」與「環境中的真實值」，沒有任何自動化管道會提示兩者不符
- 事後檢視，既有元件的寫法明顯更保守，但當時沒有任何文件說明它為何保守

## 根因

三個機制疊加，缺一即不成立：

**機制一：迴避決策未被表述。** 第一份實作用寬鬆比對（萬用字元、正則的 `[^/]+`、欄位存在性檢查）取代精確推導，這是為了不對外部規則作假設。但形態本身不會說話——程式碼看起來只是「一個比對」，沒有任何註解或型別說明「此處刻意不推導 X，因為 X 的規則不在我們控制範圍內」。

**機制二：第二份實作的用途誘導精確化。** 第一份要回答的是判定問題（輸入一個值，回答是否屬於某集合），寬鬆比對足夠。第二份要回答的是定位問題（不給輸入，產出一個具體位置），寬鬆比對表面上不適用，作者因此認為必須推導。實際上定位問題也可以用列舉（掃描候選集合）迴避推導，但這條路只有在意識到「推導有風險」時才會被考慮。

**機制三：測試把唯一有風險的函式替換掉。** 為了讓測試不依賴真實環境，測試以替身取代了推導函式。剩下被測的部分是標準庫行為（目錄存在嗎、集合是空的嗎），那些不會錯。推導邏輯——整個元件裡唯一與外部環境耦合、唯一可能錯的部分——因此零覆蓋。測試數量與通過率都很漂亮，有效覆蓋是零。

三者的共振結果：錯誤產生（機制二）、無人攔截（機制一）、無法被發現（機制三）。

## 解決方案

### 結構調整

**優先序一：讓第二份實作也不推導。** 定位問題同樣可以用列舉迴避——掃描候選集合並過濾，而非計算出唯一答案。這使兩份實作對外部規則的假設量都降為零，不需共用程式碼也不會漂移。

**優先序二：若必須推導，抽為單一來源並獨立測試。** 把外部結構知識收斂到一個模組，兩份實作各取所需（判定器與定位器可以是不同函式，但共用底層結構定義）。抽取後推導邏輯自然獲得直接測試。

**優先序三：把迴避決策寫成文字。** 第一份實作的 docstring 應明載「此處刻意不推導 X」及其理由，使後續維護者看到的是約束而非空白。

### 驗證方式

對推導結果與環境真實值做一次固定值比對，且該比對必須是測試的一部分而非一次性人工檢查：

- 取環境中的真實值（列出實際存在的位置、讀取實際的協定回應）
- 以生產環境的輸入執行推導
- 斷言兩者一致

此測試不得使用替身。若因環境依賴而無法在 CI 執行，應標記為需顯式觸發的測試，而非改用替身讓它「能跑」。

## 預防措施

- 新增元件時，若它與既有元件需要對同一外部結構達成一致認知，先讀既有元件如何處理該結構，並問「它為什麼用這種寫法」
- 既有元件用了明顯保守的寫法（萬用字元、寬鬆比對、不假設格式）時，預設它是刻意的，在有相反證據前不要精確化
- 撰寫測試時，逐一檢視被替身取代的函式：若某函式是整個元件中唯一與外部環境耦合的部分，替換它等於放棄測試這個元件
- 判斷標準：移除所有替身後，這些測試還在驗證什麼？若答案是「標準庫行為」，則有效覆蓋為零
- 元件的失效模式若是「查不到 = 靜默返回」，該元件必須有一個會因定位錯誤而紅燈的測試，否則失效與正常運作在外部無法區分

## 實證案例

### 事件：memory 目錄稽核 hook 生產環境零生效（0.2.1-W3-092）

框架排除某個平台原生儲存作為知識載體，既有 PreToolUse 守衛以正則 `projects/[^/]+/memory/` 比對路徑，**刻意不推導平台的目錄命名規則**——它只需回答「這個路徑是不是 memory 位置」，萬用字元足夠。

新增的 PostToolUse 稽核 hook 需要回答「本專案的 memory 目錄在哪」，作者因此推導了目錄名稱：取專案路徑，把路徑分隔符換成連字號。

實際的平台規則同時替換分隔符、底線與句點。專案路徑含底線，推導結果與真實目錄不符：

| 項目 | 值 |
|------|-----|
| 推導 | `-Users-...-project-flutter_balance` |
| 真實 | `-Users-...-project-flutter-balance` |

`isdir` 恆為 False，hook 每次觸發皆走「目錄不存在」分支直接返回。它宣稱封閉的繞道缺口完全未封閉，而 ticket 記錄為已封閉。

測試方面，九個測試中有四處以替身取代推導函式。剩餘被測內容為「目錄存在時回傳真、不存在時回傳假」——標準庫行為。推導邏輯零覆蓋，因此全綠。

發現管道是 Phase 4 多視角審查中三個獨立視角（品味審查、冗餘審查、複雜度審查）各自指出同一點，而非任何自動化機制。

### 事後可機械檢查的訊號

- 同一提交中新增的元件，與既有元件對同一外部結構有兩份不同形態的認知
- 新元件的測試對其唯一環境耦合函式使用替身
- 新元件的所有分支中，「什麼都不做」是最常走的那條
