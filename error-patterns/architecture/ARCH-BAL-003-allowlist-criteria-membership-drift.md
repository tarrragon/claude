# ARCH-BAL-003: 白名單自訂納入判準但成員未同步，判準與名單脫節

## 摘要

**白名單在註解或文件中明文定義了納入判準，但新增符合判準的物件時沒有機制提醒同步名單，判準與成員逐漸脫節。** 脫節的白名單對外仍表現為「有原則的設計」——判準寫得越清楚，讀者越傾向相信名單完整，越不會去逐項比對。結果是符合判準卻不在名單內的物件被機制擋住，而使用者因為看到判準合理而不質疑名單，改為繞道；繞道行為本身可能製造新的資料污染。

脫節的暴露方式取決於名單語意。名單語意為准入時，漏列會擋住合格物件而以撞牆暴露；語意為防護涵蓋範圍時，漏列使防護靜默不作用，缺席與正常運作在輸出上完全相同，偵測成本因此高得多（見下方症狀變體）。

## 症狀

- 某個物件明明符合白名單註解寫的納入條件，卻仍被機制拒絕
- 使用者的第一反應是「找繞過方式」而非「檢查名單是否遺漏」——因為判準看起來合理，名單看起來就像刻意排除
- 繞道方式帶來原機制要防的副作用（借用他人識別碼、停用檢查、降級為手動流程）
- 以判準逐項掃描候選集合時，發現符合判準但不在名單內的物件不只一個

### 症狀變體：名單用於「該保護誰」而非「該放行誰」（0.2.1-W3-160 實證）

白名單語意為准入時，漏列會撞牆而暴露（上列症狀）。**名單語意為「防護涵蓋範圍」時，漏列不撞牆——防護只是靜默不作用**，缺席與正常運作在輸出上完全相同：

- 某個本該受防護的物件持續處於未防護狀態，無錯誤訊息也無告警
- 缺口只在該物件實際受害後、且有人回頭查為何防護沒攔下時才暴露
- 名單同時存在漏列與冗列（冗列項已不在實際集合中），顯示兩側從未被比對過

實證：`uv-tool-ownership-guard-hook` 的 `SKILLS` 常數列七項，卻漏列實際安裝的 `skill-sync`、冗列已不在安裝集合的 `branch-worktree-guardian`。`skill-sync` 的全域 slot 因此長期由他專案副本佔用而無告警，本專案對其原始碼的修改全數不生效（機制詳見 `ARCH-APP-002`）。此缺陷為持續存在的問題，清單校準需主動執行。

**判別提問**（兩步，第一步定偵測成本，第二步定該走哪份 pattern）：

1. 這份名單漏列一項時，會有人撞牆嗎？答案為否時，偵測成本從「等使用者回報」升為「須主動定期比對」，必須有 CI 或 hook 層的雙側比對。
2. 這份名單是人工維護還是程式產生？人工維護走本 pattern 的定期比對；程式產生走 `ARCH-BAL-010` 的結構調整（把必要欄位換成恆可計算者）。對人工名單套用結構調整無效，因為判準是人寫的宣告，不參與執行。

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 判準是宣告 | 判準寫在註解或文件，不參與執行 | 判準與名單分屬兩個平面，只靠人工維持一致 |
| 名單是執行 | 機制實際只讀名單成員 | 名單缺項即行為缺項，判準寫得再完整也不影響執行 |
| 新增物件的路徑不經過名單 | 建立新物件（新 agent、新檔案類型、新路徑）時，作者不知道有這個白名單存在 | 脫節單向累積，不會自我修正 |
| 脫節只在撞牆時暴露 | 沒有定期比對，沒有 CI 檢查 | 每次暴露都是一次繞道行為的成本 |

**與「清單過度限制」（ARCH-016）的差別**：ARCH-016 的清單沒有明文判準，撞牆時要重新論證該不該放行，爭點在判斷本身。本 pattern 的判準已經寫好且無爭議，爭點在「符合判準的物件沒被寫進名單」——是同步缺失，不是判斷缺失。這個差別決定了防護手段不同：ARCH-016 需要的是決策準則，本 pattern 需要的是機械比對。

## 案例：agent 豁免白名單漏收唯讀常駐審查委員（2026-07-26）

`agent-ticket-validation-hook.py` 的 `TICKET_EXEMPT_AGENT_TYPES` 用註解定義納入判準：「agent 工具僅含唯讀，用途為情報蒐集、文件查詢、分析規劃，不會產生持久化副作用者可豁免 Ticket ID 要求」。名單有 5 個成員。

掃描全部 agent 定義的 `tools:` 欄位，符合該判準的純唯讀 agent 共 5 個（`basil-writing-critic` / `linux` / `incident-responder` / `oregano-data-miner` / `sumac-system-engineer`），其中在名單內的是 0 個。判準與名單的交集為空。

後果鏈：PM 要派 `basil-writing-critic` 做文字品質審查 → hook 回 deny 要求 Ticket ID → PM 未察覺名單遺漏，改為借用一張尚未派發的實作票 ID → agent 依協議 claim 該票 → 該票 `who.current` 被回填為審查 agent，狀態仍是 pending → PM 若未察覺會誤判該票已派發。原本防「變更無法追溯」的機制，反而製造了「指派狀態被污染」。

分析與落地已完成，並追蹤為 error-pattern。

## 防護

| 層 | 措施 |
|----|------|
| 設計層 | 判準若可機械判定（讀欄位、比對副檔名、查工具清單），優先讓機制直接執行判準而非維護名單——名單只作為判準的例外覆寫層 |
| 檢查層 | 判準無法機械化時，加一個定期比對：以判準掃描候選集合，列出符合判準但不在名單內的物件。可掛 SessionStart hook 或 CI |
| 註解層 | 名單旁註明「新增符合判準的物件時應同步此處」，並寫出候選集合的位置（例如 `.claude/agents/` 全目錄），讓後人知道去哪裡掃 |
| 使用層 | 被白名單機制擋住時，先以判準自查是否遺漏，再考慮繞道；判斷為遺漏就修名單，不要繞 |

**判準機械化的取捨**：把判準改為執行（動態分類）可根除脫節，但也讓行為依賴被掃描物件的欄位正確性——欄位寫錯即靜默放行。名單長度小時維持靜態名單加定期比對成本更低；名單成長到需要頻繁同步時才值得改動態。本案例的 hook 註解已自訂升級點（名單長度超過 10 或誤用率升高時改自動分類），此類升級 trigger 應在名單建立時就寫下，不要等脫節暴露才補。

## 與其他 pattern 的邊界

| Pattern | 聚焦 | 差異 |
|---------|------|------|
| ARCH-016（Hook 允許清單過度限制） | 清單無明文判準，撞牆時需重新論證該不該放行 | 本 pattern 判準已明確且無爭議，缺的是成員同步 |
| IMP-BAL-003（稽核器與消費端解析器嚴格度落差） | 兩個解析器對同一資料的嚴格度不同，稽核全綠但消費端失敗 | 同屬「宣告層與執行層脫節」家族；該 pattern 的兩層都在執行，本 pattern 是宣告層根本不執行 |
| PC-V1-002（Ticket ID 引用觸發 agent 越權） | agent 把 ID 引用誤解為指派 | 本案例是其上游成因：白名單缺項使 PM 無合規出口，被迫製造誤解條件 |
| ARCH-BAL-010（可選欄位的解析成敗決定記錄是否存在） | 索引由程式產生，缺漏來自寫入條件耦合可選欄位，每次重建都重現同一缺漏 | 兩者症狀同形（缺席與正常運作輸出相同），分野在缺漏的產生機制：本 pattern 的名單由人工維護、缺漏來自未同步，故只能靠週期性雙側比對縮短暴露時間；該 pattern 的缺漏可在資料結構層根除（必要欄位換成恆可計算者），對人工名單套用該處方無效 |

## 驗證方式

修正名單後：

- 以判準重新掃描候選集合，確認「符合判準但不在名單內」的集合為空，或每個剩餘項有明文的排除理由
- 反向確認冗列：名單中每一項都在實際集合內，冗列項須移除或附保留理由。漏列與冗列並存代表兩側從未被比對過，只驗一側會留下另一半
- 新增回歸測試同時覆蓋放行案例與邊界案例（不符判準者仍被擋）
- 名單註解記錄當前長度與升級 trigger，讓下次擴充時看得到餘量
