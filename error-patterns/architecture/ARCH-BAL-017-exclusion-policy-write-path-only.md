# ARCH-BAL-017: 排除政策只在寫入路徑生效，報告路徑對其零知識

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | medium |
| 發現途徑 | ANA 根因分析（skill 庫檢查誤報排查） |
| 復發次數 | 一次（首次記錄） |

## 摘要

**一份排除清單（哪些項目不該進遠端）常只在「會產生副作用」的路徑（push、複製、傳播）生效，因為那是清單被制定時唯一想防的傷害。之後新增的唯讀報告路徑（分類、比對、統計）與寫入路徑各自獨立實作，作者在寫報告路徑時只問「這個項目和遠端狀態的關係是什麼」，不會回頭問「這個項目是否根本不該和遠端比較」——因為排除政策這個維度在報告路徑的心智模型裡從未存在。**

結果是唯讀路徑對排除清單完全零知識：不是讀取了過期的清單，而是介面上從未開過接收清單的入口。報告因此把「設計上不該有遠端記錄」的項目，誤判為「有問題需要處理的缺口」，每次執行都復發同一個誤報，且誤報的建議動作（推送 / 補齊 / 同步）若被使用者依言執行，會把刻意排除的內容送上遠端——這是唯讀報告路徑產生的唯一實害。

## 症狀

- 同一批項目在寫入路徑（push/sync/apply）被正確排除，但在報告路徑（status/diff/list）被列為「缺失」「待處理」「無記錄」
- 報告訊息的措辭是「需確認」「需補齊」而非「設計如此」——顯示分類器對該項目的例外狀態一無所知，只能給出一般性建議
- 排除清單本身讀取正確（可用其他測試證明清單載入無誤），問題不在清單，在消費清單的函式簽名沒有對應參數
- 公開/共用入口函式（如 `xxx_status_report(dir)`）的簽名裡找不到任何排除、忽略、豁免類參數，呼叫端即使想傳也無處可傳
- 每次執行報告都復發同一批誤報，形成「已知噪音」——使用者學會忽略含這批名稱的那幾行，連帶降低對其餘真實訊號的警覺

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 排除清單誕生於寫入場景 | 制定清單時要防的傷害是「寫入了不該寫的內容」 | 清單的讀取點只接在寫入路徑上 |
| 報告路徑後於寫入路徑新增 | 新增報告功能時參照的是「如何取得與比對資料」，不是「哪些資料不該比對」 | 排除政策這個維度未進入報告路徑的介面設計 |
| 公開入口收攏了取檔與分類，唯獨沒收攏排除 | 介面重構常以「消除重複」為目標，重複的是取檔與分類邏輯，排除邏輯本就只有一份（在寫入側），不會被同一次重構觸及 | 收攏後的介面依然沒有排除政策參數，且看起來像已經是「單一入口」而不會再被檢視 |
| 兩個判斷各自正確 | 寫入路徑「排除此項目」正確；報告路徑「此項目和遠端狀態不同」也正確（單看報告路徑的問題定義） | 誤報不是任何一段程式碼的邏輯錯誤，而是兩段程式碼對「這個項目算不算需要處理」有不同、卻都各自自洽的定義 |

**與單純「清單過期」的差別**：清單過期是清單本身失準，重新產生或同步即可修復。本 pattern 的清單從未過期——清單本身正確，是消費清單的另一條路徑從未讀過它，屬於「一個宣告載體，多條路徑各自決定要不要理會」的家族（可對照 `ARCH-BAL-002` 識別符雙載體只讀一側），但本 pattern 更窄：不是兩個載體各讀一側，而是同一個載體只有一側讀。

## 案例：skill 庫檢查將 private skill 誤列為遠端無記錄

### 事件鏈

1. 專案建立 `private` 排除清單，語意為「這個 skill 進本地 repo 但不推送到框架 repo」，讀取者是 push 路徑的 overlay 複製與 `--clean` 傳播兩處
2. 之後新增一段獨立於 push 目標 repo 的「skill 發佈庫檢查」，比對本地 skill 與另一個遠端（skill 發佈庫）的內容雜湊，向使用者回報一致 / 分歧 / 遠端無記錄等分類
3. 該檢查段的分類函式從實作第一版起就只有三種判斷依據：本地客製標記檔、遠端 manifest 是否有此 key、雜湊是否相符——從未讀過 `private` 清單，因為寫這段程式碼時參照的心智模型是「本地與遠端的資料關係」，不是「這個 skill 該不該被推送」
4. 公開入口函式的簽名同樣沒有任何排除參數，即使呼叫端想傳排除清單也無處可傳
5. private skill 因此在遠端 manifest 中確實找不到記錄（設計如此），被分類為「遠端無記錄，需確認遠端是否該有此 skill 後 push」，每次執行收尾都復發
6. 誤報的建議動作若被依言執行（把該 skill push 上發佈庫），會直接違反建立 `private` 清單時的原始意圖——唯讀報告路徑因此產生了寫入路徑等級的實害

### 驗證

以 `inspect.signature` 印出分類函式與其公開入口的簽名，確認排除清單無參數可傳：

```
_classify_sync_status 簽名 = (local_manifest, remote_manifest, skills_dir) -> tuple[...]
sync_status_report 簽名    = (skills_dir, repo_url=None) -> SyncStatus
```

兩者均無任何排除、忽略、豁免類參數。同時驗證清單本身載入正確（`load_sync_skills_config()` 回傳含目標 skill 的 `private` 清單），排除誤報成因為「清單過期」的可能，鎖定為「消費清單的介面缺口」。

## 防護

| 時機 | 動作 |
|------|------|
| 新增排除 / 過濾 / 豁免類清單時 | 明確列出所有會消費「此項目是否算數」這個判斷的路徑（寫入、報告、統計、告警），逐一確認排除清單的讀取點是否涵蓋每一條路徑，而非只涵蓋建立清單當下要防的那一條 |
| 新增報告 / 統計 / 診斷類路徑時 | 檢查同一批資料是否已存在其他路徑的排除 / 過濾邏輯；若有，公開入口的簽名必須開放接收該政策，即使本路徑當下不主動讀取 |
| 收攏重複邏輯到單一公開入口時 | 收攏範圍的檢查清單需包含「取檔」「分類」「排除政策」三個維度分別確認，不能因為取檔與分類已收攏就視為整條流程已完整收攏 |
| 報告訊息措辭為「需確認」「需處理」時 | 反問：此項目是否有已知的設計例外（客製標記、排除清單、豁免宣告）？若有相關清單存在於程式庫的其他角落，本路徑是否讀取了它 |
| 誤報的建議動作具破壞性（會產生寫入副作用）時 | 優先級提升——唯讀路徑的誤報不只是噪音，而是可能誘導使用者手動觸發原本要防止的寫入 |
