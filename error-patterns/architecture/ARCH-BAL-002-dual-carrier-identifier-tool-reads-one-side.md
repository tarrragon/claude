# ARCH-BAL-002: 識別符雙載體但工具只讀一側，修復動錯側使驗收假通過

## 症狀

- 同一識別符同時存在於兩個載體（frontmatter 欄位與檔名、常數與設定檔、DB 欄位與程式碼列舉），兩側可獨立編輯
- 出現重號、查不到、配號器發出已被佔用的號碼等症狀
- 修復只改了「人看得到的那側」（如 frontmatter `id:`），驗收項（如「重號清除」）看似達成，但工具行為完全沒變——查詢仍找不到、配號器仍發重號
- 症狀在下一次操作復發，且復發時看起來像新問題

## 根因

工具的解析邏輯只讀單一側（實證：`doc query` 以檔名 stem 解析、`_next_id` 以檔名 stem 掃描已用號），另一側對工具不可見。當兩側不同步時：

- **配號器盲區**：工具看不見已佔用的號碼，必然重複發號——重號不是偶發疏失，是結構性產出
- **修復動錯側**：人依直覺改「宣告 ID 的地方」（frontmatter），但工具讀的是檔名；改完後人工檢查（看 frontmatter）通過、工具行為不變
- **驗收假通過**：驗收條目若寫成「重號清除」而非「工具可唯一解析」，改錯側也能勾選

深層成因：命名慣例（檔名帶 ID 前綴）只存在於文件約定，無工具強制。慣例無強制力時，新檔案各自發明格式，工具盲區隨檔案數線性擴大。

## 解決方案

- **修復前先確認工具實際讀哪一側**：讀原始碼（解析函式、掃描函式）而非依直覺，兩側都改才算完成
- **驗收條目寫成工具可觀測的行為**，不寫成人可觀測的狀態：用「`doc query <id>` 對兩份皆可唯一解析」「`next-id` 回傳正確下一號」取代「重號已清除」
- **慣例轉工具強制**：產生端預設輸出合規格式，並加驗證器偵測不合規的既有檔案（opinionated-default-design 主張 1：預設行為勝過文件規範）

## 預防措施

- 設計識別符系統時避免雙載體；不可避免時（檔名需人類可讀 + frontmatter 需結構化）明定哪一側為工具權威，並讓另一側由工具產生或驗證
- Code review 訊號：看到「慣例上檔名應包含 X」這類文件敘述而無對應驗證器 → 該慣例遲早失效
- 修復重號類問題時先問：「工具是怎麼知道號碼被佔用的？」——答案指向的載體才是必須修的那側
