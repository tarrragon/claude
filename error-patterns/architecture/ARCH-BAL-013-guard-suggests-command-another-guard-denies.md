# ARCH-BAL-013：防護元件之間的互斥指示

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | medium |
| 發現途徑 | 文字品質審查（阻擋訊息的可執行性檢查） |
| 復發次數 | 四次（`0.2.1-W3-282` 修一處後 `W3-285` 發現同型殘留為同批兩例；`0.2.1-W3-303` 為另一 ticket 家族的獨立第三例；2026-09-01 的派發骨架案為自指變體的第四例） |

## 症狀

防護元件 A 阻擋操作時，訊息附上「修復方式」；執行者照抄該命令，卻被防護元件 B 阻擋。執行者收到兩則互相矛盾的阻擋訊息，無從判斷何者為準，最終學會繞過整條防護鏈。

**實證表**：

| # | A 的建議 | B 的阻擋 |
|---|---------|---------|
| 1 | 清理提醒建議 `git add -A` 後不帶 pathspec 的 `git commit` | 並行期的裸 commit 守衛對無 pathspec 的 commit 一律拒絕 |
| 2 | 清理提醒先印「強制移除將遺失修改內容」，緊接建議 `git worktree remove --force` | 同批新增的 dirty 守衛對任何未提交變更阻擋 remove |
| 3 | `sync-claude-push.py` 偵測到孤兒後提示「請重跑：`sync-push --clean`」 | no-change early-exit 僅檢查 `user_message` 與 `--force`，未把 `--clean` 納入跳過條件，判定 hash 未變、無新 commit 而 abort；須再加 `--force` 才能完成刪除傳播 |
| 4 | `agent-prompt-length-guard-hook` 的阻擋訊息在「為什麼阻止」段附上 `ticket track dispatch {ticket_id} --as {agent_name}` 作為修復方式 | **同一個 hook**：該命令產出的骨架為 39 行（`where.files` 觸及 hooks 目錄的 ticket 因附加區塊而為 47-48 行），超過自身 `PROMPT_LINE_LIMIT = 30`，其硬上限檢查（該 hook 註解稱 Layer 1）無豁免直接 exit 2 |

**實例 4 為自指變體，擴展本模式的邊界**：前三例皆為「防護 A 建議 → 防護 B 阻擋」的跨元件互撞，實例 4 中建議者與阻擋者是同一個元件——hook 建議執行的命令，其產出被該 hook 自己的規則拒絕。

此變體的偵測門檻遠低於跨元件情形：不需通盤掃描其他防護的訊息常數，只需把自己的建議餵給自己一次。門檻雖低，該缺陷仍潛伏至消費專案實際派發受阻才被發現（成因見「根因」節）。

自指變體另有一項專屬後果：**篩選方向顛倒**。走正規 CLI 者被擋、手寫短 prompt 者放行，而後者同時靜默略過該 prompt 本應攜帶的其他強制條款。

實例 2 尤其明顯：同一段訊息先警告會遺失，再建議執行造成遺失的命令。實例 3 與前兩例不同源：early-exit 守衛與孤兒提醒分屬不同開發批次（W3-075 vs 孤兒偵測機制），驗證此模式不限「同批新增防護互撞」，跨批、跨功能的守衛也會落入同一結構性風險。

## 根因

**新增防護時只驗證自己的阻擋條件，未回頭掃描既有訊息中的處置建議是否落入自己的阻擋範圍。** 防護元件各自獨立測試（自己的阻擋條件正確、自己的訊息文字通順），沒有任何一層測試涵蓋「A 的建議命令拿去餵給 B 會怎樣」。

放大成因：

- 阻擋訊息屬於「文字」，習慣上由撰寫者一次寫成後不再回訪，不像程式碼有呼叫關係可追蹤
- 訊息中的命令是字串常數，靜態檢查與型別系統都看不出它是「將被另一個元件檢驗的輸入」
- 新防護的作者通常只讀自己要改的檔案，不會通盤讀其他防護的訊息常數

**自指變體（實例 4）的補充根因**：建議者與阻擋者為同一元件時，上述「未回頭掃描其他防護」不成立——該情形不需跨元件掃描即可發現。其成因改為：命令的產出方與判定方分屬不同維護面（CLI 側的骨架常數與 hook 側的上限常數），而兩側測試各自只驗自己的維度。缺陷被發現當時 `test_agent_prompt_length_guard_hook.py` 全程綠燈，因其只斷言 `has_template_keywords` 的字串偵測行為，未比對骨架行數與 `PROMPT_LINE_LIMIT`；該行數綁定測試已於修復時補上。

## 解決方案

1. **新增防護後，掃描所有既有防護訊息中的命令建議**，逐一比對是否落入新防護的阻擋範圍；命中即同步修正。
2. **把「訊息中的命令不得被自己的規則拒絕」寫成迴歸斷言**：對每個阻擋訊息，斷言其建議命令不含自己已知會拒絕的樣式（本案已對裸 `cd` 與無 pathspec commit 各加一條）。
3. **警告與建議必須同向**：訊息先陳述某操作會造成損失時，其修復方式不得包含該操作；若該操作在特定前提下仍合法，必須明寫前提。

## 預防措施

| 情境 | 動作 |
|------|------|
| 新增任何阻擋型防護 | 提交前 grep 全部防護元件的訊息常數，比對建議命令是否觸發新規則 |
| 撰寫阻擋訊息的「修復方式」 | 每條建議命令逐字寫完整，並確認它能通過現行所有防護 |
| 訊息同時含警告與建議 | 檢查兩者方向一致——警告 X 有害時，建議中不得出現 X |
| 修正一處互斥指示 | 同批掃清同型，不只修被指出的那一處（本案即因未掃清而在同批復發） |
| 阻擋訊息建議的命令由本系統自己產出 | 加一項測試直接斷言「該命令的實際產出通過本防護的判定」，把兩個維護面綁在同一條斷言上；只驗各自維度會讓產出長期漂移而不紅燈（實例 4） |

## 一般化

不限於 hook 之間。任何「錯誤訊息附帶修復指令」的系統——CLI 的 usage 提示、API 的 error response、lint 的 autofix 建議——只要系統中存在多個獨立的檢驗層，就有同一風險。判準是：**訊息中的指令是否會再次進入本系統的檢驗？** 會，就必須把該指令當作受檢輸入來測試，而不是當作說明文字。

### 三個切面：示範性內容未經它所屬的檢驗

本模式的上位形態不限「阻擋訊息」。凡是**使用者會照抄的示範性內容**，以字串常數存在、型別上合法，而「照抄後的產物」這一層沒有型別可檢查，測試驗的是程式行為而非資料，就不會有測試去執行它。2026-09-03 由兩個 consumer 對照出三個切面（`tarrragon/claude#79`）：

| 切面 | 示範性內容 | 未經誰驗證 | 發現途徑 |
|------|-----------|-----------|---------|
| 本筆四例 | guard 阻擋訊息給的處置指令 | 其他 guard（或自己） | 把建議命令餵給防護鏈 |
| hook 訊息內嵌範例 | `needs-context` 類 hook 訊息中的 yaml 範例 | 該 hook 自己的解析器 | 驗收時直接餵給解析器（測試綠燈不覆蓋此項） |
| SKILL.md 範例 | `ticket create --parent "<id>" --action ... --target ...` 建票範例 | 該 skill 自己的 `enforce_checklist` | 逐字執行：缺四個必填欄位即被擋下，形態正確、有輸入有輸出，通過「是否為完整成品」的分類判準卻不可用 |

第三切面的後果與前兩者同：讀者照抄後撞牆，且撞牆時先懷疑自己而非文件。三者的共同發現途徑只有一種——**把示範內容直接餵給它所屬的解析器或檢查**；靜態審查與單元測試對這一層皆無涵蓋。可機械化：對文件中每個示範命令做 dry-run，對每個內嵌結構化範例跑所屬解析器。
