# ARCH-BAL-013：防護元件之間的互斥指示

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | medium |
| 發現途徑 | 文字品質審查（阻擋訊息的可執行性檢查） |
| 復發次數 | 三次（`0.2.1-W3-282` 修一處後 `W3-285` 發現同型殘留為同批兩例；`0.2.1-W3-303` 為另一 ticket 家族的獨立第三例） |

## 症狀

防護元件 A 阻擋操作時，訊息附上「修復方式」；執行者照抄該命令，卻被防護元件 B 阻擋。執行者收到兩則互相矛盾的阻擋訊息，無從判斷何者為準，最終學會繞過整條防護鏈。

**實證表**：

| # | A 的建議 | B 的阻擋 |
|---|---------|---------|
| 1 | 清理提醒建議 `git add -A` 後不帶 pathspec 的 `git commit` | 並行期的裸 commit 守衛對無 pathspec 的 commit 一律拒絕 |
| 2 | 清理提醒先印「強制移除將遺失修改內容」，緊接建議 `git worktree remove --force` | 同批新增的 dirty 守衛對任何未提交變更阻擋 remove |
| 3 | `sync-claude-push.py` 偵測到孤兒後提示「請重跑：`sync-push --clean`」 | no-change early-exit 僅檢查 `user_message` 與 `--force`，未把 `--clean` 納入跳過條件，判定 hash 未變、無新 commit 而 abort；須再加 `--force` 才能完成刪除傳播 |

實例 2 尤其明顯：同一段訊息先警告會遺失，再建議執行造成遺失的命令。實例 3 與前兩例不同源：early-exit 守衛與孤兒提醒分屬不同開發批次（W3-075 vs 孤兒偵測機制），驗證此模式不限「同批新增防護互撞」，跨批、跨功能的守衛也會落入同一結構性風險。

## 根因

**新增防護時只驗證自己的阻擋條件，未回頭掃描既有訊息中的處置建議是否落入自己的阻擋範圍。** 防護元件各自獨立測試（自己的阻擋條件正確、自己的訊息文字通順），沒有任何一層測試涵蓋「A 的建議命令拿去餵給 B 會怎樣」。

放大成因：

- 阻擋訊息屬於「文字」，習慣上由撰寫者一次寫成後不再回訪，不像程式碼有呼叫關係可追蹤
- 訊息中的命令是字串常數，靜態檢查與型別系統都看不出它是「將被另一個元件檢驗的輸入」
- 新防護的作者通常只讀自己要改的檔案，不會通盤讀其他防護的訊息常數

## 解決方案

1. **新增防護後，掃描所有既有防護訊息中的命令建議**，逐一比對是否落入新防護的阻擋範圍；命中即同步修正。
2. **把「訊息中的命令不得被自己的規則拒絕」寫成迴歸斷言**：對每個阻擋訊息，斷言其建議命令不含自己已知會拒絕的樣式（本案已對裸 `cd` 與無 pathspec commit 各加一條）。
3. **警告與建議必須同向**：訊息先陳述某操作會造成損失時，其修復方式不得包含該操作；若該操作在特定前提下仍合法，必須明寫前提。

## 預防措施

| 情境 | 動作 |
|------|------|
| 新增任何阻擋型防護 | 提交前 grep 全部防護元件的訊息常數，比對建議命令是否觸發新規則 |
| 撰寫阻擋訊息的「修復方式」 | 每條建議命令逐字寫完整，並確認它能通過現行所有防護 |
| 訊息同時含警告與建議 | 檢查兩者方向一致——警告 X 有害時，建議中不得出現 X |
| 修正一處互斥指示 | 同批掃清同型，不只修被指出的那一處（本案即因未掃清而在同批復發） |

## 一般化

不限於 hook 之間。任何「錯誤訊息附帶修復指令」的系統——CLI 的 usage 提示、API 的 error response、lint 的 autofix 建議——只要系統中存在多個獨立的檢驗層，就有同一風險。判準是：**訊息中的指令是否會再次進入本系統的檢驗？** 會，就必須把該指令當作受檢輸入來測試，而不是當作說明文字。
