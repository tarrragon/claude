# ARCH-BAL-019: 改變共享狀態的機制使依賴該狀態的其他機制靜默失效

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 高 |
| 首次發現 | 2026-08-21 |
| 來源版本 | v0.2.1 |
| 適用範圍 | 任何有多個讀取者的共享狀態：日誌檔案、索引、快取、資料庫 schema、版控 index、設定檔格式、目錄結構。改動者與讀取者分屬不同模組、不同載體（程式碼 vs 文件）、或不同時間時風險最高 |
| 關聯 | `ARCH-BAL-014`（因果方向相反：該模式是下游本已有缺陷、上游修復使其首次暴露；本模式是下游本來正確、上游改變使其失效）、`PC-165`（綠燈不等於正確，本模式為其在跨機制邊界上的表現） |

## 摘要

**一個機制改變了某項共享狀態後，所有讀取該狀態的其他機制都成為它的隱式下游，而這種依賴通常沒有被聲明。** 上游的改動經過完整測試、行為正確、達成目的；下游的程式碼一行未改，卻因為它依賴的前提消失而開始產出錯誤結果。

失效是靜默的：下游仍然執行、仍然回傳、輸出格式仍然正常，只是內容不再對應現實。沒有例外、沒有紅燈、沒有錯誤訊息——**唯一的異常是答案錯了，而沒有人在對答案**。

## 症狀

| 症狀 | 觀察點 |
|------|--------|
| 某項改動落地後，一個未被修改的模組開始產出可疑數值 | 該模組的輸出與獨立量測不符 |
| 診斷工具在改動後回報「無資料」「無記錄」「零命中」，而該資料實際存在 | 手動查證資料來源 |
| 統計數字在改動後出現數量級跳動，但業務量未變 | 對照歷史趨勢 |
| 驗證某項改動的工具，其判準本身依賴被該改動變更的狀態 | 檢視驗證工具的輸入來源 |
| 所有測試通過、所有檢查綠燈，但實際行為與預期不符 | 端到端實測 |

## 根因

**三層結構共振**：

1. **共享狀態沒有所有權**。日誌目錄、索引檔、快取、版控 index 這類狀態通常沒有明確的擁有者，任何模組都可讀、部分模組可寫。改動者無從得知讀取者是誰。

2. **依賴是隱式的**。下游不 import 上游、不呼叫上游的 API，只是讀同一份資料並對它的格式、分布、語意做出假設。這種依賴在型別系統、import 圖、測試覆蓋率中都不可見。

3. **下游的假設從未被寫下**。「每次觸發產生一個檔案」「這些資料涵蓋七天」「檔案存在代表最近被呼叫」——這些假設支撐著下游的推論，卻只存在於當初寫它的人的腦中。假設消失時沒有任何機制會注意到。

**放大因素**：上游的改動通常是修復或改善，本身正確且有測試背書。改動者的驗證範圍是「我改的東西行為對嗎」，而失效發生在「別人依賴我改的東西的方式」上——那不在任何人的驗證範圍內。

## 五個復現案例（同一時段內獨立發生）

| # | 上游改動 | 隱式下游 | 下游依賴的假設 | 失效表現 |
|---|---------|---------|--------------|---------|
| 1 | 設定檔的執行命令加上顯式解譯器前綴 | 健康監測器的檔名解析 | 命令字串的第一個 token 是腳本路徑 | 解析全數回傳空值，逐支存活偵測靜默停擺 |
| 2 | 日誌改為每日輪替 append | 頻率統計 | 每次觸發產生一個檔案 | 檔案數恆等於保留天數，觸發次數統計失真 |
| 3 | 日誌改為每日輪替 append | 診斷文件中的鑑別步驟 | 目錄有檔案代表最近被呼叫 | 對停止觸發的元件得出「最近有執行」的反向結論 |
| 4 | 一次性清理歷史資料 | 相對基線判定 | 資料涵蓋完整的基線窗口 | 分母坍縮，判定式恆真，全部對象報異常 |
| 5 | 提交流程改走隔離索引 | 共用索引 | 每次提交都會刷新共用索引 | 共用索引凍結成舊快照，任何走舊路徑的提交會回捲歷史 |

**第五例特別值得注意**：上游改動的目的正是修復另一個缺陷（並行提交的跨範圍污染），它成功了；而它的副作用製造了一個後果更嚴重的新缺陷——原缺陷造成歸屬錯置，新缺陷造成內容回捲。**防護機制的副作用可能比它防的問題更危險。**

另有一例為自指形態：觀測器把自己的告警輸出寫入日誌，而它的頻率統計以日誌行數為據，於是它的告警行為製造了它自己的告警條件。

## 偵測方式

改動任何共享狀態前，依序回答：

1. **誰在讀這個狀態？** 不只找 import 與呼叫關係——grep 該狀態的路徑、檔名樣態、欄位名，並涵蓋文件與註解中的診斷步驟（那些不會出現在任何依賴圖上）。
2. **他們對它做了什麼假設？** 格式、數量關係、時間語意、存在性語意。逐條寫下來。
3. **改動後哪些假設不再成立？** 對每條失效的假設，找出下游會產出什麼錯誤結論。
4. **那個錯誤結論看起來像正常輸出嗎？** 若是，該下游必須在同一次改動中一併處理，不可延後。

第 4 問是優先級判準：**會拋出例外的下游可以之後修，會靜默給出錯誤答案的下游必須同時修**。

## 處置

| 情境 | 動作 |
|------|------|
| 改動前 | 依偵測四問盤點下游，將受影響者納入同一次改動的範圍或同批 ticket |
| 已落地才發現 | 先判斷下游的錯誤輸出是否已被當成決策依據；若是，回溯依該輸出做出的決策 |
| 下游在文件而非程式碼中 | 同樣須改。文件中的診斷步驟是給人執行的程式，失效方式相同且更難察覺 |
| 驗證上游改動的工具本身是下游 | 不可用該工具驗證該改動。須另尋獨立管道，或先修下游再驗證 |

最後一列是本模式最危險的變體：**改變資料分布的操作，不可用依賴該分布的工具驗證其結果**。案例 1 與案例 4 皆屬此類——驗證遷移的監測器被遷移弄瞎、驗證清理的基線被清理破壞。

## 預防措施

- **共享狀態的格式或語意變更，視同 API 破壞性變更**。API 有型別系統與 import 圖可追蹤下游，共享狀態沒有，所以需要更嚴格的人工盤點而非更寬鬆。
- **下游的假設必須寫在讀取處**。讀取共享狀態的程式碼與文件，應在該處註明它假設了什麼（「此處假設每次觸發一個檔案」），使上游改動者 grep 得到。
- **靜默降級是本模式的傳播途徑**。讀取失敗時回傳空值、預設值、或零，會使失效表現為合法結論。共享狀態的讀取端應在「資料不符預期形態」時明確報錯，而非降級。
- **防護機制落地後，盤點它改變了什麼狀態**。防護的副作用不會出現在它的測試裡——測試驗證的是它擋住了該擋的，不是它沒有弄壞別的。
