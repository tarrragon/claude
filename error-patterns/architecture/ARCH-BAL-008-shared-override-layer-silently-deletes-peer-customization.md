# ARCH-BAL-008: 以單一消費者內容覆寫共用覆蓋層，靜默刪除其他消費者的獨有內容

## 摘要

**當某個資產同時存在「共用覆蓋層」與「各消費者本地層」，且覆蓋層優先級高於本地層時，把任一消費者的本地版複製到覆蓋層，會讓其他所有消費者的本地獨有內容失效。** 操作者看到的是「修好了我這邊的問題」，其他消費者看到的是「我的規則忽然不生效了」，而兩邊都不會察覺這是同一次操作造成的——覆蓋層的變更不出現在任何消費者的版本控制歷史裡。

危險之處在於這個操作看起來是收斂而非破壞。覆寫後所有消費者確實「版本一致」了，一致性指標變好，但一致的代價是把 N 份各自演化的內容壓成 1 份，其餘 N-1 份的差異部分無聲蒸發。

## 症狀

- 某消費者回報「這條規則明明寫在檔案裡，但執行時沒有生效」，而該檔案內容確實完好
- 檢查該消費者的本地檔案找不到問題，因為問題不在本地檔案而在它沒被載入
- 全域掃描某條獨有規則，發現它在全部副本中只存在於一處，而那一處正被覆蓋
- 覆寫操作的執行者所屬的消費者一切正常（覆寫來源就是他），故無人回報異常
- 版本號看起來是前進的（舊版被新版取代），掩蓋了「新版不含舊版某些內容」的事實

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 覆蓋層優先級高於本地層 | 平台為了讓使用者能全域覆寫而設計此優先序 | 覆蓋層的任何內容都會壓過所有消費者的本地版本 |
| 覆蓋層不在任何同步邊上 | 同步機制設計時只考慮本地層與中央倉庫兩端 | 覆蓋層的變更無版本控制、無審查、無痕跡 |
| 各消費者的本地層獨立演化 | 每個消費者依自身需求增修，彼此不知情 | 版本號非線性，高版本號未必包含低版本號的全部內容 |
| 覆寫以版本號為判準 | 操作者用「新版覆蓋舊版」的直覺決定方向 | 分支關係被誤判為落後關係，分支獨有內容被當成過時內容刪除 |
| 受害者與操作者不重疊 | 覆寫來源的消費者無感，其他消費者無從歸因 | 損害不會產生回饋訊號，可長期潛伏 |

**與 ARCH-V1-002（雙向覆蓋同步產生重複頂層定義）的差別**：ARCH-V1-002 的症狀是內容重複膨脹，本 pattern 的症狀是內容靜默消失，兩者是同一機制在不同方向上的失效。

**與 ARCH-BAL-003（白名單判準與成員脫節）的差別**：ARCH-BAL-003 是宣告與執行分屬兩平面而人工同步失敗；本 pattern 的宣告與執行在同一份檔案內，問題出在「哪一份檔案被載入」這個更上層的選擇。

## 案例：全域 skill 目錄覆寫使另一專案的獨有條文失效（2026-07-28）

Claude Code 的 skill 解析為同名覆蓋且 `~/.claude/skills/`（personal）優先於 `<project>/.claude/skills/`（project）。某次修復發現專案版 skill 未生效，處置方式是把該專案的版本 rsync 到 personal 目錄。

事後盤點：同一個 `wrap-decision` skill 存在 9 份副本（8 個專案各一份 + personal 一份），版本分佈為 2.2.0 / 2.3.0 / 2.5.0 / 2.6.0（四個專案共用）/ 2.7.0，rsync 後 personal 成為 2.7.0。

交叉檢查證明版本非線性：2.7.0 不含 2.5.0 的「基礎設施累積型」絆腳索條文（`grep -c` 為 0），2.5.0 亦不含 2.6.0 的「requirement-protocol 分工邊界」（`grep -c` 為 0），故 2.5.0 是分支而非落後。全域掃描確認該絆腳索條文在全部 9 份副本中僅存於一個專案的 SKILL.md 第 400 行。

後果：該專案的 project 版被 personal 2.7.0 遮蔽，其獨有條文在該專案不再生效。檔案未被刪除、內容完好、版本控制歷史無任何變更紀錄，唯一的變化是它不再被載入。修復方僅驗證了自己專案的 skill 恢復生效，未檢查其餘 7 個專案。

補充事實：中央倉庫的最後一次推送早於全部分歧演化，故 canonical 不持有任何一份分歧內容——分歧只在副本之間橫向累積，從未向中央收斂。覆蓋層之所以能造成損害，前提是收斂機制本已閒置。

## 防護

| 時機 | 動作 |
|------|------|
| 準備寫入共用覆蓋層前 | 先確認該層有幾個下游消費者。若大於 1，任何寫入都是對全部消費者生效，不是對自己生效 |
| 判斷覆寫方向前 | 用內容特徵字串交叉檢查而非版本號比大小。`grep -c <來源獨有特徵> <目標>` 與反向各一次，兩次都命中才是包含關係，否則是分支 |
| 發現本地版未生效時 | 先確認實際載入的是哪一份（多數工具會回報載入路徑），再決定是移除覆蓋層還是同步覆蓋層。移除通常成本更低且可逆 |
| 收斂分歧時 | 走中央倉庫的三方合併，不走消費者之間的直接複製。三方合併能保留各方新增，直接複製只能保留單方 |
| 設計此類架構時 | 共用覆蓋層維持空置為預設。確有跨消費者共用需求時，內容應存放於有版本控制與合併能力的中央層，由各消費者拉取 |

**判別提問**：「我要寫入的這個位置，有幾個東西會讀它？」答案大於 1 時，寫入行為的性質從「修改」變為「發佈」，須套用發佈的審查標準而非修改的隨手標準。
