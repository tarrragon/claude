# ARCH-LLM-001: CLI 結束碼語意改變，以子程序呼叫它且把非 0 當全失敗的消費端靜默退化

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | medium |
| 發現途徑 | 改 CLI 結束碼的變更在合併前，grep 該命令的子程序呼叫點時發現另一個 skill 的消費端 |
| 復發次數 | 一次（首次記錄），同族先例見 ARCH-BAL-023 |
| 來源版本 | v3.1.0 |

## 摘要

**CLI 的結束碼是它與子程序呼叫端之間的契約。把某個情境的結束碼由 0 改為非 0（例如「部分完成、輸出仍可用」改回降級碼）時，呼叫端若對 `returncode != 0` 一律走全失敗分支，就會把原本可用的輸出整份丟棄。兩端各自的測試都綠：CLI 端測試斷言新結束碼，呼叫端測試以 mock runner 寫死舊結束碼。**

退化不產生錯誤：呼叫端的全失敗分支本來就設計成「不阻擋、只記錄」，所以結果是靜默地少了資料，而不是報錯。

## 症狀

- CLI 變更的目的正確（讓呼叫者知道涵蓋不完整），審查只看 CLI 本身時找不出問題
- 呼叫端住在另一個 skill 或 hook，以 `subprocess.run([... , "<subcommand>", ...])` 呼叫，不 import CLI 的符號，靜態搜尋 import 找不到它
- 呼叫端對非 0 結束碼的處置是「轉為 error、回傳空結果、不阻擋」，所以退化後流程照跑，只是下游看到「查詢未完成」而非「部分完成」
- 呼叫端測試用假 runner 回傳固定的 `returncode`，CLI 結束碼改變不會讓這些測試翻紅

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 契約只寫在 CLI 端 | 結束碼語意記在 CLI 的 `--help` 與 skill 文件，呼叫端以自己的分支邏輯解讀 | CLI 端改語意時，沒有任何文件同時被兩端引用來提醒呼叫端 |
| 呼叫端二分「0／非 0」 | 「非 0 即失敗」在 CLI 只有成功與失敗兩態時成立 | CLI 新增「部分完成」第三態並用非 0 表達時，二分法把它歸錯類 |
| 子程序邊界隔開 import 圖 | 呼叫端刻意以子程序呼叫，避免載入期依賴另一個 skill | 「改了誰會受影響」的靜態工具（import 圖、codegraph callers）看不到這條邊 |
| 測試以 mock 固定結束碼 | 呼叫端測試的 fake runner 回傳寫死的 `returncode` | 兩端測試各自全綠，交界處沒有任何測試涵蓋 |

## 案例：dedup 結束碼改為降級碼

framework-issue 的 `dedup` 原本在有 token 查詢失敗而被略過時仍回 0，只在報告末行寫略過數。為了讓呼叫者不會把不完整的查重當成完整（tarrragon/claude#95），改為有略過時回 3（降級碼），報告照常完整輸出。

ticket skill 建票時以子程序呼叫 `dedup`，其執行器對 `returncode != 0` 一律回傳「查重未完成」並丟棄命中清單；原本 rc 0 時它會解析報告、保留命中並標記 partial。若照原樣合併，建票遇部分 token 失敗時，會從「partial、命中可用」退化為「全部失敗、命中丟失」，且不阻擋建票、不報錯。

合併前以 grep 子程序呼叫點（`section_comment.py dedup`）找到這個執行器，在同一變更內改為：rc 3 且 stdout 含報告末行時照舊解析為 partial，其餘非 0 仍走全失敗；並補「新結束碼 + 完整報告」、「新結束碼 + 無報告」、「其他非 0 + 有報告」三個對照測試。

## 解決方案

1. 改結束碼之前，以命令名與子命令字串 grep 全 repo 的子程序呼叫點（含其他 skill、hook、scripts），不只看 import
2. 對每個呼叫點讀它的非 0 分支：新結束碼落進哪個分支、該分支會不會丟掉仍可用的輸出
3. 結束碼契約與受影響的呼叫端在同一變更內調整；呼叫端以「結束碼 + 輸出可解析」兩個條件一起判定第三態，不單看結束碼
4. 呼叫端測試補新結束碼的案例，並對照「同結束碼但輸出不可解析」仍走失敗

## 預防措施

| 措施 | 層級 |
|------|------|
| 結束碼有三態以上時，CLI 文件明列每個結束碼代表的狀態與「輸出是否仍可用」 | 文件 |
| 改 CLI 行為時的同步檢查（`skill-cli-sync-check`）把「子程序呼叫點」列為與文件同級的同步對象 | 規則 |
| 呼叫端解析時以輸出結構為準、結束碼為輔；只有輸出不可解析時才視為全失敗 | 設計 |
| 呼叫端測試不只斷言 0 與單一非 0，涵蓋 CLI 已宣告的每個結束碼 | 測試 |
