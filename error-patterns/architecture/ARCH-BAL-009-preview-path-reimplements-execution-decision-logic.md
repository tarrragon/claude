# ARCH-BAL-009: 預覽路徑各自實作執行路徑的判定邏輯，兩者必然漂移使預覽閘門失效

## 症狀

工具提供不可逆操作前的預覽（dry-run、audit、confirm prompt），使用者依預覽結果決定是否執行。預覽輸出與實際執行結果不符——預覽說會刪 0 個而實際刪 3 個、預覽建議 minor 而實際做 patch、預覽列出的清單含實際不會動的項目。

典型表徵：

- 預覽與執行是兩個函式，各自走訪同一份資料並各自判定
- 執行路徑後來新增或修改了判定條件，預覽路徑未同步
- 預覽的輸出措辭是「建議」「預估」「將會」，使不符看起來像容許誤差而非缺陷
- 使用者依預覽下的決策（中止 / 放行 / 選擇版本）因此建立在錯誤資訊上

## 根因

**預覽的價值來自它等於執行，而「等於」若靠兩份程式碼各自維持，就沒有任何機制保證它成立。**

三個放大因素：

1. **預覽通常先寫、後續改動只碰執行路徑。** 加防護、加過濾、修判定時，改的是會產生實際後果的那一邊；預覽不動也「看起來正常」，因為它仍會輸出一份清單，只是清單錯了。錯誤不會以失敗形式出現。

2. **預覽的失效方向是靜默的。** 執行路徑判定錯會產生可觀察的後果（檔案被刪、版本跳號）；預覽判定錯只產生一段文字，而讀者無從對照。要發現它，必須同時取得預覽輸出與執行結果並逐項比對——這件事沒有人在日常流程中做。

3. **措辭吸收了落差。** 「建議」「預估」讓不符讀起來像設計上的近似。但使用者不是把它當近似——預覽存在的唯一理由就是讓人在不可逆操作前判斷，判斷需要的是準確而非近似。

## 影響

預覽不準時，該閘門實質上不存在，而使用者仍以為它存在——這比沒有預覽更危險。沒有預覽時使用者會謹慎；有錯誤預覽時使用者會依它放行。

方向決定嚴重度。預覽低報（說不會動而實際會動）直接導致未預期的破壞；預覽高報（說會動而實際不會）導致不必要的中止與對工具的不信任，長期使人繞過該閘門。

同一個 codebase 內若有多處預覽，它們通常各自漂移到不同程度——修好一處不代表其餘正確，且已修好的那處會讓人誤以為整類問題已處理。

## 解決方案

**預覽與執行共用同一判定函式**，而非各自實作。

| 手法 | 做法 |
|------|------|
| 抽出判定為純函式 | 判定邏輯（要不要排除 / 要不要刪 / 用哪個等級）抽為無副作用函式，預覽與執行皆呼叫它 |
| 走訪與動作分離 | 走訪資料並產出「將發生的動作清單」為一個函式；預覽印出該清單，執行套用該清單。兩者輸入同一清單，不可能不一致 |
| 共用不可行時交叉標註 | 若共用成本過高，在兩處各自註明「本判定須與 X 同步」並在測試中斷言兩者對同一輸入給出相同結果 |

**測試層**：對同一組輸入同時取預覽輸出與執行結果，斷言兩者一致。這是唯一能持續攔住漂移的手法——只測預覽或只測執行都不會發現不一致。

已發生不一致時，先確認漂移方向（低報或高報）再決定修法優先序：低報屬資料風險，高報屬信任風險。

## 預防措施

- 新增或修改執行路徑的判定條件時，先問「有沒有預覽也在判定同一件事」，有則同批修改
- 預覽輸出的措辭避免「建議」「預估」，除非它真的是近似；若它應等於執行結果，措辭就該是斷定式
- 程式碼審查訊號：一個檔案內出現 `def preview_*` 或 `def *_dry_run` 與對應的執行函式，且兩者各自走訪同一資料結構
- 判定邏輯（尤其是排除集合、閾值、版本規則）的消費點應可枚舉；枚舉時把預覽路徑一併列入，不因它「不改變世界」而略過
