# ARCH-BAL-020: 同名解析函式存在兩份且優先序相反，呼叫端無從得知拿到哪一份

同一個語意（「專案根目錄在哪」「設定檔在哪」「當前使用者是誰」）有兩份同名實作，各自的解析優先序相反，且兩者皆為合法設計——差異服務於不同情境。呼叫端以 `import` 決定拿到哪一份，而 import 語句不表達「我需要哪種優先序」，於是選擇由習慣、複製貼上或搜尋結果順序決定。

**Why**：兩份實作各自正確時，衝突不在任一份內部，而在**呼叫端的選擇無從驗證**。既沒有型別差異、也沒有名稱差異，選錯不會有任何靜態或執行期訊號——回傳值型別相同、多數情境下值也相同。差異只在特定情境（本案：於 git linked worktree 內執行）才顯現，而那正是最少被測試覆蓋的情境。

**Consequence**：

| 層級 | 影響 |
|------|------|
| 缺陷分佈 | 單一根因散射為多個看似不相干的症狀，各自被當獨立缺陷分析。本案 3 個獨立分析同時進行才收斂到同一根因 |
| 診斷成本 | 症狀之間無明顯關聯（測試讀錯資料 / log 寫錯位置 / 狀態檔多出副本），交叉比對前無人會把它們放在一起看 |
| 修復風險 | 「統一為其中一份」會回歸另一份所服務的情境。本案 `hook_base` 的 worktree 優先序本身是先前一張票的修正，直接統一會撤銷該修正 |
| 觀測 | 選錯的呼叫端在多數執行路徑下行為正確，只在特定情境失準——與「實作正確」在行為上不可區分 |

**Action**：

| 情境 | 做法 |
|------|------|
| 發現同名函式有兩份實作 | 先確認兩者的解析優先序是否相同。相同則屬單純重複（合併即可）；相反則屬本模式，合併會造成回歸 |
| 兩份皆為合法設計 | **改名使選擇顯性**——名稱表達優先序而非功能（如 `get_worktree_aware_root` / `get_env_anchored_root`），使 import 語句本身成為選擇的宣告 |
| 判斷既有呼叫端是否選對 | 問「這個呼叫端在 worktree（或其他分歧情境）內執行時，應該拿到哪一個根」。答不出來的呼叫端就是風險點 |
| 診斷多個症狀時 | 症狀分散於「讀到錯的資料 / 寫到錯的位置 / 產生非預期副本」三類且同時出現時，優先懷疑共用的路徑解析而非各自的邏輯 |

**識別訊號**：`grep -rn "def <name>" <lib-dir>` 命中多於一處；兩處 docstring 各自描述優先序且順序不同；codebase 中已有呼叫端附註解說明「刻意用這一份」（該註解即為前人踩過的痕跡，但註解不會傳播到新呼叫端）。

**邊界**：本模式針對**優先序相反**的同名實作。優先序相同的重複實作屬一般 DRY 問題，合併無回歸風險，不適用本模式的改名建議。與 `PC-BAL-001`（建立端與驗證端清單不同步）的差別：那是同一份資料的兩個副本漂移，本模式是兩份**行為規則**並存且各自正確。

**實證來源**：`.claude/lib/hook_base.py:97` 的 `_find_project_root()` 優先序為「worktree 感知 → `CLAUDE_PROJECT_DIR` → `git rev-parse`」；`.claude/lib/git_utils.py:308` 的 `get_project_root()` 優先序為「`CLAUDE_PROJECT_DIR` → `git rev-parse`」。前者 7 個呼叫端、後者 8 個。三個獨立分析各自定位到此處：

- 測試以 `monkeypatch.setenv` 設定 `CLAUDE_PROJECT_DIR` 隔離，但 pytest 於 worktree 內執行時該設定被無條件覆蓋，hook 讀到真實專案資料而非 fixture（5 個測試紅燈）
- 同一 hook 的狀態檔解析與 log 解析走不同實作，導致作用在主 repo、痕跡寫在 worktree，使問題在主 repo 側完全不可見
- worktree 內產生非預期的狀態檔副本

`hook_base` 的 worktree 優先序為先前一張票的刻意修正（避免 worktree 內的 hook 動作洩漏至主 repo），故三個分析皆選擇不動共用模組，改在各自呼叫端顯式指定——此為正確處置，但也顯示問題會持續複製到下一個呼叫端。
