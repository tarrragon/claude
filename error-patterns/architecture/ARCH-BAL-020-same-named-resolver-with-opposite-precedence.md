# ARCH-BAL-020: 同名解析函式存在兩份且優先序相反，呼叫端無從得知拿到哪一份

同一個語意（「專案根目錄在哪」「設定檔在哪」「當前使用者是誰」）有兩份同名實作，各自的解析優先序相反，且兩者皆為合法設計——差異服務於不同情境。呼叫端以 `import` 決定拿到哪一份，而 import 語句不表達「我需要哪種優先序」，於是選擇由習慣、複製貼上或搜尋結果順序決定。

**Why**：兩份實作各自正確時，衝突不在任一份內部，而在**呼叫端的選擇無從驗證**。既沒有型別差異、也沒有名稱差異，選錯不會有任何靜態或執行期訊號——回傳值型別相同、多數情境下值也相同。差異只在特定情境（本案：於 git linked worktree 內執行）才顯現，而那正是最少被測試覆蓋的情境。

**Consequence**：

| 層級 | 影響 |
|------|------|
| 缺陷分佈 | 單一根因散射為多個看似不相干的症狀，各自被當獨立缺陷分析。本案 3 個獨立分析同時進行才收斂到同一根因 |
| 診斷成本 | 症狀之間無明顯關聯（測試讀錯資料 / log 寫錯位置 / 狀態檔多出副本），交叉比對前無人會把它們放在一起看 |
| 修復風險 | 「統一為其中一份」會回歸另一份所服務的情境。本案 `hook_base` 的 worktree 優先序本身是先前一張票的修正，直接統一會撤銷該修正 |
| 觀測 | 選錯的呼叫端在多數執行路徑下行為正確，只在特定情境失準——與「實作正確」在行為上不可區分 |

**Action**：

| 情境 | 做法 |
|------|------|
| 發現同名函式有兩份實作 | 先確認兩者的解析優先序是否相同。相同則屬單純重複（合併即可）；相反則屬本模式，合併會造成回歸 |
| 兩份皆為合法設計 | **改名使選擇顯性**——名稱表達優先序而非功能（如 `get_worktree_aware_root` / `get_env_anchored_root`），使 import 語句本身成為選擇的宣告 |
| 判斷既有呼叫端是否選對 | 問「這個呼叫端在 worktree（或其他分歧情境）內執行時，應該拿到哪一個根」。答不出來的呼叫端就是風險點 |
| 診斷多個症狀時 | 症狀分散於「讀到錯的資料 / 寫到錯的位置 / 產生非預期副本」三類且同時出現時，優先懷疑共用的路徑解析而非各自的邏輯 |

**識別訊號**：`grep -rn "def <name>" <lib-dir>` 命中多於一處；兩處 docstring 各自描述優先序且順序不同；codebase 中已有呼叫端附註解說明「刻意用這一份」（該註解即為前人踩過的痕跡，但註解不會傳播到新呼叫端）。

**邊界**：本模式針對**優先序相反**的同名實作。優先序相同的重複實作屬一般 DRY 問題，合併無回歸風險，不適用本模式的改名建議。與 `PC-BAL-001`（建立端與驗證端清單不同步）的差別：那是同一份資料的兩個副本漂移，本模式是兩份**行為規則**並存且各自正確。

**實證來源**：`.claude/lib/hook_base.py:97` 的 `_find_project_root()` 優先序為「worktree 感知 → `CLAUDE_PROJECT_DIR` → `git rev-parse`」；`.claude/lib/git_utils.py:308` 的 `get_project_root()` 優先序為「`CLAUDE_PROJECT_DIR` → `git rev-parse`」。前者 7 個呼叫端、後者 8 個。三個獨立分析各自定位到此處：

- 測試以 `monkeypatch.setenv` 設定 `CLAUDE_PROJECT_DIR` 隔離，但 pytest 於 worktree 內執行時該設定被無條件覆蓋，hook 讀到真實專案資料而非 fixture（5 個測試紅燈）
- 同一 hook 的狀態檔解析與 log 解析走不同實作，導致作用在主 repo、痕跡寫在 worktree，使問題在主 repo 側完全不可見
- worktree 內產生非預期的狀態檔副本

`hook_base` 的 worktree 優先序為先前一張票的刻意修正（避免 worktree 內的 hook 動作洩漏至主 repo），故三個分析皆選擇不動共用模組，改在各自呼叫端顯式指定——此為正確處置，但也顯示問題會持續複製到下一個呼叫端。

**實例二：讀共用狀態的 hook 在 linked worktree 內讀到舊副本**

在 linked worktree 內，`hook_base` 版忽略 `CLAUDE_PROJECT_DIR` 而回 worktree 根。讀 ticket md 的收尾閘門（acceptance-gate）因此讀到 worktree 內的舊票面副本（主倉庫那份已全數勾選、副本未勾選），錯擋收尾；讀 `dispatch-active.json` 的並行期守衛則因 worktree 內不存在該檔而判為無派發。兩者輸出與「真的未勾選」「真的無派發」同形，無任何訊號。同一批 hook 中，改走 `git_utils` 版的讀取者在 hook 環境有 `CLAUDE_PROJECT_DIR` 時指向主倉庫而正常，使分歧只在部分 hook 顯現。

處置依 Action 表第二列的邊界延伸：**不改同名函式的優先序**（`hook_base` 版仍服務日誌與 worktree 內寫檔，統一會撤銷其修正），也不只靠改名，而是**依狀態類別分流**——另立 `get_shared_state_root` 專供 shared 狀態，per-worktree 狀態維持原函式。選擇依據由「呼叫端的 import 習慣」改為「狀態屬於哪一類」，對照表見 `.claude/references/hook-system-reference.md`「Hook 狀態類別與根解析對照」。

**對本模式的補充**：兩份解析規則各自合法、差異來自被解析對象的屬性（shared 或 per-worktree）時，改名只標示優先序，不足以告訴呼叫端該選哪一個；需再補一張「狀態類別 → 函式」對照表，使選擇可由狀態屬性推出。此修法的未完成範圍：`get_active_dispatches` 仍由呼叫端傳入根，承接中。

**實例三：分流函式的「預設根」參數被當成「指定根」使用**

`get_shared_state_root(default_root)` 依 hook 行程的 cwd 判定：cwd 在 linked worktree 時一律回推主 repo，`default_root` 只在 cwd 不在 worktree 時才被採用。一次遷移把 registry 的路徑函式由「有傳入根就用傳入根，未傳入才分流」改成「一律 `get_shared_state_root(傳入根)`」。合併閘門的測試快照本身是 linked worktree，測試傳入的 tmp 根因此被改寫成真實主 repo：skill 套件 12 個測試紅燈，主 checkout 的共用狀態檔被寫入測試假資料。hooks 套件有隔離環境變數使分流函式回 fallback，同型問題在那裡被遮住，只在沒有該隔離的 skill 套件顯現。

**對本模式的補充**：分流函式解決了「該選哪一份」，但參數名 `default_root` 與呼叫端習慣的「傳入根」同形，呼叫端會把它讀成「指定根」。判準：

| 傳入的根從哪來 | 能否包分流函式 |
|------|------|
| 本來就是依 cwd 推出的專案根（如 `get_project_root()`） | 可以，被覆蓋屬預期 |
| 另外解出來的根（測試 tmp 根、目標檔所屬 checkout、命令實際作用目錄、他 repo） | 不行；傳入根優先，或先比對 git common dir，同一 repo 才包 |

**識別訊號**：函式簽名同時接受 `project_root` 參數，又在內部呼叫分流函式；測試在 worktree 或閘門快照內跑時，主 checkout 的狀態檔 mtime 變動。**防護**：回歸測試必須涵蓋「cwd 在 linked worktree、傳入另一個根」的組合，並關閉隔離環境變數。

**實例四：配對狀態檔與它描述的檔被分到不同的根**

某個 hook 依清冊重建一份每個 checkout 各有一份的設定檔，另外留一個狀態檔記錄上次產生的條目，用來判定哪些條目「已從清冊移除、應刪」。遷移時，設定檔的根改成程式碼所在的 checkout，狀態檔則被歸類為日誌，搬到所有 checkout 共用的日誌目錄。結果兩個 checkout 的 session 交替執行時，共用的狀態檔每次都被後執行的一方覆寫，造成兩種錯誤：一是 A 的設定檔裡，用戶自加且指令與 B 清冊某列相同的條目，被判成「已移除」而刪掉；二是 A 清冊剛移除的列反而漏刪。這個問題在送閘前的審查中被攔下，修法是狀態檔仍放在共用目錄，但檔名改帶上它所描述那份設定檔的根的雜湊，讓兩者一對一配對。

**對本模式的補充**：判定狀態檔歸哪一類根時，除了看它是不是日誌或共用狀態，還要問一句：這個檔是否與另一個依根分開的檔配對？若是，配對檔的根決定它怎麼分，不能單獨把它搬到共用根。這條判準與實例三同屬「根的歸類只看單一檔的屬性，漏看它與其他檔的關係」。

**防護**：遷移狀態檔時，用 grep 找出讀它的函式，確認判定所需的另一半資料取自哪個根；回歸測試要讓兩個根交替執行，並以「改回共用單檔」的版本做對照，確認測試能翻紅。
