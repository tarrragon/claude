# ARCH-BAL-022：同一名稱同時存在於兩個同步狀態，讀者把分歧歸因至錯誤的一邊

## 摘要

**同一個名稱（skill 名、套件名、模組名）同時出現在兩套獨立的同步狀態中，而只有其中一套決定本地實際有什麼檔案。工具同時輸出兩者的狀態時，讀者會把 A 套的分歧當成 B 套的分歧，據以推論對方缺少某些檔案。** 錯誤結論在邏輯上完全合理，只是前提取自錯誤的來源。

與 `ARCH-BAL-002`（同一識別符雙載體、工具只讀一側）不同：該筆的失效方在工具，兩側都真實存在而工具盲於一側；本筆的失效方在讀者，兩套狀態工具都正確輸出，讀者歸因至錯誤的一套。

## 症狀

- 同步工具的輸出同時包含兩套來源的狀態清單，兩者共用同一批名稱
- 讀者依其中一套的分歧推論實際內容差異，結論自洽但與事實不符
- 被誤判的一方持有該內容，且正在使用它
- 工具輸出**已附免責說明**指出兩者指涉對象不同，誤讀仍發生
- 錯誤不易自我察覺：推論鏈成立，唯一的缺陷在最初取用了哪份清單

## 根因

1. **名稱在兩套狀態中相同，而狀態的所屬 repo 只出現在區塊標題或末行免責句。** 名稱是讀者的定位錨點，來源標示不是；當清單有九列而免責句只有一行時，注意力分配天然偏向前者。
2. **免責句放在清單之後。** 讀者掃到清單即形成判讀，免責句抵達時判讀已成立，其功能從「預防誤讀」降為「事後可援引的依據」。
3. **兩套狀態的更新時機不同但輸出並列。** 一套隨每次同步更新，另一套僅在手動推送時更新，並列呈現使讀者預設兩者時效一致。

## 防護

| 時機 | 動作 |
|------|------|
| 依同步工具輸出推論「對方缺少某內容」前 | 先確認該清單屬於哪一套同步狀態，再確認該套是否決定本地檔案存在與否 |
| 需確認對方是否持有某檔案 | 直接請對方執行存在性檢查（`ls` / 版本欄位），不從分歧清單反推 |
| 設計同時輸出多套狀態的工具 | 免責句前置於清單，或在每列名稱前綴來源標記，使名稱與來源同時進入視線 |

**檢查問句**：這份清單裡的名稱，決定的是「本地有什麼檔案」還是「另一個 repo 有什麼檔案」？兩者若不同，我的結論用的是哪一份？

## 邊界

- 與 `ARCH-BAL-002` 的分工見摘要末段：該筆失效方在工具，本筆在讀者。
- 與 `PC-BAL-064` 的關係：本筆是「取樣落在錯誤的來源」而非「取樣落在單一維度的單一格」，兩者同屬結論正確性依賴未被檢視的前提，但前者的缺陷在來源選擇，後者在範圍涵蓋。
- 不適用於工具未輸出來源標示的情形——那屬工具缺陷，應補標示而非要求讀者辨識。

## 實例

跨 consumer 協作中，一方依同步工具輸出的九列 skill 雜湊分歧清單，推論另一方「尚未拉取某 skill 的新版本，故缺少該版本新增的兩個檔案」。實際上該分歧清單比對的是**本地與 skill 發佈庫**，而非本地與框架 canonical repo；被誤判的一方持有完整新版本，且正以該版本新增的工具發出協作訊息。

工具輸出在該清單末尾附有一行說明「此為 skill 發佈庫，與同步目標 repo 不同」，雙方在每次拉取與推送時都會看到該段輸出，誤讀路徑對雙方皆開放。

推論本身無誤：若分歧確實在 canonical，該推論成立。缺陷只在最初取用了哪一份清單。
