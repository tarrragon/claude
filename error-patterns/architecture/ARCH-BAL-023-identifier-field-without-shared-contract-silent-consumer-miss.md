# ARCH-BAL-023: 寫入端與消費端各自自洽，識別欄位缺共同格式約定且缺席無訊號

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | medium |
| 發現途徑 | 跨 consumer 收束 framework issue 時，同儕 session 的七張 issue 對本方 SessionStart 檢查不可見 |
| 復發次數 | 一次（首次記錄），同族先例見 ARCH-BAL-017 |
| 來源版本 | v0.2.1 |

## 摘要

**一個自由文字的識別欄位（owner、session、consumer 名）由寫入端填入、由另一條路徑的消費端以某種推導規則辨識。兩端各自正確：寫入端接受任何非空字串並成功寫入，消費端以自己的推導規則篩選並靜默略過不符者。兩端之間沒有任何一份共同的格式約定，於是「寫入成功但永遠不被消費」這個狀態在兩端都不產生訊號。**

失效在寫入當下即成立，但要等消費端該做的事（通知、回收、檢查）沒有發生時才可能被察覺，而「沒有發生」本身也沒有訊號。發現途徑通常是第三方比對兩端資料時才看到。

## 症狀

- 消費端的過濾器（前綴推導、正則、白名單）對某批記錄全數不命中，但這批記錄在寫入端全部成功且外觀正常
- 消費端沒有「略過了幾筆」的輸出，或有輸出但被視為正常噪音
- 寫入端的欄位說明只寫「識別」「名稱」，沒有寫格式，執行者用手邊最近的字串填（代理人型別名、`pm` 字樣、含底線的專案名）
- 同一欄位在不同寫入者手上出現三種以上形態，每一種單獨看都說得通
- 缺口由第三方發現，且發現方式是「我方檢查怎麼看不到你方的記錄」，不是任一端自己報錯

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 欄位語意用途詞命名 | 欄位叫 owner／session，名稱描述「這是誰」，不描述「長什麼樣」 | 寫入者以為任何能代表「誰」的字串都對 |
| 消費端的推導規則寫在消費端 | 前綴推導、kebab 轉換寫在讀取那一側的程式碼與 docstring 裡 | 寫入者不會讀消費端程式碼，約定對寫入者不可見 |
| 兩端由不同時間、不同人建立 | 消費端後於寫入端加上，或反之；各自以當時手邊的資料形態為準 | 沒有任何一份文件同時被兩端引用 |
| 不符者被靜默略過是消費端的合理設計 | 消費端本來就要容忍雜訊（搜尋粗篩、fail-open） | 靜默略過把「格式不對」與「本來就不是我的」合併成同一個無訊號狀態 |

**與 ARCH-BAL-017 的差別**：017 是一份既有的宣告（排除清單）只有一條路徑讀；本 pattern 沒有任何宣告存在，兩端各自持有半份約定。修法也不同：017 補一個參數把清單接進去，本 pattern 要先寫出約定、再把驗證放在寫入端。

## 案例：framework issue 區段 owner 欄

### 事件鏈

1. comment-as-section 協定的區段標記首行為 `<!-- section: <名稱> owner: <session> -->`，CLI 的 `init --owner` 接受任何非空字串
2. SessionStart 的擁有 issue 檢查在登記檔缺失時，以專案目錄名 kebab 化推導前綴（`flutter_balance` → `flutter-balance-`），再以 `startswith` 篩選區段 owner
3. 三個 session 各自填了三種形態：`flutter-balance-99`（符合推導）、`flutter_balance-pm`（底線且無序號）、`framework-issue-curator`（代理人型別名）；後兩者的 init 全部成功、外觀正常
4. 後兩者擁有的 issue 從此收不到「當前結論落後最新觀測」的主警訊，而該警訊是協定裡 owner 得知有新觀測的唯一機械管道
5. 發現方式：本方向同儕詢問分工時，對方回報「七張全部以代理人名 init」，本方比對推導規則才知道七張都不可見。任一端單獨運作永遠不會發現

### 驗證

```
grep -o 'owner: [^ ]*' <七張 issue 的區段 comment 首行>   # 三種形態
grep -n 'startswith\|replace("_"' session-start-issue-check-hook.py  # 推導規則只在消費端
```

## 解決方案

1. **把約定寫成一份兩端都引用的文字**：格式（`<專案目錄 kebab-case>-<session 序號>`）、正則、範例、違反後果，放在協定文件的標記格式節；寫入端 CLI 說明與消費端 hook docstring 都指向它
2. **驗證放在寫入端**：`init`／`add`／`transfer-owner` 共用同一個 `validate_owner`，不合法 exit 3 並印格式與範例。消費端發現漏檢等於永遠不會發現
3. **所有寫入入口共用同一驗證**：新增任何會寫該欄位的子命令時，驗證函式是必經呼叫，不能只掛在最早的入口（同儕提醒：判準明確而執法只在一個入口，存量會從另一個入口累積）
4. **存量處理**：對既有不合法值提供轉換命令（`transfer-owner`），不要求手動 PATCH

## 預防措施

| 層級 | 措施 |
|------|------|
| 設計 | 任何會被另一條路徑以規則篩選的識別欄位，欄位說明必含格式、正則、範例三項；只寫「識別」不算說明 |
| 寫入端 | 驗證函式與欄位定義同檔，所有寫入子命令共用 |
| 消費端 | 被過濾器略過的筆數要出現在輸出（「略過 N 筆不符格式」），不可靜默 |
| 審查 | 新增識別欄位時問一句：「消費端怎麼認出它？寫入端知道嗎？」兩個答案不在同一份文件即為本 pattern |
