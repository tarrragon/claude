# ARCH-BAL-004: 參考文件範例與同檔規則矛盾，範例成為缺陷散播源

## 摘要

**同一份技術文件的範例段示範了後段規則明文禁止的做法，範例在前、規則在後，讀者讀到範例即照抄，缺陷隨每次照抄複製一份。** 關鍵不在「文件寫錯了要改」，而在範例的示範力大於規則的約束力，且位置在前者更甚——範例是可直接貼上的成品，規則是需要自行轉譯的約束；讀者取得可用產物後就停止閱讀。更難察覺的是每個照抄實例都有文件依據，審查者比對文件會找到那段範例並判定「符合參考文件」，於是缺陷在每一次審查中被確認為正確，靜默複製到十餘個位置。

## 症狀

- 多個實例犯同一個錯，且每個實例的作者都能指出文件依據
- 錯誤實例的註解或 commit 訊息帶有共同字面（複製痕跡），版本上呈批次分佈而非零星出現
- 該文件同時存在正解——規則章節寫得完整且正確，只是位置在範例之後
- 逐一審查每個實例都通不出問題（因為都符合範例），要並列文件的範例段與規則段才看得出矛盾
- 修復提案被誤判為「十餘個獨立缺陷」，實際是一個源頭加十餘次套用

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 範例是可執行產物 | 範例可直接複製貼上並跑起來 | 讀者取得可用結果後即停止閱讀，不會續讀後段規則 |
| 規則是待轉譯約束 | 規則需讀者自行對應到自己的情境才能套用 | 認知成本高於複製，在有現成範例時被跳過 |
| 位置決定閱讀順序 | 範例在前、規則在後 | 先讀到的版本先寫進讀者的心智模型，後讀到的規則被當成補充而非否決 |
| 照抄產生合法外觀 | 每個實例都能追溯到文件段落 | 審查比對文件會確認「有依據」，缺陷通過審查而非被攔下 |
| 文件的兩段各自正確地被維護 | 規則章節後續補強、範例段未同步 | 矛盾隨時間擴大，且兩段都有維護紀錄，看不出誰是待修的一方 |

**為何比一般文件過期更難發現**：文件過期時實例與文件不一致，比對即暴露；本 pattern 的實例與文件一致，暴露條件是「同時讀到文件的兩個相隔數十行的段落並發現互斥」。前者靠例行比對就會撞見，後者需要有人刻意做同檔內部一致性檢查。

## 案例：hook effort 短路缺陷複製到 12 個 hook（2026-07-26）

`.claude/references/hook-architect-technical-reference.md` 第 327-349 行的「effort 感知範例」示範：

```python
if effort == "low":
    return 0
```

同檔第 369-391 行的「設計鐵則：事實判斷型 hook 必擋 + effort 解耦」明文禁止此做法：「事實判斷型 hook 的核心 block 邏輯永不依 effort 短路」。兩段相隔約 20 行，範例在前、鐵則在後。鐵則章節當時已成形並附 4 個 hook 的落地案例對照表，即正解與缺陷並存於同一檔案。

該片段被 W14-034 / W14-036 / W14-037 三批次逐字複製進 12 個 hook，註解字面「Effort 感知（v2.1.133+，W14-03x）：low effort 短路放行」是複製痕跡。

實證數字：

| 指標 | 數值 | 來源 |
|------|------|------|
| 照抄該範例的 hook 數 | 12 | 註解字面掃描 |
| 實際觀測到的短路次數（跨 6 個 hook） | 669 | hook-logs 掃描 |
| `sibling-blockedby-validator` 短路次數 | 477 / 2463 | 同上；12 者中唯一 exit 2 阻擋型 |
| payload 交叉統計樣本 | 2492 筆 | hook-logs 取樣 |
| `effort=low` 事件 | 471 筆，全數來自 frontmatter 宣告該值的 subagent | 同上 |
| `effort=high` 事件 | 2021 筆，全數來自主線程 | 同上 |

判準本身也是反的：`effort` 是 agent frontmatter 的固定屬性，同一個 agent 寫一行註解與重構整個模組皆為 `low`，與任務複雜度零相關。故該範例的實際效果並非「簡單任務走快路徑」，而是「對受監督程度最低的執行者關閉閘門」——24/33 個 agent 宣告 `effort: low`。

三批次期間無人質疑，因為每個 hook 的短路都能追溯到參考文件的範例段。缺陷是在調查另一個單一 hook 的問題時，掃描才發現同一片段散佈於 12 處。

修復：範例改寫為 effort 僅控制 audit log 詳細度，前置「交叉引用（先讀這裡）」指向鐵則章節；同時刪除 8 個事實判斷型 hook 的短路。分析與改寫已應用。

> 註：`0.2.1-W3-019` 對 `comment-qa` 與 `ticket-quality-gate` 兩者「可接受」的具體理由經 `0.2.1-W3-028` 覆核與實際不符，修正由 `0.2.1-W3-030` 承接。本 pattern 引用的是該分析的根源判定與統計資料部分。

## 防護

### 寫文件時：範例段的三項必要條件

| 項目 | 具體動作 | 判定通過的標準 |
|------|---------|--------------|
| 前置交叉引用 | 範例上方加一行「交叉引用（先讀這裡）」，指名同檔規則章節的標題，並說明該範例示範的是規則的哪一種允許用法 | 只讀範例區塊（含前置行）的讀者能知道有一條約束存在且知道去哪讀 |
| 反例明寫在範例內 | 在範例的程式碼註解或緊接的說明句寫出被禁止的形態字面（如「禁止以 `if effort == "low": return 0` 形式短路放行」） | 讀者照抄時，禁止形態出現在他複製的文字範圍內 |
| 規則章節回指範例 | 規則章節列出「本規則對應的範例位於某節」，形成雙向連結 | 從任一段進入都能到達另一段 |

**Why**：讀者的閱讀邊界是範例區塊，不是整份文件。防護必須落在該邊界之內才會被讀到；寫在四十行外的規則章節在行為上等於不存在。

**Consequence**：只補規則章節而不動範例，下一位讀者仍然照抄，缺陷數量繼續增加，且新增實例同樣具備文件依據而通不出審查。

### 審查文件時：範例與規則的交叉驗證動作

依序執行，每步有可判定的輸出：

1. **列出文件內所有可複製產物**——程式碼區塊、設定片段、指令、範本。這是缺陷散播的完整候選集合。
2. **列出文件內所有禁止式語句**——含「禁止」「不得」「永不」「必須不」「僅允許」的句子，記錄其約束對象。
3. **逐項比對**：對每個可複製產物，逐條檢查是否觸犯第 2 步的任一禁止式語句。禁止只憑印象判斷「應該沒問題」；比對必須是產物 × 禁令的完整笛卡兒積，項目少時人工可行，項目多時以關鍵字先篩。
4. **對命中者判定方向**：範例與規則矛盾時，先確認何者為正解（通常規則章節較新、較完整、附案例表），修正另一方，而非取中間值或並列兩種寫法。
5. **檢查前後順序**：正確的範例若仍位於規則之前，補前置交叉引用；不需要為此調整章節順序（範例在前有其教學理由）。

### 發現矛盾後：必須做的擴散掃描

文件矛盾一旦確認，該範例已存在多久就可能被照抄多久。修文件只是必要條件，不是充分條件。

| 步驟 | 動作 |
|------|------|
| 1 | 從錯誤範例中取一段不易改寫的字面（變數名、註解字串、特定條件式）作為指紋 |
| 2 | 全 repo grep 該指紋，取得候選實例清單 |
| 3 | 逐一判定該實例是否真受影響（同形不一定同害），分為必修 / 可接受 / 待評估三組並附依據 |
| 4 | 檢查測試：若有測試把錯誤行為固化為期望值，該測試是缺陷的迴歸鎖，須與實作同批修 |
| 5 | 修文件範例（源頭）與所有必修實例，同一批次完成；否則下一次照抄會從未修的那份開始 |

**本案例的第 4 步實證**：`.claude/hooks/tests/test_effort_awareness.py` 把短路行為寫成期望值，若只改實作會紅燈，若只信測試會判定實作正確。

### 既有文件自查：優先掃描哪些檔案

同時滿足以下條件的文件優先自查，符合越多優先級越高：

- 含可複製的程式碼或設定範例
- 同檔另有規範性章節（設計鐵則、判準、禁止清單）
- 該文件被多個實例引用為依據（agent 定義、hook 開發、範本產生）
- 文件長度使讀者不會通讀（超過數百行）
- 規則章節有後續修訂紀錄而範例段沒有

快速訊號：`grep -n "禁止\|不得\|永不\|必須不" <file>` 與程式碼區塊起始行號並列，若禁止式語句的行號全數大於某個程式碼區塊，該區塊即為待驗證對象。

## 與其他 pattern 的邊界

| Pattern | 聚焦 | 差異 |
|---------|------|------|
| ARCH-BAL-003（白名單判準與成員脫節） | 判準已明確，缺的是成員同步 | 共同上位是「宣告層與執行層不一致」；載體不同——ARCH-BAL-003 的兩層是判準與名單（同屬機制內部，執行時只讀名單），本 pattern 的兩層是範例與規則（同屬文件內部，兩者皆不執行，經由人類複製才進入執行層）。防護手段因此不同：前者靠機械比對名單，後者靠文件內部一致性審查與擴散掃描 |
| ARCH-016（Hook 允許清單過度限制） | 清單無明文判準，撞牆時需重新論證 | 本 pattern 的正解已寫在同一份文件內，不需要新的論證，只需要讓讀者讀到 |
| IMP-BAL-003（稽核器與消費端解析器嚴格度落差） | 兩個執行中的解析器嚴格度不同 | 該 pattern 兩層皆在執行，矛盾由執行結果暴露；本 pattern 兩層皆不執行，矛盾只在有人並列閱讀時暴露 |
| PC-066（文件明示性不足） | 文件沒說清楚 Why / Consequence / Action | 本 pattern 的文件說得很清楚，問題是說了兩套且互斥 |

## 驗證方式

修正文件與擴散實例後：

- 以錯誤範例的指紋重新 grep 全 repo，確認命中集合為空或每個剩餘項有明文的保留理由
- 重讀範例區塊（僅範例本身加前置行），確認只讀這段的讀者能得知約束存在
- 確認迴歸測試已改為驗證正確行為，且測試名稱不再描述舊行為
- 文件版本註記寫明「此範例曾與某章節矛盾並為某批次缺陷的散播源」，讓後續修訂者知道此處有歷史
