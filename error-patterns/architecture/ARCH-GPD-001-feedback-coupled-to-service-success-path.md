# ARCH-GPD-001: 互動回饋掛在服務的成功路徑上，服務越不可用回饋越少

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | ARCH-GPD-001 |
| 類別 | architecture |
| 風險等級 | 高 |
| 發現日期 | 2026-09-08 |
| 來源版本 | 0.1.0 |

## 症狀

使用者按下一個互動元件，畫面**完全沒有反應**——沒有按下的視覺、沒有等待指示、沒有成功
或失敗訊息。功能在背後失敗了，而失敗被降級處理收斂成某個狀態值、或被寫進一行使用者
看不到的日誌。

關鍵形態不是「失敗沒提示」，而是**回饋與服務可用性正相關**：服務正常時回饋齊全，服務
壞掉時回饋一起消失。使用者最需要知道發生什麼事的那一刻，正是系統最沉默的一刻。

**本案實例**（實機驗證，2026-09-08）：使用者按下重新掃描按鈕，觀察到「沒有觸發授權，
也沒有看到任何啟動的提示或者動畫」。實際發生的事：

| 層次 | 實際情形 |
|------|---------|
| 按下確認 | 狀態瞬間切換（完成邏輯落在同一 microtask），pressed 視覺存在時間短於一幀 |
| 等待指示 | 掃描中骨架同理，從未被繪出 |
| 結果通知 | 平台呼叫拋 `MissingPluginException`（原生端 handler 未註冊），依規格「其他結果視為 denied」被收斂 |
| 例外的去向 | 一行 `WARNING` 級日誌，而該日誌所用的 API 不進標準開發迴圈的 console，需另開偵錯工具才看得到 |

四層各自都有「合理的」理由，疊起來的結果是使用者按了按鈕、什麼都沒發生、也無從得知
為什麼。而 App 不崩潰、畫面正常、自動化測試全綠（替身取代了整個服務介面，不經過真實
平台邊界）。

**識別特徵**：

- 回饋的觸發點寫在服務回應的處理路徑裡（`then` / `await` 之後 / 成功分支內）
- 例外處理把失敗收斂為某個狀態值，而該狀態值沒有對應的可見表現，或其可見表現另有前提條件
- 「已優雅降級」被當成已處理，不再追問降級後使用者看得到什麼
- 元件的回饋定義只列成功路徑；失敗、逾時、服務不可用不在同一張表上

## 根因

**回饋的責任被放錯歸屬。** 回饋是互動的性質，不是服務的性質——使用者按下按鈕這件事本身
已經發生，與按鈕背後接的東西能不能運作無關。把回饋掛在服務回應上，等於讓一件確定發生的
事（互動）去依賴一件不確定的事（服務可用性）。

由此推出那條反向相關：

- 服務正常 → 走成功路徑 → 回饋齊全
- 服務異常但可預期 → 走失敗分支 → 回饋通常較少（如果有人寫）
- 服務不可用／接線錯誤／功能未實作 → 連分支都沒進去，或進了統一降級 → **回饋為零**

三種情況裡，使用者最需要訊息的是第三種，得到的最少。

第二層根因是**降級與靜默被混為一談**。優雅降級（把不可預期的結果收斂為已知狀態值）解決的
是行為確定性——讓上層不必處理無限多種失敗形態。它不是、也不該是「這件事已經處理完了」的
結論：收斂之後的那個狀態值仍然要有可見表現，否則收斂等於銷毀證據。

第三層是**日誌被誤當回饋**。開發者看得到日誌，使用者看不到。日誌滿足的是可觀測性要求
（見 `quality-baseline` 規則 4、`observability-rules` 規則 1），與使用者回饋是兩套獨立
義務，滿足其中一項不抵扣另一項。本案的日誌甚至連開發者都看不到——所用的 API 不寫入標準
開發迴圈的 console。

## 解決方案

1. **回饋依觸發時序分三層，逐層歸屬不同承擔者，不得混併。** 按下確認（互動元件層）由
   按下這個事件本身觸發，在任何服務呼叫發出之前就已經成立，承擔者是元件自身，與背後
   是否掛服務無關。等待指示（服務受理層）由「已送出、尚未回應」這個狀態觸發，承擔者是
   服務——事件送出之後，是服務要對「收到了、正在處理」負責，不是元件的義務；把這層
   回饋歸給元件，等於讓服務側完全沒有回饋義務，服務可以什麼都不做而條文仍讀得通。結果
   通知（event 效果層）由服務處理完成後才觸發，只**追加**結局資訊，不是前兩層回饋的
   觸發來源。

2. **判準問句**：把這個元件背後的服務整個拔掉，使用者按下去還看得到反應嗎？答案為否，
   表示回饋掛錯位置。這個問句可在設計期回答，不需要等實作。

3. **降級後的狀態必須有可見表現。** 把例外收斂為某個狀態值時，同時指出該狀態值在畫面上
   長什麼樣；若該表現另有前提條件（例如只在特定畫面或特定時機出現），前提不成立時的
   替代表現也要寫。收斂到一個沒有表現的狀態，等於把失敗變成靜默。

4. **元件的回饋定義涵蓋失敗路徑。** 成功、失敗、逾時、服務不可用列在同一張表上；沒有
   「這個情況不會發生」這種填法——不會發生的情況正是沒有人寫處置的情況。

5. **日誌不抵扣使用者回饋。** 兩者是獨立義務。審查時分別確認。

6. **輸出端（driven port）有結構平行、消費者不同的對應形態。** 本則的三層歸屬與判準問句是輸入端（使用者互動）的特化；服務往外呼叫外部系統（開檔案、存取資料庫、呼叫 API）時，三個可觀測時刻改為呼叫發出／外部系統受理／結果，消費者從使用者換成呼叫端程式碼、日誌、監控追蹤，且三者互不抵扣（同構於本則第 5 點）。完整定義見 [Port 回饋契約](../../methodologies/clean-architecture-implementation-methodology.md)。

## 預防措施

| 時機 | 動作 |
|------|------|
| 設計互動元件的回饋定義時 | 先回答判準問句（拔掉服務還有沒有反應）；答否即改掛載點 |
| 寫例外處理／降級邏輯時 | 每個收斂目標狀態同時指出其可見表現；沒有表現的收斂目標不得使用 |
| 審查「已優雅降級」的結論時 | 追問一句「降級之後使用者看到什麼」；答不出來即為靜默失敗 |
| 撰寫元件回饋契約時 | 成功與失敗列在同一張表；失敗欄留空或填「不會發生」皆不接受 |
| 實機驗證時 | 對每個互動元件測一次「服務不可用」情境（拔線、停服務、故意讓依賴失敗），觀察畫面是否仍有反應 |
| 例外 | 刻意設計為無回饋的互動（例如純裝飾、或回饋由相鄰元件統一承載）——須在契約中明寫承載者是誰，不得留空 |

## 行為模式分析

寫程式的人是照著「事情會成功」的路徑思考的：呼叫服務、拿到結果、更新畫面、顯示訊息。
回饋自然地被寫在那條路徑的末端，因為那是「有東西可以顯示」的地方。失敗路徑上沒有結果
可顯示，於是也就沒有東西被寫進去——不是有人決定不給回饋，是那個位置從來沒被造訪過。

自動化測試無法暴露這件事，因為測試用替身取代服務，而替身總是可用的。替身讓服務的
成功路徑恆為真，於是掛在該路徑上的回饋恆存在——測試驗證的是一個永遠不會失敗的世界。

這也是為什麼本案只能由實機驗證發現，而發現它的不是自動化斷言，是一個人按了按鈕之後說
「沒有反應」。

## 相關

- `quality-baseline` 規則 4（異常可觀測性）與 `observability-rules` 規則 1：日誌側的義務。
  本則主張該義務與使用者回饋義務獨立，不互相抵扣
- 元件庫的回饋契約（六類回饋事件：可互動提示／焦點／按下確認／定位提示／狀態變更提示／
  等待與結果）：本則要求「按下確認」（互動元件層）與「等待與結果」（服務受理層／
  event 效果層）依三層歸屬分別掛載，服務受理層的義務由服務承擔，不得併入元件
- 跨邊界驗證形態（fake 覆蓋 App 端邏輯、實機驗證覆蓋平台端事實）：本則是該形態存在理由的
  實例——替身讓服務恆可用，靜默失敗只在真實邊界上顯現
