# ARCH-BAL-011：以主題命名的機制群造成該主題已被涵蓋的假象

## 基本資訊

- **Pattern ID**: ARCH-BAL-011
- **分類**: 架構設計（architecture）
- **來源版本**: v0.2.1
- **發現日期**: 2026-07-31
- **風險等級**: 高（缺口不會被搜尋到，因為搜尋該主題會命中一批同名機制並停在那裡）
- **影響範圍**: 任何以主題字詞命名多個機制的系統——hook 集合、middleware 鏈、validator 群、guard 群

## 摘要

**同一主題下存在多個以該主題命名的機制，使人以為該主題已被涵蓋；實際上這些機制處理的是該主題的周邊事務，核心保證從未存在。** 查證者以主題字詞搜尋，命中一批名稱相符的機制，於是停止深究——名稱回答了「有沒有」，但沒有回答「保證了什麼」。

這比完全沒有機制更難發現。零命中會促使人繼續找或直接補；多筆命中會終止搜尋。

## 症狀

- 以某主題字詞搜尋設定或程式碼，命中數個名稱含該字詞的機制
- 被問到「這個主題有沒有把關」時，回答者引用機制名稱而非其職責描述
- 逐一讀那些機制的 docstring 後發現它們的觸發前提，正是那個本應被保證的行為——機制在「該行為發生時」介入，不使該行為發生
- 缺口存在期間無任何告警，且事後回顧找不到「應該要有人發現」的時點
- 相關文件可能載有「由 X 把關」的敘述，但 X 在當前環境不存在或不做該事

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 命名依主題而非職責 | 機制名取自它處理的領域（`pre-test` / `post-test`），非它提供的保證 | 名稱無法區分「使 X 發生」與「X 發生時介入」 |
| 查證以名稱為終點 | 搜尋命中即視為覆蓋確認，不逐一讀職責 | 多筆命中反而終止進一步查證 |
| 周邊機制的數量掩蓋核心缺口 | 主題越受重視，周邊機制越多，假象越強 | 重視程度與誤判機率正相關 |
| 缺口是否定性事實 | 「沒有任何東西保證 X」無法被單一查詢證實，須窮舉可能位置 | 查證成本高於確認存在，因此少有人做 |

核心是**命名回答的問題與查證者要問的問題不是同一個**。

## 解決方案

### 查證方式

主題覆蓋的查證必須以「保證」而非「名稱」為單位。對每個命中的機制問一句：

> 它的觸發前提是什麼？若那個前提正是我要保證的行為，它就不提供該保證。

判定「無覆蓋」屬否定性命題，須窮舉可能位置並逐一記錄結果，不以「搜尋過了」代替。

### 命名調整

機制名應載明其提供的保證或其觸發前提，而非所屬主題：

| 主題式命名 | 職責式命名 | 差別 |
|-----------|-----------|------|
| `pre-test-hook` | `test-env-readiness-check` | 後者明示它檢查環境就緒，不保證測試被執行 |
| `post-test-hook` | `test-failure-triage` | 後者明示它在失敗後分流，前提是測試已跑 |

改名成本高時，退而要求 docstring 首行即寫出「本機制不保證什麼」。

## 預防措施

| 層級 | 措施 |
|------|------|
| 查證 | 主題覆蓋問題一律逐一讀職責，禁止以名稱命中數作答；否定性結論須附窮舉清單 |
| 命名 | 新機制命名以保證或觸發前提為準，不以所屬主題為準 |
| 文件 | 敘述「由 X 把關」時附 X 的實際判準與觸發前提，使讀者可自行驗證該敘述在其環境是否成立 |
| 審查 | 看到同主題三個以上同名機制時，主動問一次「核心保證由哪一個提供」 |

## 驗證方式

- 對每個宣稱被涵蓋的主題，列出提供該保證的**單一**機制名稱與其判準；列不出即為本模式
- 否定性結論須有窮舉清單（檢查了哪些位置、各自結果），可供他人以相同指令複驗

## 實證案例：hooks 測試無 gate（2026-07-31）

`.claude/settings.json` 掃 `test` 關鍵字命中五個 hook：`test-timeout-pre`、`pre-test-hook`、`pre-test-scan`、`mcp-run-tests-validator`、`post-test-hook`。名稱皆與測試相關。

逐一讀 docstring 後：`pre-test-hook` 是「測試前環境檢查」（Flutter SDK / `pubspec.lock` / `.dart_tool` 就緒狀態），`post-test-hook` 是「測試超時監控 + 測試失敗評估」。**兩者的觸發前提都是「測試正在被執行」**——它們不使測試被執行。

窮舉六個可能位置後確認無任何 gate：`.github/workflows`（不存在）、`.pre-commit-config.yaml` 與 `.husky`（不存在）、`.git/hooks`（僅 14 個 `.sample`）、`core.hooksPath`（未設定）、`settings.json` 的 test 類 hook（如上）。

實際代價：`0.2.1-W3-181` 改動一個常數使測試紅燈，跨兩張票的 commit 均無提示，潛伏 27 分鐘至另一張無關 ticket 的代理人碰巧跑全套件才撞見。若未碰巧，潛伏無上界。

附帶一例同型：`.claude/skills/ticket/SKILL.md` 的 append-log 說明寫「維持 pre-commit hook 把關」，該敘述對有 pre-commit 的 consumer 成立，對本專案不成立——文件敘述了一個在當前環境不存在的保證。
