# ARCH-BAL-014: 修好上游過濾層使原本被攔下的資料抵達下游，同根因的下游缺陷暴露面反而擴大

## 摘要

**當同一個根因同時存在於「過濾層」與「顯示層」，而過濾層的缺陷恰好攔下了會觸發顯示層缺陷的資料時，只修過濾層會讓該類資料首次抵達顯示層，使用者看到的錯誤反而從零變成有。** 修復者依測試綠燈與端對端驗證判定「修好了」，因為他驗證的是過濾層的行為；而新增的暴露面在顯示層，不在他的驗證範圍內。

危險之處在於這與一般迴歸不同。一般迴歸是「改動破壞了原本正確的行為」，可由既有測試攔截；這裡的顯示層從一開始就是錯的，只是沒有資料走到那裡，因此沒有任何既有測試會轉紅。修復是正確的，測試是綠的，缺陷是舊的，但使用者體感是「這次改動之後才出問題」。

## 症狀

- 修復通過全部測試與端對端驗證，但使用者在修復後才首次遇到某類錯誤顯示
- 追查發現出錯的程式碼未被本次改動觸及，`git blame` 指向數月前
- 該段程式碼的錯誤路徑從未被回報過，因為上游缺陷使其從未被執行
- 修復者的驗證清單完整覆蓋自己改的層，未涵蓋「改動後才會被走到的下游路徑」
- 事後審查者容易誤判為「既有 bug，與本次無關」而不追蹤，或誤判為「本次引入」而歸咎修復

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 同一根因散落多層 | 過濾層與顯示層各自實作了同一個判斷，皆用錯對象 | 修一層不會連動另一層 |
| 過濾層缺陷遮蔽下游 | 上游把會觸發下游缺陷的資料全數攔下 | 下游錯誤路徑零執行，零回報，零測試覆蓋 |
| 修復範圍以「根因所在」界定 | 修復者定位根因在過濾層，驗證亦止於過濾層 | 下游新增的可達路徑不在驗證清單內 |
| 既有測試不會轉紅 | 下游本來就錯，不是被改壞的 | 測試綠燈成為「無新問題」的假訊號 |
| 暴露面變化無度量 | 無人統計「修復後哪些程式碼路徑從不可達變為可達」 | 風險不進入任何檢查表 |

**與一般迴歸的差別**：迴歸是既有正確行為被破壞，本 pattern 是既有錯誤行為被啟用。前者可由測試套件攔截，後者不能——因為沒有測試會為「從未執行的錯誤路徑」而寫。

**與 PC-165（測試綠燈不等於 runtime 正確）的關係**：PC-165 描述綠燈與 runtime 的落差來自 mock 遮蔽，本 pattern 的落差來自可達性變化，兩者都使綠燈失去「使用者不會遇到問題」的保證力，但機制不同。

## 案例：修好 handoff stale 過濾使來源票 ID 首次顯示給使用者（2026-08-06）

handoff JSON 有 `ticket_id`（來源，誰交出的）與 `target_ticket_id`（對象，誰要接手）兩類欄位。`is_handoff_stale` 用來源票判斷「這個 handoff 是否還需要做」，導致以 `--next` 建立、來源已完成的 handoff 被判為 stale 而全數過濾掉。

修復把過濾判準改為 target 後，這類 handoff 首次通過過濾。但 Stop hook 與 SessionStart reminder hook 的顯示層同樣以 `data.get("ticket_id")`（來源）作為 pending 清單項目、排序鍵與 `/ticket resume <id>` 建議命令的對象——兩個 hook 的 `resolve_target` 呼叫數實測為 0。

於是修復後首次出現的行為是：清單顯示已完成的來源票，並指引使用者去 resume 它。修復前這條路徑零執行，因為 handoff 在抵達顯示層前就被過濾掉了。三套測試（2840 + 3478 項）全綠，端對端驗證涵蓋 GC 判定與 context_bundle 抽取兩處皆通過，皆未觸及此暴露面。

該暴露面由 Phase 4 的獨立掃描委員發現，掃描指令為「找出仍以來源票為對象但語意上應為 target 的位置」，涵蓋範圍是整個 `.claude/` 而非本次改動的檔案——正是這個「不以改動範圍界定掃描範圍」的設定使其被捕獲。

## 防護

| 時機 | 動作 |
|------|------|
| 修復過濾 / 守衛 / 前置檢查類缺陷時 | 在驗證清單加一項：修復後有哪些程式碼路徑從不可達變為可達？逐一檢視這些路徑是否含同根因缺陷 |
| 界定修復範圍時 | 範圍以「根因涉及的判斷」界定，非以「缺陷回報位置」界定。同一判斷在幾層出現就檢查幾層 |
| Phase 4 / 審查派發時 | 至少一位委員的掃描範圍不受改動檔案清單限制，改以「根因語意」為搜尋條件全域掃描 |
| 審查發現下游同根因缺陷時 | 不因「程式碼未被本次觸及」而判定無關；暴露面變化屬本次修復的後果，須建 ticket 追蹤並標明優先級高於一般既有缺陷 |
| 撰寫 acceptance 時 | 「掃描並列出所有消費者」類條目須明確定義掃描範圍與判定產出，否則易被理解為只掃改動處 |
