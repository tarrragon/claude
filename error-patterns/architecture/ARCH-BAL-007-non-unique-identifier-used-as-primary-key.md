# ARCH-BAL-007：非唯一識別符被當主鍵，集合去重靜默丟棄同鍵資料

## 基本資訊

| 欄位 | 值 |
|------|-----|
| 風險等級 | 高 |
| 來源版本 | v0.2.1（0.2.1-W3-110 ANA） |
| 發現日期 | 2026-07-28 |

## 摘要

**一個識別符在多數情況下唯一，於是下游工具用它建 `set` 或 `dict` 做去重與存在性判定；當現實中出現重複鍵時，同鍵的第二筆之後全被靜默丟棄。** 丟棄不產生錯誤、不產生警告、不產生空洞——輸出看起來完整且自洽，因為被丟的那筆從未進入輸出，也就沒有任何位置能顯示它缺席。

與 ARCH-BAL-002 的差別在於失敗發生的層。ARCH-BAL-002 是同一識別符存在兩個載體、工具只讀其中一側；本 pattern 是識別符本身不唯一，工具讀的載體正確，但用了一個假設唯一性的資料結構。前者換讀取來源即修，後者必須改主鍵。

## 症狀

- 某清單、索引或彙總的筆數少於來源檔案數，但差額不對應任何已知的排除規則
- 輸出內部完全自洽：無重複列、無死連結、統計數字互相吻合，靜態檢查全綠
- 程式碼中出現 `{item["id"] for item in rows}` 或 `seen = set()` 形式的去重，而 `id` 的唯一性從未被約束強制（無 unique index、無 assert、無 schema 保證）
- 上游對重複鍵的存在是**知情且接受**的（文件明文記載、註解標為已知情形），下游卻仍假設唯一
- 問題只在有人做交叉計數（來源數 vs 輸出數）時暴露，日常使用完全無感

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 識別符「幾乎」唯一 | 絕大多數情況一對一，重複是少數例外 | 寫程式時的心智模型是唯一鍵，測試資料也是唯一鍵 |
| 真實主鍵是別的東西 | 真正保證唯一的是檔案路徑 / 複合鍵 / 序號，識別符只是其中一個欄位 | 用識別符當鍵在語意上就錯，只是多數時候看不出來 |
| `set` / `dict` 的去重是靜默的 | 插入重複鍵不報錯、不回傳失敗，只是無事發生 | 資料丟失沒有任何執行期訊號 |
| 缺席不佔位 | 被丟的那筆從未進入輸出，輸出中沒有「應該有但沒有」的位置 | 事後檢查輸出無法發現缺漏，只能靠比對來源 |
| 上游的知情不會傳到下游 | 重複鍵被記錄在方法論或註解裡，但沒有轉成程式碼層的約束或測試 | 下游各自重新假設唯一，且互不知情 |

**為何「輸出自洽」是這個 pattern 最危險的性質**：多數資料缺陷會留下矛盾——重複列、死連結、對不上的計數。這個 pattern 不留任何矛盾，因為丟棄發生在輸出生成之前。任何以輸出為檢查對象的守衛（格式檢查、死連結掃描、schema 驗證）都會通過。唯一能發現它的方式是**跨越輸出邊界去數來源**，而這不是任何例行檢查會做的事。

## 案例：error-patterns README 索引丟失 7 個 pattern（2026-07-28）

`.claude/skills/error-pattern/lib/readme_index.py` 的 `merge_category_table` 以 pattern ID 建集合判定新舊：

```python
file_ids = {row["id"] for row in new_rows}          # L233
...
for row in new_rows:
    if row["id"] not in existing_ids:               # L243
        merged.append(render_row(row))
```

error-patterns 目錄中有 7 組 ID 碰撞（`ARCH-010`、`IMP-049`、`PC-010`、`PC-019`、`PC-020`、`PC-030`、`PC-105`），每組兩個內容完全不同的 pattern 共用一個 flat 號。碰撞來自 canonical 框架初次匯入（commit `f375ae6`）一次性繼承，且被 `error-pattern-numbering-methodology.md` L45 明文凍結——上游知情、刻意保留、禁止重編。

同 ID 的兩筆 `new_rows` 中，第一筆被判為新列加入索引後 `existing_ids` 即含該 ID，第二筆永遠不會被加入。結果是 7 個 pattern 在 README 索引中完全不可見。實例：`PC-019` 索引只有 `design-decision-memory-only` 一列，`worktree-merge-state-loss` 無列。

**同一去重邏輯也影響死連結移除**：碰撞雙方其一被刪除時，因另一檔仍使該 ID 留在 `file_ids` 中，殘留列不會被清掉。

> **後續更正（2026-08-09）**：上述七組中的 `ARCH-010` 事後查證**不是碰撞**。其 `module-assembly-omission` 一側早在 2026-05-04 已於上游重編為 `ARCH-021`，本庫的 `ARCH-010-module-assembly-omission.md` 是隨初次匯入殘留的孤兒重複檔（內容與 `ARCH-021` 實質等價），已刪除。凍結登記表同步改為 6 組（跨 2 category）。本案例的機制論述不受影響——去重丟棄的行為與計數差額的訊號價值皆成立，僅「碰撞組數」與該組的性質判定更正為：真碰撞 6 組、孤兒重複 1 組。此更正本身也印證本 pattern 的主張：差額能指出「有東西被丟掉」，但指不出被丟掉的是哪一類問題。

**發現路徑**：`0.2.1-W3-099` 收尾驗收時做了一次交叉計數——379 個 pattern 檔對應 372 個唯一 ID，README 索引 372 列且無重複、無死連結。三者「自洽」，差額 7 才是異常訊號。若不數這一次，索引可以永遠看起來是完整的。

**修復方向**（`0.2.1-W3-117`）：把 `merge_category_table` 與 `scan_category_rows` 的鍵從 pattern ID 改為可區辨碰撞雙方的複合鍵（`(id, slug)` 或檔案 stem），並保留既有列逐字原樣保留的保守 upsert 語意。

## 預防措施

1. **對每一個當作鍵使用的識別符，先問「什麼保證它唯一」**。答案必須是一個具體機制（unique constraint、檔名唯一性、分配器序號），不能是「目前看起來沒重複」。找不到機制就不是主鍵。
2. **上游明文接受重複時，該事實必須轉成下游的約束或測試**，不能只寫在方法論裡。文件層的知情不會自動傳導到程式層——本案例中碰撞被記載在方法論與某個 hook 的 docstring 中，但索引工具對此一無所知。
3. **去重點加碰撞情境測試**：測試資料必須含同鍵多筆，斷言兩筆都出現在輸出中。用唯一鍵的測試資料無法暴露這類缺陷。
4. **對「來源 → 輸出」的轉換加交叉計數**：輸出筆數與來源筆數的差額必須能被明確規則解釋，無法解釋的差額即為缺陷訊號。這是唯一能發現靜默丟棄的例行手段。
5. **靜默丟棄改為顯性記錄**：`set` 去重命中重複時至少寫一行 warning（quality-baseline 規則 4 可觀測性的延伸）。丟資料不可以是無聲的。

## 偵測方式

```bash
# 找出以 id 欄位建集合做去重/存在性判定的位置
rg -n '\{[a-z_]+\["id"\] for |\.add\([a-z_]+\["id"\]\)|\["id"\] (not )?in ' --type py

# 對任何以識別符為鍵的目錄，做來源數 vs 唯一鍵數的交叉計數
(cd <dir> && for f in */[A-Z]*.md; do basename "$f" .md | sed -E 's/^([A-Z]+-[0-9]+)-.*/\1/'; done \
  | sort | uniq -d)
```
