# ARCH-BAL-005：自證式豁免（豁免理由無消費者、無時效）

## 摘要

**一份豁免清單把「豁免哪些對象」與「為什麼豁免」放在兩個欄位，執行路徑只讀前者，後者沒有任何程式碼消費者。** 理由因此退化為裝飾文字：寫什麼都不改變豁免是否生效，寫錯也沒有任何管道會告訴你。豁免一經寫入即永久成立，既無驗證亦無時效。

關鍵在於這不是「有人忘了維護理由」。理由沒有讀者，也沒有到期日——維護與否不影響任何行為，因此不維護是這個資料結構下的理性行為。把它當成人的疏失去處置（加提醒、要求複查）不會改變任何事；要改變的是結構：讓理由接上消費者，或讓它會過期。

## 症狀

- 豁免清單的理由欄位在整個程式碼庫中 grep 零命中，只有寫入者，沒有讀取者
- 理由與事實脫節而長期無人察覺：對象已搬遷、已被繼任者取代、宣稱的呼叫方根本不存在
- 出現「寫入當下即為假」的理由（如在 Flutter 專案裡寫「Node.js 專案不適用」），且存活數月
- 某個豁免理由把一個問題正當化，使既有檢查對它閉嘴，缺陷因而潛伏
- 清單只有整檔一個 `last_updated`，無法分辨哪一條是新的、哪一條放了半年

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 決定與理由在結構上分離 | `exclude: [...]`（陣列）決定行為，`notes: {...}`（map）承載理由 | 兩者可任意漂移，資料結構不強制其一致 |
| 只有決定被消費 | 消費端只讀決定欄位，理由欄位從未被解析 | 理由是純裝飾。錯誤的理由與正確的理由對執行完全等價 |
| 理由無時效 | 無逐條時間戳，整檔單一 `last_updated` 且無法佐證 | 沒有任何時點會觸發複查，豁免永久生效 |
| 寫入門檻低於刪除門檻 | 新增一條豁免只需寫一句話；移除則需論證 | 清單單向增長，且增長的是無人稽核的部分 |

**理由無讀者的第二層後果**：理由不只無法阻止錯誤豁免，它還會反向掩護錯誤。一句「CLI 工具，透過 argv 使用」讓後續讀者停止追問「這個檔為什麼沒被註冊」，把一個未註冊的死碼包裝成一個有原則的例外。理由的可信度來自它看起來被審查過，而實際上它從未被任何東西審查過——這個落差正是它的危害所在。

## 案例：hook 豁免清單的 `notes` 欄位（2026-07-27）

`.claude/hooks/hook-exclude-list.json` 的形態：

    {
      "exclude": ["a.py", "b.py"],       <- 被消費，決定行為
      "exclude_patterns": ["*-backup.py"],
      "notes": { "a.py": "理由文字" }     <- 無消費者，純裝飾
    }

**理由零消費者**：`hook_checker.py` 的 `get_exclude_patterns()` 只讀 `exclude` 與 `exclude_patterns` 兩鍵。`grep -rn "notes" hook_checker.py hook-completeness-check.py` → exit 1（零命中）。

**12 條豁免理由的稽核結果**（`0.2.1-W3-035`，逐條實查）：

| 分組 | 條數 | 內容 |
|------|------|------|
| 理由屬實 | 2 | `dispatch_stats.py`（確為 argparse CLI）、`*-backup.py`（前瞻性防護） |
| 理由過期 | 7 | 5 條宣稱「被其他 Hook 引入」的檔案已搬遷至 `.claude/lib/`（其中 `hook_utils.py` 全 repo 已不存在）；`archived/*` 對 basename 比對恆假，寫了等於沒寫；`eval_pyyaml.py` 評估已結案而豁免仍在 |
| 理由從未成立 | 3 | `phase-contract-validator-hook.py`（宣稱 argv CLI，實測零 argv caller）、`dart-presence-detection-hook.py` 與 `test-timeout-post.py`（皆宣稱「Node.js 專案不適用」，而本專案為 Flutter/Dart） |

**掩護死碼的具體案例**：`phase-contract-validator-hook.py` 的理由「CLI 工具（透過 argv 使用），非 stdin JSON Hook」使 `hook-completeness-check` 對此檔閉嘴，把「未在 settings.json 註冊」正當化。實測全 repo 零 argv caller，settings.json 命中數 0——它不是 CLI 工具，是無人呼叫的死碼。理由把死碼包裝成合理例外，直到 `0.2.1-W3-023` 才暴露。後續稽核發現同型殘留檔另有兩個（`dart-presence-detection-hook.py` 已被 `presence-detection-hook.py` 取代、`test-timeout-post.py` 已被 `post-test-hook.py` 吸收），三者的豁免理由皆與「被繼任者取代」這個真實原因無關。

**兩條「Node.js 專案不適用」是模板污染的指紋**：依這兩條理由自身的邏輯，在 Flutter 專案裡這兩個檔應該要註冊而非豁免。理由在寫入當下就沒有針對本專案驗證過，而沒有任何管道會發現這件事。

**時效亦不存在**：`last_updated: 2026-03-08` 是整檔單一時間戳，且本 repo 為單一 squash import commit，git 無從佐證任一條目的新舊。時效與理由同屬自我宣告、無消費者、無驗證。

稽核詳見 `0.2.1-W3-035`；惰性條目清除見 `0.2.1-W3-037`；機制層落地屬 `0.2.1-W3-040`。

## 與相鄰 pattern 的邊界

三者的共同上位是「宣告層與執行層不一致」，但**失效的環節不同，處置手段因而不可互換**：

| Pattern | 兩層是什麼 | 失效環節 | 處置 |
|---------|-----------|---------|------|
| `ARCH-BAL-003`（判準與成員脫節） | 納入判準 vs 名單成員 | **同步**。判準有讀者（設計者依判準決定成員），只是新增對象時沒有機制提醒同步名單 | 定期以判準掃描候選集合，列出符合判準但不在名單內者 |
| `PC-BAL-010`（驗證管道對現象不敏感） | 檢查條件 vs 待驗現象 | **敏感度**。管道存在且會執行，但其輸出不隨待驗現象改變 | 人工檢視因果連結，重寫檢查條件 |
| 本模式（自證式豁免） | 豁免決定 vs 豁免理由 | **根本未接線**。理由連讀者都沒有，不存在可談的檢查條件 | 把理由接上消費者，或讓它會過期 |

讀者遇到新實例時的判別順序：先問「這個宣告有沒有任何程式碼讀它」——答案為否即本模式，且不必再談檢查條件是否敏感（沒有檢查條件可談）。答案為是，再問「讀它的那個檢查會不會隨事實改變結果」——否即 `PC-BAL-010`。兩問皆通過而仍出錯，才是 `ARCH-BAL-003` 的同步問題。

把本模式折入 `PC-BAL-010` 會使後者膨脹為「所有未經驗證的東西」而失去診斷價值（此判定由 `0.2.1-W3-035` 作出）。與 `IMP-BAL-003`（稽核端與消費端解析器嚴格度落差）亦相鄰而不同：該模式兩端都有解析，只是寬嚴不一；本模式是一端根本不解析。

## 防護

### 第一原則：不要靠提醒人維護

理由沒有讀者也沒有到期日，「請記得複查」對這個結構不產生任何作用力。防護只有兩條路——**接上消費者**（讓理由可被驗證）或**讓它過期**（讓不複查有可見後果）。走哪一條由宣稱類型決定。

### 依宣稱類型分流

先把自由文字的理由升級為結構化欄位，讓 `kind` 決定驗證器：

    "dart-presence-detection-hook.py": {
      "kind": "superseded_by",             // imported_lib / cli_tool /
      "by": "presence-detection-hook.py",  // superseded_by / one_off / backup
      "asserted_at": "2026-03-08"
    }

**可機械驗證者——接上消費者**：

| 宣稱類型 | 驗證手段 | 抓得到什麼 |
|---------|---------|-----------|
| 「被 X 引入」 | AST 或 grep 掃 importer，零 importer 即警告 | 對象已搬遷或已消失的惰性條目 |
| 「已被 Y 取代」 | 要求理由指名繼任者，驗證繼任者確實已註冊 | 未指名繼任者的空泛取代宣稱、繼任者本身也沒接上的情形 |
| 「專案類型不適用」 | 比對 `pubspec.yaml` 等專案標識 | **寫入時即為假的理由**。本案唯一能被機械抓到的那一類，且實作成本最低（比對一個字串），投報率最高 |
| 「透過 argv 使用的 CLI」 | 部分可：可驗證檔內確有 argparse 或 `sys.argv` 處理 | 結構不符者。無法驗證「真的有人用」——人工 CLI 無 caller 是正常狀態，不構成證偽 |

**不可機械驗證者——加時效**：「一次性評估腳本」這類純意圖宣告沒有事實對應物可查。對它寫「應該驗證」等於沒寫，強行找代理指標只會逼出假訊號。唯一有效的處置是逐條 `asserted_at` + 到期複查提示：超過 N 個月未重新確認即輸出警告。**時效必須逐條記錄**，整檔一個 `last_updated` 無法分辨哪條新哪條舊，等於沒有時效。

### 結構檢查（不碰理由語意，零誤判風險，可先做）

- **惰性條目偵測**：清單中不匹配任何真實對象的條目 → 警告
- **pattern 語法有效性**：比對對象為 basename 時，含 `/` 的 pattern 恆假 → 警告
- **理由覆蓋率**：決定欄位有條目而理由欄位無對應鍵 → 警告（防退化）
- **副本一致性**：同一份清單若有硬編碼 fallback 副本，兩者不一致 → 警告

### 界線：機制的職責是讓錯誤可見，不是自動修正

不建議做理由文字的自然語言分析，也不建議自動移除失效豁免。本案中 `dart-presence-detection-hook.py` 的**排除結論是對的，只是理由寫錯**——自動移除會誤傷。同理，理由驗證失敗應輸出警告要求人為判斷，不應直接改變豁免行為。

## 驗證方式

修正後確認：

- 理由欄位在程式碼中有實際讀取點（grep 該欄位名有非測試的消費者命中）
- 對每條豁免執行其 `kind` 對應的驗證器，全部通過或每個失敗項有明文追蹤
- 逐條 `asserted_at` 存在，且有機制在逾期時輸出提示
- 新增一條理由為假的豁免作為反向確認，驗證機制確實報錯（否則驗證器本身可能命中 `PC-BAL-010`）
