# ARCH-BAL-010：可選欄位的解析成敗決定記錄是否存在

## 基本資訊

- **Pattern ID**: ARCH-BAL-010
- **分類**: 架構設計（architecture）
- **來源版本**: v0.2.1
- **發現日期**: 2026-07-31
- **風險等級**: 高（資料集長期不完整而下游把它當全集使用，無任何告警）
- **影響範圍**: 任何「掃描來源集合產生索引 / manifest / 清單」的程式碼，特別是索引項含可選的描述性欄位時

## 摘要

**建立索引時把一個可選欄位（版本字串、標題、描述）的解析結果當成寫入條件，解析不到就整筆不寫入。** 記錄的存在與否於是取決於一個本應可有可無的欄位，來源集合中缺該欄位的成員從索引裡完全消失——不是欄位留空，是整筆不見。

下游讀索引的程式無從分辨「這個成員不存在」與「這個成員存在但沒被記錄」，因為兩者在索引裡的表現完全相同。缺漏因此不會觸發任何錯誤路徑，可以潛伏任意久。

## 症狀

- 索引的條目數少於來源集合的實際成員數，且差額固定不變
- 缺漏的成員全部具有同一特徵（缺某個可選欄位），但該特徵與「是否應被索引」無邏輯關聯
- 下游的狀態分類對缺漏成員無任何輸出——不是回報「未知」，是根本不進入迴圈
- 缺漏持續數週至數月無人察覺；修復後回頭查，缺漏成員的加入時間遠早於發現時間
- 修復往往是其他工作的副產物（重寫該函式時順手改變了寫入條件），而非針對缺漏本身

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 寫入條件與欄位解析耦合 | 形如 `if parsed: index[key] = parsed`（示意，非原文引用）— 解析成功才寫入 | 欄位的可選性被寫入條件取消，實際成了必填 |
| 索引項的型別是純量 | 條目值就是那個欄位本身（`{name: "2.7.0"}`） | 沒有「有這個成員但該欄位為空」的表達形式，缺欄位只能整筆不寫 |
| 缺漏無告警路徑 | `if` 不成立就往下一輪，沒有 else、沒有 log、沒有計數 | 缺漏與正常執行在輸出上不可區分 |
| 下游以索引為全集 | 消費端迴圈跑索引鍵集合 | 不在索引裡等於不存在，缺漏成員永遠不被處理 |

核心是**純量索引項沒有留下記錄存在性與欄位完整性的區分空間**。條目值即欄位值時，「欄位缺失」與「條目缺失」被迫共用同一種表達。

## 解決方案

### 結構調整

把索引項從純量改為物件，並分離必要欄位與可選欄位：

| 設計 | 寫入條件 | 缺欄位時的表現 |
|------|---------|--------------|
| 純量 `{name: version}` | 版本可解析 | 整筆消失 |
| 物件 `{name: {id: ..., version?: ...}}` | 必要欄位可計算 | 條目存在，可選欄位缺席 |

必要欄位應選「對來源成員恆可計算」者（內容雜湊、路徑），而非「作者可能沒寫」者（版本字串、描述）。

### 驗證方式

修復後比對索引條目數與來源集合實際成員數，兩者相等才算完整。差額不為零時逐項列出差集，不以「條目數增加了」為滿足。

## 預防措施

| 層級 | 措施 |
|------|------|
| 設計 | 索引項的必要欄位必須對來源集合恆可計算；可選欄位一律以「缺席」表達，不以「整筆不寫入」表達 |
| 實作 | 掃描迴圈中每個 `continue` / 未寫入分支都要有計數或 log，使跳過可觀測（對應 quality-baseline 規則 4） |
| 驗證 | 索引產生後斷言條目數等於來源成員數，不等即失敗或告警 |
| 審查 | 讀到 `if <parse_result>: index[key] = ...` 形式時，問「解析失敗的成員該不該在索引裡」——若該在，這就是本模式 |

## 實證案例

`skill-sync` 的 `versions.json` 記錄 49 個 skill，repo 實際有 55 個。差集為 `cc-release-impact-review`、`data-extraction`、`framework-issue`、`neurodivergent-output`、`saas-tech-selection`、`teaching-sync` 六項，其中五項自 2026-06-23 起即存在（`neurodivergent-output` 為 2026-07-21），歷時逾一個月無告警。逐項列名而非只給差額，是本檔驗證方式章節對自身的要求。

該檔位於上游 `tarrragon/claude-skills`，不在本專案內（本專案 `.claude/skills/` 是不同集合，數量亦不同，勿以本地目錄數對照）。重跑方式：

```bash
gh api repos/tarrragon/claude-skills/contents/versions.json --jq '.content' | base64 -d | python3 -c "import json,sys; print(len(json.load(sys.stdin)))"
gh api "repos/tarrragon/claude-skills/git/trees/main?recursive=1" --jq '[.tree[] | select(.path|test("^[^/]+/SKILL\\.md$"))] | length'
```

49 與 55 為 `0.2.1-W3-160` 執行當下的快照值；修復後兩數已相等，重跑會得到相同的兩個數字而非原始差額。

舊實作（`0.2.1-W3-131` 之前）：

```python
m = re.search(r"\*\*Version\*\*:\s*(\S+)", text)
if not m:
    m = re.search(r"^version:\s*(\S+)", text, re.MULTILINE)
if m:
    versions[name] = m.group(1)
```

（上為 `git show b0a6bde~1` 的逐字內容。關鍵在最後一行位於 `if m` 之內——抽不到版本字串即整條不寫入。）

那 6 個 skill 的 `SKILL.md` 無版本標註，於是整條消失。下游的 `_classify_sync_status` 迴圈跑索引鍵集合，對它們不輸出任何狀態——不是「未知」，是不存在。

修復是別的目的的副產物：`0.2.1-W3-131` 為了「版本字串不足以判定內容同一性」而改以內容雜湊為必要欄位、版本字串為可選，寫入條件因此與版本字串解耦，6 條自動補回。缺漏是在 `0.2.1-W3-160` 落地時比對前後條目數才被發現，不是被針對性修復的。新格式中這 6 條確實只有 `hash` 無 `version`，與成因互相印證。

**修復的邊界**：解耦的是「寫入條件與可選欄位」，跳過分支本身仍在。現行實作（`skill_sync/cli.py:105-106`）為：

```python
content_hash = compute_content_hash(skill_md.parent)
if content_hash is None:
    continue          # 無 log、無計數
```

觸發條件從「版本字串抽不到」換成「雜湊算不出」，但跳過即消失且不留痕跡這個結構沒有改變——正是本檔預防措施實作層要求排除的形態。目前該分支不可達（條目來源是 `*/SKILL.md` 的 `.parent`，目錄必然存在，而 `compute_content_hash` 僅在目錄不存在時回 None），但可達性依賴呼叫端的巧合而非分支自身的保證。此殘留已被識別，同時作為本檔預防措施的一個活反例。
