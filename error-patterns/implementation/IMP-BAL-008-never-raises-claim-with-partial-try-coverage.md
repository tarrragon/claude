# IMP-BAL-008: docstring 宣稱「永不拋出」，但 try 只包住前半段，消費資料的後半段在保護之外

## 摘要

**函式宣告不拋出例外時，保護邊界常只圍住「取得外部資料」的動作，而不圍住「消費那份資料」的動作；但外部資料的形狀不可信，消費端才是真正會炸的位置。** 撰寫者的心智模型是「危險 = I/O」，於是 `try` 包住 fetch、load、subprocess；解包、索引、迭代這些看似純粹的操作留在外面。當外部資料的型別或形狀不符預期，例外從保護之外逃逸，宣稱失效。

危害被執行位置放大：這類「永不拋出」的函式多半跑在主要工作完成之後（收尾報告、清理、統計），例外逃逸的結果是已成功的操作以非零碼結束並噴出 traceback，使用者看到的是失敗，而實際上該失敗的只是那份附加資訊。

## 症狀

- docstring 或註解出現「永不拋出」「不會中斷」「失敗降級為警告」這類承諾
- `try` 區塊只有二至三行，涵蓋 fetch / load / import，其後的處理邏輯在區塊之外
- 被消費的資料來自網路、檔案、或他模組的回傳值，型別註解宣告為 `dict` 但實際來源是 `json.loads`（可回傳任何型別）
- 對回傳值做元組解包、字典索引、或迭代，且無型別守衛
- 測試只覆蓋「取得階段失敗」（網路不通、檔案不存在），未覆蓋「取得成功但內容形狀不符」
- 該函式的呼叫點位於主要流程成功之後

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 危險的心智模型錯位 | 撰寫者把「危險」等同於「I/O」 | `try` 邊界劃在 I/O 結束處，而非資料消費結束處 |
| 型別註解給了虛假保證 | `-> dict` 標在實際可回傳任意型別的函式上 | 下游依註解假設形狀，不加守衛 |
| 解包與索引看似安全 | `a, b, c, d = f()`、`d["key"]` 語法上不像 I/O | 不觸發「這裡需要保護」的直覺 |
| 跨模組回傳值的形狀無契約 | 上游可自由變更回傳元組的長度或字典的鍵 | 上游一改，下游解包即 `ValueError` |
| 測試沿著撰寫者的心智模型寫 | 測「網路不通」而非「回傳 `null`」 | 未覆蓋處恰是宣稱最可能破的地方 |

**與一般例外處理不足的差別**：一般不足是沒寫 `try`，缺口顯而易見；本 pattern 有 `try`、有 docstring 承諾、有針對降級路徑的測試，三者共同構成「已處理」的外觀，缺口在外觀之下。

## 案例：push 收尾的漂移報告（2026-08-08）

### 事件

某腳本在推送成功後執行一份資訊性檢查，函式 docstring 明寫：

> 永不拋出：本函式在 push 成功之後執行，檢查失敗只代表少了一份資訊，不該讓已完成的推送看起來像失敗。

`try` 涵蓋「載入他模組 + 取得遠端 manifest」三行；其後的分類呼叫、四元組解包、迭代格式化全在區塊之外。分類函式內部對 manifest 呼叫 `.get()`，假設其為 dict。

### 實證

審查者注入 list 型的遠端回應：

```
fetch_remote_skill_manifest → ['a','b']
結果: RAISED past the guard: AttributeError 'list' object has no attribute 'get'
```

該呼叫點所在的外層 `try` 只接特定的 timeout 例外，因此例外會在「成功推送」訊息已印出之後噴 traceback 並以非零碼結束——正是 docstring 承諾要避免的情境。

### 附帶缺口

同一函式對「取得成功但內容為空」也無守衛：遠端回 200 但內容為 `{}` 時，全部項目落入「無遠端雜湊」分類，報告輸出「一致 0、分歧 0、無遠端雜湊 N」，讀起來像檢查通過，實際上什麼都沒比對。這與例外逃逸互補——一個炸得太響，一個安靜得像成功。

## 防護

| 時機 | 動作 |
|------|------|
| 寫下「永不拋出」類承諾時 | 把承諾當作待驗證的斷言：逐行檢視函式體，任何在 `try` 之外的解包、索引、迭代、屬性存取都是反例 |
| 決定 `try` 邊界時 | 邊界劃在「最後一個消費外部資料的操作」之後，而非「取得外部資料」之後 |
| 消費 `json.loads` 的結果時 | 先做型別守衛（`isinstance(x, dict)`）再消費；型別註解不構成保證 |
| 解包他模組回傳的元組時 | 視為契約點：若無測試釘住 arity，該解包應在保護範圍內 |
| 為降級路徑寫測試時 | 除了「取得失敗」，必須另有「取得成功但形狀不符」與「取得成功但內容為空」兩類 |
| 降級訊息的內容 | 帶上例外型別（`type(e).__name__`）與失敗階段，否則契約破損與網路不通會呈現為同一行文字，無從分辨該重試還是該修安裝 |
