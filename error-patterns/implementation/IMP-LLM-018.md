# IMP-LLM-018: 只報告的掃描改為阻擋閘門時，沿用的掃描函式把逐項失敗放進降級結果通道，閘門不讀而放行

## 基本資訊

- **Pattern ID**: IMP-LLM-018
- **分類**: 實作（implementation）
- **風險等級**: 高（閘門宣稱 fail-closed，實際對逐項失敗放行；測試全綠，要讀到被沿用的掃描函式才看得出來）
- **來源版本**: 3.5.0
- **相關 Pattern**: IMP-GPD-005（姊妹：失敗以例外形式被外層吞成放行；本則的失敗沒有例外，是正常回傳）、IMP-BAL-005（錯誤訊號只被顯示、不參與判定）、IMP-APP-005（驗證工具對空輸入集回報通過）

---

## 問題描述

**名詞**：「降級結果通道」指掃描函式回傳值裡專門收納「這一項沒有處理成功」的欄位或分類，例如 `unreadable`、`skipped` 清單，或把查詢失敗歸進某個無害分類。函式透過它回報逐項失敗，不拋例外。

### 症狀

- 一個原本只輸出報告的掃描被改成阻擋閘門：有命中就中止
- 閘門用 try/except 包住整體掃描，掃描拋例外就阻擋，並宣稱「掃描失敗即阻擋（fail-closed）」
- 閘門的判定只讀命中欄位（例：`result.files`），沒有讀降級結果通道
- 某一項讀取失敗時（權限錯誤、非 UTF-8 內容、子程序失敗），該項未被掃描，閘門照樣放行
- 閘門的測試全綠：測試涵蓋「有命中 → 擋」「整體掃描失敗 → 擋」「無命中 → 放行」，沒有「某一項讀不到」的輸入

### 根因

被沿用的掃描函式是為報告設計的。報告的需求是韌性：一個檔案讀不到，不應讓整份報告中止，所以函式把逐項失敗收進降級結果通道，繼續掃其餘項目。這是報告情境下的正確設計。

改成閘門時，失敗的安全方向反過來了：

| 消費者 | 逐項失敗時的安全方向 |
|-------|-------------------|
| 報告 | 繼續掃描、在報告中列出未掃描項 |
| 阻擋閘門 | 視為無法確認，阻擋 |

改造者只處理了「失敗以例外出現」的出口，因為那是閘門自己的程式碼裡看得見的出口。降級結果通道在被沿用函式的回傳結構裡，閘門程式碼看不到它，它的語意便沿用報告的「繼續」，落到閘門就成了放行。

同一機制的變體：失敗沒有進入獨立欄位，而是被歸進某個正常分類。例如「查不到刪除紀錄即視為未刪過、偏向保留」，對刪除動作是安全的方向，對「有待刪項就要求明示」的閘門則是放行方向。安全方向取決於消費者，函式內部的「偏向保留」不能直接沿用到新的消費者。

### 為何難以察覺

- 閘門的 except 子句讓人以為失敗都已處理；降級結果通道不是例外，不會經過它
- 失敗方向是放行，放行與「輸入本來就沒有命中」在輸出上同形
- 改造的 diff 只含閘門端；被沿用函式沒有改動，審查不會讀到它的回傳結構
- 測試從閘門的視角設計，只會想到閘門程式碼裡出現的分支

## 解決方案

### 改造時盤點被沿用函式的所有非例外失敗出口

把只報告的掃描改成閘門前，讀被沿用函式的回傳結構與內部的 except 子句，列出每一個「這一項沒有處理成功，但函式照常回傳」的出口：

- 回傳結構裡的旁路欄位（`unreadable`、`skipped`、`errors`、`warnings`）
- 內部 except 子句的落點：`continue`、`append` 到某清單、回傳預設值、回傳某個分類
- 子程序回傳碼非 0 時的處理（回傳空集合、False、「未知」）

每一個出口在閘門端逐一判定：阻擋、放行（寫明理由），或改由新的回傳欄位明示。

### 閘門以單一判定屬性收斂所有通道

在結果型別上提供一個閘門專用的判定，涵蓋命中欄位與所有降級結果通道，閘門只讀它：

```python
@dataclass
class VersionCheck:
    mismatches: list
    skipped: list
    missing_authority: list

    @property
    def ok(self) -> bool:
        return not (self.mismatches or self.skipped or self.missing_authority)
```

之後在結果型別新增降級通道時，新增者同時要更新 `ok`，閘門端不需要改。

### 正向對照包含逐項失敗的輸入

閘門測試至少含一個「整體掃描成功、但某一項讀不到」的輸入，斷言閘門阻擋。這個輸入要能從閘門入口跑到被沿用的掃描函式，不在閘門層 mock 掉掃描結果。

## 預防措施

| 時機 | 做法 |
|------|------|
| 把報告、提醒、WARNING 類輸出升級為阻擋 | 範圍宣告列入被沿用的掃描函式；盤點其非例外失敗出口後，再寫閘門判定 |
| 審查宣稱 fail-closed 的閘門 | 不只看閘門的 except 子句，追到被呼叫函式的回傳結構，確認每個降級通道都有判定 |
| 函式內部帶「偏向保留」「偏向放行」這類預設 | docstring 寫明此偏向是對哪個消費者而言；新消費者沿用前重新判定方向 |
| 撰寫閘門測試 | 依 `.claude/rules/core/test-assertion-design-rules.md` 規則 E2，正向對照輸入要涵蓋每一種失敗出口，不只「有命中」與「整體失敗」 |

## 案例

### 案例 1：推送前規則 8 檢查（本則來源）

框架發版推送腳本 `.claude/scripts/sync-claude-push.py` 原本在推送前輸出規則 8（框架禁引用專案層級識別符）的報告，不阻擋。改為阻擋時：

- 判定沿用 `.claude/scripts/rule8-stock-report.py` 的 `scan`，有未豁免命中即中止推送
- 守衛載入失敗、`git diff` 失敗以例外出現，閘門的 except 子句接住後阻擋
- `scan` 讀檔遇 `OSError` 或 `UnicodeDecodeError` 時，把該檔放進 `ScanResult.unreadable` 後繼續，註解寫「列入報告，不中止」
- 閘門只讀 `result.files`，待推送檔讀不到時未經掃描即放行

測試全綠。合入前審查讀到 `scan` 的回傳結構時發現，補上 `_report_unreadable`：`unreadable` 非空即列出檔案並阻擋。

### 案例 2：真孤兒推送前阻擋（同型變體，失敗被歸進正常分類）

同一腳本另一項改造：遠端有「本地已刪除」的孤兒檔、且推送未明示 `--clean` 或 `--no-clean` 時，推送前中止。孤兒清單沿用 `--clean` 的刪除判定。判定中查本地刪除紀錄的 `git log` 回傳碼非 0 時，函式回傳「未刪過」，該檔被分類為「可能為他方貢獻，保留」，不進孤兒清單。

對 `--clean` 而言，這個「偏向保留」是安全方向，可避免誤刪。對新閘門而言，查詢失敗的檔不算孤兒，閘門不要求明示，推送照舊放行。後果較案例 1 輕：放行後的行為與改造前相同（遠端留下孤兒），不會讓禁止的內容外流。

### 對照：版本住址一致性閘門（正確做法）

skill 版號住址的一致性檢查從一開始就為閘門設計：讀不出版號的住址一律放進 `skipped`，不當成一致；結果型別的 `ok` 要求分歧、`skipped`、缺權威欄位三者皆空，閘門測試只斷言 `ok`。每一條 `skipped` 路徑各有一個正向對照輸入。
