# IMP-LLM-003: 以環境變數做一次性交接，讀取端讀後不移除，變數被子行程繼承；新版讀取端遇上舊版生產端時，失敗只在合併閘門出現

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | implementation |
| 來源版本 | 3.1.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-11-10 |

**判準**：環境變數若只用來做一次性交接，讀取端讀完就要移除它（`os.environ.pop`），不能只讀（`os.environ.get`）。

## 症狀

shim 以 `VAR=$(pwd) exec <cli>` 把呼叫者的 cwd 傳給 CLI，CLI 讀到後 chdir。這種寫法有兩種失敗形態：

| 形態 | 徵狀 |
|------|------|
| 讀後不移除 | CLI 再啟動的子行程（測試閘門的 pytest、git hook）會繼承這個變數。子行程只要在 import 時或入口處讀到它，就會跟著 chdir。結果測試跑在錯的目錄，相對路徑變成 `../../../...` |
| 新舊版混用（自舉） | 合併閘門用 main 上的舊版 CLI 驗證分支。舊版 CLI 是生產端，不讀也不移除這個變數；分支上的新版程式碼是讀取端，會讀它並 chdir。結果本機直接跑測試全綠（環境裡沒有這個變數），只有在閘門裡會紅燈。紅燈出現在與本次修改無關的測試檔 |

## 根因

交接用的環境變數一旦設定，生命週期就延伸到整棵子行程樹，不止於交接的那一層。讀取端只讀不移除，等於把交接的值廣播給所有下游。

新舊版混用時，生產端與讀取端分屬不同版本。只修讀取端的那一版，要到合併之後才會被生產端使用。合併前的閘門環境，同時具備「舊生產端漏出變數」和「新讀取端會讀這個變數」兩個條件，這組合在合併前後都不存在，只存在於閘門裡。

## 解決方案

1. 讀取端一律用 `os.environ.pop(VAR, None)`：讀一次就移除，子行程看不到。
2. 會直接呼叫 CLI 入口（`main()`）的測試，在 conftest 加 autouse fixture：`monkeypatch.delenv(VAR, raising=False)` 加上 `monkeypatch.chdir(os.getcwd())`。測試不得依賴環境裡碰巧存在的交接變數。
3. 縱深防禦：閘門 spawn 測試子行程時，從複製出來的 env 移除這類變數。

## 預防措施

- 新增交接用環境變數時，同時加兩個測試：讀取後 `os.environ` 不再含有該變數；之後啟動的子行程也看不到該變數。測試方式：`subprocess.run([sys.executable, "-c", "import os;print(os.environ.get(VAR))"])` 應印出 `None`。
- 分支若修改閘門本身用到的工具（CLI、shim），驗收前要用「帶該變數」的組合在本機重跑一次，模擬閘門環境。不帶變數的本機綠燈不能當作閘門會綠的依據。

## 驗證方式（本次）

- 讀後不移除：新增的兩項斷言放在修正前的實作上跑，9 failed（3 個實作 × 讀後移除與子行程不可見）。
- 自舉：帶變數跑「直接呼叫 main() 的測試檔 + 依賴 cwd 的測試檔」是 13 failed；用 `env -u` 去掉變數後是 98 passed，與閘門的失敗數一致。加上 conftest 隔離後重送閘門，四個套件全綠。
