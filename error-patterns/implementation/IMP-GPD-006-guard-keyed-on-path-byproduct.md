# IMP-GPD-006: 守衛以某條實作路徑的副產物判定操作類型，另一條合法路徑不產生該副產物而被誤擋

## 基本資訊

- **Pattern ID**: IMP-GPD-006
- **分類**: 實作（implementation）
- **風險等級**: 高（同一判定點兩個方向都錯：合法操作被擋，違規操作被放行；且成功案例遮蔽缺陷）
- **來源版本**: 0.5.0
- **相關 Pattern**: DOC-GPD-005（判準以類別名為鍵，新成員繼承舊裁決；本模式的鍵是副產物而非類別名）、PC-169（合併中斷後的空合併 commit；同樣與 MERGE_HEAD 有關，但屬操作流程，不是判定依據）、IMP-GPD-008（守衛只認得無全域選項的 git 字面；與本模式的變體共用「框架規範寫法正是守衛的盲區」這一層未發現機制）

---

## 問題描述

### 症狀

- 守衛要判斷「這次寫入是不是合併」，以給合併豁免。判定依據是「MERGE_HEAD 是否存在」
- 用 `git merge` 合併時 MERGE_HEAD 會出現，豁免正常
- 另一條合法的合併路徑：以 `merge-tree --write-tree` 加 `commit-tree` 產生雙 parent commit，再用 `update-ref` 寫入（CAS 合併）。這條路徑刻意不碰共用 index，因此不建立 MERGE_HEAD。守衛判定為「非合併」，只要合併內容含非豁免路徑就擋下
- 反方向同時成立：MERGE_HEAD 殘留時，一筆單 parent 的普通提交會被判定為「合併中」而放行

### 根因

判定依據取自「某一條實作路徑的副產物」，不是被判定對象本身的屬性：

| 依據 | 性質 | 兩條路徑下的值 |
|------|------|--------------|
| MERGE_HEAD 是否存在 | `git merge` 這條實作的副產物，屬工作區狀態 | `git merge` 有；CAS 合併沒有 |
| 新 commit 的 parent 數 | 被寫入的 commit 本身的屬性 | 兩條路徑都是 2 |

副產物與「是否為合併」只在單一實作路徑下同時出現。新增一條刻意不產生副產物的合法路徑後，兩者就脫鉤了。

### 缺陷為何長期未被發現

CAS 合併多數只動到豁免路徑（框架檔、文件），豁免路徑本來就不需要合併豁免，所以合併照樣成功。第一筆含產品檔的 CAS 合併才暴露缺陷。在此之前的成功案例全部落在「不需要該豁免」的子集裡，看起來像豁免運作正常。

---

## 解決方案

判定依據改為被判定對象本身的屬性：逐 commit 讀 parent 數，大於 1 才算合併。副產物（MERGE_HEAD）只保留給它真正對應的用途，例如提示「MERGE_HEAD 已寫入、不會隨本次 deny 撤銷」。

| 情境 | 依副產物 | 依對象屬性 |
|------|---------|-----------|
| CAS 雙 parent 合併，含非豁免檔 | 擋（誤擋） | 放 |
| MERGE_HEAD 殘留，單 parent 提交 | 放（誤放） | 擋 |
| `git merge` 雙 parent | 放 | 放 |
| `git merge --squash` 單 parent | 擋 | 擋 |

---

## 變體：以執行者的位置推導判定範圍

**核心**：判定依據取自「執行者在哪裡」，不是「被寫入的目標在哪裡」，屬同一根因的另一種代理屬性。

- **症狀**：Bash 寫入邊界守衛以 payload 的 cwd 推導所屬 checkout，只把落在該 checkout（及其內嵌 worktree 目錄）的路徑換算成相對路徑再判定範圍。worktree 工具的預設版面是主 checkout 同層的 `<repo>-<ticket>` 目錄；派發的代理人以主 checkout 為 cwd、用絕對路徑寫同層 worktree 時，目標不在 cwd 所屬 checkout 內，守衛換算失敗後直接放行，連最基本的 `echo x > <worktree>/lib/a` 也放行。反方向（cwd 在同層 worktree、絕對路徑寫主 checkout）同樣放行
- **根因對照**：

| 依據 | 性質 | 同層 worktree 版面下的值 |
|------|------|----------------------|
| cwd 所屬 checkout | 執行者的位置 | 主 checkout，與目標無關 |
| 目標路徑所屬 checkout，且與 cwd 同屬一個 repository（git common dir 相同） | 被寫入目標本身的屬性 | 同層 worktree，判定成立 |

- **為何未被發現**：測試 fixture 只建守衛假設的版面（cwd 即 worktree、或 worktree 在 checkout 內的子目錄），而框架的標準派發版面正是守衛不認得的形態。這與 IMP-GPD-008 的未發現機制同構：框架規範的寫法（`git -C`、同層 worktree 加絕對路徑）是守衛最常遇到、也最先失效的輸入
- **解法**：對每個解析後的絕對路徑找出它自身所屬的 checkout 根，以 git common dir 比對是否與 cwd 所屬 checkout 同一個 repository；同 repo 即以目標的 checkout 為根套用既有範圍判定。common dir 直接讀 `.git` 目錄或 gitlink 檔的 `commondir`，不在熱路徑呼叫 git 子行程
- **預防**：守衛測試的 fixture 至少要有一筆採用框架工具實際產生的版面（例如以 worktree 工具或 `git worktree add` 建出的真實同層 worktree），不能只用守衛自己假設的目錄結構
- **第二例（派發驗證守衛）**：派發前檢查 prompt 中 `.claude` 絕對路徑的守衛，前提是「repo 外的 worktree 內 `.claude` 會被 runtime 拒絕」，因此把 checkout 根目錄以外的 `.claude` 路徑一律判為外部而阻擋。框架標準版面的同層 worktree 位於 checkout 根目錄之外，代理人在該處編輯 `.claude` 實際可行，守衛卻擋下寫出該路徑的 prompt；prompt 文字中的佔位路徑也被當成具體路徑。此缺陷會阻擋其自身修正的派發——派發修正票時以文字描述測試範例即被擋。解法同上：以目標所屬 checkout 與 git common dir 判定同 repo，再依 runtime 的實際限制（repo 外位置）決定是否阻擋，判定失敗落在阻擋側

## 預防措施

1. **設計判定依據時自問**：這個訊號是被判定對象本身的屬性，還是某條實作路徑順帶產生的狀態？若是後者，列出所有能達成同一操作的路徑，逐一確認訊號是否都會出現
2. **新增實作路徑時反查**：新路徑刻意省略某個副產物（不碰 index、不建狀態檔、不寫日誌）時，搜尋哪些守衛讀那個副產物
3. **測試必須包含需要該豁免的案例**：豁免邏輯的正向對照要用「沒有豁免就會被擋」的輸入（例如含非豁免路徑的合併），不能只用本來就會放行的輸入。只用豁免路徑測試，豁免壞掉也全綠（`.claude/rules/core/test-assertion-design-rules.md` E2）
4. **成功紀錄不等於判定正確**：一連串成功若都落在「不需要該判定」的子集內，不能當作判定有效的證據
