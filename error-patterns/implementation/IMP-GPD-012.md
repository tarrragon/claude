# IMP-GPD-012: 以為在函式型別加選填參數可向後相容，既有實作端（測試替身）卻因此不再符合型別

## 基本資訊

- **Pattern ID**: IMP-GPD-012
- **分類**: 實作（implementation）
- **風險等級**: 中（修改範圍在規劃階段被低估，執行時才發現要改的檔超出票面範圍；編譯期即可攔下，不會靜默進入產品）
- **來源版本**: 0.5.0
- **相關 Pattern**: 無

---

## 問題描述

### 症狀

- 規劃時寫下「在函式型別別名（typedef）上加一個選填參數，既有呼叫端與測試替身都不必改」
- 呼叫端確實不必改；但所有「提供」這個型別的函式（預設實作、測試以 override 注入的替身閉包）都不再符合新型別，全部編譯失敗
- 這些替身散布在多個測試檔，通常不在票面的修改範圍內，實作者只能停手回報

### 根因

「加選填參數向後相容」只對**呼叫端**成立，對**實作端**不成立。函式型別的參數是逆變的：

| 角色 | 加選填參數後 | 原因 |
|------|------------|------|
| 呼叫端（呼叫這個型別的函式） | 不受影響 | 不傳新參數仍合法 |
| 實作端（被當作這個型別使用的函式） | 不再符合型別 | 新型別承諾「呼叫者可以傳這個參數」，舊函式不接受它 |

Dart 與 TypeScript（strictFunctionTypes）都是這個規則；具名選填參數也一樣。規劃者通常從呼叫端的角度思考「加參數」，忽略了以函式值形式注入的實作端，而依賴注入框架（例如以 provider 覆寫函式）正好讓實作端大量出現在測試裡。

---

## 解決方案

依實作端的數量與位置擇一：

1. **實作端少且都在修改範圍內**：直接在型別上加參數，一併更新所有實作端
2. **實作端多或分散在範圍外**：型別不變，改走獨立通道。例：要讓掃描函式回報進度，不改掃描函式的型別，改由擁有掃描流程的物件提供進度入口，預設實作在內部接上；替身不回報進度，屬可接受行為

## 預防措施

- 規劃「在函式型別加參數」前，先以 grep 列出所有提供該型別的地方（預設實作、`overrideWithValue`／`overrideWith` 注入的閉包、mock），數量計入修改檔數
- 票面不要寫「既有實作不必改」，除非已區分呼叫端與實作端並逐一確認

## 實例

一個 Flutter App 要在 Domain 載入中顯示「已處理 N 個節點」。PM 規劃在掃描函式的 typedef 加選填的 `onProcessed` 回呼，並在票面寫「既有呼叫端與測試替身不必改」。實作者盤點時發現：散在 3 個範圍外測試檔裡的替身閉包會編譯失敗。停手回報後，PM 改採獨立進度通道，typedef 不變。
