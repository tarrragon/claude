# IMP-BAL-009: 對非 UTF-8 檔案 grep 非 ASCII 關鍵字，0 命中被當成語意結論而非前提失效

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 首次發現 | 2026-08-10 |
| 適用範圍 | 任何對下載檔案做非 ASCII 關鍵字搜尋的情境，外語一手資料查證為高發區 |
| 偵測成本 | 低（`file -I` 一次呼叫，或 ASCII 錨點反證） |

## 摘要

**grep 做的是位元組比對，不是字元比對。** 以 UTF-8 編碼的「射場安全」去比對 Shift_JIS 編碼的檔案，兩者位元組序列完全不同，命中數必然為 0——與該檔案是否真的含有這個詞無關。

危害不在於 0 這個值本身，而在於它的外觀：0 命中讀起來像「這份資料裡沒有這個詞」這種具體、可引用的語意發現，實際上是「我根本沒有在讀這份資料」的前提失效。前提失效偽裝成語意結論，後續推論全部建立在空地上，且每一步都自洽。

這是 [[guard-must-parse-ssot-with-consumer-parser]] 的同構情形：用錯的解析器得到的「發現」，會遮蔽「解析器根本不匹配」這件事。

## 症狀

- 對已知主題明確的檔案 grep 主題關鍵字，命中數為 0
- 同一檔案 ASCII 關鍵字（`href`、`charset`、`<title>`）有命中，非 ASCII 關鍵字全部為 0
- `file -I` 回報 `charset=unknown-8bit`，或 HTML meta 宣告非 UTF-8
- 檔案來源為日文、簡體中文、韓文的舊站台，或政府機關 / 研究機構的長年未改版頁面（Shift_JIS、EUC-JP、GB2312、Big5 常見）
- 終端印出的內容出現規律性亂碼，而非隨機二進位雜訊
- 因 0 命中而改變了搜尋方向（「這頁沒有，換一個來源找」），且新方向也沒有結果

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| grep 的比對層級 | 位元組序列比對，不做編碼正規化 | 編碼不同即不命中，無警告、無錯誤碼 |
| 0 是合法回傳值 | 「找不到」與「找錯對象」共用同一個輸出 | 兩種本質不同的情形無法從輸出區分 |
| 非 UTF-8 在特定語系圈仍普遍 | 日本政府機關、JAXA 等站台長年沿用 Shift_JIS | 查外語一手資料時命中率高，且正是最需要精確引用的場合 |
| ASCII 部分照常可讀 | HTML 標籤、URL、數字全部正常顯示 | 檔案「看起來讀得到」，不觸發編碼懷疑 |
| 0 命中的語意誘導 | 空結果易被讀成「已查證，不存在」 | 前提失效被記述為查證結論，並向下游傳播 |

**與一般搜尋失敗的差別**：一般搜尋失敗是關鍵字選得不好，換詞會有命中；本 pattern 換再多同義詞都是 0，因為問題不在詞彙層而在位元組層。持續換詞會強化「這份資料真的沒有」的錯誤信心。

## 案例：查證 JAXA 發射管制隊編組（2026-08-10）

### 事件

為查證某分類的出處，下載 JAXA 頁面 `jaxa.jp/countdown/f13/column/index_j.html` 後 grep 日文組織名稱，結果為：

```
打上げ管制隊: 0
気象班: 0
施設設備班: 0
射場安全: 0
飛行安全: 0
```

據此判定「index 是目錄頁，不含實質內容」，並轉而尋找子頁面。接著 grep `href` 抽連結，同樣是 0，才出現矛盾——一份 17 KB 的 HTML 不可能沒有任何 `href`。

### 實證

```
$ file -I f13col.html
text/html; charset=unknown-8bit
$ LC_ALL=C grep -aoiE 'charset=[a-zA-Z0-9_-]+' f13col.html
charset=Shift_JIS
```

`iconv -f SHIFT_JIS -t UTF-8` 轉碼後重跑同一組 grep：

```
打上げ管制隊: 9
施設設備班: 2
射場安全: 3
班: 30
```

該頁不僅含有目標內容，而且是整個查證中最關鍵的一手證據來源。

### 附帶觀察

`href` 的 0 命中是本次的救援訊號，但它出於偶然——當時抽連結是為了找子頁，不是為了驗證編碼。若第一次 grep 恰好只查了非 ASCII 關鍵字就停手，錯誤結論會直接進入產出。**ASCII 錨點反證需要成為主動步驟，不能依賴碰巧。**

## 防護

| 時機 | 動作 |
|------|------|
| 下載檔案後、第一次 grep 前 | 先 `file -I`；HTML 另查 `LC_ALL=C grep -aoiE 'charset=[a-zA-Z0-9_-]+'`（meta 宣告本身是 ASCII，不受編碼影響必可讀） |
| 非 ASCII 關鍵字得到 0 命中 | 一律先當編碼嫌疑，不當查證結論。轉碼後重跑，才有資格說「這份資料沒有」 |
| 驗證檔案確實有內容 | 用純 ASCII 錨點反證（`href`、`charset`、`<title>`、`{`）。ASCII 有命中而非 ASCII 全 0，幾乎必為編碼不符 |
| 轉碼 | `iconv -f SHIFT_JIS -t UTF-8`；失敗改 `iconv -c -f CP932`（CP932 為 Shift_JIS 超集，`-c` 丟棄無法轉換的位元組） |
| 引用外語一手資料前 | 逐字引用的前提是確實讀到了原文位元組；未確認編碼即引用，等同引用未讀過的來源 |
