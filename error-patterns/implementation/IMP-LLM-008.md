# IMP-LLM-008: fail-open 的 try 範圍涵蓋訊息組裝，訊息部分新增可失敗的邏輯會把已定的阻擋翻成放行

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 高 |
| 首次發現 | 2026-11-13 |
| 來源版本 | 3.3.0 |
| 適用範圍 | 呼叫端以 `try/except` 包住「判定函式」並在例外時放行（fail-open）的守衛 hook；判定函式同時回傳阻擋理由文字者為高發區 |

## 症狀

- 守衛原本恆擋某類輸入，改動只動到阻擋訊息的內容（例如依環境改寫訊息裡的建議命令），diff 看起來與判定無關
- 改動帶進可拋例外的新呼叫（import、檔案系統走訪、外部命令），例外發生時，原本該擋的輸入被放行
- 測試全綠：既有測試只走「訊息組裝成功」的路徑，沒有讓訊息組裝拋例外的案例
- 放行時通常只在 stderr 留一行「判定失敗，fail-open」，與真正的判定失敗同形，事後看不出是訊息出錯

## 根因

1. **判定與訊息共用一個回傳值**：`build_block_reason()` 回傳 `None` 表示放行、回傳字串表示阻擋，阻擋理由的文字就在判定函式內組好。函式內任何一行拋例外，都會讓整個函式沒有回傳值。
2. **呼叫端的 fail-open 不分例外來源**：`except Exception: block_reason = None` 是為了「判定本身出錯時寧可漏擋」而設計，但它攔下的是整個函式的例外，包括判定已經做完、只是訊息組不出來的例外。
3. **改動者把訊息當成無副作用的部分**：在訊息組裝裡加入可失敗的邏輯時，改動者的心智模型是「只改訊息內容」，不會想到訊息失敗會沿著 fail-open 路徑改掉判定結果。

三者組合後，判定已經得出「阻擋」，卻因為後續的文字組裝出錯而被呼叫端改成「放行」。

## 解決方案

訊息組裝中可失敗的部分，就地用 `try/except` 包住並退回固定文字，不讓例外離開判定函式：

```python
def _rewrite_hint(project_dir: str) -> str:
    try:
        from lib.launcher import launch_argv
        return " ".join(launch_argv(["tool", "test"], project_dir))
    except Exception as exc:  # 只影響訊息內容：退回固定寫法，阻擋照舊
        sys.stderr.write("改寫判定失敗，退回預設寫法: {}\n".format(exc))
        logger.error("改寫判定失敗，退回預設寫法: %s", exc)
        return "tool test"
```

並加一個測試：讓訊息組裝拋例外（monkeypatch 該呼叫），斷言結果仍是阻擋。以拿掉 `try` 的變異副本跑這個測試，應該要失敗。

## 預防措施

- **審查放寬類改動時，追到呼叫端的 except**：判定函式被 fail-open 包住時，函式內每一個新增的可失敗呼叫都要問「它拋例外時，呼叫端會把結果當成什麼」。只看 diff 內的行看不出來，因為 fail-open 在 diff 範圍之外。
- **訊息與判定分離**：判定函式回傳列舉或布林，訊息由另一個不會改變判定的函式組裝；或在判定函式內，訊息組裝一律自帶 fallback。
- **守衛測試補「訊息組裝失敗」案例**：凡是阻擋訊息含動態內容的守衛，測試要有一個讓動態部分拋例外、仍斷言阻擋的案例（對應 `test-assertion-design-rules` 規則 E2 的正向對照）。

## 實例

- 改寫阻擋訊息時，在訊息組裝中加入 import 與外部判定，例外會被呼叫端的 fail-open 吞掉，原本恆擋的命令因此放行。合併前審查攔下，改為就地 try 並退回固定文字。
- 守衛新增「讀專案覆寫檔、合併到判定設定」的步驟，合併函式已處理列舉得到的錯誤，但呼叫點沒有包 try，守衛整支也不是 fail_closed；合併時出現未列舉的例外會讓該擋的輸入放行。合併前審查攔下，要求呼叫點包 try 並退回基礎設定。審查當時舉的例子（YAML 以清單當鍵造成 TypeError）經實作方查證不成立：PyYAML safe_load 對清單鍵直接拋 ConstructorError，屬 YAMLError，已由解析失敗分支接住。try 因此是防禦層，鑑別它是否生效的測試要以 monkeypatch 讓合併函式拋例外，不能靠構造輸入。第二例顯示形態不限於訊息組裝：凡是在判定之前或之中新增的可失敗步驟，都要問同一個問題。

## 與既有模式的關係

- `IMP-BAL-010`：輔助函式以空值兼表「結果為空」與「判定失敗」，呼叫端的布林轉換讓守衛語意反轉。本模式的反轉來源不同：判定已經正確完成，是判定之後的訊息組裝出錯，被呼叫端的 fail-open 一併吞掉。兩者共同點是「失敗被壓成放行」，發生在跨函式邊界的呼叫端，單看被改的函式看不出來。
