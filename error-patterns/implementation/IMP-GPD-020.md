# IMP-GPD-020: 假資料期的程式以慣例樣式組出檔案路徑，註解寫「待真實資料整合後才會走到」卻沒有綁票；接上真實資料時沒人回頭檢查，真實檔名與慣例不符，功能對全部資料靜默失效

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | implementation |
| 來源版本 | 0.5.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-10-30 |

## 症狀

畫面的「開啟原始檔」以 `docs/usecases/<id>.md` 組出路徑。專案內真實的用例檔名都帶描述字尾（`UC-02-assess-change-impact-by-domain.md` 這類），所以這個樣式對全部用例都不成立：使用者按下按鈕，畫面一律回報「原始檔已不存在」。

這段程式的註解寫明：假資料沒有真實檔案，此路徑的成功分支「待真實資料整合後才會走到」。之後畫面接上了真實資料，這段卻沒有被重新檢查，錯誤在使用者可見的狀態下存在了數週，直到另一張清理票逐行讀碼才發現。測試全部綠燈，因為測試用的是 fake opener 與假資料，沒有一筆用真實檔名。

## 根因

**延後條件寫在程式註解裡，沒有綁定任何票**。「待真實資料整合後」是一個外部事件，不是可追蹤的觸發點（決策 trigger 綁定規則 2：合法 trigger 限 ticket ID）。真實資料整合的那批工作，沒有任何一處要求回頭掃描這類註解，條件成立了，卻沒有人收到通知。

**路徑的權威來源是資料，不是慣例**。真實系統裡，每個節點本來就帶有自己的檔案路徑。改用 ID 依慣例重組路徑，等於另立一個平行的權威；只要檔名慣例與實際不一致，兩者就會分歧，而且分歧時不會報錯，只會走「找不到」分支。

**測試輸入與實作共用同一個假設**。假資料的路徑由同一個慣例產生，測試自然與實作一致。測試沒有一筆輸入來自真實資料的形狀，這個假設就從來沒有被檢驗過。

## 解決方案

- 路徑一律取自資料節點本身（例如投影層提供 `node.path`），畫面不自行組路徑。
- 測試至少放一筆真實形狀的輸入（帶描述字尾的實際檔名），斷言傳出的正是這個字串。
- 修正前以符號或字面對整個原始碼目錄搜尋同型寫法，確認沒有其他位置（PC-GPD-053）。

## 預防措施

- 寫下「待某條件成立後才會走到／才會生效」的程式註解時，同時建一張票作為觸發點，並在註解中引用該票。沒有票的延後註解，視同沒有人負責。
- 接上真實資料（或解除任何假資料階段）的工作，驗收項加一條：全庫搜尋假資料期的延後註解（「假資料」「fixture」「待真實資料」等字面），逐一確認是否已經處理。
- 審查時看到程式依 ID 組檔案路徑、URL 或鍵值，問一句：「資料本身有沒有這個值？」有的話就改用資料本身的值。
