# IMP-LLM-001: 重試預算從單次毫秒級的操作原樣複製到單次數分鐘的操作，牆鐘上限讓重試次數實質固定

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 分類 | implementation（重試策略的參數來源） |
| 來源版本 | 3.1.0 |
| 首次觀測 | 2026-11-10 |

## 症狀

合併閘門的 CAS 合併在多 session 並行時中止：4 次嘗試的套件全綠，每次都在寫入 ref 時發現 base 已被他方前進而落空，第 4 次後回報「重試超過上限」，ref 未變。同一分支在 main 一段時間未前進時重送，1 次即寫入。

重試預算的常數（必做次數 3、累計等待 5 秒、牆鐘 20 秒、退避 0.5/1/2 秒）依程式碼註解複製自票務提交的重試函式。票務提交的單次嘗試是毫秒級 git 操作；閘門的單次嘗試含數分鐘的測試套件。

## 根因

**重試預算的單位是「嘗試成本」的假設，複製常數時假設沒有跟著換**。牆鐘上限以「自第一次嘗試起算」計，原用途下 20 秒可容納數十次毫秒級嘗試；搬到單次數分鐘的操作後，第一次嘗試結束時牆鐘已超過上限，條件「必做次數之後還在牆鐘內」永遠不成立，上限退化成固定的「必做次數 + 1」次嘗試。

這個退化與之後嘗試的成本無關：即使後續嘗試只需沿用前次驗證結果、數秒即可完成，也沒有下一次機會。成功與否因此取決於「某一次數分鐘的窗口內恰好沒有他方提交」，提交頻率一高（並行 session 的票務自動提交）就近乎必然失敗。

為何不易察覺：程式碼註解誠實寫出了來源，單元測試以注入的時鐘驗證預算邏輯本身正確；錯的是預算與新呼叫端的成本量級不相稱，兩邊各自看都沒有錯。

## 解決方案

- 重試上限改以新呼叫端的成本量級重新定義，不沿用來源函式的數值。
- 牆鐘上限若要保留，起算點與上限都要對應單次嘗試的實際耗時；或改為「只計等待時間、不計嘗試本身」。
- 區分昂貴嘗試與廉價嘗試：可沿用前次結果的嘗試（差異只有豁免檔）不應與需要重跑的嘗試共用同一個次數額度。

## 預防措施

- 複製重試、逾時、退避常數時，在同一處寫明來源函式的單次嘗試耗時量級，並比對新呼叫端的量級；量級不同就不能原樣複製。
- 重試邏輯的測試除了以注入時鐘驗證預算本身，再加一個以新呼叫端實際耗時量級驅動的案例，斷言重試次數符合設計意圖（不是只斷言「最終會中止」）。
- 協調面：以「請並行方暫停提交」壓低 base 前進頻率不可靠，約定只約束收到訊息的一方；修法應落在重試與沿用判準本身。
