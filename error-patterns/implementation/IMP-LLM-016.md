# IMP-LLM-016: 修改函式的預設值，但呼叫端都明確傳參，修改在命令路徑上沒有作用

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 高 |
| 分類 | implementation（修改點與實際執行路徑不交會） |
| 來源版本 | 3.5.0 |
| 首次觀測 | 2026-11-14 |

## 症狀

修法改的是函式在某參數為 `None`（缺省）時的行為，例如把「未傳 `repo` 時取目前 checkout 的根」改成「未傳時取主 checkout 的根」。修改後：

- 直接呼叫該函式、且不傳該參數的單元測試全綠，新預設值確實生效。
- 實際的命令路徑（CLI 子命令、hook 進入點）呼叫該函式時都明確傳入該參數，例如 `merge_fn(repo=get_project_root())`。缺省分支在命令路徑上從不執行，命令的行為與修改前完全相同。
- 修改前後對同一命令觀測，相關輸出（操作的 repo、閘門取用的根、日誌寫入位置）都沒有變化。

外觀與「已修好」相同：票面寫修好、測試綠、審查看 diff 也合理。只有對照「命令層級的修改前後輸出」才看得出修改沒有作用。

**連帶風險**：同一次修改若另在別的進入點改了取根方式（例如清理端改用新預設值），兩端會開始用不同的根，日誌與狀態檔分散兩處。原本要解的問題沒解，還多了一個新的不一致。

## 根因

1. **修改點選在函式內部，而不是行為的決定處**。參數由呼叫端決定時，函式的預設值只在「沒人傳參」時生效。命令路徑上的呼叫端都已經傳參，行為的決定處是呼叫端，不是被呼叫的函式。
2. **測試的進入點與實際的進入點不同**。單元測試直接呼叫函式並省略參數，正好走缺省分支；命令路徑走的是明確傳參分支。測試覆蓋的是修改點，不是使用者會走到的路徑，所以測試綠對「命令行為是否改變」沒有鑑別力。
3. **驗證比對的是函式回傳值，不是命令輸出**。只看函式在缺省時回傳了新值，沒有在命令層級比對修改前後的可觀測輸出。

此模式不限語言或領域：任何「參數有預設值、呼叫端可覆寫」的設計（keyword 參數、設定檔預設、依賴注入預設實作、CLI 旗標預設值）都可能發生。

## 解決方案

1. 列出命令路徑上該函式的所有呼叫端，標出每一處是否明確傳入該參數。
2. 若呼叫端都已傳參：修改點應移到呼叫端傳入的值本身（例如 `get_project_root()` 的取根方式，或呼叫端改傳另一個值），或移除呼叫端的明確傳參，讓預設值真正接手。選哪一種，取決於該值是否還有其他使用者；改共用的取值函式前，先盤點它的其他呼叫端。
3. 若只修改了一端的取值方式，確認同一資源的其他讀寫端（日誌、狀態檔、鎖）用的是同一個根，避免兩端分歧。
4. 修改無作用時，撤回該修改，不保留「無害但無效」的預設值變更。它會讓後來的讀者以為行為已經改變。

## 預防措施

| 時點 | 措施 |
|------|------|
| 修改預設值前 | grep 該函式的所有呼叫端，確認命令路徑上是否明確傳入該參數：`grep -rn "<函式名>(" <src>`，逐處看是否帶該參數。全部都傳時，改預設值不會改變命令行為 |
| 驗證時 | 以命令層級做修改前後對照：同一命令、同一環境，在修改前後各執行一次，比對可觀測輸出（操作對象、寫入位置、日誌內容）。兩次相同即代表修改沒有作用 |
| 撰寫測試時 | 除了直接呼叫函式的單元測試，至少加一個從命令進入點出發的測試，斷言命令層級的輸出（見 `test-assertion-design-rules` 的 E1：傳與不傳各跑一次，斷言兩者產物不同） |
| 審查時 | 審查預設值變更的 diff 時，問「這個預設值在命令路徑上會被用到嗎」；diff 只顯示函式內部，看不到呼叫端是否傳參 |

## 案例

框架的合併閘門中，一次修法把合併 CAS 函式在 `repo` 為 `None` 時的取根方式改成主 checkout，直接呼叫該函式的單元測試通過。審查時發現 worktree 管理工具的合併路徑以 `repo=get_project_root()` 明確傳入目前 checkout 的根；查證確認修改前後，CAS 操作的 repo、合併閘門取用的根、閘門日誌位置三者都相同，新預設值完全沒有作用。同一次修改在清理端改用新的取根方式，會讓兩端日誌寫到不同的根。最後撤回該修改，改由後續票從呼叫端的取值方式處理。
