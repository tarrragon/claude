# IMP-GPD-016: 提交階段的內容守衛只掃 diff 的新增行，純排版改動讓既有內容成為新增行，被判為新違規；修正若只以人造案例驗證，仍會漏掉真實的排版形態

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | implementation |
| 來源版本 | 0.5.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-10-29 |

## 症狀

編輯階段的偵測器（魔術數字、寫死字串等）被提交階段的守衛重用，掃描對象改為 staged diff 中以 `+` 開頭的行。一次性格式化（例如 `dart format` 整批執行）把既有的程式碼合併或拆行，這些行全部以新增行出現在 diff 裡，守衛把原本就存在的字面判為新寫入的違規，擋下整個格式化提交。

可用的繞道都會讓提交偏離原意：在該行加豁免註解（純排版提交夾帶內容修改）、切到警告模式（等於暫停守衛）。

修正時若只用人造案例驗證（例如「同一行重新縮排」），會漏掉真實的排版形態。實際格式化做的是「三行合併為一行、去掉尾逗號」，以整行片段為比對鍵的修正仍會判為新增。

實證（2026-10-29）：一次性格式化 340 檔中的 117 檔，提交被擋在 1 處既有的 `isHeader ? 0 : ...`。第一輪修正以整行片段比對，測試全綠，但拿真實 diff 重建前後內容實跑仍會擋；第二輪先合併括號未閉合的多行、以命中字面為鍵，真實 118 檔判出 0 檔，修正前的守衛對照為 1 檔。

## 根因

**「新增行」與「新增內容」不是同一件事**。diff 的行層級表示把移動、合併、拆分都表現為刪除加新增；守衛若把新增行當成新增內容，任何純排版變更都會讓既有存量重新受審。同一個守衛模組裡，另一個檢查已經用「改動前後各算一次、取淨增量」的方式處理，這個檢查沒有比照。

**比對鍵含排版成分**。以整行或行片段為鍵時，換行位置、尾逗號、前後文都會讓同一個字面得到不同的鍵；鍵必須只含與排版無關的成分。

**驗證案例由修正者自己設計**。人造案例只覆蓋修正者想到的排版形態，真實的格式化工具會產生它沒想到的形態。

## 解決方案

- 提交階段的內容守衛一律以改動前、改動後兩份全文各跑一次偵測，以多重集合取淨增量回報。
- 比對鍵只取命中的字面本身（加類別），比對前先把未閉合括號的多行合併、去除尾逗號等排版成分。
- 驗收時拿觸發本次修正的真實 diff，重建改動前後內容實跑新舊兩版守衛：新版 0、舊版非 0，才算修正成立。

## 預防措施

- 把編輯階段偵測器搬到提交階段時，檢查掃描對象是否從「本次寫入內容」變成「diff 新增行」；若是，改為改動前後的淨增量比對。
- 守衛的測試除了正向對照（新增一個真的違規仍被擋），再加一個「純排版重排」案例，形態取自實際格式化工具的輸出，而非手寫。
- 修正提交前的守衛時，派發方保留觸發案例的原始 diff，供驗收時重放。
