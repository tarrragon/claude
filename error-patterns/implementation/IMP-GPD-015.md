# IMP-GPD-015: 中斷後的自動收尾只接在失敗當下，重跑時入口閘門先擋下既有的殘留狀態，收尾永遠走不到

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | implementation |
| 來源版本 | 0.5.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-10-28 |

## 症狀

工具為非原子操作（刪除大量檔案、搬移、多步驟寫入）加上「失敗後自動收尾」：操作失敗時，若中間狀態可安全判定，就由工具完成剩下的步驟。收尾邏輯只接在操作失敗的那一刻。

測試全綠，是因為測試只在同一次執行內注入失敗。真實殘留多半來自上一次執行，例如舊版工具留下的、程序被殺留下的、或修法上線前就存在的。使用者重跑工具時，入口的前置檢查（例如「有未提交變更就拒絕」）看到殘留，直接拒絕，根本走不到收尾。結果修法上線後，原本要救的那批殘留仍然清不掉。

實證（2026-10-28）：worktree 清理加上「移除逾時後條件式強制收尾」，審查時發現：既有的半刪 worktree 重跑清理，會先被「未提交變更」閘門擋下。在入口閘門對同一安全條件放行之後，兩個既有的半刪 worktree 才在實機上清掉。

## 根因

**收尾掛在失敗事件上，沒有掛在狀態上**。設計者以「這次執行失敗了」為觸發，然而需要收尾的是「目前處於中間狀態」，這和由誰、在哪一次執行造成無關。

**入口閘門與收尾條件各自判定同一個狀態**。入口閘門把中間狀態歸為「不安全，拒絕」，收尾邏輯把同一狀態歸為「可安全完成」，兩者沒有共用判定，前者先執行，後者便成為死碼。

**測試只覆蓋同一次執行**。在同一個測試函式裡注入失敗，再斷言收尾結果，無法發現「另起一次執行」的路徑。

## 解決方案

- 把收尾條件寫成單一判定函式（例如「殘留全是已追蹤檔的刪除，且分支已併入主線」），入口閘門與失敗處理都呼叫它，不要各寫一套。
- 入口閘門遇到中間狀態時，先問這個判定函式：成立就放行並走收尾，不成立才拒絕，並列出不成立的條件。
- 入口閘門的成功訊息要標明走了收尾路徑，不要沿用「乾淨」的措辭。

## 預防措施

- 設計自動收尾時，逐一回答：這個中間狀態還能從哪些路徑出現（上一次執行、程序被殺、舊版工具、手動中斷）？每條路徑重跑時，會先遇到哪道檢查？
- 測試至少一個「另起一次執行」的案例：先在 fixture 裡直接做出殘留狀態，再呼叫工具入口，斷言殘留被清除。
- 搭配正向對照：同一殘留只要多一個不安全的元素（例如未追蹤檔），入口必須拒絕。
