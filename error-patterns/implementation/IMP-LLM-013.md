# IMP-LLM-013: Edit 以空字串刪除行尾片段時連同換行一起刪除

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 高 |
| 分類 | implementation（文字編輯工具的刪除語意） |
| 來源版本 | 3.3.0 |
| 首次觀測 | 2026-11-15 |

## 症狀

大量文字清理（例：刪除行尾的票號引用）時，代理人以 Edit 工具、`new_string` 為空刪除某行行尾的片段。結果該行與下一行接成一行：

- Markdown：兩條列項或兩條 `**Version**` 行變成一行，渲染後內容仍在，閱讀時不易察覺。
- Python：下一行的程式碼被併進上一行的註解，變成註解。某 hook 的變數指派行因此失效，執行時 NameError；既有測試沒有覆蓋該路徑，測試與合併閘門全綠。

3.3.0 一次清理中，執行者自行發現並還原 34 處；合併前的機械抽查再找出 4 處（分布 3 張票），其中 1 處為上述 Python 缺陷。

## 根因

Edit 工具在 `new_string` 為空時，會把緊接在 `old_string` 之後的換行一併刪除，**`old_string` 不含換行也一樣**。2026-11-19 實測（scratch 檔內容為 `line1 keep\nline2 delete-me TAG\nline3 keep\n`，`TAG` 代表行尾的待刪片段）：

| 案例 | old_string | new_string | 結果 |
|------|-----------|-----------|------|
| A | 整行 + `\n` | 空 | 整行刪除，正常 |
| C | 整行，不含 `\n` | 空 | 整行連同換行刪除（不留空行） |
| F | 行尾片段 ` TAG`，不含 `\n` | 空 | **行合併**：`line2 delete-meline3 keep` |
| B | 行尾片段 + `\n` | 空 | **行合併**（同 F） |
| G | 行中片段（其後還有文字） | 空 | 只刪片段，正常 |

C 與 F 是同一個行為：工具為了讓「刪整行」不留空行而吃掉後隨換行，但它不判斷 `old_string` 是否從行首開始。片段剛好落在行尾時，刪掉的換行是這一行與下一行之間的分隔。

因此「old_string 不要帶換行」這種直覺防護無效（F 案例）。可靠的寫法是讓 `new_string` 非空：把行尾片段連同其前方的保留文字一起放進 `old_string`，`new_string` 寫出保留文字。

## 並行 Edit 遺失更新（另一機制，未重現）

同一清理批次另回報「同檔並行 Edit 遺失 5 處更新」。實測 Edit 的讀改寫：Read 之後由外部改寫檔案，再對未受影響的區段做 Edit——外部改動保留，工具回報檔案自上次讀取後已被修改。Edit 每次以磁碟現況為基礎替換，「持有舊內容覆寫」不發生在 Edit 層。

未重現的可能來源（皆未驗證）：Write 整檔覆寫、Bash 腳本讀改寫、工具內讀與寫之間毫秒級的 race。同批次另有 scratchpad 根目錄被並行 session 覆寫清單檔的實例，屬共用路徑問題，以專屬子目錄解決。

## 解決方案

已發生的接行逐處拆回兩行；以下節的機械偵測找出所有接行處。

## 預防措施

| 層 | 措施 |
|----|------|
| 派發（自律） | 刪除行尾片段時 `new_string` 不可為空：連同保留文字一起替換；刪整行時 `old_string` 寫整行 |
| commit 前／合併前（機械） | 相鄰行接合偵測：diff 中某新增行以刪除行 D[i] 開頭且含 D[i+1] 開頭；`.py` 另做 AST 結構比對（字串常數正規化後比 `ast.dump`），程式行被併進註解必然不同 |
| 計數（輔助） | 純刪除片段的清理，每個 hunk 的刪除行數應等於新增行數；不等即可疑（合法刪整行除外） |
