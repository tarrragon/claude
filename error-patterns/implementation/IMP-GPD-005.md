# IMP-GPD-005: fail-open 守衛新增阻擋種類時漏補對應資源，例外被外層吞成放行

## 基本資訊

- **Pattern ID**: IMP-GPD-005
- **分類**: 實作（implementation）
- **風險等級**: 高（新增的阻擋從未生效，hook 以非阻擋碼結束，只驗「有沒有擋」以外的測試全綠）
- **來源版本**: 0.5.0
- **相關 Pattern**: PC-GPD-033（放寬守衛只驗誤擋消失；本模式是收緊守衛時新路徑未接通）、IMP-003（Hook 失敗必須對用戶可見）

---

## 問題描述

### 症狀

- 守衛新增一個阻擋種類（例如「目標無法解析」），判定函式正確回報該種類
- 實際執行時，該情境仍被放行；日誌只有 traceback，沒有阻擋行
- 若測試只呼叫判定函式、斷言回傳了新種類，測試全綠

### 根因

守衛的阻擋路徑依種類查表取資源（訊息、處理函式、續行提示）。新增種類時只改了判定端（產生種類、加進阻擋集合），漏補資源表中的對應項目。阻擋路徑查表時拋 KeyError，外層的安全包裝（未設 fail-closed 的 `run_hook_safely` 一類）把例外轉為非阻擋的退出碼，結果與「沒有這條阻擋」相同。

判定端與資源端分在不同模組時更容易發生：改判定端的人看不到資源表，資源表又沒有和阻擋集合綁在一起的約束。

### 為何難以察覺

- fail-open 是刻意設計（守衛壞掉時不要擋住所有操作），所以例外被吞是預期行為，不會被當成異常追查
- 失敗方向是放行，而放行與「輸入本來就沒問題」在輸出上同形
- 判定函式的單元測試會通過，因為判定本身沒錯

---

## 解決方案

### 結構性斷言

對阻擋集合的每個成員，斷言阻擋路徑能完整產生輸出、不拋例外：

```python
def test_every_blocking_op_has_deny_message():
    for op in BLOCKING_OPS:
        assert build_deny_message(op).strip()
```

這個斷言與種類的數量無關：之後再新增種類卻漏補資源時，它會先紅。驗證它的鑑別力：在記憶體中從資源表拿掉一項，確認斷言拋例外。

### 端到端應擋測試

新種類至少一個從 hook 入口跑起的應擋案例，斷言退出碼為阻擋碼（例如 2），而不只斷言判定函式的回傳值。

---

## 預防措施

| 時機 | 做法 |
|------|------|
| 新增阻擋種類 | 同一批修改判定端與資源端；兩者分屬不同檔案時，兩檔都要列入範圍宣告 |
| 範圍不足以同時改兩端 | 停手回報擴大範圍，不要只改判定端交差，也不要借用其他種類的訊息湊數（訊息會誤導） |
| 審查 fail-open 守衛的收緊修改 | 確認存在「每個阻擋種類都有完整輸出」的結構性斷言，以及從入口跑起的應擋案例 |

---

## 案例

一個裸 commit 守衛要對「覆寫目標含變數、無法靜態解析」保守阻擋。判定端在 lib 模組新增種類並加進阻擋集合；阻擋訊息由另一個模組依種類查表產生，表中只有既有的幾個種類。實作者在修改前停手指出：只改判定端時，新種類查表會拋 KeyError，被外層 fail-open 包裝轉成非阻擋退出碼，等於仍放行。擴大範圍後補上訊息，並加入上述結構性斷言；從表中拿掉任一既有項目即 KeyError，確認斷言有鑑別力。
