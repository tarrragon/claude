# IMP-GPD-003: 可重入鎖以環境標記交給子程序辨識，子程序載入另一棵樹的舊版協定碼，等待自己祖先持有的鎖

## 基本資訊

- **Pattern ID**: IMP-GPD-003
- **分類**: 實作 bug（implementation）
- **來源版本**: 0.5.0
- **發現日期**: 2026-10-15
- **風險等級**: 高
- **影響範圍**: 持有全機或跨程序鎖，並在持有期間啟動「本身也會取同一把鎖」的子程序的工具（本案為合併閘門持有 heavy 名額，期間經 timeout 包裝器跑全套件）
- **觸發案例**: 2026-10-15 合併閘門改為整段持有名額的那次合併

---

## 問題描述

### 症狀

持有鎖的程序啟動子程序後，子程序報告「等待名額」，而它等待的持有者正是自己的祖先程序。兩者互等，直到子程序的等待上限逾時才結束。結束前，這把全機鎖一直被占用，其他使用者都在排隊。

單元測試全綠：「持有鎖時子程序不會再次取得」這一條已有測試覆蓋，而且通過。

### 根因

可重入的做法是：持有者在環境中放入標記（例如持有者 pid），子程序看到有效標記就略過取得。這個做法有個隱含前提：**持有者與子程序對標記的解讀協定一致**。

本案中，持有者的程式從被合併分支的樹載入（新版，會寫標記）。子程序的路徑則以「專案根目錄」組成，載入主 checkout 的包裝器與鎖模組（舊版，不認得標記）。舊版照常排隊，等待的是祖先程序手上的鎖。

只要兩邊分別從不同的程式樹解析，版本就可能不一致。最常見的時機是引入或修改標記協定的那一次變更本身：新協定尚未進入子程序所解析的那棵樹。

### 為何難以發現

測試以注入的 runner 取代真實的子程序啟動，持有者與子程序在同一個 Python 程序內共用同一份模組，結構上不可能出現版本不一致。測試驗證的是協定邏輯，沒有驗證「子程序實際載入哪一份程式」這個接線。

---

## 解決方案

1. **同樹解析**：子程序的入口（包裝器腳本）從持有者程式碼所在的同一棵樹解析，例如以 `Path(__file__)` 推導，不以專案根目錄或工作目錄組路徑。這樣兩邊必定載入同一份協定碼。
2. **持有期間縮短子程序的等待上限**：標記有效時子程序完全不等待，所以子程序一旦開始等待，就代表協定不一致。持有期間把子程序的等待上限設為短值（本案 30 秒），出錯時快速失敗、釋放鎖，不會占用到預設上限（本案 3600 秒）。
3. **提示區分來源**：持有者自己排隊時的提示，要和子程序的提示使用不同前綴，避免把「持有者在排隊」誤讀成「子程序在等」。

---

## 預防措施

- 設計「持有者經環境或檔案把權限交給子程序」的機制時，在設計文件中寫明：子程序從哪一棵樹解析入口。
- 補一個 E2 測試：以一支會取鎖、但不處理標記的 stub 子程序模擬舊版，斷言持有者在短時間內得到失敗，而不是等到預設上限。修正前在舊碼上實跑，確認為紅。
- 引入或修改標記協定的那一次合併，是最容易出現版本不一致的時機。合併前確認子程序會載入哪一份程式。
