# IMP-BAL-021: 查詢型命令暗含歸檔副作用且無持久日誌，加上檔名鍵與查找鍵不一致，讓正常歸檔被誤判為資料遺失

## 基本資訊

| 欄位 | 值 |
|------|-----|
| 類別 | implementation |
| 風險等級 | medium |
| 來源版本 | 0.2.1 |
| 發現情境 | 驗收一張修正 stale 判定的 CLI 票時，兩個待恢復 handoff 檔在四分鐘內自 pending 目錄消失；以目標票 ID 在 archive 查無同名檔、全部 hook 日誌無刪除紀錄，PM 一度判為資料遺失並建 ANA 追查 |

## 症狀

- 名義上唯讀的命令（儀表板／清單）執行後，協調狀態目錄的檔案數減少；命令輸出只有一行 stderr 提示，事後任何日誌都查不到。
- 到歸檔目錄以「自己認知的鍵」（目標票 ID）找不到檔案，得出「被刪除而非歸檔」的結論。
- 受控探針有時重現有時不重現，因為觸發的是序列中不起眼的那條查詢命令，而不是被懷疑的清理命令。

**觸發條件常在別處、且早於症狀數小時**：本案的檔案存在數週未被動，直到另一方的批次收尾把它們指向的票關閉。該類協調檔的 `direction` 指向自身來源票（self-redirect），清理判準把「目標已 closed」與「已 completed」併為同一條，於是關票的那一刻全批同時成為可清理狀態，只等下一次任何人呼叫帶副作用的查詢命令。排查時若只看症狀時窗內的命令，會漏掉真正的狀態轉換時刻。

## 根因

三個各自合理的設計疊加：

| 層 | 設計 | 單獨看 | 疊加後 |
|----|------|--------|--------|
| 副作用 | 儀表板每次呼叫順手把 stale handoff `rename` 到 archive | 省一次手動 gc | 讀者不預期讀取命令會寫檔，排查時把它排除在候選外 |
| 可觀測性 | 歸檔訊息 `sys.stderr.write`，例外 `except Exception: pass` | 不干擾主輸出 | stderr 被 `2>&1 \| head` 或代理人摘要吞掉後零痕跡；失敗完全靜默 |
| 命名鍵 | handoff 檔以**來源票** ID 命名，內容以 `direction` 指向**目標票** | 來源唯一、目標可變 | 讀者記得的是目標票（提醒 hook 顯示目標），到 archive 用目標票名查 → 查無 → 誤判刪除；`rename` 保留原 mtime，依時間排序也找不到 |

另有一條同語意的並行路徑（Stop hook 的 GC）用 `unlink` 刪除而非 `rename` 歸檔，使「該檔到底會被歸檔還是刪除」取決於誰先跑到，排查時兩種假設都能自圓其說。

## 為什麼難以察覺

- 副作用藏在「讀取」命令裡，排查者的候選清單天然排除它。
- stderr 一次性輸出在自動化與代理人摘要環境等同無輸出。
- 檔名鍵與提醒訊息展示的鍵不同，查找者用錯鍵時得到的是「確定不存在」而非「找不到」，信心反而更高。

## 解決方案

1. **副作用可見**：任何在讀取路徑上的清理／歸檔，必寫持久日誌（來源路徑、目標路徑、原因、時間），例外路徑記 warning 而非 `pass`（觀測性規則 4：catch 必有日誌）。
2. **同語意同處置**：同一資料的 GC 在所有入口統一為歸檔（`rename`）或統一為刪除，不可並存；本案統一為歸檔。
3. **鍵一致或可反查**：檔名鍵與使用者面對的鍵不同時，提醒訊息／歸檔日誌同時輸出兩個鍵，或提供以目標鍵反查的命令；排查 SOP 改為先 `grep -l "<目標鍵>" archive/*` 再下「不存在」結論。

## 預防措施

- 設計「順手清理」時先問：這個命令的名字會讓讀者預期它寫檔嗎？不會就不要放，或放進名稱帶動詞的獨立子命令（`gc`）。
- 排查「檔案消失」時，候選清單必含所有在時窗內執行過的命令（含查詢型），以 hook 日誌的命令全文為準，不以「這個命令應該只讀」剔除。
- 對協調狀態目錄，用內容 grep 而非檔名查找確認存在性；`rename` 保留 mtime，依時間排序找不到最新歸檔。

## 關聯

- 同型錯誤家族：讀取路徑帶寫入副作用而無日誌（快取回填、索引重建、自動修復）皆命中前兩層。
- 修復追蹤：consumer 專案兩張 IMP（儀表板 auto-GC 補持久日誌；Stop hook GC 改歸檔）。
