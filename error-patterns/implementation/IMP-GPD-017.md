# IMP-GPD-017: 以世代計數丟棄晚回結果時，呼叫端在推進世代的那個操作之前就記下世代，該操作自己的結果回來時被判為過期而丟棄

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | implementation |
| 來源版本 | 0.5.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-10-29 |

## 症狀

規格要求「情境改變（例如切換專案）之前發出、之後才回來的結果不呈現」。常見做法是維護一個世代計數：情境每改變一次就加一；呼叫端在 await 前記下世代，回來時世代不相等就丟棄結果。

如果推進世代的那個操作（例如 `select()`）本身也是一個會被 await、而且會回傳結果的呼叫，呼叫端照同一套寫法，在 await 它之前記下世代，回來時世代必然已經改變，這個操作自己的結果（例如「選定成功但偏好未能記住」的提示）就會被判為過期而丟掉。這和規格相反：規格明寫這類提示是本次操作產生的，應該在清除之後送出。

實證（2026-10-29，設計審查時攔下，未進入實作）：一份切換專案時清除提示、丟棄晚回結果的設計，把世代遞增放在選定入口，晚回比對套用到所有呼叫端。只要照這份設計實作，「未能記住」提示就會在每次選定時被吞掉。

## 根因

**世代守衛混淆了兩種結果**：一種是「與情境改變無關、碰巧跨越了改變」的結果，另一種是「改變本身產生」的結果。前者應該丟棄，後者是改變的一部分。用同一套「await 前記下、回來時比對」的寫法套用全部呼叫端，後者一定會被誤判。

**誤判在一般測試下不會出現**：正常路徑測試只驗證「晚回結果被丟棄」，不會刻意構造「推進世代的操作自帶結果」這個情況，所以誤判是無聲的。

## 解決方案

- 推進世代的操作自己產生的結果，不走晚回比對；或者在該操作完成之後才記下世代。
- 晚回比對只套用在跟本次改變無關的非同步呼叫，例如在改變之前開始的檔案開啟、掃描。

## 預防措施

- 設計世代守衛時，先列出所有會被 await 的呼叫，逐一標出它是「推進世代的操作」還是「可能跨越改變的操作」。
- 測試除了「晚回結果被丟棄」之外，再加一個正向對照：推進世代的操作自帶的結果確實有呈現。
- 規格若寫了「由本次操作本身產生者不清除」這類例外，就把它當成世代守衛的必測案例。
