# IMP-BAL-014: 讀取端 sanitizer 修補記憶體但不寫回，損毀資料永久留存且警告退化為背景噪音

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 首次發現 | 2026-08-26 |
| 來源版本 | v0.2.1 |
| 適用範圍 | 任何在解析／載入路徑上偵測並修補損毀輸入的元件（編碼 sanitizer、schema 補值、格式正規化、遷移層 shim） |
| 偵測成本 | 低（同一命令連跑兩次，警告行數不變即命中；行數通常等於損毀筆數） |

## 摘要

**在讀取路徑上修補損毀資料而不把修補結果寫回來源，等於把一次性的資料修復工作，換成每次讀取都要重付的固定成本。** 修補只存在於回傳值，磁碟上的損毀原封不動，下一次讀取重新偵測、重新修補、重新警告。

危害分三層，且都不會表現為錯誤：

1. **輸出污染恆定不衰減**：每次載入固定噴 N 行警告，N 等於損毀筆數。修不修都不影響流程成敗，因此沒有任何機制推動它被處理。
2. **警告訊號退化**：常駐警告訓練讀者略過該類訊息，日後真正的新警告淹沒其中，可見性形同失效。
3. **警告不可行動**：這類訊息描述的通常是機制（偵測到 X，已替換為 Y），不指出是哪一筆資料。讀者知道有東西壞了，卻無從得知壞在哪、壞了幾筆，必須自行寫掃描才能定位。

sanitizer 選擇不寫回，動機多半正當——讀取端擅自改寫使用者內容風險更高。問題不在這個選擇本身，而在於選擇之後沒有留下關閉迴圈的路徑：既沒有把損毀位置報出來，也沒有提供把修補落盤的顯式入口。

## 症狀

- 同一命令重複執行，stderr 固定輸出相同數量的同一則警告，次數不隨執行次數衰減
- 警告訊息描述偵測到的問題類型與已採取的替代行為，但不含任何來源定位（檔名、欄位、識別碼）
- 流程本身成功，退出碼為 0，警告不影響任何結果
- 修補邏輯本身有測試覆蓋且測試通過——測的是「修補行為正確」，不是「損毀資料已清除」
- 團隊對該警告的普遍認知是「一直都有，不用理」

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| sanitizer 位置 | 掛在解析／載入路徑上 | 每次讀取都重新執行一次完整偵測與修補 |
| 修補作用域 | 只作用於回傳值（記憶體） | 來源資料維持損毀狀態，下次讀取重演 |
| 不寫回的設計動機 | 避免讀取端靜默改寫使用者內容 | 動機成立，但迴圈沒有出口——既不寫回，也不提供修復入口 |
| 警告粒度 | 描述機制而非來源 | 讀者無法從警告本身定位損毀筆數與位置，處理門檻高於忽略門檻 |
| 損毀無流程後果 | 修補讓流程照常成功 | 沒有任何 gate 會因它失敗，處理優先級永遠排在最後 |

## 最小重現

任何符合下列三條件的元件皆可重現，與具體語言或資料格式無關：

1. 載入函式在回傳前對輸入做修補（替換非法字元、補預設值、正規化格式）
2. 修補結果只進入回傳值，未觸發對來源的寫入
3. 修補發生時寫警告到 stderr

驗證方式：對同一份資料連續執行兩次載入，比較兩次的警告行數。行數相同即命中——第一次的修補對第二次毫無影響。行數通常直接等於來源中的損毀筆數，可作為盤點起點。

## 案例：CLI 每次全量載入固定噴六行編碼警告（2026-08-26）

某 CLI 的 frontmatter 解析器偵測到孤立 UTF-16 代理碼位時，會替換為 U+FFFD 並寫 stderr 警告，理由充分——這類碼位無法被 UTF-8 編碼，不修補則後續任何寫入都會拋例外。但修補只在記憶體發生，磁碟檔案未被改寫。

結果是任何載入全量資料的命令都固定輸出六行相同警告，持續存在到有人主動追查為止。追查時發現警告只述機制，得另寫掃描腳本才能定位——命中六筆，全部落在同一組六個檔案的同一個欄位，數量與警告行數完全吻合。

修復本身是單點字串替換，成本遠低於它存續的時間。真正的成本不在修，而在於沒有任何機制指出「該修什麼」，使一個一次性工作維持在永久待辦狀態。

## 防護

| 時機 | 動作 |
|------|------|
| 設計讀取端 sanitizer 時 | 決定不寫回，就必須同時提供關閉迴圈的路徑：一個把修補落盤的顯式命令或旗標（例如 `--fix` 子命令），使修復成本從「自行寫掃描」降到「執行一個命令」 |
| 撰寫修補警告訊息時 | 訊息必須含來源定位（檔案路徑、欄位名、識別碼），使讀者能直接行動。只述機制的警告在多筆損毀時無法區分，實質等同不可行動 |
| 檢視既有 sanitizer 時 | 同一命令連跑兩次比對警告行數；行數不變即代表來源未被修復，該行數就是損毀筆數，可直接作為盤點基準 |
| 發現此類警告時 | 防線前移至寫入端：拒絕損毀輸入落盤，而非在讀取端反覆修補。讀取端修補是相容既有資料的過渡層，不是長期防線 |
| 見到「一直都有、不用理」的常駐警告 | 視為未關閉的資料修復迴圈，先數行數再定位來源，不預設它無害 |
