# IMP-GPD-026: 寫入端正規化在補償讀取端的解析缺陷，只修寫入端會造成讀取端回歸

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 首次發現 | 2026-11-05 |
| 來源版本 | v0.6.0 |
| 適用範圍 | 寫入前會改寫內容（降級、跳脫、正規化）、而讀取端以同一份格式解析的元件對 |
| 偵測成本 | 低（以含觸發字元的合成輸入直接對讀取端求值） |

## 摘要

**寫入端的改寫若有副作用，常被當成寫入端自己的 bug；但這個改寫可能剛好讓讀取端的缺陷不會被觸發。** 如果把寫入端「修好」，卻沒先修讀取端，原本被遮住的讀取端缺陷就會在正常輸入上爆發。這種情況表面上像修 bug，實際上是回歸。

## 症狀

- 寫入端對內容做無差別改寫（例：所有行首 `## ` 一律降為 `### `），在某類輸入上明顯改壞內容（例：code block 內的 markdown 範本），因此被開成 bug。
- 修法提案只描述寫入端：「改寫時跳過那類輸入」。
- 票面的前提是「讀取端不會把那類輸入當成結構」，但這個前提沒有經過驗證。

## 根因

寫入端的改寫是當初為了保護讀取端而加的防線（例：防止 H2 切斷章節範圍），讀取端本身沒有區分輸入語境（例：不追蹤 code fence 狀態）。兩端合起來才正確。只看寫入端的人會看到「多餘的改寫」，看不到它擋住了什麼。

## 解決方案

1. 修寫入端之前，先用會觸發改寫的合成輸入直接對讀取端求值。例：一段 Solution 的 code block 內含 `## x`，檢查讀取端切出的 Solution 是否完整。
2. 讀取端也有缺陷時，修法順序固定：先讓讀取端能區分語境，而且要收斂到單一共用函式，把各自寫的 regex 一併替換；全部收斂後，寫入端才放寬改寫。
3. 測試含正向對照：讀取端在修正前截斷（紅燈）、修正後完整；寫入端在修正後只改寫該改的部分。

## 預防措施

- 寫入端的改寫邏輯旁註明它在保護哪個讀取端行為，讓後來的人知道拿掉它的前提是什麼。
- 讀取端的同一解析規則不要散落成多份 regex；散落時，「讀取端已修」很難成立，寫入端的補償也就拿不掉。

## 實例

ticket CLI 的 append-log 把所有行首 `## ` 降為 `### `，改壞了 code block 內的範本。實測共用切段函式與 acceptance checker 的 regex，都會在 code block 內的 `## ` 處切斷 Solution；降級其實是在補償這兩處。觀測寫在 tarrragon/claude#55。
