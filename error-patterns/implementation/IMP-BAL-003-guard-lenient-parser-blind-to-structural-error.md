# IMP-BAL-003: 稽核器與消費端解析器嚴格度落差

## 症狀

同一份結構化 SSOT 檔案被兩類程式讀取——稽核 hook 用寬鬆解析器（regex / 逐行掃描），
功能消費端用嚴格解析器（`yaml.safe_load` / JSON parser）。當檔案出現結構錯位時：

- 稽核 hook 照常輸出語意層具體發現（「某欄位不合規」），讀者據此認定檔案已被檢查過。
- 消費端解析失敗，走容錯路徑降級運作，其警告混在正常輸出中不易辨識。
- 兩份輸出在同一 session 內並存卻互不參照，結構錯誤本身不出現在任何一方的結論裡。

**識別特徵**：

- 稽核器原始碼註解寫著「採 regex 逐項解析，避免額外引入套件依賴」。
- 稽核器的 warning 清單只涵蓋語意規則（欄位值是否合規），無「檔案是否可被解析」項。
- 消費端錯誤訊息含「解析失敗，將改用 ... 方式」而 exit code 為 0。

## 實證案例（flutter_balance 0.2.1-W3，2026-07-26）

`docs/todolist.yaml` 的 `0.2.1` 版本條目被誤置到檔尾 `references:` mapping 之後，
而非 `versions:` list 內。同一 session 的兩份輸出：

| 讀取方 | 解析手法 | 輸出 |
|--------|---------|------|
| `version-tracking-consistency-guard-hook`（SessionStart） | `VERSION_ENTRY_PATTERN.finditer(content)` | 「closed 票延後承諾稽核: 0.0.2-W1-001 closed_by 非合法 Ticket ID」——語意層具體發現，未提解析狀態 |
| `ticket track dashboard` | `yaml.safe_load` | 「解析 todolist.yaml 失敗 (ParserError: line 124 ... line 133)，將使用目錄掃描方式偵測版本」 |

regex 只比對 `- version: "X"` 與其後的 `status:`，對縮排歸屬完全不敏感，因此
`0.2.1` 條目掛在 `references:` 之下時 regex 仍抓得到，八項漂移偵測全數放行。
消費端則因整份檔案無法解析而失去 `versions` 清單，退回目錄掃描猜版本——本次
湊巧猜對 `0.2.1`，若目錄命名與 todolist 不同步就會判到錯誤版本。

## 根因

1. **解析器嚴格度落差未被視為介面契約**。稽核器為避開依賴而選 regex 是合理的
   局部取捨，但一旦稽核對象是「供嚴格 parser 消費的檔案」，寬鬆解析器就無法覆蓋
   消費端會遇到的失敗集合。稽核器實際稽核的是自己那套寬鬆語法，不是消費端契約。
2. **稽核規則清單只列語意規則，未列解析前提**。八項漂移全部形如「欄位 A 與事實 B
   不一致」，隱含前提「檔案結構正確」從未被列為受檢項，因此前提失效時無人負責報告。
3. **具體語意發現遮蔽前提失效**。稽核器輸出愈具體（附 ticket ID 與欄位值），
   讀者愈確信檔案已被完整檢查，反而降低追查解析警告的動機。

## 防護

| 層級 | 措施 |
|------|------|
| 稽核器層 | 稽核 SSOT 前先驗證「消費端所用的同一解析器」能成功解析；失敗即輸出 ERROR 級警告（含行號與 parser 例外訊息）並中止語意層掃描，避免輸出誤導性的具體發現 |
| 稽核器層 | 若稽核器不得引入解析依賴，改為結構驗證：確認頂層鍵型別（`versions` 為 list）與條目歸屬層級，而非僅 regex 比對欄位樣式 |
| 消費端層 | 解析失敗的降級路徑輸出須與正常輸出可區分（ERROR 前綴 / 非零 exit code / 明示降級後果），不可只在多行 stdout 中夾一行提示 |
| 測試層 | 以錯位樣態（合法條目掛到錯誤 mapping 之下）建回歸測試，斷言稽核器報錯而非放行 |

**判定順序**：檔案可否被消費端解析（前提） → 結構型別是否正確 → 欄位語意是否合規。
前一層失敗時，後續層級的結論不具意義，不應輸出。
