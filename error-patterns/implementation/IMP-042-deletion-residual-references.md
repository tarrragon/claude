# IMP-042: 簡化/刪除操作後殘留引用未同步清理

## 錯誤摘要

| 項目 | 說明 |
|------|------|
| **分類** | Implementation |
| **嚴重性** | Medium（語義矛盾，不影響功能但誤導讀者） |
| **發現版本** | v0.2.0 |

## 症狀

- 刪除章節或概念後，frontmatter description、其他章節的描述文字仍引用已刪除的名稱或數量
- 具體案例：刪除「核心抽象（遞迴展開器）」章節後，frontmatter 仍寫「遞迴需求展開器」；刪除維度 4-7 後，Layer 2 描述仍寫「沿 7 個維度掃描」
- 表現為文件內部的事實矛盾

## 根因分析

- 刪除操作聚焦於目標區段本身（被刪除的章節），未搜尋同檔案或跨檔案中引用該概念的其他位置
- 人類（和 AI）在執行「刪除」時，心智模型是「移除這個區塊」，而非「移除這個概念的所有痕跡」
- frontmatter 和其他章節的描述文字不在刪除的心智範圍內

## 防護措施

**刪除後全檔搜尋檢查清單**（刪除任何章節/概念後必須執行）：

| 步驟 | 搜尋目標 | 範例 |
|------|---------|------|
| 1 | 被刪除的標題/名稱 | grep「遞迴展開器」「核心抽象」 |
| 2 | 相關數量詞 | grep「7 個維度」「7 維度」 |
| 3 | frontmatter description | 手動檢查 description 是否引用已刪除概念 |
| 4 | 跨檔案引用 | grep 相關檔案（模板、代理人定義等） |

**驗證方式**：三人組多視角審查可有效捕獲此類殘留（本次即由 code-reviewer 發現）。

## 變體：刪除程式符號，殘留在測試檔與收集不到的腳本

**症狀**：刪除一個 hook 函式後，本機只跑與該 hook 相關的測試檔，全綠。送進合併閘門才紅燈：另一個測試檔只驗證這個函式存在與它的簽名，`AttributeError` 找不到該函式。同時還有兩支散落的手動腳本，以 `importlib` 載入 hook 再呼叫這個函式。它們不在 pytest 的收集範圍內，閘門也不會跑到，只能靠搜尋發現。

**根因**：「相關測試檔」是依被改檔案選出來的，引用被刪符號的檔案不一定在這個集合裡。文件概念的殘留只會讓內容互相矛盾；程式符號的殘留會造成執行期錯誤，而且藏在沒有被選中的測試、以及完全不被收集的腳本裡，本機綠燈對它們沒有鑑別力。

**防護步驟**（刪除或改名函式、類別、模組層常數之前）：

| 步驟 | 動作 | 命令 |
|------|------|------|
| 1 | 以符號名搜尋整個 `.claude/`，含測試目錄與不在測試收集範圍的腳本；排除 `.claude/worktrees/`（其他 worktree 的副本，不是本 checkout 的引用） | `grep -rn '<符號名>' .claude/ --include='*.py' --exclude-dir=worktrees` |
| 2 | 搜尋以字串取用的寫法（`getattr`、`monkeypatch.setattr`），這類引用沒有 import 語句 | `grep -rn "getattr(.*'<符號名>'\|\"<符號名>\"" .claude/ --include='*.py' --exclude-dir=worktrees` |
| 3 | 逐筆分類命中：要一起改、要一起刪（只驗證該符號存在的測試），或屬歷史紀錄（CHANGELOG），歷史紀錄不改 | — |
| 4 | 刪除後再跑一次步驟 1，結果只剩歷史紀錄，才算完成 | 同步驟 1 |

**判讀**：相關測試檔全綠，只證明「被選中的測試沒壞」，不證明「沒有其他地方引用它」。殘留與否以步驟 4 的搜尋結果為準。

## 學習要點

- 「刪除」不等於「移除」：刪除是物理操作（移除區塊），移除是語義操作（消除概念的所有引用）
- 簡化任務的審查重點應包含「殘留引用搜尋」
- frontmatter 是最容易被遺忘的殘留位置
- 刪除程式符號時，相關測試檔全綠不足以證明無殘留；以符號名搜尋整個 `.claude/`（含測試與收集範圍外的腳本）為準
