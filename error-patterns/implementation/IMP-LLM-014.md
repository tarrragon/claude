# IMP-LLM-014: 合併寫入位置後，依位置區分寫入來源的判定失去鑑別力

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 高 |
| 分類 | implementation（偵測器的歸屬判定） |
| 來源版本 | 3.5.0 |
| 首次觀測 | 2026-11-12 |
| 適用範圍 | 以「寫在哪裡」判定「誰寫的」的偵測器、哨兵、守衛，且其觀測的位置被改成多個寫入者共用 |

## 摘要

**偵測器原本靠寫入位置區分寫入來源：受測方寫 A 處、正常運作寫 B 處，A 處有增長就判洩漏。把兩者的寫入合併到同一處之後，位置不再帶有來源資訊，正常寫入與洩漏同形，判定必然誤判。修法是把來源標記寫進紀錄本身，判定改讀標記。**

位置是隱性的來源標記。合併位置的變更通常是為了別的目的（集中日誌、共用狀態），不會有人意識到同時拿掉了一個標記。

## 症狀

- 洩漏哨兵、污染偵測或「測試不得寫入正式位置」類守衛，在受測程式碼完全正確時判紅
- 紅燈內容指向的檔案屬於呼叫者自己：檔名是呼叫者的 session id、行程 id 或使用者名稱
- 誤紅的發生與「偵測期間呼叫者有沒有做事」相關：呼叫者在偵測窗口內有任何正常寫入（例：自身工具呼叫寫一行日誌）就紅，閒置則綠
- 反方向的形態：為消除誤紅而放寬判定後，真正的洩漏也一起放行，且沒有任何訊號

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 偵測器的判準 | 「某位置的某檔增長 = 洩漏」 | 判準隱含「只有受測方會寫這裡」 |
| 位置合併 | 正常運作的寫入改落同一位置（甚至同一檔名） | 隱含前提失效 |
| 檔名或路徑相同 | 寫入者用相同的識別值命名（例：呼叫者自己的 session id） | 連檔案層級也分不開，只剩內容可分 |
| 內容無來源欄位 | 紀錄只寫了「發生什麼」，沒寫「在什麼執行脈絡下寫的」 | 偵測器無從區分 |

偵測器修正時常見第二個漏洞：**只處理被回報的那一種寫入者**。共用位置通常有多種寫入者（各 session 的 hook、日誌輪替、評估檔、首次建立的目錄），被回報的只是剛好撞上的一種。逐案修正會在下一種寫入者出現時再次誤紅。

## 解決方案

### 1. 來源標記寫進紀錄

受測環境在啟動時產生一個本次執行專屬的識別值（例：快照時產生的 run id），經環境變數傳給所有子行程；寫入端在該變數存在時把它寫進每筆紀錄。偵測器只把「帶有本次識別值的新增紀錄」判為洩漏。

| 寫入來源 | 紀錄帶標記？ | 判定 |
|---------|------------|------|
| 本次受測行程的洩漏 | 是，且等於本次識別值 | 洩漏 |
| 呼叫者自己的正常寫入 | 否 | 不判 |
| 其他並行執行的測試 | 是，但值不同 | 不判（屬於對方的偵測範圍） |

### 2. 以 byte 位移讀取並行 append 的檔案時，前後兩端都要處理半行

偵測器在快照時記下檔案大小，事後只讀「快照大小之後的新增內容」。寫入者是並行的，兩端都可能落在一行中間：

| 位置 | 判別 | 處理 |
|------|------|------|
| 尾端 | 新增內容最後一段未以換行結尾 | 寫入者尚未寫完，忽略這一段 |
| 前端 | 快照大小 > 0 且位移前一個 byte 不是換行 | 快照時寫入者正寫到一行中間，丟棄新增內容直到第一個換行 |
| 中間 | 以換行結尾的完整行 | 照常解析；解析失敗要判為異常並寫 stderr（fail-closed），不可當半行忽略 |

只處理尾端是常見寫法，前端半行會把「上一行的後半段」當作一筆獨立紀錄解析，解析失敗即誤判。

### 3. 擴大比對範圍前，先列出該範圍的所有寫入者

把偵測範圍擴大到共用區時，先列一張表：寫入形態、寫入者、與洩漏是否同形、判定方式。每一列都要有結論，不能只處理被回報的那一列。

### 4. 加不上標記時，保留一條必經且帶標記的旁路

某些寫入形態無法帶標記（例：寫入端不在掌控內、只是新建一個空檔或目錄）。此時放寬對該形態的判定，但確認受測方的洩漏必然還會經過另一條帶標記的路徑（例：每次 hook 執行必經的包裝函式會寫一筆帶標記的紀錄），偵測靠那條路徑保留。放寬掉的偵測面要建票追蹤，不可只寫在註解。

## 預防措施

| 時機 | 檢查 |
|------|------|
| 修改寫入位置（集中、合併、改共用根） | 問：「有沒有任何偵測器靠這個位置判斷寫入者是誰？」有則同一次變更內補來源標記 |
| 設計偵測器 | 判準不依賴「只有某方會寫這裡」；改讀紀錄內容的來源欄位 |
| 偵測器以位移讀並行 append 檔 | 前端、尾端半行各有處理與測試；完整行解析失敗走 fail-closed |
| 擴大偵測範圍 | 先產出寫入者盤點表再改判準 |

## 案例

一個測試框架的洩漏哨兵在測試前後對 hook 日誌目錄拍快照，檔案增長即判洩漏。某次變更把 hook 日誌從各 worktree 改為集中寫到主 repo 的共用根，並讓哨兵同時比對共用根。合併閘門由某個 session 在 worktree 中發動，閘門測試期間該 session 自己的工具呼叫照常觸發 hook，寫入共用根下以自身 session id 命名的 liveness 檔。哨兵判定「呼叫者 id 檔增長 = 洩漏」，套件全綠仍判紅，所有線的合併都被擋下。

第一次修正為 liveness 紀錄加上測試執行標記，只修了被回報的 liveness 檔；共用根第一層還有其他 session 的 hook 新建的評估檔，閘門再次誤紅。第二次修正時才補列寫入者盤點表，對無法帶標記的第一層新增項目放寬，並確認未隔離的測試必然經過寫入帶標記紀錄的包裝函式。
