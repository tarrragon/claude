# IMP-GPD-018: 把多處重複的日誌或回報函式抽成共用 helper 時，把各呼叫點自帶的識別（日誌 tag、元件名）一併收斂成 helper 自己的值，事後無法分辨來源，且可能違反規定「由呼叫點標示」的規格

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | implementation |
| 來源版本 | 0.5.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-10-29 |

## 症狀

同一段日誌函式在多個元件各有一份私有副本，每份都用該元件自己的 tag。抽成共用 helper 的計畫把 tag 改成 helper 檔自己的 tag，理由是 helper 也有自己的 tag 慣例。

抽出後所有日誌的來源都變成同一個值，無法從日誌分辨是哪個元件發出的。如果規格明寫「name 為呼叫點所在元件的 tag」，這次重構就成了靜默的規格違反：既有測試只斷言「有日誌」或「不呈現」，不會斷言 tag，所以全部綠燈。

實證（2026-10-29，設計審查時攔下，未進入實作）：四個畫面各自的「晚回結果丟棄」留痕函式，計畫抽成共用檔並改用該檔的 tag。規格的留痕條文要求 tag 取自呼叫點元件。

## 根因

**DRY 只看見重複的程式碼，沒看見各副本之間不同的部分**。各副本唯一不同的就是 tag，而這正是它們存在的理由之一。抽共用時把差異當成可以統一的雜訊，就把資訊抹掉了。

**套用 helper 自己的慣例，蓋過了呼叫端的語意**。「每個檔案有自己的 tag」這個慣例套在 helper 上，表面上合規，但日誌的 tag 要表達的是「事件發生在哪裡」，不是「程式碼寫在哪裡」。

## 解決方案

- 共用 helper 透過參數接收呼叫端的識別（如 `log(tag: _tag, ...)`），不在 helper 內寫死。
- 測試從至少兩個不同的呼叫點觸發，斷言收到的識別各不相同，證明沒有寫死。

## 預防措施

- 抽共用前，先逐一比對各副本，列出彼此不同的部分，每一項都判斷是「可統一的雜訊」還是「呼叫端的語意」。
- 規格若規定了日誌或事件的欄位來源，重構票的驗收要加一條斷言那個欄位的值。
