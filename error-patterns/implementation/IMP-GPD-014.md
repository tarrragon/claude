# IMP-GPD-014: 共用命令包裝函式的預設逾時偏短，重量級操作沒傳 timeout 就繼承了它；同類操作中只有一個被單獨調高，其餘照舊

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | implementation |
| 來源版本 | 0.5.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-10-28 |

## 症狀

共用的子程序包裝函式（例如 `run_git_command(args, timeout=10)`）以短預設值服務輕量查詢。某個重量級操作（大量檔案的新增、移除、複製）沒有傳 `timeout`，於是套用預設值。檔案量小時看不出問題；檔案量一大，操作在預設秒數被強制中斷，留下做到一半的狀態，例如刪了一部分檔案、管理資料還在。

同一組操作中的另一個（例如「新增」）先前因為逾時被單獨改成具名常數，而對稱的操作（「移除」）沒有一起改。修正只落在當時出事的那一個呼叫點。

實證（2026-10-28）：worktree 的 add 已用 120 秒常數，remove 仍繼承包裝函式的 10 秒預設；一天內四次移除被中斷，每次都留下數千筆刪除到一半的檔案，需要用戶手動強制清理。

## 根因

**預設值的服務對象與實際呼叫者不一致**。包裝函式的預設值是為最常見的輕量呼叫設計的，卻同時套用到所有沒傳參數的呼叫，包括耗時與資料量成正比的操作。

**修正停在出事的呼叫點**。調高逾時時沒有盤點同一包裝函式的其他重量級呼叫，對稱的操作被漏掉。

**中斷不是無害的失敗**。逾時直接殺掉子程序，對非原子操作會留下中間狀態，後續清理還可能被保護性守衛擋住。

## 解決方案

- 重量級呼叫一律顯式傳入具名的逾時常數，並記錄實際耗時。
- 逾時或失敗時，若中間狀態可以安全判定（例如殘留全是已追蹤檔的刪除、分支已併入主線），由工具自動收尾；判定不成立就停手並回報不成立的條件。

## 預防措施

- 修一個呼叫點的逾時時，用 grep 列出同一包裝函式的所有呼叫，逐一判定是否屬於重量級操作，一起修。
- 包裝函式的預設逾時只服務輕量查詢；重量級操作在呼叫端寫具名常數，避免靜默繼承預設值。
- 測試以注入很小的逾時重現中斷，斷言工具會停手或收尾，不會留下無法清理的狀態。
