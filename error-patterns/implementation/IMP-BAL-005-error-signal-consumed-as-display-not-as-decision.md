# IMP-BAL-005：錯誤訊號被消費為顯示而非判定

## 基本資訊

- **Pattern ID**: IMP-BAL-005
- **分類**: 實作 bug（implementation）
- **來源版本**: v0.2.1
- **發現日期**: 2026-07-30
- **風險等級**: 高（造成不可逆的靜默資料遺失，且缺陷在畫面上偽裝為已處理）
- **影響範圍**: 任何回傳錯誤清單並在收尾段推進持久化狀態的流程；實證於 `.claude/scripts/sync-claude-pull.py` 的三方合併路徑

---

## 摘要

**函式如實回傳了錯誤狀態，呼叫端也如實把它印出來，但沒讓它參與任何判定，流程照原路走完。** 錯誤因此同時具備兩個看似矛盾的性質：它是可見的（畫面有紅字），也是未被處理的（後續步驟當作沒發生）。

這個組合正是它難被發現的原因。程式碼審查者掃過呼叫端會看到錯誤訊息被列印，於是把「有處理」這件事勾掉；而真正該問的是「印完之後呢」。與完全沒有錯誤處理的程式碼相比，這種形態的偵測難度更高——沒有錯誤處理是一眼可見的缺口，印了但不判定則長得像已經處理過。

## 症狀

- 函式回傳 `(結果, 錯誤清單)` 形態的 tuple，呼叫端解包後只把錯誤清單用於 `print` / `log`，未出現在任何 `if` 條件中
- 錯誤訊息在執行畫面上確實顯示，但後續步驟（提交、標記完成、推進狀態、寫入檢查點）無條件執行
- 事後追查時，log 裡找得到當初的警告——問題不在於沒有記錄，而在於記錄沒有改變行為
- 對錯誤數量的判斷停留在「有幾個」（用於格式化訊息），沒有進到「是否為零」（用於決定分支）

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 回報與判定被當成同一件事 | 撰寫者把「讓使用者知道」誤認為錯誤處理的完成態 | 錯誤處理停在輸出層，未進入控制流 |
| 訊息本身提供了虛假的完成感 | 紅字、警告色、計數都讓呼叫端看起來已在處理錯誤 | 審查者的注意力被訊息吸走，不再追問後續分支 |
| 部分成功缺少明確語意 | 「大部分成功、少數失敗」的收尾行為未被定義 | 預設落入「當成成功」，因為那是不寫任何條件時的行為 |
| 收尾步驟寫在共同路徑上 | 狀態推進、檢查點寫入放在所有分支之後的公共段落 | 任何分支的失敗都無法阻擋它 |

**與靜態設定型未消費的差異**：`ARCH-BAL-005` 描述的是設定檔中的理由欄位無任何讀取者，退化為裝飾文字。本模式的訊號**有**讀取者，只是讀取者用錯了用途（顯示而非判定）。前者靠 grep 零命中即可偵測，後者 grep 會命中，必須讀懂命中處是在字串格式化還是在條件判斷裡，偵測成本高一個量級。

## 案例：sync-pull 的 base SHA 在有衝突時仍被推進（2026-07-30）

`.claude/scripts/sync-claude-pull.py` 的三方合併路徑：

    applied, conflicts, residue = apply_upstream_delta(...)
    print_color(f"   已套用 {applied} 個 delta 變更", "green")
    if conflicts:
        print_color(f"   {len(conflicts)} 個檔案衝突，已存入 .sync-conflicts/", "red")
        for c in conflicts:
            print_color(f"     - {c}")
    ...
    # 共同收尾段
    head_result = run_git(["rev-parse", "HEAD"], cwd=str(temp_dir))
    if head_result.returncode == 0:
        write_base_sha(claude_dir, head_result.stdout.strip())

`conflicts` 非空代表這些檔案的上游變更**沒有**套進本地（本地原檔保留，衝突副本另存）。但收尾段把 base SHA 推進到上游 HEAD，等同宣告「本地已與該 commit 同步」。下次同步從新 base 計算差異，這批未套用的變更不再出現在差異集中，永久遺失。

注意 `if conflicts:` 這一行**確實存在**——它只是用來決定要不要印訊息。整段程式碼裡，`conflicts` 從未影響 `write_base_sha` 是否被呼叫。

實證後果見 `0.2.1-W3-145`：某 skill 目錄缺 7 個檔案且無法透過重新同步恢復。

## 解決方案

讓錯誤訊號進入條件判斷，決定收尾步驟是否執行：

    if conflicts:
        print_color(f"   有 {len(conflicts)} 個未解衝突，暫不推進 base SHA"
                    f"（請人工解決 .sync-conflicts/ 內衝突檔後重新 pull）", "yellow")
    else:
        head_result = run_git(["rev-parse", "HEAD"], cwd=str(temp_dir))
        if head_result.returncode == 0:
            write_base_sha(claude_dir, head_result.stdout.strip())

三個設計要點：

1. **對齊既有的心智模型**。此處採 git merge 語意——衝突未解則 HEAD 不動。選一個使用者已經理解的模型，比自創規則更容易被正確預期。
2. **不推進時必須給出口**。訊息要說明為何停住、以及做什麼可以繼續，否則使用者只知道失敗不知道下一步。
3. **明示接受的代價**。此方案下衝突若長期未解，狀態會永久停在舊點並重複告警。這是刻意的取捨：吵但不遺失，優於安靜但永久遺失。把取捨寫進註解，避免後人把它當成待修的缺陷而「修回去」。

## 預防措施

| 時機 | 檢查 |
|------|------|
| 撰寫回傳錯誤清單的函式時 | 在 docstring 明寫「呼叫端應如何依此清單分支」，而非只寫「回傳衝突檔清單」 |
| 審查呼叫端時 | 對每個錯誤變數問「它出現在哪些 `if` 裡」。只出現在字串格式化中即為本模式 |
| 設計有「部分成功」可能的流程時 | 部分成功的收尾行為必須被明確決定並記錄理由，不可讓它落入「不寫條件時的預設行為」 |
| 放置狀態推進 / 檢查點寫入時 | 確認它是否在所有分支的公共段落上。若是，確認每個分支的失敗都有辦法阻擋它 |

**測試層對應要求**：針對此類修復的測試必須直接斷言**持久化狀態本身**（狀態檔內容、資料庫欄位），而非函式回傳值。回傳值正確不代表寫入點遵守同一判定——本模式的缺陷正好發生在兩者之間。同時測試需先斷言錯誤路徑確實被觸發（如衝突副本檔存在），再斷言狀態未推進，否則造不出錯誤的測試會走過正常路徑而假綠。
