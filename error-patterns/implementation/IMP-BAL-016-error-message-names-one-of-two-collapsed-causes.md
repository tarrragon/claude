# IMP-BAL-016：兩種成因壓成同一回傳值，錯誤訊息指名其中一種

## 基本資訊

- **Pattern ID**: IMP-BAL-016
- **分類**: implementation（回傳值語意與錯誤訊息的對應）
- **風險等級**: 高
- **關聯**: [[IMP-BAL-017]]（訊息指名的抽象層與判準讀取的層不同；彼處落差在跨層改寫，此處在同一層內的成因合併）、[[IMP-BAL-005]]（錯誤訊號被消費為顯示而非判定）、[[PC-005]]（CLI 失敗歸因假設）、[[ARCH-BAL-019]]

一個函式對兩種語意相反的情況回傳同一個值（典型為 `False` / `None` / `-1`），呼叫端無從分辨，於是選一種寫進錯誤訊息。當實際發生的是另一種時，訊息不只是不精確——它主動指名一個不存在的問題，把診斷者導向唯一不該去的方向。

**Why**：合併兩種成因的動機通常是介面簡潔（「回傳是否成功」讀起來乾淨），而兩種成因在函式內部確實都導致「沒有寫入」。缺陷不在合併本身，在於呼叫端仍須產生一句具體的訊息，而它只有一個位元可依據。此時任何措辭都是猜測，且猜錯不會被任何機制發現——訊息的正確性沒有測試覆蓋，因為斷言通常只檢查退出碼。

診斷者的處境更不利：訊息描述的是一個可觀察的狀態（「找不到 X 欄位」），而該狀態可被直接查驗且**查驗結果為否**。此時多數人的推論是「訊息說找不到、但它明明在，所以是解析失效」——訊息成功地把注意力鎖在解析層，而真因在別處。

**Consequence**：

| 層級 | 影響 |
|------|------|
| 診斷 | 訊息指名的層級與真因無交集，依訊息展開的排查全屬無效工時 |
| 存活期 | 依訊息建立的追蹤票會把錯誤根因寫進票面，後續接手者以該根因為前提，錯誤因此固化 |
| 副作用 | 誤判為失敗常伴隨提前終止，使該呼叫之後的步驟（索引同步、狀態寫回）永不執行，產生第二層資料不一致 |
| 偵測 | 提前終止路徑通常無測試覆蓋——測試多驗「值不同時會更新」，不驗「值相同時的行為」 |
| 觸發頻率 | 冪等呼叫在「先寫檔再同步索引」類工作流中是必經路徑，非邊角情境 |

**Action**：

| 情境 | 做法 |
|------|------|
| 函式回傳布林表示「是否成功」 | 檢查是否存在兩種以上導致 `False` 的路徑。有則改回傳三態（列舉或 `Optional` 加原因），不得由呼叫端猜 |
| 以「結果是否與輸入相同」判斷是否成功 | 該判斷把「無需變更」歸為失敗。先以獨立查詢確認前提（欄位是否存在、目標是否可達），再判斷是否需要變更 |
| 冪等呼叫 | 預設為成功。重複執行同一操作而狀態已符合預期，是達成而非失敗 |
| 撰寫錯誤訊息 | 訊息指名的成因必須是呼叫端**實際查證過**的那一個。無法查證時改述可觀察事實（「未寫入任何變更」），不要推測原因 |
| 接手一張以錯誤訊息為根因的票 | 先復現並讀產生該訊息的程式碼路徑，不以票面根因為前提。訊息指名的層級是最不可能的方向 |

**識別訊號**：函式 docstring 寫「回傳是否成功」但函式內有多個 `return False`；以 `if result == original: return False` 判斷失敗；錯誤訊息描述一個可直接查驗且查驗為否的狀態；票面記載「訊息說 X 不存在，但 X 明明存在」。

**邊界**：與 `IMP-BAL-005`（錯誤訊號被消費為顯示而非判定）相反——那是訊號正確但未被當判定用，本模式是訊號本身指錯方向。與 `PC-005`（CLI 失敗歸因假設）的差別：那是歸因未經查證，本模式是查證了也會被誤導，因為被查證的對象由訊息指定。

**實證來源**：`doc update <ID> --status <S>` 在檔案 status 已等於 `S` 時回報「找不到 status 欄位」。`_update_frontmatter_status` 以 `re.sub` 結果是否與原文相同判定成功，值相同時替換結果逐字相同故回傳 `False`；呼叫端把 `False` 一律解讀為欄位不存在並 `sys.exit(1)`。`re.search` 可證欄位存在，regex 亦正常匹配。

該 `sys.exit(1)` 位於索引同步之前，故檔案 status 已達目標值時索引永不同步——一次實測為四份文件的檔案 frontmatter 為 confirmed/confirmed/confirmed/draft，索引四筆全為 draft，讀檔的指令顯示正確而讀索引的指令顯示錯誤，雙方皆無錯誤訊號。

對應追蹤票的 Why 欄逐字記載「執行 `--status discussing` 回報找不到 status 欄位，但 frontmatter 第 4 行明確有 `status: discussing`」——舊值與目標值為同一字串，該句本身即為冪等呼叫的證據，但當時被讀為解析失效的證據，票面因此帶著錯誤根因存續 36 天。發現者由症狀直接讀該函式而繞過誤導，其自述觸發條件為「訊息與眼前檔案內容直接衝突」；若檔案值恰好不同而訊息僅為「更新失敗」，同樣會依訊息方向排查。**誤導性訊息的成本上限由矛盾的顯著程度決定，而非由診斷者的能力決定。**
