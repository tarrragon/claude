# IMP-BAL-007：共用 runner 的輸出正規化破壞格式敏感解析

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | high |
| 發現途徑 | Phase 4 多視角審查（重用視角掃描既有共用層） |
| 偵測難度 | 高（單元測試全綠，缺陷只在首行且下游表現為語意誤判而非崩潰） |

## 症狀

一個被多處呼叫的共用命令 runner 對子行程 stdout 做整體 `strip()`，下游解析器依固定欄位寬度切分該輸出。若輸出格式的**首行第一個字元可能是有意義的空白**，整體 strip 會使首行左移，造成：

- 欄位值錯位（狀態碼取到下一個字元）
- 內容截斷（路徑或名稱掉首字元）
- 語意翻轉（未 staged 被判為已 staged、未追蹤被判為已追蹤）

只有第一行受影響，其餘行正確。下游不會拋錯，只會安靜地做出錯誤判斷。

**本案具體樣態**（`lib/git_utils.run_git_command` 與 `lib/hook_io.run_git`）：

`git status --porcelain` 的格式是 `XY filename`，X 為 index 狀態、Y 為 worktree 狀態。worktree-modified 而未 staged 的檔案，X 是空白。實測固定值：

```
真實 stdout 首行:  " M aaa.txt"
經 runner strip 後: "M aaa.txt"
消費端解析結果:     status='M ' path='aa.txt' is_staged=True
```

檔名掉首字元，且「未 staged」被判為「已 staged」。已確認的受害端：依 `is_staged` 分組的狀態提醒（首個檔案歸錯組）、依路徑比對的 ticket md 提醒（比對失敗而靜默漏報）。

## 根因

兩層獨立成因疊加，缺一即不會發生：

**成因一：共用層做了下游不知情的正規化。** `strip()` 對「取單一值」的呼叫端（分支名、commit hash）是便利；對「解析多行結構化輸出」的呼叫端是破壞。runner 不知道呼叫端要如何解讀，卻替它做了不可逆的預處理。便利與破壞來自同一行程式碼，所以不會被「這行有什麼問題」的檢視抓到。

**成因二：測試 mock 的層級高於缺陷所在層級。** 既有測試 mock 的是 runner 的回傳值（直接餵入帶前導空白的字串），而 strip 正發生在 runner 內部——mock 把缺陷點整段替換掉了。測試名稱甚至叫「格式保留」，斷言的卻是「若 runner 回傳未被破壞的字串，解析正確」，與「runner 是否破壞字串」無關。測試全綠且看似正相關，實則從未執行過缺陷路徑。

**為何長期潛伏**：受害端的表現是「少報一個」或「歸錯一組」，不是崩潰。使用者看到輸出就相信它完整，沒有對照組可比。

## 解決方案

1. **runner 只做可逆的最小處理**：需要去除尾端換行時用 `rstrip("\n")`，不用無參數 `strip()`。若既有呼叫端依賴整體 strip 的副作用（如比對分支名），在呼叫端自行 strip，不在共用層代勞。
2. **測試 mock 下移至真正的外部邊界**：mock `subprocess.run` 而非 mock runner，使 runner 內部的處理邏輯進入受測範圍。
3. **對真實輸出做一次固定值對照**：取原始 stdout 與經共用層後的結果並列比對，逐字確認（本案即以此確證，非依賴推論）。

## 預防措施

| 情境 | 動作 |
|------|------|
| 共用層要對命令輸出做任何正規化（strip / 大小寫 / 分行 / 去引號） | 先問「有沒有呼叫端依賴原始位元組」；有則不做，把處理留給呼叫端 |
| 撰寫解析器的測試 | mock 點必須在被測邏輯之外——若缺陷可能在 runner 內，就不能 mock runner |
| 既有測試名稱含「格式保留」「format preserved」類字樣 | 檢查它 mock 的層級是否讓斷言變成恆真 |
| 輸出格式含固定寬度欄位或有意義的前導空白 | 在解析器的 docstring 標明「本函式要求原始輸出未經 strip」 |

## 一般化

「共用層的便利處理破壞下游語意」不限於 strip：JSON 解析器自動轉型數字、日誌框架自動 trim 訊息、HTTP client 自動 decode，都屬同一族。判準是**該處理是否不可逆，以及下游是否有辦法知道它發生過**。不可逆且不可知，就是這個模式的溫床。

與 [[TEST-BAL-001]] 的差別：該模式是測試 fixture 的格式由撰寫者構造而與真實輸入分歧；本模式的 fixture 格式正確，問題出在 mock 的**層級**把缺陷點排除在受測範圍外。兩者都導致「測試全綠但真實輸入失準」，但修法不同——前者換 fixture，後者移動 mock 邊界。
