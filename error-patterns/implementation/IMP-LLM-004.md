# IMP-LLM-004: 程序內快取讓檔案鎖失效：鎖外載入的舊內容在鎖內被當成現況改寫，覆蓋期間他方的寫入

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | implementation |
| 來源版本 | 3.2.0 |
| 風險等級 | 高 |
| 首次觀察 | 2026-11-10 |

**判準**：凡是在鎖內做「讀、改、寫」，讀這一步都必須讀到鎖內當下的檔案。一個不比對檔案狀態的程序內快取，只要被鎖內的讀取命中，鎖就形同虛設。

## 症狀

兩條寫入路徑都對同一個檔案加了檔案鎖，結果仍然發生遺失更新：A 程序的寫入，被 B 程序整份寫回的舊內容覆蓋。git 歷史裡看得到 A 的 commit，下一個 commit 中那段內容就消失了。外觀上兩方都成功，沒有任何錯誤或警告。

實例（ticket CLI，2026-11-10）：

- 主控以 `append-log` 追加審查票的四段 Solution。
- 同一時間，另一個程序在跑 `ticket create --source-ticket <審查票>`。這個程序一開始為了驗證來源票而載入它，接著花數十秒做 GitHub 查重，最後在鎖內把新票號追加進來源票的 `spawned_tickets`。
- 鎖內的讀取命中了程序內快取，拿到的是數十秒前的版本。寫回之後，主控追加的四段全部消失。

## 根因

- 檔案鎖保證的是「鎖內的讀與寫之間沒有別人寫」，前提是讀取確實讀了檔案。
- 程序內快取（例如以路徑為 key 的 dict，程序結束才失效）把讀取變成讀記憶體。快取的內容是在鎖外、更早的時點載入的，鎖內命中它，等於拿鎖外的快照當成現況。
- 常見的成因是快取為效能而加（同一程序內重複載入同一個檔），加的人只考慮了唯讀路徑，沒有盤點鎖內的讀改寫路徑也會經過它。
- 常見的併發測試抓不到：兩個新程序各自首次載入，快取都是空的。這個缺陷只出現在「同一程序先讀，隔一段時間，再於鎖內改寫」的形狀。

## 解決方案

1. 快取命中時比對檔案狀態（例如 `(st_mtime_ns, st_size)`），不符就丟棄並重讀。修在載入函式一處，所有經過它的鎖內路徑都一併受益。ticket CLI 的修法即此：`parser.load_ticket` 新增與快取並列的 stat 記錄，命中時比對。
2. 或者鎖內的讀取一律繞過快取（讀之前先移除該 key）。
3. 補一個正向對照測試：同一程序先載入，外部程序改寫檔案，再於鎖內改寫，斷言兩方的寫入都保留；確認修正前為紅燈。

## 預防措施

- 新增程序內快取時，盤點所有在鎖內呼叫該載入函式的路徑，逐條標明是否受影響。
- 遇到鎖保護的讀改寫時，code review 要追問「這個讀取讀的是檔案，還是記憶體」。
- 殘餘風險：外部改寫之後，mtime 與 size 都沒變時偵測不到。需要更強的保證時，改比對內容雜湊。
