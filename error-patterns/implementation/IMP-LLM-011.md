# IMP-LLM-011: 先啟動子程序、後安裝訊號轉送 handler，兩者之間收到的訊號不會轉送

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 分類 | implementation（訊號處理、子程序生命週期） |
| 來源版本 | 3.3.0 |
| 首次觀測 | 2026-11-13 |

## 症狀

驗證「父程序收到 SIGTERM 時轉送給子程序群組」的測試會隨機紅燈：子程序應寫出的紀錄檔不存在，而父程序原本的 handler 收到了訊號。單獨執行這個測試類時，即使系統負載高也全綠；只有其他測試套件同時執行時（例如合併閘門跑全套件）才會紅。前一次修正已把計時等待改為就緒檔同步，修正後在低負載下取樣 5 次全綠，之後在並行環境中又復現。

## 根因

轉送 handler 在子程序啟動之後才安裝：

```python
with subprocess.Popen(...) as proc, forward_sigterm_to_group(proc):
    ...
```

從 `Popen` 回傳到 context manager 安裝好 handler，中間有一段時間窗。若主執行緒在這段期間被排程延遲，送達的 SIGTERM 會由原 handler 處理，不會轉送，子程序群組因此收不到訊號。

測試的就緒檔由子 shell 在安裝 trap 之後寫出，只能證明子程序已準備好接收，不能證明父程序已準備好轉送。同步只涵蓋了兩個前提中的一個，所以時間窗在測試中依然存在。只有並行負載讓主執行緒延遲時才會落入時間窗，單獨執行的取樣量測不到。

## 解決方案

先安裝 handler，再啟動子程序。子程序建立前收到的訊號先記錄，建立後補送：

```python
with forward_sigterm_to_group() as forwarder, subprocess.Popen(...) as proc:
    forwarder.attach(proc)   # 補送建立前收到的 TERM
```

- 子程序尚未建立時，handler 只記錄訊號，不轉送也不交還原 handler。
- 呼叫 `attach(proc)` 時，先把訊號補送給子群組，再交還原 handler。
- 若子程序啟動失敗，離開 context 時還有待處理的訊號，就交還原 handler，不吞掉訊號。

測試以注入方式直接驗證時間窗：patch `Popen`，在子程序建立前對自身送 TERM，斷言子程序以 `-SIGTERM` 結束。這則測試修改前必紅、修改後必綠，結果不受負載影響。

## 預防措施

- 「啟動資源」與「安裝保護它的 handler」這兩步，順序是先裝保護、再啟動資源。
- 測試的就緒同步要涵蓋斷言所依賴的每一方。子程序一側的就緒檔，無法證明父程序已就緒。
- 時序類紅燈的取樣條件，要對應實際的觸發條件。本例的觸發條件是並行套件造成的主執行緒延遲，而非負載數值；用負載當取樣條件，N 再大也量不到（另見 PC-168）。
- 能用注入延遲或 patch 打開時間窗的競態，優先寫成確定性的注入測試，不靠隨機取樣判定是否修好。

## 關聯案例

框架共用函式庫中 `run_with_graceful_timeout` 的 SIGTERM 轉送：合併閘門的 hooks 套件出現隨機紅燈，前一次修正只做了子程序一側的就緒檔同步，未能根治；改為先安裝 handler 並補送訊號後修好（3.3.0 執行期，2026-11-13）。
