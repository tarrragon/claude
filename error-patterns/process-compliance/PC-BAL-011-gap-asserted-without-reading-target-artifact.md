# PC-BAL-011: 未讀目標載體即斷言缺口存在，據以建票或決策

## 症狀

建立 ticket 或做出「需要新增」決策時，理由欄寫著目標載體缺少某項處理（「無任何文件說明適用邊界」「此例外是否延伸未定義」「需新建偵測工具」），實際打開該載體後發現對應處理早已存在。

典型表徵：

- ticket 的 `why` 欄位描述的缺口，在該票 `where.files` 指向的檔案內已有章節處理
- 執行者接手後的第一個動作（讀目標檔案）就推翻了建票理由
- 建票者與執行者為同一人時，表現為「執行到一半發現自己寫的前提是錯的」
- 同一工作階段內反覆出現，因為根因未被辨識為模式

## 根因

**缺口判斷所需的證據，與建票所需的證據，不是同一組。** 建票只需要「我注意到某個問題」，缺口判斷需要「我確認目標載體沒有處理它」。前者的門檻遠低於後者，而流程沒有在兩者之間設檢查點，於是「注意到」被直接當成「確認缺口」。

三個放大因素：

1. **部分閱讀即形成判斷**。讀了規則的主表就停下來，未讀主表之後的補充章節；而框架文件的慣例正是把邊界、例外、判準放在主表之後。
2. **搜尋詞與既有實作的命名不匹配**。要找「依賴型引用偵測」，既有實作名為 `reference-stability-rule8-guard`——語意相同、字面不同，關鍵字搜尋不會命中。
3. **建票被視為低成本動作**。建票不改動任何產物，直覺上「先建了再說」風險為零，因此驗證動作被跳過。實際成本落在下游：執行者若未察覺，會依錯誤前提工作。

## 影響

錯誤前提的破壞力與其導向的動作成正比。若前提是「規則缺失需補寫」，代價是重複定義造成的規則衝突；若前提是「需大規模清理」，代價是對大量合法內容執行破壞性變更。後者遠高於不作為。

派發放大此風險：建票者若直接派發代理人執行，代理人拿到的是已成文的前提，其驗證動機遠低於建票者本人。

## 解決方案

**建票時，`why` 欄位若含「缺少 / 未定義 / 無 / 需新建」等缺口斷言，必須先完成對應的驗證動作再落筆。**

| 斷言形態 | 驗證動作 |
|---------|---------|
| 目標文件缺少某項處理 | 讀該文件全文（至少讀完該規則所屬章節與其後續補充章節），非僅搜尋關鍵字 |
| 需新建工具 / 模組 | 掃描對應目錄的既有實作，並以功能語意而非命名關鍵字比對 |
| 兩條規則衝突且無邊界說明 | 讀兩份文件的完整相關章節，確認是否已有分級、附則或交叉引用 |
| 某機制未被涵蓋 | 查該機制的權威定義檔，而非依賴記憶或他處引述 |

驗證結果寫入 ticket 的 Problem Analysis，使執行者可據以判斷前提可信度，而非只看到結論。

## 預防措施

- 缺口斷言的門檻是「我讀過並確認沒有」，不是「我沒看到」。兩者的差別在於是否執行過查證動作，這個差別必須在 ticket 內可辨識
- 若建票當下無法完成驗證，`why` 改為疑問形態（「需確認 X 是否已被涵蓋」）並將驗證列為第一條 acceptance，不寫成既成事實
- 派發前重讀自己寫的 `why`：其中的事實宣稱有哪些是查證過的、哪些是推斷的？推斷的部分應在 prompt 中明示要求執行者先驗證
- 執行者側的對應防護：接手後的第一個動作是讀目標載體，發現前提失真時回報並縮小範圍，不硬做

## 關聯

- `PC-068`（規劃階段決策自寫 utility 前未掃描既有實作）：同一根因的不同載體。PC-068 的載體是實作策略文件，本模式的載體是 ticket 的缺口斷言；預防措施共用「決策前掃描既有涵蓋」
- `PC-BAL-008`（並行寫入共用索引掃入他方暫存檔）：同屬「既有機制已記錄但未被套用」的家族。差別在 PC-BAL-008 是知道規則卻沒執行，本模式是不知道規則已存在
