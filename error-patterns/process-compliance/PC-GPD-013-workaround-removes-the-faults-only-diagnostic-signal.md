# PC-GPD-013: 繞道路徑成功，使共用資源的故障失去唯一的診斷訊號

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 高 |
| 來源版本 | 0.1.0 |

## 症狀

一項共用資源（鎖檔、快取、佇列、連線池）故障了，但**所有使用者都在正常工作**。原因是主要路徑早已改走一條不觸碰該資源的替代實作，故障因此不再產生任何人會看到的症狀。

故障持續期間，唯一的外部表現是**次要路徑的零星失敗**——而那些失敗通常被歸因為並行環境的常態抖動，因為它們的錯誤訊息與真正的暫時性競爭**逐字相同**。

**本案實例**：`.git/index.lock` 殘留 15 分鐘，三個並行 session 全程正常提交。原因是框架已將代理人票務提交的預設改為隔離索引（`GIT_INDEX_FILE`），該路徑全程不建立也不等待 `.git/index.lock`。只有需要共用 index 的操作（`git add`／`git restore --staged`／裸 commit）會撞上，而這些操作在該環境屬低頻。

**判定殘留而非競爭的四項依據**（缺一不可，且各答不同問題）：

| 依據 | 本案觀測 | 為何不可省 |
|------|---------|-----------|
| 鎖檔大小 | **0 bytes** | 鎖檔的實作方式是「新內容寫進 `.lock`，再 rename 成目標」。0 bytes 表示行程在建鎖之後、寫入之前被中止，鎖裡沒有任何意圖。**這一欄決定的是「丟棄」還是「把那一步做完」**，見下節 |
| 持有者（`lsof <鎖檔>`） | 零行程 | 答「此刻誰持有這個 fd」 |
| 同類行程存在性（`ps`） | 零個該工具的行程 | 答「有沒有行程正要來持有」 |
| 存活時長 | 15 分鐘 | 正常競爭的鎖存活數十毫秒 |

**持有者與行程存在性是兩根不同的軸，不可互相替代**。`lsof` 只反映當下持有 fd 的行程；一個剛啟動、尚未開啟鎖檔的行程，在 `lsof` 下與「不存在的行程」完全同形。只查 `lsof` 就移除，可能刪掉一把正要被使用的鎖。

**存活時長單獨不足以判定，且其解讀隨長短反轉**：同一路徑上 1 分鐘的鎖與 15 分鐘的鎖是相反的東西——後者幾乎必然是殘留，前者很可能是正在進行的操作。因此**年齡小時，`ps` 檢查從建議升為必要**；年齡大時 `ps` 仍應查，但主要作為佐證。

### 有內容的鎖：內容即意圖，處置與空鎖相反

大小非零時**不可套用空鎖的處置**。非零表示寫入已完成、rename 未執行——行程死在那兩步之間，而**鎖裡裝的是一個未完成操作的遺囑**。

**本案第二起實例**：一次建票操作死亡，同時留下三個鎖。其中 `.git/refs/heads/main.lock` 為 **41 bytes**，內容是一個完整的 commit hash；該 commit 真實存在、內容為一份新建文件的 184 行新增零刪除，且其 parent 恰為當時的 HEAD——一個乾淨的 fast-forward。

**正確處置是把那一步做完，不是移除**：

```
git update-ref refs/heads/main <鎖內的 hash> <當時的 HEAD>
```

若照空鎖的方式直接 `rm`，該 commit 即成為無任何 ref 指向的孤兒，而**磁碟上的檔案看起來完好無損**——`ls` 查得到、`git log` 查不到，沒有任何人會發現它從未進入歷史。這是本模式第三層（損害集中在無人再看的項目）在單一操作尺度上的重演。

**兩類的分辨與處置**：

| 鎖檔大小 | 語意 | 處置 |
|---------|------|------|
| 0 bytes | 死在寫入之前，無意圖 | 上表四項依據確認後移除 |
| 非零 | 寫入完成、rename 未執行，內容即意圖 | **先讀懂內容**，判定該操作是否應完成；能完成則補完，不能則記錄內容後才移除 |

**同一次死亡通常留下多個鎖，且各自阻斷不同的操作**。本案第二起的三個鎖分別阻斷 ref 更新、HEAD 更新、與該版本目錄下的一切建票——每一方只會撞上自己用到的那一種，因而各自把它看成孤立的偶發失敗。**盤點時要掃全部鎖檔，不能只看擋住自己的那一個**：

```
find .git -name "*.lock" -maxdepth 3 -exec ls -l {} \;
```

**識別特徵**：

- 同一個共用資源上，某類操作**連續**失敗（非偶發），而另一類操作全部成功
- 失敗訊息與該資源的正常競爭訊息**完全相同**，因此被套用「重試即可」的既有處置
- 團隊中沒有人回報異常——每個人都在成功的那條路徑上
- 該替代路徑的引入理由，往往正是為了規避這個資源的競爭問題（見根因）

## 根因

繞道路徑通常是**上一次診斷的產物**：某資源的競爭被記錄為問題後，建議的修法就是不要用它。修法落地之後，該資源仍在系統裡、仍會故障，但**已經沒有任何主要流程會因它而失敗**。

診斷訊號與故障之間的連結被切斷了，而切斷它的正是修法本身。

本案可逐項對上：既有記錄（`IMP-046`，2026-03-29）已完整描述 `index.lock` 殘留機制，其「中期建議」第 2 條即為「Hook 中使用 `GIT_INDEX_FILE` 環境變數，讓 git 操作使用獨立的 index 副本」。該建議後來成為代理人票務提交的預設。**繞道成功到讓故障失去了原本會觸發診斷的症狀**——同一份記錄裡另有一條「長期建議：建立自動清理超過 10 秒的殘留鎖」，那一條沒有落地，而它正是唯一針對故障本身而非針對症狀的處置。

**這使本模式具有反直覺的方向性**：緩解措施做得越徹底，故障越不可見。一個部分成功的繞道會留下噪音提醒你根因還在；一個完全成功的繞道不會。

### 第二層：同步失敗以 WARNING 出現在成功訊息的相鄰行

故障期間，工具的「寫入內容」與「同步共用資源」是兩個獨立步驟。前者成功、後者失敗時，一次輸出裡會同時出現失敗與成功兩行：

```
warning: Unable to create '.../.git/index.lock': File exists
[OK] 已追加日誌
```

**內容確實寫進去了，所以成功訊息不是謊話**；失敗的只是共用資源的同步。讀者看最後一行即得到「成功」，而依 `bash-tool-usage-rules` 規則二的輸出過濾方向，警告行通常比正常輸出短、措辭不同，`tail` 與 grep 白名單都更容易把它濾掉。

**這一層不只是人眼漏看**：該次呼叫的 **exit code 仍為 0**——工具把「主要工作完成」視為整體成功，同步失敗降級為警告。因此 `cmd_a && cmd_b` 的串接同樣不會停下，重試包裝與 CI 判定也不會。**要在工具層攔截，判準必須是 stdout 中出現同步失敗字樣，不能是 exit code**；以 exit code 為判準的自動化在這一層完全無鑑別力。

### 第三層：殘留損害集中在無人再碰的檔案

故障排除後，共用資源上的殘留狀態**對「之後又被寫過的項目自我修復」**——下一次寫入會重新同步。**對「故障期間建立、之後沒人再碰的項目則永久停留」**。

本案的具體形態：故障期間新建的兩份文件，其共用 index entry 停在建立之前，即「staged 刪除」。任一方此後執行裸 commit 都會直接刪除那兩份檔案，而 `git log` 外觀完全正常、無任何訊號。

**損害因此恰好集中在沒人正在動的項目上，而那也正是沒人會去查的項目。** 這不是巧合，是同一個機制的兩面：正在被動的項目會被寫入修復，正在被看的項目也是它們。

## 解決方案

1. **繞道落地時，同步保留一個針對資源本身的檢查點**。繞道解決的是「我的流程不再受影響」，不是「資源不再故障」。兩者都要處理——否則故障會累積到某個共用操作上一次爆發。本案的既有記錄已寫出這個檢查點（自動清理超過 N 秒的殘留鎖），只是沒落地。
2. **對共用資源的操作連續失敗時，先判定是競爭還是殘留**，依症狀節的四項依據（大小／持有者／同類行程存在性／存活時長）逐項確認後才移除。**連續失敗與偶發失敗的處置相反**：偶發重試即可，連續重試永遠不會成功。
3. **故障排除後，主動掃描殘留狀態，且掃描範圍必須涵蓋「沒人在動的項目」**。只檢查自己正在處理的檔案會系統性地錯過全部損害（見根因第三層）。三平面比對是可機械執行的判準：

   ```
   git show :<path>        # 共用 index
   git show HEAD:<path>    # 已寫入版本歷史
   cat <path>              # 工作區
   ```

   index 落後 HEAD 即為殘留快照，以 `git restore --staged <path>` 重設；index 領先 HEAD 且等於工作區則是進行中的正常工作，**不可重設**。

4. **先用一行機械訊號縮小範圍，再逐檔三平面比對**。`git diff --cached --stat HEAD` 的輸出中，**純刪除、零新增**的行即是「故障期間建立、之後無寫入修正」的簽名——該項目的 index entry 停在檔案尚不存在的狀態，相對於已含全文的 HEAD 必然全數呈現刪除。三類的分辨為：

   | `--stat` 形態 | 判定 | 處置 |
   |--------------|------|------|
   | 純刪除、零新增 | 高度可疑為殘留 | 三平面確認後 `git restore --staged` |
   | 含新增行 | 可能是未提交的新工作 | 必須逐檔三平面比對，不可一律重設 |
   | 無輸出（index == HEAD） | 乾淨 | 不動 |

   **這一步的價值在於它不需要人判斷「這個項目之後有沒有人再碰」**——第三層的分界本身要靠這個判斷，而在並行環境中沒有任何一方掌握全局。純刪除這個形態把它化為可直接掃出的訊號。

## 預防措施

| 時機 | 動作 |
|------|------|
| 為某資源的競爭問題引入繞道路徑 | 同時建立針對該資源本身的檢查或清理機制；只做繞道等於把故障轉為靜默 |
| 同一操作對共用資源連續失敗三次以上 | 停止重試，改判定殘留（大小／持有者／同類行程存在性／存活時長）。**大小非零者先讀內容再決定**，可能需要補完而非移除；**鎖很新時 `ps` 檢查為必要而非建議** |
| 判定某鎖為殘留之後 | 盤點全部鎖檔（`find .git -name "*.lock"`）——同一次死亡通常留下多個，各自阻斷不同操作，只清擋住自己的那一個會留下其餘 |
| 共用資源故障排除之後 | 全量掃描殘留狀態，範圍涵蓋近期無人寫入的項目；只掃自己的工作檔會錯過全部損害。先以「純刪除、零新增」訊號縮小範圍（解決方案 4） |
| 讀取會同步共用狀態的工具輸出 | 不以最後一行、**也不以 exit code** 判定成敗；同步失敗常降級為警告而 exit code 仍為 0，`tail` 與 grep 白名單易濾掉相鄰的警告行 |
| 並行環境中依他人回報的狀態表執行修正 | 重新量測後才動手——共用資源狀態屬瞬時平面，他人量測在其觀測當下為真，不承載持久結論 |

## 與相關模式的關係

- **`IMP-046`**（git index.lock 競爭條件）：本模式的**前一次診斷**，涵蓋鎖殘留的機制本身與處置指令。兩者的分界是時序——該則描述故障如何發生，本則描述其修法落地後故障如何變得不可見。引用該則時應一併檢查其「長期建議」是否落地，那是唯一針對故障本身的處置。
- **`PC-MON-001`**（工具防護落地於可繞過的執行點導致復發）：同屬「繞道使機制失效」家族，方向相反——該則是**防護**被繞過因而擋不住問題，本則是**故障**被繞過因而不被發現。前者漏的是攔截，後者漏的是診斷。
- **`PC-BAL-008`**（共用 git index 掃入他人已 staged 檔案）：本模式第三層產生的殘留 entry 是該則的燃料——殘留使 index 與 HEAD 分歧，此時任一次廣域 staging 或裸 commit 即命中該則。
- **`PC-GPD-009`**（檢查器正確執行，但量的軸與所問的問題不同）：**本模式的排查過程特別容易觸發它**。故障被繞道遮蔽時，排查者手上沒有直接訊號，只能用間接檢查代替——而間接檢查與所問問題不同軸時，會在鎖存在與不存在的兩種情況下給出**相同輸出**。本案至少兩次命中：一次以 `ticket create --dry-run` 能否推進來驗證「鎖是否已解除」（該命令有鎖無鎖皆會推進）；一次以 `git fsck` 的 unreachable commit subject 是否出現在 main 的 log 來驗證「有無工作遺失」（stash commit 的 subject 依設計永不出現在 log，該判準對此零鑑別力）。**先有無鑑別力的檢查，才有機會被巧合的因果騙過去**——移除鎖之後管道恢復、於是歸因於移除，而管道從未被它擋住。
- **規則落點**：`.claude/rules/core/bash-tool-usage-rules.md` 規則三（index.lock 短暫重試為預設）與規則七的「版本邊界（過期 index 快照）」邊界段。本則補上兩者之間的缺口——規則三說重試，規則七說如何偵測過期快照，但**沒有一條說「連續重試失敗時該改判殘留」**，也沒有說殘留掃描的範圍必須涵蓋無人再碰的檔案。

## 行為模式分析

繞道是對的決定，本模式不主張不要繞道。問題在於繞道之後，**沒有人再對那個資源負責**——它從每個人的主要路徑上消失了，於是也從每個人的注意力裡消失了。

三個並行 session 在故障期間各自遇到過共用 index 操作失敗，各自套用了「並行環境常態、重試即可」的既有處置，各自繞了過去，**沒有任何一方把它當成事件回報**。訊息與處置都正確，只是那套處置是為偶發競爭設計的，而這次是連續失敗。連續與偶發在單次觀測下同形，區分它們需要的是「我剛剛已經失敗過幾次」這個跨呼叫的計數——而那正是每次呼叫獨立判斷時最容易掉的資訊。
