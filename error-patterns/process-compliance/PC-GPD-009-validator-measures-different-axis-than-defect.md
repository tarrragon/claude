# PC-GPD-009: 驗證器驗的維度與缺陷所在的維度不同軸，每次都是「查了，而且通過了」

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-GPD-009 |
| 類別 | process-compliance |
| 風險等級 | 高 |
| 發現日期 | 2026-09-08 |
| 來源版本 | 0.1.0 |

## 症狀

一個名稱宣稱保證性質 P 的檢查，實際量的是一個容易量的代理指標 Q。Q 與 P 之間有縫，缺陷落在縫裡：**檢查跑了、通過了，而缺陷完好無損**。

這不是檢查器壞掉——它正確地量了 Q，回報也誠實。壞的是「通過 Q 即滿足 P」這個從未被寫下來的假設。

**識別特徵**：

- 檢查名稱或訊息用性質的語言（「不溢位」「範圍正確」「條件齊備」），實作用代理指標的語言（不拋例外、檔名相符、條目數 >= N）
- 缺陷被發現時，回顧發現**該檢查當時是綠的**，而且再跑一次還是綠的
- 修正缺陷之後，若不動檢查器，同一形態的下一個缺陷仍會通過

本模式有兩種來源，防護方向不同，須分開處理。

### 來源一：工具的宣稱與量測不符

工具本身宣稱在驗 P（名稱、訊息、`--help` 描述都這樣說），實際量的是 Q。使用者沒有理由懷疑——**橋是工具搭的**。

**單一 session 內的實例**（2026-09-08，同一天由不同活動各自撞上）：

| 檢查 | 宣稱保證（P） | 實際量測（Q） | 縫 |
|------|-------------|-------------|-----|
| 派發前檢查的路徑項 | where.files 指向本票要改的檔案 | 該路徑在檔案系統存在 | 路徑真實存在但與本票無關（寫成 `x_dispatch.py` 而目標在 `x_dispatch_validate.py`），通過只證明不是手誤 |
| 派發前檢查的驗收項 | 本票有可驗收的目標 | acceptance 條目數 >= 門檻 | 未填樣板恰好滿足門檻且句型完整，恆通過（詳見 `PC-GPD-008`） |
| 提交前的範圍核對 | 這次 commit 只含目標檔 | `git diff --cached` 的檔名清單相符 | 檔名對而 index entry 相對新 HEAD 已過期，裸 commit 靜默回滾他人內容 |
| 元件測試的溢位斷言 | 內容沒有超出容器 | 上一次 pump 沒有拋例外 | 固定高度容器對超出的文字是靜默裁切、不拋例外，字形被切而測試全綠 |
| 整套測試綠燈 | 功能在真實環境可用 | 以替身執行的斷言全部通過 | 替身恆可用，掛在服務成功路徑上的回饋因此恆存在（詳見 `ARCH-GPD-001`） |
| worktree 清理守衛的遺失警告 | 強制移除會遺失修改內容 | git status 首欄為 `D` | `D` 是刪除不是修改，且磁碟內容與已合併的主線完全相同，警告的損害不存在 |
| CLI 參數說明 | 這個參數怎麼用 | 這個參數是什麼 | 兩個外觀同構的參數，一個吃逗號分隔一個不吃，說明文字給不出區分依據 |

載體完全不同——票務驗證器、git 工具、測試斷言輔助、整個測試套件、清理守衛、命令列說明——形狀相同。

### 來源二：使用者臨時發明的代理指標

工具從未宣稱它回傳 P，是使用者當下把它當成 P 用。**橋是使用者自己搭的**，沒有人誤導。

**實例**（同日）：以 `ls -t | head -1` 當作「我剛建立的那張票」的識別。並行環境中三個 session 同時在動 ticket 檔案，`ls -t` 量的是最近被修改（Q），不是我剛建立（P）。結果是把一組 acceptance 寫進了另一張票——**而該操作成功執行，因為那張票真實存在**。

**這一類比壞掉的工具更難防**：壞掉的檢查器修一次就不再壞；臨時發明的代理指標每次發明的都不一樣（這次是 `ls -t`，下次可能是序號遞推、或「剛才那個 commit 的檔案清單」），形態不同但都會失敗。防護不能列黑名單，只能禁行為——**用建立動作本身的回傳值，不用代理指標去找剛建立的東西**（該次 `ticket create` 有報 ID，未讀）。

**變體：以「帶著實查數字」為「結論已驗證」的代理指標**（同日，兩個 session 互相示範）。

一則同儕回報寫「index 與來源分支差 18 檔，所以有人解過衝突」。前半是實測值，後半是推論且錯誤——乾淨的自動合併本來就同時含兩邊變更，該數字不區分「自動合併」與「人工解決」。接收方（PM）採信了整句，未自行查證是否真有衝突（正確判準是 `CONFLICT` 輸出或 `git ls-files -u` 的 unmerged 條目）。

此處的代理指標是接收方發明的：**Q = 這段陳述帶著實查數字；P = 這個結論已被驗證**。發訊方沒有宣稱後半已驗證，是數字的存在讓整句讀起來像驗證過的。

**最難拆開的形態是已驗證前提與未驗證推論寫在同一句**（發訊方事後自陳）。分兩句寫、或依既有的三類標註（已驗證／推測／未知）分別標記，接收方才有機會只採信前半。

**截斷方向的推廣**（同日）：先前記錄的截斷失誤（以 `head -8` 讀 staged 清單並把截斷後的數量當總數）另有一層——被切掉的兩項是新增檔（`A`），而新增檔正是合併被撤銷後唯一不可從 HEAD 復原的類別。`git diff --cached` 的排序讓新增檔落在後段，`head` 因此系統性地切掉風險最高的那些。

由此收窄判準：**不是「該用 `head` 還是 `tail`」，而是「這個輸出的排序，與我要找的東西的分佈有沒有相關性」**。相關即不可截斷——全取，或改變查詢使分類不再依賴位置（例如 `--name-status` 直接給出狀態碼，不必從順序推斷）。既有規則的例子是警告行在頭（`tail` 會切掉），本例是高風險項在尾（`head` 會切掉），兩個方向都成立。

### 脫鉤是結構性的，不是機率性的

代理指標的問題不在於「用了代理」——代理本身無可避免，真正的性質往往量不起。問題在於**沒有先問這個代理在什麼情況下會與被代理者脫鉤**，而答案經常是「在某一整類輸入上，依設計必然脫鉤」。

| 代理（Q） | 想問的性質（P） | 脫鉤的結構性保證 |
|-----------|----------------|-----------------|
| commit 的 subject 是否出現在 main 的 log | 該 commit 的內容是否已在 main | stash commit 的 subject（`WIP on ...` / `index on ...`）**依設計永不進入 log**；CAS 重試產生的重複 subject 亦然 |
| `--dry-run` 能否推進到欄位驗證 | 鎖是否已釋放 | 該命令**有鎖無鎖皆會推進**——鎖從未被檢查 |
| `ls -t \| head -1` | 我剛建立的那張票 | 並行環境中任何一方的寫入都會改變排序 |
| `rg -c '^#### 4\.'` 的計數 | 該章節的條目數 | 通用約定（`4.0.x`）與條目共用同一個前綴 |

四例的共同點：**脫鉤不是偶發，是對某類輸入的必然**。因此「這次剛好對」不構成證據——換一批輸入它會穩定地錯。

判斷代理是否可用的問題不是「它準不準」，而是「**有沒有一整類東西會讓它必然錯，那類東西在我的輸入裡嗎**」。前者要靠統計，後者只需讀懂代理與性質的定義，成本低得多。

### 兩類共同的危險特徵

**它回傳一個合法值而非錯誤。** 上述所有實例中，整條執行路徑沒有任何一步報錯：`ls -t` 給出真實存在的票號、`set-acceptance` 對該票執行成功、清理守衛的警告內容格式正確。錯誤只在有人閱讀內容時才顯形，而閱讀者往往不是操作者。

## 根因

代理指標之所以被選中，正是因為它**容易量**：檔案存在性是一次 stat，條目數是一次 len，例外有無是一次 takeException。真正的性質（相關、已填、新鮮、沒被裁切、真實邊界可用）都需要更多脈絡或更貴的手段。

寫檢查的人知道自己在量 Q，但檢查一旦被命名為 P，**名稱就成了讀者的認知**。此後每個讀者看到綠燈，得到的是「P 成立」的印象，而不是「Q 成立」。這個落差沒有任何機制會提醒——綠燈的外觀不因為量的是代理指標而有所不同。

由此推出這類缺口最難處理的性質：**同一個驗證器跑第二次永遠揭露不了**。它會再次正確地量 Q，再次通過。發現缺陷的唯一途徑是**換軸重查**——用另一個維度的觀測去撞它。上表實例中，沒有一個是被原檢查器發現的：多數由人工覆核撞到，其餘由實機目視或另一個 session 的獨立查證揭露。

**為何殘留下來的多是這一類**（並行 session 於同日提出）：能被**字面偵測**的缺陷多半已經有 hook 擋了。而「acceptance 是未填樣板」「where.files 指錯檔案」「這個路徑跟本票相關嗎」都需要**語意判斷**，寫不成字面規則。

所以這批缺陷集中在語意判斷區間不是巧合，**是既有防護體系篩選之後的殘留分佈**：字面層大致已被清空，剩下的多是需要判斷的那些。這也解釋了為何它們幾乎只能由人（或另一個帶著不同脈絡的 session）發現——目前沒有機械手段能站在那個位置。

### 修正：字面層未必已清空，守衛可能只實作規則的一個子集

上段原以「規則 8 的專案識別符違反有固定格式，一寫進去就被攔」作為字面層已清空的例證。**該例證本身不成立**，且推翻它的實例就出在規則 8 上：

`reference-stability-rule8-guard-hook.py` 的掃描迴圈只迭代兩個 ticket ID 樣式。而規則 8 的條文禁止的是「ticket ID、worklog 路徑等專案層級識別符」，並指名失效形態為 sync 到其他專案後成為死連結。**專案文件路徑同樣有固定格式、同樣命中該失效形態、同樣寫得成字面規則——守衛就是沒實作它。**

一次框架方法論的編輯中，同一份檔案同時寫入了兩類違規：changelog 段落的 ticket ID，以及三處指向某份專案規格文件的路徑。守衛攔下前者，執行者依提示改寫後通過，並在完成回報中將此事記為「框架層小插曲，無需處理」。後者三處全數放行，而該方法論新增條款的整個前提就掛在那個引用上。

**守衛的部分覆蓋不只是沒攔到，它主動製造了合規的外觀。** 沉默與命中對讀者的可解讀性不對稱：

| 守衛狀態 | 讀者的合理推論 | 是否仍會自查 |
|---------|--------------|------------|
| 沉默 | 未檢查，或檢查了沒事 | 可能會 |
| 命中並被滿足 | 已檢查，且問題已解決 | 幾乎不會 |

因此**部分覆蓋而會命中的守衛，對它未覆蓋的那一類比不存在的守衛更不利**——守衛不存在時，該規則在讀者心中仍是待辦；守衛命中並被滿足時，該規則已結案。本例中執行者與驗收者雙方同時結案，無人再查。

**與本文主軸的關係**：這是「量錯軸」的變體——軸沒錯，但只量了該軸的一段，而**量到的那一段有沒有涵蓋全部，檢查本身不會說**。它同時是〈解決方案 4〉邊界宣告義務的反面實例：換軸或建檢查時未宣告涵蓋邊界，檢查一旦命中，未涵蓋的部分就被它的命中所掩蓋。

**Action**：判斷一個守衛的保護範圍時，讀它的**偵測樣式**，不讀它的**名稱**，也不從「它剛才攔過東西」推論它涵蓋整條規則。守衛名稱取自規則，偵測樣式取自實作，兩者的落差沒有任何機制會提醒。

## 解決方案

1. **檢查的名稱與訊息說出量的是什麼，不說宣稱保證什麼**。「where.files 路徑全數存在」比「路徑正確」誠實；讀者看到前者會自己補問「存在但相關嗎」，看到後者不會。
2. **為每個檢查寫下 Q 與 P 的差距**，放在檢查的實作註解或文件裡。寫不出差距有兩種可能：Q 確實等於 P（少見），或作者沒想過（常見）。這個問題本身就有診斷價值。
3. **確定性判準該硬、啟發式判準該軟**。Q 與 P 有大縫的檢查不該硬擋（誤報成本高），但也不該讓它的綠燈被當成 P 的保證——分級本身要與縫的寬度對應。
4. **換軸重查是唯一有效的複驗**。同一檢查跑第二次不產生新資訊。複驗要問「有什麼是這個檢查結構上看不到的」，再用另一個維度去看。

   **換軸之後必須宣告新軸的涵蓋邊界，否則只是換個地方過度宣稱。** 換軸解決的是「這個檢查在答另一個問題」，**沒有**自動解決「這個檢查答得多完整」——兩者是獨立的缺口，修了前者不代表後者不存在。

   實例（2026-09-09）：一次「有無工作遺失」的檢查，原判準為 unreachable commit 的 subject 是否出現在 main 的 log（錯軸——stash commit 的 subject 依設計永不出現，見下節結構性脫鉤）。換軸為「該 commit 觸及的檔案路徑是否存在於 HEAD」後結果為零，但同時宣告了邊界：**只證明沒有整檔遺失，不證明沒有檔案內的內容遺失**——後者需逐檔比對 blob，而 ticket body 多為累加式、後續 commit 本就涵蓋前次內容，兩者在這根軸上分不開。

   同日另有四次換軸修正未附邊界宣告，形態一致：拿到新結果就直接宣告結論。**沒有邊界的新軸，與有名稱沒有量測說明的舊檢查是同一個問題**——讀者依然得到「P 成立」的印象。
5. **縫太寬時補檢查，而不是補提醒**。文件寫「請注意路徑要相關」不會被讀到；把相關性納入檢查（例如比對路徑與 ticket 標題或 how.strategy 的關鍵字）才會生效。
6. **來源二專屬：不用代理指標定位剛建立的東西**。用建立動作本身的回傳值（`create` 回報的 ID、寫入函式回傳的路徑），不用「最近修改的那個」「序號加一」「剛才那批檔案」這類當下推導出來的識別。此條無法以檢查器落實——代理指標是使用者臨場發明的，工具不知道它被發明了；只能作為行為禁令。

## 預防措施

| 時機 | 動作 |
|------|------|
| 設計任何檢查、斷言或守衛時 | 明寫「本檢查量的是 Q」與「Q 與宣稱性質 P 的差距」；差距寫不出來時，先確認是真的沒有還是沒想過 |
| 為檢查命名或撰寫訊息時 | 用量測的語言，不用性質的語言 |
| 檢查通過但仍懷疑時 | 不要重跑同一檢查——問「這個檢查結構上看不到什麼」，換軸觀測 |
| 換軸重查得到新結果時 | 宣告新軸的涵蓋邊界再下結論；換軸修的是「答錯問題」，不自動修「答得不完整」（解決方案 4） |
| 決定採用某個代理指標時 | 問「有沒有一整類輸入會讓它必然錯，那類輸入在我的資料裡嗎」——脫鉤多為結構性而非機率性，讀定義即可判定，不需統計 |
| 缺陷修復後 | 追問「原檢查為何沒攔到」；答案是「軸不同」時，缺陷修完仍要處理檢查 |
| 新增檢查以攔某個既有缺陷時 | 驗證新檢查在修復前會失敗——沒有先看它變紅，就不知道它抓不抓得到 |
| 需要指涉「剛剛建立的那個東西」時 | 用建立動作的回傳值，不用「最近修改的」「序號加一」這類臨場推導的識別（來源二） |
| 對某個工具輸出下結論前 | 問「這個管道承載我要的訊號嗎」。輸出缺席只在管道確實承載該訊號時才構成證據 |
| 例外 | 代理指標與性質確實等價的情形（如雜湊比對、二元存在性判定）；此時仍應寫明等價的理由，不預設讀者看得出來 |

## 行為模式分析

綠燈的心理作用是「這件事已經確認過了」，而確認過的事不會被再問一次。檢查器因此不只沒有攔到缺陷——**它主動降低了缺陷被人工發現的機率**，因為它佔據了「這裡已經有人看過」的位置。

這也解釋了為何五個實例都是在做別的事情時撞到的：沒有人是為了驗證那些性質而去看的，是為了別的目的碰巧從另一個軸經過。

最後一個實例（整套測試綠燈 vs 真實環境可用）把這個性質推到極端：一整套測試都是同一個軸上的觀測，數量再多也不會跨出那個軸。

## 與 `PC-GPD-015` 是同一骨架的兩個載體

兩則的骨架逐字對應：

> **手段本身無瑕疵、其產出為真，但它回答的是另一個問題；而覆核動作只驗手段的真實性，因此必然通過。**

**不合併的理由是防護動作不同**——合併會把兩條可操作的檢查退化成一條抽象原則，而抽象原則在當下不會觸發任何動作：

| | 載體 | 產出的東西 | 該問的那一句 | 何時問 |
|---|---|---|---|---|
| 本則 | 量測／檢查 | 一個關於某性質的判定（通過／不通過） | **通過這個量測是否蘊含它宣稱保證的性質？** | 設計檢查器時，或準備採信一個綠燈時 |
| `PC-GPD-015` | 權威依據 | 一個有依據支撐的決定 | **這條依據回答的是什麼問題，和這裡要決定的是不是同一個？** | 撰寫或覆核一個附了依據的判斷時 |

**最接近的一對是本則來源二（使用者臨時發明的代理指標）與 `PC-GPD-015` 的層級變體**——兩者都是讀者自己搭的橋，沒有人誤導。判別依據是替身的形態：本則來源二的替身是**一個量測動作**（例如以最近修改時間找「我剛建立的那張票」），該則層級變體的替身是**一個既有事實被當作另一層的證據**（例如以定義檔存在證明該型別可派發）。

**遇到第三種載體時掛在這個骨架下，不必另立新則**。判斷是否屬本骨架的問題只有一個，**但它有一個必須寫出來的前提**：

> **前提：已判定此處存在缺陷。** 在此前提下——覆核者若去查證這個手段本身，會不會得到「屬實」？會，就是本骨架。

**前提不可省略。** 沒有它，這一問會吞掉全部正確的工作：一個完全正確的量測——量的正是待答問題的那個軸——查證起來同樣「屬實」，照字面也會被判為本骨架。這一問回答的是「**給定已有缺陷，歸哪一則**」，不是「什麼算本骨架」；手段為假歸一般錯誤，手段為真才歸此處。
