# PC-LLM-005: 等待迴圈以代理訊號判斷資源佔用，孤兒行程使條件恆真，迴圈與「真的有人佔用」不可區分

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 分類 | process-compliance（等待條件的訊號選擇） |
| 來源版本 | 3.1.0 |
| 首次觀測 | 2026-11-10 |

## 症狀

一條執行線要在其他合併閘門結束後才送出自己的合併，寫了背景等待迴圈，條件是 `pgrep -f "\.claude/worktrees/merge-gate-"` 無命中。之後三個閘門依序跑完，迴圈仍未結束，該線約一小時沒有送出合併，也沒有回報。

查證：命中的是三個 flutter_tester 行程，PPID 1、存活約 18 小時，命令列帶著另一個專案某次閘門快照的路徑；那個快照目錄早已移除。行程本身 CPU 0%，不佔用任何閘門名額。

## 根因

**等待條件用的是代理訊號，不是資源的權威狀態**。「有沒有行程的命令列含快照路徑」只在閘門正常收尾時與「閘門正在佔用名額」同義；孤兒行程讓代理訊號恆為真，而權威狀態（名額鎖是否被持有）早已釋放。兩者在正常情況下一致，所以寫條件時看不出差別。

**觸發等待的指示本身多餘**。協調方要求執行線「送出合併前先確認沒有其他閘門在跑」，但合併命令本身會先取得名額、有人佔用時自動排隊。執行線為了遵守一個工具已內建處理的檢查，自行寫了等待迴圈，把工具的權威判斷換成自製的代理判斷。

為何不易察覺：迴圈卡住與「閘門真的一直有人在跑」在輸出上同形，都是條件持續成立；等待方不會主動回報，協調方從外部只看到該線久無動靜。

## 解決方案

- 停掉等待迴圈，直接送出合併命令，由它自己排隊取得名額。
- 孤兒行程交由所屬專案處理；本例由該專案主控確認後終止。

## 預防措施

- 協調方要求各線先做某項檢查前，先確認工具是否已內建同樣的保護（排隊、鎖、重試）；已內建就不要求，避免各線各自寫代理判斷。
- 必須自行等待時，條件取資源的權威狀態（鎖檔是否被持有、工具提供的查詢命令），不以行程名稱或命令列字串比對代替。
- 等待迴圈一律設上限時間，逾時回報當下命中的對象（pid、PPID、存活時間），讓「條件恆真」能被看見。
- 以行程比對時排除 PPID 為 1 且存活時間遠超預期的對象，或先列出命中對象再決定是否等待。
