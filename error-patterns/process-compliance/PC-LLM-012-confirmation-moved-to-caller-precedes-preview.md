# PC-LLM-012: 確認點從被呼叫端搬到呼叫端時，確認與預覽的先後被對調

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 3.4.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-11-11 |

## 症狀

- 原本由腳本（被呼叫端）在破壞性操作前「先印預覽、再詢問 y/N」，改由呼叫端（command、上層流程、UI）承擔確認後，呼叫端在執行腳本之前就詢問用戶
- 用戶按下同意時，畫面上還沒有預覽內容；預覽要等呼叫端帶著「已確認」旗標執行腳本後才印出，那時操作已經在進行
- 測試與外觀都正常：確認對話框存在、旗標有傳、預覽也有印，只是順序錯了，沒有任何訊號指出用戶在不知情下同意

## 根因分析

### 行為模式

搬移確認點時，搬的是「詢問」這個動作，沒有一起搬「詢問前用戶已經看到的資訊」。在被呼叫端內，預覽與詢問位於同一段程式碼，先後由程式順序保證；搬到呼叫端後，預覽仍留在被呼叫端，而呼叫端只會在詢問之後才呼叫被呼叫端。原本由程式順序隱含提供的「先看再答」保證，在搬移中消失。

### 具體案例：sync-pull 全量 overlay 確認

| 階段 | 流程 | 用戶同意時看得到清單嗎 |
|------|------|--------------------|
| 搬移前 | 腳本計算將覆蓋／將刪除清單 → 印出清單 → 終端機 y/N 詢問 → 同意後套用 | 看得到 |
| 搬移後（缺陷） | 為修非互動環境讀到 EOF 的問題，把 y/N 改由 command 的 AskUserQuestion 承擔：command 先詢問 → 同意後帶 `--confirm-overlay` 執行腳本 → 腳本此時才印清單並直接套用 | 看不到 |
| 修正後 | command 先不帶旗標執行腳本，腳本印出清單後以專屬結束碼中止、不改動檔案 → command 把清單放進 AskUserQuestion → 同意後帶旗標重跑 | 看得到 |

修正後的兩段式另帶來新的落差：重跑時重新取得上游，上游在兩次執行之間有新提交時，套用的內容會多於用戶確認的清單；後續以「確認時印出的上游 commit 必須與套用時相符」綁定才收斂。這說明預覽與套用分成兩次執行時，還要保證兩次看到的是同一份輸入。

### 結構性原因

1. 確認語意由「預覽 → 詢問 → 執行」三者的順序構成，但程式碼只把「詢問」視為確認點，搬移時只搬了詢問
2. 搬移的動機通常是另一個問題（非互動環境、UI 一致性），審查焦點在新動機是否解決，不在確認語意是否保留
3. 測試多半斷言「有確認」「旗標有生效」，很少斷言「詢問發生時預覽已經可見」

## 解決方案

### 事後處理

改為兩段式：被呼叫端在未帶確認旗標時只產出預覽並以專屬結束碼中止（不做任何改動）；呼叫端取得預覽後再詢問，同意後帶旗標重跑。重跑會重新取得輸入時，以預覽時的輸入識別（如上游 commit）綁定確認，不符即中止並重新預覽。

### 預防措施

| 措施 | 說明 |
|------|------|
| **搬移前列出確認前可見資訊** | 搬移確認點前，先列出搬移前用戶在回答前看得到的所有資訊（預覽清單、數量、目標），搬移後逐項核對仍在回答前可見 |
| **預覽與確認綁定同一份輸入** | 預覽與套用分成兩次執行時，以輸入識別綁定確認，不讓套用的範圍超過用戶看過的範圍 |
| **測試斷言順序** | 測試除了斷言確認存在，還要斷言詢問時預覽已輸出、未確認時不做任何改動 |
| **確認點以專屬結束碼交接** | 被呼叫端以專屬結束碼表達「需要確認、預覽已印出」，呼叫端只依結束碼分流，不比對輸出文字 |
