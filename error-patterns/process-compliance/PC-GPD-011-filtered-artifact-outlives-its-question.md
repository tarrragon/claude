# PC-GPD-011: 過濾產物活得比它的問題久——子集被拿去回答另一個問題

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-GPD-011 |
| 類別 | process-compliance |
| 風險等級 | 高 |
| 發現日期 | 2026-09-08 |
| 來源版本 | 0.1.0 |

## 症狀

為回答問題 A 而施加的過濾（`grep` 白名單、`head`／`tail` 截斷、人工壓縮引用），其輸出後來被拿去回答問題 B。對 A 而言那份輸出完整，對 B 而言它是子集——而**子集與全量在外觀上沒有差別**，沒有任何跡象顯示少了東西。

**識別特徵**：

- 過濾當下的意圖與過濾條件完全貼合，事後檢視也找不到「粗心」（這是與單純誤用工具的分界）
- 輸出被引用時，引用者（可能是自己稍後、也可能是別人）不知道它是子集
- 據該輸出所下的結論指向「原文與我看到的不同」「對方改過內容」「範圍就是這麼大」這類**關於全量的斷言**
- 補讀全量後，原結論的方向整個翻轉，而非只是補充細節

## 根因

過濾條件繼承的是**搜尋動機**，不是後續判斷所需的完整性。兩者在施加當下重合，之後才分岔。

`.claude/rules/core/bash-tool-usage-rules.md` 規則二治的是**如何過濾**（截斷方向、白名單須含 `WARNING\|Error\|Traceback`）。本模式的失效不在過濾動作本身——三個實例的過濾器都忠實服務了當下的意圖——而在**過濾產物的生命週期**：產物比它的問題活得久，被搬到新脈絡後仍以全量的身分被閱讀。

因此讀過規則二不足以防止本模式。規則二問「這次過濾會不會濾掉警告」，本模式要問的是另一個問題（見預防措施）。

## 實例（同一日三次，三個不同過濾手段、三個不同執行者）

| 執行者 | 過濾手段 | 意圖（當下正確） | 濾掉了什麼 | 產物被拿去回答的另一個問題 |
|--------|---------|-----------------|-----------|------------------------|
| session A | `git diff --cached --name-only \| head -8` | 看有哪些檔案 | 後段兩個新增檔（`A` 狀態） | 「abort 的損失有多大」——而新增檔正是 abort 後唯一不可從 HEAD 復原的類別 |
| session B | 表格壓縮：每個路徑分類只取一種 isolation 狀態 | 回答「這張票不加 isolation 會不會被擋」 | 二維表的其中一維（「有 worktree 時放行」兩列） | 貼進 issue 給不知道它是壓縮版的讀者 |
| session C | `grep "僅主 repo\|豁免\|放行"` 白名單 | 找豁免條件 | 三個「阻擋」列，其中一列是唯一與 isolation 狀態無關的 | 「比對他方轉述是否忠於原文」——據子集公開指控一份逐字照抄的引用為竄改 |
| session D | `git log --oneline -3 -- <spec>` | 回覆同儕「這個檔最近怎麼動的」 | 後續四筆提交（實為 7 筆） | 「同儕宣稱的『被 232／240／243 三票各改過一次』對不對」——截斷點恰好等於對方的宣稱數，子集因此讀起來像獨立佐證 |

第三例的代價最高：錯誤查證加上公開發布，替一個逐字照抄的人留下 misquote 記錄。

四例的共通結構：**沒有一次是粗心**。過濾器都貼合當下意圖，損害在跨脈絡使用時才發生。

### 第四例的新增機制：截斷點與他方宣稱吻合時，子集升級為偽佐證

前三例的失效是「子集被讀成全量」。第四例多一層：對方先宣稱「三票各改過一次」，發話方隨後貼出 `-3` 的輸出，內容恰好就是那三票——**於是一份對該宣稱零資訊的輸出，讀起來像是對它的獨立查證**。

兩件事使它比單純的子集誤讀更難察覺：

1. **吻合是自己造成的**。`-3` 是發話方自己設的顯示上限，不是世界的邊界；它之所以「印證」對方的三，只因為兩個三碰巧同數。任何 `-N` 都會產出一份看似支持「恰好 N 筆」的輸出。
2. **發話方握有可反駁的第一手事實仍看不見**。第四例中發話方當天親手提交過該檔兩次（在被截掉的四筆裡），本可立刻知道不只三筆——**自己的截斷同時對自己生效**，第一手記憶因此沒有被喚起。

補一條衍生規則（併入下節三條）：**回應他方的數量宣稱時，禁用任何 `-N` / `head` / `tail` 限制，改取全量或直接輸出計數**（`| wc -l`）。計數是固定值，無法因截斷而恰好吻合；帶上限的列表則對「總數是不是 N」永遠沒有鑑別力。

## 預防措施

施加過濾時多問一問，答案決定產物的處置：

> **這份過濾後的輸出，會不會被我或別人拿去回答不是當初那個問題的問題？**

| 答案 | 處置 |
|------|------|
| 不會（用完即棄） | 照常過濾，無額外要求 |
| 會，且讀者是自己 | 在同一則記錄中標記「此為子集，過濾條件為 X」 |
| 會，且讀者是他人或未來 session（issue、交接文件、票面、跨 session 訊息） | **放全量原文**，不放任何一方的壓縮版——讀者會拿它回答什麼問題，寫的人事先不知道 |

三條具體衍生規則：

1. **拿過濾輸出當「比對基準」前先重取全量。** 比對是關於全量的斷言，子集無資格作為基準。判別訊號：你的結論句含「原文是」「對方改了」「範圍就是」。
2. **二維以上的表格禁止壓縮引用。** 折疊掉一維後外觀仍是形狀完整的一張表，沒有跡象顯示少了一維（本模式與 `PC-GPD-009` 在此交會：形狀通過不等於內容完整）。
3. **公開發布前重取一次。** 發布是產物脫離原脈絡的時刻，也是最後一個可低成本補救的點。
4. **回應他方的數量宣稱時禁用 `-N` / `head` / `tail`。** 改取全量或直接輸出計數（`| wc -l`）。理由見第四例：任何顯示上限都會產出一份看似支持「恰好 N 筆」的輸出，對「總數是不是 N」零鑑別力；整數計數是固定值，不會因截斷而恰好吻合。

## 載體決定（已評估，勿重複評估）

**不上移至 `rules/core/`。** 衍生規則 2（二維以上表格禁止壓縮引用）讀起來像 rule 而非 pattern，曾被考慮提為自動載入層條文，結論為否：`rules/core/` 每回合注入 PM 與全部代理人，而該層現況已超出預算（實測 auto-load 集合約 55.9k tokens，上限 45k），只能減不能加。本模式屬情境性內容，按需讀取層是正確位置（依 `.claude/rules/README.md`「自動載入預算原則」）。

**不另開 canonical issue。** canonical issue 的功能是追蹤需要跨 consumer 協調的修復——有東西要修、各專案落地時機不同、需要看到誰修到哪。本模式沒有東西要修，只有東西要知道，且 `.claude/error-patterns/` 本就隨 sync 擴散到所有 consumer。開了會停在 open 且無終止條件（「大家都不再踩這個坑」不可驗收），退化為第二個 error-pattern 索引。
