# PC-GPD-047: 收尾票的 blockedBy 在建票時列齊當時的兄弟票，之後追加的兄弟票沒有同步加入，收尾票可能在前置未完成時被派出

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-10-28 |

## 症狀

父票拆出一組遷移子票，以及一張「收尾」子票（移除過渡路徑、改名、刪舊 API 等），收尾票的 blockedBy 列出其他所有遷移子票。執行中範圍擴大，又追加了幾張遷移或分析子票。其中一部分被補進收尾票的 blockedBy，另一部分沒有。

票系統依 blockedBy 判斷收尾票是否可以開工，漏列的兄弟票未完成時，收尾票照樣顯示為可派發。若被派出，收尾動作會在仍有呼叫端未遷移時執行，結果是編譯失敗，或殘留的舊用法被靜默移除。

實證（2026-10-28，文字元件行數政策）：收尾票 blockedBy 列了 11 張遷移子票，範圍擴大後追加的 4 張中，只有 2 張被補進。漏掉的一張負責的檔案還有 7 處舊建構子呼叫，另一張是決定新 API 變體範圍的分析。用戶要求確認收尾票狀態時，比對 main 上的殘留分布才發現。

## 根因

**追加子票與更新收尾票是兩個獨立動作**。`ticket create --parent` 只建立父子關係，不會更新兄弟收尾票的 blockedBy；補不補靠建票者記得。

**收尾票的前提是「集合已清空」，blockedBy 只是集合的快照**。真正的前提是「舊用法在主線的出現次數為 0」，blockedBy 只是建票當下對這個集合的列舉，集合擴大時快照不會自己更新。

## 解決方案

- 發現漏列時，以追加模式補齊 blockedBy（`set-blocked-by --add`）。
- 以固定值核對：在主線 grep 舊用法的出現處，每一處都要對應到 blockedBy 中某張未完成的票，或收尾票自己的 where.files。

## 預防措施

- 對已有收尾子票的父票追加子票時，同一步驟判斷新票是否為收尾的前置；是的話立即補進收尾票的 blockedBy。
- 收尾票的 acceptance 加一條固定值前提：開工前在主線 grep 舊用法，出現處只能落在本票的 where.files。不靠 blockedBy 列舉是否完整。
- 協調者排佇列時，把收尾票的 blockedBy 與父票目前的 children 清單逐一比對。

## 關聯 Ticket
