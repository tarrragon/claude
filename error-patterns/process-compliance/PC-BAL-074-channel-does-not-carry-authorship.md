# PC-BAL-074: 以內容經由哪條通道抵達推斷誰是作者——通道不承載作者身分

## 基本資訊

| 欄位 | 值 |
|------|-----|
| 類別 | process-compliance |
| 風險等級 | medium |
| 來源版本 | 0.2.1 |
| 發現情境 | 多個專案經共用 repo 同步框架資產，一日之內三次把內容的作者歸給送達它的那條通道所連的另一方 |

## 症狀

- 「這批東西在我拉取後才出現在我的樹裡，所以是對方的」——實際是自己專案早先的產出，只是隨同一次同步一起回來。
- 「這個 commit 從共用庫來，所以是共用庫上一個推送者的」——實際推送者只是中轉，內容出自第三方。
- 歸屬判斷的後果不對稱：把自己的東西當別人的，會不敢動它、把該做的處置往外推；把別人的東西當自己的，會在版本紀錄裡冒領。

## 根因

**推論用的是路徑，不是來源**。「經由哪條通道抵達我手上」與「誰寫的」是兩個獨立的事實，同步機制把兩者在觀察上耦合起來——內容出現的時點與同步動作重合，於是同步的對端被當成作者。

**沒有付查證成本**。判定作者只需一次 `git log --diff-filter=A -- <path>` 找首次加入的 commit，成本是一次命令；而通道推斷零成本且大多數時候恰好正確，於是預設路徑永遠是後者。共用資產的同步越頻繁，「大多數時候正確」越容易維持，錯的那幾次也越不容易被察覺。

**同步後的樹是三方內容的疊加**。本地樹在一次拉取後同時含有：自己早先推上去又回來的、對端新增的、第三方經對端中轉的。三者在檔案系統上完全同形，時間戳全部是拉取當下。

## 解決方案

1. **歸屬一律查首次加入的 commit**，不看內容出現在自己樹裡的時間，也不看它隨誰的推送抵達：

   ```bash
   git log --diff-filter=A --format='%h %ad %s' --date=short -- <path>
   ```

   共用 repo 上找不到時，回各自的專案 repo 查同一條命令。

2. **版本紀錄據實標注來源**。取回他方產出時寫明「由另一個 consumer 撰寫並經共用庫傳入」；不確定作者時寫「來源待查」，不寫成自己的。
3. **對端說「那是你的」不構成證據**。對端的判斷同樣可能來自通道推斷；雙方各查一次首次加入的 commit，比互相指認可靠。

## 預防措施

- 共用資產的同步報告若列出「新增／變更」，把它讀成「相對於我上次同步的差異」，不要讀成「對端的產出」。
- 涉及歸屬的敘述（版本紀錄、issue、跨 session 訊息）在寫下之前先跑一次查證命令；歸屬錯誤一旦寫進版本紀錄就會被下游沿用。
- 同一日內第二次發生同型誤判時，處置對象是「歸屬判定有沒有固定的查證步驟」，不是再提醒一次要小心。

## 關聯

- 同型家族：以載體推斷內容屬性的其他形式——以檔案所在目錄推斷擁有者、以 commit 作者欄推斷實際撰寫者（多 session 共用同一 git identity 時該欄無鑑別力）。
- 上游原則：記錄平面與世界平面的區分——「我記得這是誰做的」屬記錄平面，git 首次加入的 commit 屬世界平面。
