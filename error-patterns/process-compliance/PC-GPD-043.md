# PC-GPD-043：不變性驗收條件派進 worktree，派發前未備妥基準

## 基本資訊

- **Pattern ID**: PC-GPD-043
- **分類**: 流程合規（process-compliance）
- **來源版本**: v0.5.0
- **發現日期**: 2026-10-28
- **風險等級**: 中（不會造成錯誤合併，但會讓驗收條件停在未勾，回到派發者手上補做；補做若被省略，不變性就只剩推論）
- **影響範圍**: 驗收條件要求「某輸出與改動前逐字／逐位元相同」（sha256、快照、golden file、產物檔），且派發位置是 worktree 或其他隔離環境

## 摘要

**驗收條件要求「改動後的輸出與改動前相同」時，比對需要一份改動前的基準。派發前若沒有把基準值寫進票面，worktree 內的執行者通常拿不到它：改動前的產物不在 worktree 裡，而還原舊檔重跑會被寫入守衛擋下。** 結果是執行者只能憑機制推論「應該沒變」，把該條驗收留給派發者事後補做。

## 症狀

- 執行者回報其他驗收條件全數達成，唯獨不變性條件未勾，理由是「無法取得改動前的基準」
- 執行者附上改動後的值（例如 sha256），並說明只能推論路徑或內容沒變
- 執行者曾嘗試還原舊檔取基準，被寫入邊界守衛擋下
- 主 checkout 的產物目錄沒有對應基準（產物不入庫，或只留有部分變體）

## 根因

1. **基準是改動前的世界狀態，worktree 只有改動後的工作面。** 產物目錄通常被 ignore，worktree 從乾淨的 commit 建立，不會帶入主 checkout 先前跑出的產物。
2. **在 worktree 內重建基準需要暫時回退產品檔。** 這屬於寫入產品路徑的操作，守衛會擋；即使不擋，回退再還原也容易把舊內容誤留進提交。
3. **派發者把不變性條件當成和其他條件同一類。** 其他條件只需要改動後的狀態就能驗，不變性條件多一個「改動前」的輸入，但票面與派發 prompt 都沒有提供這個輸入。

## 解決方案

**事後補救（本案做法）**：派發者在主 checkout 用改動前的版本跑同一個產生命令（主 checkout 在合併前就是改動前的狀態），取得基準值後與執行者回報的值逐字比對，把兩組值與比對結果寫進票面的 Test Results，再勾選該條件。

## 預防措施

| 時機 | 動作 |
|------|------|
| 建票時 | 驗收條件寫成「與基準值 X 相同」，X 直接寫進票面；寫不出 X 時，在條件裡指名基準由誰、在哪裡取得 |
| 派發前 | 若基準尚未取得，派發者先在主 checkout 跑一次並把值寫入票面，再派發 |
| 派發 prompt | 指向票面的基準值，不要求執行者自行還原舊版 |

**判別問題**：這條驗收條件只看改動後的狀態就能驗嗎？答案為否時，改動前的那一半輸入必須在派發前備妥。

## 與相近模式的分界

- **PC-BAL-022**：談隔離環境內的失敗歸因缺少 baseline 對照，對象是「紅燈是不是新的」。本模式談的是驗收條件本身需要改動前的值，對象是「綠燈的證據從哪裡來」。
- **PC-154**：談 worktree 派發的起步前置條件（base 是否含檔案、票是否已認領）。本模式的前置是驗收所需的資料，不影響執行者起步。
