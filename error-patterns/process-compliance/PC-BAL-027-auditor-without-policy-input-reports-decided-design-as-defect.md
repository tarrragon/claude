# PC-BAL-027: 稽核器未讀既有決策登記表，把已裁定的刻意設計持續報為缺陷

## 症狀

新建的一致性稽核器對某類異常輸出 WARNING，異常本身**測得正確**（數字、集合差、重複項都是真的），但其中多數是既有決策文件明文裁定過的刻意設計。稽核器每次執行都重複朗讀這些已裁定項，訊號中真正需要處置的新異常被淹沒。

常伴隨第二個症狀：有人依據同一異常數字建立了「修復」ticket，票面主張與既有決策文件的裁定**方向相反**（決策文件寫「禁止重編」，票面寫「產出重編方案」）。

---

## 根因

異常偵測與異常解釋是兩件事，工具與人都容易只做前者：

| 層 | 該做什麼 | 漏掉時的結果 |
|----|---------|-------------|
| 偵測層 | 量出異常（集合差、重複、缺漏） | —— 通常正確 |
| 解釋層 | 判定該異常是缺陷還是已裁定的設計 | 把政策當缺陷 |

解釋層需要一份**政策輸入**——既有的決策文件、凍結登記表、豁免清單。稽核器若不讀它，就沒有能力區分「未登記的新碰撞」與「登記在案的刻意重號」；建票者若不查它，就會把已結案的決策重新開啟。

助長條件：異常以數字呈現（「7 組碰撞」）時，數字看起來自明，不像敘述那樣會促使讀者追問「這是誰決定的」。

---

## 實例（2026-08-09，flutter_balance）

某框架的 error-pattern 知識庫有 420 個檔案卻只對應 413 個唯一 ID。查得七組 ID 各被兩份不同模式共用。

- **當下判讀**：ID 是跨檔引用錨點，碰撞使引用無法指向唯一對象，屬缺陷 → 建 ANA 票要求「裁定七組的重編方案」，並在新建的索引一致性 Hook 中把 ID 碰撞列為 WARNING。
- **查證後**：`.claude/methodologies/error-pattern-numbering-methodology.md` 早已把這七組登記為 legacy 凍結重號，明文「引用時須以 slug 區辨語意，**禁止重編**」，理由是跨專案一致、無 sync 惡化風險，重編的引用 churn 成本遠高於碰撞危害。七組中另有一組實為孤兒重複（該教訓早已重編到新號，舊檔隨初次匯入殘留），與碰撞是不同性質的問題。
- **後果**：ANA 票的前提整個錯置，需在分析階段先推翻票面才能繼續；新 Hook 在完全正確運作的前提下，每次 session 啟動輸出六筆政策允許的告警。

若未在 ANA 階段攔下，會進一步執行違反既有裁定的重編，churn 86 檔次框架引用與 74 檔次歷史紀錄。

## 偵測

| 訊號 | 檢查 |
|------|------|
| 準備為某個量測異常建缺陷票 | 先 `grep -rl "<異常涉及的識別符或概念>" .claude/methodologies/ .claude/rules/ .claude/references/`，確認該異常未被裁定為刻意設計 |
| 新稽核器把某類項目列為 WARNING | 問「這類項目有沒有合法存在的情況？合法清單從哪讀？」答不出來即缺政策輸入 |
| 稽核器輸出的告警數長期不變 | 恆定的告警集合通常是政策項而非待處置缺陷 |

---

## 防護措施

1. **稽核器的合法例外清單必須是外部輸入，不是硬編碼**。以既有決策文件（凍結表、豁免清單）為資料來源解析，決策更新時稽核器自動跟上；硬編碼會在下次政策調整時再次分岔。
2. **分流而非靜音**。已登記的例外歸 INFO、未登記者維持 WARNING。直接移除該類檢查會連同「未登記的新異常」一起失去偵測——真正的價值在報出未登記者。
3. **政策輸入解析失敗時 fail-open 為全部 WARNING**，並輸出解析失敗原因。靜默退回「無例外」或「全部例外」都會讓判定基準在無人察覺下改變。
4. **建缺陷票前先查既有裁定**。量測結果只證明異常存在，不證明它是缺陷。異常涉及編號、命名、目錄結構這類有既定慣例的對象時，查證成本低而錯置成本高。
5. **票面前提可以被承接者推翻**。ANA 承接時若查得票面前提與既有決策相反，正確動作是先在分析中推翻並記錄，而非照票面執行——這是分析票存在的意義之一。
