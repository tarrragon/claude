# PC-BAL-019：交接內容的完整度被誤讀為交接已建立

## 基本資訊

- **Pattern ID**: PC-BAL-019
- **分類**: 流程合規（process-compliance）
- **來源版本**: v0.2.1
- **發現日期**: 2026-07-31
- **風險等級**: 高（下一 session 拿不到交接目標，且既有防護對此情形零覆蓋）
- **影響範圍**: 任何「內容產出」與「指標寫入」分屬不同動作的交接機制——session handoff、任務轉派、值班移交、跨團隊 ticket 交接

## 摘要

**交接的內容被完整寫進了載體（ticket body、文件、commit 訊息），但把該載體登記進讀取端的那個動作沒有執行，於是下一手的工具查不到任何交接訊號。** 內容準備得越完整，越不會有人回頭檢查登記步驟——完整的產出本身就讀起來像流程已經走完。

內容產出與指標寫入是兩個獨立動作，回饋量相差懸殊：前者產生一整段結構化文字與一個 commit，後者只寫一個 JSON 或一行索引且成功時安靜。回饋量的落差使人把前者的完成感誤投射到後者，因此這不是遺漏了一個瑣碎步驟，而是兩個動作的可見度不對等所致。

## 症狀

- 上一 session 的 commit 訊息明寫「X 交接準備」，ticket body 有完整交接章節（已查證事實表、風險說明、必答問題、範圍邊界）
- 但 `.claude/handoff/pending/` 是空目錄，`ticket resume --list` 回報「沒有下 session 建議項目」，worklog 最新的「下一站」段落所指向的目標已與現況脫節
- 新 session 的接手流程（dashboard-first）完全正常運作，只是看不到交接目標——該 ticket 被當成普通 pending 混在 priority 清單中段
- 接手者依工具輸出推薦任務，把真正的交接目標埋在清單裡，需要人介入指出「應該有交接目標才對」
- 事後查證：交接意圖的唯一痕跡在 git commit message，任何工具都不讀那裡

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 內容與指標是兩個獨立動作 | 寫 ticket body 用 append-log；建交接指標用另一個 CLI 子命令 | 前者完成不蘊含後者完成，但執行者的完成感來自前者 |
| 回饋量不對稱 | 內容產出有大量可見輸出與 commit；指標寫入成功時只印一行 | 缺少指標寫入時沒有任何缺席訊號，安靜的成功與安靜的未執行無法區分 |
| 既有防護以「內容已寫」為前提 | 同步檢查 hook 偵測「worklog 有交接段但無指標」；批次補建工具從 worklog 反推指標 | 兩者都要求 worklog 那一格有東西。兩軌皆空時，前者無觸發條件，後者無來源可掃 |
| 讀取端只讀單一軌道 | 接手用的 dashboard 讀 ticket frontmatter（status / priority），不讀交接指標 | 即使指標存在於另一軌，dashboard 也不會顯示；反之亦然，兩軌從不互相校驗 |

核心是**完成度訊號長在錯誤的地方**。交接是否成立，取決於讀取端能否查到；但執行者的判斷依據是自己產出了多少內容。兩者之間沒有任何連結。

## 解決方案

### 立即補救

1. 查三個位置確認交接是否真的存在，缺一即視為未建立：交接指標檔案、worklog 的下一站段落、ticket 狀態
2. 補建指標時使用絕對指向（直接寫 target ticket id），而非「來源 + 方向」的間接推導。間接推導要求讀取端從來源 ticket 加方向反推目標，來源狀態一旦改變（completed、被 GC 歸檔）推導就失效，而絕對指向不依賴來源票的存活
3. 回寫 worklog 下一站，內容須含起手指引與已知陷阱，不只是 ticket 編號。只寫編號時接手者仍須自行重建「該從哪讀起、哪些前提已被推翻」，交接省下的成本會在接手端原樣付出

### 判別準則

| 訊號 | 是否構成交接已建立 |
|------|------------------|
| 讀取端工具查得到（指標檔 / worklog 下一站） | 是 |
| ticket body 有完整交接章節 | 否——那是交接的內容，不是交接本身 |
| commit 訊息寫了「交接準備」 | 否——沒有任何工具讀 commit message |
| 「我記得我交接了」 | 否，見 `tool-output-trust-rules` 規則 5：記錄平面不是 ground truth |

## 預防措施

下表三項工具層措施目前**皆為提案，尚未實作**，唯一可立即執行的是自律層。讀者不可據本表認定防護已覆蓋——若把提案讀成既存機制，正是本 pattern 描述的錯誤在本檔自身重演。

| 層級 | 措施 | 狀態 |
|------|------|------|
| 執行者自律 | 產出交接內容後，立刻執行指標寫入並以讀取端指令驗證（跑一次接手查詢，確認自己的目標出現在輸出中） | 可立即執行，無需工具支援 |
| 工具設計 | 內容寫入命令在偵測到「本次寫入的是交接類章節」時，提示尚未建立指標——把兩個動作在使用點合併，而非靠文件提醒 | 提案，無票承接 |
| Hook 層 | 偵測「session 有 ticket 活動但兩軌皆空」，可用訊號為本 session 的 commit 紀錄、append-log 紀錄、ticket 狀態變更 | 提案，缺口分析由 `0.2.1-W3-178` 進行，該票結論才決定是否實作 |
| 讀取端 | 接手視圖納入交接指標，使單一入口同時覆蓋兩軌，消除「指標存在但看不到」的另一半風險 | 提案，同由 `0.2.1-W3-178` 的 acceptance 3 評估 |

**設計原則層面**：這是 `opinionated-default-design` 主張 1 的一個實例——若需要寫文件提醒「記得也要執行指標寫入」，代表工具的預設行為還有改善空間。正解是讓內容寫入的預設路徑帶出指標寫入，而非增加一條需要記憶的規則。

## 與相關模式的關係

| 模式 | 關係 |
|------|------|
| `PC-009` | 同屬交接機制家族，但該模式是「對已完成 ticket 用錯旗標」（動作執行了但參數錯），本模式是「動作根本沒執行」 |
| `ARCH-BAL-005` | 同屬「產出未被正確消費」家族的零讀者側。該模式是豁免理由寫了但無人消費，本模式是交接內容寫了但未登記 |
| `IMP-BAL-005` | 同家族的有讀者側。該模式的錯誤訊號有讀取者但用途錯（顯示而非判定），本模式的交接訊號寫在 commit message 這個零讀者位置 |

三者的共同形狀是**產物存在且品質良好，但它所在的位置不在任何消費者的讀取路徑上**。偵測手段依有無讀者分流，不是同一套：

| 側 | 成員 | 偵測方式 | 成本 |
|----|------|---------|------|
| 零讀者 | 本模式、`ARCH-BAL-005` | grep 該產物的識別字，零命中即成立 | 低 |
| 有讀者但用途錯 | `IMP-BAL-005` | grep 會命中，須讀懂命中處在字串格式化還是條件判斷裡 | 高一個量級（`IMP-BAL-005` 根因末段） |

依 `ARCH-BAL-005` 的判別順序（該檔「讀者遇到新實例時的判別順序」段）：先問「這個宣告有沒有任何程式碼讀它」，答案為否即落在零讀者側。本模式的交接意圖只存在於 commit message，全專案無任何工具讀該處，故屬零讀者側。

## 驗證方式

修正後應通過下列固定值查證（對應 `tool-output-trust-rules` 規則 3，這些命令的輸出無法憑預期腦補）：

| 檢查 | 命令 | 通過判準 |
|------|------|---------|
| 指標檔存在 | `ls .claude/handoff/pending/` | 有對應來源 ticket 的 JSON |
| 指標指向正確 | 讀該 JSON 的 `target_ticket_id` | 等於預期接手的 ticket id |
| 讀取端查得到 | `ticket resume --list` | 輸出含該 ticket id，非「沒有下 session 建議項目」 |
| worklog 軌道同步 | grep worklog 的下一站段落 | 最新一則指向同一 ticket id |

四項須同時通過。任一項不通過即視為交接未建立，內容寫得多完整都不算。

## 案例：W3-174 的交接指標從未寫入讀取端（2026-07-31）

事發時點的固定值證據（現況已修復，下列為修復前狀態）：

| 位置 | 事發時實測 |
|------|-----------|
| `.claude/handoff/pending/` | 空目錄（`ls -la` 只有 `.` 與 `..`） |
| `ticket resume --list` | 輸出「沒有下 session 建議項目」 |
| worklog 最新下一站 | 停在 `v0.2.1-main.md:664`，指向的六張票中兩張已 completed |
| commit `b530248` | subject 為 `docs(0.2.1-W3-174): 寫入交接 context 並更正 Context Bundle 的失效快照`，交接意圖在**內文首句**「W3-174 交接準備」，非 subject |

`0.2.1-W3-174` 的 ticket body 同時具備完整交接章節（五項已查證事實表附重現指令、前提誤判史、執行前必答的三選項比較、範圍邊界、共用 repo 寫入注意事項）。內容完整度與指標存在與否完全無關，正是本模式的核心。

新 session 的 dashboard-first 流程照常運作，該 ticket 以普通 P1 pending 列在清單第 4 位，接手者依工具輸出推薦任務時把它埋在中段，經使用者指出「應該有交接目標才對」才發現。
