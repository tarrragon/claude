# PC-GPD-037: 對下游閘門行為下判斷（會擋／不擋）前未讀其現行判定碼，憑設計印象轉述

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-GPD-037 |
| 類別 | process-compliance |
| 風險等級 | 中 |
| 發現日期 | 2026-10-20 |
| 來源版本 | 0.5.0 |

## 症狀

同一個 session 內發生兩次，方向相反：

1. **誤報「會擋」**：PM 判斷某張票的 complete「會被 hook 證據閘門擋下，要等另一張修正票合併」，並把這個判斷寫進票面、設成阻擋。實際上 complete 時的判定集合早已排除唯讀宣告，這張票的 complete 根本不受影響。後來實跑才發現判斷錯誤，撤回阻擋。
2. **漏報「不擋」**：轉告一筆放寬型變更時，PM 寫的失敗落點是「漏交 hook 證據的票會在 complete 被閘門擋下，不會靜默通過」。主控讀了 checker 的程式碼才發現另有一條過渡期路徑：驗收條件的字面只要命中關鍵詞，就放行並只發一則 WARN。所以實際的失敗落點不一定在 complete。

兩次的判斷都來自 PM 對閘門「設計上應該怎麼判」的印象，沒有讀判定碼的現行分支。

## 根因

1. **閘門的現行行為不等於當初的設計意圖**。一個閘門經過多次修改後，會累積過渡期分支、排除集合、放行旁路。PM 記得的是設計意圖，讀不到這些後加的分支。
2. **「下游會擋」是放寬型變更的核心論據**。放寬型變更能不能放行，取決於失敗會落在哪裡。這個論據一旦錯了，放行決策就建立在不存在的保護上。而說「會擋」的人通常就是要求放行的人，沒有誘因去質疑自己的論據。
3. **判斷「會擋」與判斷「不擋」同樣需要讀碼**。誤報「會擋」會製造假阻擋，拖慢後續工作；漏報「不擋」則讓缺陷靜默通過。兩者都不是保守做法。

## 解決方案

1. 在票面、轉告訊息或阻擋設定中寫下「X 閘門會擋 Y／不會擋 Y」之前，先讀該閘門判定函式的現行碼，並附上判定所在的符號名（例：`check_hook_protection_acceptance` 的過渡期分支）。
2. 能實跑的就實跑：用 `--dry-run`、或在 tmp repo 建一張最小票觸發該閘門，以實際輸出取代推論。
3. 讀碼時特別找三類分支：過渡期或相容旁路（`_TRANSITION_*`、`legacy`）、排除集合（write-only、`::read` 過濾）、WARN 而非 deny 的出口。

## 預防措施

| 層級 | 措施 |
|------|------|
| 放寬型變更轉告 | 失敗落點一欄必須附判定函式符號名與所讀的分支；只寫「會被 X 擋下」而未附來源者，視為未查證 |
| 設定阻擋（blockedBy、票面 NeedsContext） | 以「某閘門會擋」為阻擋理由時，先實跑或讀碼確認；未確認不設阻擋 |
| 與既有規則的關係 | 屬 `tool-output-trust-rules` 規則 5「記錄平面不是 ground truth」的一個實例：對閘門的記憶屬記錄平面，判定碼才是世界平面 |
