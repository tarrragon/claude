# PC-BAL-053: 依檔名查證失效引用，對「功能被合併進不同名檔案」為盲，產出功能缺口假結論

## 基本資訊

| 項目 | 說明 |
|------|------|
| 分類 | Process Compliance |
| 風險等級 | 高 |
| 來源版本 | v0.2.1 |
| 發現日期 | 2026-08-22 |
| 發現途徑 | 依假結論建票後，執行該票時查證推翻自身前一票的判定 |

## 症狀

修復失效引用時，對每個 `grep` 命中的路徑執行兩步查證：

```bash
[ -e "$path" ] || echo "MISSING: $path"        # 步驟 1：原路徑是否存在
find . -name "<basename>" -not -path "*/archived/*"   # 步驟 2：是否只是搬了位置
```

兩步皆無命中，遂判定為「功能缺口——文件宣稱的能力未部署」，並據此建立 ANA 票與 error-pattern。

實際狀態：該功能存在且運作中，被**合併**進另一個**不同名**的檔案。接手者的 docstring 明寫「合併以下 2 個 Hook」並列出原檔名，核心邏輯（四類錯誤分類的 enum 與 pattern 表）逐項保留，且已註冊於對應事件。

**假結論的下游代價**：依此建立的 ANA 票問錯了問題（「應重建或改寫為人工協議」，而正確答案是「更新文件路徑」），據此寫下的 error-pattern 立論實例整個不成立，而該 error-pattern 屬跨專案同步資產。

## 根因

### 根因一：接手者取新的上位語意名時，按檔名搜尋必然落空

遷移有三種形態，前兩種可由檔名定位，第三種不行：

| 遷移形態 | 接手者名稱 | `find -name <basename>` |
|---------|-----------|------------------------|
| 搬移（relocate） | 相同 | 命中 |
| 改名（rename） | 不同但通常有共同詞根 | 部分命中 |
| **合併（merge）** | **完全不同；接手者常取新的上位語意名** | **取上位語意名時必然不命中** |

實例中兩個 hook 合併為一個以「時機」命名的新 hook（原名分別以「功能」與「階段」命名），三個名稱無任何共同詞根。按名字搜尋在此形態下沒有任何命中機會，這不是搜尋範圍不夠廣的問題，是搜尋維度錯了。

### 根因二：「找不到」被當成結論，而它只是「這個方法沒找到」

`find` 回傳空集合的正確語意是「以檔名為鍵、在此範圍內、無命中」。把它讀成「此功能不存在」，是把方法的邊界誤當成世界的邊界。功能是否存在的權威證據是**該功能的行為是否仍被觸發**——對 hook 而言即註冊表，對函式而言即呼叫端；檔名不構成證據。

### 根因三：查功能歸屬時查了名字，沒查註冊表

事件驅動的元件有一份權威清單（此處為 `settings.json` 的事件註冊）。該清單回答的正是「這個事件上現在誰在跑」，與檔名無關。查證時完全沒有讀它，卻對它所描述的事實下了結論。

## 防護措施

### 判定「功能缺席」前的三層查證，缺一不可

| 層 | 問題 | 指令 | 這一層能排除什麼 |
|----|------|------|----------------|
| 1 | 原路徑存在嗎 | `[ -e "$path" ]` | 無失效 |
| 2 | 同名檔搬去哪了 | `find . -name "<basename>" -not -path "*/archived/*"` | 搬移與改名 |
| 3 | 這個職責現在誰在承擔 | 讀權威清單（hook 讀事件註冊；函式讀呼叫端；CLI 讀入口點宣告），並在候選接手者中搜尋**原檔名字串** | **合併** |

**反向搜尋層**（本文件的第 3 層；`IMP-BAL-011` 分流順序中的同一動作亦以此名互引，兩檔各自的序號只作內部排序，不跨文件引用）真正做功的動作是「在接手者內部搜尋原檔名」而非「搜尋叫這個名字的檔案」——合併型遷移的接手者通常在 docstring 或註解留有併入紀錄。除 git 歷史（`git log --follow`、commit message）外，那是工作區內唯一可按原名命中的位置。

```bash
# 反向搜尋層（本文件第 3 層）：在權威清單所列的所有現役元件內部，搜尋原檔名字串
grep -rn "<原檔名>" .claude/hooks/ .claude/skills/*/hooks/
```

### 三層皆無命中才可下「缺席」結論，且結論須標明查證方法

寫下「此功能未部署」時，一併記錄用了哪三層查證。**Why**：讀者無從判斷這是「查遍了確實沒有」還是「用一個對合併為盲的方法沒查到」，兩者導向的下一步完全相反。**Consequence**：不標方法時，假結論與真結論在文字上無法區分，下游會在假前提上建票、建 error-pattern、甚至重建已存在的功能。**Action**：結論句附查證方法清單，例「三層皆無命中（路徑不存在 / 同名檔全庫無 / 事件註冊表所列現役元件內未見原檔名）」。

### 合併型遷移的產出方責任

執行合併時，在接手者的 docstring 或檔頭列出原檔名，逐一列全。**Why**：除 git 歷史外，這是合併後工作區內唯一能按原名命中的線索，也是實例中接手者確實留下、而查證方沒去讀的那份紀錄。**Consequence**：不留此紀錄，任何後續按原名的追查都會得到「不存在」，且無從得知該去哪裡找。**Action**：合併時檔頭寫「合併以下 N 個元件：<原名清單>」；同時更新引用原名的文件路徑，不留待後人考古。

### 移除某物之前，按它的每一種被引用形態各搜一次

同一個東西在文件中至少有三種寫法，各自需要不同的搜尋樣式：呼叫形態（`/commit-as-prompt`）、
檔名形態（`commit-as-prompt.md`）、裸名形態（「依 commit-as-prompt 規範」）。

**Why**：搜尋樣式即判準——樣式綁定單一形態時，得到的不是「有幾處引用」而是「有幾處用這種
寫法引用」，而兩者的差距不會出現在輸出裡。**Consequence**：據此清單執行移除，未被搜到的
形態會在移除後成為死引用，且因為「清單已全數處理」而被認定為完工。實例：一次 slash command
廢止任務，以帶斜線的呼叫形態搜得 4 處，執行者獨立以裸名再搜，另得 2 處（目錄樹示例中的檔名、
散文中的裸名引用）。**Action**：移除清單以最寬的裸名搜一次（`grep -rn "<裸名>"`），再對命中項
逐一判讀是否為同名不同物——寧可撈進誤報後人工剔除，不要靠窄樣式換取零誤報。同名不同物必然
存在，該實例中即有一處「`test-progress` 更新」是 hook 活動命名，與被廢止的指令無關。

## 學習要點

- 空集合是方法的輸出，不是世界的狀態；下結論前先問「這個方法對哪類情形為盲」
- 查「某職責現在誰在承擔」要讀權威清單（事件註冊 / 呼叫端 / 入口宣告），不是查檔名
- 合併型遷移在工作區內只有接手者內部留下原名線索（git 歷史另計），故需**反向搜尋層**：不是找叫這名字的檔案，是找提到這名字的檔案
- 搜尋樣式即判準：綁定單一引用形態時，輸出是「有幾處用這種寫法引用」而非「有幾處引用」，兩者的差距不會出現在結果裡
