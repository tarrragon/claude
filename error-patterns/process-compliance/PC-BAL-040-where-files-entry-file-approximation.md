# PC-BAL-040: where.files 以模組入口檔近似宣告，漏列 AC 實際承載檔案

## 基本資訊

- **類別**: process-compliance
- **風險等級**: medium
- **發現日期**: 2026-08-18
- **關聯案例**（首發；後續案例見「## 案例」段）: 2026-08-18 同一 session 連續兩例——multi-PM lease 子票的顯示層接線 AC、runqueue 群組切分子票的 CLI 接線 AC，均因承載檔未列入宣告而被範圍約束擋下

## 案例

2026-08-18 同一 session 連續兩例（multi-PM 協調層 Phase 3 實作波）：

1. lease 生命週期子票：AC 要求「STALE session 持票在 sessions/runqueue 輸出標 reclaimable」，但票面只宣告 CLI 入口分派檔，實際承載的 sessions 與 runqueue 兩個獨立命令檔未列入。代理人 SR 上報停手，PM `set-where` 擴入後於本票續完。
2. 群組切分子票：AC 要求 `--groups` 旗標接線，承載檔為 runqueue 獨立命令檔，票面同樣只宣告入口分派檔。同型 SR 往返、同型處置。

### 2026-08-20 續案：派發前檢查攔截六例

同一 session 內六張 ticket CLI 修復票，PM 於派發前逐條 AC 反推承載檔案時發現同型缺口，全數在派發前以 `set-where` 修正，未產生任何 SR 往返成本。其中兩例的缺口形態：

1. WARNING 輸出子票：命中的是原 pattern 未涵蓋的變體——不是漏列，而是列到平行的另一個分支。該票 AC 要求「when 欄位含 ticket 引用而依賴欄位為空時輸出 WARNING」，票面宣告的測試根承載 hook 層與跨層整合測試，該功能的實際測試位置卻在 CLI 單元測試根。專案存在兩個測試根且分工不同，以「測試目錄」這種粗粒度直覺近似時會選到錯的那一個。
2. re-export 清空遷移票：AC 要求遷移全部消費者（實測近百處），票面宣告僅列被清空 re-export 的那一個模組入口檔。承載檔實際橫跨函式庫層、命令層與兩個測試根。此例與原案例同型：宣告的是「問題所在的檔案」，AC 描述的是「修復波及的範圍」。

其餘四例形態一致：宣告填「發現問題時觀察到的那一個檔案」，而 `why` 與 `acceptance` 描述的是整類問題的範圍。

**兩種變體的判別在宣告集合與實際承載集合的關係**：範圍太窄是宣告集合為承載集合的子集（同一分支往下漏了檔），範圍平移是兩集合無交集（選到平行的另一個同類分支）。判別方式為對每條 AC 以 grep 定位承載檔後與票面宣告取交集——交集為空即平移，交集非空但有遺漏即太窄。兩者處置動作不同：太窄往同一分支下補檔，平移須整組換到正確的分支。

成本對照：原案例是事發後修（每例一輪 SR 上報、PM 裁決、擴宣告、續派），續案是派發前修（每例一次 grep 定位加一次擴宣告）。派發前檢查即為此攔截點，執行方式見預防措施「建票時逐條 AC 反推承載檔案」。


### 2026-08-22 續案：實作檔與其測試檔的配對遺漏，由執行者自行補正

PM 於收窄 `where.files` 的同一次操作中，漏列兩支待改 hook 對應的 3 個測試檔。背景為一則「降級 hook 可執行位防護」的實作票：PM 接手驗證時依 PC-162 把建票時的目錄級宣告改為精確路徑，並實測確認原宣告目錄下不存在票面宣稱的承載內容——收窄動作本身正確，缺口出在同一次操作未展開實作檔與測試檔的配對。

**本例與前兩批的差異在缺口形態**：前兩批是「同一分支往下漏了檔」（子命令實作分散於多檔）或「選到平行的另一個分支」（兩個測試根選錯）。本例是**實作檔與其測試檔的配對關係未被展開**——本專案的 hook 皆有配對測試檔，行為變更即需同步改測試（本例 3 個，含一個因功能刪除而整檔移除的 451 行檔案），此配對可從專案結構推導，卻不會被「建票時逐條 AC 反推承載檔案」捕捉：AC 描述的是行為變更（降級 chmod 邏輯），grep 定位到的是實作檔，測試檔要再往前推一步才會浮現。

**處置路徑亦為新變體**：執行者未如前兩批走 SR 上報停手，而是在呼叫 `ticket track commit` 前先以 `ticket track set-where` 將 3 個測試檔補入宣告，使宣告與實際變更範圍一致後才走該命令的子集驗證，一次通過，未改走「`git add` 加裸 `git commit`」的備援路徑。該處置消除了原案例每例一輪上報加裁決的往返成本，且執行者於回報中主動揭露此動作。

**衍生觀察**：此變體使「執行者可自行擴充寫入範圍宣告」成為既成事實，連帶使 PM 驗收時「commit 檔案集合為 `where.files` 子集」這項檢查恆成立而失去鑑別力——宣告本身可能已被調整。本 pattern 對此只給當前可行的驗收做法（見預防措施「PM 驗收以宣告的變更歷史為準」）；範圍約束是否該在機制層改動（宣告變更需審批、或 `set-where` 補獨立提交痕跡）屬另一維度，另有專票追蹤；線索：該票評估維持現狀／補提交痕跡／擴宣告需審批三選項，發現於本案例的 PM 驗收階段。

本例對應的預防措施為「實作檔入宣告時同步展開其測試檔」與「執行者可自行補正漏列的宣告」兩條。

## 症狀

某條 acceptance 需要修改的檔案不在票面 `where.files` 宣告範圍內。此缺口有兩種可觀測形態，PM 端的辨識訊號不同：

（形態一）代理人回報 partial_success 並停手待裁決，依「範圍外用 add-spawn-request 上報、不自行擴 scope」約束。訊號直接可見，事發後才發現時每例多付一輪 SR 上報、PM 裁決、擴宣告、續派的往返成本。

（形態二）代理人未回報 partial_success，而是在 commit 前自行以 `set-where` 補正宣告後繼續（預防措施「執行者可自行補正漏列的宣告」授權此路徑）。此形態無 partial_success 訊號，PM 端辨識改看兩處：回報中是否揭露該次宣告變更，以及 ticket md `where.files` 欄位的 git 變更歷史。只依形態一的訊號辨識會完全漏掉此形態。

同型缺口會在單一 session 內重複出現，已記錄三批案例（兩例、六例、一例）。

## 根因

PM 建票時以「模組入口檔 + 目錄」直覺近似 `where.files`（例：宣告 CLI 入口檔代表某子命令功能），未逐條 acceptance 反推實際承載檔案。當目標模組的子命令實作分散於多檔（入口分派檔與各子命令獨立檔並存）時，宣告與實際承載即出現缺口。缺口在派發前不可見——dispatch-readiness 對 where.files 與 acceptance 的一致性檢查採啟發式，無法驗證「每條 AC 的承載檔案都已列入」。

## 解決方案

事發時：PM 用 `ticket track set-where` 擴入實際承載檔案，`resolve-spawn-request --status dismissed` 註明「宣告缺口在 PM」，通知代理人於本票續完。缺口屬 PM 建票疏漏時修宣告，不另開票（避免把單一功能拆成人為兩票）。

## 預防措施

1. **建票時逐條 AC 反推承載檔案**：每寫一條 acceptance，先問「這條要動哪個檔？」用 grep/codegraph 定位實際檔案再寫入 where.files；禁止以模組入口檔或目錄名近似。專案存在多個同類根目錄（多測試根、多套件根）時，除定位承載檔外須確認選到的是承載該 AC 的那一個根，不以類別名稱代表任一個。
2. **派發 prompt 的授權範圍直接引用票面 where.files**，不在 prompt 另列一份清單——無同步機制的兩份清單會漂移，且 prompt 版本較窄時代理人會被錯誤約束擋下。
3. **代理人端遇宣告外的檔案即 SR 上報停手**：擅自擴 scope 會與他票的宣告範圍重疊而造成跨票汙染，勿因本 pattern 放寬此約束。與「執行者可自行補正漏列的宣告」一條的分界不取「AC 是否需要此檔」——該問題由執行者自我判定，而觸發判定的動機本身就是為完成 AC 而需動此檔，該側恆真、無法據以分流。分界改取可查證的重疊事實，見該條的雙條件。
4. **實作檔入宣告時同步展開其測試檔**：`where.files` 列入實作檔時，一併確認該檔對應的測試檔是否需隨之修改。該實作檔已有測試覆蓋時，行為變更即需同步改測試，此配對可從專案結構推導；無測試覆蓋者不適用。功能整體移除時另須檢查是否有整檔刪除的測試檔。「建票時逐條 AC 反推承載檔案」不足以捕捉此形態——AC 描述行為變更，grep 定位到實作檔即停，測試檔需再往前推一步。漏列的成本在執行期必然兌現：執行者 commit 前撞上宣告外的檔案，此時走上報付一輪往返，走自行補正則削弱 PM 驗收的鑑別力，兩條路都已產生成本。
5. **執行者可自行補正漏列的宣告**：發現待改檔案不在 `where.files` 內時，可先以 `set-where` 補入再走 `ticket track commit`，不必然走 SR 上報。此為 SR 上報之外新增的並行路徑，不取代該路徑——症狀段形態一（回報 partial_success 停手）在下列條件不成立時仍是唯一正確處置。放行需**兩個條件同時成立**：

   - (a) 該檔確屬本票 acceptance 的承載範圍；
   - (b) 該檔未落入其他 active ticket 的 `where.files`——以 `ticket track conflicts` 查證，該命令列出 pending 與 in_progress 票的宣告交集（含實作檔到測試檔的啟發式推導，標記 `[heuristic]`）。

   (b) 不成立或無法查證時一律 SR 上報。條件 (a) 由執行者自我判定故不足以單獨分流（見「代理人端遇宣告外的檔案即 SR 上報停手」一條），(b) 取的是可機械查證的重疊事實，補上前者缺的約束力。效益是消除往返成本，且宣告與實際範圍一致優於維持不一致。

6. **PM 驗收以宣告的變更歷史為準**：「執行者可自行補正漏列的宣告」一條生效後，「commit 檔案集合為 `where.files` 子集」恆成立而不再具鑑別力——宣告本身可能已於執行期被調整。驗收改比對 ticket md `where.files` 欄位的 git 變更歷史與執行者回報：有變更而回報未提及，即為未揭露的擴充，須回頭確認該次補正是否滿足該條的雙條件。此判準不依賴執行者主動揭露即可執行；揭露仍是執行者端義務，但不作為 PM 端的唯一訊號。
