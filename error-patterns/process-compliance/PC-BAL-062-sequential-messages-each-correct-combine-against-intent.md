# PC-BAL-062：連續訊息各自正確，合成後的方向與發送者意圖相反

## 基本資訊

| 欄位 | 值 |
|------|-----|
| 風險等級 | 中 |
| 來源 | 跨 session 修復票派發（2026-09-03） |
| 發現日期 | 2026-09-03 |

## 摘要

**先論證某方案較優、再補一項該方案的實作約束，兩則訊息各自正確，接收者整合後得到的淨方向卻是選另一案。** 補充約束時未重述它對先前建議的影響，接收者無從判斷這是「該案仍較優、只是要處理這件事」還是「該案有問題、應重新考慮」，而後者是聽起來較保守的讀法，預設會被採納。

發送者不會察覺，因為逐則檢查每則訊息都與其意圖一致；問題只存在於訊息之間，而訊息之間沒有被檢查的載體。

## 症狀

- 接收者的選擇與發送者的建議相反，而發送者找不出自己哪一句寫錯
- 逐則回讀每則訊息皆正確，且皆能對應發送者當時的意圖
- 後一則訊息陳述的是事實或風險，本身不含建議，故不被視為「改變建議」
- 接收者的產出附有合理理由，該理由引用的正是發送者提供的材料
- 發送者事後重讀才發現：兩則合起來的推論方向，與自己想要的相反

## 根因

1. **建議與約束是兩種語意，補充時混用同一通道。** 前者回答「該選哪個」，後者回答「選了之後要處理什麼」。約束單獨送達時，接收者須自行推斷它屬於哪一種，而無標記的風險陳述預設被讀成前者。
2. **保守讀法有預設優勢。** 「這個方案有風險」與「這個方案較優但有風險」之間，接收者傾向前者——它的錯誤代價看起來較低，且不需要承擔覆蓋發送者顧慮的責任。
3. **訊息之間沒有檢查載體。** 每則訊息可被審視，訊息序列的合成效果不落在任何一份可審視的產物上，直到接收者的行動把它顯現出來。
4. **時間差掩蓋關聯。** 兩則訊息若間隔數個回合，發送者已離開先前的論證脈絡，補充時不會回頭核對它與既有建議的關係。

## 防護

| 時機 | 做法 |
|------|------|
| 補充約束或風險時 | 明寫它對先前建議的影響：「此約束不改變建議，請在設計中處理」或「此約束推翻先前建議，改採 X」。無此一句即為缺漏 |
| 補充材料來自第三方時 | 標明是建議或指定，並明說接收者可不採納。轉遞本身會被讀成背書 |
| 送出第二則之後 | 把兩則並排重讀一次，問「只讀這兩則的人會做什麼決定」，而非「每則是否正確」 |
| 接收端（對建議） | 收到與先前建議方向不一致的補充時，回問其對建議的影響，不自行推斷 |
| 接收端（對規則） | 讀到聲稱具強制力的條款時，回問其實際強度——有無執法層、由誰檢查。兩者觸發時機不同：對建議的回問發生在收到補充時，對規則的回問發生在讀到硬措辭時 |

## 本條防護的實際強度：無執法層，依賴發送者自覺

上表「無此句即為缺漏」是判定標準，不是攔截機制。**本條沒有執法通道**，其生效方式是發送者在寫訊息前想起這份記錄——而那正是本檔根因第 3 點所述的情形：訊息之間沒有檢查載體。條款措辭的硬度與其實際強度不一致，故在此明寫，避免讀者誤以為有機制會擋。

技術可行性另計，已知與未驗證須分開陳述：**已證實**——`PreToolUse` 的 matcher 涵蓋 `Agent`、`AskUserQuestion`、`TodoWrite`、`WebFetch`、`WebSearch` 等非檔案類工具，故「非檔案操作不可攔截」不成立。**未驗證**——訊息類工具（`SendMessage`）是否發出該事件。既有五者皆為 harness 內建核心工具，跨 session 通訊工具不必然走同一條註冊路徑；matcher 清單中無此項只證明本專案未曾掛過，兩個方向都不證明。要驗證只需加一個對應 matcher 的 no-op hook 發一則訊息觀察是否觸發，本專案未執行該實驗，因不打算掛此類 hook。

上述區分本身即本檔所屬族群的實例：觀測到一類成立便推論另一類成立，而兩類之間的那條軸未經驗證。

未實作的原因不是能力不足，是偵測精度——判定一則訊息是否「補充了與先前建議相關的約束」，需要知道先前訊息是否構成建議，以及本則的約束是否指向該建議。可機械判讀的只有字面特徵（風險詞、轉折詞），以此為觸發條件會對大量正常訊息誤報，而低精度的攔截層在本專案已有裁決記錄：警告對代理人無約束力，而誤報會使執行者學會忽略該通道，反使真訊號失效。

故現階段的正確定位是：本條為判定標準供事後審查與自我檢查使用，不宣稱事前攔截。若日後出現可靠的觸發判準（例如訊息類工具提供結構化欄位，可標記「本則屬建議／屬約束」），再評估執法層。

## 邊界

- 與 `ARCH-BAL-004`（文件範例與同檔規則矛盾）同屬「局部正確不蘊含整體正確」，但載體與機制不同：該筆是靜態同檔、範例示範力大於規則約束力、讀者取得可用產物即停止閱讀；本筆是連續訊息、後一則未標明對前一則的影響、接收者採保守讀法。
- 與 `PC-BAL-045` 的「驗證做了但驗證的涵蓋範圍沒被驗證」共享上位形態，但該筆檢查的是觀測面涵蓋，本筆檢查的是訊息序列的合成方向。
- 不適用於單則訊息內部的自相矛盾——那屬一般的表述缺陷，逐則檢查即可發現。

## 實例

派發一張修復票時，PM 先向執行者論證方案一優於方案二（理由：方案二在效果上等同再發一次警告，而該專案已有「警告對代理人無約束力」的裁決記錄）。隨後補充一項方案一的實作約束（帶衝突標記的檔案若是 hook，寫回工作區可能使後續 hook 失敗）。

該約束為真，且 PM 的意圖是「請在設計中處理它」，但訊息未如此標明。兩則合起來讀，接收者會得到「方案一有危險」的印象，而 PM 剛否定的正是方案二。

由第三方指出後，PM 補送第三則重構該約束——問題應定為「如何讓失敗可診斷」而非「如何避免失敗」，因為靜默降級（session 起得來但 hook 用著舊版）正是該票要修的缺陷形態，而立即失敗至少可診斷。此補正同時說明了：原約束不是不該提，是提的時候少了它與建議的關係。
