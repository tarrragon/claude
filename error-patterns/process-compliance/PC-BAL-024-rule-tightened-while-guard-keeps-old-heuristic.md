# PC-BAL-024: 規則收緊為全禁而守衛停留在舊啟發式，落差被規則文件寫下卻未被修補

## 摘要

**當一條規則從「符合某些特徵才禁止」收緊為「一律禁止」，而其自動守衛仍以舊特徵為偵測條件時，守衛會對絕大多數新違規放行。** 更隱蔽的變體是：規則作者在收緊時已意識到舊守衛「必然漏掉」某類違規，把這句話寫進規則文件作為收緊的論證依據，卻沒有同步修改守衛——落差被完整記錄下來，然後留在原地。

危險之處在於守衛仍在執行、仍會偶爾報警、看起來運作正常。沒有任何錯誤訊息說「我的判準已過期」。維護者看到守衛已註冊、規則已收緊，合理推論該規則有執法保護，於是不再人工檢查。

## 症狀

- 規則文件的判準與守衛程式碼的偵測條件不一致，且不一致的方向是守衛較寬鬆
- 規則文件內含「守衛只能偵測 X，必然漏掉 Y」一類自陳，該句被用作收緊規則的理由
- 違規以規則明訂禁止、但不觸發守衛條件的形態持續產生，且數量隨時間累積
- 人工審查偶然發現違規時，第一反應是「守衛怎麼沒擋」，查證後才知守衛判準是舊版
- 守衛的測試全綠——測試覆蓋的是舊判準，與規則現況同樣脫節

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 規則與守衛分屬兩個載體 | 規則在文件、判準在程式碼，兩者無自動一致性檢查 | 任一方演進不會驅動另一方 |
| 收緊規則的成本遠低於收緊守衛 | 改文件一次編輯；改守衛需處理存量誤報、避免噪音壓力 | 規則先行、守衛滯後成為預設路徑 |
| 落差被記錄即被視為已處理 | 把「守衛必然漏掉」寫進規則就結束了 | 記錄取代了修補，且該記錄使後續讀者以為落差是已知且可接受的 |
| 守衛存在即被推定有效 | 註冊清單顯示守衛在跑 | 維護者停止人工檢查，覆蓋率反而下降 |
| 存量違規構成收緊阻力 | 全面收緊會使既有違規全部報警 | 守衛維護者理性選擇不動，落差長期固化 |

**與 PC-V1-006（規則變更未盤點既有規則矛盾）的差別**：PC-V1-006 是兩條規則互相矛盾，本 pattern 是同一條規則的規則層與執法層版本脫節。

**與 PC-V1-012（防護置於便利介面而非真實源頭）的差別**：PC-V1-012 是攔截位置錯誤，本 pattern 的位置正確，過期的是判準內容。

## 案例：框架 ticket ID 引用禁令收緊為全禁後守衛仍只認跳轉詞（2026-08-06）

某框架規則禁止在跨專案同步的框架檔案中引用專案 ticket ID。該規則原本採「移除 ID 後能否理解」的語意判準，守衛只能退而偵測句型——ticket ID 鄰近出現「詳見 / 參見 / 參考 / 依據 / 根據 / 來源是 / 相關文件」時才報警。

規則後續改採全禁原則：ticket ID 在框架檔案的任何出現，除兩類機械可判定的豁免外一律禁止。改版理由明文寫在規則文件內——「守衛只能退而偵測句型，必然漏掉不用該句型的依賴型引用」。

守衛未同步。實測餵入 `# 0.2.1-W3-308: 顯示對象改為 target`（規則明訂禁止的時點標注型引用，無跳轉詞），守衛 exit 0 放行。

後果是兩張連續 ticket 新增 16 處違規全程無攔截，直到 Phase 4 人工文字審查才發現。同一批檔案另有 5 至 15 處/檔的存量違規，同樣從未被攔。更間接的代價是：其中若干處違規來自主導者的明確指示（要求把註解內的 ticket 短碼「補全為完整 ID」以利搜尋），該指示與規則直接衝突，而守衛的沉默沒有提供任何糾正訊號。

## 防護

| 時機 | 動作 |
|------|------|
| 收緊任何有自動守衛的規則時 | 同一次變更內確認守衛判準是否需同步；不能同步則在規則文件標明「守衛僅覆蓋 X 子集，Y 需人工檢查」，而非只記錄落差存在 |
| 在規則文件寫下「守衛做不到 X」時 | 這句話是待辦不是結論。當場建 ticket，或明確記錄為已接受的殘缺並附覆蓋缺口的替代檢查手段 |
| 審查守衛有效性時 | 不看「守衛是否註冊 / 測試是否綠」，而是自行構造一個規則明訂禁止的最小案例餵進去，確認確實被攔 |
| 存量違規阻礙收緊時 | 分階段：新增內容全禁、存量以 allowlist 凍結、隨清理逐步收緊。不要因為無法一次到位就維持舊判準 |
| 規則與守衛所在檔案 | 互相引用路徑，使任一方的修改者能看見另一方 |
