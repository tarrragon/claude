# PC-BAL-023：自我擴張集合的覆蓋率以起始快照為分母

## 症狀

任務目標是「對集合 S 的每個成員做處理 P」，收尾時以「已處理數等於 S 的大小」宣告 100% 覆蓋。兩個條件同時成立時，該宣告為偽：

| 條件 | 具體樣態 |
|------|---------|
| 分母是起始快照 | S 的大小在任務開始時量測並寫入 acceptance（「71 張全數完成判定」），此後不再重取 |
| 任務自身擴張了 S | 執行過程 spawn 子 ticket / 產生新檔案 / 新增設定項，新成員屬於 S 的定義域但落在快照外 |

驗收時的表面證據看起來充分：

```
grep -rl "<處理標記>" <目錄> | wc -l   → 72
<取集合全集> | wc -l                   → 72
```

兩數相等，讀起來像完全對應。實際是「71 張全集內已標記 + 1 張全集外命中」與「72 張全集」兩個不同集合恰好同數——左側的搜尋範圍寬於全集（掃了整個目錄，含已完成項），右側只取當下的待處理項。一漏一多恰好抵銷，是偽全量最難察覺的形態。

**與 PC-BAL-012 的區別**：兩者都以純量代替逐項證據，問「錯在哪一側」即可分辨。PC-BAL-012 錯在**主張側**——一次查詢的結果被分攤給 N 個並列主張，查詢本身無誤。本模式錯在**集合側**——只有一個主張，但構成該主張的兩個計數取自範圍或時點不同的集合。判別問句：證據數被多個主張共用嗎？是則 PC-BAL-012。主張只有一個，但兩側計數各自量測的是什麼集合說不清楚嗎？是則本模式。

## 根因

**集合論層**：`|A| = |B|` 不蘊含 `A = B`。計數是集合的一個投影，投影相等不足以推導原像相等。證明覆蓋需逐元素對應——對 B 的每個成員，檢查它是否在 A 中，而非兩側各取一個純量再比較。

**時間層**：`S` 不是常數。盤點、稽核、批次處理三類任務有共同結構——任務本身就是 S 的寫入者：盤點會 spawn 追蹤 ticket，稽核會產生報告檔，批次遷移會新增設定項。分母在任務開始時凍結，被除數卻持續增長，覆蓋率的定義域從任務中段起就已失效。

**放大條件**：acceptance 條目把快照數字寫成字面常數（「71 張全數完成」）。此後所有驗證都以 71 為準，新成員不在 71 之內，缺口在自身的驗收框架內永遠不可見——驗收通過與缺口存在並不矛盾，因為兩者談的是不同集合。

## 後果

- 驗收宣告 100%，實際為 71/72。缺口不會被本 ticket 的任何後續步驟發現，因為驗收框架已「通過」
- 漏網成員是任務自己產生的，而這類成員尚無任何 context，正是標記機制要保護的對象
- 下游若以「該集合已全數處理」為前提（如「所有 pending ticket 皆有 issue 歸屬，可直接依標記派發」），錯誤前提會沿 ticket 鏈傳遞
- 兩個計數相等提供了虛假的交叉驗證感，使逐項比對的動機消失（此確認偏誤共振點與 `PC-BAL-012` 共有，兩者的判別方式見症狀節）

## 解決方案

**覆蓋率用逐元素比對驗證，分母在驗證當下重取。**

```bash
# 反例：兩側各取純量再比較
grep -rl "<標記>" <目錄> | wc -l    # → 72
<取全集> | wc -l                     # → 72
# 相等，宣告 100%。實際掩蓋了「一漏一多」

# 正例：對驗證當下的全集逐元素檢查，直接列出未覆蓋成員
current=$(<取全集>)                            # 驗證當下重取，不沿用任何既有數字
echo "acceptance 記載 ${ACCEPTANCE_N} 項，當下全集 $(echo "$current" | wc -l) 項"
missing=0
for id in $current; do
  f=$(<定位該成員的檔案> "$id")
  grep -q "<標記>" "$f" || { echo "UNMARKED $id"; missing=$((missing+1)); }
done
echo "未標記數: $missing"
```

正例做了兩件反例做不到的事。其一，輸出未覆蓋成員的識別碼而非通過與否的布林值，缺口自帶定位資訊，補齊動作不需要二次調查。其二，先印出 acceptance 記載值與當下全集大小的對照——這一行是「分母重取」的可見化，兩數不同即代表集合在任務期間擴張過，此時仍拿 acceptance 的舊數字當分母就會落入本模式。

分母的時效性無法由程式碼結構保證，只能由執行紀律保證：`<取全集>` 必須在驗證當下執行。把它存進變數再沿用整個任務期間，寫法看起來一樣，效果與反例相同。

**已用計數相等下過結論時的補救**：重跑逐元素比對，發現的缺口即時補齊，並在 ticket 內記錄「原驗證的分母定義錯誤」而非僅記錄「補了一張」——後者會讓下一個接手者以為是單純遺漏，而非驗證方法的系統性缺陷。

## 預防措施

| 時機 | 檢查 |
|------|------|
| acceptance 寫入集合大小的字面數字時 | 該集合在任務執行期間會被自己寫入嗎？會則改寫為「驗證當下的全集」而非常數 |
| 任務執行中 spawn 子 ticket / 產生新檔案時 | 新成員是否落入本任務要處理的集合定義域？是則立即補處理，不留到收尾 |
| 用兩個 `wc -l` 相等作為覆蓋證據時 | 相等的是計數還是集合？改為逐元素比對並輸出未覆蓋成員清單 |
| 接手他人宣告 100% 的盤點結果時 | 用當下全集重跑一次逐元素比對，而非採信既有數字（`tool-output-trust` 規則 5：記錄平面不是 ground truth） |

**結構性防護**：盤點 / 稽核 / 批次處理類 ticket 的 acceptance 措辭，把「N 張全數完成」改為「驗證當下 pending 全集逐張完成，未覆蓋數為 0」。前者鎖定快照，後者鎖定不變式——不變式在集合擴張後仍然可驗證，快照不行。
