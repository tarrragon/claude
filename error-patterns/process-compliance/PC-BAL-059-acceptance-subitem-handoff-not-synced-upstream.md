# PC-BAL-059: 驗收子項被下游票承接後上游票 acceptance 未同步，使上游無人能合法收尾

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.2.1 |
| 風險等級 | 中 |
| 首次觀察 | 2026-08-28 |

## 症狀

上游 ANA 票的 acceptance 寫成單一條目內含多個以分號並列的子項（AND 語意）。執行過程中其中一個子項被判定不屬本票範圍，改由下游票承接，該裁決被寫入下游票的 `decision_tree_path` 或 Solution。上游票的 acceptance 從未被修訂。

結果是上游票進入無人能合法收尾的狀態：勾選 acceptance 等於宣稱一個未達成的條件成立，不勾選則 `complete` 被 acceptance-gate 阻擋。收尾者面對這個選擇通常兩者皆不做，票停在 `in_progress` 直到被 stale 掃描列出。

實證（2026-08-28）：一張分析派發追蹤缺陷的 ANA 票，其 acceptance 含子項「SubagentStop cleanup 能匹配該記錄」。該票衍生的修復票執行時暴露此子項的成因不在上游範圍（非 worktree 派發的 `tool_response` 無 `agentId`），另衍生一張分析票承接，且承接票的 `decision_tree_path` 明載「修復票的驗收項 2 改為引用本票」。修復票依此裁決完成，承接票亦完成，唯獨最上游的 ANA 票無人處理——票面 acceptance 仍是移交前的原文，停在 `in_progress` 累積 3054 分鐘（約 51 小時）後被 dashboard 列為 stale，並因 registry 無 lease 佐證而需走 reclaim 鑑識才能重新接手。

## 根因

**移交裁決寫在承接方，缺料方是被移交方**。判定「此子項不屬上游範圍」的時點在下游票執行中，執行者手上的票是下游票，寫裁決的自然位置也是下游票。上游票在該時點沒有任何執行體持有——它處於 `in_progress` 但實際無人在動，裁決因此不會傳達回去。

**acceptance 的 AND 結構使部分達成不可表達**。單一條目內多子項並列時，勾選狀態只有全有與全無兩種。子項層級的「已移交」在資料結構上無處可放，只能靠改寫條目文字表達，而改寫需要有人主動意識到該做這件事。

**懸置狀態不產生錯誤訊號**。票停在 `in_progress` 與「正在被處理」在行為上不可區分，唯一訊號是 stale 掃描的時間閾值——那是滯後訊號，且觸發時原始脈絡（誰移交、移交給誰、依據為何）已散落在多張票的不同章節。

## 解決方案

移交發生的當下，由**做出移交裁決的一方**同步修訂上游票的 acceptance 條目，而非只寫在自己的票上：

```bash
ticket track set-acceptance <上游票 id> --edit <index> \
  "<原條目>；<該子項>因<成因>不成立，成因與修復改由 <承接票 id> 承接（依 <裁決出處>）"
```

修訂後上游票的 acceptance 才是可判定的：勾選時宣稱的是「已達成或已合法移交」，不是未達成的原始條件。

收尾方接手懸置的上游票時，處置順序為：

1. 逐一比對 acceptance 子項與實況，確認哪些子項已由下游票承接（查 `spawned_tickets` 與下游票的 `decision_tree_path`）
2. 先修訂 acceptance 反映移交，再勾選，不可跳過修訂直接勾選
3. 在 Solution 或 Completion Info 記錄移交的來源與依據，使後續追溯不需重讀全部下游票

## 預防措施

| 層級 | 措施 |
|------|------|
| 建票 | ANA 的 acceptance 拆成多個獨立條目，一子項一條。AND 語意由「全部勾選才能 complete」承擔，不靠條目內的分號並列 |
| 執行 | 下游票判定某上游驗收子項不屬上游範圍時，同一動作內修訂上游票 acceptance，不只寫在自己票上 |
| 收尾 | 接手 stale 的上游 ANA 票時，先跑 `ticket track deps <id>` 展開衍生鏈，確認是否有子項已被承接，再決定勾選方式 |
| 偵測 | 上游票 `spawned_tickets` 全數 completed 但自身仍 `in_progress` 是本模式的特徵訊號，`ticket track stuck-anas` 已涵蓋此判準 |

## 與既有模式的邊界

| 模式 | 差異 |
|------|------|
| `PC-008` | 該模式的失配在建票當下即存在（套模板的通用條件不適用於本票），屬靜態失配；本模式的失配由執行中的範圍轉移產生，建票當下條件是合理的 |
| `PC-055` | 該模式是 AC 被其他票的行為外溢達成但票未收，方向是「已達成未收」；本模式是子項確定不會由本票達成而移交，方向是「不會達成需改寫」 |
| `PC-017` | 該模式是 ANA 完成但未建衍生 IMP；本模式的衍生票已建齊且已完成，缺的是反向的 acceptance 同步 |

## 觀察來源

2026-08-28 一次 stale 上游 ANA 票的 reclaim 收尾（分析派發追蹤狀態檔從未被寫入的缺陷）。該票的衍生鏈為三層：上游 ANA、修復 PEP 723 依賴的 IMP、承接殘留缺陷的第二張 ANA；移交裁決寫在第三張票，缺料方是第一張。
