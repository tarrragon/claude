# PC-BAL-046: 上游分析結論被後續實驗推翻後，衍生自舊結論的待辦票無回溯重估管道

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 風險等級 | 高 |
| 首次觀察 | 2026-08-18 |

## 症狀

一份分析結論衍生出數張待辦票後，該結論本身被後續實驗推翻或大幅修訂。修訂動作會更新結論的載體（error-pattern 檔案、方法論、規則文件），但已經衍生出去的待辦票停留在舊結論上：票面的 `why` 引用舊主張、`acceptance` 依舊主張設計、Context Bundle 快照舊主張的原文。

這些票在任何清單、排序、儀表板上與其他票沒有形態差異——狀態同為 `pending`，優先級照舊，`blockedBy` 為空，readiness 顯示 `ready`。接手者依既定流程執行，會實作出一個建立在已知為假的前提上的交付物。

實證（2026-08-18）：一次 hook 載入模型的實驗推翻了某 error-pattern 的核心機制主張，該 error-pattern 隨即更新版本；但衍生自其舊主張的一張待辦票（要求「在註冊當下寫待生效標記、由啟動流程宣告本 session 起才生效」）維持 `pending` 且 readiness 為 `ready`。該票若照原樣執行，會對每一個新註冊的守衛顯示一個永不到期的倒數——不是失效，是系統性產出假陳述。此票是靠實驗票的一名審查者主動提出「既有待辦票前提失效」才被撈出重估，不是靠任何機制偵測到。

## 根因

**衍生關係是單向的**。建票工具記錄 `source_ticket` / `spawned_tickets` 雙向欄位，這使「從結論找到衍生票」在技術上可行；但沒有任何時機會去走這條邊。結論被修訂時的自然工作範圍是「改正該結論的載體」與「同步引用該載體的下游文件」，衍生票不在其中——它們是工作項目而非文件，不會出現在引用一致性掃描的結果裡。

**前提失效不改變任何可觀測欄位**。票的狀態機由執行進度驅動（pending / in_progress / completed），沒有一個維度表達「這張票的前提還成不成立」。一張前提已死的票和一張正常待辦票在資料層完全同形，因此排序、篩選、儀表板都無法把它們分開。

**放大因素：一次修訂對多張票**。分析型任務常一次衍生大量票（上述實證中一張實驗票衍生 10 張）。修訂發生時，需要回溯重估的是整個扇出面，而人工重估的觸發完全依賴當事人是否想到這件事。扇出越大，漏網機率越高。

**與相近 pattern 的區別**：

| Pattern | 問題發生時點 | 前提的認識論狀態 |
|---------|------------|----------------|
| PC-BAL-031 | 傳播當下 | 從未驗證，複製時未標記不確定性 |
| ARCH-BAL-018 | 來源到達終態時 | 快照與來源的狀態不同步 |
| 本 pattern | 結論被推翻後 | 建票當下有效，事後被實驗否證 |

三者的防護點不同：PC-BAL-031 要在寫入時標記，ARCH-BAL-018 要在來源終態時失效快照，本 pattern 要在結論修訂時回溯扇出面。

**generic 化**：任何「分析產出結論 → 結論衍生工作項目 → 結論可被後續證據修訂」的系統皆可重現。issue tracker 的 epic 結論變更後其 child issue、RFC 修訂後依 RFC 開的實作 ticket、事故報告結論更新後依報告排的改善項——共同結構是「工作項目繼承了結論的一個時間切片，而結論本身會演化」。

## 解決方案

修訂一份已衍生工作項目的結論時，把「回溯重估扇出面」納入修訂工作本身，而非留給後續發現。

| 步驟 | 動作 |
|------|------|
| 1 | 修訂結論的同時，列出其全部衍生工作項目（`ticket track deps <id>` 或等價的扇出查詢） |
| 2 | 逐張判定：前提是否被本次修訂影響。未受影響者明載「不受影響」，不留空白 |
| 3 | 受影響者依「該票的核心機制在新結論下是否仍可接受」判定 kill / 改寫 / 部分保留，不預設「前提變了就砍」也不預設「有票就做」 |
| 4 | kill 者以 close 記錄（`--reason requirement_vanished` + `--resolved-by <重估票>`）並將逐條對照寫入票面，使未來若結論再變可由記錄逆向定位判斷依據 |

**判定的著力點是機制類型，不是前提真假**。前提失效不必然導致 kill——同一份失效前提下，「開環宣告」（無條件宣稱一個狀態，不觀測）與「提前動作」（做一件在兩種前提下都有益的事，不宣稱任何時點）的處置相反：前者的正確性隨前提翻轉，後者只是收益量級變化。上述實證中三份受影響資產即依此判定為 kill（開環宣告）／只改註解不改行為（rationale 失效但動作仍正確）／完全不動。

## 預防措施

| 層級 | 措施 |
|------|------|
| 流程層 | 分析型結論的修訂工作，其驗收條件包含「扇出面已逐張重估並載明結論」；修訂票與被修訂結論的衍生票之間建立可查詢的關聯 |
| 工具層 | 提供「列出某結論的全部衍生工作項目及其狀態」的單一查詢（本框架的 `ticket track deps` 已具此能力，缺的是修訂時去呼叫它的時機） |
| 偵測層 | 對「結論載體檔案有版本變更、而其衍生票仍為 pending 且建立時間早於該變更」的組合發出提示。此為候選方向，未實作 |

**不建議的方向**：對所有 pending 票定期做前提複查。成本隨票量線性成長，而前提失效是稀疏事件——觸發點應綁在「結論被修訂」這個明確事件上，不是綁在時間上。
