# PC-GPD-029: 代理人終止背景測試後憑記憶回報已終止，實際由它啟動的子程序仍在執行

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 分類 | process-compliance |
| 來源版本 | 0.4.1 |
| 來源事件 | Graph 可維護性 topic 首批並行派發（worktree 內跑全套測試） |
| 首次觀測 | 2026-10-01 |

## 症狀

代理人回報「第一次全套測試卡住，已終止，改用較低並行度重跑」。實際上第一次啟動的測試執行器與它的編譯伺服器子程序在該 worktree 內又空轉約 1.5 小時。

這段期間機器負載長時間偏高（load 50～150），其他代理人在同一台機器上的全套測試因磁碟寫滿失敗一次。失敗本身被當成那張票的問題處理，與殘留程序之間沒有任何訊號連結。

**再現（同日，主線程以 `pgrep` 加程序工作目錄逐一查核）**：另有 5 個殘留的測試程序。其中 2 個屬於一位已回報「舊的測試鏈已清掉」的代理人，分別跑了 2 小時 20 分與 1 小時 22 分；2 個來自一天前的派發，已跑 1.5 天以上；1 個已成孤兒（父程序為 init、工作目錄指向已刪除的 worktree），跑了將近 8 天。範本約束只防得住新派發；既有殘留與孤兒須由主線程主動掃描。

**再現（主線程自身，同日）**：主線程以背景 Bash 跑全套 pytest，之後以 TaskStop 停止該任務，工具回報「Successfully stopped」。以 `pgrep` 查核發現外層 shell、其下的 `uv` 與 `python` 三個程序仍在執行，逐一 SIGTERM 後才退出。可見「終止的對象不是程序樹」不限代理人自己送的 kill，harness 的背景任務停止同樣如此；停止任何背景測試任務後都須以程序清單驗證。

**再現（另一 consumer，逾時包裝來源）**：以 `perl -e 'alarm N; exec @ARGV'` 包住 `flutter test` 做逾時，逾時後 `flutter_tester` 被 launchd 收養並累積，17 個存活 19 至 20 小時。其代理人改以全機 `pkill` 清除，波及其他 worktree 與其他專案。此例沒有任何人送出「終止」：逾時包裝自身就是產生孤兒的來源，終止後自檢不會被觸發。

## 根因

1. **終止的對象與殘留的對象不是同一個程序**。代理人終止的是自己的背景 shell 或工具任務；測試執行器另外啟動的長駐子程序（編譯伺服器、測試隔離程序）不一定隨之結束。「我送出了終止」與「程序樹已全部結束」是兩件事。
2. **回報依據的是記錄平面**。「已終止」是代理人對自己動作的記憶，不是對世界狀態的查詢；代理人在終止後沒有以程序清單驗證，與 `tool-output-trust-rules` 規則 5「重大狀態以世界平面為準」同形。
3. **後果落在別人身上**。殘留程序消耗的是共用機器的 CPU 與磁碟，受害的是並行的其他代理人；造成者自己的任務已改用重跑完成，從它的視角看不到任何異常。
4. **逾時包裝只對單一程序送訊號**。`alarm` 加 `exec`、背景 `sleep` 後 `kill <pid>` 這類寫法，逾時時只終止最上層程序。實驗依據（macOS arm64，以自毀式替身程序與真實 `flutter test` 各測一次，清理只對記下的 PID 或群組編號送訊號）：

   | 做法 | 觀察 |
   |------|------|
   | `alarm` 加 `exec` 包住會產生子程序的命令 | 逾時後子程序存活，父程序變為 1，程序群組編號不變 |
   | 真實 `flutter test` 的程序樹 | fvm、flutter 工具、frontend_server、`flutter_tester` 同屬一個程序群組；只對最上層送訊號時 flutter 工具不隨之結束，測試照常跑完 |
   | 以新程序群組啟動，逾時對整個群組先 TERM 後 KILL | 子程序與巢狀子 shell 內的孫程序皆結束，存活數 0 |
   | Bash 工具逾時 | 不終止命令，只把它移到背景；之後停止該背景任務時，未脫離群組的子程序一併結束 |

   被留下的程序保留原群組編號，故對群組送訊號可涵蓋整串。macOS 預設環境沒有 `timeout`、`gtimeout`、`setsid`，照抄文件中以 `timeout` 開頭的測試命令即失敗，使用者各自改寫成單一程序寫法，這是此來源反覆出現的原因。
5. **清理時改用全機比對**。以測試執行器名稱為樣式的 `pkill -f` 依命令列比對整台機器，必然一併終止其他 worktree 與其他專案的測試；且命令列不一定含專案路徑，改為「限縮成專案路徑樣式」仍會漏比對、也仍波及同專案的其他 worktree。

## 解決方案

1. 以啟動位置定位殘留：`pgrep -fl <worktree 絕對路徑>` 列出命令列含該路徑的程序；必要時以 `lsof -p <pid> | grep cwd` 確認工作目錄。
2. 確認父程序屬於該 worktree 後，先送 SIGTERM，再以同一個 `pgrep` 確認已退出；仍在才升級。並行 session 常跑形狀幾乎相同的測試命令，送訊號前除命令列外，再比對工作目錄（`lsof -a -p <pid> -d cwd`）與啟動時間（`ps -o lstart= -p <pid>`），不以命令列片段單獨認定歸屬。
3. 回報中寫明驗證結果（「`pgrep` 無輸出」），而非「已終止」。

**`pgrep -f` 的比對陷阱**：macOS 的 `pgrep` 預設排除自身與祖先程序，但不排除其他 shell。命令列含有相同樣式字串的其他程序（例如另一個等待迴圈 `until ! pgrep -f "<樣式>"; do sleep 5; done`）會被比對到。實例：兩個等待同一樣式的迴圈互相比對到對方，實際測試早已結束，兩者卻都空等超過 15 小時。查到結果後以 `ps -o command= -p <pid>` 確認命中的是實際測試程序，而不是另一個帶著同樣字串的 shell；等待特定程序結束時，優先等已知 PID（`kill -0 <pid>`）。

## 預防措施

| 層級 | 措施 |
|------|------|
| 啟動方式 | 測試逾時一律經 `python3 .claude/scripts/run-with-timeout.py <秒數> -- <命令>`（新程序群組、逾時對群組先 TERM 後 KILL、結束碼 124），不用 `timeout`、`alarm` 加 `exec` 或背景 `sleep` 後 `kill` 單一 PID |
| 清理 | 以 `python3 .claude/scripts/orphan-test-procs.py` 列出本專案範圍內被收養的測試執行器，以及包裝腳本登記過而包裝腳本已不在的程序群組，確認後加 `--kill`；禁用 `pkill`／`killall` |
| 派發 prompt | 凡要求代理人跑長時間測試，加一條：終止測試後必須以 `pgrep -f <worktree 路徑>` 確認無殘留，結果寫進回報 |
| 驗收 | 收到「終止後重跑」類回報時，主線程以同一命令查一次該 worktree 的殘留程序 |
| 判讀 | 並行環境中出現負載異常、磁碟寫滿等與票內容無關的失敗時，先查各 worktree 的殘留程序，再歸因到失敗的那張票 |
