# PC-BAL-031: ticket why 欄位的未驗證假設經自動抽取機制傳播至衍生票 context

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 風險等級 | 中 |
| 首次觀察 | 2026-08-11 |

## 症狀

建票者在 `why` 欄位陳述問題成因時，把「基於少數案例的歸納」寫成既定前提的句型，例如「檔案重疊是比措辭更穩定的重複訊號」。該句在建票當下有兩個案例支撐，但未經任何量化驗證。

該假設隨後以三條路徑擴散：

| 路徑 | 機制 |
|------|------|
| 同票的 `how.strategy` | 建票者依 `why` 的前提設計策略，策略的方案空間被前提限定 |
| 同票的 `acceptance` | 驗收條件預設前提成立，只驗「怎麼做」不驗「該不該這樣做」 |
| 衍生票的 Context Bundle | ticket CLI 於 `create --source-ticket` 時自動抽取來源票的 `what` / `why` / `where.files` / `acceptance` 寫入新票 Context Bundle |

第三條路徑是本 pattern 與既有 pattern 的區別所在：傳播不經人手，建票者對衍生票的 context 內容沒有逐句決定的機會。

## 根因

`why` 欄位的語意定位是「為什麼要做這張票」，其自然文體是敘述性的因果陳述，而非帶不確定性標記的假設陳述。建票者在此欄位中寫「X 是 Y」比寫「初步觀察顯示 X 可能是 Y，未量化驗證」更符合欄位的寫作慣性。

**放大因素**：`why` 欄位位於 frontmatter，形態上與 `id` / `status` / `where` 等結構化事實欄位並列，繼承了結構化資料的權威外觀。Context Bundle 抽取後，該文字出現在衍生票的「Rationale Chain」小節下，語意上代表「已確立的理由鏈」。

**與 Context Bundle 人工撰寫的差異**：人工撰寫 Context Bundle 時，撰寫者對每一句有標註「已驗證／推測／未知」的機會（PC-BAL-004 的防護即建立於此）。自動抽取沒有這個環節——欄位原文被逐字複製，原文若無不確定性標記，衍生票的 context 就沒有。

**generic 化**：任何「來源物件的自由文字欄位被機械複製到衍生物件」的系統皆可重現——issue tracker 的 description 繼承、需求文件的背景章節引用、API 契約的 rationale 註記。共同結構是「自由文字的認識論狀態不隨複製而標記」。

## 案例

2026-08-11，一張評估「重複偵測是否應納入 `where.files` 重疊維度」的 ANA 票，其 `why` 欄位末句為：「重複偵測現行僅比對標題文字，未納入 where.files 維度，而檔案重疊是比措辭更穩定的重複訊號」。

該句的前半段是可查證的實作事實，後半段是基於兩個案例（一為完全吸收——被吸收票零變更；一為部分吸收——被吸收票仍有共用函式收斂與迴歸測試的實質產出）的歸納。兩者以同一句連接詞串接，讀者無從區分認識論狀態。

該票執行時對當版全量 446 張票做 frontmatter 解析，量測結果：

| 過濾條件 | 命中 pending 票 | 佔比 |
|---|---|---|
| where.files 有交集 | 69 / 95 | 73% |
| 完全涵蓋（子集） | 43 / 95 | 45% |
| 子集 + 吸收方較晚建立 + 吸收方唯一 | 11 / 95 | 12% |

最嚴格條件下逐組比對標題語意，真重複僅 2-3 組，精準度 20-27%。「穩定」成立（不受措辭差異影響——完全吸收案例的兩票措辭完全不同仍被命中），「可作判準」不成立——低精準度源於 `where.files` 粒度，371 個路徑中僅 207 個為單票獨佔，目錄層宣告使「同檔」約等於「同子系統」。

該票原 `how.strategy` 只列出兩條實作落點（納入 create 的重複偵測、或 dashboard 側空轉預警），兩者皆在「偵測」框架內，即前提成立時的方案空間。實驗證偽前提後，透過反向框架（把問題從「如何偵測重複」重寫為「為什麼票被吸收後沒人知道」）才產生第三個介入點——於 `complete` 時由剛讀完程式碼的收尾者判定。該方案不在原方案空間內。

**未實現的後果**：若該票未做量化實驗而直接依原 `why` 結論建立衍生實作票，未驗證假設會經 Context Bundle 原文流入衍生票，實作票的執行者將在「檔案重疊是可靠訊號」的前提下設計偵測強度，而該前提在 45% 的 backlog 上不成立。

## 防護

**建票時：`why` 欄位區分事實與歸納**。同一 `why` 內混用兩類陳述時，以句型標記區分。

| 陳述類型 | 句型 | 例 |
|---|---|---|
| 可查證事實 | 直述 + 取得方式 | 「重複偵測現行僅比對標題文字（相似度模組未讀 where 欄位）」 |
| 未量化歸納 | 明示樣本數與待驗證狀態 | 「兩個案例顯示檔案重疊可能是更穩定的訊號，樣本 n=2，未量化」 |

**ANA 執行時：把 `why` 的歸納句列為待驗證假設**。ANA 票的重現實驗章節應包含「本票 `why` 欄位提出的假設」與「實驗對該假設的判定」。PC-063 要求實驗先於方案，本條補其對象——實驗要驗的不只是「問題是否重現」，也包括「建票者對問題成因的歸納是否成立」。

**衍生票建立時：檢視自動抽取的 Context Bundle**。`create --source-ticket` 後 CLI 會輸出抽取了哪些欄位。若來源票的 `why` 含已被推翻或已被修正的歸納，在衍生票 Problem Analysis 補一段「來源假設的修正」，不依賴衍生票執行者自行察覺 Context Bundle 內容已過期。

**不採取的防護**：不建議在 CLI 層阻擋或改寫 `why` 的抽取。抽取機制本身正確（衍生票需要來源脈絡），問題在原文的認識論標記缺失，應在寫入端解決而非傳播端。
