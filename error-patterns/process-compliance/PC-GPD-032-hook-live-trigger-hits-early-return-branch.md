# PC-GPD-032: hook 實地觸發的命令落在提早返回分支，驗證看似通過卻沒有執行到目標邏輯

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 來源事件 | 同一 session 內兩次 hook 實地觸發驗證，觸發方式都讓 hook 在目標邏輯之前返回 |
| 首次觀測 | 2026-10-14 |

## 症狀

修改 hook 後，以一條觸發命令證明修正已在 runtime 生效。命令執行成功、輸出格式正確，但 hook 根本沒有走到被修改的邏輯。兩個實例：

| 驗證目標 | 觸發方式 | hook 在哪裡返回 | 看到的結果 |
|---------|---------|----------------|-----------|
| 分派器隔離子程序輸出：掃描型 hook 啟動的子程序輸出不能汙染分派器 stdout | `uv run --directory .claude/hooks python hook-dispatcher.py`，payload 為測試命令 | `--directory` 把 cwd 改到 `.claude/hooks`，掃描型 hook 以相對路徑判斷測試檔不存在，掃描前就 return 0 | stdout 是合法 JSON，看起來修正有效；但子程序根本沒啟動，等於沒驗 |
| 測試前 hook 清理逾時殘留的監控檔 | 以背景命令（run_in_background）執行全套件 | 測試前 hook 對背景命令刻意不寫監控檔，也不進入清理 | 殘留數量不變，也沒有新監控檔；若只看「命令沒出錯」會誤判已驗證 |

兩次都是靠「預期的正向副作用沒有出現」才察覺：前者 stderr 沒有掃描結果，後者沒有清理日誌、檔數沒變。改用 `uv run --project`（cwd 不變）與前景單檔測試重跑後，才分別看到掃描結果出現在 stderr，以及「已清理 N 個」的日誌與檔數下降。

## 根因

1. **hook 依輸入或環境提早返回的分支很多**：工具名過濾、命令關鍵字比對、背景命令跳過、相對路徑不存在、cwd 解析出不同的專案根。這些條件散落在 hook 的開頭，驗證者通常只記得被修改的那段邏輯。
2. **觸發命令的選擇以方便為準**：`uv run --directory` 是 Bash 規則一推薦用來避免裸 cd 的寫法，背景執行是長命令的慣用做法。兩者在一般情境都正確，卻剛好改變了 hook 判斷所依賴的環境。
3. **「沒出錯」與「有生效」在輸出上同形**：hook 提早返回時 exit 0、輸出合法，與修正生效時的外觀相同。只看成功與否、或只看輸出格式，無法分辨兩者（與 PC-165「測試綠燈不等於 runtime 正確」同源，差別在這裡連 runtime 觸發本身都沒有打到目標）。

## 解決方案

1. 驗證結果必須包含目標邏輯專屬的正向副作用，例如特定日誌行、檔案數量變化、只有目標路徑才會產生的輸出。找不到這類訊號時，觸發不算數。
2. 發現觸發無效時，在 ticket 的 Test Results 照實記錄無效的那次與原因，再記錄重跑的結果；不要只留下成功的那次。

## 預防措施

1. 設計觸發命令前，先讀 hook 從入口到目標邏輯之間的所有 return，列出觸發命令必須滿足的條件（工具名、命令形態、前景或背景、cwd、相對路徑基準）。
2. hook 依 cwd 或相對路徑判斷時，用 `uv run --project`（只指定環境，cwd 不變）而不是 `uv run --directory`（會切換 cwd）。
3. 驗證測試監控、計時類 hook 時，用前景命令；背景命令在這類 hook 中通常被刻意跳過。
4. 同一次觀察最好同時看到正反兩種結果（例如逾門檻的被清理、門檻內的保留），等同測試的 E2 正向對照（`.claude/rules/core/test-assertion-design-rules.md` 規則 E2）。
