# PC-LLM-052: 守衛行為變更的回報只寫判定機制，沒有逐輸入列出放行與阻擋結果

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 3.5.0 |
| 風險等級 | 高 |
| 首次觀察 | 2026-11-13 |

## 症狀

守衛（hook、gate、檢核器、驗證命令）的判定邏輯被修改後，實作方向審查方或協調方回報變更，回報內容只描述判定機制，例如「判定根改為作用根」「找得到並觸發閘門」「限縮為只查某目錄」。收方依機制描述推斷變更性質（只追加提示、只放寬、只收緊），推斷錯誤，合併前該做的檢查因此沒做。

**識別特徵**：

- 回報或盤點表的「結果」欄寫的是動詞或機制（「觸發」「判定為」「改以 X 為準」「視為舊結構」），不是固定值（allow、deny、exit 0、exit 1、EXIT_BLOCK、只寫日誌）
- 盤點表的輸入由實作方自選，列的是實作方意識到的輸入類別；「缺席」「為空」「讀取失敗」這幾類常常不在表上
- 同一個變更同時含放寬與收緊兩個方向，回報只提其中一個方向，或兩個方向都沒提
- 審查端以輔助函式的 docstring 或註解判斷結果，沒有追到最終輸出 permissionDecision、exit code 或 rc 的位置
- 問題通常在合併後讀程式碼、或端到端實測時才被發現，守衛自己的測試全綠

## 根因分析

### 行為模式

守衛的對外行為只有一組：每個輸入對應一個放行或阻擋的固定值。判定機制是產生這組結果的手段，同一句機制描述可以對應多組不同的結果。回報方寫機制時，等於把「從機制推出每個輸入的結果」這一步交給收方，而收方手上沒有程式碼的完整取值，只能依直覺補上，補錯的方向是隨機的：可能漏報阻擋，也可能誤報阻擋。

放寬類變更另有一個結構性盲點：判定式用 `x or 預設值` 正規化、或用 `any()`／`all()` 對清單求值時，「整段缺席」「設定為空」與「存在但為空」會在判定式裡合流成同一個值。實作方挑的對照輸入只涵蓋自己意識到的類別，合流的那一類就落在表外，而它的結果常常是放行。

### 案例一：判定根改變，兩個方向的結果都翻轉

- 經過：一支禁止裸 cd 的守衛，判定根由環境變數指向的主 checkout 改為作用根（目前所在工作樹的根）。合併前回報寫成「判定改以工作樹為準」，協調方據此判為只追加提示。
- 實際結果：在「環境變數指向主 checkout、cwd 在工作樹」的情境下，兩個方向都翻轉：`cd <工作樹根>` 由 deny 變放行（放寬），`cd <主 checkout 根>` 由放行變 deny（收緊）。收緊這一側影響所有文件中「污染後 cd 回專案根」的指引，合併前應做的文件 grep 沒有做。合併後讀程式碼才發現並更正。
- 審查端的同一實例：協調方在合併前審查時也判為「命中只追加 warning，不阻擋」。依據是只讀到負責找出 cd 目標的輔助函式，它的 docstring 寫「warn 不 deny」；協調方沒有追到主函式對命中的實際處置（deny）。回報端只寫機制，審查端以輔助函式的說明代替最終決策，兩端一起漏掉這次收緊。

### 案例二：盤點表的結果欄仍寫成機制描述

- 經過：另一次變更已要求代理人提交「輸入 × 舊版結果 × 新版結果」盤點表。代理人把一支 UserPromptSubmit 閘門的新版結果寫成「找得到並觸發閘門」，沒有寫出結果是 EXIT_BLOCK（會擋下用戶的 prompt）。PM 讀了程式碼的阻擋分支才發現。
- 與案例一的差異：案例一沒有表；本案例有表，但結果欄仍寫成機制。只要求「列表」不夠，結果欄的值域也要限制。

### 案例三：反方向，誤報阻擋

- 經過：PM 補正案例二時，讀到同一支閘門的 `should_block` 判定式與 EXIT_BLOCK 分支，就回報「新版會擋下 prompt」。協調方讀碼後提出異議，端到端實測新舊兩版的 rc 都是 0：缺少決策樹只會讓 `is_valid` 附提醒，不會讓它變成 False，阻擋分支在該輸入下走不到。
- 意義：讀碼停在分支本身，而沒有追到判定式每個輸入的取值，會得出錯誤結論；方向可以是漏報阻擋（案例一、二），也可以是誤報阻擋（本案例）。

### 案例四：放寬的對照沒有涵蓋「缺席」這一類輸入

- 經過：一個文件驗證命令依裁定方向，把某章節的舊結構由報錯降為提示。合併前回報附了兩項正向對照：新結構漏列項目仍報錯、讀檔失敗落在報錯側；兩項都是實作方自選的輸入，對應測試全綠。
- 發現：協調方逐類列改動前後的結果，發現一類輸入被放寬到裁定範圍外：宣告了來源、但該章節整段不存在。改動前 exit 1，改動後只印「視為舊結構」提示，exit 0。
- 機制：`_extract_section(...) or ""` 把「章節不存在」與「章節存在但為空」合流成空字串，而新判定式正好以「空」作為舊結構的訊號。
- 驗收方的缺口：驗收時核對了測試名稱與結果，沒有逐行讀放寬分支的 diff。測試清單只反映實作方挑的輸入，讀放寬分支本身才看得到 `or ""` 這類合流。

### 案例五：設定清單為空被當成「全部不在範圍內」

- 經過：一個檔名驗證命令放寬為只查某類目錄內的檔案，範圍由設定中的 path pattern 清單決定。盤點表列了實作方想到的四種輸入，對照測試全綠；問題是協調方讀實作才發現的。
- 機制：pattern 清單為空時，建出的 regex 清單也是空的，`any([])` 回 False，該型別的檔案全部被判為「不在範圍內」而跳過，檢查靜默失效。另外 pattern 不含 `/` 時，取目錄片段的索引運算會拋 IndexError，「設定格式不符」這一類也沒有在表上。
- 與案例四的關係：同一類。案例四是 `x or ""` 把缺席與空合流，本案例是空清單經 `any()` 的預設值變成「全部不在範圍內」；兩者都是「設定或區段缺席」被判到放行側，沒有新機制。

## 解決方案

回報守衛行為變更時，附一張盤點表，以輸入為列：

| 輸入類別 | 代表輸入 | 改動前結果 | 改動後結果 | 方向 |
|---------|---------|-----------|-----------|------|
| 存在且合規 | （具體輸入） | allow | allow | 不變 |
| 存在但為空 | | | | 放寬／收緊／不變 |
| 整段缺席或設定為空 | | | | |
| 讀取失敗或格式不符 | | | | |
| （變更動機涉及的其他輸入） | | | | |

- **結果欄只填固定值**：allow、deny、exit 0、exit 1、exit 2、EXIT_BLOCK、exit 0 加提示、只寫日誌。不接受「觸發」「判定為」「改以 X 為準」這類動詞或機制描述。
- **兩個方向都要列**：每列標放寬、收緊或不變。判定根、範圍、比對方式改變時，預設假設兩個方向都可能翻轉，逐列確認。
- **結果以實際 rc／decision 為準**：能實跑就端到端實跑，記錄 rc 或 permissionDecision。只能讀碼時，要追到輸出 permissionDecision 或 exit code 的位置，並追判定式在該輸入下每個子條件的取值；不以中間函式的 docstring、註解或分支存在與否為準。
- **放寬類變更的輸入類別至少四列**：存在且合規、存在但為空、整段缺席或設定為空、讀取失敗。判定式用 `any()`／`all()` 時，在表上寫出空集合時的結果（`any([])` 為 False、`all([])` 為 True），並寫明它落在放行還是阻擋側。用 `x or 預設值` 正規化的位置要特別標出，因為它讓「缺席」與「空」在判定式中無法區分。

## 預防措施

1. **派發與回報範本**：守衛類變更的派發 prompt 與合併前回報範本，要求附上述盤點表，結果欄值域固定。
2. **驗收方自列輸入類別**：放寬類變更由驗收方逐行讀放寬分支的 diff，並自行列出輸入類別，不沿用實作方的測試清單；實作方自選的正向對照只涵蓋實作方意識到的類別。
3. **審查追到最終決策點**：審查守衛變更時，從命中處一路讀到輸出 permissionDecision、exit code 或 rc 的位置；輔助函式的 docstring 只作線索，與最終處置不一致時以最終處置為準，並另行修正 docstring。
4. **收緊方向觸發文件同步**：盤點表出現任何「收緊」列時，合併前 grep 文件中指導使用者執行該輸入的段落，一併更新。

## 與其他模式的關係

- `PC-GPD-033`（放寬守衛只驗證誤擋已解除，未驗證應擋者仍被擋）：該模式談放寬時的測試覆蓋；本模式談變更的回報與審查載體。本模式的盤點表是在回報層把 PC-GPD-033 要求的「應擋者」列出來。
- `PC-GPD-032`（hook 實地觸發落在提早返回分支）：同屬「看到分支存在、沒追到該輸入實際走到哪裡」，案例三是其讀碼版本。
- `test-assertion-design-rules` 規則 E2（守衛的測試必須含正向對照輸入）：本模式案例四、五說明正向對照由實作方自選時，仍會漏掉缺席與空集合兩類。
