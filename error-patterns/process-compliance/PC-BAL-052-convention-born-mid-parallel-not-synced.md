# PC-BAL-052: 技術判準在並行期間誕生，未回頭同步給仍在執行的同批票

## 基本資訊

- **類別**: process-compliance
- **風險等級**: medium
- **發現日期**: 2026-08-22
- **來源版本**: 0.2.1
- **關聯案例**: 2026-08-22 一批兩張並行 DOC 票處理文件中的 hook 呼叫形式，判準於其中一票的驗收回饋中誕生，另一票當時仍在執行、依派發當下資訊選了相反前綴，兩票各自通過驗收而產出矛盾

## 摘要

**PM 驗收並行批次中先完成的票時，若回饋促成了一條新的技術判準，該判準對同批仍在執行的票不可見，各票會就同一技術問題各自決定，產出彼此矛盾。** 判準誕生的時點落在派發之後、其餘票收尾之前，這段窗口內沒有任何機制把新判準推送給已在跑的執行者。

危險之處在於各票單獨看都正確：先完成者依驗收回饋補上判準，後完成者依派發當下可得的資訊做了合理選擇，兩者的 acceptance 都能勾滿。矛盾只在跨票比對時浮現，而 PM 逐票驗收的預設節奏正好不做跨票比對。

## 症狀

- 同批並行票的產出對同一技術對象採用不同處置，且各票的驗收紀錄都完整
- 其中一票的產出內含一條判準，另一票的產出違反該判準，但後者收尾時該判準尚不存在或未送達
- PM 逐票驗收時全部通過，矛盾在後續閱讀、跨檔查證或第三方複核時才被發現
- 追查責任歸屬時找不到違規者——後完成的票在其資訊條件下的選擇是合理的

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 判準的誕生時點不受控 | 判準常在驗收回饋中被提出，而非派發前就備妥 | 派發時無法把尚不存在的判準寫進票面 |
| 並行票之間無共享狀態 | 各執行者只讀自己的票，不讀同批其他票的產出 | 先完成者建立的判準對後完成者不可見 |
| PM 驗收節奏為逐票 | 每票完成即驗收，驗收範圍是該票的 acceptance | 跨票一致性不在任何一次驗收的檢查範圍內 |
| 各票 acceptance 獨立成立 | 判準不在後完成票的 acceptance 內，違反它不影響驗收通過 | 矛盾不觸發任何紅燈 |

## 解決方案

判準誕生當下即推送，不等該票結案：

1. 驗收回饋中提出技術判準時，先確認同批是否有票仍在執行（`ticket track list --status in_progress`）。
2. 有則立即以 SendMessage 把判準送達各該執行者，不等提出判準的那張票完成修正。
3. 送達時說明判準的適用範圍與判定方式，而非只給結論——執行者需能自行判斷手上的檔案是否命中。
4. 已完成且違反該判準的產出，以修正回饋處理，不回退既成工作（quality-baseline 規則 6）。

## 預防措施

1. **並行批次的收尾驗收加一道跨票比對**：逐票驗收確認各票 acceptance，收尾時另比對同批產出對共同技術對象的處置是否一致。共同技術對象指同批多票都會觸及的同一檔案、同一類指令形式、同一組命名或格式慣例。
2. **判準優先寫入共享載體而非單票產出**：判準若適用於同批多票，寫入規則或 reference 層並在各票 Context Bundle 引用，不要只寫進其中一票的產出檔案——寫進單票產出時，其他票沒有理由去讀它。
3. **派發前預判判準缺口**：同批票觸及同一類技術決策（指令前綴、路徑形式、命名慣例）時，派發前先確認該決策是否已有明文判準；沒有則先立判準再派發，不要讓各票各自發明。
4. **驗收回饋視為可能的跨票事件**：PM 給出的每條技術性回饋都要問一句「這條只適用這張票，還是同批其他票也該遵守」。答案是後者時，走上述解決方案的推送流程。

## 案例

2026-08-22，一批兩張並行 DOC 票同時處理文件中的 hook 呼叫形式。

PM 驗收先完成的那張時，發現其改寫把一個佔位符範例寫成 `python3` 前綴，指出該專案 115 支 hook 中 111 支含 PEP 723 依賴宣告、讀者代入自己的 hook 照做會撞 `ModuleNotFoundError`，要求補上選用判準。執行者據此在該檔寫下「檔頭含 `# /// script` 用 `uv run --quiet --script`，純 python 無此區塊才用 `python3`」，並額外驗證判準兩側都有真實成員。

同批另一張票此時仍在執行，其範圍包含另一個檔案中對同一支 hook 的呼叫，該執行者依派發當下可得的資訊選了 `python3` 前綴。兩張票各自完成、各自通過驗收，同一支 PEP 723 hook 在兩份文件中被以不同前綴呼叫。

矛盾在 PM 讀第二張票的完成報告時才浮現。查證發現 `python3` 形式在該機器上**執行成功**（exit=0），追查後確認其依賴來自系統 python3 的既有安裝而非 hook 自帶，換至無該套件的環境即失敗——單次執行成功在依賴類問題上不構成正確性證據。

進一步全域掃描發現此形態早於本批次即存在：14 個文件、22 處以 `python3` 呼叫 hook，其中 6 支目標 hook 含 PEP 723 宣告。並行批次沒有造成這個問題，只是在它的收尾處暴露了它，並且因為判準未同步而又新增了一處。存量部分另立票全域校正。
