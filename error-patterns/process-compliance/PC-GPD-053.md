# PC-GPD-053: 改共用元件時，以「畫面目錄」盤點使用處來決定局部測試範圍，漏掉 App 入口、錯誤處理等目錄外的使用處；影響範圍應以符號引用全庫搜尋

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 風險等級 | 低 |
| 首次觀察 | 2026-10-30 |

## 症狀

修改一個共用元件前，執行者為了決定局部測試範圍去盤點「這個元件用在哪些畫面」，並回報「只用在 X 畫面」。審查方改用符號名對整個 `lib/` 搜尋，結果多找到一處：App 入口在致命錯誤時，也用這個元件取代整個畫面；另外還有一個畫面測試引用了它。那兩處的測試原本都不在局部測試範圍內。

合併閘門會跑全套件，所以這類遺漏最後還是會被抓到。但局部測試的用意，就是在送閘門前把影響範圍內的紅燈先找出來。範圍漏掉的話，問題會被推遲到閘門才爆，修完還得重送。

## 根因

**以目錄慣例代替引用關係**。「元件用在哪」被理解成「哪些畫面用它」，搜尋範圍就自然只落在畫面目錄。但共用元件的使用者不只畫面，App 入口、全域錯誤處理、外框（shell）也都可能用到。

**回報的是推論，不是搜尋結果**。執行者回報時，給的是「只用在 X」這個結論，沒有附上搜尋指令和範圍，審查方也就無從判斷涵蓋得夠不夠。

## 解決方案

- 盤點使用處時，以符號名對整個原始碼目錄搜尋（例如 `grep -rlw <Symbol> lib`），或用程式碼圖譜查呼叫者，不要只搜畫面目錄。
- 對每一處使用，找出覆蓋它的測試檔，再把這些測試檔納入局部測試範圍。
- 回報時附上搜尋指令與命中清單，讓審查方可以直接重跑核對。

## 預防措施

- 局部測試範圍的申請，格式固定為「搜尋指令 + 命中檔案 + 對應測試檔」三欄，不接受只寫結論的「只用在 X」。
- 審查方核准時段前，自己重跑一次全庫符號搜尋，比對命中數是否相同。
