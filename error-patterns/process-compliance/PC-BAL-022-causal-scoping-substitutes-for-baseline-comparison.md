# PC-BAL-022：失敗歸因以因果範圍核對取代 baseline 對照

## 基本資訊

- **Pattern ID**: PC-BAL-022
- **分類**: 流程合規（process-compliance）
- **來源版本**: v0.2.1
- **發現日期**: 2026-08-03
- **風險等級**: 高（同一 session 內連續兩次派發皆發生，且兩次都須由派發者自行重跑才推翻）
- **影響範圍**: 任何「執行者在隔離環境自行驗收」的流程——CI 容器、git worktree、暫時性沙箱、遠端 runner；不限測試，凡以「這是既有狀況」結案的判斷皆適用

## 摘要

**執行者用「失敗項是否落在我的改動範圍內」判定紅燈與自己無關，並據此標為既有問題。該判準只回答「是不是我造成的」，不回答「這是不是新的」，而環境造成的新失敗同時滿足前者為否、後者為是，因此被錯誤歸類。** 唯一能區分兩者的是 baseline 對照：在乾淨基準上跑同一命令看結果。

因果核對只需讀失敗清單並比對檔名，成本近乎為零；baseline 對照須在另一個環境完整重跑一次，成本高一到兩個數量級。成本差距使執行者傾向前者，而前者的結論在措辭上（「與本次變更無關」）完全成立，讀起來像已經查證過，因此不會觸發覆核。

## 症狀

- 執行者回報大量測試失敗，同時聲明「已逐筆核對，無一屬於本次改動的檔案」或「pre-existing unrelated failure」
- 該聲明的因果部分經查為真——失敗檔案確實與改動的檔案無交集
- 但派發者在主環境以**完全相同的命令**重跑，結果為零失敗
- 失敗數與環境特徵相關而非與改動相關：例如執行耗時同時異常膨脹（本案為 4.5 倍），或失敗集中在讀取共用資料的測試（掃描目錄、讀索引檔、列舉檔案）
- 隔離環境內殘留大量非預期檔案，而主環境跑完同一套件後不存在這些檔案
- 執行者無從發現：它看不到主環境的樣子，隔離環境是它唯一的觀測窗口

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 兩個判準被當成同一個 | 因果核對問「失敗是否由我的 diff 引起」；baseline 對照問「失敗是否在乾淨基準上也存在」 | 前者為否不蘊含後者為是。環境造成的新失敗落在這個縫隙裡，兩個判準的答案相反 |
| 成本差距懸殊 | 因果核對讀清單即可；baseline 對照須完整重跑一次 | 在無明文要求時，理性選擇必然是前者 |
| 結論措辭掩蓋方法 | 「與本次變更無關」在因果上完全正確 | 覆核者讀到的是一個為真的陳述，沒有可疑之處，故不會追問方法 |
| 隔離環境是單一觀測窗口 | 執行者只能看到隔離環境內的狀態 | 「這個環境是否正常」對它是不可觀測的，它沒有對照組可用 |
| 隔離的目的與副作用相反 | 隔離用於避免執行者互相干擾 | 但隔離環境自身的污染因此也被隔離，不會被其他執行者或既有流程發現 |

核心是**判準的適用範圍被默認擴大**。因果核對是有效工具，用於排除「我改壞了」；問題在於它被用來回答「這是既有的」，而後者需要的是時間軸上的對照，不是因果上的排除。

## 解決方案

### 立即補救

1. 收到任何「pre-existing」「既有失敗」「與本次變更無關」的結案聲明時，在乾淨基準上以**完全相同的命令**重跑一次。命令必須逐字相同——範圍、旗標、忽略清單任一不同，兩組數字就不可比
2. 比對三個數字而非一個：基準結果、執行者結果、合併後結果。合併後與基準的差額應等於本次新增的測試數，差額對不上即為回歸
3. 若基準為全綠而執行者為紅，檢查隔離環境的殘留檔案（未追蹤檔案清單）與執行耗時，兩者通常同時異常

### 判別準則

| 執行者的陳述 | 是否足以結案 |
|-------------|-------------|
| 「失敗檔案與我的 diff 無交集」 | 否。這是因果核對，未回答是否為新失敗 |
| 「這些是 pre-existing failures」 | 否，除非附上基準環境的實測數字 |
| 「基準跑同命令得 N passed / 0 failed，我這裡 M failed」 | 是。已構成對照，可據以判定為環境問題 |
| 「我用 --ignore 隔離了有問題的子目錄」 | 否。隔離使該子目錄長期無人執行，覆蓋等同關閉且無告警路徑，須另行追蹤 |

### 預防措施

| 措施 | 狀態 | 說明 |
|------|------|------|
| 派發模板要求 baseline 對照而非僅因果核對 | 未落地 | 須在派發指示中明文要求，因成本差距使執行者不會自發採用 |
| 執行者回報格式要求附基準數字 | 未落地 | 「與改動無關」須附對照組，否則視為未驗證 |
| 修復隔離環境的污染來源 | 進行中 | 消除誘因，但不解決判準本身的缺口——污染以外的環境差異仍會落入同一縫隙 |
| 執行耗時異常作為早期訊號 | 未落地 | 本案耗時膨脹 4.5 倍與失敗數同源，且比失敗數更早可見 |

上表刻意標註狀態欄。預防措施若以既存語氣書寫，讀者會誤判防護已覆蓋，而那正是本 pattern 的主題在自身文件中重演。

## 與相關 pattern 的邊界

- `PC-162`（接手者應獨立重新驗證描述的數量與範圍）處理**描述可能過期**；本 pattern 處理**描述當下即不成立**，且不成立的原因是判準選錯而非資訊變動
- `PC-165`（測試綠燈不等於 runtime 正確）處理**綠燈的假陽性**；本 pattern 處理**紅燈的假歸因**，方向相反但同屬「測試結果的解讀失準」
- `ARCH-BAL-003`（名單語意為「該保護誰」時漏列不撞牆）處理**防護靜默失效**；本 pattern 中的 `--ignore` 隔離是其實例——被排除的子目錄從此無人執行且無告警

## 案例

`0.2.1-W3-218` 與 `0.2.1-W3-220` 為同一 session 內連續兩次派發，皆重現：

| 項目 | W3-218 | W3-220 |
|------|--------|--------|
| 執行者回報 | 682 passed / 16 failed | 2532 passed / 137 failed |
| 派發者自跑基準（同命令） | 696 passed / 0 failed | 2661 passed / 0 failed |
| 合併後 | 698 passed / 0 failed | 2671 passed / 0 failed |
| 隔離環境殘留檔案 | 11 個 | 15 個 |
| 耗時對比 | 未量測 | 773.52s vs 172.92s |

兩次的合併後差額（+2、+10）皆等於各自新增的測試數，證實零回歸。兩次執行者的因果判斷皆正確，兩次的「既有」描述皆不成立。第二次的失敗規模是第一次的 8.5 倍，若僅憑第一次的低失敗數估計風險會嚴重低估。

### 同一 pattern 發生在派發者身上（0.2.1-W3-223）

第二次事件中，執行者以 `--ignore=tests/test_checkpoint_state` 隔離一個「疑似掛起」的子目錄，並將該隔離寫入回報。**派發者接受了這個隔離前提，其後三次驗證全部沿用該旗標，未查證隔離在主環境是否必要。** 實測結果為不必要——該子目錄在主環境是 68 passed / 8.76s，完全不掛起；掛起只發生在隔離環境，根因與污染同源。三次驗證因此各少跑 68 個測試。

這使本 pattern 的適用對象擴大：**不只執行者會用因果核對代替對照，覆核者也會用「沿用他人的環境結論」代替自行對照。** 兩者結構相同——都以一個成本低廉且看似合理的判斷，取代了成本較高但唯一有效的實測。

差別在於藉口強度：執行者有環境限制（它看不到主環境，這是真的）；派發者沒有，查證成本只是單獨跑一次該子目錄，不到 9 秒。**藉口越弱，越不容易被自己察覺**——執行者的限制是顯性的、會被寫進回報，派發者的省略是隱性的、不會留下任何痕跡。

推論：凡是從執行者回報中「繼承」下來的環境前提（隔離旗標、跳過清單、已知失敗名單、`--ignore` / `--skip` / `xfail` 標記），都應視為未經驗證的斷言，在主環境各查證一次後才可沿用。
