# PC-BAL-067：沉默有多種成因而其中一種被預設，觀測與工具皆正確但結論超出觀測的射程

## 摘要

**觀測到「零」——零阻擋、零日誌、零命中、空輸出——並將其讀為某個特定成因，而該成因只是多種可能之一。觀測本身正確，觀測工具也正確，錯的是「這個觀測能回答什麼問題」這個未被查證的假設。**

判別此型的關鍵在於三件事同時成立：觀測值真實、取得觀測的工具無缺陷、而被觀測對象的職責範圍未被讀過。前兩型（見邊界）至少有一個環節可被檢查出瑕疵，本型每個環節單獨看都無可指摘。

## 症狀

- 結論建立在一個親手量得、數值精確的「零」上
- 該零被賦予單一成因，而其他成因未被列舉即排除
- 被觀測元件的檔頭、規格或「已知限制」節載有其職責範圍，但未被讀取
- 事後回看，正確的第一步不是重新量測，而是讀該元件在保護什麼／記錄什麼
- 錯誤結論在形式上完全成立——只有前提取自對該元件用途的假設

## 根因

1. **沉默不攜帶成因資訊。** 一個非零值指向某件事發生過，其形態限縮了解釋空間；零不指向任何事，解釋空間由觀測者的預期填補，而預期通常只有一項。
2. **職責範圍寫在對象裡，不在觀測裡。** 日誌、計數、輸出都由元件產生，但「這個元件負責什麼」寫在它的原始碼檔頭或規格，兩者不在同一處，觀測時不會被一併取得。
3. **量測的正確性被誤讀為結論的正確性。** 親手跑出來的精確數字提供強烈的可靠感，該可靠感屬於數字而非推論，但兩者在下結論當下不被分開。

## 防護

| 時機 | 動作 |
|------|------|
| 觀測到零並準備據以下結論 | 先列舉該零的所有可能成因，再讀被觀測元件的職責定義（檔頭 / 規格 / 已知限制節）逐一排除 |
| 觀測對象為防護元件，值為零阻擋 | 確認該防護的射程涵蓋本次情境；「沒擋過」可能是失效，也可能是不在射程內 |
| 觀測對象為日誌，值為零筆 | 確認該元件是否有記錄呼叫；零日誌可能是從未執行，也可能是根本不寫 log |
| 引用他人回報的零值 | 同上，且需額外確認回報者是否讀過該元件的職責定義 |

**檢查問句**：這個零有幾種可能的成因？我讀過這個元件說自己負責什麼嗎？

## 邊界

本型與兩個相鄰模式的分工，依**失效環節**與**處置動作**切分：

| 型 | 失效環節 | 處置 |
|----|---------|------|
| `PC-BAL-066` | 同一產出中查證與猜測並列，可信度自查證側溢出 | 分離產出中的查證與猜測，標明每個數字的來源 |
| `PC-BAL-064` 第三層 | 觀測**工具**的涵蓋範圍未被驗證（判準選了無鑑別力的訊號） | 用已知答案的輸入跑一次，確認工具涵蓋 |
| 本筆 | 觀測**對象**的職責範圍未被查證 | 讀被觀測元件的職責定義，確認觀測落在其射程內 |

**本型的處置無法由另外兩型達成**：分離來源不會揭露前提錯誤（數字確實是查來的）；以已知答案驗證工具也不會（工具沒問題）。

**與 `PC-BAL-066` 的判別**：套用該筆的判別問題「拿掉查證的那部分，錯誤還會不會發生」——本型答案為會。即使把親手量得的數字換成道聽塗說的印象，只要仍假設該元件保護本情境，同一個錯誤結論照樣成立。可信度溢出不是成因，前提從頭到尾獨立且未被檢驗。

## 實例

同一天兩個 consumer 各一次，形狀相同：

| 觀測 | 被預設的成因 | 實際成因 | 揭露方式 |
|------|------------|---------|---------|
| 某分支保護 hook 當日判定數百次、零阻擋，而工作分支為受保護分支 | 該防護失效，所有提交皆未受保護 | 該 hook 檔頭明載僅解析明確指向外部 repo 的命令形式，cwd 隱含形式不解析（理由為 hook 進程看不見工具的持久 cwd）；零阻擋是設計如此 | 對端指出後讀檔頭確認 |
| 某執法型 hook 零日誌落檔 | 該 hook 從未被呼叫 | 該 hook 完全未接日誌工具，logging 呼叫數為 0；零落檔是預期 | 觀測者在下結論前自行查證，屬僥倖非流程 |

第一例的錯誤已對外傳播並據以修改 ticket 的證據段，經對端指正後移除該引用。第二例未致錯，但觀測者自陳「查了才沒錯下去，那是運氣不是流程」——本模式的防護價值正在於把該查證變成必經步驟而非個人警覺。

兩例的共同形狀：**沉默有多種成因，而我們預設了其中一種**。要區分都得離開觀測本身，去讀對象的定義。

## 本筆自身的同構風險（依 `PC-BAL-065` 自指檢查）

本筆的處置是「讀被觀測元件的職責定義」，而缺陷失效的能力是「觀測者在下結論當下沒想到要去讀」。兩者為同一個能力，故依 `PC-BAL-065` 判定，本筆以自律層形式落地時即為它所要修的那類機制的另一個實例。

**已證不足的旁證**：規則層已有涵蓋——`.claude/rules/core/tool-output-trust-rules.md`「規則 5 延伸」明列「測試執行結果」為瞬時平面，並載明「並行環境下對瞬時狀態下持久結論，會據不存在的問題向外傳播」。該檔屬自動載入層，每回合注入 context。同一天兩個獨立實例仍發生：其一為對並行期測試結果下持久結論（該條文在該 session 的 context 內）；其二為整輪以 `| tail` 過濾輸出，而 `bash-tool-usage-rules.md` 的截斷方向條款同樣在 context 內且明寫應改用 `head` 或兩段皆取。**規則在自動載入層不等於被援引。**

**依 `PC-BAL-065` 的 Action**：採納帶同構風險的修法時，須為「角色未被執行」補一個可機械檢查的訊號。本筆的候選訊號為兩個實例共有的文字形狀——**從一個計數為零的觀測，導出一個關於被觀測物是否正常運作的結論**（「零阻擋 → 保護是空的」「零落檔 → 從未執行」）。該形狀比「讀定義」更接近可機械化，但偵測率與誤報面未經驗證，故以分析票先行驗證規模，不直接實作——取樣既有文本標註本模式實例、量測候選樣態的偵測率與誤報率，依結果決定規劃 hook 落點或判定不可機械化並記錄理由。採此路徑而非直接實作偵測，依據 `PC-BAL-065` 第三例先例：判定同構不等於不修，而是先驗證問題規模再決定機制。

在該機械化落點成立之前，本筆的效力僅及於自律層，此限制應被明示而非被本筆的存在所掩蓋。
