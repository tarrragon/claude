# PC-GPD-039: 以臨時文字處理讀取票面結構化欄位，解析失敗的空值與欄位真空同形

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-GPD-039 |
| 類別 | process-compliance |
| 風險等級 | 中 |
| 發現日期 | 2026-10-20 |
| 來源版本 | 0.5.0 |

## 症狀

PM 規劃多條工作線時，要一次看多張票的依賴（`blockedBy`）。它沒有呼叫 ticket CLI，而是自己寫 awk 片段，從票面 frontmatter 擷取這個欄位。

frontmatter 的 `blockedBy` 是 YAML 區塊清單，每個元素各佔一行，以 `- ` 開頭。awk 片段預期的卻是另一種寫法，結果整批票都讀出空值。PM 據此告訴用戶「這幾張票的依賴都是空的」，排出三條平行的線，並派發下去。

其中一條線動工前用 CLI 查證，才發現有三張票仍被未完成的票擋住：一張的前置票分屬另外兩條線，一張必須等同線的前一張完成，一張要等另一張分析票收尾。結果佇列前後重排兩次，用戶拿到的分線依據也有一部分是錯的。

## 根因

| 層 | 原因 |
|----|------|
| 工具選擇 | 結構化欄位已有權威讀取路徑（ticket CLI 的查詢與依賴子命令），PM 卻為了批次查看方便，另寫臨時解析器 |
| 驗證缺失 | 臨時解析器沒有先用一張已知有依賴的票試跑。讀錯時它不報錯，只輸出空值 |
| 輸出同形 | 「解析失敗」和「欄位真的是空的」輸出完全相同，讀者無從分辨。這與守衛只給正常輸入、無法鑑別自身是否失效是同一個結構 |
| 結論外推 | 讀到空值後沒有懷疑。依賴全空本身就是罕見結果，在有父子票、跨主題拆分的票群上更不尋常，卻被直接寫成結論交給用戶 |

## 解決方案

1. 讀取票面結構化欄位（`blockedBy`、`children`、`status`、`who` 等）時，用 ticket CLI 的對應子命令，不自寫解析器。
2. 確實需要批次自寫解析時，先挑一張已知非空的樣本試跑，確認讀得出值，再套用到整批。
3. 批次結果出現「全部為空」「全部相同」這種罕見的整齊分布時，先懷疑解析器，抽一張用 CLI 交叉驗證。

## 預防措施

- 把依賴判斷當成結論寫給用戶或寫進派發訊息之前，至少要有一張票的依賴經 CLI 查證過。
- 規劃派發時，用 CLI 確認每張票的未解除阻擋（例如以依賴子命令逐張查），不以臨時文字處理代替。

## 與其他模式的關係

- 與測試斷言設計規則 E2「守衛的測試必須含正向對照輸入」同源：臨時解析器也是一種判定器，沒有正向對照，就分不出它是在工作還是已經失效。
- 與工具輸出信任規則 3「關鍵事實用無法腦補的固定值交叉驗證」相鄰：本例的工具輸出是真的，但產出它的程式是錯的，所以固定值查證要對準權威路徑，不能對準自寫的程式。

## 實例

2026-10-20，主控 PM 規劃三條產品線時，以 awk 讀取 8 張票的 `blockedBy`，全數讀成空值，並以此作為分線依據。其中一條線動工前查證，發現 3 張票受阻，主控隨即修正佇列，並記錄本模式。
