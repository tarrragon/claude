# PC-BAL-054: 分析票只落地判定不落地逐筆清單，下游票依賴不存在的資料

## 基本資訊

| 項目 | 說明 |
|------|------|
| 分類 | Process Compliance |
| 風險等級 | 高 |
| 來源版本 | v0.2.1 |
| 發現日期 | 2026-08-23 |
| 發現途徑 | 落地票驗收時複驗判定，發現原始判定所本的逐筆清單不存在，需自行重新掃描才能複驗 |

## 症狀

一張 ANA（分析）票對一批可枚舉對象（40 個 skill、235 筆跨界引用）做全量掃描與分類，Solution 章節寫下統計表、逐類判定、與前五大配對範例，票面看起來完整、有數字、有結論。但那 235 筆逐筆清單本身——每一筆的來源檔案、行號、目標路徑——只存在於執行當下的 inline Python 變數，未落地為任何檔案。

同一批次內，三張依賴這份判定的後續票各自撞上不存在的資料：

| 票 | 依賴形態 | 受阻情形 |
|---|---|---|
| 落地票 A | acceptance 要求「以原分析票的清單抽樣複驗」 | 清單不存在，執行者被迫以同一定義重新掃描，得到與原數字不同的另一批筆數（同一定義三次重跑三個不同數字，因語料庫在量測之間持續變動） |
| 落地票 B | how.strategy 寫「取原分析票分出的子集清單」逐一處置 | 清單不存在，PM 加 blockedBy，待落地票 A 補建分類邏輯後重推 |
| 落地票 C | acceptance 要求「對原分析票已分類的樣本跑掃描器複驗」 | 樣本不存在，PM 移除該條目，改以落地票 A 事後產出的抽樣表為 ground truth |

## 根因

### 根因一：分析票的產出物模型混淆「判定」與「資料」

ANA 票的 Solution schema 要求的是結論——分類統計、逐類判定、候選方案比較。逐筆清單只是達成結論過程中的中間產物，在票的產出物模型裡從未被視為需要落地的「產出物」本身。執行者依 schema 字面完成 Solution 撰寫時，票確實「完整」——但完整的是判定，不是判定所本的資料。

### 根因二：量測不可重現使缺口延後到下游才被發現

分析票 complete 當下，驗收只檢查判定文字是否合理、統計表是否對得上敘述，不會去問「支撐這個判定的逐筆對象現在還能不能被重建」。缺口要等到下游票真的需要那份清單時才會暴露，此時已經跨過驗收關卡，回頭補救的成本已轉嫁給下游執行者。

而回頭補救本身還有一層陷阱：語料庫在多次量測之間持續變動（其他工作並行修改被掃描的對象），同一定義重跑三次得到三個不同數字。下游執行者拿到不一致的重跑結果時，無從判斷落差來自「自己算錯」「量測目標真的變了」還是「原始分析本身有誤」——不可重現把「資料遺失」進一步惡化成「資料遺失且無法確認遺失前的真值」。

### 根因三：判定當下「看起來完整」正是缺口不會被攔下的原因

若分析票的 Solution 明顯缺結論（無統計表、無分類），驗收會直接卡住。但本案例的 Solution 是完整的——正因為完整，才沒有觸發任何人去問「這些數字是從哪份清單算出來的，那份清單在哪」。判定完整與資料完整是兩件事，但前者的完整外觀會遮蔽後者的缺席。

## 防護措施

### 逐筆清單落地的強制觸發條件（三條件同時成立才強制）

分析票不是任何情況都要落地逐筆清單——多數 ANA 票的結論不需要，逐一列舉逐筆判定原則上也違反方法論撰寫「不需要窮舉」的精神。只有以下三條件同時成立時，Solution 必須把逐筆清單落地為獨立檔案：

| 條件 | 判準 |
|------|------|
| 1. 判定對象可枚舉且量大 | 分析對象是一組具體項目（檔案、行號、ticket、skill 配對等），且集合大小超出可在 Solution 內文合理列舉的規模（經驗閾值：> 15 筆，與抽樣複驗慣例對齊） |
| 2. 至少一張下游票逐筆依賴 | 下游票的處置動作是「對集合中每一筆分別判斷/處置」（如「33 筆分別轉條件語」），而非「對整批做同質處置」（如「全部套用同一個 flag」，此類不需要清單） |
| 3. 量測結果具時間敏感性 | 判定對象所在的語料庫會因其他並行工作變動，重新量測可能得到不同結果——即「事後可以重跑」不能替代「當下沒有留存」 |

三條件同時成立時，Solution 撰寫流程必須新增一步：把逐筆清單（來源檔案、行號、分類結果三欄最低限度）寫入獨立檔案，路徑建議 `docs/work-logs/v{version}/tickets/artifacts/{ticket-id}-<slug>.csv`（或 `.md` 表格，依下游消費方式選擇：下游需程式化讀取用 csv/json，下游是人工核對用 md 表格），並在 Solution 內文附上該路徑與筆數，供下游直接引用而非重新量測。

### acceptance 寫法：可驗證，不是「應保留清單」

acceptance 條目不可只寫「已保留逐筆清單」——這句話無法被驗收者客觀檢查通過與否。改寫為兩個可獨立驗證的子條件：

1. 「逐筆清單已落地至 `<明確路徑>`，檔案存在且非空」（驗收者可直接 `test -f` 或 `wc -l` 核對）
2. 「清單筆數與 Solution 內文宣稱的統計數字一致」（驗收者可直接比對數字，不需重新量測）

### 分析票驗收時新增一問

ANA 票 complete 前的驗收清單，除既有「判定是否合理」外，補一問：「若判定對象滿足上述三條件，逐筆清單是否已落地，路徑是否已寫入 Solution」。此問只在三條件成立時觸發，不對所有 ANA 票加負擔。

## 與相關模式的邊界

| 模式 | 對象 | 與本模式的關係 |
|------|------|--------------|
| PC-034 | 多步驟流程產出物未落地，跨 session 進度遺失 | 同屬「產出物必須落地」家族的更早期一般化原則；PC-034 談的是流程步驟的輸出格式未定義持久化策略，跨 session 邊界丟失。本模式更窄且不需要跨 session——即使在同一 session 內，分析票的 Solution schema 本就不把逐筆資料視為需要落地的產出物，資料在票 complete 的當下就已經只剩摘要。PC-034 的解法（進度追蹤檔案）不直接適用，本模式需要的是「判定對象滿足三條件時強制落地清單檔案」這個更具體的觸發規則 |
| PC-BAL-053 | 依檔名查證合併型遷移為盲，產出功能缺口假結論 | 同屬「資訊在某個環節遺失，下游據此產出錯誤結論」家族，但遺失的資訊種類不同：該模式遺失的是「新舊檔名的對應關係」，機制是搜尋方法對合併型遷移的盲區；本模式遺失的是「支撐統計判定的逐筆原始資料」，機制是票的產出物模型未涵蓋資料本身 |
| IMP-BAL-012 | 合併多套標記語彙的正則抹除來源，下游清理任務誤傷另一機制 | 同屬上述家族，但該模式的遺失發生在正則合併的語法層（`|` 併集抹除分支來源），本模式的遺失發生在票的產出物範圍界定（Solution 只涵蓋判定，不涵蓋資料）——兩者遺失的環節不同，防護手段也不同（該模式要求複用正則前查組成，本模式要求分析票依三條件觸發落地） |

## 學習要點

- 判定完整不代表資料完整；驗收判定合理性時容易忽略「這個判定所本的逐筆對象還能不能被重建」
- 「事後可以重跑」不能替代「當下沒有留存」——量測目標若隨時間變動，重跑得到的是新的量測結果，不是原始判定的復原
- 逐筆清單不是所有分析票都要留，落地與否應由可枚舉量大 + 下游逐筆依賴 + 量測時間敏感性三條件共同判斷，避免無差別加重每張 ANA 票的負擔
