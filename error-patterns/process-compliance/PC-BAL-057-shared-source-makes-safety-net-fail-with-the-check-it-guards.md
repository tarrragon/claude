# PC-BAL-057：安全網與它保護的判斷共享輸入，於是跟著錯而非攔住

## 基本資訊

- **Pattern ID**: PC-BAL-057
- **分類**: process-compliance（防護機制的獨立性）
- **風險等級**: 高
- **關聯**: [[PC-GPD-002]]（兩個來源共享同一個抽取方法時一致性不是證據；彼處為兩個獨立來源共享量測手段，此處為兩道判斷共享資料來源，同族的兩種形態）、[[PC-BAL-056]]（潛伏缺陷的發現率取決於操作多樣性）、[[IMP-BAL-017]]（訊息指名的抽象層與判準讀取的層不同）、[[PC-BAL-010]]（驗證管道對待驗現象不敏感）

一個判斷可能出錯，於是加一道安全網在它後面攔截。若安全網求值時讀的是與該判斷相同的輸入，則輸入失準時兩者一起失準——安全網不是沒攔住，是得出與被保護判斷一致的錯誤結論，並為它背書。

**Why**：安全網通常在原判斷之後才加，加的人手上已經有一個現成的、格式正確的值（原判斷正在用的那個），直接沿用比另尋來源省事，且在輸入正確的絕大多數情況下兩者結論相同，看不出差別。獨立性因此在實作時被靜默放棄，而放棄的動作不留痕跡——程式碼讀起來是「先判斷、再用另一個方法覆核」，只有追到輸入來源才看得出兩個方法吃的是同一份可疑資料。

更深一層：安全網的存在會降低對原判斷的警覺。設計者知道「就算判錯了還有那道防護」，於是原判斷的邊界條件不再被仔細推敲。**共享輸入使安全網的實際攔截率為零，而它的心理效果照常生效**，淨結果比沒有安全網更差。

**Consequence**：

| 層級 | 影響 |
|------|------|
| 攔截率 | 對「輸入失準」這一整類成因的攔截率恆為零，而該類正是安全網被加上去的理由 |
| 誤導 | 安全網與原判斷結論一致，讀者將其解讀為交叉驗證通過，實際只是同一個錯誤被讀了兩次 |
| 後果放大 | 安全網常掛在破壞性動作前（刪除、覆寫、回退）；它放行時執行的是不可逆操作 |
| 偵測 | 輸入正確時兩者結論相同，測試若只覆蓋正確輸入則永遠綠燈；失準情境多由環境差異產生，不在測試矩陣內 |
| 心理效果 | 安全網的存在使原判斷的邊界條件不再被推敲，形成「有防護」的假象而實際防護為零 |

**Action**：

| 情境 | 做法 |
|------|------|
| 為某判斷加安全網 | 先問「這道網讀的輸入，與被保護的判斷是同一份嗎」。是則它防不了輸入失準這一類，須另尋獨立來源 |
| 判斷獨立性 | 問「若第一個判斷因輸入失準而錯，第二道網會用什麼機制發現」。答案是「它重新讀了一次同樣的東西」即不獨立 |
| 安全網掛在破壞性動作前 | 獨立性要求提高：來源不同、求值路徑不同、失敗模式不同，三者至少滿足前二 |
| 既有安全網稽核 | 從輸入回溯而非從程式碼結構判斷。結構上看是兩個函式，來源上看可能是同一個變數 |
| 撰寫測試 | 必須覆蓋「輸入本身失準」的情境，而非只覆蓋「輸入正確但判斷邏輯有誤」 |

**識別訊號**：安全網的參數由被保護判斷的同一個區域變數傳入；兩者呼叫的底層查詢針對同一個路徑字串；程式碼註解寫「以 X 二次確認」但 X 的輸入來自 Y 而 Y 正是待確認的對象；缺陷回顧時發現「防護有跑，只是它也認為該刪」。

**邊界**：與 `PC-GPD-002`（兩個獨立來源共享抽取方法）為同族兩形態——該模式的共享物是量測手段（兩個來源各自量，但用同一支尺），本模式的共享物是資料來源（兩道判斷各自算，但吃同一份輸入）。共同的判斷方法為同一問：若第一個錯了，第二個會用什麼機制發現。與 `PC-BAL-010`（驗證管道對待驗現象不敏感）的差別：那是單一管道對某屬性沒有分辨力，本模式是兩個管道各自有分辨力但同時瞎。與 `IMP-BAL-017` 的差別在對象——那是訊息與判準的層次落差，本模式是兩個判準之間的獨立性落差。

**實證來源**：`sync-claude-pull.py` 的 `cleanup_stale_files._walk` 以磁碟 dirent 的大小寫字串判斷該路徑是否存在於 `remote_files`，不在即視為 stale；其後的安全網 `_is_git_tracked` 用來確認「已追蹤的檔案不得直接刪除，須移至 `.sync-conflicts/`」。

該安全網以**同一個磁碟大小寫字串**查 `git ls-files --error-unmatch`，而該查詢的 pathspec 比對固定大小寫敏感（實測確認 `core.ignorecase=true` 只影響 checkout / status，對此無效）。磁碟 dirent 的大小寫偏離 git index 時，兩處同時失準：前者誤判為 stale，後者誤判為未追蹤，`item.unlink()` 刪除已追蹤內容。

八組合受控實驗（index × disk × upstream 各大小寫，隔離 fixture repo）得出觸發式：**在 `cleanup_stale_files` 走訪路徑上**，刪除發生若且唯若磁碟大小寫同時偏離 upstream 與本地 index。安全網在該路徑的該參數區間攔截率為零。修復方式為給安全網一條獨立求值路徑（exact match 失敗時改列同目錄的 git 追蹤條目做大小寫不敏感比對），修復後該路徑的八組合皆不再誤刪。

**本實驗未涵蓋的範圍**：窮舉的是三個大小寫軸的**參數**組合，執行的**操作種類**只有一種（走訪式 stale 清理）。同一工具另有一條刪除路徑——delta 套用層把上游的純大小寫改名拆為 delete 與 add 兩個獨立操作，delete 半邊在大小寫不敏感檔案系統上命中本地檔案——該路徑不經過本模式所述安全網，不在本實驗涵蓋內。覆蓋率應以已執行的操作種類計而非參數數量計，判準見 [[PC-BAL-056]]；本檔實證恰為該判準的一個反例。

該類缺陷的存活期特徵見 [[PC-BAL-056]]；本例的具體事實是變更檔名屬罕見操作，故潛伏至某次跨專案同步才被調查。**觸發該次調查的現場症狀（消費端三個檔案消失）走的是哪一條刪除路徑未經確認，故本檔不對該次執行的內部行為作任何斷言**——受控實驗確立的是「該路徑在該參數區間會誤刪」，不是「現場那三個檔案由該路徑刪除」。

**附帶觀察（單一案例，待其他實例驗證）**：本例伴隨一個措辭訊號——原判斷與安全網在程式碼中相鄰且註解明確寫出保護意圖（此例為「移至 `.sync-conflicts`，不靜默刪除」），意圖陳述的存在使審查者確認「這裡有考慮過」而不再追問輸入來源。**意圖越明確，越不會有人去查它是否真的獨立。**

**Action**：稽核安全網時，把「附近有寫明保護意圖的註解」當成**必須追查輸入來源**的訊號，而非已考慮過的證據。意圖陳述說明的是設計者想防什麼，不說明該防護讀的是哪一份資料。
