# PC-SCLK-007: Hook 讀取錯誤的 payload 欄位名，取得空值後走「無事可做」分支而靜默失效

---

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-SCLK-007 |
| 類別 | process-compliance |
| 風險等級 | 高 |
| 首發時間 | 2026-07-31（screen_clock 1.4.0-W2-029 執行 hook 重複註冊比對時附帶發現） |
| 姊妹模式 | PC-165（測試綠燈不等於 runtime 正確）、PC-SCLK-006（規格散文與形式定義矛盾） |

---

## 症狀

事件驅動的處理器（hook、webhook handler、event listener、callback）從輸入 payload 讀取欄位時使用了錯誤的欄位名。該讀取不會拋出例外——字典取值附帶預設值（`get(key, "")`、`get(key, {})`）會回傳空值，處理器接著以空值做判斷，命中「條件不滿足，無事可做」的正常分支並 return。

結果是處理器**從註冊之日起從未執行過任何實際工作**，但外觀與「條件確實未滿足」完全相同：無例外、無錯誤日誌、無退出碼異常。註冊清單顯示它在，健康檢查顯示它可執行，只有它該產生的副作用從未出現——而副作用不出現這件事，沒有人在監看。

---

## 實例（2026-07-31，screen_clock）

Claude Code 的 PostToolUse 事件 payload 中，工具執行結果位於 `tool_response` 欄位。三個 commit 後置 hook 的讀取方式：

| 檔案 | 讀取方式 | 實際行為 |
|------|---------|---------|
| `post-git-commit-hook.py:120` | `input_data.get("tool_response") or {}` | 正確，取得 stdout 後正常運作 |
| `changelog-update-hook.py:126` | `input_data.get("tool_result", {})` | 欄位名錯誤，恆為空 dict |
| `post-commit-fetch-hook.py:37` | `data.get("stdout", "")`（頂層而非巢狀） | 欄位層級錯誤，恆為空字串 |

後兩者取得空值後，其 `is_commit_successful()` 類判斷因 stdout 不含 commit 成功特徵而回傳 False，隨即 return。CHANGELOG 更新檢查與 commit 後背景 fetch 兩項功能，自註冊起未曾實際執行。

**發現路徑具偶然性**：本缺陷並非被任何檢查機制捕獲，而是在處理另一個問題（四個 hook 重複註冊造成 git index.lock 競爭）時，因為必須逐項比對「合併版是否涵蓋被合併版的全部行為」，才在閱讀原始碼時撞見。若當時未設下「比對先於移除」的前置條件、逕行移除註冊，這兩個 hook 會被當作「功能已被合併版接手」而移除，缺陷連同其存在一起消失，永遠不會被記錄。

**外顯訊號的不對稱**：同批重複註冊的第三個 hook（`commit-handoff-hook.py`）讀取欄位正確，因此每次 commit 產生兩份一字不差的提醒——這個雙份輸出被觀察到並觸發了調查。讀錯欄位的兩個反而完全沒有外顯訊號。**能被看見的是重複，不是缺席**。

---

## 根因

| 層次 | 說明 |
|------|------|
| 直接原因 | 欄位名與平台實際 payload 不符（版本演進改名、複製自其他事件類型的處理器、或憑記憶書寫） |
| 為何不報錯 | 帶預設值的字典取值把「鍵不存在」轉換為合法的空值，型別正確、流程繼續，錯誤在此被吸收 |
| 為何空值不觸發告警 | 空值恰好與「條件不滿足」的合法情境同構。處理器無從區分「沒有資料」與「資料顯示不需處理」 |
| 為何長期未被發現 | 監控對象是「處理器是否報錯」，而非「處理器是否產生預期副作用」。不做事的處理器在所有健康檢查中都是健康的 |

---

## 防護

### 實作端：區分「無資料」與「資料顯示無需處理」

payload 必要欄位缺失時，不得與「條件不滿足」共用同一條 return 路徑。

**Why**：兩者在程式流程上都走向「不執行實際工作」，但前者是缺陷、後者是正常運作；共用路徑使兩者在事後無法區分。
**Consequence**：不區分則缺陷被偽裝成正常行為，且因為「正常行為」不需要日誌，連事後追查的材料都不存在。
**Action**：讀取必要欄位時不給預設值（讓 `KeyError` 拋出），或顯式檢查存在性後寫入 warning 日誌再 return。此為 quality-baseline 規則 4「Hook 失敗必須可見」在 payload 解析環節的具體落地——靜默的 no-op 也是一種失敗。

### 驗證端：以副作用而非以退出碼驗收

處理器的驗收條件必須包含「產生了預期的副作用」，不得僅以「執行未報錯」為準。

**Why**：讀錯欄位的處理器退出碼為 0、無例外、無 stderr，任何以退出碼為準的驗收都會判定通過。
**Consequence**：驗收通過而功能未運作，且該處理器會持續出現在註冊清單與健康檢查中，製造「此功能已覆蓋」的假象，直到有人因其他原因閱讀原始碼。
**Action**：新增或修改處理器後，實際觸發一次目標事件，確認其副作用（日誌行、檔案變更、通知輸出）確實出現。副作用不可觀測者，應先為其加入可觀測的日誌再驗收。

### 審查端：合併或移除處理器前，逐項比對行為而非比對宣告

以「某處理器已被合併版取代」為由移除註冊前，必須逐項比對被移除者的每個功能點在合併版中的對應位置。

**Why**：合併宣告寫在 docstring，是作者的意圖陳述，不是行為等價的證明。
**Consequence**：不比對而逕行移除，會使被移除者潛藏的缺陷隨其一併消失，缺陷不被記錄也不被學習；若合併版實際有遺漏，則造成功能靜默消失。
**Action**：比對結果落為書面對應表（被移除者的功能點 → 合併版的對應段落）。發現任一功能點無對應時停止移除、記錄缺口並上報，不得逕自補寫合併版——那會使「移除重複」在無人審查的情況下變成「變更行為」。

## 偵測訊號

| 訊號 | 說明 |
|------|------|
| 處理器存在且註冊正常，但其預期副作用從未被觀察到 | 本模式最直接的訊號，需要主動查找而非等待告警 |
| 同類處理器對同一 payload 使用不同的欄位讀取方式 | 至少有一個是錯的；本案三個 hook 出現三種讀法中的兩種錯誤 |
| payload 讀取普遍帶預設值（`get(key, "")` / `get(key, {})`） | 缺失與空值無法區分，屬本模式的溫床 |
| 事件處理器從其他事件類型複製而來 | 不同事件的 payload 結構通常不同，欄位名易沿用錯誤 |
