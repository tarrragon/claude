# PC-GPD-033: 為減少誤擋而放寬守衛判定，只驗證誤擋已解除，未驗證應擋者仍被擋

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-GPD-033 |
| 類別 | process-compliance |
| 風險等級 | 高 |
| 發現日期 | 2026-10-15 |
| 來源版本 | 0.5.0 |

## 症狀

守衛（hook、gate、檢核器）原本會擋下某些正常輸入。修改者為減少誤擋而放寬判定：加入排除條件、過濾條件、改用更寬的比對、或改寫解析器。修改後的測試證明「原本被誤擋的輸入現在放行了」，全綠合併。之後才發現，放寬的同一個缺口也讓一類**應該被擋的輸入**一起放行，而修改前它們是被擋下的。

**識別特徵**：

- 修改的動機寫的是「誤擋」「多擋」「誤報」，方向是讓守衛少擋
- 新增的測試全部是「應放行」的輸入；沒有任何一個「修改前被擋、修改後仍應被擋」的輸入
- 繞過常出現在放寬條件的邊界：路徑未正規化（`..`、`./`、symlink）、只取第一個目標、只看某幾種寫法而漏看等價寫法（環境變數覆寫、選項旗標）、解析變慢導致 hook 逾時被放行
- 常由事後的安全審查、或他線的端到端比對發現，不是由守衛自己的測試發現

## 根因

守衛的失效方向是放行，而「放行」與「輸入本來就沒問題」在輸出上同形。放寬判定時，修改者的注意力集中在要放行的那一類輸入，驗收自然只覆蓋那一類；守衛原本擋住的範圍沒有被重新列舉，也就沒有被重新驗證。放寬條件寫得越寬（前綴比對、第一個 token、靜態只看字面），越容易把語意等價的應擋寫法一起放過。

與 `test-assertion-design-rules` 規則 E2（守衛測試必須含正向對照）同源：E2 要求「守衛的判準擴充時，同批補一個落在新判準內的該紅輸入」；本模式是其鏡像：**守衛的判準收窄（放寬）時，同批補落在被放寬邊界上的該紅輸入**，否則邊界零覆蓋。

## 解決方案

1. 放寬前列出守衛修改前會擋下的輸入類別（不是只列要放行的那類）。
2. 對每個放寬條件，構造「語意上仍應被擋、但字面落在放寬條件內」的輸入：路徑以 `..`／`./`／symlink 繞回受保護區、多目標只有第一個合法、以環境變數或選項覆寫目標、命令拉長到接近逾時。
3. 用新舊兩版對同一組輸入做端到端比對：找出「新版放行、舊版擋下」的寫法。存在即為回歸，不得合併；屬已接受的殘留須經用戶裁定並寫入殘留文件。
4. 若放寬牽涉解析器，確認最壞情況輸入下的解析時間；hook 逾時即放行時，能被拖慢就能被繞過。

## 預防措施

- 守衛類修改的驗收固定含兩組：應放行組（要解除的誤擋）與應擋組（放寬邊界上的等價寫法），兩組都要有，缺一不得結案。
- 推送後安全審查若標記該守衛（即使只有標題），預設先做新舊版比對，不預設為誤報。
- 同一支守衛第二次被標記時，對該守衛的所有同類寫法做全面最壞情況量測，不只修第一個被指出的入口。

## 案例（2026-10-15，同一天 3 例）

- 裸 commit 守衛改為依派發條目的工作位置過濾並行期：只取第一個 commit 目標、漏看 `GIT_DIR`／`--git-dir` 覆寫，跨 checkout 提交被放行（修改前一律擋下）。
- 驗收 gate 排除「只改 tests」的票：路徑比對未正規化 `..`，`hooks/tests/../<hook 本體>` 被判為只改測試，跳過必含檢查。
- 寫入邊界守衛擴大 sed 辨識的正則：平方級回溯讓長命令拖到 hook 逾時，逾時即放行；第一次修正只修到最先指出的入口，第二次被標記後才全面改為線性解析。

三例都在推送後被只有標題的安全審查標記，並經新舊版端到端比對確認為回歸。協調流程見 `multi-session-orchestration` skill 的 review-flags reference。
