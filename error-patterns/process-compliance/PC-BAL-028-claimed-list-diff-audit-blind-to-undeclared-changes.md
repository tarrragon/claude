# PC-BAL-028: 差集稽核以宣稱清單對帳實際狀態，對「從未宣稱的變更」有結構性盲區

## 分類資訊

| 欄位 | 值 |
|------|-----|
| 類別 | process-compliance |
| 風險等級 | medium |
| 發現時點 | 2026-08-10（flutter_balance 追查 canonical repo pattern 檔遺失時） |
| 關聯 | PC-APP-002（宣稱與實際刪除脫節）、tarrragon/claude#63 |

## 摘要

以「宣稱清單 vs 實際狀態」做差集的稽核法（如 CHANGELOG 宣稱新增 vs HEAD 實際檔案），只能偵測「宣稱過但實際不存在」的遺失；對「新增與刪除都從未被宣稱」的變更，差集兩邊都沒有它，稽核結果呈現乾淨。差集法的覆蓋上界是宣稱清單的完整度——宣稱端缺漏越多，稽核越樂觀。完整偵測需改以事實層自身對帳（git 歷史 `diff-filter=A` 全量新增 vs HEAD 存在性），宣稱清單只能當輔助軸。

## 症狀

- 差集稽核回報 MISSING 數遠小於實際遺失數，且被漏掉的項目共同特徵是「新增當時的 commit 未寫入宣稱載體」（隨手 commit、訊息空泛如 "--help"）。
- 稽核結論「共 N 筆缺漏」被下游當作完整清單引用，補救動作只覆蓋 N 筆，其餘遺失延續。

## 根因

差集法隱含前提：「所有值得追蹤的變更都會出現在宣稱清單」。此前提在宣稱靠人工紀律維護（CHANGELOG、commit 訊息、發布說明）時必然有破口——恰恰是最不守紀律的變更（未寫宣稱的新增、未宣告的刪除）最可能同時是問題變更。稽核工具與被稽核對象共享同一個失效來源（人工宣稱），形成相關失效而非獨立驗證。

## 實證（2026-08-10，canonical repo pattern 檔遺失追查）

canonical 框架 repo 以 CHANGELOG「新增 PC-xxx」清單（89 筆）對比 HEAD 檔案，差集僅抓到 2 筆缺漏；實際上同一個未宣告刪除的 commit 掃掉的共有 5 檔——其中 3 檔新增當時的 commit（訊息僅 "--help"）未寫 CHANGELOG 宣稱，於是「新增無記錄、刪除無記錄」，差集雙盲。改以 `git log --all --name-status --diff-filter=A/D` 對帳才得出完整 5 筆遺失清單。完整案情見 tarrragon/claude#63。

## 防護

| 步驟 | 動作 | 目的 |
|------|------|------|
| 1 | 遺失類稽核以事實層自身對帳為主軸：`git log --all --diff-filter=A` 全量新增清單 vs HEAD 存在性 | 覆蓋不依賴宣稱紀律 |
| 2 | 宣稱清單差集降為輔助軸，並在結論顯性標註「本法對無宣稱變更為盲區」 | 防止下游把差集結果當完整清單 |
| 3 | 稽核報告列出「宣稱覆蓋率」（有宣稱的新增數 / git 實際新增數） | 量化盲區大小，覆蓋率低時強制改用步驟 1 |

**Why**：差集的偵測域是兩清單的對稱差，落在兩清單之外的變更在數學上不可見；宣稱清單靠人工維護時，缺漏與問題變更高度相關。

**Consequence**：把差集結果當完整遺失清單，補救只覆蓋被宣稱過的部分，未宣稱的遺失延續多輪且稽核蓋章「已全量查核」，反而提高後續發現成本。

**Action**：做「宣稱 vs 實際」類稽核時，先問「不在宣稱清單裡的變更會被誰抓到」；答案是「沒有人」就必須補一條以事實層（git 歷史、檔案系統掃描）為基準的獨立對帳軸。
