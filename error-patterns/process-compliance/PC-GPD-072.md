# PC-GPD-072：送出成功不等於對方收到

## 基本資訊

| 項目 | 內容 |
|------|------|
| Pattern ID | PC-GPD-072 |
| 分類 | process-compliance（多 session 協調的派工確認） |
| 風險等級 | 中 |
| 來源版本 | 0.6.0 |
| 首次觀測 | 2026-11-02 |
| 關聯 | [[PC-GPD-070]]（同屬「把動作送出當成動作已生效」） |

## 摘要

**主控以跨 session 訊息同時指派多條線時，訊息工具回報送出成功，只代表訊息進了對方的收件匣，不代表對方的模型讀到或開始執行。** 對方 session 可能在等它自己的用戶核准、在其他權限模式下保留訊息，或一直閒置沒有接收。主控若不追蹤每一條線是否回覆，這條線的工作就會停住，直到別的現象（看板、用戶提問）暴露出來。

## 症狀

- 主控同一輪傳訊指派四條線，四則都回報送出成功。
- 其中三條線在幾分鐘內回覆並開工，第四條線始終閒置，指派的票維持 pending。
- 主控持續處理另外三條線的回報，約 50 分鐘後用戶問起看板異常，才發現第四條線從未開工；而這條線負責的正是修看板的票。

## 根因

- 訊息工具的成功回報與「對方已開工」語意不同，主控把前者當成後者。
- 有回報的線會不斷占用主控的注意力，沉默的線不會產生任何事件，主控也就不會想到它。
- 沉默的成因不只一種，首例的實際成因是對方 session 的工具輸出整段失效（所有工具回傳空白，包含 `echo`）：對方其實讀到了訊息，卻讀不到票，也發不出回報，從外部看起來和沒收到一樣。所以主控追蹤的對象要定在「有沒有回覆」，不能只檢查「訊息是否送達」。

## 防護

| 情境 | 做法 |
|------|------|
| 傳訊指派一條線 | 指派時加 `notify_when_idle`，或在下一輪主控接續時，逐條核對各線是否已回覆收到 |
| 某條線在其他線都已回覆後仍沒有回覆 | 查該 session 狀態（ListAgents 的 idle／busy）與佇列第一張票的狀態；仍是 idle 且票為 pending，就請用戶到該 session 確認是否有卡在核准的訊息 |
| 紀錄指派 | 協調票的指派紀錄只寫「已傳訊」，等對方回覆後才寫「已開工」 |

## 檢查問句

每輪處理回報之前問：上一輪指派的每一條線，都回覆過了嗎？沒回覆的那條，它的票有沒有動？
