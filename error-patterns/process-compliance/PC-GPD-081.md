# PC-GPD-081：裁定落到規格，沒有落到實作

## 基本資訊

| 項目 | 內容 |
|------|------|
| Pattern ID | PC-GPD-081 |
| 分類 | process-compliance（裁定的落地完整性） |
| 風險等級 | 中（功能缺口不會讓測試紅，只能靠盤點發現） |
| 來源版本 | 0.6.0 |
| 首次觀測 | 2026-11-04 |
| 關聯 | [[PC-GPD-075]]（規格與實作被契約綁在一起時要同批；本則是規格先行，實作沒有承接） |

## 摘要

**用戶對畫面行為的裁定，由規格追修票寫進規格之後，如果沒有同時建實作票，這個裁定就只存在於規格裡。** 規格票的驗收只看規格是否寫對，結票後沒有任何東西會提醒「程式還沒做」。測試也不會紅，因為新狀態從來沒有被實作，也就沒有對應的測試。

## 症狀

- 規格寫了某個畫面狀態與它的 i18n key，lib 裡完全沒有使用這些 key。
- 查遍當前版本的票，找不到任何實作票承接這個裁定。
- 首例是在另一張票盤點 key 表與 ARB 的差集時才發現，距離規格追修已經過了一段時間。

## 根因

1. **規格票的驗收只涵蓋規格。** 「規格已寫入」就達成驗收，票可以合法結案。
2. **裁定的去向沒有清點。** 一次裁定常同時需要規格與實作兩種產出，但只有規格這一份有建票。
3. **缺口沒有訊號。** 沒有實作就沒有測試，main 照樣全綠。

## 防護

| 情境 | 做法 |
|------|------|
| 用戶的裁定會改變畫面行為或新增狀態 | 建規格追修票時，同批建實作票（blockedBy 規格票），或在規格票的驗收列一條「實作票已建立：<ID>」 |
| 規格票結案前 | 對新增或改動的狀態與 key，`grep` lib 確認有沒有使用；沒有的話，確認已有承接的實作票 |
| 盤點時發現規格有、程式沒有 | 先查有沒有承接的票，再判斷是待實作，還是規格寫錯 |

## 檢查問句

規格追修票結案前問：這次寫進規格的行為，是哪一張票負責實作？答不出票號，就先建票。

## 實例

- 2026-11-04，一個 Flutter 專案在評估契約測試改用集合比對時，取 key 表與 ARB 的差集，發現規格中節點詳情的兩個狀態與 3 個 key 在 lib 中完全沒有使用。這兩個狀態是用戶先前的裁定，由一張規格追修票寫入規格，當時沒有建實作票。事後補建實作票承接。
