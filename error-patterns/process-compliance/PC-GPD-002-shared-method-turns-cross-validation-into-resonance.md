# PC-GPD-002：共享方法使交叉驗證退化為共振

## 核心主張

兩份獨立取得的結果一致，通常被當作正確的擔保。**該推論只在兩者的取得方法真的不同時成立。** 若兩者共享同一個抽取方法、同一個判斷依據、或同一個輸入來源，一致性不提供任何額外資訊——它們會同時錯，而且錯得完全一樣，因此連「不一致」這個唯一的警示訊號也不會出現。

交叉驗證的價值來自獨立性，不是來自次數。**重跑一次共享方法，得到的是共振而不是驗證。**

## 症狀

| 表現 | 讀者當下的感受 |
|------|---------------|
| 文件記載的值與後續獨立量測一致 | 「兩邊對上了，可信」 |
| 兩者皆遺漏同一批資料，或皆包含同一個不存在的項目 | 無異狀——遺漏的東西不會自己現身，而多出來的項目落在合理範圍內 |
| 安全網與它要保護的判斷同時失效 | 「有防護」——防護存在，只是跟著錯 |

## 兩種形態

| 形態 | 共享的是 | 後果 |
|------|---------|------|
| 獨立來源共享方法 | 抽取／量測手段 | 兩份記錄互相印證，而兩者皆偏離現實同一個方向 |
| 兩道判斷共享輸入 | 資料來源 | 安全網不是沒攔住，是與被保護的判斷同時失準 |

## 案例一：獨立來源共享抽取方法

一份設計規格記載 artboard 的字級分佈為 `{10, 11, 12, 13, 14, 15, 19}`。後續實作票的執行者**未採信文件、獨立重新量測**，得到 `{9, 10, 11, 12, 13, 14, 15, 19}`——與規格幾乎相同，多一個 9。兩份記錄互相印證，實作據此建立四階尺度與原始值映射表。

覆核時以容許小數的字元類重量：

```
9    → 0 次        ← 兩邊都記了這個不存在的值
9.5  → 4 次
10.5 → 58 次       ← 全設計最高頻字級，兩邊都漏
11.5 → 55 次       ← 次高頻，兩邊都漏
12.5 → 30 次
```

根因是雙方都用 `[0-9]+`（只抓整數）而非 `[0-9.]+`。**該字元類對每一個半像素值產生完全相同的變形**：`10.5` 被切成 `10` 與 `5`，兩者都落在既有值域因此毫無異狀；`9.5` 被切出的 `9` 則成為一個看似合理的新值。

所以兩次量測的一致不是巧合，是**同一個 regex 對同一批輸入必然給出同一個錯誤**。獨立重量這個正確動作，因為方法相同而失去全部鑑別力。

## 案例二：兩道判斷共享輸入

一支同步腳本的清理邏輯以**磁碟目錄項的大小寫**判斷檔案是否為上游已移除的殘留。其安全網（避免刪除仍被追蹤的檔案）以**同一個磁碟大小寫字串**查詢版控索引，而該查詢的路徑比對固定大小寫敏感。

磁碟大小寫偏離索引時，主判斷誤判為殘留，安全網同步查詢失敗而誤判為未追蹤，已追蹤內容被刪除。

**安全網不是沒攔住，是跟著錯。** 兩道判斷共用同一個可能失準的來源，因此不存在任何一道能獨立發現另一道的錯誤。

> **本案例的證據範圍**（2026-08-28 補）：上述機制由受控實驗確立——在隔離 fixture 上窮舉三個大小寫軸的組合，該路徑於特定參數區間必然誤刪。**該實驗確立的是「這條路徑在這個參數區間會誤刪」，不是「觸發調查的那次現場刪除來自這條路徑」。** 後續查證顯示該次現場刪除實際走的是另一條路徑（三方合併的 rename delta），該路徑不經過本案例所述的安全網。
>
> 兩件事分開陳述的理由正是本模式自身：**若把受控實驗的結論直接套到現場事件，就是拿一個為回答 A 而設計的驗證去回答 B**——而在只有一條已知刪除路徑時，A 與 B 的答案集合完全重合，看不出是兩個問題。此點的完整論述見他專案的 `PC-BAL-058`（本庫無副本）：某類別只有一個已知成員時，問題的範圍無法被觀察，答案自動繼承提問的範圍。

## 根因

| 層 | 內容 |
|----|------|
| 表層 | 一致性被當作正確性的擔保 |
| 中層 | 「獨立」被理解為「不同的人／不同的時間／不同的執行體」，而真正決定獨立性的是**方法與輸入** |
| 深層 | 共享方法產生的錯誤具有一致性，而一致性正是我們用來偵測錯誤的訊號。**偵測手段與缺陷的表現形式重合，於是缺陷取得了偵測手段的外觀** |

**Why**：交叉驗證的效力來自「兩條路徑的錯誤不相關」這個前提。前提不成立時，第二次量測的資訊量為零，但它產生的信心增量不為零——付出了成本、提高了信心、沒有增加任何保障。

**Consequence**：比單次量測更危險。單次量測留有「這只查過一次」的自覺；兩次一致會關閉後續查證的動機，且該關閉發生在正確的動作之後（確實重量了），因此不會被流程審查捕捉。案例一中，執行者做對了「不採信文件、自己重量」，結果反而強化了錯誤。

**Action**：見下節。

## 判斷標準

宣稱「兩個來源一致所以可信」之前，問一個問題：

> **如果第一個來源錯了，第二個來源會用什麼機制發現？**

答得出具體機制（不同的抽取工具、不同的資料來源、不同的判斷依據）→ 獨立性成立。
答不出，或答案是「它重跑了一次」→ 不獨立，一致性不構成證據。

## 防護措施

| 措施 | 做法 |
|------|------|
| 覆核時換方法而非換人 | 重新量測的價值來自方法差異。要驗一個 regex 的結果，就別再用 regex——改用逐值計數、改用不同的解析器、改用不同的粒度 |
| 安全網不得與被保護判斷共用輸入 | 若主判斷讀 A、安全網也讀 A，安全網只在 A 正確時有效，而 A 正確時本來就不需要它 |
| 對「兩邊一致」保持與「只有一邊」同等的懷疑 | 一致性不降低查證需求，除非能說明兩條路徑的錯誤為何不相關 |
| 抽取類量測先驗字元類 | 見下 |

```bash
# 抽取數值前，先確認字元類不會靜默切開資料
# 反例：[0-9]+ 對 "10.5px" 產生 10 與 5，兩者都可能落在合理值域
grep -ohE 'font-size: *[0-9.]+px' <files> | grep -oE '[0-9.]+' | sort -n | uniq -c
```

**逐值計數（`uniq -c`）比集合列舉（`sort -u`）有鑑別力**——前者會讓「某個值出現 58 次卻不在文件裡」變得顯眼，後者只給出一個集合，缺項不產生任何訊號。

## 為何這類缺陷特別不容易被審查發現

**意圖陳述的存在會抑制對獨立性的追問。**

案例二的安全網旁寫著明確的設計意圖（「移至衝突區，不靜默刪除」）。審查者讀到它，確認「這裡有考慮過」，於是停止追問——**而該追問正是唯一能發現它讀錯輸入的動作**。

**Why**：審查在有限時間內尋找的是「有沒有想到」，而意圖陳述直接回答了這個問題。它回答得越明確、越像深思熟慮的產物，越能終止該處的檢視。**意圖的清晰度與實作的正確性無關，但前者會被當成後者的證據。**

**Consequence**：防護措施比無防護措施更難稽核——無防護處會被標記為缺口，有防護處會被標記為已處理，而「已處理但處理錯了」不在任何一類。案例二的安全網存在了整段開發期，每次審查都經過它，沒有一次查它讀的是哪一份輸入。

**Action**：讀到防護措施旁的意圖陳述時，把它當成「需要驗證的宣稱」而非「已完成的驗證」。具體追問一句：**這道防護讀的輸入，與它要保護的判斷讀的是同一份嗎？** 是同一份即命中本族模式，與意圖寫得多好無關。
