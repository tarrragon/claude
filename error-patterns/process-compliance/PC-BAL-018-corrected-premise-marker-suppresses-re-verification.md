# PC-BAL-018：「前提已更正」標記使後手停止驗證

## 基本資訊

- **Pattern ID**: PC-BAL-018
- **分類**: 流程合規（process-compliance）
- **來源版本**: v0.2.1
- **發現日期**: 2026-07-31
- **風險等級**: 高（錯誤更正推翻已執行決策，衍生的執行票方向與既有票相反）
- **影響範圍**: 任何帶有「前提已更正」「已修正」「經覆核」等前手宣告的 ticket、分析報告或規則文件

## 摘要

**ticket 的 `why` 欄被前手標上「【前提已更正】」，後手讀到該標記後接受「前提已由他人處理」，不再驗證更正本身是否正確。** 更正若是錯的，它反而比原始錯誤更難被發現——原始前提會被質疑，已標記為「更正過」的前提不會。

關鍵在於這不是後手偷懶。更正標記是一個**可信度訊號**，它的功能就是告訴讀者「這裡已經有人想過了」。後手據此把注意力分配到別處，是該標記設計上要達成的效果。問題在於標記本身不帶任何佐證——誰更正的、依據什麼、驗證過嗎，一概不載。讀者收到的是結論的權威感，卻拿不到產生該權威感的證據。

## 症狀

- ticket 的 `why` 或 `strategy` 以「【前提已更正】」「原前提錯誤」「經覆核修正為」開頭，後續分析全部建立在該更正之上
- 後手的分析方法嚴謹、證據層級自覺良好、推論顯性化，但結論與同 repo 內一個月前已執行並 commit 的決策正面矛盾
- 矛盾未被承認——後手不是反駁了既有決策，是不知道它存在
- 衍生的執行票與既有 pending 票方向相反，兩者同時存在，執行結果取決於誰先跑
- 事後查證只需一條 `git log --grep <關鍵字>` 即命中決定性證據

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 更正標記承載權威但不承載證據 | 「已更正」是結論，標記格式不要求附查證方法或依據 | 讀者無從評估更正的可信度，只能全盤接受或全盤重查 |
| 重查成本與接受成本不對稱 | 接受是零成本；重查要重建前手的調查範圍 | 預設行為必然是接受 |
| 更正動作本身缺少驗證關卡 | 修改 `why` 欄不觸發任何 hook 或審查 | 錯誤更正與正確更正在系統中無法區分 |
| 調查範圍未涵蓋 repo 歷史 | Context Bundle 從來源票繼承語意脈絡，不含關鍵字的 git 歷史查詢 | 已執行的相反決策對後手不可見 |

**為何比原始錯誤更危險**：原始前提是一個待查證的宣稱，讀者的預設態度是懷疑。標記為「已更正」的前提是一個已結案的宣稱，讀者的預設態度是信任。錯誤一旦通過更正這道程序，就從「待驗證」升級為「已驗證」，而這個升級沒有經過任何實際驗證。

## 案例：W3-159 的兩角色判定（2026-07-31）

`0.2.1-W3-159` 的 `why` 欄被前手改寫為：

    【前提已更正】原前提為「0.2.1-W3-133 的 integration-patterns 改名未傳播至
    claude-skills.git」，該前提錯誤。實測兩者為不同產物非同一內容改名⋯⋯

PM 接手後依此展開分析，判定兩個目錄是「兩個角色而非新舊名」，並據此建立三張執行票，其中一張要求把某 consumer 的目錄名還原。

多視角審查的架構視角指出矛盾，逐項查證後確認：

| 查證 | 結果 |
|------|------|
| `git log -1 --format="%s%n%b" 644ad2c` | 訊息明寫「integration-patterns 是 project-integration 的**前身**」，已刪 8 檔、改 11 處引用 |
| `git show --stat --name-status 6e830d33 \| grep "^R"` | 8 筆 **R100** 改名標記，內容 100% 相同 |
| 兩 commit 時間差 | 7 分鐘，屬同一次跨專案收斂 |
| 跨專案清點 | 五個專案一律只有新名，無任一持有舊名 |

原始前提是正確的。那句「該前提錯誤」才是錯的。而 PM 從未對關鍵字做過 repo 歷史查詢——一條 `git log --grep integration-patterns` 即會命中決定性證據。

損害：據錯誤判定建立的還原票與既有 pending 票方向相反，執行後該 consumer 會成為生態中唯一持有舊名者，重現原決策明文註記的風險。該票已關閉。

## 解決方案

### 對更正者

修改既有 ticket 的 `why` / `strategy` 前提時，更正內容須同時載明三項，缺一即視為未完成更正：

| 項目 | 內容 |
|------|------|
| 查證方法 | 具體指令或檔案路徑行號，使後手可獨立重現 |
| 查證範圍 | 查了什麼、**沒查什麼**。後者尤其重要——它標示出更正的效力邊界 |
| 既有決策檢索 | 對關鍵字做過的 repo 歷史查詢及其結果（含「查了但無命中」） |

### 對後手

看到前提更正標記時，把它讀成「這裡曾有爭議」而非「這裡已經沒問題」。爭議點正是最需要獨立查證的位置，因為前手已在此投注過判斷，其結論的錯誤會被後續所有工作繼承。

最低查證動作是一條關鍵字的歷史檢索：

    git log --grep <關鍵字> --oneline
    git log -S <關鍵字> --oneline

命中任何已執行決策時，必須顯式裁決自己的結論與它孰是孰非，不可繞過。

### 對審查

分析結論與既有已執行決策矛盾時，這是阻擋級發現，不是可討論的意見分歧。「兩張票各自成立、互不知情」是比任何一方錯誤都糟的狀態——它讓兩個方向相反的執行票同時 pending，結果取決於執行順序而非判斷。

## 預防措施

| 時機 | 檢查 |
|------|------|
| 認領帶有更正標記的 ticket | 更正是否附查證方法與範圍？無附註即視為未驗證宣稱，須自行查證 |
| ANA 開始調查前 | 對核心關鍵字執行 `git log --grep` 與 `git log -S`，結果寫入 Test Results |
| 建立執行票前 | 檢索同關鍵字的既有 pending 票，確認方向不衝突 |
| 多視角審查派發時 | 明列「本結論是否與既有已執行決策矛盾」為必查項 |

**與 `PC-162` 的邊界**：PC-162 要求接手者獨立重新驗證前手記錄的數量與範圍，對象是**事實資料**（幾處、哪些檔案）。本模式的對象是**判斷結論**（前提對不對），且該結論已被標記為經過更正。前者驗證的是計數是否漂移，後者驗證的是一個宣稱已完成的驗證是否真的完成過。

**與 `ARCH-BAL-005` 的關係**：後者描述豁免理由無消費者而退化為裝飾文字；本模式描述更正標記有消費者，但消費者只讀結論不讀依據——因為依據根本沒被要求寫下來。兩者都是「權威感與證據脫鉤」，方向相反。
