# PC-GPD-010: 編輯使用中的工具，危險窗口是「還沒改完」而非「改壞了」

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 來源版本 | 0.1.0 |

## 症狀

多個執行體（session / agent）共用同一支框架 CLI（如 `ticket` / `doc` / `worktree`）時，若有人正在編輯該 CLI 的原始碼，其他執行體在編輯到一半的瞬間呼叫該 CLI，會拿到與自己操作內容無關的 `SyntaxError` / `ImportError`。這類失敗不重現（下次呼叫就正常），且症狀與呼叫者當下在做的事毫無關聯，容易被誤判為環境問題或偶發抖動而被忽略，不會被追查到「有人正在編輯這支 CLI」這個真正的根因。

## 根因

Python 在每次 CLI 呼叫時 import 原始碼執行，所以「有人正在編輯 CLI 原始檔」與「有人正在呼叫該 CLI」是同一份資源的讀寫競爭。編輯器寫入檔案不是原子操作——從第一個位元組落盤到儲存完成之間，檔案可能處於語法不完整的中間狀態；任何一次 import 落在這個窗口，就會得到與檔案「最終改壞或改對」都無關的錯誤。

**這與「改壞了」是兩種性質完全不同的失效**，混為一談會讓危險性判斷失準：

| 維度 | 改壞了（邏輯錯誤） | 還沒改完（讀寫競爭） |
|------|--------------------|----------------------|
| 持續時間 | 一直壞到修好 | 只有寫入到寫入完成之間的幾百毫秒 |
| 失效方式 | 邏輯錯誤，與改動內容相關 | `SyntaxError` / `ImportError`，與改動內容**無關** |
| 被發現機率 | 高——穩定重現，下次呼叫依然壞 | 低——不重現，下次跑就好了 |
| 事後歸因 | 可行——症狀指向改動邏輯 | 幾乎不可行——症狀與改動內容無關聯，難以聯想到「有人正在編輯這支 CLI」 |

**排程依據是有無執行體正在呼叫，而非有無他人正在編輯。** 「同儕也在編輯同一支 CLI」不是危險訊號本身——兩個人各自看著自己的編輯器互不干擾。真正的危險訊號是「這個檔案會不會在我編輯的這一刻被別的行程載入執行」，即編輯窗口與呼叫窗口是否重疊。只確認「有沒有人在改」而不確認「有沒有人在跑」，會漏掉真正的風險來源，也會對無風險的並行編輯過度謹慎。

## 代價不對稱（本則的重點，不是機率）

窗口短、機率低——若只論機率，結論會是「可以忽略」。真正該排序的理由是**落點**：呼叫失敗可能發生在代理人的收尾階段（`complete` / `set-exit-status`），那是整條路徑上最難重來的位置——工作已全部做完、卡在最後一步，而失敗原因與代理人自己做的事完全無關，無法靠重跑自己的邏輯排除。低機率乘以高代價（工作報廢或需要額外一輪排查才能定位真正根因），值得為它主動排序，而非用「機率低」帶過。

## 適用邊界

本則管的是**被多個執行體即時呼叫的工具**——本框架的 `ticket` / `doc` / `worktree` 等 CLI、hook 腳本，凡是「呼叫當下會 import 執行原始碼」且「可能同時有多個執行體在呼叫」的資源。

**一般產品程式碼的編輯不適用**：它們不會在編輯當下被別的 session import 執行（例如應用程式的業務邏輯檔案，只在建置或啟動時載入，不會被另一個並行 session 即時呼叫）。判準是單一問題：「這個檔案會不會在我編輯的這一刻被別的行程載入執行？」答案為否，本則不適用。

## 案例

某次修改本框架 `ticket` CLI 其中一個子命令的實作原始檔時，同時有三個 session 共用該 CLI，另兩個 session 各有代理人正在跑 `claim` / `append-log` / `complete`。PM 排序這次修改的派發時機時，判斷依據是「另兩個 session 是否有執行體正在呼叫這支 CLI」，而非「另兩個 session 是否也在編輯它」——因此把這次修改排到那些代理人收工之後才進行。兩個 session 事後交換確認，皆認定此判準具一般性，值得固化為 error-pattern。

## 處置

- 編輯共用 CLI 原始碼前，先確認是否有執行體正在活躍呼叫該 CLI（而非確認是否有人也在編輯它）。
- 若有執行體正在呼叫，且對方即將進入收尾步驟（`complete` / `set-exit-status` 等難以重來的動作），優先排到其收工之後再編輯。
- 若排程無法延後，明確告知並行 session／代理人暫停呼叫該 CLI，待修改完成後再恢復。
- 修改完成並確認語法正確（如 `python3 -m py_compile <file>` 或直接跑一次該 CLI）後，才視為安全可恢復呼叫。
