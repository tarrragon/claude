# PC-GPD-058: 判斷合併閘門會跑哪些測試時只讀專案宣告檔；宣告只取代內建的 Flutter 對應，.claude/ 路徑的內建對應仍然生效，審查得出「閘門不跑任何測試」的錯誤結論

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 風險等級 | 低 |
| 首次觀察 | 2026-10-30 |

## 症狀

一條線要合併只改 `.claude/skills/<skill>/` 的分支，合併前查閘門範圍：讀專案的 `merge-gate.yaml`，所有 suite 的 prefixes 與 files 都不涵蓋該路徑，於是在票面寫「合併時閘門不會跑任何測試」。主控以同一份檔案複驗，同意這個結論。

實際合併時，閘門跑了 hooks pytest（數千筆）。結論是錯的，兩方都只讀了宣告檔。

## 根因

**閘門範圍的定義分在兩處**。worktree skill 的〈合併前全套件〉對應表定義內建對應：`.claude/` 各路徑固定跑 hooks pytest 等套件；專案宣告檔只「取代內建 Flutter 對應」。兩者疊加才是閘門的實際範圍。只讀宣告檔，等於只讀了一半。

**宣告檔看起來像完整清單**。宣告檔列出所有 suite 與 prefixes，形狀是一份完整的對應表，讀者不會想到還有另一份。

**複驗者用同一份來源**。複驗用的是同一份檔案，只能抓到抄錯，抓不到來源本身不完整（PC-166 的固定值交叉驗證，前提是固定值的來源本身是權威）。

## 解決方案

- 判斷閘門範圍時，兩份都要讀：worktree skill 的內建對應表（`.claude/` 路徑），加上專案宣告檔（取代內建 Flutter 對應的部分）。
- 最直接的做法是讀閘門程式本身的判斷結果：在 worktree 內以閘門的 dry-run 或選擇邏輯列出這次會跑的 suite，不用人工比對兩份文件。

## 預防措施

- 審查清單中「這次會不會跑閘門、跑哪些」一項，答案來源寫成「閘門程式的選擇結果」，不寫「merge-gate.yaml」。
- 框架方向：閘門提供一個只列出選中 suite、不執行的模式，讓派工與審查直接取用；屬框架修補，依修補節奏先觀測。
