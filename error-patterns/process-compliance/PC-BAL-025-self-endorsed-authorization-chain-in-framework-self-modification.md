# PC-BAL-025: 框架防護變更的授權鏈同源自我背書，用戶選擇發生在結論已寫進選項之後

## 摘要

**當同一決策者完成「分析 → 建票 → 寫選項 → 派發」全鏈，用戶的授權動作（在 AskUserQuestion 選了某個選項）發生在該決策者已把結論寫進選項標題之後，這個授權是對既成結論的追認，不是獨立檢驗。** 削弱框架防護能力的變更若只憑這種授權鏈通過，等於決策者自我背書。

危險之處在於授權「形式上存在」：ticket 有建、選項有列、用戶有選、流程全合規。事後審查看到完整的授權紀錄，容易判定變更經過用戶同意而放行。但選項空間由分析者框定，選項標題已內嵌其結論（如「降級為 advisory」），用戶在此框架內的選擇無法補足分析本身缺乏的獨立檢驗——分析若有錯誤前提，錯誤會原封不動地穿過整條授權鏈。

## 症狀

- 框架防護能力的增減變更（守衛出口強度、hook 註冊、enforcement 等級）追溯授權來源時，分析、建票、選項設計、派發皆出自同一決策者
- AskUserQuestion 的選項標題直接寫結論動作（「降級為 X」「移除 Y」），而非中性描述待決事項
- 執行系統對變更發出削弱守衛類安全警告，但因存在選項層級授權而判定模糊——警告說無授權過嚴，說有充分授權又不符實情
- 變更的論證引用某份分析作為依據，該分析與變更決策同源，全程無第二視角檢驗
- 事後獨立重評（WRAP、多視角）發現原分析含未證立前提（如把「本 hook 的 exit 2 實作壞了」誤述為「exit 2 是錯的出口」），而該前提在原授權鏈中無人質疑

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 授權檢查只驗形式存在 | 有 ticket、有選項、有用戶選擇即視為已授權 | 授權的獨立性（誰框定選項、結論何時寫入）不在檢查範圍 |
| 選項空間由分析者框定 | 決策者寫選項時結論已定，選項標題即結論 | 用戶的選擇被收窄為「同意或換一個我列的」，無從觸及分析前提 |
| 單人專案無天然第二視角 | 分析者、建票者、派發者是同一 session 的同一角色 | 自我背書是預設路徑，獨立檢驗需刻意引入 |
| 分析錯誤沿授權鏈無衰減傳遞 | 用戶依選項標題判斷，不重跑分析 | 錯誤前提獲得「用戶已同意」的合法性外衣，事後更難翻案 |
| 安全警告判準二元化 | 警告只分「有授權 / 無授權」 | 對「有形式授權但同源自我背書」的中間態無法表達，判定模糊反而削弱警告可信度 |

**與 PC-053（PM 對小修改跳過 Ticket）的邊界**：PC-053 管「有沒有 ticket」——框架修改必須建 ticket 追蹤，違規形態是跳過流程。本 pattern 管「ticket 內容的授權效力」——ticket 存在且流程合規，但其內容（分析、選項）與變更決策同源，授權鏈缺乏獨立檢驗。PC-053 合規是本 pattern 的前提：先有 ticket，才談 ticket 承載的授權是否自我背書。

**與 PC-V1-006（規則變更未盤點既有規則矛盾）的邊界**：PC-V1-006 是變更內容與既有規則衝突未被盤點；本 pattern 的變更內容可以完全無矛盾，缺陷在授權程序的獨立性。

## 案例：品質閘 hook 降級的授權鏈全程同源（2026-08-07）

某專案 commit `5aef790`（0.2.1-W3-045）將 `ticket-quality-gate-hook` 的 enforcement 從 exit 2 阻擋降為恆定 exit 0。降級論證來自 0.2.1-W3-031 的分析；該分析、W3-045 的建票、AskUserQuestion 選項設計（標題含「降級為 advisory」）、派發，皆由同一決策者完成。用戶在選項層級授權了降級，但選擇發生在結論已寫進選項標題之後。

執行系統發出 Self Modification 安全警告：「削弱守衛且無明確用戶授權（ticket 描述不構成授權）」。後續獨立重評（0.2.1-W3-049 WRAP）逐項核對後判定：警告說「無授權」過嚴——選項層級授權確實存在；但警告指出的結構問題成立——授權鏈為「我分析 → 我建票 → 我寫選項 → 用戶選 → 我派發 → agent 執行」，屬同一決策者自我背書。

重評同時發現原分析含未證立前提：降級論證寫「exit 2 是錯的出口」，實情是「本 hook 的 exit 2 路徑 stderr 恆為 0 bytes（實作壞了）」——exit 2 機制本身是 CC runtime 設計中的回饋通道，修好 stderr 即可運作。此前提錯誤在原授權鏈中全程無人質疑，直到事後獨立重評才被揭出。

## 防護

| 時機 | 動作 |
|------|------|
| 框架防護能力增減類變更（守衛出口、hook 註冊、enforcement 等級）需用戶授權時 | 選項標題中性描述動作與後果（「將 X hook 出口改為恆不阻擋，保留提示」），不寫結論式標籤（「降級為 advisory」）；分析依據以路徑引用附於 description，讓用戶可核 |
| 無法引入獨立審查者的單人專案 | 對此類變更以完整 WRAP（含反向框架、最強版本論證）替代第二視角，且結論定位為「向用戶呈報的評估」而非逕自定案；WRAP 產出與變更決策至少分屬不同 ticket |
| 安全警告與選項層級授權衝突時 | 不以「有授權」一筆勾銷警告；逐項核對警告主張，區分「授權形式存在」與「授權鏈獨立性」兩個問題（參照 tool-output-trust-rules 規則 6 的逐項核對精神） |
| 審查歷史變更的授權效力時 | 追問三件事：選項由誰框定？結論何時寫入選項？分析與決策是否同源？三者皆指向同一決策者即命中本 pattern，變更應補獨立重評 |
