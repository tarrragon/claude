# PC-LLM-056: 執行者另寫的步驟清單漏列驗收項，須在不可逆節點前完成者到 complete 才被擋

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 3.6.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-11-25 |

## 症狀

一張票的 acceptance 有多項，其中一項必須在某個不可逆節點之前完成（例如版本凍結、發版、合併、對外發佈）。執行者為了排程，在 Solution 另寫一份自己的執行順序（「1. 交裁定 2. 建票 3. 截斷 4. 凍結 5. 結案」），之後照這份順序推進。這份順序漏列了那一項驗收。

執行者照順序走過不可逆節點，沒有任何訊號提醒。acceptance 的原文一字未改，所以沒有人「收窄」範圍，也沒有改寫紀錄可查。缺口要到 complete 時，acceptance 閘門逐項檢查勾選狀態才浮現；那時不可逆節點已經過了，該項只能事後補做，而事後補做的結果若要改變已凍結（已發佈、已合併）的內容，就得走例外路徑。

**識別特徵**：

- Solution 有一份執行者自寫的步驟清單（「執行順序」「收尾步驟」「整合流程」），項目數少於 acceptance，或兩者的項目無法一一對應
- 漏掉的那一項，內容是審查或查證（「逐一寫明理由」「確認無遺漏」），不產生步驟清單上看得到的產物
- 漏掉的那一項有隱含時效：它的結論會影響不可逆節點的內容，但 acceptance 的措辭沒有寫出「在 X 之前」
- 不可逆節點之前的檢查只看步驟清單，不回頭對 acceptance

**實證**（2026-11-25，版本規劃期的主題 ANA 票）：acceptance 四項，第 3 項是「open framework issue 中拖慢專案標記達 2 則者逐一寫明選入或不選的理由」。主控在 Solution 寫了五步的凍結整合執行順序（裁定、建落地票、維護截斷、凍結程序、結案），第 3 項不在其中。凍結照順序完成，complete 時閘門以「acceptance 未全勾」擋下，主控才補審。補審結果是唯一達標的 issue 不選入，凍結範圍不必改；若結論是要選入，就得走凍結後改範圍的例外路徑。

## 根因分析

1. **執行者以衍生清單取代 acceptance 作為行動依據**。acceptance 是驗收的權威，但它通常按「要交付什麼」列，不按「什麼時候做」排。需要排程時，執行者自寫一份按時序排的清單，之後只看這份清單。清單是從 acceptance 衍生的，衍生時漏項不會留下痕跡，因為 acceptance 本身沒被改動。PC-GPD-044 與 PC-BAL-034 的缺口都留在 acceptance 的改寫上，本模式的缺口留在 acceptance 之外的另一個載體，所以比對 acceptance 的歷史也找不到。
2. **審查類項目在步驟清單上沒有自然的位置**。建票、截斷、凍結各自產生可見的產物（票、scope_blocker、todolist 欄位），寫步驟清單時會被想到。「逐一寫明理由」只產生一段文字，沒有命令、沒有產物，排程時最容易被略過。
3. **時效沒有寫進 acceptance，閘門只有一個檢查點**。acceptance 閘門在 complete 時逐項檢查勾選狀態。對沒有時效的項目，這個時點足夠；對須在不可逆節點前完成的項目，complete 晚於該節點，閘門擋下時已無法在原時點補做。不可逆節點本身（凍結程序、發版流程）沒有回頭核對 acceptance 的步驟。

## 解決方案

事後發現時：

- 立即補做漏掉的項目，並在 Solution 寫明「本項應在 X 之前完成，漏在 X 之後才補」。
- 補做的結論若要改變不可逆節點已定的內容，走該節點既有的例外路徑（凍結後改範圍、發版後的維護版），不回退節點本身。回退已凍結或已發佈的節點，成本高於走例外路徑，也會牽動已依該節點行動的下游。
- 補做的結論不需改變內容時，照常勾選並結案，更正說明保留在票面。

## 預防措施

- **步驟清單逐項標注對應的 acceptance**。執行者自寫的執行順序，每一步寫出它滿足哪一項 acceptance；寫完後反查一次，每一項 acceptance 都要出現在某一步。沒有對應步驟的 acceptance 項，補一步或寫明在哪一步一併處理。
- **不可逆節點之前加一道 acceptance 對照**。在凍結、發版、合併、對外發佈這類節點的程序中，第一步是重讀觸發它的票的 acceptance，逐項確認：已完成、不受本節點影響、或結論會改變本節點內容而必須先完成。第三類未完成就不進入節點。
- **有時效的驗收項把時效寫進措辭**。建票時若某項的結論會影響後續的不可逆節點，acceptance 寫成「在 X 之前……」，讓步驟清單的撰寫者與節點程序的執行者都看得到。

## 與其他模式的關係

本模式與下列兩則同屬「驗收項在執行中掉落，到收尾才浮現」，差別有兩點：掉落發生在 acceptance 之外的步驟清單，比對 acceptance 的改寫紀錄查不到；漏掉的項目必須在不可逆節點前完成，而唯一的檢查點在節點之後。

- `PC-GPD-044`（子票改寫自己的 acceptance 時無聲收窄）：該模式發生在跨票承接（父票的 acceptance 拆給子票），子票改寫了 acceptance 本身。本模式在單一票內，acceptance 原文不變。
- `PC-BAL-034`（派發前注入的新 context 取代既有 acceptance）：該模式是外部注入的方向取代 acceptance，最後 acceptance 被換掉，比對改寫紀錄查得到。本模式是執行者自己的排程取代 acceptance 作為行動依據，acceptance 沒被動過。兩者的最終狀態都具備完成的外觀。
