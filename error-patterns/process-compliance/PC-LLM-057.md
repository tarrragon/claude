# PC-LLM-057: 手寫固定格式行的錯處被解析器靜默吸收，只在下游以假狀態出現

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 3.6.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-11-25 |

## 症狀

人或代理人在票面、日誌等文件裡手寫一行給程式解析的固定格式文字（狀態標記、佇列行、待辦行）。格式只差一點：分隔符用錯、標記字面裡夾了附註。解析器沒有報錯，而是用最寬鬆的方式解讀：把讀不懂的部分當成附註，或整行略過。寫入當下沒有任何提示，下游的看板或狀態查詢照常輸出，但內容是錯的。

**識別特徵**：

- 下游出現與事實不符的狀態，例如已解除的等待仍被列出、還有票的佇列被判為「已完成」，而且不只一條線同時出現
- 寫入的那一行用肉眼看格式「差不多對」，差異在分隔符、括號位置、粗體範圍這類細節
- 同一位寫入者重複犯同一個錯，因為第一次寫錯時沒有回饋，之後照同樣寫法繼續寫
- 解析器的設計原則是「不認得就當附註」或「只認行首字面」，本意是容錯，避免一個筆誤讓整份文件解析失敗

**實證**（2026-11-25，多 session 協調票）：

| 行 | 寫錯的地方 | 解析結果 | 下游表現 |
|----|-----------|---------|---------|
| 等待解除行 | 日期寫進粗體標記內（`**等用戶解除（日期）**：`） | 只認行首字面，整行略過 | 兩張已解除的票持續被列為「等用戶」 |
| 現行佇列行 | 票與票之間用「、」，格式只認 `→`、`∥` | 第一張票之後全部當成附註 | 三條還有票的線同時被判為「佇列已完成未收線」 |

佇列行的錯從規劃期就開始，寫入者寫了十幾次都沒有回饋，直到三條線同時出現假過期項才被發現。

## 根因

1. **容錯的方向選成「吸收」而不是「標出」**。解析器遇到不認得的內容，選擇當成附註或略過，讓整體繼續運作。這對「讀者是人」的文件合理，但這些行的讀者是程式，吸收之後產出的是錯誤狀態，而不是部分正確的狀態。
2. **寫入端與解析端分離，寫入當下沒有驗證**。行是用一般的追加日誌命令寫入的，該命令不知道內容是哪一種固定格式行，不做格式檢查。寫入後的檢查 hook 只檢查特定項目（例如待辦行有沒有完成行），沒有檢查格式本身。
3. **格式規格與寫入者的記憶分離**。格式寫在 skill 的參考文件裡，寫入者憑印象手寫；「、」是中文列舉的自然寫法，與規格要求的箭頭不同，寫入者不會意識到這是格式錯誤。

## 解決方案

發現下游狀態與事實不符時：

- 先懷疑寫入的那一行的格式，對照解析器實際接受的字面（讀解析程式的常數或測試案例），不要只對照文件中的說明。
- 改正寫法後重新查詢下游狀態，確認假狀態消失。
- 同一寫入者過去寫的同類行一併檢查，因為沒有回饋的錯誤通常會重複出現。

## 預防措施

- **解析器把「疑似寫錯」標成可見的過期項**：附註裡出現票號、標記字面附近有近似寫法時，不是靜默吸收，而是列為「格式不合規」，讓寫入者在下一次查詢時就看到。
- **寫入後的檢查 hook 涵蓋格式本身**：hook 已在每次寫入後執行，順便以同一套解析判定格式；解析結果與寫入意圖明顯不符（一行寫了多張票、解析出一張）就提示。
- **高頻固定格式行改用專用 CLI 寫入**：符合制式化內容生成的三條件（固定 schema、多個寫入者、已有錯誤紀錄）時，由 CLI 組出格式，寫入者只提供語意值。
- **解析案例放進共用測試資料，並含「容易寫錯」的正向對照**：讓解析器的每一種容錯行為都有對應的「應標出」案例。

## 與其他模式的關係

- `structured-content-generation` 原則（`.claude/rules/core/structured-content-generation.md`）：本模式是該原則第 3 層（事後檢查）缺席、第 1 層（CLI 制式化）尚未建立時的典型失效。
