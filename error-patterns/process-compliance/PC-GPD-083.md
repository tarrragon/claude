# PC-GPD-083：方案比較要先查每個方案依賴的承載處是否存在

## 基本資訊

| 項目 | 內容 |
|------|------|
| Pattern ID | PC-GPD-083 |
| 分類 | process-compliance（方案分析與裁定交付） |
| 風險等級 | 中（不會讓錯誤進 main，但會讓用戶的裁定不完整，需要第二輪裁定，且第二輪的選項會改變第一輪方案的代價） |
| 來源版本 | 0.6.0 |
| 首次觀測 | 2026-11-04 |
| 關聯 | [[PC-GPD-081]] |

## 摘要

**交給用戶裁定的方案表，每個方案的「新增面」欄位必須先查過它依賴的承載處（畫面、設定入口、元件、資料欄位、平台能力）在現況中是否存在。** 承載處不存在時，要把「新建承載處」列為該方案的代價，並把承載處的位置一起列為待裁定項。否則用戶會依一個被低估的代價做出選擇，裁定之後才浮現第二個要裁定的問題。

## 症狀

- 分析票的方案表寫「新增面：設定頁一列」這類增量描述，好像承載處已經存在。
- 用戶依方案表選定方案後，PM 建規格票時才發現承載處不存在，必須回頭請用戶再裁定承載處的位置。
- 第二輪裁定的結果（例如新建一個畫面）會讓原方案的代價明顯變大，回頭看，第一輪的比較其實建立在錯的前提上。

## 根因

1. **方案分析只比方案彼此的差異，沒有比對現況。** 方案表列的是「A 比 C 多出什麼」，沒有列「A 需要現況中已經有什麼」。增量描述天然預設了承載處存在。
2. **PM 派發前的盤點只核對票面引用的規格，沒有核對方案會用到的規格。** 盤點的對象是票面 why 提到的條文是否仍成立；方案依賴的承載處要等方案出現後才知道，所以不在盤點清單內。
3. **代理人與 PM 讀到的都是同一份增量描述。** 規格中寫明承載處不存在的條文（例如「App 無設定畫面可承載入口」）位在另一個章節，兩方都沒有以方案依賴的名詞去搜尋。

## 解決方案

方案已裁定、承載處缺口才浮現時：

1. 把原裁定記為已解決，承載處缺口另列為新的待裁定項，不要自行替用戶選承載處。
2. 新的待裁定項附上候選位置與各自的代價，並註明它會改變原方案的代價，讓用戶判斷是否要重新評估原方案。
3. 規格票先建立、暫不派發，等承載處裁定後再開工；規格票的範圍納入新建承載處的狀態列。

## 預防措施

- **分析票的方案表加一欄「依賴的承載處／現況是否存在」**，每一列以名詞到規格與程式碼中搜尋一次（例：`grep -rn "設定頁\|設定畫面" docs/spec lib/screens`），並寫出搜尋結果。
- **派發方案分析類 ANA 時，在 prompt 寫明要查方案依賴的承載處是否存在**，不存在時列為代價與待裁定項。
- **PM 收到方案表時，對每個「新增面」的名詞做一次存在性搜尋**，再轉交用戶裁定。

## 實例

- 2026-11-04，一個 Flutter 桌面專案分析「破洞項開啟原始檔並定位至行號」的方案。方案 A 寫「新增面：一個設定鍵、設定頁一列」。用戶依此選定方案 A 後，PM 建規格票時發現規格寫明「App 無設定畫面可承載入口」、程式也沒有設定畫面，只好請用戶再裁定設定入口要放在選單列偏好設定、導覽列新頁，或其他位置。
- 2026-11-04，同一個專案的同一張票，在實機驗證時又出現一次，這次是執行能力不存在。主控把「由線用 computer-use 驅動 GUI」列為選項交給用戶裁定，用戶選了之後，那條線的 session 才發現自己沒有桌面版 computer-use 工具，只有瀏覽器工具。結果用戶得再裁定一次，改成先結案、另開實機驗證票。預防方式相同：把「由某 session 用某工具做」列成選項之前，先請該 session 用 ToolSearch 確認工具存在。
- 2026-11-04，同一個專案的另一張分析票出現了相反方向的情況。方案表把「維持現狀＋規格補明文」寫成「零畫面變更、靜默」，但沒有查現況實際顯示什麼。主控做 WRAP 反向思考時發現，在這個現況下，格式寫錯的宣告會在狀態行被計成「未宣告」，等於向使用者顯示錯誤的原因。用戶因此改選新增的方案。預防方式：「維持現狀」也是一個方案，同樣要寫出現況在這個情境下的實際輸出。
- 2026-11-04，同一個專案的另一張分析票，把「交上游新增邊型」一案的代價寫成「新開 issue 需逐次授權、落地慢」，前提是上游由別人維護。主控轉交前查證，發現本專案就是框架主控方，而且已有在本專案直接修改 schema 的前例，所以這項代價不成立。主控補正後才交給用戶裁定。代價被高估跟被低估一樣，都會讓比較失準；預防方式是把每一項代價依據的權限與承載處都查證一次。
