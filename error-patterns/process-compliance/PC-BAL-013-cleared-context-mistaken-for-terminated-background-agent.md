# PC-BAL-013: 主線程 context 中斷被當成背景代理人已終止，據以重派造成雙寫入者

## 症狀

主線程 context 中斷（`/clear`、session 崩潰、compact 後派發記錄未留存）後，對中斷前派出的背景代理人做出「已隨 session 一起結束」的判定，並依此重新派發同一任務。

典型表徵：

- 判定依據是「我的 context 裡沒有它了」，未查任何 session 外部狀態
- 重派後兩個代理人同時修改同一檔案，後寫入者覆蓋前者，且雙方都不知情
- ticket frontmatter 顯示 `assigned: true` / `started_at` 有值，被解讀為「上次 claim 的殘留」而非「正在執行中」
- 工作區有大量未提交變更，被歸類為「前 session 遺留」並考慮 revert

## 根因

**背景代理人是獨立進程，其生命週期與主線程 context 無綁定關係。** 主線程失去的是「與它通訊的 handle」，不是「它的執行」。這兩件事在主線程的觀測面上無法區分——兩者都表現為「我不知道它在做什麼」。

三個放大因素：

1. **記錄平面與世界平面的不對稱**（`tool-output-trust-rules` 規則 5）。派發記錄寫入是 at-most-once，世界副作用是 at-least-once。context 一旦重置，記錄平面歸零而世界平面完好，於是「零記憶」被誤讀為「零副作用」。
2. **team 狀態以建立 team 的 session 為 key，非以當前 session 為 key。** 新 session 查不到自己名下的 team，容易得出「沒有活躍代理人」的結論，實際上 team 仍在另一個 key 底下運作——而且訊息照樣送得到新 session（見預防措施），所以「查不到 team」與「收不到回報」是兩件事。
3. **重派的成本感知偏低。** 重派看起來只是「再跑一次」，直覺上最壞情況是浪費 token；實際最壞情況是兩個 writer 對同一檔案做不同方向的修改，產出無法用 diff 辨識對錯。

## 影響

損害與被重派任務的寫入範圍成正比。唯讀類任務（審查、分析）重派只浪費資源；寫入類任務重派會產生互相覆蓋的變更，且因為兩者都是「合理的修改」，事後從 diff 無法判斷哪些行屬於誰、哪個方向才是完整的。

若原代理人已完成部分 acceptance 而 ticket body 尚未回填，重派者會看到 placeholder 而認定「什麼都沒做」，把已完成的工作重做一遍並覆蓋掉更成熟的版本。

## 解決方案

**context 中斷後、重派任何背景任務前，必須先查世界平面確認代理人是否存活。**

| 查證對象 | 命令 | 判據 |
|---------|------|------|
| 目標檔案是否仍在被寫入 | `stat -f '%Sm' -t '%H:%M:%S' <file>` 對照當前時間 | mtime 晚於中斷時間點 = 存活 |
| 改動規模是否對得上任務 | `git diff --stat -- <file>` | 有實質改動 = 有人在工作 |
| ticket 是否被 claim | `ticket track query <id>` 看 `started_at` | 時間戳晚於中斷時間點 = 中斷後仍在推進 |
| team 成員清單 | `ls ~/.claude/teams/*/config.json` 逐一查 members | 成員在列且 inbox 有近期 mtime = team 仍存在 |
| 是否已產出衍生物 | 查 `spawned_tickets`、未追蹤檔案 | 中斷後新增 = 存活 |

mtime 是無法腦補的固定值（`tool-output-trust-rules` 規則 3），單獨一項即可證明存活；`git status` 顯示「有未提交變更」證明不了任何事，因為它不帶時間資訊。

## 預防措施

- 「我的 context 沒有它」不是終止的證據，只是通訊中斷的證據。這兩者必須在判斷語言上分開陳述
- 重派前的最後一問：中斷之後，世界上有沒有任何東西被改過？有 → 有人在做，不重派
- 確認存活後，處理方向從「重派」改為「等它做完並驗收」。**通訊未斷**：本次實證 team 訊息路由不綁 `leadSessionId`，代理人的完工回報與 idle 通知會送達 `/clear` 之後的新 session。resume 原 session 的價值是取回對話脈絡，不是取回收信能力，這兩者不可混為一談
- 確認已死才重派時，先讀 ticket body 與未提交 diff 判斷已完成到哪，把進度寫進新 prompt，避免從零重做
- 反向適用：確認代理人存活後，工作區的未預期變更不可當污染 revert（同 `tool-output-trust-rules` 規則 5 的 ghost branch 條款）
