# PC-BAL-065：修法本身是它所要修的缺陷的另一個實例

## 基本資訊

| 欄位 | 值 |
|------|-----|
| 風險等級 | 中 |
| 來源 | 跨 session 框架修復（2026-09-03），兩個獨立實例 |
| 發現日期 | 2026-09-03 |

## 摘要

**發現缺陷後提出的修法，其運作機制與該缺陷相同，於是修法在自己身上重演一次同樣的失效。** 修法通過驗收（它確實處理了原始案例），失效發生在它自己被套用的場合，而那個場合通常不在驗收範圍內。

判別問句只有一句：**這個修法會不會是問題的另一個實例？** 在提出修法之後、實作之前問一次。

## 症狀

- 修法的說明能逐字套用到它所要修的缺陷上，只需替換主詞
- 修法引入的新機制依賴的能力，正是原缺陷證明不可靠的那個能力
- 驗收通過而問題復發，且復發的位置在修法本身而非原始位置
- 事後回看，修法與缺陷共享同一個未言明的假設

## 根因

1. **修法由發現缺陷的同一視角產生。** 能看見缺陷的視角，往往就是產生缺陷的視角；同一視角下的解法自然沿用同一套機制。
2. **驗收對象是原始案例，不是修法自身。** 驗收問「修法有沒有處理掉那個案例」，不問「修法自己會不會犯同樣的錯」。
3. **修法的正當性掩蓋其形態。** 修法被歸類為「解決問題的東西」，該歸類使人不再把它當成可能出錯的東西檢視。

## 防護

在提出修法之後、實作之前，執行一次自指檢查：

| 步驟 | 動作 |
|------|------|
| 1 | 把缺陷的描述寫成一句話 |
| 2 | 把修法的描述寫成一句話 |
| 3 | 檢查第 2 句能否透過替換主詞變成第 1 句 |
| 4 | 若能，該修法即為缺陷的另一個實例，需換機制而非調參數 |

**邊界**：不是所有「修法與缺陷相似」都構成本模式。判準是**機制相同**而非主題相同——同一領域的修法自然會提到相同的名詞，那不算；要檢查的是它依賴的能力與缺陷失效的能力是否為同一個。

### 同族分級：失效時輸出無訊號或錯訊號

本筆與「失效時外觀訊號正常」的數筆屬同一族（處置或機制使問題更難被觀察）。族內依**失效當下輸出什麼**再分兩級，防護強度需求不同：

| 級別 | 失效時的輸出 | 為何後者更難繞過 |
|------|------------|-----------------|
| 無訊號 | 什麼都沒發生，或訊息字面正確而未述推論 | 不阻止查證——觀察者若起疑仍會去確認 |
| 錯訊號 | 主動宣告成功 | 使查證顯得多餘。觀察者要先懷疑訊號本身，才會想到去確認 |

實例對照：同步工具衝突檔整檔跳過（訊息「本地原檔保留」字面正確但未述其推論）屬無訊號；PostToolUse hook 在寫入被拒時仍輸出「已更新於 <ticket-id>」屬錯訊號。

**Action**：判定為錯訊號級時，防護不得僅補充說明文字——說明會被讀成對既有宣告的補述而非否定。須改為使錯誤宣告本身不產生（收窄觸發條件、或以實際結果而非命令形式決定是否宣告）。

## 實例

| 缺陷 | 曾被考慮而否決的修法 | 為何是同一個實例 |
|------|-------------------|-----------------|
| 同步工具在衝突檔上整檔跳過，靜默丟棄上游變更；輸出訊息字面正確但未述其推論 | 維持不動並在輸出補一行「未套用 N 個 hunk」 | 該補充是再發一次會被忽略的提示，而缺陷的核心正是「提示被忽略」。改採把合併結果寫回工作區——衝突標記無法被忽略 |
| 修法會在風險最高的檔案（hook、被 import 的模組）寫入衝突標記，可能使其靜默失效 | 對這類檔案特殊化為維持不動 | 維持不動即是靜默降級，正是本次要修的形態。改採確保失敗可診斷而非避免失敗 |
| error-pattern 的技術事實因敘事框架不同而未被檢索到，即記錄存在但未被關聯 | 為 error-pattern 新增「跨領域適用範圍」欄位 | 該欄位須由記錄者判斷本筆對哪些領域有指導意義，而缺陷正是「記錄者的視野無法涵蓋未來的檢索場景」。故先以分析票驗證問題規模，不直接實作欄位 |

第三例的處置值得注意：判定「修法可能同構」不等於「不修」，而是**先驗證問題規模再決定機制**。同構風險使該修法從預設選項降為候選之一，不是被否決。

### 第四例：判定同構後仍採納——風險以「依賴人的角色」形式殘留

| 缺陷 | 採納的修法 | 同構點 |
|------|-----------|--------|
| 問題 context 散落於單一 consumer 的 ticket 池，無人整合 | 以 framework issue 的 comment 承載跨 consumer 協作，設「當前結論」區段為整合角色 | comment 池同樣無天然邊界；若「當前結論」不被持續維護，得到的是同一問題換了載體 |

與前三例的差別：前三例判定同構後換機制，本例判定同構後仍採納，因為兩者有一處不同——ticket 池沒有整合角色，本協定有。同構與否因此取決於該角色是否真的被執行，使其成為**依賴人的防護**：失效時不產生任何訊號（區段停在最後一次更新，讀者無從得知是否仍成立）。此類防護與 `PC-BAL-062`「本條無執法層」同屬自律層。本例由第一個外部 consumer 在實際使用後指出，非設計者自行發現。

**Action**：採納帶同構風險的修法時，須為「角色未被執行」補一個可機械檢查的訊號（本例：「當前結論」的更新時間落後於最新觀測超過某期間，兩者皆由 API 可取），使依賴人的防護至少在失效時可被觀察。

**本例的附帶實例——警訊沿用缺陷的量尺**：為該修法設的第一個警訊「open issue 成長率高於關閉率」，是把 ticket 池的失效量尺（張數增長）直接搬到 issue 上，未先問兩者計數單位是否相同。ticket 一張對應一個執行單位、狀態不可逆，張數隨工作量線性增長是設計結果；issue 一張對應一個問題領域、狀態可逆，open 數沒有壞的方向。用錯量尺的警訊不只無效，還會把真正的失效（同領域裂成多張 issue）誤讀成活躍。由用戶指出後撤換。**Action**：為修法設警訊時，先確認警訊的計數單位與修法的載體一致，不從缺陷側直接繼承。
