# PC-GPD-048: 以識別符（i18n key、常數名）grep 測試目錄判定「零覆蓋」，但測試斷言的是渲染後的字面，零命中被當成缺口並建出不該存在的補測票

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 風險等級 | 低 |
| 首次觀察 | 2026-10-28 |

## 症狀

審查時要判斷某個 UI 行為有沒有測試，做法是拿程式碼裡的識別符（i18n key、常數名、元件 key）去 grep 測試目錄。零命中，就判定「零覆蓋」，並寫進審查補充，後續的分析票再據此規劃補測子票。

子票派出後，代理人才發現測試早就存在，只是斷言寫的是渲染後的文字（例如 `find.text('…')` 比對中文文案），沒有出現識別符。子票前提不成立，只能零變更結案，白白消耗一次派發和一個 worktree。

實證（2026-10-28）：審查以提示的 i18n key 名 grep 測試目錄，結果零命中，判為零覆蓋。實際上同一檔裡已有兩條斷言渲染文案的測試，一條是正向（findsOneWidget），一條是反向（findsNothing），由更早的票引入。補測子票派出後零變更，以重複關閉。

## 根因

**同一個行為在程式碼和測試裡的表示不同**。程式碼經由識別符取值，測試常常直接比對最終字面，好讓斷言貼近使用者看到的畫面。拿其中一種表示去 grep，另一種就成了盲區。

**零命中與真的沒有測試，在 grep 結果上長得一樣**。沒有正向對照，例如先確認這種 grep 能命中一個已知有測試的同類行為，零命中就沒有鑑別力。

## 解決方案

判定零覆蓋之前，至少用兩種表示搜尋：識別符本身，以及它在預設語系（或每個語系）解析後的字面。兩者都零命中，才判定零覆蓋。

## 預防措施

- 覆蓋盤點的 grep 清單同時列出識別符和渲染字面，例如 i18n key 加上各 ARB 檔中的值。
- 審查補充寫「零覆蓋」時，附上實際使用的搜尋字串，讓下游的建票者可以覆核。
- 建補測票前，派發方先用渲染字面再 grep 一次，成本低，能避免派出零變更的票。
