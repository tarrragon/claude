# PC-BAL-068: 派發期間更新規範，執行者以開場讀入的版本收尾且雙方皆無訊號

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | medium |
| 發現途徑 | 八個 curator 並行收束 ticket 期間，PM 依前批回報三次修改收束配方與代理人定義 |
| 復發次數 | 一日內四個代理人各命中一至兩次 |
| 來源版本 | v0.2.1 |

## 摘要

**並行派發時，PM 依先完成者的回報修正規範（配方、代理人定義、acceptance 口徑），後完成者仍以派發當下讀入的版本執行到收尾。規範檔在磁碟上已更新，執行者的 context 裡仍是舊版；PM 以為新規則已生效，執行者以為自己合規，兩端各自自洽，直到執行者回報「規範與實作矛盾」或 PM 發現產出不符新規則。**

失效不在規範改錯，而在改對的規範沒有到達正在執行的人。訊息通道可以補送，但只有 PM 記得要送、且執行者尚未轉 idle 時才有效。

## 症狀

- 執行者回報「規範 X 與實作 Y 相反」，PM 查磁碟版本發現兩者一致，分歧來自執行者讀取時點
- 執行者依舊規則產出（對照表寫錯章節、以舊提交規則不 commit、以舊區段命名），被新規則下的 gate 擋住或留下未提交結果
- 同一批派發中，先完成者與後完成者的產出形態不同，事後看像兩套規範
- PM 為每次規範變更逐一發訊給執行中的代理人，訊息在收件匣排隊，執行者轉 idle 後才被喚醒處理，時序已過
- 執行者在同一 acceptance 條文上出現「字面口徑」與「等價口徑」兩種勾選理由

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 規範在派發開場一次讀入 | 代理人在 prompt 指示下 Read 規範檔，之後以 context 內的內容工作 | 磁碟更新對執行中 context 不可見 |
| PM 依回報即時改規範是正確行為 | 先完成者撞到的缺口若不立刻修，後續執行者會撞同一個 | 改得越及時，與執行中代理人的版本落差越大 |
| 訊息通道是推送、規範檔是拉取 | 訊息只在執行者下一個工具回合被讀取；轉 idle 後要靠新訊息喚醒 | 通知的到達時間不可控，PM 也無從得知是否已讀 |
| acceptance 條文與規範同步改 | 票面 acceptance 是派發當下的口徑，規範改後票面未同步 | 執行者面對「票面字面」與「規範現況」兩個判準 |

## 案例：一日內三次改配方，四個 curator 各以不同版本收尾

1. 第一批四個 curator 派發後，先完成者回報 acceptance gate 把來源票對照表判為 spawn 規劃；PM 改配方「對照表寫 Test Results」並發訊給執行中的三個
2. 同批另一 curator 回報 close 結果未提交；PM 把「不手動 commit」改為「隔離索引 CAS 提交」，再發訊給執行中的五個
3. 第三批 curator 收尾時以開場版本核對 acceptance，回報「ticket-intake 與協定檔對後綴區段涵蓋的描述相反」，PM 查磁碟兩者已一致，執行者補撤回觀測
4. 三個 curator 在收尾時自行重讀規範發現差異，各以「等價口徑」改寫 acceptance 並記錄取代關係；另兩個以舊版本完成，由 PM 事後補提交其結果
5. 執行者在回報中明寫：「兩份規範都在我執行中途被更新，我以開場讀入的版本工作到收尾，兩次都靠你提醒才發現」

## 解決方案

1. **規範檔加「收尾前重讀」條款**：執行者在核對 acceptance 之前重新 Read 規範檔與代理人定義，以當下版本核對；差異寫入 Solution 的取代關係表。成本是一次讀取，收益是消除「以舊版本收尾」這整類失效
2. **PM 改規範時同步改票面**：規範變更影響 acceptance 口徑時，PM 對執行中的派發票以 `set-acceptance --edit` 改寫（受 identity-guard 限制時發訊由執行者改），不留「票面舊、規範新」的雙判準
3. **訊息只作提示，不作生效機制**：發訊內容寫「規範已改，請重讀 <檔>」而非貼規則全文；生效以磁碟版本為準
4. **批次派發前凍結規範**：可預期的缺口在派發前修完；派發後的規範修正累積到下一批，只對當批以訊息提示

## 預防措施

| 層級 | 措施 |
|------|------|
| 代理人定義 | 自檢清單首項為「已重讀規範檔（版本或 commit）」，並在 Solution 記錄讀取時點 |
| 派發 prompt | 引用規範時寫「以磁碟當下版本為準」，不把規則全文貼進 prompt |
| PM | 規範變更後對執行中的派發票列一張「受影響票／已通知／已改 acceptance」表，未勾完不派下一批 |
| acceptance 撰寫 | 驗收條件不寫死版號或當下的規範措辭，改寫為「等於執行當下重讀的版本」。**Why**：寫死的版號在派發到收尾之間會過期，執行者依票面字面達成即算通過，而通過的是一個已不存在的目標；改為指向「當下版本」使票面隨規範自動對齊，無需 PM 逐票追改。**來源**：跨 consumer 實例——一張票寫死「拉取某 skill 1.8.0」，執行時發佈庫已到 1.10.2 |
| 工具 | 派發登記檔記錄派發時規範檔的 commit，收尾時比對 HEAD 版本，不同即提示重讀（候選，未實作） |
