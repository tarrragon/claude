# PC-BAL-010：驗證管道對待驗現象不敏感（恆真與恆偽雙向，家族層）

## 症狀

驗證條件（測試斷言、acceptance 條目、hook 規則、驗收用的 grep）以某個觀察管道表述，而該管道的輸出不隨待驗現象改變。驗證因此喪失鑑別力，結果與被驗對象無關，只有兩種樣態：

| 樣態 | 表現 | 讀者當下的感受 |
|------|------|---------------|
| 恆真（該紅不紅） | 修復前後都通過；缺陷存在時也通過 | 「已驗證」的錯覺，無異狀可見 |
| 恆偽（不該紅卻紅） | 工作正確也不通過；照著提示改仍不通過 | 「這個檢查在找碴」，傾向繞過或關掉 |

兩向的共同判準是同一句話：**這個檢查條件的結果，會隨被驗對象的正確與否而改變嗎？** 答案為「否」即命中本模式，與它目前顯示綠或紅無關。

## 家族層定位

本模式是抽象層，既有 pattern 庫中至少三個成員屬其下位：

| 下位成員 | 管道 | 方向 |
|---------|------|------|
| `TEST-BAL-001` | validator 的解析 regex 只認理想化 fixture 格式，對真實格式抽取回空集 | 恆真 |
| `PC-MON-002` | CLI 必填檢查只驗非空，不驗語意型別 | 恆真 |
| `PC-BAL-005` | hook 觸發詞 regex 無合規術語豁免層，命中標準章節名 | 恆偽 |

獨立成家族層的理由：三者分散在不同分類（test / process-compliance）、載體不同（測試 fixture / CLI 參數 / hook regex），讀者遇到新實例時無共同上位可檢索，只能憑「這像哪一個既有案例」聯想；而三者的核心主張、偵測手段、防護方向其實同一。查到本檔的讀者應同時取用下位成員的具體處置。

## 案例：恆真組（驗證該紅不紅，缺陷靜默通過）

| 案例 | 驗證條件 | 管道為何不敏感 | 後果 |
|------|---------|---------------|------|
| PEP 723 遷移後的環境 mock | mock `PATH` 與 `shutil.which` 以模擬「無 homebrew python3」 | 受測函式改用 PEP 723 後根本不碰這兩者，mock 對其為無操作 | 測試宣稱覆蓋的降級路徑實際從未被執行 |
| 短路放行的遺留測試 | 斷言 stdout 含 `allow` 以證明「走了短路放行」 | 完整驗證路徑的輸出恰好也含該字樣，修復前後皆通過 | 短路缺陷修復與否無法由該測試分辨 |
| fixture 殘留的 acceptance（驗收方撰寫） | 「跑完後 `git status` 乾淨」證明無 fixture 殘留 | 殘留物是空目錄，git 不追蹤空目錄，殘留與否 `git status` 皆乾淨 | acceptance 通過但殘留仍在 |
| `TEST-BAL-001` | validator 對真實檔案 exit 0 即視為通過 | 解析 regex 只認理想化格式，真實格式抽取回空集；「沒有不符」與「沒東西可檢查」在輸出上同形 | gate 的動機被自己架空，一項都沒檢查 |
| `PC-MON-002` | CLI 必填欄位（`--resolved-by`）存在即視為有效 | 必填只驗非空，任意自由文字皆穿透 | 追蹤鏈斷裂，防護表面存在而實質可穿透 |

恆真的共同特徵：驗證的**輸出通道**與現象之間隔了一層不變的中介（不再被呼叫的 mock、恰好共用的字樣、不追蹤空目錄的 git、抽取回空集的 parser、只檢查非空的 argparse），現象在中介處被吸收。

## 案例：恆偽組（驗證不該紅卻紅，誤指控正確工作）

| 案例 | 驗證條件 | 管道為何不敏感 | 後果 |
|------|---------|---------------|------|
| 以 grep 驗收文件修正（驗收方撰寫） | `grep -c` 某段錯誤主張的字樣，預期為 0 | grep 無法區分「主張 X」與「引用 X 並否定它」；三處更正說明引用原文即命中 | 一度判定正確完成的修正為未完成 |
| `PC-BAL-005` | hook 以觸發詞 regex 偵測延後決策 | 觸發詞比對無合規術語豁免層，標準章節名含該詞即命中 | 合規產出被擋，作者被迫改寫措辭繞過檢查 |

恆偽的共同特徵：驗證的**輸入通道**比現象粗（字面命中取代語意判斷），把與現象無關的訊號一併吞入。

## 根因

**Why**：撰寫驗證條件時，人取用的是「當下手邊最容易表述、且此刻看起來會過的觀察管道」，而不是「與待驗現象有因果連結的管道」。`git status`、`grep -c`、`stdout` 含某字樣、`shutil.which` 被 mock、欄位非空——這些管道的共同優點是可立即執行、輸出簡短、當下確實給出預期值。管道與現象之間的因果連結是否成立，是一個需要另外推導的問題，而該推導在驗證通過時沒有任何觸發點提醒你去做。

這不是單方的產出品質問題。上列七例中，撰寫者橫跨實作方與驗收方：實作方寫測試斷言時如此，驗收方寫 acceptance 與驗收用的 grep 時同樣如此。取用便利管道的傾向來自「表述驗證」這個動作本身，不來自角色。

**Consequence**：兩向後果不對稱，防護不可只寫一側。

| 方向 | 後果 | 實證 |
|------|------|------|
| 恆真 | 缺陷靜默通過，可潛伏多輪才暴露；期間所有「已驗證」的結論都不成立，且回溯時難以界定哪些結論受影響 | 一個 whitelist 紅燈在恆真斷言下潛伏跨越六張票才被發現 |
| 恆偽 | 對正確完成的工作發出錯誤指控，該指控可能被寫入 worklog 成為後續票的既定事實；更遠的後果是該驗證被視為雜訊而遭繞過、放寬或關閉，連它原本能抓的真問題一併失去 | 一次驗收差點判定已完成的修正為未完成；繞過與過度放寬的樣態見 `ARCH-016` |

恆偽側的樣本數少不代表風險低——恆偽會直接損害驗證機制本身的可信度，而信任一旦流失，之後的真紅燈也會被當成又一次誤報。

## 偵測：無機械捷徑

**本模式無自動化偵測手段，必須人工檢視「檢查條件」與「待驗現象」之間的因果連結是否成立。** 此點必須明說，否則讀者會期待工具代勞而略過人工檢視，這正是本模式得以長期潛伏的條件。

與姊妹模式 `PC-BAL-009` 對照可見差異：該模式可用 pass、fail 與總數的算術對帳機械判定成因，因為它的症狀（兩份結果不一致）本身就是機械可比的。本模式的症狀是「結果不變」，而「不變」在單次觀測下與「正確地通過」完全同形，沒有可供比對的第二份輸出。

人工檢視的執行方式是對每個驗證條件問一次因果三段：

1. 待驗現象是什麼？（用被驗對象的性質表述，不用觀察工具表述）
2. 現象若為假，這個管道的輸出會如何改變？（答不出具體差異即命中恆真）
3. 現象為真但周邊條件變動時，這個管道會不會照樣報錯？（答得出情境即命中恆偽）

**輔助訊號（非充分條件，不可寫成判準）**：以下訊號提高嫌疑，但不出現也不代表安全，出現也不代表命中。

- 斷言含多個 `or` 分支（任一分支恆真即整體恆真）
- 檢查條件描述的是環境狀態（`git status` 乾淨、檔案存在、輸出含某字樣）而非被測對象的實作性質
- 驗證的通過與否不隨被測對象的改動而變化（需要實際做一次改動觀察，成本高但結論確定）

## 防護

### 撰寫驗證條件時（實作方與驗收方同適用）

1. 驗證條件用**被驗對象的性質**表述，再選管道；禁止反向從手邊便利的管道倒推出一個「看起來會過」的條件。
2. 新增或修改斷言、acceptance、hook 規則時，執行上節的因果三段自問，並把第 2 問的答案（現象為假時輸出如何改變）寫進條件旁邊。這句話是後續審查者唯一能據以複查的材料。
3. 對關鍵驗證做一次**反向確認**：暫時破壞被驗對象（還原修復、塞入違規樣本），確認驗證確實翻紅。無法翻紅即為恆真，該驗證條件作廢重寫。

### 症狀為恆真時（驗證通過但可疑）

4. 追問「這次檢查實際檢查到幾項」，不以 exit 0 或綠燈為滿足；抽取計數為 0 卻通過是恆真的高辨識度訊號（處置細節見 `TEST-BAL-001`）。
5. 檢查條件涉及必填、存在性、格式等分層驗證時，逐層確認驗到哪一層（處置細節見 `PC-MON-002`）。

### 症狀為恆偽時（驗證報錯但工作看似正確）

6. **在改寫被驗對象以繞過檢查之前，先判定檢查條件本身是否恆偽。** 若合規產出必然命中該檢查，問題在檢查而不在產出；此時改寫產出等於用產出品質換取檢查通過，且掩蓋了檢查的缺陷。
7. 判定為恆偽時，兩件事都要做：當下記錄繞過方式與成本（讓後續讀者知道此處被繞過），以及建立追蹤票修正檢查條件（加豁免層、改語意判斷、縮小比對範圍）。只做前者會使繞過永久化，只做後者會讓當下工作卡住。
8. 恆偽的檢查禁止直接放寬到「不再報錯」為止——放寬必須針對誤傷的具體樣態（如標準章節名白名單、引用語境排除），不得改為降低整體嚴格度，否則失去它原本能抓的真問題（過度放寬與過度限制的兩難見 `ARCH-016`、`PC-BAL-005`）。

### 驗收方特有

9. 以 grep、`git status` 等字面或環境管道作 acceptance 時，先確認該管道能區分待驗現象的兩個狀態。grep 不區分主張與引用、git 不追蹤空目錄，這類管道極限應在寫下 acceptance 當下就標明。
10. 驗證結果與預期不符時，在寫下「未完成」「回報失實」這類歸因結論之前，先跑一次上節的因果三段檢查驗證條件本身。

## 邊界

| | 本模式 | `PC-BAL-009` | `PC-165` |
|---|--------|--------------|----------|
| 驗證的鑑別力 | 無——結果不隨被驗現象改變 | 有——但結果隨執行環境翻轉 | 有——但覆蓋範圍不含 runtime |
| 症狀形態 | 恆真（該紅不紅）或恆偽（不該紅卻紅） | 同一驗證在兩處給出不同顏色 | 穩定綠燈 |
| 錯誤結論 | 「已驗證」或「未完成」 | 「對方回報失實」 | 「已修好」 |
| 偵測 | 人工檢視因果連結，無機械捷徑 | pass/fail 總數算術對帳，機械可判 | acceptance 補 runtime 層級驗證 |

判別順序：**先確認鑑別力（本模式），再確認結果穩定性（`PC-BAL-009`），最後確認覆蓋範圍（`PC-165`）**。順序不可顛倒——對一個無鑑別力的驗證做環境對帳或 runtime 補強，都是在修一個從一開始就不會反映現象的東西。

兩兩可疊加：一個驗證可能既無鑑別力又隨環境變（cwd 差異使某分支永不執行，退化為恆真）；也可能鑑別力僅存在於非 runtime 層（`PC-165` 的遮蔽情形）。疊加時仍依上述順序處理。

## 關聯

- `TEST-BAL-001`、`PC-MON-002`、`PC-BAL-005`：本模式的下位成員，各自載有具體載體上的處置細節
- `PC-BAL-009`：姊妹模式，驗證有鑑別力但結果隨 cwd 翻轉；其算術對帳手段不適用於本模式
- `PC-165`：測試綠燈遮蔽 runtime 失效；其驗證有鑑別力，只是覆蓋範圍不足
- `ARCH-016`：過度限制的 hook 允許清單；恆偽側「驗證被視為雜訊而遭繞過或放寬」的後果樣態
- quality-baseline 規則 1 邊界（測試綠燈不等於 Runtime 正確）、`tool-output-trust-rules` 規則 3（關鍵事實用無法腦補的固定值交叉驗證）
