# PC-BAL-015: idle 通知加上尚未落地的寫入被當成代理人未執行，據以前台重做

## 症狀

PM 以 `SendMessage` 對既有 named agent 追加任務後，短時間內查證世界平面（ticket body、git log、檔案內容），見不到該任務的痕跡，同時收到該 agent 的 `idle_notification`，據此判定「代理人未執行指派」，改由前台自行完成同一任務。

典型表徵：

- 判定依據三項並列：關鍵字在 ticket 命中 0、最後 commit 時間早於指派時間、收到 `idle_notification`
- 前台重做完成後，代理人送出完整回報，內容與前台產出高度重疊
- 同一 ticket 出現兩份結論相同的章節，來源不明，後續讀者無法判斷哪份是權威
- 若任務為寫入類，兩個寫入者對同一區域產生不同措辭的重複內容

### 症狀變體：以字面為真的標籤消化範圍外發現（0.2.1-W3-192 實證）

上述主症狀是**讀者**誤判代理人狀態；本變體方向相反——**代理人**以一個字面正確的分類標籤處置了範圍外的發現，使該發現不再被追究。

- 代理人在執行任務時撞見與本任務無關的問題（測試紅燈、既有缺陷）
- 回報中以標籤消化該發現，標籤的每個字面成分皆經查證且為真
- 但標籤的隱含意涵與事實不符，且該隱含意涵正是「不需上報」的依據
- 驗收者若接受標籤，該發現不進入任何追蹤載體

實證：代理人執行 memory 工作流清理時跑全套件，撞見 `test_all_seven_skills_covered` 紅燈，回報為 `pre-existing unrelated failure`。查證後 `pre-existing`（早於該代理人開工）與 `unrelated`（與其任務無關）**字面皆成立**，但該組合的隱含意涵「屬長期背景雜訊」為偽——回歸於 27 分鐘前由同 session 的另一張票引入。

**判別**：代理人驗證的是「是否早於我」與「是否屬我」，未驗證「是誰造成」。前兩者決定歸屬，後者才決定該不該上報。依 quality-baseline 規則 5，範圍外發現應建票而非以標籤消化。

**與 `PC-BAL-020` 的分野**：本變體的所有字面陳述皆經查證，問題在標籤作為處置決定；`PC-BAL-020` 的問題在陳述本身有未經查證的成分卻以確定語氣書寫。

## 根因

**代理人的執行進度與其世界平面痕跡之間存在延遲窗口，而 `idle_notification` 不承載「指派任務已完成」的語意。**

三個構成因素：

1. **寫入落地延遲。** 代理人的產出多在其回合結束時才一次寫入（`append-log` 的 auto-commit、檔案 Edit）。在此之前它已讀完材料、跑完實驗、寫好內容，但世界平面上完全無痕跡。查證時機落在此窗口內，得到的「0 命中」是真實輸出，卻不代表零工作。

2. **`idle_notification` 的語意窄於 PM 的解讀。** 該通知的 `idleReason: available` 描述的是「進程當前無執行中的回合」，不是「已處理完你剛才的指派」。訊息投遞與回合排程之間有間隙，通知可能反映的是指派抵達**之前**的閒置狀態。PM 把它讀成「它已經看過我的訊息且沒事做」，是把傳輸層事件當成應用層完成訊號。

3. **三項證據看似獨立，實則同源。** 「關鍵字 0 命中」「commit 早於指派」「idle 通知」全部指向同一件事——**在我觀測的那一刻，寫入尚未落地**。三項互相印證會製造高信心，但它們不是三個獨立樣本，而是同一現象的三個側影。這與 `PC-BAL-013` 的「零記憶誤讀為零副作用」同屬記錄平面與世界平面的不對稱（`tool-output-trust-rules` 規則 5），差別在本例的落差來自時間延遲而非 context 重置。

## 影響

損害隨任務性質分為兩級。

唯讀分析類：產生兩份重疊結論，ticket 可讀性下降，後續讀者需要額外的對帳章節才能判斷權威來源。若兩份結論分歧，還會產生「哪份算數」的裁定成本。

寫入類：兩個 writer 對同一區域產出不同措辭的內容，`append-log` 的追加語意使兩份並存而非覆蓋，表面上無衝突，實際留下語意重複的檔案。若改用 Edit 則後寫入者覆蓋前者，且雙方都不知情（退化為 `PC-BAL-008` 的形狀）。

附帶損害是判斷校準失效：PM 一旦有過「代理人不回應」的成功前台救援經驗，會降低後續等待意願，使誤判頻率上升。

## 解決方案

追加指派後判定代理人是否執行，須滿足下列全部條件才可下「未執行」結論：

| 條件 | 具體做法 |
|------|---------|
| 給足落地窗口 | 至少等待一個完整回合的時間再查；查證前先做其他不相干的前置工作，不空等 |
| 直接問而非推斷 | 以 `SendMessage` 詢問進度，等待回覆逾時後才視為無回應 |
| 排除同源證據 | 「關鍵字 0 命中 + commit 早於指派 + idle 通知」計為**一項**證據（寫入未落地），不計為三項 |
| 確認通知語意 | `idle_notification` 只表示進程當前無執行回合，不表示指派已處理完畢；不可作為未執行的依據 |

判定為未執行後，處置優先序：重新 `SendMessage`（代理人 context 完整，成本最低）> 重派新代理人 > PM 前台執行。前台執行只在任務屬 PM 職責範圍（唯讀分析、規劃、ticket bookkeeping）且已確認代理人確實無回應時採用。

若重複執行已發生，依 `quality-baseline` 規則 6 不回退既成工作：保留兩份產出，加對帳章節標明各自來源、成因與分歧處置，使後續讀者可判斷權威來源。獨立雙軌得到相同結論時，該結論的可信度反而提高，應在對帳章節明說這項收益。

## 預防措施

- 派發或追加指派後，PM 立即切換到下一個前置工作，不進入「查證—失望—再查證」循環（與 `PC-062` 的反覆檢查為同一反模式的兩個方向：一個查太多次，一個查太早就下結論）
- 對 named agent 追加任務時，在訊息中要求「開始執行前先回一則確認」，使「已收到」與「已完成」成為兩個可區分的訊號
- 世界平面查證的時機寫入判定條件而非憑感覺：查證前先確認距離指派是否已超過一個回合
- ticket body 出現來源不明的重複章節時，優先查 `git log` 的 commit 時間序而非猜測，時間序可還原兩個寫入者的交錯順序
