# PC-BAL-035: 驗收條件措辭預先鎖死攔截點，AC 全綠掩蓋威脅事件未覆蓋

## 基本資訊

- **Pattern ID**: PC-BAL-035
- **分類**: process-compliance（驗收設計失誤）
- **風險等級**: 高
- **關聯**: [[PC-V1-012]]（防護置於便利攔截介面而非變異源頭，本模式為其上游成因）、[[PC-MON-001]]（守衛建在可繞過的執行點）、[[PC-165]]（測試綠燈不等於 runtime 正確）、[[PC-BAL-049]]（驗收措辭失誤家族的另一機制：攔截點落在錯誤的動作類型而非錯誤的位置）

## 錯誤症狀

驗收條件把「防護手段」而非「威脅事件」寫進條文，實作照條文做到 100%、單元測試全綠、Phase 4 前的所有訊號皆正常，但威脅事件仍可由條文未涵蓋的路徑完整重現。典型表現：

- AC 寫成「執行動作 X 時檢查條件 Y」，而真正要防的是「壞狀態 Z 存在」。動作 X 只是壞狀態 Z 的其中一條產生路徑。
- 實作者無從察覺偏差——條文既已指定攔截點，實作滿足條文即為達標，偏離條文反而像是超出範圍。
- 缺陷要到多視角審查（Phase 4）或事故復發才暴露；此前 AC 勾選、測試通過、覆核重跑三層訊號一致為綠。
- 常伴隨順序依賴漏洞：只要調換操作順序使動作 X 發生在壞狀態 Z 產生之前，檢查點必然撲空。

## 根因分析

### 根因 1：AC 寫的是解法而非現象

驗收條件的職責是描述「什麼狀態算通過」，一旦寫入具體攔截點（哪個工具、哪個檔案、哪個時機），就從「驗收」退化為「設計指令」。設計決策被前移到還沒做設計的階段，且以不可協商的條文形式固定下來。

### 根因 2：條文即護欄，實作者不會反向質疑

實作者的合規壓力指向「滿足條文」。條文指定了攔截點時，重新評估攔截點正確性等同質疑 ticket 本身——在有 acceptance-gate 硬擋的流程裡，這個方向的偏離成本高於順從成本，因此系統性地不會發生。

### 根因 3：驗證迴路封閉在條文內

測試依 AC 設計、覆核依 AC 重跑、gate 依 AC 勾選。三層驗證共用同一份條文作為真值來源，故條文本身的覆蓋缺口對整條驗證鏈不可見。這是「測試綠燈不等於 runtime 正確」（[[PC-165]]）在驗收設計層的同構表現。

## 解決方案

### 步驟 1：AC 一律以威脅事件或最終狀態描述

| 反模式（鎖死攔截點） | 正確（描述威脅事件） |
|---------------------|---------------------|
| 呼叫 API X 時驗證參數 Y | 非法參數 Y 不得抵達下游處理器 |
| 提交前執行檢查 Z | 不符合 Z 的內容不得存在於主分支 |
| 寫入設定檔新增註冊時，若目標檔缺可執行位則失敗 | 缺可執行位的 hook 檔案不得在任何路徑下進入生效狀態而不被偵測 |

> 前兩列為泛化形態，末列為本模式的原始案例（特化度最高，置末以免讀者誤以為本模式僅適用於 hook 場景）。本表為三列對照的權威來源；`.claude/methodologies/acceptance-criteria-methodology.md` 反向引用本表，不另存副本。

判準：把 AC 唸一遍，問「若實作把攔截點換到別處但威脅事件同樣被擋住，這條 AC 還算通過嗎？」答「不算」即為鎖死，須改寫。

### 步驟 2：建立 AC 時同步列出威脅事件的產生路徑

寫防護類 AC 前，先列該壞狀態的所有已知產生路徑（工具、自動化流程、VCS 操作、外部同步），再問「條文涵蓋幾條」。涵蓋不足時，AC 應以「所有路徑」措辭表達，把路徑盤點的責任交給實作階段而非預先裁定。

**時序不可調換**。防護票的真實成形順序通常是攔截點先於 AC——起因是「想加一個機制攔住 X」，AC 屬回填。在該順序下，步驟 1 的判準問句會失效：撰寫者被要求改寫為威脅事件時，寫出的是已選攔截點的精確補集（措辭合格、覆蓋缺口原封不動），且面對判準問句會誠實回答「算通過」，因為他想不到別的路徑——而想不到別的路徑正是本模式的內容。步驟 1 的判準問句預設撰寫者具備列舉替代路徑的能力：該預設成立則步驟 1 多餘，不成立則步驟 1 撲空，沒有第三種狀態。供給該能力的唯一機制是本步驟，故它必須發生在 AC 撰寫之前，不可移到派發前或實作階段。

### 步驟 3：防護類 ticket 的 AC 必含順序置換驗證

對「動作發生時檢查」型的防護，加一條 AC 要求驗證操作順序調換後仍有效。順序依賴是攔截點鎖死最常見的具體後果，且單元測試若照條文設計必然不會覆蓋它。

## 預防措施

三項措施皆已落地為自律層。措施 2 另於可機械判定子集（type=IMP 且 `where.files` 觸及 hooks 目錄或 skill 私有 hooks 目錄）加設硬擋，**檢查對象為產生路徑盤點表的正本**（撰寫者寫在實作策略欄位，機器解析並輸出計數），不檢查 acceptance 中的數字宣告——對副本設閘門而正本不設，與本模式根因同構。形態選擇的判準見本節末「硬擋形態的判準」。

| 機制 | 內容 | 落地位置 |
|------|------|---------|
| 建票時（步驟 1） | 防護類 ticket 的 AC 描述威脅事件或最終狀態；攔截點決策移至 `how.strategy` 或 Solution（兩者分屬不同欄位，非二選一） | `.claude/pm-rules/ticket-body-schema.md`「防護類 ticket：威脅事件寫 acceptance，攔截點寫 how.strategy」節；`.claude/methodologies/acceptance-criteria-methodology.md` 禁用規則表「禁止以攔截點替代威脅事件（防護類）」列 +「防護類驗收條件：威脅事件測試」節 |
| 建票時（步驟 2，**須先於撰寫 AC**） | 於實作策略欄位列出威脅事件的產生路徑盤點表，作為 AC 措辭與後續攔截點選擇的共同依據。該表為唯一正本，不在 acceptance 重複宣告數字 | 自律層（已生效）：同上 schema 節 Action 的第一步（含欄位定義與範例）。強制層：checker 解析盤點表——缺表阻擋、有表輸出計數、解析失敗 fail-open。**該行為的實作進行中**，現行版本檢查的仍是 acceptance 中的數字宣告（以 regex 而非 substring，因後者實測 128 張有 23 張會因「測試覆蓋……」誤過）。派發前存在性確認見 `.claude/references/agent-dispatch-template.md`「填空檢查清單」 |
| Phase 4 | 多視角審查必問「AC 全綠但威脅事件是否仍可經未涵蓋路徑重現」，此問題不可由 AC 自身回答 | `.claude/skills/parallel-evaluation/references/lens-prompts.md`「跨情境必問：防護類標的的驗收覆蓋」節（四問模板，附加於任一視角 prompt 尾部，不佔額外 agent 名額） |

### 硬擋形態的判準：宣告是否對外部事實可證偽

強制層的可行性由**宣告與外部事實的關係**決定，不由檢查是否「更嚴格」決定。

| 宣告性質 | 特徵 | 可否被外部事實判錯 | 適合的層級 |
|---------|------|------------------|----------|
| 自我認證 | 沒有可對照的外部參照物，宣告即其自身的證據 | 否 | 提示層 |
| 可證偽 | 存在外部參照物，宣告可拿去對照並被判錯 | 是 | 硬擋 |

具體對照：「不得在缺可執行位的情況下放行」是自我認證的——沒有任何外部事實能證明它假。「盤點 4 條、覆蓋 2 條」是可證偽的——可拿去跟真實產生路徑數對照，且會被判錯。

**這條軸解釋為何措辭硬擋失敗**：要求 acceptance 含威脅事件措辭時，撰寫者可將既有攔截點條文原地改寫——「寫入設定檔新增註冊時，若目標檔缺可執行位則失敗」改為「不得在目標檔缺可執行位的情況下放行」。改寫後的條文字面宣稱涵蓋全部路徑，實際覆蓋範圍未變，且無外部事實可用於判錯。

**硬擋能保證的與不能保證的**：硬擋只能保證某個欄位存在且形態合規，不能保證其中的判斷有品質。可證偽性決定的是「事後有沒有辦法發現它錯了」，不是「當下能不能寫錯」。設計閘門時應以前者為目標，並明確承認後者不在射程內。

> **反例：不可宣稱「某類硬擋不可空洞滿足」**。本節初版曾以「維度型 vs 形式型」為軸，主張前者（就具名面向各表態）不可空洞滿足，並引既有必含項檢查為正面實證。該主張被實作事實推翻：`hook_protection_acceptance_checker.py` 的判定機制是把整份 acceptance 串成一塊文字做關鍵詞 substring 比對，`異常時 fail-closed` 六字即通過失敗語意項，且該字串跨 ticket 完全可互換。以該節自己的判準問句檢驗它自己的正面實證，會把該實證判成反例——分類軸因此不成立。**教訓**：判準的正面實證必須查證實作，不能只讀規格文字；規格宣稱的檢查語意與實作的檢查機制可以完全不同。

**與既有框架機制的關係**：`.claude/rules/core/structured-content-generation.md` 的三層防護模型（CLI 制式化 → WARNING 引導 → Hook 事後檢查為保險）已處理同一問題。Hook 是第 3 層保險而非主防線；本節的可證偽性判準用於決定「這個宣告值不值得放進第 3 層」，不改變其保險定位，也不賦予它第 1 層的強度。

負向 keyword 形態另有獨立的不可行理由：以單一版本全量 543 張 ticket、1854 條 acceptance 條目實測，攔下含工具名或攔截時機者命中 541 條（29.2%），抽樣全為合法 AC。誤判源自結構性衝突——schema 自身要求 acceptance 寫出具體驗收指令與時機，該要求與「不得寫攔截點」在字面層不可區分。

觸發條件方面，「防護類」的外延大於任何可判定的路徑條件（CLI 參數驗證、schema 約束、gate 條件皆屬防護類但不觸及 hooks 目錄），故可證偽宣告硬擋只施加於可機械判定子集（type=IMP 且 `where.files` 觸及 hooks 目錄或 skill 私有 hooks 目錄），子集外仍為自律層。與 [[PC-MON-001]] 的差別可檢驗，不繫於敘述者是否自覺：子集外未被降級為無防護（仍適用自律層），且子集未涵蓋的情形已具名列於下方殘餘風險表（「ticket 未被認出是防護類」列）。殘餘風險本身未因此縮小，改變的只是宣稱涵蓋的範圍。

另有一項自我參照約束：若把建票時的機制寫成「AC 禁含工具名或攔截時機」的措辭禁令，該條文本身即是「以條文預先鎖死做法」，與本模式根因「AC 寫的是解法而非現象」同構——規則會示範它所禁止的模式。故條文形態定為**位置指引**（攔截點寫哪裡）而非**措辭禁令**（AC 不准寫什麼）。

### 不成立的理由：以存量合規率推斷閘門不可行

本節初版曾以「正向 keyword 會攔下該類 95.2%，形態上是牆而非閘門」作為不設硬擋的理由之一。**該推理不成立，保留於此以免重複援引。**

存量合規率量的是既有 ticket 的回溯符合度，閘門只對新建 ticket 生效，兩者不是同一個量。反證見 `.claude/pm-rules/ticket-body-schema.md`「防護類 hook ticket 額外 acceptance」節：該硬擋落地時存量合規率同樣接近 0，照樣部署且持續運作。

**Action**：評估任何新閘門時，禁止以「存量不合規比率高」推論「不可設閘門」。該比率的正確用途是估算**遷移成本**（既有項目是否需回溯補齊），與閘門對新項目的可行性無關。

### 形式化合規的現狀：未知，觀察窗不足

必含項硬擋治下的 acceptance 常以固定標籤開頭（「既有 session 生效策略：」等）。此現象曾兩度被下結論，兩次都不成立，現正確狀態為**未知**：

> 該標籤已於 2026-08-18 改名為「本 session 實地觸發確認」（PC-BAL-033 機制收窄的下游同步）。此處保留舊標籤字面，因為被觀察的樣本正是以舊標籤書寫的；引用時勿當作現行填法。

| 版本 | 結論 | 為何不成立 |
|------|------|-----------|
| 初版 | 前綴即 cargo cult，據以反對硬擋 | 只看前綴未看內容。前綴之後的內容是否跨 ticket 可互換才是判準 |
| 次版 | 全樣本實測顯示 cargo cult 不成立 | 觀察窗在原理上無法偵測該現象。詳見下段 |

**次版量測的方法缺陷**：該實測的「治下」樣本共 5 張票，其中一張是建立該硬擋的票本身，寫在閘門存在之前，屬類別錯誤（且其條目為全樣本中最短）。真正治下的僅 3 張，出自同一代理人、同一 session、53 分鐘之內，且該 session 正是此議題被密集討論的時段。形式化合規是**衰減現象**——它在閘門成為例行公事、注意力移開之後才出現。在落地後不到一小時、在設計者本人的 session 內量測，是在結構上不可能觀察到它的時點取樣。

混淆變項亦完全共線：硬擋、schema 的合格填法範例（自律層文字）、單一代理人、高注意力期間，四者在該 3 張票上同時出現，此資料無法辨識其中何者在起作用。若真正生效的是範例文本，則「自律層 + 強化範例」這個更便宜的選項從未被實際比較過。

**判別方式（供將來重測）**：檢查前綴**之後**的內容是否跨 ticket 可互換。可互換者為樣板，不可互換者為承載判斷的陳述。重測需滿足：樣本跨 3 個以上 session、出自 2 個以上撰寫者、且不含閘門設計期間的票。

**殘餘風險**：

| 風險 | 可觀測早期警訊 |
|------|--------------|
| 條文寫了但建票時沒被讀到 | 後續防護類 ticket 的 AC 仍以「執行 X 時檢查 Y」措辭出現 |
| ticket 未被認出是防護類 | 出現威脅事件重現的案例，回查其 ticket 並無防護類自覺（三項措施皆以「有人認出這是防護類」為前提，此前提本身不受任何機制保障） |

baseline 與重測程序：可機械判定子集（type=IMP 且 `where.files` 觸及 hooks 目錄或 skill 私有 hooks 目錄）的威脅措辭比率為 4.8%（6/124，單一版本語料）。重測方式為解析各 ticket frontmatter 的 `acceptance` 欄位，以正向詞集（不得／不應／任何路徑／均不／皆不／不可／無一／所有路徑）計命中率；負向詞集為工具名（hook／grep／pytest／npm／ticket track／git／CLI／exit 0／commit 等）與攔截時機詞（complete 時／claim 時／寫入／執行／呼叫／觸發／進入／時檢查）。升級強制層的討論應以該比率變化為依據，不以印象判斷。

## 觸發案例

2026-08-13 至 08-14，一張「前移 hook 可執行位檢查至註冊當下」的實作票。其首條 AC 寫為「寫入 hook 設定檔新增註冊時，若該 hook 檔案不具可執行位則於當下失敗並指出修復命令」。實作完全滿足此條文：38 項新增測試通過、3778 項全量套件通過、PM 覆核重跑結果一致。

Phase 4 五視角審查揭露，真正的威脅事件是「一個 `.py` 以 100644 進到 hooks 目錄並被註冊」，而該 AC 指定的攔截點在下列情境全部撲空——

- 先寫註冊、後建檔（此時目標檔不存在，走 fail-open 放行，隨後建檔為 100644 完全無檢查），事故原狀在合法操作順序下完整重現。
- 經 MultiEdit、Bash 重定向、git merge 等路徑寫入設定檔。
- skill 目錄下的 hook 檔案（既不在 session 啟動時全量掃描的頂層 glob 範圍，也因屬既有註冊項而不進差集）。

該票的問題分析已載明「新建 hook 在建立它的 session 內不被載入」的遞迴性陷阱，並據此要求首條 AC 的驗收限於單元測試。該條款正確地防止了另一類誤判（把必然觀察到的零效力誤讀為實作失敗），卻同時使「條文覆蓋是否足夠」這個問題徹底無從在該票內被觸及——兩層封閉疊加，是本模式在該案例中未被更早發現的直接原因。

> **前提已收窄（2026-08-18），本段結論不變**：上述遞迴性陷阱的前提「新建 hook 在建立它的 session 內不被載入」經實測為**版本相依**——2026-08-13 觀測到的 runtime 上成立，2026-08-18 觀測到的上不成立（另有一條與版本無關、恆成立的成因：檔案缺可執行位時 runtime 無從啟動它）。詳見 PC-BAL-033「機制更正」節。
>
> **為何結論仍成立**：本段主張的是「首條 AC 把驗收限於單元測試，使覆蓋範圍問題無從被觸及」這個**封閉結構**，該結構由 AC 條文的限縮造成，不由陷阱前提是否成立造成。前提在當時被相信即足以促成該限縮；即使前提後來被收窄，兩層封閉在該票發生的事實不變。此處保留原敘述並加註，而非改寫——把已收窄的前提回填成「當時就知道是版本相依」會製造事後諸葛的假象，反而遮蔽本模式的真正教訓：**AC 條文一旦寫入某個當時可信的機制前提，就把驗收範圍鎖死在該前提的射程內，前提事後被推翻也不會自動解鎖**。
