# PC-GPD-042: 元件搬入框架慣例目錄後只驗證元件自身測試，目錄慣例的掃描與判定到合併閘門才暴露

**類別**: process-compliance
**嚴重度**: 中
**發現日期**: 2026-10-27
**來源版本**: 0.5.0
**相關情境**: 把一個獨立元件（plugin）搬進框架以目錄名稱賦予語意的位置（如 `.claude/skills/<name>/`）

## 核心原則

**把元件搬進框架以目錄位置賦予語意的地方，等於讓它加入該目錄的全部慣例：註冊、版號、命名、子目錄名的語意判定。驗證範圍必須包含掃描該目錄的框架測試與 SessionStart 檢查，不能只跑元件自己的測試套件。** 元件自身測試全綠，只證明元件本身沒壞，不證明它符合新位置的慣例。

## 症狀

同一次搬移連續撞上三種慣例，各自在不同時點暴露：

| 慣例 | 判定方 | 暴露時點 | 表現 |
|------|--------|----------|------|
| 目錄必須有 SKILL.md | skill 註冊 SessionStart 檢查 | 每次 session 啟動 | 報 `missing SKILL.md` |
| 版號必須可擷取 | 版本擷取器與其覆蓋率測試 | 合併閘門的框架套件 | 測試紅燈「版本擷取落空」 |
| `<skill>/hooks/` 是 Claude Code hook 腳本 | 派發骨架與 acceptance-gate 的防護類 hook 範圍判定 | 派發與 complete | 要求 hook-logs、fail-open 等不相干的證據 |
| `<skill>/tests/` 是 pytest 測試 | 合併閘門的套件產生規則 | 補上版號後重送閘門 | 自動產生 pytest 套件，收集 0 個測試回 exit 5，判紅 |

元件自己的測試套件每次都全綠，代理人據此回報完成。第四項在前三項修完後才暴露：閘門遇到第一個紅燈就停，後面的慣例檢查要等前一個修好才輪得到。

## 根因

框架對特定目錄的檔案按「位置」而非「內容」套用規則：位於 `skills/<x>/` 就被視為 skill，位於 `skills/<x>/hooks/` 就被視為 hook 腳本。搬移者以元件的角度定義驗收（元件測試全綠、型別檢查 0 error），沒有把「新位置對它施加了哪些慣例」列為驗收項。慣例散在 SessionStart hook、框架測試、CLI 判定三處，沒有一處列出「進入此目錄須滿足的清單」，所以搬移前無從得知。

## 解決方案

1. 搬移前列出目標目錄的慣例來源：以目錄名 grep 框架測試、SessionStart hook、CLI 的路徑判定（如 `skills/`、`/hooks/`）
2. 每條慣例逐一決定「符合」（補 SKILL.md、補版號）或「判定誤認」（向判定方回報，例如 plugin 的 `hooks/` 不是 hook 腳本）
3. 驗收時除了元件測試，也在 worktree 內跑會掃描該目錄的框架測試，以及相關的 SessionStart 檢查
4. 搬移清單除了 tracked 檔，也列出原位置的生成物與其 ignore 規則：生成物目錄內 tracked 的 `.gitignore`（如內容為 `*`）若未一起搬，新位置一旦產生生成物就會以 untracked 出現；原位置留下的 gitignored 生成物則成為孤兒，須指定清除時點。實例：plugin 的型別生成目錄搬移後，新位置 `git check-ignore` 不命中，舊位置的型別目錄仍被臨時型別檢查引用

## 預防措施

- 搬移類的票，acceptance 加一條：「目標目錄的慣例檢查（SessionStart 與框架測試）全綠」
- 派發 prompt 指名要跑的框架套件，不只寫元件的測試指令
- 判定方若依子目錄名推斷語意，應改以該目錄的**內容**判定（例如 `hooks/` 內有沒有可執行腳本、`hooks.json` 有沒有事件鍵），不以旁證判定。「同層有 `.claude-plugin/plugin.json` 就不視為 hook」這類旁證太寬：plugin 的 `hooks.json` 本身就能宣告真正的事件 hook，用旁證豁免會讓真 hook 一併逃過防護要求
