# PC-GPD-049: 票面約束以 session 代號指名對口（「改規格前先告知 X」），該 session 結束後約束仍被逐票繼承，執行者找不到對口而停手上報

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 風險等級 | 低 |
| 首次觀察 | 2026-10-29 |

## 症狀

多 session 協作時，某個 session 暫時負責某份規格，於是票面寫入「改此規格前先告知 <session 代號>」。這條約束會被複製進後續的分析票、子票的 how.strategy 和執行日誌。

該 session 結束後，約束仍以原代號流傳。執行者照票面要告知，卻在存活 session 清單裡找不到這個代號，只能停手問協調者「這是誰、現在由誰持有」。協調者也得回頭翻舊票，才查得出代號原本的角色。

實證（2026-10-29）：一條規格維護約束的代號出現在多張 10 月中旬的票，兩週後由新的分析票與其子票繼承。那時該 session 早已結束，期間的規格修改也已改由執行線改寫、協調者審查，約束其實早就失效，只是票面沒有反映。

## 根因

**約束綁的是實例，不是角色**。「告知 X」真正要的是「讓規格維護角色核對連動」，寫成 session 代號，等於把角色和一個有生命週期的實例綁在一起。實例結束時，角色可能已經轉移，票面卻不會跟著變。

**角色轉移沒有回寫點**。維護角色從某個 session 轉給協調者時，沒有任何動作會掃描並改寫既有票面上的代號，所以失效的約束會一路被繼承下去。

## 解決方案

- 執行者遇到找不到的代號時，交給協調者裁定現行持有者，並在票面改註為角色名稱加裁定出處。
- 協調者在協調票記下角色的現行持有者，供後續查詢。

## 預防措施

- 票面約束用角色名稱寫（「規格維護者」「協調者」），角色與 session 的對照只放在協調票的一處。
- 某個 session 結束或交出角色時，交接清單要包含「grep 票面上本代號的約束並改寫」。
- 建子票、複製 strategy 時，若遇到 session 代號，先確認它是否還存活。
