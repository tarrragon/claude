# PC-GPD-012: 共識不構成查證——繼承來的前提在交叉檢查中免於審查

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-GPD-012 |
| 類別 | process-compliance |
| 風險等級 | 高 |
| 發現日期 | 2026-09-08 |
| 來源版本 | 0.1.0 |

## 症狀

兩個以上的行為者各自獨立查證、互相挑錯、多次推翻彼此的結論——**過程沒有任何鬆懈，結論照樣錯**。錯誤來自一個雙方共享但從未被任何一方檢查的前提。

**識別特徵**：

- 錯誤的論斷是雙方都同意的，且同意發生得很早、很自然，沒有人記得它被討論過
- 該前提在後續每一輪論證中被當作已知條件重複使用，因此看起來被反覆確認過（實際是被反覆引用）
- 交叉檢查的密度越高，錯誤越穩固——每一輪都在前提之上展開，沒有一輪回頭檢查前提本身
- 由**未參與該對話的第三方**指出，而非由密集互查的雙方發現
- 事後回顧，該前提查證成本極低（通常是讀一個常數或一段條件判斷）

## 根因

**共識只證明前提被共享，不證明前提被檢查過。**

多方協作提高的是「已提出的論斷被挑戰」的機率，不是「未被提出的前提被檢視」的機率。前提之所以是前提，正因為它不在論證的討論面上——它是雙方展開論證的地面，而地面不會被走在上面的人測試。

信任加劇此效應且無法靠減少信任解決：協作者之所以被信任，是因為他們的查證多數時候正確（本案例中雙方互相推翻三次皆成立）。這個信任有正當基礎，但它會讓**繼承而來的前提免於審查**——接收方把「對方也這麼認為」計為一次驗證，而對方從未驗證過它。

因此本模式與「協作品質不足」無關，它出現在協作品質高的情境；協作品質低時反而不會累積出這種穩固的錯誤，因為論證不會走到那麼深。

## 實例

三個 session 就一個框架守衛的行為達成共識，寫進 canonical issue 的主文作為核心論斷：

> 守衛擋的不是危險的合併，是慢了一步的合併。

雙方在此結論之前已互相推翻三次（衝突解決的推論、表格轉述的指控、實例歸屬的判定），每次都由被推翻方查證後接受。但共享前提「fast-forward 略過守衛」被讀成「fast-forward 略過內容檢查」——**兩處的「略過」不是同一件事**：FF 略過的只有 `_check_branch_verify`（判定「你現在站在哪個分支上提交」），內容檢查綁在 ref 寫入事件、涵蓋 `refs/heads/*` 全部，內容早在 feature 分支落地時已受檢。

查證成本是讀兩行常數判定（`_HEADS_PREFIX` 的定義與使用）。由一個未參與該對話的 session 提出異議才被發現。

後果：canonical issue 的主文把一個一致的狀態描述為缺陷，會引導其他 consumer 去修一個沒有壞的機制。更正需公開撤回核心論斷。

## 預防措施

**標記前提的來源，把「繼承來的」與「自己查的」分開。**這是本模式的處方，與量錯維度（`PC-GPD-009`）的「量對維度」、過濾產物失真（`PC-GPD-011`）的「留全量」是不同的動作。

| 情境 | 動作 |
|------|------|
| 採信協作者提供的事實 | 記下「此項來自 X，我未獨立查證」；引用它下結論前補查 |
| 準備把結論寫入跨 consumer 載體（issue、方法論、規則） | 逐條列出結論所依賴的前提，對每一條問「誰查過？以什麼證據？」——答不出證據的即為未查證 |
| 論證進行了三輪以上而前提從未被重述 | 停下來重述前提並查證；論證越深，前提被檢查的機率越低 |
| 要推翻或修改自己先前的公開論斷 | 先自行查證再改，不因對方說服而改——說服與證據是兩件事 |

**判別問句**：「這個結論如果錯，最可能錯在哪個我從沒查過、但一直當作已知的東西上？」
