# PC-GPD-051: 驗收以「某字面在目錄與歷史中計數為 0」判定，文件為了說明這項檢查而寫出該字面，檢查被自己污染；寫入歷史後只能靠改寫歷史歸零

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-10-29 |

## 症狀

驗收條件寫成「`grep <字面>` 在目錄與 `git log -p` 中的計數皆為 0」，用來確認機密（如 API key 的前綴）沒有外洩。之後撰寫協議或說明文件時，為了交代這項檢查，把那個字面原樣寫進受檢目錄裡的檔案。

commit 之後計數變成 1。即使下一個 commit 立刻改寫，`git log -p` 仍會留下新增行與刪除行，計數至少為 2。要讓字面計數歸零，只能改寫已推送的歷史，也就是 force push。這通常不在授權範圍內，還會影響共用這條歷史的其他人。

實證（2026-10-29）：研究資料目錄的取樣協議附錄寫了「提交前 <前綴> 計數必須為 0」，commit 後自查計數為 1，立即改寫；歷史中留下 2 筆，都是說明句本身。改以 key 的完整形狀（前綴加長度、字元集）做 regex 搜尋，歷史與目錄皆為 0，證明沒有真的外洩。

## 根因

**檢查對象與檢查說明共用同一個字面，卻落在同一個受檢範圍內**。字面計數無法區分「機密本身」與「提到這個機密格式的文字」，任何說明這項檢查的文件都會讓它失敗。

**檢查以字面而不是形狀定義**。只比對前綴，比對的是一個常見的短字串，不是機密的完整格式，說明文字、範例、測試替身都會命中。

## 解決方案

- 改以機密的完整形狀做 regex 檢查（前綴、分段、最小長度、字元集），說明文字不會命中。
- 字面計數若仍要保留，就另外列出，並逐筆說明命中的是什麼。
- 已推送的命中不改寫歷史，改在報告揭露。

## 預防措施

- 設計「計數為 0」的驗收時，同時決定說明文件怎麼指稱這個字面（例如寫「AC 編號的字串」或寫出 regex），並寫進驗收本身。
- 機密外洩的檢查一律以形狀 regex 定義，不用短前綴。
- 受檢目錄內的文件，提交前先跑一次該檢查。
