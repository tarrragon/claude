# PC-GPD-036: 線或 session 結束時把發現寫成收尾段的「未開票」備註，結束後無人接手

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-GPD-036 |
| 類別 | process-compliance |
| 風險等級 | 低 |
| 發現日期 | 2026-10-20 |
| 來源版本 | 0.5.0 |

## 症狀

多 session 分線協調時，一條線被裁定結束。結束前，它在票面的收尾段列出結束狀態、檔案位置，並附上一筆實作票 Phase 4 記錄的技術債，標註「未開票」。該技術債為：套件宣告支援的最低 Python 版本，低於新守衛所 import 的標準庫模組要求的版本。

這一行的形式與其他收尾資訊相同，讀起來像已交代清楚。但寫下這行的 session 隨即結束，沒有任何票承接這筆技術債。主控在查證該線的收尾時讀到這行，才代為建票。

## 根因

| 層 | 原因 |
|----|------|
| 寫入端 | 收尾的重點是「把狀態留在票面」，發現被當成狀態的一部分寫下。標註「未開票」說明作者知道該建票，但收尾指示沒有要求這一步，於是延到一個不存在的「之後」 |
| 程序端 | 協調手冊的收尾指示與回報摘要只問佇列、分支、閘門，沒有問「收尾時記下的發現是否已建票」。回報格式裡沒有這一欄，漏掉了也看不出來 |
| 接手端 | 線結束後，收尾段只有主控會讀。主控若只核對 commit 是否在 main，不逐行讀收尾段，這筆發現會永久停在一份已完成票的 Problem Analysis 裡 |

「未開票」三個字等於自承違反「發現即建票」，但一般讀者讀到時不會把它當成待辦。

## 解決方案

1. 線結束前，收尾時記下的技術債或發現先建票，回報摘要列出新建票號。
2. 主控查證一條線的收尾時，逐行讀收尾段；看到尚未開票的發現就代建，`--source-ticket` 指向發現所在的票。
3. 代建前照常查重（本地票與框架 issue），查重結論寫進 why。

## 預防措施

- 協調手冊 multi-session-orchestration 的 `references/wrap-up-and-handoff.md` §1 已補「收尾時記下的發現，結束前先建票，回報列出票號」，並補「PM 查證線的收尾」一段。
- 收尾段若出現「未開票」「之後再開」「待建」等字樣，一律視為待辦，不視為已交代。

## 與其他模式的關係

- 本模式是「發現即建票」（quality-baseline 規則 5）在 session 生命週期邊界上的失效：發現本身被記錄了，但記錄的載體是一份即將結案的票面，而不是一張會被排程的票。
- 與「無 trigger 延後」（decision-trigger-binding 規則 1）同源：「未開票」是沒有綁定 ticket 的延後。

## 實例

2026-10-20，一條協調線結束時在收尾段記下一筆技術債並標「未開票」。主控查證收尾時代建為 P3 實作票，並把收尾程序的缺口補進協調手冊。
