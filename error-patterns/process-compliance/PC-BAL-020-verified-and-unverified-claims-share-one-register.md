# PC-BAL-020：已查證與未查證的陳述共用同一確定語氣

## 基本資訊

- **Pattern ID**: PC-BAL-020
- **分類**: 流程合規（process-compliance）
- **來源版本**: v0.2.1
- **發現日期**: 2026-07-31
- **風險等級**: 高（結論正確使驗收者停止查證，錯誤成分因此寫入持久化產物）
- **影響範圍**: 任何寫入持久化載體的回報——ticket body、分析報告、commit 訊息、交接文件

## 摘要

**一段陳述中，承載結論的成分經過觀察，不承載結論的成分未經觀察，兩者以相同的確定語氣書寫。** 讀者無法從文字分辨哪些被查過，於是整段獲得同一級別的可信度。

錯誤落在裝飾性成分上——成因解釋、舉例、數字分解——這些不影響結論成立，因此驗收若只檢查結論就會全數放行。它們卻進入了持久化產物，後人引用時無從察覺其可信度低於同段的其他句子。

寫作者不是為掩飾不知而編造。他是在補完一段敘述時把**完整性**當成目標，而完整性不要求每個成分都被觀察。

## 症狀

- 結論經覆核成立，但支撐它的具體實例、成因說明或數字分解與事實不符
- 錯誤成分具有高度具體性（確切檔名、確切數字、確切機制），具體性使它讀起來像查過的
- 同一段內出現互相矛盾的數字，而書寫者未察覺（一處由觀察得來、一處由推導得來）
- 查證該成分的成本極低（單一指令、即時完成），且書寫者當下具備執行條件
- 驗收者若只檢查結論，全數放行；發現多屬偶然（讀到時起疑、或注意到段內矛盾）

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 敘述完整性優先於成分可驗證性 | 補一個成因或實例會讓段落更完整、更好讀 | 完整性的誘因壓過「這句我查過嗎」的自問 |
| 語氣無分層機制 | 陳述句不區分「觀察所得」與「推導所得」 | 讀者只能全信或全查，而全查成本高於信任 |
| 結論正確產生溢出的可信度 | 驗收者確認結論後傾向接受整段 | 錯誤成分搭著正確結論通過驗收 |
| 具體性被當成可信度訊號 | 附確切檔名或數字比模糊陳述更像查證過 | 錯誤成分的具體性反而降低被質疑的機率 |

核心是**可信度以段落為單位授予，而查證以成分為單位發生**，兩者粒度不匹配。

## 解決方案

### 書寫端：語氣分層

未經觀察的成分必須降格書寫，或補上查證：

| 原寫法 | 分層後 |
|-------|-------|
| 「命中 0。目錄檔名為 kebab-case（如 `x.md`）」 | 「命中 0（實測）。成因推測為命名慣例變動，未查證」 |
| 「17 passed（新增 4 個，原 13 個）」 | 「17 passed（實測）。增量組成未逐一核對」 |

降格的成本是一句括號，遠低於事後更正。

### 驗收端：拆解至成分

驗收不以結論為單位。對每段問：

1. 這段的結論是什麼？（承載成分）
2. 其餘句子分別主張了什麼？（不承載成分）
3. 每個不承載成分，書寫者要看什麼才能知道？那個東西他看了嗎？

段內數字互相矛盾是最廉價的訊號——不需外部查證即可發現，讀報告時即應觸發。

## 預防措施

| 層級 | 措施 |
|------|------|
| 書寫 | 寫下確切檔名、確切數字、確切成因前，自問「這是我看到的還是我推的」；推的就標為推的 |
| 派發 | prompt 要求回報區分觀察與推導，特別是數字的前後值與增量組成 |
| 驗收 | 逐成分拆解而非逐結論；優先掃段內數字一致性（零成本） |
| 更正 | 發現後以更正而非回退處理——結論成立時產出可用（quality-baseline 規則 6），但更正必須留在同一載體，否則後人仍會讀到原句 |

## 驗證方式

- 對一段回報，列出其承載結論成分與不承載成分；不承載成分若無法指出「書寫者看了什麼」，即為本模式
- 段內出現同一量的兩個不同值即命中，不需外部查證

## 實證案例（三例；例一與例三為 2026-07-31 同一 session，例四為 2026-08-03 併入）

> 編號沿用 `0.2.1-W3-192` 的原始三例判定，其中例二經該票判定屬另一模式，故此處無例二。

### 例一：為已成立的結論補未觀察的解釋

`0.2.1-W3-091` 的 Solution 寫：

> `_count_memory_feedback()` 以 `memory_dir.glob("feedback_*.md")` 掃描。memory 目錄現行檔名為 kebab-case slug（如 `pm-write-path-restrictions.md`），**命中 0**。

| 成分 | 真偽 |
|------|------|
| glob 命中 0 | 真 |
| 成因是檔名改為 kebab-case | 偽——本專案該目錄為空，無檔名可討論 |
| 舉例 `pm-write-path-restrictions.md` | 偽——`find ~/.claude/projects` 全域零命中 |

結論（移除該稽核無行為回歸）成立，但成立機制是目錄為空。查證成本為單一 `ls`。

### 例三：由總量回推未觀察的分解

`0.2.1-W3-191` 的 Test Results 寫「17 passed（新增 4 個測試，原 13 個既有測試全數維持通過）」，同節另一行寫「3 個淨新增測試」。

實測組成為 14 + 3 = 17。後值經觀察，前值由「我加了 4 個」的印象回推，而該印象本身錯誤。段內兩個數字（4 與 3）互相矛盾且書寫者未察覺。

查證指令：`git show <sha> -- <test file> | grep -c "^+    def test_"`，即時完成，且該 commit 是書寫者自己剛做的。

### 例四：錯誤成分是判定依據，當次結論不受影響但判準會被沿用

`0.2.1-W3-019` 分析四個 hook 的 `effort=low` 短路是否可接受。同一份報告內兩類段落：

| 段落類型 | 內容 | 覆核結果（`0.2.1-W3-028`） |
|---|---|---|
| 量測型 | 2492 筆 payload 交叉統計、669 次觀測短路、12 個 hook 清單 | 全部屬實 |
| 讀碼推斷型 | `comment-qa:697` 可接受，依據「無對模型可見輸出」 | 證偽——實有 3 處 `emit_hook_output` |
| 讀碼推斷型 | `ticket-quality-gate:587` 可接受，依據「啟發式建議」 | 證偽——實有 `EXIT_BLOCK(2)` 路徑被旁路 |

四處分類經覆核全部維持，程式碼零變更——證偽的是**依據**不是結論。

本例補上前三例未涵蓋的一類後果：**不承載當次結論，不等於無後果。** 判定依據會被後續作者當判準沿用，而「無輸出所以可短路」與「無阻擋所以可短路」是兩條寬嚴不同的規則。錯誤依據流通後，下一個 hook 作者會以為「只要不 print 就能短路」。

因此驗收時對「依據」的查證強度不可低於對「結論」——結論只影響本次，依據影響往後每一次。

### 四例的共通點

四例查證成本實測皆為單一指令、即時完成，且書寫者當下具備執行條件——**成本不是未查證的原因**。錯誤全部落在非承載結論的成分上，故只驗收結論會全數放行。

## 與相關模式的關係

| 模式 | 關係 |
|------|------|
| `PC-166`（confabulation） | 本模式的虛構實例屬其家族，但三點不同：發生在持久化產物而非對話中的工具結果；成分不承載當次結論（裝飾性如例一、例三，或判定依據如例四）；偵測須逐成分拆解而非比對工具輸出 |
| `PC-BAL-018`（「前提已更正」標記使後手停止驗證） | 同一後果的互補成因。該模式是**有一個明確標記**宣告已查證而使後手止步；本模式是**沒有任何標記**區分已查證與未查證，缺的是分層而非有誤導性標記 |
| `PC-BAL-015`（idle 通知與未落地寫入被讀成代理人未執行） | 相鄰但不同。該模式是回報的分類標籤與實際狀態不對應（見其症狀變體：以字面為真的標籤消化範圍外發現）；本模式的所有標籤皆無誤，問題在陳述的確定性未分層 |
| `PC-BAL-004`（派發者將未查證的事實寫入 ticket context） | 同屬「未查證內容被當事實流通」，但方向與位置相反。該模式發生在**派發端**，未查證內容是**輸入**——派發者為執行者準備 context 時把搜尋結果當事實，執行者依錯誤前提開工；本模式發生在**執行端**，未查證內容是**輸出**——執行者產出的分析內部證據強度不均，驗收者無從分辨。判別方式：問「這段文字是給後續工作用的前提，還是本次工作的產出」，前者查 PC-BAL-004，後者查本模式。兩者可在同一條鏈上接連發生（PC-BAL-004 的錯誤前提被執行者採信後寫進分析結論，即成為本模式的一個成分） |
