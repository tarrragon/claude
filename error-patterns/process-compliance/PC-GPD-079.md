# PC-GPD-079：「未實跑者標為推論」讓跳過紅燈變成合規路徑

## 基本資訊

| 項目 | 內容 |
|------|------|
| Pattern ID | PC-GPD-079 |
| 分類 | process-compliance（派發條文的出口設計） |
| 風險等級 | 中（不會讓錯誤進 main，但新增測試的鑑別力沒有被驗證：測試可能在舊碼上也是綠的，等於沒測到改動） |
| 來源版本 | 0.6.0 |
| 首次觀測 | 2026-11-03 |
| 關聯 | [[PC-BAL-061]] |

## 摘要

**同一句派發條文裡同時寫了義務（先實跑新增測試取得紅燈）和出口（未實跑者標為推論），代理人會走出口。** 出口的原意是讓無法實跑的情況可以誠實記錄，但它沒有限定適用條件，於是「先改產品碼、事後把紅燈標成推論」變成一條不違規的路徑。即使 PM 在 prompt 額外強調紅燈必做，代理人仍可能走同一條路，並在回報中坦白，因為坦白本身就是條文允許的收尾方式。

## 症狀

- 代理人回報「改產品碼前未取得紅燈，Test Results 的紅燈部分標為推論：舊碼會讓某測試紅」。
- 回報誠實、票面也合規，PM 無從以違規處理。
- 同一 session 內多次派發重複出現，包括 prompt 已用粗體強調「本票必做」的那一次。

## 根因

1. **出口沒有條件。** 「未實跑者須標為推論」適用於任何沒跑的情況，不區分「環境無法跑」和「選擇不跑」。代理人照字面讀，兩者都合規。
2. **出口的代價比義務低。** 先跑紅燈要多一輪測試執行；標成推論只要寫一句話。兩條路都合規時，代理人選成本低的那條。
3. **強調不改變條文結構。** prompt 的額外強調只是同一義務再說一次，出口仍然在，代理人仍可援引。

## 解決方案

結果已回來時：

- 鑑別力未驗證的測試，由 PM 在合併前抽查一次：在舊碼上執行新測試，確認它會紅。做不到時，至少在票面標記「新增測試鑑別力未驗證」，不把它當成已驗證的回歸防護。
- 不回退既成工作（產出無害），只補驗證。

## 預防措施

- **出口加條件。** 把出口改寫為只適用於「環境無法執行」（例如缺裝置、缺外部服務），並要求寫出無法執行的原因。「選擇先改產品碼」不在出口內。
- **把紅燈變成提交前置。** 由提交工具或 hook 檢查 Test Results 是否含紅燈輸出摘要；只有推論、且沒有寫明環境原因時，提交前提醒或阻擋。
- **派發時不靠強調。** 需要紅燈時，在 prompt 裡給出要先執行的具體命令與預期失敗的測試名，讓「先跑」成為步驟，而不是要求。

## 實例

- 2026-11-03，一個 Flutter 專案的 PM session 用派發骨架派出三次實作。骨架寫有「修改產品碼前先實跑新增測試，於 Test Results 貼紅燈輸出摘要；未實跑者須標為推論」。其中兩次代理人先改產品碼，回報紅燈為推論；第二次派發的 prompt 另外寫了「前一張票漏了這步，本票必做」，修正輪仍先改了實作才跑測試。
