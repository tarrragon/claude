# PC-BAL-021：待認領的衍生票被範圍較廣的票連帶完成

## 基本資訊

- **Pattern ID**: PC-BAL-021
- **分類**: 流程合規（process-compliance）
- **來源版本**: v0.2.1
- **發現日期**: 2026-08-03
- **風險等級**: 中（重做已完成的工作；若照票面描述套用修改，可能把較新的正確版本改回舊形態）
- **影響範圍**: 任何存在「窄範圍衍生票 + 寬範圍審查票」並存的 ticket backlog

## 摘要

**衍生票在 pending 期間，其驗收條件的實質內容被另一張範圍較廣的票（審查票、重構票、批次修正票）連帶做完，而衍生票的狀態、frontmatter、body 全部沒有任何變化。**

票的狀態機記錄的是「這張票被誰處理過」，不是「這張票描述的缺陷是否還在」。缺陷存不存在是世界平面的事實，票是記錄平面的物件，兩者之間沒有回寫通道（`tool-output-trust-rules` 規則 5 的同一組不對稱）。

接手者若照 acceptance 直接開工，輕則重做，重則把後來改對的內容改回票面描述的舊形態。

## 症狀

- 認領一張 pending 衍生票後，發現目標檔案的現況已滿足部分或全部 acceptance
- 該檔案的 git log 顯示，滿足 acceptance 的變更來自另一張票的 commit，且該票的標題與本票無關
- 本票的 frontmatter 與 body 完全沒有反映這件事——`status` 仍是 `pending`，`updated` 停在建立日
- 連帶完成本票的那張票，其 Solution 不會提到本票 ID（它不知道本票存在）

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 衍生票晚綁定執行 | ANA 產出的 IMP/DOC 進 backlog 排隊，與被修的檔案脫鉤數天到數週 | 排隊期間該檔案可能被任何其他票改動 |
| 寬範圍票不反查 backlog | 審查票／重構票以「檔案」為工作單位，完成時不掃「有哪些 pending 票描述了我剛修掉的東西」 | 連帶完成不留痕跡 |
| 缺陷消失無事件 | ticket 系統對「缺陷被修掉」沒有事件通道，只有人主動 complete 才改狀態 | 票的狀態永遠不會自己變對 |
| 票面描述仍然通順 | 檔案還在、行號可能還在、敘述讀起來合理 | 接手者沒有任何起疑的理由 |

核心是**票以缺陷為描述對象，但狀態機只追蹤票自己被誰碰過**，兩者的更新來源不同。

## 為何機械偵測不可行

直覺的偵測是「建票後 `where.files` 被其他 commit 動過即為候選」。實測此訊號不可用：

| 步驟 | 結果 |
|------|------|
| 掃描 v0.2.1 的 pending 衍生票 | 70 張 |
| 套用「建票後檔案被非本票 commit 動過」 | 36 張命中 |
| 排除目錄型 `where.files`（`.claude/` 等對任何 commit 都命中） | 24 張高特異性候選 |
| 對 3 張逐一實測現況 | 3 張全部仍未完成，皆為誤報 |

誤報的成因是**兩件事不同層級**：commit 動的是檔案，票描述的是缺陷。同一檔案可以被改十次而票描述的那一行毫髮無傷。`.claude/settings.json` 這類高頻共用檔更會讓所有引用它的票同時命中。

實測的三張誤報票：

| 票 | 驗證方式 | 結果 |
|---|---|---|
| `0.2.1-W3-074`（移除 dart-style-guardian-hook 重複註冊） | `grep -c` settings.json | 仍 3 處，重複註冊還在 |
| `0.2.1-W3-075`（handoff_session_mgmt 應註冊或排除） | `grep -c` settings.json | 仍 0 處，未處理 |
| `0.2.1-W3-098`（建 error-patterns README 索引檢查 hook） | `ls .claude/hooks/` | 無對應 hook |

結論：**沒有廉價的全域掃描能取代逐票重驗。** 偵測必須靠「以剛改過的檔案為錨點反查」，不是「以所有 pending 票為錨點正查」——前者的候選集小且時機明確，後者的候選集是整個 backlog 且無時機。

## 解決方案

### 接手端：先重驗現況，再決定要不要開工

認領 stale 衍生票（建立日距今數天以上）後的第一個動作是逐條核對 acceptance 的**當下狀態**，不是讀 Problem Analysis 就開工：

1. 對每條 acceptance，找出能判定其成立與否的最小觀察（讀該行、跑該指令、grep 該字串）
2. 已滿足者，查 `git log -- <file>` 找出是哪張票做的，記入 Problem Analysis
3. 全部已滿足 → 補記依據後 complete，不產生檔案變更
4. 部分已滿足 → 只做剩下的，並在 Completion Info 寫明哪幾條是被誰連帶完成

第 2 步的記錄不可省。缺了它，這張票看起來就像「做了很少卻宣稱完成」。

### 產出端：寬範圍票完成時反查

審查票／重構票 complete 時，以該票 commit 觸及的檔案為錨點，列出 `where.files` 含這些檔案的 pending 票，提示 PM 重驗。錨點是「剛改過的檔案」而非「整個 backlog」，候選集因此可控。

## 預防措施

| 層級 | 措施 |
|------|------|
| 建票 | 衍生票的 `where.files` 寫具體檔案路徑，不寫目錄——目錄型 where 讓任何反查都失去特異性 |
| 認領 | stale 衍生票一律先逐條重驗 acceptance 現況，重驗結果寫入 Problem Analysis |
| 完成（寬範圍票） | 以本票觸及的檔案反查 pending 票，命中者提示重驗 |
| 驗收 | 「未產生檔案變更」的 completed 票，必須附「是誰連帶完成」的 commit 證據，否則視為未執行 |

## 驗證方式

- 認領後對 acceptance 逐條做最小觀察，若任一條在開工前即已成立，即命中本模式
- 對已 completed 且無檔案變更的票，檢查 Completion Info 是否指出連帶完成的來源 commit

## 實證案例（2026-08-03）

`0.2.1-W3-212`（補強 test-effectiveness 變異測試程序的失敗路徑與還原保證）由 `0.2.1-W3-209` 衍生，建立後未被認領。

期間 `0.2.1-W3-210`（對同一 skill 的多輪文字審查）在 Round 1-3 改寫了同一節：

```
-2. 備份後注入，跑測試
-3. 還原
+3. 在複本上注入：複製被測模組到臨時目錄再改，不對正式檔案注入。
+   執行者中途失敗時，正式檔案會被留在被注入狀態且靜默失效
+4. 跑測試，確認工作區乾淨：以版本控制狀態驗證，不依賴記得還原
```

commit：`135c0cfb` / `9574fcc2` / `bec7cb3a`，皆掛在 `0.2.1-W3-210` 名下，訊息未提及 `0.2.1-W3-212`。

三條 acceptance 中，第 1 條（含失敗路徑處理）與第 2 條（還原驗證方式明確）已被上述變更滿足；只有第 3 條（工具化可行性評估）未被觸及。PM 認領後重驗現況才發現，改為只執行第 3 條。

值得注意的是連帶完成的品質**高於**本票原本會做的：`0.2.1-W3-210` 把注入對象從正式檔案改為臨時複本，讓「未還原」這個失敗態不再存在；而本票的 acceptance 只要求「描述失敗路徑」，照字面執行會得到一段更完整的文字說明，但失敗態仍在。若接手者照票面開工而不重驗，很可能把已經結構性消除問題的版本，改回「有問題但有說明」的版本。

## 與相關模式的關係

| 模式 | 關係 |
|------|------|
| `PC-162`（Ticket 描述含過時環境狀態） | 相鄰但成因與偵測皆不同。該模式的 staleness 在**建票當下**就存在（描述基於舊記憶，引用的檔案可能已不存在，機械可測）；本模式的描述在建票時完全正確，staleness 在**排隊期間**累積，且檔案仍在、敘述仍通順，機械不可測 |
| `PC-075`（spawned 與 children 狀態檢查語義不對稱） | 同屬衍生票的狀態失真，方向相反。該模式是 spawned 仍 pending 卻讓來源 ANA 完成（票該擋沒擋）；本模式是 spawned 描述的工作已完成卻仍 pending（票該通沒通） |
| `PC-BAL-018`（「前提已更正」標記使後手停止驗證） | 互補。該模式是**有標記**宣告已查證而使後手止步；本模式是**沒有任何標記**顯示工作已被別票做掉，後手因此不會想到要查 |
