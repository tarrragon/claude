# PC-GPD-066：以版控內容相同沿用另一工作樹的測試結果

## 基本資訊

| 項目 | 內容 |
|------|------|
| Pattern ID | PC-GPD-066 |
| 分類 | process-compliance（驗證結果的沿用） |
| 風險等級 | 中 |
| 來源版本 | 0.5.0 |
| 首次觀測 | 2026-10-13 |
| 關聯 | [[PC-BAL-022]]（以因果範圍核對取代 baseline 對照；本模式是以內容核對取代重跑）、[[PC-GPD-043]]（派進 worktree 的比對未備妥基準）、[[PC-166]] 規則 5（記錄平面與世界平面） |

## 摘要

**以「兩棵樹在版控內的內容相同」為由沿用測試結果，這個論證只涵蓋版控內的輸入。** 典型情境是：測試在隔離工作樹（如 git worktree）跑完，合併後不重跑，直接當成主線的結果。

測試結果另外取決於兩類輸入：

- 不在版控內的輸入：未入庫的套件鎖定檔、建置快取、產生物、本機工具版本。
- 受測樹起跑時的工作區狀態：未提交的修改、未追蹤檔。

論證沒有列出這兩類，結論就只成立一半；受測樹清除後，這一半再也無法補驗。

## 症狀

- 合併後不在主線重跑，以「主線的 `lib`、`test`、設定檔等子樹雜湊與受測樹逐一相同，故全量結果沿用」結案。
- 比對清單只有版控內的路徑；鎖定檔、建置快取、產生物與起跑時的 `git status` 都不在清單上。
- 事後稽核要求補驗時，受測工作樹已清除，起跑狀態沒有任何紀錄，只能在主線整套重跑。

實例（2026-10-13，Flutter 專案）：PM 於 worktree 跑完 analyze、schema 子套件與全量測試，全數通過。合併進主線後，以五個路徑的子樹雜湊與受測樹相同為由沿用結果，未在主線重跑。事後驗收稽核指出論證漏列套件鎖定檔與建置快取，也沒有記錄起跑時的工作區狀態，而受測 worktree 已清除。最後於主線直接重跑全套，並在起跑時記錄 HEAD、鎖定檔的雜湊前綴、`git status --porcelain` 與殘留測試行程數。

## 根因

- **Why**：版控內容相同是可以用雜湊直接驗證的事實，驗證動作本身精確，容易讓人以為整個論證都精確。但「測試結果相同」需要的前提是「所有會影響結果的輸入相同」，版控只是其中一部分。比對清單由論證者列出，論證者只會列出想得到的、可雜湊的項目。
- **Consequence**：

| 層級 | 影響 |
|------|------|
| 結論可信度 | 不在版控內的輸入若不同（鎖定檔解析出不同的套件版本、快取殘留舊產生物、起跑時有未提交的修改），沿用的通過結果不代表主線的狀態 |
| 補驗可能 | 受測工作樹清除後，起跑狀態與不在版控內的檔案一併消失；論證的缺口無法事後補上，只能整套重跑 |
| 稽核成本 | 稽核者要先判定論證缺了什麼，再要求重跑；沿用省下的時間在稽核時付回去 |

## 解決方案

- **Action**：沿用另一工作樹的測試結果前，先列出並比對三類項目；任一類無法比對，就在主線重跑，不沿用。

| 類別 | 要列出的項目 | 比對方式 |
|------|------------|---------|
| 版控內的輸入 | 程式碼、測試、設定檔、宣告檔 | 子樹雜湊（`git rev-parse <ref>:<path>`） |
| 不在版控內而會影響結果的輸入 | 套件鎖定檔（未入庫時）、建置快取、產生物、工具與執行環境版本 | 起跑時記錄檔案雜湊或版本字串；兩邊都要有紀錄才能比對 |
| 受測樹起跑時的狀態 | 未提交的修改、未追蹤檔、殘留的測試行程 | 起跑時記錄 `git status --porcelain` 與行程數；非空時沿用不成立 |

事後發現論證缺項而受測樹已清除時：不嘗試重建當時的狀態，直接在主線重跑，並在起跑時記錄上表第二、三類項目。

## 預防措施

- 在隔離工作樹跑全量測試時，把上表第二、三類的起跑紀錄寫進測試紀錄，讓沿用論證有資料可比。
- 受測工作樹在沿用結論定案前不清除。
- 合併流程若能在合併後的快照上直接跑測試，就不需要沿用論證；有這條路徑時優先走它。
