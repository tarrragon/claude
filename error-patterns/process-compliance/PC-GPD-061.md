# PC-GPD-061: 修改合併閘門某套件的命令時，這次合併只觸及設定檔，閘門依路徑對應不會執行被修改的套件；新命令未經閘門驗證就進 main，錯誤留到下一條線合併時才爆

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 風險等級 | 低 |
| 首次觀察 | 2026-10-31 |

## 症狀

一張票修改閘門宣告檔中某個套件的 command（加一個依賴、多收一個測試目錄）。合併時閘門 rc=0，看起來已驗證。

實際上，閘門依「本次改動的路徑」選套件。這次只改了宣告檔本身，路徑落在設定目錄，對應到的是 hooks 等內建套件，被修改的那個套件（prefixes 指向另一個目錄）沒有被選中。新命令唯一的執行紀錄，是實作者在 worktree 內的手動實測。

若新命令有錯（依賴名稱打錯、目錄路徑錯、YAML 縮排讓 argv 拆錯），合併照樣綠燈。下一個改到該套件 prefixes 的人合併時才會紅燈，而那個人的改動與錯誤無關，會先懷疑自己的程式。

## 根因

**閘門的選擇邏輯以改動路徑為輸入，設定檔不在任何被修改套件的 prefixes 內**。設定檔描述套件，但不屬於套件的觸發範圍，形成自指盲點：改閘門的那一次合併，閘門不檢查自己被改的部分。

**閘門 rc=0 被讀成「這次改動已驗證」**。綠燈只代表「被選中的套件全綠」，不代表「改動涉及的行為已被執行」。讀報告時若不看選中了哪些套件，兩者無從區分。

## 解決方案

- 修改某套件 command 的票，驗收要求實作者以「改後宣告中的同一組 argv」實跑一次，並附一個 E2 正向對照（故意弄壞一條測試，確認 rc 不為 0）。這是閘門之外唯一的驗證，必須寫進 Test Results。
- 合併報告中，寫明「這次閘門跑了哪些套件、沒有跑被修改的套件」，並指名下一次觸及該套件 prefixes 的合併為第一次閘門內執行，屆時核對 passed 數。

## 預防措施

- 驗收閘門結果時，先看「選中了哪些套件」，再看 rc；不把 rc=0 當成「改動已被測過」。
- 框架方向：宣告檔中某套件的區段被修改時，閘門把該套件加入本次的選中集合。屬框架修補，依修補節奏先觀測。

## 變體：反方向的誤報

閘門命令修改後，下一條線合併時已用新命令跑過被修改的套件，報告卻寫「這次閘門不含該目錄」。報告者沒有讀這次的閘門輸出，而是沿用修改前的認知。結果與本模式相反：實際已驗證，紀錄卻說沒有。

判別方式是用固定值核對：逐目錄 `--collect-only` 數測試數，加總後與閘門回報的 passed 數比對。數字相符，代表該目錄已被執行。

預防：合併報告中關於閘門涵蓋範圍的句子，必須出自這次閘門的輸出或計數核對，不能憑先前的印象撰寫。
