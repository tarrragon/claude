# PC-GPD-014: 正確結論配錯誤理由當下無症狀，要等前提改變才暴露，而那時沒人記得回頭查

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-GPD-014 |
| 類別 | process-compliance |
| 風險等級 | 高 |
| 發現日期 | 2026-09-09 |
| 來源版本 | 0.1.0 |

## 問題描述

### 症狀

一則陳述的**結論正確**，但支撐它的**機制解釋錯誤**。當下沒有任何症狀：結論通過每一次觀測、每一次交叉檢查、每一次驗收，因為被檢查的是結論。

錯誤理由造成的損害不在陳述本身，在**下游**：

1. **推論下一步時**：他人把理由當前提往下推一層，得到錯誤的結論。此時錯的不是他的推理，是他繼承的前提。
2. **前提改變時**：理由裡的隱含條件不再成立，正確結論隨之失效——但**錯誤理由不會自己失效**，它會繼續給出看似合理的指引，指向一個已經不安全的做法。

**識別特徵**：

- 陳述形如「X 不會發生，因為 Y」，而 X 不會發生為真、Y 卻不是原因
- 該陳述被引用、被驗收、被寫進規格，全程無人反對——因為結論確實對
- 暴露時機不是觀測，是**有人拿它去推下一步**，或**前提被檢視**

**與錯誤結論的時間結構對比**（本則的核心）：

| | 錯誤結論 | 錯誤理由 |
|---|---|---|
| 當下症狀 | 有——與觀測不符 | **無** |
| 暴露機制 | 下一次觀測即打臉 | 前提改變，或有人往下推一層 |
| 暴露時距 | 短 | **不定，可能很長** |
| 暴露時的處境 | 錯誤仍在視野內 | **通常已無人記得該陳述存在，更不會回頭查它的理由** |

### 根本原因 (5 Why 分析)

1. **Why 1**：為什麼錯誤理由沒被發現？因為驗收檢查的是結論，不是理由。
2. **Why 2**：為什麼驗收只檢查結論？因為結論可與觀測直接比對，理由不行——理由是對機制的主張，要驗證得另外查機制的權威來源。
3. **Why 3**：為什麼不查機制的權威來源？因為結論已經被觀測證實，查證的動機在那一刻消失——**正確的結論構成了停止查證的理由**。
4. **Why 4**：為什麼結論正確就足以停止查證？因為隱含假設是「結論正確代表推導正確」，而這個假設在一對多的情形下不成立：同一個結論可以由多條理由推出，其中只有一條是真的。
5. **Why 5（根本原因）**：**論證的正確性與結論的正確性是兩個獨立性質，而只有後者有廉價的檢驗手段。** 因此在沒有刻意要求的情況下，論證層必然缺乏檢驗——不是因為它不重要，是因為檢驗它需要額外成本而當下沒有觸發該成本的訊號。

## 解決方案

### 正確做法

**一、寫下結論時一併寫下理由，且讓理由可被否證。** 「X 不會發生」是不可稽核的；「X 不會發生，因為載體 L 的性質 P，見 `<權威來源>`」可以被查。一份只寫結論不寫理由的文件，在本模式底下是不可稽核的——**沒有理由就沒有可檢查的對象**。

**二、更正時明寫「結論不變、理由變了」，不要只默默改掉理由。** 讀者若只看到結論沒變，會以為什麼都沒發生。要讓下游知道：先前依該理由做的推論需要重驗。

**三、繼承他人的理由往下推一層之前，先驗證那個理由。** 收到「X 因為 Y」而要用 Y 推導 Z 時，Y 已從結論變成前提，**前提要獨立查證**。這一步的責任在推論者，不在提供者。

**四、機制類主張查權威來源，不查專案內的間接證據。** 「這個框架的元件不會重疊」該查框架原始碼或官方契約，不該從專案內幾個呼叫點的寫法反推。

**五、偵測手段只能作用在論證結構上，不能作用在結論上。** 可機械檢查的形式是：涉及機制的結論句是否附帶理由、理由是否指向可查的來源。**不要試圖用「檢查結論是否正確」來偵測本模式——依定義它會通過。**

### 錯誤做法 (避免)

- 結論被觀測證實後即停止查證其推導
- 更正理由時只改文字不說明理由變了，使下游無從得知需要重驗
- 把他人給的理由直接當前提往下推，不獨立查證
- 從專案內的使用慣例反推框架或函式庫的機制性質
- 以「結論一直都對」作為論證健全的證據
- 設計偵測手段時瞄準結論的正確性

## 實例（2026-09-09，同一 session 內兩則，互為對照）

兩則都由不同的 session 提出，都是正確結論配錯誤理由，且都在**前提被檢視時**才暴露。

### 實例一：暴露於「有人往下推一層」

| 項目 | 內容 |
|------|------|
| 陳述 | 「兩則暫態提示在版面上不會重疊，因為顯示前無條件呼叫了關閉當前提示的方法」 |
| 結論 | 正確——不會重疊 |
| 真實理由 | 該載體的訊息管理器本身持有佇列且**只呈現佇列最前端一則**，不重疊是載體的性質，與呼叫端有沒有先關閉當前提示無關 |
| 錯誤理由實際決定的是什麼 | **取代 vs 排隊**——先關閉再顯示會截斷前一則；不關閉直接顯示則排隊等待。這是另一個軸 |
| 暴露路徑 | 另一 session 發現有一處呼叫**沒有**先關閉當前提示，依錯誤理由推得「不重疊的結論因此失效」。實際上結論仍成立，失效的是理由 |
| 查證手段 | 讀框架 SDK 原始碼，確認訊息管理器的佇列型別與只呈現首項的實作 |

**若不更正的後果**：日後換成非該訊息管理器的載體時，「佇列保證單一呈現」這個前提不再成立，而「先關閉所以安全」這個錯誤理由會讓人以為照樣先關閉就沒事。

### 實例二：暴露於「前提被查到不成立」

| 項目 | 內容 |
|------|------|
| 陳述 | 「把日誌加在元件內部涵蓋全部呼叫點含未來新增的，結構上不可能漏」 |
| 結論 | 正確——在其適用範圍內確實不可能漏 |
| 未被說出的前提 | **所有提示都經過該元件** |
| 暴露路徑 | 查到有一處直接呼叫框架原生 API、完全繞過該元件，因此零日誌 |
| 正確表述 | 「**在所有呼叫都經過元件的前提下**不可能漏」，且該前提本身需要被強制（例如禁用原生 API 直呼），否則它只是假設 |

**共通形態**：兩則的錯誤都不在觀測，在**對觀測結果的機制解釋**。兩則都通過了當時的所有檢查。

## 與相鄰模式的分界

| 模式 | 錯在哪 | 當下有無症狀 |
|------|-------|-------------|
| `PC-GPD-009`（驗證器量錯軸） | **量測**——檢查器量的是代理指標而非宣稱保證的性質，輸出可信但答非所問 | 結論可能錯，缺陷完好無損 |
| `PC-GPD-012`（共識不構成查證） | **查證的獨立性**——繼承來的前提在交叉檢查中免於審查 | 多方一致，看似已驗證 |
| **本則** | **理由**——量測沒問題、結論沒問題，錯的是支撐結論的機制解釋 | **完全無症狀** |

與 `PC-GPD-012` 相鄰但不重疊：該則講**前提為何逃過審查**（因為被共享故不被質疑），本則講**理由錯了為何長期無代價**（因為檢驗只落在結論）。兩者可同時發生——實例一即是：理由由一方提供、另一方繼承後未查證即往下推。
