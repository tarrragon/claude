# PC-GPD-052: 並行 session 協作時，執行線預告「做 X 前會先申請」，主控把它記成待收的回報，執行線卻停下來等一個從未送出的申請被核准；雙方都以為下一步在對方，工作靜默空轉

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-10-30 |

## 症狀

執行線在回報末尾寫「接下來做 Y，跑測試前會先申請時段」。主控讀到後，把這句理解為「執行線會在需要時主動申請」，於是等候下一則回報，不再追問。執行線則把同一句話理解為「時段要先被核准才能動手」，停在 claim 之前等核准。

雙方都沒有違反任何規則，各自也都在「等待」，因此沒有錯誤訊息，也沒有逾時訊號。工作就這樣空轉，直到用戶察覺兩條線都沒有動靜才發現。

實證（2026-10-30）：執行線回報收尾並宣布下一張票，之後一整晚沒有新的 commit，票仍是 pending，也沒有 worktree。主控查詢後，執行線回覆「沒有卡住，在等時段」，並在該回覆中才第一次正式提出申請。

## 根因

**預告沒有綁定行動者**。「會先申請」描述的是未來的一個動作，但沒有說清楚由誰在什麼時點發出。讀的一方可以把它讀成「對方會發」，也可以讀成「我在等對方同意」，兩種讀法都說得通。

**等待在外觀上和進行中相同**。跨 session 協作時，主控只看得到對方的訊息和 git 痕跡。對方在等、在跑長指令、在等權限提示，三者在主控端都同樣是「沒有新訊息」。沒有預期回報時點的話，靜默無法和正常進行區分。

## 解決方案

- 主控收到「之後會申請／會回報」這類預告時，當下就把它轉成明確的下一步：當場核准（「時段先給你，開始時回報」），或要求對方立刻送出申請。不要把預告記成待收事項。
- 執行線需要核准才能動手時，申請要在同一則訊息直接送出，不要只寫成預告。

## 預防措施

- 回報的最後一行，寫明下一步由誰執行；如果是等待，寫清楚在等什麼。
- 主控對每條線記錄「預期下次回報的觸發事件」，例如「閘門結果」「傾印完成」。觸發事件不明確的靜默，視為需要追問。
- 協作 skill 的共用時段規則，要明寫申請由使用方主動發出，核准方不負責推測需求。
