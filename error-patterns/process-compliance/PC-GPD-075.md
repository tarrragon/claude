# PC-GPD-075：被契約測試綁住的規格與實作要同批進 main

## 基本資訊

| 項目 | 內容 |
|------|------|
| Pattern ID | PC-GPD-075 |
| 分類 | process-compliance（建票切分與合併閘門） |
| 風險等級 | 中（不會讓錯誤進 main，但會讓文件票卡在閘門，需要 incident 分析與返工） |
| 來源版本 | 0.6.0 |
| 首次觀測 | 2026-11-02 |
| 關聯 | [[PC-BAL-036]]、[[TEST-GPD-002]] |

## 摘要

**如果有一支契約測試同時讀規格文件和實作產物，並斷言兩者一致，那麼改規格與改實作必須放在同一張票、同一批合併。** 依「文件先行」的習慣拆成文件票與實作票時，不論哪一張先進 main，閘門裡的契約測試都會看到只有一側更新，於是翻紅。

## 症狀

- 文件票只改規格文件（不碰程式碼與測試），代理人在 worktree 跑的是該票相關測試，沒有跑到那支契約測試，因此提交時一切正常。
- 送合併閘門跑全套件時，契約測試失敗。訊息通常是「規格列出的項目在實作產物中找不到」，或固定計數斷言不符（例：`hasLength(N)` 變成 N+1）。
- 實作票排在文件票之後，`blockedBy` 指向文件票，兩張互等：文件票等實作補齊才能過閘門，實作票等文件票合併才能開工。

## 根因

1. **建票時沒有盤點跨產物的契約測試。** 切分依據是「改哪一類檔案」（docs／lib／ARB），但實際的耦合單位是「哪些檔案被同一個斷言讀取」。後者在檔案類型上看不出來。
2. **「純文件票不影響測試」是錯誤前提。** 測試套件可以讀取任何檔案。只要有測試以 `File(...)` 讀規格文件，該規格就屬於測試輸入，不再是單純的文件。
3. **代理人只跑相關測試。** 規則要求代理人只跑該票相關的測試檔，全套件留給合併閘門。所以這類衝突一定在閘門才會發現，而且是最貴的發現時點。

## 解決方案

票已拆、閘門已紅時，有兩種處理方式，依「哪一側已定案」選擇：

- **A：把另一側併進同一張票。** 文件票補上實作產物（ARB 條目、計數更新），同批合併。適用於實作側很小、文件票的執行者有權限改的情況。
- **B：把會被斷言讀到的那部分從文件票移出。** 規格改用契約測試不會解析的形式記載（例：表格列改為表外敘述，並註明由實作票同批加入表列），文件票先合併；實作票同批補回表列、實作產物與計數。適用於實作側需要另一位代理人、或文件票的執行者不得改程式碼的情況。

## 預防措施

- **建票前盤點契約測試。** 拆分規格與實作前，先搜尋測試碼中讀取該規格檔的位置（例：`grep -rn "<規格檔名>" test/`）。有命中時，把命中的斷言範圍視為不可拆的單位。
- **契約測試要能提示耦合。** 契約測試的檔頭註解寫明它讀取哪些規格檔、哪些區段，讓建票者搜尋規格檔名就能找到它。
- **固定計數斷言改為推導值。** `hasLength(N)` 這類寫死的計數，會讓任何單側新增都翻紅，即使兩側最後會一致。改為比對兩側集合相等，可以把失敗訊息從「數量不符」變成「缺哪一個 key」，診斷更直接。

## 實例

- 2026-11-02，一個 Flutter 專案的文件票在元件庫規格的 i18n key 表新增 3 個 key，ARB 條目交給後續實作票。合併閘門的契約測試逐列比對 key 表與 ARB，並斷言 key 數固定為 32，結果變成 33，翻紅。incident 分析確認根因是同批契約被拆成兩票，處理採方案 B：三個 key 改為表外敘述，表列、ARB 條目與計數由實作票同批加入。
