# PC-BAL-064：判準的驗證取樣落在單一維度的單一格，適用範圍被誤讀為全域

## 基本資訊

| 欄位 | 值 |
|------|-----|
| 風險等級 | 高 |
| 來源 | 跨 session 框架修復（2026-09-03），三個獨立實例 |
| 發現日期 | 2026-09-03 |

## 摘要

**驗證一個判準時只問「它對不對」，不問「我的取樣落在哪些維度的哪一格」，得到的結論只在該格成立，卻被當作全域結論使用。** 判準在被驗證的那一格確實正確，故驗證通過；換格後鑑別力歸零或翻轉，而換格不會產生任何訊號。

與樣本數不足（見邊界）不同：本模式的樣本可以很多，只要全部落在同一格，增加數量不改善涵蓋。

## 症狀

- 判準經驗證通過，實務使用時卻在某類情境下系統性失效
- 失效情境與驗證情境的差別不在數量而在種類，且該差別在驗證當下不被視為變因
- 事後回看，驗證用的樣本全部具有某個共同屬性，而該屬性未被列為條件
- 判準的表述不含適用範圍，讀者預設為全域
- 換格後的失效多為靜默：判準給出答案，只是答案不再有鑑別力

## 根因

1. **維度只有在被列舉後才可見。** 驗證者知道自己測了什麼，不知道自己沒測什麼——未列舉的維度不會在驗證過程中以缺席的形式出現。
2. **順利路徑掩蓋隱含條件。** 驗證在最自然的情境下進行，而最自然的情境往往是各維度的預設格；預設格成立的條件不會被察覺為條件。
3. **判準表述省略適用範圍。** 寫下的是「以 X 判斷 Y」，不是「在條件 Z 下以 X 判斷 Y」，讀者無從得知 Z 存在。

## 防護

驗證判準時，逐一列舉下列維度並記錄取樣落在哪一格；只取一格者，判準的適用範圍即以該格為限，須在結論中明寫。

| 維度 | 兩端範例 |
|------|---------|
| 族群 | 自有與他有、內部與外部、本層與跨層 |
| 基數 | N=1 與 N>1（單一元素時，「該元素消失」與「整個集合消失」同形） |
| 時序 | 單側變更與雙側變更、變更前與變更後、同步與非同步 |
| 狀態 | 執行中與已停止、初始與穩態、正常與降級 |

本表為最小集，依判準性質增列。**檢查問句**：我的樣本是否全部共有某個屬性？若是，該屬性即為未列出的條件。

**對應根因 3 的動作——明寫歸納來源**：判準或條款寫下時，附上它歸納自哪些案例（「本條歸納自 argparse 長輸出案例」）。來源案例的偶然特徵（該例輸出很長）會被讀者當成必要條件；附來源後，讀者面對不同情況（3 行短輸出）時知道要自行判斷是否適用，而非預設涵蓋。適用範圍因此從隱含變顯式。此動作由另一 consumer 在其判準撰寫票中先行採用（2026-09-03），本筆收為通用防護。

### 更省的觸發方式：外部的開放追問

枚舉四個維度要求驗證者**主動想到**要枚舉，而根因 1 正是「未列舉的維度對驗證者不可見」——要求不可見的東西提醒自己去找，成立條件苛刻。

實測顯示更便宜的替代存在：**下結論前由外部問一次「你怎麼知道」或「這樣夠嗎」即可**。該追問不需指向任何具體缺口，提問者也不需懂該領域。它有效的機制是要求驗證者**重走一次過程**，而非重看一次結論——重看結論只會再次確認結論，重走過程才會碰到未取樣的格。

兩者的成本差別在：枚舉要求驗證者想到，追問只要求他回答。故實務上優先建立追問的時機（結論產出後、據以行動前），枚舉清單作為追問無人可問時的自助版本。

**邊界一（形式）**：追問須為開放式且不預設答案。「這個判準對嗎」會得到「對」（驗證者已驗過那一格）；「你怎麼知道它對」才會逼出取樣範圍。

**邊界二（時機）**：追問須發生在結論被據以行動之前。重走過程的成本隨結論已落地的程度上升——結論尚未落地時重走只需重查，已依該結論改動產物後重走則須連帶推翻既成工作，此時驗證者傾向辯護而非重查。故追問的時機是其有效性的條件，不只是形式。實務落點：結論產出後、據以行動前，該窗口一過，同一句追問的效力顯著下降。

**追問只創造機會，機會須有人接**：外部追問無法強制對方重走過程。對方若以既有結論作答（重看結論而非重走過程），追問不產生任何效果。故本防護的實際強度依賴接收方的回應方式，與 `PC-BAL-062` 的「本條無執法層」同屬自律層機制。

## 兩個下游效應

### 一、寫下的防護宣稱會繼承其驗證範圍，讀者卻讀成全域

防護若在單一格驗證後被寫成無範圍限定的宣稱（「已避免 X」「已處理 Y」），該宣稱在文件上長期存在，而**防護的存在本身成為不再檢查的理由**。這比「沒人想過這個問題」嚴重：無防護時讀者會自行判斷風險，有宣稱時讀者認為這一塊已處理過。

實例：一支 hook 的 docstring 載明「content 內文出現該關鍵字不會觸發（避免自我實測時的 false positive）」。該防護在 content 參數這條軸上確實有效，但正則以 `search` 掃整個命令字串，content 之外的任何位置仍會命中——**風險被預見過、防護也寫了，防的是另一條軸**。

**Action**：防護宣稱須帶適用範圍（「已避免 content 內文誤觸發」而非「已避免 false positive」）。範圍寫在宣稱裡，讀者才有機會發現自己的情境不在範圍內。

### 二、修法收益不得以觀察到的發生次數估計

當缺陷的**發生**與其**被觀察到**依賴不同條件時，觀察次數是發生次數的下界而非估計值，且兩者的比例未知。以觀察次數估計收益會系統性低估。

實例對照：同一支 hook 的誤觸發每次符合條件的呼叫都在發生；被觀察到則需額外條件——一方是 CLI 拒絕與 hook 宣告兩個矛盾訊號恰好同時可見，另一方（同族的 `append-log` 靜默失敗）因輸出以 `tail` 截斷而三次未被發現，失敗與成功的回音在該截斷下完全同形。

**Action**：判定優先級時分開估計發生條件與觀察條件。兩者差距大者，優先級應依發生條件而非回報次數決定。

### 三、驗證工具本身的涵蓋範圍未被驗證，而正確的結果會掩蓋它

本模式多一層：不只判準的取樣落在單一格，**用來驗證判準的工具**（grep pattern、進程探針、計數命令）其涵蓋範圍同樣未被驗證。此層更難察覺，因為驗證工具給出**符合預期的結果時不會觸發任何重查**——只有結果與預期矛盾才會有人回頭看工具。

兩個實例（同一天、兩個 consumer）：

| 實例 | 工具的涵蓋缺口 | 如何被發現 |
|------|--------------|-----------|
| 以 `grep -c 'issuecomment-55236'` 數回填的四個連結，得 3 | 前綴從可見的多數歸納，四個 id 中一個以 `55235` 開頭不在範圍 | 數字對不上。**若當時第四個 id 也以 `55236` 開頭，得到 4，pattern 的缺口永遠不會被發現** |
| 以 `ps aux \| grep "[p]ytest"` 數進程，得 3 與 2，實際為 0 | 命令列含字面字串 `pytest`，被自己的 `ps` 匹配 | 使用者追問「我沒看到代理人在執行」 |

**Action**：陰性結果先懷疑探針（既有規則），陽性結果同樣不證明探針正確——驗證工具用於下結論前，先用一個**已知答案**的輸入跑一次確認其涵蓋（已知有 4 個連結時 pattern 是否數到 4；已知 0 個進程時探針是否回 0）。無已知答案可用時，在結論中明寫「驗證工具的涵蓋範圍未經確認」。

#### 再一層：流程未記錄時，結果對不對無從判斷

上文處理「結果對而流程可能錯」。另有一層更難：**流程沒被記錄時，連判斷流程的材料都不存在**。以「查證是否記錄」與「結果是否正確」兩軸：

| 流程記錄 | 結果 | 可判斷嗎 | 後果 |
|---------|------|---------|------|
| 有 | 對 | 可 | 正常 |
| 有 | 錯 | 可 | 能發現並修正 |
| **無** | **對** | **否** | 在每個可觀察訊號上與第一列完全相同，下次沿用時才暴露 |
| 無 | 錯 | 否 | 錯誤延續且無跡可循 |

第三列最難處理：它不是處置讓問題更難看見，是**省略記錄**讓問題無從被看見。實例：一方查證「既有 77 張 issue 無同領域者」結論正確，但未記錄所用關鍵字集合，另一方採信該結論而無從重跑；後補查時用了五組關鍵字並寫入 issue body，使該集合本身成為可被檢驗的對象。

**Action**：查證類結論須連同**所用工具與輸入**（關鍵字集合、命令、取樣範圍）一起記錄，不只記結果。正確的查證結果配上不可重現的流程，與不可驗證沒有差別。

## 邊界

### 同一根因的兩個方向：過窄與過寬

本筆主文處理**過窄**——該涵蓋的沒涵蓋，使用者以為安全（截斷方向條款只寫長輸出，3 行短輸出同樣命中）。同一根因（判準的適用範圍未經枚舉即被寫下）另有**過寬**方向——不該涵蓋的被涵蓋，合法操作被擋。實例：命令守衛以命令位置 token 判定 `reset --hard`，不看 `-C` 指向的目標，拋棄式 clone 上的同一命令也被擋；命中為真陽性，但擋它沒有保護價值。

| 方向 | 後果 | 讀者遇邊界情況時的問題 |
|------|------|---------------------|
| 過窄 | 該涵蓋的沒涵蓋 | 「條款沒涵蓋我，我要自行判斷是否適用」 |
| 過寬 | 不該涵蓋的被涵蓋 | 「條款涵蓋了我，但這是誤擋還是真違規」 |

兩種判斷都需要條款的歸納來源（見防護節「明寫歸納來源」）；只寫結論的條款，讀者分不出自己是漏網還是誤傷。

**過寬會轉化為過窄**：過寬通常被判為可接受（保守優於漏擋），但代價不是零——繞道成本若高到讓執行者想繞過守衛，執行者不再遵守它而是找方法讓它不觸發，此時守衛對該執行者的實際涵蓋歸零。轉化條件是繞道成本，不是誤擋次數。實例對照：`-C` 目標誤擋的繞道是重新 clone（成本低，未轉化）；守衛 DENY 訊息未給可達路徑時執行者改走 `-a` 豁免（`PC-BAL-024` 案例二，已轉化）。**Action**：判定過寬「可接受」時，同時記下該情境的繞道成本；若日後同類操作出現反覆執行的流程（如拋棄式 clone 上需多次 reset 的驗證），繞道成本累積即為重看涵蓋範圍的觸發點。

**同一事實的兩種讀法**：守衛剛修好時的第一次命中，可讀為「它會動」（運作確認）或「涵蓋可能過寬」（準度質疑）。命中樣本不足時前者優先——先確認會動，再談準不準；樣本累積後第二種讀法才有材料。

- 與 `PC-BAL-050`（單點量測升級為分佈宣稱）、`PC-168`（N<5 取樣的幸運連勝）處理的是**取樣數量**——樣本太少使結論不穩。本筆處理的是**取樣維度**——樣本可以很多，只要全落在同一格，增加數量不改善涵蓋。兩者的處置不同：前者加樣本數，後者換格。
- 與 `PC-BAL-045` 為總分關係：該筆是本模式在「觀測面涵蓋範圍」上的具體實例（其更正段記載「觀測面數量不能替代涵蓋範圍的確認」），本筆是該句的一般形式並補上可枚舉的維度清單。

## 實例

同一次跨 session 框架修復中出現三個獨立實例，分屬三個維度：

| 維度 | 實例 |
|------|------|
| 族群 | 判定「代理人清單未列出即已停止」。驗證用的是本 session 自有的代理人，該格成立；目標族群是他 session 所屬的代理人，該清單完全不列，判準鑑別力歸零 |
| 基數 | 記錄「停止代理人後清單區塊消失」並據此設計判準。驗證時僅有一個代理人，N=1 下「該列消失」與「整個區塊消失」同形；另一方持有 20 個時停止其一，該列消失而區塊保留。以區塊存在性為判準者在 N>1 恆為真 |
| 時序 | 判定「三方合併無衝突即代表兩側內容一致」。該推論在雙側皆變更時成立；單側變更時合併同樣不衝突而是靜默採納，故「無衝突」對「兩側是否一致」無鑑別力 |

三者的共同結構：判準在被驗證的那一格正確，換格後失效，而換格本身不產生訊號。三者皆由第三方指出，非驗證者自行發現——這一點與根因 1 一致：未列舉的維度對驗證者不可見。

### 第三方的門檻比預期低：兩個開放追問實例

上述三例的指出者為另一名驗證者（懂該領域、能自行定位缺口）。另有兩例顯示門檻更低：

| 實例 | 追問內容 | 逼出的結果 |
|------|---------|-----------|
| 一份評估的三處實質錯誤 | 使用者問「這樣夠嗎、不需要再探索了嗎」 | 驗證者回頭逐字讀主檔，發現三處錯誤。追問前對該評估無任何不安 |
| 代理人狀態誤判 | 使用者問「我沒看到代理人在執行，這合理嗎」 | 同時逼出兩件事：該代理人實為停滯而非執行中（原判斷來自採信其自我回報）、以及查證用的進程探針正在自我匹配（命令列含字面字串被自己的 `ps` 匹配到） |

兩例的提問者皆未指向任何具體缺口，也未預設答案。故「第三方」不需具備領域知識，也不需知道問題在哪——**只需是外部的、不預設答案的追問**。其有效性來自它要求對方重走過程，而重走過程才會碰到未取樣的格。
