# PC-BAL-047: 守衛的禁止範圍大於受控介面的提供範圍，差集成為無合法路徑的操作

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 風險等級 | 中 |
| 首次觀察 | 2026-08-18 |

## 症狀

一份資料同時受兩個機制管理：守衛（guard）禁止直接編輯，受控介面（CLI 子命令、API）提供合法的修改途徑。兩者的覆蓋範圍各自演化，當守衛的禁止範圍大於介面的提供範圍時，差集內的欄位既不能直接改、也沒有命令可以改——該欄位進入不可修改狀態，且沒有任何錯誤訊息會說明這件事。

加深誤導的是守衛的阻擋訊息：它通常列出「請改用以下命令」的清單，而該清單是撰寫守衛當時的介面快照。介面後續若未擴充，清單會持續指引使用者去用不存在或不涵蓋該欄位的命令。使用者依訊息嘗試，得到的是另一個失敗，而非「此欄位無合法途徑」的明確告知。

實證（2026-08-18）：ticket 系統的 `title` 欄位——CLI 子命令清單無 `set-title`；相鄰的 `set-what` 只改 `what` 不同步 `title`；直接編輯 frontmatter 被 guard 以 exit 2 阻擋，其訊息列出六個替代命令，其中無一能改 `title`。結果是某張票依上游評估結論縮小範圍後，`what` 與 `acceptance` 已更新而 `title` 停留在舊範圍，且無法修復。此不一致有實際後果：清單類視圖（dashboard、runqueue）顯示的是 `title`，接手者依它判斷是否認領，取得與實際範圍不符的認知。

## 根因

**兩個機制的擴充驅動力不同**。守衛的擴充驅動力是「防止誤改」，其自然寫法是對整份資料設一道禁令（禁止直接編輯 frontmatter），一次覆蓋全部欄位。受控介面的擴充驅動力是「有人需要改這個欄位」，逐欄位增量新增。前者一次到位、後者按需成長，差集因此在守衛建立的當下就存在，並隨新欄位加入而擴大。

**差集不可觀測**。沒有任何機制比對「守衛禁止的範圍」與「介面提供的範圍」。差集只在有人實際需要修改該欄位時才暴露，而那通常是在一個更大的任務中途——發現時的自然反應是繞道或放棄，不是回頭修工具。

**阻擋訊息是靜態快照**。守衛的訊息硬編碼了替代命令清單，與介面的實際子命令沒有共用來源。介面新增或移除子命令時，訊息不會同步。這使訊息從「協助」退化為「誤導」，且退化過程無訊號。

**generic 化**：任何「以守衛禁止直接操作 + 以受控介面提供合法途徑」的組合皆可重現——資料庫的觸發器禁止直接 UPDATE 加上 stored procedure 介面、檔案系統的唯讀掛載加上管理工具、API gateway 的欄位白名單加上 admin console。共同結構是「禁止面與提供面由兩份獨立定義維護，而正確性取決於兩者的差集為空」。

## 解決方案

差集為空是這類設計的正確性條件，應使其可驗證而非靠人工維持。

| 步驟 | 動作 |
|------|------|
| 1 | 明確列出守衛的禁止範圍（哪些欄位不可直接改）與介面的提供範圍（哪些欄位有 setter） |
| 2 | 比對兩者差集。差集非空時，對每個欄位判定：補 setter、或將該欄位移出守衛範圍、或明確宣告其為不可變欄位 |
| 3 | 「不可變」是合法結論但必須顯性——守衛訊息應能區分「此欄位請改用命令 X」與「此欄位設計上不可修改」，兩者對使用者的下一步完全不同 |
| 4 | 阻擋訊息的替代命令清單改為由介面的實際子命令註冊表生成，而非硬編碼 |

**判定「補 setter」還是「宣告不可變」的依據**：該欄位是否會因合法的業務事件而需要變更。若某欄位在物件生命週期中確實可能需要修訂（範圍調整、錯字、上游結論變化），它就需要 setter；若它是建立時決定且永不改變的識別符，宣告不可變才正確。實證案例中 `title` 屬前者——票的範圍會因上游評估結論而縮小，屆時 title 必須跟著改。

## 預防措施

| 層級 | 措施 |
|------|------|
| 設計層 | 新增受守衛保護的欄位時，同步決定其修改途徑（setter / 不可變宣告），不留「之後再說」 |
| 工具層 | 阻擋訊息的替代命令清單由介面註冊表生成，使清單不可能過期 |
| 偵測層 | 對「守衛禁止範圍」與「介面提供範圍」的差集做自動比對，非空且未標記為不可變者發出提示 |

**訊號**：當使用者為了修改一個欄位而開始尋找繞道（直接改檔、用 `--force`、改用其他工具）時，這通常不是使用者不守規矩，而是差集暴露了。把繞道行為當成缺口訊號，而非合規問題。
