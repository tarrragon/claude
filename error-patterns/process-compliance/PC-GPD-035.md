# PC-GPD-035: 守衛收斂後推送後審查反覆重報已登記的殘留風險，各線逐次轉送使原線重複判定

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-GPD-035 |
| 類別 | process-compliance |
| 風險等級 | 低 |
| 發現日期 | 2026-10-20 |
| 來源版本 | 0.5.0 |

## 症狀

一支靜態解析命令的守衛，經用戶裁定收斂：只有刻意構造才會觸發的繞過記為殘留風險，寫進分類表，不再開修正票。之後每次有人推送，推送後的自動安全審查都會重讀該守衛的現行檔案，再報一次同一批項目。

多線並行時，收到審查通知的不一定是維護那支守衛的線。最小重現：

1. 守衛由 A 線維護，殘留風險已登記在 A 線票面的分類表。
2. B 線推送一個與守衛無關的 commit，審查通知送到 B 線，內容是 A 線早已登記的同一批項目。
3. B 線把通知轉給主控，主控再轉給 A 線，A 線重新逐項比對、判定。
4. 通知若被截斷，只顯示「+N more」，A 線無法重跑審查，也無法從 B 線的推送範圍對回是哪一次審查。

結果：一則不帶新資訊的通知，佔用三方各一輪處理；被截斷的那一項還會被追查，最後追不到。

## 根因

| 層 | 原因 |
|----|------|
| 審查端 | 審查讀的是推送當下的檔案狀態，不是這次推送的變更範圍。守衛只要還在 repo 裡，每次推送都可能被點名，與推送者改了什麼無關 |
| 轉送端 | 轉送者不知道守衛已收斂，也不知道分類表在哪，只能把每則通知都當成新發現往上報 |
| 對照端 | 審查無法手動重跑，原線只能憑觸發審查的 commit 找原文；轉送時沒附 commit，原線無從對照 |

收斂裁定本身只回答「要不要修」，沒有回答「之後的審查通知怎麼過濾」。

## 解決方案

1. 轉送前先比對該守衛的殘留風險分類表。表內已有的不轉；只轉不在表內、或描述明顯不同的項目。
2. 轉送時附上觸發該次審查的 commit。找不回 commit 的截斷項目不追，記為「無法對照」即可。
3. 分類表登記時，每列寫明該失效會出現在判定日誌的哪一欄，讓收到通知的人能自行判斷是否已登記，不必回頭問原線。

## 預防措施

- 協調手冊 multi-session-orchestration 的 `references/review-flags-and-verification.md` §1 步驟 2，已寫入「守衛收斂後，轉送前先比對殘留風險分類表，並附觸發審查的 commit」。
- 主控宣告某守衛收斂時，同時把分類表的位置轉知所有線，讓各線轉送前能自行查表。

## 與其他模式的關係

- 這是收斂之後的運作成本，不是守衛缺陷。守衛缺陷的判準見 `.claude/references/hook-architect-technical-reference.md`〈靜態解析命令的守衛：parser differential 的處置判準〉。
- 回歸不在本模式範圍：審查項目若是本次修改造成的「修前擋、修後放」，不論是否刻意構造都要修回，不能因為疑似重報而略過。判別方式是以修改前、修改後兩個版本跑同一個輸入，並附一筆兩版都該擋的基準輸入。

## 實例

2026-10-20，寫入邊界守衛收斂後，維護該守衛的線以外的另一條線收到推送後審查通知，共 4 項，其中 3 項與分類表已登記的殘留風險相同，第 4 項被截斷、找不回觸發的 commit。
