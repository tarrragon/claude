# PC-BAL-043: 規範載體未送達執行者 context，違規為結構必然而非個體疏失

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 高 |
| 發現時機 | 復核一則既有 error-pattern 的歸因時，實測發現其歸因語言與載體實況相反 |
| 發現日期 | 2026-08-18 |
| 觀測次數 | 兩條獨立失效路徑（agent 定義的 @-import 不展開；自動載入層 stub 與主文分離），另有一則既有診斷文件的誤植 |

## 症狀

症狀分屬兩個觀測對象。執行者側訊號顯示可能有規範失效，但不指出屬哪一型；診斷文件側訊號則指出既有歸因可能未經實測。

**執行者側**：

- 規範已寫入某份框架文件並被視為「已生效」，但執行者行為持續違反
- 違規分佈均勻且跨不同執行者、跨不同時間，不呈現個體差異——與「疏失」的分佈特徵不符
- 執行者被強制層擋下時無法說明自己違反了什麼（此項為 delivery gap 獨有，見下方識別訊號說明）
- 補送規則原文後違規消失，移除後即復發，且與執行者是誰無關

**診斷文件側**：

- 既有診斷以「執行者不會主動載入該規則全文」解釋違規，但從未實測該規則是否在執行者 context 內
- 既有診斷的 gap 分類未標記時點與當時載體位置

## 根因

規範失效有兩型。兩者都可能以「調整規範所在載體」收場，但**調整的目的相反**——這是分流的關鍵軸，不是「換不換載體」：

| 面向 | Delivery gap（載體未送達） | Compliance gap（送達但未遵守） |
|------|---------------------------|------------------------------|
| 定義 | 規範所在載體從未進入執行者 context | 規範在 context 內，行為未遵守 |
| 違規性質 | 結構必然——執行者不可能遵守不存在的規則 | 個體偏離 |
| 載體調整的目的 | **補送**：使條文本身進入 context | **縮短距離**：把條文移到決策點旁 |
| 有效修法 | 把條文移到已驗證送達的層級，或在派發路徑上補送 | 強制層檢查；把條文移到執行者做該決策的當下位置 |
| 無效修法 | 只加強制層檢查（執行者被擋而不知為何，傾向轉為繞過） | 只調整載體層級而不縮短條文與決策點的距離 |
| 成立前提 | 主文所在檔不在執行者注入清單內 | 主文所在檔確實在清單內 |

「派發時貼上規則原文」在兩型中都會出現，但性質不同：對 delivery gap 它是補送（context 中原本沒有該條文），對 compliance gap 它是縮短距離（條文已在 context，只是離決策點太遠）。用它來分流會失敗，理由見下節。

三層成因，由深至淺：

1. **「寫進文件即生效」的假設從未驗證**。框架設計者能讀到檔案，便預設執行者也讀得到；但兩者的 context 組成由平台載入機制決定，與檔案是否存在無關。
2. **引用語法不等於載入語法**。在某些載體中 `@path` 形式的引用只是字面文字，不觸發展開；同一個語法在另一種載體中卻會展開。語法外觀相同、行為不同，靠閱讀原始檔無法分辨。
3. **stub 與主文分離使送達變成部分成立**。為收斂自動載入預算而把規則主文外移、原處留速查 stub 時，送達的是一張寫著「完整規則在別處」的路由卡。檔名仍在清單內，規範本身卻不在。

## 辨識判準

**判準綁載體，不綁規則。** 三步：

1. 定位規範主文的實際所在檔。規則掛名的那一檔未必是主文所在檔——stub 與主文分離時，兩者是不同檔案，且掛名檔通常仍以規則名稱命名。
2. 查該檔是否在執行者的注入清單內。判準是「在不在清單」，**不是「第幾項」**——序位隨該層檔案增刪浮動，把序位寫進論證等於埋一個會自然腐壞的事實。
3. 若主文位於按需讀取層而只有 stub 送達，判為 delivery gap。部分送達即未送達：路由卡不含規範內容，執行者無從遵守。

**驗證手段**：派探針執行者，**禁用其全部工具**，要求逐字回報自身 instructions 實況（是否含該檔內容、注入清單為何、引用行是字面還是已展開）。

禁用工具是這個手段能否成立的關鍵。不禁的話探針會去讀檔再回報檔案內容，回答的是「這個檔存在嗎」，而不是「這個檔在我的 context 裡嗎」——後者才是待驗證的命題，且只有執行者能第一人稱回答。

## 推論：載入機制分層時，同一條規則會在兩種 gap 之間遷移

**本節是根因表兩型定義的直接推論，不是需要案例支撐的經驗命題。** 兩型的定義項就是「條文所在載體的載入狀態」，因此分類必然是**載體的屬性**而非規則的屬性；規則文字不動，只要主文換一個載入層級，分類就翻面。

**成立前提**：此推論在滿足兩個條件的框架中才有實際發生的機會——載入機制分層（存在自動載入層與按需讀取層之分），且存在把主文外移、原處留 stub 的實務（通常由自動載入預算驅動）。缺任一條件的框架中遷移罕見，但推論本身不因此失效。

**Consequence**：診斷文件寫「此規則屬 X gap」而不標時點，會隨下一次載體重構失效，且失效無訊號——文件讀起來仍然通順，只是斷言已經不成立。後續同類問題依該斷言選修法，選到的是對面那一種。

**Action**：診斷須同時記錄「當時主文所在檔」與「該檔當時屬哪個載入層」。gap 分類寫成帶時點的觀測，不寫成規則的固有標籤。

**已觀測到的一次遷移（示範，非支撐）**：某條規範 ticket body 章節結構的規則，原寫於自動載入層，執行者確實收得到卻未遵守，屬 compliance gap；其後為收斂自動載入預算，主文外移至按需讀取層、原處僅留速查 stub，同一條規則即轉為 delivery gap。前後相隔約一個月，規則文字未改。

本例與下方案例三同源（同一份診斷文件），為單一觀測。作為「遷移確實會發生」的存在性證明已足；不支撐任何頻率推論，亦不宜與基本資訊表「兩條獨立失效路徑」的獨立性宣告合併計算。

## 解決方案

處置順序固定為「先判型、後選修法」。判型之前寫下的根因會反過來決定後續看什麼證據，這是既有診斷誤植的來源。

| 步驟 | 動作 |
|------|------|
| 1 | 對疑似規範失效，先跑辨識判準三步，**不要先寫根因** |
| 2 | 判定 delivery gap → 把規範主文移至已實測送達的載體層級，或在派發路徑上補送 |
| 3 | 判定 compliance gap → 補強制層檢查或縮短規則距離 |
| 4 | 判定混合態（stub 送達、主文未送達）→ 把執行者實際需遵守的條文本身放進送達層，stub 只留路由 |

## 預防措施

前三項作用於規範載體的規劃與維護階段，第四項作用於失效已發生後的判讀階段。

| 機制 | 角色 |
|------|------|
| 規劃規範載體前先驗證傳遞路徑（探針實測，非閱讀原始檔推論） | 主路徑 |
| 外移規則主文至按需讀取層時，同步評估「執行者是否仍收得到需遵守的條文」 | 外移作業的必要檢查項 |
| 診斷文件的 gap 分類一律標記時點與當時載體位置 | 標記成本為一行，失效則無訊號且導向反向修法；成本不對稱，故不設頻率門檻 |
| 「派發時再貼一次規則就有效」出現時，視為**應啟動探針實測的疑似訊號**，不逕自判為任一型 | 訊號辨識（見下方說明） |

**識別訊號為何不能單獨用來分流**：補送規則原文對兩型都有效——對 delivery gap 是把原本不在 context 的條文送進去，對 compliance gap 是把已在 context 但離決策點過遠的條文移到眼前。一個對兩型都有效的手段不具區分力，依此分流會系統性誤判。

可區分的是另一項：**執行者被強制層擋下時能否說出自己違反了什麼**。說不出來指向 delivery gap（條文不在其 context），說得出來則指向 compliance gap。此項仍屬間接證據，唯一可靠的判別是辨識判準第 2 步的探針實測。

## 案例

**案例一：agent 定義中的 @-import 為字面值**。某框架以一份共用前置檔承載跨 agent 的通用約束（收尾責任、git 操作限制、工具選擇優先序等），各 agent 定義以 `@` 引用該檔。探針實測顯示該引用行在執行者 instructions 中為字面路徑文字，其後直接接該 agent 自身的角色描述，前置檔內容完全未出現。行為側的旁證與之相符：執行者 transcript 中常態出現該前置檔明文禁止的動作。此旁證未經本次獨立計數，僅作方向一致性參考，判型仍以探針實測為準。

**案例二：自動載入層 stub 與主文分離**。同一批探針確認自動載入層目錄下逐檔注入執行者 context（本專案當時為二十餘檔，此量級隨專案而異，不構成預期值），某結構標準檔確實在清單內。但該檔已收斂為速查 stub，探針逐字貼回的開頭即為「完整規則：（按需讀取路徑）」——執行者需遵守的章節結構條文位於該按需讀取檔，未送達。

**案例三：既有診斷文件的歸因誤植**。一則記錄「規則存在但行為未遵守」的既有 error-pattern，其主文以「執行者在派發時不會主動載入該規則全文」解釋違規，屬 delivery gap 的語言；但該規則當時位於自動載入層，實測確實送達，該歸因不成立。同一份文件的案例段落後來補入一則校準註記，其內容與主文互相牴觸，兩段並存數月。該矛盾未觸發任何檢查機制——兩段皆通過既有 lint 與人工審查，因為各自單獨讀都通順，牴觸只在並讀時顯現。（此矛盾已於 2026-08-18 修正，見 PC-123 Why 段的撤回聲明；該檔現行內容不再呈現此狀態。）

## 與既有模式的分界

以下四個既有模式與本模式共享「送達假設未經驗證」的主題，分界依**送達的方向**（規範到執行者 vs 執行產出到派發方）與**送達的偏差類型**（未送達 vs 過度送達）區分。表中的 gap 分類依本模式的 Action 要求標記時點。

| 既有模式 | 主張 | 分界 |
|---------|------|------|
| PC-123 | 規則存在但行為層未遵守 | 該模式描述的是 compliance gap 的實例（案例發生時 2026-05-05；同一規則於 2026-06-12 主文外移後轉為 delivery gap）；本模式提供其上位的分類判準，並修正該模式原用 delivery gap 語言解釋 compliance gap 的歸因 |
| PC-V1-004 | 注入訊息受眾錯配（PM 專屬訊息注入執行者 context） | 同一座標軸的反向端：該模式是**過度送達**（送給不該收的人），本模式是**未送達**（該收的人沒收到） |
| PC-BAL-038 | 背景執行者的文字輸出未送達派發方 | 同屬「送達假設未驗證」家族，但對象為執行產出而非規範載體，方向亦相反（執行者到派發方） |
| PC-112 | 執行者對非程式碼檔誤選寫入工具後 early stop | 該案的規則位於自動載入層且確實送達，屬 compliance gap（2026-08-18 覆核時），可作分流表的對照樣本 |
