# PC-BAL-033: 已註冊的防護 hook 可能從未被呼叫，且失效與正常在可觀測面同形

> 檔名 slug 仍為 `newly-registered-hook-inert-for-existing-sessions`，反映本檔初版單一成因（註冊快照）的視角；該成因現判定為版本相依，且已非唯一成因。**經量測後決定不改名**（2026-08-18）：框架層（`.claude/`）以完整檔名引用本檔者為 0 處，改名在該層無任何收益；而 14 處完整檔名引用全數落在已完成 ticket 的執行紀錄中，那是不改寫的歷史文本，改名只會把它們變成失效路徑。slug 因此固定作為穩定引用鍵，語意由本段與 H1 標題承擔。

## 機制更正（2026-08-18 實測，適用範圍收窄）

本模式原以「runtime 於 session 啟動時快照 hook 命令集」為**唯一**機制模型。2026-08-18 一組雙探針對照實驗（兩支僅差可執行位的 no-op 探針，各自記錄 `session_id` 與觸發命令）顯示該模型在當時的 runtime 上**不成立**；但 2026-08-13 的日誌鑑識顯示它在當時的 runtime 上**成立**。本檔據此改為承認兩條並存成因，並標明何者版本相依。下表的「否證」僅指 2026-08-18 觀測到的 runtime 行為，不宣稱跨版本恆真。

| 主張 | 2026-08-18 實測結果 |
|------|--------------------|
| 中途註冊對既有 session 零效力 | 於 2026-08-18 的 runtime **不成立**。一個 session 執行了在其啟動後 4 分鐘才建立、6 分鐘才註冊的 hook，經 `session_id` 與命令哨兵雙重歸因確認。但 2026-08-13 的日誌鑑識**正面支持**此主張（見下「兩組觀測的版本相依」），故判定為版本相依而非全面否證 |
| 反註冊須等下個 session | 於 2026-08-18 的 runtime 不成立。移除註冊後日誌即停止增長，哨兵零命中。同屬版本相依，未於 2026-08-13 的 runtime 上驗證 |
| 缺可執行位者於本 session 被丟棄且不再重試（session 級負向快取） | 否證。第二輪判別實驗於單一 session 內造出「先 exec 失敗、後補可執行位」序列：同一 session 對同一支 hook 先失敗一次，`chmod +x` 後同一 session 立即成功執行，探針自記 `session_id` 直接歸因 |
| 缺可執行位時 hook 不會被啟動 | **維持成立**（根因 5 的操作性成因）。補可執行位前 exec 探針有筆數、noexec 探針零筆，與隔離執行的 `rc=126` 一致。惟根因 5 尾段「修復若發生於 SessionStart 內則該次 session 仍不受益、須等下次重啟」的推論同被否證 |

**收窄後的適用範圍**：本模式描述的「已註冊但零效力且日誌零筆」有兩條各自成立的成因。缺可執行位（根因 5）與 runtime 版本無關，恆成立，恢復條件是一次 `chmod +x` 且不需重啟 session。註冊快照（根因 1、根因 2）為**版本相依**：在 2026-08-13 觀測到的 runtime 上成立，在 2026-08-18 觀測到的 runtime 上不成立。遇到症狀時兩條都要查，不可因本節而略過根因 1。

**實測涵蓋範圍**：兩輪實驗皆於 `PreToolUse` event 進行，`SessionStart` / `Stop` / `UserPromptSubmit` 等其他 event 未驗證。本節結論的直接適用範圍限 `PreToolUse`。實驗量到的是端點（註冊前不觸發、註冊後觸發、反註冊後不觸發），可確認磁碟狀態不晚於下一次工具呼叫即被反映；重載的觸發機制本身（每次呼叫重讀 / file watcher 帶 debounce / 週期輪詢）未量測，故不宣稱「每次工具呼叫都重讀」。

**Consequence（依舊模型產出的東西需回頭重檢）**：舊模型指導過兩類產物——防護類 ticket 的 acceptance（曾被要求含「已通知既有 session 重啟」或「已標註本 wave 不生效」）、以及新增守衛的交付流程（曾要求等待既有 session 結束）。兩類皆應依收窄後範圍重寫；前者的強制層見「預防措施」節所指的 acceptance checker。

**回退偵測的承擔者**：本檔核心主張之一是此類失效不可觀測（防護 hook 正常狀態即無輸出），故回退偵測不可綁在「再度觀察到症狀」這個訊號上——那是本檔已論證偵測不到的東西。改為主動時機：**任何新增防護類 hook 的 ticket 開始前**，由該類 ticket 的 acceptance 檢查機制（見「預防措施」節）要求撰寫者實地確認一次「本 session 內註冊即生效」，確認失敗即代表 runtime 行為已變，須重跑雙探針實驗而非沿用本檔任一版本的模型。

**兩組觀測的版本相依**：本更正基於 2026-08-18 的實測，原始觀測則在 2026-08-13。兩組資料各自自洽且互相矛盾，最合理的解讀是 runtime 載入模型在兩個時點之間改變。

2026-08-13 側支持快照模型的五項獨立事實（來源日誌受保留期限制，已逐字轉錄至追查該問題的分析票）：

1. 涉事 hook 的非命中路徑日誌行存在於其**第一個 commit**，故「零筆」等於「零呼叫」，不存在「有呼叫但未落檔」的解釋空間。
2. 該 hook 自取得可執行位起至首筆 runtime 呼叫止，內容未經任何 commit 變更。
3. 可執行位於當日中午即由自動修復補上並提交；同日稍後以 shebang 直接執行成功，獨立佐證可執行位確實存在。
4. 補上可執行位後仍有 93 分鐘零呼叫，同期同一 `PreToolUse` block、同一 matcher 的對照守衛有 47 次呼叫。
5. 首筆 runtime 呼叫發生於一次新 session 啟動之後。

**一度出現的誤判（供後續讀者避開）**：初次更正時，曾把上述第 3 點所指的手動隔離執行日誌誤讀為 runtime 呼叫，據此宣稱原始觀測「全程零筆」不成立、並將差異定性為原始判讀錯誤。該推論已撤回——來源票本身早已註明該筆屬手動執行。教訓是查證外部指出的反證時，須一併查來源是否已解釋該證據，而不是只確認證據存在。

**行為指引**：遇到「已具可執行位、已註冊、卻零效力」時，先重跑雙探針實驗確認當前 runtime 屬哪一種載入模型，再決定處置——快照模型下須等新 session，即時模型下應改查 matcher、設定遮蔽、路徑存在性等其他成因。

**主文結構的刻意選擇（2026-08-18 決策）**：曾有把快照模型整批下沉為檔尾歷史節的提議，提出時該模型看似已全面否證。v2.2.0 改判為版本相依後此提議不再採納——根因 1、2 在 2026-08-13 觀測到的 runtime 上成立，讀者遇到症狀時仍須逐條查證；下沉為歷史節會讓它們讀起來像已死成因，與本節「兩條都要查，不可因本節而略過根因 1」的指引相反。現行安排（更正節置頂、根因 1 與 2 就地標註版本相依）已達成該提議的原意，即讀者不會先讀到過時模型而不自知。

## 症狀

於 session 進行中新增一個 hook 並註冊到 `settings.json`，該 hook 可能完全不被呼叫。兩條成因各自成立：檔案不具可執行位時，它對**所有 session（含新開者）** 零效力直到一次 `chmod +x`；在採快照載入的 runtime 版本上，它另外對**所有當時已在執行的 session** 零效力直到各自重啟（版本相依，見「機制更正」節）。它要防的操作照常通過，沒有阻擋、沒有警告、沒有日誌。

檔案存在於磁碟、註冊存在於設定檔、單元測試全綠——但它從未被呼叫過一次。

最惡劣的一點：**這個失效的可鑑別性依 hook 是否覆蓋 `run_hook_safely` 共用執行框架而不同**（涵蓋率與例外路徑見根因 4）。日誌零筆不再永遠同時符合三種互斥情形，但覆蓋外的 hook 仍舊如此：

| 情形 | 覆蓋 `run_hook_safely` 的 hook | 覆蓋外的 hook（含根因 4 所述的降級 stub） |
|------|------|------|
| hook 未被呼叫（本模式） | 零筆——與「崩潰於 import 期」同形，兩者本身仍無法互相區分 | 零筆——與其餘兩種情形同形 |
| hook 被呼叫但未命中判準 | 至少一筆 DEBUG「Hook execution time」，可鑑別（非零筆） | 零筆（若僅在命中時記錄）——與其餘兩種情形同形 |
| hook 被呼叫但崩潰於寫日誌之前（import 期錯誤） | 零筆——與「未被呼叫」同形 | 零筆——與其餘兩種情形同形 |

換言之：在覆蓋 `run_hook_safely` 的 hook 上，缺席可鑑別為「未呼叫」或「import 期崩潰」兩者之一（僅這兩者本身仍同形，需步驟 2、3 佐證）；在覆蓋外的 hook 上，三種情形依舊完全同形、缺席不可鑑別。而防護類 hook 的正常狀態本來就是「什麼都沒發生」，於是在覆蓋外的路徑上，「零效力」與「一切正常」在可觀測面上依然完全同形。

## 四個假訊號

本模式之所以難以自我察覺，是因為部署者會連續拿到四個都指向「已受保護」的訊號：

| 假訊號 | 為何為假 |
|--------|---------|
| 單元測試全綠 | 測的是判準函式對命令字串的分類正確性，與「runtime 是否會呼叫它」正交 |
| `settings.json` 已註冊 | 註冊的是**磁碟狀態**，而磁碟狀態不保證檔案具備被啟動的條件——缺可執行位時 runtime 無從執行它（根因 5）。此外在採快照載入的 runtime 版本上，磁碟已註冊不等於當前 session 的 registry 已收到（版本相依，見「機制更正」節） |
| 手動 dogfooding 通過 | dogfooding 常以「隔離執行」（直接餵 stdin 給 hook 檔案）進行，該路徑由呼叫者指定解譯器，繞過了 runtime 依賴的可執行位；hook 判準因此驗得過，實際仍無法被 runtime 啟動 |
| 自動化完整性檢查（如 hook-completeness-check）於 SessionStart 回報「權限已確認可執行」全綠 | 回報全綠的原因是它自己在同一次啟動中才把該檔案 chmod 成可執行。修復本身即時生效（無 session 落差），但「已修復」與「本來就正常」共用同一份全綠輸出——讀者無從得知這次啟動前該防護處於失效狀態，也無從得知失效持續了多久 |

第三項最關鍵：驗證行為本身選在一條繞過故障點的路徑上進行，而且是**自然而然**地選在那裡——隔離執行是排查 hook 的第一直覺。第四項最陰險：它是四者中唯一由自動化機制主動產出、而非人為選擇的訊號，且它回報的「已修復」與「已生效」共用同一份輸出，使自動化本身變成誤導來源。

## 觸發情境

| 條件 | 說明 |
|------|------|
| 新增的 hook 檔案不具可執行位，且以裸路徑（依賴 shebang）註冊 | 主要觸發點。以 `uv run <path>` 等指定解譯器的形式註冊則不觸發 |
| 該 hook 的職責是**防護**（阻擋破壞性操作） | 失效方向為 fail-silent，無人察覺 |
| 以「隔離執行」（直接餵 stdin 給 hook 檔案）作為部署驗收 | 驗收路徑繞過可執行位這個故障點 |
| 有其他 session／代理人正在並行執行 | 受害範圍。缺可執行位對所有 session 一致失效，並行只放大後果；若 runtime 採快照載入（版本相依），並行本身即為獨立成因 |

並行派發情境下風險加乘：新增防護的動機通常正是「剛發生過一次事故」，而此時並行代理人都還在跑——**最需要防護的那一刻，正是防護處於失效狀態而無人知曉的那一刻**。

## 根因

### 根因 1：註冊是 session 啟動時的快照，無 session 內失效手段（機制層，**版本相依：2026-08-13 觀測支持、2026-08-18 觀測不支持，見「機制更正」節**）

hook 註冊於 session 啟動時載入為快照。磁碟上的 `settings.json` 是世界平面，runtime 持有的註冊表是啟動瞬間的記錄平面，兩者在新增後必然分歧，直到下個 session 才收斂。

與 [[PC-145]]（`uv tool install` 快照，可用 reinstall 使其失效）的差別在於：**本機制沒有任何 session 內的失效手段**，這點與 [[PC-BAL-014]] 相同。

> 本條依證據形態與 [[PC-BAL-014]] 對同一 runtime 的 skill 註冊表所獨立確立的同機制推得，非直接讀官方文件實測。

**必要非充分（2026-08-13 差分實測）**：本模式的示例 hook 於當日 09:38 隨 `settings.json` 一併註冊。本根因的推論意味著「session 於註冊之後啟動即可正確載入」，但同日 12:52 啟動、晚於註冊 3 小時 20 分的新 session，對該 hook 依然是零效力——同一個 PreToolUse block 內其餘 18 個 hook 全程持續被呼叫，唯獨這一個全程零筆（全 block 掃描 + 即時探針差分實測，見鑑別方法步驟 2、3）。單靠本根因無法解釋此觀測；操作性成因見根因 5。

### 根因 2：部署延遲等於最長 session 壽命，但無人把它當延遲（**僅在根因 1 成立的 runtime 版本上適用，見「機制更正」節**）

一般會預期「改了設定檔就生效」。實際的生效延遲是**所有既有 session 結束為止**，可能是數小時。這段延遲沒有任何介面呈現，也沒有任何倒數或提示。

### 根因 3：防護類機制缺 liveness 訊號

防護 hook 的正常輸出是「無輸出」，因此它與「不存在」在可觀測面同形。系統沒有提供「這個 hook 剛才確實被呼叫了」的正向訊號，使得部署者只能用「沒出事」推論「有在保護」——而這正是 [[PC-BAL-014]] 家族的共同陷阱。

### 根因 4：`run_hook_safely` 涵蓋率非 100%，降級路徑完全不寫日誌（獨立成因）

「症狀」節描述的部分鑑別力，來自 `.claude/lib/hook_logging.py` 的共用執行框架 `run_hook_safely`：main_func 返回後無條件寫入一筆 DEBUG「Hook execution time」，`FILE_HANDLER_LEVEL = logging.DEBUG` 使其落檔，`FileHandler(delay=True)` 使「日誌檔存在」等價於「確有寫入」。但此框架的涵蓋率僅 88/103（`rg -l run_hook_safely .claude/hooks/ -g '*.py'` 實測），其中 4 個 hook 在 `from lib import` 失敗時降級為自訂 no-op stub——該路徑完全繞過 `run_hook_safely`，不寫任何日誌。

**Why 這是與根因 1 獨立的成因**：根因 1 的病灶是「registry 未收到新註冊」；本根因的病灶是「即使 hook 已被此 session 載入且確實被呼叫，只要落入這 4 個 hook 的降級路徑，寫日誌的能力本身就被繞過」。兩者觸發條件互不相依——根因 1 只需新註冊發生在 session 中途，本根因需 `lib` import 於該 hook 執行環境中失敗——但終端症狀相同：日誌零筆。

**Consequence**：鑑別方法步驟 1（日誌零筆檢查）若未先排除降級路徑，會把「hook 正常運作但走了 no-op stub」誤判為「未被此 session 載入」，使原本可鑑別的一類 hook 也被誤歸為不可鑑別。

**Action**：鑑別前先確認待驗 hook 是否覆蓋 `run_hook_safely`（`grep -n run_hook_safely .claude/hooks/<hook-name>.py`）；覆蓋但仍零筆時，再確認是否落入 `from lib import` 失敗的降級 stub 路徑（`grep -n "except ImportError\|from lib import" .claude/hooks/<hook-name>.py`）。兩者皆非，零筆才等於「未呼叫或 import 期崩潰」。

### 根因 5：以 shebang 直接執行的 hook 缺可執行位，狀態與 session 生命週期無關（獨立成因，2026-08-13 實測）

`settings.json` 對本類 hook 的呼叫方式是直接執行檔案路徑（例：`$CLAUDE_PROJECT_DIR/.claude/hooks/<hook-name>.py`），依賴檔案自身的 shebang（如 `#!/usr/bin/env -S uv run --quiet --script`）啟動，而非透過 `python3 <path>` 間接呼叫。作業系統以此方式啟動程式時要求檔案具備可執行位（`+x`）；不具備時程序從未起跑，連 import 都不會發生。

`git ls-tree` 逐 commit 查證（見鑑別方法步驟 5）顯示：本模式的示例 hook 於建立並註冊當下即以模式 `100644` 提交，同日稍後的一次補強提交仍維持 `100644`；直到一次獨立的自動權限修復提交才轉為 `100755`。事故發生時段全程處於不具可執行位的狀態。

**Why 這是與根因 1 獨立的成因**：根因 1 的病灶是「該 session 的 registry 快照未收到新註冊」，其修復只需換一個在註冊之後啟動的 session；本根因的病灶是「即使 session 於註冊之後啟動、registry 快照確實含有此 hook，只要磁碟上的檔案模式仍是 `100644`，該 session 依然無法啟動它」。兩者可獨立成立、獨立失效——見根因 1「必要非充分」段落的差分實測：session 於註冊後 3 小時 20 分才啟動（滿足根因 1 的前提），該守衛仍全程零效力，證明單靠根因 1 不足以解釋此次失效，操作性成因是本根因。

**Consequence**：若復盤只查根因 1（結論為「等重啟即可」）而未查檔案模式，會誤判「已經過了一個 session 邊界，下次應該就會生效」，但只要磁碟模式仍是 `100644`，重啟幾次都不會生效。本模式的示例 hook 就出現過這種誤判：補強提交發生於原始註冊之後，但當時模式仍未修正。

**Action**：新增或修改以 shebang 直接執行的 hook 時，在寫入 `settings.json` 的當下（而非事後排查時）驗證檔案可執行位，將此檢查點前移，不依賴「下次事故再回頭查」。

**跨 session 持續、重啟不修復**：檔案模式是 git 追蹤且由磁碟持久化的狀態，不隨 session 的開始或結束而改變。重啟本身不會讓一份已提交為 `100644` 的檔案變成可執行，需要一次獨立的 `chmod` + commit（人工或自動化）才會改變——**重啟不是修復手段，`chmod +x` 才是**。

> **原尾段已否證（2026-08-18）**：本節原斷言「若修復動作發生在某 session 自身的 SessionStart 階段內，該次 session 仍不受益，須等下一次重啟」，並以「runtime 解析可執行性的時點早於 SessionStart hook 執行時點」為解釋。第二輪判別實驗在單一 session 內造出「先 exec 失敗、後補可執行位」序列，該 session 於 `chmod +x` 後立即成功執行同一支 hook（探針自記 `session_id` 直接歸因），故不存在 session 級的負向快取，修復即時生效。原斷言所依據的「該 session 於修復後仍全程零筆」這項觀測，亦已被同日的 hook 日誌檔推翻（該守衛在原觀測窗內存在命中筆）。詳見「機制更正」節。

> **根因 5 結構性消除（2026-08-22）**：本根因成立的前提是「`settings.json` 以裸路徑依賴 shebang 直接執行」。實測 `settings.json` 全部 hook 註冊已改為顯式解譯器形式（`uv run --quiet <path>` 或 `python3 <path>`），不存在裸路徑殘留——`uv run` 與 `python3` 皆以直譯器讀檔執行，不依賴檔案本身的可執行位。本根因描述的失效模式（缺可執行位使 shebang 直接執行的程序從未起跑）在此前提下不再成立，屬**歷史根因，非持續有效**。鑑別方法步驟 5（檔案模式溯源）與相關防護（可執行位落地檢查類 hook）已同步降級為純觀察，不再自動修復，理由與本段一致。若未來 `settings.json` 出現裸路徑註冊倒退，本根因會重新成立，需另行復核。

> **結構性消除的範圍限定（2026-08-22）**：上段消除的僅是 **runtime 呼叫路徑**（`settings.json` 對 hook 的實際觸發）對可執行位的依賴。另一條獨立路徑——**手動驗證慣例**（開發者或文件教學直接以 `echo '{...}' | .claude/hooks/foo-hook.py` 這類裸路徑依賴 shebang 執行 hook 本體，常見於 dogfooding、隔離執行排查、PC-124/IMP-069/PC-148 等文件的重現步驟）——未被上段消除，因為這條路徑從不經過 `settings.json`，重寫該檔案的註冊形式對它沒有影響。`settings-registration-exec-guard-hook.py` 降級為純觀察後，此路徑的可執行位缺失同樣不再被任何機制自動修復，僅被動記錄。經盤點，全站至少 8 個檔案、16 處這類裸路徑手動驗證範例（含本檔第 233 行的樣板行）；後續決策採「改寫文件消除依賴」而非恢復自動 chmod（理由：本 hook 的監控面本就不含 Bash 直接建立、git checkout/merge/pull 落地等路徑，恢復 chmod 也無法達成「消除依賴」而只能縮小失效視窗），改寫工作另行追蹤處置。本檔第 233 行的範例本身即屬此類，予以保留供讀者理解「隔離執行」技術本身（見「四個假訊號」第三項），標註本身不隨此次修訂變更。

## 鑑別方法（五步）

缺席的鑑別力依覆蓋範圍而異（見步驟 1）：覆蓋外的 hook 上仍完全不可鑑別，**必須用差分而非單點觀察**；覆蓋 `run_hook_safely` 的 hook 上零檔案本身可初步鑑別，但仍分不清「未呼叫」與「import 期崩潰」兩者，故亦建議續行差分佐證。前三步依成本遞增，用於確認「是否被呼叫」，任一步命中即可停；步驟 4、5 用於在確認「未被呼叫」後，進一步鑑別根因是缺可執行位（根因 5）、`run_hook_safely` 覆蓋缺口（根因 4），還是其他載入問題（根因 1）：

### 步驟 1：日誌零筆檢查（成本最低，鑑別力依 hook 是否覆蓋 `run_hook_safely` 而定）

```bash
ls -la .claude/hook-logs/<hook-name>/
```

先確認待驗 hook 是否覆蓋 `run_hook_safely`（見根因 4）：

```bash
grep -n run_hook_safely .claude/hooks/<hook-name>.py
```

**覆蓋 `run_hook_safely` 的 hook**：main_func 返回後無條件寫入 DEBUG「Hook execution time」，故「零檔案」（目錄下無任何日誌檔）與「檔案存在但零筆」是兩種不同結論，不可混為一談——後者不會發生（只要被呼叫過就至少留下一行）；一旦觀察到「有檔案但零筆」，代表覆蓋判斷有誤，或該 hook 落入根因 4 的降級 stub 路徑，須回頭核對。因此對這類 hook，**零檔案本身即是結論**：等同「未呼叫」或「import 期崩潰」兩者之一（仍無法再細分，需步驟 2、3 佐證）；目錄下若有檔案，即代表已被呼叫，不需再往下鑑別。

> **每日輪替改造後部分失效（2026-08-21 標註）**：上段建立於「一次觸發即一個新檔」的假設。hook 日誌自某次改造起改為每日輪替 append（同一 hook 同一天的所有觸發皆寫入同一檔案，檔名含日期），該假設在「檔案存在性」與「時間解析度」兩個層面產生不同後果：
>
> - **「零檔案＝未呼叫」仍成立**：清理僅在該 hook 自身被觸發、重新設定 logger 時才執行（`.claude/lib/hook_logging.py::_maybe_cleanup`，逐目錄觸發、無跨目錄掃描），故已停止觸發的 hook 不會有殘留檔案被自動清除——目錄若曾經產生過檔案，會一直存在。零檔案因此仍等同「從未被呼叫過」。
> - **「有檔案＝已被呼叫，不需再往下鑑別」已失效**：「有檔案」不再保證任何有意義的時間窗。持續觸發的 hook，最舊檔案可達保留期（7 天）之前，無法從「有檔案」判斷是今天還是 6 天前被呼叫；已停止觸發的 hook，目錄凍結在最後一次觸發的那天，「有檔案」與「近期被呼叫」之間的距離不可界定（可能 1 天前，也可能數月前）。
>
> **Consequence**：依「目錄下若有檔案即不需再往下鑑別」略過步驟 2-5，會把「很久以前呼叫過一次、之後就停了」誤判為「現在仍在正常運作」。
>
> **Action**：需要確認的是「近期 / 本次 session 是否被呼叫」而非「歷史上是否曾被呼叫過」時，本步驟不再足夠，必須改查 liveness 索引（`.claude/hook-logs/_liveness/<session_id>.jsonl`）——`mark_hook_entry` 於 `run_hook_safely` 內、main_func 執行前無條件寫入一筆含 ISO timestamp 的「已進入」訊號，不受檔案輪替影響：
>
> ```bash
> grep "\"hook\": \"<hook-name>\"" .claude/hook-logs/_liveness/*.jsonl
> ```
>
> 此索引僅涵蓋 `run_hook_safely` 之後的路徑；覆蓋外的 hook（根因 4 所述降級 stub）不受此索引記錄，仍須沿用步驟 4、5。

**覆蓋外的 hook（含根因 4 所述的降級 stub 路徑）**：零檔案仍是**嫌疑訊號**而非結論，維持原本三種情形同形的判斷——仍可能是「有跑但都沒命中且不寫 DEBUG」。先確認該 hook 是否在**未命中**時也記錄：

```bash
grep -n "logger.debug\|logger.info" .claude/hooks/<hook-name>.py
```

若存在「未命中也寫一行」的路徑，且該路徑的日誌等級確實會落檔（檢查既有日誌檔內是否含 DEBUG 行），可縮小嫌疑範圍，但仍不足以單獨定論，須續行步驟 2 或 3。

### 步驟 2：同 matcher 對照組（決定性）

找一個**註冊時間更早**、matcher 相同的 hook 當對照：

```bash
ls -la .claude/hook-logs/<peer-hook-with-same-matcher>/ | tail
```

對照組持續產出、待驗 hook 零筆 → runtime 有在跑該 matcher 的 hook，但沒跑這一個。這一步把「runtime 沒觸發任何 hook」的可能性排除掉。

### 步驟 3：即時探針（可重現、可寫進 ticket 當證據）

發一個無害的、必然觸發該 matcher 的命令，然後立刻對照兩邊日誌：

```bash
echo "liveness probe $(date '+%H:%M:%S')"
# 隨即：
ls -la .claude/hook-logs/<hook-name>/ | tail -2
ls -la .claude/hook-logs/<peer-hook>/ | tail -2
```

對照組有新檔、待驗 hook 沒有 → **同一 session、同一 matcher、同一刻的差分**，證實該 hook 未被此 session 載入。這是可重現的實證，不是推論。

> **每日輪替改造後失效（2026-08-21 標註）**：步驟 2、3 皆以「出現新檔」或「檔案數增加」判定差分，前提是「一次觸發即一個新檔」。改每日輪替 append 後，同一 hook 同一天的所有觸發皆寫入同一檔案，第一次觸發之後檔案數就不再變化——**若待驗 hook 當天已觸發過至少一次，即時探針送出後沿用「有無新檔」判斷，會恆得出「沒有新檔」，把「剛剛才確實執行過」誤判為「未被此 session 載入」**，方向與原設計相反（假陰性而非假陽性）。
>
> **Action**：改用行數或 mtime 差分，或直接查步驟 1 標註提及的 liveness 索引：
>
> ```bash
> wc -l .claude/hook-logs/<hook-name>/<hook-name>-$(date +%Y%m%d).log 2>/dev/null
> echo "liveness probe $(date '+%H:%M:%S')"
> # 隨即：
> wc -l .claude/hook-logs/<hook-name>/<hook-name>-$(date +%Y%m%d).log 2>/dev/null
> ```
>
> 行數增加即證實該 hook 於探針前後被此 session 呼叫。若該 hook 覆蓋 `run_hook_safely`，直接查 `.claude/hook-logs/_liveness/<session_id>.jsonl` 更準確——不需計算行數差，且每筆自帶精確時間戳。

> 步驟 1-3 的共同設計原則：**不要問「它有沒有擋住」（無輸出無法回答），要問「它有沒有被呼叫」（可用差分回答）。** 步驟 4、5 接續回答「若未被呼叫，是哪一層原因」。

### 步驟 4：隔離執行（排除「判準錯誤」，把嫌疑收斂到載入層）

以 stdin 直接餵 hook 協定 JSON，繞過 runtime 的載入機制、直接執行 hook 本體：

```bash
echo '{"tool_name":"Bash","tool_input":{"command":"git stash"}}' | .claude/hooks/<hook-name>.py
```

若印出預期訊息、exit code 正確、且日誌新增一筆 → hook 本體（判準、import、日誌管線）皆正常運作，問題必然在「runtime 是否呼叫了它」，而非「它自己的邏輯是否正確」。此步驟排除「崩潰於寫日誌前」與「判準未涵蓋」兩種假設，把嫌疑範圍收斂到載入層（根因 1 或根因 5）。

### 步驟 5：檔案模式溯源（鑑別根因 5：缺可執行位）

```bash
git ls-tree <commit-hash> -- .claude/hooks/<hook-name>.py
```

對建立、修改、修復等相關 commit 逐一查詢，比對是否曾以 `100644`（無 `+x`）完成提交。

**Why `git ls-tree` 是這一步的必要工具**：`git log` 與 `git show --stat` 等預設精簡輸出（僅顯示 commit 訊息或增刪行數）不會顯示模式變化——對一次純權限修復的 commit 執行 `git show --stat` 會顯示 `0 insertions(+), 0 deletions(-)`，看起來像空提交。`git show`／`git diff`（不帶 `--stat` 的完整 diff）會顯示 `old mode`/`new mode` 行，但前提是已經知道要比較哪兩個版本；`git ls-tree <commit>` 可直接查詢任一 commit 當下的磁碟模式，不需要先鎖定「是哪次提交改的」——因此是回答「事故當下磁碟狀態為何」時，唯一不依賴預先知道異動 commit 的管道。

### 輔助：時間軸交叉比對

```bash
git log --format="%h %ad %s" --date=iso -- .claude/settings.json .claude/hooks/<hook>.py
git reflog --date=iso | head -20
```

若「hook 註冊 commit 時間」早於「事發時間」，則「涵蓋不足」的假設可被排除，指向載入而非判準問題。反之若晚於事發，才是涵蓋問題。

## 解決方案

### 立即處置

1. 以上述鑑別方法確認是載入問題而非判準問題（**先做這件事**，否則會誤修判準），並以步驟 5 檢查檔案可執行位（根因 5）。
2. 缺可執行位者直接 `chmod +x`。在 2026-08-18 觀測到的 runtime 上修復即時生效、不需重啟，且同一 session 內先前的執行失敗不會使該 hook 被永久略過；在採快照載入的版本上仍須等新 session。以雙探針實驗確認當前屬哪一種，不要憑本檔任一版本假定（見「機制更正」節）。
3. 若該 hook 防的是不可逆操作，在確認它至少被實際呼叫過一次（liveness，見根因 3）之前不得依賴它作為 gate——可執行位已補不等於判準正確。

### 結構修正方向

| 方向 | 說明 |
|------|------|
| 部署即驗證 | 新增防護類 hook 的 ticket，acceptance 必含「已於本 session 實地觸發並確認落檔」，不得只驗單元測試。（原條文要求「已通知既有 session 重啟」或「已標註本 wave 不生效」，依「機制更正」節已不適用） |
| liveness 訊號 | 防護 hook 提供可查詢的「最後一次被呼叫時間」，讓「沒出事」與「沒在跑」可分辨 |
| 缺席可鑑別 | 未命中路徑一律寫一筆可落檔的日誌，使「零筆」成為明確結論而非嫌疑 |
| 驗收環境對齊 | dogfooding 須在**註冊當下的那個 session** 內實地觸發一次。原條文的理由（新開 session 系統性排除問題情境）已不適用，但要求本身保留——理由改為：於註冊 session 內觸發是唯一能同時驗到「檔案可執行」與「判準命中」的路徑 |
| 可執行位落地檢查 | 以 shebang 執行的 hook 檔案**落地的當下**即驗證可執行位，不留待下次事故才發現（見根因 5）。攔截點是檔案落地事件，**不是**寫入 `settings.json` 的註冊動作——威脅事件為「`.py` 以 644 落地」，而註冊與落地可任意順序發生，且以註冊為攔截點會漏掉「先註冊後建檔」與所有不經設定檔的落地路徑。原條文以註冊為攔截點，2026-08-18 依實作重設計更正；該錯誤攔截點的成因見 PC-BAL-035 |

### 與 fail-open 的疊加（獨立但同向）

若該 hook 的錯誤處理是 fail-open（例外時放行、僅 PreToolUse 的 exit 2 才阻擋），則本模式與 fail-open 疊加後，防護在兩個獨立維度上都靜默失效。部署防護類 hook 時應同時檢查失敗語意，兩者是不同缺口。

## 預防措施

- 新增防護類 hook 的 ticket，acceptance 增列三項：本 session 實地觸發確認（取代原「既有 session 生效策略」——依「機制更正」節，註冊即生效，需驗的是可執行位與判準而非 session 世代）、liveness 驗證方式、失敗語意（fail-open / fail-closed）。此三項由 `.claude/hooks/acceptance_checkers/hook_protection_acceptance_checker.py` 於 complete 前強制檢查；該 checker 的判準措辭已於 2026-08-18 同步（模組說明、項目 1 label、缺項提示訊息三處）。偵測用的 substring 關鍵詞清單刻意保留舊模型用詞，以免既有 pending 票的原措辭由通過翻為被擋——清單是寬鬆偵測網，填法建議由 label 與提示訊息承擔。
- 任何「hook 應該擋卻沒擋」的事故，**第一步查載入而非查判準**——判準問題會留日誌，載入問題不會。
- 事故復盤時，「日誌無記錄」不得作為「該操作未發生」或「該操作繞過了防護」的證據；缺席不可鑑別，必須補差分觀察。

## 通用化檢驗

將專案細節（`workspace-wipe-guard-hook` / `git stash` / `settings.json`）替換為通用描述後仍成立：

> 「於系統執行中新增一個以啟動時快照載入的防護機制，該機制對所有既有執行體零效力；因防護機制的正常狀態即為無輸出，其失效與正常在可觀測面同形，無法從日誌缺席判讀；且部署者會連續取得（單元測試綠 / 註冊已寫入 / 新環境手測通過 / 自動化完整性檢查全綠回報）四個都指向已受保護的假訊號。」

→ 屬跨專案可重現的結構性缺陷。任何以「啟動時載入設定」為模型的系統（hook / plugin / middleware / sidecar 註冊）在執行中新增防護時都會踩到。

**通用化敘述的範圍限定（2026-08-18）**：上段引文以「啟動時快照載入」為前提。Claude Code 的 hook 機制經實測**不屬**此類（每次工具呼叫讀取當前磁碟狀態，見「機制更正」節），故本檔對本專案的實際適用形態是其變體——「新增的防護機制因缺少被啟動的條件（可執行位）而零效力，且失效與正常在可觀測面同形」。通用化敘述對真正採快照載入的系統仍然成立，但套用前須先確認目標系統的載入模型，不可由本檔的分類推定。
