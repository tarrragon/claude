# PC-GPD-045: 修法選項的成本以缺陷盤點數呈現給決策者，未換算成該修法實際的影響面

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-10-28 |

## 症狀

分析票盤點了缺陷的發生處（N 處），並提出數個修法候選。其中一個候選的作法是改 API 本身（例如移除預設建構子、把參數改為必填），它的影響面是「該 API 的所有使用處」，而不是「有缺陷的 N 處」。轉問決策者時，選項描述沿用盤點數寫成「N 處全改」，決策者依此成本選了該候選。

落地拆票、做到最後一步（移除過渡路徑）時才發現，實際要改的是 API 的全部使用處，數量是 N 的數倍，另外還暴露出 API 原本沒有涵蓋的用法。成本在決策後才放大，決策者當初比較的是錯的數字。

實證（2026-10-28，文字元件行數政策）：盤點 19 處「body 變體未帶行數參數」的呼叫端，候選 C 為「行數必須明示（必填或拆變體）」，選項描述寫「19 處全改」。落地時才實數到移除預設建構子會影響 lib 約 70 處與 test 約 89 處，且新建構子只支援 body 變體，caption 等變體的多行需求沒有寫法。決策者被重新詢問一次範圍。

## 根因

**盤點的單位是缺陷，修法的單位是 API**。盤點回答「哪裡有問題」，影響面要回答「這個修法會碰到哪裡」。兩者只在「逐處修補」型的修法下相等；改 API 契約型的修法，影響面是 API 的使用集合，盤點數只是它的子集。

**選項描述由轉問者撰寫，轉問者沿用了分析票的數字**。分析票只有盤點數，轉問者把它當成每個候選的成本寫進選項，沒有對每個候選分別換算。

## 解決方案

成本放大在落地時才發現：停下範圍相關的動作（不建票、不讓代理人擴大範圍），實數影響面，重新轉問決策者，並把新數字與新暴露的 API 缺口一起呈現。

## 預防措施

- 轉問修法選項前，對每個候選分別問「這個修法碰到的集合是什麼」，用固定值實數（例如 `git grep -c` 該 API 的使用處），寫進該選項的描述，不沿用缺陷盤點數。
- 改 API 契約型的候選，同時列出新 API 尚未涵蓋的既有用法（例如只支援部分變體），作為該選項的已知缺口。
- 分析票的候選比較表，成本欄寫「影響面（集合名稱 + 實數）」而不是「修改處數」。
