# PC-BAL-017: 以複製作為分發手段時副本凍結於複製時點，之後的上游修復不傳播且驗證易假設已含

## 症狀

把檔案從一處複製到另一處作為分發手段（更新落後專案的腳本、補齊缺漏的模組、建立參照副本）。複製完成後，上游在同一工作階段內又修了該檔案的缺陷。副本停在複製那一刻的狀態，仍帶著已被修好的缺陷，而驗證副本時假設它已含最新修復。

典型表徵：

- 複製與上游修復發生在同一段連續工作中，時序相隔不遠，因此不覺得需要重新確認
- 驗證副本時選擇「應該最安全」的操作（如 `--help`、`--dry-run`、`--version`），而那恰好是該缺陷的觸發入口
- 驗證結果看起來像新問題，實際是已知缺陷在舊版本上的重現
- 副本所在的位置往往是外部 repo 或他人環境，缺陷在那裡的後果比在來源處更難察覺

## 根因

**複製是一次性快照，而修復是持續發生的事件；兩者的時間關係不會被任何機制記錄。**

三個放大因素：

1. **同一階段內的時序被壓縮成「同時」。** 複製發生在 T、修復落地在 T+1，兩件事在同一段工作記憶裡並存，於是「我複製了現行版」與「現行版已修好」被當成同一件事——而它們差一個修復。

2. **驗證選最安全的操作，而那可能正是觸發點。** 挑 `--help` 驗證 import 是否正常，正因為它應該無副作用。若缺陷本身就是「無副作用的操作變成有副作用」，這個選擇會從最安全變成唯一危險。

3. **副本的缺陷後果外溢。** 副本通常放在落後的專案或他人環境，那裡缺少來源處已建立的防護、測試與觀察習慣。同一缺陷在來源處會被測試攔住，在副本處直接生效。

## 影響

損害隨副本位置與缺陷性質而定。唯讀類缺陷只造成誤判；副作用類缺陷（觸發同步、寫入狀態、刪除檔案）會在缺少防護的環境直接執行。

最容易被忽略的是**副本會繼續分發**。副本一旦進入該專案的版本控制並被合併，就成為該專案的現行版；後續任何人依它工作都繼承那個缺陷，而缺陷的來源（複製時點）已無跡可循。

## 解決方案

| 時機 | 動作 |
|------|------|
| 複製前 | 記錄來源的 commit hash 或版本，使副本的來源時點可追溯 |
| 複製後、驗證前 | 確認來源自複製後是否有變更（`git log <來源檔> --since=<複製時間>` 或比對內容雜湊） |
| 驗證時 | 選「已知會產生輸出但不改變狀態」的操作，而非「應該無副作用」的操作。前者可觀察，後者依賴假設 |
| 副本進入版本控制前 | 對副本重跑來源的關鍵測試，或至少驗證來源最近修復的那個行為 |

**若上游在同一階段仍在變動，複製應延後至該階段結束**——分發一個正在被修的檔案，等於分發它的缺陷。

## 預防措施

- 複製作為分發手段時，在 commit 訊息記錄來源版本或 commit hash，使「副本落後多少」可被後續讀者計算
- 驗證副本用「來源最近修好的那個行為」作為探針，而非用通用的健康檢查——後者不會覆蓋剛修的部分
- 避免把「應該無副作用」的操作當驗證入口；改用會產出可比對輸出的操作
- 同一階段內若上游持續變動，複製排在最後；已複製而上游又變動時，主動重新複製而非等問題出現
