# PC-GPD-041: 同一守衛有多個執行點，判定調整只改到主入口，另一執行點自行串接判定而未跟上

**類別**: process-compliance
**嚴重度**: 中
**發現日期**: 2026-10-27
**來源版本**: 0.5.0
**相關情境**: 放寬內容守衛的豁免範圍後，於 commit 時被同一守衛的另一執行點擋下

---

## 基本資訊

| 項目 | 值 |
|------|-----|
| 風險等級 | 中 |
| 來源版本 | 0.5.0 |
| 偵測時機 | 依新豁免寫入的檔案在編輯時放行、在提交時被擋 |

## 核心原則

**一個守衛若同時在編輯時（PreToolUse）與提交時（commit 閘門、reference-transaction）執行，調整判定時必須找出全部執行點逐一改，或讓各執行點呼叫同一個「是否豁免」的合併判定函式。** 只改其中一個入口的 main 流程，其他執行點會繼續套用舊判定，同一個檔案在兩個時點得到相反結論。

## 症狀

- 檔案在 Edit／Write 時守衛不擋，`git commit` 或 CLI 提交時被同一守衛名稱擋下
- 提交層的擋下訊息與編輯層同名同格式，看起來像「豁免沒做好」，實際上是豁免只接到一個入口
- 提交層的程式碼重用守衛模組的個別判定函式（如各類豁免的 `is_*`），但由自己決定呼叫哪幾個、順序為何

## 根因

守衛模組對外提供多個細粒度判定函式，主入口的 main 依序呼叫它們；另一個執行點載入同一模組後，**自己重新串接這些函式**，而不是呼叫一個代表「完整判定」的函式。新增的豁免函式被加進主入口的 main 時，重寫串接的執行點不會自動得到它。模組本身沒有重複實作，重複的是「呼叫順序與組合」這一層，因此程式碼審查只看判定函式時看不出漂移。

本案的方向是多擋（fail-closed），代價是合法提交被擋、阻塞產品線。反方向同樣成立：若調整的是收緊（新增擋下條件），沒跟上的執行點會靜默放行，而且沒有任何訊號。

### 變體：同一執行點在各 worktree 有不同版本的守衛副本

git hook 的 shim 以 `git rev-parse --show-toplevel` 定位守衛腳本，所以在 linked worktree 內提交時，跑的是**該 worktree 分支上的守衛程式**，不是 main 上的版本。守衛的修正合併進 main 之後，分出時間早於這次合併的 worktree 仍跑舊判定：同樣的提交在主 checkout 會放行，在舊 worktree 會被擋。

實例：修正 commit 層豁免的票合併後，另一張早已派發、等著提交的票在自己的 worktree 重跑提交，仍被舊版守衛擋下。把 main 快轉（或合併）進該 worktree 分支後才通過。

處置：守衛修正合併後，等待提交的 worktree 先同步 main 再重試；分支有自己的 commit 時，以合併同步，不用 rebase 改寫已回報的 commit。

## 解決方案

1. 以守衛模組名稱 grep 全部載入點（`_load_module(..., "<guard>.py")`、`import`），列出每個執行點實際呼叫的判定函式
2. 讓漏接的執行點補上新判定；較佳做法是在守衛模組提供單一合併判定（如 `is_exempt_path` 涵蓋所有豁免類別），各執行點只呼叫它
3. 補測試時兩個執行點各一組，並各含 E2 正向對照（應被擋的輸入仍被擋）

## 預防措施

- 調整守衛判定的票，where.files 須包含守衛模組的全部載入點；建票前以模組檔名 grep 確認
- 守衛模組若已有「合併判定」函式（例如合併兩類豁免的 `is_exempt_path`），新增豁免類別時一併併入，而不是只在 main 另加一行
- 驗收至少在提交路徑實測一次，不只在編輯路徑實測
