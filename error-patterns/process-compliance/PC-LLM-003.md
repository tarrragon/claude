# PC-LLM-003: 推薦寫法只以引發修正的那類用途驗證就全面替換，依賴舊語意的另一類用途隨之失效

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 分類 | process-compliance（規則條文修訂的驗證範圍） |
| 來源版本 | 3.1.0 |
| 首次觀測 | 2026-11-10 |

## 症狀

每回合自動載入的 Bash 規則原本推薦 `uv --directory path run ...` 在指定目錄執行 uv 命令。一則 issue 回報 skill CLI 經此寫法執行時，子行程 cwd 被改成 path，相對路徑與專案根目錄解析到錯誤位置，外觀同測試紅燈。修正票把推薦寫法整句換成 `uv run --project path ...`（不改子行程 cwd），並以 skill CLI 的情境實測通過。

合併前審核在 repo 根目錄實測同一推薦寫法跑測試套件：`uv run --project .claude/hooks pytest --collect-only -q` 得 `no tests collected`（exit 5），舊寫法得八千多個測試。框架內另有近百處以舊寫法跑測試套件。新條文若合併，照規則執行的 session 跑測試會收集到 0 個。

## 根因

**被替換的寫法同時服務兩類用途，修正只看見引發它的那一類**。`--directory` 改子行程 cwd：對「路徑相對呼叫者」的命令（skill CLI、帶相對路徑引數的測試）是缺陷，對「以該目錄為收集起點」的命令（pytest 全套件）正是所需語意。修正以 issue 描述的用途為驗收依據，實測也只取該用途，另一類用途沒有出現在任何驗證步驟中。

為何不易察覺：

- acceptance 寫成「不再推薦會讓 X 出錯的寫法」，新寫法對 X 確實正確，驗收照字面通過。
- 推薦寫法所在的條文是速查表一列，看起來像單一用途的語法提示，讀者不會聯想到它也是全框架跑測試的範本。
- 失效形態是「收集到 0 個測試」而非紅燈；未讀 exit code 時容易被看成「沒有測試要跑」。

## 解決方案

- 推薦寫法依用途拆開，各自寫明適用條件與一則實測：路徑相對呼叫者的命令用 `--project`，跑該目錄自己的測試套件用 `--directory`。
- 修訂後的條文以兩類用途各實測一次，結果附在條文的詳細版。

## 預防措施

- 修訂規則中的推薦命令前，先以 grep 盤點框架內既有用法，依命令類型分組；每一組至少實測一次新寫法，任一組失效就不能整句替換。
- 修訂票的 acceptance 除了「不再推薦會出錯的寫法」，同時寫「既有用途 Y 仍可依新條文執行」，使另一類用途進入驗收。
- 審核修改自動載入層推薦命令的票時，審核者以與引發修正不同的用途實測一次。
