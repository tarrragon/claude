# PC-LLM-001: 以版本准入規則壓低修法深度：修法保留了造成缺陷的結構

## 基本資訊

| 項目 | 值 |
|------|-----|
| 風險等級 | 中 |
| 來源版本 | 3.0.2 |
| 偵測時機 | patch 規劃期，用戶質疑 PM 推薦的修法 |

## 摘要

版本准入規則（patch 只收承諾未達成的缺陷）回答「哪些問題進這一版」，不回答「進來的問題要修多深」。把前者套到後者，會推薦 diff 最小、但保留缺陷成因的修法：這一次的缺陷消失了，產生它的結構還在，下一次同類變更照樣出錯。

## 症狀

| 症狀 | 觀察點 |
|------|--------|
| 選項描述寫明了根因，推薦的選項卻不消除它 | 選項文字寫「這正是漏改的原因」，推薦的卻是「對齊另一份實作」 |
| 以「patch 要最小」「不動已修好的程式」作為不消除根因的理由 | 理由引用的是版本範圍，不是該修法的技術風險 |
| 根因延到某張後續票，但沒查那張票的範圍是否涵蓋 | 延後目標是候選池的票，可能被放棄；它的 what 談的是另一個面向 |
| 要收斂的「既定規則」沒有對權威來源實測 | 把某份實作的現行判定當成正確規格，搬進共用位置 |

## 案例（2026-11-09）

一個 hook 誤報。同一份 gitignore 涵蓋判定在兩個 hook 各寫一份，前一版只修了其中一份。開 patch 時 PM 列出三個修法：

- A：讓第二份對齊第一份的規則
- B：把判定抽到共用 lib，兩個 hook 都呼叫
- C：改用 git check-ignore

PM 推薦 A，理由是 patch 範圍最小、不動前一版已修好的 hook、重複實作留給下一個 minor 的候選票。用戶質疑「消掉根因才是正確的改動」。檢討結論如下：

1. A 不是修法，是複製缺陷的前提。判定仍有兩份，下次規則一改就會再漏一份。
2. 「不動已修好的 hook」這個理由，高估了動它的風險。那個 hook 有測試，合併閘門會重跑；重複實作的風險卻沒有任何測試覆蓋，沒有測試斷言兩份判定一致。
3. 延後目標票處理的是另一組名稱的錨定問題，不涵蓋兩份實作的重複；候選池的票也可能因連續兩輪未選入而放棄（PC-APP-001 的實例）。
4. 改採 B 之後又發現，「前一版已定的規則」本身也錯。consumer 用不帶斜線的裸名，git 實測可涵蓋巢狀位置，前一版的 hook 卻判為缺項；兩份實作各錯在不同寫法。只做 A，會把錯誤規則複製到第二份；做 B 但沿用現行規則，會讓錯誤集中後更一致。最後以 git check-ignore 對十種寫法的實測真值表作為判定規格，測試以 git 為對照。

## 根因

| 層 | 說明 |
|----|------|
| 規則誤用 | 把版本准入規則（決定哪些問題進 patch）讀成修法深度的上限。框架的收斂規則只規定准入，沒有要求修法要淺 |
| 風險代理 | 以 diff 大小代理風險。實際風險有兩項：同類缺陷再發生的機率，以及改動破壞未受測試保護之行為的機率。前者 A 最高；後者 B 有測試保護 |
| 現狀偏誤 | 「已修好的程式不要碰」把碰它的成本算得比留下重複的成本高 |
| 延後未查證 | 把根因延到後續票，沒有核對那張票的範圍（PC-APP-001） |
| 規格未驗證 | 把某份實作的現行行為當成正確規則，沒有對權威來源（本例為 git）實測 |

## 正確的判斷方式

修法深度由兩個問題決定，與版本範圍分開判斷：

1. **這個修法會不會重現產生缺陷的條件？** 會，就不算修法。
2. **消除根因需不需要一個還沒做的設計決策？** 不需要（例如只是把同一份知識移到它唯一的位置），本版就做。需要（例如換判定方法，且取捨尚未評估），只把那個決策延後，並確認延後目標票的範圍涵蓋它。

**Why**：准入規則控制版本的工作量與承諾邊界，修法深度控制缺陷會不會回來，兩者回答不同的問題。**Consequence**：混用時，每個 patch 都只修掉當次的症狀，同一根因在後續版本反覆以新症狀出現，每次都要重新診斷。**Action**：列修法選項時，先問上面兩個問題，再看版本範圍是否容得下；問題已進本版，就不再拿版本範圍壓低修法深度。

收斂到單一實作之前，先對權威來源實測要收斂的規則：集中一份錯的規則，只會讓錯誤更一致。PC-006 的分界仍然適用：要收斂的是知識重複（同一條規則、同一份資料），不是語法相似。

## 防護措施

| 時點 | 動作 |
|------|------|
| 列修法選項時 | 每個選項標明是否消除根因；推薦不消除根因的選項時，寫出它在等哪一個未做的設計決策 |
| 推薦理由引用版本範圍時 | 檢查理由回答的是不是「這個問題要不要進本版」；問題已進本版，這類理由不能用來壓低修法深度 |
| 延後根因時 | 讀延後目標票的 what 與範圍，確認涵蓋（PC-APP-001） |
| 收斂判定到共用位置前 | 對權威來源（工具本身、規格原文）實測，並以實測結果作為測試對照 |
