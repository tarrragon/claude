# PC-GPD-080：實機驗證要先對環境與觀測工具做正向對照，零結果才算證據

## 基本資訊

| 項目 | 內容 |
|------|------|
| Pattern ID | PC-GPD-080 |
| 分類 | process-compliance（runtime 驗證與觀測判讀） |
| 風險等級 | 高（環境故障被讀成程式缺陷時，會派出不存在問題的修正批；觀測工具漏行被讀成事件不存在時，結論會一路錯下去） |
| 來源版本 | 0.6.0 |
| 首次觀測 | 2026-11-03 |
| 關聯 | [[PC-165]]、[[PC-166]] |

## 摘要

**實機驗證得到「零事件」「沒有 log」這類否定結果時，只有在兩個前提都經正向對照證實之後，才能拿它當證據：(1) 環境確實送得出被測的事件；(2) 觀測工具確實收得到並且沒有漏行。** 缺任一個前提，「沒收到」與「不存在」在觀測面上完全同形，判讀會被引向錯的層級。

## 症狀

- 實機上看不到預期的平台事件（檔案監看、通知、感測器等），測試套件全綠。
- 判讀者依序懷疑程式碼的各個環節，派出 incident 分析或補 log 的修正批，但每一環從程式碼看都有接上。
- 觀測腳本給出的結果前後矛盾，例如一次說「零事件」，重測時又冒出被截斷的記錄。
- 不同的觀測讀法得出互相衝突的時序判讀，例如時間戳是原始時間還是腳本印的連線時間。

## 根因

1. **否定結果沒有鑑別力。** 「App 沒收到事件」同時符合三種成因：程式碼斷鏈、平台沒有送出事件、觀測工具沒接到。只看這一個結果，分不出是哪一種。
2. **觀測工具被當成透明的。** 多層 `grep` 管線、背景 monitor 的緩衝、自行印出的 `new Date()` 時間戳，都會改寫或吞掉資料。工具本身沒驗證過，它給出的零結果就不是證據。
3. **探針沒有先證明自己能看到「有」。** 用來判斷環境的探針如果從沒收到過正向事件，探針寫錯與環境故障同樣會產生零結果。

## 實例（macOS 桌面 App 檔案監看實機驗證，2026-11-03）

一個以 `package:watcher` 監看 `docs/` 的 Flutter macOS App，實機驗證中連續出現三次誤判，最後都是加入已知正確的對照組後被推翻：

| 誤判 | 推翻它的對照 |
|------|-------------|
| 「App 收不到事件，斷點在監看第一環」 | 同一支 FSEvents 探針查歷史可收到上萬筆、查即時 0 筆，加上宿主 `fseventsd` 持續 100% CPU：環境不推送即時事件，與 App 無關。重啟 `fseventsd` 後，同一份 build 在同一組操作下立即正常觸發，確認因果 |
| 「VM service 新連線只重送到首輪完成」 | 改為直接寫檔、不經管線，連兩次各得完整且相同的記錄，`sequenceNumber` 連續 |
| 「重送記錄的時間戳是連線當下」 | 讀記錄本身的 `timestamp` 欄位而不是腳本自印的時間：記錄保留原始時間 |

## 解決方案

1. **環境健康閘門**：驗證前先檢查平台事件來源的健康度（例：`fseventsd` 的 CPU 使用率），不健康就回報「環境不可驗證」，不判程式失敗。
2. **金絲雀正向對照**：用最小探針在新建的空目錄觸發一次已知事件，必須看到事件才進入正式驗證。探針收不到時，先懷疑環境或探針，不懷疑被測程式。
3. **觀測工具自證不漏行**：收 log 直接寫檔，不經 `grep` 管線；以序號連續性判讀有沒有漏行，事後用重連取得的完整歷史交叉比對。
4. **判讀順序**：環境閘門 → 金絲雀 → 觀測完整性 → 才判讀被測程式。前一層沒過，後一層的否定結果一律不採計。

## 預防措施

- 實機驗證配方（verify skill 一類）把環境閘門與金絲雀寫成必經的第 0 步，閘門紅時輸出與程式失敗不同的結論碼。
- 派發 incident 分析前，先確認否定結果已通過上述三層前提；未通過時，分析對象應是環境或觀測工具，不是程式碼。
- 與 [[PC-165]] 互補：PC-165 處理「測試綠燈不等於 runtime 正確」，本 pattern 處理「runtime 的否定觀測不等於 runtime 缺陷」。
