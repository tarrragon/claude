# PC-GPD-020: 明示的意圖與明示的失敗，在可觀測面與預設或成功不可區分

| 項目 | 值 |

| 編號 | PC-GPD-020 |
| 類別 | process-compliance |
| 風險等級 | 高 |

| 來源版本 | 0.1.0 |

## 症狀

呼叫端做了一個**明確的區分**——傳了一個旗標、指定了一個值、或收到一次失敗——而系統的可觀測輸出對這個區分**沒有任何表示**：與不傳旗標、與預設值、與成功，逐字相同。

**識別特徵**：

- 明示與不明示產生**完全相同**的產物，不是相似，是逐字相同
- 沒有警告、沒有非零退出碼、沒有任何一處記下「你指定過而我沒照做」
- 因此無論觀測得多仔細都無法察覺——這與 `PC-GPD-019`（觀測者太早停手）互斥：那邊多看一眼就會發現，這邊多看一眼也一樣
- 測試常是綠的，因為測試恰好走在「該區分不產生差異」的那條路徑上
- 發現途徑幾乎總是**同批多筆對照**（同時做傳與不傳兩次，並排比對產物），不是單次檢視

## 根因

**區分存在於呼叫端的意圖裡，但沒有被編碼進任何一個會被讀到的地方。**

三種常見的具體成因：

| 成因 | 機制 |
|------|------|
| 回傳值不帶區分 | 函式對「使用者明確要求不做」與「使用者沒說」回傳同一個值（如都回 `None`），呼叫端無從分辨，於是走同一條後續邏輯 |
| 分支不可達 | 處理該旗標的分支寫了，但只在另一條路徑失敗時才會走到——**旗標只在它不改變任何結果的情境下生效** |
| 錯誤未進入輸出通道 | 失敗訊息寫在輸出的一端（如 argparse 的 usage 在頭），而呼叫端只看另一端；或內容為空仍照常送出並回傳成功 |

**為何它比一般的靜默失敗嚴重**：一般靜默失敗至少在「有沒有發生」上留下差異（東西沒被建立、狀態沒變）。本模式的產物**存在且外觀正確**，只是內容取自預設而非你指定的值。下游因此不會有任何一環察覺，會一路把它當成你的決定往前推。

## 實例（同一日，兩個並行 session 各兩則）

| 明示的是什麼 | 系統的可觀測輸出 | 為何無法察覺 |
|-------------|----------------|------------|
| `--no-topic` 旗標（要求不指派主題） | 與不傳旗標時**指派了同一個主題**；同批三筆對照（不傳／傳 `--no-topic`／傳 `--topic`）才顯形 | 推導成功時回傳值與「什麼都沒指定」相同，處理該旗標的分支只在推導失敗時可達 |
| 建票時 `--who` 指定的預期執行者 | 該代理人**從未被派發**，而欄位照樣顯示它是持有者 | 欄位語意混用「預期執行者」與「當前持有者」，兩者在顯示上同形 |
| CLI 參數錯誤（未知旗標） | 錯誤在輸出頭部、內容原樣回吐在尾部；`\| tail` 之下與成功回音同形 | 判別依據落在被截斷的一端 |
| 送出空內容（heredoc 未接上 stdin） | 照樣 POST、`exit 0`、印出可解析的成功 URL | 寫入命令零長度檢查；`update` 這一支的空內容會直接清空既有區段 |

## 解決方案

發現後：不要只修那一個旗標。**問「這個區分在哪一步被丟掉」**——回傳值、分支可達性、輸出通道三者之一，修那一步；只補一個 `if` 常常補在已經丟失資訊的下游。

## 預防措施

**寫入操作的驗證要兩段，且順序固定**：

1. **先讀 exit code**：`out=$(cmd 2>&1); rc=$?`。`rc` 是整數固定值，免疫輸出截斷、過濾與原樣回吐。
2. **再回讀產物**：確認送出去的是你給的東西。

**回讀的對象必須是世界平面的產物**——遠端 API 讀回的內容、檔案的實際行、版本歷史裡的內容。**不能是同一個命令的自我回報**：那個回報與被驗證的動作出自同一段程式，它錯的時候會一起錯，回讀只是把同一個謊聽第二遍。

**設計側**：新增一個旗標或一個「明確指定」的參數時，寫一個對照測試——同批各跑一次傳與不傳，斷言**產物不同**。只斷言傳了之後的產物正確，會在旗標完全無效時照樣通過（實例一的既有測試即如此：fixture 走不到會產生差異的那條路徑）。
