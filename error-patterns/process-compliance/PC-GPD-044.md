# PC-GPD-044: 父票把 acceptance 拆給子票承接後，子票改寫自己的 acceptance 時無聲收窄，漏掉父票要求的路徑

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 風險等級 | 中 |
| 首次觀察 | 2026-10-28 |

## 症狀

父票因超過拆分門檻，拆成數張子票，Problem Analysis 寫明「本票的 acceptance 由子票分別承接，子票完成後收尾」。其中一張子票在執行中改寫了自己的 acceptance，改寫後的情境清單少了父票 acceptance 要求的一條路徑。沒有任何一方寫下「這條路徑不做」的裁決，父票的 acceptance 也維持原文。

缺口要到父票收尾、逐項把 acceptance 對到子票證據時才浮現。這時子票都已合併，收尾者只能在「以推論勾選」與「另開補測票」之間選，而以推論勾選等於把那條路徑留成零覆蓋。

實證（2026-10-28，Domain 視圖矩陣與泳道同源修正的父票）：父票 acceptance 第一條要求 RED 重現測試涵蓋四條路徑（重掃中、取消後、從詳情卡進入泳道的疊加、跨輪錯位）。資料同源子票把自己的 acceptance 改寫成「重掃中／取消／失敗／新一輪／切專案」，「從詳情卡進入泳道」不在其中。這條路徑另有獨立症狀（定位欄的查詢回 null 而失效），子票自己也註明「未納入畫面測試」。父票收尾時才發現該路徑沒有 RED 證據，主控裁定另開補測子票，父票順延。

## 根因

**承接關係只寫在父票，子票的 acceptance 沒有反向連結**。父票寫「由子票承接」時，沒有把父票的每一條 acceptance 對應到某張子票的某一條。子票改寫自己的 acceptance 時，看不到哪些條目是在替父票承接，收窄因此不觸發任何檢查。

**子票改寫 acceptance 的理由是局部合理的**。子票依自己的實作範圍重新列情境，從子票視角看是更精確；遺漏的那條路徑在子票看來「行為等效」或「不在本票」，不會被當成移交裁決寫下來。

**與 PC-BAL-059 的差異**：PC-BAL-059 是移交裁決已寫在承接方，上游未同步；本模式是根本沒有移交裁決，收窄是無聲的。PC-055 則是反方向：acceptance 被他票外溢達成。

## 解決方案

缺口已發生時：收尾者不以推論勾選，另開補測子票（`--parent <父票>`），RED 用原修正前的 lib 取得；父票等補測完成再 complete。

## 預防措施

- 父票拆子票時，在 Problem Analysis 列出「父票 acceptance 第 N 條 → 子票 X 的第 M 條」的對應表，不只寫「由子票承接」。
- 子票改寫 acceptance 時，若 parent 有承接對應表，先比對改寫後是否仍覆蓋對應條目；不覆蓋的部分寫成移交裁決，並依 PC-BAL-059 同步修訂父票。
- 子票合併時，PM 把「父票收尾」排進該線佇列，讓逐項對證據在子票剛合併、脈絡還在時發生，而不是數日後。
