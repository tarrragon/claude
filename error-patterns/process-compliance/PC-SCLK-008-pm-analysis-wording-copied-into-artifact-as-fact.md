# PC-SCLK-008：PM 前置分析的斷言措辭被照抄進產出

---

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-SCLK-008 |
| 類別 | process-compliance |
| 風險等級 | 中 |
| 首發時間 | 2026-08-03（screen_clock 1.4.0-W3-007 Phase 4 審查，文字與架構兩視角獨立指向同一措辭源頭） |
| 姊妹模式 | ARCH-BAL-004（文件範例成為缺陷散播源）、PC-040（派發前寫 Context Bundle） |

## 症狀

PM 依 PC-040 在派發前把分析寫入 ticket 的 Problem Analysis / Context Bundle，其中包含對風險點的提示。執行者忠實依 ticket 執行，並把 PM 的措辭**逐字搬進程式碼註解或文件**。

該措辭若是關於程式碼性質的斷言，而 PM 的推導又不夠精確，錯誤就從 ticket（暫時性載體）沉澱進原始碼註解（長期性載體）。後續讀者把它當作關於程式行為的事實，而它從來沒有被任何測試或審查驗證過。

**本案具體樣態**（1.4.0-W3-007 Swift 重構）：

- PM 在 Context Bundle 標示風險點，寫成：「若 generation 隨 session 一起消失，會失去攔截在途幀的能力」。
- 執行者採納該理由，寫進 `generation` 欄位的 doc comment。
- Phase 4 審查時兩個視角獨立指出該宣稱有問題：文字視角判定「程式碼未證成到此強度」（實際上 session 為 nil 時在途幀已被第二道 guard 攔下，實際成立的是較窄命題），並明確註明「此措辭源自 ticket 原文，非執行者自創」；架構視角則指出該理由是「實作順序上的偶然，不是本質」，真正的理由是世代序號區辨的是 session 之間而非 playing 對 idle。
- 兩個視角的切入軸不同，但都指向同一個源頭：PM 的措辭。

## 根因

**ticket 內文對執行者具有規格效力，但 PM 撰寫時的心理定位是「分析筆記」。** 兩者的精確度要求不同：筆記允許粗略的方向性描述，規格不允許。PM 寫下風險提示的意圖是「請在此處小心」，執行者讀到的是「這是關於此欄位的既定事實」。

放大因素有三：

1. **PC-040 要求把 context 寫進 ticket 而非 prompt**，這個要求本身正確（避免 prompt 膨脹、保留可追溯記錄），但也讓 PM 的措辭獲得了更持久的載體。
2. **執行者沒有理由質疑 PM 的分析**——那是它被要求依循的規格，照抄反而是合規行為。
3. **acceptance 通常不涵蓋註解準確性**，所以這類錯誤不會在驗收時被攔下。本案五條 acceptance 無一涉及註解，執行者自評全數通過是誠實的。

與 ARCH-BAL-004 同族（文件範例成為缺陷散播源），差別在載體：該案是參考文件的範例被複製到實作，本案是 ticket 的分析措辭被複製到註解。共同結構是**上游文字被下游當作權威來源複製，而上游從未按權威標準被審查**。

## 解決方案

1. **區分語氣**：風險提示寫成可驗證的預測，不寫成關於程式碼性質的斷言。
   - 斷言句（錯）：「若隨 session 消失，會失去攔截在途幀的能力」——關於程式行為的宣稱，錯了會沉澱成錯誤註解。
   - 預測句（對）：「此處若判斷錯誤，場景 17 與重置後續幀推進兩類測試會紅燈」——關於驗證結果的宣稱，錯了會被測試抓到。
2. **語態改造優於語氣改造**：把「理由 + 措辭」改寫為「約束 + 驗收」。前者提供了現成可貼的句子，後者提供同樣的資訊卻沒有適合貼進 doc comment 的形式。
   - 理由語態（會被抄）：「世代作為參數傳入使 startNewPlayback 遞增而 reset 不遞增的差異在呼叫端顯性」
   - 約束語態（抄不走）：「約束：`scheduleDeadline` 的 generation 必須是參數，不得在函式內讀取。驗收：`resetExistingPlayback` 呼叫處可見傳入未遞增值。」
3. **可證偽預測須檢查判準存在性**：寫「若 X 則測試 Y 紅燈」時，同時確認測試 Y 當下確實存在。判準不存在的預測形式上可證偽、實際上懸空，卻因形式正確而取得它不該有的可信度。不確定時明說「該分支目前無獨立覆蓋，需先補測試才可判定」。
4. **發現後歸因到源頭**：修正時同時修 ticket 措辭與已擴散的註解，只修其一會在下次派發重現。

### 防護必須覆蓋 ticket 的所有欄位，不只風險提示欄

本 pattern 首次記錄後，PM 於次一張票（1.4.0-W3-009）實施防護：把風險提示改為「若 X 則測試 Y 紅燈」的預測形式。文字審查查證該三條措辭確實未出現在 Solution、commit 或任何 doc comment——**該欄位的照抄路徑被結構性切斷**（沒有人會在 doc 裡寫「若…則測試會紅燈」）。

但同一張 ticket 的 `how.strategy` 仍為斷言語態，並被逐字繼承兩次：`how.strategy` →  commit 訊息 → `scheduleDeadline` 的 doc comment。

**教訓**：防護窄化到「PM 意識到有風險的那個欄位」，同一份文件中結構相同的其他欄位仍是敞開的。ticket 的每個自由文字欄位（`why` / `how.strategy` / Problem Analysis / Context Bundle）對執行者都有同等的規格效力，防護須覆蓋全部，不是覆蓋撰寫時最警覺的那一個。

## 預防措施

| 情境 | 動作 |
|------|------|
| PM 在 ticket 寫風險提示 | 用「若判斷錯誤，X 測試會紅燈」的預測形式，避免「若 X 則會 Y」的性質斷言。同時確認 X 測試當下確實存在 |
| PM 在 ticket 寫實作策略 | 用「約束 + 驗收」語態，不用「理由 + 措辭」語態。策略草案標明為草案；執行者偏離時要求說明理由，而非默認採納草案措辭 |
| PM 實施本 pattern 的防護 | 逐一檢視 ticket 的**每個**自由文字欄位（`why` / `how.strategy` / Problem Analysis / Context Bundle），不只加固當下最警覺的那一個 |
| 重構類 ticket 的 acceptance | 若重構動機涉及「註解與實作不符」，acceptance 應含一條註解準確性條款，否則該面向不進驗收範圍 |
| Phase 4 審查發現註解問題 | 追問措辭來源：是執行者自創，還是 ticket 原文？後者須回頭修 ticket，否則同一措辭會在後續票再次擴散 |

**一般化**：任何被下游當作規格依循的文字（ticket、設計文件、參考範例），其精確度要求等同規格，不因撰寫時的心理定位是「筆記」而降低。判準：這段文字有沒有可能被逐字複製到比它更長壽的載體？有 → 按規格標準寫。
