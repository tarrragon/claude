# PC-GPD-006: 「各專案自建」目錄跨 consumer 整包複製，夾帶他方識別符

## 症狀

共用資產裡有一類目錄的設計語意是「不隨同步傳遞、由各專案自建」，用來裝該專案的落地耦合（任務系統對應、規則索引、案例集）。當某個守衛開始要求該目錄下的某個檔案存在，而本專案還沒建過這一層時，最省事的做法看起來是從另一個 consumer 整包複製——那邊的檔案齊全、格式正確、而且共用的上游規格位元相同。

複製進來的內容通篇引用對方的 ticket 編號、版本號與檔案路徑。這些引用在本專案查不到對應項，索引也指向本專案沒有的檔案。

## 根因

| 層級 | 機制 |
|------|------|
| L1 語意反轉 | 「不隨同步傳遞」被讀成「可以自由搬運」。實際語意相反：正因為內容綁著單一專案，才不放進同步範圍 |
| L2 相同性的誤推 | 上游規格（skill 本體、設定檔）位元相同，很容易推論「所以整合層也適用」。位元相同的是被映射的對象，不是映射之外的敘事內容 |
| L3 守衛觸發的急迫感 | 缺檔會直接擋提交，處置壓力指向「最快讓它通過」，而整包複製是最快的路徑 |

## 案例

框架升版帶入一個一致性守衛，要求 `<skill>/references/project-integration/triggers-alignment.yaml` 存在，否則擋提交。本專案原本沒有這一層。

因兩專案的 skill 本體與設定檔位元相同，映射檔內容確實適用，於是整個目錄八個檔一起複製了進來。提交時被引用穩定性守衛擋下：其中六個檔含他專案的 ticket 編號，案例集一份就有十九個。

改為只取兩份——映射檔本身（其註解裡的一個編號改寫為描述性說法），以及一份約束清單（它引用的全是本專案也有的框架檔案）。其餘五份不取，索引改寫為本專案版本，並列出還缺的部分與各自的建立時機。

守衛的判斷是對的：那些編號在本專案查不到對應項，跨專案同步後會變成死連結。

## 防護

**Why**：一份檔案能不能跨 consumer 複製，取決於它的內文引用了什麼，不取決於它所在的目錄或它映射的對象是否相同。整合層的存在理由就是裝那些不能共用的東西。

**Consequence**：整包複製會把他方的編號、版本與檔案路徑當成本專案的歷史寫進框架層。輕則索引指向不存在的檔案，重則後續讀者把他方案例當本專案紀錄去追，追不到再回頭懷疑自己的紀錄有缺漏。

**Action**：

| 步驟 | 做法 |
|------|------|
| 判斷可取範圍 | 逐檔掃他專案識別符（ticket 編號、版本號、專屬路徑）。零命中且引用的檔案本專案都有的才可取 |
| 對可取但有零星命中的檔 | 把該處改寫為描述性說法（「另一 consumer 的分析產出，某年某月定案」），不保留編號 |
| 對不可取的檔 | 不取。索引改寫為本專案版本，列出缺的部分與各自的建立時機，避免索引指向不存在的檔案 |
| 若確有保留他方內容的價值（如案例集） | 於檔頭明寫來源、寫明「在本專案查不到對應紀錄」、寫明累積自己的內容後逐條替換。只做這一步不足以通過引用穩定性守衛，仍須移除編號本身 |
| 事後 | 該目錄的索引裡記下這一層的建立經過，讓下一個讀者知道哪些是自己的、哪些是借來的 |
