# PC-BAL-026：驗證管道經快取層讀取，輸出滯後於待驗現象

## 基本資訊

| 項目 | 值 |
|------|-----|
| 風險等級 | 中 |
| 分類 | process-compliance |
| 來源 Ticket | 0.2.1-W3-352 |
| 家族上位 | PC-BAL-010（驗證管道對待驗現象不敏感） |

## 症狀

執行寫入操作（push / 上傳 / 發布）後立即以工具內建的檢查命令驗證，報告顯示狀態完全未變，看起來像操作靜默失敗。重跑操作得到「無變更可推送」，形成「工具說沒變、報告說沒生效」的矛盾狀態。

實例（0.2.1-W3-352）：`skill-sync push` 連續推送 14 個 skill 全部回報成功，隨即執行漂移報告仍顯示 `diverged 14`，與 push 前完全相同。

## 根因

驗證管道與寫入管道走不同的讀取路徑，其中驗證側經過快取層：

| 管道 | 路徑 | 是否經快取 |
|------|------|-----------|
| 寫入 | `git push` 至 origin | 否，直達 |
| 驗證 | `raw.githubusercontent.com/<repo>/main/versions.json` | 是，branch 路徑有 CDN 快取 |

快取的失效延遲使驗證側在一段時間內持續回傳寫入前的內容。這與 PC-BAL-010 的恆真/恆偽不同——管道本身有鑑別力，只是輸出滯後於現象；症狀出現在時間軸上，重跑同一命令在快取過期前得到相同錯誤結果，看起來像穩定的失敗事實而非暫態。

加重因素：HTTP `Cache-Control: no-cache` 請求標頭與 query string cache-buster 對此類 CDN 皆無效，使「我已經繞過快取了」的自我驗證也失準。

## 解決方案

以不經快取層的第二管道交叉驗證，判定「操作失敗」與「驗證滯後」：

| 驗證手段 | 是否經快取 | 用途 |
|---------|-----------|------|
| `git clone` / `git fetch` 後讀工作區檔案 | 否 | 權威判定 |
| 以 commit SHA 取代 branch 名的 raw 路徑 | 否（immutable 路徑不快取） | 快速交叉驗證 |
| branch 路徑 raw URL | 是 | 不可作為即時驗證依據 |

判定準則：第二管道顯示已生效 → 操作成功，報告滯後，等待快取過期後重驗即可；第二管道也顯示未生效 → 操作確實失敗，進入除錯。

## 預防措施

1. **工具層**：驗證用的讀取路徑應與寫入路徑同源（讀 clone 而非 CDN），或在 immutable 路徑（帶 commit SHA / 內容雜湊）上讀取。以可快取的 branch 路徑作為狀態權威，等於把驗證正確性押在快取行為上。
2. **流程層**：寫入後立即驗證得到「毫無變化」時，先問「驗證管道是否與寫入管道同源」，再問「操作是否失敗」。順序顛倒會導致重跑寫入操作（可能產生重複副作用）或錯誤回滾已生效的變更。
3. **與 tool-output-trust-rules 規則 6 的關係**：該規則處理「驗證器判準過期」（建立端已更新、驗證端清單未同步）；本模式處理「驗證器資料過期」（判準正確，讀到的資料是舊快照）。兩者都要求遇衝突時查更權威的來源，差別在權威來源分別是建立端定義與非快取管道。
