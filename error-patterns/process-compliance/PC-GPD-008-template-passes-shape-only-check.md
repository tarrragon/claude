# PC-GPD-008: 未填樣板通過數量型檢查，因為它形狀正確而內容空白

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-GPD-008 |
| 類別 | process-compliance |
| 風險等級 | 中 |
| 發現日期 | 2026-09-08 |
| 來源版本 | 0.1.0 |

## 症狀

工具產生的預設樣板恰好滿足下游驗證器的數量門檻，因此無論是否被填寫都恆通過。
驗證器回報 PASS，人讀了也覺得合理——樣板句型完整、有動詞有受詞，只有大括號佔位符
洩漏它是空的。

**本案實例**：ticket CLI 建票時未給 `--acceptance`（或以 `--force` 建立）產生的預設
驗收條件恰好三條，而 `dispatch-validate` 規則 4 檢查的是「acceptance 項數 >= 3」。
規則對這類缺陷零鑑別力：

| 樣板條目 | 洩漏處 |
|---------|-------|
| 指定功能（`{feature_name}`）實作符合設計規格 | 大括號 |
| 文件內容完整：包含標題、背景、正文、結論、附錄等 `{N}` 部分 | 大括號 |
| 格式符合規範：遵守專案入口文件的文件格式規則 | **無**——這一條讀起來完全正常 |

第三條是關鍵：同一批樣板裡有的條目連佔位符都沒有，純粹靠泛稱撐起一個看似可驗收的句子。
針對佔位符的偵測抓得到前兩條，抓不到第三條。

同一 session 三次命中（兩張 spawn 票、一張 `--force` 建立的票），全部在人工逐票覆核時
才被發現。其中一張更是在覆核者先前誤記「已補齊」之後，才由查證推翻。

**識別特徵**：

- 驗證器的判準是「數量 >= N」「非空」「欄位存在」這類**形狀檢查**
- 被檢查對象有一份工具產生的預設樣板，且樣板恰好滿足該形狀
- 樣板條目讀起來像成品（完整句、有結構），不像明顯的空白欄位

## 根因

形狀檢查與內容檢查是兩件事，而樣板的設計目標**正是提供正確的形狀**。兩者相遇時，
驗證器量到的是樣板作者的工作成果，不是使用者的。

這與 `PC-110`（schema 分隔符使 body 檢查偽陰性）同屬「檢查器量到的東西不是它以為在量的東西」，
但觸發方式相反：PC-110 是檢查器解析失誤而漏看內容，本案是檢查器正確讀到了內容、
而該內容碰巧滿足判準。前者修解析，後者要改判準。

加重因素：樣板是**唯一**能同時滿足「形狀正確」與「內容空白」的東西，因此它必然落在
形狀檢查的盲區正中央——不是偶然的邊緣案例，是結構上的必然。

## 解決方案

1. **形狀檢查旁邊補一道來源檢查**：判斷內容是否仍等同建立端的預設樣板。判準不是
   「有沒有佔位符」（如上表第三條所示，樣板可以不含佔位符），而是「是否與樣板逐字相同」。
2. **樣板字串的權威來源是建立端**，不在驗證端另建副本清單——兩份清單會各自漂移
   （見 `PC-BAL-001`）。驗證端應引用建立端的常數。
3. **選填欄位需區分「沒填」與「留樣板」**：選填的語意是「可以不填」，不是「可以留樣板」。
   兩者現在在多數 schema 下無法區分——空白與樣板都通過。
4. 覆核者側：看到形狀檢查全 PASS 時，**額外抽讀內容**。PASS 只證明形狀對。

## 預防措施

| 時機 | 動作 |
|------|------|
| 設計任何「數量 >= N」「非空」型驗證器時 | 問：被檢查對象有預設樣板嗎？樣板會通過嗎？會就補來源檢查 |
| 設計預設樣板時 | 讓樣板**故意不滿足**下游的形狀判準（例：預設兩條而門檻是三條），使未填必然被擋 |
| 建票／建檔工具提供預設值時 | 預設值以明顯的未填標記呈現，不以完整句呈現 |
| 覆核他人或代理人產出時 | 驗證器 PASS 不代表內容已填；逐項抽讀是唯一能區分的手段 |
| 例外 | 樣板本身即為合法終態的情形（如「本欄不適用」是有效答案），此時應改為明示的枚舉值而非自由文字樣板 |

## 行為模式分析

樣板的存在理由是降低填寫成本，而它降低成本的方式正是「先把形狀擺好」。驗證器若只檢查形狀，
等於在驗證樣板作者是否盡責，而非使用者是否盡責——兩者都盡責了，只是沒人做真正的工作。

覆核者這一側還有第二層：形狀檢查全綠會**降低**抽讀內容的動機。綠燈本應是抽讀的替代品，
在這個場景它是抽讀的阻礙。這也是為什麼三次命中全部發生在有人因別的理由打開票面時，
而不是在檢查流程裡。

## 相關

- `PC-110`（schema 分隔符使 body 檢查偽陰性）：同為檢查器失去鑑別力，但成因相反——
  該案是解析漏看內容，本案是判準本身對樣板無鑑別力

- 落地票：`dispatch-validate` 規則 4 補來源檢查（本專案 0.1.0 Wave 3 建立）
