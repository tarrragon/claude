# PC-GPD-068：產出合併前即標為完成

## 基本資訊

| 項目 | 內容 |
|------|------|
| Pattern ID | PC-GPD-068 |
| 分類 | process-compliance（隔離交付的結案時點） |
| 風險等級 | 中 |
| 來源版本 | 0.5.0 |
| 首次觀測 | 2026-10-13 |
| 關聯 | [[PC-108]]（代理人提交後未主動完成票；本模式是反方向：在隔離分支上完成得太早）、[[PC-BAL-002]]（合併後的產物自述完整而無驗證；本模式是票面狀態自述完成而無驗證） |

## 摘要

**以隔離分支（如 git worktree）交付時，「提交完成」與「產出進入主線」是兩個時點。票在前者就標為完成，票面狀態便宣稱了一件尚未發生的事。** 之後的合併前審查、修正、合併都發生在「已完成」之後，只能以追加段落記在票面；完成時間早於審查與合併，讀票的人看不出產出是何時才真正生效。

## 症狀

- 票的 `completed_at` 早於該票的合併前審查、審查要求的修正提交，以及合併提交。
- 票面出現「票面狀態雖為 completed，產出尚未進入主線」這類暫停紀錄。
- 合併前審查判定「須修正後合併」，修正與複審以追加段落補在已完成的票上。
- 依狀態排程的工具把該票當作已交付，而主線上沒有它的產出。

實例（2026-10-13）：一張腳本修正票在 worktree 提交後隨即標為完成，此時尚未審查、未合併。隨後機器負載過高、派發暫停，票停在「completed 但未合併」。恢復後才做合併前審查，審查要求六項修正，修正、複審、合併都追加在已完成的票上。事後驗收稽核把「產出合併前即標為完成」列為記錄錯誤。

## 根因

- **Why**：「完成」的判準沿用非隔離開發的時點：提交即生效。隔離交付多出一段「合併前審查、合併閘門、合併」的過程，而票務的完成指令在隔離分支內同樣可以執行，沒有東西把它擋在合併之後。另一條相鄰的規範要求代理人提交後主動完成票（見 [[PC-108]]），在隔離交付下照做就會落入本模式。
- **Consequence**：

| 層級 | 影響 |
|------|------|
| 狀態一致性 | 票面為已完成，主線沒有產出；合併閘門紅燈或審查不放行時，需要重開票 |
| 排程與依賴 | 以「前置票已完成」放行的下游票可能在產出缺席時開工 |
| 紀錄可讀性 | 完成時間不再代表交付時間；審查與合併的紀錄落在完成之後，稽核要逐段重建時序 |

## 解決方案

- **Action**：隔離交付的完成時點定在「合併進主線並通過合併前測試之後」，由負責合併的一方在主線執行完成指令；代理人在隔離分支止於提交。

| 角色 | 隔離分支內 | 合併後於主線 |
|------|-----------|-------------|
| 實作代理人 | 提交、填寫票面紀錄、回報 | 不執行完成 |
| 合併方（PM） | 審查、決定是否合併 | 合併、通過測試後執行完成 |

事後發現已提早完成而產出未合併時：在票面寫明「狀態為完成、產出未合併」與分支、提交位置，合併後補記合併提交；合併不放行時重開票，不讓已完成狀態停在主線沒有產出的情況。

## 預防措施

- 完成指令在偵測到執行環境是隔離工作樹時提示或拒絕，指向「合併後於主線完成」。
- 驗收稽核把「`completed_at` 晚於合併提交時間」列為檢查項。
