# PC-BAL-075: 全樹 overlay 推送前未先拉取，靜默移除他方已在共用庫的內容

## 基本資訊

| 欄位 | 值 |
|------|-----|
| 類別 | process-compliance |
| 風險等級 | high |
| 來源版本 | 0.2.1 |
| 發現情境 | 多專案共用的框架庫，一方連推兩版後由另一方發現其前一版的 12 處內容被回滾 |

## 症狀

- 推送成功、無警告、無錯誤碼；`git log` 只顯示一次正常推送，沒有任何「刪除」的痕跡。
- 遺失形態一致且違反直覺：**新增的檔案存活，對既有檔的修改被回滾**。
- 受害方通常在數小時後因某個功能不再生效才發現（本次是身分綁定的事前防線消失）。
- 推送方毫無自覺——自己的內容全部正確送達，看不出少了什麼。

## 根因

**推送模型是全樹 overlay，而推送者的樹是上一次拉取時的快照。** 推送把本地 `.claude/` 整棵覆蓋上去；本地缺少對方在這之間推上去的修改，覆蓋即回滾。新增檔存活是因為三方比對認定它們不在共同 base 中、不屬「過時檔」，但對既有檔的修改沒有這層保護——它們在本地就是「舊版本的那一行」，overlay 照樣寫上去。

**方向判讀在這條路徑上不存在。** 逐 skill 的同步工具會做三方方向判定並印出版號比對；全樹 overlay 的推送腳本只檢查本地是否有未提交變更（commit-first），不問「共用庫是否已前進」。前者的紀律不自動適用於後者，而兩者的操作者往往是同一個人、在同一個收尾流程裡連續執行。

**受害面積與推送者的落後時間成正比，且推送者無從估計。** 落後多久取決於別人推了幾次，那是推送者這一側讀不到的資訊。

## 解決方案

1. **推送前先拉取**，與逐 skill 同步的「先讀方向再決定」是同一條紀律，適用於任何 overlay 語意的推送。
2. **推送後比對**：以推送前的共用庫 HEAD 與推送後的樹做一次差集，列出「共用庫原有而現在沒有」的檔案與行，非空即為回滾。
3. **復原方式**：受害方自共用庫歷史取回被回滾的內容合併回自己的樹再推，而非要求推送方回退——推送方那一版同時含有其正確的新內容，回退會連帶撤銷。

## 預防措施

- 對共用資產的寫入，區分兩種語意：逐項同步（有方向判定）與整樹覆蓋（無）。後者的每一次執行都要當作「我即將宣告整棵樹的權威狀態」來對待。
- **「測試全綠」不涵蓋「應該存在而不存在的測試」**。本次的漏檔之一是一個測試函式，被覆蓋後測試數減少而通過率仍為 100%；通過數是測試集合的投影，與 `PC-BAL-069` 的低維表徵家族同構。驗證是否漏檔要比對測試**名稱集合**，不是通過數。
- 事故發生後優先復原而非追責：受害方通常比推送方早發現，主動通報與提供被覆蓋清單比等對方自查成本低得多。
