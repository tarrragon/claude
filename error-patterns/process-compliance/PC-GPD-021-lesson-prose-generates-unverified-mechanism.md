# PC-GPD-021: 教訓段落生成未經查證的機制解釋——體裁獎勵因果完整而非證據標示

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-GPD-021 |
| 類別 | process-compliance |
| 風險等級 | 高 |
| 發現日期 | 2026-09-10 |

## 症狀

同一則輸出裡，**結論段落的事實有查證、教訓段落的機制解釋沒有**。教訓段落（Insight、經驗總結、根因說明、error-pattern 的「根因」節、回顧的「所以我們學到」）寫出一個具名元件、具體時序、完整因果的機制敘述，而該敘述從未被任何工具呼叫驗證過。

**識別特徵**：

- 教訓段落含具名對象與具體機制（「壞的是 X 那一側」「Y 被砍在 Z 的中途」），但同一則輸出的工具呼叫記錄裡沒有任何一次讀過 X 或 Z
- 敘述結構完整到自帶反省——「我先前照 A 去看，實際上正確的下一步是 B」——而 B 也沒被執行過
- 結論段落同時存在，且該段的事實**確實有查證**，兩段的證據標準不一致而作者無感
- 讀者（含作者稍後、他人、下一個 session）把它當查證結果引用，因為它讀起來就是
- 揭穿途徑幾乎總是外部：他人引用回來、或被要求據此建立記錄時才回頭重現

## 根因

**兩種段落的體裁要求不同，而作者只對其中一種套用證據標準。**

結論段落的體裁要求是「說發生了什麼」，讀者預期看到數字、路徑、退出碼，缺證據會顯眼。教訓段落的體裁要求是「說這件事的意義」，讀者預期看到因果與洞察——**一個乾淨的因果故事就是該體裁的成功樣態，而附證據反而打斷敘事節奏**。於是同一位作者在同一則輸出裡，對兩段套用了不同的證據門檻，且不會察覺切換。

生成側的機制與 `PC-166`（confabulation）同源：模型在沒有 grounding 時以先驗分布填補。差別在觸發條件——`PC-166` 的觸發是工具結果尚未返回，本模式的觸發是**體裁切換**：進入「總結教訓」的語域後，因果完整度取代了證據可得性成為主導的生成約束。

與 `PC-GPD-019`（形狀相符終止查證）的關係是**遞進而非重複**：`019` 至少有一個真實觀測，錯的是它與待答問題的關係；本模式**連觀測都沒有**，機制解釋是純生成的。一則輸出可以同時犯兩者，且本模式較難發現——`019` 的錯誤觀測留在工具記錄裡可被回查，純生成的機制解釋在記錄裡沒有對應痕跡，只能靠重現。

## 實例（2026-09-10）

一次 `worktree create` 因子行程逾時而中止（該 skill 的已知缺陷），留下一個無法以 `git worktree remove` 或 `prune` 清除的殘骸。清理完成後，作者寫下一段 Insight：

> 它的 `.git` gitfile 內容完全正常（`gitdir:` 指向正確的 admin 路徑），所以從呼叫端看不出問題。壞的是 admin 那一側——逾時把 `worktree create` 砍在建立 admin 目錄的中途。⋯⋯我先前照那句錯誤訊息去看 `.git` 檔本身⋯⋯實際上正確的下一步是去看指向的目標存不存在。

**該段的工具記錄**：`cat` 過 worktree 側的 `.git` 檔（真實觀測）。`.git/worktrees/<name>/` 這個 admin 目錄，從頭到尾**沒有被讀過一次**。

**用戶把該段當事實引用並要求據此建立記錄後，作者重現一次，結果與敘述不符**：

| 查證項 | 敘述宣稱 | 重現實測 |
|--------|---------|---------|
| admin 目錄 | 建立到中途 | **建完**——`commondir` `gitdir` `HEAD` `locked` `logs` `refs` 齊備 |
| 兩側 gitdir 指標 | 呼叫端正常、admin 側壞 | **兩側都正確** |
| 實際差異 | （未提及） | 僅缺 `index`（檢出被砍在寫 index 之前） |
| `remove` 的錯誤訊息 | `is not a .git file, error code 7` | 重現版為 `contains modified or untracked files`——訊息隨檢出進度而不同 |

原始那次（檢出 0 個檔）的 `error code 7` 真正成因**至今未診斷**，且原始殘骸已刪除，無法回查。也就是說該段 Insight 附帶提出的「錯誤訊息指錯層」這個更上位的教訓，**同樣未被確立**（另記為 `PC-GPD-022` 的待驗證假說）。

**為何逃過作者自己的檢查**：同一則輸出的其他部分證據充分——刪除前查過目錄內容與分支指向、刪除後三處查證（目錄、admin 目錄、登記項）、`prune` 的輸出逐字引用。作者對「我做了什麼」套了嚴格標準，對「這件事為什麼發生」沒有。

## 預防措施

**核心動作**：教訓段落寫完後，逐句問「這句話對應哪一次工具呼叫？」答不出來的句子，要嘛去查，要嘛改寫為明示的假說。

| 句型 | 處置 |
|------|------|
| 具名對象 + 具體機制（「壞的是 X」「被砍在 Y 中途」） | 必須有讀過 X／Y 的工具呼叫；沒有就去查 |
| 「實際上正確的下一步是 Z」 | Z 若未執行過，改寫為「Z 可能是正確的下一步，未驗證」 |
| 「所以 A 導致 B」 | A 與 B 各自要有觀測；只有 B 有觀測時，A 是推測不是機制 |
| 無法當場查證且成本高 | 保留敘述但加標示：「此為推論，未查證」——標示本身就阻斷了下游把它當事實引用 |

三條具體衍生規則：

1. **教訓段落與結論段落套同一個證據門檻。** 判別訊號：同一則輸出裡，結論段有退出碼與路徑，教訓段只有因果連接詞。
2. **反省句不豁免查證。** 「我先前錯在⋯⋯正確的做法是⋯⋯」這個結構讀起來像已經想清楚，但它的後半段常常也是生成的。承認錯誤不等於已經找到原因。
3. **被他人引用回來時，先重現再回應。** 引用是這個模式唯一可靠的外部觸發點；此時的正確反應不是補充說明，是回頭查證原敘述是否成立。

**不適用**：明示標記為假說、猜測、待驗證的段落。本模式的違規要件是**未經查證的機制解釋以已查證的語氣呈現**，而非「有推測」本身。
