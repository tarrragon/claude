# PC-BAL-038: 背景 agent 的純文字產出不送達主線程，idle 通知被誤讀為交付完成

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 高 |
| 發現時機 | 一次三視角並行審查，其中一個視角的報告連續三次未送達 |
| 發現日期 | 2026-08-18 |
| 觀測次數 | 三次（同一 agent 類型的兩個獨立執行體，第一個兩次、重派的第二個一次） |

## 症狀

- 背景 agent 完成工作並產出完整報告，主線程只收到 `idle_notification`，報告內容零到達
- agent 自身認為已交付——它確實輸出了報告，只是輸出到了主線程看不見的地方
- 重派同類型 agent 並不能解決：新執行體以相同方式輸出，複製同一失效
- 主線程若不追問，會把 idle 通知讀成「該視角已完成且無發現」，整條視角的結論靜默消失
- 失效無錯誤訊息、無告警、無日誌——所有觀測到的訊號都與「順利完成」一致

## 根因

背景 agent 有兩條輸出路徑，語意完全不同但對 agent 而言同樣自然：

| 路徑 | 到達主線程 | agent 的主觀感受 |
|------|-----------|-----------------|
| 一般文字輸出 | **否** | 「我寫出報告了」 |
| SendMessage | 是 | 「我寫出報告了」 |

兩者在 agent 側是同一個動作（產出文字），差別只在有沒有包進工具呼叫。派發 prompt 若只說「產出審查報告」「回報結論」，並未指定管道，agent 走預設的文字輸出是完全合理的解讀。

第二層是訊號誤讀。`idle_notification` 的語意是「執行體閒置可接新任務」，不是「產出已交付」。但這兩件事在正常情況下高度相關（做完才閒置），主線程因此把它當成完成訊號使用。當交付管道失效時，這個相關性斷裂，而 idle 通知仍照常送達——**唯一還在運作的訊號，剛好是最容易被誤讀為成功的那個**。

第三層是不可重試性。主線程若只是重派，新執行體會走同一條預設路徑，產生同樣的結果。連續三次觀測中，第三次正是重派後的複製失效。

**家族歸屬**：本模式與 `PC-BAL-042`、跨 session 接管判準（`parallel-dispatch.md` 沉默方向）同屬「唯一可觀測訊號最易被誤讀」家族（PC-BAL-042 命名）：後兩者的誤讀對象分別為「同儕來訊被誤讀為本 session 對話延續」「同儕沉默被誤讀為未工作或工作中」，本模式的誤讀對象是「idle 通知被誤讀為交付完成」。三例偵測策略一致——收到訊號時暫停推斷，先查世界平面（SendMessage 內容或檔案／commit／ticket 副作用），不以訊號本身斷定結果。

## 解決方案

**發現當下**：向該 agent 發 SendMessage 索取，並在訊息中明確說明「純文字輸出不會送達，必須經 SendMessage」——agent 不知道自己失敗過，不告知它會第四次重複。索取時附上已知的其他視角結論，並明確要求「一致就說一致，不需重寫」，避免重複產出。

**派發時**：prompt 明寫回報管道，不能只寫「回報結論」。有效的寫法是指定動作而非結果，例如「完成後以 SendMessage 將結論送回主線程」。

**驗收時**：把 `idle_notification` 與「產出已收到」在心智上分開。判定 agent 交付完成的依據只有兩種——收到它的 SendMessage 內容，或在世界平面（檔案、commit、ticket 狀態）查到它的副作用。idle 通知不是其中任何一種。

## 預防措施

| 時機 | 檢查 |
|------|------|
| 撰寫派發 prompt | 產出物是「報告／結論／判斷」這類純資訊時，明寫以 SendMessage 送回；產出物是檔案變更時，明寫寫入路徑 |
| 收到 idle 通知 | 問「我拿到它的產出了嗎」，而非「它做完了嗎」。純資訊型任務未收到 SendMessage 即視為未交付 |
| 準備重派 | 先確認失效原因是否為管道問題；若是，重派前必須修正 prompt，否則新執行體複製同一失效 |
| 多視角並行審查收斂 | 逐一點名清點各視角是否都有實際內容送達，不以「agent 數量都跑完了」代替 |

**自動化方向**：agent 進入 idle 時，若該 agent 生命週期內零 SendMessage 且零檔案寫入，發出提示。此判準會對「確實無事可報」的 agent 產生誤報，故適合做成提示而非阻擋。

## 案例

一次針對已完成 commit 的事後多視角審查，派出三個視角：語言慣例、文字品質、Good Taste。前兩者的報告正常送達，Good Taste 視角連送兩次 idle 通知、零報告內容。

主線程當時的處置是向它索取，並在索取訊息中預告「若屆時仍無結論，將以兩份視角建票並在票內註明該視角缺席」。它隨後交出報告，開頭自述「前兩次以純文字輸出，未經 SendMessage，故未送達——我的錯誤」。

值得注意的是這份遲到報告的內容：它推翻了主線程原本的分票規劃，並發現了另外兩位視角都沒看到、且主線程根本沒問到的最嚴重項——一批死參數在函式簽章與 help 文案之間形成兩份互相矛盾的事實來源。若主線程當時把 idle 通知讀成「無發現」，這些結論會全數遺失，且不會有任何訊號提示遺失發生過。

同一批次中，主線程另外重派了一個同類型執行體以補齊視角。該執行體同樣只送 idle 通知——重派本身不解決管道問題，這是第三次觀測。

## 與既有模式的分界

| 模式 | 失效點 |
|------|--------|
| PC-050 過早判定 agent 完成 | agent **尚未**完成，主線程提前判定 |
| PC-062 派發後焦慮性檢查 | agent 正常運作，主線程過度介入 |
| 本模式 | agent **已完成且產出正確**，交付管道靜默失效，唯一到達的訊號恰好形似成功 |
