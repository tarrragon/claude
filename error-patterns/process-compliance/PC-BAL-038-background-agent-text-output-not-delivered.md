# PC-BAL-038: 背景 agent 的純文字產出不送達主線程，idle 通知被誤讀為交付完成

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 高 |
| 觀測次數 | 三次（同一 agent 類型兩個執行體：第一個兩次，重派未修正 prompt 的第二個一次，複製同一失效） |

## 症狀與案例

背景 named agent 完成工作並產出完整報告，主線程只收到 `idle_notification`，報告內容零到達，訊號全與「順利完成」一致。一次事後三視角審查中，其中一視角連送兩次 idle 通知、零報告內容；索取後交出的報告推翻原分票規劃，並發現另兩視角與主線程都未問到的最嚴重項。同批重派的補位執行體同樣只送 idle 通知，複製同一失效。

## 根因

表層是通道失配：`idle_notification` 語意為「執行體閒置」而非「產出已交付」，通道正常時兩者高度相關，通道失效時相關性斷裂但訊號仍照常送達，成為最容易被誤讀為成功的訊號。

但這不是事故根因。要求「以 SendMessage 送出報告本體」的條款當時已存在於 `agent-dispatch-template.md`（引言區塊 + 交付通道速查節，已引用 `PC-BAL-015`），派發者卻未依此寫 prompt。真正根因是**規範載體未送達派發者當下 context**——該檔為 999 行按需讀取檔，條款位於檔案前段，一般派發不會觸發完整讀取，屬 `PC-BAL-043` 的 delivery gap，本案「執行者」是撰寫 prompt 的派發者而非背景 agent。現行防護（通道對照表、L0 Fallback SOP、重派複製失效防護）見該檔「交付通道速查」節，不在此重複。

## 區辨因子（受控取樣補強）

初始 N=3 單 session 觀測不足以定位區辨因子（PC-168）；後續受控取樣：路徑 A（spawn 完工回傳）N=9（named 6 / unnamed 3，3 種 agent 型別、長短輸出對照）、路徑 B（SendMessage 索回）N=6，逐樣本記錄 GREEN/RED。

| 候選因子 | 取樣結果 | 判定 |
|---------|---------|------|
| 派發形態（named vs unnamed） | named 純文字 0/6 送達（完工訊號 `idle_notification` 結構不載文字）；unnamed 3/3 送達（完工通知含 `result` 欄位） | **主區辨因子，結構性而非機率性**——「未送達」不是遺失，是訊號類型本身不攜帶文字 |
| 取回路徑 | named 經 SendMessage 索回 6/6 送達 | 索回是 named agent 唯一驗證可行的文字管道；初始觀測的索回連續失敗本輪 0/6 重現，索回存在跨 session/時機變異，非 100% 保證，失敗時重發一次後改查世界平面 |
| agent 型別 | 3 種型別在兩路徑結果完全一致 | 非因子——重試或換型別對「spawn 回傳不送達」無效 |
| 輸出長度 | 長（60+ 行）短（1 行）各路徑判定相同 | 非因子（證偽確認） |

**增量觀測**：idle 通知本身可能延遲或缺席（取樣中一例逾 3 分鐘未到）——索回訊息可直接發送排入 agent 佇列，不需等 idle 訊號。**取樣限制**：單一 session；named/unnamed 分割 9/9 零例外屬結構性機制形態，跨 session 重現性未另行驗證。

操作防護（通道對照、L0 Fallback SOP、prompt 撰寫條款）的權威來源為 `agent-dispatch-template.md`「交付通道速查」節，本節僅提供因子判定證據，不重複條款。

## 與既有模式的分界

| 模式 | 失效點 |
|------|--------|
| PC-050 | agent **尚未**完成，主線程提前判定 |
| PC-062 | agent 正常運作，主線程過度介入 |
| PC-BAL-043 | 本模式根因即該模式一個 delivery gap 實例，差異僅在「執行者」是撰寫 prompt 的派發者 |
| 本模式 | agent **已完成且產出正確**，交付管道靜默失效，唯一到達的訊號形似成功 |
