# PC-BAL-048: 一次性量測腳本的 fallback 分支輸出與主分支結果印在同一容器，分桶鍵被誤讀為運算結果

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 風險等級 | 高 |
| 首次觀察 | 2026-08-19 |

## 症狀

分析型任務中，以 heredoc 或一次性腳本跑量測，腳本對「主要路徑」與「不符合前提的資料」分別處理，兩者的輸出寫入同一個結果容器（同一個 dict、同一份列表、同一段 stdout）。輸出讀起來合理——筆數對、格式一致、與預期相符——但其中一部分不是運算結果，而是 fallback 分支的分類鍵。

撰寫者當下不會察覺，因為輸出符合預期。錯誤在結論被寫進交付物、被下游引用之後，才由獨立驗算揭穿。

實證（2026-08-19，一份任務群組化排程的分析交付物）：一段並查集（union-find）腳本對任務單集合分組，並查集只建在 `pending` 子集上；查詢的十個目標項中九個非 pending，落入 `else` 分支並以 status 字串為鍵分桶：

```python
for t in sorted(target):
    if t in P: loc[dsu.find(t)].append(t)          # 主分支：連通分量根節點為鍵
    else:      loc["(非pending:"+status+")"].append(t)  # fallback：status 字串為鍵
```

輸出四個桶，被寫進分析交付物的實驗結果章，表述為「此判準下這十項裂為四塊」。實際上那四個桶是四個 status 類別（解析失敗 / completed / in_progress / pending），與連通分量無關——真正的連通分量計算對其中九項從未執行。以正確方式重算後，血緣判準為 7 塊、混合判準為 1 塊（且該塊含全庫 95% 的項目），與「四塊」無任何對應關係。

該數字是該分析一項核心發現的唯一證據，並已據以選定方案、衍生五張實作票。

## 根因

**條件分支的兩側寫入同一個容器，型別相容使錯誤不會拋出**。`dsu.find(t)` 回傳字串，status 拼接也是字串，兩者作為 dict 鍵型別相同，Python 不會抗議。若 fallback 寫入獨立容器，或鍵型別不同（例如主分支用 int 根索引），錯誤在讀取當下即顯現。

**「處理例外資料」被實作為「換一個鍵繼續放進結果」**。撰寫一次性腳本時，遇到不符前提的資料，最省事的寫法是給它一個描述性的鍵先放著，打算之後再看。但輸出一旦看起來合理，回頭檢查就失去觸發訊號——輸出本身消除了重看的動機，除非有外部要求。

**一次性腳本不受任何品質機制覆蓋**。它不進版控、無測試、不經審查、通常也不留存（heredoc 執行完即消失）。產品程式碼會被 code review 攔下的錯誤，在這裡直達交付物。而分析型任務的交付物恰恰是「數字」，數字的可信度完全由這段無人審查的程式碼承擔。

**輸出的自洽性掩蓋了計算的缺席**。四個桶、十個項目、每項恰好出現一次，所有表面一致性檢查都通過。它們檢查的是輸出的形狀，而錯誤在輸出的來源。能揭穿它的手段都得繞到形狀之外：重算一次，或加入一條與內容語意相關的斷言（見預防措施）。撰寫者不會自發做這兩件事，因為輸出看起來沒有問題。

## 解決方案

**發現當下**：不回退既成工作（quality-baseline 規則 6）。以更正紀錄形式追加至原交付物，保留原文並逐項標明實測值與成因，使引用過該數字的下游能自行判斷影響。若結論方向改變，衍生票的回溯重估依 `PC-BAL-046`（上游結論修訂後衍生票無回訪管道）處理，本檔不重述其步驟。

**腳本層**：

| 反模式 | 正確寫法 |
|-------|---------|
| 不符前提的資料以描述性字串為鍵寫入結果容器 | 寫入獨立容器，並在輸出時分兩段印，段標明寫「以下項目未參與計算」 |
| 主分支與 fallback 的鍵型別相同 | 讓型別不相容（主分支用 int / tuple，或 fallback 一律 `raise`），使誤讀在執行期即失敗 |
| 靜默篩選（只算某一狀態、只取某一粒度）不印出被排除的筆數 | 每個篩選點印出 `納入 N 筆 / 排除 M 筆`，讓分母始終可見 |
| 把解析失敗歸類為「資料限制」 | 先排除自己的解析實作再歸因外部；分隔符樸素切分吞入內文同形符號是常見來源 |

## 預防措施

**寫入交付物前重算一次，換一種實作**。分析結論引用的每個數字，在寫進交付物之前用不同寫法重跑（換資料來源範圍、換演算法、或改用既有 CLI 命令交叉核對）。兩次不一致即停手查因。成本是一次腳本執行，收益是攔在交付物之前而非之後。

**「換一種實作」不含代數等價的公式重排。** 同一統計量的兩種數學等價寫法（例如以列聯表計算與以成對枚舉計算某分群一致度指標）共用同一組中間量，兩者必然一致，無法攔截中間量產生過程中的任何錯誤。此類重排會讓本項預防措施被形式化滿足而實質失效——自檢表填了「已換實作重算」，實際上錯誤仍原樣通過。

判準：第二次計算若與第一次共用任何中間結果，即不算獨立。合格的替代路徑是從最原始的輸入重新走一遍，例如自原始資料暴力枚舉，而非自第一次算出的彙總量再推導。此判準經一次實證——某分析的自檢表宣稱已換實作重算，經審查發現兩種寫法代數恆等，真正的獨立驗算由審查方補做才完成。

**量測宇宙與結論宇宙必須一致**。腳本篩選了什麼，結論就只能宣稱什麼。上述實證中，並查集建在 pending 上而結論宣稱涵蓋十項（九項非 pending）——這個不一致在方法描述階段就可攔下：寫「對 X 集合計算」時，檢查目標對象是否全在 X 內。

**輸出斷言**：一次性腳本印出結果前加一行檢查，例如「每個鍵都應是有效的節點 ID」`assert all(k in ids for k in loc)`。此類斷言一行可寫，且正是本案會失敗的地方。

**審查層**：分析型 ticket 的多視角審查應含 Evidence 視角，並明確要求「獨立重算至少兩項數字」而非「核對敘述是否自洽」。本案的四項證據中，三項經重算成立、一項不可復現——差別只有重算與否。
