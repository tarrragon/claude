# PC-GPD-076：分類判準要先用已知正例試跑，再交給代理人全量套用

## 基本資訊

| 項目 | 內容 |
|------|------|
| Pattern ID | PC-GPD-076 |
| 分類 | process-compliance（派發前的判準驗證） |
| 風險等級 | 中（結果不會直接寫錯，但整輪代理人產出要重做，且判準的缺陷要等結果回來才看得到） |
| 來源版本 | 0.6.0 |
| 首次觀測 | 2026-11-03 |
| 關聯 | [[PC-BAL-036]]、[[PC-GPD-075]] |

## 摘要

**PM 寫好一條分類或入選判準、交給代理人逐項套用前，要先挑兩三個「答案顯然是要入選」的已知正例，自己用判準跑一次。** 已知正例沒有入選，就是判準漏掉了主要對象，要在派發前修。跳過這一步時，代理人會忠實套用有缺陷的判準，整輪結果回來才發現大部分該入選的都落選。

## 症狀

- 代理人回報的入選數遠低於預期，有些類別是 0。
- 抽查落選項目，發現最核心的對象（例如真正實作該功能的主票）被排除，排除理由是判準的某一項字面不符。
- 少數入選的項目反而偏向枝節。它們剛好符合判準的字面特徵，但不是判準想要選的對象。
- 代理人沒有違規：它照判準執行，也把判不定的項目列出來了。問題出在判準本身。

## 根因

1. **判準是從「想要的性質」推出來的，不是從資料長相歸納的。** PM 想要「實作該 UC 的票」，於是寫了「票面明確寫出該 UC 的 ID」作為可檢驗的代理條件。但實際資料裡，實作票引用的是 SPEC 和狀態鍵，很少寫 UC ID。代理條件和想要的性質在這批資料上相關性很低。
2. **可檢驗性壓過了效度。** 寫判準時刻意排除「依標題判斷」這類主觀做法，改用可 grep 的字面條件。可檢驗性提高了，但沒有驗證這個字面條件是否真的對應到目標對象。
3. **派發後 PM 就看不到過程。** 判準的缺陷只會在代理人全量執行後的結果裡顯現，代價是一整輪代理人執行。

## 解決方案

結果已回來時：

- 先不合併。用已知正例對照結果，確認是判準缺陷，而不是代理人執行錯誤。
- 把判準缺陷和替代判準列成選項，交給決策者裁定（判準影響產出形態時）。不要直接放寬判準重派。
- 已完成的部分（候選清單、判不定清單、排除理由）保留在票面，改判準後重派時可以重用。

## 預防措施

- **派發前試跑**：寫完判準後，PM 自己挑 2 到 3 個已知正例，再挑 1 個已知反例，用判準逐項跑一次，結果寫進票面的判準段落。正例落選或反例入選，就先修判準再派發。
- **檢查代理條件的覆蓋率**：判準裡任何「字面出現 X」的條件，先用 grep 量一下目標對象中有多少比例真的出現 X。比例很低時，這個條件不能當作必要條件。
- **在派發 prompt 裡留回報出口**：請代理人在入選率異常低（例如某類別為 0）時，先停下來回報抽樣結果，不要跑完全量。

## 實例

- 2026-11-03，一個 Flutter 專案要把 UC 和「實作該 UC 的票」連起來，供追溯視圖第四層使用。PM 的判準要求票面明確寫出 UC ID 或 flow 步驟 ID。代理人照判準執行，6 份 UC 中有 3 份入選 0 張；真正實作破洞報告畫面的主票，因為票面只寫 SPEC 與狀態鍵而落選；入選的少數票裡還有一張只是補強測試鑑別力。如果派發前用破洞報告主票試跑判準，第一張就會現形。
