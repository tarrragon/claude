# PC-BAL-060: 逃生閥只解除發放它的那道閘門，其餘閘門的判準不隨之放行

## 基本資訊

| 項目 | 值 |
|------|------|
| 類別 | process-compliance |
| 風險等級 | 高 |
| 首次發現 | 2026-09-02 |
| 相關 | `IMP-BAL-012`（標記語彙合併抹除來源）、`PC-BAL-024`（規則層與強制層涵蓋範圍脫節） |

## 症狀

同一份內容受兩道以上閘門管轄，執行者為通過其中一道而加上該閘門的逃生閥 marker，其餘閘門仍應阻擋卻被以 `--force` 略過，違規內容照常送出。

外觀特徵：逃生閥使用正當（類別與理由皆符合該閘門的規範）、marker 語意成立、該閘門確實放行，因此「有合法授權」的印象成立；另一道閘門的阻擋則被讀成同一件事的重複告警而非獨立判定。

## 根因

**逃生閥的授權範圍等於發放它的那道閘門所檢查的判準，不及於任何其他判準。** 兩道閘門檢查同一份內容時，各自問的問題不同：

| 閘門 | 問題 | 對「逐字搬移的專案識別符」的答案 |
|------|------|-------------------------------|
| 引用穩定性守衛 | 這段文字是不是既有內容的逐字位置搬移？ | 是 → 放行 |
| 可攜性守衛 | 這份資產能不能給別的專案使用？ | 不能 → 阻擋 |

同一份內容對前者無害、對後者有害。前者的逃生閥宣告的是「搬移屬實」，不是「內容適合外流」，後者的判準完全不在該宣告的射程內。

執行者的推理錯誤在於把「這個操作在語意上合法」讀成「所有相關檢查都應放行」——合法性是對單一判準的答案，不是通行證。

## 解決方案

遇到第二道閘門阻擋時，先回答「這道閘門問的問題是什麼」，再判斷手上的逃生閥是否回答了那個問題。

| 情境 | 處置 |
|------|------|
| 第二道閘門的判準已被逃生閥涵蓋 | 該閘門應有對應的豁免機制，使用它；若無，屬閘門缺陷，建票 |
| 第二道閘門的判準未被涵蓋 | 修改內容使其同時滿足兩者，不以 `--force` 略過 |
| 兩道判準互斥、無法同時滿足 | 停手上報，由決策者裁定犧牲哪一邊，不由執行者自行選邊 |

觀察案例的修法屬第二種：移除句首的識別符前綴而保留其後的描述性內容，兩道閘門同時滿足——原句的資訊承載在描述而非識別符，移除後句意完整。

## 預防措施

**派發前**：Context Bundle 提及某道閘門的逃生閥時，同時列出該內容受哪些閘門管轄，避免執行者把單道授權讀成全域授權。觀察案例中的 Context Bundle 只提了引用穩定性守衛的搬移類別，未提可攜性守衛，執行者依指示行事並誠實回報 gate 觸發，判斷錯誤在派發方。

**執行中**：`--force` 略過任何閘門前，在 ticket 記錄該閘門的判準與略過理由。略過本身不是違規，未經判斷的略過才是。

**設計層**：對外傳播型操作（推送至共用庫、發布、對外 API）的閘門不應接受其他閘門的逃生閥作為放行依據；判準彼此獨立的閘門，其豁免機制亦應彼此獨立。

## 與既有模式的邊界

`PC-BAL-024` 處理「規則層與強制層涵蓋範圍脫節」——同一條規則的宣告面與執法面不一致。本模式處理「兩條不同規則各自有完整的宣告與執法，執行者誤把其一的豁免當成其二的豁免」，兩者的閘門數與規則數關係相反。

`IMP-BAL-012` 處理標記語彙合併後下游無法辨識來源，屬 marker 的識別問題；本模式的 marker 識別無誤，錯在其授權範圍的推定。

## 觀察來源

2026-09-02，一次 skill 格式修復作業。為保留版本紀錄中 `**Source**:` 行的實質資訊而加上引用穩定性守衛的搬移類逃生閥，通過該守衛；推送時觸發可攜性守衛（該 skill 宣告 `metadata.portable: true`），以 `--force` 略過，7 處專案層級識別符因而進入跨專案共用庫。

後果具體可驗證且同日已有同型前例：其他專案取得該資產後提交會被自身的引用穩定性守衛阻擋——同日稍早，本專案自共用庫取得另一個 skill 時正是遭遇此機制，當時的處置是拒絕該次取得並建票，數小時後卻由本專案製造了同樣的內容給別人。

本模式的撰寫過程本身即為一次自我示範：初稿在觀察來源段落引用了專案 ticket 編號，遭同一道引用穩定性守衛阻擋。該處若加搬移類逃生閥可通過，但 error-pattern 屬跨專案框架資產，逃生閥同樣不解除可攜性要求，故改為描述性標籤而非援引豁免。
