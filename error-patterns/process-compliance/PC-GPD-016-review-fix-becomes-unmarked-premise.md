# PC-GPD-016: 審查中採納的修法產物進入下一輪時不帶標記，被當成既有前提而不再受檢

**類別**: process-compliance
**嚴重度**: 高
**發現日期**: 2026-09-09

## 基本資訊

| 項目 | 值 |
|------|-----|
| 風險等級 | 高 |
| 來源版本 | 0.1.0 |
| 偵測時機 | 多輪審查中，某一輪的 finding 修完之後、下一輪派發之前 |

---

## 症狀

審查者提出一個缺陷，作者當場採納並改寫；改寫後的內容與原本就寫在那裡的內容在文件上完全同形。下一輪的審查者讀到它時，看到的是一段已經在文件裡的文字，沒有任何標記說明它是幾小時前為了修一份缺陷清單而寫的、且從未被獨立驗證過。

**它不會被質疑的理由是它看起來已經通過審查了**。事實相反：它是審查的產物，不是審查的對象。原本的內容至少被前幾輪的 frame 掃過，替代結構連一次都沒有。

**失效的形態是替代結構帶進來的新性質**——維度不正交、判斷標準無法執行、要求的輸入取得不到、對反例免疫。這些新性質與它修掉的那份缺陷清單零交集，所以「它修好了清單上每一項」是真的，而它同時是壞的。

## 根因

| 層級 | 機制 |
|------|------|
| L1 產物與既有內容同形 | 修法寫進文件之後就是文件的一部分，沒有欄位記錄它的來歷。下一輪的 reviewer 讀到的是內容，不是內容的履歷 |
| L2 採納的當下不觸發驗證 | 審查者提出的替代結構逐項對應缺陷清單，作者驗的是「它有沒有修掉清單上的項目」，那個驗證通過即採納。清單之外的性質沒有人問 |
| L3 中間輪次把它當前提 | 一旦寫進去，後續輪次的 finding 會建立在它之上（引用它、擴充它、為它補路由），到最後一輪才發現它有問題時，回退成本已經包含那些下游 |

## 實證

一份方法論的三輪審查，Round 1-2 共採納七項替代結構，全部由 reviewer 提出、作者當場採納。Round 3 的 steelman frame 對七項逐項做三題驗收（它帶進來的新性質是什麼、它要求的輸入取得得到嗎、它對反例免疫嗎），結果：

- 四項未通過。其中一項是「以兩個量的裁決是否分歧」作為某個設計期決策的觸發條件——那是執行期才存在的可觀測量，設計期兩個裁決都不存在，輸入取不到；而它取代掉的舊判準原本在設計期可用。
- 兩項是軸名取了次好的代理變數：真機制寫在同一張表格自己的某一格裡，而表的鍵用的是它的代理，反例落在代理與機制分岔處。
- 一項的理由被反證：作者以「兩個概念是包含關係」為由不改名，而該概念的原型實例被同一份文件的另一段明文排除，關係其實是部分重疊。

七項中有三項在 Round 2 已被其他 frame 當成前提引用過。

## 解決方案

1. **採納時就標記**。修法寫進文件的同時，在審查記錄裡列出這一輪採納了哪幾項替代結構、各自修掉的是哪幾則 finding。這份清單是下一輪的輸入。
2. **下一輪的派發指令明寫它們是必查對象**，且明寫「由 reviewer 提出而作者採納、沒有經過獨立驗證，不得當成既有前提」。不寫這一句，reviewer 會把它當文件的一部分。
3. **三題驗收逐項跑**：它帶進來的新性質是什麼、它要求的輸入取得得到嗎、它對反例免疫嗎。第三題最容易漏——一個對反例免疫的判準讀起來像很周全的判準。

## 預防措施

| 措施 | 落點 |
|------|------|
| 每輪修完後產出「本輪採納的替代結構」清單，作為下一輪 context 的固定欄位 | 多輪審查的輪次交接 |
| 最後一輪的 steelman 指令必含該清單與三題 | 派發指令範本 |
| 替代結構的採納在當下只驗「它修掉清單上每一項嗎」，不驗清單之外——這一點要寫進採納的動作本身，讓作者知道自己只做了一半的驗證 | 修法決策 |

## 行為模式分析

作者採納替代結構時的判斷是「它比原本的好」，而那個比較的基準是被指出的缺陷。缺陷清單是具體的、替代結構對它的覆蓋是可檢查的，所以採納這個動作有明確的通過條件。清單之外的性質沒有對應的通過條件，也就沒有人去問——**不是被判定為不需要問，是根本沒有進入判斷**。

這與「多次修法會合成缺陷」相鄰而不同：那一則講的是兩次各自正確的修法合成出對兩個 frame 都不可見的缺陷，本則講的是單次修法本身從未被驗證。兩者可以同時發生。
