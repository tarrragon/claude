# PC-GPD-063: 給用戶的憑證設定步驟未先查前次的提供方式，步驟中重新讀入機密的指令覆蓋了 shell profile 已載入的正確值，第一次真跑即 401

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 風險等級 | 低 |
| 首次觀察 | 2026-10-31 |

## 症狀

一個需要 API key 的實驗，key 不經過 session，由用戶在自己的終端機執行指令。用戶先前已把 key 寫入 shell profile（例如 `~/.zshrc` 的 `export <VAR>=...`），這件事記在前一張實驗票的票面上。

session 給用戶的執行步驟包含「以 `read -rs <VAR>` 輸入 key」或類似的重設動作。用戶照做，貼上的內容沒有完整進入（事後量得長度只有幾個字元），覆蓋了 profile 已載入的正確值。第一次真跑回 401 invalid key。

附帶現象：401 之後，session 憑 key 的前綴形狀猜測「這不是 API key」，判斷沒有根據，後來需要向用戶收回。

## 根因

1. **設定步驟是從零寫的，不是從前次的提供方式延續。** 「key 怎麼提供」是一個已經答過的問題，答案在前一張票的票面。session 沒有查，直接寫出一套通用的設定步驟。
2. **「設定」與「檢查」混在同一步。** 步驟想確認變數存在，用的卻是會重新寫入變數的指令。檢查應該是唯讀的，寫入讓檢查本身變成破壞來源。
3. **機密值不可見，覆蓋後無訊號。** `read -rs` 不回顯，貼上不完整時用戶看不到；變數被覆蓋後與正確時在終端機上同形，只有 API 回 401 才暴露。

## 解決方案

- 改為只 `source <profile>` 後執行，不另外要求 `read`／`export`。
- 401 後先以不洩漏內容的方式量測（變數長度、是否為空），再判斷原因；不憑前綴形狀推論 key 的種類。

## 預防措施

| 時機 | 動作 |
|------|------|
| 要給用戶涉及機密的執行步驟前 | 先查前一次同一機密是怎麼提供的（相關票面、說明文件），沿用該方式；查不到才寫新步驟 |
| 步驟需要確認機密已設定 | 只用唯讀檢查：`[ -n "$VAR" ] && echo set`、`echo ${#VAR}`。禁止用 `read`／`export` 當檢查 |
| 真跑回認證錯誤 | 先量長度與來源（`echo ${#VAR}`、`grep -c VAR <profile>`），再推論；不從 key 前綴猜 key 種類 |
| 確實需要重設機密 | 寫明會覆蓋 profile 載入的值，並附回復方式（重新 `source <profile>`） |
