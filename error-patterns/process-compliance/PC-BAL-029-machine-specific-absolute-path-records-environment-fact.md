# PC-BAL-029：ticket 以機器專屬絕對路徑記錄環境事實

## 基本資訊

- **Pattern ID**: PC-BAL-029
- **分類**: 流程合規（process-compliance）
- **發現日期**: 2026-08-10
- **風險等級**: 中（不造成資料損壞，但使待執行 ticket 的操作指示靜默失效，且接手者最可能的誤判方向是歸咎自己）
- **影響範圍**: 任何在 ticket、worklog、error-pattern、規則文件中記錄「環境實測結果」的場合——`$HOME` 下的路徑、外部 repo 的絕對路徑、掛載點、暫存目錄

## 摘要

**ticket 以 `/Users/<name>/...` 這類機器專屬絕對路徑記錄實測得到的環境事實。換機（換使用者帳號、換裝置、換容器）後這些路徑全數解析不到，而失效訊息是 `No such file or directory`——它只說路徑不存在，不會說「這是在另一台機器上量的」。** 接手者讀到的是一份看似完整、實則前提已消失的操作指示，最可能的誤判方向是自己打錯路徑或環境沒裝好，而不是懷疑 ticket 本身。

同一批實測結論若寫成 `~/...` 或專案相對路徑，換機後仍然成立或至少能被 shell 展開到正確位置；成本差別只在寫的當下多想一步，代價卻由後續每一位接手者分攤。

## 症狀

- 待執行 ticket 的 `where.files` 或 acceptance 含 `/Users/<某個名字>/...`，而該名字不是當前環境的使用者
- 依 ticket 記載執行 `ls` / `cat` / `grep` 全數回報路徑不存在，且錯誤訊息之間沒有共同線索指向「跨機」
- ticket 的 `why` 引用了「實測確認」「已驗證」等字樣，但那次實測的環境已不存在
- 同一 wave 內多張 ticket 同時受影響——實測在同一台機器上連續進行，殘留因此成批出現而非零星
- 已完成的 ticket 也帶同樣路徑，但無人察覺：完成者不再被執行，失效不會被觸發

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 實測輸出即為絕對路徑 | `ls`、`find`、`git rev-parse --show-toplevel` 回報的是絕對路徑 | 把實測輸出貼進 ticket 是最省事的記錄方式，機器專屬前綴隨之寫入 |
| 記錄當下前提為真 | 撰寫者所在環境路徑確實存在，驗證即通過 | 撰寫時沒有任何訊號提示這個記錄形式有問題 |
| 失效訊息不含成因 | `No such file or directory` 只描述結果 | 接手者無法從錯誤訊息推得「這是跨機殘留」，最省力的解釋是自己弄錯 |
| ticket 是單向文件 | 寫入時驗證過，之後不再重新驗證 | 環境變動不會回頭觸發 ticket 的重新檢查，前提失效沒有告警路徑 |
| 完成與未完成的曝險不對稱 | 只有待執行 ticket 會被執行 | 存量問題規模看起來很大，實際待處理面很小；不先分流會誤估工作量一個數量級 |

核心是**環境事實被以「當下可解析」而非「跨環境可解析」的形式固化**。這與「描述是草稿、接手者須自行重新驗證」的通則（`PC-162`）差別在於：該通則假設接手者會發現描述過期，而本 pattern 的失效形態恰好讓接手者**不會**往描述有問題的方向懷疑。

## 解決方案

### 立即補救

1. 盤點範圍必須涵蓋三處，只掃 ticket 目錄會漏掉另外兩處（實證：某次校正只掃 ticket 目錄，事後審查在 worklog 主檔找到 3 處、框架資產找到 6 檔同型殘留）：

   ```
   grep -rn "/Users/" docs/work-logs/**/tickets/*.md   # ticket
   grep -rn "/Users/" docs/work-logs/**/*-main.md      # worklog 主檔（含實測探針記錄）
   grep -rn "/Users/" .claude/ --include=*.md --include=*.py   # 框架資產
   ```

   其他平台改用 `/home/`、`C:\Users\`。框架資產的殘留額外具跨專案同步後成死引用的風險，影響面比 ticket 內殘留更大。盤點時排除通用佔位符（`/Users/me`、`/Users/x` 等）與逐字引用的證據原文。

2. **先依 frontmatter `status` 分流**：completed / closed 屬歷史記錄，不追溯改寫；pending / in_progress 才是待校正面。

   注意此分流有順序依賴的漏洞：同批同型的殘留，只因其所屬 ticket 早幾分鐘完成就落入「不追溯」而永久免修。分流的本意是「不再被執行的不用修」，但同批殘留的成因與修法完全相同，逐一判定的成本遠低於重新盤點。**同批同型者應一併處理，不以完成時間切分。**
3. 校正時**當場跑一次存在性命令並把 raw stdout 貼進記錄**，不可只去掉使用者名，也不可貼「實測確認 X」這類結論句。二元輸出（EXISTS / MISSING）與 realpath 是可複驗的固定值，結論句則無論寫得多具體都不構成證據。**但固定值只在產生它的環境內有效**——本 pattern 原先在此處引用的實例（「去掉使用者名後的路徑不存在，正確位置是複數形目錄」）在撰寫它的 working copy 為真，在並行的另一個 working copy 為假。校正跨環境共用的記錄時，貼 raw stdout 的同時必須標註是哪一側量的；兩側佈局不同時，`~` 換寫只是把失效方向倒過來，須改記用途與尋找方式而非路徑（見案例節「第一層」）
4. `where.files` 以 `ticket track set-where` 更新（frontmatter 與欄位同步），acceptance 內文以 Edit 修改；避免 `remove-acceptance` + `add-acceptance`，該組合會重排索引，破壞其他 ticket 對「acceptance 第 N 條」的位置引用

### 判別準則

| 記錄形式 | 是否可接受 |
|---------|-----------|
| `docs/work-logs/...`（專案相對路徑） | 可。專案內路徑不受 `$HOME` 影響 |
| `~/.claude/skills/x`（HOME 相對） | 可。跨機可解析，且語意是「personal 層位置」而非特定機器 |
| `/Users/<name>/...`、`/home/<name>/...` | 否。除非該路徑本身就是被討論的對象 |
| `${<REPO>_REPO:?<提示>}/...`（跨 repo，可執行命令用；`<REPO>` 為 repo 名大寫，如 `BLOG_REPO`） | 可。共用資產內只留變數名，變數定義放不同步的本機設定 |
| `<repo 識別>: <repo 內相對路徑>`（跨 repo，知識溯源用） | 可。不含 HOME 之下任何路徑段 |
| `~/<Dir>/<repo>/...`（跨 repo 但 HOME 相對） | 僅限單一環境內的記錄。多環境並行時必於某一側失效，「附一句實測」不足以補救——實測在哪一側做的結果就只在哪一側成立 |
| 「實測確認 X」而未標註量測環境 | 否。實測結論須標註量測環境（HOME、平台、日期），否則無法判斷是否仍成立 |

### 預防措施

| 措施 | 狀態 | 說明 |
|------|------|------|
| 記錄環境事實時用 `~` 或專案相對路徑 | 已落地 | `references/reference-stability-rules.md` 規則 9，與規則 7（時間軸）、規則 8（跨專案 sync）並列為第三個失效軸；`rules/core/document-format-rules.md` 有路由與檢查清單條目 |
| 實測記錄標註量測環境（HOME / 平台 / 日期） | 已落地 | 同上。規則 9 以「操作指引 vs 實測記錄」兩類判準給出相反處置，避免一律改寫使記錄宣稱量到從未量到的值 |
| ticket 建立或 claim 時掃描機器專屬絕對路徑 | 已落地 | ticket CLI 的 create 與 claim 路徑各接一次掃描，命中輸出 WARNING 不阻擋。通用佔位符（`/Users/me`、`/Users/<user>` 等）不列入，否則文件示例路徑會逐一觸發而使警告被當雜訊 |
| 校正後以 `grep -c` 逐檔驗證計數為 0 | 已落地 | 機械驗證，不依賴人工目視 |

上表四項皆已落地，但**落地不等於覆蓋**。仍未涵蓋的部分：

- 自動偵測只在 ticket 的建立與認領兩個時點。worklog、框架文件、規格文件的殘留無任何機械偵測，仍須依本 pattern 的立即補救手動盤點
- 規則 9 屬按需讀取層，靠撰寫者主動查閱；未讀規則而寫入的殘留，只有在該內容進入 ticket 時才會被掃描攔下
- 偵測無法區分「敘述性提及」與「操作指引」——討論本問題的文件會被一併命中。判讀交由使用者，這是警告不阻擋定位下的已知代價

**本表的維護規則**：任何一列若回到未生效狀態，狀態欄不得只寫「未落地」——無 trigger 的「未落地」在「以後」與「永不」之間沒有可驗證邊界，等同讓該項在文件上被揭露、在流程上被遺忘（`decision-trigger-binding` 規則 1 只承認「已決策」與「綁 trigger 的延後」兩種狀態）。寫法為「落地中（已建票追蹤）」，承接票號記於本 pattern 的來源 ticket 而非此處——框架資產禁止引用專案層級識別符（跨專案同步後成死連結）。

## 與相關 pattern 的邊界

- `PC-162`（ticket 描述是草稿，接手者須獨立重新驗證數量與範圍）是上位通則，涵蓋「描述可能過期」的一般情形；本 pattern 是其中一個**具體觸發條件**，特徵是失效不自我揭示——接手者不會往「描述有問題」的方向懷疑，因此通則所依賴的「接手者會自行重驗」這個前提在此不成立
- `ARCH-BAL-003`（規則寫了但失效對作者不可見）描述**防護靜默失效**；本 pattern 是其在文件層的實例——ticket 的操作指示等同一份未被執行的規則，其失效同樣不回饋給撰寫者
- `PC-BAL-018`（前提已修正的標記反而抑制重新驗證）方向相反：該 pattern 處理「標記說已修好所以不再查」，本 pattern 處理「沒有任何標記說前提已變」。兩者共同指向同一個缺口——**前提的有效期沒有載體**

## 案例

某版本一個 wave 對 personal skills 層的全部實測在 `$HOME=/Users/mac-eric` 的環境完成；2026-08-10 以 `echo $HOME` 實測當前環境為 `/Users/tarragon`，`ls -d /Users/mac-eric` 回報 No such file or directory。

> **[更正 2026-08-12] 立案敘述把「並行的兩個環境」寫成了「先後的一次換機」**
>
> 上段描述為時間序的環境替換（先 A、後 B、A 已消失）。2026-08-12 的鑑識顯示實際形態是**兩個 working copy 長期並行**，各自 HOME 與 HOME 下的目錄佈局都不同：
>
> | 判別依據 | 觀測 |
> |---------|------|
> | harness 產生的 scratchpad 目錄名（由 cwd 編碼，非模型輸入） | 2026-07-25 的記錄含 `-Users-<A>-Projects-<repo>`，證明該環境為真 |
> | 同日兩個 git author 身份的時段分布 | 身份甲活躍於 00/04/07/08/21/22/23 時，身份乙活躍於 09-18 時 |
> | 本 working copy 的 hook 日誌時段（gitignored，僅本機產出） | 只覆蓋 09-18 時；21-23 時零檔案 |
> | 觸發本 pattern 的那次校正的撰寫時間 | 身份甲，21:44-22:12——落在本 working copy 無日誌的時段 |
>
> 即該次校正在**另一個 working copy** 執行，它對自身環境的觀測正確。錯誤不在觀測，在於把「在我這台可解析」的路徑當成跨環境通用值寫進共用的 ticket。
>
> **這對本 pattern 的主張有兩點修正**：
>
> 1. 失效軸不是「換機後路徑全滅」（單向、一次性），而是「並行環境間路徑互不相容」（雙向、持續）。後者更難察覺——每一側各自跑都正常，只在讀對方寫的記錄時失效。
> 2. **`~` 正規化不足以修好跨環境路徑**。本 pattern 的判別準則表把 `~/<dir>/<repo>/...` 列為可接受形式，前提是各環境 HOME 下佈局一致。實際兩側佈局為 `Projects/`（複數、首字大寫）與 `project/`（單數、小寫），`~` 換掉的只是使用者名那一段，剩下的仍然互斥。把記錄從一側的形式改成另一側的形式，只是把失效方向倒過來。
>
> **待辦**：跨 repo 引用（如 blog）缺少環境無關形式，需獨立設計；規模數字（32 檔 / 109 次 / 5 張 / 3 張）建立在單向換機的模型上，需依並行模型重算。已建票追蹤，票號記於本 pattern 的來源 ticket（框架資產禁止引用專案層級識別符）。

| 項目 | 數字 |
|------|------|
| 該版本 tickets 目錄中含失效路徑的檔案 | 32 檔（該字串共 109 次出現） |
| 其中 status 非 completed / closed | 5 張 |
| 扣除以該問題本身為主題的兩張（校正票與本 pattern 的建立票） | 3 張待校正 |

存量 32 檔與待處理 3 張的落差說明分流的必要：未分流會把 32 檔全部視為工作面，實際只有 3 張會被執行到。

~~校正過程另外驗證了「去掉使用者名不足以修好路徑」：`/Users/mac-eric/project/blog/...` 去掉前綴後為 `~/project/blog/...`，實測不存在；當前環境的實際位置為 `~/Projects/blog/...`。~~

**[更正 2026-08-12]** 上段的實測在**撰寫它的那個 working copy** 成立，在另一個並行的 working copy 不成立。於後者重測（macOS Darwin 25.5.0）：單數小寫形的 `~/<dir>/blog` EXISTS，複數大寫形 `~/<Dir>/blog` MISSING。兩側 HOME 下的目錄佈局本就不同，故該路徑無論寫成哪一側的形式，都會在另一側失效——上段寫入的值已被改成本側可解析的形式，這只是把失效方向倒過來，不是修好。

真正該從此處學到的有兩層：

**第一層**：`~` 正規化處理的是使用者名那一段，處理不了 HOME 之下的佈局差異。跨 repo 引用（本例的 blog）在本專案的 git 樹外，沒有專案相對形式可用，`$CLAUDE_PROJECT_DIR` 與 `git rev-parse` 都指不到它。這類引用不能寫成任何含 HOME 之下路徑段的形式，否則必在某一側壞掉。已定案兩種替代形式，見上方判別準則表：可執行命令用 `${<REPO>_REPO:?<提示>}`（變數定義放不同步的本機設定），知識溯源用「repo 識別 + repo 相對路徑」（例 `blog repo: content/record/x.md`）。

**第二層**：一份宣稱已實測的記錄，其可信度不高於它貼出的 raw stdout，且 raw stdout 只在產生它的環境內有效。上段當時寫成了確定語氣的實測敘述，五位審查委員逐一過目而無人重跑 `ls`——因為審查框架各自聚焦欄位、範圍、措辭，沒有人把「新值在**我這一側**是否存在」列為檢查項。校正路徑時若只做字串替換而不在自己環境當場執行命令，會產出一份看起來已修好、實際仍解析不到的路徑，且因為已經「處理過」而更不容易再被檢查。

校正完成後的驗證方式為三張票各自 `grep -c` 該字串計數為 0。
