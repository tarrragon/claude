# PC-GPD-062: 以字面字串 grep 驗收「機密未外洩」時，描述這條檢查的文件本身含該字串，計數永遠不為 0；驗收被迫在「勾選不實條文」與「force push 改歷史」之間選

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 風險等級 | 低 |
| 首次觀察 | 2026-10-31 |

## 症狀

一張需要 API key 的實驗票，acceptance 寫「`git log -p -- <dir>` 與 `<dir>` 中 grep `<key 前綴>` 的計數皆為 0」。

收尾時計數為 2。兩處都不是 key，而是同目錄下前一個實驗的判讀規則文件裡的一句話：「提交前 `<key 前綴>` 計數必須為 0」。那句話後來被刪，但仍留在 git 歷史中。

執行者無法勾選這條 acceptance：直接勾，票面與事實不符；要讓計數歸零，只能 force push 改寫歷史，代價遠大於風險（那兩處根本不是機密）。

## 根因

**量測字串同時是被量測範圍內的文件內容**。驗收規則要求把檢查方式寫成文件，而文件放在受檢目錄裡，檢查字串就成了它自己的命中來源。這是檢查方式的自指，與機密是否外洩無關。

**用字面前綴代替機密的形狀**。前綴是任何談論這條檢查的文字都會用到的字，機密本身卻有固定格式（前綴後接一長串字元）。用前綴當量測，等於把「提到這種 key」和「寫入一把 key」視為同一件事。

## 解決方案

- acceptance 的量測改用機密的形狀，例如 `<key 前綴>-[A-Za-z0-9_-]{20,}`，不用裸前綴。
- 已寫成字面前綴的票，收尾時改寫 acceptance 條文（說明字面命中的來源 commit，並附形狀計數），再勾選。不 force push。

## 預防措施

- 撰寫「機密未寫入」類 acceptance 時，量測欄直接寫形狀 regex。
- 在文件中描述這類檢查時，以佔位符代替真實前綴，或把文件放在受檢範圍之外。
- 量測範圍要涵蓋條文列出的每個位置（檔案、票面、commit、日誌），不只程式目錄。
