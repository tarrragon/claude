# PC-LLM-002: 修好恆放行的檢查，浮出被它掩蓋的規則衝突與倚賴它的例行流程

## 基本資訊

| 項目 | 值 |
|------|-----|
| 風險等級 | 中 |
| 來源版本 | 3.1.0 |
| 偵測時機 | 執行期修 fail-open 檢查，合併前盤點收緊影響 |

## 摘要

一個檢查長期恆放行（fail-open）時，與它矛盾的規則、以及靠它放行才跑得通的例行流程，都不會產生任何訊號。把檢查修好的那一刻，這些矛盾同時浮出，表現為「照文件做的例行操作突然被擋」。修 fail-open 的票若只驗證檢查本身（對照測試全綠），會把規則衝突帶進 main，由下一個照文件操作的人撞上。

## 症狀

| 症狀 | 觀察點 |
|------|--------|
| 檢查的失敗路徑一律回「放行」或「降級警告」 | 解析失敗回 None、子程序失敗回 0、例外被吞成通過 |
| 另一條規則要求的操作順序與該檢查的前提相反 | 例：檢查要求「合併前票已 completed」，收尾規則要求「合併後才 complete」 |
| 例行流程從未帶過用來豁免該檢查的旗標，卻一直能過 | 旗標被當成例外用途，實際上每次都該帶 |
| 修好後的第一個例行操作被擋，訊息與文件步驟對不上 | 阻擋訊息是正確的，文件才是過時的 |

## 案例（2026-11-09）

`worktree merge` 的「合併前票須 completed」檢查逐行找含 status 字樣的行解析人讀輸出：一般票回 None 而降級放行。同期用戶裁定的〈隔離派發的收尾界線〉規定 PM「合併並驗證後才 complete」，即例行合併時票必為 in_progress。兩條規則矛盾，但檢查恆放行，矛盾從未顯現。

修好檢查（改讀 frontmatter，讀不到即阻擋）後，例行合併若不帶 `--pre-acceptance` 即被擋。修法票的對照測試全綠；矛盾是在合併前依「收緊時 grep 會被新判準擋下的例行步驟」盤點時才發現，交用戶裁定後同票改文件。

同一批次另一例：cleanup 的 Level 1（未提交變更，唯一不可繞過的閘門）在 git status 失敗時回 0 而放行；merge 的前置檢查共用同一函式，修好時兩條路徑同時收緊。

## 根因

fail-open 的檢查等於不存在，但它的存在本身讓規則撰寫者以為該前提有人把關，於是另一條規則可以安心訂下與之矛盾的順序。兩條規則各自看都合理，矛盾只在檢查生效時才成立。測試只驗證檢查函式本身，不驗證「現行文件的例行流程在新判準下是否還能跑」。

## 解決方案

修 fail-open（或任何把放行改為阻擋）的票，合併前多做一步：

1. 列出呼叫該檢查的所有入口（共用函式要追到每個呼叫端）。
2. 在框架文件 grep 這些入口的例行步驟範例，逐一套新判準判斷是否會被擋。
3. 會被擋者：同票改文件（或改為等效 CLI），並檢查是否與其他規則（尤其用戶裁定）矛盾；有矛盾則合併前交裁定，不由修法票自行選邊。

## 預防措施

- 收緊類變更的合併前回報，固定附「會被擋下的例行步驟清單」（multi-session-orchestration〈行為變更的判準與分級〉收緊列已有此要求）。
- 新增規則訂定操作順序時，確認其前提檢查不是 fail-open；是的話在規則內註明依賴的豁免旗標。
