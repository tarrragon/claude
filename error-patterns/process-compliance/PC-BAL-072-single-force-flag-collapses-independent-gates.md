# PC-BAL-072: 單一 --force 收掉多道獨立閘門，而關鍵判讀行印在成功訊息之前，操作者只讀最後一行

## 基本資訊

| 欄位 | 值 |
|------|-----|
| 類別 | process-compliance |
| 風險等級 | high |
| 來源版本 | 0.2.1 |
| 發現情境 | 向多消費端共用的發佈庫推送一支 skill，同一份內容在兩小時內覆蓋另一個消費端的版本兩次；第二次覆蓋的正是對方為修復第一次覆蓋而做的合併版本 |

## 症狀

- 推送成功，無錯誤碼，事後才由第三方發現遠端少了東西。
- 回頭看輸出，警告文字寫得毫不含糊（「版號與遠端相同」「兩側各自變動過」），操作者當下確實看到了，仍然繼續。
- 同一個操作者在明確知道這個風險、且剛剛才親手處理過一次同型事故之後，再犯一次。

## 根因

**三道閘門收在一個旗標下**。該推送命令的 `--force` 同時關掉：可攜性檢查、三方方向判讀、版號比對。三者的風險等級與可接受條件完全不同——可攜性違規多半是既有債務可以帶著推，版號落後遠端則絕不可推。收在同一個旗標下，操作者為了通過第一項而付出的代價是連後兩項一起關掉，而且不會意識到自己付了什麼。

**關鍵判讀行的位置在成功訊息之前**。`[Version] local X vs remote Y` 印在推送過程中段，`Pushed ...` 印在最後。操作者用 `| grep` 或 `| tail` 過濾輸出時（長輸出的常規做法），最容易保留的就是最後那行成功訊息；即使全讀，人的注意力也停在結果而非中段。這與「截斷方向」是同一類問題：判別成敗的資訊在頭或中段，而過濾習慣保留尾端。

**再犯的成因不是不知道**。第一次事故後我已寫下「push 前先判方向」並轉告同儕，第二次仍然發生——因為知識存在於敘事層（我知道要判方向），而操作發生在肌肉層（`--force` 是通過閘門的既定手勢）。**知道規則不會改變預設手勢，改變手勢要靠拿掉那個手勢的可用性**。

## 解決方案

1. **先跑不帶 `--force` 的同一命令，讀完版號行再決定**。這一步的成本是一次額外呼叫，收益是把「決定」從肌肉層拉回判斷層。
2. **本地版號不高於遠端時一律先取回合併，不推**。這是可機械執行的判準，不需要理解三方比對的語意。
3. **工具側：把版號落後從警告升為硬擋，另設專用旗標**。與可攜性、方向判讀分開——後兩者用 `--force` 略過合理，版號落後不該與它們共用同一個開關。
4. **工具側：關鍵判讀行與成功訊息同行或置後**。成功訊息帶上 `local X -> remote Y` 的實際結果，使 `| tail -1` 也能看見。

## 預防措施

- 對共用資產的寫入操作，把「讀哪一行才算讀過」寫進流程，而不是要求操作者「仔細看輸出」——後者對已經看過並繼續的人沒有約束力。
- 覆蓋事故的復原優先於追究：從遠端 git 歷史取回被覆蓋版本為基底、重新套用本地修正、讓號重推，並在版本紀錄留下事故經過。被覆蓋方通常會先於你發現，主動告知比等對方來問成本低。
- 同型事故第二次發生時，處置對象是手勢的可用性（工具預設、旗標粒度），不是再寫一次提醒。

## 關聯

- 上游原則：預設路徑引導正確做法——文件規範與工具預設不一致時，工具會贏。
- 同型家族：任何把多個獨立檢查收在單一 bypass 旗標下的工具（`--no-verify`、`--skip-checks`、`-f`），皆命中第一層。
