# PC-LLM-007: 長 session 中手寫的時刻取自推估而非工具輸出，與實際時刻前後都會偏

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 3.3.1 |
| 風險等級 | 低 |
| 首次觀察 | 2026-11-17 |

**判準**：寫進票面、交接段落與工作日誌的時刻，取自工具輸出（`date` 或 CLI 寫入時的時間戳），不取自自己對「現在幾點」的估計。

## 症狀

- 同一個主控 session 中發生兩次：
  - 一則進度行寫「17:45 更新」。compact 後接續時執行 `date`，實際時間是 17:37，所以這一行的寫入時間早於 17:37，手寫的時刻比實際晚。
  - 一則裁定段的標題寫「20:05」。同一次 `append-log` 由 CLI 蓋上的時間戳是 20:33，手寫的時刻比實際早。
- 兩次偏差方向相反，不是固定的時差，無法用加減一個常數修正。
- 兩次都寫在讀者不會即時核對的位置：票面的段落標題與進度行。事後拿 `date` 或 CLI 時間戳對照，才發現寫錯。

## 根因

- 模型沒有時鐘。「現在幾點」只能從 context 裡出現過的時間推估，例如上一次 `date` 的輸出、hook 日誌的時間戳、CLI 回報的寫入時間。
- 長 session 的兩次工具呼叫之間，常隔著數十分鐘的背景等待（代理人執行、合併閘門跑測試）。推估值會停在最後看到的時間，或依「感覺過了多久」往後推，兩種做法都可能偏，方向也不固定。
- `append-log` 寫入時本來就會蓋上正確的時間戳。內容裡另外手寫的時刻和它並列，讀者看到兩個不同的時間，無從判斷哪一個對。
- 手寫的時刻精確到分鐘，看起來像量測值，讀者不會懷疑。這和 PC-166 的虛構工具結果同類：一個沒有工具依據的值，用預期填上了。

## 解決方案

1. 已寫錯的：以 CLI 時間戳或 `date` 的輸出更正，或刪掉時刻只留日期。
2. 寫入前需要時刻時，先執行 `date '+%Y-%m-%d %H:%M'`，再以它的輸出填入。
3. 經 CLI 寫入的段落（例如 `append-log`），內容中不另寫時刻，以 CLI 時間戳為準。

## 預防措施

- 交接段落的標題要帶時刻時，只在同一回合剛執行過 `date` 才寫；否則只寫日期。
- 讀者側：票面上手寫的時刻與 CLI 時間戳不一致時，以 CLI 時間戳為準。

## 關聯

- [[PC-166]]：工具呼叫後以預期填補結果。本模式填補的是時刻：同樣是沒有工具依據的值，看起來卻像量測結果。
- `.claude/rules/core/tool-output-trust-rules.md` 規則 3：關鍵事實以固定值命令交叉驗證。時刻屬於這類事實，`date` 就是固定值命令。
