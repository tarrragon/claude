# PC-BAL-049: 驗收條件以書寫動作替代可驗證狀態，錯誤的全稱結論照樣滿足條件

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 高 |
| 首次發現 | 2026-08-20 |
| 適用範圍 | 任何要求執行者下全稱結論的驗收條件（「已全部覆蓋」「無其他實例」「已閉環」「掃描完畢」）；系列性修復任務的最後一張票為高發區 |
| 關聯 | [[PC-BAL-035]]（同屬驗收措辭失誤家族，機制不同——該模式鎖死攔截點，本模式鎖死的是「書寫」而非「正確」）、[[PC-165]]（綠燈不等於正確，本模式為其在驗收條文層的表現） |

## 錯誤症狀

- 驗收條件寫成「記錄 X 是否成立」「說明是否已全部處理」「在 Solution 記錄掃描結果」，執行者寫下一個**錯誤的**結論，條件仍被勾選且驗收通過
- 票面留下「已閉環」「無其他實例」「已全數覆蓋」的斷言，實際查證後不成立
- 所有訊號一致為綠：條目勾選、測試通過、gate 放行、代理人 exit_status 為 success
- 缺口只在下一位讀者恰好獨立複驗時才暴露；若無人複驗，錯誤結論成為後續決策的前提

## 根因分析

### 根因 1：條件的動詞決定了攔截點

「記錄」「說明」「填寫」是書寫動作，其完成條件是「有沒有寫」。「驗證」「掃描並逐一判定」「確認 N 處皆…」是查證動作，其完成條件是「查了沒有、怎麼查的」。前者的攔截點落在文件存在性，後者落在事實。條件寫成前者時，內容正確與否從一開始就不在驗收範圍內。

### 根因 2：全稱結論的證偽成本不對稱

「已修復 X」是單稱陳述，看 diff 即可確認。「無其他同類問題」是全稱陳述，確認它需要掃過全部候選集合。執行者處於剛完成修復的位置，注意力集中在已修的目標上，傾向以「我改的地方都對」推論「整體沒問題」——而全稱結論恰恰不能由單稱結論推得。

### 根因 3：驗證迴路封閉在條文內

測試依條件設計、覆核依條件重跑、gate 依條件勾選，三層共用同一份條文作真值來源。條文只要求「寫下結論」時，三層都不會去驗結論本身。此為 [[PC-165]]「測試綠燈不等於 runtime 正確」在驗收條文層的同構表現。

## 解決方案

全稱結論類的驗收條件，必須把**查證程序**寫進條文，使條件本身可獨立複驗：

| 反模式（要求書寫） | 正確（要求查證程序） |
|-------------------|---------------------|
| Solution 記錄該檔問題是否已全數閉環 | 以指定指令掃描全檔所有候選點，逐一列出並判定是否為同類問題，結果寫入 Solution |
| 說明是否還有其他受影響的呼叫端 | 列出該符號的全部呼叫端（附取得清單的指令），逐一標註是否受影響 |
| 確認無其他同類實例 | 以指定條件列舉候選集合，附集合大小與逐項判定結果 |
| 記錄變更是否有回歸風險 | 執行完整測試套件，記錄通過數與失敗數 |

**判準問句**：把條件唸一遍，問「執行者若寫下一個錯誤的結論，這條條件還算滿足嗎？」答「算」即表示攔截點落在書寫而非事實，須改寫。

改寫方向是把「結論」換成「產生結論的程序 + 程序的輸出」。條文指定了指令與輸出形式後，驗收者可用同一指令複跑比對，錯誤結論不再能通過。

## 預防措施

- **辨識訊號**：條件含「是否」「說明」「記錄…結果」且對象是全稱判斷時，先套用判準問句
- **系列任務的最後一張票特別檢查**：「這是系列最後一項，完成後閉環」的票天然會要求全稱結論，是本模式的高發位置
- **驗收方複驗全稱宣稱**：驗收者遇到「已閉環」「無其他」「已全部」時，獨立跑一次列舉。成本通常是一行指令，遠低於錯誤結論被當作前提的代價
- **代理人 prompt 同步要求**：派發時把查證程序寫進 prompt，不要只寫「確認是否閉環」
