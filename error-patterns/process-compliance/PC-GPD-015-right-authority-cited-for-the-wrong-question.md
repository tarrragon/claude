# PC-GPD-015: 引用了對的權威來源，但它回答的不是被問的那個問題

| 項目 | 值 |

| 編號 | PC-GPD-015 |
| 類別 | process-compliance |
| 風險等級 | 高 |

| 來源版本 | 0.1.0 |

## 問題描述

### 症狀

一個判斷附了權威依據，依據**確實存在、引用逐字準確、也確實適用於它自己所回答的那個問題**——但那個問題不是當下被問的問題。結論因此建立在一個正確但無關的基礎上。

**這比引錯規則難發現得多**：引錯規則時，讀者去查來源會發現不對題；引對規則答錯題時，讀者去查來源會發現**完全吻合**，於是驗證通過、判斷被採納。

**識別特徵**：

- 判斷形如「依 X 規則，故採 Y」，而 X 規則確實存在且內容確實如所述
- 覆核者查證引用時得到「屬實」，因而停止追問
- 錯誤只在有人問出「這條規則回答的是什麼問題」時才現形——而那個問題平常沒有人問，因為引用已經看起來完成了論證
- 同一權威來源在別處被正確使用過，使誤用更難察覺

### 根本原因 (5 Why 分析)

1. **Why 1**：為什麼誤用沒被發現？因為覆核的動作是「查證引用是否屬實」，而引用確實屬實。
2. **Why 2**：為什麼覆核只查引用屬實？因為引用的真偽有廉價的驗證手段（去讀來源），而引用的**切題性**沒有——切題與否要重建當下的問題，那需要理解整個判斷脈絡。
3. **Why 3**：為什麼不重建問題？因為附了依據的判斷在形式上已經完整，**依據的存在本身就構成了停止追問的訊號**。
4. **Why 4**：為什麼依據的存在會構成停止訊號？因為「有依據」在多數情境下與「已被驗證」高度相關，這個相關性讓它成為可靠的啟發式——直到遇上這一類。
5. **Why 5（根本原因）**：**權威來源通常各自回答一個特定問題，但引用時只帶走結論不帶走問題。** 問題一旦被剝離，同一條規則就可以被套到任何表面相似的情境上，而套錯時沒有任何形式上的破綻。

## 解決方案

### 正確做法

**一、引用時把「這條規則回答的是什麼問題」一併寫出來。** 不是寫「依 X 規則，故 Y」，而是「X 規則處理的是『甲問題』，本處要決定的正是甲，故 Y」。多寫一句，誤用就從無破綻變成當場自相矛盾。

**二、覆核引用時問兩件事，不是一件。** 第一件是「這條規則是否如所述存在」（廉價，多數人會做）；第二件是「**這條規則回答的問題，是不是這裡要決定的問題**」（昂貴，多數人不會做）。第二件才是本模式的攔截點。

**三、同一份權威在多處被引用時，逐處分別檢查切題性。** 它在別處正確不構成此處正確，而「這條規則我們一直在用」正是最容易讓人略過檢查的說法。

**四、注意「證明了 A 層，用來否證 B 層的主張」這個變體。** 引用的可以是實測結果而非規則：量測本身無誤、數據為真，但它量的是另一個層面。判別方式相同——問「這份證據回答的是哪一層的問題」。

**五、過去式證據不回答現在式問題。** 「上次這樣做成功了」證明的是觀測當下，對現在是否仍成立沒有鑑別力。用它去否證一個關於當前狀態的主張，屬本模式的時間軸變體。

### 錯誤做法 (避免)

- 只寫「依 X 規則」而不寫該規則處理的問題
- 覆核時只驗證引用屬實就採納
- 以「這條規則我們一直這樣用」作為此處適用的依據
- 用某一層的事實去否證另一層的主張，未先確認兩者同層
- 用過去某次的成功／失敗去斷言當前狀態

## 實例（2026-09-09，同一 session 內兩則，變體不同）

### 實例一：規則變體——用對規則答錯問題

| 項目 | 內容 |
|------|------|
| 當下要決定的 | 一個缺陷該在本地修，還是升級到框架 canonical repo 修 |
| 引用的依據 | 一條「建立端優先於驗證端清單」的判定順序規則 |
| 引用是否屬實 | **是**——該規則存在、內容如所述、且該缺陷確實是驗證端落後於建立端 |
| 為何錯 | 該規則回答的是「**兩者衝突時誰是權威**」，不是「**該在哪裡修**」。後者的判準在另一份升級流程文件，是兩條 AND（抽象可攜性、資產範圍），套用後結論相反 |
| 暴露路徑 | 第三方以正確判準覆核另一張票時，順帶指出同一判準套到這張票也成立 |

**若不更正的後果**：一個存在於每一個 consumer 的缺陷會被在本地修掉，修復困在本地 commit 歷史不傳播，下次同步可能被上游未修的舊版覆蓋，且無 canonical 記錄可查。

### 實例二：層級變體——證明了 A 層，用來否證 B 層

| 項目 | 內容 |
|------|------|
| 當下的爭點 | 某些代理人型別是否仍可派發 |
| 提出的證據 | 定義檔全部存在於版控目錄；以及「一小時前才成功派發過四次」 |
| 證據是否為真 | **是**——檔案確實都在，那四次派發確實成功 |
| 為何錯 | 定義檔存在屬**專案資產**層（持久、版控），可派發性屬 **harness 能力**層（瞬時、可 per-session 不同），兩者由不同機制決定，前者不蘊含後者。而「一小時前成功」是過去式證據，對當前可派發性無鑑別力 |
| 正確的訊號 | **派發失敗本身**——不是任何一份清單，也不是檔案是否存在 |

**共通形態**：兩則的引用或量測都無誤，錯的是**它回答的問題與當下要決定的問題不同**。兩則都通過了「查證引用是否屬實」這一關。

## 與相鄰模式的分界

| 模式 | 錯在哪 | 覆核時會發生什麼 |
|------|-------|-----------------|
| `PC-GPD-009`（驗證器量錯軸） | 檢查器量的是代理指標而非宣稱保證的性質 | 檢查通過，缺陷完好無損 |
| `PC-GPD-011`（過濾產物活得比它的問題久） | **資料**被拿去回答它不是為之而生的問題 | 資料為真，結論錯 |
| `PC-GPD-014`（正確結論配錯誤理由） | **理由**錯而結論對 | 當下完全無症狀 |
| **本則** | **依據對、引用準確，但它回答的是另一個問題** | **查證引用得到「屬實」，因而停止追問** |

與 `PC-GPD-011` 最近但載體不同：該則的誤用對象是產出的資料（一份過濾結果），本則是權威來源（規則、判準、或某一層的事實）。與 `PC-GPD-014` 相鄰而互補——那則是理由錯，本則是**依據對而問題錯**，後者更難發現，因為前者至少在被檢視時說不通，後者被檢視時完全說得通。

### 與 `PC-GPD-009` 是同一骨架的兩個載體

兩則的骨架逐字對應，此處寫明，避免讀者把它們當成無關的兩件事：

> **手段本身無瑕疵、其產出為真，但它回答的是另一個問題；而覆核動作只驗手段的真實性，因此必然通過。**

**不合併的理由是防護動作不同**——合併會把兩條可操作的檢查退化成一條抽象原則，而抽象原則在當下不會觸發任何動作：

| | 載體 | 產出的東西 | 該問的那一句 | 何時問 |
|---|---|---|---|---|
| `PC-GPD-009` | 量測／檢查 | 一個關於某性質的判定（通過／不通過） | **通過這個量測是否蘊含它宣稱保證的性質？** | 設計檢查器時，或準備採信一個綠燈時 |
| 本則 | 權威依據 | 一個有依據支撐的決定 | **這條依據回答的是什麼問題，和這裡要決定的是不是同一個？** | 撰寫或覆核一個附了依據的判斷時 |

**最接近的一對是 `PC-GPD-009` 來源二（使用者臨時發明的代理指標）與本則的層級變體**——兩者都是讀者自己搭的橋，沒有人誤導。判別依據是替身的形態：前者的替身是**一個量測動作**（例如以最近修改時間找「我剛建立的那張票」），後者的替身是**一個既有事實被當作另一層的證據**（例如以定義檔存在證明該型別可派發）。

**遇到第三種載體時掛在這個骨架下，不必另立新則**——例如「跑了對的測試，但它驗的不是這個行為」（載體是測試）、「取得了正確的統計，但它統計的不是待答的母體」（載體是資料聚合）。

判斷是否屬本骨架的問題只有一個，**但它有一個必須寫出來的前提**：

> **前提：已判定此處存在缺陷。** 在此前提下——覆核者若去查證這個手段本身，會不會得到「屬實」？會，就是本骨架。

**前提不可省略。** 沒有它，這一問會吞掉全部正確的工作：一個完全正確的引用——回答的正是被問的問題——查證起來同樣「屬實」，照字面也會被判為本骨架。這一問回答的是「**給定已有缺陷，歸哪一則**」，不是「什麼算本骨架」；手段為假歸一般錯誤，手段為真才歸此處。

> **本節初版即是本則的實例。** 該問句最初寫成不帶前提的形式，於是它自己成了「一個判準被剝離問題後套到任何表面相似情境上」的例子。修法正是本則解決方案第一條（引用時把這條規則回答的是什麼問題一併寫出來）的直接應用——**判準句自己也要遵守它所要求的形式**，否則它是一條要求別人寫出問題、自己卻沒寫的規則。
