# PC-BAL-056：潛伏缺陷的發現率是操作多樣性的函數，不是稽核強度的函數

## 基本資訊

- **Pattern ID**: PC-BAL-056
- **分類**: process-compliance（缺陷發現方法的資源配置）
- **風險等級**: 高
- **關聯**: [[PC-V1-009]]（機械缺陷誤診為流程缺陷；彼處處理事後歸因，此處處理事前發現，兩者可疊加）、[[PC-BAL-010]]（驗證管道對待驗現象不敏感；為本模式的下位，該模式指單一管道的不敏感，本模式指以讀的方式尋找只能由做才會顯現的東西）、[[ARCH-BAL-011]]（名稱造成職責已涵蓋的假象）

想找出尚未浮現的缺陷時，直覺做法是加一輪審查、多派幾位 reviewer、換更多視角。但一整類缺陷只在特定操作被執行時才產生可觀察的差異；該操作沒被執行過，缺陷就沒有任何表徵可供閱讀，無論讀的人有多少、多仔細。

**Why**：審查讀的是**產物的當前狀態**，而這類缺陷不存在於狀態中，只存在於**狀態轉換的規則裡**。判斷基準綁在某個維度上而該維度沒被改動過、傳輸通道對某種變更不敏感而該變更沒發生過、驗證管道對某個屬性不敏感而該屬性沒被測過——這些都是「規則有洞」而非「內容有錯」。閱讀內容找不到規則的洞，因為洞的證據要等到規則被套用在它處理不了的輸入上才會產生。

增加審查輪次會提高「內容錯誤」的發現率，於是產生審查有效的正回饋，掩蓋了它對「規則有洞」這一類的發現率恆為零這個事實。輪次越多，「已經審過這麼多輪」的信心越強，而該類缺陷的存活期越長。

**Consequence**：

| 層級 | 影響 |
|------|------|
| 資源配置 | 尋找潛伏缺陷的預算投入審查，該投入對目標類別的邊際效益為零，而執行一次非常規操作的成本通常低得多 |
| 假信心 | 審查通過被讀為「已檢查過」，使後續更不可能去執行那個未曾執行的操作 |
| 存活期 | 缺陷存活期由觸發頻率決定而非嚴重性決定，故低頻操作路徑上的高嚴重性缺陷可長期潛伏而不與嚴重性成比例地被優先處理 |
| 發現時點 | 該類缺陷通常在最不方便的時刻被觸發——某人第一次做那件平常不做的事，而那件事往往是為了完成別的任務 |

**Action**：

| 情境 | 做法 |
|------|------|
| 目標是找出未知缺陷 | 列出「這個系統支援但我們從未執行過」的操作，執行其中之一。這比再加一輪審查更可能產生新資訊 |
| 已跑過多輪審查仍不放心 | 追問「不放心的是內容還是規則」。若是規則，再加輪次不會改變結果，改為設計一個會觸發該規則的輸入 |
| 判斷某缺陷該由審查或執行發現 | 問「這個缺陷在系統靜止時有表徵嗎」。無表徵者只能由執行發現 |
| 評估既有防護的覆蓋 | 覆蓋率應以「已執行過的操作種類」計，非以「已審查過的檔案數」計 |
| 排定潛伏缺陷的處理順序 | 觸發頻率低不等於風險低。低頻路徑的缺陷發現得晚、發現時脈絡最少、且往往正卡在某個進行中的任務上 |

**識別訊號**：以「已經跑過 N 輪審查」作為品質論據；提議「再加一輪 / 多派幾位 reviewer」以尋找未知問題；缺陷回顧時發現「所有人都看過那段程式碼但沒人質疑」；缺陷由某次非常規操作或某個自動閘門攔下而非由審查發現。

**邊界**：與 `PC-V1-009`（機械缺陷誤診為流程缺陷）軸向不同——該模式處理**事後歸因**（事故後不該為機械缺陷加人工關卡），本模式處理**事前發現**（找潛伏缺陷不該靠加審查輪次）。兩者可疊加：一個由執行才能發現的缺陷，事後又被歸因為缺人工審查，等於在對該類別無效的方向上追加投資。與 `PC-BAL-010`（驗證管道對待驗現象不敏感）**並列而非上下位**——該檔標題與「家族層定位」節自述為家族層並列出三個下位成員，本模式不重新分層。兩者的切法不同：`PC-BAL-010` 切的是管道對待驗屬性有無分辨力（管道敏感度），本模式切的是「用讀的方式尋找只能由做才會顯現的東西」（手段與現象的錯配），審查是其中一種讀。同一事件可同時是兩者的實例。

**實證來源**：一組跨專案協作中，四個框架缺陷在同一段時間內被發現——自動產生的 CHANGELOG 帶入專案識別符而觸發自身守衛、發佈通道記錄的檔名大小寫與本地分歧、以忽略大小寫的比對驗證大小寫結論、提交守衛對 rename 檔案以新路徑解析比對基準因而將整份檔案判為新增。

四者無一由審查發現，全部由同一件非常規操作觸發：**變更檔名**。該操作在此前的維護中極少執行，故四個缺陷各自潛伏至該次操作為止。其中第三項尤其說明問題——它是在為第二項做驗證的過程中，因驗證本身出錯而暴露的。

同期另一實例：一份 skill 在三輪、十二位 reviewer 的多視角審查中，其可攜性宣告的誤標未被任何一位提出；該問題最終由推送時的自動閘門攔下。審查的對象是內容，而該誤標的證據要等到推送規則被套用時才產生。

第三個實例更尖銳，因為出錯的正是審查所用的量尺。某張票的驗收條件之一寫「實跑涵蓋缺文件的老專案」，實跑到的專案並不缺文件（變更記錄五百餘行、規則檔近三百行），其問題是文件對待審的五個維度零回答。而該次審查最高價值的發現恰為「判準問有沒有文件，該問文件答不答得出產物」——**驗收條件本身用了存在性措辭，與它要審的對象犯同一個錯**。

該驗收條件寫於審查開始之前，故三輪、十二位 reviewer、六個專案實跑全程無人回頭檢視它：審查的對象是被審物，不是驗收條件。它最終被發現，是執行者在收尾時逐條把驗收拿去對實測結果——仍是執行，不是閱讀。

此例顯示本模式的一個加強形態：當規則的洞與待找的洞屬同一類時，審查不僅無效，還會以「已依此判準審過」的形式為該洞背書。

**三個實例的共同結構**：缺陷不在被讀的東西裡，而在讀的人沒有執行過的規則裡。增加讀的人數對此無效，執行一次即有效。

## 必要細分：執行本身也分維度

「靠執行發現」易被讀成「有跑過就會發現」，該讀法過寬。**執行的對象必須涵蓋待驗的維度**，否則執行只是換一種方式確認已經在確認的事。

實例：一個修復通過了二十一項測試、真實腳本的 live-trigger、以及自我驗證（該修復放行了自己的提交），三者皆為執行而非閱讀。但這些執行的對象是**程式碼的正確性**，而該修復的實際問題是它**從未離開所在的儲存庫**——三個訊號無一檢查位置。消費端拉取後拿到的仍是缺陷版本，而來源端的每一個訊號都顯示已修復。

此處缺的不是嚴格度：三項驗證各自加嚴到任意程度，仍然一次都不會問到位置。**問錯維度時，加強既有維度的投入其邊際效益為零**，與本模式主文所述「增加審查輪次對規則的洞無效」為同一結構，只是從閱讀換成了執行。

判別方式：列出目前所有驗證手段各自回答的問題，若它們的答案全部落在同一個維度（皆為「對不對」或皆為「在不在」），則另一維度無覆蓋，需新增手段而非強化既有手段。
