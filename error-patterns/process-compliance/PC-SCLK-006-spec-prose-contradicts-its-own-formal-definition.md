# PC-SCLK-006: 規格內的自然語言結論與其自身形式定義相反，TDD 循環無法自曝

---

| 項目 | 值 |

| 姊妹模式 | PC-165（測試綠燈不等於 runtime 正確）、PC-SCLK-004（推測性歸因取代逐字證據） |

## 症狀

規格文件在同一節內同時給出兩種表述：

1. **形式定義**——可機械求值的語意（區間表示、程式碼片段、數學不等式、API 語意引用）
2. **自然語言結論**——以「故」「因此」「也就是說」承接形式定義而導出的散文句

兩者相反，而規格明文要求下游依此撰寫測試。

關鍵特徵：**兩種寫法各自都能通過 TDD 循環**。測試從哪一句抄，斷言就照那句寫；實作再照測試寫。紅燈綠燈全程正常，因為測試與實作內部自洽——只是兩者共同偏離了形式定義所描述的真實 API 行為。缺陷要到實機驗證或真實資料進來才暴露，此時測試與實作都已寫成，回頭要同時改兩邊。

---

## 實例（2026-07-31，screen_clock 1.4.0-W2-006）

TDD Phase 1 產出的螢幕判定契約，同一節內：

| 位置 | 表述 |
|------|------|
| §2.1 形式定義 | 「涵蓋判定採 `NSRect.contains(_:)` 的半開區間語意：`minX <= x < maxX`、`minY <= y < maxY`」 |
| §2.1 散文結論 | 「故相鄰螢幕的共用邊界座標**歸屬左／下側**螢幕」 |
| §4 GWT 場景 3 | 「Given 兩螢幕於 x=1920 相鄰；When 游標恰在 x=1920；Then 命中**右側**螢幕」 |

推演形式定義即可判定散文為誤：螢幕 A 為 `[0, 1920)`，螢幕 B 為 `[1920, 3840)`，游標 x=1920 時，A 的判定為 `0 <= 1920 < 1920` 即 false，B 的判定為 `1920 <= 1920 < 3840` 即 true，故歸屬右側。場景 3 正確，散文結論相反。

該散文句在規格中被明文標為「契約的一部分，Phase 2 須有邊界座標案例鎖定」——即它是要被寫成測試的對象。

**未被攔截的路徑**：本次派出六個審查視角，其中一致性視角逐項執行了四表交叉檢查，並把「GWT 場景 3 ↔ §2.1 半開區間語意」這一格標記為「一致」。該視角確認了兩處都在談邊界語意、都提到半開區間，但沒有代入具體座標推演，因此得出「一致」的誤判，反而製造了「此處已檢查」的假象。缺陷由另外兩個視角（架構品味、文字品質）各自獨立推演後抓出。

## 二度發生：本 pattern 建檔後，由記錄者本人復發

本節記錄一次復發，用以區分「撰寫端提醒」與「句型層改寫」兩種防護的效力差異。

同一張 ticket、同一日、本檔建立**之後**，PM 在轉述審查建議時寫下座標系契約：

> 所有 `NSPoint` / `NSRect` 為 AppKit 全域左下原點，第二螢幕置於主螢幕**上方或左方**時 frame 座標為負

方向同樣有誤。AppKit 全域座標的 y 軸向上為正，上方螢幕的 y 是正值（如 `+1080`），負 y 來自**下方**螢幕。該句於下一階段由測試設計者建立 fixture 時發現並更正。

這次復發的三個特徵使其比首發更有診斷價值：

| 特徵 | 意義 |
|------|------|
| 犯錯者是本檔的記錄者 | 「知道這個 pattern 存在」對防護無效——記憶層防護在此類錯誤上不成立 |
| 發生在轉述他人正確建議時 | 來源建議正確，錯誤在複述環節產生，與首發的「形式定義正確、散文複述出錯」同構 |
| 上下文其餘部分完全正確 | 「AppKit 全域左下原點」正確、「須有負座標案例」正確，只有方向詞錯；正確的上下文不會擋下方向詞錯誤，反而提高可信度 |

**推論**：撰寫端的「小心一點」式提醒在本案無效——記錄者本人在知曉且高度警覺的狀態下仍於數十分鐘內復發。單一樣本不足以否定提醒層的一般效力，但足以說明防護重心應放在**句型層**：優先讓方向詞不出現（改為引用不變的參照），而非要求撰寫者更小心。

攔截仍可依賴下游審查——本次復發即由測試設計者於建立 fixture 時抓出，該攔截本身正來自審查端的人工推演。故兩者分工為：句型層負責讓錯誤難以寫出，審查端保留為第二道防線。落地方式見下節「防護」的撰寫端與審查端 Action。

## 根因

| 層次 | 說明 |
|------|------|
| 直接原因 | 撰寫者以自然語言複述形式定義時，方向詞（左右／上下／前後／大於小於）在腦中轉換出錯，而複述句未經回代驗證 |
| 助長條件 | 形式定義正確，使撰寫者與審查者對該節產生「已經很嚴謹」的信任，散文句被視為附註而非契約 |
| 為何 TDD 攔不住 | TDD 的紅綠燈驗證「實作是否符合測試」，不驗證「測試是否符合真實 API 語意」。當測試源頭本身有二義，兩種選擇都會得到綠燈 |
| 為何交叉檢查攔不住 | 逐項交叉檢查若以「兩處是否提及同一主題」為判準，而非「代入具體值後結論是否相同」，則對本類矛盾完全不敏感 |

---

## 防護

### 撰寫端

形式定義與自然語言結論並存時，散文句必須可由形式定義機械推導。撰寫後回代至少一個具體邊界值驗證方向詞。

**Why**：方向詞的錯誤不會被形式定義的正確性掩蓋，兩者在文件中地位相同，下游無從判斷何者為準。
**Consequence**：不驗證則散文與定義的矛盾會原樣傳入測試設計，且因兩種寫法都能綠燈而不被 TDD 攔截。
**Action**：優先刪除以方向詞描述的散文句，改以「語意等同 `<API 名稱>`」直接引用權威語意，且該 API 名稱須與同節形式定義所用的符號一致（本案形式定義引用 `NSRect.contains(_:)`，散文即應寫「語意等同 `NSRect.contains(_:)`：邊界座標歸屬該值為其 `minX`／`minY` 的螢幕」；`NSPointInRect` 為其 C API 等價形式，混用兩個符號會製造本 pattern 的弱化版）。方向詞依座標系而變，API 語意不變。

### 審查端

交叉一致性檢查的判準是「代入具體值後兩處結論是否相同」，不是「兩處是否提及同一主題」。

**Why**：主題相符的兩段文字可以得出相反結論，主題比對對此類矛盾零敏感度。
**Consequence**：以主題比對產出的「一致」結論會標記該處已檢查，使後續審查跳過，缺陷因而通過閘門。
**Action**：檢查表中每一格填「一致」之前，取一個具體輸入值代入兩處表述各求一次結果；兩者相同才可標為一致。無法代入求值的表述（純敘述性、無形式定義）另標為「不適用」，不與「一致」混用。

### 流程端

規格層審查不可只派單一視角。本案的攔截來自兩個視角的獨立推演，兩者皆非一致性視角，而專責一致性的視角反而誤判。

**Why**：任一視角都有其判準的盲區，一致性視角的盲區恰好落在「主題相符但結論相反」。
**Consequence**：單視角審查通過不代表無矛盾，且會因「已審查」而降低後續警覺。
**Action**：規格層審查維持多視角並行，且視角間允許職責重疊；重疊處出現判定分歧時，以能出示具體推演過程者為準，不以視角的專責範圍為準。

## 偵測訊號

| 訊號 | 說明 |
|------|------|
| 規格句以「故」「因此」「也就是說」承接一段形式定義 | 該句是複述而非定義，屬本模式高風險位置，須回代驗證 |
| 同一份文件的散文與範例／測試場景對同一輸入給出不同結果 | 直接命中本模式 |
| 交叉檢查表大量填「一致」但無推演記錄 | 判準可能是主題比對而非求值比對 |
| 契約中出現左／右／上／下／前／後等方向詞 | 方向詞依座標系而變，應改為引用 API 語意 |
