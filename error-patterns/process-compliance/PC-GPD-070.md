# PC-GPD-070：先寫「已完成」再看動作結果

## 基本資訊

| 項目 | 內容 |
|------|------|
| Pattern ID | PC-GPD-070 |
| 分類 | process-compliance（交接文件的狀態宣告） |
| 風險等級 | 中 |
| 來源版本 | 0.5.0 |
| 首次觀測 | 2026-11-01 |
| 關聯 | [[PC-166]] 規則 1（工具呼叫後不續寫預期結果）與規則 5（重大狀態以世界平面為準） |

## 摘要

**在同一回合並行發出一個寫入動作與一筆「該動作已完成」的紀錄，紀錄會在動作結果回來之前就寫入交接文件。** 動作被 hook、權限判定或錯誤擋下時，紀錄仍已寫入並推送；讀者看到的是從未發生的狀態。這是 PC-166 規則 1 的變形：預期結果沒有寫在對話裡，而是寫進了持久的交接載體。

## 症狀

- 主控並行發出兩個呼叫：一是 Edit 修改設定檔（切換協調票），二是 Bash 以 append-log 寫入「設定檔已切換」並推送。
- Edit 被 hook 擋下（路徑不在主線程白名單），設定檔沒有改變。
- append-log 照常成功，協調票上留下「已切換」的錯誤宣告，之後要另寫一筆更正。

## 根因

- 並行呼叫之間沒有依賴順序：紀錄呼叫不讀取動作呼叫的結果，兩者各自成功或失敗。
- 撰寫紀錄時，把「打算做的事」當成「已做完的事」，這和 PC-166 規則 1 的點火動作同形。
- 交接文件是持久平面。寫錯的宣告被下一個 session 或其他線讀到，就會照著它行動。

## 防護

| 情境 | 做法 |
|------|------|
| 紀錄內容宣告某動作的結果（已切換、已刪除、已合併、已推送） | 動作與紀錄拆成兩個回合：先等動作結果回來，再寫紀錄 |
| 想並行以節省回合 | 只並行彼此獨立、且紀錄不宣告對方結果的呼叫 |
| 動作可能被 hook 或權限判定擋下（寫 `.claude/` 非白名單路徑、刪除檔案、跨 repo 寫入） | 一律序列化，並以固定值查證（`git diff`、`test -f`、`git log -1`）後再記錄 |
| 已寫入錯誤宣告 | 追加一筆更正，寫明原宣告不正確、實際狀態與成因；不改寫歷史紀錄 |

## 檢查問句

寫入交接文件之前問：這筆紀錄宣告的結果，在本回合是否已經由工具輸出證實？沒有證實，就把這筆紀錄移到下一回合。
