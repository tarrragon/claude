# PC-BAL-012：複合條件搜尋的加總計數遮蔽單一詞項的零命中

## 症狀

以單一次 `grep -E "A|B"`（或多值 `--include`、多路徑、多欄位查詢）取得一個**加總指標**，再用該指標同時支撐「A 有覆蓋」與「B 有覆蓋」兩個獨立主張。實際上加總可能完全由 A 貢獻，B 的命中為零。

| 表現 | 具體樣態 |
|------|---------|
| 證據數字很漂亮 | 「13 檔 59 處命中」——非零且量大，讀起來像充分證據 |
| 主張數量多於查詢次數 | 一次搜尋支撐 N 個並列主張（N >= 2） |
| 未做逐項拆解 | 沒有分別回報每個詞項各自的命中數 |
| 結論方向與期待一致 | 查詢動機是「確認可以刪」，加總非零正好支持該方向 |

**與 PC-161 的區別**：PC-161 是 grep 範圍/方法有誤導致絕對量詞（「0 個」）失真，錯在**單一主張的證據不成立**。本模式的 grep 語法與範圍皆正確、回報數字也真實，錯在**用一項證據覆蓋多項主張**——每個主張都需要自己的證據，加總不可分攤。

## 根因

**機制層**：`grep -E "A|B"` 的輸出是聯集，計數是聯集的大小。聯集非空無法推導任一子集非空。這是集合論層面的無效推論，不是工具缺陷——工具忠實回答了被問的問題，只是被問的問題（「A 或 B 出現幾次」）不等於想回答的問題（「A 出現幾次，且 B 出現幾次」）。

**行為層**：合併查詢的動機是省一次呼叫。省下的那次呼叫正是拆解證據的那次。查詢成本的節省與證據強度的損失同時發生且不可見——輸出裡沒有任何欄位提示「其中一項為零」。

**放大條件**：當查詢者已有傾向結論（如「這個檔案可以刪」），非零加總會被讀成確認，逐項拆解的動機隨之消失。此時本模式與確認偏誤共振，錯誤結論的信心反而升高。

## 後果

以假通過的覆蓋證明為前提，做出不可逆或高成本決策：

- 刪除仍是唯一載體的內容（本案：`memory-capture-guide.md` 的「結論式標題」在框架內無他處承載，加總證據卻宣稱已覆蓋）
- 將前提寫入 ticket 的 `how.strategy` 與派發 prompt，使下游執行者繼承錯誤前提
- 若下游無獨立驗證環節，錯誤直達產出；本案靠派發時要求的「刪除前重新驗證」絆腳索攔下

## 解決方案

**每個並列主張各自一次查詢，分別回報命中數。**

```bash
# 反例：一次查詢支撐兩個主張
grep -rc "結論式\|原子" .claude/skills/compositional-writing/ | awk -F: '{s+=$2} END {print s}'
# → 59。用於宣稱「結論式與原子性皆已覆蓋」。實際 結論式=0、原子=59

# 正例：逐項拆解，各自回報
for term in 結論式 原子; do
  printf '%s: ' "$term"
  grep -rc "$term" .claude/skills/compositional-writing/ --include="*.md" \
    | awk -F: '{s+=$2} END {print s+0}'
done
# → 結論式: 0 / 原子: 59。零命中立即可見
```

**已用加總下過結論時的補救**：回頭對每個詞項各跑一次，任一為零即結論作廢，不做部分挽救。

## 預防措施

| 時機 | 檢查 |
|------|------|
| 寫下含「且」「皆」「兩者都」的覆蓋主張時 | 主張數 N 是否對應 N 次獨立查詢？ |
| 用搜尋計數當證據時 | 這個數字是加總還是單項？加總則拆解後再引用 |
| 查詢結果與既有傾向一致時 | 提高而非降低拆解標準（確認偏誤共振點） |
| 派發 prompt 寫入實測數字時 | 數字的取得方式一併寫入，讓執行者能重跑驗證 |

**結構性防護**：對「刪除既有內容」類決策，把覆蓋驗證設為**執行者的前置步驟**而非派發者的既成結論，並明寫「驗證不通過即停止回報，不得續行刪除」。本案即因此攔下——派發者的前提錯誤由執行者的獨立重驗發現。
