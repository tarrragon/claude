# PC-GPD-023: 先把尚未分配的識別符寫進文件、後才向共用計數器申請，並行環境下該引用會指向他人的物件

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-GPD-023 |
| 類別 | process-compliance |
| 風險等級 | 中 |
| 提出日期 | 2026-09-10 |
| 證據強度 | 一次實際命中並在提交前攔下（三個執行體並行於同一 repo） |

## 模式內容

識別符由**共用的單調計數器**分配（任務編號、issue 編號、錯誤模式編號、migration 序號、PR 號）時，若執行順序為：

1. 在文件中寫下「處置見 `<推測的下一個號碼>`」
2. 才呼叫分配器實際建立該物件

則在步驟 1 與步驟 2 之間，任何並行執行體都可能取走那個號碼。分配器不會失敗，它會正常配給你**下一個**可用號碼，而文件裡寫的那一個現在屬於別人。

**Consequence（失效為靜默）**：留下的引用格式正確、號碼存在、物件確實可被開啟——它只是指向一個無關的東西。沒有任何工具會報錯：格式檢查通過（是合法識別符）、存在性檢查通過（該物件確實存在）、連結檢查通過（可解析）。唯一能發現它的是人去讀那個物件並發覺主題不符。引用越是寫在「處置見 X」這類讀者不會當場點開的位置，被發現得越晚。

**與單機環境的差別**：單一執行體時「下一個號碼」可準確預測，此寫法長期無害，因此會固化為習慣；並行度提高後同一習慣才開始失效，而失效不產生任何訊號，所以不存在「從此以後要改」的觸發時刻。

## 實際案例（三個執行體並行於同一 repo）

執行者在一份規格文件寫下「三者的日誌現況為三組互斥欄位，本規格不承認其為可消費形態（處置見 `<當時推測的下一號>`）」，隨後才執行建票命令。建立成功，但配到的是**再下一號**——原先推測的那個號碼已在這段間隔內被另一個執行體用於一張主題完全無關的框架守衛票。

兩個號碼相鄰、格式相同、皆為當日建立的真實票，從規格側看不出任何異狀。攔下的原因是執行者在建票後多跑了一次查詢確認號碼，而非任何工具報警。若略過該確認，規格會長期指向他人的票，且讀起來完全正常。

## 防護措施

| 措施 | 內容 |
|------|------|
| 順序反轉（主防線） | **先建立物件取得真實識別符，再把該識別符寫進文件。**分配器的回傳值是唯一可信來源 |
| 佔位符 | 若因敘述需要必須先寫，先寫不可能被誤讀為真實識別符的佔位符（如 `<待建票>`），建立後再回填。佔位符的好處正是它**不合法**——格式檢查會擋，失效不再靜默 |
| 建立後查證 | 建立命令的輸出可能被截斷或過濾（`bash-tool-usage-rules` 規則二），不以「指令沒報錯」推斷號碼；以獨立查詢命令讀回真實識別符後才回填 |
| 提交前掃描 | 同一批變更中新寫入的識別符引用，逐一確認其指向的物件主題與引用脈絡相符 |

**不適用的場合**：識別符由內容決定而非計數器分配時（git SHA、內容雜湊、UUID）不存在本模式——那些識別符不會被別人「取走」。
