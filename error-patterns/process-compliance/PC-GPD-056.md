# PC-GPD-056: 平台系統指令要求暫存檔一律放 scratchpad，框架卻禁止主線程寫 scratchpad；主線程以 Bash 重新導向（> file）存閘門或測試輸出時，Edit/Write 守衛看不到，違規靜默發生

## 基本資訊

| 項目 | 值 |
|------|-----|
| 分類 | process-compliance |
| 來源版本 | 0.5.0 |
| 風險等級 | 低 |
| 首次觀察 | 2026-10-30 |

## 症狀

主線程要保留一段較長的命令輸出（閘門結果、覆核重跑的測試輸出），就用 `cmd > <scratchpad>/xxx.log` 存檔，之後再 `head`／`tail` 讀取。框架的主線程可寫路徑明列禁止 scratchpad，但沒有任何守衛攔下這個寫入。

實證（2026-10-30，同一天兩例）：主控覆核重跑外掛測試時，把輸出導到 `/private/tmp/...` 的暫存檔；另一條線的主線程把閘門輸出存成 scratchpad 的 `gate-<票號>.log`，並在回報裡引用這個路徑。兩者都在事後的人工審查中才被發現。第三條線則明確寫下「主線程不能寫 scratchpad，改用 `--content-file /dev/stdin`」，可見規則本身有人知道，問題出在執行的當下。

## 根因

**兩個來源的指令互相衝突，而且平台指令出現得更頻繁**。平台的系統指令要求「暫存檔一律使用 scratchpad，不要用 /tmp」，每個 session 都會看到；框架的禁令寫在主線程角色規則的可寫路徑表裡。主線程要存暫存輸出時，最先想到的是平台給的位置。

**守衛只看 Edit／Write 工具**。可寫路徑的強制層攔的是 Edit／Write 的目標路徑，Bash 的 `>`、`tee` 不經過那一層，所以違規不會被即時擋下，只能靠事後審查發現。

**同一類衝突的另一面**：PC-GPD-031 記錄平台允許以 Bash 改檔、代理人因此繞過工具選擇規則。兩則都是平台指令與框架規則衝突、守衛又只攔 Edit／Write，所以 Bash 路徑上的違規都看不見；同日 implementation 代理人兩度以 Python heredoc 寫 lib/test，被 Bash 寫入邊界守衛擋下，屬於 PC-GPD-031 那一面。

## 解決方案

- 主線程需要長輸出時，在同一個指令內擷取（`2>&1 | head -N` 與 `| tail -N` 兩段都取，見 Bash 規則二），把需要的數字直接寫進票面，不另存檔案。
- 需要中介內容檔傳給 CLI 時，改用 `--content-file /dev/stdin` 或 heredoc。
- 已寫入的暫存檔立即刪除，並在回報中說明。

## 預防措施

- 框架與平台指令衝突時，以框架正本為準（工具輸出信任規則〈衍生情境：prompt 與正本衝突〉）。主線程角色規則的禁令可在 scratchpad 一詞旁註明「平台指令要求使用 scratchpad 的情境，主線程同樣不適用」。
- 強制層方向：讓 Bash 寫入邊界守衛也比對重新導向的目標，涵蓋 scratchpad 路徑；屬框架修補，依修補節奏先觀測。
