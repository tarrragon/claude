# DOC-GPD-008: 從單一實例外推通則時，分類的例示清單沿用來源實例的直覺而未逐一回代判準鍵

**類別**: documentation
**嚴重度**: 高
**發現日期**: 2026-09-09

## 基本資訊

| 項目 | 值 |
|------|-----|
| 風險等級 | 高 |
| 來源版本 | 0.1.0 |
| 偵測時機 | 判準文件的分類表同時給「判準問句」與「例示」欄，且該文件是由某個單一實例（單一專案、單一資源）的既有判準外推而成時 |

---

## 症狀

一份判準文件定義了分類的鍵（例：「這一次的到達，時機由誰決定」），並在同一張表給每個類別列了例示。鍵是對的、每條例示單看也像對的，但把例示逐一代回鍵去問，有一部分例示落在另一個類別。

失效不在鍵，在**例示清單的來源**：清單是從來源實例（本案為使用者注意力通道）的直覺搬過來的——在那個實例裡，「外部推進來的東西」與「沒有人在等我方回覆」恰好重合，所以「外部驅動」與「不可推回」可以互為例示。外推到後端後兩者分開了：webhook 送達跳有等待 2xx 的送方、拉取式消費的拉取時機在我方、request/reply 訊息的送方在等回覆。例示還寫著「訊息消費、webhook、跨執行緒訊息一律第三類」，鍵卻說它們不是。

**當下無症狀**：文件自洽、審稿人讀鍵覺得對、讀例示也覺得對，只有把兩者對起來才發現矛盾。三名審查者中兩名各自獨立指出同一處，第三名（文字視角）未觸及——這類矛盾要靠「拿例示回代鍵」的動作才浮現，不靠通讀。

**本案的下游後果**：仲裁器對第三類的溢出策略是「丟棄並計數」（無人可推回）。仲裁申請訊息被例示歸為第三類，於是仲裁器過載時申請被靜默丟棄，申請方永遠等不到回覆——設計層死鎖，且是由分類例示而非由任何一條判準引入的。

## 根因

| 層級 | 機制 |
|------|------|
| L1 例示的來源錯 | 例示應由鍵推導（拿候選事件問鍵、依答案歸類），實際是由來源實例的直覺搬運（在來源實例裡這些東西「感覺上」屬同一類）。兩個性質在來源實例恰好重合，外推後分離，例示跟著舊的重合走 |
| L2 例示與鍵無回代步驟 | 撰寫流程有「寫鍵」與「寫例示」，沒有「把每條例示代回鍵」。例示越具體、越像常識，越不會被回代——「webhook 當然是外部驅動」 |
| L3 讀者依例示不依鍵 | 分類表的消費者遇到具體事件時，先比對例示（快、具體）而非套用鍵（慢、要想）。例示一錯，鍵形同虛設；DOC-GPD-007 從讀者端描述同一機制（範例被讀為契約全集），本模式描述撰寫端如何把錯的範例寫進去 |

## 與相關模式的關係

| 模式 | 關係 |
|------|------|
| DOC-GPD-005 判準以類別名為鍵 | 那裡鍵選錯（綁名稱不綁性質）；本模式鍵正確，例示錯。兩者症狀相同（每一句自洽、失效無訊號），根因層級不同 |
| DOC-GPD-007 範例被讀為契約全集 | 那裡範例正確而讀者過度推論；本模式範例本身與鍵矛盾。L3 共用同一讀者行為，修法不同：007 補值域說明，本模式改例示 |
| 「正確的結論配上錯誤的理由」（同日對接材料歸納的第三個坑） | 同族：鍵正確、例示（作為鍵的具體化）錯，當下無症狀，失效發生在有人依例示推導下一步（本案：依例示決定溢出策略） |

## 解決方案

1. **逐條回代**：對分類表每個類別的每一條例示，寫出它對鍵的回答，答案與所在類別不符者移動或刪除。本案結果：webhook 送達跳、request/reply、對仲裁器的申請移入「等待型」；拉取式消費移入「自發型」；第三類收窄為「來源不等我方任何回覆」的推送。
2. **逐跳套用**：同一個事件在不同跳可屬不同類別（送達跳等待型、確認後的處理自發型），在表首明寫「逐跳套用」，避免讀者為一個事件找唯一類別。
3. **給類別語意名**：「第一／二／三類」的裸序數讓例示成為讀者唯一的辨識依據；改為「等待型／自發型／推送型」後，名稱本身就帶著鍵，讀者比對例示前先被名稱提醒。

## 預防措施

| 措施 | 落點 |
|------|------|
| 從單一實例外推通則的文件，審查時指定一名審查者用**外推目標場景**逐條套用（本案：三個後端場景），不只通讀 | parallel-evaluation 派發 prompt：外推類文件必含「以 N 個目標場景逐條套用」焦點 |
| 分類表的每條例示附一欄「對鍵的回答」，或至少在撰寫檢查清單加「例示已逐條回代鍵」 | document-writing-style 二次審查清單 |
| 類別命名帶鍵，不用裸序數 | methodology-writing 原則 |

## 行為模式分析

外推通則時，撰寫者對來源實例的判準有信心（它已被驗證過），對外推目標沒有實例可驗，於是把來源實例裡「一起出現」的性質當成「同一性質」搬過去。寫例示時腦中浮現的是來源實例的具體事物，例示因此描述來源實例的世界而非目標世界。矛盾要靠把目標世界的具體事物拿來問鍵才會出現，而撰寫者手上沒有那些事物——這是為什麼補救必須由持有目標場景的審查者做，撰寫者自審通常抓不到。
