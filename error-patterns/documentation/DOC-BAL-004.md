# DOC-BAL-004：設計規格依記憶寫框架 API，未對照專案鎖定版本

## 基本資訊

- **Pattern ID**: DOC-BAL-004
- **分類**: 文件（documentation）
- **來源版本**: v0.3.1
- **發現日期**: 2026-11-06
- **風險等級**: 中（規格階段零成本可攔，漏到實作階段才在編譯或測試時暴露，且下游測試設計、虛擬碼已依錯誤 API 撰寫）
- **影響範圍**: 任何在規格、介面定案、測試設計或虛擬碼中寫出第三方框架 API 名稱的文件

## 摘要

**規格撰寫者以記憶中的框架 API 寫介面定案，記憶對應的是某個舊版或通用版本，而專案鎖定的版本已移除或改名該 API。** 規格文件不經編譯，錯誤 API 在文字層完全合法，會原樣流入測試設計與實作策略，直到 Phase 3b 編譯才被發現，屆時上游三份產出都要回頭改。

## 症狀

- 規格或 Solution 出現框架 API 名稱（如狀態管理庫的取值屬性、套件回傳型別的欄位），但文件未標註依據版本
- 專案程式碼現行寫法使用另一個名稱，規格與現行程式碼並陳時兩者不一致
- 只有對照 lock 檔版本並查該版套件原始碼的審查者能發現，其餘視角（文字、品味、拆分）皆不會觸及

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 撰寫依據 | 規格撰寫者依框架通用知識寫 API，未讀 lock 檔版本 | 知識所對應的版本與專案鎖定版本可能不同 |
| 驗證機制 | 規格文件不經編譯、無型別檢查 | 不存在的 API 在文字層無任何錯誤訊號 |
| 下游傳遞 | 測試設計與虛擬碼直接引用規格的 API 名稱 | 錯誤沿 Phase 2、3a 擴散，修正成本隨階段累加 |

## 解決方案

1. 規格審查（多視角審查）至少一個視角明確負責「規格中出現的每個框架 API，對照 lock 檔版本的套件原始碼確認存在」
2. 確認方式用固定值：讀 lock 檔版本 → 在本機套件快取該版本目錄 grep API 名稱 → 命中數為 0 即不存在
3. 優先以專案現行程式碼的既有寫法為準；規格引入專案尚未使用過的 API 時，標註依據版本

## 預防措施

- 撰寫規格時，凡寫出框架 API，先在專案程式碼 grep 是否已有同類用法，沿用既有寫法
- 規格審查派發 Consistency 類視角時，檢查項列入「規格 API 與鎖定版本一致」
- 首次在專案引入的 API（例如第一次使用某種 provider 類別），規格中標註版本與出處

## 實例

一次 Phase 1 介面定案寫了狀態管理庫的「可空取值」屬性，該屬性在專案鎖定的主版本已移除（改由同名非可空屬性在 loading／error 時回 null）。五視角規格審查中只有負責跨文件一致性、且實際讀了 lock 檔的視角抓到；同一定案在另一視角中被當作正確前提引用。查證以套件快取目錄 grep 命中 0 次確認。
