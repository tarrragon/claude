# DOC-GPD-007: 介面文件只示範一種參數形式，讀者將範例讀為契約全集因而推論出不存在的限制

## 症狀

一支 CLI／API 的文件以單一具體範例示範某參數（`--content-file <path/to/content.md>`），讀者據此推論該參數的**值域就是範例的形狀**，於是在自身條件不滿足該形狀時得出「此功能對我不可用」的結論——而實際上參數接受更廣的值域，功能一直是可用的。

失效的不是文件的正確性：範例本身完全正確，執行它會成功。失效的是**讀者從一個正例反推出了一個並不存在的否定命題**。

**本案實例**：一支對 GitHub issue 附加觀測的工具，唯一參數形式是 `--content-file <path>`。兩個並行的 PM session 各自需要用它，兩者的角色都禁止寫入暫存目錄（hook 硬擋）。兩者**各自獨立**推得同一結論：

> 唯一介面是 `--content-file` → 需要一個我能建立的檔案 → 我沒有可寫的暫存路徑 → 這個功能對 PM 不可用。

實際上該工具的實作是 `Path(content_file).read_text()`，而 `/dev/stdin` 是實體路徑——`--content-file /dev/stdin` 配 heredoc 立即可用，且該用法**正是框架既有規則所指定的做法**（長文字以 heredoc 直傳 CLI、禁繞暫存目錄）。兩個 session 在遵守該規則的同時，誤判了它在這支 CLI 上有沒有可行的落地形式。

其中一個 session 因此把內容改寫進本地 ticket 並註明「限制未解時內容留在本票即可」，另一個則把它列為需要新增功能的介面缺陷開票——**兩種處置都建立在同一個不存在的限制上**。

**識別特徵**：

- 使用者／代理人回報「做不到」，理由是某參數的形式與自身條件不相容，而非該功能不存在
- 文件對該參數只有一種示範形式，且該形式恰好是最常見的那一種
- 實作對該參數的處理是通用的（`open()`／`read_text()`／`Path()`），沒有任何形式限制
- **兩個以上的獨立讀者得出相同的錯誤結論**——這排除了個別讀者能力問題，指向文件

## 根因

**範例的作用是示範，但讀者用它做界定。** 寫作者提供一個具體範例是為了讓抽象參數可執行；讀者在沒有其他資訊時，把那個範例當成參數的規格，因為文件沒有給出任何「還有別的形式」的訊號，而缺席在語法上沒有痕跡——讀者不會看到一個標記說「此處省略了其他合法形式」。

這與 `DOC-004`（CLI 命令推論幻覺）是**同一個機制的兩個方向**：讀者都在文件的留白處填補，`DOC-004` 填出了不存在的能力（幻覺），本則填出了不存在的限制（自我設限）。兩者的可見性差異極大——幻覺的命令一執行就報錯，自我設限則**永遠不會被執行，因此永遠不會被反證**，只會安靜地轉為「改用替代方案」或「開一張修不存在問題的票」。

**成本落點**：本則的代價不在文件，在下游。讀者不會回報「文件不清楚」，他會回報「這個功能對我不可用」，並帶著這個結論去做設計決策、開票、改寫流程。錯誤結論一旦進入 ticket 或規格，就取得了與事實同等的地位。

## 解決方案

1. **參數文件寫值域，不只寫範例**：`--content-file <path>` 的說明應寫明「任何可讀路徑，含 `/dev/stdin`」，而非只給一個 `path/to/content.md`。
2. **在遇阻的第一站放訊號**：`--help` 的參數說明比 references 文件更早被讀到——遇阻者的第一個動作是 `--help`，不是翻文件。訊號放在最遠的地方等於沒放。
3. **規則指出方向時，文件須給出該方向在本工具上的具體形式**：本案的框架規則已明文要求「長文字 heredoc 直傳 CLI」，但沒有任何地方說明這支 CLI 要怎麼做到。**規則與工具之間的那一跳，是讀者自己補的，而他補錯了。**
4. **考慮讓最自然的寫法也成立**：`--content-file -` 是慣例上的 stdin 標記；支援它比要求讀者想到 `/dev/stdin` 可靠。此為選配，但不支援時應記錄理由。

## 預防措施

| 時機 | 動作 |
|------|------|
| 為 CLI 參數寫文件或 `--help` 文字時 | 問「這個範例會讓讀者以為值域只有這麼大嗎？」是則補值域描述 |
| 收到「這個功能對我不可用」的回報時 | **先讀實作**再判斷。回報者給的是他的推論鏈，不是實作事實；本案兩次回報的推論鏈各自完整且都錯 |
| 同一個「做不到」結論由兩個以上獨立讀者得出時 | 視為文件缺陷的強訊號，不是讀者問題。獨立重現排除了個別能力因素 |
| 撰寫「因為 X 限制所以做不到」的 ticket 或決策記錄時 | 該限制須經實測，不得只有推論。**推論鏈完整不等於前提為真** |
| 例外 | 參數確實只接受受限值域時（如列舉值），單一範例加值域列舉即足夠，不需額外訊號 |

## 與相關模式的關係

- **`DOC-004`**（CLI 命令推論幻覺）：同機制反方向——讀者在文件留白處填補，該則填出不存在的能力、本則填出不存在的限制。關鍵差異在可見性：幻覺會被執行並立即報錯，自我設限不會被執行，因此不會被反證。
- **`DOC-GPD-004`**（標籤壓縮）：同屬「作者側成立、讀者側不成立」家族，但壓縮的失效是讀者知道自己不懂而去查證，本則的失效是讀者**以為自己懂了**並據以行動。

## 行為模式分析

寫文件的人知道參數接受任意路徑，範例只是為了讓讀者能複製貼上；讀者沒有那份知識，範例是他唯一的資訊來源。這個落差在作者側完全不可見——他讀自己的文件時，那個範例只是諸多可能中的一個。

本案的暴露路徑值得記：問題不是由審查發現，也不是由文件的讀者發現，而是由**第三方追問「那要怎麼處理」**而暴露。被追問的一方為了回答而去讀了實作，五分鐘內就推翻了兩個 session 共同持有的結論。**在此之前，兩個獨立的錯誤結論互相佐證，看起來像是已驗證的事實。**
