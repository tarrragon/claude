# DOC-BAL-001：規則只寫 Action 未寫 Consequence

## 基本資訊

- **Pattern ID**: DOC-BAL-001
- **分類**: 文件（documentation）
- **來源版本**: v0.2.1
- **發現日期**: 2026-07-31
- **風險等級**: 高（讀過該規則的人仍會違反，且違反時不覺得自己在違反）
- **影響範圍**: 任何以「預設應該做 X」「一律不做 Y」形式書寫的規則、慣例、風格指南

## 摘要

**規則寫了該怎麼做，沒寫不這樣做會失去什麼，讀者因此無從評估違反成本，把它讀成風格偏好而非硬約束。** 違反者不是沒讀過規則——他讀過、記得、也認同，只是在當下判斷「這次不照做應該沒差」，而規則本身沒有提供任何反駁該判斷的材料。

這與「讀者沒讀規則」是完全不同的失效模式，兩者的修法相反：後者要提高規則的曝光度（前移、加 hook 提醒），前者提高曝光度無效，因為讀者已經讀到了。

## 症狀

- 違反者能複述該規則的內容，且在事後回顧時同意它是對的
- 違反發生在「這次情況特殊」的判斷下，而非疏忽或不知情
- 規則文字形如「預設 X」「一律 Y」「優先 Z」，後接例外清單，但無任一句說明違反後果
- 加強提醒（前移位置、加粗、hook 注入）後違反率不變
- 事後追查時，違反者的理由是一個看似合理的局部收益（方便、一致、省一步），該收益與規則要防的損失不在同一個量級，但損失從未被寫出來供比較

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 規則的三明示只有 Action | 寫了「該怎麼做」與「例外何時適用」，缺「不這樣做會發生什麼」 | 讀者手上只有一半的決策材料，無法做成本比較 |
| 局部收益具體，全域損失抽象 | 違反能換到的好處當場可見；規則要防的損失是未來的、機率性的 | 未寫出的損失在心智帳本中權重為零，比較必然偏向違反 |
| 規則語氣像慣例 | 「預設不帶 X」讀起來與「命名一律小寫」同級 | 讀者把它歸類為風格偏好，而風格偏好本來就容許情境判斷 |
| 違反的後果延遲且不歸因 | 損失發生在下游、由他人承擔或延後顯現 | 違反者拿不到回饋，同一判斷會重複做出 |

核心是**規則要求讀者做取捨，卻只給了取捨的一邊**。

## 解決方案

每條約束型規則至少寫滿兩層，缺 Consequence 時補上：

| 層 | 內容 | 缺席時 |
|----|------|-------|
| Action | 該怎麼做、例外何時適用 | 讀者不知道要做什麼 |
| Consequence | 不這樣做會失去什麼，損失由誰承擔、何時顯現 | 讀者無從評估違反成本，退化為偏好 |
| Why | 為何有此約束（可選，Consequence 常已隱含） | 讀者無法判斷規則是否適用於新情境 |

Consequence 的寫法要求：

- 具體到可與局部收益比較（「唯讀型 agent 的產出必然遺失」而非「可能有問題」）
- 標明承擔者與時點（「PM 會誤判失聯而重派，付出全額重複成本」）
- 若違反的代價是改變了某個機制而非只是次優，明說它是機制變更（「帶 name 是實質的通道變更，不是命名偏好」）

## 預防措施

| 層級 | 措施 |
|------|------|
| 撰寫 | 寫下「預設 / 一律 / 優先」這類字眼時，緊接著問「違反會怎樣」，答不出來就代表這條可能不該是規則 |
| 審查 | 審規則文件時對每條約束檢查 Consequence 是否存在且可與收益比較，缺席即列為 finding |
| 修訂 | 發現有人違反已存在的規則時，先查該規則有無 Consequence 層，再考慮加強提醒——若缺 Consequence，加強提醒無效 |
| 判別 | 違反者能複述規則卻仍違反 → 本模式；違反者不知道規則存在 → 曝光度問題，兩者修法相反 |

## 驗證方式

- 對規則文件執行：每條含「預設 / 一律 / 優先 / 禁止」的句子，檢查同段或緊鄰段落是否有違反後果的描述
- 後果描述須通過「可比較性測試」：把它與違反能換到的好處並列，讀者能判斷孰輕孰重
- 修訂後回訪違反案例：同樣情境下，補上的 Consequence 是否足以推翻當時的判斷

## 實證案例：帶 name 派發（2026-07-31）

`agent-dispatch-template.md` 第 47 行已明訂「循序一次性任務、獨立分析/實作任務一律不帶 `name`」，並列出兩種例外（Agent Teams、同 Wave 3+ 同類型 ticket）。

PM 派兩位 `basil-writing-critic` 做文字品質審查——循序一次性唯讀任務，明確落在「一律不帶」那側——仍帶了 `name`，理由是「兩個代理人要分別定址比較方便」。

規則當時未寫的代價：背景 named agent 的最終回覆文字不送達主線程。唯讀型 agent 因此既不能落檔也無 final message，產出必然遺失。實際發生的是代理人完成七份檔案的審查（1 Critical + 16 Warning + 29 Info），報告零送達，PM 兩次催件無回應後誤判失聯並重派第二位，直到補寫 `SendMessage` 要求才取回。

**這條規則 PM 讀過**——它就在同一份模板、同一次派發前查閱的章節裡。缺的不是曝光度，是「方便定址」這個當場可見的收益，對面沒有任何可比較的東西。補上代價句後，同一句規則才有支撐判斷的重量。
