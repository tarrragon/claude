# DOC-008：同一文件內定義替換遺漏（局部替換）

## 症狀

修復文件中的定義不一致問題時，只修改了其中一處，同一文件的其他位置仍保留舊定義。
事後由多視角掃描（parallel-evaluation）發現遺漏。

**典型症狀**：

- 修改一個定義（如豁免條件描述）後，grep 掃描發現同一文件仍有舊字串殘留
- 並行評估的 Consistency 視角報告「不一致問題仍然存在」，但主 Ticket 已 complete

## 根因分析

### 問題行為

執行文件定義替換時，採用**精準定位（Find + Edit 特定行）**策略，而非**全局替換（global replace）**：

1. 問題分析階段用 grep 找到「最明顯」的一處
2. 只對那一行執行 Edit（old_string → new_string）
3. 沒有驗證同一文件是否還有其他相同字串

### 為何容易發生

- 文件長度超過 200 行時，grep 結果只顯示第一個 hit 就停止掃描
- 問題描述為「位置 X 有問題」→ 修改 X → 完成，未問「是否還有其他地方？」
- Edit 工具的 `replace_all` 參數預設為 false，不提醒是否有多個匹配

## 解決方案

### 修復步驟

1. 執行全局搜尋確認所有殘留位置：
   ```bash
   grep -n "舊定義文字" 目標文件.md
   ```
2. 逐一修復或使用 `replace_all: true` 執行一次性替換

### 預防措施

#### 原則：替換前後都要 grep

做任何定義替換時，強制執行：

```
1. 替換前：grep -n "舊字串" 文件 → 確認所有位置
2. 執行替換（replace_all: true 或逐一 Edit）
3. 替換後：grep -n "舊字串" 文件 → 確認 0 個結果
```

#### 使用 replace_all 的判斷標準

| 情境 | 建議 |
|------|------|
| 替換純文字定義（無上下文差異） | 使用 `replace_all: true` |
| 替換有細微上下文差異的文字 | 先 grep 確認所有位置，再逐一 Edit |
| 不確定是否有多處 | 先 grep，再決定策略 |

## 變體：驗收條件以位置界定範圍

**症狀**：驗收條件列出要改的位置（條文編號、章節名、表格列名），執行者照列表改完即回報完成；同一概念在列表以外的位置仍是舊寫法，被執行者明確判定為「票面範圍外」而保留。

**與主症狀的差異**：主症狀是執行者沒搜到其他位置；本變體是執行者搜到了，但驗收條件的列舉讓「沒列到的位置」讀起來像被排除在範圍外。替換前後的 grep 照做也擋不住，因為執行者已看到殘留，卻判定不屬於本次範圍。

**Why**：列舉位置的驗收條件同時傳達兩件事：「這些位置要改」，以及隱含的「其他位置不在範圍內」。概念替換真正的目標是這個概念在整份文件中不再以舊寫法出現，位置列舉只是撰寫驗收時已知的命中點，不代表全部。

**Consequence**：一次改寫要經過多輪才收斂，每輪各漏一批。殘留的舊寫法與新寫法並存，讀者無從分辨哪一個是現行規格。

**Action**：

| 角色 | 做法 |
|------|------|
| 撰寫驗收的人 | 概念替換的驗收以「全文 grep 舊字樣只剩歷史列」為主條件，位置列舉只作為已知命中點的參考，不作為範圍邊界。規劃期先 grep，把已知命中的檔案放進 where |
| 執行者 | 全文 grep 發現列舉以外的命中時：命中在 where 內的檔案，同一概念一律納入本次修改，並在 Solution 列出新增的位置；命中在 where 以外的檔案，停手回報命中清單，由 PM 擴充 where 後再改（`.claude/pm-rules/verification-framework.md`〈檢查 2 的 where 擴充程序〉）。語意不同的命中一律停手回報 |
| 驗收者 | 以舊字樣全文 grep 驗收，不以「列舉位置都已改」驗收 |

**觀測實例**：同一份規格文件的同一概念改寫連續兩輪各漏一處。第一輪的驗收只列條文編號範圍，其他條文的同一寫法沒被掃到；第二輪補改時，執行者回報一處同字樣殘留，並以「票面範圍外」為由保留。

## 防護

**檢查點**：修改文件定義後，執行 `grep -n "舊字串" 文件` 確認 0 個結果再關閉 Ticket。

**parallel-evaluation 角色**：Consistency 視角是此類問題的自動防護網，可以在 post-wave 掃描中發現遺漏點。
