# DOC-BAL-002：同檔案內的行為契約隨程式碼變更漂移

## 基本資訊

- **Pattern ID**: DOC-BAL-002
- **分類**: 文件（documentation）
- **來源版本**: v0.2.1
- **發現日期**: 2026-08-01
- **風險等級**: 高（讀者依契約推論行為而不讀實作，錯誤推論不會被任何機制攔截）
- **影響範圍**: 任何在程式碼旁以自然語言宣告行為的位置——模組 docstring 的「行為契約」段、函式 docstring 的回傳值與副作用說明、README 的功能清單、設定檔註解、API 文件字串

## 摘要

**改行為時沒有回頭改契約。程式碼有測試守著，契約沒有任何東西守著。**

這不是寫錯，是沒跟上。契約寫下的當刻是正確的，之後每一次行為變更都可能讓它偏離一點，而偏離不會觸發任何錯誤路徑——測試驗證的是程式碼行為，不是「文字描述是否仍符合該行為」。於是同一個檔案裡，程式碼持續被驗證，緊鄰它的散文持續腐化。

危險在於契約的讀者信任度高於一般註解。標著「行為契約」「回傳」「副作用」的段落被當成規格讀，讀者據此推論而不去讀實作。契約一旦落後，錯誤推論就有了權威來源。

**收斂與重寫會放大這個問題**：長篇 docstring 的漏述被大量細節稀釋，壓縮到一半篇幅後，缺的那個分支變得顯眼——但也可能在壓縮過程中被當成冗餘一併刪掉。

## 症狀

- docstring 描述的分支數少於實作的分支數，且少的通常是最近新增的那個
- 摘要行用的動詞與實作的判斷條件不是同一件事（描述「被重建」而實作判斷「非空」）
- 契約宣稱某路徑「靜默返回」，實際該路徑會寫日誌、送遙測或觸發回呼
- 文件說某缺口「另案追蹤」，而該案早已完成或早已被否決
- 全套測試綠燈，且新增測試也綠燈——測試從不斷言文字
- 漂移只在有人逐字比對契約與實作時才現形，通常發生在審查或重寫的場合
- **契約含「不會 X」「不可能 Y」的否定式保證，而某條分支正好會 X**（加重形態，見下）

## 根因

**程式碼與契約的變更偵測能力不對稱。**

| 載體 | 改壞時 | 沒跟上時 |
|------|-------|---------|
| 程式碼 | 測試紅燈 | 測試紅燈 |
| 契約（自然語言） | 無反應 | 無反應 |

程式碼有兩道防線（型別、測試），契約一道也沒有。所以「行為變更」與「契約更新」這兩個動作只有前者被強制執行，後者純粹依賴撰寫者當下記得。而變更行為時的注意力在「讓新行為正確」，不在「檢查散文是否仍成立」——後者要求主動離開當前任務去掃描一份看起來已經寫好的文字。

三個放大因素：

1. **契約與實作的距離造成假的安全感**。同一個檔案、相隔幾十行，看起來不可能失同步。但物理距離近不代表注意力會掃過去——改 `main()` 的人不會回頭讀檔頭。
2. **新增分支比修改分支更容易漏**。修改既有行為時，契約裡有對應句子可改；新增一個分支時，契約裡沒有任何東西提醒你它應該多一句。
3. **漏述的往往正是最該寫的那個**。新分支通常是為了處理某個剛發現的邊界情況（可觀測性、降級、告警），它的存在理由就是「讓某個狀態不再無跡可循」——契約漏了它，等於在文件層把該機制取消。

### 加重形態：契約宣告的是否定式保證，而非正面描述

**當落後的契約句是一個「不會發生 X」的保證，危害從「描述不準」升級為「宣告一條不存在的防線」。**

三個層面使否定式保證比正面描述危險：

| 層面 | 正面描述（「本函式回傳 X」） | 否定式保證（「本函式不會 X」） |
|------|---------------------------|------------------------------|
| 承重性 | 讀者據此預期行為，錯了就發現 | 呼叫端據此**省略防護**，錯了要到出事才發現 |
| 可驗證性 | 測一個輸入即可確認 | 需窮舉所有路徑才能確認，實務上沒人做 |
| 對閱讀行為的影響 | 不影響 | **提供停止閱讀的理由**——既然保證了，就不必讀那個分支 |

第三點是關鍵：否定式保證會主動阻止讀者去查證它。維護者讀到「不會把真正的命中漏放」，就不會往下讀那個 `else`。文件因此不只是落後，而是變成了讓人不去看真相的屏障。

**加重形態的典型長相**：函式 docstring 在「務實邊界」「已知限制」之類的段落末尾補一句總結性保證，語氣是安撫的（「誤判方向偏保守，不會⋯」）。那句總結通常寫於某個分支尚未存在時，或寫作者只考慮了主路徑。

**判別方式**：在契約中搜尋否定詞（不會、不可能、絕不、永遠不、一律不），對每一句問「哪一段程式碼保證這件事？」答不出具體位置，該保證就沒有實作根據。

## 解決方案

### 結構調整

**優先序一：讓契約可被機械檢查。** 把「有幾個分支」這類可枚舉的事實從散文改為結構化描述（列表、表格、常數名對照），使人與工具都能逐項比對實作。散文段落無法比對，逐條列出的分支可以。

**優先序二：把契約審查綁定到行為變更事件，而非靠記憶。** 任何新增或移除分支的變更，其驗收清單必須含一條「契約已同步」。綁在事件上才會被執行，寫成通則提醒則不會。

**優先序三：縮短契約的宣稱範圍。** 契約承諾越具體越容易過期。「零候選則靜默返回」是可過期的宣稱；「零候選的處置見 `handle_empty()`」則把細節留在唯一的來源。指標比複述耐久。

### 驗證方式

審查任何含行為契約的檔案時，執行一次逐項對照，且對照方向必須是**從實作到契約**而非反向：

1. 列出實作的所有分支（每個 `return`、每個 `raise`、每個提前退出）
2. 對每個分支，在契約中找到對應描述
3. 找不到者即為漏述——這是漂移的主要形態

反向掃描（讀契約找實作）會漏掉「實作多了一個分支」的情況，而那正是最常見的一種。

## 預防措施

- 新增任何提前退出或副作用時，同一次修改內更新契約，不留到之後
- 改摘要行的動詞前，確認它與實際的判斷條件是同一件事（描述狀態變化 vs 描述狀態本身是不同的宣稱）
- 收斂或重寫長 docstring 時，先列出實作的分支清單當作檢查表，避免把「該補的漏述」與「該刪的冗詞」混為一談
- 契約提到「另案追蹤」「後續處理」時附 ticket ID，並在該 ticket 完成時回頭改契約——沒有 ID 的延後宣稱無法被追回
- 審查者拿到「文件太長」的任務時，同時檢查是否有「文件太短」的部分：篇幅過剩通常伴隨覆蓋不足，兩者常同時存在
- **寫下任何否定式保證前，先指出保證它的那段程式碼**。指不出來就別寫——沒有實作根據的保證，比不寫更糟
- **新增分支時，回頭檢查既有的否定式保證是否仍成立**。新分支最容易違反的正是那些寫於它出現之前的「不會 X」
- 修不了行為時，**至少先修那句保證**：把「不會 X」改成「已知在 Y 條件下會 X（ticket 追蹤）」。錯誤的保證留著會持續阻止別人發現問題，而標註過的缺陷至少不再誤導

## 實證案例

### 事件：memory 稽核 hook 的契約在單一 campaign 內三度落後（0.2.1-W3-092 / W3-194 / W3-202）

同一組檔案在三張連續 ticket 中，每一輪都出現一次契約與行為不符，且每次由不同機制發現：

| 輪次 | 契約宣稱 | 實際行為 | 發現管道 |
|------|---------|---------|---------|
| 一 | 豁免範圍寫某缺口「封閉方式需獨立選型，另案追蹤」 | 該案已完成，缺口的處置已定 | 驗收時逐條核對驗收條件 |
| 二 | 摘要行寫「偵測目錄**被重建**」 | 實作判斷的是目錄**非空** | 多視角審查（文字品質視角） |
| 三 | 行為契約寫「零候選 -> **靜默返回**」 | 零候選會呼叫告警函式寫 warning 日誌 | 多視角審查（規格作者驗收自己的規格） |

第三次最能說明本模式的危險：那個 warning 是前一輪才新增的，存在理由正是「讓零候選不再與『目錄乾淨』無法區分」。契約把它描述成靜默，等於在文件層把該機制取消——讀契約的人會得出「這條路徑無跡可循」的結論，而那正是該機制已經解決的問題。

三次的共同點：全套測試在每一輪都是綠的，測試數在第三輪的重整前後完全相同。沒有任何一次是靠自動化機制發現的。

### 事件：命令守衛的抑制機制宣告了一條不存在的防線（0.2.1-W3-193）

同一個 campaign 的第四次發作，形態是加重版——落後的不是描述而是保證。

某 hook 的字面區段抑制函式，其 docstring 末尾寫著：

> 這些區段僅用於「抑制 DENY」，誤判方向偏保守（少抑制 → 維持 DENY），**不會把真正的裸 cd 漏放**。

實測兩個反例皆重現，兩者都讓真實命中被放行：

| 輸入 | 結果 |
|------|------|
| 引號內含 heredoc 標頭字面，換行後接真實的目錄切換命令 | 該命令被放行（阻擋機制被繞過） |
| 同樣字面，換行後接真實的原地編輯命令 | 該命中被漏放 |

根因兩層：heredoc 標頭掃描不知道自己身在引號內，故引號裡的字面被當成真標頭；找不到結束 delimiter 時抑制範圍**延伸至命令結尾**。後者是全函式抑制最激進的一處，而 docstring 宣告的正是它的反面。

**此例展示三個層面的危害如何同時發生**：該保證承重（呼叫端據此不再自行檢查）、不可驗證（要窮舉所有 heredoc 形態才能證偽）、且阻止閱讀（讀到「不會漏放」就沒有理由往下讀那個 `else`）。缺陷因此存活到有人為了別的目的重讀該函式才暴露。

處置為分離修正：行為修正需要重寫為單趟狀態機，成本高且風險獨立，故轉獨立 ticket；但**那句假保證在同一批改動內就先改掉**，換成明載已知漏放路徑與實測反例。理由是行為缺陷還在的期間，錯誤的保證會持續阻止別人發現它。

### 事後可機械檢查的訊號

- 同一提交同時新增了提前退出分支，而 docstring 的 diff 為零
- docstring 中列舉式的分支描述，其項數與實作的 `return` 數不等
- 契約含「另案追蹤」「後續處理」等延後宣稱，但無 ticket ID
- 摘要行的動詞描述狀態變化（被建立、被重建、被修改），而實作判斷的是狀態本身（存在、非空、長度大於零）
- 契約含否定詞（不會、不可能、絕不、永遠不、一律不），而該保證在程式碼中指不出對應的實作位置
- 否定式保證所在的函式，其分支數在該保證寫下之後增加過
