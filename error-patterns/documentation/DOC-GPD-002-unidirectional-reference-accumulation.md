# DOC-GPD-002: 資產間引用單向累積，既有資產出度隨時間下降且不自我暴露

### 症狀

同一領域內多個文件資產（skill、規則檔、方法論）彼此以名稱指名互相引用時，引用只會
單向累積：新資產指向既有資產，既有資產不指回。時間越久，早期建立的資產出度越低——
而早期資產往往正是使用者的入口。

實例（UX 設計族六個 skill，以名字指名同族成員的引用計數）：

| skill | 出度 | 入度 |
|-------|------|------|
| component-contract-design（新建） | 3 | 2 |
| foundation-design（前次修法已補反向路由） | 2 | 2 |
| ux-design-evaluation | 0 | 2 |
| dart-style-guardian | 0 | 1 |
| impeccable（外來 skill，不屬本框架引用網） | 0 | 0 |
| frontend-with-playwright（本體系可攜成員） | 0 | 0 |

六個裡有四個出度為零，其中兩個（`ux-design-evaluation`、`dart-style-guardian`）
仍有入度、能被同族其他成員導向；另兩個（`impeccable`、`frontend-with-playwright`）
出度入度皆零，只能靠 description 的觸發詞被載入——使用者若不知道存在，沒有任何
路徑會帶他過去。兩個孤立節點性質不同：`impeccable` 外來且宣告獨立版本體系，孤立
屬正常；`frontend-with-playwright` 是本體系可攜成員（`category: frontend-engineering`），
孤立是缺陷。

### 根因

**行為模式**：新資產的作者在撰寫當下知道自己依賴哪些既有資產，會主動補上指向它們
的引用；但既有資產的作者早已交付，不會在新資產出現後自動回頭補上指向新資產的引用，
除非有人專門去做這件事。

三層原因：

1. **時序不對稱**：引用只在資產「被建立」的那個時間點被主動撰寫。新資產建立時舊
   資產已存在，作者能查到並引用；反向的引用需要在新資產建立**之後**由某個流程觸發
   既有資產的修改，而預設流程不含這一步。
2. **測試路徑偏誤**：作者驗證新資產的路由完整性時，一律從新資產出發（讀者是否能
   從這裡找到我依賴的東西），看到的路徑全部暢通。從既有資產出發測試（讀者是否能
   從這裡找到後續新增的資產）不在作者的驗證動作清單裡，因為那條路徑不是他正在寫
   的東西。
3. **入度掩蓋出度缺陷**：只查族內互引時，「能被找到」（入度非零）與「連通）」
   容易被混為一談。入度非零只代表存量讀者路由不斷鏈，不代表新讀者從既有資產出發
   時能發現新資產——兩者是引用圖上獨立的兩個方向，需分別查驗才會顯性化。

### 影響範圍

| 影響 | 說明 |
|------|------|
| 缺口不自我暴露 | 作者從新資產出發測試路由，看到的都是通的，沒有訊號提示反向缺失 |
| 早期入口首當其衝 | 使用者最常先接觸的往往是早期建立、族內功能較泛用的資產，這批資產的出度最先落後 |
| 跨階段工作漏做整塊 | 使用者做完前一階段工作（如畫面級狀態設計）後，若既有資產沒有指向下一階段資產的路由，後續工作會被誤判為「已完成」而整塊漏做 |
| 隨資產數量非線性擴大 | 每新增一個資產都對既有全部資產產生一次潛在反向缺口，缺口數隨資產數增長 |

### 解決方案

| 步驟 | 動作 | 驗證方式 |
|------|------|---------|
| 1 | 列出目標領域內以名稱指名互相引用的全部資產 | 逐檔 `grep` 資產名稱，建出度／入度對照表 |
| 2 | 找出入度非零但出度為零的資產（只有入度） | 對照表中出度欄為零、入度欄非零者 |
| 3 | 找出出度入度皆零的資產（完全孤立） | 對照表中兩欄皆零者；區分是否為外來資產（版本體系獨立、license 不同） |
| 4 | 對每個「只有入度」的既有資產，補一處指向新資產的反向路由，附觸發時機 | 反向路由句需回答「使用者做完什麼事之後該讀這裡」，非泛稱的相關連結 |
| 5 | 對本體系內完全孤立的資產，另評估接線（非本次新增資產的直接上下游時延後，但須記錄） | 記於待辦或另開 issue，不可默認「之後有人會發現」 |
| 6 | 新增資產合入前，把步驟 1-2 併入檢查項 | 新增資產的驗收清單加一條：既有依賴對象是否已補反向路由 |

### 預防措施

| 措施 | 說明 |
|------|------|
| 新增資產時強制查既有依賴對象的出度 | 建新資產引用既有資產時，同一動作內检查該既有資產是否已指回；未指回即當場補，不留待事後 |
| 定期以「入度非零、出度為零」為篩選條件掃描族群 | 單看引用是否存在不夠，需分別統計方向；掃描頻率隨族群成長速度調整 |
| 區分孤立節點的性質再決定是否處置 | 外來資產（獨立版本體系、不同 license）孤立通常無需處置；本體系可攜成員孤立才是缺陷 |
| 反向路由寫觸發時機而非泛稱連結 | 「相關：X skill」不會被讀到；「做完 A 之後，B 由 X 承接」才會在正確時機被看到 |

### 變體：修正單向接線的那次修法本身只補一端（2026-09-08）

主案的兩端分屬不同時期、不同作者，時序不對稱是根因。本變體的兩端在**同一份文件內、
同一次編輯範圍內、由同一人處理**，時序不對稱不成立，缺口仍以相同形狀出現。

**實例**：一份元件庫規格新增一節「定位提示的容器執行約定」，該節引言宣稱三個元件條目
「以某句措辭路由至本節」，而那三個條目當時都沒有回指句——單向。審查指出後的修法補上了
三個條目的回指句，卻**未同步引言的措辭**（引言仍以原統稱描述，與三處實際寫法不符）；
同一次修法另新增兩處接線，兩處各自又只做了一邊（引用的來源列不涵蓋該路徑；被觸發狀態
變更的那個容器條目未回指觸發方）。一次針對單邊接線的修正，修好一處、留下一處、新增兩處。

**額外根因（主案三層之外）**：修法的注意力錨定在審查報告指出的那一端。報告寫「A 未回指
B」，執行者補 A 的回指句即視為閉合，而 B 側描述 A 的措辭是否仍準確，不在被指出的範圍內；
新增接線時同理——寫下「X 時做 Y」的那一格是作者當下的焦點，Y 所在的條目是否也記載了這條
由 X 觸發的邊，不在焦點內。

**額外處置（主案六步之外）**：接線類修改的自檢改為**成對檢查**——對每一處新增或修改的
跨章節引用，同時開啟兩端，確認兩側措辭互相對應（被指向端寫的回指句，與指向端描述它的
措辭，是否指同一件事）。只檢查自己剛寫的那一端，缺口必然重現；這是本變體與主案共用的
不變式，差別只在主案的另一端要跨檔案找、本變體的另一端就在同一份文件裡。
