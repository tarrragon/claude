# DOC-V1-001: 位置編號引用隨目標文件演進靜默失效

**類別**: documentation
**嚴重度**: 中
**發現日期**: 2026-06-12
**相關 Ticket**: 1.0.0-W8-011（檢視 blog skill 回流時發現）

---

## 症狀

引用方以「位置編號」指向目標文件的內部結構（「第三原則」「見 Stage 3」「如第 4 點」），目標文件改版後該位置不存在或承載不同內容，引用句字面完好、解析不報錯，讀者被靜默導向錯誤或不存在的內容。

**本案實例**：`ask_user_question_reminders.py` 的 checkpoint 提示引用「writing-documents.md 第三原則」，該檔（英文結構）無此錨點——`git show HEAD` grep 計數為 0，引用自寫入起即懸空，每次 ticket complete 都對 PM 顯示一次無效指引，無任何機制告警。

**識別特徵**：

- 引用句含「第 N 原則」「第 N 點」「Stage N」「步驟 N」等位置詞且目標是活文件（會演進的規則 / 方法論 / skill reference）
- broken-link 掃描器不報錯（路徑有效，失效的是文件內定位）
- 引用方與目標文件由不同維護流程更新（hook 文字 vs skill 內容），無同步觸發點

## 根因

位置編號是結構排列的衍生值（derivation），不是穩定事實：目標文件插入、刪除、重排任一單位，後續編號全部位移。比 broken link 更難偵測——連結斷掉會報錯，編號錯位會成功解析到錯的東西（misdirected 優於 broken 的偵測難度）。引用寫入當下編號正確，失效發生在目標文件後續任何一次改版，時間差使作者無從自查。

## 解決方案

1. 引用錨點改用**語意標題**：「見『Indexing by document type』Worklog 段」而非「第三原則」——語意標題在重排後仍可 grep 定位，錯了會明顯找不到（fail loud）
2. 目標文件的結構單位標題承載核心意義（「Stage 3：核心問題」），編號僅作排序前綴；引用一律取語意半邊
3. 修復既有引用時順手驗證目標錨點真實存在（`grep "<語意錨>" <target>`）

## 預防措施

| 時機 | 動作 |
|------|------|
| 寫入跨文件引用（hook 提示文字、規則路由、ticket 模板）時 | 錨點用語意標題；寫完 grep 目標文件確認錨點存在 |
| 重排活文件結構的 commit | 全 repo 掃位置編號式引用：`rg "第[一二三四五六七八九十0-9]+(原則|點|條|章)|Stage [0-9]|步驟 [0-9]" .claude/` 比對受影響引用 |
| 例外 | 發布方凍結的編號（RFC 段號、法條、quality-baseline 規則編號這類「編號即 API、hooks 依賴的穩定錨點」）是 fact 可引用——判準為目標編號是否有凍結承諾 |

## 第二實例：被命名端的同型失效（2026-08-18）

前述本案實例為**引用端**（引用方以位置編號指向他人）。同一根因在**被命名端**同樣成立：文件為自身結構單位取位置編號式標題時，日後鄰居增減會使該標題語意錯位，而非引用方失效。

**實例**：`tool-output-trust-rules.md` 規則 6 之後新增一則衍生條文，初版標題為「衍生情境（第三例）」。「第三」是「規則 5、6 已有兩例」的 derivation——後續任一次規則新增或重排，標題字面完好、grep 仍命中，但「第三」所指已非原本那兩例的延伸。Layer 2 審查（`basil-writing-critic`）攔下，改語意標題「衍生情境：prompt 與正本衝突」。

**與引用端的差異**：引用端失效由目標文件改版觸發（作者無從自查）；被命名端失效由自身檔案後續編輯觸發（同一維護者可見，但編輯當下注意力在新增內容，不會回頭檢視既有標題的相對語意）。兩者防護一致——標題與引用皆取語意半邊，位置編號僅作排序前綴。

**Action**：為新結構單位命名時，問「這個標題在鄰居增減後是否仍指同一件事」；答否即含 derivation，改語意命名。

## 第三實例：URL fragment 與標題文字的可偵測性落差（2026-09-08）

前兩例聚焦「位置編號」；本例是同一根因的另一種載體——**跨檔引用他人章節時，錨點本身的兩種寫法**，何者失效可被偵測。

**兩種形態的失效行為對照**：

| 錨點形態 | 目標標題被改時的行為 | 可偵測性 |
|---------|-------------------|---------|
| URL fragment（如 `file.md#port-回饋契約`） | 不報錯、不留痕跡，只是跳不到 | 靜默；anchor 生成規則由渲染器決定，各消費端不同（GitHub／本地 markdown 渲染器／純文字閱讀各一套），同一引用可能一處還能用、另一處已壞 |
| 標題文字（引用「Port 回饋契約」這串字） | 引用點仍在，指向的字串不再存在 | `rg -F "<標題文字>"` 找得到全部引用點 |

**關鍵差異是可偵測性，不是穩定性**：兩種形態都會因標題改動而失效——差別在標題文字失效可被 `rg -F` 機械搜出，fragment 失效靜默且因消費端而異。把這點寫成「fragment 比較脆弱」會失準：fragment 不是比較容易壞，是**壞掉時沒有人會知道**。

**與前兩例的關係**：位置編號綁的是序位（結構排列的衍生值），fragment 綁的是渲染器的 anchor 演算法（另一種衍生值，且演算法本身跨消費端不一致）；標題文字是穩定事實本身，不是衍生值——與前兩例「改用語意標題」的解決方案同源，本例進一步指出「語意標題」仍有兩種寫法（fragment vs 純文字），只有後者具備機械可偵測性。

**實例**：一次交接（2026-09-08）在 `clean-architecture-implementation-methodology.md` 新增「## Port 回饋契約」章節（commit `8db1f6d4`），執行者交接下游三處引用時提出此判準並建議只寫標題文字（非 `#port-回饋契約` fragment）；後續任務採納為約束並據此執行三處引用。

**Action**：跨檔引用他人文件的章節時，寫該章節的標題文字，不寫 URL fragment；既有 fragment 引用不強制回溯修改，但新增引用一律取標題文字。

## 與相關模式的關係

- **DOC-GPD-003**（敘述中實例化可變計數，集合增減一員即全量失效）：同一根因的另一方向——本案是排列的衍生值（位置編號），DOC-GPD-003 是大小的衍生值（計數）；兩者防護原則相同（引用改用語意標題／權威名稱，不寫死衍生值本身）。
- **規則落點**：`.claude/references/reference-stability-rules.md` 規則 10「可變計數不實例化」——由 DOC-GPD-003 固化，與本案同屬「衍生值不得實例化」家族，判準問句與例外表可相互對照（本案的「發布方凍結的編號」對應規則 10 的「凍結承諾的數字」）。

## 行為模式分析

寫引用的當下，位置編號比語意標題「更省字」且當下正確，作者無從感知未來失效；目標文件改版者看不到散落各處的引用方。失效是雙盲的——防護只能放在寫入端（語意錨點慣例）與重排端（編號引用掃描），不能依賴讀者發現。本案由 blog 回流的 `reference-by-semantic-title-not-number` 原則在檢視時對照出來，skill 原則與本 error-pattern 互為通用規範與本框架實證案例。
