# DOC-GPD-005: 判準以類別名為鍵，類別後來獲得性質不同的新成員，新成員繼承舊裁決而被誤放行

## 症狀

一條分類判準寫成「類別 X → 裁決 Y」。後來 X 這個類別獲得新成員，而新成員不具備當初讓 Y 成立的那個性質。判準仍以類別名匹配，仍套用 Y。

**沒有任何一步會出錯**：判準文字完好、範例仍然正確、每一次套用都符合字面、grep 不報錯。錯的只有落在新成員上的那些裁決，而它們與正確裁決在形式上無法區分。

## 根因

| 層級 | 機制 |
|------|------|
| L1 鍵選錯 | 判準綁的是類別的**名稱**，而裁決依據的是該類別成員當時共有的**性質**。名稱穩定而外延會變，兩者在寫下的當刻恰好重合 |
| L2 繼承無關卡 | 新成員加入類別時，沒有任何一步會問「它是否具備當初讓該裁決成立的性質」。加入的動作只需要符合命名慣例 |
| L3 失效無訊號 | 與計數過期不同，這裡沒有數字會變錯。判準的每一句都仍然自洽，因此既沒有壞掉的東西可以被發現，也沒有可以 grep 的字面 |

## 案例

一條引用規範以識別符類型分類，列出「框架 error-pattern ID → 可在框架文件引用」，理由記為「框架內部分類」。該裁決在寫下時成立：當時的 error-pattern 編號都已隨同步送達每個 consumer，引用必定可解析。

後來編號體系新增了 consumer 分域形式。這些編號在命名上完全符合「框架 error-pattern ID」，但其中一部分是某個 consumer 本地剛建、尚未推上共用通道的——引用它們會在其他 consumer 手上成為懸空引用。

判準對此無鑑別力：新成員名字對得上，於是繼承「可引用」的裁決。修法是把鍵從類別名換成性質（是否已到達共用通道），原本一列拆為兩列。

**缺口存在期間沒有任何訊號**。它由跨 consumer 協作中的另一方在寫入引用時察覺，不是由守衛、測試或審查發現的。

## 與相關模式的關係

| 模式 | 失效對象 | 是否可被發現 |
|------|---------|------------|
| DOC-GPD-003（敘述中實例化可變計數） | 數字 | 是——集合一變，所有帶數字的敘述同時變錯，grep 找得到每一處 |
| 本模式 | 裁決 | 否——判準文字不變且始終自洽，錯的只有落在新成員上的結果 |

兩者同源於「集合會演進」，但 DOC-GPD-003 的損害會自我暴露，本模式不會。同一次集合擴充可能同時觸發兩者：計數變錯（看得見）與判準失準（看不見）。

## 防護

**Why**：判準的正確性來自成員的性質，不來自成員的名稱。以名稱為鍵時，判準在類別外延改變的那一刻就與其理由脫鉤，而脫鉤本身不產生任何可觀測的變化。

**Consequence**：錯誤裁決會被當成合規結果通過，且通過的紀錄看起來與真正合規的紀錄相同。發現只能靠外部——某個實際受害者在下游撞到。等到那時，依該判準做出的決定已經累積了一段時間。

**Action**：

| 時機 | 做法 |
|------|------|
| 寫下分類判準時 | 裁決欄同時寫明**理由所依據的性質**，不只寫類別名。「類別 X → Y（因為 X 的成員都具備 P）」比「類別 X → Y」多一個可被檢查的錨點 |
| 類別新增成員時 | 回頭問每一條以該類別為鍵的判準：新成員是否具備 P。這一問要在新增成員的流程裡，不能等到判準被套用時 |
| 判準已存在而不確定是否脫鉤 | 列舉該類別的當前成員，逐一驗證裁決對每一個都成立。找不出反例才算通過；只確認「判準文字沒改」不構成驗證 |
| 修法時 | 把鍵換成性質而非補例外。補例外會讓下一批新成員再次落入同一個縫 |

**判別問句**：這條判準是靠「它叫什麼」還是靠「它是什麼」做出裁決的？
