# CQ-BAL-002: 單一 expected_agent 比對假設與專案多代理人依領域分工架構衝突，遷移前未量測即假警告率壓倒真訊號

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 首次發現 | 2026-09-02 |
| 來源版本 | v0.2.1 |
| 適用範圍 | 任何「比對單一預期值判定是否正確」的檢查邏輯，套用於實際上採多代理人／多角色依領域分工的專案 |
| 偵測成本 | 中（需對既有語料全量或抽樣執行檢查邏輯，統計警告率並人工核對成因，非單靠讀程式碼可判斷） |

## 摘要

**一段檢查邏輯的判準假設（「每個對象都該符合唯一預期值」）若與其套用對象的
實際結構（多角色分工）不一致，遷移或啟用該檢查時若未先對真實語料量測，
會在毫無察覺的情況下讓假警告率壓倒真訊號，使檢查對使用者而言等同雜訊，
即使程式碼本身邏輯正確、測試全綠。**

危害不在於邏輯有 bug（判準本身按其設計正確執行），而在於判準的前提假設
與部署環境不符——這類缺陷不會被單元測試發現（單元測試通常也依同一組
假設撰寫），只有對真實資料量測警告率／假警告比例才會現形。

## 症狀

- 檢查邏輯本身邏輯正確、測試通過，但實際啟用後產生的警告量遠超預期
- 抽樣檢視警告內容，發現大多數「違規」其實是系統性的、有意的例外（非
  隨機雜訊），指向判準假設與實際結構脫節而非個別誤用
- 若此類檢查此前因其他原因（如觸發模型失配）從未在真實環境執行過，此
  症狀不會在既有紀錄中出現任何痕跡——量測是唯一能揭露此問題的手段

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 判準設計時的隱含假設 | 「每個對象都該符合唯一預期值」（如：每張任務都該指派給同一個負責人） | 隱含假設在設計文件或程式碼註解中未必顯式標註，容易在後續遷移/複用時被忽略 |
| 部署環境的實際結構 | 依領域/角色分工，多個負責人並存且各自正確 | 與判準假設直接衝突：非唯一值本身就是正確狀態，而非需要修正的偏差 |
| 遷移動作缺乏對真實語料的量測步驟 | 僅依賴程式碼審查與單元測試判斷「邏輯正確即可遷移」 | 邏輯正確與「對部署環境有效」是兩個獨立命題，前者成立不保證後者 |
| 若此前從未在真實環境執行過 | 觸發模型失配等原因可能使一段檢查邏輯長期存在於程式碼庫但實際零執行 | 該判準的缺陷從未真正曝光，遷移或修復觸發問題時若直接原樣啟用，等同把一個從未驗證過的假設直接推上生產路徑 |

## 最小重現

```python
# 判準：expected_agent 唯一，實際值不符即警告
def validate_who_field(ticket, expected_agent):
    current = ticket["who"]["current"]
    if current != expected_agent:
        return f"who.current = '{current}' 不符 '{expected_agent}'"
    return None
```

## 案例：ANA-created ticket metadata 驗證遷移（2026-09-02）

`ana-ticket-metadata-validation-hook.py` 因註冊事件（PostToolUse+Write）與
ticket 檔案的實際寫入管道（CLI/Bash subprocess）不匹配，從未對真實 ticket
執行過驗證（另一張分析票的結論）。將其三項驗證邏輯遷移至 `ticket create`
CLI 內部呼叫時，若僅依「程式碼邏輯正確、單元測試通過」為遷移依據，會把
一個從未在真實環境驗證過的判準直接送上每一次建票的關鍵路徑。獨立對全庫
1410 個既有 ticket 執行該邏輯量測後，才發現 who 欄位檢查的 744 筆警告中
95.8% 命中框架基礎設施路徑（`.claude/`），且抽樣核對顯示這批全數為專案
既有的多代理人分工正確指派，非真實漂移——若未量測直接遷移，會使每一次
建立框架範疇的實作 ticket 都產生一則假警告，淹沒任何真正的訊號。

## 防護

| 時機 | 動作 |
|------|------|
| 遷移/啟用一段長期未在真實環境執行過的檢查邏輯前 | 對真實語料（全量或代表性抽樣）執行該邏輯，統計警告率，而非僅以「程式碼審查通過」為遷移依據 |
| 檢查邏輯的判準涉及「比對單一預期值」時 | 明確自問：部署環境是否存在多角色/多分工並存的合法情況？若是，判準需相應調整（如依領域範疇排除，而非全域套用） |
| 統計出的警告量高於預期時 | 抽樣核對警告內容的實際成因，區分「真實違規」與「判準假設與環境不符」兩種可能，不預設警告量大即代表問題嚴重 |
| 檢查邏輯此前從未在真實環境執行過（如觸發模型失配） | 視為「從未驗證過的假設」，遷移時的量測步驟不可省略，不可僅因程式碼本身邏輯正確就假設其對真實資料同樣有效 |
