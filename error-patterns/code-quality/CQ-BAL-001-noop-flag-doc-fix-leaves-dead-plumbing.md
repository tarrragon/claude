# CQ-BAL-001: 宣告旗標為無作用時只改文案，未刪承載它的死傳遞鏈

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 中 |
| 發現時機 | 一次「文案誠實化」變更的事後審查，審查者在未被問到的維度上命中 |
| 發現日期 | 2026-08-18 |

## 症狀

- 某旗標／參數被判定為無作用，處置為修改其使用者可見說明（help 文字、文件）使之如實描述
- 變更後說明正確、測試通過、使用者不再被誤導——表面上問題已解決
- 但翻進程式碼仍會困惑：該旗標的值依然被讀取、傳遞、進入函式簽章，只是下游從不使用
- 因此形成新的兩份矛盾事實來源：**說明宣稱「無行為差異」，函式簽章宣稱「我依此參數決定行為」**
- 諷刺的是，這類變更的起因往往正是上一次兩份事實來源漂移

## 根因

**風險判斷對象錯位**是本模式的核心：維護者傾向保留 plumbing 是因為「刪東西有風險」，但這裡的風險評估對象搞錯了。

| 對象 | 刪除的風險 | 應否保留 |
|------|-----------|---------|
| argparse 旗標定義 | 高——既有呼叫端帶此旗標會變成參數錯誤 | 保留（Never break userspace） |
| 內部參數傳遞與死分支 | 零——無任何外部呼叫端依賴內部簽章 | 刪除 |

把兩者當成同一件事，就會為了保護前者而一併保留後者。**留 argparse 定義、刪內部傳遞，是唯一自洽的組合。**

這個錯位的成因是「這個旗標沒作用」有兩個承載面：面向使用者的說明，與面向維護者的程式結構。修正時容易只處理前者，因為問題是從前者被發現的（讀 help 發現不符），且前者改動成本低、風險低。但無作用的來源不在說明，在傳遞鏈：`register` 讀取旗標 → `execute` 取值 → 傳入下游函式 → 下游收下後不使用。說明只是這條鏈的末端描述。改說明等於在鏈的末端貼一張正確的標籤，鏈本身仍在。

## 解決方案

宣告某旗標為無作用時，兩步依序執行，順序是實質的：

1. **先刪死傳遞鏈**：移除下游不使用的參數、移除兩分支內容相同的條件判斷。argparse 定義保留。
2. **再改說明文字**：此時說明與程式結構已一致，改動不會再產生新的矛盾對。文案應為無時間性的事實陳述加下一步指引（「無作用旗標：預設即 X；如需 Y 請用 Z」），避免「暫時保留」「目前無差異」這類隱含未來變更卻無 trigger 的措辭。

## 預防措施

| 時機 | 檢查 |
|------|------|
| 判定某旗標為 no-op 時 | 追一次完整傳遞鏈：`register` → `execute` → 下游函式，確認值在哪裡停止被使用，該點之後全是死 plumbing |
| 撰寫「文案誠實化」類變更 | 問「改完之後，讀程式碼的人會不會得到與讀說明不同的結論」；會，則變更未完成 |
| 審查此類變更 | 不以「說明現在正確了」為驗收；驗收條件應包含程式結構與說明的一致性 |
| 保留任何無作用結構時 | 區分外部契約（保留）與內部實作（刪除），不以「刪東西有風險」一概而論 |

## 案例

一組 CLI 子命令的某旗標被判定為無作用——預設行為已涵蓋該旗標宣稱的效果。處置為修改五個子命令的 help 文字，改為如實描述「與預設行為無差異」，並補上測試與文件說明。變更本身正確，未破壞任何既有呼叫。

事後審查發現說謊的來源沒改：五處的旗標值仍從 `register` 一路傳到 `_gather_tickets`，其中四處在函式簽章收下後函式體完全不引用，第五處的 `elif <旗標>:` 與 `else:` 兩個分支逐字相同——一個不是分支的分支。

審查者的判語指出了這個模式最尖銳的一面：現在 help 說「無行為差異」、函式簽章說「我依此參數決定範圍」，而這次變更存在的原因，正是上一次兩份事實來源漂移。修法零風險——argparse 定義留著（外部契約不破），刪五個死參數與一個死分支即可。
