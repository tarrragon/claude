# PROC-LLM-001: 放大故障後果的變更早於偵測合入，或偵測器沒跟著目標換根

## 基本資訊

| 項目 | 內容 |
|------|------|
| 風險等級 | 高 |
| 分類 | process（變更排序與偵測覆蓋） |
| 來源版本 | 3.5.0 |
| 首次觀測 | 2026-11-12 |
| 適用範圍 | 任何會讓既有缺陷的後果變重的變更（改寫入目標到共用或正式位置、放寬權限、移除隔離層），且該缺陷有偵測器在看守 |

## 摘要

**某些變更本身正確，卻會放大既有缺陷的後果：例如把日誌根從隔離位置改到正式共用位置，原本只污染暫存區的測試洩漏，改後直接污染正式資料。這類變更必須排在偵測就位之後，或與偵測在同一次合併中進入；偵測器的觀測位置也要跟著目標一起換，否則合併後會有一段時間缺陷照常發生、後果更重、而偵測器看著舊位置回報一切正常。**

## 症狀

- 變更合入後，正式位置出現測試或其他非預期來源的資料，事後翻閱才發現
- 偵測器在同一段期間全綠：它看的是變更前的位置，那裡已不再有人寫入
- 審查時兩張票各自正確：「改位置」的票測試全綠，「改偵測器」的票測試全綠，問題只存在於兩者合入的先後之間

## 根因

| 環節 | 事實 | 後果 |
|------|------|------|
| 後果與機率分離 | 缺陷的發生機率不變，變更只改變發生後的影響範圍 | 變更本身的測試看不出風險，風險在缺陷再次發生時才兌現 |
| 偵測器綁定位置 | 偵測器以變更前的路徑、根目錄或資源名稱為觀測對象 | 目標換位置後，偵測器的觀測範圍變成空集合，結果恆為綠 |
| 拆票與排序 | 「改目標」與「改偵測」常因範圍控制被拆成兩票，各自排程 | 兩票合入的時間差就是無偵測、後果加重的空窗 |
| 綠燈的解讀 | 偵測器全綠被讀成「沒有缺陷」 | 實際是「偵測器看不到」，兩者在輸出上同形 |

## 解決方案

1. 識別放大型變更：問「這個變更合入後，若既有的某類缺陷再發生一次，後果是否比變更前更重？」是則屬本類。
2. 列出看守該缺陷的偵測器，逐一確認它們的觀測位置是否依賴變更前的目標。
3. 排序：偵測器的修改先合入，或與放大型變更同一次合併。拆票時以 blockedBy 綁定順序，不靠口頭約定。
4. 偵測器在換根期間同時看新舊兩處，直到確認舊位置不再有寫入者。
5. 附正向對照：在新位置刻意製造一次缺陷，斷言偵測器判紅。只斷言「偵測器在正常情況下綠」不能證明它看得到新位置。

## 預防措施

| 時機 | 檢查 |
|------|------|
| 規劃改寫入目標、移除隔離層、放寬權限 | 是否會放大既有缺陷的後果？有哪些偵測器在看守？ |
| 拆票 | 改目標與改偵測若分屬兩票，以依賴關係固定合入順序；或明確選擇同一次合併 |
| 驗收放大型變更 | 偵測器對新位置有正向對照（刻意洩漏判紅） |
| 驗收偵測器修改 | 偵測器的觀測位置與目標的新位置一致，不只是測試綠 |

## 案例

一個框架把 hook 日誌根從各 worktree 改為集中寫到主 repo 的共用根。既有已知缺陷是部分子行程測試未繼承隔離環境變數，會把紀錄寫進真實日誌目錄；改根前，洩漏只落在該 worktree，改根後會直接落進主 repo 的正式日誌，並汙染其他流程依賴的 liveness 證據。

規劃時先讓「快照比對式洩漏哨兵」作為獨立票先合入，改根票以依賴關係排在其後。哨兵合入後才發現它以測試檔所在 checkout 為觀測根；改根後洩漏會寫到主 repo，哨兵看不到。因此改根票追加規格：哨兵同時對測試檔所在根與共用根拍快照，且必須與改根在同一次合併中進入，並附「在 worktree 內刻意洩漏到主 repo，哨兵判紅」的正向對照。曾提出的「哨兵雙根另拆一票」方案因會留下空窗而不採用。
