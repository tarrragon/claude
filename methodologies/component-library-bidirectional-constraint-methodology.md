# 元件庫雙向約束方法論

## 核心概念

元件庫是設計端與工程端之間的雙向約束：設計端從元件庫拼組頁面（先設計元件，再組合為複合元件與整體空間配置），工程端只從元件庫取件（禁止散落自製元件）。Design token（顏色、尺寸、間距）只是參數共識；元件庫才是成果約束——相同行為有相同反應、相同外觀承載相同語意，頁面體現一致的產品風格，使用者看到相同元件即能理解功能，減少引導需求。

規範文件本身無法約束成果：AI agent 無跨 session 記憶，散落自製元件是「只靠文件約束」的高度可重現結果（agent 每 session 冷啟動，文件遵循率隨 context 壓力衰減）（實證：某 Flutter 專案 token 層收斂後，presentation 層仍累積約百處原生元件直用與 43 處手工邊框（權威清點以各專案 spec 禁用對照表的存量統計欄位為準，無此欄位者先補）；共用同一 design token 系統的 Chrome Extension 端更甚——HTML/CSS 無原生元件邊界，任意標籤加樣式即可成件，內嵌 CSS 規則與 design-system 外樣式宣告散落速度更快）。約束必須由「SPEC 階段元件庫先行 + 流程閘門 + 工具執法」三者共同承載。宿主技術的自由度越高（HTML/CSS > 元件類別框架），雙向約束越必要。

本方法論與具體 UI 框架無關，適用於 Flutter、Web 框架（React / Vue）、Tauri、Python GUI 等任何元件化 GUI 開發。判準以三層承載：L1 通用原則（本方法論）、L2 語言/框架實作規範、L3 專案元件庫章節，定義見〈分層架構〉。適用時機：新專案或新 UI 框架導入（見執行步驟）、UI 類提案的 SPEC 階段（見流程整合點）、存量元件治理與遷移。

術語速查：design token＝集中管理的樣式參數；variant＝同一元件的預設變化形；RWD 斷點＝依畫面寬度切換版型的門檻值；rebuild / re-render＝框架重新繪製元件的動作。

## 雙向約束判準

### 設計端（樣式的定義者）

| 判準 | 內容 |
|------|------|
| 元件先行 | 設計新頁面前，先確認所需元件在元件庫存在；缺件先補元件定義，再設計頁面 |
| 從元件拼組 | 頁面 = 元件庫元件的組合 + 空間配置；頁面級一次性樣式視為設計債（發現即建 ticket 追蹤） |
| 樣式收斂 | 同一語意只有一種外觀；避免過於多樣化的設計，頁面須體現一致的產品風格。語意是否相同以元件語意標註為比對基準，標註缺漏時先補標註 |
| 元件語意標註 | 每個元件標註設計意義：何時使用、何時不使用、對應的使用者心智模型 |

### 工程端（樣式的使用者）

| 判準 | 內容 |
|------|------|
| 禁自製元件 | 實作只從元件庫取件；元件庫缺件時停下補元件（走元件票——補元件定義與實作的獨立 ticket，設為原設計/實作票的 blockedBy 前置），不就地自刻 |
| 依語意選件 | 依語意選擇變體（確認操作用 confirm 變體），不依外觀湊件 |
| 商業邏輯註記 | 工程端補上元件的業務邏輯與注意事項：何種資料狀態對應何種元件狀態、邊界條件 |
| 狀態綁定一致 | 元件狀態變更遵循 L2 規範選定的狀態管理模式；禁混用指同一類共享狀態使用多種模式，元件內部暫態（區域 state）與全域 store 並存屬正常分層，不在禁列 |

**缺件前置範圍擴充**：「元件缺件停下補元件」判準比照適用於 i18n 系統與 design token 層——實作若發現尚未建立的多語系資源 key 或未定義的 design token，同樣停下補齊（走對應的 i18n / design-system 前置 ticket），不得在元件或頁面內就地假設文字字面或樣式數值。i18n、design-system、UX 審查、元件庫四塊的建置順序與相互依賴見〈地基波 build 順序〉。

### 命名與通用元件判準

命名是存在必要性的檢視工具：命不出目的的元件，多半可由通用元件取代。

| 判準 | 內容 |
|------|------|
| 命名體現目的 | 元件名承載設計目的（如 ConfirmDialog、RiskBadge）；無法命名出目的即為「此元件是否該獨立存在」的警訊。本判準僅適用特化元件；通用前綴元件的目的即「涵蓋無特殊語意的預設場景」，免受此檢視 |
| 通用前綴為預設 | 無特殊目的的通用元件以統一前綴標示（common / App 等，依專案約定），語意為「預設選用這個」；工程端選件順序：先通用元件，有明確設計目的才選特化元件 |
| 存在必要性檢視 | 新元件提案先問「能否以通用元件 + variant / 參數達成？」能 → 不建特化元件 |
| 通用元件可擴充性 | 通用元件以 variant 標籤（預設數種，數量定於 L2；有語意時優先語意名）+ 參數微調涵蓋變化；每遇新情況就得新建特化元件，即為通用元件 API 設計不足的訊號，應先擴充通用元件 |

驗收點：新元件的命名與存在必要性檢視，綁定元件票驗收條件，由 PM 驗收。

### 元件契約判準

元件契約是 L3 元件庫章節中每個元件條目的必填內容，定義「接手者不必再想的事」。雙向約束判準管元件從哪裡來（元件庫）與由誰定義（設計端）；本節管每個元件必須定義到什麼程度，才能被「只選件、只排位」地使用。

**Why**：元件庫的價值來自「相同行為有相同反應」，而行為不只是顏色與尺寸。文字要不要換行、空間不足時怎麼處置、按鈕橫排的最小間距，這些若不寫進契約，每個畫面的實作者會各自決定，元件庫只剩樣式參數、無行為契約。**Consequence**：實測兩種形態——一個專案有通用元件與多版型零溢位測試，元件各自不溢位，組合起來卻互相重疊而遮住鄰件的點擊區，因為排列關係沒有元件承載；另一個專案逐元件寫了狀態矩陣與互動反應，仍在實作期反覆補「這個數字可不可以縮」「這個標題要不要截斷」，因為內容政策與尺寸契約空白。**Action**：每個元件條目填滿下表十一欄；缺任一欄即契約不完整，元件票不得驗收，畫面票（實作單一畫面或頁面的 ticket）不得引用該元件。

#### 十一欄位表

| 欄位 | 須定義的內容 | 缺失後果 |
|------|-------------|---------|
| 語意與內容角色 | 何時用、何時不用；承載標題／內文／標籤／數值／動作中的哪一種 | 依外觀湊件：把內文元件拿去放標題，字級對了語意錯了，日後改標題樣式時漏改 |
| 變體 | 語意變體（如 positive／negative／neutral）各自的外觀差異與行為差異；變體數量與命名定於 L2 | 同一語意長出多種樣子，或用參數微調拼出未定義的第 N 種變體 |
| 狀態集 | 元件可處於的狀態（enabled／hover／pressed／focused／disabled／loading／selected／error／empty 中適用者），每個狀態的顯示／可用操作／進入條件／退出路徑四欄 | 狀態在實作期臨場增補，各畫面的同一元件狀態集不一致；退出路徑缺失即死胡同 |
| 操作機制 | 該形態的使用者用什麼動作完成這個元件的任務（點選／拖動／步進／直接輸入／長按）與按下後走哪個回饋通道（引用形態因素矩陣的回饋通道列），每個形態各一份；判準是任務所需精度對上該形態的輸入精度，精度不足時提供替代機制（加減按鈕、數值輸入彈窗），不以放大版面解決 | 桌機能精確拖動的滑桿原樣搬到手機，使用者調不到要的值；機制留給實作者臨場決定，同一語意在各畫面長出不同操作方式 |
| 尺寸契約 | 固有尺寸或填滿父容器；最小與最大尺寸（可點元件的最小尺寸不得小於該形態的最小命中區 token）；形態因素矩陣列出的每種視窗或裝置尺寸下的行為 | 元件在小視窗溢位或在大視窗拉成不成比例的形狀；父容器不知該給多少空間 |
| 內容政策 | 每個文字 slot 可否換行、最大行數、超出時的處置（截斷／淡出／縮放／換行）、用於測試的最長文案 | 換行與溢位由呼叫端決定，同一元件在不同畫面截斷方式不同；長文案首次出現在實機才被發現 |
| slot 契約 | 可插入的內容位置、各位置接受的型別；使用者可見文字依〈元件文字歸屬〉三層規則處理：由呼叫端傳入者走 i18n key，預設文案與排版字元的例外見該節 | 呼叫端塞入契約外的內容，元件為配合它加特例參數，通用元件退化為特化元件 |
| 組合規則 | 可放入哪些容器；不得放置的區域（引用形態因素矩陣的禁放區：手機四角、系統手勢區）；對齊基準；作為表格或列表的一欄時的欄比例與內距。與鄰件的間距不在此定義，由容器契約的排列不變式承載 | 排列關係由頁面用原生佈局臨場拼裝，重疊與錯位發生在組合層，而元件各自的測試全綠 |
| 無障礙 | 輔助技術的使用者怎麼用它：朗讀標籤（元件是什麼、目前值）、狀態變化播報、非視覺替代訊號（顏色不作唯一訊號）、焦點順序與鍵盤或輔助技術的操作路徑；標籤跨形態共用，操作路徑每形態各一份 | 看不見畫面的使用者聽到一顆沒有名字的按鈕、變化後無播報；事後補朗讀等於重寫元件的狀態集 |
| 測試契約 | 一支測試逐一渲染全部變體與狀態（golden 或 widget test，形態定於 L2）；形態因素矩陣的每種尺寸皆不溢位；最長文案依內容政策處置 | 「不溢位」只在預設尺寸與短文案下成立；契約與實作漂移無機制發現 |
| 反例 | 不該拿它做什麼；容易誤用的相鄰元件 | 兩個語意相近的元件被交替使用（如空狀態與阻擋狀態），使各自的驗收互相污染 |

欄位順序即填寫順序：先定語意，再定變體、狀態與操作機制，接著定尺寸與內容，然後定組合與無障礙，最後定測試。反例最後寫，因為要有相鄰元件可比。操作機制的輸入形式判準（鍵盤型別、送出模型、IME）見 `ux-design-evaluation` skill 的輸入機制 reference，本欄只要求每形態各答一次。

**與既有判準的關係**：狀態集四欄的填法見 `ux-design-evaluation` skill 的畫面狀態矩陣，本節只要求元件層級也要有，不重述填法。slot 契約的文字規則即〈元件文字歸屬〉，本節只要求列出 slot。不重述的理由：同一判準寫在兩處，修改時只改一處即漂移。十一欄位與容器條目的產物形狀定於 `doc` skill 的元件庫規格範本，該範本須含此兩類條目。

#### 容器亦為元件

**凡是決定多個元件如何相對排列的佈局結構都是元件，須有自己的契約條目**；按鈕列、兩欄說明列表、帶操作欄的表格列、附說明文字的區塊皆屬此類。頁面直接用原生佈局原語（水平或垂直堆疊、格線）排列元件，視同自製元件，適用工程端「禁自製元件」判準。

**Why**：元件各自的契約只能保證元件自身不溢位；兩個都不溢位的元件放在一起會不會重疊，取決於排列它們的佈局結構。該結構若不是元件，就沒有契約、沒有測試、沒有人對重疊負責。**Consequence**：重疊事故的典型形態——按鈕來自元件庫、顏色與尺寸皆引用 token、每顆按鈕的測試全綠，頁面用原生水平堆疊把它們排成一列，視窗縮小時後面的按鈕蓋住前面的，被蓋住的按鈕點不到。事故不在任何一個元件內，所以元件層級的執法（裸值掃描、禁自製掃描）全部通過。**Action**：容器元件的契約除十一欄位外，必填「排列不變式」三項：

| 不變式 | 內容 |
|--------|------|
| 不重疊 | 子件的邊界盒兩兩不相交；測試以形態因素矩陣的每種尺寸與子件數量上限驗證 |
| 最小間距 | 相鄰子件的最小間距為具名 token，不接受呼叫端覆寫為更小值 |
| 空間不足策略 | 三選一且只選一：換行（wrap）、捲動（scroll）、收合（collapse，如放不下的項目收進更多選單）；契約寫明策略與觸發條件 |

容器元件的 slot 契約另須寫明接受的子件類型與數量上限；子件數量無上限者必然觸發空間不足，其空間不足策略不得留空。子件的組合規則不得另定間距，以容器的最小間距為準。框架容器（頁面根堆疊、殼層）另承載該形態的安全區（SafeArea 或同等機制）與禁放區留白，畫面票與一般元件不各自處理。

判別問句：畫面上任兩個元件的相對位置是誰決定的？答案若是「頁面本身」，該處缺一個容器元件。

#### 派發語言

**畫面票的實作策略只述選件與排位，不述設計。** 契約齊全後，畫面票的 how 應可寫成「用元件 X 的變體 Y，放進容器 Z 的第 N 格（格位）」；寫不成這個形式時，缺的是元件或契約，先補元件票，不在畫面票內設計。

**Why**：契約的目的是把設計決策從實作期前移到元件庫；畫面票若仍要求實作者「考慮版面」「處理溢位」，前移就沒有發生，契約對實作不產生約束。**Consequence**：實作者在畫面票內做設計決策，同一決策在每張畫面票各做一次，結果各不相同，且沒有任何一處記錄它們。**Action**：

| 欄位／情境 | 寫法 | 反例 |
|-----------|------|------|
| how | 逐畫面狀態列「元件 + 變體 + 容器 + 格位」；狀態來源指向狀態矩陣 | 「依設計稿實作列表頁」「注意文字不要溢位」 |
| acceptance | 「頁面檔的元件 import 只來自元件庫的統一匯出入口」（可 grep；無 import 邊界的宿主改以〈Web/HTML 端 L2 特別判準〉的不並存斷言替代）；「狀態矩陣每列都以契約內的元件組成」 | 「畫面正確顯示」「不溢位」（不溢位由元件契約的測試保證，畫面票不重驗） |
| 發現缺件時 | 停手、建元件票、設為本票 blockedBy（同工程端「禁自製元件」判準） | 就地用原生佈局補一個 |

畫面票驗收時 PM 對照契約：頁面出現契約外的元件、或以原生佈局原語排列元件，即為「禁自製元件」違規，處置同工程端判準。

### 元件文字歸屬（i18n-first）

元件庫 text-agnostic 是 i18n-ready 的結構保證：多語系決策可延後，結構成本先付清——元件不綁文字，日後導入多語系只動呼叫端與資源檔，元件庫零改動；反之，寫死文字的改造成本隨元件採用面積單調上升，「開發到一定程度才決定支援多語系」的高成本大頭正是散落元件內的寫死文字。

| 層 | 規則 |
|----|------|
| 使用者可見文字 | 禁止字面寫死於元件；文字由呼叫端經參數 / slot 傳入，呼叫端從 i18n 系統取值 |
| 強語意預設文案 | confirm / cancel 類按鈕標籤、載入預設提示、無障礙標籤，得由元件引用 i18n key 作預設值，三條件 AND：走 i18n 系統非字面、參數可覆蓋、key 列入元件 API 契約（多端共用時進跨平台命名契約，防雙端預設文案漂移） |
| 非語意排版字元 | 省略號、分隔點、數字格式符號不屬文案，可內嵌 |

違反成本：元件寫死文字使「相同行為相同反應」在語言維度破功——同一元件在不同呼叫點切換語言時行為不一致。

### 形態因素先決（Form Factor）

**形態由使用者的操作方式定義，不由顯示空間定義。** 手機（單手觸控、行進中、短時注意）、平板（雙手觸控或筆、坐姿）、桌機（指標加鍵盤、多視窗、長時工作）是三種不同的操作方式，同一個任務在三者上的容器版型各自設計；同一形態內的螢幕或視窗尺寸差異，才由容器的排列不變式（換行／捲動／收合）承載。以寬度門檻切換版型的 RWD 斷點不是形態判準：兩個寬度相同的裝置可以是不同形態，同一裝置旋轉後仍是同一形態。

元件庫設計前先定形態因素矩陣；其結論決定元件庫結構（單一形態，或多形態各一套容器版型）。

| 維度 | 決策問題 |
|------|---------|
| 支援的形態 | 手機 / 平板 / 桌機 / 摺疊機展開態，各以操作方式界定（主要輸入模態、持握姿勢、注意力情境），各自是否為正式支援目標？ |
| 同形態內的方向支援 | 直持 / 橫持是否皆支援？方向切換不構成新形態，其版面差異由該形態的容器契約（尺寸契約各列一種方向）承載 |
| 特殊表面 | 桌面 widget、懸浮視窗、畫中畫等系統表面是否需要？其操作方式若與主形態不同（如只能瞥視不能操作）即為獨立形態 |
| 同形態內的尺寸適應策略 | 兩種合法形式擇一或並用：(a) 約束視窗尺寸（下界 minSize、長寬比）使版型不需切換，其餘差異由容器的排列不變式承載；(b) 設計上刻意提供使用者可選的版型（如雙欄／單欄，為設定項由使用者切換）。禁止依寬度門檻自動切換版型，不在元件內硬編碼任何尺寸門檻。桌機常駐展開側欄的版型屬 (a)：限縮視窗尺寸比例，不是寬度不夠就自動收成漢堡選單 |
| 覆蓋表面對映 | bottom sheet、drawer、dialog、popover、常駐側欄等覆蓋或附屬表面，依各形態的操作方式選件並記於矩陣（手機：bottom sheet 與抽屜；平板：側欄或 popover；桌機：對話框、彈出面板、常駐側欄）；元件與容器的組合規則引用此對映，不由畫面票臨場選 |
| 回饋通道 | 每形態的按下回饋通道：視覺／觸覺（震動）／聲音。手機的按鈕會被手指遮住，視覺回饋看不到，須有觸覺或聲音回饋；平板得提供觸覺；桌機視覺即可。記於矩陣，元件的操作機制欄引用 |
| 最小命中區 | 每形態一個具名 token：手機的可點元件有平台指引的尺寸下限（手指命中），桌機的指標命中區可小得多。元件的尺寸契約引用此 token，不各自定值 |
| 禁放區與安全區 | 每形態的禁放區（手機四角觸控不靈敏、系統手勢區、瀏海與底部指示條）不得放置可點元件，由元件的組合規則引用；安全區（SafeArea 或同等機制）由框架容器（頁面根堆疊）承載，畫面票與元件不各自處理 |

矩陣為最小集，L3 得依產品增列維度（如 hover 態與命中區尺寸依輸入模態而異；文字縮放適應：a11y 動態字級下元件是否須彈性高度）。

**多形態的契約結構**：十一欄位中語意與內容角色、變體、狀態集、slot 契約、反例、無障礙的朗讀標籤跨形態共用（元件是什麼不隨形態變）；操作機制、尺寸契約、內容政策、組合規則、測試契約、無障礙的操作路徑與容器條目每形態各一份（元件怎麼被操作、怎麼擺、文字怎麼截、放進哪個容器隨操作方式變）。同一語意可落在不同容器：導覽項這個元件跨形態共用，承載它的容器在手機是收合的抽屜（漢堡選單觸發），在平板與桌機是常駐展開的側欄；數值調整這個語意在桌機是可拖動的滑桿，在手機是步進按鈕或輸入彈窗。畫面票的派發語言隨之帶形態前綴：「桌機形態：容器 Z 第 N 格放元件 A」。

判準：形態因素矩陣記錄於 L3 元件庫章節開頭（欄位＝維度、結論、理由）。支援幾個形態即幾套容器版型，多形態約等於元件庫容器層多軌的長期維護成本，屬用戶簽核決策——PM 不得自行拍板，須提供各形態的操作方式差異與成本對比後提請專案擁有者批准，須於 SPEC 階段決定並記錄；未明文即預設單一形態。

### 豁免三條件（AND，全滿足才可豁免直用）

1. 結構性無法收斂：第三方套件內部元件、測試斷言、效能豁免（元件組合無法達標的手工優化，須附 profiler 證據）、非視覺輔助結構件（無障礙包裝層），或一次性且不可重用的刻意破格（如行銷 campaign 頁，須限定表面範圍清單）。可重用的「元件庫缺件」不得引用本條件——缺件的指定路徑是元件票（見工程端判準），不是豁免
2. 記錄理由：每筆豁免寫「路徑 + 具體理由」，禁無 trigger 的「暫時豁免」
3. 列入工具白名單：豁免項登記於執法工具白名單，使工具與文件一致

豁免核可與權威源：豁免由 PM 於票驗收時核可，禁止實作端自行滿足三條件即視為豁免生效；L3 豁免清單為單一權威來源，執法工具白名單由其生成或定期比對。

原型豁免：標記為 spike / 實驗性且不合入生產路徑的程式碼，豁免禁自製判準；轉正（合入生產）閘門要求全數替換為元件庫元件或走元件票，轉正前其直用計數不納入版本驗收。

## 分層架構

| 層 | 載體 | 內容 |
|----|------|------|
| L1 通用原則 | 本方法論 | 雙向約束判準、命名與通用元件判準、元件契約判準（十一欄位、容器亦為元件、派發語言）、形態因素先決、豁免三條件、流程整合點；與 UI 框架無關 |
| L2 語言/框架實作規範 | 框架 references/ 或專案 spec | 元件目錄結構、狀態綁定模式、最小重繪邊界、效能預算、測試斷言規範、執法工具偵測規則 |
| L3 專案元件庫章節 | 專案 spec 文件 | 元件清單、逐元件契約（十一欄位）、容器元件與排列不變式、原生元件禁用對照表、豁免清單、跨平台命名契約；無原生元件邊界的宿主（HTML/CSS 等）另含元件規則 SSOT 模組與選擇器清單（見〈Web/HTML 端 L2 特別判準〉） |

最小適用集：單端小型專案得裁剪為「token 層 + 禁自製 + 豁免清單」三件底線；元件契約的十一欄位得縮至語意與內容角色／尺寸契約／內容政策三欄，排列不變式不裁（組合層重疊在小專案同樣發生）；跨端契約與形態因素矩陣依端數 / 表面數啟用，執法依執行步驟 6 的生態降級梯度調整。

### L2 狀態綁定判準

狀態綁定模式必須在元件庫設計時決定，不留給實作時各自選擇。理由：綁定模式決定三件事——

| 決定項 | 說明 |
|--------|------|
| 元件 API 形狀 | 傳值（值 + callback）或傳可觀察物件（observable / notifier / signal）。此二分屬框架相依決策軸，L2 得以該框架實際慣例改寫（如 React 以區域 state / 提升 / context / 外部 store 分層） |
| 最小重繪範圍 | rebuild / re-render 邊界落在元件內或元件外。手動邊界框架（Flutter、React）須於 L2 明文邊界標準寫法；自動依賴追蹤框架（Vue / Solid / Svelte）由框架承載，L2 僅需高頻場景檢核 |
| 效能預算 | 高頻場景（長列表每格、動畫、即時輸入）的效能檢核方式（如 Profiler 抽查），於元件設計時評估而非上線後補救；量化上限為選配 |

L2 規範須明文：本專案選定的狀態管理方案、元件接收狀態的標準形式、重繪邊界的標準寫法（自動依賴追蹤框架免列，僅列高頻檢核）、高頻場景的效能檢核方式。

### Web/HTML 端 L2 特別判準

HTML/CSS 缺乏原生元件邊界，元件化必須由約定補足。本節屬跨框架 L2 元判準，Web 端專案的 L2 規範須涵蓋下列三項：

| 判準 | 內容 |
|------|------|
| 封裝強制 | 元件一律以工廠函式或框架元件封裝（createButton / createCard 等）；禁止裸 HTML 標籤 + inline style 直接成件 |
| CSS 收斂 | 樣式宣告收斂於 design-system；token 化配置的 utility 系統（如以 token 生成的 utility class 設定檔）與受 design-system 約束的 CSS-in-JS 屬收斂範圍內，禁的是繞過 token 的裸樣式值與頁面內嵌散落 CSS 規則 |
| variant 命名 | 工廠參數用語意 variant 名（primary / confirm / danger），與 token 對映，禁以外觀值傳參 |
| **元件規則 SSOT** | design token 在 Web 端需**第五類**來源模組：元件的 CSS rule block 本身。顏色／間距／字體／陰影四類管的是值，rule block 管的是「哪個選擇器套用哪些值」，在有原生元件邊界的框架上這層由元件類別承擔，HTML/CSS 沒有這層就會散回頁面內嵌 `<style>` |
| **元件邊界的可驗產物** | 無原生元件邊界時，「元件一律封裝」無法由語言機制保證，須有可機械檢查的產物：**選擇器清單 + 存在性斷言 + 不並存斷言**（該選擇器只出現在 design-system，不同時出現在頁面）。缺此產物時封裝強制只是約定，違反不會紅燈 |

> **Why 補後兩條**：前三條說了怎麼封裝與什麼該收斂，沒說**產物是什麼**。四塊 build 順序的第 4 塊要求「依 L3 元件清單建立元件實體」，在有元件類別的框架上清單即實體；vanilla DOM 沒有這個對應，實作者知道要封裝卻不知道交付什麼、如何驗收。**Consequence**：三個實測專案（瀏覽器擴充套件、前後端分離的 vanilla JS、Flutter 桌面工具的無框架部分）在此格皆停住，且停因相同——不是缺判準，是判準沒有可投影的產物定義。**Action**：Web 端專案的 L3 元件庫章節須含元件規則 SSOT 模組與選擇器清單兩項產物。
>
> **實證**：一個瀏覽器擴充套件把 popup 內嵌 `<style>` 的 31 條共用 rule block 遷入 `design-system.css`，來源模組 `component-rules.js` 自述為「generator 的第 5 個來源模組，與 colors / spacing / typography / shadows 同為 SSOT」；配套 snapshot test 守護「規則值一律引用 `var(--*)`、禁 raw hex」，選擇器清單另存為 test helper，以存在性與不並存兩組斷言攔截漂移。同一專案的元件目錄有 5 個檔案、契約檔 0 個——**有實體無契約正是缺這兩項產物的形態**。

### 多端共用 design-system 的跨端契約

同一 design token 系統被多端使用（如原生 App + Web Extension）時：

| 判準 | 內容 |
|------|------|
| 命名契約 | L3 元件庫章節須含跨平台對照表（元件語意名、variant、size、引用 token 的各端對映），指定單一權威端（權威端於 L3 對照表明文） |
| 契約變更同步 | 任一端變更元件命名或語意即為契約變更：契約版本標記於 L3 對照表（contract-version 欄位）；跨 repo 通知走既有追蹤機制（上游框架 repo 的 issue 或對方專案 ticket，雙方票面互相引用） |
| 差異分級 | 實作層差異（響應式單位 vs 固定 px）不屬契約；語意名與 token 引用屬契約 |

## 流程整合點

| 階段 | 閘門 | 執法載體 |
|------|------|---------|
| SPEC 階段 | UI 類提案必須先有 design token 層 + 元件庫章節（L3），才能開 UI 實作票 | 版本規劃流程 checklist |
| 功能設計階段 | 介面設計只引用元件庫元件名；缺件先開元件票再繼續設計 | 設計職責條款 |
| 實作階段 | 禁止直接建構被元件庫涵蓋的原生元件 | hook / lint 靜態偵測：先警告模式（hook WARNING / lint warn）觀察誤報率，升為阻擋（hook deny / lint error）由 PM 依誤報率實證提請用戶簽核（觀察期與閾值量化值定於 L2 規範）；無現成偵測生態時依執行步驟 6 降級 |
| 版本驗收 | 原生元件直用計數為 0（豁免清單除外），計數來源＝執法工具掃描報告 | 發布前健康檢查 |

### 地基波 build 順序

測試設計（Phase 2）開始前，須依序完成四塊地基實作，才能進入測試設計：

| 順序 | 地基塊 | 內容範圍 |
|------|--------|---------|
| 1 | i18n 實作 | 多語系資源檔與取值機制建立，涵蓋本波所需文案 key |
| 2 | design-system 實作 | design token 層（顏色 / 間距 / 字體 / 圓角 / 陰影）與 L2 狀態綁定模式落地為可執行程式碼 |
| 3 | UX 審查 | 互動反應、動畫、提示、導航跳轉 / 退出、生命週期四類行為的畫面級審查（見 `.claude/skills/ux-design-evaluation/SKILL.md`） |
| 4 | 元件庫實作 | 依 L3 元件清單建立元件實體，文字經 i18n key 傳入、樣式取 design token |

四塊完成後才進入測試設計。

**Why**：測試設計（尤其 zh/en 文字溢位測試與元件互動反應測試）驗證的對象是 i18n 系統與元件實體的實際行為；這兩者若未先存在，測試案例沒有可驗對象，只能先寫佔位斷言、事後回補，測試設計流於形式（實證：UC 完成後即規劃測試設計，經指正應先完成四塊地基）。

**Consequence**：此順序若不寫入方法論、僅存在於單次對話糾正中，orchestration 層（如 `version-bootstrap` skill）在設計「測試設計前置檢查」時沒有權威判準可引用，只能倚賴 PM 記憶重建順序；記憶會在下個版本或下個專案流失，同樣的跳步會重複發生。

**Action**：流程編排 skill（如 `version-bootstrap`）的地基波前置檢查，須引用本節四塊順序作為權威來源；四塊未完成不得開啟測試設計 Ticket。

## 執行步驟（新專案或新 UI 框架導入）

1. 定形態因素矩陣（支援的形態 / 同形態內方向 / 特殊表面 / 同形態內尺寸適應策略），決定單一形態或多形態各一套容器版型
2. 建立 design token 層：顏色、間距、字體、圓角、陰影參數集中管理（載體依生態：Flutter 常數類、Web CSS 變數 / utility 設定檔、Qt QSS + 常數模組、Tkinter style 常數模組）
3. 選定狀態綁定模式並寫入 L2 規範（含最小重繪邊界與效能檢核約定）
4. 依 UC / spec 頁面清單盤點建立首批元件（按鈕、卡片、對話框、分隔、輸入、標籤為常見基本集），並以〈容器亦為元件〉的判別問句盤點容器元件；每個元件依〈元件契約判準〉十一欄位填寫 L3 條目，容器另填排列不變式
5. 在 spec 建立 L3 元件庫章節：元件清單 + 逐元件契約（十一欄位）+ 容器條目 + 禁用對照表 + 豁免清單
6. 建立工具執法：偵測直用（注意 naive 比對誤報——自製元件命名、theme 設定類、helper 方法常與原生元件共用字根，須用 word-boundary 與排除規則）。依生態成熟度調整：無現成 hook / lint 機制的生態（如 Python GUI）可自寫 AST / grep 掃描（原生元件字根可偵測），最低降級為 PR checklist + 定期人工清點；降級時版本驗收的計數來源同步改為人工清點記錄
7. 存量遷移按 feature 目錄拆票並行（互不相依、單票檔案數受認知負擔閾值約束）

## 檢查清單

- [ ] UI 實作票開立前，design token 層 + L3 元件庫章節已存在？
- [ ] 設計產出只引用元件庫元件，缺件已開元件票？
- [ ] 實作無元件庫已涵蓋的原生元件直用，豁免有記錄理由並列白名單？
- [ ] 元件狀態綁定遵循 L2 規範選定的模式，同類共享狀態未混用？
- [ ] 新元件有設計語意標註 + 工程商業邏輯註記？
- [ ] 每個元件條目十一欄位齊全（語意與內容角色／變體／狀態集／操作機制／尺寸契約／內容政策／slot 契約／組合規則／無障礙／測試契約／反例），缺欄者未被畫面票引用？
- [ ] 畫面上每個排列關係都有容器元件承載，容器契約含排列不變式三項（不重疊／最小間距／空間不足策略）？
- [ ] 畫面票的 how 只述選件與排位，acceptance 含「元件 import 只來自統一匯出入口」？
- [ ] 高頻場景元件的重繪成本已於設計時評估？
- [ ] 新元件命名體現設計目的，或已確認通用元件 + variant / 參數無法涵蓋？
- [ ] 元件庫元件無字面寫死的使用者可見文字，預設文案走 i18n key 且參數可覆蓋？
- [ ] 形態因素矩陣已於 SPEC 階段明文（含版型是否拆分的決策）？
- [ ] 禁令由工具執法承載，而非僅文件提醒？
- [ ] 測試設計前，地基波四塊（i18n 實作 / design-system 實作 / UX 審查 / 元件庫實作）已依序完成？
