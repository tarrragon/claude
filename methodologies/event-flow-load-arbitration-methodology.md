# 事件流負載仲裁方法論

多個事件流競爭同一個稀缺通道時，「誰讓步、誰等、誰被丟、丟了怎麼留痕」由該通道的單一仲裁器依三個參數裁決：**到達類別**（時機由誰決定）、**級別**（丟棄後果由誰承擔）、**佔用量**（通道現在有多滿）。稀缺資源是參數，不是前提——使用者注意力、CPU 時間、連線數、isolate 事件迴圈，全部套同一組判準；差別只在各節標明的「實例化條件」。

每條判準附兩欄：**它回答的問題**與**為何這樣定**。**規格條文引用本方法論的判準時，須連同「它回答的問題」一起引用**——判準脫離它回答的問題之後，讀者無法判斷自己碰到的情況是不是這條要管的；而結論正確配上錯誤的理由在當下無症狀，失效發生在有人依那個理由推導下一步時。教學與案例材料引用判準時不受此限，它們的讀者手上有完整脈絡。

## 核心概念

| 參數 | 定義 | 注意力通道實例 | 後端通道實例 |
|------|------|--------------|-------------|
| 通道 | 一次只能服務有限個請求、有「尚未被消費的請求」可言、且**在可預見的負載下會被填滿**的資源，有一個明確持有者。永遠不會飽和的資源不必走本方法論 | 畫面上的提示載體（一次一則） | DB 連線池、worker pool、單一 isolate 的事件迴圈 |
| 到達類別 | 這一次的到達，時機由誰決定 | 使用者操作／App 自行發起／平台推送 | 同步 API 請求／排程與背景工作／不等回覆的推送 |
| 級別 | 這個請求被丟棄後，後果由誰承擔、可否回復 | 必須決策／必須知悉／可補查 | 不可棄／須留痕／可棄 |
| 佔用量 | 通道上已到達且尚未被消費的請求量 | 載體佇列長度 | in-flight 數、佇列深度、最老請求年齡 |

**四個詞在本方法論有特定所指，且其中三個在本框架的其他檔案另有用法，讀之前先對齊**。

| 詞 | 本方法論指什麼 | 別處指什麼 |
|----|--------------|-----------|
| **通道** | 上表定義的那類資源。通訊原語只是其中一個實例，連線池、worker pool、事件迴圈、畫面提示載體同樣是通道 | 並行程式設計慣例：執行體之間的通訊原語（Go 的 channel、訊息管道）。框架內另有兩義——元件庫方法論的「回饋通道」指回饋的感官模態，可觀測性規則的「雙通道輸出」指 stderr 與日誌兩個輸出口。**本方法論的 Reference 表會把讀者送到前者，跳過去時該詞換了意思** |
| **卸載**（load shedding） | 仲裁器在佔用量越過閾值時，依〈讓步與卸載順序〉拒絕或丟棄請求；被卸載的請求不會被轉移到任何地方 | 中文技術寫作慣例：移除安裝，或把工作轉移到別處（offload） |
| **滯後**（hysteresis） | 進入與離開卸載刻意留的閾值差，用來防止在臨界點反覆進出 | 框架內多處指「輸出落後於待驗現象」（lag），與本方法論的用法無關；兩者在中文同形 |
| **留痕** | 請求被丟棄或降級時留下的可追溯記錄，粒度依級別而異（見〈可觀測性〉） | 框架內多處指「留下操作痕跡」（稽核軌跡），語意相鄰但對象不同——那裡的對象是人的操作，這裡是被丟棄的請求 |

**本方法論有兩個執行者，各節的動作分屬其一**。**設計期的執行者是讀本方法論的人**：他為一個具體系統走〈執行步驟〉，量測閾值、標定類別與級別、填出各步的產出物，並把它們寫進該系統的規格與 domain map；各步的訪談問句、已套用的案例與產出物表格骨架在 `event-flow-arbitration-design` skill，本方法論只給判準。**執行期有兩個執行者**：**仲裁器**讀取類別、級別、佔用量三個輸入，輸出一個取自〈讓步與卸載順序〉動作集的決策；**估計器**在執行期回填成本實測、依實際過載次數調整分位數、並在容量上限未知的通道上推導閾值。估計器改的是仲裁器讀的那些值，本身不裁決任何請求；設計期決定它調什麼、調的範圍上下界、以及它多久調一次。**仲裁器只裁決不做工**——不執行請求本身，不推導級別，也不判讀業務結果；判準表裡凡是需要量測、選值、填表的動作，全部屬設計期，仲裁器在執行期只讀結果。

無佇列的直通型資源（accept backlog 為零的連線接受、SYN flood 防護）沒有「未消費的請求」，佔用量只有零與一，不屬本方法論的通道；那裡只能用到達率，歸入口配額處理。

## 1. 通道與仲裁器

| 判準 | 它回答的問題 | 為何這樣定 |
|------|------------|-----------|
| 每個通道恰有一個仲裁器；仲裁器落在通道的持有層，不落入任何 domain 內部 | 誰決定這個請求現在能不能佔用通道？ | 各 domain 互相確認需要 N² 條協調邊，且迫使每個 domain 知道其他 domain 存在；向單一持有者請求只需 N 條邊，domain 之間維持互不知情 |
| 協調圖有兩個軸：**發出請求的 domain**與**請求的來源**（租戶、客戶、上游系統）。前者與依賴方向 DAG 正交，後者在單一 domain 內部也成立——同一個 domain 的同一條事件流，來自不同租戶的請求彼此競爭 | 哪些請求之間需要仲裁？ | DAG 描述資料方向；競爭發生在任何兩個會對同一通道發出請求的 domain 之間，不分層級。只查 DAG 會得到「無關係」的結論，看起來像已確認過 |
| 仲裁器與通道處於同一 failure domain 時，仲裁器不新增單點，只把通道本有的單點顯性化；仲裁器若是通道之外的獨立行程，它就是新增的可用性單點 | 仲裁器會不會成為新的單點？ | 通道本身就是單點（一個連線池就是一個）；仲裁器與它同生共死時沒有新的失效模式，分離時「仲裁器掛而通道還能動」是新的停服路徑，且對等待型請求 fail-closed 會放大它。落點規則見〈跨執行緒與 isolate〉 |
| 多核心、多實例時，仲裁器隨通道分片，不做跨仲裁器協商；前提是分片後的通道確為真持有者。多個副本各持一個連線池連向同一個資料庫時，真持有者是資料庫，仲裁器應放到真持有者處（連線 proxy），或承認協調配額是刻意新增的單點 | 通道不只一個時仲裁器怎麼擴？ | 一個連線池、一個 isolate 各是一個通道時，各自一個仲裁器即可；讓多個仲裁器互相協商就回到 N²。但「各自不滿而下游已飽和」證明分片對象不是真持有者，此時分片未達成仲裁的目的——各分片的佔用量都不反映真持有者的餘裕 |
| 分片即靜態配額，閒置份額不跨仲裁器流動 | 分片的代價是什麼？ | 一個分片閒置時它的配額不會流回其他分片，這是接受的代價，不是可以靠協商消除的缺陷 |
| 禁止的是**並行持有**：持有一份的同時申請第二份。**序列重借**（用完歸還、再借下一份）不在禁列，它任一時刻只持有一份。並行持有的份數若在入口就知道，一次申請；份數依資料而定而無法預知者，改為在該請求進入前先確認餘裕足夠，或把它降級為可被中斷的形態 | 一個請求可不可以在持有通道時再要一份？ | 「持有並等待」是佔用量計不到的狀態（已計為 in-flight），也是死鎖成立的必要條件之一——一個請求持有一份資源的同時等待另一份，多個這樣的請求就可能互相等成環；而不可棄的等待型請求不由仲裁器卸載，死鎖一旦形成無人能打斷 |

## 2. 到達類別

判準的輸入是「這一次的到達，時機由誰決定」，**逐跳套用**：同一個事件在送達跳與處理跳可以屬不同類別。實作是否非同步不進入判斷：在我方選定時刻發出的 `await` 屬自發型，由平台同步回呼推進來的事件屬推送型。**分類的對象是這一次的發生，不是那段程式碼**——同一份掃描程式碼，由使用者按下按鈕觸發屬等待型，由啟動時自動執行屬自發型。

| 類別 | 判準問句 | 可否延後啟動 | 可否拒絕（推回） | 誰在等 | 負載下的預設動作 |
|------|---------|:---:|------|------|----------------|
| **一、等待型**（使用者操作、同步 API 請求、等待 2xx 的 webhook 送達跳、request/reply 訊息、對仲裁器的申請） | 能否回溯到一個正在等待我方回覆的外部發起者？ | 否 | 可，且拒絕必須送達發起者 | 發起者 | 拒絕並附可重試資訊 |
| **二、自發型**（排程、背景掃描、重試、預熱、對帳、我方決定何時拉取的訊息消費、已確認收訖之後的事件處理） | 開始的決定點是否在我方程式碼內？ | 可 | 不適用，不發即可；拉取型的推回是停止拉取 | 無人 | 延後或跳過 |
| **三、推送型**（平台回呼、作業系統訊號、檔案系統監看事件、不等 ack 的 pub/sub 或串流訊框、fire-and-forget 的跨執行緒訊息） | 我方是被通知方，且來源不等我方任何回覆？ | 否，事件已到達 | 否，無人接收拒絕 | 無人，但事件已存在 | 緩衝；溢出時依級別處置並留痕 |

| 判準 | 它回答的問題 | 為何這樣定 |
|------|------------|-----------|
| 推回不是卸載：推回把請求留在發起者手上由它重試，卸載是我方讓它消失。等待型的不可棄請求不由仲裁器卸載，但可推回給**持久的持有者**（會重送且重送預算未耗盡的發送端、broker、佇列）；推回給揮發性發起者（瀏覽器、一次性用戶端）等於丟棄，不適用 | 不可棄的請求可以回 503 嗎？ | 兩個動作對「這個請求還在不在」給出相反的答案，而答案取決於接住它的是誰。推回之後請求仍存在於發起者處——前提是那個發起者還在、且還會再送一次 |
| 不可棄的推回率本身是容量訊號：同一來源的不可棄請求連續推回次數逼近其重試預算時，即為容量失敗訊號 | 一直回 503 算不算把它服務了？ | 不設這個門檻，一個把全部不可棄請求都推回的系統永遠不發容量失敗訊號、指標上看起來健康，而發送端的重試預算耗盡時該請求不可回復地消失。門檻取自發送端宣告的重試次數，不另設常數 |
| 推回（backpressure）可行若且唯若存在一個等待中的發起者能接收「否」 | 這個請求能不能推回去？ | 等待型的發起者正在等，回應碼或即時拒絕回饋都送得到；推送型的來源已經走了，緩衝上限是它唯一的推回替代品；自發型的發起者是自己，推回等於延後 |
| 逐跳分類：等待 ack 的 webhook 在送達跳屬等待型（非 2xx 即推回），確認收訖之後的處理屬自發型；拉取式訊息消費在拉取決策屬自發型，拉進來的批次是它的接收緩衝 | 一個 webhook、一個 broker 消費者到底屬哪一類？ | 把送達跳歸為推送型會放棄回應碼這個唯一的推回手段；把拉取歸為推送型會忽略「停止拉取」這個推回手段。不可棄事件須在確認收訖前落持久佇列，否則確認後的處理無從延後 |
| 跨執行緒、跨 isolate 的訊息依同一判準分類：送方等待回覆者為等待型，fire-and-forget 者為推送型；兩者在接收方都已到達，都需要接收緩衝 | 多執行緒下訊息算哪一類？ | 分類鍵是「有沒有人在等」，不是「跨不跨執行緒」；把等待回覆的申請當推送型處理，溢出時會被靜默丟棄，申請方永遠等不到回覆 |
| 拉取進來的批次，其中每一個事件在處理時屬推送型；屬自發型的只有「要不要拉這一批」這個決定 | 批次裡的事件算哪一類？ | 拉取決策做完之後，個別事件的到達時機我方未曾決定，而它已經在我方緩衝內——這正是推送型的兩個條件。把批次內事件也算自發型會得出「可以延後啟動」的結論，而它已經到了，沒有啟動可言 |
| 推送型的協調點在接收後、呈現或執行前；等待型與自發型在發起前 | 仲裁器在流程的哪一點被詢問？ | 推送型事件已進入我方邊界，只能決定何時處置與是否處置；沒有緩衝時「延後」無處可放，實作會退化為立即處理或直接丟棄 |

## 3. 級別

級別的鍵是**丟棄後果由誰承擔、可否回復**，不是產生方認定的技術嚴重度。稀缺資源屬於接收方；以產生方視角分級會讓「很嚴重但接收方無事可做」的事件搶到高優先序。

| 級別 | 判準 | 丟棄後果 | 注意力實例的慣用名 | 對應非同步工作的失敗語意 |
|------|------|---------|------------------|----------------------|
| **不可棄** | 丟棄使流程停滯、狀態不可回復、或違反對外義務 | 不可回復 | 必須決策（L1） | 不可丟，須與業務寫入同 transaction |
| **須留痕** | 可丟，但無其他管道得知，事後必須能補做 | 資訊遺失，可補做 | 必須知悉（L2） | 不可丟，須有死信去處 |
| **可棄** | 重算即得，或另有管道可得知 | 無 | 可補查（L3） | 可丟 |

| 判準 | 它回答的問題 | 為何這樣定 |
|------|------------|-----------|
| 級別是請求的屬性，不是端點的屬性；等待型與推送型在進入我方邊界時標定，自發型在發起點標定，之後傳播 | 級別是靜態標註還是動態推導？ | 同一個查詢在結帳流程中屬不可棄、在儀表板刷新中屬可棄，端點層級的靜態標註無法區分；但推導級別需要業務脈絡，仲裁器不該擁有業務知識，所以推導發生在邊界或發起點，仲裁器只讀取 |
| 傳播單調不升：呼叫方可為子呼叫指派不高於自身的級別，不可升。**例外是優先權繼承**——低級別請求持有高級別請求正在等的資源時，該低級別請求在持有期間暫時取用等待者的級別，釋放後還原 | 一個不可棄請求發出的子呼叫算什麼級別？ | 不可棄的結帳呼叫推薦服務，少一排推薦可回復，該子呼叫依鍵屬可棄；只傳播不降會讓它以不可棄佔通道，正是分級要防的事；允許自我升級則任何請求都能自我拔高。優先權繼承不是自我升級——級別由等待者給予、不由持有者宣稱，且隨資源釋放而終止；不給這個例外會出現優先權反轉：不可棄請求等一個可棄請求持有的資源，而那個可棄請求因為級別低而被搶佔，兩者一起停住 |
| 邊界無法取得脈絡時退回端點的靜態預設級別，並把「以預設標定」記為可觀測事件。**預設值的方向由誤標代價決定**：誤標為低級別會丟掉本該保住的請求（不可回復），誤標為高級別只是佔用餘裕（可回復），因此預設取該端點可能承載的最高級別；受稽核或有對外義務的系統一律預設為不可棄 | 標定失敗怎麼辦？預設該取哪一級？ | 靜默退回預設會讓「本該不可棄的請求以可棄被丟」無從追溯。而預設向下取值時，記了事件也已經丟了——事件證明的是丟棄發生過，不是丟棄可回復；兩種誤標的代價不對稱，預設要往可回復的那一邊倒 |
| 級別與到達類別正交，三乘三共九格各有處置（見〈讓步與卸載順序〉） | 兩個參數會不會互相決定？ | 一個 webhook 可以是可棄（重複的心跳）也可以是不可棄（付款完成通知）；一個使用者操作也同樣橫跨三級 |

## 4. 競爭與佔用量

**競爭 = 通道上第二個請求抵達時，第一個尚未被消費。** 消費只有三種形態：完成、撤回（發起者撤回或仲裁器撤回）、逾期；漏列任一種，佔用量會把已消費的請求繼續計入。

| 判準 | 它回答的問題 | 為何這樣定 |
|------|------------|-----------|
| **佔用量不是一個數，是一組三個量：in-flight 數、佇列深度、最老未消費請求年齡。三者量綱不同，不相加**；裁決規則是任一項越過自己的閾值即進入卸載，全部低於各自的離開閾值才離開 | 佔用量到底是什麼形態的量？ | 三項各自量到不同的東西——前兩項量「有多少在等」，第三項量「等了多久」，一個階躍型通道可能前兩項爆而第三項為零。把它們合成單一標量必須給權重，而權重無來源；改為逐項比較則每一項都可獨立驅動卸載，且哪一項先觸發本身是診斷資訊 |
| 卸載的判準是佔用量的三項，不是到達率 | 什麼時候開始卸載？ | 到達率是預測量（尖峰會持續多久未知），佔用量是狀態量（通道現在有多滿）；多核心下每個通道各有自己的佔用量，仲裁以通道為單位，「系統整體到達率」對任何單一通道都不是可裁決的量。延遲型與自適應型准入控制的決策變數都是佔用量的一項，到達率從未進入 |
| 到達率的合法用途有二：入口配額（單一來源的公平額度）與自發型的啟動時機（已知尖峰前不啟動批次）；卸載不用它 | 那 rate limit 和排程算什麼？ | 入口配額解的是「一個 client 不得吃光全部」，卸載解的是「通道不得溢出」；只有配額時單一慢查詢仍可拖垮通道，只有卸載時單一 client 可以合法佔滿通道。自發型可以重排，選啟動時刻是它唯一合法使用預測量的場合 |
| 通道不暴露佇列深度時，以最老未消費請求年齡的代理量（事件迴圈 lag、frame 逾時）作輸入，並標明它是佔用量的年齡項而非佔用量的替代物 | 讀不到佇列的通道怎麼算佔用量？ | 單一執行緒的事件迴圈不暴露佇列長度，唯一可觀測的是等待時間；它足以驅動卸載（延遲型准入控制只用這一項），但不能反推有多少請求在等 |
| 進入卸載狀態與離開卸載狀態的閾值不同，離開閾值低於進入閾值 | 什麼時候恢復？ | 同一閾值會在臨界點反覆進出（震盪），每次進出都是一次可觀測事件與一次背景工作的暫停恢復 |
| 閾值的形態由通道的容量是否已知決定：容量有明確上限（連線池大小、worker 數）用該上限的比例表示；上限未知或隨環境變動（事件迴圈、CPU）改由等待時間訊號推導 | 閾值該寫成固定數字還是推導量？ | 比例只有在分母存在時才有意義；沒有分母的通道只剩等待時間可量，自適應准入控制的加減調整就是這種通道上的閾值推導形態 |
| **閾值程序先分損害機制**，三種各有取法：**延遲膨脹型**（連線池、worker pool、事件迴圈——佔用量高使等待變長）用下一列的程序；**資源耗盡型**（記憶體——損害是耗盡而非變慢，等待時間可能到最後一刻都正常）閾值取自可用量減去單次最大配置，與等待時間無關；**固定服務型**（提示載體這類串行且服務時間固定者——等待時間恆與佇列長度成正比、無轉折點）閾值取自使用者或下游能容忍的最長等待除以單次服務時間 | 為什麼量不出轉折點？ | 「佔用量本身不造成損害，佔用量轉化為等待時間才造成」只對延遲膨脹型成立。對資源耗盡型，越過臨界的下一次配置就失敗，之前毫無徵兆；對固定服務型，曲線永遠是直線，找轉折點的程序永遠得不到答案而登記為待量測，那個登記無法被消除 |
| 延遲膨脹型通道**年齡項**的進入閾值取在等待時間開始隨負載超線性成長處：逐步加負載，記錄年齡；年齡的成長由平緩轉陡時，該處的年齡值即為初值。**in-flight 與佇列深度兩項的進入閾值不由此程序決定**——有明確上限的通道在飽和之前無人等待、年齡恆為零，該程序對它們是階躍而非曲線；兩項取上限的一個比例，比例的選擇看該通道從越過閾值到實際飽和之間要留幾個請求的餘裕，餘裕的下界是同期間可能抵達的請求數 | 三項各自的第一個數字從哪來？ | 佔用量本身不造成損害，佔用量轉化為等待時間才造成；在轉折點之前卸載是浪費容量，之後才卸載則已經在賠等待時間。量不到轉折點時任取一個值並登記為待量測，不可留白——留白的結果是實作者在程式裡填一個沒有人知道來源的常數 |
| 兩個閾值的差距下界是**單一請求完成造成的佔用量變化**；差距小於這個變化量等於沒有滯後 | 兩個閾值要差多少？ | 差距小於一個請求的份量時，一次完成就把狀態翻回去，震盪照舊發生。以上限 20 的連線池為例，一條連線是 5 個百分點，差距至少要能容納數次完成的抖動 |
| 暫停由某個不可棄事件觸發（而非由佔用量觸發）時，恢復另需該事件已被消費，且被暫停工作的擁有者在恢復點重驗前提；仲裁器只提供「已消費」訊號 | 恢復條件為何不只看佔用量？誰驗前提？ | 觸發暫停的事件其結果可能使背景工作的前提失效（使用者拒絕授權、上游 schema 已變更），只看佔用量會立刻恢復一個註定失敗的工作並在下一輪再產生一次相同的請求；而判讀前提是否失效需要業務知識，仲裁器不該擁有，所以由工作自己驗。注意力通道的暫停多為事件觸發，連線與 CPU 通道的暫停多為佔用量觸發，後者只需滯後 |

**失效條件**：以請求數計與以資源單位計對同一通道給出不同的裁決時，以請求數計的佔用量失去意義，須依〈資源成本異質〉分池。

## 5. 資源成本異質

| 判準 | 它回答的問題 | 為何這樣定 |
|------|------------|-----------|
| 佔用量以資源單位計（連線數、CPU 時間、記憶體），不以請求數計 | 一個請求算多少佔用？ | 一個全表掃描與一個主鍵查詢在請求數上相等，在通道佔用上差數個數量級；以請求數計會讓少數貴請求在指標上隱形 |
| 成本未知的請求以同類歷史的高分位數預估，完成後以實測回填；分位數以近似結構或離線回填取得，不在仲裁路徑上精算 | 沒量過的請求怎麼計？ | 以平均值預估會讓長尾請求系統性低估；不預估則新請求進不了仲裁；精確分位數不是常數時間，會違反〈跨執行緒與 isolate〉對仲裁器的要求 |
| 分位數取在**低估的殘餘機率足以接受**的位置，不取固定值：低估使通道過載（不可回復），高估只讓通道保守（下一次回填即修正），兩種誤差的代價不對稱 | 該取哪一個分位數？ | 代價不對稱時最適點不在中位數而在高分位；長尾越重、過載代價越高，取值越往上。多數通道以 p95 起步，回填累積後依實際過載次數調整。**無歷史可用的冷啟動**以該通道的容量上限為預估——最保守、必然高估，第一批完成後即被實測取代 |
| 分池的觸發在設計期回答：**單一最貴請求的資源佔用，是否足以使該通道對其餘請求的餘裕降到閾值以下**。成本分佈跨一個數量級是它在多數系統上的代理判準，兩者不一致時以前者為準 | 什麼時候該分池？ | 分池買到的是延遲隔離——貴請求不再吃掉便宜請求的餘裕。觸發條件必須在設計期答得出來（此時仲裁器尚不存在，任何以「兩種計法的裁決是否分歧」表述的條件都取不到輸入），而「最貴請求佔掉多少餘裕」由容量上限與成本估計即可算。**與依級別分池的分界**：依成本分池防的是貴請求吃掉餘裕，依級別分池防的是低級別在有序通道上擋住高級別，兩者可同時成立於同一通道 |

**實例化條件**：注意力通道的請求成本同質（一則就是一則），因此只分級不分量成立；這是注意力實例的性質，不是通則。分池的訪談與 day-one 做法在 capacity-performance 維度的「貴操作隔離」，本節只給觸發判準。

## 6. 讓步與卸載順序

三條讓步規則，可機械檢查：

1. 高級別抵達時**可**搶佔低級別
2. 同級別**不得**互相搶佔——排隊或合併
3. 低級別**排隊等待**，不得搶佔任何請求

**搶佔的形態依通道的可回收性而異**，且並非每種通道都做得到搶佔。逐一列出：

搶佔的可行性由**該請求現在的位置**與**它有沒有中斷點**兩個問題決定，不由通道叫什麼名字決定：

| 請求的位置 | 有中斷點 | 無中斷點 |
|-----------|---------|---------|
| **尚未開始**（在佇列裡、已排程未觸發） | 取消，零成本回收 | 取消，零成本回收——尚未開始者不需要中斷點 |
| **執行中** | 於中斷點停下，已完成的部分保留 | 只能終止並重算，或不搶佔；重算成本計入該工作的級別判定 |

各通道落在哪一格由它的實作決定，不可由通道類型推定。常見實例與**容易判錯的地方**：

| 通道 | 尚未開始者可否取消 | 執行中可否中斷 |
|------|------------------|--------------|
| 提示載體 | 可（未顯示的移出佇列） | 可（截斷顯示，代價是那一則未被看見） |
| worker pool | 可（取消未派工者） | 依工作自身有無中斷點 |
| 連線池 | 可（拒絕新的低級別等待型請求） | **依資料庫而定**——支援取消進行中語句者可中斷，代價是終止並重算；不支援者已借出的收不回 |
| 單一執行緒的事件迴圈 | **依排程手段而定**——可取消的計時器與可中止的請求能取消，已入佇列的 microtask 不可 | 通常否；工作自帶分塊讓出時可 |
| 有序消費的訊息通道 | 只在同一次拉取的批次內成立，跨批次須依級別分流 | 依消費端實作 |

**表列的是常見形態，不是窮舉**。通道不在表內時直接回答上方兩個問題；判斷依實作查證，不依這張表的名稱對號入座。

**截斷條件綁在級別上，不綁在呼叫路徑上**——以呼叫路徑決定截斷，會讓第三條在無人察覺下被違反：低級別請求從另一個入口進來就截斷了高級別。

表中兩格另有實例化條件。**worker pool 執行中的工作**：搶佔以該工作提供可中斷點為前提，無中斷點時退化為終止並重算，重算成本計入該工作的級別判定。**有序消費的訊息通道**：跨批次的分流是依級別分池，與〈資源成本異質〉依成本分池並列，兩者可同時成立於同一通道。

**卸載順序表**（到達類別 × 級別，列序即卸載順序）。動作集為：接受、延後、拒絕、丟棄、合併、降級；表中「跳過」是自發型的丟棄，「緩衝」是推送型的延後，「搶佔」是對被搶者的延後或丟棄。

| | 可棄 | 須留痕 | 不可棄 |
|---|------|--------|--------|
| **自發型** | 跳過，不補跑 | 延後至離開卸載狀態；逾期則跳過並留痕，留痕由下一次排程消費 | 延後不丟；逾期即為容量失敗訊號 |
| **等待型** | 拒絕＋可重試資訊 | 拒絕＋可重試資訊＋留痕 | **不由仲裁器卸載**；可推回給持久持有者，推回率逼近其重試預算即為容量失敗訊號 |
| **推送型** | 緩衝滿時先合併再丟棄，丟最舊，只計數；最新值語意的事件保留最新一則加計數 | 緩衝滿時先寫留痕再丟棄 | **不得只存在於記憶體緩衝**，必須落持久佇列；仲裁器對它只能延後消費，延後至接收視窗填滿即為容量失敗訊號 |

| 判準 | 它回答的問題 | 為何這樣定 |
|------|------------|-----------|
| 卸載順序：先無人等待者（自發型），再可重試者（等待型低級別），不可回復者永不由仲裁器丟棄 | 高負載時先停哪些請求？ | 自發型沒有人在等，跳過的成本為零；等待型低級別的發起者能重試，成本由發起者分攤；不可棄的丟棄成本不可回復，而仲裁器手上沒有任何可用來抵銷它的東西 |
| 不可棄請求無法服務即發出**容量失敗訊號**，該訊號的接收端是容量維度的 tripwire 表，不屬仲裁範圍 | 全部都是不可棄怎麼辦？ | 仲裁器只能在有請求可讓步時裁決；無請求可讓步時任何裁決都是丟棄不可回復的請求，正確動作是把訊號交給容量維度 |
| 可重試資訊含退避與抖動；重試紀律見 reliability 維度 | 拒絕之後會不會更糟？ | 只給「稍後重試」不給退避，被拒者同時重試就製造下一波到達尖峰，機制與自發型補跑相同 |
| 可棄的推送型丟最舊 | 緩衝滿時丟哪一端？ | 可棄的定義含「重算即得」，新值取代舊值；丟最新會留下最無價值的一批 |
| 合併需三條件 AND：同一來源、同一級別、對其中任一則的處置對其他則同樣適用；合併後保留計數 | 高頻事件能不能合併？ | 第三條排除「看起來像但需要分別決策」的情形；不保留計數則接收方無從判斷要不要展開 |
| 同級別時推送型優先於自發型 | 兩者同時抵達誰先？ | 自發型可以重排，推送型不行；優先給不能讓步的一方，總延遲較低。這是唯一一處推送型享有優先，其餘一律依級別 |

## 7. Deadline 傳播

| 類別 | deadline 來源 | 逾期動作 |
|------|-------------|---------|
| 等待型 | 由發起者持有，請求攜帶剩餘預算 | 回報逾期，不再佔用通道 |
| 自發型 | 下一次排程時刻 | 可棄跳過不補跑；須留痕跳過並留痕，留痕由下一次排程消費（窗口驅動的工作把窗口併入下一輪）；不可棄不得逾期，逾期即容量失敗訊號 |
| 推送型 | 事件自身的價值衰減期 | 可棄丟棄、須留痕先留痕、不可棄不逾期 |

| 判準 | 它回答的問題 | 為何這樣定 |
|------|------------|-----------|
| 下游呼叫繼承剩餘預算；剩餘預算不足以完成該步驟的最小成本時不啟動，直接回報逾期 | 一個已經來不及的請求要不要繼續做？ | 發起者已放棄的請求繼續佔用通道，是對其他請求的純損失；在入口擋下比在中途發現便宜 |
| 自發型逾期不即時補跑；狀態驅動的工作（下一輪自動涵蓋本輪未做的範圍）直接跳過，窗口驅動的工作（對帳、結算、摘要）留痕並由下一次排程消費該留痕 | 錯過的排程要不要補？ | 補跑會在恢復瞬間堆積出一個自製的尖峰，而剛離開卸載狀態時通道的餘裕最小；但窗口驅動的工作沒有「下一輪自動涵蓋」可言，不留痕就是資料缺口 |
| 上界取自來源自身的有效期，不另設常數 | 上界的數字從哪來？ | 另設常數會產生第二個需要與來源同步的數字，而無同步機制時兩者會漂移；注意力通道的上界即載體的自然存活期 |
| 發起者未提供 deadline 時，邊界指派預設並標記為「指派」而非「攜帶」 | 沒帶 deadline 的請求怎麼辦？ | 兩者在追溯時意義不同：逾期是發起者的決定還是我方的預設，決定該修哪一邊 |

## 8. 部分降級

可切分的資源（CPU、連線）允許部分降級；不可切分的資源（注意力，一次只有一則可見）只有讓步沒有降級。這是實例化條件。

| 判準 | 它回答的問題 | 為何這樣定 |
|------|------------|-----------|
| 降級的單位是功能，不是請求；功能的級別取其服務的請求中的最高級別，可棄功能先關，事前決定 | 超出上限時關什麼？ | 逐請求降級等於卸載，已在〈讓步與卸載順序〉；功能層的取捨需要業務判斷，事故當下即興決定會偏向當下症狀最明顯的功能 |
| 降級不可靜默：回應或畫面必須攜帶降級標示（標頭欄位、常駐徽章） | 使用者或呼叫端怎麼知道現在是降級？ | 沒有標示時降級回應與正常回應同形，接收方會依殘缺結果做決策；這與被丟棄的請求無留痕是同一類失效：接收方拿到與正常同形的殘缺結果 |
| 降級是狀態不是暫態提示：進入與離開皆為可觀測事件，離開含滯後 | 降級怎麼結束？ | 暫態提示會被錯過；沒有滯後會震盪 |

降級預案的清單與訪談問題在 capacity-performance 維度的「高峰活動 readiness」，本節只給判準。

## 9. 跨執行緒與 isolate

| 判準 | 它回答的問題 | 為何這樣定 |
|------|------------|-----------|
| 仲裁狀態不跨執行緒**以鎖**共享；仲裁器與它的通道住在同一個執行緒或 isolate，其他執行緒以訊息申請。**無鎖的原子計數（號誌、比較並交換）不在此禁令內**——它沒有等待者、不構成第二個通道，是有界池的標準實作 | 多執行緒下仲裁器放哪？ | 禁的是鎖不是共享：鎖有等待佇列，那個佇列本身就是一個未被仲裁的通道。原子計數只做一次不會阻塞的讀改寫，沒有佇列可言。需要鎖才能維持的仲裁狀態（分級佇列、年齡排序）改以訊息申請，申請訊息的送方在等回覆，依〈到達類別〉是等待型 |
| 仲裁器的決策為常數時間，狀態有界：每（類別 × 級別）各一條 FIFO、各有上限；deadline 只在出隊時懶檢查，不做排序 | 仲裁器自己過載怎麼辦？ | 仲裁器若做線性掃描、依 deadline 排序或無界佇列，它在高負載時的延遲會隨負載成長，成為它要保護的通道之外的第二個瓶頸；共用一個總上限時可棄事件洪水會佔滿緩衝，使不可棄事件進不來，等於低級別以佔位搶佔高級別 |
| 仲裁器佇列深度是它自身的佔用量指標；溢出時對等待型的申請回覆拒絕，對推送型的通知丟棄並計數 | 仲裁器溢出時的預設是什麼？ | 對等待型 fail-open（放行）等於仲裁器失效時通道無保護；對等待型丟棄則申請方永遠等不到回覆，是設計層死鎖；推送型無處可推回，只能丟棄並讓計數可見 |
| 擴充只能靠通道分片，條件與代價見〈通道與仲裁器〉 | 單一仲裁器成為瓶頸時怎麼擴？ | 協商回到 N²；分片後每個仲裁器仍是自己通道的唯一持有者 |

**逐級別有界這一條被省略時會發生什麼**：某個可棄的推送來源開始高頻送出——一次部署把心跳週期改短、或一個下游開始重試——仲裁器的共用佇列被這些請求佔滿。此時不可棄的請求申請不進來，在仲裁器門口就被擋掉，而通道本身還有餘裕。**它不會被發現的理由是每一個指標都正常**：通道佔用量不高、卸載計數落在可棄那一格看起來合理、仲裁器沒有回報錯誤。被擋掉的不可棄請求只在分級延遲的高級別那一欄留下痕跡，而那一欄要與可棄欄並排看才顯得異常。發現時通常是下游先報資料缺漏，止血是重啟仲裁器清空佇列，代價是清空時在途的請求全數遺失。

## 10. 可觀測性

**不變式：每一個請求離開通道都是一個可觀測事件**，攜帶請求識別、到達類別、級別、通道、離開方式、佔用量快照、deadline 剩餘。**離開方式不只有仲裁決策**：出隊時懶檢查判定的逾期、推回、以及被高級別搶佔而終止，三者都不經過仲裁器的決策路徑，若只在決策點發事件，這三條出口全部無痕。被丟棄的請求若沒有這個事件，丟棄與靜默失敗在日誌上同形——這與 Port 回饋契約的「呼叫發出」不變式同構，對象從外部系統呼叫換成仲裁決策。

| 判準 | 它回答的問題 | 為何這樣定 |
|------|------------|-----------|
| 留痕粒度依級別：不可棄逐筆；須留痕逐筆但可攢批，識別不可省；可棄只計數加取樣樣本 | 全部留痕會不會讓留痕本身成為負載？ | 不可棄永不被丟，量小；須留痕的識別是補做的唯一依據；可棄的個別內容無人會查，計數與樣本足以回答「丟了多少、長什麼樣」 |
| 留痕的載體不得共用被保護的通道；寫入須非阻塞且有界，寫不進時計數不丟 | 留痕寫到哪？ | 共用時留痕本身在高負載時被卸載，正好在最需要它的時候消失；寫入阻塞則緩衝維持滿載，堵住它要保護的事件迴圈 |
| **有對外交代義務的系統，不可棄請求的留痕不得有損**：寫不進時該請求不得被丟棄，改為推回或等待留痕可寫；「寫不進計數不丟」只適用於須留痕與可棄 | 稽核軌跡可以掉嗎？ | 「允許有損」發生的時刻正是卸載發生的時刻，而那正是要交代的那一批。對只需事後診斷的系統，掉幾筆換取不阻塞是划算的；對必須逐筆交代的系統，掉的那幾筆就是要交代的內容，這筆交易不成立 |
| 告警綁狀態變遷與增量（進入或離開卸載、卸載計數增量、最老請求年齡跨閾值），不綁「佔用量高」 | 高負載時哪些訊號還有資訊量？ | 「佔用量高」在高負載時恆真，輸出恆非空且增量不可見時資訊量趨近零，且背景雜訊讓真正的新事件更難被看見——比沒有偵測更糟 |
| 指標只收能回答一個事故當下問題的項目；篩選原則沿用 observability 維度，此處不重述 | 該收哪些指標？ | 指標不對應事故當下要回答的問題時無人會查它，只增加告警雜訊與收集成本 |

**最小指標集**：

| 指標 | 它回答的問題 |
|------|------------|
| 佔用量，每通道，並按（類別 × 級別）分解 | 現在有多滿、是誰把它填滿的 |
| 完成計數，每級別 | 通道有沒有在推進——佔用量高而完成數為零是死鎖或活鎖，完成數穩定是單純飽和，兩者處置相反 |
| 卸載計數，每（類別 × 級別） | 丟了誰 |
| 分級延遲 p50 / p99，每級別，拆排隊等待與服務時間 | 高級別有沒有被低級別拖累；變慢還是變多 |
| 最老未消費請求年齡 | 有沒有請求飢餓（starvation） |
| 仲裁器佇列深度 | 仲裁器本身是否過載 |
| 降級狀態與進出時刻 | 現在缺什麼功能、缺了多久 |
| 以預設標定級別與指派 deadline 的計數 | 有多少請求是在缺脈絡下被裁決的 |

分級延遲是量測不是排程：以固定桶直方圖累計，不進仲裁路徑。

**前提與退化形態**：逐筆留痕以 structured log 與 request id 為前提，兩者是 observability 維度的 day-one 底線。前提缺席時本節退化為「計數＋狀態變遷事件」的最小形態，仍須成立；只有元件層日誌而無仲裁決策事件的系統，對「被丟棄的請求」零可追溯。

## 11. 測試義務

與 [Port 回饋契約〈測試義務〉](./clean-architecture-implementation-methodology.md#測試義務) 同構：不需要替身的驗證只確認仲裁器發出的事件或輸出欄位本身，用記錄器（spy）或固定輸入輸出即可；需要替身的驗證是仲裁器依通道狀態（佔用量、佇列深度、緩衝內容）做出的決策分支，需要注入可控的通道或佇列狀態複本以驅動特定分支——這裡的複本模擬被仲裁的通道，不是外部系統。

| 判準 | 驗證目標 | 是否需要替身 |
|------|---------|-------------|
| 仲裁決策事件（〈可觀測性〉不變式） | 每個仲裁決策都產生事件，且事件攜帶請求識別、到達類別、級別、通道、決策、佔用量快照、deadline 剩餘七項欄位 | 不需要——用記錄器確認事件被發出、欄位是否齊全即可，不模擬通道行為 |
| 三條讓步規則（〈讓步與卸載順序〉） | 高級別可搶佔低級別、同級別不得互搶、低級別不得搶佔任何請求，以三級別（不可棄／須留痕／可棄）× 兩到達順序（高級別先到、低級別先到）窮舉驗證 | 需要——注入可控的通道佔用量狀態，驅動搶佔分支，驗證仲裁器輸出的決策而非通道本身的執行結果 |
| 卸載順序九格表（到達類別 × 級別） | 九格各自的動作（接受、延後、拒絕、丟棄、合併、降級）與〈讓步與卸載順序〉表定一致，每格至少一測 | 需要——每格各固定一組（到達類別、級別、佔用量狀態）輸入，用假通道記錄仲裁器輸出的決策 |
| 進入與離開卸載的閾值（〈競爭與佔用量〉） | 閾值在臨界點來回穿越時，狀態變遷有滯後、不因單次抖動而震盪 | 需要——注入可控的佔用量數值序列，模擬臨界值來回穿越 |
| 仲裁器自身溢出（〈跨執行緒與 isolate〉） | 仲裁器佇列溢出時，等待型的申請收到明確拒絕，不是被靜默丟棄 | 需要——注入仲裁器佇列已滿的狀態複本，驅動溢出分支 |
| 可棄推送型的卸載順序（〈讓步與卸載順序〉） | 緩衝滿時丟最舊的一則，不是丟最新 | 需要——注入緩衝區已滿且含多筆有序事件的狀態複本 |
| 級別傳播單調不升（〈級別〉） | 子呼叫的級別不高於發起它的父請求的級別 | 不需要——用固定的父／子請求級別輸入配對驗證輸出，不涉通道狀態 |

## 12. 旁路的存在與可靠性

本方法論有三處把工作交給通道之外的旁路：留痕的載體、不可棄推送型的持久佇列、容量失敗訊號的接收端。**三者在條文裡都被當成存在**，而個案實跑顯示同一個系統可能三者皆無。

| 判準 | 它回答的問題 | 為何這樣定 |
|------|------------|-----------|
| 每個旁路在設計期逐一確認三件事：它存不存在、它的可靠性等級、它與被保護的通道是否共用底層資源 | 交出去之後有人接嗎？ | 三處旁路各自隱含一個不同的等級——留痕允許有損（非阻塞、有界、寫不進時計數不丟）、持久佇列必須無損、容量失敗訊號的接收端必須有人或有一張會被讀的表。把三者一律當成存在，會在旁路缺席的系統上產出看起來完整而執行不了的設計 |
| 旁路缺席時的處置依等級而異：**允許有損者**降級為同進程的計數（留痕退化為「丟了幾筆」）；**必須無損者**若無持久儲存，該格的級別標定就是錯的——沒有持久佇列的系統不能宣稱自己有不可棄的推送型事件；**接收端缺席者**指名一個人，指不出來就承認該通道沒有容量升級路徑 | 沒有旁路的系統怎麼辦？ | 前兩者的差別是可回復性：計數丟了還能重建趨勢，事件丟了不能。第三者是本方法論唯一會把問題推出邊界的出口，推出去而無人接住等於沒有處置——單一使用者的桌面應用對「注意力不夠」沒有任何擴充選項，此時正確的答案是承認該通道的容量固定、把設計改成不產生超出它的請求 |
| 旁路與被保護的通道共用底層資源時，「載體不得共用通道」退化為「非阻塞、有界、寫不進時計數不丟」 | 只有一顆磁碟怎麼辦？ | 前者是後者在資源充裕時的實作方式，不是獨立要求；資源不足時保留後者即可 |

## 13. 登記類條款的消費要件

前幾節在三個位置允許以登記代替完成：閾值量不到轉折點時登記「待量測」、設計期查不到的項目登記「現況不明」、方法論尚未覆蓋的通道登記為已知缺口。這三者不是文件慣例——**未校準的閾值是上線後真正在裁決卸載的那個數字**，它的偏差直接落在使用者身上。

| 判準 | 它回答的問題 | 為何這樣定 |
|------|------------|-----------|
| 登記只有在連接消費機制時才算完成，三者任一即可：指名的消費者（誰負責回來把它消掉）、期限（到期後該項升為阻擋項）、或自動升級閾值（例如以待量測值裁決的卸載次數達到某量即升級） | 寫下「待量測」之後呢？ | 沒有消費機制的登記是永久豁免，而它與「認真做過但做不到」在產物上完全同形；三處登記共用同一個形狀，逐處補限定句只會讓條文膨脹而形狀不變 |
| 每則登記附「已嘗試什麼」一句：量測登記寫量測方式與為何得不到轉折點，查找登記寫已查過的位置 | 怎麼分辨認真做過與直接跳過？ | 這一句是兩者產物的唯一區別。少了它，第三方面對同一張表無法判定哪幾格是查過的「不明」、哪幾格是省力的「不明」 |
| 需要判斷的驗收項附「依據」欄，不以勾選代替；結構性項目（可由第三方以固定值命令反證者）維持勾選即可 | 檢查清單為什麼有些項目要寫字？ | 勾選對可被外部反證的項目足夠，對判斷性項目不可證偽——全勾與逐項確認的產物同形。下方檢查清單以「附依據」標出屬後者的項目 |

**分級的舉證**：三級量表的中間值「須留痕」是後續建設成本最低的一級——不可棄要求持久佇列與容量失敗訊號鏈，可棄要求論證重算即得，須留痕兩者皆免。標定為須留痕時，級別標定依據欄須同時寫出**為何不是不可棄**（丟棄後果何以可回復），否則該級別成為零後續動作的預設出口。

## 執行步驟

1. **列通道**：找出每一個一次只能服務有限請求的資源，確認真持有者，指定各自的持有層與仲裁器落點（不落入 domain）。
2. **標類別與級別**：對每一條事件流的每一種觸發路徑逐跳標到達類別；級別在邊界或發起點標定，寫明標定依據的脈絡與傳播規則。
3. **定佔用量**：選單位（兩種計法給出不同裁決時分池），定進入與離開卸載的兩個閾值——形態依通道容量是否已知決定，進入閾值取等待時間由平緩轉陡處，兩者差距不小於單一請求完成造成的變化；量不到轉折點時填任一值並標「待量測」。
4. **填卸載順序表**：九格各填動作，推送型指定緩衝上限與溢出動作，不可棄的推送型指定持久佇列。
5. **定 deadline 來源**：三類各自的來源與逾期動作，自發型區分狀態驅動與窗口驅動，下游繼承規則。
6. **確認旁路**：留痕載體、不可棄推送型的持久佇列、容量失敗訊號的接收端三者各自存不存在、可靠性等級、是否與被保護的通道共用底層資源；缺席者依〈旁路的存在與可靠性〉處置。
7. **定可觀測事件與最小指標集**：離開通道事件的欄位、留痕粒度與載體、告警綁定的變遷。

## 檢查清單

- [ ] 每個通道恰有一個仲裁器，且不在任何 domain 內部；分片對象是真持有者，靜態配額代價已寫明
- [ ] 同一請求對同一通道的佔用一次申請，無「持有並等待」路徑
- [ ] 每條事件流逐跳標定，分類對象是「這一次的發生」；等 ack 的送達跳、拉取式消費、request/reply 訊息未被誤歸推送型
- [ ] **附依據**：級別在邊界或發起點標定、傳播單調不升；標定失敗有可觀測事件。標為須留痕者，依據欄寫出為何不是不可棄
- [ ] 卸載判準是佔用量；到達率只出現在入口配額與自發型啟動時機
- [ ] **附依據**：進入與離開卸載的閾值不同，且各自寫得出「這個數字怎麼來」；差距不小於單一請求完成造成的佔用量變化。以「待量測」登記者，依據欄寫已嘗試的量測方式與消費機制
- [ ] 事件觸發的暫停有「已消費」訊號與擁有者重驗
- [ ] 兩種計法（請求數／資源單位）裁決一致，否則已分池；有序通道上的級別分流已定
- [ ] **附依據**：每個通道的搶佔形態已對照〈讓步與卸載順序〉的通道表確認，依據欄寫各通道落在表中哪一列

- [ ] 降級有標示、有進出事件、有滯後；功能級別取所服務請求的最高級別
- [ ] 跨執行緒申請以訊息進行且屬等待型；仲裁器每（類別 × 級別）各自有界且決策常數時間
- [ ] 每個仲裁決策有可觀測事件；留痕寫入非阻塞；指標含完成計數與佔用量分解；告警綁變遷不綁「佔用量高」
