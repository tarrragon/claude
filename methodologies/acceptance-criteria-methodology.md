# 驗收條件方法論

本文件定義驗收條件（Acceptance Criteria）的標準化格式規範，確保驗收條件可量化、可追溯、可驗證。

> **完整格式模板與範例**：標準格式三式、好/壞範例 6 組、與 Ticket 系統/驗收代理人/建議追蹤整合的完整 YAML/Markdown 模板與轉換範例，見 `.claude/references/acceptance-criteria-templates.md`。撰寫具體驗收條件、套用 Ticket 模板或設計系統整合時按需讀取。

---

## 核心原則

> **驗收條件是契約**：用戶和執行者之間的明確約定，雙方都能清楚判斷任務是否完成。

### 4V 原則

| 原則 | 說明 | 判斷標準 |
|------|------|---------|
| **可驗證 (Verifiable)** | 能明確判斷完成/未完成 | 有具體確認方法 |
| **可量化 (Quantifiable)** | 明確列出項目數量 | 有編號和總數 |
| **可追溯 (Traceable)** | 引用設計文件來源 | 有來源連結 |
| **可記錄 (Documented)** | 要求完成證據 | 有狀態標記 |

## 驗收情境分類

不同的驗收情境需要不同的確認方法和證據類型。

| 情境 | 說明 | 典型項目 | 主要確認方法 |
|------|------|---------|-------------|
| **功能驗收** | 程式功能是否正確實作 | 子命令、API、Widget | 執行命令、執行測試 |
| **流程驗收** | 開發流程是否正確執行 | 測試通過、品質檢查 | 執行測試、狀態檢查 |
| **文件驗收** | 文件是否正確更新 | SKILL.md、worklog | 檔案檢查 |
| **建議驗收** | 建議是否被正確處理 | 採納/拒絕決定 | 清單核對 |

### 情境判定規則

| 驗收項目關鍵字 | 對應情境 |
|---------------|---------|
| 「實作」「建立」「功能」「子命令」 | 功能驗收 |
| 「測試通過」「lint」「analyze」「品質」 | 流程驗收 |
| 「更新」「撰寫」「文件」「README」 | 文件驗收 |
| 「建議」「採納」「拒絕」「處理」 | 建議驗收 |

## 強制驗收維度：集中化（i18n / 常數 / token）

**適用**：任何含 UI 產出的 IMP ticket（新增/修改畫面、widget、樣式、user-facing 文字）。

含 UI 的 IMP 完成前，acceptance 必含一條集中化驗收：本 ticket 引入的 user-facing 文字、顏色、魔術數字皆已集中（i18n key / theme token / 具名常數），無新增裸 `Color()` / 字面字串 / 字面尺寸。

- **Why**：1.2.0-W1-015 根因——框架既有 hook（l10n-sync / style-guardian）對「應有設施缺席」失明，edit-time 強制依賴設施存在才生效。升為 per-feature acceptance gate，使每個功能在驗收時被強制檢查，不再依賴 greenfield 是否 bootstrap 設施。
- **Consequence**（不設此維度）：硬編碼在無 i18n/theme 的專案可暢行至 1.0（v1.0 實證：app 21 文字 / 19 數字 / 18 顏色全程未攔）。
- **Action**：建含 UI 的 IMP 時，acceptance 加一條「集中化：本功能 user-facing 文字→i18n、顏色→token、魔術數字→常數，無新增裸值」，驗收以 grep 確認變更碼無裸 `Color()` / 字面字串。豁免：純後端 / CLI（如 Go server log）依語言慣例可標註豁免理由。

### 證據類型定義

| 證據類型 | 說明 | 格式範例 |
|---------|------|---------|
| **命令輸出** | CLI 命令的執行結果 | `$ ticket track tree {ticket-id}` + 輸出內容 |

| **狀態輸出** | 工具狀態檢查結果 | `dart analyze: 0 issues` |

| 文件驗收 | 檔案存在 或 檔案內容 | 區段存在 |

## 驗收條件禁用規則

| 規則 | 說明 | 違規範例 |
|------|------|---------|
| 禁止「或」連接 | 不可用「或」連接不同方案 | 「移除或實作」 |
| 禁止模糊目標 | 不可有相反的選項 | 「達成 A 或 B（A、B 相反）」 |
| 禁止缺乏業務意圖 | 必須說明為什麼要這樣做 | 只說「一致性」不說明方向 |
| 禁止最低成本陷阱 | 不可設計讓執行者選擇最省力方案 | 「更新文件（可移除或修正）」 |
| 禁止以攔截點替代威脅事件（防護類） | 防護類條件描述威脅事件或最終狀態；攔截點（哪個工具、哪個時機）移至 `how.strategy` 或 Solution | 「寫入設定檔新增註冊時，若目標檔缺可執行位則失敗」 |
| 禁止以書寫動作替代查證程序（全稱結論類） | 要求下全稱結論（已全部、無其他、已閉環）的條件必須寫入查證程序與輸出形式，不可只要求記錄結論 | 「Solution 記錄該檔問題是否已全數閉環」 |

### 防護類驗收條件：威脅事件測試

防護類驗收條件描述**威脅事件或最終狀態**，不寫攔截點——適用於防護、守衛、閘門、檢查類條件（目的為阻止某個壞狀態出現者）。

本節是下方「實質要求與驗證代理指標的分離撰寫」在防護類條件上的具名特例：該節的「項目 vs 確認方法」對應本節的「威脅事件 vs 攔截點」，判別問句形式亦相同。差別在於分離失敗的後果——通用情況下裁決者無法區分「要求沒做到」與「量尺壞了」，防護類情況下則是威脅事件仍可經未涵蓋路徑重現而三層驗證全綠。

**判準問句**：若實作把攔截點換到別處但威脅事件同樣被擋住，這條驗收條件還算通過嗎？答「不算」即表示攔截點已被寫入條文，須改寫。

**反模式與正確措辭的三列對照**見 `.claude/error-patterns/process-compliance/PC-BAL-035-acceptance-wording-locks-interception-point.md`「步驟 1」（該表為權威來源，本節不另存副本）。

- **Why**：驗收條件的職責是描述「什麼狀態算通過」。寫入具體攔截點後，它同時成為設計指令，而測試依它設計、覆核依它重跑、閘門依它勾選——三層驗證共用同一份條文作真值來源，條文自身的覆蓋缺口對整條驗證鏈不可見。實作者也無從察覺偏差：條文既已指定攔截點，滿足條文即為達標，偏離反而像是超出範圍。
- **Consequence**：實作 100% 符合條文、測試全綠、覆核一致，威脅事件仍可經未涵蓋路徑重現。最常見的具體後果是順序依賴——調換操作順序使攔截時機發生在壞狀態產生之前，檢查點必然撲空，而依條文設計的單元測試不會覆蓋該情境。
- **Action**：三步驟，**順序不可調換**——(1) 先列該壞狀態的所有已知產生路徑（工具、自動化流程、版控操作、外部同步）成盤點表；(2) 依盤點結論以威脅事件措辭撰寫條件，涵蓋不足時用「所有路徑」措辭，不預先裁定攔截點；(3) 對「動作發生時檢查」型防護，另加一條要求驗證操作順序調換後仍有效。步驟 1 先行的理由（防護票的真實成形順序是攔截點先於條件，此時判準問句會失效）見參考文件「時序不可調換」段。盤點表欄位與範例見 `.claude/pm-rules/ticket-body-schema.md` 同名節。
- **邊界**：本節約束防護類的威脅描述條目，不影響同一 ticket 其他條目依「驗收條件格式規範」寫出具體指令與時機。「條件必須寫具體指令」與「防護條件不得寫死攔截點」在字面層不可區分，差異只在語意層——該指令是驗收手段（合法）還是防護攔截點（須移位）。此不可區分性使本節無法降為機械檢查，判定責任在撰寫者。

### 全稱結論類驗收條件：查證程序測試

要求執行者下全稱結論（「已全部覆蓋」「無其他實例」「已閉環」）的條件，必須把**產生該結論的查證程序與輸出形式**寫入條文，不可只要求記錄結論。

本節與上方「威脅事件測試」是驗收措辭失誤的兩種不同機制：該節的攔截點落在錯誤的**位置**（寫防護手段而非威脅事件），本節的攔截點落在錯誤的**動作類型**（寫書寫動作而非查證動作）。

**判準問句**：執行者若寫下一個錯誤的結論，這條條件還算滿足嗎？答「算」即表示攔截點落在書寫而非事實，須改寫。

**反模式與正確措辭的四列對照**見 `.claude/error-patterns/process-compliance/PC-BAL-049-acceptance-wording-accepts-false-universal-conclusion.md`「解決方案」（該表為權威來源，本節不另存副本）。

- **Why**：「記錄」「說明」「填寫」是書寫動作，完成條件是「有沒有寫」；「掃描並逐一判定」是查證動作，完成條件是「查了沒有、怎麼查的」。條件用前者措辭時，內容正確與否從一開始就不在驗收範圍內。全稱結論尤其危險——「已修復 X」看 diff 可證，「無其他同類問題」需掃過全部候選集合，而執行者剛完成修復，傾向以「我改的地方都對」推論「整體沒問題」，但全稱結論不能由單稱結論推得。
- **Consequence**：錯誤的全稱結論使所有訊號一致為綠（條目勾選、測試通過、閘門放行），缺口只在下一位讀者恰好獨立複驗時才暴露；若無人複驗，該結論成為後續決策的前提。
- **Action**：把「結論」換成「產生結論的程序 + 程序的輸出」——條文指定列舉指令與輸出形式後，驗收者可用同一指令複跑比對。派發時亦須把查證程序寫進 prompt，不要只寫「確認是否閉環」。
- **高發位置**：系列性修復任務的最後一張票。該類票天然要求「完成後閉環」的全稱結論。
- **驗收方責任**：遇到「已閉環」「無其他」「已全部」等宣稱時獨立跑一次列舉，不採信回報。成本通常是一行指令。

### 違規拆解範例

**錯誤寫法**：「SKILL.md 只列已實作指令，或實作缺失指令」

**問題分析**：兩個相反方案（移除 vs 實作）用「或」連接；執行者會選擇最低成本方案（移除）；業務意圖不明確（這些是規劃功能還是錯誤記錄？）。

**正確做法**：先確認業務意圖 → 選擇一個方案 → 設計對應驗收條件。
- 若為規劃功能：「保留未實作指令描述，新增『規劃中』標記，建立實作 Ticket」
- 若為錯誤記錄：「移除未實作指令描述，記錄移除原因」

## 條件式驗收條件的設計判準

> **定位**：AC 撰寫階段預先避免「爭議需要臨場裁決」的缺口。裁決時的完整判準、判別問句、PM 操作流程見 `.claude/pm-rules/verification-framework.md`「驗收條件爭議裁決框架」。

### checkbox 的工具限制：無 N/A 狀態

Ticket 系統的 AC 用 `[ ]` / `[x]` 表達完成狀態，僅有二元狀態，沒有「不適用」或「尚未到期」的第三態。撰寫條件式 AC（「X 完成後做 Y」）時，若不預先規劃前提未成立時的表達方式，裁決者事後只能在「勾選（遷就工具）」與「改寫 AC 文字（遷就工具）」兩個錯誤選項間選一個——兩者都是讓工具的二元限制反過來扭曲業務事實。

**正確設計**：條件式 AC 應搭配 `blockedBy` 欄位使用，而非依賴改寫 AC 文字表達依賴關係。

| 反模式 | 正確做法 |
|-------|---------|
| AC 寫「X 完成後做 Y」，未設 `blockedBy`，前提未成立時裁決者臨場決定勾選或改寫 | AC 建立時即標註對應的前置 ticket，並在 frontmatter 設 `blockedBy: [<X 對應 ticket ID>]` |
| 前提未成立時把 AC 改寫成「已符合」以求 complete | 前提未成立時 ticket 狀態退回/維持 `pending`，AC 保留未勾選，靠 `blockedBy` 表達等待關係 |

**判別問句**：撰寫「X 完成後做 Y」形式的 AC 前，自問——若 X 之後 Y 仍然要做，此 AC 應該如何表達「Y 現在還沒到該驗證的時候」，而不是「Y 已經完成」或「Y 不適用」？答案通常是 `blockedBy`，不是改寫 AC 文字。

### 實質要求與驗證代理指標的分離撰寫

AC 的「項目」欄位（見上方必要欄位定義）描述的是**實質要求**（業務事實）；「確認方法」欄位描述的是**驗證代理指標**（可執行的觀察管道，用來逼近實質要求是否達成）。兩者撰寫時必須分離陳述，不可讓確認方法的措辭反過來定義了實質要求的邊界。

**判別問句**：若把「確認方法」欄位的驗證管道修正後重新驗證，「項目」欄位陳述的完成與否結論會不會因此改變？不會，代表兩者已分離撰寫；若答案是「項目和確認方法根本是同一句話，改了確認方法等於改了項目」，代表兩者混為一談，裁決時將無法區分「要求沒做到」與「量尺壞了」。

**反例**：「項目」寫「grep 命中數為 0」——此時實質要求與驗證方法合一，一旦驗證管道本身有缺陷（如例外清單不完整），裁決者無法區分「要求沒做到」與「量尺壞了」，因為 AC 原文根本沒有留下實質要求的獨立表述可供對照。

**正確寫法**：「項目」寫業務事實（如「規則變更後，受影響代理人定義已同步更新」），「確認方法」才寫「grep 命中數為 0（例外清單：...）」。驗證方法出錯時，只需修正確認方法欄位，項目欄位（實質要求）不受影響。

**具名特例**：防護類條件的「威脅事件 vs 攔截點」是本原則的特例，見上方「防護類驗收條件：威脅事件測試」節。該特例額外要求先做產生路徑盤點，因為防護類的「實質要求」邊界（壞狀態有幾條產生路徑）在盤點前對撰寫者不可見。

### 與 acceptance 漂移反模式的邊界

上述設計判準**不是**放寬驗收標準的授權。分離撰寫「實質要求」與「驗證代理指標」是為了讓裁決時能精確定位問題出在哪一層，不是讓執行者藉此弱化實質要求本身。實質要求的措辭仍須遵守本文件上一節「驗收條件禁用規則」（禁「或」連接、禁模糊目標、禁缺乏業務意圖、禁最低成本陷阱）；若實質要求本身未達成卻以「這只是驗證方法問題」為由試圖放行，屬 acceptance 漂移（見 `PC-055`），必須依實況判定未完成。

## 交付物約束相容性

> **上位原則**：acceptance 必須在代理人操作約束內可達成。交付物本身所受的內容約束是代理人的操作前提，acceptance 若要求違反該約束的內容，代理人只能靜默改寫或靜默違規——兩者皆破壞 acceptance 的契約語意（「用戶和執行者之間的明確約定」）。本節定義當交付物受內容約束時，PM 如何撰寫相容的 acceptance。

### 框架資產交付物與規則 8

**交付物為 `.claude/` 框架檔案時，acceptance 不得要求交付物包含專案層級識別符（ticket ID、專案名稱等）。**

**Why**：框架檔案受 `.claude/references/reference-stability-rules.md` 規則 8 約束——禁止包含專案 ticket ID、worklog 路徑、專案名稱等只存在於當前專案的識別符（sync 到其他專案後為死連結）。若 acceptance 要求「交付物含某 ticket 的結論」或「交付物引用某專案名稱」，代理人面臨二選一：違反規則 8（將專案識別符寫入框架檔案），或靜默改寫 acceptance 語意後仍勾選完成。

**Consequence**：量化實證顯示框架資產 ticket 中 11.2% 的 acceptance 含其他 ticket ID，其中約 27% 為 demand-in-deliverable 型（要求交付物本身包含該識別符）。已有兩次實證暴露代理人處置不一致：一次主動回報改寫（docstring 案例），一次靜默改寫未回報（error-pattern 案例）。acceptance 勾選狀態不再反映字面達成，稽核者讀 acceptance 會誤以為識別符存在於交付物中；可追溯性靜默流失，且是否流失取決於個別代理人自主判斷。

**Action**：PM 撰寫 `where.files` 含 `.claude/` 的 ticket 的 acceptance 時，改用規則 8 白名單替代錨點（見下表）。

#### acceptance 引用型別判準

並非所有 acceptance 中出現 ticket ID 都構成衝突。區分兩種型別可避免誤禁合法引用：

| 型別 | 定義 | 合法性 | 範例 |
|------|------|--------|------|
| **demand-in-deliverable** | acceptance 要求交付物本身包含專案識別符（「含」「引用」+ ticket ID 或專案名稱） | **禁止** | 「交付物含某 ticket 的修法結論」「註解引用某 ticket」 |
| **context-reference** | acceptance 引用 ticket ID 作為輸入/背景/比較基準，不要求識別符出現在交付物中 | **合法** | 「以某 ticket 的非法值為測試輸入」「格式與某 ticket 的產出一致」 |

**判別問句**：「這條 acceptance 是否要求 ticket ID / 專案名稱出現在 `.claude/` 交付物的文字內容裡？」是 → demand-in-deliverable（禁止）；否 → context-reference（合法）。

#### 規則 8 白名單替代錨點

demand-in-deliverable 型的識別符須改為以下規則 8 允許的形態（沿用既有機制，不另造）：

| 替代錨點 | 適用情境 | 範例 |
|---------|---------|------|
| 日期 | 實測事件的時間標記 | 「2026-07-29 全量測試的實測依據」 |
| 框架 issue 引用 | 跨 consumer 的修法/議題追蹤 | 「`claude#50` 的修法結論」 |
| 描述性事件標籤 | 框架內案例敘事 | 「某次 full overlay 導致 7 檔遺失的實證」 |
| error-pattern ID | 框架內部分類識別 | 「IMP-BAL-006 的根因分析」 |
| `canonical_issue` frontmatter | error-pattern 的 canonical 去重錨點 | 欄位值 `tarrragon/claude#50`（既有欄位，多數檔案為 null） |

**邊界**：ticket body 的 Context Bundle、Rationale Chain、source_ticket 等欄位位於 `docs/work-logs/` 下的 ticket 檔案，不在 `.claude/` 交付物內，不受本條款約束——這些欄位可自由使用專案 ticket ID 作為跨票追溯。

### （預留：acceptance 引用驗證手段的存在性查證）

> 本節與上節同屬「交付物約束相容性」上位原則的子類型。上節處理「交付物受內容禁制約束」（規則 8 相容性），本節預留處理「acceptance 引用的驗證手段本身是否存在」（如命令旗標、API 端點的可用性）。兩者共同擴展 4V 原則的「可驗證」維度：不僅要求驗證方法可執行，還要求驗證方法的前提（內容約束、工具存在性）不與 acceptance 矛盾。待相關分析完成後落地。

## 業務意圖要求

### 必填欄位

每個 Ticket 的驗收條件必須包含業務意圖說明：

| 欄位 | 說明 | 範例 |
|------|------|------|
| 業務目標 | 這個任務要達成什麼業務價值 | 「保留規劃功能，確保後續可實作」 |
| 期望結果 | 完成後應該是什麼狀態 | 「所有規劃功能都有實作 Ticket」 |
| 禁止結果 | 完成後不應該是什麼狀態 | 「不可損失規劃中的功能」 |

### 業務意圖確認問題

撰寫驗收條件前，必須回答以下問題：

| 問題 | 目的 | 範例回答 |
|------|------|---------|
| 這個任務要解決什麼問題？ | 確認問題定義 | 「SKILL.md 與實作不一致」 |
| 問題的根本原因是什麼？ | 防止只處理表面症狀 | 「文件記錄了規劃中的功能」 |
| 理想的解決結果是什麼？ | 確認期望狀態 | 「文件與實作一致，且保留規劃功能」 |
| 什麼結果是不可接受的？ | 設定禁止邊界 | 「損失規劃中的功能」 |

### 不一致問題的處理規則

當發現「文件 vs 實作」不一致時，必須先判斷不一致的性質：

| 情況 | 判斷依據 | 正確處理 | 錯誤處理 |
|------|---------|---------|---------|
| 規劃中的功能 | 文件有設計、有預期用途 | 保留標記 + 建立實作 Ticket | 移除描述 |
| 錯誤記錄 | 無設計依據、無預期用途 | 移除描述 | 建立實作 Ticket |
| 過時功能 | 曾經實作但已移除 | 標記為 deprecated | 直接移除 |
| 重命名/移動 | 功能存在但位置不同 | 更新文件引用 | 重複實作 |

## 方案評估矩陣

### 評估維度

選擇方案前，必須評估以下維度：

| 評估維度 | 問題 | 必填 |
|---------|------|------|
| 技術可行性 | 這個方案技術上可行嗎？ | 是 |
| **業務價值** | 這個方案符合業務意圖嗎？ | **是** |
| **副作用評估** | 這個方案會損失什麼？ | **是** |
| **替代方案** | 有沒有更好的方案？ | **是** |
| 長期影響 | 這個方案對未來有什麼影響？ | 建議 |

### 評估範例

| 方案 | 技術可行 | 業務價值 | 副作用 | 結論 |
|------|---------|---------|--------|------|
| 移除未實作指令 | 簡單 | 損失規劃功能 | **高** | **拒絕** |
| 實作缺失指令 | 可行 | 保留功能 | 無 | 考慮 |
| 保留標記 + 建立 Ticket | 可行 | 規劃清晰 | 無 | **採用** |

**關鍵洞見**：「移除」方案技術上最簡單，但業務價值最低，副作用最高。

### 方案選擇規則

| 規則 | 說明 |
|------|------|
| 禁止只考慮技術可行性 | 必須同時考慮業務價值和副作用 |
| 最低成本方案需警惕 | 最簡單的方案往往有隱藏的業務成本 |
| 不可逆操作需謹慎 | 移除、刪除等操作需要確認是否正確 |
| 替代方案必須考慮 | 不可只評估單一方案 |

## 驗收條件設計檢查清單

> **重要**：在撰寫驗收條件前完成此檢查清單，避免設計缺陷導致驗收問題。

### 4V 原則檢查

- [ ] 每個項目都**可驗證**（有明確的確認方法，非「完成」「正常」）
- [ ] 每個項目都**可量化**（有具體數字或逐項清單，非「所有」「相關」）
- [ ] 每個項目都**可追溯**（有來源引用，如 SKILL.md L97）
- [ ] 每個項目都**可記錄**（結果可以寫入文件，有證據類型）

### 禁止規則檢查

- [ ] 沒有使用「或」連接多個選項（如「移除或實作」）
- [ ] 沒有使用模糊詞彙（「適當」「正常」「完成」「相關」）
- [ ] 沒有合併不同層級的需求在同一項目
- [ ] 沒有讓執行者可選擇最低成本方案的設計

### 業務意圖檢查

- [ ] 驗收條件與業務目標一致（解決正確的問題）
- [ ] 沒有「技術正確但業務錯誤」的風險
- [ ] 考慮了方案的負面副作用
- [ ] 不可逆操作（刪除、移除）已確認業務意圖

### 完整性檢查

- [ ] 每個需求都有對應的驗收條件
- [ ] 需要逐項列出的項目已**逐項列出**（非籠統描述如「所有標記移除」）
- [ ] 複合需求已拆分為獨立的驗收項目
- [ ] 涉及多個檔案/功能的任務，每個都有獨立驗收項目

### 交付物約束相容性檢查

- [ ] `where.files` 含 `.claude/` 時，acceptance 無 demand-in-deliverable 型專案識別符（ticket ID / 專案名稱要求出現在交付物中）
- [ ] demand-in-deliverable 型已改為規則 8 白名單替代錨點（日期 / `claude#NN` / 描述性標籤 / error-pattern ID）
- [ ] context-reference 型保留（引用 ticket ID 作背景/輸入，不要求出現在交付物中）
