# 引用穩定性規則

> **本檔承載原 `.claude/rules/core/document-format-rules.md` 規則 7-8**。規則 1-6、YAML frontmatter、檢查清單骨架仍保留在 document-format-rules.md 自動載入。

本文件定義「引用穩定性」相關規範：規格文件的引用穩定性（規則 7）和框架文件對專案層級識別符的引用禁制（規則 8）。兩者共享「哪些來源可信、哪些引用會在時間或跨專案 sync 中失效」的核心主題。

| 情境 | 涉及規則 |

## 規則 7：規格文件引用穩定性

**規格文件（docs/spec/、docs/use-cases.md）禁止引用臨時性文件**

| 文件類型 | 穩定性 | 可被規格引用 |
|---------|--------|------------|
| 規格文件（docs/spec/） | 穩定 | 是 |
| Use Cases（docs/use-cases.md） | 穩定 | 是 |
| 提案文件（docs/proposals/） | 穩定 | 是 |
| CLAUDE.md | 穩定 | 是 |
| Worklog（docs/work-logs/） | 臨時 | **否** |
| Ticket 檔案 | 臨時 | **否** |
| Plan 檔案 | 臨時 | **否** |

**允許的例外**：
- 變更歷史中記錄 Ticket ID 作為「來源標注」（如：「本次變更由 0.17.0-W1-002 執行」）
- 這是記錄歷史事實，不是建立依賴

**禁止的模式**：

| 禁止 | 原因 | 正確做法 |
|------|------|---------|
| `詳見 v0.17.1 W1-001` | Ticket 可能被遷移、刪除、重新編號 | `待定義於匯出規格章節` 或直接在此定義 |
| `參考 docs/work-logs/v0.17/...` | Worklog 會被歸檔，路徑可能失效 | 引用對應的 spec 文件 |
| `依 0.18.0-W2-001 的分析結論` | 結論應提煉為規格，而非依賴分析過程 | 將結論寫入規格文件 |

**理由**：
- 規格文件是開發的**唯一穩定依據**，worklog 和 ticket 是**過程記錄**
- 過程記錄可能遺失、修改、遷移，規格文件不應依賴不穩定來源
- 如果規格需要引用的資訊尚未定義，標記為「待定義」而非指向臨時文件

## 規則 8：框架文件禁止引用專案層級識別符

**`.claude/` 框架文件禁止引用專案特定的 ticket ID、worklog 路徑等專案層級識別符（commit hash 條件允許，見下「實證錨點型」章節）**

`.claude/` 是**跨專案共用框架**，透過 sync 機制同步到多個專案（如 `.claude/skills/sync-push`、`sync-pull`）。專案層級識別符只存在於當前專案，sync 到其他專案後會變成死連結和誤導性資訊。

| 識別符類型 | 範例 | 可在框架文件引用？ |
|---------|------|-----------------|
| 專案 ticket ID | `0.18.0-W5-001`、`W2-007` | **否** |
| 專案 commit hash | `8f74d08`、`abc1234` | **條件允許**（實證錨點型，見下「實證錨點型：commit hash 的條件允許」章節） |
| 專案 worklog 路徑 | `docs/work-logs/v0.17/...` | **否** |
| 專案 proposals ID | `PROP-007` | **否**（除非已提煉為方法論） |
| 框架 error-pattern ID | `PC-050`、`IMP-003`、`ARCH-002` | **是**（框架內部分類） |
| Claude Code 版本號 | `CC 2.1.97` | **是**（外部平台識別） |
| 框架檔案路徑 | `.claude/rules/core/pm-role.md` | **是**（框架內部結構） |

**適用範圍**（與守衛 `reference-stability-rule8-guard-hook.py` 的 `SCAN_PREFIX` 判準一致，不逐目錄列舉）：

`.claude/` 全域（含所有現有與未來新增的子目錄，如 `.claude/config/`、`.claude/lib/`）皆適用規則 8；唯一豁免路徑前綴為 `.claude/handoff/archive/`（歷史紀錄，合理保留原樣）。此描述對齊守衛程式碼的 `SCAN_PREFIX = ".claude/"` + `EXEMPT_DIR_PREFIX = ".claude/handoff/archive/"` 邏輯——新增子目錄自動落入規則 8 範圍，不需回頭補表，一致性不依賴人工逐目錄同步。

| 範圍 | 適用規則 8？ | 備註 |
|------|-------------|------|
| `.claude/` 下所有子目錄與檔案（含 `rules/`、`pm-rules/`、`references/`、`methodologies/`、`agents/`、`skills/`、`best-practices/`、`config/`、`lib/` 等） | 是 | 全域判準，本列為說明範例非窮舉，新增目錄自動涵蓋 |
| `.claude/error-patterns/` 內容（檔名除外） | 是 | 檔名本身為框架內部分類（見上「識別符類型表」），非本規則的豁免對象 |
| `.claude/hooks/` Python docstring/comment | 是 | 同上，全域規則的一部分，非獨立子範圍 |
| `.claude/handoff/archive/` | **否**（唯一豁免路徑前綴） | 歷史紀錄，合理保留 |
| 專案 `docs/` | **否**（不在 `.claude/` 下） | 專案內部，可引用 |
| `CLAUDE.md` | **否**（不在 `.claude/` 下） | 專案入口，可引用 |

**Memory 和 ticket 也是專案層級**：

用戶/專案 auto-memory（`~/.claude/projects/<project>/memory/`）和 ticket（`docs/work-logs/`）**都不會跨專案 sync**，所以「把原則寫到 memory」不能取代框架規則。需要跨專案落實的原則必須寫入：
- `.claude/rules/`（自動載入規則）
- `.claude/error-patterns/`（錯誤學習經驗）
- `.claude/methodologies/`（方法論）

**禁止的模式**：

| 禁止 | 五類分類（見下「引用性質判準」） | 改為 |
|------|------|------|
| `（來源：0.18.0-W4-002）` | 論證依據型 | `（防範 Hook error 干擾代理人判斷）` |
| `（W5-021 教訓）` | 論證依據型 | `（多代理人 permissionMode 批次修復教訓）` |
| `**Ticket**: 0.17.3-W12-001`（在 error-pattern 內） | 論證依據型 | 移除整行（檔名 PC-XXX 已是足夠識別） |
| `來源：PROP-007` | 論證依據型 | 以提案內容的抽象描述取代 |
| `# 遷移後此處改用 X（W-xxx）` | 時點標注型 | `# 遷移後此處改用 X`；需要時間資訊時改標日期 |
| `W-xxx 事件中用戶發現...`（案例敘事） | 案例敘事主詞型 | 改描述性標籤，如「某次全域物件缺失崩潰事件中用戶發現...」 |

**允許的例外**：

| 例外 | 說明 |
|------|------|
| error-pattern 檔名本身 | `PC-050-premature-agent-completion-judgment.md` 是框架內部分類 |
| 觸發日期 | 「2026-04-12 新增」可保留，日期不是專案識別符 |
| 通用 CC 能力版本號 | 「CC 2.1.97 新增 /agents 分頁」屬外部平台能力 |
| 被說明對象型 ticket ID（白名單路徑） | 見「引用性質判準」第 4 類，如 `ticket-id-conventions.md` 中作格式範例展示的 ID |
| 測試資料型 ticket ID（測試路徑內） | 見「引用性質判準」第 5 類，測試檔內作為被測資料的 ID |
| 實證錨點型 commit hash（`error-patterns/` 實證段落，敘事自足） | 見下「實證錨點型：commit hash 的條件允許」章節。**注意**：此為 commit hash 專屬的獨立判準，非上方 ticket ID 五類分類的第六類 |

**理由**：
- `.claude/` 經 sync 跨專案共用，專案識別符在其他專案是死連結
- 框架文件的價值在於**抽象原則**，專案引用是耦合而非依賴
- Memory/ticket 也是專案內部，不能承擔跨專案原則的傳遞責任

### 引用性質判準：全禁原則與五類分類

> **本章節定位**：規則 8 上文是「載體 + 識別符類型」維度的禁制（哪些檔案、哪類識別符）。本章節定義「引用性質」維度的判準——ticket ID 在框架文件中的任何出現，除落入下方兩個機械可判定的豁免類別，一律禁止（全禁原則）。本章節取代原「依賴型 / 歷史錨點型」兩類判準，對應關係見章末「與舊兩類判準的對應」。**權威關係**：`.claude/agents/AGENT_PRELOAD.md` 規則 12 是本章節的自動載入速查版，供代理人改框架檔案時即時查表；兩者判準內容如有出入，一律以本章節（規則 8）為準，速查版須修正對齊，不得反向要求本章節開豁免遷就速查版舊表述（曾有分析誤依速查版的舊兩類判準下結論，反向建議本章節加豁免註，方向已反轉並修正速查版）。

**Why**：框架檔案禁止以 ticket ID 承載推理依據——ticket 是過程記錄載體，只存在於當前專案，sync 到其他專案後查無此票。簡單理由應直接寫進註解，重要邏輯概念應先提煉為方法論再引用方法論路徑，兩者皆不依賴 ticket ID 即可被讀者理解。舊兩類判準的操作依據「移除 ID 後能否理解」需逐句語意判斷，守衛只能退而偵測句型（如「詳見」「來源：」），必然漏掉不用該句型的依賴型引用。

**Consequence**：語意判準的執行落差會隨 session 數與代理人數累積——不同代理人對同一句型可能給出不同分類，守衛偵測不到的漏網引用持續存在。且未命名的引用型態（測試 fixture、格式說明文件的被說明對象、案例敘事主詞）若未先分類就套用全禁，機械守衛初次執行即產生大量誤報；依 ARCH-016 失效模式，該守衛會在誤報壓力下被停用或加旁路，全禁等於沒做。

**Action**：改採全禁為預設，僅開放兩個路徑可機械判定的豁免類別（被說明對象型、測試資料型）；其餘引用一律視為需移除，依五類分類表決定移除後的具體處置。

#### 五類分類

| # | 類別 | 判準（移除 ID 後的可理解性測試） | 處置 |
|---|------|------|------|
| 1 | 論證依據型 | 移除 ID 後句子語意不完整，讀者需查該 ticket 才能理解本句 | 禁止：移除。依兩層分流補寫理由（見下） |
| 2 | 時點標注型 | 移除 ID 後語意完整，ID 僅標「何時改的」，不提供額外理解 | 禁止：移除。需要時間資訊時改用日期（規則 8 主表已允許日期） |
| 3 | 案例敘事主詞型 | ID 作為案例 / 事件的識別標籤（如「W-xxx 事件中...」），功能是命名而非導向查證 | 改描述性標籤（如「某次全域物件缺失崩潰事件」），標籤本身須不依賴 ID 即可理解 |
| 4 | 被說明對象型 | ID 是文件說明的主題本身（文件職責即展示 / 定義 ticket ID 格式），非指向其他內容的引用 | 豁免：限白名單路徑（見下） |
| 5 | 測試資料型 | ID 出現於測試檔案作為輸入值或斷言值，等同字串字面量 | 豁免：限測試路徑（見下） |

第 1-3 類判準延續舊判準的操作方法（移除測試），差異在於：第 2 類（原可保留的歷史錨點型）現改為禁止——理由已寫出時 ID 不提供額外資訊，需要時間資訊則日期即可完成同一功能且跨專案有意義；第 3 類（案例敘事主詞型）為舊判準未命名的型態，實測顯示其為 error-patterns 類文件的最大宗引用型態。

#### 機械可判定性：守衛只需判定豁免

前三類（論證依據型、時點標注型、案例敘事主詞型）處置雖不同——依序為「移除且依兩層分流補寫理由」「移除改日期」「改描述性標籤」——但**共同前提都是移除該 ticket ID**，差異僅在移除後補什麼，不影響「是否該移除」的判斷。

因此守衛不需逐句語意判斷屬於第幾類，只需判定一件事：**該 ticket ID 出現位置是否落在第 4 類或第 5 類的豁免路徑**。豁免路徑判定是路徑字串比對，不涉及語意理解，可完全機械化：

| 判定步驟 | 機制 | 是否需要語意理解 |
|---------|------|----------------|
| 1. 樣式偵測 | 命中 ticket ID 樣式（版本化或裸格式）即為候選 | 否，純正則 |
| 2. 豁免判定 | 候選所在檔案路徑符合第 4 類白名單或第 5 類測試路徑樣式 | 否，路徑字串比對 |
| 3. 判定結果 | 未落入豁免 → 觸發告警（不需再細分第幾類，處置皆為「移除」） | 否 |

守衛偵測規則與路徑樣式的具體實作獨立追蹤，不在本文件重複。

#### 兩層分流指引：簡單理由寫進註解，重要概念先寫方法論再引用

第 1 類（論證依據型）移除 ticket ID 後，原本承載的推理依據不可憑空消失，須依內容重量分流：

| 分流 | 適用情境 | 做法 |
|------|---------|------|
| 簡單理由 → 寫進註解 | 一兩句話可交代清楚，理由只在此處成立，不需外部追溯 | 直接在引用處內聯改寫為自足 WHY（範例見下「框架 code 邏輯註解的識別符衛生」） |
| 重要邏輯概念 → 先寫方法論再引用方法論 | 概念可被複用（跨檔案 / 跨情境皆適用的判準、決策框架、設計原則） | 先在 `.claude/methodologies/` 建立或擴充對應方法論，原引用處改為指向方法論路徑 |

**判別準則**：問「這段推理依據只在這一處成立，還是換個情境也適用？」只在此處成立 → 寫進註解；換情境也適用 → 先寫方法論。「不知道該寫註解還是寫方法論」本身即訊號——寫不進一兩句註解，通常代表概念重要到該提煉為方法論。

#### 第 4 類白名單（被說明對象型）

| 路徑 | 符合原因 |
|------|---------|
| `.claude/references/ticket-id-conventions.md` | 文件職責即定義 ticket ID 格式規範，文中出現的 ID 是被說明的格式範例本身，非指向其他內容的引用 |

**成員上限**：本類白名單維持不超過 3 個檔案。若後續擴張超過 3 個檔案，改採可陳述的通用條件（如「文件主體目的即為展示或定義 ticket ID 格式」）取代逐檔列舉，避免走向與 ARCH-BAL-003 相同的成員清單漂移問題。

#### 第 5 類豁免路徑（測試資料型）

路徑滿足以下任一條件即豁免：

| 條件 | 範例 |
|------|------|
| 路徑含 `/tests/` 目錄區段 | `.claude/hooks/tests/test_xxx.py` |
| 檔名符合 `test_*.py` 或 `*_test.py` 樣式 | `test_ticket_builder.py` |

具體正則與守衛整合實作獨立追蹤，不在本文件定義。

#### 判準單位：整句 / 整個引用事件

同一句或同一括號內常同時出現多個 ticket ID（如「來源：A、B 實證」）。逐 ID 個別判定會出現同句一半判「移除」、一半判「語意完整」的破碎結果，難以據以修改。移除測試以「整句 / 整個引用事件」為單位——句中任一 ID 已提供足以理解本句的說明即整句視為語意完整（進入第 2 / 3 類判斷，ID 仍須移除，差別在改寫難度）；句中完全無 ID 帶說明才整句視為第 1 類。

#### 內聯說明的實質性判準：短標籤 vs 實質說明

「括號內是否有說明」若只看「有無括號」會誤判——`W10-011（擴充註解規則）` 的括號只是主題標籤，複述標題，並未交代 W10-011 實際的規則內容，讀者仍須開啟該 ticket 才能理解，應判第 1 類；而「（worktree 隔離對 daemon-rooted dart MCP 寫入工具不生效）」的括號是完整子句，直接陳述具體事實，讀者不需開啟該 ticket，屬語意完整（進入第 2 / 3 類判斷）。判定括號內容時追加子測試——「括號內容本身是否已陳述具體事實 / 機制（一個完整子句），而非僅複述主題或標題」：

| 括號內容 | 判定 |
|---------|------|
| 複述主題 / 標題（名詞短語，未陳述事實） | 視同無說明，第 1 類 |
| 陳述具體事實 / 機制（完整子句） | 視為有效內聯說明，進入第 2 / 3 類判斷；但第 2 / 3 類本身仍禁止 ID 留存，僅差在「內容已交代清楚」影響改寫難度而非是否可保留 ID |

**與「相關文件」章節列舉的邊界**：「相關文件」章節列 `W10-011（擴充註解規則）` 判第 1 類，原因有二疊加——括號僅主題標籤，且「相關文件」章節本身的存在目的就是列出「需要時去查」的清單，脈絡本身已是指向動作。即使補上實質說明，仍建議改用檔案路徑（規則 8 主表允許框架檔案路徑）而非 ticket ID，以維持該清單「可直接點開」的操作價值。

#### 正反範例

第 1-3 類（禁止，一律移除）：

| 引用 | 類別 | 移除測試 | 修正 |
|------|------|---------|------|

### 實證錨點型：commit hash 的條件允許

> **本章節定位**：識別符類型表原列「專案 commit hash：否」，本章節將其改為「條件允許」。此判準與上方「引用性質判準」五類分類同屬規則 8，但適用對象不同——五類分類處理 **ticket ID** 的引用性質判準，本章節處理 **commit hash** 的條件允許判準。兩者是規則 8 下並列的獨立判準，**本章節不是五類分類的第六類**：五類分類「前三類一律移除」的處置邏輯僅適用 ticket ID，不因本章節鬆動。

**Why**：ticket ID 與 commit hash 雖同屬「專案層級識別符」，功能維度不同——ticket ID 的主功能是路由（讀者須跟進該 ticket 才能理解論證，移除常使論證不完整），commit hash 的主功能是驗證（讀者不需 hash 即可理解案例敘事，hash 提供 `git show` 審計能力，移除幾乎不影響理解）。同一套「全禁」判準套用在功能維度不同的識別符上會誤傷——全面禁止 commit hash 會使 error-pattern 實證段落失去可查證性，而實證段落存在的意義正是「可查證」，移除查證手段只剩敘事文字的自我宣稱。

**Consequence**：不區分兩者會讓實證段落陷入選擇困境——要嘛違規保留 hash（規則字面禁止），要嘛全數改為描述性標籤（實作成本高，且失去 `git show` 可驗證的審計能力，這是 ticket ID 案例不具備的損失維度）。

**Action**：commit hash 改為「條件允許（實證錨點型）」，條件是「移除 hash 後周圍敘事仍可理解」——與 ticket ID 的「一律移除」邏輯不同，不要求移除，而是要求移除後不影響理解（敘事自足性），hash 本身視為附加的可驗證性標記，非理解所需的必要元件。

#### 條件定義

| 條件 | 判準 | 說明 |
|------|------|------|
| 敘事自足 | 移除 hash 後，周圍文字仍可理解案例要點（讀者不需 `git show` 即能掌握「發生了什麼」） | 若 hash 是敘事中唯一的案例識別（如僅以 hash 區分兩個相似案例），移除後讀者無法區分，需補描述性標籤使之自足 |
| 附日期 | commit hash 出現處建議鄰近標注日期（如「2026-07-28 案例」） | 日期提供時點脈絡，hash 提供驗證錨點，兩者互補而非重複 |

**判別準則**（移除測試，與 ticket ID 判準同構但結論不同）：問「移除這個 hash 後，讀者還能理解這句在說什麼案例嗎？」能 → 實證錨點型，條件允許保留；不能（hash 是唯一的案例識別）→ 需補描述性標籤補足自足性，hash 本身仍可保留（不像 ticket ID 依賴型須被移除）。

#### sync 後的失效模式：有害 vs 無害

| 識別符 | sync 後失效模式 | 有害性 |
|--------|----------------|--------|
| ticket ID（第 1/2 類，一律移除） | 死連結，讀者被引導查一個不存在的 ticket，論證斷裂 | 有害 |
| commit hash（實證錨點型，符合自足性條件） | hash 成為惰性文字，敘事本身仍完整，僅失去 `git show` 審計能力 | 無害（僅失審計，不失理解） |

類比：ticket ID 像學術論文的 in-text citation（讀者理解論證所需）；commit hash 像 footnote reference number（可供查證但非理解論證所必需）。

#### 守衛豁免的機械可判定性

沿用「引用性質判準」章節建立的原則——守衛不做語意判斷，只做機械偵測：

| 判定步驟 | 機制 | 是否需要語意理解 |
|---------|------|----------------|
| 1. 樣式偵測 | commit hash 樣式（7-40 位十六進位字元，前後無其他英數字元）即為候選 | 否，純正則 |
| 2. 位置豁免 | 候選位於 `.claude/error-patterns/` 目錄的實證 / 案例 / 事件段落（可綁段落標題關鍵字或位置標記） | 否，路徑 + 段落位置比對 |
| 3. 判定結果 | 落在豁免範圍 → 放行；其餘位置（非 `error-patterns/` 目錄，或 `error-patterns/` 內規則正文 / 防護條款而非實證段）→ 循一般規則 8 識別符判定 | 否 |

「敘事自足性」本身無法機械判定（需語意理解才能判斷「移除後是否仍可理解」），故守衛只做「位置 + 樣式」兩層機械篩選，自足性要求維持為撰寫者與 reviewer 的人工判定責任——這與「硬性強制的範圍：樣式偵測可機械化，改寫品質仍需人工判定」章節的原則一致：樣式偵測可機械化，改寫品質（本例為敘事自足性）仍需人工判定。守衛的具體正則與段落位置偵測實作獨立追蹤，不在本文件定義。

`.claude/error-patterns/` 目錄的 ticket ID 清理工作（案例敘事主詞型 ticket ID 依慣例改為描述性標籤）與本章節裁決正交：commit hash 不是 ticket ID，不在該清理範圍。commit hash 依本章節「實證錨點型」條件獨立處置——符合自足性條件即保留，不需改寫為描述性標籤。此為銜接說明，記錄於本檔供該清理工作參照。

| 引用 | 移除測試 | 判定 |
|------|---------|------|
| `commit `73e4ea3` 標題為某票收尾、內容全為另一票檔案` | 移除後「某次 commit 標題為某票收尾、內容全為另一票檔案」仍可理解 | 實證錨點型，條件允許保留 |

### 框架 code 邏輯註解的識別符衛生

> **本章節定位**：前述「引用性質判準」的五類分類已明訂——框架 code 邏輯註解與其他載體適用同一套全禁原則，第 1 類（論證依據型）依兩層分流指引處理。本章節針對邏輯註解這個特定載體，把兩層分流的第一層（簡單理由寫進註解）具體化為**自足 WHY** 撰寫法，並定義第二層跨 consumer 需要中央錨點時的**結構化溯源載體**，將 ticket ID 完全移出邏輯註解。本章節是文件慣例（降級為慣例，不上 regex hard hook 判斷「寫得是否夠自足」，理由見下「硬性強制的範圍：樣式偵測可機械化，改寫品質仍需人工判定」；但「是否含 ticket ID」本身已可機械偵測，見上「機械可判定性」）。

**Why**：框架 code 經 sync 跨專案共用，邏輯註解內的 project-local ticket ID 在其他專案斷源（該 ticket 不存在）或偽源（編號巧合對應到別的 ticket）。全禁原則下，即使句子在移除 ID 後仍完整（原歷史錨點型），留著 ticket ID 對讀者仍無操作價值——讀者無法在自己專案查到該編號，反而誤以為是有效引用。自足 WHY 把「為什麼這樣寫」的決策依據直接寫進註解，不依賴外部 ticket 即可理解，是更穩定的設計脈絡記錄方式。

**Consequence**：邏輯註解保留 ticket ID 會在 sync 後讓其他專案的讀碼開發者面對死編號——查無此 ticket，無法追溯設計脈絡，反而比沒有註解更困惑（誤以為脈絡可查卻查不到）。當設計脈絡需要可追溯的中央錨點時，缺結構化溯源載體會迫使開發者把追溯責任塞回 ticket ID，回到斷源/偽源問題。

**Action**：框架 code 邏輯註解禁嵌 project-local ticket ID。改以下兩條路徑取代：

| 取代路徑 | 適用情境 | 形式 |
|---------|---------|------|
| 自足 WHY | 設計依據可直接用一兩句話說清，不需外部追溯 | 註解直接寫「為什麼這樣寫」的決策依據，不含任何 ticket ID |
| 結構化溯源載體 | 設計脈絡需可追溯的中央錨點（跨 consumer 共享） | frontmatter provenance 欄或 commit trailer 引 `claude#NN`（見下「frontmatter provenance 欄與 commit trailer 溯源慣例」） |

**自足 WHY 正反範例**：

反例（邏輯註解嵌 project ticket ID，禁止）：

```python
# 此處改用 globalThis 取代 global（W-xxx）
target = globalThis
```

```python
# 依 W-xxx 的分析，這裡要先檢查 None 再 dispatch
if payload is None:
    return
```

正例（自足 WHY，移除 ticket ID 並把決策依據內聯）：

```python
# Service Worker 環境無 global，改用 globalThis 確保跨環境可用
target = globalThis
```

```python
# payload 為 None 時 dispatch 會拋 AttributeError 中斷 hook，先擋掉
if payload is None:
    return
```

正例（需中央錨點時，改引結構化溯源載體）：

```python
# 此防護源於 Service Worker 全域物件缺失崩潰；跨 consumer 修復追蹤見 provenance
# Provenance: claude#42
target = globalThis
```

**判別準則**：問「移除 ticket ID 後，這條邏輯註解是否已說清『為什麼這樣寫』？」

- 已說清 → 註解本身即自足 WHY，無需任何溯源載體
- 未說清（ticket ID 是唯一的脈絡來源） → 把決策依據內聯為自足 WHY；若脈絡需跨 consumer 共享追溯，補結構化溯源載體（`claude#NN`），而非留 project ticket ID

### frontmatter provenance 欄與 commit trailer 溯源慣例

> **本章節定位**：定義兩個結構化溯源載體——frontmatter `provenance` 欄（檔案層級）與 commit trailer（提交層級）——作為框架 code 邏輯註解移除 ticket ID 後的替代追溯錨點。兩者共同目標是把溯源資訊移出邏輯註解，改用跨專案穩定的錨點（GitHub Issues `claude#NN`）。

**Why**：框架變更（含 code 與 doc）需要可追溯的設計脈絡，但 project-local ticket ID 跨專案 sync 後失效（規則 8 主傷害模型）。關聯決策（issue tracker 三重用途設計）定框架採 GitHub Issues 作 canonical 錨點——issue 編號由 server 原子分配，跨 consumer 唯一且持久，是比 project ticket ID 更穩定的 provenance 載體。frontmatter 欄與 commit trailer 把這個錨點放在「不污染邏輯註解、機器可解析」的位置。

**Consequence**：缺結構化溯源載體慣例，開發者要記錄跨 consumer 設計脈絡時只能塞回邏輯註解的 ticket ID（斷源/偽源）或散落在 commit message 正文（不可機器解析、難以聚合追蹤）。有統一慣例則溯源資訊集中於可預期欄位，升格/跨 consumer 修復追蹤時可批量查詢。

**Action**：依載體類型採以下慣例。`claude#NN` 形式（如 `tarrragon/claude#42`）為首選，對齊框架 GitHub Issues canonical 決策。

**慣例 1：frontmatter provenance 欄（檔案層級）**

適用於有 YAML frontmatter 的框架檔案（error-pattern、methodology 等）需標注設計脈絡來源時。欄位為**可選**——零摩擦捕獲時不填，升格或需跨 consumer 追蹤時才 stamp。

| 欄位 | 性質 | 值形式 | 說明 |
|------|------|-------|------|
| `provenance` | 可選 | `claude#NN` 或 `owner/repo#NN` | 通用設計脈絡錨點，適用任意 code/doc 變更 |
| `canonical_issue` | 可選 | `owner/repo#NN`（如 `tarrragon/claude#42`） | error-pattern 專屬：指向 canonical 去重身份的 framework issue |

範例 1（error-pattern frontmatter 引 canonical issue）：

```yaml
---
id: PC-112
title: subagent 對非程式碼檔誤選 MCP 寫入工具
canonical_issue: tarrragon/claude#42
---
```

範例 2（methodology frontmatter 標通用 provenance）：

```yaml
---
title: knowledge-carrier-allocation-methodology
provenance: tarrragon/claude#57
---
```

**慣例 2：commit trailer（提交層級）**

適用於框架 code/doc 變更需在提交層級標注溯源，取代「邏輯註解嵌 ticket ID」。trailer 置於 commit message 末尾，鍵值對形式，機器可解析。

| trailer 鍵 | 值形式 | 說明 |
|-----------|-------|------|
| `Provenance` | `claude#NN` 或 `owner/repo#NN` | 此變更的設計脈絡錨點 |

範例 1（框架 code 變更 commit trailer）：

```
fix(hooks): Service Worker 環境改用 globalThis 取代 global

global 在 Service Worker 不存在，導致 hook 啟動崩潰。改用 globalThis
確保跨環境可用。

Provenance: tarrragon/claude#42
```

範例 2（框架 doc 變更 commit trailer）：

```
docs(references): 規則 8 補框架 code 註解識別符衛生條款

Provenance: claude#58
```

**邊界**：本慣例的 `provenance` / `canonical_issue` 載體存放於 frontmatter 與 commit trailer，**不存放於邏輯註解**——邏輯註解仍依上節「框架 code 邏輯註解的識別符衛生」要求自足。功能字串（運行時輸出）一律不嵌任何溯源識別符（含 `claude#NN`），維持運行時輸出對最終用戶無誤導。

### 硬性強制的範圍：樣式偵測可機械化，改寫品質仍需人工判定

> **本章節定位**：早期量測（naive regex 全域掃描，未先命名豁免類）曾得出「識別符衛生應降級為文件慣例、不上 regex 強制層」的結論。全禁原則 + 五類分類重新拆解了這個問題——「是否含 ticket ID 且未落在豁免路徑」與「移除後補寫的內容品質是否足夠」是兩個不同問題，前者現已可機械化，後者仍需人工判定。本章節更新舊結論，並保留原始量測資料作為「豁免類必須先命名」的實證。

**Why**：對「框架文件含 project ticket ID」做未先命名豁免類的 naive regex 偵測，誤報面過大——早期一次全域量測命中 8686 處，其中 322 處屬合法命中（`source_ticket` 等 frontmatter 欄位範例、被說明對象型格式展示、規則正文的範例引用），naive regex 無法區分這些與真正的第 1 類違規引用，會全數誤殺。此資料正是「引用性質判準」一節所述——未命名豁免類即執法會產生數千筆誤報（ARCH-016 失效模式）的先前印證。

**Consequence**：若不拆分「樣式偵測」與「改寫品質判定」兩層，會重蹈同一誤報問題；反之，若因為「改寫品質判定需要人工」而連「是否含 ticket ID」都放棄機械偵測，等於捨棄了全禁原則帶來的「可完整執法」優勢，回到判斷型規則執行落差隨 session 數累積的舊狀態。

**Action**：拆分為兩層對待：

| 層次 | 判定內容 | 是否可機械化 | 執行方式 |
|------|---------|------------|---------|
| 樣式偵測 + 豁免判定 | 是否含 ticket ID 樣式，且是否落在第 4 / 5 類豁免路徑 | 是 | 守衛前向執行（獨立追蹤，見上「機械可判定性」） |
| 改寫品質判定 | 移除 ID 後的自足 WHY 是否真的說清楚、方法論引用是否選對方法論 | 否，需語意理解 | 維持人工判定（撰寫前檢查清單 + code review） |

守衛只擋「樣式偵測 + 豁免判定」這一層；改寫品質不進入機械阻擋範圍，由撰寫者與 reviewer 依「兩層分流指引」的判別準則自律執行。

### 豁免機制

某些情境下，框架文件確實需要保留產品名稱或專案層級識別符作為情境舉例（例如測試任務的具體系統名稱、業務情境驅動的程式碼註解正例、5 Whys 真實事件分析）。完全禁止會破壞寫作教學的可讀性或事件記錄真實性。豁免機制提供合法的「具體舉例」保留路徑。

**Why**：規則 8 主目標是防止 sync 後死連結與誤導，但「具體舉例」的價值在於可讀性與場景感，與「框架描述」（如「本專案是 X」聲明）性質不同。一刀切禁止會傷及寫作教學的核心目的。

**Consequence**：缺豁免機制會出現兩種失敗模式：(1) 嚴格執行→教學範例失去場景感（如「系統 X」「平台 Y」），讀者無法建立心智模型；(2) 寬鬆執行→A 類框架描述漏網，sync 後跨專案誤導。

**Action**：依下方判別表將每處產品名稱出現分為「A 類框架描述（需泛化）」vs「B 類具體舉例（可豁免）」，B 類處加標準格式 HTML comment 豁免註解。

#### A/B 類判別表（角色二分）

| 類別 | 語意角色 | 處理 | 範例情境 |
|------|---------|------|---------|
| A 類 | 框架描述（「本專案是 X」聲明、跨專案通用 agent 的目標清單列舉） | 泛化為通用描述 | agent 定義中的「本專案」聲明 / data-miner agent 中的具體網站清單 |
| B 類 | 具體舉例（測試任務情境設定、業務情境驅動正例、業務意圖正例、過度驗證反例、5 Whys 真實事件記錄） | 加豁免註解保留 | 寫作 SKILL 的 dry-run 測試任務 / 程式碼註解範例 / 文件正例表格 / 反例 Widget Key 命名 / 事件分析鏈中的 storage key |

**判別準則**：問「若此處改為『系統 X』『平台 Y』後，讀者還能理解教學/事件意圖嗎？」

- 不能理解 → B 類（具體舉例，加豁免註解保留）
- 仍能理解（甚至更清晰）→ A 類（框架描述，泛化）

#### HTML comment 標準格式

```html
<!-- 規則 8 豁免（reference-stability-rules.md / DOC-010）：[此處 XXX] 作為 [情境類型]。[泛化會失去 YYY] 故保留。本豁免經 [評估方式] 後保留。 -->
```

**欄位填寫要求**：

| 欄位 | 內容 | 範例 |
|------|------|------|
| `[此處 XXX]` | 具體指出豁免對象（產品名稱 / 識別符） | 「以下任務描述中的某產品名稱」「`platform_icon_<product>` Widget Key」「`<product>_books` storage key」 |
| `[情境類型]` | 為何屬於 B 類（語意角色） | 「dry-run 測試的具體任務情境設定」「業務情境驅動正例 Dart 註解」「5 Whys 真實事件分析鏈中的 storage key」 |
| `[泛化會失去 YYY]` | 泛化會喪失的具體價值 | 「測試人員需具體系統名稱才能模擬撰寫情境，改為『系統 X』會失去場景感」「降低反例真實性」 |
| `[評估方式]` | 豁免決策來源（不引用專案 ticket ID） | 「跨檔評估」「規則 8 自律審視」 |

#### 撰寫慣例

**禁止**：

| 禁止 | 改為 |
|------|------|
| 在豁免註解中引用專案 ticket ID（如 `(W{N}-{seq} 評估)`） | 改為抽象描述（如「跨檔評估」） |
| 用「Why: 因為這樣比較好讀」這類無具體價值理由 | 必須說明「泛化會具體失去什麼」 |
| 一筆豁免覆蓋多處不同性質的內容 | 每個 B 類處獨立加註解，理由不可共用 |

**允許引用的權威**：

| 引用 | 屬性 |
|------|------|
| `reference-stability-rules.md` | 規則 8 本身路徑 |
| `DOC-010` | error-pattern 框架內部分類（規則 8 例外） |
| 其他 framework error-pattern ID（`PC-XXX` / `ARCH-XXX` / `IMP-XXX` / `TEST-XXX`） | 框架內部分類同上 |

#### 範例對照

合法 B 類豁免：

```html
<!-- 規則 8 豁免（reference-stability-rules.md / DOC-010）：以下測試反例中的 `platform_icon_<product>` Widget Key 命名是反例事件的真實 Key 名稱。事件分析記錄真實事件特徵；改為 `platform_icon_xxx` 會降低反例真實性。本豁免經跨檔評估後保留。 -->
```

不合法的「偽豁免」：

```html
<!-- 規則 8 豁免：此處保留產品名稱 -->                <!-- 缺欄位、無理由 -->
<!-- 規則 8 豁免：W{N}-{seq} 評估保留 -->             <!-- 引用專案 ticket ID -->
<!-- 規則 8 豁免：這樣比較好讀 -->                    <!-- 無具體價值說明 -->
```

#### 決策追溯慣例

- 豁免註解本身不含專案 ticket ID（保持規則 8 自律）
- 大規模豁免應用後，應在 `DOC-010` 觸發案例表新增一筆紀錄（採抽象模式描述）
- 後人查找豁免決策依據時，從 `DOC-010` 觸發案例表往回追溯到對應 ANA ticket（ANA ticket 位於 `docs/work-logs/`，規則 8 不適用於 `docs/`）

## CLAUDE.md 章節外移決策樹

**Why**：縮減 `CLAUDE.md` 體量時，章節外移目標必須依「內容是否含專案層級識別符」決定，誤將專案內容外移到 `.claude/references/`（跨專案 sync 範圍）會觸發規則 8 違反；誤將通用內容外移到 `docs/`（專案內部）則喪失跨專案知識複用。

**Consequence**：外移目標選錯會讓 `.claude/` sync 機制把專案專屬內容（如 `src/` 路徑、產品名稱）擴散到其他專案，造成跨專案誤導；或讓跨專案通用知識被困在單一專案 `docs/` 失去複用機會。

**Action**：執行 `CLAUDE.md` 章節外移前依下方決策樹判定目標，外移後執行檢查清單驗證合規。

### 觸發條件

| 訊號 | 處理 |
|------|------|
| `CLAUDE.md` 單檔行數 > 200（或某章節 > 50 行） | 評估外移 |
| 章節內容只在特定情境（如寫程式碼前）才需要 | 評估外移為 lazy-load reference |
| 章節含具體實作細節（命名清單、檔案位置表） | 評估外移以保持 `CLAUDE.md` 抽象層級 |

### 外移目標選擇決策樹

依序回答以下問題：

| 步驟 | 問題 | 是 → 目標 | 否 → 下一步 |
|------|------|----------|------------|
| 1 | 章節是否含**專案層級識別符**（`src/` 路徑、產品名稱、專案 ticket ID、專案 commit hash、專案 worklog 路徑）？ | `docs/<descriptive-name>.md` | 進入步驟 2 |
| 2 | 章節是否含**跨專案可複用的通用知識**（如 Chrome Extension 限制、Manifest V3 行為、Python 通用規範）？ | `.claude/references/<descriptive-name>.md` | 進入步驟 3 |
| 3 | 章節是否為**混合內容**（部分專案、部分通用）？ | 拆檔：專案部分放 `docs/`、通用部分泛化後放 `.claude/references/` | 留在 `CLAUDE.md`（無法外移） |

### 目錄性質對照表

| 目錄 | sync 範圍 | 可含專案識別符？ | 適用情境 |
|------|----------|---------------|---------|
| `docs/` | 專案內部，不 sync | 是 | 專案專屬規範、架構說明、需求/規格 |
| `.claude/references/` | 跨專案 sync | 否（規則 8） | 跨專案技術速查、通用 lazy-load 參考 |
| `CLAUDE.md` | 專案入口，不 sync | 是 | 高層概覽 + lazy-load 指引 |

### 外移後檢查清單

- [ ] 新檔目標目錄符合決策樹結論（`docs/` vs `.claude/references/`）
- [ ] `CLAUDE.md` 引用路徑已更新（`@docs/<檔名>.md` 或 `@.claude/references/<檔名>.md`）
- [ ] 原檔案已刪除（外移而非複製）
- [ ] 若放 `.claude/references/`，內容已通過規則 8 自檢（無 `src/` 路徑、無產品名稱、無專案 ticket ID）
- [ ] 若放 `docs/`，已在新檔頂部說明「存放位置原因」（避免後續誤搬回 `.claude/`）
- [ ] 執行 `grep -rn "<新檔關鍵字>" .claude/ docs/` 確認無殘留舊路徑引用

### 範例對照

| 章節性質 | 外移目標 | 範例 |
|---------|---------|------|
| 專案錯誤處理體系（含 `src/core/errors/` 路徑） | `docs/project-conventions.md` | 含 `src/` 路徑與專案 enum 清單，屬步驟 1 命中 |
| Chrome Extension Manifest V3 通用限制 | `.claude/references/chrome-extension-quickref.md` | 通用限制速查表（require/global/Storage API），泛化後保留 |
| Flutter 專案的命名規範 + 通用 Dart 風格 | 拆檔：專案命名放 `docs/` 下 flutter-naming-conventions 檔、通用 Dart 風格放 `.claude/references/` 下 dart-style 速查檔 | 混合內容拆檔範例（路徑為示意） |
