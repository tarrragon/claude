## 核心主張

規則 5 區分記錄平面（transcript、對話記憶）與世界平面（filesystem、git、ticket），要求重大狀態判斷以世界平面為準。這個二分正確但不完整：**世界平面本身還有瞬時與持久之分**。

| 觀測對象 | 平面性質 | 原因 |
|---------|---------|------|
| `git status` / 工作區檔案內容 / 測試執行結果 | 瞬時 | 並行環境下共用工作目錄隨時被其他 session 改寫，觀測只在當下成立 |
| `git log` / commit 內容 | 持久 | 已寫入版本歷史，內容不受其他 session 之後動作影響（除非該 commit 被 revert/reset，此類操作本身也留下歷史紀錄） |

對工作區的觀測是真實的——在觀測的那一刻，它確實反映了目錄狀態。但它不能作為持久結論（「已進 main」「已解決」「已違反規則」）的依據。持久事實只在 git 歷史裡。

---

## Why：為何區分「真實」與「可作為持久結論依據」

規則 1-4 處理「輸出是否真實」（防 confabulation）；規則 5 原文處理「記錄平面 vs 世界平面」（防止依賴自己的對話記憶）。但即使一次工具呼叫回傳的是貨真價實的 raw stdout（不違反規則 1-4），且觀測對象確實是世界平面（不違反規則 5 原意），並行環境下這個觀測仍可能在下一秒就不再成立——因為工作目錄是共用資源，其他 session 隨時在改寫它。

**Consequence**：把瞬時觀測當持久結論，會產生兩類後果。其一，觀測到的問題在查證時已消失（虛驚），浪費查證與回報成本。其二——後果更嚴重的一類——觀測到的問題從未真實存在於持久記錄中，卻已被當成事實向外傳播（回報、派工），接收方若未再次查證直接照辦，會為不存在的問題引入變更，且真實情況永不被發現。

**Action**：對工作區觀測下「已進 main」「已解決」「已違反規則」等持久結論前，必須以 `git log` / `git show <commit>:<path>` 等 git 歷史查詢交叉驗證該狀態是否已寫入版本歷史。僅憑 `git status` / 檔案內容 / 測試結果下持久結論即屬違規。

## 三次實例（2026-08-26 單日）

三次實例跨越 git 衝突、merge 狀態、測試紅燈三種載體，形狀相同，屬規則缺口而非個案。

### 實例一：git status 顯示 UU，查證時 merge 已完成

`git status` 顯示某檔為 `UU`（both modified）。查證時 `MERGE_HEAD` 已不存在、unmerged paths 為空——merge 在兩次觀測之間，被另一個 session 完成。第一次觀測（`UU`）在觀測當下是真實的，但不能代表持久狀態：兩次觀測之間工作目錄已被改寫。

### 實例二：代理人回報衝突未解決，PM 查證時已解除

代理人回報 repo 處於未解決的 merge 衝突，並附完整 `git status` 輸出佐證。PM 查證時，衝突已解除。代理人的回報在其觀測當下同樣真實，但傳遞到 PM 查證的時間差內，世界平面（工作目錄）已再次變動。

### 實例三：pytest 紅燈誤判為「已進 main」（後果最完整的一例）

PM 對測試檔跑 `pytest`，得到 2 failed，據此判定「紅燈已進 main、違反 quality-baseline 規則 1」，並向上回報、據此準備派工修復。事後查該檔的 commit 歷史，帶缺陷的版本從未被任何 commit 承載——PM 讀到的是另一個代理人本地編輯過程中的瞬時狀態（該代理人正在修改該測試檔，尚未完成也未 commit）。

若這次派工被執行者照單全收，會為一個不存在的問題引入變更；且因為問題本來就不存在，真實情況永遠不會被發現——沒有「發現派工是錯的」這一步，因為表面上一切正常。此次誤判被攔下，是因為執行者在動手修復前先查了該檔的 commit 歷史，發現帶缺陷版本從未進入版本控制，才回頭質疑派工依據。

## 判準與交叉驗證命令

| 待確認的持久結論 | 交叉驗證命令 | 判據 |
|-----------------|-------------|------|
| 「衝突已進 main / 未解決」 | `git log --oneline -3 -- <path>` + `git status --porcelain` 同時查 | commit 歷史有無對應變更；`MERGE_HEAD` 是否存在 |
| 「紅燈已進 main」 | `git show <commit>:<path>` 取出該 commit 實際內容重跑測試，或 `git log -p -- <path>` 確認缺陷版本是否曾被 commit | 缺陷內容是否出現在任一 commit 的檔案內容中 |
| 「某檔已違反規則 X」 | 對照 commit 內容而非工作區內容 | 工作區可能是他人正在編輯的中間態 |

**與規則 3 的分工**：規則 3 的固定值命令（`git rev-parse HEAD` 等）驗證「輸出是否為真」；本節的交叉驗證驗證「真實觀測是否可作為持久結論的依據」，兩者可疊加使用——先確認輸出未被虛構（規則 3），再確認觀測對象屬持久平面而非瞬時快照（本節）。
