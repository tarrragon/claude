# 工具選擇規則詳細說明（Tool Selection Details）

本檔是 `.claude/rules/core/tool-selection.md` 的按需讀取層，收錄自動載入層只以一列表格與一行路由呈現的條文論證。

> **載入方式**：按需讀取。遇到平台以「too complex to verify」拒絕複合命令、或不確定某次拒絕能否以拆分處理時讀取。

## 規則 2 例外：平台以「too complex to verify」拒絕複合命令

### 條文

複合 Bash 命令（含 `&&`、`;`、管線、子 shell、多段 heredoc 等）被平台權限判定以「too complex to verify」拒絕時：

1. 可以把原命令拆成其中的單一命令，分次執行。
2. 拆開後每條命令都必須是原命令中原樣可見的操作，不新增原命令沒有的間接層。
3. 禁止改用 `python -c`、`bash -c`、`eval`、寫入後再執行的腳本檔等寫法，把實際操作包進平台看不見內容的形式。
4. 拆開後任一條仍被拒絕，就停手：在 ticket NeedsContext 記錄原命令與拒絕訊息全文，回報 PM。

來源：用戶裁決，2026-10-14。

### Why：為何拆分不算繞過

規則 2 第三列禁止繞過非專案來源的拒絕，理由是那類拒絕的語意是「不該做這件事」。「too complex to verify」的語意不同：平台無法把複合命令拆解到足以逐項判定，所以拒絕的對象是命令的形狀，不是命令裡的操作。

拆成單一命令之後，每條命令仍各自送進同一個平台判定。平台這時看得清楚每一項操作，可以逐條放行或拒絕，判定權沒有被拿走。拆分做的事是把命令還原成平台能判定的形狀，平台的判斷照樣執行。

### Consequence：讀錯例外的兩種代價

| 誤讀方向 | 結果 |
|---------|------|
| 讀太窄：所有非專案來源拒絕一律停手 | 合法操作（例如一串唯讀查詢）因命令寫法被擋，每次都要上報 PM，平台本會放行的操作被迫中斷 |
| 讀太寬：把 `python -c` 或腳本檔當成「拆分」 | 實際操作被包進一個平台看不見內容的命令，平台只能判定「執行一段 Python」，判定形同被架空。這和規則 2 第三列禁止的 Bash 內嵌腳本繞過是同一件事 |

讀太寬的情況更危險：表面上命令變短、拒絕消失了，但平台已經沒在判定實際操作，也不會留下任何訊號。

### Action：遇到拒絕時的步驟

1. 確認拒絕訊息含「too complex to verify」。訊息不同（例如 classifier 給出具體拒絕理由、permissionMode 拒絕、OS 權限錯誤）時不適用本例外，回到規則 2 第三列。
2. 把原命令拆成單一命令，依原順序分次送出。原命令依賴前一步的工作目錄或環境變數時，改用絕對路徑或 `git -C`（見 `.claude/rules/core/bash-tool-usage-rules.md` 規則一），不靠 `cd` 串接。
3. 任一條被拒，停手並記錄：原命令全文、被拒的那一條、拒絕訊息全文。不再嘗試其他寫法。

### 邊界

| 情況 | 是否適用本例外 |
|------|--------------|
| 專案 hook（`.claude/hooks/` 的 PreToolUse 等）拒絕 | 否。專案 hook 的拒絕訊息會附處置方式，依該訊息處理 |
| 拒絕訊息不是「too complex to verify」 | 否。回到規則 2 第三列 |
| 拆分後把中間結果寫到 scratchpad 檔供下一條讀取 | 可以，前提是寫檔與讀檔本身都是可見的單一命令，沒有被執行的腳本 |
| worktree 內多行內容（heredoc 被守衛拒收含換行參數）傳給 `append-log` | 可以，首選：以 Write 寫入 scratchpad 內容檔（非票檔），再以 `append-log --content-file <路徑>` 單一命令讀取；命令列不含換行。分次單行 append 降為 `--content-file` 不可用時的替代 |
| 管線（`a \| b`）或命令替換（`$(...)`）拆開後需要傳遞中間結果 | 可以，做法同上一列：前一條以可見的重導向寫入 scratchpad 檔，下一條以單一命令讀取該檔。不得改用 `xargs`、`eval`、`bash -c` 把兩段串回一條 |
| 拆分時順便改寫成原命令沒有的操作 | 否。拆分只改形狀，不改內容 |

## Bash 改檔放寬的實驗依據

> 完整實驗方法、任務原文與逐 run 結果記在產生本節結論的分析票（3.6.0 版，主題為放寬 Bash 改檔範圍）的〈實驗執行〉與 Solution 章節，票號見落地本節的實作票的父票欄位。本節只留結論。

### 結論

| 軸 | 實測 | 對規則 1 的意義 |
|----|------|----------------|
| 正確率 | 同一組 6 類任務（單行、多行、中文、跨 5 檔、YAML／JSON、4552 行大檔），Bash 組 30/30、Edit 組 29/30；Edit 組唯一失敗來自 session 未提供 Grep／Glob，不是 Edit 寫錯 | 正確率不是限制 Bash 改檔的理由 |
| 守衛覆蓋 | 路徑層：Bash 寫 `.claude/**`、`lib/`、`test/` 在 PreToolUse 被擋；內容層：12 支守衛對 Bash 寫入只在 commit 層補檢；三支完全無 Bash 對應 | 限制的實質理由，故受管路徑維持 Edit／Write |
| 可審查性 | Bash 組改檔皆為字面 `str.replace` 或定位後整行指定並附次數斷言，只讀命令即可確定改了什麼 | 寫法條件第一項的依據 |
| 失敗型態 | 多檔腳本非原子：斷言以行數而非出現次數計算，中途失敗時前幾檔已寫回 | 寫法條件第二、三項的依據 |

### 覆蓋邊界

- Bash 組全部選用 `python3` heredoc，沒有 sed 或 awk，BSD 與 GNU 旗標差異造成的失敗率未驗證，所以寫法條件禁用 sed／awk 旗標，而不是證明其安全。
- 只測 general-purpose 代理人；專案代理人與 Code Mode 下的結果未驗證。

### 規則 2 維持的理由

非專案來源拒絕的語意是「不該做這件事」，實驗量的是正確率與守衛覆蓋，對此理由沒有影響。PM 接到代理人被拒的回報後，自行補 `where.files` 再代改，等於繞過拒絕所表達的判斷，所以交用戶裁定。

## Code Mode 注意事項

> 實測依據記在 3.6.0 版 Code Mode 採用評估的分析票（母票），見其〈實驗執行：C 段結果〉與 Solution；本節只留結論。

Code Mode 是 Claude Code 的實驗功能：模型寫一段 JavaScript，在單一步驟內發出多個工具呼叫。採用範圍判定為「用戶自行開啟，框架不代為開啟、不提供專屬 hook」，原因是 hook 觸發與守衛結果與一般模式相同，而 token 降幅未達支援門檻（兩個對照任務一降 17.4%、一升 2.0%，範圍重疊）。

### 開啟條件

| 項目 | 內容 |
|------|------|
| 支援環境 | 只支援互動終端。`claude -p` 無法開啟，框架內的 headless 流程不受影響，也無法替它們開啟 |
| 開啟方式 | 用戶在啟動 session 前自行設定環境變數 `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1`；專案 settings 的設定無效 |
| 框架立場 | 不代為開啟；功能屬 experimental，可能隨版本變更或移除，本節須隨之維護 |

### 三點注意事項

| # | 注意事項 | Why（實測） | Consequence | Action |
|---|---------|-------------|-------------|--------|
| 1 | 同一段程式內某個呼叫被 hook 拒絕後，後面的呼叫照樣執行 | 實測 2 支探針（兩支各有一個呼叫被 hook 擋下），被擋呼叫之後的呼叫都照常執行；模型要等整段程式跑完才看到拒絕結果。另一支探針後續的 `git add && git commit` 是自己失敗（pathspec 不存在），不算此類實例 | 依賴被擋呼叫的後續呼叫會在前提不成立下執行 | 有相依關係的呼叫不放進同一段程式，拆成不同步驟 |
| 2 | git 寫入不得放進 `Promise.all` 並行發出 | 實測兩個並行 `git commit` 無守衛介入，其一因 `HEAD.lock` 失敗（exit 128） | 並行寫入同一 index 競爭鎖，一成一敗，狀態不一致 | 依 `bash-tool-usage-rules` 規則三，同一 worktree 的 git 寫入依序發出 |
| 3 | 被拒的處置比照 tool-selection 規則 2（規則上的要求，不是實測結果；未實測被拒後的處置行為） | 實測只證明內部呼叫以原工具名稱（Bash、Read、Write、Edit、Agent）照樣經過 PreToolUse hook，hook 沒觸發的次數為 0；因此規則 2 的拒絕語意在 Code Mode 下同樣適用 | 被拒後改寫成別的寫法，等於繞過拒絕所表達的判斷 | 停手並記錄原命令與拒絕訊息，不改寫、不繞過 |

> 附帶觀察：settings 沒有任何 hook 掛在 `REPL`（執行程式的工具名稱）上，框架只能逐一看到內部呼叫，看不到整段程式。
