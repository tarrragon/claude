# 各線的接續狀態與主控自我接續

本檔說明兩件事：

- 主控 PM 怎麼判斷每條線目前的接續狀態：已收線、`/clear` 後繼續、`/compact` 後繼續，或由新 session 接手。
- 主控自己 `/clear` 或 `/compact` 之後，怎麼在不靠用戶提示的情況下接回協調工作。主控 session 長駐，清除屬例外，§4 是例外發生後的程序。

內容包括：判讀用的資料來源、四種狀態的判讀依據與接續動作、線停在等用戶的判讀、主控寫給用戶的待辦、主控長駐的定位與例外時的自我接續步驟、主控收到 Stop hook context 保護提醒時的判讀。

**為何要有本檔**：

- 線執行 `/clear` 之後，對話 context 全部消失；執行 `/compact` 之後，只剩摘要；換成新 session 時，從零開始。三種情況的接續動作不同。
- 但從 `ListAgents` 看，三種情況都只是「一個名稱，閒置中」。主控如果只看名稱與啟動時間，就會判斷錯誤。
- 實例：一個 session 在 13 小時前啟動，主控判斷它是「舊 session、尚未換手」。實際上它 13 秒前才做過 `/clear`，已經只能讀票面接手。

**量測版本**：Claude Code 2.1.314（2026-10-31，macOS）。session 檔與 SessionStart 的 `source` 欄位都是 Claude Code 的內部行為，沒有相容承諾。升版後先依 §6 重新核對。

## 1. 資料來源

| 來源 | 讀什麼 | 用途 |
|------|--------|------|
| 協調票 `## Solution` 段 | 每條線最後一行現行佇列行：線號、session 名稱、票序 | 線的佇列與持有者。格式見 `session-naming.md`〈用語〉 |
| `ListAgents` | 同儕 session 的名稱與閒置狀態；第一行是本 session 的自稱 | 哪些名稱目前可以定址；主控確認自己的名稱 |
| `~/.claude/sessions/<pid>.json` | `name`、`sessionId`、`cwd`、`status`、`pid`、`procStart` | 名稱對應到現行 `sessionId`；存活判定見 `shared-resources.md` §6。只讀 `*.json`，不讀 `*.key` |
| `.claude/hook-logs/session-source-diagnostic/diagnostic.log` | 每行 `[<時間>] source=<值> session_id=<前 8 碼>` | 某個 `sessionId` 最近一次 SessionStart 的來源：`startup`、`resume`、`clear`、`compact` |

**`sessionId` 的變化規則**：

- `/clear`：pid 和名稱不變，`sessionId` 換新，log 記錄的是新的 id。實測：兩個 session 各執行一次 `/clear`，log 都寫 `source=clear`，id 也都等於 session 檔中的新 `sessionId`。
- `/compact`：`sessionId` 不變。實測：同一個 id 在 log 中出現兩次 `source=compact`。
- 新開的 session：pid 是新的，log 記一筆 `source=startup`。這一點是依 SessionStart 欄位的定義推得，本次量測沒有觀察到新開 session 的實例。
- 不能用 `startedAt` 判斷 `/clear`：實測 `/clear` 之後，`startedAt` 沒有更新成 `/clear` 的時間。

**限制**：

- log 由本專案的 SessionStart hook 寫入，只記錄在本 repo 啟動的 session。
- log 在 gitignore 範圍內，只存在本機。
- 在 worktree 內啟動的 session，會寫入 worktree 自己的 `.claude/hook-logs/`。
- 讀不到某個 id 的紀錄時，判為「來源不明」，不要猜測。

## 2. 四種接續狀態

| 狀態 | 判讀依據 | 該線剩下的 context | 主控的接續動作 |
|------|---------|-------------------|---------------|
| 已收線 | 該線最後一行現行佇列行的票序是 `（無）` 或 `（結束）` | 不需要 | 不再派票。session 若仍在 `ListAgents` 中，請用戶關閉，否則它可能被誤選為傳訊對象（`session-naming.md` §4） |
| `/clear` 後繼續 | pid 和名稱不變；session 檔的 `sessionId` 在 log 中最後一筆是 `source=clear`，時間晚於主控上次核對 | 對話全部清空，只剩票面 | 確認該線的接手點已寫進票面（〈階段收尾狀態〉或接續點段落）。若沒有寫，舊對話已經清空，無法再請該線補寫，改由主控依 git log 與票面重建接手點並寫入。傳訊時寫明票號和段落名稱，指出接手位置。名稱沒變，所以現行佇列行不用改 |
| `/compact` 後繼續 | `sessionId` 不變，log 中同一個 id 最後一筆是 `source=compact`，時間晚於主控上次核對 | 只剩摘要，細節可能遺失 | 不需要重新指派。該線下一次寫協調票時，主控核對寫法。壓縮後最常見的錯誤是把佇列行改寫成條列文字，見 SKILL.md〈佇列變動時同一步寫現行佇列行〉 |
| 新 session 接手 | `ListAgents` 出現新名稱，pid 是新的，log 最後一筆是 `source=startup` | 從零開始 | 以 `ListAgents` 中的實際名稱寫目標行和現行佇列行，再傳訊指派（`session-naming.md` §4）。如果接手的是舊線，而舊 session 還在，請用戶關閉舊 session |

**另一種情況：線還有佇列，但持有它的 session 已經不在**。判讀依據是：現行佇列行上的名稱不在 `ListAgents` 中，或 session 檔的存活判定不符。這條線目前沒有任何 session 持有，不要對它傳訊。處理方式二選一：請用戶開新 session 接手，或依 SKILL.md〈線空出時移票〉把票移給其他線。

### 等用戶

等用戶與接續狀態無關：線可能處於任一種接續狀態，同時停在等用戶。等用戶也不代表過期，所以工具把它另列一段，不併入過期項。

**為何要偵測**：線停下來等用戶時，若只把事項寫在票面、沒有傳訊，主控讀不到，只有用戶問起才會發現。偵測讓「忘了傳訊」的情況仍然看得見。

**判讀依據**：以下三種訊號任一成立，就判定該線在等用戶。只看該線最後一行現行佇列行，跳過狀態為 completed 的票。已收線的線不判。

| 訊號 | 讀什麼 | 寫入方 | 解除 |
|------|--------|--------|------|
| S1 票面標記（主訊號） | 票的 `## Solution` 段中，行首（不容前導空白）為 `**等用戶**：<事項>` 的行；同一張票以最後一行標記為準。冒號後沒寫事項照樣列出，只有解除行能清除 | 線本身，以 `ticket track append-log <票號> --section Solution` 寫入 | 追加一行 `**等用戶解除**：<結果>`；最後一行是解除行就不列。票 completed 後也不列 |
| S2 session 等待中 | 該線 session 檔 `status` 為 `waiting`，事項取 `waitingFor` | Claude Code（AskUserQuestion、權限詢問） | session 狀態變動即解除 |
| S3 佇列行註記 | 現行佇列行中票的註記或純文字含字面「等用戶」，例如 `511（等用戶開 --debug）`。只要出現這三個字就算，`（等用戶已回覆）` 也會列出 | 主控 | 主控追加新的現行佇列行並拿掉註記；不要改寫成「等用戶已回覆」 |

**不算訊號的寫法**：

- 票面的自由文字，例如「待用戶」「尚待」：這種文字沒有解除記號，實測後仍會殘留在票面，算進來就會誤報。
- 寫在 Solution 段以外、寫在行中、縮排、或在 fenced code block 內的 `**等用戶**：`：例如判準說明裡引用的格式。
- 同一條線較早的佇列行：那是歷史。

**漏報邊界**：線停下時沒寫 S1，session 也已閒置，三種訊號都不成立，工具偵測不到。所以 SKILL.md〈停下等用戶時同一步寫標記並傳訊〉把寫 S1 定為規則。標記寫在不在佇列裡的票上（例如新衍生的票），工具不讀。

**工具輸出**：一段 `等用戶（N）`，每項一行，依 S1、S3、S2 的順序。沒有任何一項時寫 `等用戶：無`。

| 情況 | 一行的格式 |
|------|-----------|
| 有票號（S1、S3 的票註記） | `L<n>（名稱）<票號>：<事項>（S1）` |
| 沒有票號（S2、S3 的純文字） | `L<n>（名稱）：<事項>（S2）` |
| 佇列行沒寫 session 名稱 | `L<n> <票號>：<事項>（S3）`，線號與票號以空白分隔 |

**主控的接續動作**：

| 訊號 | 動作 |
|------|------|
| S1 | 把事項轉給用戶，附票號。用戶回應後轉回該線；該線在同一步寫解除行 |
| S2 | 該線正在等用戶回答問題或核可權限，請用戶到該 session 處理。主控不代答 |
| S3 | 主控寫的註記，主控本來就知道。確認事項仍成立；已解決時追加新的現行佇列行，拿掉註記 |

S1 已列了很久，但用戶其實已經回應過：多半是該線漏寫解除行。請該線補寫，不要由主控改他線的票。

### 用戶待辦

用戶待辦是主控要用戶處理的事項，例如裁定、開 session、授權、實機驗證。主控把它寫在協調票上，看板最上方的「用戶待辦」群組會列出。

**為何寫在協調票**：寫在回覆裡的事項，會被 Stop hook 的回應與各線訊息淹沒，用戶找不到。寫在票面，看板就能直接讀出、不經 LLM 生成，session 結束後也還在。

**格式**：寫在協調票的 `## Solution` 段，以 `ticket track append-log <協調票號> --section Solution` 寫入。

| 行 | 格式 | 說明 |
|----|------|------|
| 待辦行 | `**用戶待辦**（<鍵>）：<事項>` | 鍵有票號就用票號，沒有就用短代稱，例如 `sync-push`。事項以動詞開頭，例如開、裁定、授權、核可、實測；要用戶開 session 時，把指令寫進事項 |
| 完成行 | `**用戶待辦完成**（<鍵>）：<結果>` | 鍵與待辦行逐字相同 |
| 不帶鍵的待辦行 | `**用戶待辦**：<事項>` | 只用於既有的舊行。完成行要寫 `**用戶待辦完成**：<事項全文>`，事項全文須逐字相同才配對 |

**配對規則**：

- 同一個鍵以最後一行為準。寫了完成行就不列；完成之後再寫一次待辦行，就重新列出。
- 完成行的鍵配不到任何待辦時，不影響其他項。
- 帶鍵與不帶鍵的項目分開配對：不帶鍵的完成行內容恰好等於某個鍵時，不會解除該帶鍵項，反之亦然。
- 判讀規則與 S1 相同：行首不容前導空白，清單項（`- **用戶待辦**…`）、fenced code block 內、Solution 段以外的行都不算。所以說明段裡的格式範例不會被列出。
- 鍵不得為空，也不得含全形右括號 `）`：空括號的行會被略過，含 `）` 的行不符格式，都不會列出。
- 帶鍵的好處是：改寫事項文字之後，完成行照樣配得上。不帶鍵的行改了一個字，就配不到完成行。

**看板顯示**：各線群組之上有一個可收合的群組「用戶待辦（N）」，預設展開。沒有任何一項時，只顯示一行「用戶待辦：無」；session 狀態讀不到時改寫「用戶待辦：無（session 狀態讀不到，S2 未判）」。協調票讀不到時不顯示，因為這時判不出有沒有待辦。

| 來源 | 一行的格式 |
|------|-----------|
| U1 協調票的待辦行（在前） | `<事項>｜<鍵>`；不帶鍵的行寫 `<事項>｜主控` |
| U2 各線等用戶（在後，判定同 §2〈等用戶〉） | `<事項>｜L<n> <短票號>（S1／S3）`；沒有票號（S2、S3 的純文字）時寫 `<事項>｜L<n>（S2／S3）`。S2 以洋紅粗體顯示，表示用戶要到該 session 處理 |

`line_status` 的輸出不含 U1：待辦是主控自己寫的，主控本來就知道。

## 3. 判讀步驟

以下三種時機都要判讀：每一輪佇列更新前、主控自己接續時、用戶提到某條線換過 session 時。

**主路徑：呼叫 `line_status` 工具**。line-board plugin 註冊了 `mcp__line-board__line_status`（不需參數，唯讀），在 ToolSearch 後面，先以 ToolSearch 搜尋 `line_status` 載入再呼叫。它一次完成下方步驟 1、3、4、5，輸出：

- 每條未收線的線一行：狀態（§2 的四種，加上「無人持有」「來源不明」）與判讀依據（`sessionId` 前 8 碼、log 時間與 `source`，或判不出的原因），之後接 context 段（見下方〈context 段的判讀〉）
- 已收線的線合併一行
- 過期項：票序以 `（無）` 開頭但後面還有文字（例如 `（無）— 說明`，看板不視為收線）、名稱不在存活 session 中但仍有佇列、佇列的票全部 completed 但還沒寫 `（無）`
- 等用戶：S1、S2、S3 任一訊號成立的項目，判讀與接續動作見 §2〈等用戶〉

**context 段的判讀**：接在依據之後，以 `｜` 分隔。判定與看板線標題同一份（門檻：一般線持有 in_progress 票 45%、未持有 30%，主控 60%）：

| context 段 | 意義 | 主控的接續動作 |
|-----------|------|---------------|
| `ctx <百分比>%（<距量測>）` | 用量未達門檻 | 無 |
| 後接 `［待 compact］` | 持有進行中的票且用量達門檻 | 在用戶待辦列「在 <線名> 執行 /compact」，該線的票做到可交接點時再做 |
| 後接 `［待 clear］` | 沒有進行中的票且用量達門檻 | 在用戶待辦列「在 <線名> 執行 /clear」；之後該線依 §2「/clear 後繼續」接續 |
| 後接 `［/compact 後已恢復 HH:MM］`（或 `/clear`） | 恢復開工後 10 分鐘內 | 依 §4〈線 session 的恢復開工通知〉只核對下一張票，不回覆 |
| `｜phase compacted（<來源>，HH:MM）` | compact／clear 做完但還沒送出下一個 prompt | 該線停著：確認用戶是否還要在那條線送一句話 |
| `｜phase resumed（<來源>，HH:MM）` | 已恢復開工（不受 10 分鐘限制） | 同上方徽章 |
| `ctx 未量測（<距量測>）` | compact 後還沒有下一次回應，用量未知 | 不判定；下一次呼叫再看 |
| `ctx 無用量檔` | 該 session 沒有用量檔（尚未回應過，或 plugin 版本早於用量檔） | 不判定 |
| `ctx 用量檔解析失敗：<原因>` | 用量檔存在但讀不成立（寫到一半、格式不符、檔內 sessionId 與檔名不符） | 再呼叫一次；持續出現時回報看板線 |

名稱未寫、名稱不在存活 session 中、session 檔沒有 `sessionId` 的線沒有 context 段，原因已寫在依據裡。

工具不判斷「時間是否晚於主控上次核對」，也不讀 `ListAgents`：拿輸出的 log 時間和協調票上的核對時間比對（步驟 5），並以步驟 2 核對名稱，再做步驟 6。判讀規則只在工具內實作一份，本節的步驟是工具的規格，也是工具不可用時的備援。

**備援：工具不可用時**（plugin 未載入、ToolSearch 查不到、工具回報無法判讀）依序執行：

1. 讀 `.claude/project-integration/multi-session.json` 的 `coordinationTicket`，再以 `ticket track full <協調票>` 取得 `## Solution` 段。每條線以這一段中最後一行現行佇列行為準。Completion Info 中若有舊的佇列行，不要當作現況。
2. 執行 `ListAgents`，記下每個同儕的名稱和本 session 的自稱。
3. 讀 `~/.claude/sessions/*.json`，以 `cwd` 篩出本 repo 的 session，取得每個名稱對應的 `pid` 和 `sessionId`。
4. 以每個 `sessionId` 的前 8 碼 grep `diagnostic.log`，取最後一筆的 `source` 和時間。
5. 以協調票上主控最後一次核對的時間為基準，依 §2 判斷每條線的狀態。
6. 只要有一條線的狀態和協調票上的記錄不同，就在協調票追加一段〈各線接續狀態核對（<日期 時間>）〉。這一段逐線寫出狀態和判讀依據（`sessionId` 前 8 碼和 log 時間），並更正先前的誤判。

備援時，步驟 3、4 可用以下唯讀查詢（只讀 `*.json`），在 repo 根目錄執行。它只讀主 checkout 的 log，在 worktree 內啟動的 session 會判為來源不明，工具則合併各 checkout 的 log：

```bash
python3 - <<'EOF'
import json, glob, os
repo = os.getcwd()
log = open('.claude/hook-logs/session-source-diagnostic/diagnostic.log').read().splitlines()
for f in glob.glob(os.path.expanduser('~/.claude/sessions/*.json')):
    d = json.load(open(f))
    if d.get('cwd') != repo:
        continue
    sid = d['sessionId'][:8]
    last = [l for l in log if f'session_id={sid}' in l][-1:]
    print(d.get('name'), d['pid'], sid, d.get('status'), last or '來源不明')
EOF
```

## 4. 主控長駐，與例外時（`/clear` 或 `/compact` 後）的自我接續

**定位：主控 session 長駐**（用戶裁定，2026-10-31）。主控不例行 `/clear` 或 `/compact`。

- 理由：各線的佇列、裁定、交接都經過主控，主控的對話是協調脈絡最完整的一份。清除之後只能從協調票重建，票面沒寫到的脈絡（口頭轉達的裁定、尚未寫入的佇列調整、等待中的授權）就遺失了。
- 例外：context 耗盡、或用戶明示要清除。本節以下的步驟是例外發生後的程序。
- 長駐不等於可以不寫票面：§4 的接續之所以可行，前提是主控平時就把裁定與佇列變動寫進協調票（見本節末〈這套流程的前提〉）。

**觸發條件**：主控 session 在 `/clear` 或 `/compact` 之後收到第一則訊息時，不論訊息內容是什麼，都先完成以下步驟，再處理訊息。不需要等用戶指出協調票或接續點。

**自動提示**：SessionStart hook `scripts/master_resume_hint.py`（專案 `settings.json` 註冊）在名為「主控」的 session 以 `source=clear` 或 `compact` 啟動時，以 additionalContext 提示本節步驟：呼叫 `line_status`、讀協調票、追加〈主控接續〉段。其他名稱或 `startup`／`resume` 不提示。名稱取自 `~/.claude/sessions/<pid>.json`：先以 `sessionId` 比對，比對不到再沿父行程鏈找 `<pid>.json`（`/clear` 不換 pid）。hook 只負責提醒，判讀由 `line_status` 做；沒收到提示不代表不用接續，觸發條件仍以本段為準。

**判斷自己是不是主控**：名稱是「主控」的 session 就是主控線（用戶裁定，2026-10-31）。以 `ListAgents` 第一行列出的本 session 自稱為準。

| 情況 | 做法 |
|------|------|
| 本 session 名為「主控」 | 本 session 就是主控，依下方步驟接續 |
| 本 session 不叫「主控」，而 `ListAgents` 中有其他 session 叫「主控」 | 本 session 是一般的線，不執行主控接續 |
| 沒有任何 session 叫「主控」 | 不要自行決定由誰擔任主控。列出目前的 session 和各自持有的線，請用戶指定其中一個 session 擔任主控，並請用戶在那個 session 輸入 `/rename 主控` |

**步驟**：

1. 依 §3 步驟 1 找到協調票，讀 `## Solution` 段最後幾段，找出前一個主控最後處理的事項和各線的現行佇列。
2. 呼叫 `line_status`（§3 主路徑；不可用時依 §3 步驟 2 到 5）判讀每條線的接續狀態。用戶常常在清除主控的同時，也清除其他線，所以不能沿用前一個主控的判斷。
3. 在協調票追加〈主控接續（<clear 或 compact>，<日期 時間>）〉段，內容包括：
   - 各線狀態（格式同 §3 步驟 6）
   - 前一個主控留下的待辦
   - 需要更正的地方
4. 推送協調票的 commit。
5. 先向用戶回報各線狀態和下一步，再處理用戶的訊息。

**名稱與線不一致時，提醒用戶**：判讀各線時也要核對名稱。用戶和主控靠名稱確認「現在討論的是哪一條線」，這是唯一的依據。名稱不符時，雙方會以為在談同一條線，實際上談的是不同的線。下表中的每項提醒都要寫出具體的名稱，讓用戶可以直接照著輸入。

| 情況 | 提醒用戶 |
|------|---------|
| 某個 session 的主軸已經換成另一條線，名稱仍是舊線的主題 | 請用戶在該 session 輸入 `/rename <新線主題>`。主控在同一步追加現行佇列行，括號內填新名稱（`session-naming.md` §3） |
| 要開新 session 接線 | 先告訴用戶新 session 的名稱，例如 `claude -n 拆檔`。等名稱出現在 `ListAgents` 中，才寫目標行和現行佇列行 |
| session 的名稱是自動產生的衍生名稱（例如 `<repo>-3e`），而它持有一條線 | 請用戶改成線主題的名稱 |

**`/compact` 和 `/clear` 的差別**：`/compact` 之後主控還有摘要，但摘要可能漏掉佇列細節和前一輪的更正。所以 `/compact` 之後同樣要重讀 Solution 段最後幾段，並重新判讀各線，不能只依靠摘要。

**這套流程的前提**：主控在 `/clear` 之前，已經把只存在對話中的待辦寫進協調票（`wrap-up-and-handoff.md` §3）。沒有寫進去的事項，接續之後無法找回。

### 線 session 的恢復開工通知

一般的線在 `/compact` 或 `/clear` 之後重新開工時，該線的 line-board plugin 自動通知主控。主控不必呼叫工具或詢問該線，就知道它已經回到工作狀態。

**判定**（plugin 事件，不靠 AI 回報）：

| 時點 | 事件 |
|------|------|
| compact 完成 | `session.compact` 完成且未被否決；`/compact` 與 auto compact 都算，precompute 與 subagent 自己的 compact 不算 |
| clear 完成 | `session.end` 的 reason 為 `clear` |
| 已恢復開工 | 上兩者之後第一個送出的 prompt（含 slash command）；`/compact`、`/clear` 本身不算 |

只有「已恢復開工」才通知。compact 做完時 session 可能還停著沒動，主控要知道的是它開始工作了。

**不通知**：新開的 session、resume、主控自身、已收線的線、名稱比對不到協調票現行佇列行的 session。

**兩個管道**：

| 管道 | 內容 | 主控怎麼看到 |
|------|------|-------------|
| 主管道（預設關閉，見〈已知限制〉） | 一則跨 session 訊息，固定一行：`L<n>（<名稱>）已恢復開工：<時間>，來源 compact／clear` | 直接出現在主控的對話 |
| 輔管道 | 該 session 的用量檔（`.claude/hook-logs/line-board/context/<sessionId>.json`）的 `phase` 欄位：`compacted`（做完未開工）或 `resumed`（已開工），附來源與時間 | 看板線標題與 `line_status`（讀取端依序上線） |

**送出紀錄檔**：主管道沒收到通知時，讀主 checkout 的 `.claude/hook-logs/line-board/resume-notice.log` 定位原因。該線每次恢復開工寫一行，欄位以 tab 分隔：`<時間>`、`session=<sessionId 前 8 碼>`、`source=<compact|clear>`、`step=<步驟>`，之後依步驟帶結果欄位。檔案只保留最後 500 行。

| step | 意義 | 結果欄位 |
|------|------|---------|
| `sent` | 已呼叫跨 session 傳送 | `isDelivered=true`；或 `isDelivered=false` 加 `reason=<拒絕原因>` |
| `skipped` | 判定不送 | `reason=`：`no-session-name`（狀態檔比對不到 sessionId）、`coordinator`（主控自身）、`lane-not-found`（名稱比對不到現行佇列行）、`lane-ended`（已收線） |
| `config-unavailable` | 專案設定讀不到或不成立 | `detail=<判定>：<訊息>` |
| `state-unavailable` | session 狀態檔或協調票讀不到 | `detail=session 狀態：<訊息>` 或 `detail=協調票：<訊息>` |
| `error` | 過程中丟出例外 | `detail=<例外訊息>` |
| `send-disabled` | 主管道開關關閉 | 無 |

紀錄檔沒有對應的一行，代表恢復開工沒有被判定到（例如熱重載遺失待通知狀態），問題不在傳送。

**主控收到通知時**：只核對，不回覆該線。核對內容：該線現行佇列行的下一張票是否和它接著要做的一致；不一致就依 §3 步驟 6 更正，並寫進協調票。

**已知限制**：

- 待通知狀態存在 plugin 的模組層變數。plugin 在 compact／clear 與下一個 prompt 之間熱重載時，狀態遺失，這一次不會發通知。不補救：輔管道的 `phase` 也會缺這一筆，主控以 `line_status` 判讀接續狀態（§3）為準。
- session 名稱以 `sessionId` 比對 `~/.claude/sessions/<pid>.json` 取得。`/clear` 換新 sessionId 但不換 pid，狀態檔若尚未更新成新的 sessionId，就比對不到名稱，主管道不送；`phase` 仍會寫入。
- 主管道的訊息在雙方權限模式不同時，會先被主控那邊暫扣，等用戶核可。實測被暫扣時，line-board 會關閉主管道，改以輔管道為主。
- **auto mode 下主管道不可用，以用量檔 phase、看板徽章、`line_status` 為準。** 實測（2026-10-31）plugin 在事件中主動送訊沒有對應的使用者請求，auto mode classifier 不給判定，紀錄檔為 `step=sent isDelivered=false`。這與暫扣同類，line-board 因此預設關閉主管道（紀錄檔為 `step=send-disabled`）。拒絕訊息裡的「重送一次」是給模型的指示，plugin 不自動重送，也不改用其他時點設法讓 classifier 放行。

### Stop hook 保護提醒的判讀

Stop hook〈Session Context 保護提醒〉會在回合結束時列出未完成的 context 敏感票，並要求評估「能不能清除」。這個提醒是給一般線的；在主控身上，正確的判讀問題不是「能不能清除」，而是「萬一要清除，協調票是否已經足以重建」。

| 步驟 | 做法 |
|------|------|
| 1. 列出本輪新增的協調事項 | 用戶的新裁定、轉達給各線的指示、佇列的排定與改派、等待中的授權、暫行規則 |
| 2. 逐項比對協調票 | 每一項都已寫進協調票的 `## Solution` 段（現行佇列行、目標行或裁定段）？ |
| 3. 沒寫的當下補寫並推送 | 補寫後才結束回合，不留到下一輪 |
| 4. 回報的結論 | 寫「本輪協調事項已全數寫入協調票（commit <hash>）」或列出補寫了哪些；不寫「可以 `/clear` 主控」，也不向用戶建議清除 |

違反的後果：把提醒讀成「現在可以清除」，主控會向用戶建議 `/clear`，而長駐是用戶的裁定。若當時有協調事項只在對話裡，清除後就遺失。實例：主控 `/clear` 實測完成後，對這則提醒做出「隨時可以 `/clear` 主控」的結論，由用戶更正（2026-10-31）。

提醒列出的其他線的票，主控不需要評估它們的 context：那些票的脈絡由持有它們的線負責寫進票面。

## 5. 用戶說「繼續工作」時：開線計畫表

**做法**：主控收到「繼續工作」這類沒有指定對象的指示時，不直接派票，依序做三件事：

1. 依 §4 完成自我接續，取得各線的現況。
2. 整理工作內容：各線現行佇列、未分派的票、等用戶裁定的事項。
3. 以下方固定格式列出開線計畫表，經用戶確認後才開線、寫佇列行、傳訊。

理由：「繼續工作」只授權推進，不代表授權開哪些線、開幾條線。主控直接派票的話，用戶要等到看見各線動作，才知道主控做了哪些安排。開線計畫表把這些安排先攤開，讓用戶在任何 session 啟動之前就能調整。

**開線計畫表格式**（每條線一列，已收線的線不列入）：

| 欄位 | 內容 |
|------|------|
| 線 | 線號，例如 `L37`。新線使用下一個未用過的號碼 |
| 動作 | 從下列五種中選一種：`新開`、`/clear 後接續`、`/compact 後接續`、`沿用`（session 正在執行，佇列沒有變動）、`改名接續`（session 不變，主軸換成這條線） |
| session 名稱 | 該線使用的名稱（線主題，主控為「主控」） |
| 用戶要做的事 | 用戶照著輸入的指令，例如 `claude -n 拆檔`、在 UX實驗 輸入 `/rename 版面斷言`。不需要用戶操作時寫 `—` |
| 目標 | 一句話寫出這條線要完成什麼。新線的目標會成為目標行 |
| 佇列 | 票序，格式同現行佇列行的票序 |
| 名額 | `heavy` 或 `light`，寫在哪一張票會用到 heavy |
| 注意 | 前置條件、等待的裁定、和其他線的衝突；沒有時寫 `—` |

表格下方另列兩項：

- **未分派的票**：這次不開線處理的票，每張附一句不開線的理由，例如「等用戶裁定」「依框架修補節奏不排線」。
- **待用戶裁定**：開線之前需要用戶回答的問題。

用戶確認後，主控依表格逐線處理：名稱出現在 `ListAgents` 中，才寫目標行與現行佇列行，然後傳訊指派。用戶修改表格的話，先更新表格，再依修改後的內容處理。

## 6. 升版後的確認方式

1. 在測試用的 session 執行 `/clear`。確認：
   - session 檔的 `sessionId` 已經換新，`name` 沒有變。
   - log 中有一筆 `source=clear`，id 是新的 `sessionId`。
2. 執行 `/compact`。確認 `sessionId` 沒有變，而 log 中同一個 id 多了一筆 `source=compact`。
3. 以 `claude -n <名稱>` 開一個新的 session。確認 log 中有一筆 `source=startup`。

只要有一項不符，就表示行為已經改變。先修正本檔 §1 和 §2，再繼續使用。
