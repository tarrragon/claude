# 審查標記與查證

多線並行時，PM 收到的「某處可能有問題」來自三種來源：推送後的背景安全審查、各線轉交的發現、PM 自己的巡查。本檔規範怎麼查證這些標記，以及怎麼驗證守衛類修正。

---

## 1. 只有標題的背景安全審查標記

**現象**：推送或 commit 後的背景審查常只送達一行標題（例如「authorization-bypass in <檔案>」），沒有細節。

**原則**：只有標題的標記不能預設為誤報。這類標記的查證結果應累積在同一張追蹤票（見步驟 5），已累積的紀錄中有屬實的回歸，而且屬實者多半出現在「為了減少誤擋而放寬判定」的修改之後。預設為誤報的後果，是讓剛開出的繞過留在 main 上。

**處理流程**：

| 步驟 | 做法 |
|------|------|
| 1. 歸屬 | 查該檔最近的 commit，轉給改動它的那條線；轉交時附上 PM 已查到的事實 |
| 2. 比對已接受殘留 | 若該守衛有用戶已裁定接受的殘留，先比對標記是否就是其中之一；是 → 在票面註記「審查命中已接受殘留」即結束 |
| 3. 新舊版端到端比對 | 在改動前的 commit（`<commit>^1`）開 detached worktree，與現行 main 用同一組輸入跑同一個判定函式或 hook payload；找出「新版放行、舊版擋下」的寫法 |
| 4. 判定 | 新版放行而舊版擋下 → **回歸**，開 P1 子票交原線；兩版都放行 → **既有缺口**，依嚴重度另開票，不阻擋原票結案；找不到差異 → 記錄已自查的路徑與結論，標為「已自查、未取得原文、未判誤報」 |
| 5. 彙整 | 每一例都記入同一張追蹤票，累積成「審查標記命中率」的依據 |

**同一支守衛被標記兩次以上時**：不要只修標題指出的第一個入口，把該守衛所有同類寫法（例如全部正則）都用最壞情況輸入量一輪再合併。

---

## 2. 守衛類修正的驗證

| 要求 | 理由 |
|------|------|
| 正向對照：應擋的輸入在修正後仍被擋 | 守衛的失效方向是放行，只驗「原本誤擋的現在放行了」看不出新開的繞過 |
| 新舊兩版逐筆比對同一組 payload | 區分回歸與既有缺口 |
| 實地觸發用不會產生副作用的寫法 | 例如以 `false && <被守衛的命令>` 串接，命令永不執行，但 hook 仍會看到完整命令 |
| 複雜度驗證用步數，不用計時 | 計時斷言在高負載的閘門中會間歇失敗；用計數器斷言「輸入長度 4 倍時步數不超過 4 倍加常數」，計時測試標為 wallclock 不進主套件 |
| 解析失敗或逾時的方向要明寫 | hook 逾時被放行時，能拖慢解析就能繞過守衛；阻擋型守衛的解析須保證線性時間 |

## 3. 讀 log，不只信摘要

各線的摘要由各線自己寫，會漏報。以下事實一律以世界平面為準：

| 要確認的事 | 查哪裡 |
|------|------|
| 某筆合併是否經過閘門、結果為何 | 閘門 log 中以分支名配對的〔開始〕與〔結束〕兩行（佇列中多筆合併的開始與結束會交錯，不可只看相鄰兩行） |
| 目前誰持有名額、誰在排隊 | holder 檔與佇列檔；單一時刻的快照容易把剛換手的持有者與排隊者看混，有疑義時以時間序列重建 |
| 某 commit 是否在 main | `git merge-base --is-ancestor <commit> origin/main` |
| 某測試在 main 上是否本來就紅 | 經 `run-with-timeout` 在 main 單獨跑該測試 |

---

## 4. 測試涵蓋範圍的常見漏洞

| 漏洞 | 後果 | 防法 |
|------|------|------|
| 改了 A 處，壞的是 B 處的測試（不在「相關」範圍內） | 合併時以為綠燈，main 被弄紅，下一個合併的人才發現 | 合併一律走閘門全套件；派發時測試範圍依「誰呼叫被改的程式」列，不依「改了哪些檔」 |
| 手動跑測試時帶了路徑參數，測試框架（例如 pytest）忽略設定檔的測試路徑清單，只跑到一部分 | 回報「全套件通過」，實際只跑了一半，輸出看起來完全正常 | 手動跑不帶路徑參數；權威結果以閘門為準 |
| 移除某條行為後，舊測試仍以該行為的資料模擬 | 被移除的路徑由其他測試檔繼續「驗證」，閘門紅燈 | 以被移除行為的特徵 grep 全部測試檔，不憑檔名猜 |
| 刪除某個結構前只搜結構名 | 讀取結構內欄位的測試沒被找到，刪除後紅燈 | 搜結構內每個欄位名在測試中的讀取 |
