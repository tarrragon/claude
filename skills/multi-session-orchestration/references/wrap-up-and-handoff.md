# 階段收尾與交接

額度限制、預定休息、或 session 可能意外結束時，主控 PM 要讓「下一個 session 只讀票面與工作日誌就能接手」。本檔是收尾程序與總表格式。

---

## 1. 給各線的收尾指示（逐線發送）

1. 不再派發新的代理人，不開始新的票。
2. 正在跑的代理人：快完成的讓它完成並提交；其餘請它把進度寫進票面後停手。
3. 已送出的閘門程序讓它自行跑完（閘門程序與 session 獨立，結果會寫進閘門 log）；尚未送出的合併與批次先不送。
4. 每張 in_progress 的票，在 Problem Analysis 補〈階段收尾狀態〉（欄位見下節）。
5. 收尾時記下的技術債或其他發現，先建票再結束，不能只在票面寫「未開票」。
6. 票面 commit 推送到 origin。
7. 回報摘要：今日結案、in_progress 與分支、閘門佇列中的項目、重開後的佇列順序，以及第 5 步新建的票號。

**理由**：中止已在佇列中的閘門會浪費已排的時間；讓它跑完，重開後讀 log 就知道結果。線結束後，記下發現的那個 session 就不在了，只寫在收尾段的發現沒有人會再去處理。

**PM 查證線的收尾**：讀該線寫下的收尾段，看到尚未開票的發現就由 PM 代建，`--source-ticket` 指向發現所在的票。

---

## 2. 〈階段收尾狀態〉欄位

| 欄位 | 內容 |
|------|------|
| 進度 | 做到哪一步（實作完成／審查通過／已送閘門／已寫入未 complete） |
| 分支與 commit | worktree 分支名與最後一個 commit |
| 閘門 | 是否在佇列中、最近一次閘門結果（寫入／紅燈／拒絕）與失敗細節位置 |
| 下一步 | 重開後第一個動作，含其前置條件（例如「等某票寫入 main 後再重派」） |

**代理人停在實作開始之前是最乾淨的中斷點**：只要設計要點已寫在票面，重派即可接手。實作到一半只存在 worktree 的內容最容易遺失。

---

## 3. PM 的總表

收齊各線摘要後，PM 把總表寫進版本工作日誌（不是只回覆給用戶）：

| 區塊 | 內容 |
|------|------|
| 各線重開後的佇列 | 每線一列：閘門中、已審查未送、重開順序；已停止的線註明交接位置 |
| PM 待辦 | 只存在 PM 對話中的事：待用戶授權的動作、等其他票的前置條件、待落地的慣例 |
| 仍有效的暫行規則 | 每條附撤除條件 |
| 本日用戶裁定 | 逐條列出，避免重開後重問 |

**收尾期間新增的裁定要補寫**：收尾後用戶若又做了裁定（例如「某件事完成後再做 X」），立刻補進總表並推送。

**PM 本身換 session 時，總表要能被 handoff 機制讀到**：工作日誌只有被人主動讀才有用，新 session 啟動時自動提示的是 `.claude/handoff/pending/` 下的 handoff 檔。兩者要同時建立：

| 步驟 | 做法 | 不這樣做的後果 |
|------|------|---------------|
| 標題 | 交接段標題以「下個 Session 接手 Context」開頭（關鍵字前只能有 `#` 或空白，日期放在後面） | 解析器只認行首關鍵字；標題不符時，`ticket handoff --from-worklog` 與 Stop hook 的雙軌同步檢查都看不到這段 |
| 票號 | 段內列一行完整票號（`<版本>-W<波次>-<序號>`），依建議順序 | 表格裡的短寫（例如只寫序號）解析不到，偵測到段落卻沒有票 |
| 建 handoff | 以本 session 最後完成的票為來源：`ticket handoff --from-ticket-id <已完成票> --next <第一張接手票>` | pending 的票不能當交接起點，`--from-worklog` 對它們會失敗；不建 handoff，新 session 啟動時沒有任何提示 |
| 驗證 | 手動跑一次 SessionStart 的排程提示 hook，確認輸出帶出第一張接手票 | 寫了但格式不對時，要到新 session 開啟才發現 |

handoff 檔在 gitignore 範圍內，只存在本機；換機器接手時，以工作日誌的交接段為準。

---

## 4. 收尾後的例外恢復

用戶可能在收尾後指定少數幾件事先完成（例如發佈前必須先修的回歸）。做法：只讓負責的線恢復那一件，訊息中明寫「其他票維持暫停」；完成後再回到收尾狀態。沒有寫明時，各線容易把恢復訊息讀成收尾全面解除，重新開始派發，收尾時寫好的交接狀態隨即過期。

---

## 5. 重開時的第一步

0. 主控 session（名為「主控」）在 `/clear` 或 `/compact` 後，先依 `line-continuity.md` §4 自我接續，再執行以下步驟。
1. 讀版本工作日誌的收尾總表。
2. 讀閘門 log 中各筆的結束行，以分支名配對，確認收尾時在佇列中的合併結果。
3. 讀各 in_progress 票的〈階段收尾狀態〉，以此為準（總表是索引，票面是權威）。
4. 依總表的 PM 待辦，向用戶確認待授權事項。
