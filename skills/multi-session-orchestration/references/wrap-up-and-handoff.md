# 階段收尾與交接

額度限制、預定休息、或 session 可能意外結束時，主控 PM 要讓「下一個 session 只讀票面與工作日誌就能接手」。本檔是收尾程序與總表格式。

---

## 1. 給各線的收尾指示（逐線發送）

1. 不再派發新的代理人，不開始新的票。
2. 正在跑的代理人：快完成的讓它完成並提交；其餘請它把進度寫進票面後停手。
3. 已送出的閘門程序讓它自行跑完（閘門程序與 session 獨立，結果會寫進閘門 log）；尚未送出的合併與批次先不送。
4. 每張 in_progress 的票，在 Problem Analysis 補〈階段收尾狀態〉（欄位見下節）。
5. 票面 commit 推送到 origin。
6. 回報摘要：今日結案、in_progress 與分支、閘門佇列中的項目、重開後的佇列順序。

**理由**：中止已在佇列中的閘門會浪費已排的時間；讓它跑完，重開後讀 log 就知道結果。

---

## 2. 〈階段收尾狀態〉欄位

| 欄位 | 內容 |
|------|------|
| 進度 | 做到哪一步（實作完成／審查通過／已送閘門／已寫入未 complete） |
| 分支與 commit | worktree 分支名與最後一個 commit |
| 閘門 | 是否在佇列中、最近一次閘門結果（寫入／紅燈／拒絕）與失敗細節位置 |
| 下一步 | 重開後第一個動作，含其前置條件（例如「等某票寫入 main 後再重派」） |

**代理人停在實作開始之前是最乾淨的中斷點**：只要設計要點已寫在票面，重派即可接手。實作到一半只存在 worktree 的內容最容易遺失。

---

## 3. PM 的總表

收齊各線摘要後，PM 把總表寫進版本工作日誌（不是只回覆給用戶）：

| 區塊 | 內容 |
|------|------|
| 各線重開後的佇列 | 每線一列：閘門中、已審查未送、重開順序；已停止的線註明交接位置 |
| PM 待辦 | 只存在 PM 對話中的事：待用戶授權的動作、等其他票的前置條件、待落地的慣例 |
| 仍有效的暫行規則 | 每條附撤除條件 |
| 本日用戶裁定 | 逐條列出，避免重開後重問 |

**收尾期間新增的裁定要補寫**：收尾後用戶若又做了裁定（例如「某件事完成後再做 X」），立刻補進總表並推送。

---

## 4. 收尾後的例外恢復

用戶可能在收尾後指定少數幾件事先完成（例如發佈前必須先修的回歸）。做法：只讓負責的線恢復那一件，訊息中明寫「其他票維持暫停」；完成後再回到收尾狀態。沒有寫明時，各線容易把恢復訊息讀成收尾全面解除，重新開始派發，收尾時寫好的交接狀態隨即過期。

---

## 5. 重開時的第一步

1. 讀版本工作日誌的收尾總表。
2. 讀閘門 log 中各筆的結束行，以分支名配對，確認收尾時在佇列中的合併結果。
3. 讀各 in_progress 票的〈階段收尾狀態〉，以此為準（總表是索引，票面是權威）。
4. 依總表的 PM 待辦，向用戶確認待授權事項。
