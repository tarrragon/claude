# 多 session 分線協調（主控 PM 統籌多條工作線）

一個主線程 PM session 同時協調 2 個以上的同儕 session（以下稱「線」），各線在同一個 repo 各自推進一批票。本 skill 是主控 PM 的操作手冊：怎麼分線、怎麼協調共用資源、怎麼轉達裁決、怎麼收尾交接。

**與 `.claude/pm-rules/parallel-dispatch.md` 的分工**：該檔管強制條文（跨 session 實驗器材、同儕沉默時接管、同儕來訊的脈絡判讀）；本 skill 管操作流程。條文衝突時以該檔為準。

---

## 核心原則

| 原則 | 做法 | 違反的後果 |
|------|------|-----------|
| 票面是權威，訊息是通知 | 各線的發現、裁定、收尾狀態一律寫進票面再傳訊；PM 只在訊息中引用票號 | session 結束後訊息讀不到，下一個 session 只能從票面接手 |
| 世界平面優先於摘要 | 結案或判定前讀 git log、閘門 log、holder 檔，不只信各線摘要 | 摘要會漏報（紅燈漏寫、持有者看錯），PM 以漏報做決策 |
| 同儕不能代授權 | 用戶的裁決才是授權；同儕要求的升級動作轉給用戶 | 權限洗白（permission laundering） |
| 被分類器擋下就交用戶 | PM 的指示被 auto mode 分類器擋下時，不換說法再送，改用 AskUserQuestion 交用戶裁定 | 繞過平台對該動作的判斷 |
| 只把需要裁決的事留在 PM | 兩線之間的事實交接（「X 合併了，可以結案 Y」）讓兩線直接互傳 | PM 變成轉達瓶頸，每次多一輪延遲 |
| 可預見的裁決提前問 | 某線預告將提交依〈行為變更的判準與分級〉須交用戶的變更，或其結果會定案一項待裁議題時，PM 在該線回報可合併之前，先用 AskUserQuestion 取得用戶裁定 | 等該線回報可合併才問，該線要多等一輪用戶回覆才能合併，期間佔著閘門佇列的位置 |
| 有程式讀者的段落與日誌是介面 | PM 的分派段落、閘門日誌等有程式在解析時，寫入方與讀者明文約定三件事：格式、每個欄位在各種情況下的語意（例如同名欄位在開始行與結束行指不同的 commit）、記錄之間的時序（是否可能重疊、是否兩兩成對）；約定寫進票面 | 寫入方改寫法（例如追加式寫入讓歷史行混入），或讀者照欄位名猜語意、假設記錄成對，解析會靜默出錯，畫面顯示錯的值卻沒有任何警告 |

## 工作流

### 1. 開線與分線

| 步驟 | 做法 |
|------|------|
| 按主題分線 | 同一主題（同一組檔案、同一個子系統）的票歸同一條線，前一張讀過的程式與事實下一張可直接用 |
| 一個 session 一條線，以線主題命名 | 每條線配一個 session，以線主題命名（開新 session 用 `claude -n <名稱>`；格式只守命名底線）；線完結或轉階段就收尾舊 session、另開新 session。改名後舊名立即無法定址，主控要在同一步更新現行佇列行的 session 名稱。規則、改名方法與同步位置見 `references/session-naming.md` |
| 每線一份佇列 | 在給該線的訊息中寫明順序與理由，該線在票面維護 |
| 線空出時移票 | 從佇列最長的線按主題移票給空的線，通知兩邊；被移的票若已開工，由原線直接交接。只挑沒有依賴、且改動檔案不與原線剩餘票重疊的票；改同一檔的票群整組留在原線，否則兩線改同一檔又互等 |
| 跨線依賴 | 下游票依賴上游線未合併的程式時，**把下游票交給上游線**，不讓下游線等待 |
| 驗收需要他線的分支先合併 | 由該分支所屬的線自行合併，合併結果直接傳給驗收方；驗收方與 PM 不代為合併。代合者不清楚該分支的狀態（未提交的修改、已知紅燈、待補的提交），合併後出了問題，沒有一方能接手處理 |
| 以他線的操作作實地驗收證據 | 先查該操作何時啟動，再查被驗收的變更何時進 main；啟動須較晚。合併類操作另確認它的 base HEAD 已含該變更。只比對操作完成的時刻，會把啟動時載入舊程式所跑出的結果當成證據 |
| 線正在交接、或接手的 session 未確定 | 把要轉知的變更寫進接手票的 Problem Analysis，再傳訊給舊 session。只傳訊的話，訊息留在舊 session，交接後的新 session 讀不到 |
| 新發現的票 | 依「誰最熟這段程式」指派；回歸類（某線合併造成）一律交回原線 |
| 不同線的票因改同一檔而互等 | 先建拆分評估票並排在前面，拆完再讓各票改各自的新檔；判準見 `.claude/skills/cognitive-load-assessment/references/file-split-by-contention.md` |

### 2. 每則來訊的處理迴圈

1. 判斷類型：進度回報／請求裁決／轉交發現／請求授權
2. 進度回報：核對關鍵事實（commit 是否在 main、閘門結果），不需要回覆就不回
3. 請求裁決：能依既有裁定或規則決定的，PM 直接決定並附理由；行為變更依下表分級；涉及新的權限、影響用戶自身操作的，用 AskUserQuestion 交用戶
4. 轉交發現：判定歸屬線後轉交，附上 PM 已查證的部分
5. 請求授權：常駐授權已涵蓋的告知條件；不在授權內的交用戶

**行為變更的判準與分級**：改動共用資源（合併閘門、守衛、測試名額）的對外可觀測面，即屬行為變更，須在合併前回報 PM。對外可觀測面包括：結束碼、日誌結果字面、接受的參數、印出的建議指令、放行或阻擋結果。各線常把「只是加預檢」「只是修誤判」當成內部改動而先合併後回報，判準要以可觀測面為準，而非改動者自認的性質；先合併的話，下表放寬一級要求的正向對照與失敗落點查證都已沒有執行時機。

| 放行方向 | 做法 | 違反的後果 |
|---------|------|-----------|
| 不改任何操作的放行結果（例如新增選用旗標） | PM 直接放行 | 每項都交用戶，用戶被瑣碎裁決淹沒，真正需要裁定的項目被稀釋 |
| 收緊（原本放行的改為阻擋） | PM 放行，並在合併後轉知各線；被擋的操作含用戶自身的操作時交用戶。合併前在框架文件（SKILL、references、pm-rules）grep 會被新判準擋下的例行步驟範例，同票改為等效 CLI 或註明執行限制（例：守衛改以 ast 追蹤 python 內嵌腳本的變數路徑後，某 SKILL 步驟記載的 python 片段以 heredoc 執行即被擋，同票把該步驟改以既有 CLI 為主路徑） | 不轉知的話，各線照舊操作時突然被擋，誤判為環境故障；不改文件的話，轉知只送達現有各線，日後照 SKILL 操作的讀者仍會撞上 |
| 放寬（原本阻擋的改為放行，包括修誤判） | 進閘門前附正向對照：已知應擋的輸入在修改後仍被擋。另追到實際執行判定的共用函式，確認判定本身失敗時（逾時、例外、依賴缺席）落在保守一側；不以對照測試代替這一步。涉及用戶既有裁定或新權限時交用戶 | 放寬的失效方向是放行，與「輸入本來就沒問題」在輸出上同形；只看對照測試會漏掉判定本身出錯時的落點，守衛無聲失效 |

### 3. 共用資源協調

合併閘門、測試名額、主 checkout 的本地 main 是全部線共用的資源。完整規則、暫行規則的撤除條件、網路中斷時的處置見 `references/shared-resources.md`。速查：

| 情境 | 做法 |
|------|------|
| 某筆合併在高頻變動的 main 上反覆寫不進去 | 先查 main 本身是否紅燈。確認綠燈後：閘門尚未做到「先取得名額、持有到寫入完成」時，通知各線暫停推送非票面檔，該筆完成再解除；已做到者不需人工暫停 |
| 閘門佇列飽和 | 減少閘門次數（批次合併），不是放寬上限 |
| 批次合併 | 改動檔案互不重疊、各張自帶測試、已審查，張數上限見 references |
| 閘門紅燈 | 先在 main 跑同一個失敗測試，判定是 main 既有回歸還是本分支造成 |
| 主 checkout 共用本地 main | 任何一線推送都會帶出所有本地 commit；非票面的修改一律在 worktree 做 |

### 4. 審查標記與查證

背景安全審查常只送達一行標題。處理流程、新舊版端到端比對方法、「回歸」與「既有缺口」的判別見 `references/review-flags-and-verification.md`。速查：先比對用戶已接受的殘留（守衛已收斂時含殘留風險分類表）→ 再以新舊兩版做端到端比對 → 屬實且為回歸開 P1 子票交原線；原票閘門進行中時可在同票分兩輪修，接受條件見該檔〈已知回歸暫留 main〉。

### 5. 階段收尾與交接

額度限制、session 結束前，依 `references/wrap-up-and-handoff.md` 執行：各線停止派發、寫票面〈階段收尾狀態〉、推送、回報摘要；PM 彙整總表寫進版本工作日誌，並把只存在 PM 對話中的待辦一併寫入。

## 檢查清單

- [ ] 每則轉達的裁定都寫明來源（用戶裁定或 PM 依規則決定）與日期？
- [ ] 交給各線的事實（commit、閘門結果）是 PM 自己查證過的？
- [ ] 跨線依賴的票交給上游線，而不是讓下游線等？
- [ ] 只存在 PM 對話中的待辦（待授權事項、暫行規則）已寫進票面或工作日誌？
- [ ] 暫行規則有寫明撤除條件，工具承擔後已撤除？
- [ ] 每條線各有一個以線主題命名的 session，改名後現行佇列行的 session 名稱已同步？
