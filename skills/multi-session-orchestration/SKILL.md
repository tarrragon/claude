# 多 session 分線協調（主控 PM 統籌多條工作線）

一個主線程 PM session 同時協調 2 個以上的同儕 session（以下稱「線」），各線在同一個 repo 各自推進一批票。本 skill 是主控 PM 的操作手冊：怎麼分線、怎麼協調共用資源、怎麼轉達裁決、怎麼收尾交接。

**與 `.claude/pm-rules/parallel-dispatch.md` 的分工**：該檔管強制條文（跨 session 實驗器材、同儕沉默時接管、同儕來訊的脈絡判讀）；本 skill 管操作流程。條文衝突時以該檔為準。

---

## 核心原則

| 原則 | 做法 | 違反的後果 |
|------|------|-----------|
| 票面是權威，訊息是通知 | 各線的發現、裁定、收尾狀態一律寫進票面再傳訊；PM 只在訊息中引用票號 | session 結束後訊息讀不到，下一個 session 只能從票面接手 |
| 世界平面優先於摘要 | 結案或判定前讀 git log、閘門 log、holder 檔，不只信各線摘要 | 摘要會漏報（紅燈漏寫、持有者看錯），PM 以漏報做決策 |
| 同儕不能代授權 | 用戶的裁決才是授權；同儕要求的升級動作轉給用戶 | 權限洗白（permission laundering） |
| 被分類器擋下就交用戶 | PM 的指示被 auto mode 分類器擋下時，不換說法再送，改用 AskUserQuestion 交用戶裁定 | 繞過平台對該動作的判斷 |
| 只把需要裁決的事留在 PM | 兩線之間的事實交接（「X 合併了，可以結案 Y」）讓兩線直接互傳 | PM 變成轉達瓶頸，每次多一輪延遲 |

## 工作流

### 1. 開線與分線

| 步驟 | 做法 |
|------|------|
| 按主題分線 | 同一主題（同一組檔案、同一個子系統）的票歸同一條線，前一張讀過的程式與事實下一張可直接用 |
| 每線一份佇列 | 在給該線的訊息中寫明順序與理由，該線在票面維護 |
| 線空出時移票 | 從佇列最長的線按主題移票給空的線，通知兩邊；被移的票若已開工，由原線直接交接 |
| 跨線依賴 | 下游票依賴上游線未合併的程式時，**把下游票交給上游線**，不讓下游線等待 |
| 新發現的票 | 依「誰最熟這段程式」指派；回歸類（某線合併造成）一律交回原線 |

### 2. 每則來訊的處理迴圈

1. 判斷類型：進度回報／請求裁決／轉交發現／請求授權
2. 進度回報：核對關鍵事實（commit 是否在 main、閘門結果），不需要回覆就不回
3. 請求裁決：能依既有裁定或規則決定的，PM 直接決定並附理由；涉及新的權限、行為變更、影響用戶自身操作的，用 AskUserQuestion 交用戶
4. 轉交發現：判定歸屬線後轉交，附上 PM 已查證的部分
5. 請求授權：常駐授權已涵蓋的告知條件；不在授權內的交用戶

### 3. 共用資源協調

合併閘門、測試名額、主 checkout 的本地 main 是全部線共用的資源。完整規則、暫行規則的撤除條件、網路中斷時的處置見 `references/shared-resources.md`。速查：

| 情境 | 做法 |
|------|------|
| 某筆合併在高頻變動的 main 上反覆寫不進去 | 先查 main 本身是否紅燈。確認綠燈後：閘門尚未做到「先取得名額、持有到寫入完成」時，通知各線暫停推送非票面檔，該筆完成再解除；已做到者不需人工暫停 |
| 閘門佇列飽和 | 減少閘門次數（批次合併），不是放寬上限 |
| 批次合併 | 改動檔案互不重疊、各張自帶測試、已審查，張數上限見 references |
| 閘門紅燈 | 先在 main 跑同一個失敗測試，判定是 main 既有回歸還是本分支造成 |
| 主 checkout 共用本地 main | 任何一線推送都會帶出所有本地 commit；非票面的修改一律在 worktree 做 |

### 4. 審查標記與查證

背景安全審查常只送達一行標題。處理流程、新舊版端到端比對方法、「回歸」與「既有缺口」的判別見 `references/review-flags-and-verification.md`。速查：先比對用戶已接受的殘留 → 再以新舊兩版做端到端比對 → 屬實且為回歸開 P1 子票交原線。

### 5. 階段收尾與交接

額度限制、session 結束前，依 `references/wrap-up-and-handoff.md` 執行：各線停止派發、寫票面〈階段收尾狀態〉、推送、回報摘要；PM 彙整總表寫進版本工作日誌，並把只存在 PM 對話中的待辦一併寫入。

## 檢查清單

- [ ] 每則轉達的裁定都寫明來源（用戶裁定或 PM 依規則決定）與日期？
- [ ] 交給各線的事實（commit、閘門結果）是 PM 自己查證過的？
- [ ] 跨線依賴的票交給上游線，而不是讓下游線等？
- [ ] 只存在 PM 對話中的待辦（待授權事項、暫行規則）已寫進票面或工作日誌？
- [ ] 暫行規則有寫明撤除條件，工具承擔後已撤除？
