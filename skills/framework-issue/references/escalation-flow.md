## 角色：主控方與 consumer

**判定**：專案的 `CLAUDE.md` 宣告本專案是框架主控方，該專案就是主控方；其他使用本框架的專案都是 consumer。同一時間只有一個主控方。框架規則中提到「主控方」或「consumer」之處，都依本節判定。

| 角色 | 框架問題的處置 | 取得框架的方式 |
|------|--------------|--------------|
| 主控方 | 修改 `.claude/`，依版本規劃排入 patch 或 minor，發版時才執行 `sync-push` 並打 `v<版號>` tag | 本身即來源 |
| consumer | 只回報：建 issue 或以 `observe` 附加既有 issue，回報時附上 `.claude/VERSION`。不修改 `.claude/` 通用資產 | `sync-pull` 拉取已發版的 tag |

**例外：skill 開發上游**。skill 依下游專案的需求而長出來，開發地點可以在 consumer。consumer 的 `CLAUDE.md` 宣告本專案是某個 skill 的開發上游時，該 consumer 可以在本地修改這個 skill，完成後以 `skill-sync push` 送進發佈庫（`tarrragon/claude-skills`），不執行 `sync-push`。主控方發版前以 `skill-sync pull <name>` 從發佈庫收入，隨發版推送到框架 canonical。例外只涵蓋宣告的 skill；同一 consumer 對其他 `.claude/` 資產仍只回報。

| 步驟 | 執行者 | 動作 |
|------|-------|------|
| 1 | 宣告為該 skill 上游的 consumer | 修改 skill，`skill-sync push <name>` 送進發佈庫 |
| 2 | 主控方 | 發版前 `skill-sync pull <name>` 收入，檢查框架引用錨點未斷，commit |
| 3 | 主控方 | 發版時 `sync-push`，其他 consumer 以 `sync-pull` 取得 |

**Why**：`sync-push` 只在主控方發版時執行，canonical 上的每個 tag 都是一個有規劃的版本。consumer 沒有把修改送上 canonical 的通道；skill 開發上游的修改改走發佈庫，由主控方收入。

**Consequence**：consumer 若在本地修改 `.claude/`，修改只存在該專案，下一次 `sync-pull` 會被上游版本覆蓋，而且 canonical 沒有紀錄，其他 consumer 仍帶著同一缺陷。

**Action**：開始處理框架問題前，先讀本專案 `CLAUDE.md` 判定角色。consumer 一律走〈兩條路徑〉的路徑 A；問題落在本專案宣告為上游的 skill 時，改依上方例外修改並 `skill-sync push`。主控方依〈修復時點〉的版本分診決定何時修。

## 介入判斷：框架問題 vs 專案問題

**判準**（同時符合視為框架問題）：

| 判準 | 說明 |
|------|------|
| 抽象可攜性 | 敘述替換掉本專案名稱與檔案路徑後依然成立（「Hook X 對某類副檔名誤判」而非「本專案的 Y 檔案有 bug」） |
| 資產範圍 | 根源在 `.claude/` 下的通用資產（hooks／skills／rules／methodologies／agents），非 `lib/`、`docs/` 等專案專屬產物 |

**Why**：框架資產由 sync-push／sync-pull 在多個 consumer 間共享，本地直接修復只解決當前專案的徵狀，其他 consumer 仍帶著同一缺陷；貼著單一 consumer 特例的修法，日後 sync-pull 覆蓋時復發。

**Consequence**：略過判斷直接在當下 ticket 內修 `.claude/` 通用資產，修復困在本地 commit 歷史不會傳播；下次 `sync-pull` 可能用上游未修的舊版覆蓋掉本地修復，且無 canonical 記錄可查。

**Action**：識別為框架問題時走查重 SOP，再依兩條路徑擇一銜接，不在當前 ticket 直接編輯 `.claude/` 檔案了事。

## 兩條路徑

| 路徑 | 適用情境 | 動作 |
|------|---------|------|
| A：先記錄，不接手 | consumer 的所有框架問題；主控方則是當下 ticket 的主要目標不是修這個框架問題（順手發現），或依〈修復時點〉不在本版處理、也未被版本規劃選入 | 建立或附加 framework issue 記錄徵狀；為這個問題建的本地 ticket 以收束配方的 close 命令關閉（reason-note 寫「已遷至 tarrragon/claude#N」，issue 為唯一權威，版本規劃選入時從 issue 區段重新建票），並**當下**建一張驗證 ticket（pending，`why` 引用該 issue，`when` 寫「sync-pull 帶回含 fix-version 的版本後」），承擔者是執行 `sync-pull` 的 PM，在 runqueue 看到它即接手 |
| B：當下接手 | 只在主控方：依〈修復時點〉本版處理的例外（P0／P1 阻擋、用戶要求），或版本規劃已選入的範圍 | 在主控方 repo 修復，隨該版發版推送到 canonical，發版後走下方關閉協定 |

**Why**：框架問題的修復地點是 canonical repo；本地 ticket 若卡在框架缺陷上又不切割，專案層任務的驗收會綁死在框架修復進度上。

**Consequence**：路徑 A 若省略 close 與驗證票、直接放著，違反品質基線規則 5（發現必須追蹤）與決策 trigger 綁定規則。issue ref 與「sync-pull 帶回修復」都不是合法 trigger，合法 trigger 只有 ticket，所以驗證票要在路徑 A 當下建立，不等修復發生。

**Action**：路徑 A 的 close 命令與 reason-note 禁詞見 `references/ticket-intake.md` 的〈步驟五：ticket 處置〉；路徑名不可抄進 reason-note。路徑 B 修復完成後立即執行關閉協定。

## 修復時點：版本分診

**適用角色**：本節的修復時點判準只適用主控方（角色判定見〈角色：主控方與 consumer〉）。consumer 不決定修復時點，一律走路徑 A；碰到框架阻礙時照下方〈拖慢專案標記〉附一則觀測，主控方在規劃期讀取。

**原則**：主控方決定框架問題何時修，只用版本分診一套判準。發現照常當下建票（品質基線規則 5 不變），排入哪一版依 `.claude/pm-rules/version-progression.md`〈兩期：規劃期與執行期〉與〈收斂：patch 線與 minor 推進〉判定，結果記在主控方的版本規劃文件。下表前兩列是本版處理的例外，對齊〈兩期〉的 `--scope-blocker`。

| 情況 | 處置 |
|------|------|
| P0／P1 的 bug，且 PM 已查證它正在阻擋本版工作 | 本版處理（路徑 B），建票帶 `--scope-blocker <理由>` |
| 用戶要求本版修這一項 | 本版處理（路徑 B），`--scope-blocker` 理由寫用戶要求與日期 |
| 其餘 | 依〈兩期〉與〈收斂〉分診：規劃期的發現進本版規劃；執行期的發現，承諾未達成的進 patch，改善、技術債、條文缺口進下一個 minor 的候選池 |

**拖慢專案標記**：任何專案因框架問題需要繞路、重做或停工時，在該 issue 以 `observe` 附一則，首行寫「拖慢專案」與受影響的工作。只是讀到、或順手發現，不算拖慢。

**規劃期的輸入清單**：主控方每個版本進入規劃期時，整理 open issue 清單（各 issue 的拖慢標記數、觀測數、最近一次觀測時間），交用戶挑選。同一 issue 的拖慢標記達 2 則，就是之後第一個版本規劃期的必審項：選入該版，或在規劃文件寫明不選的理由。

**Why**：主控方原本有兩套修復時點判準：清理線（拖慢標記、版本收尾摘要觸發）與版本分診，觸發條件不同，PM 無從判斷該照哪一套。清理線原是 consumer 修框架時的節流機制，3.0.0 起 consumer 不修框架；主控方的框架就是產品，「專案工作是主目標、框架修補是手段」的前提不成立，節流改由〈兩期〉的執行期發現排後續版本、〈收斂〉的維護工作比例與候選池兩輪放棄承擔。拖慢標記是主控方唯一來自使用端的事件型訊號，清理線移除後改由規劃期讀取。來源：用戶裁定（2026-11-09）。

**Consequence**：判準並存時，同一問題可依一套不修、依另一套排入 patch，結果取決於 PM 讀到哪一節。拖慢標記沒有讀取端，consumer 標了也沒人用，主控方就分不出哪些 issue 真的在傷害使用者。早期訊號：某次規劃的必審項超過 10 個（門檻過寬或標記標得太鬆）；一個 minor 期間沒有任何新的拖慢標記（consumer 停止標記）。

**Action**：

- 發現時先對照上表；非本版處理的，依分診排入版本。
- ANA 結論要求的後續工作若走路徑 A，以觀測加關票落地，子票即為終態，ANA 依常規 complete，不以 `--force` 略過子票檢查。
- 每個版本進入規劃期時，整理輸入清單，必審項逐一寫明選入或不選的理由。
- 碰到框架阻礙時標「拖慢專案」。

## 修法時點分離：發現票何時能寫定修法

> 候選方案 A（純條文層）落地，觀測已送 [`tarrragon/claude#81`](https://github.com/tarrragon/claude/issues/81#issuecomment-5629166188)。

**原則一：時點分離的單位是欄位，不是票。**

**Why**：發現問題當下建票是對的（品質基線規則 5「發現即建立，不詢問確認」）；但「建票」與「這張票的欄位裡寫定一個未經檢查的修法」是兩件事，現行流程把兩者疊在同一動作完成——`title` 與 `how.strategy` 一旦寫下具體修法，此後每個讀者都會把它當成已定案的前提讀，不再視為待驗證的判斷。機械量測顯示這是預設路徑而非個案：某 consumer 專案「發現直接產出實作票」（來源票非分析票的實作票）樣本中，僅一成六帶待驗證語彙，其餘八成四在建票當下即寫定修法且無任何欄位記載其驗證狀態。

**Consequence**：不分離時點，發現當下的猜測會在無人檢查的情況下滲透進實作範圍。已發生案例：某次「收斂為單一共用元件」的修法定於發現當下，未觀測其他 consumer 的呼叫端，事後實測漏接率超過九成九。

**Action**：不要求「發現時多開一張分析票」——健康形態的成本只是一個句子：發現票的 `how.strategy` 寫下修法時，同時寫下該修法的證據狀態（已驗證／未驗證＋停手條件）。是否需要另開分析票，取決於下方擴散面判準，不是規模大小。

**原則二：豁免軸是證據狀態，不是問題規模。**

「修法看似顯然」不構成豁免依據——下方會示範「顯然」本身往往就是未觀測消費端的產物。可在發現當下寫定修法的條件是以下三問（「消費端已觀測」由下方兩列合成）皆為「是」：

| 問題 | 檢查內容 |
|------|---------|
| 執行條件已觀測 | 修法要改的東西，在什麼情況下被執行、執行時讀到什麼，是已實測而非推定？ |
| 使用者群已觀測 | 這個東西還有誰在用（其他呼叫端、其他 consumer），是已清點而非推定？擴散面判定為第一檔（見下方擴散面判準）時填「不適用」，並在票面寫出判定依據 |
| 反例已試 | 是否做過一個**若修法或其前提為錯就會產生不同輸出**的觀測？輸出為沉默、無訊號、或與「本來就沒問題」同形者不算 |
| 範圍已量 | 涵蓋的呼叫點／檔案／consumer 數是量到的數字，而非估計？本問只管數字來源；量測手段自身的鑑別力由「反例已試」一問管 |

**合成規則**：「執行條件已觀測」與「使用者群已觀測」皆為「是」或「不適用」時，兩者合成的「消費端已觀測」視為「是」；任一為「否」即為「否」。「不適用」只在擴散面判定為第一檔時可用——一個兩種讀法都成立的判準比沒有判準更糟（會讓任一結論都能引本節背書），故此處不留自由心證：判定依據需與下方擴散面判準同址可查。

**Why**：三問共同排除的是「修法在票面上與已驗證的決定不可分辨」——任一問題留在推定層級，票面的修法敘述外觀不會顯示這個落差，讀者無從得知。「執行條件」與「使用者群」分列，是因為「消費端」一詞原本在本節不同案例中被讀成「執行條件」與「使用者群」兩種互不相容的粒度，同一輸入可因讀法不同得出相反判定——拆列後每列各自二值，判準才可證偽。

**Consequence**：以規模（「只是一行」「很小的改動」）作豁免依據，會讓判準退化為主觀感受。下方第三個案例即是一例：加一個欄位看似顯然，但若該清單從未被任何自檢消費、或消費端對未列項本就忽略、或該清單刻意排除某類欄位，三種情形在發現當下的證據下不可區分——「顯然」是一個關於消費端的斷言，不是關於問題規模的斷言。

**Action**：三問任一為否時，先依下表判定擴散面歸檔，再依歸檔結果分兩檔處置，不是一律升級為分析票：

**擴散面判準**（機械事實 `should_exclude()` + 本 consumer 內是否有機械訊號兩軸組合；取代原「限本 consumer 且可逆」的未操作化描述。全樹實測：`rules/`／`references/`／`agents/`／`methodologies/`／`pm-rules/`／`error-patterns/` 六個一級目錄的排除比例皆為 0.000——規則與 skill 定義本體恆落「隨 sync 擴散」一側，故單靠 `should_exclude()` 對這些目錄的發現會使第一檔恆空，須與機械訊號軸並用）：

| 判準 | 歸檔 |
|------|------|
| `lib.sync_exclude_manifest.should_exclude()` 為 True（不隨 sync 擴散，本地專屬） | 第一檔 |
| 為 False（隨 sync 擴散）且本 consumer 內有機械訊號（測試紅燈／hook 阻擋／CI）會在修法錯誤時顯示 | 第一檔 |
| 為 False 且本 consumer 內無機械訊號 | 第二檔 |

| 擴散面 | 處置 | 成本 |
|--------|------|------|
| 第一檔 | 同一張票內把修法寫成待驗證形態：標明未驗證項與停手條件，不另開票 | 一個句子 |
| 第二檔 | 修法形狀不寫進發現票的 `how.strategy`；改為在對應 framework issue 的「待辦與來源（<consumer>）」區段新增一列，`階段=待條件`、`狀態=待裁票`，「做什麼」欄指名等待的對象（待裁的設計決策本身），修法的候選與各自代價寫進本 consumer 自己的「問題與方案（<consumer>：<主題>）」區段並由該列指回。本 consumer 在該 issue 尚無射程重疊的既有區段時用 `add`（成為該區段 owner），與既有「當前結論」射程重疊時改 `observe` 並指名重疊區段（判準見 `references/comment-as-section-protocol.md`〈init 前查重：三種關係處置〉「重複」格）；他方區段與 body 一律不動。**票型依原本的執行內容決定，不因本節而改型**——不再「發現票降為分析票（ANA）」，因為 ANA 票在現行 CLI 下 `where.files` 預設唯讀、無合法提交範圍，提交路徑比實作票更差；本節現在只要求 `how.strategy` 改寫為待裁形態 | 一則「待辦與來源」列 + 一則「問題與方案」區段（不另開 ANA） |

第二檔的待裁列由 `todo --status 待裁票`（預設只掃本 consumer 擁有的 open issue，跨 issue 需 `--all` 或 `--issue <N>`）觸發裁票，不依賴 `check` 的觀測時間差。

**三個檢驗案例**（判準須能分辨豁免與不豁免，不是只給禁令）：

| 案例 | 四問檢查 | 結論 |
|------|---------|------|
| 測試檔對已棄用 API 的直接替換（棄用旗標型別改用集合型別，範圍為兩個測試檔共六處，取自靜態分析工具的棄用告警） | 執行條件已觀測＝是（那兩個測試檔自身）；使用者群已觀測＝不適用（擴散面第一檔：測試檔為本地專屬）；反例已試＝是（棄用告警是機械訊號，換 API 後若殘留舊型別告警會重新出現，非沉默）；範圍已量＝是（六處，取自靜態分析工具告警） | **豁免**，發現當下即可寫定修法 |
| 共用工具（如共用元件）收斂為單一實例的重構提案 | 執行條件已觀測＝是（本 consumer 內如何呼叫已知）；使用者群已觀測＝否（其他 consumer 是否呼叫該工具，未觀測）；反例未試；範圍雖已量但使用者群否即消費端整體為否 | **不豁免**，修法形狀移至 issue 決定 |
| 自我檢查範本的合法章節清單缺一項欄位 | 執行條件已觀測＝否（該清單是否真被任何自檢消費，未觀測）；使用者群已觀測＝否（未列項如何處置，未觀測）；反例未試；範圍已量＝是（單一處） | **不豁免**，擴散面為第二檔（`should_exclude()`＝False 且規則層無機械訊號），修法形狀移至 issue 決定 |

**與品質基線規則 5 的銜接**

規則 5（`.claude/rules/core/quality-baseline.md`）管的是「是否建票、何時建票」——發現即建立、不詢問確認；本節管的是「同一張票的欄位承載什麼」。兩者作用對象不同：本節不改變建票時點（仍是發現當下），也不新增任何「先問 PM 再建票」的環節，與規則 5 不衝突。

唯一的接縫在規則 5 的優先級對應表：「高→當前版本（IMP Ticket）」容易被讀成「高優先級＝直接寫定修法的實作票」。正確讀法：**「高＝本版處理」，票型由上方三問的證據狀態決定，不由優先級決定**——高優先級而證據未備者，本版的處置是 `how.strategy` 改寫為上表第二檔的待裁形態，不是延後、也不強制改票型（見上表第二檔說明）；待裁列本身即是追蹤動作，不觸及規則 5「禁止以後續再說省略追蹤」的禁令，也不觸及 `.claude/rules/core/decision-trigger-binding.md`（本節不產生無 trigger 的延後：待裁列的觸發器是 `todo --status 待裁票`，指向具體的裁票動作）。

**現況**：本節為候選方案 A（純條文層），不改任何 CLI 或 hook。候選方案 B（`ticket create` 於實作票型且帶來源欄位時提示三問）**現不採用**，理由是本節為純條文層、不改 CLI 或 hook；日後若要採用，須先建 ticket 承載其評估與落地，不以 issue 討論作為啟動條件。票型閘門（候選方案 C：來源票非分析票的實作票一律先建分析票）已否決——會使健康形態的成本從一個句子放大為一張票，且對已量測樣本會使票池規模近乎倍增，與 `#81` 記錄的票池單調增長問題相斥。

## Issue 關閉協定

修復完成到正式 close 之間，必須依序完成版本號回註，讓其他 consumer 能追溯此修復落在框架的哪個版本：

```
修復完成 → sync-push（取得框架版本號）→ fix-version 回註 issue → close
```

| 步驟 | 命令 | 說明 |
|------|------|------|
| 1. 推送修復 | `/sync-push` | 推送後本地 `.claude/VERSION` 即為此次推送後的框架版本號 |
| 2. 版本號回註 | `python3 .claude/skills/framework-issue/scripts/fix_version.py <issue-ref> --summary "徵狀摘要"` | `--version` 省略時自動讀本地 `.claude/VERSION`，寫入 body 的 fix-versions 表格 |
| 3. 關閉 issue | `python3 .claude/skills/framework-issue/scripts/close_issue.py <issue-ref> [--reason completed]` | 前置檢查 fix-versions 非空，缺少即 exit 3 拒關 |

close 後在其他情境發現同一 issue 的新徵狀，不重開新 issue：對同一 issue 再跑一次「修復 → sync-push → fix-version」，版本號表格可累積多筆。

**Why**：版本號前置檢查是防止「各專案各自關閉造成同步狀態不一致」的機械閘門。**Consequence**：跳過 `fix-version` 直接 `close` 被 exit 3 拒絕；繞過閘門在網頁關閉，其他 consumer 執行查重 SOP 時誤判此 issue 已有版本可追溯。**Action**：路徑 B 或舊 issue 新徵狀，一律走三步不省略。「當下接手」與「先記錄」兩條路徑的分流見上節，本協定只管修復完成之後。

## 回報前查重 SOP

建立新 framework issue 前，先查既有 issue：

```bash
python3 .claude/skills/framework-issue/scripts/section_comment.py dedup --keywords "詞一" "詞二"
```

| 查詢結果 | 判讀 | 動作 |
|---------|------|------|
| 命中 issue，closed 且已有 fix-versions 版本號 | 該問題可能已在框架修復，只是本專案尚未同步 | `/sync-pull` 拉取該版本後驗證徵狀是否消失；仍存在則視為新徵狀，對同一 issue 追加 `fix-version` |
| 命中 issue，open 或查無版本號 | 已被記錄但尚未修復，或修復未完整回註 | 帶著既有 issue 的脈絡接續排查，以 `observe` 附加新徵狀；判定為全新獨立問題才建新 issue |
| 查無命中 | 尚未有人記錄 | 依介入判斷與兩條路徑建立新 issue |

命中清單的關係判定（重複／切分／引用）見 `references/comment-as-section-protocol.md` 的〈init 前查重：三種關係處置〉。

**Why**：`dedup` 成本遠低於重複建立後才發現。**Consequence**：略過查重使同一徵狀在框架 repo 產生多筆記錄，稀釋 canonical 追蹤的價值。一個已發生的形態：來源專案已在 canonical 修好的問題，移交線索只寫在該專案 closed 票的備註，下游 session 踩到同一誤判時查 runqueue 看不到，依流程正確地建了新票並準備升級到 canonical，目的地正是已修好的地方；每一步都正確，但「已修好」對下游不可達。`dedup` 涵蓋 comment 內文，是唯一能碰到這類事實的入口。
