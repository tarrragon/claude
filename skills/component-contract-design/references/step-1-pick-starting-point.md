# Step 1：判定起點

> **你在 step 1。** 上一步：`SKILL.md`〈起手〉——複製範本、確認 design token 層與形態因素矩陣兩項前置。下一步：`step-2-extract-components.md`，帶著本步的判定結果去選路徑。全程表在 `SKILL.md`〈全程〉。
>
> **本步的產出要留下**：起點判定屬〈契約齊全的定義〉第 6 條列管的「關機判定」——判定為某個起點即關掉另外兩條路徑的全部步驟，所以要在本規格票的 Problem Analysis 記下**命中的訊號**與**另兩個起點各自的排除理由**。沒有這則紀錄，認真判過與隨手判過在票面上無差別。
>
> **簡稱查地址**：本檔出現的方法論、範本、本規格票、統一匯出入口，地址一律查 `addresses.md`。

## 這一步在解什麼

手上有什麼材料，決定 step 2 走哪一條路徑。三條路徑的步驟不同，判準相同，而且互斥——判定完就只走一條。

## 為什麼值得慢慢判

這是全程第一個分岔，而且**判錯了不會有人告訴你**。

| 判錯方向 | 會產生什麼 | 什麼時候才發現 |
|---------|-----------|--------------|
| 該走 C（有存量程式碼）而走了 A | 契約與存量對不上；既有的重疊與截斷事故對應不到任何缺件；遷移票整批缺失 | 實作期。規格本身讀起來完好，格式齊全、判準全過，缺的是它描述的東西跟程式碼裡的東西不是同一批 |
| 該走 B（畫布是主要來源）而走了 A | 元件候選只來自狀態表的顯示欄，畫布上有而狀態表沒寫的視覺單元整批漏抽 | 填契約時發現候選表湊不出畫面，或更晚 |
| 該走 A 而走了 C | 對著 scaffold 產生的佔位元件盤點，得到一份反映鷹架而非需求的元件清單 | step 2 路徑 C 的呼叫端回收與原生佈局掃描全空時 |

三種都不會在中間步驟翻紅。排除理由紀錄之所以要留在這一步，原因就在這裡：事後要回溯「當初為什麼這樣判」，只剩這則紀錄可查。

## 判定

`SKILL.md`〈判定起點〉的速查表給三個起點各自的訊號。訊號清楚時照那張表走即可，本節處理它處理不了的三種情況。

### 全域狀態清單算不算逐畫面狀態表

規格只有一張全域狀態清單（非逐畫面分節）時，**清單每一列都有一欄的值逐字等於畫面清單中的一個畫面名**，才算逐畫面狀態表；欄名不限，一列屬多個畫面者，該欄值須逐一列出畫面名。任一列在每一欄都找不到逐字等於畫面名的值，整張清單不算逐畫面狀態表，A 的訊號不命中。不得從狀態列名稱的字首或顯示欄內容推測所屬畫面。

A 的訊號因此不命中、且 B、C 的訊號也不命中時，起點判定標「待決」，建規格補欄票（為清單補所屬畫面欄）並設為本規格票的 blockedBy，回覆前不進 step 2。

### 情況一：多個訊號同時命中

以「**哪個來源最接近使用者實際看到的畫面**」為準，**不看新舊**：

- 有可跑、且有頁面呼叫元件的程式碼 → 一律走 C。畫布較新也一樣——畫布上的差異在 step 2 路徑 C 的填契約步驟當作漂移處理，不是改判起點的理由
- 無程式碼、有畫布 → 走 B
- 只有規格 → 走 A

原則是**先萃取事實，再對照規格找漂移**。反過來（先照規格寫契約，再看程式碼對不對）會把存量的既有行為當成偏差刪掉。

### 情況二：A 與 C 之間猶豫

逐一核對 C 的三訊號，**任一命中即為 C**：

- [ ] 元件目錄非空，且其中的元件有呼叫端
- [ ] 頁面直接用原生佈局排列元件
- [ ] 曾發生重疊、截斷、功能補做

三項全否才是 A。

**三訊號無法核對時**：執行者無程式碼讀取權，或派發範圍排除程式碼，三訊號一項都查不了時，「無法核對」不等於「全否」，不得判 A。起點判定標「待決」，於本規格票 Problem Analysis 記下無法核對的訊號與原因；規格或其他輸入提及既有實作檔案者，列為請求核對的理由；提及本身不在上列三訊號之內，不據以判 C。於 NeedsContext 請求有讀取權者核對三訊號，回覆前不進 step 2。產出不落入 spec 檔的演練（如讀者走查）可暫判 A 繼續，判定紀錄標「暫判，C 訊號未核對」，其產出不得直接轉為本規格票內容。

範例：

【輸入】
```
執行者可讀規格與 skill，不可讀程式碼目錄（派發範圍排除）
規格有逐畫面狀態表
規格某節提到「既有路由設定檔」與兩個既有畫面檔名
本次產出為本規格票的起點判定
```
【產出】契約表（起點判定紀錄）
```
欄位         | 值
判定         | 待決
命中訊號     | 規格有逐畫面狀態表（A 的訊號）
C 三訊號     | 三項皆無法核對：派發範圍排除程式碼目錄
請求理由     | 規格提及既有路由設定檔與兩個畫面檔，C 訊號可能命中
處置         | NeedsContext 請求核對三訊號；回覆前不進 step 2
```
【驗證】檢驗問句
```
Q 判定欄是否為 A？                           預期：否（依據：「『無法核對』不等於『全否』，不得判 A」）
Q 是否已進 step 2 抽元件？                   預期：否（依據：「回覆前不進 step 2」）
Q 規格提及既有實作檔是否足以判 C？           預期：否，只列為請求理由（依據：「列為請求核對的理由」）
Q 若本次產出是不落 spec 的走查，可否暫判 A？  預期：可，須標「暫判，C 訊號未核對」（依據演練句）
```

### 情況三：A 與 B 之間猶豫

C 的三訊號在這裡判不了（兩者都沒有程式碼）。改用**來源就近原則**：有畫布、且畫布是主要來源 → B；只有規格 → A。

**「主要來源」的可數界線**：狀態表未覆蓋、而畫布有畫出的畫面數 ≥ 1，即判定畫布為主要來源、走 B。狀態表已覆蓋全部畫面、畫布只是同一批畫面的視覺稿時，畫布不構成「主要」，走 A（畫布留待 step 2 路徑 A 對照視覺值）。

一律不以「哪個來源比較新」替代上述任一種判法。

## 三個不照表判的例外

上表的訊號在下列三種情形下會給出錯的答案，各有指定的處置：

| 情形 | 訊號會怎麼騙你 | 實際走哪條 |
|------|--------------|-----------|
| 專案只有路由殼與佔位元件，頁面尚未呼叫任何元件 | 「元件目錄非空」命中，看起來像 C | 走 A 或 B。路徑 C 的呼叫端回收與原生佈局掃描會全空，跑了也沒有產出 |
| 已決議整體換版，且該決策有記錄 | 存量程式碼命中 C 的三訊號 | 走 B。舊碼只供路徑 C 的事故對照與呼叫端回收當**反例**來源，契約值以畫布為準 |
| 程式碼標記為 spike 且不合入生產 | 元件目錄非空且有呼叫端，命中 C | **都不走**——依方法論的原型豁免，整個 skill 對它不適用，本規格票不存在。該原型轉正時再走 C。此時的關機判定紀錄落在做出豁免判定的那張票，不落在本規格票（本規格票還不存在） |

第三列是三者中唯一會讓本步驟終止的：前兩列改的是走哪條路徑，第三列的結論是現在不做這件事。

**局部換版（僅部分 feature 換版）不落在第二列**：換版決策的範圍是判準，不是「有沒有換版決策」這件事本身。決議範圍內的 feature 走 B；決議範圍外的 feature 不受該決策覆蓋，其存量程式碼仍走本表的 C 判定，不因專案內其他 feature 已換版而一併改判。
