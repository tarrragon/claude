## 契約齊全而畫面不符的層疊成因

在有原生元件邊界的框架上，元件的樣式由元件自己決定；CSS 沒有這道邊界，一個元素最後的樣式是瀏覽器從整頁所有規則經過層疊（cascade）選出來的結果。所以 Web 端會出現一種其他平台少見的情形：**契約齊全、實作的人也照契約寫，畫面仍然不符契約**，而且瀏覽器不報錯。常見的成因如下表：

| 成因 | 畫面上的樣子 | 為什麼契約看不出來 |
|------|-------------|------------------|
| 元件庫的範圍重設寫成帶 id 的選擇器（`#app code { font-size: .86em }`） | 契約寫的字級、外距沒有生效，換成重設的值 | 重設的特定性（specificity）高過所有用 class 寫的元件規則；每一條元件規則單獨看都對 |
| 宿主頁面（host page，元件庫被嵌進去的頁面）的樣式（主題的元素規則、帶 `!important` 的自訂樣式） | 只在正式頁面多出外距、連結變色；在只載入元件 CSS 的展示頁上量不到 | 契約與展示頁都不含宿主的 CSS |
| 只替部分規則提高優先度（加 id 或多一層 class 提高特定性，或加 `!important`） | 元件自己的另一條規則被蓋過，例如連結形式按鈕的白字規則高過主要按鈕 hover 時的黑字規則，`<a>` 形式的主要按鈕 hover 時變成白底白字 | 加權的那一條是為了贏宿主，被波及的是元件內部原本靠特定性排好的勝負 |
| subgrid 項目同時帶著 `container-type`、`contain: layout`／`paint`／`content`／`strict`、`content-visibility: auto`，或是絕對定位；這組取值會讓元素建立獨立的格式化脈絡，`contain: size`／`inline-size`／`style` 不會 | 跨多列的子件接不上外層格線，瀏覽器把外層被它跨過的那幾列平分它的高度，內容被壓扁（Chromium 147 實測） | 兩種寫法各自都合乎契約，互斥是放在同一個元素上才出現 |

要分出是表裡哪一種成因，量測的人要讀計算後的樣式（computed style）才看得出實際套用的值與勝出的規則；只看截圖的人只看得出「好像不對」。

## step 2 路徑 C：接手既有 CSS，特徵測試是計算後樣式的快照

路徑 C 的特徵測試閘門（`step-2-path-c-code-extraction.md`；特徵測試是只把現況行為鎖住、不驗「應該是什麼」的測試）在 Web 端的形式是：改 CSS 之前，執行者用瀏覽器自動化工具開每一種畫面狀態，從元件庫的根元素往下走訪每個元素，記錄一組屬性的計算後值，寫成檔案。之後每一批改動重量一次、逐元素比對。元素依 DOM 位置配對（位置路徑加標籤名），class 記成一個欄位而不放進配對的鍵：合併 class、改選擇器的批次會改到 class，用 class 配對時那些元素會變成「舊版有、新版沒有」，量不到屬性差異。屬性清單依這一批會動到哪些屬性挑（字級、行高、顏色、內外距、寬高、`transform`……）；偽元素（`::before`、`::after`）要另外用 `getComputedStyle(元素, '::before')` 量；`children` 只列出一般的子元素，不含 shadow root 裡的元素。

快照比對只驗得出「兩個版本相同」：兩版共有的錯誤（整頁水平溢出這類）不會出現在比對結果裡，另外用截圖尺寸或 `scrollWidth` 量。比對結果裡的差異怎麼分成預期內與預期外、什麼時候退回，在 `frontend-with-playwright` skill 的 `references/refactor-without-visual-change.md`；專案沒有安裝那支 skill 時，最低限度是把每一處差異依「屬性、舊值、新值、元素的 class」分組列出，逐組判斷是不是這一批刻意要改的。

## step 3 要多寫的內容

**組合規則**：元件會嵌進宿主頁面時（元件庫限定在一個容器裡，容器外是別人的 CSS），填組合規則的人另外寫出：

- 宿主頁面載入哪幾份 CSS、順序為何，以及元件庫的 CSS 排在哪一份之後。
- 元件規則對宿主規則靠什麼勝出：cascade layer 的順序、比宿主高的特定性、同特定性而排在後面，或用 Shadow DOM 隔開。cascade layer 只在管得到宿主 CSS 的載入方式時可用（把宿主放進較低的 layer）；宿主沒分層、載入方式也管不到時，把元件的 CSS 放進 `@layer` 反而會輸給宿主每一條沒分層的規則。
- 宿主帶 `!important` 的規則、或用 class 選擇器而元件找不到夠用的特定性時的處置（從宿主那一邊排除元件的範圍、改用分層，或用 Shadow DOM、iframe 隔開）。
- 範圍重設（元件庫容器內的元素重設規則）的特定性：低於元件的 class 規則；跟宿主的元素規則同特定性時靠載入順序勝出，或高於宿主樣式。

這幾項的判斷標準是方法論〈Web/HTML 端 L2 特別判斷標準〉「範圍重設與宿主樣式的層疊位置」那一列。

**尺寸契約**：Web 端的每種測試尺寸是兩種寬度的組合：視窗的斷點，以及元件自己的容器查詢區段（元件依自身寬度切換版面時）。每個斷點與每個容器查詢區段至少各有一個測試寬度，取區段內部的值，不取邊界值。尺寸契約的值填 token 名，單位跟 token 一致（`px` 或 `rem`）；用 `rem` 時另記根字級改變時內容會不會溢位。

**測試契約**：除了 step 3 表裡的問句，Web 端填測試契約的人另答三問：

1. 測試在哪一組 CSS 下執行？答案要是正式頁面的那一組：展示頁依正式頁面的順序載入宿主的 CSS，或測試直接開正式頁面。在只載入元件自己 CSS 的展示頁上，量不到宿主造成的衝突。
2. 量哪些狀態？hover、`:focus-visible`、按下、`prefers-reduced-motion`、`pointer: coarse`，以及 `<details>` 展開這類由 DOM 決定的狀態；沒量的狀態寫出來，那幾個狀態的結論是「沒有量過」。`:visited` 的樣式 `getComputedStyle` 讀不到（瀏覽器為了隱私擋下），改成讀出套用到 `:visited` 的規則，依特定性與出現順序判斷哪一條勝出。
3. 量哪幾個瀏覽器？只量一個時寫出是哪一個與版本。

## 元件票的驗收：量正式頁面上的計算後值

step 4 的齊全檢查是存在性檢查，驗的是契約寫齊了，不驗畫面套用了契約。Web 端的元件票，acceptance 另加一條：在正式頁面的 CSS 組合下（〈step 3 要多寫的內容〉測試契約第 1 問），驗收的人量契約寫的值有沒有成為計算後的值，至少涵蓋字級、行高、內距、最小命中區與顏色，範圍是每一種變體乘上測試契約第 2 問列出的每一種狀態；量到的值跟契約不同時，先用 DevTools 的 Styles 面板分出是規則沒套上（選擇器沒選到，面板裡看不到這條規則）還是輸了（面板裡這條宣告被劃掉，上方另一條規則生效），再照〈契約齊全而畫面不符的層疊成因〉的表找。

## 限定改動的範圍，不等於限定影響的範圍

派發元件票或整理 CSS 的票時，「只改這個元件，其他 class 一律不動」限定的是能編輯的檔案與選擇器，限定不了層疊的結果：改了一條選擇器的特定性，跟它比過勝負的每一條規則（別的元件的、宿主的）結果都可能翻轉。所以派票的人在 Web 端這類票的 acceptance 寫兩條：

- 改動範圍：可以編輯的檔案與選擇器。
- 影響範圍：整頁（不只目標區塊）的計算後樣式快照，跟改動前比對；狀態照〈step 3 要多寫的內容〉測試契約第 2 問、寬度照尺寸契約，頁面上要有每一種變體（缺的另外插入，例如 `<a>` 形式的按鈕）；沒量的狀態與變體寫出來；預期以外的差異逐一列出與判定。

**判錯的代價**：只驗目標區塊時，被翻轉的那一條規則屬於另一個元件；要等有人打開那個元件的那個狀態（常常是 hover 這類不常量的狀態），才看得到它的畫面錯誤。
