## Examples

四則涵蓋三個模式的四個關鍵步驟（模式 A 兩則），用途是校準產出物的粒度——不是流程摘要。每則給輸入片段與該步驟的產出物形態。

**模式 A 步驟 3（存在必要性）——判定不合併長什麼樣**

輸入：spec 的 29 個畫面狀態中，空狀態出現 6 次、阻擋狀態 3 次，兩者外觀相近。
產出物（元件候選表的兩列）：

| 候選名 | 來源 | 判定 | 理由 |
|--------|------|------|------|
| 空狀態 | 狀態表 6 列的顯示欄 | 不與阻擋狀態合併 | 退出路徑不同：導向新增 |
| 阻擋狀態 | 狀態表 3 列的顯示欄 | 不與空狀態合併 | 退出路徑不同：導向切換專案 |

判準是退出路徑而非外觀。外觀相近若被當成合併理由，會得到一個靠參數分岔的元件。

**模式 A 步驟 4（容器盤點）——七個畫面得幾個候選**

輸入：七個畫面，含側欄／主區的殼層結構。
產出物（容器候選表四列）：

| 容器候選名 | 所在畫面 | 佈局結構 | 全部子件 | 排列方向 |
|-----------|---------|---------|---------|---------|
| 頁面框架 | 全部七畫面 | 殼層（側欄／主區） | 側欄、主區 | 並排 |
| 導覽項列 | 全部七畫面 | 側欄內 | 六個導覽項 | 堆疊 |
| 清單卡列表 | 專案列表畫面 | 主區內 | N 張清單卡 | 堆疊 |
| 徽章列 | 專案列表畫面 | 清單卡內 | N 個徽章 | 並排 |

**殼層框架容器易漏**：步驟 4 明文要求含框架層，而框架層不在任何狀態表的顯示欄裡，只能從畫面清單與畫布補入。少了它，齊全判準 2「每個畫面的每個排列關係都對應到一個容器」在殼層上不成立。

**模式 B 步驟 3（同型歸併）——語意不同而外觀相同時不歸併**

輸入：九份 artboard，同一款圓角卡片出現在專案摘要、錯誤提示、統計數字三處；token 表已萃取完成（前置已滿足）。
產出物（三個元件候選，不歸併）：語意問句得三個答案——內文、錯誤、數值——外觀相同不構成歸併理由，圓角降為三者共用的 token 名。
排列關係表記錄七組區塊間距，值一律引用已萃取的 token 名；量到而尚未有 token 名者停下走前置，不在本步驟自行歸納階數。

**模式 C 步驟 3 與 5（原生佈局掃描與事故對照）——事故對應到缺件而非缺陷**

輸入：十個通用元件、三種測試尺寸皆零溢位，仍發生按鈕重疊。
產出物（事故對照的一列）：

| 事故 | 掃描命中 | 判別問句（相對位置是誰決定的）答案 | 對應到 |
|------|---------|-------------|--------|
| 對話框按鈕重疊 | 頁面以水平堆疊直接排列三顆元件庫按鈕 | 頁面 | 缺「按鈕列」容器 |

每顆按鈕的契約都齊全，缺的是承載它們相對位置的容器——所以元件票只建一張容器票，加三個 feature 目錄各一張遷移票，不動任何按鈕。

## 正例

四類正例的第一類（清單卡的元件契約欄位）在 `field-questions.md`〈正例：清單卡的元件契約欄位〉，逐欄呼應該檔「常見空格與來源」欄。本節接續同一個去識別化情境——清單頁依資料狀態呈現三種畫面樣貌（正常有項目／空清單／清單來源阻擋無法讀取），元件候選為清單卡、狀態徽章、主要操作按鈕、狀態提示，容器為清單容器與頁面框架——寫其餘三類：容器條目、畫面票 how 與 acceptance、狀態提示的歸併判斷。

**容器條目：頁面框架**

對應第 4 章條目：4.5 頁面框架（框架容器）。

| 項目 | 值 |
|------|-----|
| 接受的子件類型 | 側欄（篩選面板，既有元件，非本情境範圍）、主區（清單容器） |
| 子件數量上限 | 2（固定：側欄 + 主區） |

| 排列不變式 | 值 |
|-----------|-----|
| 不重疊 | 側欄與主區左右並排，邊界盒不相交；測試以最小視窗尺寸驗證 |
| 最小間距 | 側欄與主區間距＝token `spacing-lg`（16px），呼叫端不得覆寫為更小值 |
| 空間不足策略 | 不觸發：上限 2，最小視窗（寬 1024px）下側欄最小寬 240px ＋ 主區最小寬 480px ＋ 1 × 最小間距 16px ＝ 736px ≤ 1024px |

「不觸發」公式在 `field-questions.md` 的排列不變式三問段只給了形態，本條目補上實際代入值——這正是清單容器（子件數無上限，必然觸發空間不足）與頁面框架（子件數固定、視窗保證放得下）的差異：兩者的空間不足策略欄合法值不同。

**畫面票：清單頁**

how（逐狀態列，狀態來源＝下方狀態矩陣）：

- 狀態 正常（有項目）：頁面框架第 1 格（側欄）放篩選面板（既有元件）；第 2 格（主區）放清單容器，清單容器逐格放清單卡變體 `default`，數量依資料筆數
- 狀態 空（無項目）：頁面框架第 2 格（主區）放空清單提示變體 `default`，取代清單容器
- 狀態 阻擋（清單來源目前無法讀取）：頁面框架第 2 格（主區）放阻擋提示變體 `default`，取代清單容器；提示文案的 i18n key `list.blocked.message` 尚無譯文，標「待決」並建 i18n 前置票，設為本畫面票 blockedBy

acceptance：

- 頁面檔的元件 import 只來自元件庫的統一匯出入口
- 狀態矩陣每列（正常／空／阻擋）都以契約內的元件組成：清單卡、狀態徽章、主要操作按鈕、清單容器、空清單提示、阻擋提示、頁面框架
- （不追加「不溢位」「畫面正確顯示」：不溢位由清單卡與清單容器各自的測試契約承載，畫面票不重驗）

阻擋狀態的 i18n key 待決是刻意保留的不完美：正例同時示範「不完美但合格」的樣子——待決欄有出口（建前置票、設 blockedBy）不是流程卡死，狀態矩陣其餘兩列與 acceptance 三條照樣完整可驗收。

**歸併與不歸併的判斷對照：狀態提示**

「狀態提示」是模式 A 步驟 2 抽出的初始候選——空清單與阻擋兩種畫面樣貌外觀相近（都是一段訊息 + 一顆按鈕），先假設能併入同一元件的兩個變體。步驟 3 存在必要性檢視逐一判斷：

| 判斷 | 空清單提示 vs 阻擋提示（不歸併） | 清單卡「查看」按鈕 vs 阻擋提示「重試」按鈕（歸併） |
|------|--------------------------------|------------------------------------------|
| 候選 | 空清單提示（清單無項目時顯示）、阻擋提示（清單來源無法讀取時顯示） | 清單卡內的查看按鈕、阻擋提示內的重試按鈕 |
| 通用元件能否涵蓋（先假設能併） | 外觀相近：一段訊息 + 一顆按鈕 | 兩者皆為觸發本畫面單一動作的按鈕 |
| 語意問句：使用者預期能做什麼 | 空清單提示：新增第一筆項目；阻擋提示：重試讀取或前往設定排除阻擋原因 | 兩者答案相同：觸發當前狀態下唯一的主要動作 |
| 判準檢查 | 退出路徑不同：空清單提示留在畫面內開啟新增流程，阻擋提示可能離開畫面前往設定頁——語意或行為差異，構成拆分理由 | 語氣不同（查看為中性、重試為修復語氣）但內容角色與退出路徑相同（皆留在畫面內觸發動作後刷新）——語氣差異一律走變體，不構成拆分理由 |
| 結論 | 不歸併：各自立元件，反例欄互指對方（「不可用於阻擋狀態」／「不可用於空清單狀態」） | 歸併：併入主要操作按鈕，新增變體 `view`（查看）與 `retry`（重試） |

判準是外觀相近或按鈕語氣本身都不構成理由；退出路徑（不歸併一例）與內容角色（歸併一例）才是。只憑外觀判斷會把空清單提示與阻擋提示錯併成一個帶參數的元件；只憑按鈕語氣判斷會把查看與重試錯拆成兩個元件。

## Troubleshooting

| 症狀 | 原因 | 處置 |
|------|------|------|
| 元件契約欄位填到一半發現元件該拆 | 存在必要性檢視併過頭，一個元件承載兩種內容角色 | 拆為兩個元件，原元件的反例欄互相指向 |
| 容器候選數量爆炸 | 同型歸併依畫面歸併而非依「子件類型 + 方向 + 策略」，或「一組」讀成兩兩相鄰對 | 重跑歸併；排除資料視圖本身（格線、樹、表格、泳道各算一個）後仍逾十個，回頭檢查歸併鍵是否混入畫面名 |
| 最長測試文案填不出來 | i18n 資源尚未涵蓋該 key | 走 i18n 前置票並設為元件票 blockedBy；契約該欄標「待決」，該元件在補齊前不得被畫面票引用 |
| 畫面票寫不成「容器 Z 第 N 格」 | 缺容器或缺元件 | 停手建元件票，不在畫面票內設計 |
| 接手專案的同一元件在各頁設定不一致 | 契約缺內容政策或尺寸契約 | 模式 C 呼叫端回收；語意差異則拆元件 |
| 執法工具全綠仍出現重疊 | 工具只掃元件層，組合層無契約 | 模式 C 的原生佈局掃描與容器候選；不以執法工具取代容器契約 |
| 元件票實作中發現需要契約外的新元件 | 元件候選盤點漏抽，或畫面狀態新增 | 停手：補契約條目（走待決出口或直接填齊）並登記 spawn request 建元件票（登記與落地規則見 `ticket` skill，停在 pending 不算落地），不就地實作；「清單不宣稱窮盡」指清單可增補，不指可先做後補契約 |
