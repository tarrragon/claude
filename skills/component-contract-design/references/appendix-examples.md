## Examples：各步產出物的粒度

五則涵蓋 step 2 三條路徑的四個關鍵步驟（路徑 A 三則，其中存在必要性步驟兩則各校準不同的分歧來源：外觀相近的兩個新候選、外觀與既有候選幾乎相同時是否算變體）。用途是校準粒度，**不是流程摘要**。

### step 2 路徑 A 步驟 3（存在必要性）——判定不合併長什麼樣

輸入：spec 的 29 個畫面狀態中，空狀態出現 6 次、阻擋狀態 3 次，兩者外觀相近。

產出物（元件候選表的兩列）：

| 候選名 | 來源 | 判定 | 理由 |
|--------|------|------|------|
| 空狀態 | 狀態表 6 列的顯示欄 | 不與阻擋狀態合併 | 退出路徑層級不同：留在畫面內（開啟新增） |
| 阻擋狀態 | 狀態表 3 列的顯示欄 | 不與空狀態合併 | 退出路徑層級不同：離開專案（切換專案） |

判準是退出路徑層級而非外觀，也不是目的地本身——目的地不同、層級相同者是 slot，不拆。外觀相近若被當成合併理由，會得到一個靠參數分岔的元件。

驗證（檢驗問句）：

- Q 兩個候選的退出路徑層級是否相同？　預期：不同 → 不合併
- Q 理由欄是否以層級（留在畫面內／離開畫面／離開專案）而非目的地表述？　預期：是（只寫「導向新增」「導向切換專案」等目的地即判錯；層級相同而目的地不同者為 slot，不拆）
- Q 理由欄是否引用外觀相近？　預期：否（引用外觀即判錯）

### step 2 路徑 A 步驟 3（存在必要性）——結構相同時仍要查退出路徑層級，不是看起來像就併

輸入：元件庫已存在候選「阻擋提示」（訊息＋按鈕「重試」，判定見上例，退出路徑層級：離開畫面前往設定頁）。新掃描出的狀態「來源已離線」外觀與阻擋提示幾乎相同——同樣是一段訊息加一顆按鈕，按鈕觸發的是「重新連線」。

產出物（元件候選表追加一列，判定新候選是否為阻擋提示的變體）：

| 候選名 | 判定 | 理由 |
|--------|------|------|
| 來源已離線提示 | 不歸併為阻擋提示的變體，另立元件 | 退出路徑層級不同：阻擋提示離開畫面（前往設定頁），來源已離線提示留在畫面內（原地重新連線，不離開清單頁） |

驗證（檢驗問句）：

- Q 兩個候選的視覺結構（訊息＋單一按鈕）是否相同？　預期：是——但結構相同不是歸併理由
- Q 兩個候選的退出路徑層級是否相同？　預期：不同（離開畫面／留在畫面內）→ 不歸併，即使外觀完全一致
- Q 若只看按鈕文案指向的處置類型（「前往設定頁」與「重新連線」皆屬「排解問題」同一類目的），是否可能誤判為同一元件的兩個變體？　預期：可能——因此判準必須落在退出路徑層級，而非目的地看起來多相近

### step 2 路徑 A 步驟 4（容器盤點）——七個畫面得幾個候選

輸入：七個畫面，含側欄／主區的殼層結構；其中「專案列表畫面」的主區為多張清單卡的堆疊清單，每張清單卡內另有一排徽章。

產出物（容器候選表四列）：

| 容器候選名 | 所在畫面 | 佈局結構 | 全部子件 | 排列方向 |
|-----------|---------|---------|---------|---------|
| 頁面框架 | 全部七畫面 | 殼層（側欄／主區） | 側欄、主區 | 並排 |
| 導覽項列 | 全部七畫面 | 側欄內 | 六個導覽項 | 堆疊 |
| 清單卡列表 | 專案列表畫面 | 主區內 | N 張清單卡 | 堆疊 |
| 徽章列 | 專案列表畫面 | 清單卡內 | N 個徽章 | 並排 |

**殼層框架容器易漏**：該步驟明文要求含框架層，而框架層不在任何狀態表的顯示欄裡，只能從畫面清單與畫布補入。少了它，step 4 齊全判準第 2 條「每個畫面的每個排列關係都對應到容器」在殼層上不成立。

驗證（檢驗問句）：

- Q 容器候選表是否涵蓋殼層層級（頁面框架）？　預期：是（框架層不在任何狀態表的顯示欄裡，只能從畫面清單與畫布補入；漏收即無法通過 step 4 齊全判準第 2 條）
- Q 「清單卡列表」與「徽章列」兩個候選是否能從輸入的畫面描述重新推導出來？　預期：能——輸入已指明專案列表畫面主區為清單卡堆疊、卡內另有一排徽章
- Q 排列方向欄的「並排」與「堆疊」是否各自對應輸入描述的實際排列？　預期：是（側欄／主區並排；導覽項與清單卡皆為堆疊；徽章列為並排）

### step 2 路徑 B 步驟 3（同型歸併）——語意不同而外觀相同時不歸併

輸入：九份 artboard，同一款圓角卡片出現在專案摘要、錯誤提示、統計數字三處；token 表已萃取完成（前置已滿足）。

產出物（元件候選表，決策表形態）：

| 候選名 | 判定 | 理由 |
|--------|------|------|
| 專案摘要卡 | 不歸併 | 語意問句答案：內文——顯示專案摘要資訊 |
| 錯誤提示卡 | 不歸併 | 語意問句答案：錯誤——顯示錯誤訊息 |
| 統計數字卡 | 不歸併 | 語意問句答案：數值——顯示統計數字 |

三者外觀相同（同一款圓角卡片）不構成歸併理由；圓角本身降為三者共用的 token 名，不因此併成一個元件。

排列關係表（節錄兩組，非窮舉七組）：

| 容器 | 子件 A | 子件 B | 間距 | 值（token 名） |
|------|--------|--------|------|---------------|
| 摘要區塊 | 專案摘要卡 | 統計數字卡 | 水平間距 | `spacing-md` |
| 錯誤提示區 | 錯誤提示卡 | （單一子件） | — | — |

量到而尚未有 token 名者停下走前置，不在本步驟自行歸納階數。

驗證（檢驗問句）：

- Q 三個候選是否僅因外觀相同（同一款圓角卡片）而被歸併？　預期：否（外觀相同不構成歸併理由）
- Q 每個候選的語意問句答案是否互不相同？　預期：是（內文／錯誤／數值三個不同答案，正是不歸併的理由）
- Q 排列關係表的間距值是否為具名 token 而非數值？　預期：是（量到而尚未有 token 名者停下走前置，不在本步驟自行歸納階數）

### step 2 路徑 C 步驟 3 與 5（原生佈局掃描與事故對照）——事故對應到缺件而非缺陷

輸入：十個通用元件、三種測試尺寸皆零溢位，仍發生按鈕重疊；重疊發生於三個 feature 目錄各自的頁面。

產出物（事故對照的一列）：

| 事故 | 掃描命中 | 判別問句（相對位置是誰決定的）答案 | 對應到 |
|------|---------|--------------------------------|--------|
| 對話框按鈕重疊 | 頁面以水平堆疊直接排列三顆元件庫按鈕 | 頁面 | 缺「按鈕列」容器 |

每顆按鈕的契約都齊全，缺的是承載它們相對位置的容器——所以 step 5 只建一張容器票，加三個 feature 目錄各一張遷移票，**不動任何按鈕**。

驗證（檢驗問句）：

- Q 結論「三個 feature 目錄各一張遷移票」的目錄數是否能從輸入回推？　預期：能——輸入已指明重疊發生於三個 feature 目錄
- Q 是否因為十個通用元件皆零溢位就判定沒有問題？　預期：否——執法工具全綠仍可能重疊，因為它只掃元件層不掃組合層
- Q 是否修改了任一顆按鈕的契約？　預期：否——按鈕契約已齊全，缺的是承載相對位置的容器，修的是容器缺件而非元件本身

## 正例

四類正例共用一個去識別化情境：**一個清單頁，依資料狀態呈現三種畫面樣貌**（正常有項目／空清單／清單來源阻擋無法讀取）。元件候選為清單卡、狀態徽章、主要操作按鈕、狀態提示；容器為清單容器與頁面框架。

四類的閱讀順序即產出順序：先判斷要不要歸併（第四類），再填元件欄位（第一類），再填容器條目（第二類），最後寫畫面票（第三類）。

### 一、清單卡的元件契約欄位

輸入：延續本節前言的清單頁情境——清單容器逐格渲染清單卡，資料態「正常有項目」時清單卡數量依資料筆數；卡片本身有 default／focused 兩個互動瞬態與 archived 一個資料態，畫面級三態（正常／空／阻擋）不在本例填寫範圍內，由呼叫端狀態矩陣承載。

逐欄呼應 `step-3-fill-contract.md`〈元件契約欄位填寫問句〉表的「常見空格與來源」欄——反例給錯誤形態，本表給合格門檻。

| 欄位 | 正例填法 | 呼應的常見空格 |
|------|---------|--------------|
| 語意與內容角色 | 顯示清單中單一項目的摘要，可點擊查看詳情；複合角色（標題 + 標籤 + 動作）——標題由標題文字承載、標籤由狀態徽章承載、動作由主要操作按鈕承載，各自對應一個 slot。何時不用：項目需要多行摘要或縮圖預覽時不用，另立元件 | 「何時不用」常空白；本例把它與複合角色的 slot 對應一併寫出 |
| 變體 | `default` 單一變體；封存項目變暗是同一張卡隨自身資料態改變的外觀，不是兩個歸併候選之間的外觀差異，不立新變體，由狀態集的 archived 狀態承載 | 以外觀值命名是常見錯誤；本例示範由元件自身狀態驅動的外觀差異進狀態集（〈共用規則一〉「降為變體」的射程是歸併候選之間） |
| 狀態集 | default（來源：—，互動瞬態基準；同步策略：本地即時；顯示標題、徽章、按鈕；可操作：點卡片進詳情、點按鈕觸發動作；進入：清單容器渲染任一列；退出：點卡片離開畫面進詳情，點按鈕留在畫面觸發動作）／focused（來源：互動瞬態（鍵盤焦點）；同步策略：本地即時；顯示同 default 但邊框反白；可操作：Enter 觸發卡片、Tab 移出；進入：鍵盤焦點移入；退出：Tab 移出回 default，或 Enter 同卡片點擊路徑）／archived（來源：資料態（項目封存旗標）；同步策略：等確認才顯示；顯示同 default 但整卡降低不透明度；可操作：同 default；進入：資料態封存旗標轉為真；退出：封存旗標轉為假回 default） | 畫面級進出常誤填在此；本例只填元件自身，畫面級三狀態（正常／空／阻擋）留給呼叫端狀態矩陣。default 與 focused 為本地互動瞬態不需接 provider；archived 為資料態，需接 provider |
| 操作機制 | 桌機：滑鼠點擊卡片本體或按鈕，精度足夠，回饋通道視覺（按下態）／手機：觸控點擊，命中區依第 1 章 token | 常直接沿用畫布手勢；本例逐形態各答一次 |
| 尺寸契約 | 尺寸模式：填滿父容器（寬）、固有高度；最小尺寸：寬 240px（token `card-min-width`）乘高 64px；按鈕最小命中區不得小於該形態的命中區 token；桌機與手機視窗下皆維持（換版型是清單容器排列不變式的責任，非本元件重複規定） | 「每種測試尺寸」常只填預設；本例明寫兩形態且指出換版型責任歸屬 |
| 內容政策 | 標題 slot：可換行＝否，最大行數＝1，超出處置＝截斷，最長測試文案＝i18n key `list.card.title.sample`（取專案 i18n 資源實測最長值） | 最長測試文案常空白；本例指名來源為 i18n 資源實測值 |
| slot 契約 | title：String（i18n key）必填，呼叫端傳入；badge：狀態徽章元件必填，元件庫子件掛載；action：主要操作按鈕元件必填，元件庫子件掛載（變體 `view`） | 文字來源常寫死；本例示範直傳值與子元件掛載兩種來源 |
| 組合規則 | 可放入的容器：清單容器（唯一具名容器，不可直接放入頁面原生佈局）；不得放置區域：手機系統手勢區（按鈕命中區需避開）；對齊基準：文字基線；作為列表一欄：不適用（本元件即列表項本身） | 「可放入任何地方」等於允許原生佈局；本例列具名容器並排除不適用子節 |
| 無障礙 | 朗讀標籤：唸出標題與狀態（如「項目 Alpha，進行中」）；狀態變化播報：徽章改變時播報新狀態；非視覺替代訊號：徽章顏色搭配文字標籤，非唯一訊號；焦點路徑（桌機）：Tab 入卡片→Enter 進詳情，再 Tab 入按鈕→Enter 觸發；焦點路徑（手機）：觸控直接命中，無 Tab 序列；對比：WCAG AA | 常空白或只填對比；本例逐形態各給操作路徑一次 |
| 回饋契約 | 可互動提示：桌機通道 hover（視覺，邊框微亮）／門檻即時／token `hover-highlight`／狀態邊不適用（不改變狀態集）；觸控形態：不可用加替代——常駐陰影提示可點。焦點：通道焦點環（視覺）／門檻即時／token `focus-ring`／狀態邊 default→focused。按下確認：通道視覺（卡片輕微下沉）加觸控形態的觸覺／門檻 100ms 內／token `press-depth`／狀態邊不適用（瞬時效果非狀態）。定位提示：不可用加替代——新項目加入清單時淡入提示（視覺）。狀態變更提示：通道視覺（徽章淡入淡出過渡）／門檻 300ms／token `badge-transition`／狀態邊徽章值 X→Y；元件不在視野時不升級系統通知（非關鍵資訊）。等待與結果：本元件不承載等待層，只承載結果（徽章文字變化即結果通知） | 定位提示與可互動提示常空白；本例逐事件四段（通道／門檻／token／狀態邊）填滿，以「不可用加替代」示範不適用事件不留空 |
| 測試契約 | 一支測試渲染 default、focused、archived 三狀態全變體；兩形態最小視窗尺寸下皆不溢位；標題最長測試文案依截斷處置驗證；token 引用非硬編碼 | 常只測預設尺寸與短文案；本例逐形態測且用最長文案 |
| 反例 | 不該拿它承載需要多行摘要或縮圖預覽的清單項——改用清單卡（詳情版，另立）；不該拿它承載空清單或阻擋提示——改用狀態提示相關元件（歸併判斷見本節第四類） | 常空白；本例的反例來源即第四類正例的落選結論 |

驗證：

- Given 清單卡渲染於 default 狀態 When 使用者以鍵盤 Tab 移入 Then 進入 focused 狀態、邊框反白，可操作變為 Enter 觸發卡片、Tab 移出
- Given 清單卡處於 focused 狀態 When 使用者按下 Enter Then 觸發與點擊卡片本體相同的路徑（離開畫面進詳情）
- 檢驗問句：把清單卡背後的服務整個拔掉，使用者點擊卡片本體或按鈕是否仍看得到反應？　預期：是——桌機的按下態、觸控的按下態皆為本地即時效果，不依賴服務回應（回饋契約欄「按下確認」段已作答掛載點判準）
- 檢驗問句：標題 slot 的最長測試文案來源是否為 i18n 資源實測值而非隨意字串？　預期：是（來源 `list.card.title.sample`）

### 二、容器條目：頁面框架

輸入：token 表已萃取側欄最小寬 240px（token `sidebar-min-width`）、主區最小寬 480px（token `main-min-width`）、區塊最小間距 16px（token `spacing-lg`）；目標支援的最小視窗寬 1024px。對應範本第 4 章條目 4.5 頁面框架（框架容器）。

| 項目 | 值 |
|------|-----|
| 接受的子件類型 | 側欄（篩選面板，既有元件，非本情境範圍）、主區（清單容器） |
| 子件數量上限 | 2（固定：側欄加主區） |

| 排列不變式 | 值 |
|-----------|-----|
| 不重疊 | 側欄與主區左右並排，邊界盒不相交；測試以最小視窗尺寸驗證 |
| 最小間距 | 側欄與主區間距＝token `spacing-lg`（16px），呼叫端不得覆寫為更小值 |
| 空間不足策略 | 不觸發：上限 2，最小視窗（寬 1024px）下側欄最小寬 240px 加主區最小寬 480px 加 1 乘最小間距 16px 等於 736px，小於等於 1024px |

「不觸發」公式在 `step-3-fill-contract.md` 只給了形態，本條目補上實際代入值。**這正是清單容器與頁面框架的差異**：清單容器子件數無上限、必然觸發空間不足；頁面框架子件數固定且視窗保證放得下。兩者的空間不足策略欄合法值不同。

驗證：

- Given 視窗寬度為最小值 1024px When 頁面框架渲染側欄與主區 Then 側欄與主區邊界盒不相交，且側欄寬 240px 加主區寬 480px 加間距 16px 的總和 736px 小於等於視窗寬度
- 檢驗問句：代入值（240px／480px／16px／1024px）是否皆有 token 或需求來源，而非憑空取值？　預期：是（三個尺寸皆引用輸入段列出的 token 名，最小視窗寬為需求目標值）

### 三、畫面票：清單頁

輸入：清單頁的三種資料態（正常有項目／空清單／清單來源阻擋），與已填滿契約的七項元件——清單卡、狀態徽章、主要操作按鈕、清單容器、空清單提示、阻擋提示、頁面框架。

how（逐狀態列，狀態來源即下方狀態矩陣）：

- 狀態 正常（有項目）：頁面框架第 1 格（側欄）放篩選面板（既有元件）；第 2 格（主區）放清單容器，清單容器逐格放清單卡變體 `default`，數量依資料筆數
- 狀態 空（無項目）：頁面框架第 2 格（主區）放空清單提示變體 `default`，取代清單容器
- 狀態 阻擋（清單來源目前無法讀取）：頁面框架第 2 格（主區）放阻擋提示變體 `default`，取代清單容器；阻擋提示的訊息 slot 放 i18n key `list.blocked.message`，該 key 尚無譯文，標「待決」並建 i18n 前置票，設為本畫面票 blockedBy（阻擋提示的契約本身已齊全：訊息 slot 型別為 i18n key，最長測試文案取自既有譯文實測值，不依賴此 key）

acceptance：

- 頁面檔的元件 import 只來自元件庫的統一匯出入口
- 狀態矩陣每列（正常／空／阻擋）都以契約內的元件組成：清單卡、狀態徽章、主要操作按鈕、清單容器、空清單提示、阻擋提示、頁面框架
- （不追加「不溢位」「畫面正確顯示」：不溢位由清單卡與清單容器各自的測試契約承載，畫面票不重驗）

**阻擋狀態的 i18n key 待決是刻意保留的不完美。** 正例同時示範「不完美但寫法合格」的樣子：待決的是本畫面票放進 slot 的值，不是元件契約欄位，因此 `step-4-verify-completeness.md`〈契約齊全的定義：六條〉第 1 條不觸發，阻擋提示仍可被引用；待決有出口（建前置票、設 blockedBy），本畫面票可建立，三列 how 與 acceptance 照樣完整，但 blockedBy 清除前不派發。待決若落在元件契約欄位（例如阻擋提示的最長測試文案因 i18n 未涵蓋而標待決），依同條與本檔 Troubleshooting「最長測試文案填不出來」列，該元件不得被本畫面票引用，阻擋列寫不成，須先清該元件票的 blockedBy。

驗證（檢驗問句）：

- Q how 每一列的寫法，是否為「容器 Z 第 N 格放元件 A 變體 a」的形式？　預期：是（三列皆指名容器、格位、元件與變體，無自由散文描述畫面）
- Q acceptance 是否追加「不溢位」「畫面正確顯示」等重複驗證？　預期：否（不溢位已由清單卡與清單容器各自的測試契約承載，畫面票不重驗）
- Q 阻擋狀態列的 i18n key 待決，是否使本畫面票寫法不合格？　預期：否（依據：`step-5-write-tickets.md`〈slot 值缺資源〉「how 仍屬合格寫法」；條件詞「識別名已定、其資源系統尚無對應內容」見輸入段「該 key 尚無譯文」）
- Q i18n 前置票完成前，本畫面票可否派發？　預期：否（依據：〈slot 值缺資源〉「blockedBy 清除前不派發」）

### 四、歸併與不歸併的判斷對照：狀態提示

「狀態提示」是 step 2 路徑 A 步驟 2 抽出的初始候選——空清單與阻擋兩種畫面樣貌外觀相近（都是一段訊息加一顆按鈕），先假設能併入同一元件的兩個變體。存在必要性檢視逐一判斷：

| 判斷 | 空清單提示 vs 阻擋提示（不歸併） | 清單卡「查看」按鈕 vs 阻擋提示「重試」按鈕（歸併） |
|------|--------------------------------|------------------------------------------|
| 候選 | 空清單提示（清單無項目時顯示）、阻擋提示（清單來源無法讀取時顯示） | 清單卡內的查看按鈕、阻擋提示內的重試按鈕 |
| 通用元件能否涵蓋（先假設能併） | 外觀相近：一段訊息加一顆按鈕 | 兩者皆為觸發本畫面單一動作的按鈕 |
| 語意問句：使用者預期能做什麼 | 空清單提示：新增第一筆項目；阻擋提示：重試讀取或前往設定排除阻擋原因 | 兩者答案相同：觸發當前狀態下唯一的主要動作 |
| 判準檢查 | 退出路徑層級不同：空清單提示留在畫面內（原地開啟新增表單，不離開清單頁），阻擋提示離開畫面（前往設定頁排除阻擋原因）——層級不同，構成拆分理由 | 語氣不同（查看為中性、重試為修復語氣）但內容角色與退出路徑層級相同（皆留在畫面內觸發動作後刷新）——語氣差異一律走變體，不構成拆分理由 |
| 結論 | 不歸併：各自立元件，反例欄互指對方（「不可用於阻擋狀態」／「不可用於空清單狀態」） | 歸併：併入主要操作按鈕，新增變體 `view`（查看）與 `retry`（重試） |

**外觀相近或按鈕語氣本身都不構成理由**；退出路徑層級（不歸併一例）與內容角色（歸併一例）才是。只憑外觀判斷會把空清單提示與阻擋提示錯併成一個帶參數的元件；只憑按鈕語氣判斷會把查看與重試錯拆成兩個元件。

驗證（檢驗問句）：

- Q 空清單提示與阻擋提示的退出路徑層級是否相同？　預期：不同（留在畫面內／離開畫面）→ 不歸併
- Q 拆分理由是否以層級表述而非目的地？　預期：是（「原地開啟新增表單」「前往設定頁排除阻擋原因」皆先標明層級，目的地只是層級之下的例證，不是判準本身）
- Q 清單卡查看按鈕與阻擋提示重試按鈕是否因語氣不同而拆分？　預期：否（語氣差異一律走變體；內容角色與退出路徑層級相同者歸併）

## Troubleshooting：卡住時的症狀處置

| 症狀 | 原因 | 處置 |
|------|------|------|
| 元件契約欄位填到一半發現元件該拆 | 存在必要性檢視併過頭，一個元件承載兩種內容角色 | 拆為兩個元件，原元件的反例欄互相指向 |
| 容器候選數量爆炸 | 同型歸併依畫面歸併而非依「子件類型加方向加策略」，或「一組」讀成兩兩相鄰對 | 重跑歸併；**排除資料視圖本身（格線、樹、表格、泳道各算一個）後仍逾十個**，回頭檢查歸併鍵是否混入畫面名 |
| 最長測試文案填不出來 | i18n 資源尚未涵蓋該 key | 走 i18n 前置票並設為元件票 blockedBy；契約該欄標「待決」，該元件在補齊前不得被畫面票引用 |
| 畫面票寫不成「容器 Z 第 N 格」 | 缺容器或缺元件 | 停手建元件票，**不在畫面票內設計** |
| 接手專案的同一元件在各頁設定不一致 | 契約缺內容政策或尺寸契約 | 走 step 2 路徑 C 的呼叫端回收；語意差異則拆元件 |
| 執法工具全綠仍出現重疊 | 工具只掃元件層，組合層無契約 | 走 step 2 路徑 C 的原生佈局掃描與容器候選；**不以執法工具取代容器契約** |
| 元件票實作中發現需要契約外的新元件 | 元件候選盤點漏抽，或畫面狀態新增 | 停手：補契約條目（走待決出口或直接填齊）並登記 spawn request 建元件票（登記與落地規則見 `ticket` skill，停在 pending 不算落地），**不就地實作**。「清單不宣稱窮盡」指清單可增補，不指可先做後補契約 |
