> 何時讀：要寫任何票（畫面／元件／遷移／決策）時；或派發前要查誰執行誰簽核時。後者發生在契約齊全之前。

> 同目錄：〈元件契約欄位填寫問句〉與〈多形態專案〉在 `field-questions.md`，三種模式在 `modes-a-b.md` 與 `mode-c.md`；〈契約齊全的定義〉留在 `SKILL.md`，**〈外部資產與跨檔用詞的地址〉在 `addresses.md`**，〈分工邊界〉在 `adjacent-assets.md`——本檔出現的方法論、範本、執法工具、統一匯出入口、L2、狀態矩陣、存在必要性檢視、事故對照、特徵測試，地址一律查該表。

## 執行者與簽核者

| 動作 | 執行者 | 核定者 |
|------|--------|-------|
| 撰寫元件庫規格（三種模式） | 工具清單含 Write／Edit 的設計類代理人，或 PM；只有唯讀與符號級工具的代理人寫不了 spec 檔，不派 | PM 於 spec 票驗收對照〈契約齊全的定義〉與範本第 9 章 |
| 建元件票、畫面票、遷移票、決策票 | PM，或工具清單含 Bash 的執行者；欄位語意與指令見 `ticket` skill（blockedBy、parent、spawn request） | — |
| 改寫既有票（補 blockedBy、回填 acceptance、拆分） | PM；執行者於 NeedsContext 列出應改內容 | — |
| 存在必要性的合併結論、呼叫端回收的選值、特徵測試規模裁定 | 執行者提案並附證據 | PM |
| 版型拆分、豁免 | 執行者提案 | 版型拆分用戶簽核；豁免 PM 於票驗收核可 |

執行者工具清單不含 Bash 時無法呼叫 ticket 系統，建票步驟改為在票面 NeedsContext 列出應建的票由 PM 代建；派發階段就把建票步驟從該票的 acceptance 移出，不要求執行者做做不到的事。

## 派發語言

契約齊全後，畫面票與元件票的寫法固定。寫不成這個形式即為缺件訊號。畫面票的 acceptance 句型、反例與缺件處置定於方法論〈派發語言〉，本節只補程序層的句型。

**畫面票**：

| 欄位 | 句型 |
|------|------|
| how | 逐狀態列「狀態 X：容器 Z 第 N 格放元件 A 變體 a、第 N+1 格放元件 B 變體 b」，狀態來源指向狀態矩陣。寫不成這個形式時停手建元件票、設為畫面票的 blockedBy |
| acceptance（與方法論〈派發語言〉同文） | 「頁面檔的元件 import 只來自元件庫的統一匯出入口」（無 import 邊界的宿主改用方法論〈Web/HTML 端 L2 特別判準〉的不並存斷言）；「狀態矩陣每列都以契約內的元件組成」。不得追加「不溢位」「畫面正確顯示」：不溢位由元件票的測試契約承載，畫面票不重驗 |
| 派發 prompt 必含 | Solution 含 `### 自檢結果` 子章節（逐 acceptance 附證據，非泛稱「已自檢」）與 Phase 4 結論；測試一律前台執行不用 `run_in_background`，回報前 `git status --porcelain` 為空——三者的固定句與觸發條件見**agent 派發範本**（〈骨架（權威版）〉與〈Solution 自檢結果子章節義務〉兩節），本節不重複；地址見 `addresses.md` |

**元件票**。粒度規範的是 acceptance 的投影單位，不是排程單位：一票一元件或一容器；多張元件票可掛同一張 parent 傘票分 wave 派發；變體與狀態集皆「不適用」的原子元件（分隔線、留白）得合併為一票，acceptance 仍逐元件投影；既有的多元件票拆分，已 claim 且實作中的票拆不動時，acceptance 以「符合 spec 條目 {編號} 的元件契約欄位表」一條加測試契約一條代替逐欄投影：

| 欄位 | 句型 |
|------|------|
| what | 「建立元件 A：{內容角色}，變體 {清單}」或「建立容器 Z：子件 {具名清單}，方向 {並排／堆疊}，空間不足 {策略}」 |
| acceptance | 元件契約欄位表對該元件的投影各一條（含回饋契約——每事件每形態的通道或「不可用 + 替代」）；容器加排列不變式三項（不重疊／最小間距／空間不足策略）各一條；測試契約一條（全變體全狀態、每種尺寸、最長文案） |
| blockedBy | 填 ticket ID，不填資產名：產出 token 表、i18n 資源、互動反應規格、測試基座的票，待決欄位的決策票；容器票另列其子件元件票；資產已存在且無票者不列；容器票所列子件元件票尚未落地時，容器票本身仍可派發不受阻——slot 依方法論〈元件契約判準〉的〈slot 暫承接規則〉以宿主基底型別暫承接，待子件票落地後由收窄票統一收回，不視為 blockedBy 未清 |
| 派發 prompt 必含 | 同上「派發 prompt 必含」列（Solution 自檢結果子章節與 Phase 4 結論、測試前台執行、回報前 `git status --porcelain` 為空），元件票逐項對照的是元件契約欄位表投影與測試契約條目，非畫面票的 import 邊界斷言 |

**遷移票**（模式 C 存量頁面）：

| 欄位 | 句型 |
|------|------|
| what | 「將 {feature 目錄} 頁面層的原生佈局改為容器 {Z}，元件設定回收至契約」 |
| acceptance | 「該目錄頁面層零原生佈局原語直接包兩個以上元件庫元件」（執法工具不偵測佈局原語者，以模式 C 步驟 3 的 grep 驗收）；「元件 import 只來自統一匯出入口」；「baseline 已縮減該目錄」（baseline 形態依執法工具而定：有目錄級白名單者移除該目錄；無者 baseline 範圍記於決策文件，同 `foundation-design` skill 接手模式的規模閘門處置） |
| blockedBy | 容器 Z 的元件票、特徵測試補齊票（覆蓋不足時）、執法工具票（工具不存在時） |

事故對照對不上的事故（不對應任何缺件或空白欄位）建分析票，不建元件票。

**多張票同時改同一份 spec 的變更歷史時，版號由合併方決定，不由各票自行處理。** 各票在自己的分支上都看得到同一個當前版號，於是都填下一號——撞號因此是常態不是意外，而它到合併時才顯現。處置比照規格範本〈變更歷史〉的並行版號條文：以合併方最終寫回的順序為準，後合入者版號順延並同步 frontmatter 的 `version` 欄。這一條跨票種通用，元件票、畫面票、遷移票共用同一份 spec 檔時皆適用。
