## 這一步在解什麼

把齊全的契約變成可派發的票。**契約齊全後，畫面票與元件票的寫法是固定的——寫不成這個形式即為缺件訊號。**

## 執行者與簽核者

| 動作 | 執行者 | 核定者 |
|------|--------|-------|
| 撰寫元件庫規格（step 1 到 4） | 工具清單含 Write／Edit 的設計類代理人，或 PM。只有唯讀與符號級工具的代理人寫不了 spec 檔，不派 | PM 於 spec 票驗收，對照 `step-4` 六條與範本第 9 章 |
| 建元件票、畫面票、遷移票、決策票 | PM，或工具清單含 Bash 的執行者。欄位語意與指令見 `ticket` skill（blockedBy、parent、spawn request） | — |
| 改寫既有票（補 blockedBy、回填 acceptance、拆分） | PM。執行者於 NeedsContext 列出應改內容，不自行編輯非派發範圍的票 | — |
| 存在必要性的合併結論、呼叫端回收的選值、特徵測試規模裁定 | 執行者提案並附證據 | PM |
| 版型拆分、豁免 | 執行者提案 | 版型拆分用戶簽核；豁免 PM 於票驗收核可 |

執行者工具清單不含 Bash 時無法呼叫 ticket 系統。建票步驟改為在票面 NeedsContext 列出應建的票由 PM 代建，且**派發階段就把建票步驟從該票的 acceptance 移出**，不要求執行者做做不到的事。

## 派發語言：四種票

畫面票的 acceptance 句型、反例與缺件處置定於方法論〈派發語言〉，本節只補程序層的句型。

### 畫面票

| 欄位 | 句型 |
|------|------|
| how | 逐狀態列「狀態 X：容器 Z 第 N 格放元件 A 變體 a、第 N+1 格放元件 B 變體 b」，狀態來源指向狀態矩陣。**寫不成這個形式時停手建元件票**，設為畫面票的 blockedBy |
| acceptance（與方法論〈派發語言〉同文） | 「頁面檔的元件 import 只來自元件庫的統一匯出入口」（無 import 邊界的宿主改用方法論〈Web/HTML 端 L2 特別判準〉的不並存斷言）；「狀態矩陣每列都以契約內的元件組成」。**不得追加「不溢位」「畫面正確顯示」**——不溢位由元件票的測試契約承載，畫面票不重驗 |
| 派發 prompt 必含 | 見下方〈派發 prompt 的三項固定句〉 |

一則完整的畫面票 how 與 acceptance 見 `appendix-examples.md`〈正例〉。

上表句型只涵蓋「單一狀態、佔格位的元件」，以下各條補齊其餘形態的寫法：

**格位起算**：格位的指稱以容器契約的 slot 契約為準。容器已具名 slot 者（如頁首、工具列、主區、側欄）寫 slot 名，不另行編號；容器以單一方向排列且未具名 slot 者，寫「第 N 格」，依排列方向由起點計數——垂直堆疊以最上方、水平並排以書寫方向起始側為第 1 格，每個直接子件佔一格。容器契約尚未寫出 slot 者，先補該容器的 slot 契約，不在畫面票內自訂編號。

**巢狀容器**：被放入格位的元件若有由呼叫端填入的 slot，該 slot 的內容於同一列續寫「元件 A 的 {slot 名} slot 放元件 B 變體 b」，直到被放入的元件不再有呼叫端須填的 slot 為止；元件自帶的子件不寫。同質子件數量隨資料而變者，寫「逐格放元件 A 變體 a，數量依資料筆數」，不逐筆列出。

**覆蓋層**：覆蓋層元件（疊於版面之上、不佔容器格位者，如選單、暫態提示、浮層、對話框）不寫進格位句。由呼叫端觸發者，於該狀態列末以「覆蓋層：元件 A 變體 a（觸發：可觀測事件；附著對象：觸發元件或視窗）」逐項列出，可在多個狀態各列一次；屬觸發元件自帶者（觸發器與其展開內容同屬一個元件契約）不列。覆蓋層的定位、尺寸與遮擋由該元件契約的尺寸契約與組合規則承載，畫面票不述。

**疊加態**：狀態矩陣中與其他狀態同時成立的疊加態，how 寫成獨立一列，列首標明「疊加於：底層狀態清單」，列內只寫增量——新增的元件與其格位、既有元件的變體改變；底層狀態列不重寫、不加疊加分支。增量格位隨底層狀態不同者，列內逐底層狀態分句。兩個疊加態可同時成立且改動同一格位者，不在畫面票裁決，回狀態矩陣補判定。

**非狀態進入情境**：how 的列固定為狀態矩陣的列（見上表「逐狀態列…狀態來源指向狀態矩陣」），規格描述的進入路徑若不在狀態矩陣列舉中，不得為此新增獨立列。該情境所含成分依性質拆解：影響既有畫面呈現者併入既有狀態列的 how；需要程式定位或聚焦者寫進該元件回饋契約「被程式定位」格（`step-3-fill-contract.md`〈填通道與四段結局〉：「使用者接近／按下／被程式定位／資料態變更時，此形態的使用者從哪個通道得知？」）；需要暫態通知者寫進上文〈覆蓋層〉子句（「由呼叫端觸發者，於該狀態列末…逐項列出」）。

**slot 值缺資源**：how 指名的 slot 值為識別名（i18n key、資源名）且識別名已定、其資源系統尚無對應內容者，how 照寫該識別名並標「待決」，建產出該資源的前置票，設為本畫面票 blockedBy；how 仍屬合格寫法，blockedBy 清除前不派發（方法論〈派發語言〉「slot 值缺資源時」列）。識別名未定者 how 寫不成，不適用本條。待決落在被引用元件的契約欄位者亦不適用——依 `step-4-verify-completeness.md`〈契約齊全的定義：六條〉第 1 條，該元件不得被畫面票引用。

**範例（巢狀容器：how 要展開到第一層容器還是葉元件）**：

輸入：狀態「正常（有項目）」的畫面結構為三層巢狀——頁面框架第 2 格（主區）放清單容器；清單容器逐格放清單卡（變體 default，數量依資料筆數）；清單卡內的徽章 slot 放狀態徽章（變體依資料的狀態值）。

產出物（判定表，每列為一種 how 寫法）：

| how 寫法 | 是否合格 | 理由 |
|---------|---------|------|
| 只寫「主區放清單容器」，不再往下展開 | 不合格 | 停在第一層容器，讀者無法只憑 how 判斷清單卡與其內徽章該用哪個元件與變體，違反「寫不成這個形式即為缺件訊號」的自我檢查目的 |
| 逐層展開到葉元件：「主區放清單容器，清單容器逐格放清單卡變體 default（數量依資料筆數），清單卡的徽章 slot 放狀態徽章變體依資料狀態值」 | 合格 | 清單容器與清單卡的徽章 slot 皆由呼叫端填入，逐一指名到不再有呼叫端須填的 slot 為止 |

驗證（檢驗問句）：

- Q how 是否續寫到被放入元件不再有呼叫端須填的 slot？　預期：是（依據：「直到被放入的元件不再有呼叫端須填的 slot 為止」）
- Q 資料驅動的格數（依資料筆數）是否以固定寫法標明，而非窮舉具體數字？　預期：是（如「數量依資料筆數」，不需列出每一筆的重複結構）
- Q 清單卡若內建固定圖示（非 slot），how 是否寫該圖示？　預期：否（依據：「元件自帶的子件不寫」）

### 元件票

**粒度規範的是 acceptance 的投影單位，不是排程單位**：一票一元件或一容器；多張元件票可掛同一張 parent 傘票分 wave 派發；變體與狀態集皆「不適用」的原子元件（分隔線、留白）得合併為一票，acceptance 仍逐元件投影。既有的多元件票拆分；「拆不動」的界線是**該票已有 commit 觸及兩個以上元件**（以 diff 涉及的元件檔案數計）——命中即視為拆不動，此時 acceptance 以「符合 spec 條目 {編號} 的元件契約欄位表」一條加測試契約一條代替逐欄投影；未命中（尚未開始或 commit 只觸及單一元件）一律照拆分規則逐票逐元件投影，不得以「稍後可能難拆」為由提前套用本例外。

| 欄位 | 句型 |
|------|------|
| what | 「建立元件 A：{內容角色}，變體 {清單}」或「建立容器 Z：子件 {具名清單}，方向 {並排／堆疊}，空間不足 {策略}」 |
| acceptance | 元件契約欄位表對該元件的投影各一條（含回饋契約——每事件每形態的通道或「不可用加替代」）；容器加排列不變式三項各一條；測試契約一條（全變體全狀態、每種尺寸、最長文案） |
| blockedBy | **填 ticket ID，不填資產名**：產出 token 表、i18n 資源、互動反應規格、測試基座的票，待決欄位的決策票；容器票另列其子件元件票；資產已存在且無票者不列。**容器票所列子件元件票尚未落地時，容器票本身仍可派發不受阻**——slot 依方法論〈元件契約判準〉的〈slot 暫承接規則〉以宿主基底型別暫承接，待子件票落地後由收窄票統一收回，不視為 blockedBy 未清 |
| 派發 prompt 必含 | 見下方〈派發 prompt 的三項固定句〉。元件票逐項對照的是元件契約欄位表投影與測試契約條目，非畫面票的 import 邊界斷言 |

### 遷移票（step 2 走路徑 C 的存量頁面）

**按 feature 目錄拆票**——一票跨多個目錄會撞認知負擔閾值且互相阻塞。「目錄」指直接含待改頁面檔的目錄，不是其上層目錄：上層目錄底下的子目錄各自成票，上層目錄本身直接含待改頁面檔者另成一票；不含待改頁面檔的目錄不建票。容器元件優先（重疊事故的根因在此），其次空白欄位補實作。

| 欄位 | 句型 |
|------|------|
| what | 「將 {feature 目錄} 頁面層的原生佈局改為容器 {Z}，元件設定回收至契約」 |
| acceptance | 「該目錄頁面層零原生佈局原語直接包兩個以上元件庫元件」（執法工具不偵測佈局原語者，以 step 2 路徑 C 步驟 3 的 grep 驗收）；「元件 import 只來自統一匯出入口」；「baseline 已縮減該目錄」（baseline 形態依執法工具而定：有目錄級白名單者移除該目錄，無者 baseline 範圍記於決策文件，同 `foundation-design` skill 接手模式的規模閘門處置） |
| blockedBy | 容器 Z 的元件票、特徵測試補齊票（覆蓋不足時）、執法工具票（工具不存在時） |

「只擋新增」的 baseline 落在執法工具的白名單設定；工具無目錄級白名單者記於決策文件；工具不存在者建工具票列為遷移票 blockedBy。

**範例（巢狀 feature 目錄：按頂層拆還是按直接含待改檔案的目錄拆）**：

輸入：存量頁面層原生佈局分布於巢狀 feature 目錄——`features/project/list/`（2 處原生佈局）、`features/project/detail/`（1 處原生佈局，與 list 同屬 `features/project/` 底下的子目錄）、`features/settings/`（1 處原生佈局，無子目錄）。

產出物（判定表）：

| 拆票依據 | 拆出的票數與範圍 | 是否合格 |
|---------|----------------|---------|
| 依頂層目錄拆 | 一票涵蓋 `features/project/`（橫跨 list 與 detail 兩個子目錄共 3 處） | 不合格——一票跨多個目錄，撞認知負擔閾值且互相阻塞 |
| 依直接含待改檔案的目錄拆 | `features/project/list` 一票（2 處）、`features/project/detail` 一票（1 處）、`features/settings` 一票（1 處），共三票 | 合格——每票對應一個直接含待改頁面檔的目錄，範圍單一不互相阻塞 |

驗證（檢驗問句）：

- Q 拆票單位是頂層目錄還是直接含待改檔案的目錄？　預期：後者（依據：「『目錄』指直接含待改頁面檔的目錄，不是其上層目錄」）
- Q `features/project/` 底下的 list 與 detail 是否合併為同一張遷移票？　預期：否——分屬不同的直接含待改檔案目錄，各自成票
- Q `features/settings/` 直接含 1 處待改檔案，是否一票？　預期：是
- Q `features/project/` 本身若直接含 1 個待改頁面檔，是否併入 list 票？　預期：否，另成一票（依據：「上層目錄本身直接含待改頁面檔者另成一票」）

### 決策票與分析票

| 什麼情形 | 建哪種 |
|---------|-------|
| 契約有欄位標「待決」 | 決策票，設為該元件票的 blockedBy |
| step 2 路徑 C 的事故對照對不上任何缺件或空白欄位 | **分析票，不建元件票** |

## 派發 prompt 的三項固定句

畫面票與元件票的派發 prompt 都必含：

- Solution 含 `### 自檢結果` 子章節（逐 acceptance 附證據，非泛稱「已自檢」）與 Phase 4 結論
- 測試一律前台執行，不用 `run_in_background`
- 回報前 `git status --porcelain` 為空

三者的固定句與觸發條件的權威是 **agent 派發範本**（〈骨架（權威版）〉與〈Solution 自檢結果子章節義務〉兩節），本節不重複；地址見 `addresses.md`。

## 多張票同改一份 spec 時的版號

**版號由合併方決定，不由各票自行處理。**

各票在自己的分支上都看得到同一個當前版號，於是都填下一號——**撞號因此是常態不是意外**，而它到合併時才顯現。處置比照範本〈變更歷史〉的並行版號條文：以合併方最終寫回的順序為準，後合入者版號順延並同步 frontmatter 的 `version` 欄。這一條跨票種通用，元件票、畫面票、遷移票共用同一份 spec 檔時皆適用。

## 契約先於實作，但契約不是不可變

「契約先於實作」指**改動先落在契約**，不指契約鎖死。

實作中發現契約值不成立（策略選錯、尺寸公式不成立）時：先改契約條目，再改實作，變更理由記入該元件票的 acceptance 修訂或 spec 變更歷史。

順序反過來（先改實作再回頭補契約，或乾脆不補）會讓契約與程式碼漂移，而下一個接手的人會走 step 2 的路徑 C 重新萃取一次。
