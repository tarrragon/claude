## 元件契約欄位填寫問句

每欄一個問句，答不出來的欄位即為空格；空格的處置是找來源，不是猜。來源不可得（決策者不可得、前置資源未產出、合併與否無人拍板）時三種模式共用同一出口：該欄標「待決」並建決策票或前置票，設為元件票的 blockedBy；存在必要性檢視的合併結論由 PM 於契約票驗收核定。

合法的佔位值只有兩個：「待決」是缺答案，「不適用」是答案，兩者不可互代。「不適用」限該欄對此元件結構上不存在時使用（無變體、狀態集只有 enabled、無 slot、無文字、純顯示且無資料態變更），須附一句理由，且只允許於下表「可填不適用的欄位」一組；「不得填不適用的欄位」一組不得填不適用（語意與內容角色是元件存在的理由，填不適用等同該元件不該存在；純顯示元件的無障礙至少有朗讀標籤與焦點路徑）。

| 分組 | 欄位 |
|------|------|
| 可填不適用的欄位 | 變體、狀態集、slot 契約、內容政策、反例、操作機制（純顯示且無任何互動的元件）、回饋契約（限純顯示且無資料態變更者） |
| 不得填不適用的欄位 | 語意與內容角色、尺寸契約、組合規則、測試契約、無障礙 |

兩組合計即元件契約欄位表全部欄位，無欄位落在兩組之外——〈契約齊全的定義〉第一條的機械檢查因此對每一欄都有唯一解。（空間不足策略不是元件契約欄位表的欄位之一，它是容器的排列不變式；其合法替代值「不觸發 + 公式」見下方排列不變式三問段。）

**誤填「不適用」的代價**：它是齊全檢查唯一的假陽性入口。「待決」被明訂為「視同空白、該元件不得被畫面票引用」，誤填只會擋住流程；「不適用」則被視為落成值，齊全檢查全數通過、元件票取得可被畫面票引用的資格，缺料要到實作期才暴露，而該處已無契約可回溯。判定不確定時填「待決」不填「不適用」——前者的代價是多一次往返，後者的代價是一個看起來齊全的錯誤契約。「見設計稿」「同上」「TBD」等未落成值的寫法視同空白。i18n key 已宣告而譯文未到者，內容政策填 key 即齊全，測試契約以當時資源檔的值執行，譯文更新後的重測屬 i18n 票驗收，不回退契約狀態。方法論〈分層架構〉最小適用集生效的小型專案，元件契約欄位表縮至語意與內容角色／尺寸契約／內容政策（回饋契約不在最小適用集），排列不變式仍須填，不隨欄位一併縮減。

| 欄位 | 填寫問句 | 常見空格與來源 |
|------|---------|--------------|
| 語意與內容角色 | 使用者看到它預期能做什麼？它放的是標題／內文／標籤／數值／動作？什麼情境不該用它？ | 「何時不用」常空白；來源是相鄰元件的語意差異。複合角色（內文 + 動作）並列寫出，每個角色對應一個 slot |
| 變體 | 同一語意有幾種行為不同的形態？各自的外觀與行為差在哪？ | 以外觀值命名（藍色版）；改以語意命名（primary / confirm / danger） |
| 狀態集 | 它自身可以處於哪些狀態？每個狀態怎麼顯示、能做什麼、怎麼進、怎麼出？此狀態的來源是互動瞬態、資料態、還是無（—）？同步策略是本地即時、樂觀更新後確認、還是等確認才顯示？ | 只列元件自身的狀態（enabled／loading／error 等），畫面級的進出由呼叫端的畫面狀態表承載；退出路徑空白即死胡同；來源與同步策略常空白，兩者不分會讓互動瞬態與資料態混在同一張矩陣，實作者不知哪個狀態要接 provider、哪個只是本地事件；四欄填法見 `ux-design-evaluation` skill 的狀態矩陣 |
| 操作機制 | 這個形態的使用者用什麼動作完成它的任務？任務要多精確？該形態的輸入做得到嗎？做不到時給什麼替代機制？按下後走哪個回饋通道？ | 常直接沿用畫布的手勢（桌機拖動滑桿搬到手機）；每形態各答一次，精度不足時填替代機制（步進按鈕、輸入彈窗）；回饋通道引用形態因素矩陣（手機須觸覺或聲音，手指會遮住按鈕）；輸入形式判準見 `ux-design-evaluation` skill 的輸入機制 reference |
| 尺寸契約 | 它自己決定大小還是填滿父容器？最小多小、最大多大？可點元件的最小尺寸有沒有達到該形態的最小命中區？每個形態各一份，同形態內每種測試尺寸下怎麼變？ | 「每種測試尺寸」常只填預設尺寸；最小命中區常沿用桌機值搬到手機；形態、測試尺寸集合與命中區 token 的來源是元件庫規格範本的形態因素矩陣節（判準見方法論〈形態因素先決〉） |
| 內容政策 | 每個文字位置可不可以換行？最多幾行？超出時截斷／淡出／縮放／換行？最長的測試文案是什麼？ | 最長測試文案常空白；來源是專案 i18n 資源檔（Flutter 為 ARB）中該 key 各語言的最長值，排除未翻譯的 fallback（與來源語系字串相同者）；語系少於三種時另加一條人工的長文案。無文字 slot 的元件填「不適用」 |
| slot 契約 | 呼叫端能放什麼進來？每個位置接受什麼型別？文字從哪來？ | 文字來源常寫死；規則見方法論〈元件文字歸屬〉。容器的子件 slot 須寫具名元件清單與數量上限，策略欄只引用此處的上限 |
| 組合規則 | 它可以放進哪些容器？哪些區域不得放它（該形態的禁放區）？對齊基準是什麼？當它是表格或列表的一欄時佔多寬、內距多少？ | 「可放入的容器」填「任何地方」即等於允許頁面原生佈局；須列具名容器。可點元件的禁放區引用形態因素矩陣（手機四角、系統手勢區）。根層框架容器填「根：無父容器」並承載該形態的安全區 |
| 無障礙 | 輔助技術會把它唸成什麼？值或狀態變了怎麼播報？不靠顏色能不能分辨？鍵盤或輔助技術怎麼走到它、怎麼操作它？ | 常空白或只填對比；朗讀標籤與播報跨形態共用，操作路徑每形態各一份；不得填「不適用」 |
| 回饋契約 | 使用者接近／按下／被程式定位／資料態變更時，此形態的使用者從哪個通道得知？元件不在視野時要不要升級為系統通知？每條狀態邊的提示是元件自播還是呼叫端觸發？ | 定位提示（locate）與狀態變更提示（state-change）常空白；來源是元件庫規格範本第 1 章回饋通道子表與第 2 章過渡提示觸發點 |
| 測試契約 | 一支測試能不能一次看到全部變體與狀態？每種尺寸都不溢位？最長文案照內容政策處置？ | 只測預設尺寸與短文案；測試形態（golden / widget）定於 L2，L2 無此條時以範本測試點的 widget test 為預設並建 L2 補條目票。測試基座（讓元件在各視窗尺寸下可渲染與斷言的測試工具與 fixture）由 `foundation-design` skill 的測試維度承接 |
| 反例 | 什麼情境會有人誤拿它來用？該改用哪個相鄰元件？ | 常空白；來源是存在必要性檢視時被否決的合併理由 |

範本子節與元件契約欄位表不同名者：狀態集＝範本的「狀態矩陣」、測試契約＝「測試點」、語意與內容角色＝條目標頭三行；完整對應表在範本檔頭註解。

**容器元件另答排列不變式三項**（不重疊／最小間距／空間不足策略）各一問：子件邊界盒在每種尺寸與數量上限下是否兩兩不相交（不重疊）？相鄰子件的最小間距是哪個 token（最小間距）？空間不足時換行、捲動、收合選哪一個、什麼條件觸發（空間不足策略）？子件有數量上限（上限先寫進 slot 契約）且最小視窗保證放得下者，策略填「不觸發：上限 N，最小視窗下 N × 子件最小尺寸 + (N−1) × 最小間距 ≤ 可用空間」，公式即不重疊的測試斷言。

### 正例：清單卡的元件契約欄位（去識別化情境）

去識別化情境貫穿本檔與 `examples-troubleshooting.md`〈正例〉節：一個清單頁，依資料狀態呈現三種畫面樣貌（正常有項目／空清單／清單來源阻擋無法讀取），元件候選為清單卡、狀態徽章、主要操作按鈕、狀態提示，容器為清單容器與頁面框架。容器條目、畫面票 how／acceptance、狀態提示的歸併判斷三類正例在 `examples-troubleshooting.md`〈正例〉節；本節只示範清單卡的元件契約欄位，逐欄呼應上表「常見空格與來源」欄。

| 欄位 | 正例填法 | 呼應上表「常見空格與來源」 |
|------|---------|------------------------|
| 語意與內容角色 | 顯示清單中單一項目的摘要，可點擊查看詳情；複合角色（內文 + 動作）——內文由標題與狀態徽章承載、動作由主要操作按鈕承載，各自對應一個 slot。何時不用：項目需要多行摘要或縮圖預覽時不用，另立元件 | 「何時不用」常空白；本例把它與複合角色的 slot 對應一併寫出 |
| 變體 | `default` 單一變體；封存項目變暗等外觀差異不立新變體，交由狀態集的對應狀態承載 | 以外觀值命名是常見錯誤；本例示範差異該進狀態集而非硬湊變體 |
| 狀態集 | default（來源：—，互動瞬態基準；同步策略：本地即時；顯示標題、徽章、按鈕；可操作：點卡片進詳情、點按鈕觸發動作；進入：清單容器渲染任一列；退出：點卡片離開畫面進詳情，點按鈕留在畫面觸發動作）／focused（來源：互動瞬態（鍵盤焦點）；同步策略：本地即時；顯示同 default 但邊框反白；可操作：Enter 觸發卡片、Tab 移出；進入：鍵盤焦點移入；退出：Tab 移出回 default，或 Enter 同卡片點擊路徑） | 畫面級進出常誤填在此；本例只填元件自身，畫面級三狀態（正常／空／阻擋）留給呼叫端狀態矩陣；來源與同步策略：本例兩狀態皆本地互動瞬態，不需接 provider |
| 操作機制 | 桌機：滑鼠點擊卡片本體或按鈕，精度足夠，回饋通道視覺（按下態）／手機：觸控點擊，卡片本體與按鈕分屬不同命中區避免雙重觸發，命中區依第 1 章 token | 常直接沿用畫布手勢；本例逐形態各答一次並處理命中區重疊 |
| 尺寸契約 | 尺寸模式：填滿父容器（寬）、固有高度；最小尺寸：寬 240px（token `card-min-width`）× 高 64px；按鈕最小命中區不得小於該形態的命中區 token；桌機／手機視窗下皆維持（換版型是清單容器排列不變式的責任，非本元件重複規定） | 「每種測試尺寸」常只填預設；本例明寫兩形態且指出換版型責任歸屬 |
| 內容政策 | 標題 slot：可換行＝否，最大行數＝1，超出處置＝截斷，最長測試文案＝i18n key `list.card.title.sample`（取專案 i18n 資源實測最長值） | 最長測試文案常空白；本例指名來源為 i18n 資源實測值 |
| slot 契約 | title：String（i18n key）必填，呼叫端傳入；badge：狀態徽章元件必填，元件庫子件掛載；action：主要操作按鈕元件必填，元件庫子件掛載（variant `view`） | 文字來源常寫死；本例示範直傳值與子元件掛載兩種來源 |
| 組合規則 | 可放入的容器：清單容器（唯一具名容器，不可直接放入頁面原生佈局）；不得放置區域：手機系統手勢區（按鈕命中區需避開）；對齊基準：文字基線；作為列表一欄：不適用（本元件即列表項本身） | 「可放入任何地方」等於允許原生佈局；本例列具名容器並排除不適用子節 |
| 無障礙 | 朗讀標籤：唸出標題與狀態（如「項目 Alpha，進行中」）；狀態變化播報：徽章改變時播報新狀態；非視覺替代訊號：徽章顏色搭配文字標籤，非唯一訊號；焦點路徑（桌機）：Tab 入卡片→Enter 進詳情，再 Tab 入按鈕→Enter 觸發；焦點路徑（手機）：觸控直接命中，無 Tab 序列；對比：WCAG AA | 常空白或只填對比；本例逐形態各給操作路徑一次 |
| 回饋契約 | 可互動提示：桌機通道：hover（視覺，邊框微亮）；門檻：即時；token：`hover-highlight`；狀態邊：不適用（不改變狀態集）。觸控形態：不可用＋替代——常駐陰影提示可點。焦點：通道：焦點環（視覺）；門檻：即時；token：`focus-ring`；狀態邊：default→focused。按下確認：通道：視覺（卡片輕微下沉）＋觸控形態加觸覺；門檻：100ms 內；token：`press-depth`；狀態邊：不適用（瞬時效果非狀態）。定位提示：不可用＋替代——新項目加入清單時淡入提示（視覺）。狀態變更提示：通道：視覺（徽章淡入淡出過渡）；門檻：300ms；token：`badge-transition`；狀態邊：徽章值 X→Y；元件不在視野時不升級系統通知（非關鍵資訊）。等待與結果：本元件不承載等待層，只承載結果（徽章文字變化即結果通知） | 定位提示與可互動提示常空白；本例逐事件四段（通道／門檻／token／狀態邊）填滿，以「不可用＋替代」示範不適用事件不留空 |
| 測試契約 | 一支測試渲染 default／focused 兩狀態全變體；兩形態最小視窗尺寸下皆不溢位；標題最長測試文案依截斷處置驗證；token 引用非硬編碼 | 「只測預設尺寸與短文案」；本例逐形態測且用最長文案 |
| 反例 | 不該拿它承載需要多行摘要或縮圖預覽的清單項——改用清單卡（詳情版，另立）；不該拿它承載空清單或阻擋提示——改用狀態提示相關元件（歸併判斷見 `examples-troubleshooting.md`〈正例〉節） | 常空白；本例的反例來源即另一類正例（歸併判斷）的落選結論 |

| 逐元件「無障礙（a11y）」 | UX 審查產出的無障礙規格；新抽出的元件不在其中者標待決並建 UX 審查補票 | 規格撰寫者抄錄，不自行設計 |
| 逐元件「使用 design token」「i18n」 | token 表、i18n 資源檔 | 規格撰寫者 |
| 原生元件禁用對照表 | 方法論工程端判準 + 執法工具的偵測 pattern | 規格撰寫者 |
| 豁免清單 | 方法論豁免三條件 | 執行者提案、PM 於票驗收核可 |
| 跨平台命名契約 | 同一 design token 系統被多端使用時才填；判準見方法論〈多端共用 design-system 的跨端契約〉 | PM |

## 多形態專案

支援多個形態時，畫布拆解與容器盤點按形態分別進行（每形態一套 artboard、一份排列關係表），元件候選與存在必要性檢視跨形態合一；畫面票的 how 帶形態前綴。

**元件契約欄位跨形態的共用範圍**：

| 分組 | 欄位 |
|------|------|
| 跨形態共用 | 語意與內容角色、變體、狀態集、slot 契約、反例、無障礙（朗讀標籤）、回饋契約（事件與對應狀態邊） |
| 每形態各一份 | 操作機制、尺寸契約、內容政策、組合規則、測試契約、無障礙（操作路徑）、回饋契約（通道）、容器條目 |

**形態因素矩陣的每形態填一次維度**（欄位填寫時引用）：

| 維度 | 內容 |
|------|------|
| 覆蓋表面對映 | bottom sheet、drawer、dialog、popover 等覆蓋表面依此對映選件，元件的組合規則引用該對映 |
| 回饋通道 | 手機按鈕被手指遮住，須震動或音效；桌機視覺即可 |
| 最小命中區 token | 可點元件的最小命中尺寸依此 token |
| 禁放區與安全區 | 手機四角與系統手勢區不放可點元件，SafeArea 由框架容器承載 |

同一語意可落在不同容器與不同操作機制：導覽項共用，承載它的容器在手機是收合抽屜、在平板與桌機是常駐側欄；數值調整在桌機是拖動滑桿、在手機是步進或輸入彈窗。同形態內不依寬度自動切版：桌機常駐側欄的版型靠視窗尺寸下界與比例約束維持；設計上刻意給使用者選版型（雙欄／單欄）時，那是設定項不是斷點。同形態內的視窗或螢幕尺寸差異不是新形態，由容器的排列不變式承載，不以寬度門檻切版型。
