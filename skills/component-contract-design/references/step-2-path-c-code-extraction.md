# 路徑 C：程式碼萃取（接手既有專案）

> **你在 step 2 路徑 C（程式碼萃取）。** 起點判定為「已有元件程式碼與頁面，無契約或契約不全」時走本檔，判定見 `step-1-pick-starting-point.md`〈判定起點〉。入口與共用規則在 `step-2-extract-components.md`；下一步是 `step-3-fill-contract.md`，讀完後另讀 `step-3-fill-contract-conditional-cases.md`〈路徑 C 專屬：證據順序與漂移判定〉。全程表在 `SKILL.md`〈全程〉。
>
> **同目錄**：`step-2-extract-components.md`（入口，含中間產出物的形態與落點、共用規則一、共用規則二）、`step-2-path-a-spec-derivation.md`、`step-2-path-b-canvas-decomposition.md`（另兩條路徑）、`step-3-fill-contract.md`、`step-3-fill-contract-conditional-cases.md`（路徑 C 專屬的證據順序與漂移判定）、`addresses.md`（簡稱查地址）。

> 溯源：原屬 `step-2-extract-components.md`〈路徑 C：程式碼萃取（接手既有專案）〉整節，依讀者任務拆出獨立檔。

接手的元件庫常見兩種病：**有元件無契約**（行為散在各呼叫端），與**有元件無容器**（頁面用原生佈局排列元件，違反方法論工程端的「禁自製元件」判準）。本路徑先盤點事實再補契約，順序與 `foundation-design` skill 的接手模式一致：盤點 → 命名 → 固化 → 補文件。（`foundation-design` 是本專案的地基設計 skill，與本 skill 同層；它與本 skill 的交界見 `SKILL.md`〈與相鄰資產的交界〉。）

```
1 元件盤點     列出元件目錄的每個 public widget（一檔多 class 各算一個；非 widget 的 helper
               不算元件，誤入匯出入口者記為清理項），與 spec 元件清單對帳：
               目錄有而清單無者補入清單，清單有而目錄無者標「待實作」或刪除（PM 核定）。
               每個元件對照 `step-3-fill-contract.md`〈元件契約欄位填寫問句〉表的**每一個問句**
               （不是每一欄）標三態：
               已定義於程式碼／隱含於呼叫端／空白；一欄內混合三態屬正常。
               值來自全域主題或框架預設（非元件本身宣告、也非呼叫端設定）時，歸「已定義於程式碼」，
               證據欄記主題檔或框架設定檔的具名常數與所在檔案；不成立第四態。
               回饋契約欄位的證據常散在動畫 controller、觸覺 API 呼叫、通知服務程式碼，
               而非 widget 宣告本身；找不到對應呼叫標空白，**不可只因缺席就填「不可用加替代」**
               ——替代方案須有實際程式碼佐證才算已定義。
               零呼叫端的元件仍屬本路徑的元件，標「待接線」，其「隱含於呼叫端」態不成立

2 呼叫端回收   「隱含於呼叫端」的欄位（如 maxLines、overflow 在頁面設定）回收進元件契約；
               呼叫端的設定值不一致時填提案值附各處證據並標「待核定」，
               PM 核定前視同待決，不另建決策票。
               另三種形態：呼叫端繞過 slot 自組內容（在 child 裡自己排 icon 與文字）
               → 記為 slot 契約缺口，提案新 slot 或收窄型別；
               spec 有而程式碼無（spec 的變體多於實作）→ 反向漂移，標「待核定」由 PM 裁定
               補實作或刪 spec；元件與呼叫端都沒設（雙空）→ 標空白，留給 step 3 處理

3 原生佈局掃描 grep **頁面層**（統一匯出入口涵蓋的目錄以外的任何 widget 檔），
               兩類節點都計入，逐處記位置：
               (a) **多子件佈局**以結構定義——接受子件清單的節點即是（帶子件清單參數、
               或以 builder 產生多個子件者；堆疊、彈性盒、格線、疊層、捲動列表、表格皆屬）。
               限**原生**佈局節點：頁面層呼叫元件庫容器（如 `面板(children: [...])`）時，
               該子件清單已由容器承載，不在此計入，屬 step 4 分母的「既有容器已承載者」；
               清單內若再出現原生佈局節點，那一個照樣計入。
               每處計為一個排列關係，**不論子件是元件庫元件還是原生葉節點**；
               每處問判別問句。
               (b) **單子件佈局輔助**（僅改空間分配、內距、對齊或尺寸，不含第二子件的包裝節點）
               每處計入，依屬性歸屬轉置到容器或元件，見下方〈佈局輔助的歸屬轉置〉；
               它不是排列關係，不問判別問句、不成容器候選。
               兩類的框架例示見下方〈原生佈局掃描（步驟 3）的框架對應〉。
               頁面層含 feature 目錄下的 sheet／dialog／card 等區域 widget
               （不在統一匯出入口即頁面層）；每頁的根堆疊也算，同型歸併為
               「頁面區塊堆疊」框架容器

4 容器候選     判別問句答「頁面」處即容器候選；依 `step-2-extract-components.md`〈共用規則二：
               同型歸併〉歸併，但**存量的策略不一致要收斂不要拆**，理由見該節。
               資料驅動 N 列的堆疊（列表、明細）是容器候選，
               只在 `appendix-examples.md`〈Troubleshooting：卡住時的症狀處置〉的計數門檻中排除

5 事故對照     既有的重疊、截斷、點不到事故逐一對應到缺哪個容器或哪個空白欄位。
               來源三選一：issue tracker 既有紀錄、ticket 描述提及的缺陷、用戶口述提供的清單，
               逐一標明取自何處；對不上的事故是新發現，另建分析票（不建元件票）。
               三者皆查無時視同零事故，本步驟為空——**零事故是關機判定**，
               要記下查過哪些來源、各自為空。零事故的專案，
               step 5 的容器優先序改依呼叫處數量（出現最多的排列關係先建）
```

**既有變體名稱（步驟 1、2）**：步驟 1 標為「已定義於程式碼」的變體名稱，以及步驟 2「spec 的變體多於實作」的名稱，都要先過 `step-4-verify-completeness.md`〈既有變體欄的差異判別〉。指不出差異的名稱降為用途描述，不標反向漂移；判別問句、證據範圍與反向漂移的分界皆以該節為準。

**呼叫端回收（步驟 2）的判準**：呼叫端設定值不一致是契約缺內容政策的訊號。同一個元件在三個頁面被設成三種 `maxLines` 時，執行者選一個值作提案並附三處證據，PM 於契約票驗收核定後其餘兩處改為引用元件預設；差異若是語意的（標題一行、內文三行），那是**兩個內容角色，拆元件**。

**範例（呼叫端設定不一致：漂移還是拆元件）**：

輸入：同一個元件在頁面甲呼叫端設 `maxLines=2`，在頁面乙呼叫端設 `maxLines=3`；兩處呼叫端的內容角色皆為條列項目說明文字，用途相同，查無任何規格文字說明兩處為何不同。

產出物（決策表）：

| 情形 | 判定 |
|------|------|
| 兩處內容角色相同，差異查無語意來源 | 設定漂移——選一個值作提案（如 `maxLines=3`）並附兩處呼叫端證據，標「待核定」 |
| 兩處內容角色不同（如一處標題一行、一處內文多行） | 不是漂移，是兩個內容角色，拆為兩個元件 |

驗證（檢驗問句）：

- Q 本例兩處呼叫端的內容角色是否相同？　預期：是（皆為條列項目說明文字）
- Q 內容角色相同時是否該拆元件？　預期：否——應收斂為提案值待核定，不得因數值不同就認定為兩個元件
- Q 若兩處內容角色不同，是否仍收斂為提案值？　預期：否——語意差異即拆元件理由，不收斂

**原生佈局掃描（步驟 3）的框架對應**：判準是結構，下列框架名只是例示、不是完整清單，未列出的節點依「接受子件清單與否」自行判定。

| 類別 | Flutter 例示 | Web 框架例示 |
|------|-------------|-------------|
| 多子件佈局：堆疊與彈性盒 | `Row`／`Column`／`Wrap`／`Flex` | 頁面元件內的 flex 容器 |
| 多子件佈局：疊層 | `Stack`／`IndexedStack` | 絕對定位疊放的容器、分頁內容切換容器 |
| 多子件佈局：捲動列表 | `ListView`／`GridView`／`CustomScrollView` 與 Sliver 系列（含 builder 形式） | 列表渲染（map 產生多個子件的容器） |
| 多子件佈局：表格與格線 | `Table`（`GridView` 已列在捲動列表，同一節點只計一處） | grid 容器、table |
| 單子件佈局輔助 | `Expanded`／`Flexible`／`Padding`／`Align`／`Center`／`SizedBox`／`ConstrainedBox` | 只為單一子件設邊距、對齊或尺寸的包裝元素 |

原生佈局出現在元件庫內部（統一匯出入口涵蓋的目錄）屬正常——容器元件自己就是用它實作的，這是本步驟唯一的排除，逐處記位置與所屬目錄；入口外的 feature 目錄下的自製 widget 屬頁面層，一併掃。

**與原生元件禁用對照表的分工**：原生葉節點（原生文字、圖示等）本身出現在頁面層，屬元件層違規，由 L3 規格的原生元件禁用對照表處理（方法論〈分層架構〉L3 列）；它所在的那個多子件佈局屬容器層，由本步驟計入。同一處 `Row(原生文字, 元件庫元件)` 因此產出兩筆紀錄：一筆元件層（原生文字換成元件庫元件），一筆容器層（這個排列要有容器）。只記其中一筆，另一層的缺口就沒有人收。

**佈局輔助的歸屬轉置**：頁面層的單子件佈局輔助一律計入，依它改的屬性轉到擁有該屬性的一方。

| 屬性 | Flutter 例示 | 轉置到 |
|------|-------------|--------|
| 填滿／空間分配 | `Expanded`／`Flexible` | 容器的具名 slot（例：「填滿區」slot），由容器決定該 slot 佔剩餘空間 |
| 間距／對齊／畫面邊距 | `Padding`／`Align`／`Center`／子件之間當間隔用的 `SizedBox` | 容器負責，或成為容器參數（邊距 token、對齊參數） |
| 單一元件的固定尺寸 | 包住單一元件、限定其寬高的 `SizedBox`／`ConstrainedBox` | 該元件的尺寸變體，記為元件契約缺口（尺寸契約欄） |

`SizedBox` 依用途分列：夾在兄弟子件之間、沒有子件的是間距，歸第二列；包住一個元件的是固定尺寸，歸第三列。

**Why**：佈局輔助留在呼叫端有兩個結構問題。第一，容器的不變式無法由容器驗證。容器契約寫「子件中恰一個填滿剩餘高」，實際由呼叫端包 `Expanded` 表達，容器看不到、也驗不了「恰一個」。第二，頁面會依賴容器的內部實作。`Expanded` 屬 Flutter 的 ParentDataWidget，只能當 Flex 的直接子件；頁面包了它，就要求容器內部必須是 Flex、而且不再多包一層。容器改動內部結構時，頁面在執行期才報錯（`Incorrect use of ParentDataWidget`），編譯期沒有任何訊號。前例是框架自己的頁面骨架：Flutter `Scaffold` 以具名 slot（`body`）承載填滿區，不要求呼叫端包 `Expanded`。**Consequence**：不轉置時，不變式停留在慣例，而且容器每一次內部重構都可能在別人的頁面上變成執行期錯誤。**Action**：依上表逐處轉置，轉置去向記在容器候選表（前兩列）或元件契約缺口（第三列）。

**絆腳索**：單一容器的排列參數或變體超過 3 個時，改拆為具名容器。參數一直增加，代表這個容器在承載多種不同的排列，已經不是同一個容器；不拆的話，容器契約的排列不變式會填不出單一值（即 `step-2-extract-components.md`〈歸併過頭的訊號〉）。觸發時在容器候選表該列標「拆分」，並列出拆出的新容器名。

**特徵測試閘門（掛在步驟 2）**：回收呼叫端設定進元件會改變頁面行為。覆蓋不足時先補特徵測試（不驗「應該是什麼」，只把現況行為原樣鎖住，改動一旦改變行為就紅燈）鎖住現況。規模補不補得起來由 PM 於票面裁定，**執行者只提報覆蓋數字、不自行裁定**；裁定為補不起時只在有覆蓋的模組內回收，其餘標「只擋新增」——這也是關機判定，要記下覆蓋數字與門檻值。判準與規模閘門見 `foundation-design` skill 的接手模式；本步驟的裁定結果會成為 step 5 遷移票的 blockedBy。

**走完之後**：帶著三態盤點表、回收提案值、容器候選表與事故對照進 `step-3-fill-contract.md`；讀完該檔後另讀 `step-3-fill-contract-conditional-cases.md`〈路徑 C 專屬：證據順序與漂移判定〉，其他兩條路徑不需要那一份。
