接手的元件庫常見兩種病：**有元件無契約**（行為散在各呼叫端），與**有元件無容器**（頁面用原生佈局排列元件，違反方法論工程端的「禁自製元件」判準）。本路徑先盤點事實再補契約，順序與 `foundation-design` skill 的接手模式一致：盤點 → 命名 → 固化 → 補文件。（`foundation-design` 是本專案的地基設計 skill，與本 skill 同層；它與本 skill 的交界見 `SKILL.md`〈與相鄰資產的交界〉。）

```
1 元件盤點     列出元件目錄的每個 public widget（一檔多 class 各算一個；非 widget 的 helper
               不算元件，誤入匯出入口者記為清理項），與 spec 元件清單對帳：
               目錄有而清單無者補入清單，清單有而目錄無者標「待實作」或刪除（PM 核定）。
               每個元件對照 `step-3-fill-contract.md`〈元件契約欄位填寫問句〉表的**每一個問句**
               （不是每一欄）標三態：
               已定義於程式碼／隱含於呼叫端／空白；一欄內混合三態屬正常。
               值來自全域主題或框架預設（非元件本身宣告、也非呼叫端設定）時，歸「已定義於程式碼」，
               證據欄記主題檔或框架設定檔的具名常數與所在檔案；不成立第四態。
               回饋契約欄位的證據常散在動畫 controller、觸覺 API 呼叫、通知服務程式碼，
               而非 widget 宣告本身；找不到對應呼叫標空白，**不可只因缺席就填「不可用加替代」**
               ——替代方案須有實際程式碼佐證才算已定義。
               零呼叫端的元件仍屬本路徑的元件，標「待接線」，其「隱含於呼叫端」態不成立

2 呼叫端回收   「隱含於呼叫端」的欄位（如 maxLines、overflow 在頁面設定）回收進元件契約；
               呼叫端的設定值不一致時填提案值附各處證據並標「待核定」，
               PM 核定前視同待決，不另建決策票。
               另三種形態：呼叫端繞過 slot 自組內容（在 child 裡自己排 icon 與文字）
               → 記為 slot 契約缺口，提案新 slot 或收窄型別；
               spec 有而程式碼無（spec 的變體多於實作）→ 反向漂移，標「待核定」由 PM 裁定
               補實作或刪 spec；元件與呼叫端都沒設（雙空）→ 標空白，留給 step 3 處理

3 原生佈局掃描 grep **頁面層**（統一匯出入口涵蓋的目錄以外的任何 widget 檔）的佈局原語
               （依框架：水平／垂直堆疊、彈性盒、格線），
               只算包兩個以上元件庫元件的位置；中間只隔**佈局輔助**（語意定義：僅改尺寸或
               內距、不含第二子件的包裝節點；Flutter 為 Expanded／Flexible／Padding／
               SizedBox／Align，框架名只是本專案的例示，其他框架依語意自行對應）仍算直接包，
               中間隔另一個元件庫元件則不算。
               頁面層含 feature 目錄下的 sheet／dialog／card 等區域 widget
               （不在統一匯出入口即頁面層）；每頁的根堆疊也算，同型歸併為
               「頁面區塊堆疊」框架容器。每處問判別問句

4 容器候選     判別問句答「頁面」處即容器候選；依 `step-2-extract-components.md`〈共用規則二：
               同型歸併〉歸併，但**存量的策略不一致要收斂不要拆**，理由見該節。
               資料驅動 N 列的堆疊（列表、明細）是容器候選，
               只在 `appendix-examples.md`〈Troubleshooting：卡住時的症狀處置〉的計數門檻中排除

5 事故對照     既有的重疊、截斷、點不到事故逐一對應到缺哪個容器或哪個空白欄位。
               來源三選一：issue tracker 既有紀錄、ticket 描述提及的缺陷、用戶口述提供的清單，
               逐一標明取自何處；對不上的事故是新發現，另建分析票（不建元件票）。
               三者皆查無時視同零事故，本步驟為空——**零事故是關機判定**，
               要記下查過哪些來源、各自為空。零事故的專案，
               step 5 的容器優先序改依呼叫處數量（出現最多的排列關係先建）
```

**呼叫端回收（步驟 2）的判準**：呼叫端設定值不一致是契約缺內容政策的訊號。同一個元件在三個頁面被設成三種 `maxLines` 時，執行者選一個值作提案並附三處證據，PM 於契約票驗收核定後其餘兩處改為引用元件預設；差異若是語意的（標題一行、內文三行），那是**兩個內容角色，拆元件**。

**範例（呼叫端設定不一致：漂移還是拆元件）**：

輸入：同一個元件在頁面甲呼叫端設 `maxLines=2`，在頁面乙呼叫端設 `maxLines=3`；兩處呼叫端的內容角色皆為條列項目說明文字，用途相同，查無任何規格文字說明兩處為何不同。

產出物（決策表）：

| 情形 | 判定 |
|------|------|
| 兩處內容角色相同，差異查無語意來源 | 設定漂移——選一個值作提案（如 `maxLines=3`）並附兩處呼叫端證據，標「待核定」 |
| 兩處內容角色不同（如一處標題一行、一處內文多行） | 不是漂移，是兩個內容角色，拆為兩個元件 |

驗證（檢驗問句）：

- Q 本例兩處呼叫端的內容角色是否相同？　預期：是（皆為條列項目說明文字）
- Q 內容角色相同時是否該拆元件？　預期：否——應收斂為提案值待核定，不得因數值不同就認定為兩個元件
- Q 若兩處內容角色不同，是否仍收斂為提案值？　預期：否——語意差異即拆元件理由，不收斂

**原生佈局掃描（步驟 3）的框架對應**：Flutter 找 `Row` / `Column` / `Wrap` / `Flex` 直接包兩個以上元件庫元件的位置；Web 框架找頁面元件內的 flex / grid 容器。原生佈局出現在元件庫內部（統一匯出入口涵蓋的目錄）屬正常——容器元件自己就是用它實作的；入口外的 feature 目錄下的自製 widget 屬頁面層，一併掃。

**特徵測試閘門（掛在步驟 2）**：回收呼叫端設定進元件會改變頁面行為。覆蓋不足時先補特徵測試（不驗「應該是什麼」，只把現況行為原樣鎖住，改動一旦改變行為就紅燈）鎖住現況。規模補不補得起來由 PM 於票面裁定，**執行者只提報覆蓋數字、不自行裁定**；裁定為補不起時只在有覆蓋的模組內回收，其餘標「只擋新增」——這也是關機判定，要記下覆蓋數字與門檻值。判準與規模閘門見 `foundation-design` skill 的接手模式；本步驟的裁定結果會成為 step 5 遷移票的 blockedBy。
