## 這張表管什麼

本套件各檔以簡稱引用下列資產與用詞。**本表是地址的權威**——消費點就近帶一句路徑或一句定義是允許的（對 agent 讀者，行內一句比一次跳轉便宜），但不得與本表衝突，衝突時以本表為準。新增引用時至少要能在本表查到。

| 簡稱 | 是什麼 | 地址 |
|------|--------|------|
| 方法論 | 元件庫雙向約束方法論。**判準的權威**——〈元件契約判準〉〈容器亦為元件〉〈命名與通用元件判準〉〈元件文字歸屬〉〈分層架構〉〈形態因素先決〉〈派發語言〉〈掛載點〉〈失敗路徑覆蓋〉〈降級不解除回饋義務〉〈元件層回饋日誌（觀測對偶）〉〈多端共用 design-system 的跨端契約〉〈Web/HTML 端 L2 特別判準〉、工程端「禁自製元件」判準、豁免三條件、〈slot 暫承接規則〉皆在其中 | 本專案的實際路徑見 `project-integration/README.md`（本 skill 宣告 portable，正文不指名特定專案的檔案路徑） |
| 元件庫規格範本 | 填契約的**產物形狀**。第 1 章形態因素矩陣、第 2 章狀態綁定模式、第 4 章容器條目、第 9 章驗收、〈實作註記〉〈變更歷史〉、檔頭註解的欄位完整對應表皆在其中。**實際填寫的是它在專案 spec 目錄的副本，不是這份源檔**——複製作法見 `SKILL.md`〈起手〉 | 本專案的實際路徑見 `project-integration/README.md`（同上） |

| 執法工具 | 抓裸值與寫死文字的檢查工具（本套件一律稱執法工具，不混用 lint）。原生元件直用的定義與判定權威在本 skill，不在執法工具——PostEdit hook 含八個 pattern 攔下新增的原生元件直用，但批次掃描腳本不偵測；判定與清點仍由本 skill 的 step-3〈原生元件禁用對照表〉承接 | Dart 專案為 `dart-style-guardian` skill；其他語言查該專案的 lint 設定檔，查無者依 `step-5-write-tickets.md` 遷移票的 blockedBy 建執法工具票 |
| 判別問句 | 「任兩個元件的相對位置是誰決定的」。答「頁面」即缺容器 | 方法論〈容器亦為元件〉。本 skill 內另有一個判別新建與存量的問句（「這個差異是有人決定的，還是沒人決定而長出來的」），在 `step-2-extract-components.md`〈共用規則二〉，兩者不同名不混用 |
| 統一匯出入口 | 元件庫與頁面層的邊界：入口涵蓋的目錄為元件庫，入口外的任何 widget 檔皆屬頁面層 | 本列即定義。**定位作法**：先找元件目錄根層的 barrel／index 檔或套件匯出宣告（如 `index.dart`、`components.ts`、`pubspec.yaml` 或 `package.json` 的 `exports`）；找不到明確匯出檔時退路為 `step-2-path-c-code-extraction.md` 路徑 C 步驟 1 的元件盤點結果——被至少一個**頁面**（定義見下）import 的 public widget 檔案所在目錄視為事實上的元件庫範圍，並建工具票補齊匯出宣告。**退路的「頁面」判定不得循環引用匯出入口本身**（頁面＝入口外的檔案、入口＝被頁面 import 的檔案會互相定義）：退路改以路由註冊點引用的檔案為頁面——找專案的路由表或導覽宣告（如 `routes.dart`、路由設定檔中的 builder／component 對映）逐項列出的檔案，這些檔案即頁面，其餘檔案依上述退路歸類 |
