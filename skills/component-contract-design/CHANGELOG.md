**Version**: 1.7.0 — 補兩條與規格範本同批新增的條文，兩條都處理「程序層知道而範本層才剛寫下」的落差。`mode-c.md` 步驟 6 補〈契約值不變的實作偏離不走漂移判定〉：該步驟原只有「待決」與「漂移」兩態，型別撞名改名、套件版本規避、等價轉換這三類改的是實作方式不是契約值，無處可歸而被歸入漂移，會為一個沒有分歧的情況觸發 PM 裁定；判別問句為「改完之後十一欄位有任何一欄的值不同了嗎」。`dispatch-language.md` 收尾補多票同改一份 spec 的版號處置：各票在自己的分支上都看得到同一個當前版號、都填下一號，撞號因此是常態而非意外，且到合併時才顯現，故版號由合併方決定而非各票自理。兩條的權威在規格範本的〈實作註記〉與〈變更歷史〉，本 skill 為程序側的對應。

**修法選擇的理由值得記**：兩個選項是「刪掉那些行內地址讓宣稱成真」或「改宣稱讓它與實際相符」，本次選後者。依據是 steelman 在 Round 3 挖出的未言明前提——地址表的整套成本論證建立在「行內路徑很貴」這個從未寫出的讀者模型上，而對本 skill 自己宣告的讀者（agent），一條行內路徑幾乎不花成本、一次間接跳轉更貴。既然如此，消費點自帶地址是對的，絕對化的宣稱才是錯的。改為「本表是地址的權威——消費點就近帶一句路徑是允許的，但不得與本表衝突，衝突時以本表為準」。

這也是整個地址表機制在四輪中的收斂點：它的價值不在「唯一住址」（那個絕對化在建表當下即破，且守不住），而在「有疑問時有一處可查、且該處說了算」。

**體量**：第 6 條的表格使 SKILL.md 觸及 6,612 超出門檻，故將〈外部資產與跨檔用詞的地址〉外移為 `references/addresses.md`。判準是它屬逐次查詢的表——讀者只查當下需要的那一格、不是每次全讀，與三種模式互斥同理。此舉併帶解消 steelman 指出的一個矛盾：檔頭假設讀者可能不經 SKILL.md 直開 reference，而表卻只在 SKILL.md，兩個假設不能同時無條件成立；移出後所有 reference 地位平等。SKILL.md 現 4,960 字元（門檻 76%），只剩三種起點、按需讀取、契約齊全的定義——即路由與判準，回到拆分當初的設計意圖。

**本輪的必查對象是 v1.3.0 自己建的地址表**——skill 明訂「前幾輪採納的替代結構是這一輪的必查對象」，因為它的豁免來自它修掉的那份清單，重問殺死前任的問題驗不到它。以它自己的三題驗收，三題全部部分失敗：檔頭承諾涵蓋 15 個受管詞而表僅 8 列（六詞落空，兩個 reviewer 獨立命中）；「元件庫規格範本」列的「是什麼」寫成「填契約的載體」而地址給框架源檔，照字面查表的讀者會去編輯框架資產（實際填的是專案副本）；表內兩處「上節」指錯（表在〈按需讀取〉之後而非〈三種起點〉之後）——位置性指涉的第三次，且這次寫在專為定址而設的表裡；「全文只在該表寫一次」在建表當下即破。

處置：補足六列（前置／狀態矩陣／存在必要性檢視／事故對照／特徵測試／baseline），現 14 列與檔頭承諾對齊、表中無列者歸零；範本列改寫為「產物形狀，實際填寫的是專案 spec 目錄的副本」；「本規格票」地址改為「票號由 PM 於 prompt 或 Context Bundle 指定，未指定時停手回報」；執法工具對非 Dart 專案給可執行動作。為騰出體量，〈分工邊界〉外移為第六份 reference——它是六檔中唯一無任何步驟消費的章節。

**最高價值的一項來自誤用梯度**：這份 skill 對「做了」有規定，對「做過了」沒有留存要求。全六檔共九種佔位標記（待決 19、提案 14、不適用 13、漂移 10、待核定 4、只擋新增 2、待實作／待接線／清理項各 1），而齊全檢查第 1 條只認得「待決」一種；`待核定` 更自稱「視同待決」卻明文不建票，既不被閘門擋也無票承載回補。修法：第 1 條全稱化（一句話關掉八個旁路），並加第 6 條要求本規格票內每個關機判定（起點、形態數、三欄制、零事故、不觸發、補不起）各有一條依據紀錄——關機判定的產物是一句宣告，沒有紀錄則認真做過與完全沒做在票面上無差別。

**個案實跑的兩項**：〈三種起點〉的「起點」欄敘述含資產有無 × 成熟度兩個維度，而「判定訊號」欄只實作前者——契約已齊全的元件庫仍命中 C 列的「元件目錄非空且有呼叫端」，四個個案中兩端各誤判一次。另〈前置〉與〈契約齊全的定義〉替代判準表對「矩陣待簽核時哪些欄標待決」給出不同清單，而該表是 v1.2.0 新增、它正確指出了〈前置〉的缺漏卻只把修正寫在新表，讀者的時序是先讀〈前置〉；已將〈前置〉補上操作機制。

另修：驗收／稽核者無入口（按需讀取五列全以起點或步驟界定，而本 skill 對外承諾的 checkpoint 第一條的判準在 field-questions，該檔何時讀把驗收者排除在外）；十一欄位表順序與方法論〈元件契約判準〉分歧（操作機制與無障礙留在表尾，使「反例最後寫，因為要有相鄰元件可比」這個順序理由在本 skill 這份上不成立），已對齊；排列不變式段被三處具名引用卻無標題也無粗體前導，補前導；v1.3.0 漏修的佔位值段插入句移出窮盡宣稱之間。

**未言明的實作前提（steelman 專項）**：地址表的存在理由寫成「逐處補路徑會使六檔佈滿重複長路徑」，而這個困難不是問題的性質，是一個未寫出的讀者模型帶進來的——對本 skill 宣告的讀者（agent），行內路徑幾乎不花成本而一次間接跳轉更貴，且 skill 喚起時 SKILL.md 本就在 context 內。代價是把「每個引用處自帶路徑」這個本地可檢查的不變式，換成跨檔多對多不變式，後者在建立的同一輪即破。本輪先修實例、保留結構，該前提記入票面待後續評估。
