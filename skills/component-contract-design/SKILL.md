# Component Contract Design

把「這個畫面該用什麼元件、文字要不要換行、按鈕排在一起會不會重疊」這類決策，從畫面實作期前移到元件庫規格。產出是一份 L3 元件庫規格（L3 指專案元件庫章節；L1 通用原則、L2 語言／框架實作規範、L3 的分層見元件庫雙向約束方法論〈分層架構〉）：每個元件十一欄位齊全、每個排列關係有容器元件承載，畫面票因此只剩「選件與排位」。

判準的權威在該方法論的〈元件契約判準〉（十一欄位表、容器亦為元件、派發語言）；產物形狀在 `doc` skill 的元件庫規格範本。本 skill 承載的是**程序**：從三種不同起點走到契約齊全，各起點的步驟不同，判準相同。

## 三種起點

先判定起點，再進對應模式。三種模式共用〈十一欄位填寫問句〉與〈派發語言〉兩節。用詞：**元件目錄**指程式碼中實際存在的元件集合；**元件清單**指規格第 3 章的總表；**元件庫**指統一匯出入口涵蓋的目錄，入口外的任何 widget 檔皆屬頁面層。

| 起點 | 判定訊號 | 模式 |
|------|---------|------|
| 有規格（狀態矩陣、畫面清單），元件庫尚未建 | spec 有逐畫面狀態表（一張全域狀態清單可拆成逐畫面者亦算）；元件目錄為空或只有 scaffold 產生的無呼叫端佔位元件（spec 有無元件清單不影響判定，清單無契約在三種模式都是常態） | A 規格推導 |
| 有設計畫布（artboard、wireframe 的統稱，設計稿為其輸出物；下文簡稱畫布），無規格或規格未到元件層 | 畫布是主要來源；畫面上的視覺單元尚未有語意名（設計工具的自動命名如 Frame 123 視同未命名；設計工具內已有具名元件但無程式碼者仍走 B，具名視為候選名，經語意問句驗證） | B 畫布拆解 |
| 已有元件程式碼與頁面，無契約或契約不全 | 三訊號任一命中即足：元件目錄非空且有呼叫端；頁面直接用原生佈局排列元件；曾發生重疊、截斷、功能補做 | C 程式碼萃取 |

多個訊號同時命中時，以「哪個來源最接近使用者實際看到的畫面」為主，判定不看新舊：有可跑且有頁面呼叫元件的程式碼一律走 C（畫布較新也一樣，畫布上的差異在模式 C 的填契約步驟當作漂移處理），無程式碼有畫布走 B，只有規格走 A。先萃取事實，再對照規格找漂移。三個例外：只有路由殼與佔位元件、頁面尚未呼叫任何元件的專案，模式 C 的呼叫端回收與原生佈局掃描會全空，仍走 A 或 B；已決議整體換版且決策有記錄者，舊碼只供模式 C 的事故對照與呼叫端回收當反例來源，契約值以畫布為準走 B；標記為 spike 且不合入生產的程式碼依方法論的原型豁免不走本 skill，轉正時再走 C。

**前置**：design token 層須已存在（token 指集中定義、程式碼只引用名字的樣式參數；顏色、間距、字級、圓角有具名常數），形態因素矩陣須已定（支援哪些形態的決策表，形態以使用者操作方式界定而非顯示空間：桌機指標加鍵盤、平板觸控、手機單手觸控各為一個形態；位於元件庫規格範本第 1 章；判準見方法論〈形態因素先決〉）。前置缺料的出口一律是建前置票，不在規格票內補：token 缺走 `foundation-design` skill 的 UI 維度，前置票設為本規格票的 blockedBy；矩陣缺先填範本第 1 章作為提案送簽核（範本的「預設單一形態」是提案值，仍須簽核；支援幾個形態屬用戶簽核，PM 不得自行拍板），簽核未回前尺寸契約與測試契約的「每種尺寸」標待決，其餘欄照填。互動反應規格是第三項輸入而非阻擋條件：未產出時建 `ux-design-evaluation` skill 的 UX 審查票，規格票照跑，只有填契約時的互動反應子節標待決並以該票為元件票的 blockedBy。

**時序**：本 skill 在 `version-bootstrap` skill 地基波的第 3 塊（UX 審查）之後、第 4 塊（元件庫實作）之前執行，互動反應規格是它的輸入。規劃波前段的 L3 章節得先只含元件清單與禁用對照，契約於此時補齊。

**多形態專案**：支援多個形態時，畫布拆解與容器盤點按形態分別進行（每形態一套 artboard、一份排列關係表），元件候選與存在必要性檢視跨形態合一；十一欄位中語意與內容角色、變體、狀態集、slot 契約、反例、無障礙的朗讀標籤跨形態共用，操作機制、尺寸契約、內容政策、組合規則、測試契約、無障礙的操作路徑與容器條目每形態各一份；畫面票的 how 帶形態前綴。同一語意可落在不同容器與不同操作機制：導覽項共用，承載它的容器在手機是收合抽屜、在平板與桌機是常駐側欄；數值調整在桌機是拖動滑桿、在手機是步進或輸入彈窗。同形態內不依寬度自動切版：桌機常駐側欄的版型靠視窗尺寸下界與比例約束維持；設計上刻意給使用者選版型（雙欄／單欄）時，那是設定項不是斷點。bottom sheet、drawer、dialog、popover 等覆蓋表面依形態因素矩陣的「覆蓋表面對映」選件，元件的組合規則引用該對映。矩陣另有三個每形態各填一次的維度供欄位引用：回饋通道（手機按鈕被手指遮住，須震動或音效；桌機視覺即可）、最小命中區 token、禁放區與安全區（手機四角與系統手勢區不放可點元件，SafeArea 由框架容器承載）。同形態內的視窗或螢幕尺寸差異不是新形態，由容器的排列不變式承載，不以寬度門檻切版型。

**產出檔案**：複製 `doc` skill 的元件庫規格範本到專案的 spec 目錄，檔名依專案 spec 命名慣例（有編號慣例者用編號，範本檔頭的建議檔名只是預設）。專案已有範本格式的元件庫 spec 者不複製，就地補缺的子節；元件清單散在 design-system spec 或其他 spec 者，新建元件庫 spec 並把原清單改為指向它，清單不雙份維護。

## 模式 A：規格推導

狀態表的「顯示」欄是元件的主要書面來源，因此先從它抽元件候選、再盤容器、最後回填 spec；順序反過來（先想元件再對表）會漏掉只在某一個狀態出現的元件。不在任何顯示欄的頁面框架（導覽、專案切換）從畫面清單與畫布補入。

```
1 收集輸入   逐畫面狀態表、畫面清單、畫布、token 表、互動反應規格（UX 審查產出）。
             畫布缺只用狀態表與畫面清單。互動反應規格的 UX 審查票已開但產出未落檔時，暫以狀態表的退出路徑欄代之並標待決；票未開者走前置出口
2 元件候選   三處來源：狀態表每列「顯示」欄的視覺單元；「可用操作」欄有視覺承載的控制項（搜尋、篩選、取消）；畫面清單與畫布中的頁面框架（導覽項、切換觸發器）。
             跨畫面、跨狀態總是一起出現的單元合為一個元件；有時一起出現的單元是該元件的可選 slot；
             只在單一畫面內共現、各自也能獨立出現的單元不是一個元件，是容器的子件，走步驟 4
3 存在必要性 每個候選問「通用元件 + variant 能否涵蓋」，能 → 併入通用元件的變體。
             退出路徑差異指離開的層級（留在畫面內／離開畫面／離開專案）；只是目的地不同者為 slot，不拆。
             排列型候選（格線、表格、樹、列表、雙欄）逕移步驟 4。與 spec 既有清單衝突時以本步驟為準，回填時標「提案」，PM 核定後去標
4 容器盤點   逐畫面列出每一個佈局結構及其全部子件（含框架層：側欄／主區、工具列／內容），每個佈局結構一個容器候選；「一組」指同一佈局結構下的全部子件，不是兩兩相鄰對。
             判準是方法論〈容器亦為元件〉的判別問句「任兩個元件的相對位置是誰決定的」；模式 A 尚無頁面，答案恆為「尚未有人決定」，所以做的是列舉不是判定。
             單一子件的包裝（Padding／Align／Center 包一個元件）無排列關係，不是容器候選，其內距屬子件的組合規則或所屬容器的格位。
             容器的子件可以是容器；巢狀容器依同一歸併鍵跨層歸併，殼層（側欄／主區）以一個框架容器承載，不再往上遞迴。
             由模式 B 進入者，本步驟以模式 B 的排列關係盤點結果代替，不重列
5 同型歸併   先以「子件類型 + 排列方向」歸併並暫記空間不足策略的假設；步驟 6 填定策略後，策略相同者二次歸併，不依出現的畫面歸併。
             容器的 slot 子件類型須為具名元件清單，填「任意元件」視同原生佈局：一個接受任意子件的水平堆疊等於加了 token 間距的原生列，判別問句形式上滿足但無約束力
6 填契約     用元件庫規格範本，每個元件依〈十一欄位填寫問句〉逐欄填；容器另填排列不變式（不重疊／最小間距／空間不足策略，問句見〈十一欄位填寫問句〉末段）
7 完整性檢查 對照〈契約齊全的定義〉；判準 2 的排列關係清單即步驟 4 的候選表，逐列核對。不齊全的元件不得被畫面票引用
8 回填與建票 元件清單回填 L3 章節所在的 spec 檔；每元件、每容器各一張元件票（粒度與合併條件見〈派發語言〉）；畫面票以 blockedBy（ticket 系統的前置依賴欄位）指向元件票——畫面票若先於元件票開出，實作者會在缺件時就地自製。
             畫面票已開者或元件票已先於契約存在者：改寫由 PM 執行（補 blockedBy、把 how 改寫為〈派發語言〉句型、依〈契約齊全的定義〉投影回填 acceptance、一票多元件者依粒度規則拆分）；
             執行者不得編輯非派發範圍的既有票，於本票 NeedsContext 列出應改內容
```

**元件候選（步驟 2）的常見遺漏**：狀態表的「顯示」欄常寫成句子（「顯示訊息與一顆前進按鈕」），名詞抽取要抽到能對應一個視覺單元為止——「訊息 + 前進動作」跨六個畫面總是一起出現，是一個空狀態元件，不是「文字」與「按鈕」兩個。判斷粒度問「這組單元跨畫面、跨狀態會不會總是一起出現」。

**存在必要性（步驟 3）的方向**：先假設能併，找不到併不進去的理由才立特化元件。判準是方法論〈命名與通用元件判準〉的「能否命出設計目的」：理由須為語意或行為差異（內容角色不同、退出路徑不同、語氣不同），外觀差異不構成理由。實測案例：空狀態與阻擋狀態外觀相近，但空狀態說「這裡目前沒有內容」、阻擋狀態說「這個專案不適用」，退出路徑不同，因此是兩個元件。

**同型歸併（步驟 5）的方向**：一個按鈕列在七個畫面出現七次仍是一個容器元件；子件從按鈕變成徽章時，若排列方向與空間不足策略相同，仍是同一個容器，slot 的具名子件清單加一項。歸併過頭的訊號是排列不變式填不出單一值，或 slot 子件清單長到只能寫「任意」。

## 模式 B：畫布拆解

畫布上只有畫素，沒有語意。本模式的核心工作是把視覺單元**命名成語意**，再進模式 A 自存在必要性起的步驟。

```
1 視覺單元盤點  逐畫面框出每個可獨立辨識的區塊；相同外觀的區塊先各自列，不預設同型
2 語意問句      每個區塊問：使用者看到它預期能做什麼？它承載標題／內文／標籤／數值／動作哪一種？
3 同型歸併      語意相同者歸併為一個元件，外觀差異降為 variant；語意不同而外觀相同者不歸併
4 排列關係盤點  逐畫面記錄區塊之間的排列（並排、堆疊、格線）與間距實測值 → 容器候選（模式 A 步驟 4 以此表代替）
5 進模式 A      自存在必要性檢視起
```

**同型歸併（步驟 3）的反向陷阱**：畫布產生器常給語意不同的單元相同外觀（同一個圓角卡片放專案摘要也放錯誤訊息）。以外觀歸併會把兩種語意塞進一個元件，之後靠參數分岔。判斷用語意問句（步驟 2）的答案，不用畫素。

**排列關係盤點（步驟 4）與 token 的關係**：間距實測值歸納為 token 階屬 token 萃取（`foundation-design` skill 接手模式的「盤點 → 命名」與其「萃取不等於照抄」案例），本步驟只記錄「哪兩個區塊之間有間距」，值引用已萃取的 token 名；token 未萃取時先停下走前置。

**畫布漂移**：畫布為準只限視覺值（圓角、間距、字級、顏色）：規格寫圓角 10、畫布量到 7，以畫布為準並更新規格，畫布是視覺決策的產物。行為、狀態、退出路徑的差異（規格有「切換專案」動作而畫布沒畫）以規格為準，標漂移待決送 PM，不從規格刪除。契約填寫時引用 token 名而非數值，視覺漂移只需改 token 表一處。

## 模式 C：程式碼萃取（接手既有專案）

接手的元件庫常見兩種病：有元件無契約（行為散在各呼叫端），與有元件無容器（頁面用原生佈局排列元件，違反方法論工程端的「禁自製元件」判準）。本模式先盤點事實再補契約，順序與 `foundation-design` skill 的接手模式一致：盤點 → 命名 → 固化 → 補文件。

```
1 元件盤點     列出元件目錄的每個 public widget（一檔多 class 各算一個；非 widget 的 helper 不算元件，誤入匯出入口者記為清理項），與 spec 元件清單對帳：
             目錄有清單無者補入清單，清單有目錄無者標「待實作」或刪除（PM 核定）。
             每個元件對照〈十一欄位填寫問句〉的每一個問句（不是每一欄）標三態：已定義於程式碼 / 隱含於呼叫端 / 空白；一欄內混合三態屬正常。
             零呼叫端的元件仍屬本模式的元件，標「待接線」，其「隱含於呼叫端」態不成立，只在另兩態間標
2 呼叫端回收   「隱含於呼叫端」的欄位（如 maxLines、overflow 在頁面設定）回收進元件契約；呼叫端的設定值不一致時填提案值附各處證據並標「待核定」，PM 核定前視同待決，不另建決策票。
             另三種形態：呼叫端繞過 slot 自組內容（在 child 裡自己排 icon 與文字）→ 記為 slot 契約缺口，提案新 slot 或收窄型別；
             spec 有而程式碼無（spec 的變體多於實作）→ 反向漂移，標「待核定」由 PM 裁定補實作或刪 spec；元件與呼叫端都沒設（雙空）→ 標空白，於步驟 6 處理
3 原生佈局掃描 grep 頁面層的佈局原語（依框架：水平／垂直堆疊、彈性盒、格線），只算包兩個以上元件庫元件的位置；中間只隔佈局輔助（Expanded／Flexible／Padding／SizedBox／Align）仍算直接包，中間隔另一個元件庫元件則不算。
             頁面層含 feature 目錄下的 sheet／dialog／card 等區域 widget（不在統一匯出入口即頁面層）；每頁的根堆疊也算，同型歸併為「頁面區塊堆疊」框架容器。每處問判別問句
4 容器候選     判別問句答「頁面」處 → 容器候選；依模式 A 的同型歸併規則歸併。
             同一排列關係在存量中策略不一致（同是對話框動作列，有的不處理、有的換行）→ 一個容器候選，策略欄填提案值附各處證據標「待核定」，不拆成兩個容器；
             資料驅動 N 列的堆疊（列表、明細）是容器候選，只在 Troubleshooting 的計數門檻中排除
5 事故對照     既有的重疊、截斷、點不到事故逐一對應到缺哪個容器或哪個空白欄位；對不上的事故是新發現，另建分析票。
             零事故的專案本步驟為空，步驟 7 的容器優先序改依呼叫處數量（出現最多的排列關係先建）
6 填契約       用範本填十一欄位；行為類欄位（狀態集、內容政策、尺寸契約、組合規則）的值以既有測試與呼叫端行為為證據，無證據者標「待決」並建決策票，不猜；
             語意與內容角色、變體、反例由存在必要性檢視推得，不需程式碼證據
7 缺件建票     容器元件優先（重疊事故的根因在此），其次空白欄位補實作；存量頁面遷移按 feature 目錄拆票（句型見〈派發語言〉遷移票）——一票跨多個目錄會撞認知負擔閾值且互相阻塞。
             「只擋新增」的 baseline 落在執法工具的白名單設定；工具無目錄級白名單者記於決策文件；工具不存在者建工具票列為遷移票 blockedBy
```

**呼叫端回收（步驟 2）的判準**：呼叫端設定值不一致是契約缺內容政策的訊號。同一個元件在三個頁面被設成三種 `maxLines` 時，執行者選一個值作提案並附三處證據，PM 於契約票驗收核定後其餘兩處改為引用元件預設；差異若是語意的（標題一行、內文三行），那是兩個內容角色，拆元件。

**原生佈局掃描（步驟 3）的框架對應**：Flutter 找 `Row` / `Column` / `Wrap` / `Flex` 直接包兩個以上元件庫元件的位置；Web 框架找頁面元件內的 flex / grid 容器；原生佈局出現在元件庫內部（統一匯出入口涵蓋的目錄）屬正常，容器元件自己就是用它實作的；入口外的 feature 目錄下的自製 widget 屬頁面層，一併掃。

**填契約（步驟 6）的證據順序**：既有測試 > 元件自身實作 > 呼叫端一致的設定 > spec 的結構化表格 > 畫布 > 規格散文。既有測試常是原作者意圖唯一的書面殘留；規格散文最容易與程式碼漂移。元件實作與 spec 表格衝突時（程式碼尺寸 64 而 spec 寫 36）：行為類欄位以實作加測試為準填入並標「spec 漂移」，spec 為近期且有決策記錄者反過來標「實作漂移」，兩者都由 PM 於驗收核定，執行者不自行選邊。

**特徵測試閘門**：回收呼叫端設定進元件會改變頁面行為。覆蓋不足時先補特徵測試（不驗「應該是什麼」，只把現況行為原樣鎖住，改動一旦改變行為就紅燈）鎖住現況；規模補不補得起來由 PM 於票面裁定，執行者只提報覆蓋數字；裁定為補不起時只在有覆蓋的模組內回收，其餘標「只擋新增」。判準與規模閘門見 `foundation-design` skill 的接手模式。

## 十一欄位填寫問句

每欄一個問句，答不出來的欄位即為空格；空格的處置是找來源，不是猜。來源不可得（決策者不可得、前置資源未產出、合併與否無人拍板）時三種模式共用同一出口：該欄標「待決」並建決策票或前置票，設為元件票的 blockedBy；存在必要性檢視的合併結論由 PM 於契約票驗收核定。

合法的佔位值只有兩個：「待決」是缺答案，「不適用」是答案，兩者不可互代。「不適用」限該欄對此元件結構上不存在時使用（無變體、狀態集只有 enabled、無 slot、無文字），須附一句理由，且只允許於變體、狀態集、slot 契約、內容政策、反例、操作機制（純顯示且無任何互動的元件）六欄；尺寸契約、組合規則、測試契約、無障礙不得填不適用（純顯示元件的無障礙至少有朗讀標籤與焦點路徑），空間不足策略的合法替代值是「不觸發 + 公式」。「見設計稿」「同上」「TBD」等未落成值的寫法視同空白。i18n key 已宣告而譯文未到者，內容政策填 key 即齊全，測試契約以當時資源檔的值執行，譯文更新後的重測屬 i18n 票驗收，不回退契約狀態。方法論〈分層架構〉最小適用集生效的小型專案，十一欄位縮至語意與內容角色／尺寸契約／內容政策三欄，排列不變式不裁。

| 欄位 | 填寫問句 | 常見空格與來源 |
|------|---------|--------------|
| 語意與內容角色 | 使用者看到它預期能做什麼？它放的是標題／內文／標籤／數值／動作？什麼情境不該用它？ | 「何時不用」常空白；來源是相鄰元件的語意差異。複合角色（內文 + 動作）並列寫出，每個角色對應一個 slot |
| 變體 | 同一語意有幾種行為不同的形態？各自的外觀與行為差在哪？ | 以外觀值命名（藍色版）；改以語意命名（primary / confirm / danger） |
| 狀態集 | 它自身可以處於哪些狀態？每個狀態怎麼顯示、能做什麼、怎麼進、怎麼出？ | 只列元件自身的狀態（enabled／loading／error 等），畫面級的進出由呼叫端的畫面狀態表承載；退出路徑空白即死胡同；四欄填法見 `ux-design-evaluation` skill 的狀態矩陣 |
| 尺寸契約 | 它自己決定大小還是填滿父容器？最小多小、最大多大？可點元件的最小尺寸有沒有達到該形態的最小命中區？每個形態各一份，同形態內每種測試尺寸下怎麼變？ | 「每種測試尺寸」常只填預設尺寸；最小命中區常沿用桌機值搬到手機；形態、測試尺寸集合與命中區 token 的來源是元件庫規格範本的形態因素矩陣節（判準見方法論〈形態因素先決〉） |
| 內容政策 | 每個文字位置可不可以換行？最多幾行？超出時截斷／淡出／縮放／換行？最長的測試文案是什麼？ | 最長測試文案常空白；來源是專案 i18n 資源檔（Flutter 為 ARB）中該 key 各語言的最長值，排除未翻譯的 fallback（與來源語系字串相同者）；語系少於三種時另加一條人工的長文案。無文字 slot 的元件填「不適用」 |
| slot 契約 | 呼叫端能放什麼進來？每個位置接受什麼型別？文字從哪來？ | 文字來源常寫死；規則見方法論〈元件文字歸屬〉。容器的子件 slot 須寫具名元件清單與數量上限，策略欄只引用此處的上限 |
| 組合規則 | 它可以放進哪些容器？哪些區域不得放它（該形態的禁放區）？對齊基準是什麼？當它是表格或列表的一欄時佔多寬、內距多少？ | 「可放入的容器」填「任何地方」即等於允許頁面原生佈局；須列具名容器。可點元件的禁放區引用形態因素矩陣（手機四角、系統手勢區）。根層框架容器填「根：無父容器」並承載該形態的安全區 |
| 測試契約 | 一支測試能不能一次看到全部變體與狀態？每種尺寸都不溢位？最長文案照內容政策處置？ | 只測預設尺寸與短文案；測試形態（golden / widget）定於 L2，L2 無此條時以範本測試點的 widget test 為預設並建 L2 補條目票。測試基座（讓元件在各視窗尺寸下可渲染與斷言的測試工具與 fixture）由 `foundation-design` skill 的測試維度承接 |
| 反例 | 什麼情境會有人誤拿它來用？該改用哪個相鄰元件？ | 常空白；來源是存在必要性檢視時被否決的合併理由 |
| 操作機制 | 這個形態的使用者用什麼動作完成它的任務？任務要多精確？該形態的輸入做得到嗎？做不到時給什麼替代機制？按下後走哪個回饋通道？ | 常直接沿用畫布的手勢（桌機拖動滑桿搬到手機）；每形態各答一次，精度不足時填替代機制（步進按鈕、輸入彈窗）；回饋通道引用形態因素矩陣（手機須觸覺或聲音，手指會遮住按鈕）；輸入形式判準見 `ux-design-evaluation` skill 的輸入機制 reference |
| 無障礙 | 輔助技術會把它唸成什麼？值或狀態變了怎麼播報？不靠顏色能不能分辨？鍵盤或輔助技術怎麼走到它、怎麼操作它？ | 常空白或只填對比；朗讀標籤與播報跨形態共用，操作路徑每形態各一份；不得填「不適用」 |

範本子節與十一欄位不同名者三處：狀態集＝範本的「狀態矩陣」、測試契約＝「測試點」、語意與內容角色＝條目標頭三行；完整對應表在範本檔頭註解。

容器元件另答排列不變式三項（不重疊／最小間距／空間不足策略）各一問：子件邊界盒在每種尺寸與數量上限下是否兩兩不相交（不重疊）？相鄰子件的最小間距是哪個 token（最小間距）？空間不足時換行、捲動、收合選哪一個、什麼條件觸發（空間不足策略）？子件有數量上限（上限先寫進 slot 契約）且最小視窗保證放得下者，策略填「不觸發：上限 N，最小視窗下 N × 子件最小尺寸 + (N−1) × 最小間距 ≤ 可用空間」，公式即不重疊的測試斷言。

範本中十一欄位以外的章節，來源與填寫者如下；它們不在〈契約齊全的定義〉內，但屬 spec 票的驗收範圍（範本第 9 章）。

| 範本章節 | 來源 | 填寫者 |
|---------|------|-------|
| 第 1 章形態因素矩陣 | 專案的裝置與視窗決策；版型拆分屬用戶簽核 | PM 提案、用戶簽核 |
| 第 2 章狀態綁定模式 | 專案的狀態管理選型（技術決策記錄） | PM |
| 逐元件「互動反應」「a11y」 | UX 審查產出的互動反應規格；新抽出的元件不在其中者標待決並建 UX 審查補票 | 規格撰寫者抄錄，不自行設計 |
| 逐元件「使用 design token」「i18n」 | token 表、i18n 資源檔 | 規格撰寫者 |
| 原生元件禁用對照表 | 方法論工程端判準 + 執法工具的偵測 pattern | 規格撰寫者 |
| 豁免清單 | 方法論豁免三條件 | 執行者提案、PM 於票驗收核可 |
| 跨平台命名契約 | 同一 design token 系統被多端使用時才填；判準見方法論〈多端共用 design-system 的跨端契約〉 | PM |

## 契約齊全的定義

一份元件庫規格可被畫面票消費，須同時滿足五條：

- 每個元件十一欄位無空白；標「待決」的欄位視同空白，該元件不得被畫面票引用，決策票設為元件票的 blockedBy
- 元件清單總表中每個畫面的每個排列關係都對應到一個容器元件
- 每個容器的排列不變式三項齊全，子件數量無上限者空間不足策略非空
- 每個文字 slot 的最長測試文案是具體字串或 i18n key，不是「長文字」
- 每個元件的無障礙欄有朗讀標籤與焦點路徑，每個有互動的元件在每個形態各有一份操作機制

五條都是存在性檢查，可機械執行（欄位為落成值或合法的「不適用」、每個排列關係有容器、三項非空、文案是字串或 key、朗讀標籤與操作機制非空）。文案放不放得下不在此判定，由測試契約的測試驗證。未齊全的元件不得被畫面票引用；元件票的驗收條件即上列四項對該元件的投影。本節四條是「可被畫面票消費」的判準；spec 票本身的驗收權威是範本第 9 章，四條是其子集。

契約先於實作指「改動先落在契約」，不指契約不可變：實作中發現契約值不成立（策略選錯、尺寸公式不成立）時，先改契約條目再改實作，變更理由記入該元件票的 acceptance 修訂或 spec 變更歷史。

## 執行者與簽核者

| 動作 | 執行者 | 核定者 |
|------|--------|-------|
| 撰寫元件庫規格（三種模式） | 工具清單含 Write／Edit 的設計類代理人，或 PM；只有唯讀與符號級工具的代理人寫不了 spec 檔，不派 | PM 於 spec 票驗收對照〈契約齊全的定義〉與範本第 9 章 |
| 建元件票、畫面票、遷移票、決策票 | PM，或工具清單含 Bash 的執行者；欄位語意與指令見 `ticket` skill（blockedBy、parent、spawn request） | — |
| 改寫既有票（補 blockedBy、回填 acceptance、拆分） | PM；執行者於 NeedsContext 列出應改內容 | — |
| 存在必要性的合併結論、呼叫端回收的選值、特徵測試規模裁定 | 執行者提案並附證據 | PM |
| 版型拆分、豁免 | 執行者提案 | 版型拆分用戶簽核；豁免 PM 於票驗收核可 |

## 派發語言

契約齊全後，畫面票與元件票的寫法固定。寫不成這個形式即為缺件訊號。畫面票的 acceptance 句型、反例與缺件處置定於方法論〈派發語言〉，本節只補程序層的句型。

**畫面票**：

| 欄位 | 句型 |
|------|------|
| how | 逐狀態列「狀態 X：容器 Z 第 N 格放元件 A 變體 a、第 N+1 格放元件 B 變體 b」，狀態來源指向狀態矩陣。寫不成這個形式時停手建元件票、設為畫面票的 blockedBy |
| acceptance（與方法論〈派發語言〉同文） | 「頁面檔的元件 import 只來自元件庫的統一匯出入口」（無 import 邊界的宿主改用方法論〈Web/HTML 端 L2 特別判準〉的不並存斷言）；「狀態矩陣每列都以契約內的元件組成」。不得追加「不溢位」「畫面正確顯示」：不溢位由元件票的測試契約承載，畫面票不重驗 |

**元件票**。粒度規範的是 acceptance 的投影單位，不是排程單位：一票一元件或一容器；多張元件票可掛同一張 parent 傘票分 wave 派發；變體與狀態集皆「不適用」的原子元件（分隔線、留白）得合併為一票，acceptance 仍逐元件投影；既有的多元件票拆分，已 claim 且實作中的票拆不動時，acceptance 以「符合 spec 條目 {編號} 的十一欄位」一條加測試契約一條代替逐欄投影：

| 欄位 | 句型 |
|------|------|
| what | 「建立元件 A：{內容角色}，變體 {清單}」或「建立容器 Z：子件 {具名清單}，方向 {並排／堆疊}，空間不足 {策略}」 |
| acceptance | 十一欄位對該元件的投影各一條；容器加排列不變式三項（不重疊／最小間距／空間不足策略）各一條；測試契約一條（全變體全狀態、每種尺寸、最長文案） |
| blockedBy | 填 ticket ID，不填資產名：產出 token 表、i18n 資源、互動反應規格、測試基座的票，待決欄位的決策票；容器票另列其子件元件票；資產已存在且無票者不列 |

**遷移票**（模式 C 存量頁面）：

| 欄位 | 句型 |
|------|------|
| what | 「將 {feature 目錄} 頁面層的原生佈局改為容器 {Z}，元件設定回收至契約」 |
| acceptance | 「該目錄頁面層零原生佈局原語直接包兩個以上元件庫元件」（執法工具不偵測佈局原語者，以模式 C 步驟 3 的 grep 驗收）；「元件 import 只來自統一匯出入口」；「baseline 已縮減該目錄」（baseline 形態依執法工具而定：有目錄級白名單者移除該目錄；無者 baseline 範圍記於決策文件，同 `foundation-design` skill 接手模式的規模閘門處置） |
| blockedBy | 容器 Z 的元件票、特徵測試補齊票（覆蓋不足時）、執法工具票（工具不存在時） |

事故對照對不上的事故（不對應任何缺件或空白欄位）建分析票，不建元件票。

## Examples

**規格推導（新專案）**：一份 spec 列 29 個畫面狀態，其中空狀態出現 6 次、阻擋狀態 3 次。元件候選步驟抽出兩個候選，存在必要性步驟問能否合併：外觀相近，但退出路徑不同（空狀態導向新增，阻擋狀態導向切換專案），不合併。容器盤點掃七個畫面，側欄六個導覽項、清單卡的列表、徽章列各是一個排列關係，得三個容器候選。

**畫布拆解**：畫布產出九份 artboard，圓角卡片出現在內容摘要、錯誤提示、統計數字三處。語意問句得三個答案（內文、錯誤、數值），同型歸併不歸併，圓角降為三者共用的 token。排列關係盤點量到七種間距值，記錄排列關係後停下，值的歸納交回 token 萃取。

**程式碼萃取**：一個專案有十個通用元件與三版型零溢位測試，仍發生按鈕重疊。原生佈局掃描掃到頁面用水平堆疊排列三顆元件庫按鈕，判別問句答「頁面」，事故對照把重疊事故對應到「缺按鈕列容器」而非任何按鈕的缺陷。元件票只建一張容器，三個 feature 目錄的遷移各一張。

## Troubleshooting

| 症狀 | 原因 | 處置 |
|------|------|------|
| 十一欄位填到一半發現元件該拆 | 存在必要性檢視併過頭，一個元件承載兩種內容角色 | 拆為兩個元件，原元件的反例欄互相指向 |
| 容器候選數量爆炸 | 同型歸併依畫面歸併而非依「子件類型 + 方向 + 策略」，或「一組」讀成兩兩相鄰對 | 重跑歸併；排除資料視圖本身（格線、樹、表格、泳道各算一個）後仍逾十個，回頭檢查歸併鍵是否混入畫面名 |
| 最長測試文案填不出來 | i18n 資源尚未涵蓋該 key | 走 i18n 前置票並設為元件票 blockedBy；契約該欄標「待決」，該元件在補齊前不得被畫面票引用 |
| 畫面票寫不成「容器 Z 第 N 格」 | 缺容器或缺元件 | 停手建元件票，不在畫面票內設計 |
| 接手專案的同一元件在各頁設定不一致 | 契約缺內容政策或尺寸契約 | 模式 C 呼叫端回收；語意差異則拆元件 |
| 執法工具全綠仍出現重疊 | 工具只掃元件層，組合層無契約 | 模式 C 的原生佈局掃描與容器候選；不以 lint 取代容器契約 |
| 元件票實作中發現需要契約外的新元件 | 元件候選盤點漏抽，或畫面狀態新增 | 停手：補契約條目（走待決出口或直接填齊）並登記 spawn request 建元件票（登記與落地規則見 `ticket` skill，停在 pending 不算落地），不就地實作；「清單不宣稱窮盡」指清單可增補，不指可先做後補契約 |
