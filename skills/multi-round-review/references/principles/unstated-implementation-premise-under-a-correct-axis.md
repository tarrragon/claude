# 軸是對的，而它底下有一個從未被當成選擇的實作前提

> **角色**：本卡是 `multi-round-review` 的支撐型原則（principle）、被 Round 3-B 的 steelman frame 與個案實跑 frame 引用。
>
> **何時讀**：規劃對抗性審查的時候（要知道 steelman 有一塊天生打不到的地方）；或是審查一套判準時發現它的推導每一步都對、結論卻很費力的時候。

## 核心原則

**一套判準可以建立在正確的軸上，而它底下有一個實作前提從未被當成選擇。**

前提不是論點，因此它躲得過所有針對論點的檢驗：對抗性審查找論點的反例、事實審查查論點的來源、斷言審查問論點的支撐——三者都預設了「要被檢驗的東西已經被說出來」。沒說出來的那個不在檢驗的射程裡。

這跟「承重論點沒被驗證」是不同的失效。那裡缺的是對一個已經說出口的主張做檢驗；這裡缺的是把一個沒說出口的選擇變成可檢驗的東西。前者的修法是驗證，後者的修法是**先讓它顯形**。

## 可辨識訊號是費力

推導每一步都對，結論卻需要一整套機制去繞開某個困難；而那個困難在換一種實作形態之後不存在。

費力本身不是缺陷（真實的取捨常常費力），但它值得一次追問：這個困難是問題本身的性質，還是選定的容器帶進來的。

實測形態：一章要處理「維度乘積會爆」的成本問題，發展出一整套分層加取樣窗口的設計，每一步都成立——而整套是多餘的，因為那個成本問題由「用時間序列實作」這個從未寫出來的假設造成，換一種資料結構就不存在。該章從頭到尾沒有提過這個選擇，它不是被論證後選定的，是預設的。

## 為什麼專業經驗讓它更難被看見

熟悉一個領域的人在該領域的語境下會自動選定實作形態，而自動的那一步不會留下決策的痕跡。這些聯想多數時候是對的，而正因為多數時候對，它們不會被拿出來檢查。

對該領域不熟的人會在這一步停下來問「這要存在哪裡」，而那個問題正是把前提顯形的動作。這解釋了為什麼外行的第一個問題有時會擊中內行的盲點——它擊中的不是知識缺口，是被自動化掉的那個選擇。

## 對 reviewer prompt 的要求

對抗性審查的 prompt 若只寫「找反例、推翻框架」，reviewer 會在論點層打轉。要抓到這一類，prompt 要多一條指示：

> 除了挑戰說出口的主張，另外找**沒說出口的實作假設**：這套判準假設東西存在哪裡、用什麼形式存、誰來查詢它？這些問題在文中答得出來卻沒有被寫成一個選擇時，就是未顯形的前提。特別注意結論很費力的地方——一整套機制存在的理由若是「否則會很貴／很慢」，先查那個困難的來源。

## 修法：讓前提顯形而非換掉它

修法不是換掉那個前提——原本的選擇可能仍然正確。修法是把它從隱含變成明示，讓讀者知道判準的適用範圍。

副產物是內容變短、判準變硬：**前提顯形之後，為了繞開它而長出來的結構會自己脫落。**

## 判讀徵兆

- 推導成立而結論費力，且那套機制的存在理由是「否則會很貴／很慢／很難維護」。
- 一個實作名詞從頭到尾沒有出現過，而全篇都在它的約束下推導。
- 判準有一個需要單獨處理的例外——例外常常是前提在特定情況下不成立的痕跡，把前提換掉之後例外會併回主線。
- 成本論證用了一個沒有換算過的量級，且沒標明它在哪種實作下成立。
- 領域內的人讀完覺得順、領域外的人第一句就問「為什麼不用某某」。
