# 修法沒有寫進檔案，而同一輪的無關改善替它簽了名

> **角色**：本卡是 `multi-round-review` 的支撐型原則（principle）、被〈整合 finding 跟 fix〉的修法落地段引用。
>
> **何時讀**：一項處置判定生效結案、兩輪之後同一個位置復發時；或準備把一輪的量測改善歸給其中某一條處置時。

## 核心原則

**一項修法有沒有寫進檔案，與那一輪的量測有沒有改善，是兩件獨立的事。** 紀錄說修了、量測說好了，兩者互相背書，而它們中間缺的那一步——修法有沒有真的落在目標檔上——流程裡沒有任何一處會問到。

兩個各自都不罕見的成因，湊在一起才產生這個形態：

**變更紀錄照修改計畫寫，而不是照實際的 diff 寫。** 寫紀錄的人手上有一份逐條的計畫，於是逐條謄完。批次套用的腳本對其中一條回報了零筆命中，而那個回報沒有進到寫紀錄的那一步。

**量測項與處置項不是一對一。** 一批修改通常含多項，而探針量的是位置、不是處置。實測那一輪的零命中來自同批另一項新增的定義表，與宣稱的那條處置無關。

## 一批多項時，改善只能歸給整批

把紀錄與量測分開查這件事有一個直接推論，而它一般得多：**同一輪套用了多項修改時，量測的改善不能歸給其中任何一項。** 要把改善歸給某一條，那一條得是該輪唯一的變項。

所以修法紀錄的兩種寫法效力不同。「本輪套用了這幾項，量測從命中轉為零命中」是可以成立的陳述。「這一項讓命中歸零」是一個歸因宣稱，它要求單變項，而一批多項時那個條件不成立。

## 判定生效之後復發，第一件事是回查 diff

復發的時候，最順的解釋是修法設計得不好——上一輪的做法沒切中，這一輪換一個。那個解釋順到不需要查證，而它會讓人重新設計一個從未被試過的修法。

更貴的一層代價在紀錄上：那個從未被試過的修法會被記成「試過而無效」，於是下一次遇到同型缺陷時，正確的做法已經在清單上被劃掉了。

**順序是先回查再重新設計**：取那次提交實際動到的檔案清單，確認目標檔在裡面。成本是一條指令，而它排除的是整輪的白工。同一條也適用在提交之前——紀錄裡提到的每個目標檔，與這次實際暫存的檔案清單逐條對照（`git diff --cached --name-only`）。

## 判讀徵兆

- 一項處置判定生效結案，而同一批還套用了其他修改
- 變更紀錄的條目與那次提交的檔案清單沒有逐條對照過
- 批次套用的工具對某一條回報了零筆命中，而紀錄照樣寫上了那一條
- 同一個位置在判定結案的兩輪之後復發
- 檢討時第一個浮現的解釋是「上一輪的修法設計得不好」
