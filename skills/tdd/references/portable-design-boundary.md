# 可攜式 TDD 流程設計邊界

本文件定義 TDD 流程的 Layer 1（通用/可攜式）和 Layer 2（框架特定）邊界，用於指導 `/tdd` SKILL 的設計。

> **目標**：將本專案的 TDD 流程標準化為可攜式工具，讓其他工程師在別的專案也能直接使用。

---

## 設計邊界總覽

```
TDD 流程架構
├── Layer 1（通用知識，任何專案可用）
│   ├── Phase 定義和目標
│   ├── 階段轉換條件
│   ├── TDD 原則和模式
│   ├── 品質基準
│   └── 任務類型豁免規則
│
└── Layer 2（框架特定，依賴本專案基礎設施）
    ├── Ticket 系統整合
    ├── Hook 系統觸發
    ├── Agent 派發規則
    ├── Commit 管理
    ├── 決策樹路由
    └── 狀態管理 API
```

## 可攜式約束規則（Layer 1 不可引用）

**作用域是全部會被同步出去的內容**：`SKILL.md`、`references/` 底下每一份（含子目錄）、`CHANGELOG.md`。一次可攜性閘門掃描的 20 條違規裡 18 條落在「`references/phase{N}/rules.md` 的非 blockquote 區域」這個舊作用域之外，在字面規則下不算違規。


| 禁止項                 | 說明                                 | 替代方式                       |
| ---------------------- | ------------------------------------ | ------------------------------ |
| `/ticket` CLI          | 如 `/ticket create`, `/ticket track` | 「任務系統」「狀態管理」       |
| 具體 agent 名稱        | lavender, parsley, sage 等           | 「設計者」「實作者」「測試者」 |
| 專案的 hook 系統  | 檢查點自動化                         | 「驗證機制」「檢查點」         |
| `decision-tree` 路由   | PM 決策邏輯                          | 「階段轉換」「路由決策」       |
| `/parallel-evaluation` | 本專案多視角工具                     | 「多維度分析」「交叉審查」     |
| 本專案路徑             | `.claude/`, `docs/` 等               | 「規則目錄」「工作目錄」       |
| Wave、Patch 概念       | 本專案版本語義                       | 「執行批次」「版本」           |

## 需要引用消費端的東西時，三種合規的出路

上面的替代方式表只涵蓋「換成中性名詞」，而它處理不了「我真的要說這條規則來自哪裡」。缺了出路的禁令會被繞過，因為違規是唯一做得到那件事的寫法。三種出路按情形選：

| 情形                                                     | 出路                                                              | 判斷標準                                                       |
| -------------------------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------- |
| **出處引用**：規則內容已寫在句內，路徑只說它來自哪       | 行內標 `<!-- portability-allow: 理由 -->`                        | 把路徑整條刪掉，讀者還做得到這件事嗎——做得到就是出處引用 |
| **真依賴**：值、表格或清單不在句內，讀者得開那個檔才判得了 | 改寫成「該專案自訂」並說明歸屬，本框架的位置放進標記              | 那個值換一個專案會不會不同——會就不該寫死                 |
| **Layer 2 段落**：整段在描述本框架的檔名、schema、CLI    | 移進 `references/project-integration/`，Layer 1 留語意並標記指過去 | 換一個專案這一段要重寫幾成——過半就移走                   |

實例三則，各對應一種：

- 出處引用：「時間相關斷言遵守 X 規則 D1：連續觸發與等待窗口內的檢查一律以固定影格推進驗證」——冒號後面就是完整規則，路徑刪掉不影響執行
- 真依賴：「紅燈票超出任務拆分閾值（見 X 閾值表）時」——閾值不在句內，改寫成「超出該專案訂的閾值時，閾值住在各專案自己的認知負荷規則裡」
- Layer 2 段落：追溯矩陣的檔名、schema 定義處與消費它的 CLI，三者換一個專案全部不同，整段移進 `references/project-integration/traceability-matrix.md`

`references/project-integration/` 不隨同步傳遞、由各專案自備，所以 Layer 1 指過去的那一句要寫明這件事。

**標記的理由要寫得讓後來的人判得出該不該信。** 寫成類型標籤（「這是必要的」「刻意保留」）就是關機鍵——它對每一條都成立，於是每一條都通過。

## 邊界模糊功能點

### 1. Phase 0 要不要納入？

**現況**：本專案包含 Phase 0
**建議**：Layer 1 包含架構審查原則，Layer 2 可選擇是否納入派發流程

### 2. 3b 拆分評估時機

**現況**：Phase 3a 完成後進行
**建議**：Layer 1 提供拆分決策邏輯，Layer 2 定義時機

### 3. Commit 管理策略

**現況**：Phase 1-3 代理人自治，Phase 3b+ PM 管理
**建議**：Layer 1 提供通用規範，Layer 2 實現角色差異

### 4. Phase 4 豁免條件

**現況**：修改 ≤2 檔案、DOC、單一模組
**建議**：Layer 1 提供判斷標準和決策樹，Layer 2 實施豁免

## 這份教義與實際結構的對應

原本列在這裡的兩個子任務（另建 `portable-tdd-standard.md`、另建 SKILL.md）已經由現行結構承接，不再是待辦：Layer 1 的完整規範分散在 `SKILL.md` 與 `references/phase{N}/rules.md`，SKILL.md 本身就是那個入口。

**還沒有的是一道會擋下來的檢查。** 這份教義與 SKILL.md 的同一段都寫著禁止引用消費端路徑，而兩份都是每次叫用會被讀到的內容，20 條違規照樣長出來——規則被讀到不等於規則被執行。目前唯一會擋的是同步工具的可攜性閘門，而它只在推送那一刻作用；寫的當下沒有任何訊號。推送前自己讀一次閘門的做法在 SKILL.md 的〈自己查，不要等閘門擋〉。
