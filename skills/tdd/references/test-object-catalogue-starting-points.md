# 五、三種起點的推導程序

> **何時讀**：要從零開始建立或擴充測試對象目錄，需要判斷專案現況屬「有規格」「有既有測試無契約」還是「有程式碼無測試」三種起點之一、並依對應步驟推導時。
>
> **同目錄**：入口檔 `test-object-catalogue.md`（單位判定、來源類別、契約欄位表、派發語言句型在此）；姊妹檔 `test-object-catalogue-completeness-criteria.md`（四、齊全判斷標準，本檔起點 A 步驟 A8 執行其機械檢查）。
>
> **溯源**：原為 `test-object-catalogue.md` 的〈五、三種起點的推導程序〉節，補齊範例後全檔超出單檔 token 門檻；三種起點互斥、單一讀者只需其中一種，依讀者任務三問判定外移為獨立檔（搬移程序見 skill-design-guide `references/splitting-an-existing-skill.md`）。

## 起點 A：有規格

適用：專案已有規格 / 使用案例 / 提案文件，可走規格→測試的映射流程。

| 步驟 | 動作 | 產出 |
|------|------|------|
| A1 | 列出所有畫面狀態規格的可驗證條目：每個狀態的每條退出路徑、每條互動行為規則 | 條目清單（畫面狀態轉換、互動規則類別） |
| A2 | 列出所有使用案例場景步驟（主成功 + 替代 + 例外），標明步驟編號 | 條目清單（使用案例行為場景類別） |
| A3 | 從元件庫規格的元件清單總表匯入元件名單，來源欄標對應章節 | 條目清單（元件契約類別） |
| A4 | 從設計 token 規格 + token 定義原始碼匯入 token 不變式 | 條目清單（Token 不變式類別） |
| A5 | 從專案技術決策記錄匯入平台契約 | 條目清單（平台契約類別） |
| A6 | 逐條填寫測試形態（依分層測試策略的判斷流程）、驗證形態、斷言來源、fixture 需求 | 契約欄位填寫 |
| A7 | 逐條評估跳過條件（依分層測試策略的跳過條件或元件庫規格豁免清單） | 跳過標記 |
| A8 | 執行 `test-object-catalogue-completeness-criteria.md`「四、齊全判斷標準」C1-C4 機械檢查 | 齊全驗證 |

## 起點 B：有既有測試，無契約

適用：專案有測試檔案但無測試對象目錄（接手既有專案）。

| 步驟 | 動作 |
|------|------|
| B1 | 盤點既有測試檔案，逐檔記錄其斷言對象 |
| B2 | 反向追溯每個斷言到規格條目（「這個斷言在驗什麼規格宣告？」） |
| B3 | 判定依序執行：(1) 一則測試只要有任一斷言追溯不到規格條目，整則即標記「無規格來源」（混用會使紅燈無法歸因，見 `references/layered-test-strategy.md`「分層之外的補位形態」節）；(2) 後續判定作用在追溯不到的斷言上，判定是否為 characterization test 或應刪除；(3) 混合測試（含可追溯與追溯不到兩類斷言）拆為兩則：一則僅含可追溯斷言、對應規格來源；另一則為 characterization test 或依判定刪除，可追溯的斷言保留為有規格來源的測試，不隨判定一併刪除 |
| B4 | 從規格側掃描未被任何測試覆蓋的條目，標記為缺口 |
| B5 | 為所有條目填寫契約欄位，缺口條目的測試形態標「待補」 |

### 追溯不到規格來源的判定範例

以下示範起點 B 步驟 B2、B3 的判定方式：部分斷言可追溯，不代表整條測試視為有規格來源。

【輸入】

```text
既有測試一則，含兩個斷言：
  斷言一：回傳結果的筆數等於 3（可對應到 {SPEC-ID} §{章節} 的筆數宣告）
  斷言二：回傳結果依某個未於任何規格出現的內部欄位排序
```

【產出】

```text
形態：決策表

情境                                                 | 判定
兩個斷言皆可追溯到規格條目                           | 標記為有規格來源
僅部分斷言（如斷言一）可追溯，其餘（斷言二）追溯不到 | 標記為「無規格來源」，並拆為兩則：一則僅含斷言一（保留為有規格來源的測試）；另一則僅含斷言二（依 characterization 或應刪除判定處置）
```

【驗證】

```text
檢驗問句：
  Q 一則測試中，只要有任一斷言可追溯到規格條目，整條測試是否即算有規格來源？預期：否。任一斷言追溯不到，該則測試即標記為無規格來源，非部分可追溯即算通過。
  Q 標記為無規格來源後，下一步是否為直接刪除該測試（含其中可追溯的斷言一）？預期：否。須先拆為兩則，可追溯的斷言一保留為有規格來源的測試；只有追溯不到的斷言二那一則才進入 characterization 或應刪除判定。
```

## 起點 C：有程式碼，無測試

適用：專案有程式碼但無測試（legacy 或 spike 轉正）。

| 步驟 | 動作 |
|------|------|
| C1 | 若有規格 / 使用案例 → 走起點 A，但 fixture 需求欄根據既有程式碼填寫（不是根據規格推導） |
| C2 | 若無規格 / 使用案例 → 以程式碼為來源建 characterization test 目錄，每個可呼叫的公開進入點一條（公開方法、模組層級的公開函式、以函式實作的公開存取子）；事件、串流等由進入點觸發的輸出，記入觸發它的進入點條目，不另立條目（理由：依 `references/layered-test-strategy.md`〈分層之外的補位形態〉characterization test「先對現有程式跑一次、把實際輸出記錄成預期值」，這類輸出是呼叫進入點後記錄下來的預期值，屬該進入點條目；是否另立條目只看它本身是否為可呼叫的公開進入點）。來源欄標 `code: {檔案}:{函式}`，同時建議補撰規格 |

### characterization 條目粒度範例

以下示範起點 C 步驟 C2「每個可呼叫的公開進入點一條 characterization 條目」的粒度判定：以可呼叫的公開進入點（此例為公開方法）為單位，而非以公開類別為單位。

【輸入】

```text
既有程式碼（無規格 / 使用案例）：
  一個公開類別，對外提供兩個公開方法：新增一筆資料、依條件查詢資料
```

【產出】

```text
形態：契約表（characterization test 目錄）

對象                                     | 來源
新增一筆資料（該公開方法的現行行為）     | code: {檔案}:{函式}
依條件查詢資料（該公開方法的現行行為）   | code: {檔案}:{函式}
```

【驗證】

```text
檢驗問句：
  Q 該公開類別，是否只建立一條 characterization 條目？預期：否。該類別對外提供兩個公開方法，各自建立一條條目。
  Q 條目數量，是隨公開類別數量增加，還是隨公開進入點數量增加？預期：隨公開進入點數量增加（此例為公開方法），單位為可呼叫的公開進入點而非公開類別。
```
