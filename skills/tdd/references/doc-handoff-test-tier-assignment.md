# 整合測試 vs 單元測試分工

> **同目錄**：入口檔 `doc-handoff.md`（觸發條件、前置閘門、映射表、種子包格式等在此）；姊妹檔 `doc-handoff-uc-to-gwt-conversion.md`（UC 步驟→GWT 轉換規則）。
>
> **溯源**：原為 `doc-handoff.md` 的〈整合測試 vs 單元測試分工〉節，補齊範例後全檔超出單檔 token 門檻；依讀者任務三問判定本節是讀者在執行步驟 4 時才需要的完整判斷程序，外移為獨立檔（搬移程序見 skill-design-guide `references/splitting-an-existing-skill.md`）。

doc 的 UC 已定義整合測試（資訊鏈），TDD 需決定哪些行為由整合測試覆蓋、哪些需拆為單元測試。

## 分工決策框架

| 行為特性                                         | 測試層級                  | 原因                               |
| ------------------------------------------------ | ------------------------- | ---------------------------------- |
| 跨元件資料流（SDK→collector→storage→query）      | **整合測試**（UC 資訊鏈） | 串接失敗只能在完整鏈路中暴露       |
| 單一元件內部邏輯（schema 驗證、欄位轉換）        | **單元測試**              | 商業規則可單獨測試，不需要完整鏈路 |
| 元件邊界行為（API 回傳格式、錯誤碼）             | **單元測試**              | 契約面由元件自身保證，不依賴上下游 |
| 多元件互動的特定路徑（error 事件的特殊處理流程） | **整合測試**              | 特定路徑的互動需完整鏈路才能重現   |
| 跨 app process 邊界（系統權限對話框、原生檔案選擇器、外部 process、通知中心） | **平台驗證測試**（見 `references/layered-test-strategy.md`「分層之外的補位形態」節「**跨邊界驗證**」） | headless 的 `integration_test` 驅動不到系統原生 UI 或外部程式，判定者是平台而非 app 自己，需另一種測試形態 |

## 判斷原則

> **UC 場景步驟中，每個步驟問「這個步驟的正確性是由自己決定，還是由串接決定？」**

- **自己決定** = 單元測試（例：schema 驗證邏輯、query 篩選邏輯）
- **串接決定** = 整合測試（例：SDK flush 後 collector 能收到、collector 存入後 query 能查到）
- **配置決定** = 參數化測試（例：不同 storage backend 的行為差異、不同 flush interval 的邊界）
- **平台決定** = 平台驗證測試（見下方「跨邊界步驟」）

### 跨邊界步驟：平台決定

自己/串接/配置三值共同的隱含前提是判定權威落在 app process 之內——自己的邏輯、app 內部件之間的串接、或呼叫時的參數配置。UC 步驟一旦呼叫離開 app process（系統權限對話框、通知中心、原生檔案選擇器、外部 process），正確性改由作業系統或外部程式的行為決定，三值都給不出答案，因為它們都沒有「離開 app process」這個選項。

**平台決定** = 平台驗證測試（例：權限對話框的允許/拒絕分支、原生檔案選擇器回傳的路徑格式、外部 process 的 exit code）。判定者是作業系統或平台 API，不是 app 自己的程式碼；headless 的 `integration_test` 驅動不到系統原生 UI，需另一種測試形態驗證。

**與既有三值的關係**：「平台決定」不是與自己/串接/配置並列的第四個同軸選項，而是先問一個更前面的問題——**這個決定發生在 app process 內，還是外面？** 落在外面才問平台決定；落在裡面才繼續問自己/串接/配置三選一。此軸與既有三值是**正交關係**（跨邊界屬性獨立於「誰決定正確性」的軸），不是對三值的並列擴充。

以下示範一個呼叫離開 app process 的步驟，展示如何判定該步驟落於「平台決定」，而非既有三值之一；app 端收到平台結果後的後續處理，另見 `references/test-object-catalogue.md`「六、派發語言」節第二則範例。

【輸入】

```text
UC 主成功場景步驟：
  使用者觸發一項需要作業系統原生對話框回應的操作，操作完成後畫面依對話框結果更新
```

【產出】

```text
形態：決策表

子步驟                         | 正確性由何者決定           | 測試層級
原生對話框本身的顯示與互動結果 | 平台（作業系統）           | 平台驗證測試
app 收到對話框結果後的畫面更新 | 自己（app 內部依結果分支） | 單元測試
```

【驗證】

```text
檢驗問句：
  Q 原生對話框的顯示與互動結果，能否歸入既有「自己、串接、配置」三值之一？預期：否。判定權威落在作業系統，三值皆假設判定權威落在 app process 之內，故不適用，須另立「平台決定」。
  Q 整個步驟，含對話框互動與後續畫面更新，是否應整段歸為平台驗證測試？預期：否。只有離開 app process 的子步驟歸平台驗證測試；app 收到結果後的處理，仍回到自己、串接、配置三選一，此處為自己決定，歸單元測試。
```

> BDD→單元拆分的完整判斷標準見 `references/bdd-behavior-testing.md`「BDD→單元拆分標準」章節。各層測試方法的詳細選擇、跨邊界步驟的具體測試形態見 `references/layered-test-strategy.md`「分層之外的補位形態」節「**跨邊界驗證**」。

## 與 UC 資訊鏈的關係

UC 的「資訊鏈整合測試」已定義端到端路徑。本框架補充的是：每個路徑中的節點，其正確性由自己、串接或配置決定，決定不同、測試層級不同。以下以一條資訊鏈為例，示範分工判斷。

【輸入】

```text
資訊鏈（節點依序執行）：
  節點 1：初始化 → 節點 2：送出資料 → 節點 3：暫存與批次處理 → 節點 4：接收端驗證 → 節點 5：持久化 → 節點 6：查詢

UC 場景步驟：資料送出後，能依條件查詢回該筆資料
```

【產出】

```text
形態：決策表

節點                 | 正確性由何者決定                 | 測試層級
節點 1 初始化        | 自己（內部狀態建立規則）         | 單元測試
節點 3 暫存與批次處理 | 自己（批次格式、重試邏輯）       | 單元測試
節點 4 接收端驗證     | 自己（欄位必填、格式合規檢查）   | 單元測試
節點 5 持久化         | 自己（寫入與併發安全規則）       | 單元測試
節點 6 查詢           | 自己（篩選、分頁、排序邏輯）     | 單元測試
整條鏈（節點 1 至節點 6 串接後能否查得到方才送出的資料） | 串接（任一節點交接失敗即整條鏈失敗） | 整合測試
```

【驗證】

```text
檢驗問句：
  Q 「送出後能查得到」這句判斷，正確性是否由單一節點自己決定？預期：否。此判斷依賴節點間交接是否成功，屬串接決定，歸整合測試。
  Q 各節點內部的格式檢查與規則驗證，是否也應歸入整合測試以求保險？預期：否。節點內部邏輯可獨立驗證，歸單元測試；併入整合測試會使失敗定位退回整條鏈，喪失單元測試的定位精度。
```
