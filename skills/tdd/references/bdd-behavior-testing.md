# BDD 行為測試指引

## 目的

定義 BDD（Behavior-Driven Development）在 TDD 流程中的定位：測試描述系統的「行為」而非「實作」。

**Why**：測試耦合實作細節時，重構內部結構（即使業務邏輯不變）會導致大量測試失敗，維護成本超過撰寫功能本身。BDD 要求測試只耦合可觀察的行為，使重構時測試保持穩定。

**Consequence**：不區分行為與實作的測試套件，在替換儲存層、重構內部類別結構等合理重構後會連鎖失敗，團隊逐漸放棄維護測試或迴避重構。

**Action**：用三問判別法篩選測試內容、用 Sociable/Solitary 框架選擇測試風格、用分層 Mock 原則控制耦合範圍。

## 行為 vs 實作判別

對每個測試斷言，依序問三個問題：

| 問題                           | 答案為「是」 | 答案為「否」 |
| ------------------------------ | ------------ | ------------ |
| 使用者能否觀察到這個結果？     | 偏向行為     | 偏向實作     |
| 改變實作方式會影響這個結果嗎？ | 偏向實作     | 偏向行為     |
| 產品經理需要關心這個結果嗎？   | 偏向行為     | 偏向實作     |

三問結果為「能觀察、不影響、需關心」→ 行為；反之 → 實作細節。

### 對照範例

測試實作（耦合結構，重構即失敗）：

```
test "save order calls database.insert":
  repository.save(order)
  verify database.insert("orders", order.to_json()) called 1 time
```

測試行為（耦合可觀察結果，重構不影響）：

```
test "使用者提交訂單 - 訂單成功儲存":
  Given: order = valid_order()
  When:  result = submit_order.execute(order)
  Then:  assert result.is_success == true
         assert result.order_id is not empty
```

## Sociable vs Solitary 選擇框架

TDD 有兩種測試風格，差別在測試邊界畫在哪一層：

| 特性          | Sociable（Classical TDD）   | Solitary（Mockist TDD）      |
| ------------- | --------------------------- | ---------------------------- |
| 測試單元      | Module（一組協作的類別）    | 單一 Class                   |
| 耦合線        | 一條（模組公開 API）        | 受測對象一條，每個替身各一條 |
| 替身範圍      | 只替換外部依賴（DB、API）   | 替換所有協作者               |
| Domain Entity | 使用真實物件                | 使用真實物件（值物件不替換） |
| 重構時表現    | 測試不動                    | 測試跟著改                   |
| 紅燈定位      | 整個 Module                 | 精確到 Class                 |

條數本身不是重點，兩種條各自的穩定性才是。Sociable 那一條是模組的公開契約、被設計成不常變；Solitary 多出來的那幾條是模組內部的協作協定，沒有人承諾過它穩定，而它正是重構會動到的東西。兩者是把誤報成本與定位成本分配到不同位置，不是精度的高低之分。

**選擇準則**：下面三個症狀是**診斷工具、不是選型公式**——它們都要有一套跑著的測試才觀察得到，而且量的都是維護經濟性。三者互相獨立，任一成立就各有處方，而處方的第一順位都不是移動邊界。

1. **責任一搬動，測試就大批要改**。成本 = 責任搬動的頻率 × 每次要重寫的替身設定量。先試把替身設定集中到一個 test support 模組（降第二個因子）；集中之後仍要改大量測試，才把邊界拉回模組。
2. **紅燈說不出哪裡壞**。先試補可觀察性（斷言訊息、中間狀態、shrinking）；補完仍然慢而模組內部步驟數本來就多，逐類別隔離才划算——前提是那個模組的結構已經不太動了。判斷結構穩不穩定要拿外部憑據（凍結的版本號、簽過的契約、發布過的規格），自評不算數。
3. **協作者拖慢或拖垮測試**。先分流：協作者本來就在外部世界（硬體、外部服務）是應用邊界的替換、與這三個症狀無關。造得起來只是慢的，先只替換那一個慢的、邊界留在模組；慢的散在各處才移動邊界。

**手上還沒有測試時**：三個症狀一個都觀察不到，判斷改看哪一邊的錯誤便宜修。預設 Sociable——畫太粗、後來定位慢，收縮是加測試；畫太細、後來結構還在動，要拆掉重來而且過程中沒有回歸網。重新評估的觸發點就是三個症狀任一出現。

**射程**：這三個症狀量的都是維護成本，而那已經是古典派的立場。倫敦學派的核心主張是**由外而內的設計發現**——用替身把還不存在的介面逼出來，替身在那裡是設計工具而不是邊界的經濟權衡。那個用途不被這三個症狀裁決，也不隨介面定案而變成「錯的」；介面定案之後那些逐類別測試要不要留，才回到三個症狀去看。

### 判斷手上的測試屬於哪一派

1. 改變 Module 內部結構（拆類別、提取方法、重命名內部方法），讓外部行為保持不變
2. 所有測試不需修改且通過 → Sociable
3. 任何測試需跟著改 → Solitary，且耦合線的位置同時現形

這個程序判的是**測試現在耦合在什麼上，不判對錯**。結果是 Solitary 而那個模組確實有理由（結構已凍結、失敗定位很貴、或替身是拿來逼出還不存在的介面），那是正確的設計；理由一個都不成立，才是該重畫邊界的訊號。

**判斷標準**：替換儲存層實作、改變內部演算法 → 測試不應失敗；改變業務規則、調整可觀察的錯誤訊息 → 測試應失敗。

## 分層 Mock 原則

核心規則：**只 Mock 外層依賴，禁止 Mock Domain Entity**。

| 類別                            | Mock？   | 理由                              |
| ------------------------------- | -------- | --------------------------------- |
| Repository / Service / Gateway  | 是       | 外部系統依賴，透過 Interface 隔離 |
| Event Publisher / Message Queue | 是       | 外部基礎設施                      |
| Domain Entity / Value Object    | **禁止** | 內層業務邏輯，必須用真實物件測試  |
| UseCase 內部 Helper             | **禁止** | Module 內部結構，Mock 即耦合實作  |

正確（Mock 外層，真實 Domain）：

```
test "使用者提交訂單成功":
  mock_repository.on_save -> return success("order-123")
  order = Order(amount=100, user_id="user-001")    // 真實 Domain Entity
  result = submit_order.execute(order)
  assert result.is_success == true
```

錯誤（Mock Domain Entity，測不到業務邏輯）：

```
test "使用者提交訂單成功":
  mock_order = MockOrder()
  mock_order.on_validate -> return true    // 跳過真實驗證邏輯
  // 測試通過但業務規則未被驗證
```

## 架構分層 × BDD 適用度

| 架構層級             | 測試方法       | 覆蓋率要求    | 說明                                 |
| -------------------- | -------------- | ------------- | ------------------------------------ |
| UseCase              | **BDD**（GWT） | 行為場景 100% | 核心應用層，每個場景一個 GWT         |
| Domain               | 單元測試       | 分支 100%     | 值物件驗證、實體不變量、業務規則邊界 |
| Behavior / ViewModel | 條件單元測試   | 複雜轉換才測  | 簡單轉換由 UseCase 層覆蓋            |
| UI                   | 整合測試       | 關鍵路徑      | 測試成本高，只測關鍵互動             |
| Interface            | **不測**       | —             | 只定義契約無實作邏輯                 |

## 與 TDD 四階段整合

| Phase            | BDD 角色                                             |
| ---------------- | ---------------------------------------------------- |
| Phase 1 功能設計 | 從需求識別使用者行為場景（正常 + 異常 + 邊界）       |
| Phase 2 測試設計 | 將行為場景轉換為 GWT 測試結構，設置 Mock             |
| Phase 3 實作     | Red→Green→Refactor，測試先行                         |
| Phase 4 重構     | 行為測試必須保持穩定——重構導致測試修改代表耦合了實作 |

Phase 4 品質判斷：替換實作不讓測試失敗 = 正確；改變業務規則讓測試失敗 = 正確。兩者反過來都是設計問題。

## BDD 前置產出物完整性（涉及 UI 時）

涉及 UI 的 BDD 操作盤點，除了操作/主情境/失敗情境表，必須額外產出**畫面狀態矩陣**（畫面 × 狀態 × 可用操作 × 退出路徑）。缺此矩陣，widget test 和導航測試無法完整覆蓋——UC 步驟轉 GWT 時只有 happy path 行為，忽略每個畫面的狀態切換和退出路徑。

**實戰教訓**：app_tunnel v1.2.0 有 192 個 unit test 全綠，實機發現 4 個畫面缺返回按鈕和斷線處理，根因是 BDD 操作盤點未產出畫面狀態機。

## BDD→單元拆分標準

當 BDD 整合測試覆蓋的 Module 變大，需判斷何時拆出獨立的單元測試：

| 訊號                                      | 動作                                         |
| ----------------------------------------- | -------------------------------------------- |
| Domain 層出現複雜分支邏輯（> 3 條件組合） | 拆為 Domain 單元測試，驗證分支覆蓋           |
| 值物件驗證規則多（> 5 個邊界條件）        | 拆為 Value Object 單元測試                   |
| BDD 測試的 Given 設置過長（> 10 行 Mock） | 考慮拆分 Module 而非加測試——本列成立只帶出「考慮」這個動作，不斷言該 Module 已過大，也不判定該 Module 應拆分；讀成「本列成立即 Module 過大」或「本列成立即應拆分 Module」都是錯的讀法，「Module 過大」是本列待查的假設，成立與否由下方〈判定不拆分 Module〉裁定；套用不移動邊界動作後，原僅服務已拆出邏輯的 Given 設置可移除，移除後 Given 設置仍 > 10 行 Mock，才考慮拆分 Module（詳見下方〈多訊號同時成立時〉）；到達考慮拆分 Module 時，先依下方〈判定不拆分 Module〉判斷 |
| 步驟正確性由元件自身決定（非串接決定）    | 拆為單元測試（見 `doc-handoff-test-tier-assignment.md` 分工框架） |
| 步驟正確性由串接決定                      | 留在整合測試                                 |
| 步驟正確性由配置決定                      | 拆為參數化測試                               |

**多訊號同時成立時**：不移動 Module 邊界的動作（拆為 Domain／Value Object 單元測試、拆為單元測試、拆為參數化測試）優先於「拆分 Module」，依據〈Sociable vs Solitary 選擇框架〉「處方的第一順位都不是移動邊界」。先套用前者；套用後原整合測試中僅服務已拆出邏輯的 Given 設置可移除，移除後 Given 設置仍 > 10 行 Mock，才考慮拆分 Module，並依〈判定不拆分 Module〉判斷。

**判定不拆分 Module**（到達「考慮拆分 Module」時適用；不論是由單一 Given 訊號直接到達，或依〈多訊號同時成立時〉移除後仍 > 10 行 Mock 到達，皆同；本段所稱「Given 設置行數」、訊號表該列的「> 10 行 Mock」行數與下方條件 2 所稱「替身設置」的行數，指同一個量）：下列兩項條件都能從測試程式碼或題設逐項查證成立時，判定 Given 設置的長度來自受測 UseCase 串起的外部依賴、不是 Module 過大，不拆分 Module；任一條件不成立、或無法查證，依「Given 設置過長」列動作考慮拆分 Module：

1. 受測 Module 對外只有一個 UseCase 進入點：該 Module 的所有 BDD 場景，When 都呼叫同一個 UseCase 進入點。
2. 適用前提：本條件通篇的「該 UseCase」指條件 1 查證成立的那一個唯一 UseCase 進入點；條件 1 不成立（該 Module 的 BDD 場景 When 呼叫兩個以上不同的 UseCase 進入點）時，「該 UseCase」沒有指涉對象，本條件不查證，直接依下方結論句作結——從多個進入點中挑一個當「該 UseCase」查證、或對每個進入點各查證一次本條件再取其中成立的那一個，都是錯的讀法。本條件的內容：計入 Given 設置行數的每一行替身設置，都屬於該 UseCase 某個流程步驟會呼叫的外部依賴——範圍是該 UseCase 的全部流程步驟，不是被判定的單一場景實際執行到的步驟；失敗場景提前結束而未走到的依賴，仍算「會呼叫」。本句只排除「場景未走到」作為否定該依賴屬流程步驟的理由，不代替「該替身是否屬該 UseCase 某個流程步驟」的查證。查證本條件需要該 UseCase 的流程步驟清單；未能取得該清單時，本條件為「無法查證」，不因替身全部是外部服務介面而成立——「是外部服務介面」與「屬該 UseCase 某個流程步驟會呼叫的外部依賴」是兩個不同的判準。判定順序：先確認該依賴是否為該 UseCase 任一流程步驟會呼叫者；判定為「是」時，該行直接計入 Given 設置行數，不進入以下兩分支——建構受測對象是否需要它在此不被詢問；判定為「否」時，才依序檢查兩分支：(1) 該依賴不是任一流程步驟會呼叫者，且建構受測對象不需要它——其設置行先刪除、不計入行數（「刪除」在本款指計數上不計入該行，本款只改變 Given 設置行數怎麼數，不要求改動任何測試程式碼；讀成「把那幾行從測試檔裡實際刪掉、改寫測試程式碼後再重數」是錯的讀法）；以刪除後的行數重新比對訊號表「> 10 行 Mock」門檻——重新比對後行數仍 > 10 行時，「Given 設置過長」訊號仍成立，依本條件末段回到本條件開頭逐項裁定條件 1、2；重新比對後行數不超過 10 行（即不再滿足「> 10 行 Mock」）時，「Given 設置過長」訊號不再成立，該訊號帶來的「考慮拆分 Module」隨之解除，本段就此作結、判定不拆分 Module，不再裁定條件 1、2，本條件末段「回到本條件開頭逐項裁定」不適用於這個情形；(2) 該依賴不是任一流程步驟會呼叫者，但建構受測對象需要它——本條件不成立，依下方結論句依上方訊號表「Given 設置過長」列動作考慮拆分 Module，其餘替身設置行的裁定不改變這個結果；本款只裁定本條件成立與否，不規範受測對象的建構方式——改寫建構子、改注入方式、把該依賴改為可選、改由 Factory 或 Test Helper 供給，使它不再是建構受測對象所需，這類改動不在本款射程內，把它們與本款的裁定並列為同級選項、或據以把本條件由不成立改判為成立，都是錯的讀法。完成每一行的計入或刪除後，回到本條件開頭逐項裁定條件 1、2，再依結論句作結。

**結論**：條件 1、2 皆成立時，判定不拆分 Module；任一條件不成立、或無法查證時，本段不判定該 Module 應拆分、也不斷言 Module 過大，把這個出口寫成「應拆分 Module」「已判定 Module 過大」或自行設計拆法都是錯的讀法，此時依上方訊號表「Given 設置過長」列動作考慮拆分 Module。

上方訊號表「步驟正確性由串接決定」一列只決定該步驟留在整合測試，不構成條件 1 或條件 2 成立的依據。判定不拆時，重複的替身設置依〈常見挑戰速查〉抽到 Test Helper／Builder，抽出的行仍計入 Given 設置行數。

**分工邊界**：UseCase 層行為用 BDD 保護；Domain 層邏輯用單元測試保護；兩者互補，BDD 覆蓋業務流程正確性，單元測試覆蓋邏輯分支完整性。

### 訊號優先序範例

以下示範同一個 Module 同時符合「Given 設置過長」與「步驟正確性由自己決定」兩項訊號時，何者優先。

【輸入】

```
一個 BDD 整合測試：Given 設置超過 10 行 Mock；其中一個步驟的正確性由該步驟自身的邏輯決定（非由與其他元件的串接決定）
```

【產出】

```
形態：決策表

訊號                         | 動作
步驟正確性由自己決定         | 優先套用：拆為該步驟的單元測試
Given 設置過長（> 10 行 Mock） | 次要訊號：單元測試拆出後，若整體 Module 的 Given 設置仍然過長，才進一步考慮拆分 Module
```

【驗證】

```
檢驗問句：
  Q 兩項訊號同時成立時，是否優先考慮拆分整個 Module？預期：否。依〈BDD→單元拆分標準〉「多訊號同時成立時」一條，不移動 Module 邊界的動作優先於拆分 Module；優先依「步驟正確性由自己決定」拆出該步驟的單元測試，Module 是否需要拆分，留待單元測試拆出後、Given 設置是否仍然過長再判斷。
  Q 拆出單元測試後，原整合測試中對應該步驟的 Given 設置，是否仍須保留全部細節？預期：否。依「多訊號同時成立時」一條，僅服務已拆出邏輯的 Given 設置可移除；該步驟細節已由拆出的單元測試覆蓋，原整合測試的 Given 可簡化為只保留串接所需的前置狀態。
```

## 常見挑戰速查

| 挑戰                                                 | 對策                                                          |
| ---------------------------------------------------- | ------------------------------------------------------------- |
| **覆蓋率盲點**：BDD 只測「重要行為」，可能漏掉程式碼 | 混合策略——UseCase 100% BDD + Domain 100% 單元 + 整體 80% 行數 |
| **行為粒度**：太粗難定位失敗，太細變回單元測試       | 一個 UseCase = 一個核心行為，名稱以動詞開頭                   |
| **測試設置複雜**：UseCase 需 Mock 多個外部依賴       | 建立 Test Helper / Builder Pattern 減少重複設置；抽到 Helper／Builder 的替身設置仍計入〈BDD→單元拆分標準〉Given 設置過長的行數 |
| **假行為測試**：看似 GWT 格式但斷言仍驗證實作        | 用三問判別法逐一檢查每個斷言                                  |
