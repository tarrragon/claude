# 測試對象目錄：從規格推導要測什麼

## 目的

`references/doc-handoff.md` 回答「規格如何映射為測試輸入」，`references/layered-test-strategy.md` 回答「該層用什麼方法測」——兩者都假設「要測哪些對象」已經確定。本文件補上這一步：定義測試對象的單位、每個對象要記載到什麼程度（契約欄位）、以及從三種起點推導出完整目錄的程序。

不做這一步的後果：測試設計品質完全依賴設計者當下的判斷，不同票之間無一致性，且「這個測試對應規格的哪一條」無處記載——這正是測試與專案需求脫鉤的結構性成因。

---

## 一、測試對象的單位判定

單位選錯會使目錄與既有規格重複，或無法涵蓋部分規格層級。以下比較候選方案：

| 候選單位 | 說明 | 問題 |
|---------|------|------|
| 使用案例場景 | 以使用案例文件的每個場景（主成功／替代／例外）為單位 | 使用案例的場景數量有限，畫面狀態、元件、token、平台契約等層級無法以場景為單位記載 |
| 元件 | 以元件庫規格的每個元件為單位 | 與元件庫規格既有的逐元件契約欄位**完全重複**——元件庫規格的測試點子節本身就是逐元件測試契約 |
| 規格條目 | 以每個可獨立驗證的規格宣告為單位（功能需求、使用案例步驟、狀態轉換、互動規則、token 不變式、平台契約） | 粒度較細，需要聚合機制；但覆蓋全部規格層級，且每個測試對象有唯一的規格來源 |

**結論：規格條目**。

**與元件庫規格不重複的論證**：元件庫規格的測試契約欄回答「這個元件要怎麼測」（全變體全狀態渲染、每種尺寸不溢位、最長文案截斷），本目錄回答「從規格推導，整個專案要測哪些東西」。元件契約只是本目錄涵蓋的來源類別之一，且本目錄對元件的記載粒度是「規格來源 + 驗證形態 + 是否已有測試」，不重複元件庫規格的逐欄契約值。

### 測試對象單位判定範例

以下示範一條含多個子句的功能需求，如何拆為測試對象目錄的多行。

【輸入】

```text
規格片段（功能需求一條）：
  該項功能需求：輸入為空時顯示提示訊息；輸入格式錯誤時顯示對應錯誤說明；輸入合法時送出資料
```

【產出】

```text
形態：契約表（測試對象目錄，僅列「對象」與「來源規格條目」兩欄）

對象                   | 來源規格條目
輸入為空時顯示提示訊息 | {SPEC-ID} FR-{N}／輸入為空分支
輸入格式錯誤時顯示說明 | {SPEC-ID} FR-{N}／格式錯誤分支
輸入合法時送出資料     | {SPEC-ID} FR-{N}／合法輸入分支
```

【驗證】

```text
檢驗問句：
  Q 該功能需求，是否整條記為目錄的一行？預期：否。該功能需求含三個各自可獨立驗證的宣告，各自拆為一行，單位為規格條目而非整條功能需求。
  Q 三行的「來源規格條目」，是否指向同一個規格宣告？預期：否。三個分支各為一個規格宣告，依 `test-object-catalogue-completeness-criteria.md` C3〈C3 比對的單位是規格宣告〉不重複；三行的欄位值分別標註不同分支，不是同一宣告以附註偽裝成不同字串。
```

## 二、來源類別

規格條目來自以下來源類別，各類別的權威文件與既有測試側目錄現況：

| 來源類別 | 規格權威（型別） | 測試對象舉例 | 既有測試側目錄 |
|---------|-----------------|-------------|---------------|
| 畫面狀態轉換 | 畫面狀態規格（狀態 × 操作 × 退出路徑矩陣） | 「載入中 → 正常」轉換的進入條件與退出路徑 | 無 |
| 使用案例行為場景 | 使用案例文件（主成功場景 + 替代/例外場景） | 「使用案例某步驟：選擇資料後進入下一狀態」 | 無 |
| 互動規則 | 互動行為規格 | 「Esc 收合浮層，焦點回到入口」 | 無 |
| 元件契約 | 元件庫規格（逐元件契約欄位） | 「按鈕元件全變體全狀態渲染不溢位」 | 有（元件庫規格自身的測試契約欄） |
| Token 不變式 | 設計 token 規格 + token 定義原始碼 | 「主題色 token 值 = 定義值」 | 部分有 |
| 平台契約 | 專案技術決策記錄 | 「沙盒關閉」「視窗最小尺寸限制」 | 部分有 |
| 終端回饋訊息 | 互動行為規格的暫態提示載體判準 + 元件庫規格的訊息設計要求 | 「某事件的提示載體判定結論」「某訊息 key 在全部語系最長值下不觸發截斷」 | 部分有（元件庫規格測試點子節的溢位項與最長測試文案項） |

本目錄承載上表**全部**來源類別的測試對象索引。元件契約類別不重複元件庫規格的逐欄契約——本目錄只記「來源 → 測試」的映射行，不記逐欄契約值。

**終端回饋訊息與元件契約兩個類別的分界**：元件契約類別的對象是元件本身（全變體全狀態渲染一次即涵蓋），終端回饋訊息類別的對象是**經該元件顯示的每一則訊息**。兩者的增長來源不同——元件數量由元件庫規格決定且變動慢，訊息數量隨事件增加，新增一則提示不會新增元件卻必然新增一個測試對象；合併為單一類別會使新增訊息在目錄上無列可站，覆蓋性判準（C1）因此對它失效。

該類別各行的「測試形態」欄為**組合值**：是否出現、內容、可讀性三類驗收各對應不同形態（見 `references/layered-test-strategy.md`「終端回饋訊息的三類驗收（是否出現／內容／可讀性）」節），缺一即視為欄位不完整（C2 不通過）。**不得拆成三行**——三行會共用同一條來源規格條目，違反來源唯一（C3）。「不得拆成三行」管的是目錄的列數，不是測試案例：依 `references/layered-test-strategy.md`〈終端回饋訊息的三類驗收〉表，是否出現、內容、可讀性三類的斷言對象與主要形態各不相同、各有斷言形態，三類驗收必須拆成不同測試案例，不得合併寫入同一案例。此外，被規格明文裁定為不需要的驗收項（如不採重排機制時的顯示位爭用斷言）填入「跳過條件與理由」欄並引用該規格條文，不留空白：空白無法區分「規格裁定不需要」與「還沒設計」。

本類別的「反例」欄常見填法：持續性標示（徽章、問題標記）與阻擋狀態元件的文字會被誤歸入本類別，它們不受停留時間約束、可反覆閱讀，屬元件契約類別。

## 三、契約欄位表

每個測試對象的記載欄位：

| 欄位 | 問句 | 缺失後果 |
|------|------|---------|
| 對象 | 這個測試對象是什麼？用唯一識別名標記 | 無識別名 → 測試票無法引用規格來源 |
| 來源規格條目 | 規格中哪一條宣告了這個對象的行為？格式：`{SPEC-ID} §{章節}` 或 `{UC-ID} 步驟 {N}` | 無來源 → 測試與專案需求脫鉤 |
| 來源類別 | 屬於「二、來源類別」表的哪一類 | 無類別 → 不知該從分層測試策略的哪一層選測試方法 |
| 測試形態 | 該對象的測試方法：單元 / widget（元件） / 整合 / 實機驗證 / golden / 組合（多種以逗號分隔） | 無形態 → 預設全部單元測試，跨元件串接與平台行為漏測 |
| 驗證形態 | fake（自動化驗證邏輯） / 實機（驗證平台端事實） / 兩者 | 無驗證形態 → 跨邊界功能的平台端事實漏驗 |
| 斷言來源 | 斷言的預期值從哪裡來？格式：`{SPEC-ID} §{章節} {具體條文}` | 無斷言來源 → 斷言值為測試設計者自行判斷，與規格脫鉤 |
| fixture 需求 | 該測試需要什麼前置條件？格式：假資料集名稱 / 測試 harness / 特定環境參數 / 依賴注入覆寫 | 無 fixture → 每個測試自行建立前置條件，不一致且難維護 |
| 跳過條件與理由 | 何時不測？依分層測試策略的跳過條件或元件庫規格的豁免清單。非空值代表合法跳過 | 無跳過條件 → 無法區分「還沒測」與「不需要測」 |
| 反例 | 什麼情境會有人誤把這個測試對象歸入此類？ | 無反例 → 來源類別邊界模糊時，重複測試或漏測 |

**驗證形態的選值判準**：依 `references/layered-test-strategy.md`〈跨邊界驗證〉「驗證形態是雙軌並行，不是二選一：fake 覆蓋 App 端邏輯……實機驗證覆蓋平台端事實……只做其中一軌都會留下分層測試觸及不到的盲區」，步驟只含可由 fake 驗證的 app 端邏輯時填 fake；步驟含需要平台端事實才能確認的部分時填實機；兩者皆含時填兩者。

### 反例欄填法範例

以下以「互動規則」類別的一個測試對象為例，示範反例欄應填具體誤判情境，而非僅寫一個相鄰類別名稱。

【輸入】

```text
規格片段（互動規則一條）：
  按下離開鍵時收合目前開啟的浮層，焦點回到觸發浮層的入口元素
```

【產出】

```text
形態：契約表（測試對象目錄一行）

欄位     | 值
對象     | 離開鍵收合浮層並歸還焦點
來源類別 | 互動規則
反例     | 誤將此對象併入「元件契約」類別下的浮層元件測試，理由是兩者外觀（同一個浮層）相近；但本對象驗的是「離開鍵觸發的收合與焦點歸還」這條跨元件互動規則，元件契約類別驗的是浮層元件自身的渲染與狀態，兩者驗證對象不同
```

【驗證】

```text
檢驗問句：
  Q 反例欄，是否僅寫一個相鄰類別的名稱？預期：否。只寫類別名稱無法讓讀者判斷為何會誤判，須寫出具體會讓人誤判的情境與誤判理由。
  Q 反例描述，是否說明了誤判的具體理由，而非只指出誤判的類別？預期：是。理由須指出兩者驗證對象的差異，而非僅憑外觀判斷。
```

### 斷言來源欄範例

以下示範「斷言來源」欄與「來源規格條目」欄重疊時的填法：兩欄同條則照抄，兩欄不同條則分別填寫。依「三、契約欄位表」，斷言來源為必填欄位，其「無斷言來源 → 斷言值為測試設計者自行判斷，與規格脫鉤」的後果不因與來源規格條目重疊而免除，重疊時仍須各自填寫，不得留空。

【輸入】

```text
規格片段：
  行為宣告（{SPEC-ID} §{章節}）：清單依建立時間新到舊排序
  另一規格片段（{SPEC-ID} §{另一章節}）：時間格式採用 24 小時制
```

【產出】

```text
形態：契約表（測試對象目錄兩行對照）

情境                                       | 來源規格條目      | 斷言來源
斷言的預期值與行為宣告同一條規格條目       | {SPEC-ID} §{章節} | {SPEC-ID} §{章節}（與來源規格條目同條，照抄）
斷言的預期值另有專屬規格條目（如格式定義） | {SPEC-ID} §{章節} | {SPEC-ID} §{另一章節}（預期值出處為另一條，分別填寫）
```

【驗證】

```text
檢驗問句：
  Q 兩欄位，是否一律填寫相同內容？預期：否。僅當斷言預期值與行為宣告同一條規格條目時才照抄；預期值另有出處時，分別填寫兩個不同的條目。
  Q 斷言來源欄，可否留空以省略重複？預期：否。兩欄重疊時仍須各自填寫，欄位缺失視為斷言與規格脫鉤。
```

### 與元件契約欄位表的結構性差異

| 維度 | 元件契約欄位表 | 測試契約欄位表（本文件） |
|------|--------------|------------------------|
| 單位 | 元件 | 規格條目（跨全部來源類別） |
| 填寫者 | 設計者 | 測試設計者 |
| 時機 | 畫面實作票之前（設計期） | 測試設計期 |
| 驅動來源 | 設計稿 / 規格狀態表 | 規格條目（功能需求 / 使用案例 / 規格條文） |
| 測的維度 | 元件渲染正確性（尺寸、文案、狀態） | 行為正確性（狀態轉換、使用案例場景、互動規則） |

### 與追溯矩陣的界線

專案若另有一份追溯矩陣（把已存在的測試對應回規格條目的資料檔），它與本目錄**不同構，且不應被改成同構**。兩者回答的是不同問題：

| 維度 | 追溯矩陣 | 測試對象目錄（本文件） |
|------|---------|---------------------|
| 問什麼 | 已存在的測試對應到哪條規格？ | 從規格推導該測哪些對象？ |
| 用途 | 審計（事後追溯，資料型） | 設計（事前推導，方法論型） |
| 單位 | 由該矩陣自己的 schema 各軸定義 | 規格條目 |
| 消費者 | 查詢工具與人工查閱 | 測試設計者（Phase 1／2） |
| 生命週期 | 隨測試實作持續更新 | 測試設計期產出，實作後穩定 |

**本目錄的來源類別不必逐一在追溯矩陣有對應軸。** 進入該 schema 的判準是三條 AND：有工具消費場景、粒度與既有軸一致、無其他權威載體。畫面狀態轉換、互動規則、元件契約三類皆不滿足——前兩類的權威載體是規格文件本身的狀態矩陣與互動規則章節，元件契約的權威載體是元件庫規格的逐元件測試契約欄位。為它們新增頂層軸會使多數軸無消費者，並讓同一份檔案混雜兩種粒度。

**Why**：不寫這條界線，讀者看到兩份都在講「測試與規格的對應」會判定其一是另一的過期副本，進而把本目錄的欄位塞進追溯矩陣（該 schema 的頂層鍵若是封閉集合且有 conformance 測試把關，此舉會撞上強制層），或反過來認為本目錄應該只列追溯矩陣已有的項目而漏掉三類來源。


本框架的追溯矩陣住在哪、schema 由誰定義、哪個 CLI 消費它，見 `references/project-integration/traceability-matrix.md`（該目錄不隨同步傳遞，由各專案自備）。<!-- portability-allow: 分層目錄由各專案自備，不隨 sync 傳遞 -->

## 六、派發語言：測試票 how 的目標句型

元件庫規格的對應句型是「用元件 X 的變體 Y 放進容器 Z 的第 N 格」。測試側的對應句型：

```text
驗證「{來源規格條目}」宣告的行為：
  Given {fixture 需求描述的前置狀態}
  When {來源規格條目描述的觸發動作}
  Then {斷言來源描述的預期結果}
  測試形態：{單元 / widget / 整合}
  驗證形態：{fake / 實機 / 兩者}
```

**When／Then 的書寫邊界**：When 只寫來源規格條目宣告的觸發條件（即句型中的 `{來源規格條目描述的觸發動作}`），Then 只寫來源規格條目宣告的可觀察結果；判準是內容是否出自來源規格條目的宣告，可用業務語言改寫，不要求逐字照抄規格文字。觸發機制的具體實作方式（回呼、事件監聽）與框架內部表示方式（如節點樹結構）是常見的違反形態，不是完整的禁止清單。用語依 `references/phase2-test-design.md`〈場景設計原則〉「用業務語言描述，不用技術術語」；形態依 skill-design-guide `references/chained-examples.md`〈【驗證】段〉執行期行為形態允許／禁止表：允許「使用者可觀測的事實」，禁止「框架事件 handler 的具體命名」與「框架測試 API 的具體方法名或選擇器語法」。狀態轉換類測試的 Given 對應規格狀態表的前一狀態、Then 對應轉換後的可觀察結果（後一狀態），依 `references/phase2-test-design.md`〈GWT 格式〉「Given: {系統的前置狀態}」「Then: {預期的可觀察結果}」定義。

**範例**（沿用 `references/doc-handoff.md` 的占位符慣例，非本目錄強制格式）：

#### 範例一：狀態轉換

【輸入】

```text
規格片段（畫面狀態矩陣一列）：
  載入中 → 正常 ｜ 觸發條件：前置資料解析完成
```

【產出】

```text
形態：契約表（測試票 how 語言，依「六、派發語言」句型）

驗證「{SPEC-ID} §{章節} 載入中→正常」宣告的狀態轉換：
  Given 前置資料已選定但解析未完成（fixture: {對應 fixture 名稱}）
  When  前置資料解析完成
  Then  畫面從骨架版面切換至目標畫面
  測試形態：widget
  驗證形態：fake
```

【驗證】

```text
檢驗問句：
  Q When 欄位是否描述了觸發此轉換的具體實作機制，例如某種回呼或事件監聽方式？預期：否。When 只描述規格宣告的觸發條件「前置資料解析完成」，不預設實作如何得知此事件。
  Q Given 與 Then，是否分別對應規格狀態表的「前一狀態」與「後一狀態」？預期：是。
```

#### 範例二：跨邊界步驟

【輸入】

```text
UC 場景步驟：
  應用程式首次啟動，使用者觸發一項需要作業系統原生檔案選擇器回應的操作
```

【產出】

```text
形態：契約表（測試票 how 語言）

驗證「{UC-ID} 步驟 {N}」：
  Given 應用程式首次啟動，無已存狀態（fixture: {對應 fixture 名稱}）
  When  使用者觸發需系統原生檔案選擇器回應的操作
  Then  畫面進入載入中狀態，顯示骨架版面與進度
  測試形態：widget（app 端）+ 實機驗證（系統原生 UI）
  驗證形態：兩者
```

【驗證】

```text
檢驗問句：
  Q 系統原生檔案選擇器本身的顯示與互動結果，是否包含在 widget 測試的驗證範圍內？預期：否。原生檔案選擇器的顯示與互動結果由平台決定，歸實機驗證；widget 測試只驗證 app 端收到選擇結果前後的狀態。
  Q 測試形態欄位，為何同時列出兩種形態？預期：本步驟含一個離開 app process 的子步驟，即原生檔案選擇器，也含一個 app 內部子步驟，即畫面狀態轉換；依「跨邊界步驟：平台決定」判準，兩種子步驟分別對應不同測試層級。
```

> 此則範例與 `references/doc-handoff-test-tier-assignment.md`「跨邊界步驟：平台決定」互為對照：該檔示範子步驟的分工判斷，本則示範判斷結果如何落成測試票 how 語言。

#### 範例三：終端回饋訊息三類驗收

【輸入】

```text
規格片段（暫態提示訊息設計要求，一則訊息 key）：
  觸發事件後顯示一則暫態提示，訊息內容為 {某訊息 key} 依語系解析後的文字
```

【產出】

```text
形態：契約表（測試票 how 語言）

驗證「{SPEC-ID} §{章節} 暫態提示的訊息設計要求」對 {某訊息 key} 宣告的三類驗收：
  Given 該 key 在全部語系中的最長值（fixture: {對應語系資源集}）
  When  事件觸發後於最小視窗尺寸與設計尺寸下各渲染一次
  Then  是否出現——畫面上可觀察到該提示，且有對應的顯示時刻紀錄
        內容——顯示文字等於該 key 帶入指定參數後的語系解析值（測試內不寫該語言的散文字面）
        可讀性——顯示行數不超過上限且末行未出現省略記號
  測試形態：組合（widget：是否出現與可讀性；單元或靜態讀檔：內容與資源檔屬性）
  驗證形態：fake
```

【驗證】

```text
檢驗問句：
  Q Then 段的三類驗收，是否出現、內容、可讀性，是否可合併為一條斷言？預期：否。三類驗收對應不同測試形態，合併會使某一類驗收失去對應的測試方法。
  Q Then 段是否描述了具體框架如何儲存畫面節點，例如某種節點樹結構？預期：否。只描述使用者可觀察的結果「畫面上可觀察到該提示」，不預設任何框架的內部表示方式。
```

## 檢查清單

建立或審查測試對象目錄時確認：

- [ ] 單位為規格條目，而非使用案例場景或元件（避免與元件庫規格重複）？
- [ ] 每個測試對象的契約欄位（見「三、契約欄位表」）皆已填寫或明確標「待補」？
- [ ] 齊全判準 C1-C4 已逐條機械檢查？
- [ ] 跳過條件皆引用分層測試策略跳過條件表或元件庫規格豁免清單的具體條款？
- [ ] 測試票的 how 已依「六、派發語言」句型撰寫，含來源規格條目、fixture、斷言來源、測試形態、驗證形態？
- [ ] 終端回饋訊息類別的每一行「測試形態」欄為組合值且三類驗收齊備，未拆成三行共用同一條來源規格條目？
