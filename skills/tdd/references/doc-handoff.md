# Doc 產出物銜接 TDD 流程指引

## 目的

定義 `/doc` skill 產出物（Proposal / Spec / UseCase 需求文件）如何作為 TDD 各階段（Phase 0 前置審查、Phase 1 功能設計、Phase 2 測試設計）的結構化輸入。銜接只做**格式映射 + 語意種子**，不重新設計——doc 端的設計決策已確認，TDD 端消費它。不經結構化銜接，Phase 1 設計者缺少 doc 端已確認的設計決策，重複推導或與 doc 結論矛盾。

**設計依據**：上游需求流程→doc 的銜接是「格式移交」（一對一映射），doc→TDD 的核心是「語意轉換」（系統做什麼→怎麼驗證做對了），轉換判斷由 TDD Phase 1 設計者執行，故銜接邏輯放 TDD 端。

---

## 觸發條件（條件式，有 doc 產出物才執行）

`/tdd start` 時，偵測以下路徑是否有對應文件：

| 路徑                  | 偵測方式                                          |
| --------------------- | ------------------------------------------------- |
| `docs/spec/{domain}/` | 功能所屬 domain 有 spec 文件                      |
| `docs/usecases/`      | 有相關 UC 文件（spec 的 `related_usecases` 欄位） |
| `docs/proposals/`     | 有來源 proposal（spec 的 `source_proposal` 欄位） |

- **有 doc 文件** → 執行本銜接流程，產出「TDD 輸入種子包」作為 Phase 0/1 的預填輸入
- **無 doc 文件** → 走現有 TDD Phase 0 流程（本銜接不是必要前置條件）

---

## 執行步驟

1. 偵測 doc 文件是否存在（§觸發條件）
2. 前置閘門檢查——§前置閘門表所列檢查項全通過才繼續。檢查項因輸入缺料而無法作成通過判定者（§前置閘門「涉及 UI」界定段的「步驟未寫明呈現通道時，先回 doc 補寫通道再判定」即屬此類），一律計入不通過，不得以「尚未判定」略過該檢查項；不通過則中止銜接回 doc 端補齊（§前置閘門）
3. 執行映射（§映射表）+ UC 步驟→GWT 轉換（見 `doc-handoff-uc-to-gwt-conversion.md`）
4. 判斷整合測試 / 單元測試分工（見 `doc-handoff-test-tier-assignment.md`）
5. 產出種子包寫入 Ticket 的 Context Bundle（背景資料區）或 Problem Analysis（問題分析區）（§TDD 輸入種子包格式、含文件分級覆寫結果——Phase 0 被豁免時此項在本步驟執行）
6. 執行檢查清單確認覆蓋完整（§檢查清單）

## 前置閘門

映射品質由輸入品質決定——FR（Functional Requirement，功能需求）空則 GWT（Given-When-Then）種子無操作可轉換、UC 空則無場景步驟可映射、無交叉引用則整合測試無法追溯 UC 場景。映射前確認 doc 產出物品質足夠：

| 檢查項                     | 條件                                      | 不通過時動作                   |
| -------------------------- | ----------------------------------------- | ------------------------------ |
| Spec FR 非空               | `docs/spec/{domain}/` 有至少 1 個 FR 定義 | 回 doc 補 spec（至少 1 個 FR） |
| UC 主成功場景有完整步驟    | UC 有至少 1 個完整場景步驟。「完整」＝該步驟可同時取出「場景步驟動作」（→ When）與「場景步驟預期結果」（→ Then），缺任一者該步驟不計入；兩項各自的「可取出」依 `doc-handoff-uc-to-gwt-conversion.md`〈轉換方法〉表判定 | 回 doc 補 UC 場景步驟          |
| Spec ↔ UC 交叉引用存在     | Spec 的 `related_usecases` 有值           | 回 doc 建立 Spec↔UC 交叉引用   |
| 畫面狀態矩陣（涉及 UI 時） | spec 含畫面 × 狀態 × 操作 × 退出路徑矩陣  | 回 doc 補畫面狀態機 spec       |

任一不通過 = doc 端設計不完整，不可硬生 TDD 輸入。閘門檢查輸入存在性；輸入品質由 doc 端的 Spec 驗證流程保證（見 `/spec validate`）。

「涉及 UI」依 `.claude/skills/version-bootstrap/SKILL.md` Step 2〈UI 類判別〉呈現通道表判定：場景步驟的產物（使用者最終查看或操作的對象）落在第一列「圖形介面」即涉及 UI，第二、三列不觸發本檢查項；步驟在應用程式內的觸發動作（按下按鈕、選單等）不單獨作為判定依據——否則任何有 app 內入口的步驟都會落入第一列。步驟未寫明呈現通道時，先回 doc 補寫通道再判定。判定只看呈現通道，不以該畫面是否本次新增或改動為條件。「圖形介面」與「非圖形的人讀呈現」在應用程式產出、版面固定的匯出檔上可能字面重疊；依 `.claude/skills/version-bootstrap/references/step-rationale.md`〈呈現通道表兩列的優先序〉，判準依查看／操作當下的呈現位置，不依版面豐不豐富——已離開本應用程式視窗、由外部程式另開檔案呈現者一律歸第二列（非 UI 類），即使版面由本應用程式產生。

### 前置閘門判定範例

以下以主成功場景其中一個步驟為例，展示「UC 主成功場景有完整步驟」與「涉及 UI」兩項檢查的判定方式。

【輸入】

```text
UC 主成功場景步驟（呈現通道：圖形介面，本應用程式渲染的視窗）：
  使用者於清單畫面（本應用程式渲染的視窗）選取一列，畫面切換為該列對應的詳情畫面
```

【產出】

```text
形態：決策表

檢查項             | 判定           | 依據
UC 主成功場景有完整步驟 | 通過   | 本步驟取出動作「選取一列」→ When 與預期結果「畫面切換為該列對應的詳情畫面」→ Then，兩者皆出自步驟的書面文字
涉及 UI            | 是，查矩陣     | 步驟的產物（切換後的詳情畫面）落在呈現通道表第一列「圖形介面」；判定只看呈現通道，不看該畫面是否本次新增或改動
```

【驗證】

```text
檢驗問句（各問句的判準出自〈前置閘門〉表該檢查項的條件欄與界定段，本段不複述其內容，只查【產出】是否據以判定）
  Q 【產出】判「UC 主成功場景有完整步驟」通過，依據欄指出本步驟取出的兩項各是哪一段文字？預期：動作「選取一列」與預期結果「畫面切換為該列對應的詳情畫面」。
  Q 【產出】判「涉及 UI」為是，依據欄指的是本步驟的哪一項？預期：步驟的產物（切換後的詳情畫面）落在呈現通道表第一列「圖形介面」。
```

## 映射表：doc 產出物 → TDD Phase 輸入

映射方向依 doc 產出物的語意層級對應 TDD 各 Phase 的輸入需求：Phase 0 需要需求邊界（Proposal 提供）、Phase 1 需要行為規格（Spec FR + UC 場景提供）、Phase 2 需要端到端路徑（UC 資訊鏈提供）。

### Phase 0 輸入映射

| doc 來源                          | → Phase 0 審查項          | 映射方式                                                                                                                                                                                  |
| --------------------------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Proposal 驗收條件                 | 需求文件完整性 → 驗收標準 | **直接使用**：Proposal「範圍界定 / 驗收條件」提供 Phase 0 需求完整性的判斷依據                                                                                                            |
| Proposal 驗收條件中的文件維護決策 | 文件分級覆寫              | **直接使用**：proposal 有「哪些文件承諾最新、配什麼機制」的決策時、逐列覆寫 `references/document-coherence.md` 分級表、結果記進種子包 Phase 0 預填；proposal 無此決策時分級表以預設值生效 |
| Spec domain 歸屬                  | 系統一致性 → 架構層次     | **直接使用**：`domain` + `depends_on_domains` 欄位供 Phase 0 檢查架構層次和依賴方向                                                                                                       |
| Spec FR 清單                      | 重複實作檢查 → 功能描述   | **直接使用**：逐一比對既有實作，確認無重複造輪子                                                                                                                                          |

### Phase 1 輸入映射（核心）

| doc 來源                                    | → Phase 1 產出種子      | 映射方式                                                           |
| ------------------------------------------- | ----------------------- | ------------------------------------------------------------------ |
| Spec FR + NFR（Non-Functional Requirement） | 功能規格文件            | **格式映射**：FR 描述→功能規格、NFR→Phase 1 非功能性需求定義的預填 |
| Spec 介面規格                               | API 介面定義            | **格式映射**：endpoint/參數/回應結構→函式簽名和資料結構定義        |
| Spec 資料模型                               | 資料結構定義            | **格式映射**：DDL/schema→Phase 1 資料結構格式                      |
| UC 主成功場景步驟                           | **行為場景（GWT）種子** | **語意轉換**：見 `doc-handoff-uc-to-gwt-conversion.md`「UC 步驟→GWT 轉換規則」 |
| UC 替代/例外場景                            | **邊界條件歸屬種子**    | **語意轉換**：替代場景→對應行為單元的邊界條件                      |
| UC 前置/後置條件                            | 驗收標準清單            | **格式映射**：UC 的成功保證→驗收標準。含可觀察結果、可計數量或門檻值者轉為量化驗收標準；僅有主觀感受描述、無可觀察對應者原文照抄並標「〔不可量化〕」，不自行發明門檻值 |

#### 驗收標準轉換範例

以下展示可量化與不可量化兩種原文情形的轉換結果。

【輸入】

```text
UC 成功保證（兩則）：
  1. 使用者送出的資料已持久留存
  2. 使用者能感受到操作已完成
```

【產出】

```text
形態：決策表

原文                       | 轉換結果                       | 判定依據
使用者送出的資料已持久留存 | 依資料識別碼查詢，回傳筆數為 1 | 「持久留存」對應一個可觀察、可計數的查詢結果，可量化
使用者能感受到操作已完成   | 原文照抄，標〔不可量化〕        | 「感受到」為主觀描述，無對應的可觀察計數或門檻值，判定不可量化
```

【驗證】

```text
檢驗問句
  Q 原文含可觀察、可計數或門檻值的描述時，是否一律轉換為量化敘述？預期：是。
  Q 原文僅有主觀感受描述且無可觀察對應時，是否仍勉強轉換為量化敘述、自行發明門檻值？預期：否。判定為不可量化，原文照抄並標「〔不可量化〕」，使該條目在清單上可與已量化條目區分，不留白。
```

### Phase 2 輸入映射

| doc 來源             | → Phase 2 產出種子 | 映射方式                                                               |
| -------------------- | ------------------ | ---------------------------------------------------------------------- |
| UC 資訊鏈整合測試    | 整合測試案例       | **直接使用**：UC 的「資訊鏈整合測試」定義直接作為 Phase 2 整合測試規格 |
| Phase 1 行為單元清單 | 單元測試案例       | Phase 1 的產出自然流入 Phase 2（非 doc 直接映射）                      |

## 執行步驟 3、4 的獨立檔（外移路由）

執行步驟 3（UC 步驟→GWT 轉換）與步驟 4（整合測試 / 單元測試分工判斷）的具體轉換規則與判斷框架已外移為獨立檔（各自為循序執行中讀者在該步驟才需要的完整程序，見 skill-design-guide `references/splitting-an-existing-skill.md`）：

- `doc-handoff-uc-to-gwt-conversion.md` — UC 步驟→GWT 轉換規則（轉換方法、無 UC 步驟的 FR → GWT 種子、轉換注意事項、GWT 種子與行為單元的分工邊界）
- `doc-handoff-test-tier-assignment.md` — 整合測試 vs 單元測試分工（分工決策框架、判斷原則、跨邊界步驟：平台決定、與 UC 資訊鏈的關係）

## TDD 輸入種子包格式

銜接流程完成後，產出以下結構寫入 Ticket 的 Context Bundle（背景資料區）或 Problem Analysis（問題分析區），使 Phase 0/1 代理人快速定位 doc 中的對應段落並取得結構化輸入（GWT 種子為完整內容；功能規格種子為路標引用，代理人需回讀 Spec 對應章節取得細節）。未寫入種子包的銜接等於未執行。

```markdown
## TDD 輸入種子包

> scaffold 文件：本種子包只在 Phase 0/1 消費時正確、Phase 1 完成即過期。
> GWT 種子是 UC 的複本、之後與 UC 的差異以 UC 為準；行為落成測試後、權威以測試為準。

### 來源文件
- Proposal: {PROP-ID}
- Spec: {SPEC-ID} (domain: {domain})
- UseCase: {UC-ID}

### Phase 0 預填
- 需求完整性：Proposal 驗收條件 {N} 項（見 {PROP-ID}）
- 架構檢查：domain={domain}, depends_on={依賴 domain 列表}
- FR 清單：{N} 個 FR（見 {SPEC-ID}）
- 文件分級：{預設生效 / proposal 覆寫}（覆寫時列出：{文件}→{級別}、機制={機制}）

### Phase 1 GWT 種子（從 UC 步驟或無 UC 步驟的 FR 轉換）

| 場景 | Given | When | Then | 來源 |
|------|-------|------|------|-------------|
| {編號} | {前置條件} | {操作} | {預期} | {UC-ID} 步驟 {N} 或 {SPEC-ID} FR-{編號} |

### Phase 1 功能規格種子（從 Spec 映射）
- 輸入定義：見 {SPEC-ID} 介面規格
- 輸出定義：見 {SPEC-ID} 介面規格
- 資料結構定義：見 {SPEC-ID} 資料模型
- NFR 預填：見 {SPEC-ID} NFR 章節
- 邊界條件歸屬：{UC 替代/例外場景 → 對應 GWT 種子編號}
- 驗收標準：{UC 前置/後置條件 → 量化指標}

### 整合測試映射（直接使用 UC 資訊鏈）
- {UC-ID} 資訊鏈：{鏈路描述}

### 待 Phase 1 設計者判斷
- [ ] GWT 種子→行為單元拆解粒度
- [ ] 邊界條件歸屬
- [ ] 跨模組共用決策（Q1-Q2）
- [ ] 非功能性需求具體數值（Q5-Q6b）
```

## 新專案起手模式

doc 產出物完整時（多份 Spec + 多個 UC），可用「批量 BDD 設計」取代逐功能 Phase 0/1/2。

### 流程

```text
doc 完整產出（Proposal + Spec + UC）
    │
    v
批量 BDD 測試設計 ANA（Phase 1+2 合併）
  → 全專案 UC→GWT→單元測試清單→測試檔案結構→Mock 策略
    │
    v
批量紅燈 ticket 建立（按模組群組拆分）
    │
    v
批量紅燈撰寫（並行派發）
    │
    v
實作讓綠（可按模組群組或一次性）
```

### 模組群組切法

「按模組群組拆分」的模組群組以 spec 的 `domain` 為單位；單一 domain 產生的紅燈票超出任務拆分閾值（見 `.claude/rules/core/cognitive-load.md` 任務拆分閾值表）時，再依架構層進一步切分。

### Phase 0 豁免條件

當 doc 產出物已含以下資訊時，Phase 0（架構審查）可簡化或跳過：

| doc 已提供                           | 對應 Phase 0 審查項 | 判定                |
| ------------------------------------ | ------------------- | ------------------- |
| Spec `domain` + `depends_on_domains` | 架構層次 + 依賴方向 | 已有 → 跳過         |
| Spec 介面規格                        | 重複實作檢查        | 已有介面定義 → 跳過 |
| Proposal 驗收條件                    | 需求完整性          | 已有 → 跳過         |

**三項全有 → Phase 0 可跳過**，直接從 Phase 1 開始。部分有則簡化 Phase 0（只補缺項）。文件分級覆寫**不隨豁免消失**：Phase 0 跳過時、覆寫動作移到本銜接流程的種子包產出步驟執行（proposal 越完整、越可能觸發豁免、而覆寫的輸入正來自 proposal——跳過 Phase 0 不能連帶跳過它）。

### 與逐功能模式的區別

| 面向        | 逐功能模式（增量開發） | 新專案起手模式             |
| ----------- | ---------------------- | -------------------------- |
| Phase 0     | 每功能一輪             | 跳過（doc 已涵蓋）         |
| Phase 1+2   | 分開執行               | 合併為「BDD 測試設計 ANA」 |
| 粒度        | 行為單元               | 模組群組                   |
| 紅燈 ticket | 每功能一個             | 按模組群組批量建立         |
| 實作 ticket | 1:1 對應測試           | N 測試 : 1 實作（按模組）  |

## 檢查清單

銜接執行完成後確認：

- [ ] 前置閘門表所列檢查項全通過？（不通過則中止銜接，回 doc 端補齊）
- [ ] Phase 0 預填已對應 Proposal 驗收條件 + Spec domain + FR 清單？
- [ ] 每個 Spec FR 都有對應的 GWT 種子或整合測試覆蓋？
- [ ] UC 主成功場景每個步驟都轉換為 GWT 種子？
- [ ] UC 替代/例外場景都歸屬為某個 GWT 種子的邊界條件？
- [ ] 整合測試 vs 單元測試分工已標註？（判斷框架見 `doc-handoff-test-tier-assignment.md`）
- [ ] 輸入種子包已寫入對應 Ticket？
- [ ] 種子包頂部帶 scaffold 標記（消費時點 + 爭議以 UC 為準）？（文件分級原則見 `references/document-coherence.md`）
- [ ] 文件分級覆寫已執行並記進種子包？（proposal 無此決策時也要標「預設生效」——沒標與沒做在種子包上長得一樣）

## 追溯矩陣初始化

doc-handoff 銜接時，同步初始化 `docs/traceability.yaml` 的骨架：

1. 讀取各 UC 的場景（主成功 + 替代 + 例外）
2. 為每個場景建立 entry（integration_tests + unit_tests 空映射）
3. 填入 spec_frs 對應（從 UC 的 `related_specs` + Spec 的 FR 編號）
4. status 初始為 `gap`，測試撰寫後改為 `covered`

### 追溯矩陣建立範例

以下示範「為每個場景建立 entry」的粒度判定：以使用案例場景為單位，而非以 GWT 種子為單位。

【輸入】

```text
UC 主成功場景：一個場景，含步驟 1、步驟 2 兩個步驟
GWT 轉換結果：步驟 1 因宣告兩個各自可獨立驗證的預期結果，拆為種子 1a、1b；步驟 2 轉為種子 2
```

【產出】

```text
形態：契約表

entry 對象 | 是否建立 entry
該主成功場景 | 是（一個場景一個 entry）
種子 1a     | 否（不另立 entry）
種子 1b     | 否（不另立 entry）
種子 2      | 否（不另立 entry）
```

【驗證】

```text
檢驗問句：
  Q entry 的建立單位，是否比照 GWT 種子（一個種子一個 entry）？預期：否。entry 以使用案例場景為單位；同一場景拆出的多個種子，仍共用同一個 entry。
  Q 一個場景因步驟拆出多個種子，entry 數量是否隨之增加？預期：否。entry 數量只隨場景數量增加，與該場景拆出多少種子無關。
```

**邊界回補流程**：測試撰寫者發現 UC 未描述的邊界時，在 `boundaries:` 區加 gap entry，PM 檢視後建 DOC ticket 回補 UC/Spec。Phase 4 掃描所有 `status: gap` 確認無遺漏。
