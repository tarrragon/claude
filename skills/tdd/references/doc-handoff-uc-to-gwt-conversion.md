# UC 步驟→GWT 轉換規則

> **何時讀**：`doc-handoff.md` 執行步驟 3（執行映射 + UC 步驟→GWT 轉換）需要具體轉換規則與範例時；或已知道要把 UC 場景步驟／無 UC 步驟的 FR 轉換為 Given-When-Then 格式，需要查對照規則、跨步驟狀態累積、角色切換等細節時。
>
> **同目錄**：入口檔 `doc-handoff.md`（觸發條件、前置閘門、映射表、種子包格式等在此）；姊妹檔 `doc-handoff-test-tier-assignment.md`（整合測試 vs 單元測試分工）；`test-object-catalogue.md`（測試對象目錄，本檔〈GWT 種子與行為單元的分工邊界〉的登載對象，見該檔 `test-object-catalogue-starting-points.md` 起點 A）。
>
> **溯源**：原為 `doc-handoff.md` 的〈UC 步驟→GWT 轉換規則〉節，補齊範例後全檔超出單檔 token 門檻；依讀者任務三問判定本節是讀者在執行步驟 3 時才需要的完整轉換程序，外移為獨立檔（搬移程序見 skill-design-guide `references/splitting-an-existing-skill.md`）。

這是 doc→TDD 銜接的核心語意轉換。GWT（Given-When-Then）是 TDD Phase 1 的標準行為描述格式，UC 步驟是使用者視角敘事，轉換為 GWT 使行為單元可直接對應測試案例。每個 UC 場景步驟轉換為一個或多個 GWT 格式的行為場景種子（拆分規則見〈轉換方法〉）。

## 轉換方法

| UC 元素          | → GWT 元素 | 規則                              |
| ---------------- | ---------- | --------------------------------- |
| 場景前置條件     | Given      | UC 的「前置條件」+ 該步驟的上下文 |
| 場景步驟動作     | When       | 「可取出」＝步驟的書面文字本身寫出該使用者/系統操作 |
| 場景步驟預期結果 | Then       | 「可取出」＝步驟的書面文字本身寫出該預期回應/狀態變更；不得由動作推導——步驟只寫動作而未寫出結果者，視為取不出此項 |

## 無 UC 步驟的 FR → GWT 種子

Spec FR 沒有對應 UC 步驟承接時，適用以下映射：

| FR 元素     | → GWT 元素 | 規則                   |
| ----------- | ---------- | ---------------------- |
| FR 前提     | Given      | 作為前提狀態           |
| FR 觸發條件 | When       | 作為觸發動作           |
| FR 宣告結果 | Then       | 作為預期回應或狀態變更 |

來源欄標記為 `{SPEC-ID} FR-{編號}`。FR 未定義觸發條件時不產生 GWT 種子，改標記「僅整合測試覆蓋」並附理由。

**一步驟多結果的拆分**：一個場景步驟宣告多個預期結果，且各結果對應不同的 Given 或 When（不同輸入分支、不同觸發條件）時，每組 Given／When 各拆為一個種子（例：5a、5b），因為一個 GWT 只有一個 When。同一組 Given／When 產生多個預期結果時，拆為多個種子（不合併為單一種子的多重 Then）。本段主詞為「一個場景步驟」，不限於本節（無 UC 步驟的 FR）——UC 場景步驟（見上文〈轉換方法〉）出現同樣的多結果情形時同樣適用。

## 轉換注意事項

- **跨步驟狀態累積**：UC 步驟有序，後續步驟的 Given 必須包含本步驟所依賴的前序累積狀態，不可假設各 GWT 場景獨立。「依賴」的判斷標準：缺少該狀態時，本步驟的 When 無法執行，或 Then 的結果會不同；不符合此判斷標準的前序狀態不必列入 Given，但列入亦不算錯誤。例：步驟 3 為「使用者查詢自己送出的事件」時，其 Given 須含步驟 1 建立的 session（無 session 無法查詢）與步驟 2 送出的事件（無事件則 Then 不同）。
- **角色切換**：UC 可能在步驟間切換操作者（使用者操作 vs 系統自動行為）。When 欄位應標注操作者，避免角色資訊在轉換中丟失。
- **替代／例外場景歸屬**：替代／例外場景是主場景的分岔路徑，歸屬分岔點所在的步驟；該步驟轉出的 GWT 種子，即為邊界條件的掛載點。分岔點橫跨兩個以上主場景步驟時，另立獨立種子，Given 寫到分岔前的累積狀態。

## 轉換注意事項範例

以下各以一個情境示範「跨步驟狀態累積」與「角色切換」兩項注意事項的判定方式。

**範例一：跨步驟狀態累積**

【輸入】

```text
UC 主成功場景（連續兩步驟）：
  步驟 1：使用者建立一筆草稿並送出，草稿轉為已送出狀態
  步驟 2：使用者查詢方才送出的項目，畫面顯示該項目
```

【產出】

```text
形態：契約表（GWT 種子）

場景   | Given                                 | When         | Then
步驟 2 | 已存在一筆已送出狀態的項目（承接步驟 1 產生的狀態） | 使用者查詢該項目 | 畫面顯示該項目
```

【驗證】

```text
檢驗問句
  Q 步驟 2 的 Given，是否只描述步驟 2 本身？預期：否。跨步驟時，Given 須承接前序狀態；此例為已送出狀態的項目。
  Q 步驟 2 的 When，未依賴的前序狀態，是否仍須列入 Given？預期：否。只須列本步驟所依賴的前序狀態（判斷標準見〈轉換注意事項〉「跨步驟狀態累積」一條：缺少該狀態時 When 無法執行或 Then 結果會不同），不須逐條列出全部前序狀態；列入未依賴的狀態亦不算錯誤。
```

**範例二：角色切換標注**

【輸入】

```text
UC 主成功場景步驟：
  使用者送出一筆請求後，系統自動將該筆請求標記為已處理
```

【產出】

```text
形態：契約表（GWT 種子）

場景   | Given             | When                   | Then
本步驟 | 使用者已送出一筆請求 | 系統：將該筆請求標記為已處理 | 該筆請求狀態變更為已處理
```

【驗證】

```text
檢驗問句
  Q When 欄位的操作者，是否維持與前一步驟相同，皆為使用者？預期：否。本步驟操作者由使用者切換為系統，When 前綴須改標「系統」。
  Q 操作者資訊是否可省略，留待讀者依上下文推斷？預期：否。角色切換時省略標注，會使操作者資訊在轉換中丟失，須明示標注。
```

## 轉換範例

以下以一個查詢情境的場景步驟為例，展示「一個場景步驟拆為多個 GWT 種子」的判定方式。

【輸入】

```text
UC 主成功場景步驟：
  查詢介面依條件回傳項目清單：不帶篩選條件時回傳全部已送出的項目；帶類型篩選條件時只回傳該類型的項目
```

【產出】

```text
形態：契約表（GWT 種子）

場景 | Given                             | When                   | Then
5a   | 已送出 3 筆項目（含 2 種以上類型） | 查詢介面未帶篩選條件   | 回傳全部 3 筆項目
5b   | 已送出包含不同類型的項目          | 查詢介面帶類型篩選條件 | 只回傳符合該類型的項目
```

【驗證】

```text
檢驗問句：
  Q 該場景步驟的預期結果，是否只有一個可獨立驗證的斷言？預期：否。原步驟同時宣告兩個預期結果，各自可獨立驗證：不帶條件回傳全部、帶條件回傳篩選結果。
  Q 一個場景步驟宣告多個預期結果，且各自可獨立驗證時，是否仍只產出一個種子？預期：否。兩個結果的 When 不同（未帶篩選條件／帶篩選條件），依〈轉換方法〉「一步驟多結果的拆分」，不同 Given 或 When 的預期結果各拆為一個種子；本步驟因此拆為 5a、5b 兩個種子。
```

## GWT 種子與行為單元的分工邊界

GWT 種子產出後，由 Phase 1 設計者（非本銜接流程）判斷行為單元粒度。以下範例示範一條分工邊界：本銜接流程的產出物只到 GWT 種子，不含行為單元拆解。種子表欄位僅限 Given、When、Then、來源四欄，依 `doc-handoff.md`〈TDD 輸入種子包格式〉種子包範本表頭「| 場景 | Given | When | Then | 來源 |」（依範本，場景欄只填 {編號}，因此是列索引，不是欄位；是否為列索引，看欄內填的是不是只有編號，不看欄名。只填編號的欄不計入四欄；填了編號以外內容的欄，不論欄名為何，都不是列索引）；行為單元或邊界條件分類等欄位超出此範圍，皆屬 Phase 1 職責。

【輸入】

```text
GWT 種子（延續前一節場景 5a、5b）
```

【產出】

```text
形態：契約表（GWT 種子表，欄位與前一節相同）

場景 | Given        | When        | Then
5a   | （同前一節） | （同前一節） | （同前一節）
5b   | （同前一節） | （同前一節） | （同前一節）
```

【驗證】

```text
檢驗問句：
  Q 本銜接流程產出的種子表是否含「行為單元」欄位？預期：否。行為單元拆解由 Phase 1 設計者判斷，不是本銜接流程的產出物。
  Q 種子表的欄位是否僅限 Given、When、Then、來源？預期：是。超出此範圍的欄位，例如行為單元或邊界條件分類，皆屬 Phase 1 職責。
```

**分工邊界**：本銜接流程負責到「GWT 種子」，行為單元拆解是 Phase 1 的職責（見 `phase1/rules.md`「行為單元識別」章節）。GWT 種子與行為單元拆解完成後，若專案已導入測試對象目錄，逐一登載為目錄條目（見 `test-object-catalogue-starting-points.md` 起點 A 步驟 A6-A7），使每個測試對象有可追溯的規格來源。
