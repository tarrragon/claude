# skill-sync 版本紀錄

新到舊。版號有三個住址，bump 時必須一起動：本檔最上方的 `**Version**:` 條目、`SKILL.md` frontmatter 的 `metadata.version`、`pyproject.toml` 的 `project.version`。三者相等由 `tests/test_cli.py::test_three_version_addresses_agree` 斷言，漏動任何一處測試即紅並印出三個值。（`uv.lock` 也帶版號，但由 uv 依 `pyproject.toml` 自動重算，不是人工住址。）版號規則見專案的 skill 同步規範。

**Version**: 1.24.0 — Removes the `_skill_exists_in_canonical` alias 1.22.2 kept for one version, and finishes the terminology change in the test suite, where 14 places outside the portability-gate section still called the publish repo "canonical". The alias is removed rather than kept because it never protected anything: 1.22.0 had already changed that function's parameter from a repo URL to an already-cloned working directory, so an external caller holding the old name was passing a URL string into a `Path` operation and failing one version before the rename. An alias preserves a name, not a contract, and preserving only the name here meant an importer's failure mode changed from `AttributeError` (which names the problem) to `TypeError` deep inside the function (which does not). Nothing in the originating project imports it: the project-level importers of this module reach for `sync_status_report`, `check_portability`, `_resolve_hook_logs_dir` and `_extract_single_version`, never this one. The test asserting the alias resolved to the renamed function is removed with it. On the test suite: the remaining occurrences were prose in sections unrelated to the gate (divergence warnings, sync base, hook-logs resolution), left in place when the rename landed because they sat outside that ticket's declared file scope; two of them meant the framework canonical repository rather than the publish repo and now say so, and one meant "the canonical location on disk" in the ordinary English sense, reworded to avoid the overloaded word entirely.

**Version**: 1.23.0 — `SKILL.md` gains a "Before you push: resolve direction first" section stating the default order of operations: determine direction (the no-name `skill-sync pull` report, or a `push <name>` preview read without confirming), pull first if the remote is ahead, check afterwards that local-only changes survived the pull, restore anything it overwrote, then push. Nothing in the tool changes — this adds no gate and no CLI behavior, and every step was already possible before. It is written down because the step people skip, step 3, is the one that loses work: a pull overwrites the local copy wholesale, and the only signal it gives is a count of files updated, which says nothing about intent lost. The section exists on the strength of a real run rather than a hypothetical: following this order on `skill-design-guide` pulled 1.11.1, surfaced a local backtick correction the pull had overwritten, restored it, and pushed 1.11.2. The operator was not looking for that conflict and did not know it was being tracked as a separate concern at the time — the order caught it anyway, which is the argument for following it by default rather than only once a conflict is already suspected.

**Version**: 1.22.2 — Terminology only, no behavior change: this tool no longer calls the skills repository it pushes to "canonical". A project installing this tool can have two upstreams — `tarrragon/claude-skills`, which this tool syncs, and `tarrragon/claude`, which holds a whole `.claude/` framework and syncs through a separate project-level script — and this code used "canonical" for the first while the surrounding project used it for the second. One word, two repositories, opposite directions. That collision has already cost a round trip: an agent authorised to "push to the publish repo, do not push to canonical" read the two names as one repository, judged the instruction self-contradictory, and stopped; a reader resolving the ambiguity the other way would have pushed to the wrong place instead of stopping, which is the worse failure and the reason this is worth a release of its own. `_skill_exists_in_canonical` is now `_skill_exists_in_publish_repo`, with the old name kept as a module-level alias for this one version (a test asserts the alias resolves to the same function; both go away next version). Every remaining use of the word in `cli.py` and `SKILL.md` that meant the skills repository now says publish repo / 發佈庫, and the two places that genuinely meant the framework repository now say so explicitly rather than relying on the reader to tell which was which. `SKILL.md` gains a terminology section at the top naming both repositories and stating that everything below refers to the publish repo. One observable output change comes with this: the portability force log's `already_in_canonical` field is now `already_in_publish_repo`, and the "already exists in the canonical repo" note now reads "already exists in the skills publish repo" — the field has no reader outside this package's own tests, and leaving the old spelling would have preserved the ambiguity in the one artifact written specifically to be read later during an audit.

**Version**: 1.22.1 — Adds `test_three_version_addresses_agree`, asserting this file's leading `**Version**:` entry, `SKILL.md`'s `metadata.version` and `pyproject.toml`'s `project.version` all carry the same string. The three are touched by different motivations — writing a changelog entry, editing the skill's documentation, adjusting packaging — and nothing checked them against each other: the existing stale-version gate compares `SKILL.md`'s version against content hashes only, and is blind to the other two. Two divergences landed on a single day: `pyproject.toml` sat at 1.0.0 while this file had reached 1.18.0, and three bumps later `SKILL.md` sat at 1.18.0 while this file had reached 1.21.0. A rule saying "remember to change all three" does not work against this failure mode, since the failure is forgetting rather than disagreeing, so a test carries it instead. A second test pins each reader against synthetic files with three deliberately different versions — without it, the first test cannot distinguish "all three agree" from "all three readers returned `None`". Verified against a mismatched copy in an isolated directory: the assertion fails and names all three values with the offending one visible. `uv.lock` is deliberately not a fourth address: uv recomputes it from `pyproject.toml`, so it self-corrects rather than drifting. The header of this file said there were two addresses; corrected to three.

**Version**: 1.22.0 — `push <name>` cloned the remote repo twice per run. The portability gate's "already exists in the canonical repo" note reads the remote `versions.json`, and since 1.17.0 that read is itself a clone (`fetch_remote_manifest`, blob-less sparse) — but the push body then clones the same repo again for the diff and the commit, and the file the first clone existed to read is already inside the second one. Two round trips for one push, on every push of a skill carrying any violation at all: the common case rather than the exception, since framework-bound skills legitimately name `.claude/` paths and the gate only consults the remote when it has violations to report. `_skill_exists_in_canonical` now takes the already-cloned working directory instead of a repo URL and reads `versions.json` out of it, and `_report_portability` correspondingly takes `repo_dir` instead of `repo_url` and no longer reaches the network itself — the judgement source is unchanged (the repo-root `versions.json` at HEAD), and read failure still fails open to `False` exactly as network failure did, now covering a missing or malformed file. The gate consequently moved from before the clone to immediately after it, still before any file is overlaid. That ordering was deliberate and its rationale is now inverted rather than forgotten: putting the gate first saved the push clone whenever the gate aborted, but cost an extra clone on every run that did not abort. Measured against the canonical repo, the two clone shapes are not comparable in cost — the manifest fetch is 1.98s / 388 KB, the push clone 4.78s / 21.5 MB — so the trade is one whole round trip off the path every push takes, against a heavier clone on the path taken only when a skill declared `metadata.portable: true` and still carries consumer-specific references, which is an error being corrected rather than routine traffic. The no-marker revert check (1.21.0) remains a separate clone and is deliberately not folded in: it needs the full history with no `--depth` limit, which the push clone (`--depth 1`) cannot supply.

**Version**: 1.21.0 — `push <name>` gains a companion, push-side check to the report side's `[SUSPECT REVERT]`: when the local skill has no recorded `.skill-sync-base` (never pushed or pulled through this CLI before), a stale copy pushed over newer canonical content previously got zero warning — the existing three-way direction logic has nothing to compare against without a base, and correctly stays silent for that reason, but silence here means the regression lands with no signal at all. Now `_check_push_revert` walks that skill's git history in canonical the same way `_check_suspect_revert` does (shared via the new `_cloned_skill_history` context manager — one clone, one log walk, two different comparisons), and checks out each historical commit's copy of the path to hash it with `compute_content_hash`, since local content isn't a git object and can't be compared via tree hash the way `[SUSPECT REVERT]` compares remote's own history to itself. A match against anything older than the latest commit prints a `[WARNING]` naming it, and now counts toward `push --force`'s "ignored N direction warning(s)" summary and `.claude/hook-logs/skill-sync-divergence-force.jsonl` record alongside the two existing warning types, so `--force` rolling past it is accounted for the same way. Skipped entirely — and confirmed by a dedicated test that the check function is never even called — when a sync base already exists, since that path is already correctly handled.

**Version**: 1.20.0 — `push <name>` gains a report-only, incremental banned-term scan: any `.md` line the push actually adds or changes that carries a `language-constraints.md` rule-2 banned term (`文檔`/`代碼`/`默認`/etc.) prints a `[BannedTerm]` note to stderr naming the file, line, term and suggested replacement, and never blocks the push. Deliberately incremental, not whole-file: this project's own installed skills already carried 15 pre-existing banned-term lines and one genuine false positive (an unbackticked term in a terminology table) at measurement time, and a whole-file gate would re-report every one of them on every unrelated future push to those files, teaching consumers to ignore the signal exactly the way an over-broad gate always does. The term list and its three exemptions (fenced code block, inline code span, `<!-- banned-term-exempt: reason -->`) are a literal copy of `skill-banned-term-scan-hook.py`'s — skill-sync ships as a zero-dependency standalone package and cannot import from `.claude/hooks/` — kept in sync by a new project-level test, `.claude/hooks/tests/test_skill_sync_banned_term_sync.py`, asserting both copies stay identical. "New/changed line" reuses the same `difflib.SequenceMatcher` opcode mechanism the push preview's `+A/-R` line count already computes.

**Version**: 1.19.0 — `sync_status_report` gains a `[SUSPECT REVERT]` classification for the specific case where the existing three-way `[SHOULD PULL]` logic is technically correct but practically misleading: `[SHOULD PULL]` only asserts "remote moved since local's last known sync point," not "remote's move was forward." A push from a party with no `.skill-sync-base` marker of their own (never synced this skill through this CLI before) carries no direction check at all, so a stale copy pushed over newer canonical content lands with zero warnings — and every other consumer's next report shows a confident `[SHOULD PULL]` that, acted on, pulls the regression back down; the party who caused it sees only "up to date." Reproduced live in an isolated repo: pushing v1, then v2, then a marker-less consumer overwriting with v1 again produced exactly this — no warning on the harmful push, `[SHOULD PULL] local(1.1.0) vs remote(1.0.0)` on the victim's report, "up to date" on the offender's own. A parallel scenario with a marker-holding pusher attempting the identical regression correctly triggered the existing "consider pull instead of push" warning, isolating the gap to marker-less pushers specifically — likely the common case today, since the marker mechanism only matured this session. Fix: for `[SHOULD PULL]` candidates only, `_check_suspect_revert` walks that skill's git history in canonical (`git rev-parse <commit>:<path>` tree-object hashes, not `compute_content_hash`'s SHA256 — the two aren't compatible, but git's own tree hash needs no new hashing scheme and no persisted lineage data structure, since canonical's commit history already is the ancestry signal) and reclassifies a match against an older commit as `[SUSPECT REVERT]`, naming the historical commit. This is a second, deliberately separate clone (`--filter=blob:none --no-checkout`, no blob content, no working tree) from the existing shallow manifest fetch, scoped to only the (typically few) `[SHOULD PULL]` candidates — cost detailed in `SKILL.md`.

**Version**: 1.18.0 — `push --force` had a third, previously undocumented effect beyond skipping confirmation and bypassing the portability gate: it also removed the `[y/N]` stop that otherwise followed a direction warning (`_diverge_warning`) or a stale-version warning (`_stale_version_warning`). Neither check was skipped and neither warning stopped printing — `--force` only took away the forced pause that made reading either warning unavoidable, turning it into a few lines of stderr ahead of the success message. This was invisible on inspection: exit code, push outcome and even a warning still visibly printed to stderr all looked identical whether or not anyone actually read it. `cmd_push` now restates, after a successful push made with `--force`, how many of these two warnings fired (`--force ignored N direction warning(s) above`) and appends one record per push to `.claude/hook-logs/skill-sync-divergence-force.jsonl` (skill name, which of the two warnings fired) — a run with no warnings, or without `--force`, writes nothing extra and prints nothing extra. `--force`'s own `--help` text and `SKILL.md` now name all three effects instead of two.

**Version**: 1.17.1 — `pull`'s `--help` no longer claims the no-name form "update[s] all installed": that form has been report-only since the 1.x rewrite that split it from `pull <name>` (no confirmation prompt, no file copy), so the old text told a reader the exact opposite of what the command does, and a consumer script that read that text and gated stdin as a defense against an assumed write operation had nothing to actually defend against there. The subcommand-level help line and the `name` argument's help both now say the no-name form prints a sync status report and writes nothing except refreshing a stale `.skill-sync-base` marker for an already up-to-date skill (the one side effect 1.16.0 introduced) — matching what `SKILL.md` already documented correctly.

**Version**: 1.17.0 — `fetch_remote_manifest` (used by `skill-sync pull`, no name, and by the portability gate's "already in canonical" check) now reads `versions.json` via a shallow, blob-less sparse clone of the remote repo instead of fetching it from `raw.githubusercontent.com`. That HTTP path sits behind a CDN whose cache entry is created at push time and can keep serving pre-push content well over a minute afterwards — three real-world measurements against the canonical repo: 158s / 0s / 308s, bounded above by the CDN's own `max-age=300` plus polling granularity. A report run inside that window misclassified a just-pushed skill as `[SHOULD PULL]`; acting on that recommendation would have overwritten the just-pushed content with the stale remote copy — reproduced live against the canonical repo (pushed `skill-sync` itself, then saw `[SHOULD PULL] skill-sync: local(6ad19284) vs remote(4d718f9b)` sixty seconds later). The GitHub REST contents API was evaluated as an alternative and rejected: its own response still carries `Cache-Control: max-age=60` (a shorter but non-zero staleness window, measured), and anonymous callers are capped at 60 requests/hour, a ceiling a report invoked more than once a minute — routine in a multi-agent session — can hit. `pull <name>` and `push <name>` already clone git directly for this repo and have never shown this staleness (git's smart HTTP protocol resolves against the live ref, no CDN in front of it); this switches the report path onto that same mechanism rather than adding a third one, and repo/URL resolution for the manifest fetch still lives in this one function (`ARCH-BAL-016`) — cloning needs no URL derivation at all, `repo_url` passes through unchanged. `versions.json` sits at the repo root, so plain `--sparse`'s default cone-mode pattern already limits the checkout to it; no follow-up `sparse-checkout set` call is needed. `REMOTE_FETCH_TIMEOUT_SECONDS` raised 5 -> 15: a clone takes longer than a single GET under ordinary conditions (~1.8s vs ~0.5s, measured), and the old bound would false-time-out on normal clone latency.

**Version**: 1.16.0 — `skill-sync pull` (no name) now re-records `.skill-sync-base` for any skill it classifies as already up to date whose marker is missing or stale (`_refresh_stale_sync_base`). Content can reach a skill through channels other than this CLI — a project's own canonical-overlay sync script, or a hand edit — without ever touching this marker; when that happens and the remote later moves on its own, `_resolve_diverge_direction` sees `local == base_hash` go false on the wrong side and reports a `[CONFLICT]` needing manual comparison instead of the clean `[SHOULD PULL]` the situation actually is. Scope, measured against this project's own 55 marker-bearing skills right before the fix: 5 already up-to-date skills had a stale marker, plus 1 more with no marker at all despite being up to date — 6 total silently mis-tracked. The refresh only fires when local content hash already equals remote (never papering over a real divergence) and only writes when the marker actually differs from that hash (a healthy report run touches no files, keeping this path's read-mostly nature for the common case) — verified by re-running the report immediately after: 0 mismatches remained among up-to-date skills. `SKILL.md` updated to no longer claim this path "writes nothing".

**Version**: 1.15.0 — `_extract_version_string` only matched `**Version**:` anywhere or a bare, unindented `^version:` line — the frontmatter form this project's own `SKILL.md` files actually use, `metadata:` followed by an indented `  version:`, was never matched. Scope: of 60 `SKILL.md` files in the originating project, 57 use the indented form and returned `None`; only 1 (using the unindented form) extracted correctly. Consequence, all silent: the `push` preview's stale-version gate (`_stale_version_warning`, added in 1.x for the "content changed but version left unbumped" pattern) never fired for those 57, because it short-circuits to `None` the moment either side's version is `None`; the `[Version] local vs remote` preview line never printed; and `update_sync_manifest`'s `versions.json` carried no `version` field for them, so status reports fell back to showing an 8-char hash prefix with nothing to cross-reference against a changelog. The existing regression tests never caught this because their fixture builder wrote `**Version**:` — a form no real `SKILL.md` in this project uses — which matched the gate's first branch regardless of the second branch's bug. Fix: `version:` matching is now scoped to the frontmatter block (text between the leading `---` pair) and allows leading whitespace, so it reads the indented form without picking up a `version:`-looking phrase in body prose (a real risk this module's own docstrings demonstrate). `**Version**:` keeps matching anywhere, unchanged — no `SKILL.md` in this project uses it, so narrowing it carried no observed benefit and widening the change surface wasn't warranted. Verified against all 60 real `SKILL.md` files: 57 now extract correctly (up from 1); the remaining 3 return `None` because they declare no version string in any form, a separate content gap tracked outside this fix.

**Version**: 1.14.0 — `push --force` 同時控制「跳過互動確認」與「旁路 portability 閘門」兩件事，但 `--help` 只寫前者；旁路發生時，完整違規列表只印在 stderr，只收集 stdout 的呼叫端（管線只轉存 stdout 供事後稽核）除了 hook-logs 的 jsonl 外看不到任何痕跡，而 jsonl 不是使用者會主動去看的地方。`--force` 的 `--help` 文字現同時說明兩種效果；`_report_portability` 在旁路時額外把同一份違規摘要印到 stdout（與既有 stderr 版共用新抽出的 `_format_violation_lines`，避免兩份截斷邏輯各自維護而漂移）

**Version**: 1.13.0 — 補記 1.12.1 之後累積但未 bump 版號的變更（版號未動使發佈庫與本庫的內容分歧無法由版號察覺；本 skill 的分歧尤其無從察覺，`SKILL.md` frontmatter 沒有 `metadata.version`，本檔是唯一的版號住址）。兩項：(1) 可攜性掃描新增裸格式 ticket ID 比對（`W\d+-\d+`，無版本前綴）。全格式 ID 內嵌裸片段，故完全落在既有全格式命中範圍內的裸格式匹配會被排除，同一段文字不記兩筆違規。裸格式的下游危害與全格式不同：內容送進部署了引用穩定性守衛的消費端時，會因裸格式命中而阻擋該端的 commit。此正則為框架權威定義的字面複製而非 import——本套件零框架依賴，跨套件 import 會讓它無法安裝到不含該套件的環境；字面一致性由專案層級的獨立測試斷言。(2) `git rev-parse` 解析專案根目錄的邏輯抽為 `_resolve_project_root()`，`get_skills_dir()` 與 `_resolve_hook_logs_dir()` 共用。後者原用未錨定的相對路徑，經已安裝的全域 shim（`uv run --directory <skill_dir>`，cwd 恆等於 skill 自身目錄）執行時，`--force` 稽核紀錄會寫進 `<repo>/.claude/skills/skill-sync/.claude/hook-logs/`，而非該函式文件承諾的 `<repo>/.claude/hook-logs/`

**Version**: 1.12.1 — 版本紀錄搬到本檔（同目錄的 `CHANGELOG.md`）。skill 是 runtime 整份載入的檔案，而沒有任何規則要求任何人讀版本紀錄。SKILL.md 末尾留一行指過去，指令內容一個字都沒改。本 skill 的 SKILL.md frontmatter 沒有 `metadata.version`（`pyproject.toml` 另有套件版號 1.0.0），兩個住址的規則在這裡尚未套用。

**Version**: 1.12.0 — Documents the gap the 1.11.0 gate still leaves open: it scans text, not runtime behavior, so a skill can pass with zero violations while its Python code crashes outright in a consumer lacking this framework's shared modules. Found the hard way — three declared-portable skills had seven files doing an unconditional `from lib import (...)` at load time, invisible to the text scan, and undetected across two review passes that both looked at a config-file fallback branch below the crash point rather than the crash point itself. `metadata.portable: true` now has a stated floor: prose is portable in the sense the gate checks; code is only guaranteed not to crash, not to be dependency-free — the minimum being a `try`/`except ImportError` with a `[WARNING]` naming what's missing, plus placeholder objects for any of the failed import's names that also appear in module-level type annotations (those evaluate at load time regardless of the `try`/`except`, a second trap the same incident surfaced).
**Version**: 1.11.0 — Closes three gaps in the 1.8.0 portability gate found during its own Phase 4 review. (1) `--force` bypassing a declared-portable skill's violations now writes the violation list to `.claude/hook-logs/skill-sync-portability-force.jsonl` before proceeding — previously a bypass left no trace of what was overridden. (2) An undeclared skill that already exists in the canonical repo (found via the same `fetch_remote_manifest` the report path already uses) now gets a suggestion, appended to its existing one-line count, to declare `metadata.portable: true` if it is genuinely shared — an earlier draft of this release escalated that case to abort-on-push, but existence in canonical proves only that a skill was pushed before, not that any other consumer installed it (a consuming project can have as few as a third of canonical's skills), so aborting on it would have blocked routine pushes for framework-only tools that were never meant to travel, undoing 1.8.0's own reasoning for reporting undeclared skills instead of blocking them. (3) The scan now also reads Python files' docstrings and `#` comments (via `ast`, not full-code text matching, to avoid flagging real runtime path construction) — two already-declared-portable skills in the originating project carried unscanned `.claude/...` references in hook/script comments, invisible to the `.md`-only scan. A fourth gap — consumer-specific references phrased in Chinese natural language rather than a literal path or ticket ID — was evaluated and left undetected: no keyword list can anchor reliably without a high false-positive rate against normal prose (documented as a known gap rather than attempted).
**Version**: 1.10.0 — `pull <name>` and `push <name>` preview now shows an added/removed line count for each modified file (real line-diff, not a total-line-count subtraction — same total length can still be a full rewrite), and prints a `[WARNING]` to stderr when the recorded sync base shows the operation is going the wrong way (e.g. pushing while the base says local is unchanged and remote has moved — pushing would overwrite the remote-only change). Neither is a new gate: direction is still never enforced, only surfaced. Two incidents motivated this — a push whose preview read `~ SKILL.md` (two lines) actually reverted three improvements on canonical, and a pull whose preview read `31 file(s) updated` actually deleted 1782 lines. Both previews looked identical to a routine sync; a raw file name told a reviewer nothing about how much content it represented.
**Version**: 1.9.0 — `pull <name>` and `push <name>` now record a `.skill-sync-base` marker (this sync's content hash) on success, and `sync_status_report` reads it back to resolve a three-way direction for each diverged skill (`pull` / `push` / `conflict`), replacing the previous always-ambiguous two-way comparison for any skill that has synced through this mechanism at least once. `skill-sync pull` (no name) groups its report accordingly: `[SHOULD PULL]` / `[SHOULD PUSH]` / `[CONFLICT]` / `[DIVERGED]` (the last one is the old output, kept unchanged for skills with no recorded base). Previously `versions.json` carried only the current hash and version, with no record of what was last synced; a hash comparison alone cannot tell which side moved, so every divergence — five out of six being an unambiguous drift, one an actual conflict — needed the same manual review, and one misjudged case overwrote canonical content with a stale local copy, reverting another consumer's changes.
**Version**: 1.8.0 — `push` gains a portability gate (`check_portability` / `_is_portable_declared`). A skill declaring `metadata.portable: true` cannot push markdown that names another project's files or embeds a project ticket ID; both were observed causing real damage across consumers — 58 references pointing at one consumer's framework directories broke on every other consumer, and a single ticket ID inside a version note made a downstream publish pipeline derive the wrong version and abort. The declaration lives in the skill rather than in a list held by this CLI, so the judgement travels with the skill it describes. Skills that do not declare portability are reported and not blocked: 44 of 57 skills in the originating project carry such references, and most are framework-bound tools for which those paths are the subject matter rather than a defect.

**Version**: 1.7.0 — `sync_status_report` / `_classify_sync_status` gain an optional `excluded_skills` parameter and `SyncStatus` gains a new `excluded_by_policy` category, distinct from `overridden` (override means "local content is deliberately customized, a remote copy still exists to compare against"; excluded-by-policy means "the remote is not supposed to have this skill at all"). This module still reads no policy of its own — a caller (project-level consumer) passes the names in. Documented boundary: `skill-sync pull` (no name) does not pass this and is unaffected.
**Version**: 1.6.0 — `update_sync_manifest` 與 `_extract_local_manifest` 掃描時，對「目錄內無精確大寫 `SKILL.md` 但存在其他大小寫變體」輸出 stderr 告警，不再靜默略過。此前這類目錄不進入 manifest，手動補寫的記錄會被下一次重算抹除，形成補齊後回退的循環。判準讀 `os.scandir` 的真實 dirent 名稱——`Path.exists()` 在 case-insensitive 檔案系統上對小寫檔回 True，`Path.glob()` 的大小寫敏感性則同時受 Python 版本（3.13 起改為探測檔案系統）與檔案系統影響，兩者當判準都會失效。同檔 docstring 原稱 glob 在 posix 平台恆為 case-sensitive，一併更正為版本相依的準確敘述。
**Version**: 1.5.0 — Documentation correction. The `skill-sync pull` (no name) row claimed it pulls outdated skills automatically and reports conflicts where the local copy is newer; it does neither. That path writes nothing, and a content hash cannot tell which copy is newer — the wording described behaviour removed when hash comparison replaced version-string comparison. Every other row was re-checked against the code in the same pass: `--force` and `-m` were undocumented, `list` also prints non-skill root entries, and the `.skill-sync-override` marker was absent from the notes entirely. `compute_content_hash` now states why it must not be confused with the identically named function in `.claude/lib/sync_exclude_manifest.py`.
**Version**: 1.4.0 — `--prune` now honours `EXCLUDE_DIRS` when removing directories the deletion emptied, so an already-empty `project-integration/` survives; previously the sweep was unconditional and the "cannot reach them" guarantee above held for files only. `unlink` tolerates a missing target and `rmdir` tolerates `OSError`, so a symlinked or unwritable directory no longer aborts a push midway through an already-modified clone. `cmd_push` folds the diff and the prune decision into one plan via `build_push_plan`, and `print_diff_preview` no longer takes a `prune` argument — callers no longer keep two views of the same policy in sync by hand.
**Version**: 1.3.0 — Adds a public `sync_status_report(skills_dir)` that owns repo resolution, manifest fetch and classification in one call, so a consumer needs one entry point instead of assembling the middle of the pipeline itself. A consumer that re-derived the fetch also re-derived the repo it pointed at, and ended up comparing local content against a different remote than this CLI used (see `ARCH-BAL-016`). Diverged entries now carry their own `pull_command` / `push_command`, so consumers print what this module says to run rather than keeping a hand-written copy that drifts from the actual subcommands. Remote fetch timeout drops from 10s to 5s.
**Version**: 1.2.0 — Adds `--prune` to `push`: deletes remote-only files when asked, keeps them by default. Without it a file deleted or renamed locally never reaches the remote, and other consumers keep pulling it down (observed: four hooks removed or renamed locally still sitting in the canonical repo). Also extracts `build_parser()`, so a downstream project that prints a `skill-sync` command can assert in a test that the subcommand exists.
