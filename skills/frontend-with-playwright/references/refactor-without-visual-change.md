# Refactor Without Visual Change

整理 CSS（改成引用 token、刪重複、合併 class、拿掉 `!important` 或 id 加權）而要確認畫面沒變時的流程：先把畫面做對再只換寫法、用計算後樣式快照與截圖當基準、比對結果的三種歸類與什麼時候退回、`!important` 與加權的替代寫法、擋住新的寫死值的檢查，以及派 agent 做整理時 prompt 要寫的範圍與驗收。id 加權指用帶 id 的選擇器提高特定性（specificity），讓一條規則贏過別的規則。

適用：重構既有 CSS、派 agent 做「只整理、不改外觀」的任務、驗收別人的 CSS 整理。
不適用：刻意改設計的工作（那是新的畫面，驗收對象是設計稿或契約，不是舊版畫面）。

> **自包含聲明**：閱讀本文件不需要先讀其他 reference。量 computed style 的基本寫法見 `playwright-in-loop.md`〈位置 2：行為驗證（規則寫完後）〉；token 該怎麼分層、擋寫死值的檢查怎麼寫，在專案安裝的元件庫 skill（`component-contract-design` 的 `references/design-system-token-layer.md`），沒有安裝時本文件的流程照樣成立。

| 要派 agent 做 CSS 整理 | 照〈派 agent 做整理時寫進 prompt 的事〉寫範圍與驗收 |

## 兩階段：先把畫面做對，再只換寫法

重構是只換寫法、不換結果的改動，驗收的對象是瀏覽器算出來的值，所以要有一個「結果正確」的版本當基準。畫面還在改的時候整理 CSS，比對的人分不出每一處差異來自畫面的修正還是整理時改壞的。

1. **第一階段：畫面做對**。照設計稿或元件契約改到正確，提交。這一版是基準。沒有設計稿也沒有契約時（接手的舊專案），以目前提交的那一版當基準，已知的畫面錯誤另外列成清單，不在整理的批次裡修。
2. **第二階段：只換寫法**。一批只做一種改動（顏色與線寬一批、字級一批、拿掉加權一批），每一批開始前寫下它的**預期屬性**：做這一批的人刻意要改變計算值的那些屬性，連同每個舊值要變成的新值（對應表），加上隨它改變的版面尺寸（字級變了，元素的寬高跟著變）。只換寫法的批次（色碼換成引用同值的 token）沒有預期屬性，任何差異都是預期以外。

一批混兩種改動時，比對的人無法把差異歸到其中一種。一批的大小也有上限：每一組差異都要追得到是哪一條宣告的改動造成的，例如一批只動一個元件或一組選擇器；幾百個 `!important` 一批全拿掉時，出現差異也追不出是哪一條。拆小的代價只是多跑幾次比對。

## 基準：計算後樣式快照與截圖，各量得到什麼

**計算後樣式快照**：用 Playwright 開每一種畫面狀態，在每個測試寬度下從要比對的範圍的根元素往下走訪每個元素，記錄一組屬性的計算後值，寫成 JSON。元素依 DOM 位置配對，class 記成一個欄位、不放進配對的鍵：合併 class 或拿掉 id 的批次會改到 class 與屬性，用它們配對時，那些元素會變成「舊版有、新版沒有」，量不到屬性差異。DOM 結構也會變的批次，改用穩定的 `data-*` 屬性配對。

```js
// 在 page.evaluate 裡執行。
// PROPS：要記錄的屬性名清單，依這一批會動到的屬性挑（字級、行高、顏色、內外距、寬高、transform……）
// "app-root"：要比對的範圍的根元素 id，換成自己頁面上那一塊的根元素
const out = {};
const walk = (el, path) => {
  const cs = getComputedStyle(el);
  const rec = { class: [...el.classList].join(".") };
  for (const p of PROPS) rec[p] = cs.getPropertyValue(p);
  out[path + " " + el.tagName.toLowerCase()] = rec;
  [...el.children].forEach((c, i) => walk(c, path + "/" + i));
};
walk(document.getElementById("app-root"), "0");
```

量之前讓兩個版本拿到相同的輸入：頁面有亂數（題目順序、選項順序）時固定種子；token 來源檔與宿主頁面（host page，元件被嵌進去的頁面）的 CSS 固定在同一個版本，版本記進比對的範圍（整理期間有設計師改了 token、或宿主主題升級時，只換寫法的批次會出現跟這次改動無關的差異）；等 `document.fonts.ready` 之後再讀值；快照腳本另外記錄 `<details>` 的 `open` 這類由腳本設定的 DOM 狀態，比對時才分得出差異是不是來自狀態不同。要確認字型確實載入了（例如合併 CSS 之後），看網路回應與 `FontFace` 的 `status`，而且只在頁面確實有用到那個字族的文字時判讀（沒有用到、或字元不在 `unicode-range` 裡的字型會一直停在 `unloaded`）；不用 `document.fonts.check()`（沒有任何字型符合時它也回傳 `true`）。

**截圖**：逐像素比對抓得到 2px 的位移，也不受屬性清單限制；但截圖的差異不帶元素與屬性，看的人無法分組，在刻意改值的批次上讀不出哪些差異是預期的。

兩者量不到的情形不同，所以兩種都要：

| 情形 | 快照 | 截圖 |
|------|------|------|
| 某個按鈕的行高從 24px 變成 26px | 抓得到，而且知道是哪個元素的哪個屬性 | 抓得到位移，不知道原因 |
| 沒放進屬性清單的屬性變了 | 抓不到 | 抓得到 |
| 兩個版本共有的錯誤（整頁水平溢出） | 抓不到：比對只驗兩版相同 | 截圖尺寸變寬時看得到；另外量 `document.documentElement.scrollWidth` |
| 字級收斂批次裡，哪些差異是預期的 | 依屬性分組讀得出 | 讀不出 |
| 不在畫面上的元素（`display: none` 的子樹，例如未開的 `<dialog>`；未展開的 `<details>` 的內容，瀏覽器用 `content-visibility: hidden` 跳過它的繪製）與 transition 時長 | 抓得到計算值；寬高這類排版屬性沒有排版可依，讀到的值不一定是展開後的值，這幾項的差異要在展開的狀態下量 | 看不到 |

**比對的範圍**要寫下來，範圍外的 0 差異是沒有量過：

- **狀態**：hover、`:focus-visible`、按下、`prefers-reduced-motion`、`pointer: coarse`、`<details>` 展開這類由 DOM 決定的狀態。
- **變體**：受影響的元件每一種變體都要在頁面上，頁面上沒有的另外插入（例如 `<a>` 形式的按鈕）。
- **寬度**：每個斷點與每個容器查詢區段各一個，取區段內部的值，不取邊界值。
- **瀏覽器**：只量一個時寫出名稱與版本。
- **輸入的版本**：token 來源檔、宿主 CSS 的版本。
- **走不到的元素**：`children` 只列出一般的子元素，不含 shadow root 裡的元素；偽元素（`::before`、`::after`）要另外用 `getComputedStyle(el, '::before')` 量；`:visited` 的樣式 `getComputedStyle` 讀不到，改成讀出套用到 `:visited` 的規則，依特定性與出現順序判斷哪一條勝出。

同一個版本量兩次都是 0 差異，只代表量到的那些元素與狀態是穩定的，不代表範圍外也穩定。

## 比對結果的三種歸類

比對腳本依「屬性、舊值、新值、元素的 class」分組，結尾印出比對了幾個元素、幾個屬性，以及兩邊配對不上的鍵有幾個（配對不上的鍵不是 0 時逐一列出）；只走舊版的鍵、略過配對不上的鍵的比對，印出來會跟「0 差異」一樣。每一支快照比對腳本第一次用時跑一次正對照（positive control）：在新版注入一條會改變計算值的規則（例如 `.x { line-height: 99px }`），確認比對報出它。比對的人逐組歸到三種之一：

1. **0 差異**：在記錄的範圍內兩版相同。
2. **差異都在預期屬性上**：每一組的舊值 → 新值要對得上這一批開始前寫下的對應表（字級收斂計畫把 15px 併到 16px，量到 15px → 14px 就不算）。寬高的差異要出現在自己或子孫的字級、行高（或內距）也有差異的元素上，才算隨字級改變的預期內差異；其餘的寬高差異歸第 3 種（例如 `<details>` 展開時序不同而只改了高度的元素）。
3. **預期以外的差異**：依序分兩層判：
   - **來自量測**：差異來自 CSS 改變不了的狀態（腳本設定的展開與否、讀值的時序），或同一個版本量兩次結果就不同。判成這一種時附上證據：舊版自己量兩次的差異輸出，或快照裡記下的 DOM 狀態不同。不算改動造成的，修量測腳本再量。
   - **來自改動**：差異出現在 CSS 屬性上時，即使那個屬性不是這批改的，先查它有沒有經由 `currentColor`、`var()` 或繼承連到這次的改動（`box-shadow` 沒寫顏色時用 `color` 的值）。確定是改動造成的之後，再讀規範判斷兩個值是否等價：等價的不算畫面改變（漸層裡的 `transparent` 與 `rgba(255,255,255,0)`），判成等價時寫出依據的規範段落；不等價的就是畫面改了。

**退回規則**：只換寫法的批次出現第 3 種裡「來自改動、不等價」的差異時，退回這一批，找出原因再做。刻意改值的批次，執行者只退回預期以外的那幾處，預期內的差異列進 commit message（屬性、舊值、新值、元素）。「有差就整批退回」只適用只換寫法的批次：套在刻意改值的批次上，每一次都會退回。

## `!important` 與加權：讀出要贏過哪一條，再選替代寫法

`!important` 與帶 id 的選擇器都是用提高優先度贏過另一條規則。拿掉之前，先讀出要贏過的是哪一條（DevTools 的 Styles 面板裡被劃掉的那條宣告，或拿掉之後量出改變的元素），再依那一條屬於誰選替代寫法：

| 要贏過的是 | 替代寫法 |
|-----------|---------|
| 同一個元件自己的 CSS 裡的一條規則 | 改寫成不跟它衝突，或用剛好高過它、或同特定性而寫在它後面的選擇器；在規則旁註明要贏過哪一條 |
| 元件自己的 JavaScript 寫的行內樣式（`el.style.transform`） | 任何選擇器都贏不過行內樣式；改成 JavaScript 切換 class 或設定自訂屬性 |
| 所有規則（`[hidden] { display: none !important }`、全站的減少動態效果重設） | 讀不出單一的那一條。相關規則都在同一份 CSS 時改寫成條件反轉（顯示的規則加 `:not([hidden])`、動態規則包進 `prefers-reduced-motion: no-preference`）；分散在很多份 CSS 或有第三方元件時保留，同一行加允許註解寫原因 |
| 宿主頁面的 CSS，宣告是一般宣告，而宿主 CSS 的載入方式管得到（檔案內容改不了也算，例如主題的 CSS 由自己的模板載入） | 把宿主放進較低的 cascade layer（`@import url(...) layer(host);`，寫在樣式表最前面），元件規則不必再比特定性；改宿主的載入方式會影響宿主的每一頁 |
| 宿主頁面的 CSS，改得了、帶 `!important` | 從宿主那一邊把元件的範圍排除；`!important` 在特定性之前就勝出，元件那一邊寫得再精確也輸 |
| 宿主頁面的 CSS 與載入方式都管不到、只有一種宿主、特定性已知 | 元件的每一條規則統一加同一個根 class 前綴，前綴的層數選到每一條元件規則的特定性都高過宿主那一條（宿主是 `.entry-content a`，(0,1,1)，元件寫 `.app .menu a`，(0,2,1)）；只跟宿主同特定性時，元件的 CSS 要排在宿主的 CSS 之後才勝出。所有規則加同一個前綴，元件內部的相對特定性不變 |
| 宿主有很多種、特定性未知或帶 `!important` | 用 Shadow DOM 或 iframe 隔開；宿主設在祖先上的顏色、字級、行高仍會被繼承，在 `:host` 重設會繼承的屬性 |

**只替部分規則加權會打亂元件內部的勝負**：加了 id 的那幾條也會高過元件自己的其他 class 規則。實例：一個元件的作者替部分規則加了帶 id 的選擇器以贏過宿主，其中連結形式按鈕的白字規則因此高過主要按鈕 hover 時的黑字規則；頁面上的主要按鈕都是 `<button>` 時看不出來，另外插入 `<a>` 形式的主要按鈕才量到 hover 時變成白底白字，拿掉 id 之後是想要的白底黑字。這類缺陷只在某一種變體與狀態的組合出現，所以〈基準：計算後樣式快照與截圖，各量得到什麼〉的比對範圍列了變體。

**加權是否還必要可以直接量**：拿掉加權，重跑快照比對。結論只對量測時在頁面上的元素、量了的狀態、量的那一種宿主頁面與那一個宿主版本成立：會受影響的選擇器，要把它的每一種變體都放進頁面、量 hover 這類狀態；元件嵌在幾種宿主頁面上就每一種各量一次。宿主是別人維護的主題時，在規則旁的註解與比對紀錄裡寫下量測時的主題版本，並設一個會在主題版本改變時重跑快照比對的觸發點（CI 對正式頁面定期重跑，或升級主題的那一次提交附上重跑結果）；沒有觸發點時，「升級之後重量」不會有人去做。

## 擋住新的寫死值：檢查在第一個整理批次之前建好

擋寫死值的檢查在第一個整理批次之前建好：整理的過程中就有人可能寫進新的 15px，而每一批結束時的違規數也是整理的進度，只減不增。這道檢查依寫法擋：

- `!important`。
- `font-size` 與 `line-height` 寫 px／rem／pt。
- 色碼、色彩函式，以及 `transparent`、`currentColor`、`inherit` 以外的色名。
- 帶 id 的選擇器（Stylelint 的 `selector-max-id: 0`，或在 diff 裡找選擇器的 `#`）；快照比對只驗得出外觀有沒有變，驗不出程式碼裡新加了 id。

接手的舊 CSS 已經有違規時，先把既有的違規記成 baseline（白名單，或「違規數不得多於 baseline」），檢查只報新增；否則每一次改到舊檔的提交都過不了檢查。

結尾印出「讀了幾個宣告、幾處違規」，一個都沒讀到時用另一個 exit code 結束。檢查讀得到哪些宣告要另外確認：

- 拿重構前的舊檔跑一次當正對照（positive control：餵進已知會違規的輸入，它應該報出很多處），正對照要跟受檢的檔案同一種形式；正對照的指令原文與它印出的計數寫進 commit message。
- 逐行比對的腳本讀得到哪些宣告依實作而定（只取每一行最後一個 `{` 之後的內容的腳本，餵進壓縮過的 CSS 時只讀到最後一條規則）。CSS 是壓縮過的、或一行寫多條規則時，改用 Stylelint 這類以 CSS parser 為基礎的工具。
- Sass 這類前處理器的原始檔裡，變數不是 CSS 宣告，檢查編譯後的產物。
- 寫死值也可能在 CSS 檔以外（markup 的 `style` 屬性、JavaScript 設定的樣式、utility class 字串）；這些位置的檢查方式在元件庫 skill 的 `design-system-token-layer.md`，沒有涵蓋的寫成「沒有量過」。

## 派 agent 做整理時寫進 prompt 的事

「只整理、不准改外觀」「只改這個元件，其他 class 不得更動」寫在 prompt 裡是範圍的說明，限定不了層疊的結果：改了一條選擇器的特定性，跟它比過勝負的每一條規則（別的元件的、宿主的）都可能翻轉。agent 對照規則檔自查，查到的是它記得的那幾條。所以 prompt 裡寫的是：

- **這一批的改動種類、預期屬性與對應表**（〈兩階段：先把畫面做對，再只換寫法〉），可以編輯的檔案。
- **基準**：第一階段那一版的 commit SHA，或派發的人事先量好的快照檔路徑。agent 拿自己改過的版本當基準時，比對結果一定是 0，跟實際比過的結果分不出來。
- **禁止的寫法與允許的例外**：禁 `!important`、帶 id 的選擇器與寫死值；例外的種類（〈`!important` 與加權：讀出要贏過哪一條，再選替代寫法〉表的「所有規則」那一列，以及 media query 條件裡的斷點值）與允許註解的格式（用檢查工具認得的格式，例如 Stylelint 的 `/* stylelint-disable-line <規則名> -- <原因> */`；自寫的檢查自訂），新增允許註解要寫出對到哪一種。
- **驗收**：整頁（不只目標區塊）的快照比對結果，連同比對的範圍紀錄（狀態、變體、寬度、輸入的版本）與比對印出的元素數、屬性數、配對不上的鍵數；依〈比對結果的三種歸類〉列出每一組差異與判定；檢查的指令原文與它印出的計數。agent 自述「已遵守」不算驗收。

## 自檢清單（dogfooding）

- [ ] 第一階段（畫面做對，或沒有設計稿時的目前版本）已經提交，整理的批次從那一版開始比對
- [ ] 擋寫死值的檢查在第一批之前建好，既有違規記成 baseline，正對照的計數寫進 commit message
- [ ] 每一批只有一種改動、大小追得到每一組差異的來源，開始前寫下了預期屬性與對應表
- [ ] 快照依 DOM 位置配對，比對印出元素數、屬性數與配對不上的鍵數，比對腳本跑過正對照
- [ ] 快照與截圖都量了；比對範圍（狀態、變體、寬度、瀏覽器、輸入的版本、走不到的元素）寫下來了
- [ ] 每一組差異都歸到三種之一，「來自量測」附了證據，「等價」寫了規範段落，「來自改動」的差異查過 `currentColor`、`var()` 與繼承
- [ ] 拿掉 `!important` 或加權之前讀出了要贏過的那一條，替代寫法對得上表裡的那一列
- [ ] 派給 agent 的 prompt 寫了改動範圍、基準、禁止與例外、整頁比對的驗收
