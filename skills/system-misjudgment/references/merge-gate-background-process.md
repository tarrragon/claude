# 合併閘門與背景程序

## MG-1 `/clear` 後分支還在，被讀成合併失敗

| 欄位 | 內容 |
|------|------|
| 症狀 | 新 session 發現 worktree 分支仍存在、main 上沒有對應 commit |
| 常見誤判 | 合併失敗，重跑合併 |
| 實際機制 | 前一個 session 啟動的閘門程序（合併、`flutter test`）在 `/clear` 後仍在背景執行，尚未結束 |
| 檢查方法 | `ps -axo pid,etime,command \| grep -E "[w]orktree|[f]lutter test"`，確認有無 merge 與測試程序；再 `git -C <repo> log --oneline -3 main` 看合併是否已落地 |
| 正向對照 | 有程序時，其經過時間（etime）應隨查詢遞增；無程序且 main 無 commit，才是真的沒合併 |
| 判讀標準 | 有程序在跑 → 等待，不重跑；無程序且分支未合入 → 才判斷是否重跑 |
| 來源 | `PC-076`、`PC-078`；`tool-output-trust-rules` 規則 5 |

## MG-2 「報告未落地」被寫成「process 已結束」

| 欄位 | 內容 |
|------|------|
| 症狀 | 收尾記錄寫「代理人已終止」，唯一依據是沒收到它的產出 |
| 常見誤判 | 沒有產出等於程序已結束 |
| 實際機制 | 產出是否交付與程序是否終止分屬兩個平面；前者可從自己 context 觀察，後者必須查 session 外部狀態 |
| 檢查方法 | 另一觀測面查證：`ps -axo pid,etime,command` 查程序是否仍在；in-process 代理人不列在 `ListAgents` 的 peer 清單 |
| 正向對照 | 對已知存活的代理人，所選的觀測面必須能看到它 |
| 判讀標準 | 狀態詞（已結束、已終止）只在查證過程狀態後才可寫；僅「無產出」只能寫成「報告未落地」 |
| 來源 | `PC-BAL-045` |

## MG-3 測試數下降，被讀成本批刪了測試

| 欄位 | 內容 |
|------|------|
| 症狀 | 合併閘門的 passed 數比上一次少 |
| 常見誤判 | 本批刪除了測試 |
| 實際機制 | 兩次合併之間的總數差，可能來自任何一條並行線的 commit，不只是本批 |
| 檢查方法 | 比對兩個 commit 之間的 test 宣告數：兩個 commit 各跑一次 `git -C <repo> grep -c "test(\|testWidgets(" <commit> -- 'test/*.dart'`（只計 Dart 測試檔；`test/fixtures` 下的 md 等非測試檔也含 `test(` 字樣，不可計入），加總各檔計數後相減；再用 `git -C <repo> log --oneline <舊>..<新> -- test/` 把差異歸因到各條線的 commit |
| 正向對照 | 對已知新增一筆測試的 commit，計數必須加一 |
| 判讀標準 | 差異歸因到具體 commit 才下結論；歸因不到本批 → 不是本批造成 |
| 來源 | 實測依據：閘門 passed 數變動的歸因過程 |

## MG-4 測試綠燈，被讀成 runtime 正確

| 欄位 | 內容 |
|------|------|
| 症狀 | 修復票測試全綠，後續行為仍未改變，或後續票以「已修好」為前提推進後回歸 |
| 常見誤判 | 綠燈等於修復生效 |
| 實際機制 | mock 取代真實依賴、斷言只查結構時，runtime 整合路徑可以完全失效而測試照綠 |
| 檢查方法 | 修復訊息、日誌、跨模組整合類問題時，驗收加 runtime 層級驗證：實機驅動 App 並觀察 log（配方見專案的實機驗證配方，如有） |
| 正向對照 | 先讓修復還原，runtime 驗證必須能重現問題；否則該驗證沒有鑑別力 |
| 判讀標準 | runtime 驗證通過且還原後能重現 → 修復生效；僅單元測試綠 → 未驗證 |
| 來源 | `PC-165` |
