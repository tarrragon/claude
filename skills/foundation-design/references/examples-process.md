# 案例集：流程操作

> 何時讀：想確認自己對 `foundation-design` skill 入口檔 `SKILL.md`〈與 orchestration 的協作〉〈工作流〉〈移植前置條件〉相關判準的理解是否正確時讀本檔。維度填答本身（產物欄怎麼填、權威缺席怎麼處置）的案例見 `references/examples.md`。
>
> 同目錄：維度與產物欄位填法的延伸細則見 `dimension-product-notes.md`；接手他人專案的盤點流程見 `handoff-mode.md`。
>
> 格式：每則範例依 `.claude/skills/skill-design-guide/references/chained-examples.md` 三段鏈式格式（【輸入】【產出】【驗證】），本檔內容皆屬「設計產出物」，驗證段一律採檢驗問句形態。
>
> 溯源：因 `examples.md` 補入 chained-examples 範例後超出單檔體量門檻，依 `.claude/skills/skill-design-guide/references/splitting-an-existing-skill.md`〈補範例後超標：觸發條件與處置順序〉拆分而成（2026-09-15），承接原檔中流程層面（非維度判斷本身）的判準案例。

本檔章節：〈文件回答不了地基問題：任一格即命中〉〈規劃波進行中與之後：地基票不算「該版票已建」〉〈產物落為地基票的粒度〉〈執法載體掃描範圍須涵蓋全部承載值的檔案〉〈降級記錄須記缺項與不成立步驟〉〈人工複核「複核者」欄的判斷順序〉。

## 文件回答不了地基問題：任一格即命中

【輸入】

```
一個現有專案已有相當規模的可執行程式碼與完整的安裝說明，但零測試、無 CI、無任何維度盤點文件。維度表六格中，「測試」與「DevOps」兩格既有文件答不出來；其餘四格（UI、資料庫、可觀測性、事件流仲裁）文件也答不出來。
```

【產出】

```
形態：決策表
  候選判定 | 內容                                                       | 結論
  甲：命中 | 只要維度表任一格既有文件答不出即命中「文件回答不了地基問題的既有實作」列 | 合格——本例六格全數答不出，遠超「任一」的最低門檻
  乙：不命中 | 須六格全部答不出才命中，只有一兩格答不出則不命中          | 不合格，見驗證段
```

【驗證】檢驗問句

```
Q 判定「文件回答不了地基問題」是否需要維度表六格全數答不出？
  預期：否——依據句「維度表中至少一格的產物，既有文件答不出——不要求六格全數答不出，一格即命中」（〈與 orchestration 的協作〉表），「至少一格」即命中，不要求全部。
```

## 規劃波進行中與之後：地基票不算「該版票已建」

【輸入】

```
某版本已由前一輪地基盤點建立三張地基票（UI 維度四塊各一，其中一張已完成），但該版功能規格對應的實作票尚未建立。本次盤點問「該版目前處於規劃波進行中還是規劃波之後」。
```

【產出】

```
形態：決策表
  候選判定     | 依據                                    | 結論
  甲：規劃波之後 | 已有票（地基票）存在，視為「該版票已建」 | 不合格，見驗證段
  乙：規劃波進行中 | 功能票尚未建，視為「該版尚未建票」      | 合格
```

【驗證】檢驗問句

```
Q 本 skill 自己前一輪建立的地基票，能否作為「該版票已建」的證據？
  預期：否——依據句「該版提案的 spec_refs 或 usecase_refs 非空（`version-bootstrap` 的 pipeline 確實跑過），且該版尚未建票」（〈與 orchestration 的協作〉表），括注明示這整條判準問的是 `version-bootstrap` pipeline 自身的產出，地基票是本 skill 的產出，不是該 pipeline 的產出。

Q 本例判定結果是規劃波進行中還是之後？
  預期：規劃波進行中——功能票尚未建立。
```

「該版尚未建票」不含本 skill 自身前一輪產出的地基票——上方【驗證】段已明示這整條判準問的是 `version-bootstrap` pipeline 自身的產出，地基票是本 skill 的產出，不是該 pipeline 的產出，故不計入「該版票已建」的判定。

## 產物落為地基票的粒度

【輸入】

```
盤點完成後，UI 維度產物為複合產物：「i18n 待建、design-system 已存在、UX 審查待建、元件庫待建」（四項狀態各自不同）；資料庫維度產物為單一「改寫產物：migration baseline」。
```

【產出】

```
形態：決策表
  候選判定         | 內容                                                                  | 結論
  甲：UI 四塊合一票 | i18n、UX 審查、元件庫合併開一張票                                     | 不合格，見驗證段
  乙：UI 四塊各自成票 | i18n 待建票、UX 審查待建票、元件庫待建票各一張（design-system 已存在不建票） | 合格
  資料庫維度       | 單一改寫產物一張票，甲乙兩候選結果相同，不構成對照                     | —
```

【驗證】檢驗問句

```
Q 「一維度一票」是否有既有先例支持？
  預期：否——依據句「四塊各自的實作票」（〈維度與產物〉表 UI 列「權威提供的預設產物」欄），已明示四塊各自成票而非合一。

Q 「已存在於 X」的產物是否仍需開票？
  預期：否——依〈工作流〉步驟 4「全部維度皆為『已存在』或『無』時不建票」。

Q 非 UI 維度內兩個需建票的子產物寫同一個檔案時，是否各自成票？
  預期：否，合併為一張——依據〈複合產物與多子樹分列〉路由至 `.claude/pm-rules/task-splitting.md`〈拆分後檢查清單〉B「共用檔案的問題已合併到同一 ticket」。
```

## 執法載體掃描範圍須涵蓋全部承載值的檔案

【輸入】

```
一個前後端混合專案，樣式規則同時寫在獨立樣式檔與標記檔內嵌樣式屬性兩處，但既有裸值執法載體只掃描獨立樣式檔這一種副檔名。
```

【產出】

```
形態：決策表
  候選判定 | 內容                                                     | 結論
  甲：通過 | 執法載體已掃描獨立樣式檔，涵蓋部分副檔名即算通過        | 不合格，見驗證段
  乙：不通過 | 須涵蓋全部承載裸值的檔案類型，標記檔內嵌樣式未涵蓋即不通過 | 合格
```

【驗證】檢驗問句

```
Q 執法載體只涵蓋部分承載該維度值的檔案類型，是否滿足移植前置條件第三項？
  預期：否——依據句「其掃描範圍涵蓋本專案實際存在的檔案？只問『有沒有』會通過一個只認特定副檔名的執法載體裝在零該副檔名檔案的專案上，該載體結構上永不觸發」（〈移植前置條件〉），「實際存在的檔案」指全部承載該值的檔案，非部分副檔名。
```

「涵蓋本專案實際存在的檔案」要求涵蓋全部承載該值的檔案類型；只涵蓋其中一部分（如本例只掃獨立樣式檔，未涵蓋標記檔內嵌樣式）視同不通過本項，不因「至少涵蓋了一種檔案類型」而算部分通過。

## 降級記錄須記缺項與不成立步驟

【輸入】

```
盤點發現被盤點 repo 沒有任何形式的決策文件（前置條件第四項缺席），需要記錄降級。
```

【產出】

```
形態：契約表
  候選記錄                 | 內容                                                                       | 結論
  甲：只記缺項             | 「本專案缺決策文件，降級處理」                                             | 不合格，見驗證段
  乙：缺項與不成立步驟皆記 | 缺項：決策文件（第四項）／不成立步驟：〈權威缺席時〉形態 1、形態 4、`handoff-mode.md`〈萃取的前提是既有 artifact 可信〉表第四列、降級記錄本身 | 合格；且依條文，本例應先建決策文件而非只記錄降級
```

【驗證】檢驗問句

```
Q 降級記錄只寫「缺哪一項」是否足夠？
  預期：否——依據句「記下缺哪一項、因此哪幾步在本專案不成立」（〈移植前置條件〉），兩者皆須記錄。

Q 缺的若是決策文件本身，正確處置是什麼？
  預期：先建立決策文件，不是只記錄降級——依據句「連決策文件都沒有時，第一個動作是建立它……否則本流程的缺席處置全部無處落地」。
```

## 人工複核「複核者」欄的判斷順序

【輸入】

```
可觀測性維度已依權威補了 log 接線點與錯誤分類骨架，機械檢查形態尚未設計，需在地基票寫複核者。該維度的權威來源（專案可觀測性規則、SaaS 技術選型 skill 的 observability 維度）皆未明訂審查角色。
```

【產出】

```
形態：決策表
  候選         | 判定
  甲：某開發者個人 | 不合格——「不得留白等待指派」，個人不是既有角色
  乙：本框架既有審查代理人 | 合格——權威來源 skill／方法論皆未明訂審查角色時，落入「或本框架既有審查代理人」分支
  複核者欄     | 本框架既有審查代理人；複核依據：可觀測性規則相關條款＋ SaaS 技術選型 skill observability 維度條款；複核產出：合格／不合格結論加理由，寫入該張地基票 Solution
```

【驗證】檢驗問句

```
Q 複核者欄是否可以留白等待指派？
  預期：否——依據句「不得留白等待指派」（〈工作流〉步驟 5）。

Q 當權威來源 skill／方法論未明訂審查角色時，複核者該落在哪一分支？
  預期：本框架既有審查代理人分支——依據句「複核者——先查該維度權威來源 skill／方法論是否已訂審查角色；已訂者用該角色，未訂時才退至本框架既有審查代理人。不得留白等待指派」（〈工作流〉步驟 5），權威本身未指名角色時退至第二來源。
```

兩個來源是先後查找順序而非任選：先查該維度權威來源是否已訂審查角色，未訂時才退至本框架既有審查代理人。具名的個人不構成此欄的合格答案——即使該人實際會執行複核，仍須落在依序查定後選中的那一個角色，不得以具名個人替代，這正是「不得留白等待指派」把答案限定在角色而非人名的理由。
