## 非 SaaS 專案的形態轉換

這三列（資料庫／DevOps／可觀測性）的權威來源 `saas-tech-selection` 以 SaaS/伺服器端專案為預設形態，對 CLI 工具、函式庫、單機 app 等非 SaaS 專案形態不符。處置依 `SKILL.md`〈權威缺席時〉「權威存在但形態不符」的既有機制——先走「改寫產物」，取權威中與形態無關的部分（例如單機 SQLite 工具仍適用 migration 版本化紀律，多租戶隔離則不適用，見 `examples.md`〈權威形態不符時的正確取用〉範例）；確認無可用部分時，那是判準層的結論，不是產物欄的答案，兩層分開填（同 `SKILL.md`〈權威缺席時〉「框架內確實無承接者」的拆兩問）。**判準層**：標「無判準」並建框架缺口票；專案自身的技術選型記錄（如 CLAUDE.md）若已涵蓋該判準，改指該記錄為替代權威並記入決策文件。**產物層**：先答〈改寫產物是主路徑〉的推導問句「這個維度要防的失效，在本專案會長成什麼樣子」——答「不存在」時（例如無任何持久化資料的 CLI 工具之資料庫維度）標「無」+ 理由（該失效為何不存在）+ 重評條件；答得出形狀時走「改寫產物」；失效可能存在但說不出形狀時標「待定」，不得以「無」代之。**不新增第二套權威**——`saas-tech-selection` 仍是這三個維度唯一的判準來源，本節只是把「非 SaaS 專案先過形態轉換」明示為預設路徑，不構成整條跳過。

## 填完產物欄仍應翻原文

實跑證實最高價值的缺口常在權威原文而不在此欄——一個有真 PostgreSQL 與 docker volume 卻零備份痕跡的服務，其最大風險是備份還原，而那條要讀到權威的防護底線才撈得到。填完產物欄後仍應翻一次權威原文。

## 複合產物與多子樹分列

**一個維度的產物可以是複合的，不必擇一。** 產物不是原子的：同一維度常有一部分已存在、另一部分待建。填「已存在於色碼常數表（符號名可查）+ 改寫產物：寬度截斷規則待落為文件」是正確答案；逼自己擇一時，選「已存在」會漏掉待建的部分，選「改寫產物」會重造已有的部分。**「待建」的部分該填哪個答案形態，仍依〈產物欄的五種合法答案〉逐列使用條件判定，不是待建就等於改寫產物**：權威預設產物對本形態成立時填「照預設」，這包含產物尚未存在、需要補建的情形——「照預設」判定後仍可能落為地基票（見 `SKILL.md`〈與 orchestration 的協作〉），「尚未存在」不是排除「照預設」的理由；符合「維度成立但預設產物對本形態不適用或有害」時填「改寫產物」。**「待定」的使用條件是該判而未能判**（見〈產物欄的五種合法答案〉）：待建的部分仍說不出它要防的失效在本專案長成什麼樣子時才填「待定」，不得逕自代入改寫產物；已判定為「照預設」或「改寫產物」者，不因它是待建而回頭改填「待定」。接手他人專案時尤其需要，別人的專案更可能是一半做過一半沒做。

複合產物落票時：「已存在」的部分不建票，「待建」的部分依〈產物欄的五種合法答案〉建補票；UI 維度依〈維度與產物〉表「四塊各自的實作票」；其餘維度同一維度內有兩個以上需建票的子產物時，票數依 `.claude/pm-rules/task-splitting.md`〈拆分後檢查清單〉B（共用檔案者合併）與 `.claude/rules/core/cognitive-load.md`〈速查三閾值〉（超標者拆）判定，本 skill 不另立分票通則。

**repo 內有多個子樹各持獨立工具鏈或獨立部署單元時，產物欄按子樹分列。** 判別看事實不看名稱：有沒有 workspaces 設定不重要，有沒有兩套以上的測試命令、建置命令或部署目標才重要。同一維度在各子樹的狀態常不同，單一格會把落後那棵子樹的缺口吃掉。

【輸入】

```
一個 repo 內有兩個子樹：子樹 A 為一個函式庫，子樹 B 為使用該函式庫的 CLI 工具。兩者共用同一份 CI 設定與同一個部署目標（皆發布為單一套件），但各自有獨立的測試命令（子樹 A 與子樹 B 使用不同的測試框架指令）。
```

【產出】

```
形態：決策表
  候選判定   | 依據                                | 結論
  甲：不分列 | 共用 CI 與部署目標，判定不需分列 | 不合格，見驗證段
  乙：分列   | 兩子樹各有獨立測試命令，符合三條件之一 | 合格
  產物欄     | 子樹 A：資料庫維度「無」；子樹 B：資料庫維度「已存在於……」——分列後兩子樹各自獨立填答 | 依「同一維度在各子樹的狀態常不同」
```

【驗證】檢驗問句

```
Q 「共用 CI 與部署目標」是否足以判定不分列？
  預期：否——依據句「有沒有兩套以上的測試命令、建置命令或部署目標才重要」，三者為條件之一即可，本例測試命令已各自獨立，滿足其一即應分列。

Q 分列後產物欄怎麼填？
  預期：各子樹各自獨立填答，不共用同一格——依據句「同一維度在各子樹的狀態常不同，單一格會把落後那棵子樹的缺口吃掉」。
```

## 改寫產物是主路徑

**改寫產物是本表的主路徑，不是例外。** 權威是從特定形態歸納出來的，套到別的形態時預設產物常需改寫。**這不是可以省略推導直接套用的個案記錄**，改寫產物的問法固定是：**這個維度要防的失效，在本專案會長成什麼樣子？** 先答這一問，再看權威的預設產物是否即是答案；若改為直接判「維度適不適用」，容易在維度其實成立時判成不適用而整塊漏掉，或在預設產物其實有害時判成適用而照做。

以下兩則示範同一工具（一個終端機 statusline 工具，其 stdout 就是產品）在**可觀測性**與 **UI** 兩個維度上，兩位讀者對推導問句給出不同答案時如何判別。

### 各維度要防的失效（權威出處）

推導問句「這個維度要防的失效，在本專案會長成什麼樣子」的起點，是各維度原本要防什麼——這一問不是本檔新立的判準，答案在維度表指名的權威原文。下表逐維度引該權威原句，供本節與其他範例的驗證段引用，不重複判準本身。

| 維度 | 要防的失效（權威原句） | 出處 |
|------|----------------------|------|
| UI | 「同一語意長出多種樣子」（元件契約「變體」欄缺失後果）；設計端判準「同一語意只有一種外觀」（樣式收斂） | 元件庫雙向約束方法論〈元件契約判準〉元件契約欄位表「變體」列；〈雙向約束判準〉設計端「樣式收斂」列 |
| 測試 | 「行為的權威載體是測試（唯一改壞當下會發聲的載體）」 | `tdd` skill SKILL.md〈核心理念〉文件連貫性原則段 |
| 資料庫 | 「不可遺失的正式狀態放哪裡、怎麼保護」；「正式狀態遺失等於事故」 | `saas-tech-selection` skill `references/dimensions/state-storage.md` 開頭段 |
| DevOps | 「壞的版本怎麼在使用者看到之前被攔下、依賴失敗時系統怎麼不跟著一起死」 | `saas-tech-selection` skill `references/dimensions/reliability.md` 開頭段 |
| 可觀測性 | 「系統壞了怎麼知道、知道了怎麼定位」 | `saas-tech-selection` skill `references/dimensions/observability.md` 開頭段；專案可觀測性規則〈核心理念〉「異常不可靜默消失，關鍵流程必須有跡可循」可互證 |
| 事件流仲裁 | 「多個事件流競爭同一個稀缺通道時，『誰讓步、誰等、誰被丟、丟了怎麼留痕』由該通道的單一仲裁器依三個參數裁決」 | 事件流負載仲裁方法論開頭段（核心概念之前） |

### 判定「失效不存在」的理由

本節是 `SKILL.md`〈產物欄的五種合法答案〉「無」列「理由（失效為何不存在）」的合格判準，不是任何維度的判準。

產物欄填「無」所附的理由，須指出權威原句所講的對象在本專案不存在。

原句的對象是原句裡會出事的那個東西：UI 是「語意」，測試是「行為」，資料庫是「正式狀態」，DevOps 是「版本」與「依賴」，可觀測性是「系統」；事件流仲裁的對象是「多個事件流競爭同一個稀缺通道」這個競爭狀態，不是單看「有沒有事件流」或「有沒有稀缺通道」——單一事件流內來自不同請求來源的並行請求同樣構成此狀態，見下段。

某一種發生途徑不存在（如沒有背景執行緒、沒有獨立部署動作、沒有圖形介面框架）不構成失效不存在，失效仍可經由其他途徑發生。

失效目前尚未發生（如目前只有一種輸出樣式）不構成失效不存在，原句講的是會不會發生，不是現在有沒有發生。

對象在本專案存在時不得填「無」：答得出對象在本專案的具體對應，即為失效在本專案的樣子，走「改寫產物」或「照預設」；答不出時標「待定」。

套用於事件流仲裁：對象是否存在，看是否有兩個以上的請求來源會對同一個稀缺通道發出請求。事件流負載仲裁方法論〈1. 通道與仲裁器〉協調圖列寫明「同一個 domain 的同一條事件流，來自不同租戶的請求彼此競爭」，因此事件流數量不是判準線。僅一條事件流且無並行請求時，對象不存在，填「無」，理由依本段判準敘明（僅一條事件流，無並行請求，對象不存在），並附重評條件：「新增第二條事件流（背景排程、外部推送、並行請求）時重新評估」。

（落檔前核對「對象」清單：每個對象詞都必須逐字出現在〈各維度要防的失效（權威出處）〉表該維度的原句中，用 `git grep -F` 確認。有任何一個不在原句中，停手回報。事件流仲裁的對象詞「多個事件流競爭同一個稀缺通道」已核對逐字出現於該表事件流仲裁列原句。）

### 可觀測性維度

【輸入】

```
一個純終端輸出的 statusline 工具，唯一輸出通道是標準輸出（stdout），沒有背景執行緒、沒有非同步任務、沒有檔案寫入或網路請求。盤點可觀測性維度時問推導問句「這個維度要防的失效，在本專案會長成什麼樣子」。
```

【產出】

```
形態：決策表
  候選判定 | 推導過程                                                                                | 結論
  甲       | 可觀測性防的是「系統壞了怎麼知道、知道了怎麼定位」；本專案沒有背景執行緒也沒有非同步任務，因此失效不存在，填「無」 | 不合格，見驗證段
  乙       | 可觀測性防的是「系統壞了怎麼知道、知道了怎麼定位」；本專案的「壞」發生在每次輸出的當下——若某欄位運算失敗，讀者仍會看到一整列不完整或錯亂的輸出而不知原因，失效存在，長成「輸出時的失敗不可見」 | 合格
  產物     | 改寫產物：失敗時的降級顯示契約——哪些欄位失敗時整列消失、哪些顯示佔位符                   | 對應乙的推導結果
```

【驗證】檢驗問句

```
Q 甲以「本專案沒有背景執行緒也沒有非同步任務」為理由，是否構成失效不存在？
  預期：不構成——依據句「某一種發生途徑不存在（如沒有背景執行緒、沒有獨立部署動作、沒有圖形介面框架）不構成失效不存在，失效仍可經由其他途徑發生」（〈判定「失效不存在」的理由〉）。

Q 乙可否填「無」？
  預期：不得填「無」——依據句「可觀測性是「系統」」與「對象在本專案存在時不得填「無」」（同節）；本工具本身即原句對象。

Q 乙把失效寫成「輸出時的失敗不可見」後，產物欄該走哪一種答案？
  預期：走「改寫產物」——依據句「答得出對象在本專案的具體對應，即為失效在本專案的樣子，走「改寫產物」或「照預設」」（同節）；「改寫產物」與「照預設」的擇一條件在 `SKILL.md`〈產物欄的五種合法答案〉表：預設產物對本形態成立走「照預設」，不適用或有害走「改寫產物」——本例的預設產物（一般錯誤日誌與監控接線）對「唯一輸出通道是 stdout、無背景執行緒」的形態不適用，故走「改寫產物」。
```

本則「失敗時的降級顯示契約」（哪些欄位失敗時整列消失、哪些顯示佔位符）是本形態（純終端輸出、無背景執行緒）的示範產出，不是另一條可查表的判準；可套用到其他形態的部分是推導問句本身，見 `examples.md`〈已驗證與未驗證的專案形態〉段「範例本身是特定形態下的具體示範，推導問句才是可套用到其他形態的部分」與上方〈各維度要防的失效（權威出處）〉表可觀測性列。

### UI 維度

【輸入】

```
同一個 statusline 工具的 UI 維度，四塊（i18n／design-system／UX 審查／元件庫）皆以圖形介面框架為前提。工具僅輸出單行文字，終端寬度有硬上限。
```

【產出】

```
形態：決策表
  候選判定 | 推導過程                                                                       | 結論
  甲       | UI 防的是「同一語意長出多種樣子」；本工具只有一種輸出樣式，樣式唯一，因此失效不存在，填「無」 | 不合格，見驗證段
  乙       | UI 防的是「同一語意長出多種樣子」；本例的「樣子」不是視覺元件外觀，而是欄位順序、色碼語意、寬度截斷規則——不同開發者各自修改時仍可能長出不一致的欄位順序或色碼用法，失效存在 | 合格
  產物     | 改寫產物：輸出格式契約（欄位順序、色碼語意、寬度截斷規則）                     | 對應乙的推導結果
```

【驗證】檢驗問句

```
Q 甲以「本工具只有一種輸出樣式，樣式唯一」為理由，是否構成失效不存在？
  預期：不構成——依據句「失效目前尚未發生（如目前只有一種輸出樣式）不構成失效不存在，原句講的是會不會發生，不是現在有沒有發生」（〈判定「失效不存在」的理由〉）。

Q 乙把「樣子」對應到欄位順序、色碼語意、寬度截斷規則，這一步依據哪條條文？
  預期：依據句「答得出對象在本專案的具體對應，即為失效在本專案的樣子，走「改寫產物」或「照預設」」（同節）；原句對象依據句「UI 是「語意」」。
```

本則「輸出格式契約」（欄位順序、色碼語意、寬度截斷規則）是本形態的示範產出，不是另一條可查表的判準；可套用到其他形態的部分是推導問句本身與 UI 對象「語意」，見 `examples.md`〈已驗證與未驗證的專案形態〉段同一句與上方〈各維度要防的失效（權威出處）〉表 UI 列。

## 無 UI 框架的元件庫產物

**無 UI 框架（vanilla DOM + 字串模板）的元件庫產物**：權威已就此給出投影，見元件庫雙向約束方法論的〈Web/HTML 端 L2 特別判準〉，其中「元件規則 SSOT」與「元件邊界的可驗產物」兩條。產物是元件規則的來源模組加上選擇器清單與其斷言，不是元件類別。

## 事件流仲裁的四種答案形態

事件流負載仲裁方法論以「稀缺資源是參數」為前提，四種答案形態對應不同的通道與執行緒現況；判準本身在該方法論，本節只給填答範例。

照預設與改寫產物的選擇依 `SKILL.md`〈產物欄的五種合法答案〉：預設產物對本形態成立走「照預設」，不適用或有害走「改寫產物」。是否有兩個以上的請求來源競爭同一個稀缺通道（`SKILL.md`〈維度與產物〉事件流仲裁列適用條件；判準見上文〈判定「失效不存在」的理由〉「套用於事件流仲裁」段）只決定對象是否存在、維度是否成立，不決定預設產物是否適用。預設產物是否適用，逐節查事件流負載仲裁方法論開頭段所稱「各節標明的『實例化條件』」：有節的實例化條件在本專案不成立時，走「改寫產物」，省略該節，附改寫後的產物＋一句為什麼預設不適用（指名不成立的是哪幾節的實例化條件）。下表「改寫產物」列是單通道、單執行緒形態的一例。

| 答案形態 | 範例 | 附帶內容 |
|---------|------|---------|
| **照預設** | 伺服器端服務有排程、外部 API 請求、訊息佇列消費三條以上事件流競爭同一連線池或 worker pool，直接套用通道清單＋仲裁器落層＋九格卸載順序表 | 無 |
| **改寫產物** | 單線程桌面 App 沒有連線池、worker pool 等後端通道，唯一的稀缺通道是使用者注意力（畫面上的提示載體一次一則）。改寫後的產物是「單一通道（注意力）的仲裁器落層＋該通道的到達類別與級別對照表」，省略以多通道或多執行緒為前提的資源成本異質、分池、跨執行緒與 isolate 三節 | 改寫後的產物 + 一句為什麼預設不適用：預設產物假設多通道並存，單通道專案套用會產生恆為零的分片與跨通道欄位 |
| **已存在於 X** | 某訊息佇列消費服務已有仲裁器實作（如特定類別）承擔九格卸載順序表 | 位置（檔案路徑或符號名） |
| **無** | 專案僅一條事件流（如單一 CLI 工具、無背景工作、無並行請求），不存在「多條事件流競爭同一通道」的情境 | 理由：僅一條事件流，無競爭 + 重評條件：新增第二條事件流（背景排程、外部推送、並行請求）時重新評估 |
