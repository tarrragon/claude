# 維度與產物：填答細則與案例

> 何時讀：已進入 `foundation-design` skill 入口檔 `SKILL.md` 的〈維度與產物〉步驟，正要為某個維度填產物欄，需要非 SaaS 專案處置、複合產物、多子樹分列、改寫產物的範例或無 UI 框架元件庫產物的判斷依據時讀本檔。只想知道哪個維度該讀哪個權威，讀入口檔的維度表本身即可，不需要本檔。
>
> 同目錄：接手他人專案的盤點流程見 `handoff-mode.md`；判準的真實案例見 `examples.md`。
>
> 溯源：`foundation-design` SKILL.md v6.2.0 收斂時外移（2026-09-08），原文分散於入口檔〈維度與產物〉節多段散文。

本檔章節：〈非 SaaS 專案的形態轉換〉〈填完產物欄仍應翻原文〉〈複合產物與多子樹分列〉〈改寫產物是主路徑〉〈無 UI 框架的元件庫產物〉。

## 非 SaaS 專案的形態轉換

這三列（資料庫／DevOps／可觀測性）的權威來源 `saas-tech-selection` 以 SaaS/伺服器端專案為預設形態，對 CLI 工具、函式庫、單機 app 等非 SaaS 專案形態不符。處置依 `SKILL.md`〈權威缺席時〉「權威存在但形態不符」的既有機制——先走「改寫產物」，取權威中與形態無關的部分（例如單機 SQLite 工具仍適用 migration 版本化紀律，多租戶隔離則不適用，見 `examples.md`〈權威形態不符時的正確取用〉範例）；確認無可用部分時，改指專案自身 CLAUDE.md 技術選型記錄，或依 `SKILL.md`〈產物欄的四種合法答案〉標「無」+ 理由。**不新增第二套權威**——`saas-tech-selection` 仍是這三個維度唯一的判準來源，本節只是把「非 SaaS 專案先過形態轉換」明示為預設路徑，不構成整條跳過。

## 填完產物欄仍應翻原文

實跑證實最高價值的缺口常在權威原文而不在此欄——一個有真 PostgreSQL 與 docker volume 卻零備份痕跡的服務，其最大風險是備份還原，而那條要讀到權威的防護底線才撈得到。填完產物欄後仍應翻一次權威原文。

## 複合產物與多子樹分列

**一個維度的產物可以是複合的，不必擇一。** 產物不是原子的：同一維度常有一部分已存在、另一部分待建。填「已存在於 `main.go:136` 的色碼常數表 + 改寫產物：寬度截斷規則待落為文件」是正確答案；逼自己擇一時，選「已存在」會漏掉待建的部分，選「改寫產物」會重造已有的部分。接手他人專案時尤其需要，別人的專案更可能是一半做過一半沒做。

**repo 內有多個子樹各持獨立工具鏈或獨立部署單元時，產物欄按子樹分列。** 判別看事實不看名稱：有沒有 workspaces 設定不重要，有沒有兩套以上的測試命令、建置命令或部署目標才重要。同一維度在各子樹的狀態常不同，單一格會把落後那棵子樹的缺口吃掉。

## 改寫產物是主路徑

**改寫產物是本表的主路徑，不是例外。** 權威是從特定形態歸納出來的，套到別的形態時預設產物常需改寫。兩個實測案例：

- 一個終端機 statusline 工具的**可觀測性**，其 stdout 就是產品，照預設建 log 接線點會毀掉輸出。正確產物是「失敗時的降級顯示契約」：哪些欄位失敗時整列消失、哪些顯示佔位符。
- 同一工具的 **UI**，四塊中 i18n 因終端寬度硬上限而為負收益、UX 審查的狀態矩陣零投影。正確產物是「輸出格式契約」：欄位順序、色碼語意、寬度截斷規則。

兩例中維度都成立，改的是產物。若改為判「維度適不適用」，前者會被判成適用而照做（產品壞掉），後者會被判成不適用而整塊漏掉。

**這兩個答案是個案記錄，不是可套用的推導。** 遇到本節未預寫的形態時，改寫產物的問法是：**這個維度要防的失效，在本專案會長成什麼樣子？** 可觀測性防的是「出事了但沒人知道」，在 stdout 即產品的工具上，它長成「失敗時畫面顯示什麼」；UI 防的是「同一概念長出多種樣子」，在單一輸出行的工具上，它長成「欄位順序與色碼語意的契約」。先答這一問，再看權威的預設產物是否即是答案。

## 無 UI 框架的元件庫產物

**無 UI 框架（vanilla DOM + 字串模板）的元件庫產物**：權威已就此給出投影，見元件庫雙向約束方法論的〈Web/HTML 端 L2 特別判準〉，其中「元件規則 SSOT」與「元件邊界的可驗產物」兩條。產物是元件規則的來源模組加上選擇器清單與其斷言，不是元件類別。
