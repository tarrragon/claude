# 接手模式

> 何時讀：已判定進入 `foundation-design` skill 入口檔 `SKILL.md`〈與 orchestration 的協作〉表「文件回答不了地基問題的既有實作」列，要執行接手他人專案的盤點流程時讀本檔。單純想知道何時該走接手模式，讀入口檔該列的判別欄即可，不需要本檔。
>
> 同目錄：維度與產物欄位填法的延伸細則見 `dimension-product-notes.md`；判準的真實案例見 `examples.md`。
>
> 溯源：`foundation-design` SKILL.md v6.2.0 收斂時外移（2026-09-08），原文為入口檔〈接手模式〉整節。

接手的專案常缺可用文件。**先做地基、後補文件**：

```
1 盤點   grep 既有裸值、既有測試、既有 schema，它們是可觀測的事實
2 命名   逐一給名字，值不變（看似雜訊的值也不在此步收斂，見〈命名與收斂分兩步〉）
3 固化   建立單一定義位置 + 機械檢查
4 補文件 此時文件是萃取結果的記錄，不是猜測
```

**為什麼這個順序比直接補文件更可靠**：憑印象寫的文件會與程式碼漂移且無機制發現；萃取自程式碼的值每一步可 grep 驗證。

**盤點測試時，測試檔存在不等於該值被涵蓋。** 一個內容為 `void main() {}` 的檔案會被 grep 命中成測試檔，保護力為零。盤點須記錄「哪些值實際被斷言涵蓋」，否則第 2 步的前提檢查會拿盤點的假陽性當通過。

**盤點表欄位**：值、位置（檔案路徑或符號名，不寫行號）、是否被斷言涵蓋（是／否；「是」附涵蓋它的測試名或路徑，「否」代表第 2 步的前提檢查尚未通過）。三欄缺一即無法支撐第 2 步的前提檢查。

**既有測試同時是原作者意圖的書面殘留。** 接手情境下它常比文件可靠：一支 22 行的測試可能是全 repo 唯一記下「這五個路由的順序承載語意、不能動」的地方，而該事實在程式碼與 500 行 changelog 裡都看不出來。盤點時把測試當意圖來源讀，不只當覆蓋率數字。

**萃取的前提是既有 artifact 可信。** 四種情形不成立：

| 情形 | 處置 |
|------|------|
| 量測腳本本身有缺陷 | 須先驗證來源。無法驗證時（腳本無意圖註記、原作者不可得）併入「已知過期」處置 |
| artifact 由產生器輸出 | 須先驗證來源。副檔名常可自證（`.g.dart`／`.freezed.dart` 等） |
| artifact 已知過期 | **排除其對現況的宣稱效力，保留其作為語意線索。** 過期不等於錯誤：一份落後一個 minor 的 changelog 仍可能是全 repo 唯一說明「`0.01` 這個常數的語意是手續費率」的來源。判斷過期的可操作訊號：版號與 artifact 內記載的落差、artifact 最後修改時間與最後 commit 的落差、與程式碼抽樣比對 |
| **artifact 的決策者不可得** | 保留原值原名，把疑義落為決策文件的待確認項，**不在地基波內改**。同「先命名、統一值另開票」的二分法 |

**「不可得」以本次地基波內能否取得決策判定，不以決策者是否仍在組織內判定。** 已向決策者詢問、而本次地基波內未獲回應，即屬不可得；未詢問者不屬之。本表各列的「不可得」皆依此判定。第四列的處置不改值、疑義留在決策文件的待確認項，決策日後到達時由待確認項承接，因此本判定不設等候期限。

【輸入】

```
盤點發現一個具名常數的原始 commit 作者已離職，另一個具名常數的作者仍在組織內，本次地基波期間已詢問但未獲回應。
```

【產出】

```
形態：決策表
  候選       | 判定                                                                  | 結論
  作者已離職 | 決策者不可得                                                         | 明確符合，組織內無法聯繫的管道
  作者未回應 | 甲：不算不可得（人還在，等回應）／乙：算不可得（已詢問，本次地基波內未獲回應） | 採乙，見驗證段
  採用       | 兩者皆保留原值原名，疑義落為決策文件待確認項，不在地基波內改        | —
```

【驗證】檢驗問句

```
Q 「作者仍在組織但未回應」是否構成「決策者不可得」？
  預期：是——依據句「已向決策者詢問、而本次地基波內未獲回應，即屬不可得」（本節表下判定句），不以決策者是否仍在組織內判定，不要求對方永久失聯。
```

**命名與收斂分兩步。** 盤點出的值看似未經設計（例如間距出現多種彼此相近、看不出尺度的值）時，第 2 步仍逐值命名、值不變，把「疑為雜訊」與候選的離散階映射記入決策文件，收斂另開一張票，與命名同批建立。理由是第 2 步的安全性掛在行為中立：命名與改值若在同一步發生，畫面一旦改變，無從分辨是改名還是改值造成的。收斂票改的是值，屬行為變更，驗收須含改動前後的畫面或特徵測試比對。來源若是設計畫布而非既有實作（尚無程式碼綁定這些值），沒有需要保持中立的行為，萃取當下即歸納為離散具名階，見 `examples.md`〈萃取不等於照抄〉。

**命名的行為中立性也有前提。** 安全性論證掛在「既有測試全程保護」，覆蓋不足時先補**特徵測試**（characterization test：不驗「應該是什麼」而是把現況行為原樣鎖住，用途是讓後續改動一旦改變行為就紅燈；寫法見 `tdd` skill 的分層測試策略）。

**但補特徵測試有規模閘門。** 在數萬行零覆蓋的專案上，補到足以保護 token 抽取的覆蓋會吞掉整個地基波。**規模閘門的判準對象是欲抽取範圍的覆蓋率，不是專案總行數**——「保護 token 抽取的覆蓋」指的是抽取範圍本身需要的覆蓋，「數萬行零覆蓋」只是舉例的量級，不是固定門檻數字；欲抽取範圍的覆蓋率為零即符合「補不起來」，不要求整體專案規模先達到數萬行等級。**前提補不起來時的替代路徑**：只在已有覆蓋的模組內命名，其餘模組改為「只擋新增、不動既有」（執法載體設 baseline，表達形式見 `SKILL.md`〈工作流〉步驟後段，兩處採同一定義不重複另定），並把未命名範圍記入決策文件。不要把整個地基波卡在補測試上。

【輸入】

```
一個五千行程式碼的模組，既有測試覆蓋率 30%，其中欲抽取的間距值恰好落在未覆蓋的 70% 範圍內。
```

【產出】

```
形態：決策表
  候選判定       | 依據                                                                  | 結論
  甲：照補特徵測試 | 五千行規模遠小於「數萬行」，判定規模閘門不成立，直接補特徵測試        | 不合格，見驗證段
  乙：走替代路徑 | 雖規模未達數萬行，但欲抽取的值恰好落在零覆蓋範圍，補測試成本仍可能吞掉地基波 | 合格
  正確判準       | 規模閘門問的不是「總行數」，而是「欲抽取範圍的覆蓋是否為零」——本例欲抽取值所在範圍覆蓋率為 0%，符合替代路徑條件 | 走替代路徑：只在已覆蓋模組內命名，其餘記入決策文件
```

【驗證】檢驗問句

```
Q 規模閘門的判準對象是「專案總行數」還是「欲抽取範圍的覆蓋率」？
  預期：欲抽取範圍的覆蓋率——依據句「補到足以保護 token 抽取的覆蓋會吞掉整個地基波」，「保護 token 抽取」指抽取範圍本身需要的覆蓋，「數萬行零覆蓋」是舉例的量級而非固定門檻數字。

Q 本例（五千行、抽取範圍覆蓋率 0%）該照補還是走替代路徑？
  預期：走替代路徑——依據句「前提補不起來時的替代路徑：只在已有覆蓋的模組內命名，其餘模組改為『只擋新增、不動既有』」。
```

另有三種情形抽取不是純命名，各自的處置：

| 情形 | 處置 |
|------|------|
| 抽取後共用同一物件實例而下游會 mutate | 抽取結果須是不可變值或每次呼叫回傳新實例的工廠函式，不得抽成一個被多處持有並修改的共用實例；已抽出才發現下游會 mutate，先補一個鎖住現況的特徵測試（見上方〈命名的行為中立性也有前提〉） |
| 值位在要求編譯期常數的位置 | 抽取後的具名定義本身也必須維持該語言的編譯期常數形式，不得退化為執行期變數——退化會讓原本編譯期就能擋下的錯誤延後到執行期才發現 |
| 值位在平台設定檔或行內樣式，抽取需改機制 | 不強行改成程式碼可 import 的名字；改在平台設定檔旁加註解指向具名定義作為單一事實來源，或由建置流程從具名定義產生平台設定檔內容，兩者擇一並記錄選擇理由 |
