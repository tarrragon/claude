# Foundation Design

規格說系統**做什麼**；本 skill 決定實作要用什麼**具名材料**來蓋。它是規格文件與程式實作之間的獨立設計區塊——不屬於任何一張功能票，卻被每一張功能票消費。

## 核心原則

| 原則 | 內容 |
|------|------|
| **具名單一住址** | 每個值（顏色、尺寸、fixture、seed、CI 步驟）都先被命名，且只有一個定義位置。程式碼與規格只引用名字，不重複值本身 |
| **萃取優先於發明** | 值從既有 artifact（設計稿、既有程式碼、真實語料）量測而來，不憑印象寫。發明的值會與現實漂移且無機制發現；萃取的值每一步可驗證 |
| **命名是行為中立的重構** | 把裸值改為具名常數不改變任何行為——測試綠燈就是綠燈。這使老專案的地基工作可以安全先行 |
| **維度條件式展開** | 不是每個專案跑全部維度。命中才進，未命中的維度標 N/A 並逐條寫理由——「未確認即略過」與「確認後不適用」在產物裡必須分得開 |
| **地基票先於功能票** | 本 skill 的產物落為實作首波（W1）的票，功能票以 blockedBy 依賴它們。否則 N 張功能票會各自決定同一批值，同一個概念長出 N 種樣子 |

## 判定產物邊界的三問

一個東西屬不屬於本 skill 的範圍，問三題（AND）：

1. 被**多個**下游消費？（單一畫面自用的樣式不是地基）
2. 漂移成本高？（兩處定義不一致時會靜默存活很久才被發現）
3. 必須先於功能實作存在？（功能票沒有它就會自己發明一份）

三題皆是 → 進本 skill；否則留給功能票。

## 維度表

| 維度 | 進入條件 | 產物 | 可機械化的驗收形態 |
|------|---------|------|------------------|
| **UI** | 產品有畫面 | design token 三層命名（原始值 → 語意 → 元件）＋跨畫面元件庫 | 產品程式碼目錄（token 目錄除外）grep 不到裸色碼、裸字級、裸間距數字 |
| **測試** | 一律進入 | fixture 策略（真實語料快照優先於生成器）、測試分層地基、假資料的極端形態清單 | fixture 以既有工具重新解析，分類結果與來源一致；極端形態各至少一筆 |
| **資料庫** | 有持久化 schema | seed 資料、migration baseline、schema 版本化策略 | 空庫跑 migration + seed 後，應用可達可用狀態；migration 可重放 |
| **DevOps** | 有建置或部署需求 | CI gate（測試、lint、裸值檢查）、部署配方、還原（rollback）步驟 | CI 在乾淨環境可全綠；還原步驟實際演練過一次 |
| **可觀測性** | 一律進入 | 統一 log 工具的接線點、錯誤分類骨架 | 專案的 log 呼叫皆經統一入口，grep 不到散落的原生輸出 |

驗收形態的共同性質：**指名外部固定值、可 grep、可重跑**。「看起來有做」與「機械檢查通過」在這裡必須是同一件事——驗收 oracle 不在執行者自己手上；oracle 在執行者手上時，空實作也能讓驗收全綠。

### UI 維度的三層命名

| 層 | 回答 | 例 |
|----|------|-----|
| 原始值 | 這個值是多少 | `teal600 = #2E6F6A` |
| 語意 | 這個值代表什麼 | `accent = teal600` |
| 元件 | 這個元件用什麼 | `NavItem.selectedBg = accent` |

畫面只引用語意層與元件層。原始值層的存在是為了讓「同一個值被兩個語意共用」顯性化——換值時才知道要不要一起換。

框架的 theme 機制（如 Flutter 的 `Theme`）是**分發機制不是決策位置**：它讓值傳到元件，但不回答「這個值是什麼、為什麼是這個」。先命名，再由 theme 分發；產品常有 theme 系統沒有對應欄位的語意角色（狀態分類色、嚴重度標記），它們必須先有名字才存在。

## 兩種模式

### 新專案：規格先行

規格與設計稿已有 → 從中萃取定案 → 落為地基票 → 功能票引用。

### 老專案：萃取先行（本 skill 的核心價值）

老專案常缺文件。**先做地基、後補文件**，順序是：

```
1 盤點   grep 出全部裸值、既有測試、既有 schema——它們是可觀測的事實
2 命名   逐一給名字，值不變（行為中立）
3 固化   建立單一住址 + 機械檢查（CI 擋新增裸值）
4 補文件 此時文件是萃取結果的記錄，不是猜測
```

**為什麼這個順序比直接補文件更正確也更安全**：

- 正確性——文件憑印象寫會與程式碼漂移，且無機制發現；萃取自程式碼的值每一步可 grep 驗證
- 安全性——命名不改行為，既有測試全程保護；寫文件沒有這個保護，錯的描述會靜默存活

## 工作流

```
1 判定模式（新專案 / 老專案）
2 維度盤點：逐維度判定進入與否，N/A 逐條標理由
3 逐維度萃取與命名（多方案取捨時委派 design-decision-framework）
4 產物落為地基票（實作首波），功能票 blockedBy 它們
5 機械檢查接入 CI（裸值 grep、fixture 重解析、migration 重放）
```

## 與其他 skill 的分工

| skill | 關係 |
|-------|------|
| `saas-tech-selection` | 上游。它的維度訪談決定「這個專案**需要哪些**維度」；本 skill 為命中的維度**設計地基** |
| `design-decision-framework` | 委派對象。維度內出現多方案取捨（選哪個套件、幾階間距）時用它評估，本 skill 不另設評估流程 |
| `version-sequencing` | 下游。它把本 skill 的地基票排進首版的第一波 |
| `tdd` | 下游。功能實作在地基之上進行 |
| `project-init` | 無關。它管環境安裝，不管設計 |

## Examples

**萃取揭露規格漂移（UI 維度，桌面文件視覺化專案）**：規格散文記「圓角 10/12、字級 12–22」，量測設計畫布實得圓角 5/7/8、字級 10–19——兩邊各寫各的、無機制發現。處置：以畫布實測值建 token、規格改為指向 token 不再複述數值——「萃取優先於發明」的實證。

**快照勝過生成器（測試維度，同專案）**：容錯策略原建立在「語料有一批格式損壞的檔案」上，複驗發現那批損壞是量測腳本的解析缺陷產物、實際不存在——**想像的損壞形態整批是假的**。fixture 因此改採真實語料快照：快照帶進實際存在的形態（無 frontmatter 但合法、路徑模式重疊等邊界案例）；生成器只能產出設計者想像所及的形態。

**萃取不等於照抄（同專案）**：設計畫布的間距實測出七種值（1/2/7/8/9/10/12），那是產生器輸出而非設計過的尺度。token 化時歸納為離散具名階並記錄映射——照抄會把雜訊固化成規格。

## Common Issues

| 症狀 | 原因 | 處置 |
|------|------|------|
| token 表建了，功能票還是各寫各的值 | 地基票與功能票無 blockedBy 依賴，順序沒被強制 | 功能票一律 blockedBy 地基票；CI 加裸值 grep 讓違規變紅燈 |
| 出現次數最多的顏色被命名為「主色」 | 出現次數是觀察不是語意 | 逐色確認實際承擔的角色再命名；次數只是線索 |
| 老專案盤點後直接開始改值「順便統一」 | 混入了行為變更，失去命名的中立性保護 | 嚴格分兩步：先命名（值不變、測試綠），統一值另開票 |
| N/A 維度沒有記錄 | 「沒確認」與「確認後不適用」在產物裡分不開 | 逐維度標 N/A + 理由 + 重評條件（如「加入編輯能力時 DB 維度重評」） |
