# 協作專案外接資料夾規格

協作或接手他人專案時，被操作的 repo 往往不具備本框架的 ticket 系統，也未必同意把
spec 與 use case 收進自己的版控。本規格定義此情境下的替代產物：一個放在被操作 repo
**之外**、由分析者持有的外接資料夾，內含盤點工作項表、spec 與 use case。

本檔是**讀法映射的單一權威**。各 skill 的建票類指令在無 ticket 系統時該怎麼讀，只在
本檔〈讀法映射〉一節定義，其他 skill 引用本節、不複述。映射若散落複述，同一個欄位會
在兩個 skill 得到不同讀法——這是本案設計階段列出的預期失效之一。

> **合法性判準的權威不在本檔**。工作項編號能否作為規則層的 trigger 與追蹤載體，由
> `.claude/references/decision-trigger-binding-details.md` **規則 2.6（協作射程）**裁定；
> 射程邊界一行見 `.claude/rules/core/decision-trigger-binding.md` 規則 2 與
> `.claude/rules/core/quality-baseline.md` 規則 5。本檔只摘要閘門並路由，不複製條文。

## 1. 適用範圍

| 判定 | 內容 |
|------|------|
| 適用 | 被操作 repo 無本框架 ticket 系統（無票庫目錄且 ticket CLI 不可用），且發現的收件方是該 repo 的維護者 |
| 不適用 | 被操作 repo 有可用的 ticket 系統。此時改用工作項表視為規避規則，仍須建票 |
| 不適用 | 發現的收件方是本框架或分析者自己的專案（框架缺陷、自身技術債）。射程由收件方決定，不由手邊有無 ticket 系統決定 |

**Why**：射程若以「手邊方不方便」界定，任何情境都可宣稱不方便，規則的可驗證邊界即失效。
上表各條都是客觀事實查核（查該 repo 有無票庫與 CLI、問這個發現要交給誰），不需判斷
「這個載體夠不夠等效」。

**Action**：進入本規格前先答這三問；答不出「收件方是誰」時停手，不預設適用。

## 2. 外接資料夾結構

### 2.1 佈局

資料夾名稱由分析者決定，本規格一律以 `<外接資料夾>` 指稱。命名要求有兩條，各自對應一種
會發生的混淆：

- **可辨識對應哪一個被操作專案**。同時進行多個協作案時，分析者端會有多個外接資料夾，
  名稱不可辨識即無從分辨手上這份盤點屬於誰。
- **不與被操作 repo 的目錄同名**。同名會讓交付時兩邊的相對路徑在對話中無法區分（見 2.4）。

```
<外接資料夾>/                     # 分析者端持有，不進被操作 repo
  README.md                       # 對照表：被操作 repo 的絕對路徑與 commit、盤點日期、
                                  # 對帳責任人與對帳觸發條件
  <工作項表>.md                    # 盤點工作項表，唯一任務主檔
  docs/                           # 此中間層必須存在，見 2.2
    app-use-cases.md              # UC 白名單 SSOT
    usecases/
    spec/{domain}/
    spec/{domain}/domain-map.md   # 單 domain 時退化為 docs/domain-map.md
    proposals/
    events/{domain}/
    proposals-tracking.yaml
    traceability.yaml
  .uc-fingerprints.json           # UC SSOT 的 fingerprint sidecar
```

`README.md` 是外接資料夾的對照表，必載欄位如下（C3 的具體內容）：

| 欄位 | 內容 |
|------|------|
| 被操作 repo 路徑 | 絕對路徑 |
| 被操作 repo commit | 盤點當下的 commit |
| 盤點日期 | |
| 對帳責任人 | 執行對帳的人或角色 |
| 對帳觸發條件 | 什麼時候該對帳（例：對方每次發版後） |
| 對帳票 | 分析者端承載本交付案的本框架 ticket（閘門 G4，見 4.3） |

### 2.2 強制約束

下列各條都是「不寫就會壞，且壞法不明顯」的約束，逐條寫明後果：

| 約束 | 內容 | 不遵守的後果 |
|------|------|-------------|
| C1 `docs/` 中間層不可省 | 外接資料夾整體作為 doc CLI 的 doc root，`docs/` 之下的相對結構與一般專案完全相同 | doc CLI 以 `<root>/docs/...` 推導全部文件路徑。省掉這一層，原本零改動即可運作的讀寫點全數失效，且失效形態是找不到檔案而非報錯設定有誤 |
| C2 CLI 一律從分析者端啟動 | 在具備本框架 `.claude/` 的 repo 內執行 doc CLI，並以 `CLAUDE_PROJECT_DIR` 指向 `<外接資料夾>` | doc 的啟動 shim 以 cwd 的 git root 是否含該 skill 判斷可否執行。從被操作 repo 啟動會直接被拒，使用者的第一個動作就失敗 |
| C3 `README.md` 必須記錄被操作 repo 的絕對路徑與 commit | 連同盤點日期、對帳責任人與對帳觸發條件一併記錄。`README.md` 是這些事實的權威，工作項表的〈摘要〉段只是就近複本 | 同時觸及文件與程式碼的命令沒有第二個根可用（見 2.5）；且「這份盤點掃的是哪一版程式碼」事後無從還原，對帳時無法判斷差異來自修復還是來自程式碼已經前進 |

### 2.3 工作項表放在根層，不放進 `docs/`

工作項表不是 doc CLI 的節點型別。放進 `docs/` 會被檔名規範檢查與 UC 編號全量掃描掃到，
產生與盤點無關的違規回報；放在根層則兩者都不觸及。

### 2.4 兩種路徑基準

工作項表同時引用兩邊的路徑，基準不同。每條路徑一律帶來源前綴，前綴隨字串走：

| 前綴 | 基準 | 用於 | 範例形態 |
|------|------|------|---------|
| `repo:` | 被操作 repo 的根 | 影響範圍 | `repo:<模組目錄>/<檔名>` |
| `ws:` | 外接資料夾的根 | 來源 | `ws:docs/spec/{domain}/<檔名>` |

**Why**：不帶前綴時，路徑的基準只能從所在欄位推知。而工作項表的既定用法包含逐項貼進
GitHub Issue、依順序層分段貼進 Slack（見第 5 節）——貼出去之後欄位名的語境就沒了。

**Consequence**：兩邊若有同名層級（例如雙方都有 `docs/`），兩種起算方式各自指得到一個
存在的檔案，讀錯的人不會遇到找不到檔案的錯誤，只會讀到錯的檔案。

**Action**：所有寫入工作項表的路徑都帶前綴，包含項目詳情的影響檔案清單。前綴不因貼進
哪個系統而省略。

### 2.5 目前的工具限制

外接模式下，doc CLI 的命令分三類。第三類的失敗形態是**成功語氣的空結果**，必須在使用前
知道：

| 類別 | 命令 | 行為 | 依據 |
|------|------|------|------|
| 已實測可用 | `domain`／`uc list`／`uc verify`（帶路徑）／`create usecase` | 以 `CLAUDE_PROJECT_DIR` 指向外接資料夾即正常運作，寫入落點正確 | 上游盤點的實測記錄 |
| 判定可用，未逐一實測 | `query`／`list`／`nav`／`status`／`validate`／其餘 `create` 型別／fingerprint sidecar 寫入 | 與已實測者共用同一套路徑推導，判定為同樣可用 | 讀程式碼路徑解析推導，非實測 |
| 須明確指定被操作 repo 路徑 | `uc verify <被操作 repo 路徑>` | 不帶路徑時只掃外接資料夾，回報「驗證通過」；帶路徑才掃得到被操作 repo。輸出的檔案定位是相對外接資料夾的跨界相對路徑，交付前須依 2.4 改寫並加前綴 | 已實測 |
| 外接模式下不可用 | `test-map` | 掃描目標落在外接資料夾，回報「沒有找到任何 UC 文件」。這是假陰性，不是「確實沒有」 | 已實測 |
| 外接模式下不可用 | `uc trace` | 無指定掃描根的參數，掃不到被操作 repo。輸出形態未實測 | 讀程式碼推導 |

**Action**：後兩類命令的輸出在外接模式下不得作為覆蓋率或引用狀況的證據；需要該結論時
改以手動 grep 被操作 repo，並在工作項表的來源欄註明取得方式。第二類命令首次使用時，
先以一筆資料確認寫入落點確實在外接資料夾內再繼續——這類命令的失敗形態與第四、五類同型
（寫到非預期位置而不報錯），實測範圍尚未涵蓋它們。

## 3. 盤點工作項表規格

### 3.1 文件組成

單一 Markdown 文件，分段與順序固定如下：

| 段 | 內容 |
|----|------|
| 摘要 | 盤點範圍、盤點日期、項目總數、各順序層的件數；另複寫 `README.md` 的被操作 repo、對帳責任人與對帳觸發條件，供填表者就近查閱。這些欄位的權威在 `README.md`（C3），兩處不一致時以 `README.md` 為準 |
| 工作項表 | 一行一項，每格單行，可直接轉 CSV |
| 項目詳情 | 每項一小節，放驗收條件全文、證據、影響檔案清單 |
| 對帳紀錄 | 一次對帳一列 |

**每格單行**是硬要求：表格是整份產物唯一能機械轉出的部分，一格內換行會讓 CSV 轉出後
欄位錯位，而錯位不會報錯，只會讓對方匯入一張看似完整的錯表。需要多行的內容一律放項目詳情。

### 3.2 欄位表

必留度分三級：**必留**（產出當下即須有值）、**交付後必留**（交付前留空，首次對帳前必須
回填）、**可選**（對方有自己的慣例時省略，省略不影響前述欄位的可驗證性）。

| 欄位 | 對應的 ticket 欄位 | 必留度 | 規格 |
|------|-------------------|--------|------|
| 項目編號 | `id` | 必留 | 該表的區域編號，形如 `INV-001`。不使用本框架 ticket ID 格式，避免外來識別符被抄進對方系統 |
| 標題 | `title`／`what` | 必留 | 動詞加受詞 |
| 原因 | `why` | 必留 | 一句話；證據放項目詳情 |
| 驗收條件 | `acceptance` | 必留 | 表內放一句摘要，全文放項目詳情 |
| 影響範圍 | `where.files` | 必留 | 帶 `repo:` 前綴的路徑（見 2.4） |
| 前置項 | `blockedBy` | 必留 | 本表的項目編號清單；無前置項留空 |
| 順序層 | `blockedBy` 推導、`wave` | 必留 | 整數，推導規則見 3.3 |
| 狀態 | `status` | 必留 | 值域見 3.4 |
| 來源 | `source_ticket` | 必留 | 盤點出處（哪個維度、哪個步驟）。路徑帶 `ws:` 前綴（見 2.4） |
| 外部編號 | 無 | 交付後必留 | 對方系統的任務編號或連結 |
| 最後對帳日 | 無 | 交付後必留 | 該列最近一次被對帳的日期 |
| 優先級 | `priority` | 可選 | 沿用對方系統的值域，不自訂 |
| 類別 | `type` | 可選 | 沿用對方系統的值域，不自訂 |
| 分組 | `parent_id` | 可選 | 父項的項目編號；子任務形態用此欄表達 |
| 負責人 | `who` | 可選 | 交付後由對方指派，分析者不預填 |
| 建議做法 | `how.strategy` | 可選 | 盤點當下未驗證的修法不寫定，標為「候選」 |

本框架內部的編排欄位（TDD 階段、決策樹路徑、版本）一律不出現。它們服務本框架的流程，
不服務追蹤的可驗證性，帶進去只會讓對方看到讀不懂的欄位而整張表被拒收。

### 3.3 順序層推導規則

```
無前置項            → 順序層 = 1
有前置項            → 順序層 = max(各前置項的順序層) + 1
```

附帶要求如下：

- 前置項必須是本表已存在的項目編號。指向表外的編號時，該列的順序層無法推導，視為欄位缺值。
- 推導不收斂（反覆代入後仍有項目算不出順序層）即表示前置項構成環，須拆項或改寫前置關係
  後重算，不得以人工指定順序層繞過。
- 順序層是推導值不是輸入值。前置項變更後必須重算，兩者不一致時以前置項為準。

**Why**：順序層存在的理由是「不依賴任何任務系統的依賴功能也能表達順序」——試算表、CSV
匯入與純文字貼文都保得住一個整數欄。若允許人工指定，順序層與前置項會各自漂移，而讀者
無從判斷哪一個是真的。

### 3.4 狀態值域

| 值 | 語意 |
|----|------|
| 待辦 | 尚未開始 |
| 進行中 | 已開始，未完成 |
| 完成 | 驗收條件全數達成 |
| 不做 | 評估後決定不處理；**必須**在項目詳情寫明理由 |

blocked 不設為狀態值。「被擋住」由前置項與順序層推導，額外設一個狀態值會讓同一件事有
兩個可寫入的地方，兩者不同步時無從判斷哪個是真的。

### 3.5 對帳紀錄格式

對帳紀錄是 append-only 的：一次對帳新增一列，不就地改寫既有列。欄位固定：

| 欄位 | 內容 |
|------|------|
| 對帳日期 | 本次對帳執行的日期 |
| 對帳者 | 執行本次對帳的人 |
| 各狀態件數 | 待辦／進行中／完成／不做 各自的件數 |
| 未對應件數 | 外部編號欄仍為空的列數 |
| 狀態有變的項目編號 | 本次對帳相較上次有狀態變化者 |

**Why**：對帳要回答的不只是「現在做到哪」——那從工作項表本身就讀得到；它要回答的是
「上次到這次之間發生了什麼」。只有逐次留存才有前後可比。

**Consequence**：就地改寫只留得住最新一次的數字，「這一項是哪次對帳才變成完成的」與
「未對應件數有沒有在減少」都不可還原，而後者正是判斷交付是否已死的唯一訊號（見第 6 節）。

**Action**：每次對帳新增一列，即使各項數字與上次相同也照樣新增——沒有變化本身就是要留的
觀測。

### 3.6 指涉穩定與狀態權威分離

**工作項編號在全時段是合法的追蹤識別，但狀態判定權威隨交付切換。** 這兩件保證常被混談，
交付前後的歸屬卻不同：

| 保證 | 交付前 | 交付後 |
|------|-------|--------|
| 指涉穩定（編號不重用、不重編） | 分析者 | 分析者。編號在全時段都是穩定識別 |
| 狀態權威（哪一份說了算） | 工作項表 | **轉移至對方系統**。工作項表降為對照表，狀態由對帳回抄，並新增一列對帳紀錄 |

**Why**：trigger 需要的是「能被指名且不漂移」，這由指涉穩定提供；「做完了沒」則是狀態
問題，交付後實際執行的是對方，分析者沒有觀測管道，事實來源只能在對方系統。

**Consequence**：不分離會出現「工作項表寫完成、對方系統還沒做」的雙主檔，而雙主檔正是
本案排除影子票所要避免的形態。

**Action**：交付後逐項的狀態欄只能由對帳回抄寫入——分析者單方改寫該欄視為違反本節。未回填
外部編號的列計為「未對應」，須先向對方系統取得任務編號或連結回填，下次對帳才能計入終態。

## 4. 讀法映射（單一權威）

各 skill 的建票類指令，在適用範圍（第 1 節）成立時依本節讀取。**本節是唯一定義處**，
引用它的 skill 加一行引用即可，不複述、不自訂映射。

### 4.1 映射表

套用本表前先確認 4.3 的閘門全數通過；未通過時本表不適用，原規則照常。

| skill 條文寫的 | 無 ticket 系統時讀作 |
|---------------|---------------------|
| 建票／開票／補票／`ticket create` | 在工作項表新增一列 |
| `blockedBy` / 前置票 / 被某票擋住 | 前置項欄，順序關係由順序層表達 |
| 狀態設為 blocked / 標記阻擋 | 不設此狀態值；以前置項加順序層表達，狀態欄維持「待辦」（見 3.4） |
| `spawned_tickets` / `children`（衍生與子任務） | 新增列，來源欄記出處；子任務形態填分組欄 |
| `wave` / 波次 / 執行順序 | 順序層 |
| ticket 完成 | 狀態改為「完成」；交付後須經對帳回抄，不由分析者單方宣告 |
| 決策票 / 待決事項掛票 | 新增列，狀態「待辦」，驗收條件寫該決策的判定條件 |
| 派發代理人建票 / 由執行者建票 | 由分析者寫入工作項表。代理人可產出待新增的列，但不直接寫入主檔——主檔只有一份，多方直寫會使 3.6 的指涉穩定失去單一保證方 |
| 引用某個工作項編號作為 trigger | 寫成 `<外接資料夾名>/<項目編號>`（例：`<外接資料夾名>/INV-003`）。編號的唯一性僅及於該資料夾，裸編號跨案會撞號 |

### 4.2 供 skill 複製的引用句

在該 skill 的建票段落加一行，措辭固定：

> 被操作 repo 無本框架 ticket 系統時，本節的建票指令依
> `.claude/skills/doc/references/external-workspace-spec.md`〈讀法映射〉讀取。

### 4.3 合法性閘門（摘要與路由）

映射成立的前提是規則層承認工作項編號。承認的射程由閘門 G1–G5 界定，全部通過才成立；
缺任一道，該編號等同無 trigger 延後，原規則照常適用。

核對順序固定：先 G5 與 G1（它們決定射程是否啟動），再核其餘。

| 閘門 | 一句判準 | 判準性質 |
|------|---------|---------|
| G5 收件方 | 射程由發現的收件方決定；框架自身與分析者端專案的發現不適用 | **分類判斷**，依 `.claude/skills/framework-issue/references/escalation-flow.md`〈介入判斷：框架問題 vs 專案問題〉的兩條 AND 判準逐條套 |
| G1 射程 | 被操作 repo 確實無本框架票庫且 ticket CLI 不可用 | 查事實 |
| G2 載體 | 編號來自工作項表主檔，且該表具備項目編號、狀態、驗收條件、前置項（含順序層）全部必留欄位 | 查欄位 |
| G3 唯一主檔 | 一個交付案只有一份追蹤主檔（逐項登記待辦、且被當作狀態來源的清單）。一次性的交接摘要與涵蓋多項的單張分析票不算 | 數份數 |
| G4 推進 | 分析者端有一張本框架 ticket 作為該交付案的對帳載體，其 acceptance 記載對帳觸發條件與承擔者。產出本表的分析票本身即可擔任，不需另開空票 | 查票 |

G1 至 G4 機械可查（查事實、查欄位、數份數、查票）；**G5 是唯一例外**，收件方歸屬屬分類
判斷，本規格不自行定義判準，改指名上表的既有 SOP。除此之外沒有一道要求判斷「這個載體
夠不夠等效」——判準一旦語意化，守衛即退回逐句判斷。

**G4 與「不開影子票」不衝突**：G4 要求的是整份交付一張對帳票，粒度是案級錨點；被排除的
影子票是逐項複製為本框架 ticket。前者不構成第二份追蹤主檔，後者構成。

**核對結果的落點就是驗證承擔者**：各道閘門的核對結果須逐道寫入 G4 那張對帳票的 acceptance
（該 repo 有無票庫與 CLI、表內必留欄位是否齊備、主檔幾份、收件方歸屬的判準套用結果）。
本規格是零工具設計，沒有 hook 會檢查外接資料夾內的檔案；G4 的對帳票是唯一被框架強制層
覆蓋的載體，因此規格的每一道要求——每格單行、外部編號回填、順序層與前置項一致、唯一
主檔——都掛在該票的 acceptance 上，由對帳承擔者在每次對帳時逐項自查。不掛上去，這些
要求就只有後果敘述而沒有檢查時機，等同自我宣告。

> **完整條文**（含承認的形態、規則 5 三種終態的對應、強制層以既有豁免標記字面扣抵的接法）
> 見 `.claude/references/decision-trigger-binding-details.md` **規則 2.6（協作射程）**；
> 射程邊界一行見 `.claude/rules/core/decision-trigger-binding.md` 規則 2 與
> `.claude/rules/core/quality-baseline.md` 規則 5。本節摘要與條文不一致時以條文為準。

### 4.4 本節不涵蓋的情況

映射處理的是「條文要求建票」。產物中**名為 Ticket 的欄位**（審查報告表、修復前評估的
記錄對象等）不在映射射程內——規則承認一個編號，不會讓一個叫 Ticket 的欄位自動接受它。
這類欄位須各自改名或補列，屬各 skill 的產物形狀問題。

**改名時用同一個欄名**：建議一律改為「追蹤編號」，值填 ticket ID 或 `<外接資料夾名>/<項目
編號>`。各 skill 各自取名會讓同一件事在不同報告裡有不同欄名，正是第 6 節要防的漂移；此處
給定一個預設名，是為了讓那批 skill 不必各自決定。

## 5. 匯入方式對照

產物要能匯入或照抄進任何任務系統，包含只有文字的 Slack。

| 對方的系統 | 做法 |
|-----------|------|
| 試算表 | 工作項表區塊直接貼上 |
| CSV 匯入 | 前置項寫在描述首行，順序層對應 section 或 label |
| GitHub Issues | 逐項建立，標題帶 `<外接資料夾名>/<項目編號>`（裸編號跨案會撞號） |
| Slack | 依順序層分段貼文 |

設計刻意不依賴任何工具的依賴欄功能：主流工具的 CSV 匯入是否保留依賴尚未對照官方文件，
把順序押在未驗證的能力上，失敗形態會是匯入後依賴靜默遺失。順序層是整數，任何工具都留得住。

**Action**：確需改用對方工具的依賴欄時，先以一列試匯並回查依賴是否保留，再決定是否放棄
順序層；未經此驗證不得逕自改用。

## 6. 已知失效形態

| 失效 | 訊號 | 防護 |
|------|------|------|
| 匯入後沒回填外部編號 | 首次對帳後外部編號欄仍有空白 | 3.6：空白列計為「未對應」，不得據以宣告終態 |
| 變成一次性報告 | 交付後零列對帳紀錄 | 交付時於 `README.md` 記下對帳責任人與觸發條件；對帳載體是 G4 的那張票 |
| 照搬 ticket 全部欄位，對方拒收 | 欄數超過 3.2 欄位表所列 | 3.2：框架內部編排欄位一律不出現 |
| 各 skill 的映射彼此不一致 | 兩個 skill 對同一欄位給出不同讀法 | 第 4 節為單一定義處，skill 只引用 |
| 順序層與前置項漂移 | 某列順序層不等於前置項推導值 | 3.3：順序層是推導值，不一致時以前置項為準 |
| 交付後分析者單方改寫狀態 | 某列狀態變動，但該次對帳紀錄未列出該編號 | 3.6：交付後狀態欄只能由對帳回抄寫入 |
| 路徑貼出後失去基準 | 對方回問「這條路徑從哪裡算起」 | 2.4：路徑一律帶 `repo:`／`ws:` 前綴，前綴隨字串走 |
