# 判讀內容要給情境與後果

> **角色**：本卡是 `compositional-writing` 的情境型 reference、被判讀 / 選型 / 決策類內容的寫作與審查引用。
>
> **何時讀**：寫「該怎麼判斷」那一層的內容時、或讀者提問「什麼情況會需要這個」時。

## 這個 reference 解決什麼

判讀類內容寫成純機制陳述時，可用程度隨讀者的既有經驗遞減——因為讀者必須自己補上「什麼時候會用到這個屬性」，而補這一塊要的正是這個判斷的輸入之一。內容的受益者因此收斂到已經握有那份經驗的一端。

遞減沿著經驗這條軸呈單峰。可用程度在中段最高：熟悉一般工程事故、不熟這個領域的讀者是補情境收益最大的一端。再往外到完全不熟這個領域的讀者，缺的已經換成術語入口，情境補了也接不上；資深端則本來就不需要。判定「這篇不需補」時要確認它落在哪一端——兩端的修法不同（見「判定不需補時，檢查換一個維度」）。

要補的是**情境**，不是實作。兩者常被一起排除，但它們的住址不同：

|      | 內容                           | 該在哪         |
| ---- | ------------------------------ | -------------- |
| 實作 | 怎麼做——程式碼、配置、指令     | 下游內容       |
| 情境 | 什麼系統會遇到、什麼事件會觸發 | **判讀層自己** |

判讀層宣告「不展開實作」是正確的分工。但判讀的定義就是「遇到 X 時該怎麼選」，把 X 拿掉之後，剩下的是分類學而不是判準。

分界線畫在**解析度**、不畫在內容類型。「webhook 訂閱、B2B 整合、對外發佈的憑證」跟「用哪個演算法、參數怎麼設」是同一件事的兩種粒度。判讀層取到讓成本可感的粒度就停——讀者要能推出這件事花多久、動到誰、卡在哪；再往下屬於下游內容，它讓讀者能執行，對「該不該做」沒有增量。用內容類型當判準會誤判形如操作步驟的句子：「要先找到對方窗口、約一個雙方都能配合的維護時間」讀起來像操作指引，實際上是判讀層必須交出的成本量級，拿掉它上一句的屬性就沒有份量。

要補的東西有三種，各自服務不同的認知動作：

| 補什麼   | 讀者用它回答   | 語言性質 |
| -------- | -------------- | -------- |
| 系統形態 | 我是不是這一類 | 分類     |
| 觸發事件 | 什麼時候要動   | 分類     |
| 微案例   | 動作晚了會怎樣 | 敘事     |

前兩種是情境（回答進入條件：這件事什麼時候跟我有關），第三種是後果的敘事化（回答走到這裡之後會怎樣）——母詞不同，不合稱「三種情境」。前兩種服務讀者的兩個時刻：形態服務設計階段、觸發事件服務事故與維運階段。判讀類內容常見的「判讀訊號」欄有時序陷阱：訊號要等設計落地才觀察得到，設計階段的讀者手上是空的，系統形態填的正是這個空缺。

第三種補的是另一個維度。前兩種都是分類語言，讀者用它們定位自己；**沒有經驗的讀者卡在定位之後**——他知道自己中了，但不知道中了會怎樣，而「會怎樣」正是他用來說服自己或說服團隊的東西。有經驗的人能自己補上這一段，這也是純分類的內容對資深讀者看起來已經完整的原因。

## 程序

1. **判定適用**。兩個問題連著問。第一，這篇在給判準嗎？分流型入口（本身就是路由）、純參考（規格表、API 文件）、程序型（步驟一二三四）都不適用。第二，**這篇的讀者站在哪個時刻**？讀者若是「已經有系統在跑、正在考慮要不要動它」，他手上有現象可觀察，內容給訊號就夠了、補形態是冗餘；讀者若在設計階段還沒有系統，訊號欄對他是空的，形態才是他能對照的東西。同一個分類裡不同篇可以落在不同時刻，逐篇判定、別整批套用。
2. **先掃出已經寫對的地方**。實測遇過的形態是同一篇裡有一兩節已經給了具體形態。掃法是找以情境起手的句子——「出現在……的架構」「當團隊……時」「什麼樣的系統」「常見於」這類起手詞有可 grep 的句法特徵。找到的段落是本篇的參照樣本，語感、顆粒度、篇幅比例都照它們對齊，比另立標準可靠；本篇找不到時，取同分類另一篇已補過的當樣本。
3. **逐節列出機制陳述**：描述屬性、承擔判準、但沒有情境的句子。
4. **對每一個問三個問題**：什麼樣的系統會走到這裡（形態）、什麼事件會逼出這個動作（觸發）、走到這裡出事會長什麼樣（微案例）。前兩個多數項目只需要其中一個，看它服務的是設計還是維運；第三個按後果直觀程度排序，最不直觀的必寫、其餘要寫出可以不寫的理由（見下方微案例段）。
5. **決定補寫形式**。動筆前先查該內容是不是已經在別節或案例庫裡——分散在別處也算有，不必為了形式整齊而複製。形態份量夠（累計超過一段）就獨立成節、緊接判讀表之後；不夠就在既有段落補前半拍。
6. **掃兩個副作用**（見下）。

## 形態的軸取決於讀者當下的變數

第 4 步問「什麼樣的系統會走到這裡」時，形態不等於「架構長什麼樣」。軸有好幾條，選哪一條取決於讀者做這個決定時**什麼是變數、什麼是已定**。

**系統架構軸**——讀者已經有系統、正在決定要不要改它。寫的是架構長相：哪些技術選擇會導致這個問題、識別特徵是什麼。例：「出現在想省掉後端中繼的架構：行動應用直接呼叫第三方 API、前端直接打雲端儲存」。

**團隊狀態軸**——選型類內容適用，因為選型當下系統可能還不存在，變數是組織現況而非系統結構。寫的是團隊處在什麼狀態、因此該先做什麼。例：「當團隊只知道系統好像怪怪的，優先補訊號；知道風險但缺安全驗證路徑，優先補驗證；知道事故已發生但協作混亂，優先補事故流程」。

**關係人約束軸**——對外契約類內容適用，變數是對方的能力而非自己的技術選擇。例：「消費者可以跟著一起部署 / 自己決定何時更新 / 無法被強制更新」，三種形態決定了紀律強度的下限。

判定「這篇缺形態」之前先問**它用的是哪條軸**。只找架構軸會把用其他軸寫成的形態誤判成缺——而誤判的成本高於漏抓：漏抓只是少補一篇，誤判會補出與既有形態並存的冗餘內容，讀者因此拿到兩套互不相干的分類法。

軸選錯也會讓補出來的內容不可用。對還沒有系統的讀者描述架構長相，他無法對號入座；對已有系統的讀者描述團隊成熟度，他要的是「我這個系統該怎麼辦」而不是「我們團隊處在哪一級」。

## 微案例：讓形態變得可想像

微案例是**無身分的短敘事**：三四句、不帶公司名、不帶年份、不帶數字帳目，只保留失敗的過程與它為什麼沒被及時發現。位置緊接在形態之後——讀者剛對號入座、動機最強。

四拍結構：

1. **當初為什麼這樣做**——寫出當時沒有人反對的理由（比較快、省一跳、兩邊都是自己人）。缺這一拍，讀者會覺得「這是別人才會犯的蠢錯」。
2. **什麼時候開始出問題**——時間推進而非同時發生。這類問題的特徵就是決策與後果之間隔著幾個月。
3. **為什麼沒有被及時發現**——監控盲區、時間差、責任分散。這一拍最不可省略：其餘三拍讀者能從機制自行推得，第三拍取決於該組織的監控與責任配置，是唯一推不出來的，也因此最常被省略。
4. **止血的代價**——修復本身要付什麼。缺這一拍，讀者會以為出事再改就好。

長度控制在三四句，要更長就代表它該進案例庫而不是留在章節裡。微案例挑後果最不直觀的一兩個形態寫；直觀的（密鑰外洩會被冒用）補了是冗餘。**「一兩個」是上限而非配額**——下限由不直觀的形態有幾個決定：先把該篇的形態按後果直觀程度排序，最不直觀的必寫，有兩個以上而只寫一個時要就地寫出漏掉的那個為什麼可以不寫。排序在動筆前做；照節次順序補到哪算哪，挑中的通常正好是後果最直觀的那幾類。舉證那一句同時是驗收痕跡——沒有它，「只寫一個」與「只挑得出一個」在成品上看起來一樣。

**四拍要有來源，寫不出來就留白**。四拍是骨架不是填空欄位：每一拍要出自親歷的事件、案例庫已記下的形態、或機制上必然如此（時間差、憑證隨產出物擴散這一類推得出來）。第三拍的風險最高，而風險來源正是它的價值——它是唯一推不出來的那一拍，推不出來就代表沒有這段經驗的人只能發明它，而模板本身不會擋下發明：編造的監控盲區讀起來跟真實的一樣完整。這個口子在方法交給缺該領域經驗的人、或交給生成工具執行時最先破，因為模板的第三格恰好是他們手上沒有的東西。

留白的理由是編造的代價不對稱：讀者據此以為監控補上那一項就夠了，而一則具體且錯誤的盲區比沒有微案例更難被後續審查推翻——它讀起來已經很像經驗。四拍都無來源時，這一節留空並登記待辦。連帶的排程後果是：微案例補不完一輪掃描的全部章節，有素材的先補、其餘登記缺口。**一輪之後所有章節都有了微案例，本身就是照模板填的訊號**。

**與真實案例的分工**：教學內容引用真實案例時要剝離身分與規模鋪陳，那些帳目的住址在案例記錄原文。這條原則禁的是搬運帳目與身分、不是禁具體敘事——無身分微案例同時滿足兩邊，它有敘事因此可想像，沒有身分與帳目因此不侵占案例記錄的責任。微案例在章節內讓形態可想像，真實案例在案例庫承擔可查證，兩者不互相取代。

## 判定不需補時，檢查換一個維度

判定「這篇不需要補形態」不等於這篇沒有缺口。缺形態與缺術語入口是同一個問題的兩種形式——**讀者都得自己補上一塊才能使用內容**，差別只在缺的是情境還是名詞。這一步對應的正是前面說的單峰兩端：資深端判定不需補之後確實沒有下一步，零經驗端的「不需補形態」只代表他卡在更前面。所以判定不需補形態時，接著查卡連結覆蓋：

掃主線術語的出現次數與連卡次數。同一個術語在一篇裡出現十幾次卻一次都沒連卡，讀者要嘛已經懂（那這篇對他有價值的部分不在這裡）、要嘛得自己去查。實測到的形態是：某篇的標題就寫著某個術語、它是該篇的核心概念，全篇卻零連卡，而同分類其他篇的卡連結數明顯高於它——**同分類內的卡連結數落差本身就是偵測訊號**，比絕對數量可靠。機制是絕對數量隨篇幅與術語密度變動，而同分類內這兩個變因相近，落差因此排除了干擾項。

補的規則是每篇第一次出現時連、後續裸用。這一步的成本遠低於補形態（幾個連結 vs 一節內容），但對落在該篇的搜尋讀者影響一樣大。

## 逐節讀會撞到錯置內容

第 3 步「逐節列出機制陳述」要求逐節讀完整篇，而逐節讀的常見副產物是發現某一節根本不屬於這篇。這是逐節讀擋不掉的，而非額外的檢查項——真正需要決定的是撞到之後怎麼處理。

辨識訊號由弱到強：節標題的主題與篇標題不同；該主題在同一個分類裡已有更專門的落點（專門的 playbook、案例庫、或另一篇主章）；**錯置內容的篇幅與主體相當或更長**。最後一項是最強的訊號，實測遇過主體三十餘行、錯置內容近四十行的情形——那時這篇實際上是兩篇擠在一起。

處置有三條規則：

**標路由目的地，不刪**。這段內容存在代表有人在某個情境下需要它，刪掉會讓需求變成隱性缺口。要標的是「它該去哪」而不只是「它不屬於這裡」——只標後者時，修改者容易選最省力的動作（刪除）而非最正確的動作（路由）。

**登記待辦，不當場搬**。搬遷是內容重組，要同時驗證來源與目的地兩端，尺度大於補情境。混在同一輪做會讓一個小任務變成大任務，而且中途難停——逐篇檢查能隨時中斷正是它的價值所在，不該被這件事破壞。

**前置條件寫明「先驗證目的地的涵蓋度」**。目的地若已經有完整的同主題內容，搬過去是製造重複，比留在原地更糟。這個驗證要在動手搬之前做，不是搬完才發現。

## 補形態會暴露出「這一列沒有解法落點」

補形態要回答「讀者對號入座之後接下來去哪」，而判讀表不問這個問題。表格的每一列可以欄位齊全（訊號、後果、控制面、路由欄都有值）而仍然沒有落點——欄位齊全正是遮住它的原因。

辨識訊號是**同一張表的列與深化段不對稱**：N 列裡有 M 列各有一節展開，其餘幾列沒有。這個不對稱在補形態之前沒有人會發現，因為表格看起來完整、而缺的那幾列也沒有空欄位。實測遇過五列的表只有四列有深化段，缺的那一列直到補形態時才現形。

這一種與「逐節讀會撞到錯置內容」方向相反：那是這篇多了不該有的內容，這是這篇少了該有的內容。處置的判準是讀者到達後能不能拿到**最小可行答案**：

**一段話加幾個連結就能讓他繼續走**——當場補判讀層該給的那一節，與同表其他列的深化段對稱。判讀層要給的是判準與成本量級，不是完整教學；把整個主題的教學搬進來會讓這一節長過它服務的那一列。

**主題需要完整推導才有價值**——只登記待辦，並在該段明說目前沒有對應章節。明說的理由是讀者找不到時的預設歸因是自己沒找到，而不是它不存在；不說的話他會把時間花在搜尋上。

**不當場寫完整章節**。完整章節是新內容生產，尺度遠大於補情境，混在同一輪做會讓逐篇檢查失去隨時中斷的能力。

## 出口盤點：跨兩個階段各跑一次

用一個問題掃全文：**讀者現在知道這是問題了，他去哪解決**。讓缺口現形的是這個換視角的動作本身——既有的檢查維度都在驗「已經寫的內容對不對」，用段落當視角時分析句讀起來完整、本身沒有缺口。

盤點要**跑兩次**，因為單位不是同時存在的。判讀表的每一列、風險邊界的每一條、out-of-scope 每一項到「不在本章範圍」為止的宣告，在文章寫完的當下就掃得到；微案例末端那句「補起來要……」要等微案例寫出來才有。整個盤點延到補範例之後，前幾類的缺口會被拖著；只在補範例之前掃一次，最後那一類永遠掃不到。範例的貢獻是多出一類單位，不是解鎖整個盤點。

檢查單位是**每一個被提出的問題**，判準是「這一句指名了一個問題而沒有就地解決它」——這是規則不是清單，收斂動作段的每一步、跨章交叉引用段同樣會生出新問題。文末的路由段回答「讀完整篇之後往哪走」，回答不了「讀到第三節這一句時該怎麼辦」；有路由段的文章仍然可以在段落層級處處落空。命中率最高的是微案例末端——四拍的最後一拍是止血代價，它把讀者推到「所以要怎麼止血」，而那個問題在分析段落裡不會被問到。

四種狀態與處置：

- **出口存在且就在手邊**——合格。
- **出口存在但在文末**——目的地承接、連結也有效，只是離問題發生的位置太遠。就地補一句連結，並在句子裡說明去那裡要拿到什麼。
- **出口不存在、主題能用最小可行答案打發**——當場補。份量夠獨立成篇的寫簡版，並在開頭明說自己是簡版與缺什麼，否則它會被當成完整內容而永遠不被補完。
- **出口不存在、主題需要完整推導**——明說它不存在並登記待辦，同時給一條最小判準讓讀者當下不至於卡住。明說是這一格的重點：讀者找不到某個主題時的預設歸因是自己沒找到，沉默會讓他把時間花在搜尋上。

**替換微案例前先掃第四拍**。止血代價那一拍常常是全篇唯一寫出止血路徑的地方，而依「挑後果最不直觀的一兩個」替換微案例時，替換的理由只評估了前三拍。實測遇過一則微案例因後果過於直觀被換掉，而它的第四拍是全篇唯一提到某個止血連鎖的地方。掃法是問那句止血描述在別處有沒有第二個出處，沒有的話先把它移進風險邊界或判讀段再替換。

## 第六種產出：共同前提沒有住址

前五種產出都是對單篇操作的。第六種只在把幾篇並置之後才出現：**同一個判斷被三篇以上當成前提引用，而沒有任何一篇承接它**。

它在單篇視角下不落空——每一篇都給了自己需要的那一角，讀者當下也走得下去。缺的是那條軸從來沒有被完整寫過，而各篇寫的都是「從我這一篇看得到的那一角」。不屬於任何一篇的那些角因此直接消失。

**前置段是它最常見的藏身處**。不屬於本篇的內容放進前置段之後有了合法容身處，因為前置段確實是本篇的適用性閘門——所以「撞到不屬於這篇的內容」那條檢查不會觸發，那條管的是不屬於、而前置段屬於。辨識訊號是：**那一段回答的問題比本篇的主題更早發生，而且對別的篇章同樣成立**。

判別缺卡還是缺章：

- 同一個名詞在多篇各被解釋一次、每次解釋的內容相同 → 術語，建卡、各篇連過去。
- 同一條判斷軸在多篇各被交代一角、每篇寫的角度不同 → 缺章，因為取捨需要並置才成立，而並置只能發生在同一篇裡。

偵測用數：同一個概念被三篇以上當前提、且各篇寫的不是同一句話時觸發評估。三篇是門檻不是定則——兩篇時通常仍是其中一篇的延伸段，三篇之後「哪一篇是主場」這個問題就沒有答案了。

處置：新開一篇承接整條軸，各篇的那一角壓縮成一到兩句加一條路由留著當閘門（刪掉會讓每個入口都少一道判斷），新篇要標明自己是誰的上游——它在所有下游篇章之前，而集合的閱讀路線多半是照編號寫的，缺這一句時新篇會變成又一篇沒有入口的內容。

## 正反例

### 例一：機制屬性缺觸發事件

**反例**——三句都正確，但讀者不知道什麼時候會用到：

> 使用者層可以撤銷單一 session 而不影響他人；系統層的憑證由所有呼叫共用，撤銷等於中斷整條整合；對應層沒有可撤銷的憑證，處理的是映射資料的一致性。

**正例**——每一層配上誰會逼出這個動作，並讓後果變成可感受的量：

> 使用者層的撤銷由個別的人的事件觸發：帳號被回報盜用、員工離職當天、使用者改完密碼要踢掉其他裝置。這一層可以撤銷單一 session 而不影響他人，所以處置能立刻執行。
>
> 系統層的撤銷由憑證本身的事件觸發：密鑰被 commit 進公開 repo、知道那把密鑰的人離職、廠商通報他們那端外洩、輪替週期到期。這一層的憑證由所有呼叫共用，撤銷等於中斷整條整合——落到實際操作是先找到對方的窗口、約一個雙方都能配合的維護時間、兩邊同時換。同一個「立刻撤銷」的需求，在這一層要用天或週計算。

差別在最後一句：屬性（撤銷等於中斷整合）本身沒有份量，換算成時間尺度之後才有。

### 例二：分類缺對號入座的入口

**反例**——分類正確、定義清楚，但讀者無法判斷自己屬於哪一類：

> 機密性：讓內容對持有密文的人不可讀。來源與完整性：證明內容出自持有密鑰的一方且未被竄改。可讀性遮蔽：讓內容在載體上不以明文出現。

**正例**——給一條貫穿的判準軸，再讓每一類掛上具體處境：

> 判斷自己需要哪一類，看的是資料會在哪裡、被誰看到：
>
> - 資料會離開自己控制的範圍時要**機密性**——備份送到第三方儲存、跨區複製、筆記型電腦上的離線副本。
> - 系統之間互相呼叫、或要接收外部推送時要**來源與完整性**——webhook 訂閱、B2B API 整合、對外發佈的授權憑證。
> - 內容要印在會被看到的載體上時要**可讀性遮蔽**——實體標籤、QR Code、放進網址的參數。

判準軸（資料會在哪裡、被誰看到）比逐類舉例更重要——沒有軸的例子清單，讀者遇到清單外的情況仍然無法判斷。

### 例三：問題節點表缺系統形態

**反例**——表格的「判讀訊號」欄要等設計已經落地才觀察得到，設計階段的讀者對照不到任何東西。

**正例**——在表後補一節，逐類給架構長相、成因與識別特徵：

> **系統憑證下放到客戶端**出現在想省掉後端中繼的架構：行動應用直接呼叫第三方 API、前端直接打雲端儲存或地圖服務、IoT 裝置與桌面應用。動機通常是離線也要能運作、或少一跳延遲。這一類的識別特徵最明確——產出物裡有一把對方系統認得的憑證。

三個成分各有用途：**架構長相**讓讀者對號入座、**成因**讓他判斷自己是不是正在走向這裡、**識別特徵**給一個可立刻執行的檢查。三者之中識別特徵最有價值也最難寫，寫不出來時通常代表這一類的邊界還沒想清楚。

### 例四：不需要補的情況

以下三種形態已經足夠，再加形態是冗餘：

**已用其他措辭給了情境**。「驗證素材定義不一致是跨團隊對接最常見的耗時來源」——「跨團隊對接」就是形態，不必再加一句「什麼樣的系統會遇到」。

**程序型內容**。判讀流程的步驟一二三四是操作順序，它的可用性靠每一步夠不夠具體，不靠形態。

**分流型入口**。整段責任是把讀者導到別處的內容，補形態會讓它變成它本來要路由過去的那篇。

## 修法的副作用

**補情境會引入第二人稱**。具象化的敘述天然帶出「你的產出物」「你得先找到窗口」，因為講情境時會不自覺對著人講。中性陳述的規範在這一步最容易破功——補完專門掃一次，把主詞換成受詞或省略（「產出物裡有一把……」「先找到對方的窗口」）。

**原本的封閉計數會失準**。缺情境常伴隨缺段落：正文寫「三種混法」而判讀表有四列，因為第四類從來沒有展開段。補上之後那個數字才浮現為錯誤。反過來用：**封閉計數與表格列數對不上，本身就是缺段落的偵測訊號**，可以在動筆前先掃一次。

檢查缺不缺的單位是「內容」而非「段落」——同一列的內容分散在別節也算有，硬要每列都有獨立段落會製造重複。

## 判讀徵兆

- 讀者的提問是「什麼情況會需要這個」「什麼樣的系統會這樣做」——缺情境的直接訊號，不是讀者不夠用功。
- 通篇是屬性陳述（X 具備 Y 特性、A 與 B 的差異在 C），沒有一句是「什麼時候會遇到」。
- 判讀表的每一列都有訊號欄，但那些訊號都要等設計落地才觀察得到。
- 同一篇裡有一兩節寫了具體形態、其餘沒有——能力在、檢查點不在。
- 內容被資深同事評為「寫得很清楚」，同時被新人評為「看不懂要幹嘛」。
