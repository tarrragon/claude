# 文件的職責數從修改紀錄讀出：長度當拆分訊號的誤判、加段落之前的檢查與拆完之後的外部引用

> **角色**：本卡是 `compositional-writing` 的支撐型原則（principle）、被 `structuring-with-solid.md` 的 S 單一責任與拆完之後的交界檢查、`writing-documents.md` 的拆分判斷 引用。
>
> **何時讀**：要往既有文件或規則檔加一節、懷疑一份文件塞了多種職責、要稽核一份累積式的規則檔，或剛拆完一份文件要處理原檔與指向它的引用時。

## 核心原則

單一職責原則把職責定義成改變的理由。放在版本控制裡的文件，每一次修改都留下一筆紀錄，所以**一份文件承擔幾種職責，可以從它被哪些主題修改過讀出來**：

```bash
# 列出一份文件的修改，每行是短 hash 與 commit 標題；--follow 讓改過檔名的檔案也看得到改名前的紀錄
git log --follow --no-merges --format='%h %s' -- <檔案路徑>
```

依 commit 標題歸類，類數就是職責數。作者預測「這份文件會因為什麼事件更新」的變動理由測試適用於還沒有歷史的新文件；有歷史的文件用紀錄，兩者互相對照。

## 長度當拆分訊號的兩種誤判

長度與職責數是兩個量。一份 600 行的設定參數表只描述同一份設定，長度觸發了拆分而它只有一種職責，切開之後讀者要在幾份檔案之間找一個欄位；一份 80 行的 README 寫了安裝、貢獻規則、發版流程與聯絡窗口，長度沒有觸發，它留在原地繼續累積主題。所以拆分的觸發條件與判斷都看職責，長度只決定一種職責之內要不要分節或分層。

集中登記型文件是例外：變更紀錄、索引頁、術語表的職責就是集中登記所有主題，被許多主題修改是它的設計目的。依職責拆它不會降低衝突，處置改成每個項目一個片段檔；不想改成片段檔的逐行清單，可以在 `.gitattributes` 設 `merge=union`，兩邊追加的行都保留、不產生衝突，代價是真正的衝突也不出標記。

## 加段落之前的檢查

一份文件多出一種職責，發生在有人往裡面加一節的那一次修改。加之前問：**這一節的修改理由，在不在這份文件既有的修改理由裡**——既有理由從修改紀錄讀，不從標題猜。不在的話，先找承接它的那一份文件；找不到才開新檔，原檔留一句連結。規則類文件（專案規範、agent 指令、skill 檔）最需要這一問：每一條規則都有人在某一次出事之後補上，它們累積段落的速度比文章快，也最少人回頭整理。

## 規則類文件的職責稽核

累積式的規則檔定期跑一次稽核：讀修改紀錄、依主題歸類、對照每一類落在哪幾節。產出是一張表（主題 / 修改次數 / 落在哪幾節 / 處置），處置分留在原處、移到承接它的檔案、拆成新檔三種。commit 標題讀不出主題時（「docs: update」）改看 diff 落在哪幾節；squash merge 會把多個主題壓成一筆，這時精度跟著降，報告上要寫明。

## 拆完之後的外部引用與原檔

拆分之後新檔彼此之間的交界缺陷另有一組檢查（見 split-defects-land-between-the-files）。新檔以外還有兩件事：

- **指向原檔的外部引用**：其他文件、腳本、agent 指令與書籤引用的是原檔路徑與原段標錨點。段落搬走之後，連到原錨點的連結仍然打得開原檔，只是停在頁面頂端；連結檢查若不比對錨點、或引用不在它的掃描範圍內（skill 目錄、其他 repo、agent 指令），失效時沒有任何訊號。拆完用 `grep -rl '<原檔路徑>'` 與 `grep -rn '<原檔名>#'` 找出來逐一改。
- **原檔保留成導覽表**：原檔的路徑已經被引用，刪掉它等於讓上一條的失效全部發生一次。原檔改成一張表，每一列寫一種讀者需求、對應的新文件與那份文件涵蓋什麼。

## 為什麼既有的檢查沒擋住

判斷該不該拆的觸發條件寫成「越寫越長」、決策表用行數門檻時，短而混雜的文件不會進入變動理由測試；而變動理由測試是作者的預測，作者對自己剛加的那一節總是預測得出它屬於這裡。拆完之後的交界檢查只列新檔之間的位置，原檔與外部引用不在清單上。

## 適用邊界

方法在一篇教材與一篇方法論裡寫過，還沒有拿實際的規則檔跑過稽核，主題數多到什麼程度該拆沒有量過，本卡不給門檻。修改紀錄當量測工具的前提是 commit 標題寫得出主題。
