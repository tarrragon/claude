# 功能說明寫出設定的作用、預設值與預設值服務的情境：只寫「在最左邊時聽不到」交付的是一次觀察，讀者換一個情境就判斷不了該不該改

> **角色**：本卡是 `compositional-writing` 的支撐型原則（principle）、被字句層 keyword bank 的〈設定步驟只寫現象與結果〉引用；判讀問句與嚴重度以 bank 那一條為準，本卡是它的推導、修法與例子。
>
> **何時讀**：寫或審一段要讀者改動某個設定（滑桿、開關、選單、設定檔裡的值）的操作說明，而說明只寫了改之前看到的現象與改之後的結果時。

## 論述基礎與限制

這張卡處理的寫法：一段操作說明要讀者把某個設定從預設值改成另一個值，說明裡寫的是改之前看到的現象（「音量滑桿在最左邊時聽不到」）與改之後的結果（「往右拉就聽得到」），沒有寫出這個設定控制的是什麼、預設值是什麼、預設值服務哪一種使用情境。**預設值服務的情境**指維持預設值時得到想要的結果的那一種用法；它不一定是設計者寫明的意圖，可以是從機制推出來的效果。

這張卡來自一個教學站的一篇文章：平板用 USB 接上電腦、在 macOS 的「音訊MIDI設定」啟用成電腦的音訊輸入之後，用 QuickTime Player 的「新增音訊錄製」視窗把這個輸入從電腦的喇叭播放。實測時，視窗打開後聽不到平板的聲音，把視窗裡的音量滑桿往右拉之後才聽得到，不必按下錄音。初稿照實測的順序寫成「再把視窗裡的音量滑桿往右拉，不必按下錄音，平板的聲音就從電腦目前的聲音輸出播出；音量滑桿在最左邊時聽不到」。使用者（委託這次寫作的人）指出這裡應該寫成：系統預設錄音時的播放音量是靜音，所以要讓平板輸入的聲音從喇叭放出來，需要把滑桿往右拉；也指出寫功能說明時不只講操作的方法，重點是分析設計的理念或考慮的背景。改寫後的版本寫出滑桿控制的是把輸入同步從喇叭播放的音量、預設在最左邊（靜音）、預設靜音的效果，以及這次為什麼要拉開。

偵測量測：在同一個教學站的教學文章用 `(時|的話)，?(聽不到|看不到|沒有聲音|不會出現|沒有反應|不會生效)` 找「某個狀態時看不到結果」的句子，22 個檔各 1 行；抽讀三行，兩行是連結文字，一行（電視數位音訊輸出格式的說明）已經寫出預設值與接收端只收 PCM 的理由。這個形態沒有穩定的詞，pattern 只找候選，偵測要逐一讀改動設定的步驟。

限制：證據只有一個個案。預設靜音的效果是從機制推出來的；廠商的設計理由沒有查到出處，所以改寫只寫效果並標明是推論，不寫成廠商的意圖。滑桿在錄音視窗打開、還沒按下錄音時就作用，是這一次實測的結果，沒有在其他版本上確認。這張卡沒有量過讀者讀兩個版本時的實際理解。

## 核心原則

**一個設定的說明寫出它控制的是什麼、預設值是什麼、預設值服務的情境，再寫出這次的用途為什麼要改。** 改動的理由也寫出來，不留給讀者從前面的內容推：滑桿控制的是把輸入同步從喇叭播放的音量；預設在靜音，服務的是用麥克風錄音、不想讓喇叭的聲音被錄回去的用法；這次的用途是把輸入當成音源播放，跟預設服務的情境相反，所以要拉開。這是 [判斷標準要寫到條件層](criteria-need-condition-action-mapping.md) 用在設定上的情形：一個設定的預設值本身就是一個判斷，作者寫出它的條件，讀者才能把自己的情境對進去。

**只寫現象與結果時，讀者拿到的是一次觀察，換一個情境就判斷不了。** 讀者照「在最左邊時聽不到，往右拉就聽得到」去做，完成得了這一次把平板的聲音播出來的用途；他下一次用同一個視窗錄麥克風時，手上只有「往右拉才聽得到」這條經驗，判斷不出這一次該不該拉，拉了就把喇叭的聲音錄進去。作者寫出預設值服務的情境，讀者才知道自己的用途跟預設一致還是相反，在那篇操作說明沒寫到的情境也判斷得了。

**作者照實測順序寫下來，初稿的句子只寫到現象與結果。** 作者實測時的經過是打開視窗、聽不到、試著拉滑桿、聽到了。設定的作用與預設值服務的情境不在這個經過裡，作者要另外去查、去推，所以初稿裡不會有。成因跟「文章照作者發現的順序組織，讀者要的是題目本身的結構」相同（那條原則的推導在 `multi-round-review` skill 的 `references/principles/article-writes-the-topic-not-the-authors-path-to-it.md`）。

**預設值服務的情境依出處寫，查不到出處的設計意圖不寫。** 官方文件寫了這個預設值的用意時，寫的人照文件寫並附出處；沒寫時，寫從機制推得出的效果並標明是推論（「預設靜音的效果是用麥克風錄音時，喇叭的聲音不會被錄進去」，讀者可以自己驗證）；效果也推不出來時，在預設值服務的情境那個位置寫「文件沒有說明這個預設值服務的情境」。後兩種寫出查過哪一份文件：「文件沒有說明」本身是一個宣稱，沒查過就寫，跟虛構的歸因是同一類。「廠商預設靜音是為了避免回授」是對設計者意圖的宣稱，沒有出處時是虛構的歸因，標了推論也一樣，所以意圖句改寫成效果。效果與意圖給讀者的判斷材料相同：讀者知道預設值服務哪一種用法就夠了，不需要知道設計者心裡怎麼想。

**這張卡管會改變系統行為的設定，預設值本身可能依環境而變。** 這張卡管的是改動之後會改變系統的輸出、可達性、資料、安全或費用的設定；只影響名稱、外觀或單次指令輸出格式的設定，維持預設值的用法與改動之後的用法沒有結果上的差別，寫出預設值服務的情境只會是一句空話。保留預設值的步驟與沒有預設值的必填欄位不在這張卡的範圍裡。預設值依軟體版本而變時，寫的人把它寫在文章已經交代版本的範圍內，或寫出它取自哪一個版本；依帳號、區域或機型而變時，寫出查法而不寫值，這是 [寫出特定實例的值，就取代了讀者本來要做的查證](written-value-replaces-the-readers-check.md) 用在預設值上的情形。

**操作與概念分成兩篇時，步驟旁仍然把作用、預設值、預設值服務的情境與這次為什麼要改各用一句寫出。** 設定的完整機制與取捨已經寫在概念文章時，操作文章的步驟旁寫這幾句、再連過去；這幾句是讀者在這一步判斷要不要改的材料，不算在操作文章裡重寫觀念。

## 反模式

- **只寫現象**：「音量滑桿在最左邊時聽不到。」讀者知道要拉，不知道滑桿控制什麼、什麼時候不該拉。
- **只寫結果**：「把滑桿往右拉，就聽得到平板的聲音。」讀者不知道滑桿控制什麼、什麼時候不該拉，而且會以為滑桿是這個功能專用的開關。
- **把效果寫成設計者的意圖**：「廠商為了避免回授，預設把它設成靜音。」沒有出處時，這是虛構的歸因。
- **寫了預設值、沒寫它服務的情境**：「這個滑桿預設是靜音。」讀者知道起點，仍然判斷不出自己的用途要不要改。
- **寫了效果、沒標推論**：效果是從機制推出來的，句子卻寫得像官方的說明；讀者分不出哪一句有出處。
- **改寫時丟掉原句的操作事實**：補上作用與預設值時，把原句的「不必按下錄音」刪了，讀者會以為要按下錄音才聽得到。

## 修法

1. **找出改動設定的步驟**：逐一讀操作說明裡要讀者把某個設定從預設值打開、關閉、拉動、切換、改選成另一個值的步驟。「某個狀態時看不到結果」這類句子是候選，但沒有穩定的詞可以掃，所以以步驟為單位讀。
2. **對每一個設定寫出作用、預設值與預設值服務的情境**：作用（「把輸入同步從喇叭播放的音量，錄音視窗開著時就作用」）、預設值（「最左邊，也就是靜音」，寫在文章交代的軟體版本之下，或寫出取自哪一個版本）、預設值服務的情境（「用麥克風錄音時，喇叭的聲音不會被錄進去」），依出處寫：文件寫了照寫並附出處，沒寫寫效果並標明推論，效果也推不出來時寫「文件沒有說明這個預設值服務的情境」。
3. **寫出這次的用途為什麼要改**：這次的用途跟預設服務的情境哪裡不同（「要讓平板輸入的聲音從喇叭放出來」），所以要改成什麼值。現象（「拉之前聽不到」）可以留下，寫成驗證的訊號，不當成理由。
4. **核對原句的操作事實都還在**：改寫前後逐項比對原句寫到的動作與條件（「不必按下錄音」），補內容時不刪掉它們。

改寫的例子：

- 改前：「再把視窗裡的音量滑桿往右拉，不必按下錄音，平板的聲音就從電腦目前的聲音輸出播出；音量滑桿在最左邊時聽不到。」
- 改後：「錄音視窗裡的音量滑桿控制的是把輸入同步從喇叭播放的音量，視窗開著時就作用，不必按下錄音；視窗打開時它預設在最左邊，也就是靜音，錄音時只把輸入寫進檔案、不從喇叭播放。這個預設的效果是用麥克風錄音時，喇叭放出的聲音不會再被麥克風錄進去（從機制推論；廠商的錄音說明頁只寫這個控制用來聽正在錄的聲音，沒有說明預設值）。所以要讓平板輸入的聲音從喇叭放出來，要把音量滑桿往右拉；拉開之後不必按下錄音，平板的聲音就從電腦目前的聲音輸出播出。」

## 判讀徵兆

| 徵兆                                                                       | 判讀                                                                |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 步驟寫「X 在某個狀態時看不到結果，改成另一個狀態就有」                     | 只交付一次觀察；補設定的作用、預設值與預設值服務的情境              |
| 步驟寫了預設值，沒寫預設值服務哪個情境                                     | 讀者知道起點，判斷不出自己的用途要不要改                            |
| 句子寫「為了……，預設……」，主詞是廠商或設計者，沒有附出處                   | 把效果寫成意圖；改寫成效果並標明推論，或補上出處                    |
| 效果句沒有出處，也沒有標明是推論                                           | 讀者分不出哪一句有出處；補上推論的標記                              |
| 讀者換一個那篇操作說明沒寫到的用途（同一個視窗錄麥克風），判斷不出該怎麼設 | 預設值服務的情境沒寫出來                                            |
| 說明照作者的實測經過排列（打開、沒反應、試著改、成功）                     | 文章照發現的順序組織；改成設定的作用 → 預設值 → 本次用途 → 改成什麼 |
| 改寫後的句子少了原句的動作或條件                                           | 補內容時刪掉了操作事實；照原句補回                                  |

## 跟其他抽象層原則的關係

- [判斷標準要寫到條件層：維度清單是判斷標準的空殼](criteria-need-condition-action-mapping.md)：最接近的原則。那張卡要求判斷標準寫出條件、後果與理由；這張卡把同一個要求用在設定的預設值上：預設值是設計者做好的一個判斷，說明要寫出它服務的條件，讀者才能拿自己的用途比對。
- 文章照作者發現的順序組織（`multi-round-review` skill 的 `references/principles/article-writes-the-topic-not-the-authors-path-to-it.md`）：同一類成因。那條原則處理文章寫進作者的認識過程；這張卡處理操作說明照作者的實測經過寫成「沒反應、改了、有了」，設定本身的作用沒有寫進去。
- [AI 生成的內容不虛構經驗與出處](no-fabricated-experience-or-attribution.md)：預設值服務的情境查不到出處時，設計意圖不寫；這張卡把那張卡的要求用在「設計理念」這一類句子上，改寫成標明推論的效果。
- [寫出特定實例的值，就取代了讀者本來要做的查證](written-value-replaces-the-readers-check.md)：預設值是會隨版本改變的值，寫的時候綁在文章交代的版本之下；讀者要自己填的值照那張卡處理。
- [教鑑別能力、不教操作流程](teach-judgment-not-procedure.md)：那張卡在文章層要求以機制理解為主線；這張卡在單一步驟的層次做同一件事，一個設定步驟也要交付讀者在別的情境用得上的判斷。
- [會誤解處補正向知識、不把誤會當敘事中心](fill-knowledge-gap-not-center-misconception.md)：「在最左邊時聽不到」是把讀者會遇到的現象當成說明的內容；那張卡的修法是補上讓誤會不發生的正向模型，這張卡補的正向模型就是設定的作用與預設值。
