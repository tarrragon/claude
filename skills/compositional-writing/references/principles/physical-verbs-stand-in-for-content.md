# 物理動詞佔住的內容：撐、扛、垮、掛在、站得住各自要寫出什麼，以及這些詞在負載情境裡的意思

> **角色**：本卡是 `compositional-writing` 的支撐型原則（principle），被字句層 keyword bank 的「物理化錯配」類別引用。
>
> **何時讀**：稿件裡出現「撐得住」「拖垮」「扛起」「掛在」「站得住」這類借來的物理動詞，要判斷它佔住什麼、改寫時要寫出什麼時；或者處理負載情境的「撐不住」「壓垮」「撐過尖峰」時。

物理化錯配的偵測方法是問這個動詞照字面成立需要什麼物理條件。偵測只負責找出候選。**每一個借來的物理動詞都佔著一個內容格，而不同的動詞佔住的格不同**，所以找到之後先判斷它佔住哪一格，再寫出那一格的內容；換成另一個同義詞，只是把同一個空位換個詞佔著。這與「問題」這個詞是同一類（見 [「問題」與「回答」當框架詞](question-answer-frame-blurs-problem-issue-request.md)）。

## 動詞與它佔住的內容

| 類別       | 常見詞形                                     | 佔住的內容                       | 改寫要寫出的                                                                                   |
| ---------- | -------------------------------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------- |
| 足夠性斷言 | 撐得住、撐不住、撐起、能撐、扛得住、頂得住   | 需求、判斷標準                   | 要滿足什麼需求、滿足到什麼程度算夠、靠什麼機制滿足或在哪一點不再滿足                           |
| 失效結果   | 拖垮、壓垮、打垮、垮掉、扛不住、頂不住、會垮 | 失效的形態與傳遞的路徑           | 哪個元件失效、失效成什麼樣子（變慢、無回應、崩潰、資料錯誤），以及經由哪一項共用的資源傳到別處 |
| 負擔       | 硬扛、扛起、交給某方自己扛、啃               | 誰承擔、承擔什麼工作、代價       | 承擔者是誰、要做哪幾件事、付出的是人力、時間、維護成本還是前置知識                             |
| 關係       | 掛在、咬合、咬得最深                         | 兩個對象之間的關係與它的程度     | 關係動詞（依賴、隸屬、由誰管理）或程度的狀態詞（耦合最緊）                                     |
| 可信度     | 站得住、站不住                               | 讀者讀完之後該產生的判斷         | 多數時候整句不寫；必須寫時，寫出它成立依賴的前提與證據的範圍                                   |
| 字面或技術 | 掛在 volume 上、程序掛在 session 上          | 設定或系統裡實際存在的附掛關係   | 不必改                                                                                         |

「扛」與「垮」各跨兩類，判斷看句子：「平台扛掉 patch 與憑證」是負擔，「服務上線後怎麼扛負載」是足夠性；「一個故障拖垮整個服務」是失效結果，「這套說法會垮」在論證裡是可信度。

失效結果這一類的資訊落差最大：讀者讀到「拖垮」只知道後果嚴重。「讓一個可以降級的功能故障拖垮整個服務的接流量能力」實際要說的是 readiness 綁了一個非必要的依賴，那個依賴一壞，整個服務就被移出接流量的名單；寫成機制，讀者知道該把那個依賴移出 readiness。

## 負載情境裡的容量、過載、故障擴散、突發緩衝與耗盡時間

| 常見寫法               | 實際在講的事                       | 業界術語                                       | 句子要寫出的內容                                                                     |
| ---------------------- | ---------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------ |
| 撐得住、撐不住、扛得住 | 元件在判斷標準下能處理多少負載     | capacity、throughput、saturation point、headroom | 負載的單位與量、判斷標準（如延遲百分位數的門檻、錯誤率）、哪一項資源先飽和、餘裕多少 |
| 壓垮、扛不住、打垮     | 負載超過容量之後發生什麼           | backpressure、load shedding、retry storm       | 超過之後的機制（佇列變長、延遲非線性上升、逾時引發重試把負載放大）與系統怎麼自保     |
| 拖垮                   | 一個元件故障或變慢，讓別的元件失效 | cascading failure、blast radius、bulkhead      | 共用的是哪一項資源（連線池、執行緒、同步呼叫）、傳遞路徑、用什麼隔離                 |
| 撐過尖峰               | 有時間限制的突發，靠緩衝度過       | burst、queue depth、Little's Law               | 超出容量的速率乘上持續時間，對照緩衝能容納多少，以及恢復需要多久                     |
| 撐多久、撐不久         | 資源以某個速率耗盡                 | time to exhaustion、capacity planning          | 目前用量、成長速率、上限，推算出的耗盡時間點與要提前多久行動                         |

「負載」這個詞本身也要寫出單位：每秒請求數、同時連線數、每秒寫入數、單筆資料量與讀寫比例會讓不同的資源飽和，「負載很高」沒說是哪一種。

**數字的寫法要和「不寫會取代讀者查證的東西」一起看。** 要求寫出負載量與判斷標準，容易被執行成把數字寫進通則句（「單台資料庫撐得住每秒三千筆」），讀者會照抄一個不屬於他系統的值。通則句寫出句子的形狀與去哪裡量；具體數字只留在文章自己的範例情境，並寫出數字來自那個情境的哪一次量測或推算。

## 非負載的用法

- 「靠一條資料契約撐住」：寫出保證什麼不變量、由誰檢查。
- 「spinner 撐不住使用者的耐心」：寫出等待時間與使用者能接受的長度，以及該給的進度回饋。
- 「橋接與適配器撐住過渡期」：寫出相容性要維持多久、維持哪些介面。

## 偵測

預先分類可以用詞形加上同一行是否有負載詞做啟發式分類，再逐行人工改判；「關係」一類常混入設定上的實際附掛（存取政策掛在某個身分上），「扛」「垮」跨類的要看句子。改寫不做全集合一次替換：每一處要寫出那個情境自己的需求、門檻或機制，替換腳本寫不出這些內容。

## 論述基礎與限制
