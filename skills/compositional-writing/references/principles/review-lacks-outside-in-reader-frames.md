# 審查框架缺 outside-in 讀者 frame

> **角色**：本卡是 `compositional-writing` 的支撐型原則、被生成端的讀者定位與情境檢查引用。
>
> **何時讀**：規劃審查 frame 時、或多輪審查判定 clean 但使用者仍指出缺口時。

## 結論

多輪審查的 frame 若全部從「已寫的內容」出發，能保證已寫內容的品質，卻看不見「應該寫但沒寫」的缺口。要補的是從「讀者的完整需求」出發的 frame。

兩類 frame 的盲區正交：

- **Inside-out**（字句層、cadence、fact-check、steelman）：看已寫的字、已寫的結構、已寫的事實、已寫的論述。盲區是缺口——看不到不存在的東西。
- **Outside-in**（讀者是誰、從哪裡來、讀完要做什麼、會搜尋什麼）：從需求反推素材。盲區是細節——看不到已寫內容的字句問題。

完整的審查需要兩者交替，缺任一類都會留下該類專屬的盲區。

## 六個實測出現過的盲點

**一、宣導語氣通過全部輪次**。用教導外行人的姿態對專業讀者說話，字面上每個字都合規，keyword bank 抓不到。審查者與作者共享同一套文體直覺，都覺得「用故事帶入」是好教學，同源盲區讓整批被合理化放行。缺的 frame 是 **reader-persona register 適配**——指定具體讀者角色，問「這個人讀到這段會覺得被低估嗎」。

**二、決策彙報資訊缺失**。審查者檢查了技術正確性與寫作規範，沒有人問「讀者讀完後能不能向決策者說明為什麼要做、要花多久」。技術文章的讀者常見下游任務是提案、估算、選型，缺成本量級與時程估算時，讀者學會了做法卻推不動。

**三、操作步驟停在 WHAT 層**。步驟在邏輯層正確、fact-check 通過，但沒到 HOW WITH WHAT（具體工具與指令），讀者知道該做什麼卻不知道用什麼做。

**四、讀者情境缺入口**。審查在既有結構內找問題，不質疑結構本身的覆蓋範圍。列出目標讀者可能進入的情境（從零開始、接手他人環境、救火後正規化、被要求稽核），檢查每個情境有沒有對應的入口。

**五、搜尋落點粒度不足**。讀者會搜尋的具體問題被埋在綜述的某個段落裡，落不到一篇聚焦的內容上。

**六、術語的常識假設未經檢驗**。作者與同源審查者共享的「常識」對讀者群裡最不熟悉的那端並非常識。

## 判讀徵兆

- 全部輪次判定 clean，但使用者一讀就指出成批的問題。
- 審查報告的 finding 全部落在字句與結構層，沒有任何一項是「這裡該有但沒有」。
- 規劃 frame 時，每個 frame 的描述都以「檢查文章的某某」開頭，沒有一個以「假裝讀者做某某」開頭。
