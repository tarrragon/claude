# 「問題」與「回答」當框架詞：一個詞蓋住問句、故障、議題與需求，以及系統被寫成應答的一方

> **角色**：本卡是 `compositional-writing` 的支撐型原則（principle），被 SKILL.md〈每一句先填槽位再成句〉與字句層 keyword bank 的「問題與回答當框架詞」類別引用。
>
> **何時讀**：文章用「X 回答的問題是」「這是 Y 的問題」組織內容，讀者分不出那個「問題」是問句、故障、要處理的事項還是需求時；或者審查時看到監控、檢查、元件被寫成在回答問題時。

中文的「問題」一個詞對應英文的好幾個詞：question（等著被回答的問句）、problem（壞掉的元件或行為）、issue（要處理的事項）、topic（談論的主題），寫成「要解決的問題」時又常常指 requirement（需求）。英文的作者寫的當下就要選一個，讀者因此知道是哪一種。中文同樣分得開——問句、故障、錯誤、事項、主題、需求都是現成的詞——只要寫的人把它寫出來。

AI 生成的技術文章特別常用「問題」配「回答」組織內容：「X 回答的問題是：……」「這一層問的是……」。這個框架把系統元件寫成回答問題的一方，在文章與一個假想的提問者之間造出一段應答，讀起來像在解釋，而讀者每遇到一次「問題」都要自己決定它是哪一種。

## 失效的形態

一篇服務端監控的教材以「每一層監控回答一個問題」組織全篇，「問題」出現 51 次、「回答」21 次，同一個詞至少承擔了四種所指：

- **檢查的內容**：「自檢回答的問題是：這個程序自己還能不能回應」——健康檢查驗證的條件（what the check verifies）。
- **故障**：「服務正常運作時仍會出的問題」——業務結果出錯、憑證到期這類失效（problem）。
- **歸屬的範圍**：「檢查要探到多深（……）是端點的設計問題」——這件事屬於端點設計的範圍（topic / concern）。
- **分類的依據**：「這一層與下一節應用層訊號的分界是問題」——兩層各自檢查的對象不同。

自創術語「問題盲區」建在這個框架上，同時帶著兩種讀法：觀察者沒有在問的問句，還是觀察者看不到的故障。英文譯者必須在 question blind spot 與 problem blind spot 之間選一個。

## 框架詞落在槽位以外

四槽位（動作者、動詞、受詞、結果）要求每一格填領域裡實際存在的實體。「自檢回答的問題是……」的動詞是「回答」、受詞是「問題」——健康檢查在領域裡做的是定期執行一條指令、依結果把容器標成 `healthy` 或 `unhealthy`，沒有回答任何提問。兩格填的都是框架的譬喻。改寫時換回領域裡的動作與對象：

> 自檢確認程序在自己的容器裡能回應：Docker 的 `HEALTHCHECK` 每隔一段時間在容器裡執行一條指令……

其餘所指各自寫成它是什麼：故障寫出哪個元件、什麼行為、什麼條件下；歸屬寫出屬於哪個範圍；需求寫出誰需要什麼、為什麼（技術文件裡 request 另有固定所指 HTTP 請求，需求寫「需求」）；內容本身是一句問句時，寫出問句並標成問句（引號、問號，或「是否」），見 [正反問句當名詞](a-not-a-question-as-noun-clause.md)。

## 判斷問句

**把這個「問題」翻成英文，要從 question、problem、issue、topic、requirement 裡選哪一個。** 選得出來，就用那個意思的中文詞重寫，並寫出內容（哪裡壞了、處理什麼、屬於哪個範圍、誰需要什麼）；同一篇裡每一處選出的詞不一樣，代表一個詞承擔了多個所指；選不出來，代表那句話沒有決定它在講什麼。

**把「回答」換成這個元件實際做的動作**：執行、量測、比對、送出、標記。換不出來時，那一句描述的是框架，不是元件的行為。

合規的情形：場景裡有人實際提問（使用者問、審查者問），業界固定的術語（「N+1 問題」「拜占庭將軍問題」），以及動詞片語「出問題」（泛指發生故障，判讀同 [泛用詞](avoid-overused-generic-words.md)，密集重複時才換成具體的詞）。

## 為什麼讀起來像解釋

應答框架的作用是製造期待：先擺出一個問句，讀者預期下一句是答案。這是口頭講解的技巧，[寫給帶問題來的讀者](write-for-readers-not-audiences.md) 把它歸在服務聽眾的演講姿態，[教學不是教室講課](teaching-is-not-lecturing.md) 的「判定標準包裝成自問自答」是同一個裝置。作者與同源審查者知道每一處「問題」指什麼，看不見這一類。

## 偵測

```bash
rg -n '回答的問題|回答的是|問的是|問題是：' <檔案或目錄>
```

一次全內容集合的量測：「回答的問題」100 處、分佈在 74 個檔案，「問的是」133 處、84 個檔案，最集中的一篇有 11 處「回答的問題」。單獨的「問題」詞頻太高，不適合直接掃；從框架詞找到集中的文章之後，在那一篇裡逐處翻譯。

這張卡的初稿自己也用了十幾處泛稱的「問題」（「這個框架本身另有問題」「骨架本身沒有問題」），用本卡的判斷問句掃過之後才改成缺陷、缺口、問句。

## 同一類的其他詞：足夠性斷言裡的「撐」與評價謂語

「問題」佔著一個內容格，而沒有把內容填進去：讀者讀到它，要自己決定那是問句、故障、事項還是需求。同一類的詞還有兩種，修法相同——寫出它佔住的那個內容，換成同義詞不算修好：

- **足夠性斷言裡的「撐」**（撐得住、撐不起、扛不住、撐不久、會垮）：佔著需求與判斷標準的位置。「這個證據撐不住」沒說要支持哪個主張、需要什麼樣的證據；「單台資料庫撐得住這個流量」沒說是在什麼延遲門檻、多少請求量之下。改寫寫出需求、判斷標準與機制；換成「足以支持」仍然沒寫。借用物理直覺是偵測的入口，修法要回到它省略了什麼，見 [word-choice-fits-concept-attributes](word-choice-fits-concept-attributes.md) 的〈足夠性斷言要寫出需求、判斷標準與機制〉。
- **正反問句裡的評價謂語**（「對不對」「通不通」）：佔著判斷標準的位置，見 [a-not-a-question-as-noun-clause](a-not-a-question-as-noun-clause.md)。

三者的判斷問句是同一個：**這個詞佔住的位置，原本應該寫的是什麼；那個內容寫在句子裡了嗎。** LLM 生成時三者都高頻，因為它們讓句子在內容還沒決定時就能寫完。

## 論述基礎與限制

證據是一篇文章的四種所指歸類（只舉例不逐一計數）、框架詞的詞頻，以及一位讀者的指認。「AI 生成的文章特別常用」沒有和人寫的文章對照過；詞頻只說明這個框架常見，不說明每一處都違規。
