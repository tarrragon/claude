# 讀者重建不了的斷言清單、展開成讀者位置的走查

> **角色**：本卡是 `compositional-writing` 的支撐型原則（principle）、被 SKILL.md 原則三（意圖顯性與層級貼合）+ 多輪審查的斷言支撐檢查引用。
>
> **何時讀**：寫作或審查時撞到條列式斷言（「拆開來看有三個毛病：1、2、3」）、或收到「這段說明不清楚、讀者可能無法理解」的 finding、要決定怎麼改寫時。

---

## 論述基礎與限制

本卡從一個段落的兩版改寫抽出：第一版列出一則註解的三個毛病（「入口」是自創行話、「由誰設定」搜尋一下就有、「用途」重複型別名稱）、而正文只給了那一行註解本身——讀者無從驗證程式裡有沒有「入口」這個識別符。三條結論都對、但讀者只能硬記或盲信。改寫成讀者位置的走查後、由提出問題的使用者判定「說得清楚非常多」並要求固化成模式。

限制兩項：**單一案例**（一個段落、一次改寫）、修法的普遍有效性是機制推導；**有效性由提需求者判定**、沒有第三方讀者的理解測試。

---

## 核心原則

**條列式斷言是作者走完推導後只輸出結論。** 每一條背後都有作者做過的動作（搜過識別符、對照過宣告）、但清單只留下動作的結果。判定用**重建測試**：讀者只憑文中已給的材料、能不能自己得出這一條。能、清單是合格的壓縮；不能、讀者拿到的是要求信任的裁決、說明的功能沒有發生。

重建測試同時暴露第二個問題：**斷言清單會把「缺材料」藏住。** 支撐結論的證據（實際的程式碼、輸出、對照）根本不在文中時、清單的形式讓缺席看起來不缺——因為結論已經寫在那裡了。

---

## 修法：讀者位置的走查

三步：

1. **把讀者放到使用產物的位置。** 不是「這則註解有三個毛病」、是「跳到這行、想從註解拿到資訊的讀者、逐字檢查它給了什麼」。位置決定判定標準——資訊拿不拿得到、不是作者覺得好不好。
2. **每條斷言換成動作加材料。** 動作是讀者可以自己做的（搜某個詞、對照某段宣告）、材料是文中直接給的（實際的程式碼、輸出）、結論由對照自己浮現。並排「合格的寫法會長怎樣」與「現況長怎樣」是最強的對照形式。
3. **可重用的檢查方式放在走完之後。** 判斷標準在走查結束時出現、是讀者已經能自己說出的東西；放在清單前面就是又一條要硬記的規則。

走查的副產物是**逼出缺的材料**：第二步做不下去的地方、就是文中該補而沒補的程式碼與對照——正是斷言清單藏住的缺口。

### 對照範例

改寫前（斷言清單）：

```text
拆開來看有三個毛病：
1. 「入口」是自創行話，程式裡沒有這個識別符。
2. 「由誰設定」grep 一下就有。
3. 「用途」只是把型別名稱再唸一次。
```

改寫後（走查、節錄第一條）：

```text
「由進入該模式的入口設定」——「入口」指什麼？在程式裡搜「入口」、搜
entry，找不到任何識別符。實際的進入點是兩個按鈕的 handler：〔程式碼〕
對照這段程式碼就看得出落差：註解若寫「由 enterBatchMode 的呼叫端設定」，
讀者搜這個識別符、一次就落在這兩行；寫「入口」，這個詞只存在於註解裡。
```

第一條裡的問句是操作型自問——讀者要執行的動作、答案由緊接的材料交付、跟懸念型問句（答案被扣住）不同類。

## 審查掛載

斷言支撐類檢查對每個結論式條列跑重建測試。曝光候選的 grep：

```bash
rg "拆開來看|[一二三四五六]個毛病|有[一二三四五六]個問題"
```

命中是候選不是判決、判定靠重建測試。兩類合規要放行：**每條自帶證據**的清單（引用的材料就在文中）；**摘要位置**的清單（前文已推導過、條列是回收不是灌輸）。規格與參考型內容（參數表、設定項清單）是查閱對象不是論證、不適用。

對應的 blog report 卡 slug 是 `assertion-list-needs-reader-walkthrough`。
