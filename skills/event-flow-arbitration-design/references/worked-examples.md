# 事件流仲裁設計套用範例

> 何時讀：需要參考已套用過的案例，理解方法論判準如何落地到具體系統時。本檔兩部分：三個場景，每則分三段——**套用結果**（判準直接套得上的部分）、**易誤套形態**（套用時最常走偏的判斷，各附走偏的後果）、**方法論對應判準**（該形態由哪一條判準管、在哪一節）；以及末節三個不繫於特定場景的常見誤解。

## 場景 (a)：HTTP API 共用資料庫連線池，另有排程對帳與 webhook 消費

一組 HTTP API 服務共用一個資料庫連線池；另有排程執行的對帳任務，與接收外部通知的 webhook 消費者，三者都會向這個池借連線。

### 套用結果

連線池是通道，資料庫是持有層的真持有者，仲裁器掛在「取用連線」這個動作之前。三種到達路徑分屬不同到達類別：HTTP 請求屬等待型（呼叫端在等回應）；排程對帳屬自發型（開始的決定點在排程本身）；webhook 逐跳分類——送達跳等待型（外部發送方在等 2xx 或非 2xx 的回應）、確認收訖後的處理跳自發型。佔用量以「已借出連線數＋等待者數＋最老等待者年齡」實例化，進入卸載與離開卸載用不同閾值。全表掃描與主鍵查詢的成本差數個數量級，依成本分池後才讓佔用量指標對兩者都有意義。

### 易誤套形態

1. **把 webhook 整條歸為推送型**。發送方會在收到非 2xx 時重送，送達跳因此有一個正在等回覆的發起者；整條歸推送型會放棄「回 503 讓對方重試」這個唯一的推回手段。
2. **把窗口驅動的排程當成狀態驅動處理**。對帳的本輪範圍是固定窗口，「逾期跳過不補跑」會直接遺漏當日窗口，不是單純的延後。
3. **把每個行程的連線池各自當成通道分片**。三種路徑各為獨立行程、各持一池時，真正的持有者是背後同一個資料庫；分片後排程閒置時它的配額不會流回 HTTP 那一分片，而各分片的佔用量都不反映資料庫的餘裕。
4. **讓同一請求對同一通道要第二份**。某個 handler 在同一交易中先借一條連線、中途又借第二條時，三參數模型把它計為兩個獨立的 in-flight 請求，實際上是「持有並等待」，是連線池死鎖四條件之一。

### 方法論對應判準

1. 〈到達類別〉逐跳分類規則：等待 ack 的 webhook 在送達跳屬等待型（非 2xx 即為推回），確認收訖之後的處理跳屬自發型。
2. 〈Deadline 傳播〉自發型細分：狀態驅動的工作逾期直接跳過，窗口驅動的工作逾期須留痕，留痕由下一次排程消費（窗口併入下一輪）。
3. 〈通道與仲裁器〉分片前提：分片對象須為真持有者；多個連線池背後是同一資料庫時，真持有者是資料庫，仲裁器應落在真持有者處，或明示協調配額是刻意新增的單點與其代價。
4. 〈通道與仲裁器〉一次申請原則：同一請求對同一通道的多次佔用必須在首次進入時一次申請完畢，禁止持有並等待。

## 場景 (b)：多 isolate 應用程式，worker isolate 執行耗時解析、主 isolate 處理互動與提示

worker isolate 負責耗時的資料解析，主 isolate 負責處理使用者互動與畫面提示；兩者透過訊息互通。

### 套用結果

三個通道各自一個仲裁器：主 isolate 事件迴圈、worker isolate、畫面提示載體。worker 回傳結果與主 isolate 派工，在接收方依「有沒有人在等回覆」分類——request/reply 形態屬等待型，fire-and-forget 形態屬推送型。解析進度提示屬自發型且可棄（重算即得），使用者觸發的對話框屬等待型且不可棄；兩者的讓步順序依〈讓步與卸載順序〉的三條規則裁決。

### 易誤套形態

1. **對讀不到佇列深度的通道套用完整的佔用量定義**。主 isolate 的事件迴圈不暴露佇列長度，能觀察到的只有 frame 逾時與迴圈 lag 這類等待時間訊號；把它們當成佔用量的替代物會誤以為能反推有多少請求在等。
2. **把事件迴圈當成可搶佔的通道**。isolate 內正在跑的計算無法從外部中斷，唯一手段是終止該 isolate；終止等於放棄目前進度、需要重算。這與 worker pool 不同——後者排隊中的工作可回收，前者已排入的連回收都做不到。
3. **把記憶體當成一般通道套用消費形態**。記憶體的釋放是垃圾回收，不落在方法論定義的三種消費形態（完成、撤回、逾期）內；且跨 isolate 傳遞時資料會被複製，佔用量在傳遞瞬間翻倍。**此項是方法論的已知缺口**，尚未修入本文；套用本場景時須明確標示，不可預設方法論已覆蓋。

### 方法論對應判準

1. 〈競爭與佔用量〉代理量規則：通道不暴露佇列深度時，以最老未消費請求年齡的代理量（事件迴圈 lag、frame 逾時）作輸入，並標明它是佔用量的年齡項而非佔用量的替代物。
2. 〈讓步與卸載順序〉通道表的**單一執行緒事件迴圈**列：該通道無法搶佔，已排入的 task 不可撤回，只能在入口不再排入。worker isolate 屬同表的 **worker pool** 列，排隊中的工作可回收、執行中的依有無中斷點；無中斷點時搶佔退化為終止並重算，重算成本計入該工作的級別判定。兩列是不同的通道，套用時不可互換。
3. 記憶體通道的消費形態與跨 isolate 複製造成的佔用量翻倍，其實例化條件的生效 trigger 是第一份宣告記憶體為稀缺通道的規格；在該 trigger 觸發前，方法論對記憶體通道不提供判準。

## 場景 (c)：訊息消費者，付款完成事件與心跳混流

同一個訊息消費者拉取同一個 partition 的事件，其中包含付款完成通知與服務心跳兩種事件。

### 套用結果

拉取式消費在「是否拉取」這個決策點屬自發型（開始的決定點在我方程式碼），拉進來的批次是接收緩衝。付款完成事件依丟棄後果屬不可棄，須落持久佇列；心跳事件屬可棄，且是最新值語意（只關心最新一則）。持久佇列即該通道的 broker，記憶體中的批次即 prefetch 視窗，不可棄事件的 ack 只能在處理完成後發出。

### 易誤套形態

1. **在有序通道上直接套用「高級別可搶佔低級別」**。同一 partition 上事件依 FIFO 順序消費並依序 ack，付款事件無法插隊到心跳事件之前——已拉取的批次之外，順序早已由 partition 固定，搶佔在該範圍不可能成立。
2. **把最新值語意的事件當成一般可棄事件整批丟棄**。心跳全部丟棄會讓下游的存活偵測誤判服務已離線；可棄的定義是「重算即得」，最新值語意事件的最新一則不可與其餘同等處置。
3. **把「停止拉取」誤判為消費者程式的缺陷**。prefetch 視窗被不可棄事件填滿、且下游處理速度跟不上時，消費者唯一能做的動作就是停止拉取，那是容量問題的正確表現而非 bug。

### 方法論對應判準

1. 〈讓步與卸載順序〉有序通道的搶佔實例化條件：有序消費的通道上，級別搶佔只在同一次拉取的批次內成立；跨批次的搶佔須改為依級別分流至不同通道（分池的一種）。
2. 〈讓步與卸載順序〉九格表推送型 × 可棄格：緩衝滿時先合併再丟棄，丟最舊；最新值語意的事件保留最新一則並加計數，不整批丟棄。
3. 〈讓步與卸載順序〉九格表推送型 × 不可棄格：不可棄事件不得只存在於記憶體緩衝，必須落持久佇列；仲裁器對它只能延後消費，延後至接收視窗（prefetch 視窗）填滿，即為容量失敗訊號，交由容量維度處理。

## 套用時的三個常見誤解

- **系統已有延遲型准入控制時不必換掉它**：CoDel、adaptive concurrency limit 這類依延遲調整的演算法看似與「卸載判準是佔用量、不是到達率」相悖，實際上 CoDel 的 sojourn time 即最老未消費請求年齡、adaptive concurrency limit 的准入決策仍在比較 in-flight 數，兩者的判準變數本就含在佔用量的組成內。**做法**：把該演算法既有的量測值填進步驟 3 佔用量與卸載閾值表的「佔用量單位」欄與「佔用量讀取方式」欄，閾值欄填「由該演算法推導」，不另建一套量測。
- **以為分級延遲統計會破壞仲裁器的常數時間要求**：兩者可同時成立，條件見方法論〈跨執行緒與 isolate〉與〈可觀測性〉——本檔不重述條件清單，套用時直接讀那兩節。
- **以為指標集只要涵蓋佔用量與卸載計數就夠**：高負載除錯還要能回答「這個通道有沒有在推進」與「誰把通道佔滿」，兩者對應的指標在方法論〈可觀測性〉最小指標集表內，勾選時不可跳過。
