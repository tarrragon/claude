# 事件流仲裁設計產出物範本

> 何時讀：執行〈執行流程〉需要填產出物，要現成表格骨架時。欄位名與事件流負載仲裁方法論條文一致；填表時不必重述判準本身，只填實例化後的值。

## 步驟 1 產出物：通道清單表

| 通道名稱 | 真持有者 | 持有層 | 仲裁器落點 | 仲裁器所在執行緒／isolate | 是否分片 | 分片依據（若分片） | 靜態配額代價（若分片） |
|---------|---------|-------|-----------|------------------------|:-------:|------------------|----------------------|
| （範例）DB 連線池 | 資料庫實例 | 資料存取基礎層 | 連線 proxy | 與連線池同一行程 | 是 | 依資料庫實例分片 | 分片閒置時配額不流回其他分片 |

**填表提醒**：「真持有者」欄若填入某個 domain 或某個行程，先回頭確認它是否只是眾多借用者之一；分片時若下游仍飽和，真持有者判斷有誤，須重填。

## 步驟 2 產出物：到達類別與級別標定表

| 事件流 / 觸發路徑 | 逐跳到達類別 | 級別 | 級別標定依據（脈絡） | 傳播規則（若有子呼叫） |
|------------------|-------------|------|-------------------|----------------------|
| （範例）webhook 送達 | 送達跳：等待型 | 不可棄 | 丟棄後我方與來源的狀態不可回復地不一致，且我方已回 2xx 構成對外義務 | — |
| （範例）webhook 確認收訖後處理 | 處理跳：自發型 | 不可棄（繼承） | 繼承自送達跳 | 子呼叫不得高於此級別 |

**填表提醒**：同一事件流若跨多跳，每跳各填一列；「以預設標定」的情形須額外標註（見步驟 6 的可觀測事件）。「級別標定依據」欄要寫**接收方丟棄後承擔什麼後果**，不寫產生方認為它多重要——後者是〈級別〉明文排除的視角，填錯會讓「很嚴重但接收方無事可做」的事件搶到高級別。

## 步驟 3 產出物：佔用量與卸載閾值表

佔用量是三個量，不是一個；每個通道一列，三項各填自己的兩個閾值，任一項越過即進入卸載。

| 通道 | 項目（in-flight 數／佇列深度／最老年齡） | 是否分池（最貴請求是否吃掉餘裕） | 進入閾值 | 離開閾值 | 讀取方式（直讀／代理量／量不到） | 若登記待量測：已嘗試什麼、誰負責消掉（要件見方法論〈登記類條款的消費要件〉） |
|------|--------------------------------|:------------------:|:-------:|:-------:|--------------------------|----------------------------------|
| （範例）DB 連線池 | in-flight 數 | 是（全表掃描單次可吃掉半數連線） | 已借出 80%（上限 20 條的比例，餘裕 4 條可容納同期抵達量） | 已借出 60% | 直讀 | 不適用 |
| （範例）DB 連線池 | 等待者數 | 同上 | 4（等於餘裕條數） | 1 | 直讀 | 不適用 |
| （範例）DB 連線池 | 最老等待者年齡 | 同上 | 量測所得：等待時間由平緩轉陡處 | 該值的一半 | 直讀 | 不適用（已量測） |

**填表提醒**：兩個閾值欄各自要寫出**這個數字怎麼來**，不接受裸數字——範例列示範的是量測形態。取值程序（進入閾值取等待時間由平緩轉陡處、兩閾值差距下界為單一請求完成造成的佔用量變化、容量上限未知時改由等待時間訊號推導）見方法論〈競爭與佔用量〉；量不到轉折點時填任一值並在欄內標「待量測」，不留白。讀不到佇列深度的通道，「佔用量讀取方式」欄填代理量的具體訊號（如 frame 逾時、事件迴圈 lag）。

## 步驟 4 產出物：九格卸載順序表

到達類別 × 級別，列序即卸載順序。動作集：接受、延後、拒絕、丟棄、合併、降級。

| | 可棄 | 須留痕 | 不可棄 |
|---|------|--------|--------|
| **自發型** | （填動作與參數，預設：跳過，不補跑） | （填動作，預設：延後至離開卸載狀態；逾期則跳過並留痕） | （填動作，預設：延後不丟；逾期即容量失敗訊號） |
| **等待型** | （填動作，預設：拒絕＋可重試資訊） | （填動作，預設：拒絕＋可重試資訊＋留痕） | 不由仲裁器卸載；無法服務即觸發容量 tripwire |
| **推送型** | （填動作，預設：緩衝滿時先合併再丟棄，丟最舊；最新值語意事件保留最新一則加計數） | （填動作，預設：緩衝滿時先寫留痕再丟棄） | 不得只存在於記憶體緩衝，須落持久佇列；延後至接收視窗填滿即為容量失敗訊號 |

**填表提醒**：六個非「不可棄」格照抄預設動作與逐格評估後採用預設，產物同形——每格除動作外須填至少一個系統特定參數（緩衝上限、重試次數與退避、留痕載體），無參數可填者於格內寫「本系統無此參數」。三個「不可棄」格已由方法論給定固定處置（見表格內文字），填表時只需確認本系統是否有例外，不重新推導；其餘六格依系統實況填具體動作與參數（緩衝上限、重試次數等）。

## 步驟 5 產出物：Deadline 來源表

| 到達類別 | Deadline 來源 | 逾期動作 | 若自發型：狀態驅動或窗口驅動 |
|---------|--------------|---------|---------------------------|
| 等待型 | 發起者持有，隨請求攜帶剩餘預算 | 回報逾期，不再佔用通道 | 不適用 |

每一列另填「本列的 deadline 是攜帶還是指派」；指派者附指派值的來源。此欄與步驟 6 的計數項對應，缺它時追溯只知有幾筆指派、不知是哪幾筆。
| 自發型 | 下一次排程時刻 | 可棄跳過不補跑；須留痕跳過並留痕；不可棄不得逾期 | （填：狀態驅動 / 窗口驅動） |
| 推送型 | 事件自身的價值衰減期 | 可棄丟棄；須留痕先留痕；不可棄不逾期 | 不適用 |

**填表提醒**：窗口驅動的自發型工作逾期須留痕，留痕由下一次排程消費；狀態驅動的可直接跳過。

## 步驟 6 產出物：可觀測事件欄位範本

每一次請求離開通道都要發出事件，攜帶以下欄位（不變式，欄位集合的權威是方法論〈可觀測性〉，本表為其鏡射）：

| 欄位 | 說明 |
|------|------|
| 請求識別 | 可追溯到具體請求的識別碼 |
| 到達類別 | 等待型 / 自發型 / 推送型 |
| 級別 | 不可棄 / 須留痕 / 可棄 |
| 通道 | 該決策發生的通道名稱（對應步驟 1 通道清單表） |
| 離開方式 | 仲裁決策六種（接受 / 延後 / 拒絕 / 丟棄 / 合併 / 降級），或三種非決策出口（出隊時判定逾期 / 推回 / 被搶佔而終止） |
| 佔用量快照 | 決策當下的佔用量數值 |
| deadline 剩餘 | 決策當下距 deadline 的剩餘時間 |

**最小指標集勾選**（依方法論〈可觀測性〉最小指標集表逐項確認是否已建立）：

- [ ] 佔用量，每通道，按（到達類別 × 級別）分解
- [ ] 完成計數，每級別
- [ ] 卸載計數，每（到達類別 × 級別）
- [ ] 分級延遲 p50 / p99，每級別，拆排隊等待與服務時間
- [ ] 最老未消費請求年齡
- [ ] 仲裁器佇列深度
- [ ] 降級狀態與進出時刻
- [ ] 以預設標定級別與指派 deadline 的計數

**填表提醒**：告警規則綁狀態變遷與增量（進入／離開卸載、卸載計數增量、最老請求年齡跨閾值），不綁「佔用量高」這種在高負載時恆真的訊號。

## 產出物落地：這些表填完之後放哪裡

各步的產出物不是獨立文件，它們各有既定的落點；填完而不落地等於沒填。

| 產出物 | 落點 | 落地形態 |
|--------|------|---------|
| 通道清單表、協調圖 | domain map 的通道與協調圖節（範本見 `doc` skill 的 `domain-map-template.md`） | 逐列填入，仲裁器落點欄不得填任何 domain 名稱 |
| 到達類別與級別標定表 | 一律填進 domain map 通道與協調圖節的「到達類別與級別實例」子表（規格驗證的機械檢核以該子表為對照）；專案另有 event catalog 時同步填進 catalog 的到達類別欄與級別欄，兩者以子表為準 | 每條事件流的每一跳各一列 |
| 佔用量與卸載閾值表、九格卸載順序表、Deadline 來源表 | 技術決策記錄的通道與卸載順序節（`saas-tech-selection` 的決策記錄範本已有該節位） | 九格全填，三個「不可棄」格只確認有無例外 |
| 可觀測事件欄位範本、最小指標集勾選 | 可觀測性的決策記錄段 | 欄位定義進實作、指標集勾選項逐項對應到已建立的指標 |

**落點不存在時**：上表的落點取自 SaaS 與伺服器端專案的既有產物。專案沒有 event catalog、沒有技術決策記錄、或沒有 domain map 時，落點改為該產出物所描述對象的規格文件，並在該文件建一節承接；**不可因為沒有現成落點就把表留在本 skill 的工作區**——沒有落點的產出物在下一個人接手時等於不存在。

**容量失敗訊號的交接**：九格表出現「不可棄請求無法服務」時，接收端是容量維度的 tripwire 表；沒有該維度的專案，接收端是負責容量決策的人或該系統的容量記錄，不可無收方。要交出的是三件事——是哪一個通道、佔用量在該時刻的分解（按到達類別 × 級別）、以及該通道的擴充選項（分池、擴容、或分片後的真持有者是誰）。只交「某某爆了」的訊號，接手的人得從頭重做前三步。

**六份表填完之後**：依方法論〈測試義務〉為七項驗證目標各建對應測試，該節逐項標明是否需要外部替身；產出物本身不驗證任何東西，驗證由那些測試承擔。

**旁路確認**（步驟 6 之前先填，缺項會使後面幾張表產出執行不了的設計；等級與缺席處置的判準見方法論〈旁路的存在與可靠性〉）：

| 旁路 | 存在嗎 | 可靠性等級 | 與被保護的通道共用底層資源嗎 | 缺席時的處置 |
|------|:-----:|-----------|:--------------------------:|------------|
| 留痕的載體 | | 允許有損 | | 降級為同進程計數 |
| 不可棄推送型的持久佇列 | | 必須無損 | | 無持久儲存時該格的級別標定就是錯的 |
| 容量失敗訊號的接收端 | | 有人或有一張會被讀的表 | | 指名一個人；指不出來就承認該通道無容量升級路徑 |

**方法論已知缺口的標示**：套用時若碰到方法論明載未覆蓋的通道形態（例：記憶體通道的消費形態），在落地文件中獨立列出「本設計涉及而方法論未提供判準的項目」，逐項寫出該項目、方法論缺口所在、本系統暫採的處置。沒有這一節時，「不涉及該形態」與「涉及但靜默略過」的設計文件同形。
