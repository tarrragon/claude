# 移版硬耦合盤點 SOP

> **什麼時候讀本檔**：決定把某個提案移到別的版本時。觸發點通常是 SKILL.md Step 1 的跨提案依賴檢查輸出 `[WARNING]`，但**任何理由的移版都適用**——移版的風險來自提案在本版留下的契約級殘留，與移版的動機無關。
>
> 本檔是 SKILL.md〈全程〉步驟表的分支，不是其中一步。跑完本檔回到你原本的那一步繼續。

提案因跨提案依賴矛盾（Step 1 檢查結果）或其他理由決定移版時，禁止整包提案原封不動搬到新版本——必須先盤點該提案在**本版**留下的 schema / DDL / 契約級殘留耦合，比照下方動機案例「契約先定形、業務邏輯後移版」的模式先行定形，斬斷後才能讓移出的主體與留在本版的部分變成獨立軌道。

**動機**：曾有版本規劃雙提案，其中一提案因依賴另一個排在更晚版本的提案而整體移版，但其變更清單第一項會動到契約 SOT 檔案（如 schema 定義）並牽動資料庫 DDL——若放任不管、等本版 DDL 凍結後才在移版目標版本定形該欄位，會重演過往「先上線、後補契約定義」造成的多階段漂移。提前在 DDL 凍結前定形該欄位形狀，才讓兩個提案真正解耦。

**盤點步驟**：

| 步驟 | 動作 | 產出 |
|------|------|------|
| 1. 契約掃描 | 對照移版提案的 checklist，逐項檢查是否觸及契約檔案（界定見下方〈契約檔案的界定〉），含資料庫 DDL、schema 定義檔等 | 觸及項清單 |
| 2. 契約鎖定點確認 | 找出本版中「契約形狀一旦被寫入就難改」的時刻，兩類都要查：(a) 明訂的凍結點（「DDL 凍結」「schema 定案」類，通常在儲存層實作票之前）；(b) 本版已存在、會讀寫步驟 1 觸及項的票。**兩類都查無，步驟 3-4 仍一律執行**——鎖定點不因未明訂而消失，尚未建立的實作票同樣會消費該契約；本步驟只決定定形票的排序約束，不決定是否盤點 | 明訂凍結點（或「無」）+ 已存在的消費票清單（或「尚無」） |
| 3. 硬耦合分級 | 觸及項逐一判斷：純程式邏輯（無耦合，可整包移版）vs 契約形狀（硬耦合，需本版先定形） | 硬耦合項清單 |
| 4. 定形票建立 | 對每個硬耦合項建立獨立 IMP ticket（比照上方動機案例的定形票模式），範圍限定「只定形契約形狀，不含業務邏輯實作」。定形票排入本版**最早可排**的 Wave；步驟 2 列出的消費票 `blockedBy` 定形票；有明訂凍結點者，定形票須在該點之前完成。尚未建立的消費票不另設期限，由 Wave 順序保證 | 定形 ticket（本版最早可排 Wave）+ 消費票 blockedBy 回填 |
| 5. 教學比對 | 確認 CLAUDE.md 是否含「教學模組對應表」章節（判準同 SKILL.md Step 3）。有此表 → 定形前讀 blog 對應模組確認欄位設計是否已有教學定義，有則優先採用，無則先在 blog 補完並登記 `docs/sync-pending.md`（`teaching-sync` skill 維護的 SOT）；無此表（專案未採用教學對應慣例）→ 本步驟合法跳過 | Solution 段落記錄教學比對結論，或標註「教學比對 skipped：無教學模組對應表」 |
| 6. Ticket 交叉標記 | 定形票 `why` 欄位引用移版提案 ID + 目標版本；移版提案的 `checklist` 對應項標記 `verified_by` 指向定形票 | 雙向可追溯 |

**契約檔案的界定（步驟 1 盤點範圍與步驟 3 分級共用）**

定義句：契約檔案，指形狀（欄位、型別、值域、key 或路徑的集合）存在鎖定點的檔案——本版一旦以該形狀發布或凍結，日後再改形狀，就必須連帶修改同一次提交改不到的東西。檔案類型不決定歸屬：同一類檔案（如路由表、多語系 key 清單）在不同專案可以落在任一側，一律依下列三問判定。

判準句（三問任一為「是」即屬契約檔案）：

| 判準 | 問句 |
|---|---|
| 判準 1：持久資料 | 本版發布後，是否會以該形狀寫入並保存資料（資料庫列、使用者端檔案、快取、佇列中的訊息），使日後改形狀必須遷移或相容讀取？ |
| 判準 2：邊界外消費方 | 是否有消費方位於另一個獨立發布或部署的單位——其他服務、其他儲存庫、外部使用者或協作方（第三方整合、以 key 對接的翻譯提供者），使改形狀無法在同一次提交內一併修改？判定單位是發布或部署單位，不是儲存庫。 |
| 判準 3：明訂凍結 | 本版文件是否已對該形狀明訂凍結點（「DDL 凍結」「schema 定案」「對外公開」類針對該形狀的宣告）？ |

**列舉與後段子句的關係**：判準 1、判準 2 問句的括號列舉（使用者端檔案、以 key 對接的翻譯提供者等）是後段子句（「使日後改形狀必須遷移或相容讀取」「使改形狀無法在同一次提交內一併修改」）的典型例證，不是與後段子句並列的第二層獨立要件。命中列舉任一項即判該問為「是」，不需要為當下情境重新驗證後段子句是否成立；未命中列舉、但情境本身符合後段子句描述者，仍判為「是」。

三問皆否：屬純程式邏輯，即使被多個模組引用（同一次提交可以一併修改）也不列入步驟 1。

常見契約檔案（非封閉列舉）：資料庫 DDL、訊息或事件 schema、持久化檔案格式、對外 API 的路徑與回應形狀、跨程序讀取的設定格式。

**判斷準則（步驟 3 分級）**：

觸及項是否硬耦合，看兩件事：(1) 該檔案經〈契約檔案的界定〉三問判為契約檔案，且 (2) 本次變更改動其形狀。兩者皆是即為硬耦合。

| 觸及類型 | 是否硬耦合 | 處理方式 |
|---------|-----------|---------|
| 修改 schema 定義檔、DDL 或其他經三問判定的契約檔案之形狀 | 是 | 建定形票，本版執行 |
| 純業務邏輯（middleware、演算法、UI） | 否 | 整包隨提案移版 |
| 僅讀取既有契約、不新增欄位 | 否 | 整包隨提案移版 |

**範例（三段鏈式：【輸入】【產出】【驗證】，格式見 `.claude/skills/skill-design-guide/references/chained-examples.md`）**

範例一（正例，判準 1 命中）：

【輸入】

```
移版提案 checklist 摘要：
  變更項 A：資料庫的訂單資料表新增一個必填欄位「折扣類型」，未填寫時預設為「無」
  變更項 B：調整內部某函式的參數順序，不涉及任何儲存或跨部署介面
```

【產出】

```
形態：決策表

觸及項判定表
觸及項    | 判準1 持久資料                                       | 判準2 邊界外消費方                           | 判準3 明訂凍結         | 契約檔案？
變更項 A  | 是——欄位寫入訂單資料表並持久保存，改回舊形狀需回填或遷移既有列 | 否——單一儲存庫內同次提交可一併修改           | 未知——本版未明訂凍結點 | 是（三問任一為是）
變更項 B  | 否——參數不落地保存                                   | 否——單一儲存庫內同次提交可一併修改           | 否                     | 否（三問皆否）
```

【驗證】

```
檢驗問句
  Q 變更項 A 判為契約檔案的依據，能否指回〈契約檔案的界定〉判準句？
    預期：能——「判準 1：持久資料」問句「本版發布後，是否會以該形狀寫入並保存資料
    （資料庫列……），使日後改形狀必須遷移或相容讀取？」，變更項 A 的欄位即寫入
    訂單資料表列，符合此問句
  Q 變更項 A 是否需要三問全部為是才判定契約檔案？
    預期：否——定義句「三問任一為『是』即屬契約檔案」，變更項 A 僅判準 1 為是已足夠
  Q 變更項 B 判為非契約檔案，是否因為它不屬於任何檔案類型清單？
    預期：否——定義句「檔案類型不決定歸屬」，變更項 B 的判定依據是三問皆否，不是
    查表所屬類型
```

範例二（前提相反對照，判準 2 命中：同一儲存庫、各自部署的兩個服務）：

【輸入】

```
移版提案 checklist 摘要：
  變更項 C：調整一則內部訊息的欄位形狀，此訊息由服務甲產生、服務乙消費；服務甲與
  服務乙的原始碼位於同一個程式碼儲存庫，但各自獨立建置、獨立部署、各有各的發布排程
```

【產出】

```
形態：決策表

觸及項判定表
觸及項    | 判準1 持久資料           | 判準2 邊界外消費方                                                             | 判準3 明訂凍結 | 契約檔案？
變更項 C  | 否——訊息為傳遞中內容，未落地保存 | 是——服務乙是另一個獨立部署單位，服務甲若改動訊息形狀，服務乙的部署版本不會隨這次提交同步更新 | 未知           | 是（三問任一為是）
```

【驗證】

```
檢驗問句
  Q 變更項 C 與服務甲同屬一個程式碼儲存庫，是否因此排除判準 2？
    預期：否——判準 2 問句明訂「判定單位是發布或部署單位，不是儲存庫」，變更項 C
    的服務甲與服務乙雖同一儲存庫，但各自獨立部署，判定單位落在部署單位而非儲存庫
  Q 若服務甲與服務乙改為同一次提交、同一次部署發布，判準 2 是否仍為是？
    預期：否——判準 2 的成立條件是「消費方位於另一個獨立發布或部署的單位……使改
    形狀無法在同一次提交內一併修改」；服務甲乙若合併為同一次提交部署，即可在同一次
    提交內一併修改，不再符合判準 2 的問句
  Q 變更項 C 判為契約檔案，是否代表這一類訊息永遠屬契約檔案？
    預期：否——定義句「同一類檔案（如路由表、多語系 key 清單）在不同專案可以落在
    任一側，一律依下列三問判定」，訊息是否屬契約檔案取決於三問結果，非其檔案類型
```
