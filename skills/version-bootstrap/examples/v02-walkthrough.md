# 版本規劃波 Walkthrough — 假想範例

依 `/version-bootstrap` 現行九步順序，走一次完整規劃波。範例情境為假想版本（不對應任何實際專案的版本歷史），情境中的提案、domain、檔案路徑皆為技術中立的示意內容，不預設任何建構畫面的技術。

多數步驟只做流程重述；六個步驟（Step 2 兩處、Step 4.5、Step 5、Step 6 兩處）附三段鏈式範例（【輸入】【產出】【驗證】），用於校準文字約束允許分歧的判斷點。三段格式與判準見 `.claude/skills/skill-design-guide/references/chained-examples.md`。

---

## 前置條件

- `todolist.yaml` 已有本版定義與提案清單
- 提案 A、B、C 狀態皆為 confirmed

## Step 2：建 Spec 骨架（含 UI 前置檢查）

```bash
doc batch-init --proposals A,B,C --domain 示例網域
```

PM 逐一填寫三份 spec 的 FR。填寫過程中依 Step 2〈UI 類提案元件庫前置檢查〉逐一判別提案是否涉及 UI。

### 範例一：UI 類提案判別（呈現通道，不以字面關鍵字判定）

【輸入】

```
提案 A FR：「使用者送出表單後，顯示確認彈窗，含摘要文字與『確定/取消』兩個按鈕」
提案 B FR：「背景排程於終端輸出純文字進度百分比，無版面配置、無互動」

判準依據句（SKILL.md Step 2）：
「依 FR 產物在哪裡被使用者看到或操作來判定，不以字面關鍵字為準」，
呈現通道分三類，見 SKILL.md Step 2〈UI 類判別〉呈現通道表
```

【產出】

```
形態：決策表

FR                           | 呈現通道                                                    | 判定                     | 動作
------------------------------|---------------------------------------------------------------|--------------------------|----------------------------------------------
提案 A：確認彈窗               | 圖形介面：由本應用程式渲染的疊層（彈窗）                        | UI 類                    | 過三項前置檢查
提案 B：終端輸出進度百分比     | 非圖形的人讀呈現：終端文字輸出                                  | 非 UI 類，不過三項前置    | 記錄該提案的呈現通道，交 foundation-design UI 維度判改寫產物
```

【驗證】

```
檢驗問句
  Q 提案 A（確認彈窗）屬哪一類呈現通道？
    預期：圖形介面——由本應用程式渲染的視窗、頁面、彈窗、疊層、應用內提示，含唯讀畫面；判 UI 類，過三項前置檢查
  Q 提案 B（終端輸出進度百分比）屬哪一類呈現通道？
    預期：非圖形的人讀呈現——終端文字輸出與終端互動、匯出文件版面、由作業系統或宿主程式渲染的通知；判非 UI 類，不過三項前置，且 Checkpoint 須記錄該提案的呈現通道，交 foundation-design UI 維度判改寫產物，不得只記「非 UI 類」
  Q 兩者的判定依據是什麼？
    預期：依 FR 產物在哪裡被使用者看到或操作來判定，不以字面關鍵字為準（見上方【輸入】判準依據句，逐字出自 SKILL.md Step 2〈UI 類判別〉）
```

### 範例二：三項前置檢查的「存在」判準（檔案存在不等於內容齊備）

【輸入】

```
提案 A（前例已判為 UI 類）進入三項前置檢查，專案現況：
  - design token 層：已有樣式檔，僅定義顏色與字體兩類參數，未定義間距與圓角
  - L3 元件庫章節：spec 文件已有章節標題「元件庫」，內容只有一句「待補」，
    無元件清單、無原生元件禁用對照表、無豁免清單
  - design-system spec 文件：不存在

判準依據句（SKILL.md Step 2 三項前置檢查表「對應載體」欄）：
  design token 層 = 「顏色/間距/字體/圓角/陰影參數集中管理」的樣式檔
  L3 元件庫章節 = 「元件清單 + 原生元件禁用對照表 + 豁免清單」
```

【產出】

```
形態：決策表

檢查項          | 現況                          | 對照「對應載體」欄定義  | 判定
----------------|-------------------------------|--------------------------|----------------
design token 層 | 樣式檔存在，但缺間距與圓角參數 | 定義要求五類參數集中管理 | 未齊備，須先補齊
L3 元件庫章節   | 章節標題存在，內容為「待補」   | 定義要求三個具體子項齊全 | 未齊備，須先補齊
design-system spec | 不存在                     | 定義要求獨立 spec 文件   | 未齊備，須先建立
```

【驗證】

```
檢驗問句
  Q 「design token 層」檔案存在，是否等同通過本項檢查？
    預期：否——判準依「對應載體」欄的內容定義（五類參數集中管理），
    現況只覆蓋兩類，不齊備；檔案存在不等於內容齊備
  Q 「L3 元件庫章節」標題存在，是否等同通過本項檢查？
    預期：否——「對應載體」欄定義為三個具體子項（元件清單／禁用對照表／豁免清單）
    的組合，僅有標題不含任一子項，判未齊備
  Q 三項是否皆須先補齊才可繼續提案 A 的 UI 實作票規劃？
    預期：是（依 SKILL.md Step 2「缺則先補齊才可繼續本提案的 UI 實作票規劃」）
```

**Checkpoint 通過**：三份 spec FR 填寫完成；提案 A 已補齊三項前置（design token 層補間距與圓角、L3 元件庫章節補三子項、新建 design-system spec）；提案 B、C 非 UI 類，略過本項。

## Step 2.6：資料契約產出

**Checkpoint 通過**：資料契約文件已產出且 `doc query` 查詢成功；第三軸必要欄位皆已填齊。

## Step 5：紅燈測試設計

對三份 spec 派發紅燈測試設計（5a 外圈、5b 內圈）。測試設計消費 Step 2.5 domain map 的兩軸：層軸（依 bundle 分層決定測試層）與不變式軸。

### 範例四：兩軸測試交集去重（同一斷言不重複建置）

【輸入】

```
domain map 的「Bundle 不變式清單」列出一項不變式：
  「某比率分母為 0 時，計算結果定義為 0（非拋出例外）」
同一 bundle 亦有一則 UC 場景：「使用者查看含零筆記錄的統計頁」，
其 Then 句已斷言「顯示的比率為 0，畫面不顯示錯誤」——與上述不變式
為同一計算邏輯與同一輸出值。

判準依據句（SKILL.md Step 5「不變式軸」）：
「與 UC 場景測試並存去重——UC 場景測試涵蓋垂直使用者行為，
不變式測試涵蓋水平 domain 規則，兩軸交集去重、聯集為完整覆蓋」
```

【產出】

```
形態：決策表

覆蓋來源                                | 是否需要獨立測試
------------------------------------------|--------------------
UC 場景測試（已斷言比率為 0）              | 保留（既有）
不變式測試（同一計算邏輯與輸出值）          | 不需另建——與 UC 場景測試落在交集，依「交集去重」不重複建立
domain map 另列、無任何 UC 場景涉及的其他不變式 | 需建立獨立不變式測試——落在「聯集」中未被涵蓋的部分
```

【驗證】

```
檢驗問句
  Q 「分母為 0」不變式與上述 UC 場景測試是否驗證同一計算邏輯與同一輸出值？
    預期：是——兩者皆斷言「比率為 0、不拋出錯誤」
  Q 兩者同時各建一份測試是否違反「交集去重」？
    預期：是——同一斷言重複建置屬交集內的重複，應去重，僅保留一份
  Q domain map 中未被任何 UC 場景涉及的其他不變式，是否可以略過不建測試？
    預期：否——「聯集為完整覆蓋」要求交集以外的不變式仍須各自建立測試，
    不因為「已有部分不變式被涵蓋」而整體略過
```

**Checkpoint 通過**：三份 spec 的 Phase 2 完成；FR↔AC 覆蓋矩陣無空行；資料契約第三軸每條契約條目已補 `tests` 或 `no_test_needed`＋`reason`。

## Step 6：匯總建票

依 Step 2-5 產出建立 W2/W3/W4 ticket。

### 範例五：GREEN 票粒度（「spec FR 或功能模組」不是任意選擇）

【輸入】

```
提案 C 的 spec 有 FR-01（查詢條件輸入）、FR-02（查詢結果清單顯示）、
FR-03（結果匯出成檔案）。FR-01 與 FR-02 的 where.files 皆含查詢狀態檔與
查詢頁面檔；FR-03 的 where.files 為匯出服務檔，與前兩者無交集。

判準依據句：
  SKILL.md Step 6：「每個 spec FR 或功能模組 1 張」
  pm-rules/task-splitting.md〈拆分後檢查清單〉B：「共用檔案的問題已合併到同一 ticket」
  rules/core/cognitive-load.md〈速查三閾值〉：「功能職責數 | > 2 須拆分」
```

【產出】

```
形態：決策表

分組方案                | where.files 交集                              | 判定
--------------------------|-------------------------------------------------|--------------------------------
FR-01 + FR-02 合併 1 張   | 交集非空（查詢狀態檔、查詢頁面檔）            | 依 checklist B 合併；合併後
                          |                                                  | 職責數 2 未超閾值，不拆
FR-03 獨立 1 張           | 與前兩者無交集（匯出服務檔）                  | 檔案無交集——依「spec FR」
                          |                                                  | 粒度獨立成票
```

【驗證】

```
檢驗問句
  Q FR-01、FR-02 是否應合併為 1 張？
    預期：是——where.files 交集非空，依「共用檔案的問題已合併到同一 ticket」合併；
    合併後功能職責數 2 未超過「> 2 須拆分」門檻，不再拆
  Q FR-03 是否應併入前兩者同一張票？
    預期：否——FR-03 的 where.files 與前兩者無交集，依「spec FR」粒度獨立成票
  Q 「每個 spec FR 或功能模組 1 張」的「或」依什麼取捨？
    預期：檔案有交集者合併（依據：「共用檔案的問題已合併到同一 ticket」），
    合併後職責數 > 2 者再拆（依據：「功能職責數 | > 2 須拆分」）
  Q 兩個 FR 共用同一狀態但 where.files 無交集時是否合併？
    預期：否，改依序列派發解決——「不以依賴為由合併」（task-splitting.md 策略 7）
```

### 範例六：並行安全（共用檔案的唯一負責票）

【輸入】

```
提案 A、B、C 的實作票皆須註冊各自的元件到同一份集中匯出檔
（元件庫的 barrel 匯出入口，Step 4.5 第 4 塊的產出）。

判準依據句（SKILL.md Step 6 PM 工作句）：
  「確認 Wave 分配、並行安全（共用檔案需整合票）」
```

【產出】

```
形態：決策表

票           | 是否可直接修改共用匯出檔 | 理由
--------------|----------------------------|--------------------------------------------
提案 A 實作票 | 否                         | 共用檔案，並行安全要求變更集中於單一票
提案 B 實作票 | 否                         | 同上
提案 C 實作票 | 否                         | 同上
整合票（新建）| 是——唯一負責              | 「共用檔案需整合票」：若各票仍可自行修改，
              |                            | 整合票即失去存在意義，並行衝突無從避免
```

【驗證】

```
檢驗問句
  Q 提案 A／B／C 的實作票是否可各自直接修改共用匯出檔？
    預期：否——「並行安全（共用檔案需整合票）」的前提是變更集中於單一票，
    各票各自修改會使並行安全的目的落空
  Q 整合票是否為共用匯出檔變更的唯一負責票？
    預期：是——依上一問的推論，若非唯一負責，整合票本身即無存在必要
```

**Checkpoint 通過**：所有 ticket 建立完成（提案 A/C 各自的功能模組票、FR-03 獨立票、整合票）；Wave 分配確認。

## 教訓

1. Step 2.5／2.6／4.5 不是可跳過的可選步驟——省略後果見 `references/step-rationale.md`。
2. Step 5 的兩軸測試設計需同時查 UC 場景與 domain map 的不變式清單，兩者交集去重、聯集完整覆蓋，見上方範例四。
3. Step 6 的建票粒度與並行安全都不是字面上的單一固定答案——粒度依認知負擔拆分閾值判斷，並行安全的共用檔案由單一整合票負責，其餘票不得直接修改。
