# 導航模式：畫面之間怎麼跳、back 回到哪

本 reference 為「設計或審查畫面間導航」情境。

適用：選擇 app 的導航架構（堆疊 / tab / drawer）；決定單次導航用 go 還是 push；使用者按 back 的行為不符預期（直接離開 app、回到不該回的畫面）；deep link 設計；跨平台 app 的導航慣例取捨。
不適用：單一畫面內部的狀態轉換（狀態矩陣範疇）；導航後畫面的載入回饋（互動回饋範疇）。

> **自包含聲明**：閱讀本文件不需要先讀其他 reference。

---

## 核心概念

導航設計的核心提問是使用者的心理模型：**使用者按 back 時，期望回到哪裡？** 每種導航模式和每個導航操作都對應一種期望；實作選擇偏離期望時，使用者會迷路（回到不該回的畫面）或意外離開 app（堆疊已空）。

## 導航模式分類

| 模式               | 心理模型               | 適用                                            | 限制                                 |
| ------------------ | ---------------------- | ----------------------------------------------- | ------------------------------------ |
| Push/pop stack     | 深入 → 返回的線性路徑  | 層級式資訊（列表 → 詳細 → 編輯）、步驟式流程    | 只有深度一條軸、無法橫向切換平行功能 |
| Declarative router | URL 表示畫面狀態       | 需要 deep link、URL 驅動、複雜條件式導航        | 需要集中管理路由定義                 |
| Tab bar            | 平行功能橫向切換       | 3-5 個平行主功能、切換頻繁；每個 tab 是獨立堆疊 | 超過 5 個 tab 過度擁擠               |
| Drawer             | 隱藏的選單、打開才看到 | 頂層功能超過 5 個、切換頻率低、放帳號設定       | 可見性低 — 核心功能不該藏在 drawer   |

多數 app 組合使用：tab bar 做頂層橫向、每個 tab 內部 push/pop 縱向深入、drawer 放次要功能。組合時 back 行為要一致 — 在 tab 內第三層按 back 回第二層（堆疊行為）、而非切到上一個 tab。

## go vs push vs pushReplacement 語意

以三種堆疊操作語意為例（下表附常見框架對應僅供查閱，決策依語意欄，不依框架名稱）：

| 語意操作     | 堆疊行為     | 按 back 回到   | 使用者意圖                 | 常見框架對應（僅供查閱） |
| ------------ | ------------ | -------------- | -------------------------- | ------------------------ |
| 替換整個堆疊 | 替換整個堆疊 | 無（離開 app） | 切換到另一個工作區         | 如 Flutter GoRouter 的 `go` |
| 推入堆疊頂端 | 推入堆疊頂端 | 前一個畫面     | 暫時離開，做完回來         | 如 Flutter GoRouter 的 `push` |
| 替換堆疊頂端 | 替換堆疊頂端 | 更早的畫面     | 流程中的下一步（不可回退） | 如 Flutter GoRouter 的 `pushReplacement` |

**替換整個堆疊 — 切換工作區**：登入成功後到首頁、登出後到登入畫面、onboarding 完成到主畫面 — 共通點是使用者不應該按 back 回到之前的畫面。

**推入堆疊頂端 — 暫時離開做完回來**：列表到詳細頁、首頁到設定頁、主畫面到一次性配對流程。最常用 — 多數導航都是這個模式。

**替換堆疊頂端 — 流程中前進**：步驟式流程（步驟 1 → 2 → 3，在步驟 3 按 back 回到流程開始前、不回步驟 2）、結果頁替換條件頁。語意是「這一步完成後使用者不需要回到這裡」。

**決策方法**：對每個導航操作問「使用者按 back 期望回哪裡」— 回前一個畫面 → 推入堆疊頂端；離開 app 或回根畫面 → 替換整個堆疊；跳過當前畫面回更早 → 替換堆疊頂端。這個決策在 UX 設計階段做、記錄在畫面狀態矩陣的退出路徑欄，實作時對照選擇。本節三種操作皆定義在單一堆疊內；tab 之間的切換不屬其中任何一種，因每個 tab 維護獨立堆疊（見上方〈導航模式分類〉「每個 tab 是獨立堆疊」）。

### 三段鏈式範例：tab 結構下的決策交界

情境：tab 結構的 app，每個 tab 各自維護獨立堆疊；使用者從「首頁」tab 切到「設定」畫面。驗證段的判定屬「設計產出物」（判定規則：產出物能在執行期被啟動、看得到它運作的屬執行期行為，驗證段寫 Given/When/Then；契約表、判定結果這類靜態文件屬設計產出物，驗證段寫檢驗問句加預期答案）。

```

【產出】

```
形態：決策表
判斷依據                                         | 結果

                                                    堆疊內推入新畫面）

是否為「切換工作區」（不應該按 back 回到之前畫面） | 否（tab 切換保留各自堆疊狀態，非放棄
                                                    首頁這個工作區；但這不代表使用者按

結論                                             | 屬 tab 切換操作，不套用「替換整個堆疊」／

```

Q 使用者在「設定」tab 內按 back，是否會離開 app？

```

## 常見誤用

情境：三個獨立的誤用情境，各自示範選錯堆疊操作的後果。驗證段的判定屬「執行期行為」（產出物是導航後的實際 back 行為）。

【輸入】

```
SPEC 片段（三個獨立情境）：
  情境一：使用者在「首頁」畫面點擊「配對」入口，配對是一次性任務，完成後應能回首頁
  情境二：使用者完成登入後畫面切換到首頁，已登入不應再看到登入頁
  情境三：使用者送出不可逆的申請資料後，畫面切換到「申請完成」頁
```

【產出】

```
形態：決策表
情境   | 誤用選擇     | 正確選擇     | 理由
情境一 | 替換整個堆疊 | 推入堆疊頂端 | 配對是「暫時去做一件事」，非切換工作區
情境二 | 推入堆疊頂端 | 替換整個堆疊 | 已登入使用者不該再看到登入頁
情境三 | 推入堆疊頂端 | 替換堆疊頂端 | 已提交的表單頁沒有回頭意義
```

【驗證】

```
Given 情境一使用者在配對完成畫面按 back
When  切換方式已改為推入堆疊頂端
Then  使用者回到首頁，而非離開 app

Given 情境二使用者在首頁按 back
When  切換方式已改為替換整個堆疊
Then  按 back 離開 app（無法回到登入畫面）

Given 情境三使用者在「申請完成」頁按 back
When  切換方式已改為替換堆疊頂端
Then  使用者回到申請流程之前的畫面，略過已提交的表單頁
```

## iOS HIG vs Material Design 慣例差異

跨平台 app 需要決定遵循哪套慣例。主要差異：

| 面向  | iOS                                           | Android / Material                                       |
| ----- | --------------------------------------------- | -------------------------------------------------------- |
| Back  | 無系統 back 鍵；導航列左上按鈕 + 左緣右滑手勢 | 系統 back 鍵（可被 app 覆寫：離開確認、放棄編輯確認）    |
| Tab   | 固定底部、永遠可見                            | 底部為主、另支援 app bar 下方的 top tabs（同類內容視角） |
| Modal | 底部滑上的 sheet、下滑 dismiss                | bottom sheet 與 dialog 為主、full-screen dialog 左上關閉 |

選擇策略：

| 策略                 | 適合                      | 代價                   |
| -------------------- | ------------------------- | ---------------------- |
| 統一用 Material      | Android 為主、快速開發    | iOS 體驗不原生         |
| 統一用 iOS HIG       | iOS 為主                  | Android 體驗不原生     |
| 各平台各自慣例       | 重視兩平台原生體驗        | 開發測試成本翻倍       |
| 共用核心、差異點適配 | 多數跨平台 app 的實際選擇 | 需判斷哪些差異值得適配 |

「共用核心、差異點適配」的常見切法：底部 tab bar、push/pop 導航兩平台一致；back 手勢（iOS edge swipe + Android 系統鍵都要支援）、modal 呈現按平台適配。適配與否的判斷問句：這項差異是否改變使用者操作平台系統機制（系統返回鍵、系統手勢、modal dismiss 手勢）得到的結果？是→系統行為類差異，必適配——違反會直接打破使用者的肌肉記憶；否→其餘差異（轉場動畫、圖示風格、未涉系統機制的導航元件樣式）一律歸視覺風格類，可不適配，適配成本高於體驗增益時保持統一。未列舉的元件或手勢逐一套用此問句，不沿用其他元件的結論。

### 三段鏈式範例：判斷系統行為類差異 vs 視覺風格類差異

情境：判斷 app bar 下方的 top tabs 樣式屬於哪一類差異，決定是否需要為 iOS 另外適配。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：一個跨平台 app 在某個頁面使用 app bar 下方的 top tabs（同類內容切換視角，
如「熱門」「最新」兩個分頁）
```

【產出】

```
形態：決策表
判斷依據                                             | 結果
top tabs 是否為系統慣用的導航結構（使用者的 back 手勢、
系統鍵預期會如何作用於它）                           | 否（top tabs 本身不改變系統 back 行為，
                                                        back 仍走該畫面的堆疊或 tab 切換邏輯）
top tabs 的視覺樣式是否為兩平台差異的來源             | 是（iOS 較少見此樣式、Android 較常見）
結論                                                 | 屬視覺風格類差異，可不適配（兩平台皆可使用
                                                        同一套 top tabs 視覺樣式，不需要為 iOS
                                                        另外設計替代結構）
```

【驗證】

```
檢驗問句
Q top tabs 是否屬於「系統行為類差異」而必須適配？
  預期：否——top tabs 不改變系統返回鍵或系統手勢的結果，依判斷問句歸視覺風格類

Q 若之後要新增「側滑切換 tab」手勢，判斷是否適配的依據會改變嗎？
  預期：不改變判斷標準本身——仍問「該手勢是否為使用者對該平台既有系統行為的預期」，
  只是套用到新元件時要重新跑一次同一個判斷，而非套用上一個元件的結論
```

## Deep link

Deep link 讓外部來源（網頁連結、推播、其他 app）直接導航到特定畫面。三個設計問題：

**機制選擇**：

- Custom URL scheme（`myapp://`）：無 ownership 驗證（任何 app 可註冊同 scheme）、只在已安裝時有效、不適合 web 分享。
- Universal Link（iOS）/ App Link（Android）：標準 HTTPS URL + domain ownership 驗證（`.well-known` 檔案），未安裝時 fallback 到網頁 — 對外分享場景的正解。
- Deferred deep link：點擊時未安裝 → 引導安裝 → 首次開啟導航到目標。需要第三方服務或自建參數傳遞。

**URL 結構**：和 router 的路由定義一致（URL path 即 route path）、query parameters 傳畫面資料。參數避免敏感資訊 — URL 會被系統日誌、分析工具、中間節點記錄。

頁面資訊不一定在 path — hash-based SPA 的路由在 fragment（`/#/library`）、pathname 永遠是 `/`，只讀 pathname 的辨識邏輯會把所有頁面靜默塌縮成根路徑。自家 app 用哪套慣例由 router 決定；讀取別人的 URL 時（browser extension 讀宿主頁面、工具讀目標站），對方的路由形態是輸入規格 — 辨識邏輯要涵蓋 path-based 與 hash-based 兩套，取完整路由用 pathname + hash 組合（組合前確認 fragment 承載的是路由還是頁內錨點 — path-based 站的 `#section` 是錨點、不是頁面）。

**堆疊重建**：從 deep link 直接進入內頁時堆疊裡沒有首頁，按 back 回首頁還是離開 app？目標畫面是日常使用的一部分 → 重建完整堆疊（back 回到 app 正常入口）；一次性操作（掃碼 → 顯示結果 → 離開）→ 只放目標畫面。「日常使用的一部分」的判斷標準：目標畫面在 app 內是否有既有入口可重複到達（清單頁、分頁、選單）。有 → 重建到該入口的堆疊；沒有（只能經外部來源單次到達，如掃碼結果）→ 只放目標畫面。進入方式（推播、deep link）不影響判定。

### 三段鏈式範例：判斷「日常使用的一部分」

情境：一則推播通知直接開啟訂單詳情頁，判斷是否需要重建包含清單頁的完整堆疊。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：使用者點擊推播通知，直接開啟一則訂單的詳情頁；該 app 平時也支援使用者
從「我的訂單」清單頁進入同一個訂單詳情頁
```

【產出】

```
形態：決策表
判斷依據                                           | 結果
訂單詳情頁在 app 內是否有既有入口可重複到達         | 是（「我的訂單」清單頁本來就能進入
                                                      同一個訂單詳情頁，非僅為了這次推播才存在）
結論                                               | 重建包含「我的訂單」清單頁的完整堆疊，
                                                      使用者在詳情頁按 back 能回到清單頁，
                                                      而非直接離開 app
```

【驗證】

```
檢驗問句
Q 判斷是否重建堆疊的依據，是「這次是不是從推播進來的」還是「目標畫面在 app 內是否
  有既有入口可重複到達」？
  預期：是後者——本情境雖由推播觸發，但訂單詳情頁本來就有「我的訂單」清單頁這個既有
  入口，屬於「日常使用的一部分」，不因為這次的進入方式是推播就改判一次性操作

Q 若這則推播改為「掃描到的一次性 QR code 結果頁」，結論是否相同？
  預期：否——QR code 結果頁在 app 內沒有既有入口（只能經掃碼單次到達），屬一次性操作，
  應只放目標畫面，不重建清單頁堆疊
```

**測試項目**：每個路由的 deep link 能打開、參數正確傳遞、app 在前景 / 背景 / 未啟動三種狀態都能處理、無效 URL 有 fallback（導首頁或錯誤頁）、domain verification 正確。

## 檢查清單

- [ ] 每個導航操作對照過「按 back 期望回哪裡」選擇替換整個堆疊 / 推入堆疊頂端 / 替換堆疊頂端？
- [ ] 登入 / 登出 / onboarding 完成用替換整個堆疊（清堆疊），暫時性任務用推入堆疊頂端？
- [ ] Tab 數量 ≤ 5、核心功能不藏在 drawer？
- [ ] 組合導航下 back 行為一致（tab 內 back 走堆疊、不切 tab）？
- [ ] 跨平台策略明確（統一 / 各自 / 核心共用），back 手勢兩平台都支援？
- [ ] 對外分享的 deep link 用有 ownership 驗證的機制？
- [ ] Deep link 的堆疊重建策略明確、無效 URL 有 fallback？
- [ ] Deep link 在 app 前景 / 背景 / 未啟動三態都測過？
- [ ] 依 URL 辨識頁面的邏輯涵蓋 hash-based SPA（不只讀 pathname）？
