# 畫面狀態矩陣：狀態 × 操作 × 退出的完整性檢查

本 reference 為「設計或審查多狀態畫面」情境的入口檔。因補齊範例後超出體量門檻，〈選取類前置呈現〉已獨立拆至同組的 `screen-state-matrix-selection-prestate.md`（逐檔互指）。

適用：設計連線 / 配對 / 同步這類多狀態流程的畫面；審查既有畫面的導航缺口；使用者反映「進了某個畫面出不去」；從 BDD 操作盤點展開 UI 設計；檢查路由定義與 UI 入口的一致性；使用者需先從一組候選中做選擇的前置狀態判定，見 `screen-state-matrix-selection-prestate.md`。
不適用：單一狀態的靜態頁面（沒有狀態轉換就不需要矩陣）；按鈕內部的 loading 狀態設計（屬互動回饋範疇）。

> **自包含聲明**：閱讀本檔不需要先讀其他 reference；`screen-state-matrix-selection-prestate.md` 判定時引用本檔〈四欄定義〉，兩檔已互相具名指路。

---

## 核心概念

畫面狀態矩陣是一張表格：每行代表一個畫面的一個狀態，每列描述該狀態的四個面向 — 顯示了什麼、使用者能做什麼、什麼條件進入、怎麼離開。目的是在實作前暴露導航缺口：**退出路徑欄位為空 = UX 死胡同**，使用者一旦進入就無法靠自己的操作離開，只能殺掉 app 或等系統逾時。

矩陣同時是可測試的設計產物 — 每一行可以直接轉成一條 UI test case（進入該狀態、驗證顯示與操作、執行退出路徑、斷言導航結果）。

## 四欄定義

| 欄       | 內容                                                       | 常見遺漏                                    |
| -------- | ---------------------------------------------------------- | ------------------------------------------- |
| 顯示     | 使用者看到的畫面元素：進度指示、錯誤訊息、表單、列表       | 少遺漏 — 規格通常都寫顯示                   |
| 可用操作 | 使用者在這個狀態下能執行的動作：按鈕、手勢、鍵盤輸入       | 常遺漏 — 規格寫「看到什麼」不寫「能做什麼」 |
| 進入條件 | 什麼事件讓畫面進入這個狀態：使用者操作、系統事件、外部事件 | 偶爾遺漏隱式轉換（自動觸發、timeout）       |
| 退出路徑 | 使用者如何離開：返回、導航他處、取消、完成後自動轉場（自動轉場不滿足下方〈檢查清單〉「至少一條使用者可自行觸發的退出路徑」要求，仍須視情況另補使用者可觸發的退出路徑；例外條件見〈退出路徑的例外邊界〉）。每條退出路徑須同時寫出觸發事件與離開後的目標狀態（或目標畫面），格式為「{觸發事件} → {目標狀態}」，缺任一段視為該條未定義。 | 最常遺漏 — 設計注意力集中在「進來之後」     |

「顯示」和「可用操作」的區別在互動性：顯示一顆重試按鈕是「顯示」、按下重試按鈕觸發重連是「可用操作」。

## 填寫範例

以一個遠端終端機 app 的連線畫面為例。驗證段的判定屬「設計產出物」（判定規則：產出物能在執行期被啟動、看得到它運作的屬執行期行為，驗證段寫 Given/When/Then；契約表、判定結果這類靜態文件屬設計產出物，驗證段寫檢驗問句加預期答案）。

【輸入】

```
SPEC 片段（視覺行為描述，非現成 enum）：
  使用者從首頁點入本畫面，畫面依序出現以下不同樣貌：
  1. 剛進入時是空白畫面（背景已自動開始建立連線）
  2. 接著出現進度指示
  3. 連線成功後畫面換成終端機介面與工具列
  4. 若連線失敗，畫面顯示錯誤訊息與重連按鈕
  5. 連線中途斷開，畫面顯示「連線中斷」與重連按鈕
```

【產出】

```
形態：契約表（步驟 1：從視覺呈現反推狀態，未先假設任何 enum）

五種視覺樣貌各自成一狀態（idle / connecting / connected / error / disconnected），
填出的矩陣（步驟 2：填四欄，先留空退出路徑）：

  狀態         | 顯示                   | 可用操作     | 進入條件      | 退出路徑
  ------------ | ---------------------- | ------------ | ------------- | --------
  idle         | 空白（自動連線）       | 無           | 進入畫面      | 無
  connecting   | 進度指示               | 無           | idle 自動觸發 | 無
  connected    | 終端機 + 工具列        | 打字、特殊鍵 | 連線成功      | 無
  error        | 錯誤訊息 + 重連按鈕    | 重新連線     | 連線失敗      | 無
  disconnected | 「連線中斷」+ 重連按鈕 | 重新連線     | 連線斷開      | 無

步驟 3：檢查退出路徑欄 — 全空，五個死胡同。修復後每個狀態補上至少一條退出路徑：

  狀態         | 顯示                   | 可用操作                     | 進入條件      | 退出路徑
  ------------ | ---------------------- | ---------------------------- | ------------- | ------------------------------
  idle         | 空白（自動連線）       | 取消                         | 進入畫面      | 取消 → 返回首頁
  connecting   | 進度指示               | 取消連線、back               | idle 自動觸發 | 取消連線 → 返回首頁；back → 返回首頁
  connected    | 終端機 + 工具列        | 打字、特殊鍵、中斷連線、back | 連線成功      | 中斷連線 → idle；back → 返回首頁
  error        | 錯誤訊息 + 重連按鈕    | 重新連線、返回、back         | 連線失敗      | 返回 → 返回首頁；back → 返回首頁
  disconnected | 中斷訊息 + 重連按鈕    | 重新連線、返回、back         | 連線斷開      | 返回 → 返回首頁；back → 返回首頁
```

【驗證】

```
檢驗問句
Q 修復前矩陣的退出路徑欄空格數？
  預期：5——五個狀態全部為死胡同

Q 五個狀態是否直接由視覺呈現的差異區分，而非讀取現成的狀態 enum？
  預期：是——五種視覺樣貌（空白、進度指示、終端機+工具列、錯誤訊息+重連、
  中斷訊息+重連）各自成一狀態，對應步驟 1「沒有明確 enum 時從視覺變化反推」

Q 修復後矩陣的每個狀態是否都至少有一條退出路徑？
  預期：是
```

## 填寫步驟

1. **列出畫面的所有狀態**。從狀態管理機制取得（enum、state 變數、reactive data）；沒有明確 enum 時從視覺變化反推 — 每種不同的視覺呈現就是一個狀態。
2. **每個狀態填四欄**。填不出來的欄位先留空 — 留空本身就是發現。
3. **檢查退出路徑欄**。空格 = 死胡同，需要補退出路徑。
4. **檢查可用操作欄**。操作欄為空可能合理（等待中），也可能是缺互動設計 — loading 狀態通常應有「取消」、error 狀態通常應有「重試」和「返回」。

一個 5 狀態的畫面約 10 分鐘填完，能同時暴露全部導航缺口 — 遠低於實機測試才發現的成本。

## 從 BDD 操作盤點展開

BDD 操作盤點（Given / When / Then）聚焦「什麼情境下做什麼得到什麼」，Then 通常描述可觀察結果 — 「畫面顯示 X」比「使用者可以做 Y」更容易寫成斷言，因此盤點系統性偏向描述顯示、遺漏操作與退出。展開步驟：

1. 從盤點列出所有畫面（每個情境至少涉及一個畫面、去重）
2. 每個畫面列出狀態（從 Given / Then 條件抽：「Given 連線已建立」暗示 connected 狀態；同時對照程式碼 enum — 盤點沒提到的狀態同樣需要設計）
3. 每個狀態填「顯示」欄（盤點的強項、直接搬）
4. 每個狀態補「可用操作」和「退出路徑」欄 — 盤點通常不提供，對每個狀態問兩個問題：使用者在這個狀態下想做什麼？怎麼離開？
5. 檢查空白格

## UC 步驟對應檢查

矩陣依畫面清單或 BDD 操作盤點推導時，來源只回答「這個畫面有哪些狀態」，不會反過來檢查「UC 的每一步驟都對應到矩陣的哪一格」。缺這道檢查時，矩陣可能每個畫面都填滿了四欄、看似完整，卻遺漏了某個使用者操作步驟根本沒有對應到任何畫面狀態或可用操作——這類缺口和退出路徑留空一樣，都是實機測試才會暴露的類型，只是藏在「矩陣外面」而非「矩陣格子裡」。UC 主要成功場景裡「使用者從一組候選中做出選擇」這類步驟最常被漏：它本身不產生新畫面內容，容易被略過，但仍需要對應到矩陣裡的一個狀態或一格可用操作（見 `screen-state-matrix-selection-prestate.md`〈選取類前置呈現：獨立成列與判定條件〉）。

**檢查方法**：逐一走過 UC 的主要成功場景（Main Success Scenario）每一步驟，在矩陣中找出對應的一格——可能是某狀態的「進入條件」（該步驟觸發了狀態轉換）、也可能是某狀態的「可用操作」（該步驟是使用者在既有狀態下的操作）。找不到對應格的步驟即為缺口：矩陣漏了一個狀態，或漏了一格可用操作，回頭補上。

**無 UC 文件時的處置**：專案沒有 UC 文件、或該畫面沒有對應的 UC 編號時，本檢查改以〈從 BDD 操作盤點展開〉產出的操作盤點（Given/When/Then）作替代來源，逐一核對盤點中每個情境的 When 步驟是否有矩陣對應格。UC 與 BDD 盤點兩者皆缺時，本檢查無法執行，須在矩陣旁註記「無 UC/BDD 來源，本檢查未執行」，不可留白視為已檢查通過——留白和「檢查過但沒發現問題」在事後審查時無法區分。

## 路由可達性檢查

矩陣管畫面內部，路由可達性管畫面之間：比較 router 定義的所有路由、和使用者從 UI 操作能到達的所有路由，兩個集合的差集就是問題。

- **router 有但 UI 不可達**：路由定義了、畫面實作了，但沒有任何 UI 元素導航過去 — 功能存在但使用者找不到入口。這是「寫了 function 沒人呼叫」的 UX 版死程式碼。
- **UI 指向但 router 沒有**：按鈕導向未定義的路由 — 404 或空白畫面。

檢查方法依規模選擇：路由少（< 10）逐一在 UI 上找到通往該路由的操作路徑；路由多時從操作盤點交叉比對（每個使用者操作的入口畫面是否從首頁可達），或自動化 — 解析 router 定義的路徑集合、grep UI 程式碼中所有導航呼叫的目標路徑、取差集。自動化能抓靜態缺口，動態導航（執行期條件決定目標）仍需人工確認。

交叉比對時注意操作的執行端：只有「使用者在這個 app 端執行」的操作需要 UI 入口，主機端 / 後台操作不需要。

## 無 UI 入口路由表

路由可達性檢查發現「router 有但 UI 不可達」時，先判斷是否為合理排除——該路由只透過 deep link 或其他模組的內部呼叫觸達，本來就不需要 UI 入口。合理排除必須記錄在矩陣外的獨立表格，不可只在下方〈檢查清單〉打勾了事：沒有記錄位置與理由，日後重跑檢查時無法分辨「已確認排除」和「還沒查過」。

表格固定三欄，放在該畫面對應規格文件旁、路由可達性檢查段落附近（不併入畫面狀態矩陣本身 — 矩陣管狀態轉換，不管路由本身是否存在 UI 入口）：

| 路由         | 原因           | 觸發來源                                     |
| ------------ | -------------- | --------------------------------------------- |
| （路由路徑） | deep link／內部 | 誰會呼叫到這條路由：推播通知、外部連結、其他模組的內部呼叫等 |

未列入此表、UI 又不可達的路由一律視為缺口，不得預設排除。

## 容易漏列的狀態：initializing

畫面查詢的對象有自己的生命週期時（browser extension 的 service worker、遠端服務、另一個 process 的常駐程式），畫面開啟瞬間「對方還沒醒、還不知道狀態」是常態 — initializing 是真實狀態，在矩陣裡需要自己的一行：顯示「初始化中」、退出路徑是收到回應轉入正常態、timeout 後才轉入離線或錯誤。判斷標準是畫面開啟當下，查詢對象是否可能處於「存在但尚未能回應」的狀態（剛啟動、休眠後喚醒中、忙於初始化）：可能→補 initializing；查詢對象隨時就緒、等待只來自本次請求的往返→屬一般 loading，不需要 initializing。是否經過網路不影響判定。

把 initializing 與離線合併的畫面，會把「查詢對象這次醒得慢」呈現成「離線」— 頻率低不減輕代價，使用者據此做錯誤決策（放棄、重裝、回報故障）。對策：被查詢方在初始化期間就能回應 baseline 的 initializing 狀態（「我在、還沒準備好」與「沒有回應」是不同資訊）；過渡狀態的顯示必須有資料來源與退出條件，硬編的「檢測中...」永遠不會離開、等於把過渡態寫成死胡同。列狀態時多問一句：畫面開啟當下，查詢對象可能還沒準備好回應嗎？可能就補 initializing。

### 三段鏈式範例：判定「獨立生命週期」

情境：判斷一個查詢對象是否需要獨立的 initializing 狀態，而非直接歸入一般 loading。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：畫面開啟時向一個背景服務查詢目前狀態，該服務在系統啟動後常駐執行，
與畫面的生命週期各自獨立（畫面關閉時服務不會跟著關閉）
```

【產出】

```
形態：決策表
判斷依據                                       | 結果
查詢對象是否有自己的生命週期（不隨畫面開關啟動/結束） | 是（服務為系統層級常駐，畫面只是查詢者之一）
查詢對象是否可能在畫面開啟當下處於「還沒準備好回應」的狀態 | 是（服務剛啟動、或忙於處理其他請求時）
結論                                           | 需要獨立的 initializing 狀態，不可與一般 loading 或離線合併
```

【驗證】

```
檢驗問句
Q 一般的單次 API 請求（發出、等待、回應到達即結束）是否也算「獨立生命週期」？
  預期：否——一般 API 請求的伺服器隨時就緒，等待只來自本次請求往返，依
  〈容易漏列的狀態：initializing〉判斷標準屬一般 loading

Q 判斷依據是不是「這是不是一個遠端請求」？
  預期：否——判斷標準是查詢對象是否有跨越本次互動的獨立生命週期，
  而非請求是否經過網路
```

## 反模式：假設使用者只走 happy path

UI 設計只覆蓋「一切順利」的情境 — 連線成功後打字、配對成功後連線 — 忽略非順利情境的需求：等待中想取消、失敗後想換方向、成功後想離開、中途想做其他事。

隱性假設的形態：「connected 後使用者不會想回首頁」「使用者遇到錯誤會想重試」（沒考慮想放棄）。這些假設在企劃、設計、實作每一層各自累積，最終產出的 app 在正常情境運作良好、任何偏離情境使用者都被困住。

矩陣之上的三條加強檢查：

- **退出路徑欄為空** → 補退出路徑。即使是過渡狀態（connecting）使用者也應該能取消。
- **可用操作欄只有一個選項** → 這條路走不通時使用者被困。至少考慮一條替代路徑（返回 / 取消）。
- **進入條件不可逆** → 使用者無法自行觸發反向操作（「連線成功」的反向「斷開連線」不存在）代表進入後只能等系統狀態變化。反向操作指執行後使本狀態的進入條件不再成立的操作（進入條件「連線成功」的反向操作執行後狀態為未連線）；只離開畫面、不改變狀態本身的導覽返回不算反向操作——它仍滿足退出路徑要求，但不讓進入條件可逆。

### 三段鏈式範例：判定「反向操作」

情境：判斷一個帶「返回上一頁」的已連線畫面，進入條件是否可逆。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：一個已連線狀態的畫面，提供「返回上一頁」與「中斷連線」兩個操作；
進入條件為連線成功（使用者觸發連線後，系統自動判定成功而進入本狀態）
```

【產出】

```
形態：決策表
條件                                              | 判定
本狀態是否有「返回上一頁」操作                     | 是
「返回上一頁」是否為「連線成功」這個進入條件的語意反向動作 | 否（只離開畫面，狀態本身未改變回未連線）
本狀態是否有「中斷連線」操作                       | 是
「中斷連線」是否為「連線成功」的語意反向動作         | 是（執行後狀態轉為未連線，與進入條件相反）
結論                                              | 進入條件可逆——但可逆性由「中斷連線」提供，非「返回上一頁」
```

【驗證】

```
檢驗問句
Q 判定可逆與否，是否只看畫面上是否存在導覽用的返回操作？
  預期：否——導覽返回不改變狀態本身，依〈反模式〉反向操作定義，只有使進入條件
  不再成立的操作才算

Q 若本狀態只有「返回上一頁」而無「中斷連線」，結論是否仍判可逆？
  預期：否——進入條件判為不可逆，須依本節加強檢查補一條使用者可觸發的反向操作
```

## 退出路徑的例外邊界

退出路徑是預設要求。可豁免的唯一情況：該狀態持續時間極短（< 1 秒）且有保證的自動轉場 — 即使如此仍建議保留取消，因為「極短」是正常情況的預期、異常情況（斷網、服務當機）會讓這個狀態停留很久。iOS HIG 和 Material Design 對 modal 畫面都要求 dismiss 機制，退出路徑欄是這個要求的普遍化檢查。

## 檢查清單

- [ ] 每個畫面的每個狀態都在矩陣裡有一行？
- [ ] 查詢對象在畫面開啟當下可能尚未能回應時，initializing 是獨立狀態（與離線 / 錯誤分開、有 timeout 退出）？
- [ ] 每個狀態至少一條使用者可自行觸發的退出路徑？
- [ ] 過渡狀態（loading / connecting）提供取消？
- [ ] error 類狀態同時有「重試」和「返回」？
- [ ] 可用操作欄只有一個選項的狀態，確認過那條路走不通時的後果？
- [ ] router 定義的每條路由都有 UI 入口，無 UI 入口者已列入〈無 UI 入口路由表〉並標明原因與觸發來源？
- [ ] UI 的每個導航目標都在 router 有定義？
- [ ] 矩陣已轉成（或規劃轉成）UI test case？
- [ ] UC 主要成功場景每一步驟都能對應到矩陣中的某狀態或某可用操作？無 UC 文件時已改用 BDD 操作盤點作替代來源，兩者皆缺時已註記「本檢查未執行」？
- [ ] 選取類前置呈現（未選定／未選取，判定條件見 `screen-state-matrix-selection-prestate.md`）已依三項判定條件確認是否須獨立成列，且已補齊四欄（尤其退出路徑）？
- [ ] 跨畫面共用的選取值已列出設定入口與清除時機（見 `screen-state-matrix-selection-prestate.md`〈跨畫面共用的選取值〉）？
