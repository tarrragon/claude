# 錯誤恢復：訊息、重試與降級

本 reference 為「設計或審查錯誤發生後的使用者路徑」情境。

適用：撰寫錯誤訊息文案；設計重試機制（自動 / 手動、間隔策略）；使用者卡在「失敗 → 重試 → 失敗」迴圈；部分功能因外部依賴不可用時的降級呈現。
不適用：錯誤還沒發生時的關卡設計（gate 與 fallback 範疇）；錯誤狀態在整個畫面狀態機中的定位（狀態矩陣範疇）— 本文聚焦錯誤發生後的訊息、重試與降級三件事。

> **自包含聲明**：閱讀本文件不需要先讀其他 reference。

---

## 核心概念

錯誤不只是紅色文字 — 是一個需要設計退出路徑的狀態。錯誤恢復設計的三個組成：錯誤訊息讓使用者理解與決策、重試機制讓可恢復的失敗自動或手動恢復、降級模式讓局部失敗不擴大成整體不可用。三者共同的底線：使用者在任何錯誤狀態下都有至少兩條路（繼續嘗試、或離開）。

## 錯誤訊息的兩個職責

錯誤訊息承擔診斷（使用者能讀懂發生什麼）和行動（使用者知道下一步做什麼）。缺診斷讓使用者焦慮（「出了什麼事？」）、缺行動讓使用者卡住（「然後呢？」）。

**診斷面**：

- 用使用者的語言 —「無法連線到伺服器」優於 `ECONNREFUSED 127.0.0.1:7681`。技術細節保留在次要位置（折疊區塊、「詳細資訊」、複製按鈕），進階使用者能取得、一般使用者不被打擾。
- 描述影響而非原因 —「終端機暫時無法使用」比「WebSocket 連線逾時」直接回答「這對我意味著什麼」。原因是補充、影響是核心。
- 語氣反映實際嚴重程度 —「嚴重錯誤」「系統崩潰」類措辭在使用者只能重試或返回的情況下是恐嚇、不是資訊。

**行動面**：

- 每個錯誤訊息至少一個可執行的下一步，越具體越好 —「連線失敗，請檢查網路後重試」給了兩個行動；「發生錯誤」給了零個。
- 行動要對使用者可操作 —「請聯繫系統管理員」在自用工具場景沒有意義（使用者就是管理員）；「請稍後再試」在服務完全不可用時沒有幫助。
- 行動選項中至少一個是退出路徑（返回 / 關閉 / 取消）— 使用者可能不想重試、只想離開。
- 行動與錯誤層級對位 — 行動解決的層級等於錯誤發生的層級：資料層錯誤（檔案格式不合法）配資料層行動（換檔案重試）；重載 app / 重啟這類執行環境層行動只配執行環境層錯誤。過重（資料層錯誤配重載）不解決問題、還附帶狀態遺失的代價；過輕（執行環境層崩潰只給「關閉」）讓使用者無路可走 — 兩個方向都是缺口，而使用者傾向照著按鈕走。通用錯誤容器把最重的行動配給所有錯誤是不對位的結構性來源 — 錯誤 UI 的複用邊界是「行動相容」、不是「都是錯誤」。層級集合至少含資料層、網路層、執行環境層。網路層錯誤（逾時、連線中斷）配對的行動須含可能原因提示（如「檢查網路後重試」），不可只給「重試」，也不升級為執行環境層行動。

### 三段鏈式範例：判斷錯誤層級

情境：一個「請求逾時」錯誤，判斷屬於哪個層級並配對應行動；同時示範層級集合不限於資料層與執行環境層兩種。驗證段的判定屬「設計產出物」（見 `.claude/skills/skill-design-guide/references/chained-examples.md`〈各段允許與禁止內容〉【驗證】段的判定規則）。

【輸入】

```
SPEC 片段：使用者上傳一個檔案，伺服器回應「請求逾時」（未收到伺服器回應，
無法判斷是網路問題還是伺服器忙碌）
```

【產出】

```
形態：決策表
判斷依據                                       | 結果
此錯誤是否屬於「資料本身有問題」（如格式不合法） | 否（並非資料格式問題）
此錯誤是否屬於「執行環境層」（app 需要重載或重啟才能恢復） | 否（不需要重載 app）
此錯誤發生的層級                               | 網路層（請求逾時，屬連線層面的暫時性失敗，
                                                  層級集合不只資料層與執行環境層兩種）
結論                                           | 行動配「檢查網路後重試」，不可只給「重試」
                                                  （未點出可能原因）；也不可升級為「重載 app」
                                                  （逾時不代表 app 本身損毀）
```

【驗證】

```
檢驗問句
Q「請求逾時」屬於資料層還是網路層？
  預期：網路層——資料層錯誤的典型例子是檔案格式不合法，逾時是連線層面的現象，
  與資料本身是否合法無關

Q 行動欄位是否只給「重試」？
  預期：否——網路層錯誤配對的行動應包含具體原因提示（檢查網路），單純「重試」
  缺少診斷資訊，使用者不知道重試前該先確認什麼

Q 若把此錯誤誤判為資料層並配「換檔案重試」，會有什麼後果？
  預期：使用者被引導去換一個檔案，但問題其實是網路連線，換檔案不會解決問題，
  屬於行動與錯誤層級不對位的錯誤示範
```

**三層結構**：標題（一句話描述影響）、說明（補充原因與 context）、行動（按鈕或連結）。就地提示（欄位驗證、toast 類，不佔據整個畫面）可省略說明層、只需標題 + 一個行動；佔據整個畫面的錯誤狀態（含嚴重錯誤）三層都要，行動選項合計至少兩個（見〈Error loop 的逃生口〉第 1 點）。

## 重試機制

策略選擇取決於兩個因素：失敗是否可能自行恢復（暫時性網路中斷 vs 伺服器不存在）、使用者是否願意等待（前景操作 vs 背景同步）。

**自動 vs 手動 vs 混合**：

| 模式 | 適用                                     | UX 要求                                                     |
| ---- | ---------------------------------------- | ----------------------------------------------------------- |
| 自動 | 背景操作（同步、上報、心跳）、暫時性失敗 | 讓使用者知道正在重試（「第 2 次嘗試」）；必須有上限         |
| 手動 | 前景操作（使用者主動發起）、需確認意圖   | 重試按鈕明顯、旁邊有退出路徑                                |
| 混合 | 連線類操作的常見模式                     | 先自動 N 次（如 3 次），失敗後切換到「失敗」畫面 + 手動重試 |

自動重試無上限的問題：不可恢復的失敗（伺服器已關閉、認證過期）下浪費資源和電量、且使用者無法察覺問題。混合模式切換 UI 的意義是向使用者傳達「自動恢復已經試過了、需要你判斷接下來怎麼做」— 使用者可能知道原因（忘了開伺服器、WiFi 沒連上），修正後再手動重試。

**間隔策略**：

- 立即重試：極短暫瞬態失敗（DNS 偶發、TCP reset）。風險是 server 過載時多 client 同時重試的 thundering herd。
- 固定間隔：簡單可預測、使用者能估算等待。
- 指數退避 + jitter：間隔加倍（1s → 2s → 4s → 8s），適合 server 過載場景 — 給 server 恢復時間、減少 client 消耗。UX 挑戰是等待越來越長，解法是顯示倒數（「12 秒後自動重試」）加手動重試按鈕（使用者可跳過等待）。

間隔策略依失敗成因選：暫時性瞬斷（網路抖動）且使用者在畫面前等待時，用固定間隔並設上限；伺服器過載訊號（如 429、503）時用指數退避 + jitter，前景場景必配倒數與立即重試按鈕；背景同步預設指數退避。前景瞬斷場景選指數退避屬誤用（見 `gate-fallback.md`〈網路 gate〉Retry with feedback 的間隔選擇原則，兩檔對同一問題給同一答案）。

**重試狀態的 UI**：使用者需要知道三件事 — 正在重試、已重試幾次、下一次在什麼時候。

### 三段鏈式範例：策略選擇與重試狀態 UI

情境：一個前景連線操作失敗後選擇重試策略，並產出重試中的畫面。驗證段的判定屬「執行期行為」（產出物含畫面實際呈現，見 `.claude/skills/skill-design-guide/references/chained-examples.md`〈各段允許與禁止內容〉【驗證】段的判定規則）。

【輸入】

```
SPEC 片段：一個前景連線操作（使用者主動點擊連線，畫面等待中），失敗原因通常是網路瞬斷、
過一段時間有機會恢復；使用者在畫面前等待，允許有限度的自動嘗試
```

【產出】

```
形態：決策表 + ASCII 線框

策略判定：
  判斷依據                               | 結果
  失敗是否可能自行恢復                   | 是（網路瞬斷屬暫時性失敗）
  使用者是否在畫面前等待（願意等有限時間）| 是（前景操作，非背景同步）
  結論                                   | 採混合模式：先自動嘗試有限次數，用固定間隔
                                           （非指數退避）——前景等待場景使用者預期短時間內
                                           知道結果，指數退避讓間隔越拉越長不利於「使用者
                                           仍在等」的場景

重試中畫面（第 2 次自動嘗試中）：

+----------------------------------+
|  連線失敗，正在重新連線...        |
|  第 2 次嘗試（共 3 次上限）       |
|  下次重試：3 秒後                 |
|  [ 返回首頁 ]                     |
+----------------------------------+
```

【驗證】

```
Given 一個前景連線操作失敗，系統已判定採混合模式 + 固定間隔
When  第 2 次自動嘗試仍失敗、下次重試排定 3 秒後
Then  畫面同時顯示「已重試幾次（第 2 次，共 3 次上限）」與「下次重試時間（3 秒後）」
And   畫面提供「返回首頁」可操作按鈕，不因為還在自動嘗試中就隱藏（〈檢查清單〉行動選項中有退出路徑）
And   若失敗訊號改為伺服器過載（如 429、503）而改採指數退避，畫面須另加倒數與立即重試按鈕（〈重試機制〉間隔策略）
And   若前景瞬斷場景選用指數退避而非固定間隔，即為誤用——指數退避用於伺服器過載訊號
      （如 429、503）或背景同步，不適合前景瞬斷等待場景
```

## Error loop 的逃生口

「失敗 → 重試 → 失敗」迴圈困住使用者的三個條件同時成立時發生：錯誤持續存在（不會因重試改變）、UI 只提供重試選項、沒有重試次數上限。典型形態：error 畫面上唯一的按鈕是「重連」，底層問題（伺服器關閉、認證過期）不會因重連消失，使用者唯一的出路是殺掉 app。

逃生口設計：

1. **每個 error 畫面至少兩個選項** —「重試」+「返回」是最小組合。
2. **自動重試達上限後切換 UI** — 從「正在重試」切到「失敗」+ 手動選項。
3. **提供診斷線索讓使用者判斷值不值得繼續重試** —「伺服器沒有回應」（可能正在重啟、重試或許成功）和「認證已過期」（重試不會改變、需要重新登入）是不同的決策。
4. **替代操作路徑** — 連特定伺服器失敗提供「選擇其他伺服器」、認證失敗提供「其他登入方式」，把「重試同樣的操作」擴展成「嘗試不同的操作」。

審查方法（設計階段可完成）：找出所有 error 類狀態，檢查可用操作欄是否只有「重試」、退出路徑欄是否為空 — 兩者同時成立 = 潛在 retry loop。

## Degraded mode

部分功能因外部依賴不可用（斷網、服務故障、權限缺失）而暫停時，讓使用者清楚知道哪些可用哪些不可用，而非整個 app 停擺。三種呈現方式：

- **靜默隱藏**：把不可用功能從 UI 移除。只適合使用者從未用過的功能——判斷依據是該功能是否有使用者用過，不是上線時間長短或採用率高低，即使採用率低，只要有使用者用過就不算「從未用過」。用過的功能突然消失會被當成 bug、恢復後重新出現加劇困惑。
- **明確標示**：UI 保留、加不可用標示。要點：說明原因（「搜尋功能需要網路連線」優於單純灰掉）、說明恢復條件（「連上網路後自動恢復」）、不只靠顏色（搭配文字或圖示）。
- **替代方案**：提供不需要失敗依賴的版本（線上搜尋 → 本地快取搜尋），並讓使用者知道在用替代版（「離線模式 — 結果可能不是最新」）。

### 三段鏈式範例：判斷「使用者從未用過的功能」

情境：同一版本裡一個全新功能與一個已上線超過一年的功能都因外部條件變動需要暫停，判斷各自能不能用靜默隱藏。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：一個 app 在本次版本新增了「批次匯出」功能，同時該版本因為第三方服務條款
變更，必須暫時停用一項使用者已使用超過一年的「雲端同步」功能
```

【產出】

```
形態：決策表
功能     | 使用者是否曾經使用過                     | 判定
批次匯出 | 否（本版本才新增，尚無任何使用者用過）   | 適合靜默隱藏（暫停期間 UI 直接移除）
雲端同步 | 是（已上線超過一年，有使用者依賴）       | 不適合靜默隱藏，須用「明確標示」
                                                     （保留 UI、標示不可用原因與恢復條件）
```

【驗證】

```
檢驗問句
Q 判斷「是否從未用過」的依據是功能上線時間長短，還是使用者是否已經用過？
  預期：是後者——即使一個功能上線已久但採用率低，仍不能因「用的人少」就套用靜默隱藏，
  只要有使用者用過，突然消失就會被當成 bug

Q「雲端同步」暫停是否可以直接從 UI 移除？
  預期：否——已有使用者依賴，移除會讓使用者以為功能損壞或資料遺失，
  須採明確標示並說明恢復條件
```

**全域 vs 功能級**：全域降級（頂部橫幅 + 所有網路功能統一標示）實作簡單、適合網路是核心依賴的 app，但可能過度限制；功能級降級（每個功能獨立宣告依賴、獨立判斷可用性）更精確、實作更複雜。

**進入與退出**：

- 進入用持續顯示的通知（橫幅類）而非自動消失的短提示 — 短提示消失後使用者忘記自己在降級中、之後的操作失敗顯得毫無脈絡。
- 防抖動：網路不穩時每秒在正常 / 降級間切換會讓 UI 閃爍，加穩定性判斷（連續 N 秒不可用才進、連續 N 秒可用才出）。N 以該功能單次請求的逾時值為下界 — 逾時值本身就是這個功能「多久算失敗」的既有判斷基準，N 若小於逾時值，等於連一次請求都還沒判定失敗就先宣告降級。
- 退出時通知（「已恢復連線」）並自動執行待完成操作（同步、補發）。

### 三段鏈式範例：計算防抖動 N 值下界

情境：一個功能的請求逾時值已知，判斷防抖動 N 該如何取值，並用一段網路抖動示範下界的效果。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：一個功能呼叫的單次請求逾時設定為 5 秒；網路狀態在正常與不穩定之間
反覆切換（斷續 1-2 秒又恢復）
```

【產出】

```
形態：決策表
判斷依據                             | 結果
該功能單次請求的逾時值               | 5 秒（既有設定，代表「多久算失敗」的既有基準）
N（連續不可用需達到的秒數才進入降級） | 不小於 5 秒（下界即逾時值本身）
若網路只斷續 1-2 秒又恢復             | 不足以觸發降級（低於下界，判定為單次請求內的
                                        正常抖動，不應顯示降級橫幅又立即恢復造成閃爍）
結論                                 | N 至少設為 5 秒（可視體驗需求設更高，但不可低於逾時值）
```

【驗證】

```
檢驗問句
Q N 是否可以設為小於 5 秒（例如 2 秒）？
  預期：否——依規則「N 以該功能單次請求逾時值為下界」，N 若小於逾時值，代表連
  一次請求都還沒被判定失敗，系統就已宣告降級，時序上不成立

Q 網路斷續 1-2 秒又恢復的情境，是否應該觸發降級橫幅？
  預期：否——低於 N 的下界（5 秒），視為正常抖動，觸發降級橫幅會造成畫面在
  正常與降級間頻繁閃爍
```

## 檢查清單
