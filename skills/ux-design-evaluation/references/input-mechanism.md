# 輸入機制：鍵盤、送出、IME 的設計決策

本 reference 為「設計或審查使用者輸入介面」情境。

適用：任何有輸入框的功能（表單、搜尋、CLI / terminal、聊天）；mobile 鍵盤行為異常（自動校正破壞輸入、建議列遮擋畫面）；密碼 / API key / secret 類欄位的安全審查；送出時機的選擇（按送出 / 即時 / debounce）。
不適用：輸入內容的業務驗證邏輯（屬後端 / domain 層）；送出按鈕本身的 loading 回饋（屬互動回饋範疇）。

> **自包含聲明**：閱讀本文件不需要先讀其他 reference。

---

## 核心概念

輸入機制是設計產物，在功能規格階段決定，和 API schema 同級。手機鍵盤的行為由多個參數控制，每個參數都是設計決策 — 影響使用者體驗、UI layout、甚至通訊協議。依賴預設值等於把決策交給平台、事後逐一踩到問題再補。

## 四個決策維度

每個輸入框過一次四維決策，結果記錄成表、code review 時逐項對照：

**Keyboard type — 顯示哪種鍵盤**。判斷依據是「使用者要輸入什麼內容」：email 用 email 鍵盤（有 `@` 鍵）、電話用數字鍵盤、密碼或 CLI 指令用 `visiblePassword` 型別（避免自動校正和建議）。CLI 指令包含路徑分隔符、flag 縮寫等非自然語言內容，一般文字鍵盤會嘗試把 `ls -la` 或 `/usr/bin/` 校正成別的詞。

**Submit model — 怎麼送出**。整行送出（按 Enter / Send 一次傳整行）vs 逐字元送出（每個按鍵即時傳送）。這個決策直接影響通訊協議：整行送出的 server 按行處理、protocol 簡單，代價是 Tab 補全等即時互動無法觸發；逐字元送出支援補全和即時控制鍵、但 protocol 複雜度和網路延遲敏感度顯著提高。決策應在 protocol spec 階段做、不是 UI 實作時臨時決定。

**IME policy — 輸入法的自動行為**。三個控制項各自獨立：

- 自動校正（autocorrect）：把輸入替換成字典詞。非自然語言內容（指令、路徑、程式碼）會被破壞。
- 輸入建議（suggestions）：鍵盤上方的候選列。可能遮擋畫面關鍵區域。
- 個人化學習（personalized learning）：IME 從輸入學習新詞、跨 app 適用。輸入可能含 secret 時是安全問題（見 IME 安全清單）。

**Special keys — 特殊按鍵**。手機鍵盤沒有 Esc / Tab / Ctrl / 方向鍵，需要這些按鍵的應用必須自建 UI（如鍵盤上方的工具列）。工具列的按鈕大小（可精確觸碰的底線：iOS HIG 44pt、Material 48dp）、排列順序、長按行為都是 UX 決策。排列依據依下列優先序，依序套用、不可疊加：(1) 有使用頻率資料時，一律依實際使用頻率排列——較常用的按鍵放在拇指自然停留處附近（如慣用手側或工具列邊緣），較少用的依序往外推；即使某鍵是完成核心操作的必經鍵，只要有頻率資料，仍依頻率決定位置，不因為它是必經鍵而額外提高順位。(2) 只有使用頻率無法確定時，才退回以完成核心操作的臨界路徑上是否必經此鍵作為排序依據——沒有使用頻率資料不是不排列的理由，退回臨界路徑判定即可。長按只用於重複觸發（如方向鍵長按連續移動），不承載與短按不同的第二功能 — 工具列缺乏視覺提示告知使用者「這顆鍵可以長按」，把第二功能藏在長按等於做了不可發現的操作。

### 三段鏈式範例：無使用頻率資料時的排列依據

情境：判斷一組特殊按鍵在缺乏使用頻率統計時該怎麼排列。驗證段的判定屬「設計產出物」（判定規則：產出物能在執行期被啟動、看得到它運作的屬執行期行為，驗證段寫 Given/When/Then；契約表、判定結果這類靜態文件屬設計產出物，驗證段寫檢驗問句加預期答案）。

【輸入】

```
SPEC 片段：一個終端機 app 的鍵盤工具列，需放置 Esc、Tab、Ctrl、上下左右四個方向鍵，
共 7 顆按鍵；產品沒有既有的按鍵使用頻率統計資料
```

【產出】

```
形態：決策表
判斷依據                                       | 結果
是否有客觀的使用頻率量測資料                   | 否（無既有統計）
完成核心操作（在終端機內移動游標並執行指令）是否必經某些按鍵 | 是——上下左右鍵用於瀏覽指令歷史與
                                                  游標移動，屬多數操作路徑必經；Ctrl 用於中斷指令
                                                  （次常見）
結論                                           | 排列依臨界路徑判定：方向鍵放拇指最近處，
                                                  其次 Ctrl，Esc / Tab 依序往外推
```

【驗證】

```
檢驗問句
Q 無使用頻率統計資料時，排列依據是留白等產品資料，還是改用臨界路徑判定？
  預期：改用臨界路徑判定——本節規則已明訂「使用頻率無法確定時，以完成核心操作的
  臨界路徑上是否必經此鍵作為排序依據」，不可用「沒有資料」為由不排列

Q 方向鍵是否因為「必經」而排在 Ctrl 之前？
  預期：是——方向鍵用於瀏覽指令歷史與游標移動，屬多數操作路徑必經，優先序高於
  次常見的 Ctrl 中斷指令
```

### 三段鏈式範例：CLI 輸入場景的四維決策

情境：一個 CLI 輸入框過四維決策。Submit 欄位「整行送出」的理由（protocol 簡單、犧牲 Tab 補全）出自上方〈四個決策維度〉Submit model 小節。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：一個終端機模擬器 app 的指令輸入框，內容為 shell 指令（含路徑分隔符、flag、
管線符號），不含固定格式的自然語言詞彙
```

【產出】

```
形態：決策表
維度         | 決策                                     | 理由
Keyboard     | 明文、無自動校正與建議的鍵盤型別（如 visiblePassword） | CLI 指令不適用自動校正，路徑與 flag 會被誤校正成字典詞
Submit       | 整行送出                                 | protocol 簡單，犧牲 Tab 補全
IME          | 全關（自動校正/建議/個人化學習皆關）     | 安全考量 + 非自然語言輸入
Special keys | 底部工具列                               | 手機無實體 Esc/Tab/Ctrl
```

【驗證】

```
檢驗問句
Q Keyboard 決策是否可沿用一般文字鍵盤？
  預期：否——本節 Keyboard type 規定 CLI 指令用避免自動校正和建議的型別；一般文字鍵盤
  會把 `ls -la` 或 `/usr/bin/` 校正成別的詞

Q 四個維度是否都有對應的理由欄，而非只給決策值？
  預期：是——理由欄說明「為什麼」，供 review 時判斷決策是否仍適用於當下輸入內容
```

事先決策並記錄、review 逐項勾選，成本低於事後逐一發現問題 — 實例：一個終端機 app 的六個輸入參數全是實機測試後 hotfix 補上的，漏掉個人化學習關閉是安全漏洞、漏掉自動校正關閉是 UX 問題。

## 場景一：表單

表單輸入以自然語言為主（姓名、email、地址），鍵盤的自動行為大部分是幫助 — 和 CLI 場景的取捨方向相反。

**Keyboard type 按欄位選**：判斷依據是欄位內容格式是否固定為單一格式；格式固定即選對應的專用鍵盤，格式不固定（可能是多種輸入內容之一）則維持一般文字鍵盤。

### 三段鏈式範例：Keyboard type 決策與規則交界

情境：一組表單欄位過 Keyboard type 決策，其中「帳號」欄位內容格式不固定（規則交界情境）。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段（欄位清單）：
  Email（僅接受 email 格式）
  電話號碼
  網址
  密碼
  數字金額（含小數點）
  帳號（可填 email 或使用者自訂的使用者名稱）
```

【產出】

```
形態：決策表
欄位     | Keyboard 決策                     | 理由
Email    | email 型鍵盤（含 @ 與網域快捷鍵） | 內容固定為 email 格式
電話     | 數字型鍵盤                        | 只顯示數字與撥號常用符號
網址     | 網址型鍵盤（含網域快捷鍵）         | 內容固定為 URL 格式
密碼     | 隱碼型鍵盤                        | 關閉自動校正，避免密碼被誤校正
數字金額 | 數字型鍵盤（含小數點）             | 內容固定為數字
帳號     | 一般文字鍵盤                       | 內容格式不固定（email 或自訂使用者名稱皆可能），
                                             email 型鍵盤的快捷鍵對使用者名稱輸入無幫助反而限制字元
```

【驗證】

```
檢驗問句
Q「帳號」欄位是否因為「可能是 email」就選 email 型鍵盤？
  預期：否——判斷標準是欄位內容格式是否固定為單一格式；「可填 email 或使用者名稱」代表
  格式不固定，應選不限制字元的一般文字鍵盤，讓兩種輸入都能正常打
```

**驗證時機**：格式明確的欄位用即時驗證但在失去焦點（on blur）才顯示錯誤 — 輸入過程中報「email 格式錯誤」（使用者才打到 `user@`）是過早報錯；多欄位交叉驗證（密碼確認、日期範圍）用送出時驗證、配 scroll 定位 + 欄位 highlight 幫使用者找到錯誤欄位。混合策略：格式驗證 on blur、業務驗證（「email 已被註冊」）on submit。未列舉的規則依「判定結果需要哪些資料」分類：只需本欄位當下的值、本地即可算出（長度、字元類型、格式樣式）→ 格式驗證，on blur 顯示；需要其他欄位的值（密碼確認、日期範圍）→ 交叉驗證，on submit；需要查詢伺服器狀態（email 是否已被註冊）→ 業務驗證，on submit。規則看起來像不像「格式」不是判斷標準。

### 三段鏈式範例：驗證時機的規則交界

情境：判斷「密碼強度」規則屬格式驗證還是業務驗證，決定顯示時機。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：密碼欄位需符合最少 8 碼、含大小寫與數字的強度要求；同一表單另有 email 欄位，
需檢查該 email 是否已被註冊過
```

【產出】

```
形態：決策表
規則             | 判定所需資料                     | 判定
密碼強度         | 僅本欄位值，本地可算            | 格式驗證 → on blur 顯示
email 是否已被註冊 | 需查詢伺服器帳號資料            | 業務驗證 → on submit 顯示
```

【驗證】

```
檢驗問句
Q 密碼強度屬於格式驗證還是業務驗證？
  預期：格式驗證——依本節分類，密碼強度只需本欄位當下的值、本地即可算出；規則看起來
  像不像格式不是判斷標準

Q email 是否已被註冊的檢查是否也能在 on blur 時觸發？
  預期：否——該規則依賴伺服器資料，若在 blur 時觸發，等於把業務驗證提早成格式驗證的
  時機，違反本節混合策略的分工
```

**Auto-fill**：正確標記欄位語意類型（autofill hints），系統才能自動填入已儲存的姓名 / 地址 / 信用卡 — mobile 上減少的打字量直接轉化為轉換率。

**錯誤回饋**：訊息緊跟對應欄位下方（不集中在表單頂部）；內容說「期望什麼」而非「哪裡錯了」（「請輸入有效的 email 地址」優於「email 格式無效」）；錯誤欄位邊框變色搭配文字、不只靠顏色（色盲使用者）。

## 場景二：搜尋

核心決策是「輸入到什麼程度觸發搜尋」— submit model 維度在搜尋場景的展開：

| 觸發模式 | 機制                          | 適用                                             |
| -------- | ----------------------------- | ------------------------------------------------ |
| 按送出   | 打完按搜尋鈕、一次搜尋        | 搜尋成本高：DB 全文搜尋、外部 API（限速 / 計費） |
| 即時     | 每個字元觸發一次              | 搜尋成本低：本地過濾、記憶體內資料集             |
| Debounce | 停止輸入 300-500ms 後觸發一次 | 遠端搜尋的常見選擇：平衡即時感和 API 呼叫次數    |

判斷依據是搜尋運算本身的「成本」，不是資料是否在本地。「本地過濾」只是低成本的常見形式之一；本地資料若運算量大（如大量記錄的全文搜尋），運算成本仍高，依上表對應「按送出」列，不對應「即時」列。不能因為資料在本地就直接判定為低成本並採「即時」。

即時觸發用在高成本搜尋的問題：輸入 `hello` 過程觸發五次 API 呼叫、前四次結果沒被看到就被覆蓋。Debounce 延遲的 trade-off：太短（100ms）接近即時觸發、太長（1000ms）使用者感到明顯延遲；搜尋框用 trailing-edge 語意（等停止輸入才觸發）。

### 三段鏈式範例：判斷搜尋成本的依據

情境：判斷本地資料庫的全文搜尋該用哪種觸發模式，示範判斷標準是「成本」而非「是否為本地」。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：一個內建十萬筆記錄的本地資料庫，支援使用者輸入關鍵字做全文搜尋
（非簡單前綴比對）
```

【產出】

```
形態：決策表
判斷依據                       | 結果
資料是否在本地（不需網路請求） | 是
搜尋運算本身的計算成本         | 高（全文搜尋十萬筆記錄，非記憶體內簡單過濾）
結論                           | 依「搜尋成本」而非「是否為本地」選擇觸發模式：
                                 採按送出，不採每字元即時觸發（Debounce 依表格
                                 適用欄定位為「遠端搜尋的常見選擇」，本情境無 API
                                 呼叫次數的考量，條文不支持在此改採 debounce）
```

【驗證】

```
檢驗問句
Q 判斷觸發模式的依據是「資料在不在本地」還是「搜尋運算的成本」？
  預期：是後者——本地資料庫的全文搜尋運算成本可能遠高於「本地」一詞給人的直覺印象
  （十萬筆全文搜尋 vs 記憶體內十筆簡單過濾），「本地」不等於「低成本」

Q 這個情境是否適用「即時」觸發模式？
  預期：否——即時觸發適用於低成本搜尋，本情境成本高，選即時會在每個字元都跑一次
  十萬筆全文搜尋運算
```

結果顯示形式：suggestion list（候選可列舉：城市、產品、使用者名）、獨立結果頁（結果量大、需分頁）、即時過濾（在已顯示的清單中隱藏不符項目）。

細節：搜尋框 keyboard type 用一般文字 + `textInputAction: search` 讓 Enter 鍵顯示放大鏡 — 使用者看到搜尋圖示知道按下去會觸發搜尋、看到換行圖示會猶豫。

## 場景三：CLI / Terminal

CLI 指令是結構化語法 — 路徑分隔符、flag、管線符號都有精確語意，為自然語言設計的鍵盤自動行為（校正、建議、學習）全部變成干擾。桌面終端機直接傳按鍵事件、沒有 IME 層；手機在使用者和 app 之間插入 IME — 按鍵可能被組合、被校正、被學習。

處理：關閉全部 IME 自動行為（`visiblePassword` + autocorrect off + suggestions off + personalized learning off 四參數）；submit model 在 protocol 層決定（整行 vs 逐字元，影響 server 端行為預期和 frame 格式）；特殊鍵用鍵盤上方工具列提供（Esc / Tab / Ctrl / 方向鍵），Ctrl 組合鍵常見實作是「按 Ctrl 進入修飾模式、下一鍵自動加前綴」。

## IME 安全清單

IME 個人化學習把輸入存進跨 app 共用的詞庫 — 處理 secret 的輸入框若不關閉，密碼 / API key / 伺服器路徑會在使用者於其他 app 打字時出現在建議列，任何看到螢幕的人都看得到。這和傳統密碼外洩（資料庫入侵、傳輸攔截）路徑不同：使用者在日常打字時被動暴露、不會意識到 IME 記住了別的 app 輸入的密碼。

適用欄位：密碼 / PIN、API key / token、伺服器位址 / 連線字串、CLI 指令（可能含前述任何一類）、信用卡號、任何 confidential 欄位。

confidential 的判斷標準是使用者不希望內容被 IME 詞庫記住。其中 secret（密碼／PIN、API key／token、伺服器位址／連線字串、CLI 指令、信用卡號：被他人看到即可冒用或取得存取權的值）四項全關，設定見下表——**下表只適用 secret 類欄位**，非 secret 的 confidential 欄位規則見表後段。

| 控制項     | secret 類欄位設定        | 理由                       |
| ---------- | ------------------------ | -------------------------- |
| 個人化學習 | 明確關閉（不依賴預設值） | 防止 secret 進入 IME 詞庫  |
| 自動校正   | 關閉                     | 防止 secret 被替換成字典詞 |
| 輸入建議   | 關閉                     | 防止 secret 出現在建議列   |
| 密碼欄位   | 依需求設定 obscure text  | 畫面不顯示明文             |

平台沒有獨立的學習開關時（如 iOS），在規格中顯式記錄「此平台無法單獨關閉學習」與接受的風險，不以關閉全部輸入輔助代替。

非 secret 的 confidential 欄位（如日記、私人備忘）不比照上表，兩項控制分屬不同判斷標準、互不影響：個人化學習只依是否為 confidential 決定，一律明確關閉；自動校正與輸入建議與是否 confidential 無關，改依內容是否為自然語言決定，結果為自然語言時兩者保留開啟、非自然語言時依上方〈四個決策維度〉IME policy 所述「非自然語言內容會被破壞」而應關閉，見下方範例。

平台邊界：這些設定對應 iOS 的 spell checking attribute 與 Android 的 no-suggestions flag，不同 IME app 的遵守程度不一 — app 端控制是「盡力而為」，設定正確的 flag 是必要條件、不是充分保證，安全敏感場景另配 secure text entry。

### 三段鏈式範例：判斷「confidential 欄位」

情境：判斷一個私人日記的內文輸入框是否算 IME 安全清單的 confidential 欄位。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：一個私人日記 app 的內文輸入欄位，內容是使用者的自由書寫文字，
不含結構化的帳密或金融資訊
```

【產出】

```
形態：決策表
判斷依據                                       | 結果
內容是否為使用者不希望被系統詞庫記住的私密資訊 | 是（日記內容涉及個人隱私，使用者通常不希望
                                                  被 IME 學習後出現在其他 app 的建議列）
內容是否為自然語言（校正/建議對輸入品質有幫助）| 是
內容是否屬於 secret（帳密、金鑰等結構化憑證）  | 否（日記內文為自由書寫，非結構化憑證）
結論                                           | 屬 confidential 非 secret 欄位，個人化學習明確
                                                  關閉；自動校正與輸入建議因內容為自然語言而
                                                  保留開啟——不比照 secret 類欄位四項全關
```

【驗證】

```
檢驗問句
Q 「confidential」的判斷依據是內容的資料型態（帳密、金融）還是使用者是否不希望被記住？
  預期：是後者——日記內文不是帳密或金融資訊，但使用者不希望被 IME 詞庫記住，
  仍屬 confidential

Q IME 安全清單四項是否因為「屬 confidential」就全部關閉？
  預期：否——個人化學習依「不希望被記住」關閉；自動校正與輸入建議依「是否為自然語言」
  判定，日記為自然語言、非 secret，兩項皆保留開啟
```
