| 檔案 | 內容 |
| --- | --- |
| `interaction-feedback.md`（入口） | 核心原則／三層回饋模型／按鈕級回饋（按鈕流程與六種按鈕狀態） |
| `interaction-feedback-waiting-and-notification.md`（本檔） | 時間門檻與回饋策略／畫面級回饋／Spinner vs Skeleton／結果通知的形式選擇 |
| `interaction-feedback-component-semantics.md` | 元件語意與版面檢查（切換標籤／可點性／選中態／溢出／版面保障） |
| `interaction-feedback-checklist.md` | 反模式速查／檢查清單／參考來源（三份內容檔共用） |

適用：判斷 loading indicator 的時機與形式（spinner / skeleton / 進度條）；決定非同步操作等待期間的回饋策略（動畫過渡 / spinner / 進度指示 / 取消選項）；連線 / 配對 / 同步類多步驟流程的畫面級回饋；操作結果的通知形式選擇（SnackBar / Dialog / Banner / Bottom Sheet）。
不適用：單一按鈕的狀態機（idle / loading / disabled，屬按鈕級回饋範疇，見 `interaction-feedback.md`〈按鈕級回饋〉）；元件語意與版面判斷標準（屬 `interaction-feedback-component-semantics.md`）；畫面狀態的完整枚舉與退出路徑（狀態矩陣範疇，見 `screen-state-matrix.md`）。

## 時間門檻與回饋策略

**本節回答 `interaction-feedback.md`〈三層回饋模型〉第 2 層「等待指示」在不同等待時長下該用哪種具體策略。**

回饋形式取決於等待時間 — 100ms 的頁面切換加 spinner 是視覺雜訊、30 秒的批次匯出只有 spinner 撐不住耐心。門檻來源：100ms / 1s / 10s 是感知與注意力門檻（Miller、Nielsen）、400ms 是生產力門檻（Doherty Threshold）：

| 等待時間             | 使用者感受 | 回饋策略                         | 範例               |
| -------------------- | ---------- | --------------------------------- | ------------------ |
| 0ms 以上、未滿 100ms   | 即時       | 點擊確認即可                     | 頁面導航、開關切換 |
| 100ms 以上、未滿 400ms | 幾乎即時   | 動畫過渡掩蓋等待                 | 快速搜尋、本地查詢 |
| 400ms 以上、未滿 1s    | 短暫等待   | Spinner / 按鈕 loading 狀態      | API 查詢、表單送出 |
| 1s 以上、未滿 10s      | 明顯等待   | 進度指示 + spinner               | 檔案上傳、資料匯入 |
| 10s 以上（含）        | 長時間等待 | 進度百分比 + 預估時間 + 取消選項 | 批次處理、大型同步 |

上表每列的「等待時間」下界為含、上界為不含（例如「1s 以上、未滿 10s」指涵蓋 1s 但不含 10s），對照數值時只需比較是否落在該區間，不必參考其他段落的範例數字。回饋策略欄以「+」相連時，代表同時採用兩者作為單一組合策略，不是擇一或取其中最低項；「進度指示」不要求精確可計算的百分比，可用文字（如「配對中」）或不定形式進度條表達，與「10s 以上」列要求精確百分比的「進度百分比」不同——結果形狀未知、無法給出精確進度時，仍應採「進度指示 + spinner」組合，不因此降級為只用 spinner。

超過 10 秒使用者開始考慮放棄；數十秒以上考慮轉背景任務、完成後通知。

**完成宣告要有窮盡證據**。批次 / 遍歷類操作的「完成」判定若只憑停滯訊號（連續 N 輪計數沒有變化），分不出「真的到底了」和「載入通道根本沒打開」— lazy-load 頁面的內容增長依賴特定觸發動作，動作缺失時計數永遠穩定，實測出現過只處理十分之一就宣告完成的事故。窮盡證據包括：來源總數對照（頁面計數、API total）、終止標記（「沒有更多」元素、載入觸發器消失）、API 側的窮盡宣告（分頁 cursor 耗盡、has_more=false）。只有停滯訊號時，完成宣告降級為「已取得 N 筆、可能還有更多」的部分結果表達；下游需要全量的操作（備份、匯出、合規留存）不適用降級 — 不完整按失敗處理、阻止下游動作。

**延遲是分布、不是常數**。同一支 API 平常 300ms、尖峰或弱網下 3s，對表用 p90 / p95 而非平均值 — 平均 300ms、p95 卻 2s 的操作，每二十次就有一次使用者盯著沒有指示的畫面等 2 秒。規格文件記錄延遲門檻時，須顯式記錄選用的統計量（p90 或 p95），不可只寫「用 p90／p95」留給實作者各自代入。兩個補充機制：

- **延遲顯示（delayed spinner）**：發請求後等 300-400ms 才掛 spinner、請求先回來就完全不顯示 — 快的請求（多數）沒有閃爍、慢的請求在使用者開始懷疑前得到指示。這是延遲分布橫跨門檻帶時的標準解。
- **最短顯示時間**：spinner 一旦顯示至少停留約 300ms、請求提早完成也不立即移除 — 消除「閃一下就消失」的視覺雜訊。

兩個數值都是業界慣例值、可依實際延遲分布調整。驗證方式：用網速節流（DevTools / proxy 限速）模擬慢回應、逐帶確認對應的 UI 確實出現。

### 三段鏈式範例：p90 與 p95 的選用須顯式記錄

情境：同一支 API 的延遲量測結果，p90 與 p95 落在不同時間門檻帶，判斷規格是否需要記錄選用哪一個。驗證段的判定屬「設計產出物」（判定規則：產出物能在執行期被啟動、看得到它運作的屬執行期行為，驗證段寫 Given/When/Then；契約表、判定結果這類靜態文件屬設計產出物，驗證段寫檢驗問句加預期答案）。

【輸入】

```
SPEC 片段：一支 API 的延遲量測結果為平均 300ms、p90 800ms、p95 1.5s
```

【產出】

```
形態：決策表
判斷依據                             | 結果
本規則要求對表用哪個統計量           | 未強制二擇一——取決於產品對「多久算慢」的
                                        容忍度，數值越保守（取 p95）代表回饋策略對
                                        尾端延遲的覆蓋越完整
本情境取 p90（800ms）落在哪個時間門檻帶 | 400ms-1s（短暫等待，Spinner／按鈕 loading 狀態）
本情境取 p95（1.5s）落在哪個時間門檻帶  | 1-10s（明顯等待，進度指示 + spinner）
結論                                 | 兩個統計量落在不同門檻帶，須先在規格中明確記錄
                                        本次選用哪一個統計量，不可讓實作者各自代入不同值
```

【驗證】

```
檢驗問句
Q 規則是否強制規定必須取 p90 或必須取 p95？
  預期：否——需要規格撰寫者明確記錄選用哪一個，本例的重點是「必須記錄選用哪個
  統計量」而非「哪個統計量才是對的」

Q 若規格沒有記錄選用哪個統計量，兩位讀者依本例的延遲數據會得出相同的回饋策略嗎？
  預期：不會——一位可能取 p90 掛 Spinner，另一位取 p95 加進度指示，這正是本例
  要補的缺口：規格必須顯式記錄選用值，而非留給讀者各自代入
```

## 畫面級回饋

按鈕級處理單一操作；連線、配對、同步、多步驟表單涉及**整個畫面的狀態轉換**，每個中間狀態需要能被區辨的 UI 與退出路徑：

| 維度     | 按鈕級                       | 畫面級                                       |
| -------- | ---------------------------- | --------------------------------------------- |
| 範圍     | 單一按鈕內的狀態變化         | 整個畫面 UI 替換                             |
| 狀態數   | 2-3（idle / loading / 結果） | 4-6（idle / 處理中 / 成功 / 失敗 / 斷線...） |
| 退出路徑 | 不需要（按鈕自己恢復）       | 每個中間狀態都必須有                         |

此表「每個中間狀態都必須有」是說明畫面級為何需要退出路徑（與按鈕級的差異），不是要求本節產出的回饋表另填退出路徑欄——退出路徑的完整枚舉與定義權威值在 `screen-state-matrix.md`，本節只負責決定每個狀態的 UI 呈現形式，見下方範例。

### 三段鏈式範例：畫面級回饋只負責 UI 呈現欄

情境：與 `screen-state-matrix.md`〈填寫範例〉相同的連線畫面情境，示範本節只需要決定每個狀態對應的 UI 回饋形式，不重複定義可用操作與退出路徑。驗證段的判定屬「設計產出物」。


【產出】

```
------------ | ---------------------------
```

```
  預期：否——本表只負責 UI 呈現（回饋形式）欄，可用操作與退出路徑的權威值
  只在 `screen-state-matrix.md` 定義一處

Q error 與 disconnected 兩狀態的 UI 呈現是否都包含「重連按鈕」？
```

## Spinner vs Skeleton

| 條件                                   | Spinner              | Skeleton Screen                  |
| --------------------------------------- | --------------------- | ----------------------------------- |
| 結果形狀已知（列表 / 卡片 / 個人資料） |                      | 適合：佔位接近最終結果、降低焦慮 |
| 結果形狀不確定（連線 / 計算結果）      | 適合：無法預畫佔位   |                                  |
| 操作觸發的等待（按鈕後）               | 適合：按鈕內 spinner |                                  |
| 頁面首次載入                           |                      | 適合：給畫面結構預期             |
| 等待短且可預測（< 2s）                 | 適合：輕量指示       |                                  |
| 等待較長（2-10s）                      |                      | 適合：結構佔位優於空白等待       |

判斷式：「知道長什麼樣 → skeleton；不知道 → spinner」。條件同時命中不同建議時裁決順序是**形狀 > 觸發 > 時長** — 按鈕載入個人資料 1.5s，形狀已知就用 skeleton。Skeleton 的佔位尺寸要與最終內容一致 — 載入完成瞬間的版面跳動比空白等待更傷體驗。

其他感知效能技巧（真實效能無法改變時降低等待感受）：**樂觀更新**（先更新 UI、失敗再回滾 — 適合高成功率操作；回滾必須走失敗通知「操作未成功、已還原」+ 重試，不能無聲消失）、**漸進式載入**（先文字後圖片，等待期間可開始閱讀）、**動畫過渡**（300ms fade-in 掩蓋 200ms 延遲，感知是「動畫」而非「等待」）。

## 結果通知的形式選擇

通知形式是設計決策，判斷標準是兩個軸的交叉：**是否需要使用者操作**（純告知可自動消失；需要回應必須持續顯示 — 自動消失等於系統擅自幫使用者選了「忽略」）× **干擾程度**（視覺佔用 + 互動阻斷，原則是剛好夠用）。

六種形式從低干擾到高干擾：

| 形式            | 干擾 | 特性與適用                                                                                     |
| --------------- | ---- | ---------------------------------------------------------------------------------------------- |
| Inline 狀態更新 | 零   | 元素原位更新（收藏填滿、欄位紅字）；結果在觸發元素的 context 內能完整呈現時的首選形式          |
| SnackBar        | 低   | 底部短暫訊息條、自動消失、可帶一顆 action；已完成的確認（「已儲存」）、可選操作（刪除 + 復原） |
| Banner          | 中   | 內容區頂部持續顯示；**狀態驅動**（「目前離線」）— 與事件驅動的 SnackBar 的關鍵差異是生命週期   |
| Bottom Sheet    | 中高 | 底部滑出、延伸當前操作（分享、篩選、選項多的選擇）；易被滑掉 dismiss、不承載重要決策           |
| Dialog          | 高   | 居中 modal、阻斷背景互動；不可逆操作確認、含關鍵資訊的結果、必須二選一的決策                   |
| 全螢幕          | 最高 | 批次結果明細（87 成功 / 13 失敗逐筆）、流程終結頁、需在結果上進一步操作                        |

選擇矩陣：

| 情境                         | 需要操作？ | 推薦形式          |
| ---------------------------- | ---------- | ----------------- |
| 操作成功、結果已反映在 UI    | 否         | Inline            |
| 操作成功、結果不在視線範圍   | 否         | SnackBar          |
| 操作成功、帶可選復原         | 可選       | SnackBar + action |
| 持續性狀態變更（離線、降級） | 否 / 可選  | Banner            |
| 結果需要選後續操作           | 是         | Bottom Sheet      |
| 不可逆操作的事前確認         | 是         | Dialog            |
| 結果含關鍵資訊（檔案路徑）   | 是         | Dialog            |
| 結果密度高、需閱讀與逐筆操作 | 是         | 全螢幕            |

**補充判斷標準 — 操作頻率**：二軸無法區分「刪除帳號」和「刪除待辦事項」（讀數相同）。低頻高代價用 Dialog 確認、高頻低代價用 SnackBar + 復原、高頻高代價（如每日多次的批次刪除）以 SnackBar + 復原為主 — 復原機制把「代價」從不可逆降為可逆，抵銷代價本身帶來的風險；復原在技術上不可行時才升級為 Dialog。頻繁操作每次都彈 Dialog，使用者訓練出「不讀直接按確定」、真正重要的確認也被跳過 — Dialog 的保護效果與使用頻率成反比。

**自動消失時間**：純文字 SnackBar 約 4 秒、帶 action 8-10 秒（要讀完訊息再決定是否按）。無障礙：帶 action 的自動消失通知，action 要在別處可復得（如復原可從歷史觸發）、或螢幕閱讀器啟用時延長停留。Banner 與 Dialog 不自動消失 — Banner 在觸發條件消失時移除、Dialog 在使用者回應後關閉。

**堆疊規則**：SnackBar 新舊替換 — 批次操作逐筆彈只剩最後一條，應彙整成摘要或改全螢幕明細。Dialog 之上再彈 Dialog 是嚴重問題（注意力分裂、dismiss 順序混亂），連續確認改成多步驟單一 Dialog 或全螢幕流程。Banner 垂直堆疊、超過兩條考慮合併摘要。可接受的跨形式堆疊：Bottom Sheet 之上彈 Dialog（context + 確認、語意分工清楚）。
