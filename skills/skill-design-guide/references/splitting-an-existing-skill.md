# 拆分既有 skill

> 何時讀：既有 skill 超出第 2 層預算（門檻值、量測指令與分段估算表見 `SKILL.md`〈Progressive Disclosure — 三層載入〉；第 3 層的單檔判準也在該節，外移產生的新檔同樣要過）、要把內容外移時。**新建 skill 不適用**——它的內容從一開始就分層放，沒有既成的內部關係要保。
>
> **亦由此進入**——`writing-the-body.md`〈外部引用：指名身分，不用檔案路徑〉要求拆分後重寫指標，檔頭三段式與路由表「涵蓋章節」欄的寫法在本檔〈結構約定〉；`SKILL.md`〈Progressive Disclosure — 三層載入〉的正文也直接把超標的讀者送到這裡。
>
> 同目錄：拆完要照 `writing-the-body.md` 的引用規則重寫指標；量測指令與分段估算表留在 `SKILL.md`〈Progressive Disclosure — 三層載入〉；新建流程見 `creating-and-adopting-skills.md`，frontmatter 寫法見 `frontmatter-and-description.md`，工作流範本與問題排除見 `patterns-and-troubleshooting.md`，設計哲學見 `seeing-like-an-agent.md`。
>
> 溯源：本檔為 skill-design-guide 的 reference，v1.6.0 拆分時補上檔頭三段式（此前缺）。

本檔章節：〈為什麼需要專屬程序〉〈外移什麼、留什麼〉〈拆分特有的必查項〉〈兩種驗證，方法不同〉〈拆分特有的高頻缺陷〉〈結構約定〉〈收尾〉〈一則最小走查〉〈相關〉。

超出第 2 層預算的 skill 要外移內容時，用本程序。

## 為什麼需要專屬程序

**位元搬移正確不等於拆分後可用。** 一次實測：拆分後驗證行覆蓋 245/245、各新檔與原區間位元相同、無重複無遺漏——而該次拆分引入了四項嚴重缺陷。壞掉的不是位元，是位元之間的關係：節界、跨檔指涉、共置、外部引用。逐行比對對這四類全部無鑑別力，因為每一行都正確地搬到了新位置。

## 外移什麼、留什麼

**分界是「讀者在選路之前還是之後用到它」，不是「一次只用其中一段」。** 後者對每一張判準表、路由表、分類表都成立——三層預算表、自由度三級表、預設值設計表當時同住入口檔且全部互斥，它把整份入口檔都判成該外移，而「入口檔留判準」又把同一批判成該留。互斥性因此不進入判定。

對每一段依序問下列四問，**每一格都要求指名入口檔路由表的具體某一列**；指不出列，就不屬於那一格：

| 問 | 判定 |
|---|------|
| 1. 它回答的問題，是路由表某一列「何時讀」欄的判斷條件嗎？（讀者不用它就判不出自己屬不屬於那一列） | **留在入口檔**——外移後讀者無從得知該開哪一份 |
| 2. 路由表每一列的讀者都會用到它嗎？ | **留在入口檔**——外移只是把「一份載入」換成「每個人多跳一次」，總量不減 |
| 3. 指得出唯一或少數幾列，且那些讀者不必讀它就知道自己是那一列？ | **外移到那幾列的目標檔**，入口檔留該列路由 |
| 4. 三問都指不出任何一列？ | 它沒有讀者情境，是論證或實證敘事 → 壓縮成主張句，敘事移入 `CHANGELOG.md` 或 ticket |

**可外部驗證的地方是「指名列」這個動作**，與 `patterns-and-troubleshooting.md`〈Degrees of Freedom — 自由度匹配脆弱性〉要求指名機械消費者同一個手法：第三方拿同一份路由表重跑，會落在同一格。

**問 1 與問 3 的分界，在門檻與程序之間。** 判斷「我超標了嗎」用的門檻與量測指令是本檔這一列的觸發條件，讀者不先知道門檻就不會找到本檔——那是問 1，留在入口檔；「既然超標，該搬什麼」是已經決定要拆的人才問的，那是問 3，住在本檔。本節就是照這個判準從入口檔搬過來的。

## 拆分特有的必查項

**本表只收檔內關係的缺陷。** 拆分同時會新生兩個檔外物件——各新檔的檔頭與入口檔的路由表，它們的要求在〈結構約定〉，兩處互指、不重複列。

| 類別 | 為什麼拆分才會壞 | 怎麼查 |
|------|----------------|--------|
| **節界** | `##` 是 markdown 的語意結構。把某節的粗體段附到另一節尾巴，位元完全正確而少了一層結構，指向它的「該節末段」隨即落空 | 搬移前後各數一次 `^## `，對照原檔的章節清單；把並列節併入同檔時逐一確認每節仍有自己的 `##`。**裸 `grep -c '^## '` 會把 fenced block 內的 markdown 範例一起算進去**，在 skill 設計類文件上實測高估到 2.7 倍（8 vs 3），且拆分前後被同等高估、前後比對仍會相符，節界遺失因此可能通過檢查。用 `awk '/^```/{f=!f;next} !f && /^## /{n++} END{print n+0}' <file>` |
| **H1 與檔名** | H1 是拆分當下新生的物件——原檔只有一個，拆成 N 檔就新生 N 個。多節併入同一新檔時 H1 常只承諾其中一節，其餘落在標題範圍外。每一行都正確搬到了新位置，逐行比對對它無感 | 逐檔對照 H1 與該檔全部 `^## `，確認每個 H2 都在 H1 承諾的範圍內；檔名同此 |
| **跨檔指涉** | 原本同檔的〈章節名〉互指，現在跨檔。「本節」「見上」「末段」這類位置詞跨檔即失效 | 窮盡列出全部 `〈〉` 與位置詞，逐處判定目標現住哪一檔、讀者站在當前檔看不看得到路。**跨檔指涉一律連檔名一起寫**——只寫〈某節〉的話，讀者要回捲到檔頭的「同目錄」列才推得出它住哪 |
| **共置關係** | 兩處互相矛盾的判準原本相鄰、讀者順讀就撞見；拆分後分居兩檔，**衝突的可發現性下降**。這一類沒有任何指涉失效，位元也全對 | 拆分前先跑一次 `multi-round-review` skill 的 **1-E 斷言支撐 frame**，把互相矛盾的判準找出來並修掉，再拆 |
| **外部引用** | 指名式引用（`` `X` skill 的〈某節〉 ``）拆分後仍有效；路徑級引用（`.claude/skills/X/SKILL.md`〈某節〉）會斷 | 全站掃引用並**逐條列出**——不要截斷輸出後下「無一處失效」這種全稱結論 |

## 兩種驗證，方法不同

| 驗什麼 | 方法 | 可機械執行 |
|--------|------|-----------|
| 搬移正確性 | 行覆蓋（每一行不是留下就是搬出，合計等於原檔行數、無重複無遺漏）+ 各新檔正文與原區間逐行比對 | 是 |
| 拆分可用性 | 讀者視角的 frame——冷讀（單檔落地讀不讀得懂）、走路線（帶著問題跨檔跳轉接不接得住）、可執行走查（照做走不走得完） | 否 |

只驗了搬移正確性就宣告拆分完成，是本程序要防的主要失誤。

## 拆分特有的高頻缺陷

**內嵌於散文的計數在結構改動時不會跟上。** 「六檔」「五條」「三則」「共用兩節」——每次改動檔數、條數或節數，這些散落各處的數字都要跟，而它們不會自己跟。修法一律是**改成不自帶計數**（「後三列」→ 指向表本身、「三則」→「涵蓋三個模式的四個關鍵步驟」），不是把數字改對——改對的數字下次還會漂。

**位置性指涉的判準卡在「目標有沒有名字」，不卡在形態，也不卡在對未來的預測。** 一次實測中同型缺陷出現四次（末段、下段、上節、下方），其中三次由修法自身引入；同批留下的四處位置指涉則全部正確且比具名寫法好讀，判準因此不是「禁用位置指涉」。兩條失效條件，任一成立即改具名：

1. **跨檔** —— 目標與指涉不在同一檔。
2. **目標帶識別字** —— 目標段有 `##` / `###` 標題、粗體引導句或檔名，卻用位置詞去指它。有名字而不寫名字，是把可掃描的指標換成不可掃描的：具名指涉在目標改名或外移時會被死名／孤兒節檢查命中，位置詞不會——目標搬走後那句話依舊落在一段看似合理的內容旁，字串合法、檢查全綠。

合規只剩一種情形：同檔、緊接、且目標沒有識別字（一張無標題的表，「見下表」是唯一寫法）。判定兩步，都是打開檔案就看得到的現況：**先看目標段有沒有標題或粗體引導句，有就寫出那個字串；沒有才留位置詞，並確認同檔緊接。**

**這兩條不問目標日後會不會動。** 舊寫法是「目標可能移動即失效」，要撰寫者對未來下斷言，而四次同型缺陷的實證正說明那個斷言做不到——其中三次由修法自身引入，寫的當下都判過不會動。新條件把同一批缺陷判得出來而不需要預測：那四處指的都是帶標題的節或帶粗體引導句的段，「有名字卻用位置詞」在寫的當下就看得見，事後也由第三方重跑得出同一個答案。

## 結構約定

**檔頭三段式：何時讀 → 同目錄 → 溯源。** 操作資訊在前、維護資訊在後——讀者要的是「這份現在對我有沒有用」，溯源是給日後維護者的。「何時讀」不可只寫主路徑：橫向入口（他檔的步驟把讀者送過來）看到的第一行是「起點為 X 時讀本檔」，等於正面告訴他這份不是給他的。要另列「亦由此進入」——**粗體標記後接在「何時讀」句中，或獨立成段，兩種皆可**；要求的是它與主路徑在視覺上分得開，不是它佔一個獨立段落。

**橫向入口的查法**：`grep -rn '<本檔名>' <skill 目錄>`，扣掉**兩類平行索引**——入口檔路由表的那一列，以及各檔檔頭「同目錄」段的那些列。剩下的每一處才是橫向入口，逐條寫進「亦由此進入」。

**扣除規則必須跟著索引的增減走。** 這兩類是索引不是入口：它們列出鄰居，不把讀者送過來，而條文對橫向入口的定義是「他檔的**步驟**把讀者送過來」。實測一份檔的檔名在全 skill 命中 10 處，其中同目錄列佔 5 處——若只扣入口檔那一列，偽陽性率是 5/9。**同目錄段被補得越完整，這個誤判越嚴重**，而補同目錄與寫查法是兩次獨立且各自正確的改動。

**這一步不可憑印象**——線索全在別的檔案裡，從本檔內部看不到任何跡象；零命中與沒查過長得一樣，故掃描前先拿一個已知會命中的檔名驗管道。

**路由表帶「涵蓋章節」欄。** 拆分後路由表以情境索引（何時讀 → 哪個檔），而文件內部與外部引用都以章節名互指。兩軸不接時，拿著章節名來的讀者在入口檔找不到落點——一次實測有 77 處外部引用寫「skill〈某節〉」，這些人開入口檔 grep 只命中一句「三種模式共用〈某節〉與〈某節〉」，確認存在但不給落點。

## 收尾

**修完掃該類，不掃該處，且逐條列出。** reviewer 給的是它抽樣到的位置，而清單的形式在暗示完整性。修完用該 finding 的特徵字串掃整批，命中歸零或剩下的逐處判定合規才算處理完。兩個補充：掃描前先拿一個已知會命中的控制字串驗管道（零命中有兩個來源，指令寫錯的那一個看起來跟乾淨一模一樣）；掃完**逐條列出而非只看計數**（計數會因 regex 邊界或 locale collation 而少報）。字串掃描仍抓不到異形殘留（「另一張表也該改」），故對 reviewer 明說是多實例的 finding，另外逐項對照實例數與已修數。

**整體通讀。** 所有 frame 跑過、所有 finding 修完，不等於這份內容現在是好的——修法本身改變了被審查的對象，兩次各自正確的修法可以合成一個對兩個 frame 都不可見的缺陷。一次實測在此步抓到三處：指標寫好後目標被移走、條數改了而括號內的機械形式沒補、共用檔由兩份增為四份而「共用兩節」沒改。判斷標準是「這份內容現在讀起來像一個人一次寫完的嗎」。

## 一則最小走查

拆前的片段（單檔，兩節相鄰）：

```markdown
## 十一欄位填寫問句
（表格 11 列）
容器元件另答排列不變式三項，問句見本節末段。

**多形態專案**：支援多個形態時，欄位分兩組⋯⋯
```

拆後（搬入同一份 reference）：

```markdown
# 十一欄位填寫問句

## 十一欄位填寫問句
（表格 11 列）
容器元件另答排列不變式三項，問句見本節末段。

**多形態專案**：支援多個形態時，欄位分兩組⋯⋯
```

逐項判定：

| 必查項 | 判定 | 為什麼 |
|--------|------|--------|
| 節界 | **不通過** | 「多形態專案」原是與前者並列的節，搬入同檔後只剩粗體、少一層 `##`。位元全對 |
| 跨檔指涉 | **不通過** | 「見本節末段」原指同節的排列不變式段；節界消失後「本節」涵蓋到多形態段，末段變成後者 |
| 共置關係 | 通過 | 兩節本就相鄰，搬移後仍相鄰 |
| 外部引用 | 通過 | 無外部指向這兩節 |
| H1 | **不通過** | 檔名與 H1 只提前者，第二節在標題範圍外 |

修法：還原 `## 多形態專案`、「見本節末段」改具名為「見〈容器排列不變式三項〉段」、H1 改複合。

**這則的價值在它有多小**：兩節、十行、一次搬移，上表的必查項就命中三項。行覆蓋與位元比對對這三項全部回報通過。
