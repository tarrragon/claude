# 拆分既有 skill

> 何時讀：既有 skill 超出第 2 層預算（門檻值、量測指令與分段估算表見 `SKILL.md`〈Progressive Disclosure — 三層載入〉；第 3 層的單檔判斷標準也在該節，外移產生的新檔同樣要過）、要把內容外移時。**新建 skill 不適用**——它的內容從一開始就分層放，沒有既成的內部關係要保。
>
> **亦由此進入**——`writing-the-body.md`〈外部引用：指名身分，不用檔案路徑〉要求拆分後重寫指標，檔頭三段式與路由表「涵蓋章節」欄的寫法在本檔〈結構約定〉；`SKILL.md`〈Progressive Disclosure — 三層載入〉的正文也直接把超標的讀者送到這裡；`chained-examples.md` 補齊範例後若使檔案超出門檻，也會把讀者送到本檔〈補範例後超標：觸發條件與處置順序〉。
>
> 同目錄：**兩件事都跟指標有關，別搞混**——「指標怎麼寫」（引用形式、指名身分不用路徑）在 `writing-the-body.md`；「拆分後新生的兩個物件長什麼樣」（各新檔的檔頭三段式、入口檔路由表的「涵蓋章節」欄）在本檔〈結構約定〉。量測指令與分段估算表留在 `SKILL.md`〈Progressive Disclosure — 三層載入〉；新建流程見 `creating-and-adopting-skills.md`，frontmatter 寫法見 `frontmatter-and-description.md`，工作流範本與問題排除見 `patterns-and-troubleshooting.md`，設計哲學見 `seeing-like-an-agent.md`；範例本身的三段格式定義在 `chained-examples.md`，本檔只處理範例補入後導致超標的處置。
>
> 溯源：本檔為 skill-design-guide 的 reference，v1.6.0 拆分時補上檔頭三段式（此前缺）。

本檔章節：〈為什麼需要專屬程序〉〈補範例後超標：觸發條件與處置順序〉〈外移什麼、留什麼〉〈拆分特有的必查項〉〈兩種驗證，方法不同〉〈拆分特有的高頻缺陷〉〈結構約定〉〈收尾〉〈一則最小走查〉〈走完之後〉〈相關〉。

超出第 2 層預算的 skill 要外移內容時，用本程序。

## 為什麼需要專屬程序

**位元搬移正確不等於拆分後可用。** 一次實測：拆分後驗證行覆蓋 245/245、各新檔與原區間位元相同、無重複無遺漏——而該次拆分引入了四項嚴重缺陷。壞掉的不是位元，是位元之間的關係：節界、跨檔指涉、共置、外部引用。逐行比對對這四類全部無鑑別力，因為每一行都正確地搬到了新位置。

## 補範例後超標：觸發條件與處置順序

**觸發條件**：依 `chained-examples.md` 補齊三段鏈式範例後，該檔在其判定的讀取方式下（整份執行量全檔、選段查閱量最大單節，判斷標準見 `SKILL.md`〈第 3 層的單檔判斷標準是讀取方式〉）超出第 2 或第 3 層門檻——超標成因是**新補入的範例**，不是原有規則文字本身過長。

**門檻的目的是避免認知超載，不是格式合規。** 補範例前的原檔若是為了通過門檻而省略判斷條件的具體範例，那份「合格」只是假象；補齊範例後才顯露出真實的複雜度，此時**回頭刪範例或壓縮規則文字以求再次達標，等於把假象做第二次**。

**處置順序（依序執行，任何一步跳過都會走錯方向）**：

| 順序 | 動作 | 依據 |
|---|---|---|
| 1 | 先套用 `SKILL.md`〈超標了怎麼辦〉診斷表——超標成分若含論證敘事或版本紀錄，先外移至該 skill 的 `CHANGELOG.md`，處置見該表第一項，不在本檔重複 | `SKILL.md`〈超標了怎麼辦〉 |
| 2 | 外移敘事後仍超標，才判定讀取方式：整份執行量全檔，選段查閱量最大單節；模板／範本類檔案的讀取方式判斷標準見 `SKILL.md`〈Progressive Disclosure〉的「機械複製動作不算整份執行」段 | `SKILL.md`〈Progressive Disclosure〉 |
| 3 | 依讀取方式判定後仍超標，才依下節〈外移什麼、留什麼〉的讀者情境四問，指名可外移的目標檔——**新補入的範例段落隨其所服務的規則文字同進同出，不得單獨移走或刪除** | 本檔〈外移什麼、留什麼〉 |
| 4 | 拆分執行後依〈兩種驗證，方法不同〉與〈走完之後〉復驗 | 本檔〈兩種驗證，方法不同〉〈走完之後〉 |

**明確排除的處置**：刪減已補入的範例、把範例移到遠離其所服務規則的附錄、壓縮規則文字回到門檻內。三者皆讓門檻數字達標而讀者理解力不變或降低，與門檻本身要防的認知超載互相牴觸。

**一則範例**（去識別化，非本專案實際 skill 或檔名）：

【輸入】

```
規則文字：某判斷標準表原無具體範例，讀者依文字描述可能推出兩種不同結果。
補入範例後：該檔全檔量測達門檻的 1.4 倍；檔內原有兩個並列步驟區塊，
分別對應互斥的執行路徑 A、路徑 B，讀者在抵達此檔前已由前置步驟判定
自己屬於哪一條路徑。
```

【產出】

```
形態：決策表

條件                                          | 動作
----------------------------------------------|--------------------------------------------
超標成因是新補入的範例，非原有規則文字過長      | 依讀者任務判定拆分對象，不得刪範例或壓規則文字
路徑 A、路徑 B 兩區塊的外移對象                | 依〈外移什麼、留什麼〉四問逐段指名路由表的列判定，
                                                | 不因兩路徑互斥而逕行各自成檔
```

【驗證】

```
檢驗問句
  Q 拆分後各檔是否皆低於門檻？                              預期：是
  Q 拆分方案是否透過刪除範例或壓縮規則文字達成？            預期：否（依據：「明確排除的處置」）
  Q 「兩路徑互斥」能否作為兩區塊各自成檔的依據？            預期：否（依據：「互斥性因此不進入判定」）
```

## 外移什麼、留什麼

**分界是「讀者在選路之前還是之後用到它」，不是「一次只用其中一段」。** 後者對每一張判斷標準表、路由表、分類表都成立——本 skill 當時同住入口檔的那幾張表（皆為歷史狀態，非現況，不必去查它們在哪）全部互斥，這條判斷標準把整份入口檔都判成該外移，而「入口檔留判斷標準」又把同一批判成該留。互斥性因此不進入判定。

**先打開該 skill 的 `SKILL.md`，找到〈按需讀取〉那張表——本節四問全部拿它當對照物。** 這張表下文一律稱「路由表」，三欄：**何時讀**（讀者的處境，例如「寫或修 frontmatter」）／**檔案**（該讀哪一份）／**涵蓋章節**（該檔的 `##` 標題逐字列出）。四問要指的「某一列」，就是這張表的一列。

對每一段內容依序問下列四問。**四個判定各自都要求你指名路由表的具體某一列**——說得出是哪一列，才算落在那一格；指不出來就不是那一格，往下一問：

| 問 | 判定 |
|---|------|
| 1. 它回答的問題，是路由表某一列「何時讀」欄的判斷條件嗎？（讀者不用它就判不出自己屬不屬於那一列） | **留在入口檔**——外移後讀者無從得知該開哪一份 |
| 2. 路由表每一列的讀者都會用到它嗎？ | **留在入口檔**——外移只是把「一份載入」換成「每個人多跳一次」，總量不減 |
| 3. 指得出唯一或少數幾列，且那些讀者不必讀它就知道自己是那一列？該列須在本次拆分之前即已存在——為本次拆分新造的列不算 | **外移到那幾列的目標檔**，入口檔留該列路由 |
| 4. 三問都指不出任何一列？ | 它沒有讀者情境，是論證或實證敘事 → 壓縮成主張句，敘事移入 `CHANGELOG.md` 或 ticket |

**問 2 與問 3 之間有一格。** 問 2 要的是「每一列都用」，問 3 要的是「唯一或少數幾列」，中間漏掉一種情形：多數列都用、只有極少數不用。**先數出不用它的是哪幾列**，再照下表判：

| 不用它的列數 | 等同哪一問 | 處置 |
|------------|-----------|------|
| 0 或 1 列 | 問 2 的「每一列」 | 留在入口檔 |
| 達路由表列數的**一半以上** | 問 3 的「少數幾列」 | 外移 |
| 介於兩者之間（多數但非全部） | 都不等同——這就是那一格 | 留在入口檔，並在路由表為那幾列的讀者加註 |

**數列數這一步不可跳過。** 落在那一格時要說得出它是那一格，不是從問 2 或問 3 裡挑一個交卷。

**問 3 的「該列須在本次拆分之前即已存在」是為防止規避。** 若允許用拆分當下新造的路由列去滿足問 3，驗的人看到的只是一個指得出的列，看不出那一列是為了通過這一問而造的——問 3 的可外部驗證性因此失效。

**可外部驗證的地方是「指名列」這個動作**，與 `patterns-and-troubleshooting.md`〈Degrees of Freedom — 自由度匹配脆弱性〉要求指名機械消費者同一個手法：第三方拿同一份路由表重跑，會落在同一格。

**問 1 與問 3 的分界，在門檻與程序之間。** 判斷「我超標了嗎」用的門檻與量測指令是本檔這一列的觸發條件，讀者不先知道門檻就不會找到本檔——那是問 1，留在入口檔；「既然超標，該搬什麼」是已經決定要拆的人才問的，那是問 3，住在本檔。本節就是照這個判斷標準從入口檔搬過來的。

## 拆分特有的必查項

**本表只收檔內關係的缺陷。** 拆分同時會新生兩個檔外物件——各新檔的檔頭與入口檔的路由表，它們的要求在〈結構約定〉，兩處互指、不重複列。

| 類別 | 為什麼拆分才會壞 | 怎麼查 |
|------|----------------|--------|
| **節界** | `##` 是 markdown 的語意結構。把某節的粗體段附到另一節尾巴，位元完全正確而少了一層結構，指向它的「該節末段」隨即落空 | 搬移前後各數一次 `^## `，對照原檔的章節清單；把並列節併入同檔時逐一確認每節仍有自己的 `##`。**裸 `grep -c '^## '` 會把 fenced block 內的 markdown 範例一起算進去**，在 skill 設計類文件上實測高估到 2.7 倍（8 vs 3），且拆分前後被同等高估、前後比對仍會相符，節界遺失因此可能通過檢查。用 `awk '/^```/{f=!f;next} !f && /^## /{n++} END{print n+0}' <file>` |
| **H1 與檔名** | H1 是拆分當下新生的物件——原檔只有一個，拆成 N 檔就新生 N 個。多節併入同一新檔時 H1 常只承諾其中一節，其餘落在標題範圍外。每一行都正確搬到了新位置，逐行比對對它無感 | 逐檔對照 H1 與該檔全部 `^## `，確認每個 H2 都在 H1 承諾的範圍內；檔名同此 |
| **跨檔指涉** | 原本同檔的〈章節名〉互指，現在跨檔。「本節」「見上」「末段」這類位置詞跨檔即失效 | 窮盡列出全部 `〈〉` 與位置詞，逐處判定目標現住哪一檔、讀者站在當前檔看不看得到路。**跨檔指涉一律連檔名一起寫**——只寫〈某節〉的話，讀者要回捲到檔頭的「同目錄」列才推得出它住哪 |
| **共置關係** | 兩處互相矛盾的判斷標準原本相鄰、讀者順讀就撞見；拆分後分居兩檔，**衝突的可發現性下降**。這一類沒有任何指涉失效，位元也全對 | 拆分前先跑一次 `multi-round-review` skill 的 **1-E 斷言支撐 frame**，把互相矛盾的判斷標準找出來並修掉，再拆 |
| **外部引用** | 指名式引用（`` `X` skill 的〈某節〉 ``）拆分後仍有效；路徑級引用（`.claude/skills/X/SKILL.md`〈某節〉）會斷 | 全站掃引用並**逐條列出**——不要截斷輸出後下「無一處失效」這種全稱結論 <!-- broken-link-exempt: 條文示範路徑，非真實引用 --> |
| **兄弟檔互指矩陣不對稱**（矩陣＝把「哪一份的檔頭列了哪些兄弟檔」排成 N×N 表，對稱指每一份都列出其餘全部） | 各新檔的檔頭「同目錄」段是拆分當下新生的物件，逐檔手寫，漏一格不會有任何徵兆。漏掉的那一格使該檔的讀者不知道那個兄弟檔存在——實測：七份 references 中唯一漏列一個兄弟檔的那一份，其讀者 3/3 全體一致沒察覺還有第三條路徑，其中一份還給出確切但錯誤的總數 | 做成矩陣看有沒有缺格：`grep -m1 '^> 同目錄' references/*.md` 逐檔取檔名引用，N 份檔各應列出其餘 N−1 個。**不對稱即為缺陷，即使那個兄弟檔對本檔讀者「用不到」**——用不到是讀者判的，不是作者代判 |
| **層級混疊**（同一件事在兩個層級各編一次號：全程有一套步驟編號，子檔內部又自成一套） | 拆分後子檔內部自成步驟編號，而全程也有一套步驟編號，兩套指同一件事卻各編一次號，且沒有任何一處說明。讀者走完子檔的「步驟 8」以為結束，實際上他跨了三個層級。這一類位元全對、指涉全對、節界全對 | 把全程的步驟清單與各子檔的步驟清單並排，看有沒有同一件事出現兩個編號。有就重新切分，讓子檔的步驟收斂在全程的一步之內 |
| **用詞定義與用詞使用分屬兩檔** | 拆分把定義搬到查表檔、把使用留在操作檔，兩邊各自都正確。讀者在操作檔遇到那個詞時不會回頭查——實測：一個在入口檔四處使用、零處定義的受管詞，1/4 讀成了另一個東西，而那兩個東西是不同的落點 | 列出入口檔與各操作檔用到的全部受管詞，逐一確認定義與首次使用同檔；不同檔時把定義搬回使用處，或在首次使用處就地帶一句定義。**檔頭的總括式指路不算數**——實測同一個詞在檔頭「地址一律查該表」下 3/3 被判為「沒說去哪查」，改為首次用點就地具名帶指路後 0/3 |
| **相對連結的層級相依** | 同 skill 內部的相對連結（如 `references/principles/x.md`）以連結所在檔案的目錄為解析基準；內容搬到不同深度的新位置後，基準點跟著移動而路徑字串未變，連結因此解析到錯誤位置甚至不存在的路徑。判別方式：比對搬移前後該連結相對於目標的**路徑深度**是否改變——不變（如兩份原本同層的檔一起搬進同一層 `references/`）通常不受影響，改變（如原本同層，其中一份搬進 `references/` 之下再深一層；或反向搬出）就會斷。**本 skill 的 `references/` 是扁平結構、全站零相對連結命中，這一項在本 skill 自身無法示範——是結構湊巧，不是規則生效，消費端有巢狀 `references/` 目錄的 skill 不享有這個巧合** | 對每個 `](path)`，以該連結所在檔案**搬移後的新位置**所在目錄解析後 `os.path.exists` 驗存在性，逐條列出解析結果。**這一項問的是「指標本身會不會因為自己搬家而改變意義」，與前三套（路由表涵蓋章節欄、檔頭同目錄索引、正文跨檔指涉）問的「指標指向的東西在不在」不同維度**——前三套假設連結字串正確、只驗證目標是否存在或可達；這一項驗證連結字串本身的解析基準是否因搬移而位移 |

## 兩種驗證，方法不同

| 驗什麼 | 方法 | 誰能判 |
|--------|------|-------|
| 搬移正確性 | 行覆蓋（每一行不是留下就是搬出，合計等於原檔行數、無重複無遺漏）+ 各新檔正文與原區間逐行比對 | 機械可判 |
| 拆分可用性 | 派低階 model 讀者探針，逐檔量位置感（這份是整體的哪一部分、整體有哪些部分）、交棒（走完之後做什麼）、缺料自覺（有哪些詞沒定義要去別處查）、第一個具體動作 | **外部可量，作者不可判** |

只驗了搬移正確性就宣告拆分完成，是本程序要防的主要失誤。

**拆分可用性不是「無法檢查」，是「作者檢查不出來」。** 作者與同源 reviewer 對這份內容已有脈絡，讀到殘缺句會自動補完，坑因此不現形——一份過了三輪高階 reviewer 九個 frame 的拆分，探針一輪量出五類割裂缺陷，無一被那三輪攔下。派發方式與題目見 `multi-round-review` skill 的 2-B⁗ frame；**入口檔要單獨跑一批**，因為「正文能不能獨立支撐操作」只有在讀者拿不到 references 時才現形。

## 拆分特有的高頻缺陷

**內嵌於散文的計數在結構改動時不會跟上。** 「六檔」「五條」「三則」「共用兩節」——每次改動檔數、條數或節數，這些散落各處的數字都要跟，而它們不會自己跟。修法一律是**改成不自帶計數**（「後三列」→ 指向表本身、「三則」→「涵蓋三個模式的四個關鍵步驟」），不是把數字改對——改對的數字下次還會漂。

**位置性指涉的判斷標準卡在「目標有沒有名字」，不卡在形態，也不卡在對未來的預測。** 一次實測中同型缺陷出現四次（末段、下段、上節、下方），其中三次由修法自身引入；同批留下的四處位置指涉則全部正確且比具名寫法好讀，判斷標準因此不是「禁用位置指涉」。兩條失效條件，任一成立即改具名：

1. **跨檔** —— 目標與指涉不在同一檔。
2. **目標帶識別字** —— 目標段有 `##` / `###` 標題、粗體引導句或檔名，卻用位置詞去指它。有名字而不寫名字，是把可掃描的指標換成不可掃描的：具名指涉在目標改名或外移時會被死名／孤兒節檢查命中，位置詞不會——目標搬走後那句話依舊落在一段看似合理的內容旁，字串合法、檢查全綠。

合規只剩一種情形：同檔、緊接、且目標沒有識別字（一張無標題的表，「見下表」是唯一寫法）。判定兩步，都是打開檔案就看得到的現況：**先看目標段有沒有標題或粗體引導句，有就寫出那個字串；沒有才留位置詞，並確認同檔緊接。**

**這兩條不問目標日後會不會動。** 舊寫法是「目標可能移動即失效」，要撰寫者對未來下斷言，而四次同型缺陷的實證正說明那個斷言做不到——其中三次由修法自身引入，寫的當下都判過不會動。新條件把同一批缺陷判得出來而不需要預測：那四處指的都是帶標題的節或帶粗體引導句的段，「有名字卻用位置詞」在寫的當下就看得見，事後也由第三方重跑得出同一個答案。

## 結構約定

**檔頭三段式：何時讀 → 同目錄 → 溯源。** 操作資訊在前、維護資訊在後——讀者要的是「這份現在對我有沒有用」，溯源是給日後維護者的。「何時讀」不可只寫主路徑：橫向入口（他檔的步驟把讀者送過來）看到的第一行是「起點為 X 時讀本檔」，等於正面告訴他這份不是給他的。要另列「亦由此進入」——**粗體標記後接在「何時讀」句中，或獨立成段，兩種皆可**；要求的是它與主路徑在視覺上分得開，不是它佔一個獨立段落。

**橫向入口的查法**：`grep -rn '<本檔名>' <skill 目錄>`，扣掉**兩類平行索引**——入口檔路由表的那一列，以及各檔檔頭「同目錄」段的那些列。剩下的每一處才是橫向入口，逐條寫進「亦由此進入」。

**扣除規則必須跟著索引的增減走。** 這兩類是索引不是入口：它們列出鄰居，不把讀者送過來，而條文對橫向入口的定義是「他檔的**步驟**把讀者送過來」。實測一份檔的檔名在全 skill 命中 10 處，其中同目錄列佔 5 處——若只扣入口檔那一列，偽陽性率是 5/9。**同目錄段被補得越完整，這個誤判越嚴重**，而補同目錄與寫查法是兩次獨立且各自正確的改動。

**這一步不可憑印象**——線索全在別的檔案裡，從本檔內部看不到任何跡象；零命中與沒查過長得一樣，故掃描前先拿一個已知會命中的檔名驗管道。

**「亦由此進入」的宣稱要能被證偽。** 「不可憑印象」是禁令，但印象仍可能通過檢查——把「主題相近」誤看成「有指向」，寫的人自己覆核一次也未必抓到。補一條可執行的證偽規則：**宣稱 X 檔把讀者送來本檔，X 檔裡就要有本檔的檔名或節名；`grep -rn '<本檔檔名或節名>' <X 檔>` 零命中，就刪掉那條「亦由此進入」的宣稱。** 這條規則是禁令被違反時的判別動作——沒有它，違反禁令的宣稱和真的查過的宣稱長得一樣。

**路由表帶「涵蓋章節」欄。** 拆分後路由表以情境索引（何時讀 → 哪個檔），而文件內部與外部引用都以章節名互指。兩軸不接時，拿著章節名來的讀者在入口檔找不到落點——一次實測有 77 處外部引用寫「skill〈某節〉」，這些人開入口檔 grep 只命中一句「三種模式共用〈某節〉與〈某節〉」，確認存在但不給落點。

## 收尾

**修完掃該類，不掃該處，且逐條列出。** reviewer 給的是它抽樣到的位置，而清單的形式在暗示完整性。修完用該 finding 的特徵字串掃整批，命中歸零或剩下的逐處判定合規才算處理完。兩個補充：掃描前先拿一個已知會命中的控制字串驗管道（零命中有兩個來源，指令寫錯的那一個看起來跟乾淨一模一樣）；掃完**逐條列出而非只看計數**（計數會因 regex 邊界或 locale collation 而少報）。字串掃描仍抓不到異形殘留（「另一張表也該改」），故對 reviewer 明說是多實例的 finding，另外逐項對照實例數與已修數。

**整體通讀。** 所有 frame 跑過、所有 finding 修完，不等於這份內容現在是好的——修法本身改變了被審查的對象，兩次各自正確的修法可以合成一個對兩個 frame 都不可見的缺陷。一次實測在此步抓到三處：指標寫好後目標被移走、條數改了而括號內的機械形式沒補、共用檔由兩份增為四份而「共用兩節」沒改。判斷標準是「這份內容現在讀起來像一個人一次寫完的嗎」。

## 一則最小走查

拆前的片段（單檔，兩節相鄰）：

```markdown
## 十一欄位填寫問句
（表格 11 列）
容器元件另答排列不變式三項，問句見本節末段。

**多形態專案**：支援多個形態時，欄位分兩組⋯⋯
```

拆後（搬入同一份 reference）：

```markdown
# 十一欄位填寫問句

## 十一欄位填寫問句
（表格 11 列）
容器元件另答排列不變式三項，問句見本節末段。

**多形態專案**：支援多個形態時，欄位分兩組⋯⋯
```

逐項判定：

| 必查項 | 判定 | 為什麼 |
|--------|------|--------|
| 節界 | **不通過** | 「多形態專案」原是與前者並列的節，搬入同檔後只剩粗體、少一層 `##`。位元全對 |
| 跨檔指涉 | **不通過** | 「見本節末段」原指同節的排列不變式段；節界消失後「本節」涵蓋到多形態段，末段變成後者 |
| 共置關係 | 通過 | 兩節本就相鄰，搬移後仍相鄰 |
| 外部引用 | 通過 | 無外部指向這兩節 |
| H1 | **不通過** | 檔名與 H1 只提前者，第二節在標題範圍外 |

修法：還原 `## 多形態專案`、「見本節末段」改具名為「見〈容器排列不變式三項〉段」、H1 改複合。

**這則的價值在它有多小**：兩節、十行、一次搬移，上表的必查項就命中三項。行覆蓋與位元比對對這三項全部回報通過。

**外移對象有兩種形狀，H1 的處置相反。先看自己在哪一列，再往下讀範例。**

| 外移對象 | 新檔的 H1 | 原本那個 `##` | 子節 |
|---------|----------|--------------|------|
| **並列的多個 `##`** 併入同一新檔 | 取一個能涵蓋全部的**複合名** | 全部**保留**為 `##` | 不動 |
| **單一 `##` 連同它全部的 `###` 子節**整體外移 | 直接沿用那個 `##` 的**字串** | **刪掉**——留著會與 H1 重複 | 每個 `###` 各**升一層成 `##`** |

上一則範例是第一列的形狀，下一則是第二列。

拆前（單檔，某節帶兩個子節）：

```markdown
## 甲功能
### 甲功能設定
⋯
### 甲功能限制
⋯
```

若照上例的路搬（H1 沿用原節字串，`##` 原樣保留）：

```markdown
# 甲功能

## 甲功能
### 甲功能設定
⋯
### 甲功能限制
⋯
```

與 H1 逐字相同的 `## 甲功能` 留了下來，全檔只剩它這一個 `##`——選段查閱在結構上不存在（最大單節等於全檔）。位元、行覆蓋、〈H1 與檔名〉三項既有檢查全部回報通過，因為新檔確實只有一個 `##` 且落在 H1 範圍內；缺陷只在「該不該有這個 `##`」上，三項既有檢查都不問這件事。

正確處置：

```markdown
# 甲功能

## 甲功能設定
⋯

## 甲功能限制
⋯
```

**兩條路的判別**：外移對象在原檔裡是**並列的多個 `##`**，還是**單一 `##` 連同其全部 `###` 子節**。前者（本節開頭範例）H1 需複合命名以涵蓋全部並列節，各節保留自己的 `##`；後者（本段範例）該 `##` 直接升格作 H1，不重複保留，其下 `###` 各自升一層。

## 走完之後

拆分完成的判斷標準不是「搬完了」，是上節〈兩種驗證，方法不同〉兩項都過。兩項都過之後：

1. 回入口檔的〈發布前檢查清單〉走一次——拆分改動了結構、YAML 以外的每一組，**〈讀者可用性〉那一組尤其不可略過**，它驗的正是本檔〈兩種驗證〉的第二項
2. 探針找出的每一項先歸因再處置：在原文 grep 那個讀法對應的字串，找得到即為文章自己這樣寫的，不是讀者誤讀
3. 處置完**再跑一次探針**。修法本身會製造新缺陷，且新缺陷與舊缺陷長得不一樣——實測有一處連續兩輪被命中，兩次修法各失敗一次：第一次改了段落沒改結構，第二次改對結構但把陳述範圍寫得比事實大
4. 版本紀錄寫進該 skill 的 `CHANGELOG.md`，含舊檔到新檔的對應表
