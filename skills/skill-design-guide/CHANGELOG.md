# skill-design-guide 版本紀錄

新到舊。版號規則與兩個住址（本檔與 `SKILL.md` frontmatter 的 `metadata.version`）見專案的 skill 同步規範。

**本檔只記變更本身**：版號、改了什麼、落在哪一節。多輪審查的 finding 分類、逐 frame 敘事、
被推翻的判定與其推導過程屬設計過程紀錄，依 `writing-the-body.md`〈嚴禁清單〉該列的處置放在
**專案的 worklog 系統**，不放這裡。

**寫每一條之前先問**：這句話裡的**每個數字與每個完成式，是同一個時點的嗎**？壓縮舊條目時，
數字取自當時、項目清單取自現在，兩者會被併進同一句而不再可分；宣告「已回溯套用」時，
做了一部分與做完在文字上同形。實測本檔在同一批修法內犯過這兩種各一次——而那一批正是在修
前三次的同型缺陷。**這一問是壓縮專用的**：既有的「同一件事寫了幾種形式」對展開有鑑別力，
對壓縮沒有——壓縮的產物只有一種形式，它只是錯的。

**Version**: 1.7.3 — 修 Round 4 第四個 frame（修法自傷復跑）留下的三則。〈外部引用：指名身分，不用檔案路徑〉在全庫統一為全名（前次只改了正文兩處，CHANGELOG 兩處未動）；「亦由此進入」的擺放由要求獨立成段改為明訂兩種皆可（五份寫在「何時讀」句中、一份獨立成段，判準本就該卡在「與主路徑視覺上分得開」）；`splitting-an-existing-skill.md` 的「五份新檔」計數移除——該處與 CHANGELOG 舊條目的「八份」對同一次實測給出不同數字，而 v1.7.2 的壓縮已刪掉後者，改法依同檔〈拆分特有的高頻缺陷〉的既有條文取消計數而非改對數字。

**這一批的取樣單位是「事」不是「本批改動位置」**：前三則的復跑之所以還能找到殘留，是因為掃描範圍改為全庫的每一種形式，不限這批動過的檔。以改動位置取樣時，新形式的對照組必然在未改動處，該類永遠回報通過。

**Version**: 1.7.2 — 修 Round 4 三個 frame 的 finding。

**重組後遺症**（兩次各自正確的修法合成一個問題）：橫向入口查法的扣除規則補上「同目錄」段（該段被補成全互指之後成為最大宗的偽陽性來源，實測 5/9）；〈觸發測試〉的無程序標註由逐項改為整組（前三項的做法落在一個已被標為無管道的層，而原標註只掛在第四項）；〈Step 4：撰寫內容〉表格內編號改為 4a–4f 並修三處跨檔指涉（原有兩套 1–6 命名空間，「Step 5」同時指節與表列）；「有兩份漏列」等內嵌計數移除。

**形式分歧**（同一件事在六份之間有幾種形式）：六份「同目錄」段補齊為各列其餘五份（原有三種完整度，缺席者恆為同一份）；三處懸空 `---` 檔尾移除；「六步」計數四處全清；**「不涵蓋」的告示收斂為固定前綴 `**不涵蓋**：`**——該類是四批修法新增最多的一類內容而原有五種形式、無共同字串可掃，約定寫入〈內容品質規則〉。

**誤報**（拿判準審明顯良好的 skill）：三條判準補上缺的那句條件——TOC 加「且被選段查閱」（被整份執行的 reference 不適用，實測同一判準在兩支 skill 上判出 25 誤報 vs 8 真違規）；「時間敏感」限定為「效力有期限的內容，不是內容有時間戳」；〈外部引用：指名身分，不用檔案路徑〉的 Action 問句**提到例外清單之前**並改寫為「它要操作的東西 vs 讀者要去讀的東西」（該問句本就在條文內，被四類例外的枚舉蓋過；實測 24 個命中裡它一次判定 23 個）。

**未修**：`description < 250 字元` 的邊界問題不是加條件能解——16,000 ÷ 58 ≈ 276 顯示 250 的真身是均分配額而非單支截斷點，而「哪幾支值得多佔」的機制尚不存在，在它存在之前任何單支閘門都會把 43% 的庫判成違規。已入判準重設計票。
