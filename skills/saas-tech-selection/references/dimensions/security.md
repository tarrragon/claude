# Dimension：Security（身份、隔離、secret、資料保護、追溯）

本維度處理「誰能對哪些資料做什麼、怎麼證明」。安全在初始化階段的特殊性：它是事後補建成本最高的維度 — 權限模型重構要動每個 endpoint、audit 紀錄無法回溯補登、外洩發生後才建的控制只剩公關價值。所以本維度必展開、且底線密度最高。

訪談姿態：安全問題用具體情境問（「客服能看到客戶的付款資料嗎」）、用名詞問（「要不要 RBAC」）使用者答不出來。

---

## 訪談問題

| 問題                                              | 為什麼問                                                                      |
| ------------------------------------------------- | ----------------------------------------------------------------------------- |
| 使用者怎麼登入 — email 密碼、社群登入、企業 SSO？ | B2B 的 SSO 需求決定要不要 day one 就接 OIDC / SAML、事後接是賣單門檻          |
| 系統內有哪幾種角色？各自能看 / 改什麼？           | 圈出授權模型的最小集合；角色 ≤ 3 個時簡單 role check 即可、過度設計同樣有成本 |
| 內部人員（客服、工程師）怎麼存取客戶資料？        | 內部存取是最常被跳過的面 — 後台權限、production DB 直連、log 裡的個資         |
| 哪些資料是個資 / 敏感資料？服務哪些地區的使用者？ | PII 盤點驅動 log 遮罩與保留政策；地區決定合規框架（GDPR 類）的適用            |
| 使用者要求刪除資料時要做到什麼程度？              | 刪除義務牽動備份策略與第三方資料殘留、day one 想過跟沒想過差很多              |

**反向問**：「這批資料全部外洩、最壞情境是什麼 — 道歉信、賠償、還是公司結束？」— 答案決定本維度的投資等級；B2B 多租戶答案通常是最後者、底線等級隨之上調。

## 子領域與選型

### 身份認證（authentication）

**Day one 預設**：用框架成熟方案或託管身份服務（Auth0 / Cognito / Firebase Auth 類）、把密碼雜湊、session 管理、重設流程、MFA 外包。自建認證的合理場景很少 — 確認使用者要自建時、把「密碼外洩責任自負」攤開講。

**B2B 注意**：企業客戶遲早問 SSO 與 SCIM；選託管服務時確認這條路存在、避免換服務重做。

**單人自架工具**：服務只有所有者使用時、認證不走 web-auth（帳號 / session / SSO）、改用**裝置綁定 + 共享密鑰**兩層 — 裝置原生生物辨識（Face ID / BiometricPrompt）認「人」、app 與服務端共享密鑰認「連線」。密鑰用裝置安全儲存（Keychain / Keystore）、不硬寫進 app（反編譯可挖）;配對走 air-gap 通道（QR 掃描）避免經網路 / 剪貼簿傳輸。失效模型跟多人 session 不同：裝置失竊等於認證邊界整個失效、無中央會話可遠端 kill、唯一收斂是服務端輪替密鑰版本強迫重新配對。

### 授權（authorization）

**Day one 預設**：角色檢查（role check）+ 物件層級擁有權檢查。兩層缺一不可 — 角色檢查擋「客服不能進管理功能」、物件檢查擋「使用者 A 改 URL 看使用者 B 的訂單」。後者（BOLA）是 SaaS 最常見的實際外洩路徑、且測試最容易漏。

有 domain map 的場合、授權配置沿 domain 邊界落點：每個 domain 對自己的 command 做擁有權檢查、跨 domain 的存取只能走公開查詢介面（介面內建租戶 / 擁有權過濾）— 授權邏輯散落在 handler 各自為政、就是邊界沒立住的訊號。

### 租戶隔離

多租戶 SaaS 的隔離是安全與資料兩維度的交集：查詢層強制 scope（詳見 state-storage 維度）、加上 API 層的租戶上下文驗證（token 內的租戶聲明對 URL / payload 內的租戶 id）。兩層各自獨立失效、疊加後漏網率才可接受。

### Secret 管理

Day one：`.env` + `.gitignore` + `.env.example`、CI / 部署平台的 secret 注入、commit 前掃描工具。已知的輪換時機（離職、外洩疑慮）寫進 README。Secret manager 服務在 secret 數量或存取主體變多時引入。

### 資料保護

PII 欄位盤點（哪幾張表哪幾欄）、log serializer 遮罩這些欄位、傳輸全程 TLS。加密儲存（at-rest）託管平台多半內建、確認開啟即可。保留與刪除：每類資料寫一行保留期限、刪除請求的處理流程（含備份內資料的處理立場）寫進決策記錄。

### Audit 與追溯

Day one 最小集：部署紀錄、管理操作 log（誰改了誰的資料）、production DB 直連的紀錄與審批立場。完整 audit log 系統可延後、但「完全沒有紀錄」狀態每多活一天、就多一天無法回答「資料怎麼變這樣」。

### 管理通道（主機與叢集的管理存取）

自建或半託管（VM、Kubernetes 節點、自管資料庫主機）時才有這一項；全託管平台沒有主機可登入，跳過。管理通道是工程師登入主機與叢集的路徑，跟「內部人員怎麼存取客戶資料」是同一類存取控制需求在基礎設施層的形態，而它最常被沉默跳過：雲端專案預設的防火牆規則通常就放行全網連 22 與 3389。

把它拆成三層加一個救援入口來問，每一層各自有失效方式：

| 層                             | 決定什麼                            | Day one 預設                                                                                                                                                                                                                                                 |
| ------------------------------ | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 網路可達性                     | 哪些來源連得到管理 port             | 管理 port 只放行身分感知代理的位址段（GCP IAP 是 `35.235.240.0/20`），或改用不開入站 port 的代理程式（AWS SSM 這類）；外部 IP 只承擔管理用途時才移除：對外流量經負載平衡器、出站另配 Cloud NAT 之後再拿掉，VM 本身就是對外入口時保留外部 IP、只收掉管理 port |
| 通道授權                       | 誰能打開通往某台主機的通道          | 用身分（IAM 角色）決定、綁給維運群組、IAM Condition 限定 port 與期限；不用來源 IP 白名單分辨人                                                                                                                                                               |
| 主機登入驗證                   | 通道打開之後，誰能登入、能不能 sudo | 由中央決定的公鑰：雲端的 OS Login，或 SSH 憑證（OpenSSH CA）讓權限自動到期；不在每台主機散放 `authorized_keys`                                                                                                                                               |
| 救援入口（break-glass access） | 以上三層有一層壞掉時怎麼進去        | 序列主控台加主機本機的救援帳號，平時關閉；上線前實際登入一次並確認 `sudo` 可用，確認後把 `serial-port-enable` 設回 `FALSE`                                                                                                                                   |

追問與判讀要點（平台無關）：

- **舊規則的處理順序**：預設的全開規則涵蓋代理的位址段，舊規則還在時連得上證明不了新規則放行了代理的連線；先停用舊規則再驗新路徑。停用之前救援入口要已經登入過、依賴舊規則的連線要先觀察出來（觀察期涵蓋最長週期的排程），並準備好恢復舊規則的指令。
- **建立主機之前的檢查**：只能在建立時決定的設定（映像檔與 CPU 架構、某些平台上的 SSH 公鑰與初始化腳本、安全開機）選錯時，補救就是重建。訪談階段還沒有主機，產出是決策記錄裡的兩列：只能在建立時決定的設定清單，以及兩條登入路徑與各自依賴的元件；支援清單與文件在建立之前讀。建立之前要做這幾件事：
  - **找出只能在建立時決定的設定**：讀修改主機的 API 或 CLI 說明，或看 IaC 的 plan 有沒有把它標成 forces replacement。
  - **讀官方文件確認支援組合**：登入路徑上每一個業者服務（代理程式型的工作階段、遠端執行指令）都要讀支援的作業系統清單、Known Issues 與前置條件，例如服務以哪個使用者執行、要不要 sudo，對照這次的機型加作業系統。元件狀態顯示 running，不代表這個組合有支援；換一個比較容易建的機型去演練，也驗不出只在這個機型上不支援的情形。
  - **文件只寫到作業系統時，再查到版本這一層**：同一個作業系統的不同版本提供的元件仍然可能不同。版本這一層的結果只回答「這個版本有沒有提供那個元件」；機型加作業系統的限制仍以 Known Issues 為準，兩者都通過才算支援。
    - 業者有依版本查詢的工具時（例如列出某個作業系統版本上代理程式可用的 plugin），用映像的作業系統版本欄位的值查，工具接受的格式跟映像名稱裡的版本號不一定相同。第一次用這支工具時，另外用同一個作業系統名稱、明顯不存在的版本（例如 99）查一次當對照：工具對它報錯，之後就不必再做；工具不報錯而回傳一份清單，代表它查不到對應時回傳不分版本的全部項目。比對時看清單的項目，不計順序：查到的跟對照不同，才採用為這個版本有沒有提供；跟對照相同，分不出是這個版本提供全部、還是工具沒有它的資料。
    - 分不出、或業者沒有這種工具時，從逐版本列出的文件確認；文件也沒有時，只能建好之後在主機上看代理程式回報的元件清單。這時不把那個元件寫成支援，登入的規劃改成兩條路徑裡至少一條不依賴它（例如建立時放公鑰、走不經過代理程式的工作階段），建好之後再確認。要選版本時，在沒有被確定排除的版本裡選，選的理由寫進決策記錄。
    - 決策記錄的支援清單那一列寫出查詢的指令、對照的項目數、實際結果的項目數，以及判定：確定有、確定沒有、分不出。
    - 建好之後的判讀：代理程式的設定裡元件是啟用、而它回報的元件清單裡沒有這一項時，先確認代理程式已經回報完、版本是最新的；仍然沒有，就以主機回報的清單為準，判成這個映像版本不提供它（查詢工具分得出時可以拿來佐證）。處置先改走另一條登入路徑，換版本重建排在最後，容量難取得時重建還要再搶一次（見容量那一項）。
  - **準備兩條登入路徑，逐項列出各自依賴的元件**：要走完整條路徑再列。代理程式型的工作階段有的經過主機的 sshd（Oracle Cloud Bastion 的 managed SSH session，由代理程式把公鑰放進 `authorized_keys`），有的由代理程式自己開 shell（AWS Session Manager 的標準工作階段），走完才知道是哪一種。最沒有把握的元件（代理程式、支援範圍）只出現在其中一條上；兩條仍共用的元件（sshd、22 port 規則）寫出來，要擋住它們就用救援入口（序列主控台加救援帳號）。第二條路徑可以就是救援入口，不為了湊兩條而另外加裝代理程式；主機不存狀態、重建便宜時，重建本身就是第二條路徑。停用其他路徑之前兩條都實際登入過。
  - **第二條路徑用自己的公鑰時，它是暫時的**：主機沒有公開 IP 時，多放一把公鑰增加的暴露很小，它承擔的是從建立到主要路徑走通之間的退路。開了 OS Login 這類中央登入驗證的平台，中繼資料裡的公鑰會被忽略，這條路徑改用中央登入驗證綁定的那把。切換到上面表裡主機登入驗證的 day one 預設（OS Login 或 SSH 憑證這類由中央決定的公鑰）之後，這把公鑰移除，退路改由救援入口承擔。
  - **容量難取得時選補救代價低的設定**：機型容量難取得時（免費額度的熱門機型、GPU），建錯的代價還要加上再搶一次容量，所以設定選補救代價低的那一種，例如建立時多放一把之後可以移除的公鑰、作業系統與版本選登入服務完整支援的那一個；沒有一個版本確定支援時，照「文件只寫到作業系統時，再查到版本這一層」那一項，讓兩條路徑裡至少一條不依賴未確認的元件。跟機型無關的設定（防火牆、登入驗證的流程）可以先在容易重建的機型上驗；跟機型有關的支援範圍，仍照讀官方文件那一項對這次的機型確認。用腳本重送建立請求時，腳本寫死了建立參數，每次重新啟動之前、以及腳本還在跑時查到會改變建立參數的新資訊時（先停掉腳本），拿上面幾項再對一次。
- **由 template 建的主機**（instance group、Kubernetes node pool）：管理通道的設定寫進 template 或 node pool 設定，逐台修改在重建後消失。
- **Kubernetes 控制平面**：公開的 API server 端點等同網路可達性全開；用以 IAM 判斷的端點，或只列維運與 CI 來源的 IP 白名單。
- **Kubernetes 節點除錯**：能在節點上建除錯 Pod 的帳號等同節點的 root；一般工作負載的 namespace 設 Pod Security Admission 的 `baseline` 以上，節點除錯集中到只有維運能建 Pod 的 namespace。
- **稽核**：開通道與登入要留下作業系統之外的紀錄，開啟之後實際連一次、查到紀錄才算完成（稽核設定常分成好幾種類型，開錯類型時設定照樣被接受、紀錄一筆都沒有），見 [protection-proves-itself-by-firing](../principles/protection-proves-itself-by-firing.md)。
- **人員離職**：角色綁在群組上時把那個人移出群組，不移除群組的角色綁定；撤銷只擋住之後的新登入，已連著的工作階段要在主機上結束，以該使用者的行程清單為空作為完成的判斷。

**GCP 的設定指令（IAP、OS Login）、舊規則的停用與回退、GKE 的控制平面與 `kubectl debug` profile、稽核紀錄的類型與查詢**見 [gcp-management-access](../implementations/gcp-management-access.md)。

## 防護底線（non-negotiable）

1. 對外 endpoint 預設要求認證、公開路由白名單放行（預設拒絕、顯式開放）。
2. 物件層級授權檢查進框架層（middleware / base query）、不依賴每個 handler 各自記得。
3. 輸入驗證 + 欄位白名單綁定（mass assignment 防護）。
4. Secret 不進 repo、TLS 全程 + 自動續期。
5. PII 欄位盤點完成、log 遮罩就位。
6. 管理操作留下紀錄。
7. Operator 帳號（雲 console、DB、部署平台、網域註冊商）全開 MFA — 一組管理憑證外洩等於全盤失守、成本接近零。
8. 有主機或叢集要登入時：22 / 3389 只放行身分感知代理或 VPN 的位址段；Kubernetes API 用以 IAM 判斷的端點（GKE 的 DNS-based endpoint），或只列維運與 CI 來源的 authorized networks；通道授權依身分、救援入口上線前實際登入過一次。

## 延後與 tripwire

| 可延後項                                          | 建議重評條件                                         |
| ------------------------------------------------- | ---------------------------------------------------- |
| WAF / 進階入口防護                                | 公開面擴大、或出現自動化攻擊流量                     |
| 完整 audit log 系統                               | 合規要求、或第一個企業客戶的安全問卷                 |
| Secret manager 服務                               | secret 數量 > 10、或存取主體（服務 / 人）> 5         |
| 滲透測試                                          | 上線後首次、之後隨重大架構變更                       |
| 單人認證升級帳號系統                              | 從單人 / 自用變成多使用者、或要分享存取給他人        |
| SSH 憑證（OpenSSH CA）取代 OS Login               | 主機分散在多個雲或地端，雲端的登入服務管不到全部主機 |
| 組織層級護欄（Organization Policy、階層式防火牆） | 專案數超過一個、或新專案由其他人建立                 |

## 決策記錄要記什麼

認證方案（託管 / 框架 / 自建 + 理由）、角色與授權模型、租戶隔離的查詢層與 API 層機制、PII 盤點結果與遮罩位置、刪除請求處理立場、防護底線段各條的狀態、延後項與重評條件。
