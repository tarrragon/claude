# Dimension：State Storage（正式狀態與資料儲存）

本維度處理「不可遺失的正式狀態放哪裡、怎麼保護」。任何 SaaS 都有帳號、訂閱、業務資料這類 source of truth、所以本維度必展開。選型的第一個動作是把資料分成「正式狀態」與「衍生資料」兩堆 — 正式狀態遺失等於事故、衍生資料（快取、索引、報表）可以從正式狀態重建；兩堆的儲存策略、備份壓力、選型自由度完全不同。

## 訪談問題

| 問題                                                                                            | 為什麼問                                                                                                                                                                                                                                                                                                       |
| ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 核心資料長什麼形狀 — 關聯密集（訂單連客戶連商品）、文件式（表單 / 設定 blob）、還是 key-value？ | 資料形狀是 DB 類型的主要依據、比「哪個 DB 流行」可靠                                                                                                                                                                                                                                                           |
| 有沒有跨多筆資料要嘛全成功要嘛全失敗的操作（扣款 + 建訂單）？                                   | 有 → transaction 邊界是硬需求、relational DB 的核心優勢；邊界沿 domain 配置 — 同 domain 內的寫入同 transaction、跨 domain 的一致性走 event + outbox、不開跨 domain transaction                                                                                                                                 |
| 檔案類資料（上傳圖片、報表、附件）量級？                                                        | 檔案進 object storage、進 DB 是常見的早期錯誤（備份爆量、查詢變慢）                                                                                                                                                                                                                                            |
| 需要全文搜尋嗎？day one 還是之後？                                                              | DB 內建搜尋能撐很久、獨立搜尋引擎是「觸發才引入」的元件                                                                                                                                                                                                                                                        |
| 多租戶的話、租戶資料要隔離到什麼層級？                                                          | 決定 shared schema / schema-per-tenant / db-per-tenant、事後改是大型遷移                                                                                                                                                                                                                                       |
| 你需要跑哪些查詢？每個查詢需要回溯多遠？回溯時需要逐筆資料還是聚合摘要？                        | 保留策略從查詢反推：debug 用逐筆（天級）、趨勢分析用小時摘要（季級）、留存分析用天摘要（年級）→ 推導出分層保留 + 降採樣策略、而非一刀切的「保留 N 天」                                                                                                                                                         |
| 主鍵 / ID 怎麼產生 — 自增序號、UUID、Snowflake？哪些 ID 會對外暴露？                            | 跨機器唯一性、DB 寫入效能（有序 vs 隨機 B-tree insert）、隱私（外部可見 ID 不應洩漏量級/時間）三個維度的取捨。三者的取捨在任一份資料庫 schema 設計教材的主鍵選擇章節都有展開，本維度只要求把選擇與理由寫進決策記錄                                                                                             |
| 哪些資料永遠不刪（發出去之後還會被查的識別碼、帳務紀錄）？每年增加多少列？                      | 有保留期的表總量會停下來，不刪除的表隨年數一直變大，長期的成本集中在不刪除的表：逐條檢查打到它的查詢讀的量由回傳筆數還是表的列數決定（篩選欄位不在索引裡的列表會隨表變慢）、常用索引放不放得進記憶體、清理與 schema 變更的耗時。同一批建立而值相同的欄位，在表還沒資料時決定存在批次那一列，事後改要重寫整張表 |
| 報表的「一天」依哪個時區切？事件最晚會晚多久寫進來？                                            | 摘要以 UTC 的時段存、日在查詢時依時區組；粒度要細到每個要支援的時區都組得出一天（整小時時差用小時、+5:30 / +5:45 類時區要 15 分鐘）。晚到的上限決定摘要的重算範圍、答不出上限時要記下每批寫入碰到的時段並監控寫入延遲                                                                                          |

**反向問**：「哪一張表的資料弄丟了、公司會出事？」— 答案圈出備份與還原驗證的優先範圍；答不出來表示正式狀態 / 衍生資料的分類還沒做。

**保留策略反向問**：「半年後你查這批資料、需要看到的是每一筆原始事件、還是每天的統計數字就夠？」— 答案區分逐筆保留和聚合保留。需要逐筆原始的查詢（debug、compliance audit）驅動原始資料的保留期；只需聚合的查詢（趨勢、留存、RFM）驅動降採樣摘要的保留期。兩者的保留期和儲存成本差距大 — 100 萬筆原始事件佔 GB 級、聚合成每小時一筆後只佔 KB。

## 候選類型差異

| 類型                                 | 適合                                    | 代價                                                    |
| ------------------------------------ | --------------------------------------- | ------------------------------------------------------- |
| Relational（PostgreSQL / MySQL）     | 關聯密集、需要 transaction、schema 明確 | schema 變更要走 migration 紀律                          |
| Document（MongoDB 類）               | schema 高頻變動、文件自包含             | 跨文件一致性弱、關聯查詢成本高、事後補 transaction 困難 |
| Key-value（DynamoDB 類）             | 存取模式固定且已知、規模極大            | 查詢模式要先於 schema 設計、ad-hoc 查詢幾乎不可行       |
| Embedded（SQLite）                   | 單機工具、邊緣場景                      | 多寫入者與水平擴展受限                                  |
| Object storage（S3 類）              | 檔案、備份、報表產物                    | 沒有查詢能力、要配 metadata 索引                        |
| 檔案系統（JSONL / CSV / plain text） | append-only 事件流、log、設定檔         | 無 transaction、無索引、查詢用 grep/jq、單寫入者        |

**檔案系統作為儲存**：開發者工具和自架服務經常用檔案系統（JSONL 一天一檔、CSV、plain text config）作為正式儲存。適用條件：資料是 append-only（不需要 update/delete）、查詢用 grep/jq 足夠、零外部依賴。升級路徑：JSONL → SQLite（需要索引或 JOIN）→ PostgreSQL / 時間序列 DB（需要高併發寫入或聚合查詢）。Tripwire：grep 查詢超過 5 秒、需要跨檔案 JOIN、需要聚合查詢（count / sum / avg over time range）。檔案輪轉設計（日切檔 + gzip 壓縮 + 保留策略）是檔案系統儲存的必備機制、和 DB 的備份對應。

**SaaS day one 預設**：managed relational DB + object storage。理由：MVP 階段存取模式未知、relational 的 ad-hoc 查詢自由度是「需求還會變」的保險；managed 把備份、升級、failover 外包給平台、符合小團隊定錨。使用者點名 document / KV 時、回到資料形狀與查詢模式確認 — 確認成立就採納、選型沒有標準答案、只有跟需求對齊的答案。

**外包深度與 bundle 判讀**：資料庫常是整個 bundle 決策的錨點 —— 因為它是跨能力 bundle 的核心那一塊（見 `principles/capability-outsourcing-depth.md`）。先分清「managed」的深度差：純 managed 關聯式 DB（RDS / Cloud SQL / Neon 類、只外包 DB 維運、schema 與 query 仍是你的）跟跨能力 bundle（同時給 DB + 認證 + 物件儲存 + 即時推送的後端平台）不在同一層。資料庫一旦選了 bundle、就要回頭看 security（認證用不用它的）、cache、async-queue（即時推送）哪幾塊一起用它、把這幾塊收進同一筆 bundle 決策、而不是各維度各接一個獨立服務。逐塊判「用它值不值得換整包遷出代價」、bundle 的整包遷出代價記進 tripwire。

**多租戶資料模型**：預設 shared schema + 每表 `tenant_id` + 查詢層強制 scope（ORM default scope 或 row-level security）。schema-per-tenant 與 db-per-tenant 在「合規要求實體隔離」或「大客戶要獨立備份 / 還原」時才引入、代價是 migration 與維運成本乘上租戶數。

## 防護底線（non-negotiable）

1. **Migration 版本化**：schema 變更全部走 migration 檔、進 repo、禁手改 production。這是部署可重現與回滾的前提。
2. **自動備份 + 還原驗證**：託管平台開自動備份只是一半、上線前實際還原一次到隔離環境才算數。還原步驟寫進 README。
3. **租戶隔離在查詢層強制**：多租戶下、依賴「工程師記得加 where tenant_id」是事故時間表、不是控制。用 ORM scope 或 RLS 讓漏寫變成查不到而不是查到別人。
4. **連線池上限明確設定**：池上限 × 實例數 ≤ DB 連線上限。預設值往往在加第二台實例時打爆 DB、day one 設好是零成本。
5. **慢查詢紀錄開啟**：規模成長「資料庫變慢」撞牆訊號的偵測源、設定即完成。

## 種子資料與 schema 規格的驗證

**種子資料（seed）是 schema 第一次承載資料的地方**：寫得進去，代表規格的資料放得進這份 schema；寫不進去，問題在寫 API 之前就浮現。合格的 seeder 符合下面幾條：

1. **經過全部約束寫入**：不暫停約束、不用 `COPY` 之類繞過檢查的方式。另外逐條約束準備一筆違規的寫入與一筆剛好合規的寫入，寫成獨立的驗證腳本：在交易裡執行、比對擋下它的約束名稱、結束時回滾，有一條不符就以非 0 結束，CI 才能用。只確認合格資料寫得進去，驗不到約束有沒有擋住該擋的。腳本自己建立需要的前置資料，空的資料庫也能跑；腳本從 `pg_constraint` 列出 schema 的全部約束，有約束沒有對應的案例時以非 0 結束。寫完故意改壞一條預期，確認它以非 0 結束，結束碼寫進決策記錄。
2. **可重現**：亂數種子固定，資料量由參數控制（開發用的小量、量測用的大量），同一組參數產生相同的資料，驗證與量測才能重跑、才能比較。
3. **在要執行的環境裡跑得起來**：執行的映像檔若以不含開發套件的方式建置（例如 `composer install --no-dev`），seeder 不依賴只在開發套件裡的函式庫（例如 Faker）；或寫明 seeder 只在開發映像裡跑。
4. **指定主鍵寫入後校正序號**：PostgreSQL 的 identity 與 sequence 不會因為指定了 `id` 而前進，寫完要 `setval`，否則程式建立的第一列會撞號。
5. **只產生正式狀態，不產生衍生資料**：彙總、快取、搜尋索引由正式的流程從正式狀態算出；seeder 自己算一份，就驗不到那條流程，兩份算法不一致時也沒有人發現。
6. **關鍵的寫入用正式路徑的同一種語句**（只有一個實作時）：例如批次建立用的 `INSERT ... ON CONFLICT DO NOTHING RETURNING`，seeder 照樣寫一次，順便確認那句在所用的框架裡寫得出來、回傳的結果怎麼對回輸入。多個實作共用一個資料庫時改由「只有一份語言中立的產生器」那一條處理，這項驗證歸各實作的整合測試。
7. **涵蓋邊界形態**：已到期、已停用、已刪除個資、沒有所屬的上層（例如沒有團隊的帳號建立的資料）、非人為的流量。只有正常路徑的資料，驗不到約束與查詢的分支。
8. **量測用的資料照容量估算的比例**：兩類資料的比例（例如自動產生的大宗資料對人工建立的資料）決定查詢計畫，比例不對時量到的計畫和正式環境不同。
9. **多個實作共用一個資料庫時，只有一份語言中立的產生器**（例如一份 SQL，各框架的 seed 指令只負責執行它）：不同語言的亂數產生器即使給同一個種子，序列也不同，兩份產生器不可能產出相同的資料，拿兩個實作做效能比較時就不是在同一份資料上量的；SQL 以集合寫入，也比任何語言逐列寫入快得多，大量的量測資料才產生得出來。各實作的測試資料（factory、fixture）不在此列，它們驗證的就是各自的實作。

**設計文件裡的 schema SQL 是規格時，它本身要能執行**：表依外鍵的參照順序排列，從文件依序取出就能在空資料庫上建出全部的表，寫完在空資料庫上實際跑一次，執行的指令與結束碼寫進決策記錄。順序錯誤讀稿看不出來：每一段 SQL 單獨讀都正確。

**同一份 schema 有多套實作**（例如兩個框架各寫一套 migration）時，比對基準是規格建出的 schema，每一套各自和它比；只拿兩套互比，兩套照同一個誤解寫錯時結果仍然一致。用 `pg_dump --schema-only` 比對時，框架自己的表要連同它的 sequence 一起排除（`-T migrations` 不會排除 `migrations_id_seq`）。框架的 migration builder 照預設寫，常和規格不同的地方：時間欄位的精度、主鍵用 serial 還是 identity、外鍵的命名、預設值表示式的寫法、唯一約束與唯一索引；這些由 dump 的差異找出，讀 migration 的程式碼看不出來。差異逐項處理：改 migration 讓它和規格一致，或把規格改成實作的寫法並記進決策記錄；比對結束時 dump 的差異是空的，這份清單是要找的位置，不是可以放行的差異。

## 延後與 tripwire

| 可延後項                                                 | 建議重評條件                                                                                                                                                                                                                                                                  |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Read replica                                             | 讀寫比明顯失衡（10:1 為起始門檻、依定錨調整）且讀延遲惡化                                                                                                                                                                                                                     |
| 獨立搜尋引擎                                             | DB 全文搜尋的查詢延遲或功能（斷詞、權重）撐不住                                                                                                                                                                                                                               |
| 分片 / 分區                                              | 有保留期的表：刪除過期資料變慢。不刪除的表：常用索引放不進記憶體、autovacuum 或建索引與還原的耗時超過可接受範圍；列數本身不是訊號。依時間分區前確認唯一約束：它必須包含分區鍵，靠某一欄防止重複的表改依那一欄的 hash 分區，或另建一張不分區的登記表（那一欄當主鍵）擔任仲裁者 |
| db-per-tenant                                            | 合約要求實體隔離、或單一大客戶資料量壓過其他全部                                                                                                                                                                                                                              |
| 熱點計數列拆開（拆成多列 / 只新增事件 / 先在記憶體合併） | 同一列計數的寫入在尖峰排隊、寫入延遲逼近目標；加連線只讓延遲更高                                                                                                                                                                                                              |
| 摘要改成寫入時累加                                       | 定期重算一輪的耗時逼近排程間隔                                                                                                                                                                                                                                                |

## 決策記錄要記什麼

選型（類型 → 具體服務 + managed 與否）、正式狀態 / 衍生資料的分類結果、**ID/主鍵策略（類型 + 對外暴露的 ID 是否隱私安全）**、多租戶隔離層級與強制機制、備份還原驗證的完成狀態、防護底線段各條的狀態、種子資料的參數與涵蓋的邊界形態、schema 規格的比對方式（基準是什麼、排除哪些表）、tripwire 條目。
