# Dimension：Verification Surface（實機驗證環境）

> 本檔屬 `saas-tech-selection` skill（初始化專案時的技術選型訪談協議）的技術維度之一：訪談者依上層 `../../SKILL.md` 的流程對專案發起人逐維度提問，本檔提供本維度的問題、判斷標準與防護底線。「反向問」＝訪談者對受訪者的挑戰句，用來暴露沒想到的失敗面。

本維度處理「完成的改動在哪個真實環境被驅動與觀察」。任何有可執行產出的專案都必展開。核心主張：測試套件綠燈驗證的是斷言、不是行為——改動最終要在一個具體環境（某台裝置、某個瀏覽器、某個 runtime）被跑起來觀察，而那個環境的選擇在選型階段就已被交付形態決定；不在訪談時問清，就會變成第一次實機驗證時的冷啟動摸索成本，且每個新 session 重付一次。

訪談答案的下游產物是**專案 verify 配方**（`.claude/skills/verify/SKILL.md`）：build / launch / observe 的可複用步驟。配方屬專案特化資產（綁定裝置、URL、版本），不隨框架 sync 推送。<!-- portability-allow: 約定位置，描述各專案自有的驗證配方應放何處，文中已載明不隨 sync 推送 -->

## 訪談問題

依交付形態進入對應節；跨形態產品（app + 後台網站）各節都過。

### Mobile App

| 問題 | 為什麼問 |
| ---- | -------- |
| 日常驗證用模擬器還是實機？ | 模擬器摩擦最低但缺硬體面（相機、GPS、生物辨識、推播）；涉硬體功能的驗證面必含實機 |
| 主力目標裝置與 OS 版本是哪台？ | 驗證環境要釘住一個明確配置（裝置名 + OS 版本），「隨便一台」= 每次驗證環境不同、觀察不可比 |
| 最低支援 OS 版本上要不要驗？ | 新 OS 模擬器通過不代表最低支援版本通過；決定裝置矩陣是一台還是兩台 |
| 驅動方式有沒有工具前提？ | 截圖以外的互動（tap、輸入）需要驅動工具（如 macOS 輔助使用授權、cliclick、平台自動化框架）；首跑前裝好、不要在驗證當下發現缺 |

**反向問**：「app 用到相機 / 推播 / 生物辨識嗎？——這些在模擬器上是假的或不存在的，涉及它們的改動在模擬器上 PASS 沒有意義。」

### Web

| 問題 | 為什麼問 |
| ---- | -------- |
| 主力驗證瀏覽器是哪個？要不要跨瀏覽器矩陣？ | 單瀏覽器是預設；用到邊緣 API（WebRTC、clipboard、PWA）時矩陣升級為必要 |
| 本機驗證的 URL 與 port 是什麼？怎麼啟動？ | dev server 指令與網址是配方的第一行；port 衝突與 proxy 前綴要先定 |
| 有沒有 staging？驗證停在本機還是要上 staging 看？ | 涉及第三方 callback（金流、OAuth）的流程本機驗不到，需要 staging 或 tunnel |
| 行動版佈局要不要驗？用 DevTools 模擬還是真機瀏覽器？ | responsive 改動的驗證面與桌面版不同；DevTools 模擬覆蓋佈局、真機才覆蓋觸控行為 |

**反向問**：「使用者實際會用什麼開你的網站？——團隊全用 Chrome 開發、使用者一半在手機 Safari，驗證面跟使用面錯開就是盲區。」

### Service / CLI / Library

| 問題 | 為什麼問 |
| ---- | -------- |
| 用什麼 runtime / 編譯器版本？跟 production 一致嗎？ | 本機新版跑過、production 舊版炸掉是經典事故；驗證環境的版本釘住 production 版本 |
| 目標平台是什麼？（OS / 架構） | 跨平台產出（arm64 / x86_64、Linux / macOS）時，驗證平台要涵蓋主要部署目標 |
| 要不要在容器裡驗？ | 部署形態是 container 時，裸機驗證通過不涵蓋 volume mount、網路 namespace、環境變數注入的差異；驗證環境貼近部署環境 |
| 入口層要不要一起驗？（nginx / reverse proxy） | 反向代理改寫 header、限制 body 大小、終止 TLS——繞過它直打服務 port 的驗證漏掉整層行為 |
| 服務怎麼啟動、就緒訊號是什麼、怎麼觀察輸出？ | 啟動指令 + ready 判斷標準 + 觀察手段（log 位置、health endpoint）是配方的骨架 |

**反向問**：「驗證時直接打服務 port、production 流量卻經過 nginx——上次改的 request size limit 你驗的是哪一層的？」

## 候選類型差異

| 驗證環境 | 適合 | 代價 |
| -------- | ---- | ---- |
| 模擬器 / 本機 dev server | 日常迭代、UI 與邏輯改動、摩擦最低 | 硬體面與網路面是假的；環境與 production 差異最大 |
| 實機 / 真機瀏覽器 | 硬體功能、觸控行為、效能觀感 | 需要裝置在手、連線設定；迭代速度慢 |
| 容器化本機環境 | 部署形態是 container 的服務；環境一致性 | 首次建置成本；I/O 與網路行為與裸機有差（見 deployment-platform 的容器取捨） |
| Staging | 第三方 callback、完整入口層、多服務整合 | 建置與維護成本最高；部署一輪才能驗 |

**day one 預設**：單一釘住的低摩擦環境（一台指定模擬器 / 一個指定瀏覽器 + 本機 URL / 釘住版本的本機 runtime），配方寫死這個環境；矩陣與 staging 寫成 tripwire（＝預先寫定的重評觸發條件，見下方「延後與 tripwire」表）、命中才擴。

## 防護底線（non-negotiable）

1. **驗證環境必須被釘住並文件化**：裝置/瀏覽器/版本/URL/啟動指令寫進專案 verify 配方（`.claude/skills/verify/SKILL.md`），不存在於任何人的記憶裡。配方跟著專案 repo 走、不隨框架 sync 推送（專案特化資產）。<!-- portability-allow: 約定位置，描述各專案自有的驗證配方應放何處，文中已載明不隨 sync 推送 -->
2. **無可驅動驗證面即為選型缺陷**：訪談結束時若某類產出說不出「在哪裡跑起來、怎麼觀察」，缺的不是文件是環境——回到對應維度補（例：說不出服務怎麼觀察 → observability 維度沒過完）。
3. **驗證面涵蓋改動會走的層**：production 流量經過的層（reverse proxy、container 邊界）就是驗證要經過的層；繞層驗證通過不得宣告該層行為已驗。
4. **硬體相依功能的驗證面含實機**：模擬器對硬體功能的 PASS 不算數，配方明記哪些流程必須實機。

## 延後與 tripwire

| 可延後項 | 建議重評條件 |
| -------- | ------------ |
| 跨瀏覽器 / 多裝置矩陣 | 用到邊緣 API、或使用者回報單一瀏覽器特有問題 |
| Staging 環境 | 接入第三方 callback（金流 / OAuth）、或多服務整合驗證需求出現 |
| 容器化驗證環境 | 部署形態確定為 container、或本機通過 production 炸掉的環境差異事故發生 |
| 自動化驅動工具（UI 自動化框架） | 手動驅動的重複成本超過工具建置成本（同一流程每週驗 3 次以上） |

## 決策記錄要記什麼

本維度的答案在決策收斂（Stage 5）收斂為決策記錄的「驗證環境」節，並直接生成專案 verify 配方種子：

```markdown
## 驗證環境（decision record 節）
- 交付形態：<mobile / web / service>
- 釘住環境：<裝置+OS / 瀏覽器+URL / runtime 版本+平台>
- 啟動：<指令>
- 觀察：<截圖 / URL / log 位置 / health endpoint>
- 實機必驗清單：<硬體相依流程，無則標「無」>
- tripwire：<矩陣 / staging / 容器化的重評條件>
```

種子落地為 `.claude/skills/verify/SKILL.md` 的初版 Build & Launch / Observe 節——首次實機驗證從冷啟動摸索變成執行預答配方，摸索成本只在訪談付一次。<!-- portability-allow: 約定位置，描述各專案自有的驗證配方應放何處，文中已載明不隨 sync 推送 -->
