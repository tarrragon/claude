# Protection Proves Itself by Firing（防護機制以實際觸發驗收）

> **角色**：本卡是 `saas-tech-selection` 的支撐型原則（principle）、被 security 維度的管理通道與稽核、capacity-performance 維度的支出停損、兩份 GCP 實作檔（`implementations/gcp-spend-kill-switch.md`、`implementations/gcp-management-access.md`）的驗收、防護底線總表的「防護機制實際觸發過一次」那一列，以及 SKILL.md 路由表的支出停損列共同引用。
>
> **何時讀**：部署停損開關、稽核紀錄、告警或自動處置這類平常不動作的防護機制之後，要判斷它算不算部署完成；或驗收紀錄寫著「部署成功」「狀態 ACTIVE」「設定已套用」、驗證查詢回傳零筆就被當成結論時。

平常不動作的防護機制，部署完成的完整證據只有一種：**讓它要防的那件事實際發生一次，在終點看到它要產生的效果**。停損開關的終點是專案的帳單狀態變成停用，稽核紀錄的終點是一筆記著帳號與目標的紀錄，告警的終點是通知送到值班的人手上。部署指令的回傳值、元件的狀態欄、函式是否被呼叫，都在這條路徑的中途。

這類機制特別需要這一條，因為它們的失效沒有訊號：平常本來就不動作，「壞掉」與「還沒輪到它動作」在任何儀表上都長得一樣，第一次露出破綻的就是它該發揮作用而沒有發揮的那一次。

## 機制還沒生效就顯示成功的位置

| 位置                   | 長什麼樣子                                                                                   | 實測過的例子                                                                                                                                      |
| ---------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 設定被接受             | 設定指令成功、值寫進去了，而那個值描述的不是需要的設定                                       | 為 IAP 開稽核紀錄只開了 `DATA_READ`，開通道的紀錄歸在 `ADMIN_READ`，連線十次左右紀錄零筆                                                          |
| 元件顯示正常           | 部署成功、狀態 `ACTIVE`，而通往它的路徑或它需要的權限斷了一段                                | 停損函式狀態 `ACTIVE`，觸發器的服務帳號缺 `roles/run.invoker`，每次推送 403，從未執行                                                             |
| 執行有發生而失敗被吞掉 | 元件確實執行了，失敗在中途發生，錯誤沒有回到呼叫的一方                                       | 函式因權限不足拋出例外，請求紀錄卻是 HTTP 200；觸發器預設不重試，Pub/Sub 把那則超支通知標為已確認收訊之後就丟了，到下一則預算通知之前帳單照常計費 |
| 測試從中途注入         | 合成的條件從路徑中途的入口送進去、終點也出現了，而入口之前把真實事件轉成條件的那一段沒被行使 | 測試訊息直接發到 topic、帳單停用；而預算的預設抵免設定扣掉抵免，帳戶有大額抵免時真實通知的花費接近 0，抵免用完前不會觸發（推導，非實測）          |

驗證查詢本身也會給錯的答案，方向是假陰性：防火牆規則剛開 logging 的最初幾分鐘，紀錄的規則名稱欄位是空的，用規則名稱過濾查到零筆；帳單被停用時，資源清單回傳零筆，重新連結後資源都還在。執行處置的指令有同一種形態：`loginctl terminate-user` 回報使用者沒有登入，而他的行程仍在執行；完成以行程清單（`pgrep -u <user>`）為準。

## 驗收做法：合成觸發

合成觸發（synthetic trigger）是在不造成實際損害的範圍內，造出機制要偵測的條件，看終點有沒有發生。

- **先寫下終點**：部署前寫出「生效時看得到什麼」，而且終點要是這個機制要達成的那個狀態（停損是帳單停用，不是函式被呼叫）。寫不出終點，代表還不知道這個機制要做什麼。
- **造出條件，寫下注入點**：停損開關用一則花費超過預算的測試訊息、稽核紀錄用一次真實的連線、告警用一次故障注入。測試訊息發到真實的觸發來源（例如 Pub/Sub topic），不直接呼叫函式，入口之後的每一段連線與權限才會被行使到；入口之前的那一段（預算範圍、抵免設定、發布權限）另外用一筆真實的輸入確認，例如讀第一則真實的預算通知、對照帳單報表的金額。
- **兩條分支都走**：「不該動作」與「該動作」各觸發一次，兩者用到的權限通常不同（停損開關的低於預算訊息只走到判斷規則就結束，讀取帳單狀態與解除帳單連結兩個權限都要等超出預算的訊息才會用到）。
- **修完從頭再觸發**：失效點是串聯的，修好一個之後下一個才會露出來，所以每修一段就回到「造出條件」重新觸發，直到終點出現。
- **查詢配正對照（positive control）**：查詢回傳零筆時，先用一條不依賴同一個欄位的查詢查一件確定存在的事（改用來源 IP 段查同一批連線、重新連結帳單後再列一次資源）；正對照也查不到，問題在查詢。
- **讓失敗看得見**：觸發失敗時要重試（Cloud Run functions 部署加 `--retry`）、錯誤回到呼叫的一方，終點之外再加一個心跳監看（dead man's switch）：監看它多久沒有收到觸發來源的訊息。觸發來源只在事件發生時才有輸入（WAF、告警規則）時，改成排程送一筆合成輸入、監看結果有沒有在期限內出現。心跳監看本身也照本節驗收一次。

合成觸發排在部署當下與每次修改之後做。停損開關的合成觸發會實際停用帳單，可能連資料一起刪除，所以只在停機可以接受的時段做；專案有停用之後不能遺失的資料時改用分段驗證（見〈邊界〉）；這個成本正是它不會被順手做掉的原因，所以寫進部署程序，不留給記憶。

## 邊界

- 合成觸發驗的是「這一次會動作」，不保證之後的每一次；平台改版、權限被別人調整都會讓它再次失效，所以重大變更後要重驗，並配上心跳監看。
- 停損開關切斷帳單之後，它自己若跑在同一個專案，此後的通知都處理不了，被入侵而有編輯權限的身分也刪得掉它；這是設計選擇，驗收時要確認這個後果可接受，不可接受就把它放在另一個專案。
- 合成觸發本身會造成不可回復的損害時（處置會刪資料、正式環境隔離不出副本），改成分段驗證：可拋棄的同構環境完整觸發一次；正式環境只驗權限（權限檢查工具）與不會動作的那一條分支；驗收紀錄寫明缺了正式環境那一次真正的處置。
